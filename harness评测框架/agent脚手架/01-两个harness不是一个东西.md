# 01 · 两个 harness 不是一个东西

> 这一章只做一件事：**把边界划清楚。**
> 讲清楚脚手架从哪开始、到哪结束，后面七章才有地方可讲。

---

## 1.1 先把三个英文词摆清楚

★ 你在中文资料里会看到"harness""脚手架""agent 框架"混用。它们其实指两类东西：

```
   ★ 名词：harness
     字面意思是【挽具、马具】——套在牲口身上让它按你要的方式使劲的那套皮带。
     ⟹ 引申到工程上：★★【套在某个东西外面、规定它怎么被使用的那层程序】。

     ★★★ 问题就出在这儿：套在【模型】外面是一层意思，
          套在【题目】外面又是另一层意思。于是同一个词有了两种用法。
```

```
   ┌─ 用法 A：evaluation harness（评测框架）───────────────────┐
   │                                                          │
   │  套在【题目】外面。                                       │
   │  职责：把 benchmark（评测集）里的题按统一格式喂给模型，   │
   │        收回答案，判对错，算分。                           │
   │                                                          │
   │  ★ 代表：lm-evaluation-harness、OpenCompass、EvalScope、 │
   │          SWE-bench 自带的 run_evaluation.py              │
   │  ⟹ 隔壁目录 [评测入门/] 讲的全是这个                     │
   └──────────────────────────────────────────────────────────┘

   ┌─ 用法 B：agent harness / scaffold（智能体脚手架）─────────┐
   │                                                          │
   │  套在【模型】外面。                                       │
   │  职责：给模型工具、跑它要的命令、把结果喂回去、           │
   │        管住上下文别爆、决定什么时候停。                   │
   │                                                          │
   │  ★ 代表：SWE-agent、Claude Code、Codex CLI、OpenHands   │
   │  ⟹ 🔑 本目录讲的全是这个                                 │
   └──────────────────────────────────────────────────────────┘
```

```
   ★ 名词：scaffold（脚手架）
     ⟹ 和 agent harness 是同义词，业界两个词换着用。
     ★★ 盖楼时钢筋水泥是主体，脚手架是让工人上得去的架子——
        楼盖完脚手架就拆了，但没有它楼盖不起来。

   ★ 名词：agent（智能体）
     ⟹ 指【模型 + 脚手架】合起来的那个能自己动手干活的东西。
     ★★★ 注意：agent 不等于模型。这是全目录最容易搞混的一点。
```

## 1.2 两者的接口窄到只有一个文件

★★★ 这是本目录能独立成册的技术原因。

```
   ┌─────────────┐        ┌──────────────┐        ┌──────────────┐
   │ 题目         │  ───▶  │ agent 脚手架  │  ───▶  │ 评测框架      │
   │ (issue 文本 │        │ 模型在里面    │        │ 跑测试、判分  │
   │  + 仓库)     │        │ 反复折腾      │        │              │
   └─────────────┘        └──────────────┘        └──────────────┘
                                  │
                                  ▼
                        ★★★ 交出去的只有一样东西：
                            一个 patch（补丁）文本
```

✅ 这不是我编的，是 SWE-bench 判卷器的源码事实。
[评测入门 08 章 §8.1](../评测入门/08-ClaudeCode与Codex怎么被评.md) 逐行引了它的注释：

```python
# pred (dict): Prediction w/ model_name_or_path, model_patch, instance_id
```

```
   ⟹ 🔑🔑 判卷器只认三个字段：
      instance_id        = 哪道题
      model_patch        = ★★ 你交上来的补丁文本
      model_name_or_path = ★ 一个你自己随便填的字符串（只当日志目录名用）

   ⟹ ★★★ 也就是说：
      【补丁怎么做出来的，评测框架一个字都不问。】
```

```
   ★★ 名词：patch（补丁），也叫 diff
     ⟹ 一段纯文本，写明"哪个文件的第几行，从什么改成什么"。
        git 生成它的命令就是 git diff。
     ★★★ 它是脚手架和评测框架之间【唯一的通信内容】。
```

## 1.3 所以"脚手架"到底负责哪一段

⚠️ 下面这张职责表是我对公开实现（SWE-agent 源码 + Claude Code / Codex 官方文档）的归纳，不是某一篇论文的原话。但每一项在后面章节都有 ✅ 出处。

```
   ┌─ ① 循环（loop）──────────────────────────── 详见 02 章 ─┐
   │  模型输出一个动作 → 脚手架真去执行 → 把执行结果拼成      │
   │  下一轮的输入 → 再问模型。★★ 这个圈转多少次、什么时候   │
   │  停，全由脚手架决定。                                    │
   └──────────────────────────────────────────────────────────┘
   ┌─ ② 工具集 / ACI ──────────────────────────── 详见 03 章 ─┐
   │  给模型哪几个动作可用（读文件？跑 shell？搜索？），      │
   │  以及【每个动作的输出长什么样】。                        │
   │  ★★★ 03 章会证明：这一项单独就值 7 个点。               │
   └──────────────────────────────────────────────────────────┘
   ┌─ ③ 上下文管理 ────────────────────────────── 详见 04 章 ─┐
   │  仓库几十万行，装不进模型的窗口。                        │
   │  ★★ 什么时候塞什么、旧的怎么压缩掉。                    │
   └──────────────────────────────────────────────────────────┘
   ┌─ ④ 权限与沙箱 ────────────────────────────── 详见 05 章 ─┐
   │  允许它改哪些文件、能不能联网、要不要问一句再动手。      │
   │  ⚠️ 这一项在评测场景里通常全开，但在你公司里是头等大事。│
   └──────────────────────────────────────────────────────────┘
   ┌─ ⑤ 采样与预算 ────────────────────────────── 详见 08 章 ─┐
   │  ★★★ 只跑一遍？还是跑 5 遍挑最好的？花到多少钱掐断？    │
   │  ⟹ 这是榜单上最常被隐藏的变量。                         │
   └──────────────────────────────────────────────────────────┘
```

## 1.4 一个反例：最简陋的"脚手架"长什么样

★★ 有对比才知道脚手架值多少钱。SWE-bench 自带一个最原始的版本
（[评测入门 08 章](../评测入门/08-ClaudeCode与Codex怎么被评.md) 引过它的源码）：

```
   ★ swebench/inference/run_api.py 的做法：

      拼一个大 prompt（把检索到的文件塞进去）
        → 调一次 API
        → 用正则从回复里抠出补丁
        → 完。

   ⟹ ★★ 一轮。没有工具。没有反馈。不跑测试。不知道自己改对没有。
```

✅ 这套做法在 SWE-bench Lite 上的成绩，SWE-agent 论文 Table 1 给了确切数字：

| 设置 | 模型 | SWE-bench Lite % Resolved |
|---|---|---|
| RAG（一轮盲写） | GPT-4 Turbo | **2.67** |
| Shell-only agent（能跑 shell，但界面是原生 Linux） | GPT-4 Turbo | **11.00** |
| SWE-agent（专门设计的界面） | GPT-4 Turbo | **18.00** |

```
   ⟹ 🔑🔑🔑 ★★★ 同一个模型，一个字没换。
      2.67 → 11.00 → 18.00。
      ★★ 差出来的 15 个点，全是【脚手架】贡献的。

   ⚠️ 我的判断：这个差距，大过当时两代模型之间的差距。
```

```
   ★ 名词：RAG（Retrieval-Augmented Generation，检索增强生成）
     ⟹ 先用关键词从代码库里搜出几个可能相关的文件，
        连同问题一起塞进 prompt，让模型一次性写出答案。
     ★★ 它不是 agent——因为它【只有一轮，不会根据执行结果调整】。
```

## 1.5 本章总结

```
    🔑 四条带走：

    ① ★★ "harness"有两个意思：套在题目外面的【评测框架】，
       和套在模型外面的【agent 脚手架】。本目录讲后者。

    ② ★★★ 两者的接口只有一个 patch 文本。
       ⟹ 评测框架完全不问补丁是怎么来的。

    ③ ★★ 脚手架 = 循环 + 工具集 + 上下文管理 + 权限沙箱 + 采样预算。
       ⟹ 五项，对应本目录 02–05、08 章。

    ④ ★★★ ✅ 2.67 / 11.00 / 18.00 —— 同一个 GPT-4 Turbo，
       换脚手架换出来的。这是全目录反复要用的锚点数字。
```
