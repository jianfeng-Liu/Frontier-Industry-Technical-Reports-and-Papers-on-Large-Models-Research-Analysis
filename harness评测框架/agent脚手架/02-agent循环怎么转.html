02 · agent 循环怎么转

⭐ 最基础的一章。看懂这个圈，后面六章都是在给这个圈的某一格加细节。
结论提前说：★★★ 模型本身不会"动手"，它只会输出文字。
【把文字变成真的动作、再把动作结果变回文字】——这一整圈就是脚手架。

2.1 先破一个误解：模型不能执行任何东西

   ★★★ 一个大语言模型（LLM, Large Language Model）能做的事只有一件：

      给它一段文字 → 它吐出一段文字。

   ⟹ 就这样。它不能读你的文件，不能跑你的命令，
      不能知道现在几点，不能知道刚才那条命令报没报错。

   ⟹ 🔑🔑 所以"AI 帮我改代码"这件事，实际发生的是：

      ① 模型吐出一段文字：「我要执行 open pvlib/pvsystem.py」
      ② ★★ 脚手架（一个普通程序）读到这句话，
         真的去磁盘上打开了这个文件
      ③ 脚手架把文件内容拼成一段新文字，接在对话后面
      ④ 再把整段对话喂给模型，问它下一步

   ★★★ 第 ②③ 步，就是脚手架干的全部活。

★★★ 还有一件事必须现在就说清，否则后面全章都会误解：模型没有记忆。

   ⚠️⚠️ 常见误解：「模型记住了我们刚才聊的内容。」
   ✅ 实际情况：★★★ 每一轮都是一次【全新的、无状态的】请求，
      脚手架把【从第一句话到现在的全部文字】重新发一遍。

   ⟹ ✅ Claude Code 官方文档把这件事写得很直白（★ 逐字）：
      "Claude Code sends your full conversation with every request, and each
       time Claude uses tools it sends another request carrying that batch of
       tool results."
      ⟹ 【每次请求都会把完整对话发过去；每用一次工具就再发一次请求，
         把那批工具结果一起带上。】

   ⟹ 🔑 所以"上下文"这个词在本目录里永远指：
      【脚手架这一轮打算发给模型的那一整坨文字】。
      ★★ 它是脚手架【每轮重新拼出来的】，不是模型里存着的东西。

2.2 名词：工具调用（tool call / function call）

   ★ 名词：tool（工具）
     ⟹ 脚手架事先向模型【声明】的一个动作。声明里写清三件事：
        名字（比如 read_file）、干什么用的、要传哪些参数。

   ★ 名词：tool call（工具调用），也叫 function call（函数调用）
     ⟹ 模型在回复里说"我要用 read_file，参数是 path=xxx"。
     ★★ 注意：模型只是【说】，动手的是脚手架。

   ★ 名词：tool result（工具结果），也叫 observation（观察）
     ⟹ 脚手架执行完，把结果（文件内容 / 报错信息 / 命令输出）
        塞回对话里，让模型下一轮能看到。
     ★ SWE-agent 论文里一律叫 observation，后面 04 章"只保留最近 5 条
        观察"说的就是它。

★★ 一轮完整的往返长这样（⚠️ 这是我画的示意，具体字段名各家不同）：

   第 1 步  脚手架 --> 模型
   ├── 系统提示词：你是一个编码 agent，可用工具有 …
   └── 用户消息：修复这个 issue：<issue 文本>
         |
         v
   第 2 步  模型 --> 脚手架
   ├── 【思考】我得先找到 PVSystem 类定义在哪
   └── 【工具调用】search_dir("class PVSystem")
         |
         v  ★★ 脚手架真的去执行了（这一步没有模型参与）
         |
   第 3 步  脚手架 --> 模型
   ├── 把上面第 1、2 步的全部文字【原样重发一遍】
   └── 再追加：【工具结果】Found 1 matches ... pvlib/pvsystem.py
         |
         v  ★★★ 回到第 2 步，再来一轮
      （循环）

   ⟹ 🔑🔑 ★★★ 请特别注意第 3 步里的"原样重发一遍"：

      第 3 步发出去的文字 = 第 1 步的全部 + 第 2 步的全部 + 新的工具结果。
      ⟹ ★★ 上下文是【只增不减】的，除非脚手架主动去删。
      ⟹ ★★★ 这一句就是 04 章整章的起点。

2.2b ⭐⭐⭐ 一个具体任务走完五轮：看着上下文滚起来

★★★ 全章最该花时间的一节。⚠️ 下面这条轨迹是我构造的示意，不是某次真实运行的日志；但每一格的格式都照 SWE-agent 论文公开的模板写（✅ 工具名、视窗 100 行、搜索上限 50 条、linter 拦下非法编辑、改完自动回显，全部是论文原文可查的设计）。

      改之前： irradiance.aoi(self.surface_azimuth, self.surface_tilt, ...)

2.3 ✅ ReAct：让模型先说想法，再说动作

★★★ SWE-agent 论文对这个循环有一句非常精确的描述（★ 逐字）：

"At each step, SWE-agent generates a thought and a command, then incorporates
the feedback from the command's execution in the environment (ReAct; Yao et al.)."

⟹ 中文：每一步，SWE-agent 生成一个"想法"和一个"命令"，然后把命令在环境中执行的反馈并入下一步。

   ★ 名词：ReAct（Reason + Act，推理 + 行动）
     ⟹ 一种提示词模式：★★ 强制模型每轮先写一句"我为什么要做这个"，
        再写"我要做什么"。
     ✅ 出处：Yao et al.，arXiv:2210.03629，被 SWE-agent 论文直接引用。

   ⟹ 🔑 为什么要强制写想法？
      ⚠️ 我的理解（论文引用了 ReAct 但没有单独论证这一点）：
      写出来的推理本身会进入下一轮的上下文，
      ★★ 相当于模型给自己留了一条"我刚才在干嘛"的笔记。
      ⟹ 回到 §2.2b 那张表：第 3 轮的思考"前两个参数反了"
         在第 4 轮还看得见 —— 所以第 4 轮不用重新推理一遍。

★★ SWE-agent 对"模型没按格式写"的处理，论文也写死了（★ 逐字）：

"Malformed generations trigger an error response, shown in Figure 32, asking the
agent to try again, which is repeated until a valid generation is received.
Once received, all past error messages except the first are omitted."

   ⟹ 中文：格式不对就回一条报错，让它重来，直到写对为止。
      ★★★ 写对之后，【除第一条外，之前所有的报错都从上下文里删掉】。

   ⟹ 🔑🔑 注意这个设计有多细：
      ① 不是"格式错了就算这题失败"——给它重试机会
      ② ★★ 但重试的垃圾不能留在上下文里污染后面
      ③ 保留第一条，是为了让模型记得"格式有要求"

   ⟹ ★★ 效果：✅ 论文 §B.9 报告，全部运行里只出现过【两次】Early Exit
      （连续格式错太多而被强行结束）。
      ⟹ ★★★ 2,294 题 × 多次运行里只有两次 —— 这个重试机制基本把
         "格式问题冒充能力问题"这一类失败清零了。

2.4 循环里最容易被忽略的一格：环境反馈怎么写

★★★ 这不是小事。SWE-agent 论文把"命令没输出"这种情况都单独处理了（★ 逐字）：

"however, if no output is generated, a specific message
('Your command ran successfully and did not produce any output') is included to enhance clarity."

   ⟹ 中文：如果命令没有任何输出，就塞一句
      「你的命令执行成功了，没有产生任何输出」。

   ⟹ 🔑🔑 为什么要专门加这一句？
      ★★ 因为如果什么都不返回，模型看到的是【空白】。
      而空白有歧义：是没执行？是执行了没结果？是报错被吞了？
      ⟹ ★★★ 模型会因此陷入反复重试同一条命令的死循环。

★ 把这件事摆成一张"同一个事实，两种写法"的对照，就很直观了：

真实发生的事 ① 坏写法：原样回传 ② 好写法：显式说明 ⚠️ 坏写法会让模型怎么想
touch newfile.py 成功，无输出 （空字符串） Your command ran successfully and did not produce any output. 「我是不是没执行？再试一次」⟹ 死循环
grep 没有命中 （空字符串） No matches found for "xxx" in /pvlib 「搜索工具坏了？」⟹ 换五种写法重搜
搜索命中 1,200 条 1,200 行原文（★★ 吃掉整个窗口） ✅ SWE-agent 的做法：一条都不给，改为提示它"把查询写细一点" 「挨个看完」⟹ ★★★ 预算烧光（03 章 §3.5）
pytest 失败，带 3,000 行日志 3,000 行原文 ⚠️ 只给失败的那几条 + traceback 末尾几行 淹没在噪音里，找不到真正的报错行

✅ 论文的第 3 条设计原则就是讲这个（★ 逐字）：

"3. Environment feedback should be informative but concise."

⟹ 环境反馈应当有信息量，但要简洁。

   ⟹ ⚠️ 我的归纳：这一条是新手最容易做错的地方。
      ★★ 直觉是"把命令的原始输出原样贴回去就行"，
      但原始输出通常是【为人设计的】：几百行、带颜色码、带进度条。
      ★★★ 对模型来说，那既贵又吵。

2.5 循环什么时候停

★★ 一个循环必须有出口，否则它会一直转到你破产。✅ SWE-agent 的出口可以从论文 Figure 7 的动作频次图直接读出来 —— 那张图的动作列表里，submit 和 exit_cost 两项就是出口。

   ⟹ 🔑 一般脚手架有五种出口。⚠️ 这个五分法是我的归纳，
      但每一条后面都标了它在 SWE-agent 里对应什么。
# 出口 触发条件 ✅ SWE-agent 里对应什么 ⚠️ 交上去的补丁算不算分
① 模型主动交卷 它自己调用了 submit 之类的工具 ✅ 动作 submit ★ 算。这是正常结局
② 成本上限 花到 X 美元 → 掐断 ✅ 动作 exit_cost；✅ 论文写明每题预算 $4 ★★★ 照样算，见下面那条逐字引用
③ 轮数上限 转了 N 轮还没完 → 掐断 ⚠️ SWE-agent 论文没给这个数（它用成本而不是轮数卡）；✅ 对比：DeepSeek-V4 报告写的是 500 步（07 章） ★ 一般算
④ 上下文塞满 对话长到装不下 → 掐断或压缩 ⚠️ SWE-agent 靠"折叠旧观察"让它基本不会发生（04 章） ★ 一般算
⑤ 格式连续写错 连续若干轮都不按格式输出 → 放弃 ✅ 论文 §B.9 叫 Early Exit，★★ 全部运行里只出现过 2 次 ⚠️ 算，但几乎总是 0 分

★★★ 第 ② 条有一个极容易说错的细节，论文写得很明确（★ 逐字）：

"Due to budget constraints, we set the per-instance budget to $4; if a run exceeded
this budget, existing edits were submitted automatically."

✅ 附录 Figure 17 的图注再说了一遍：

"exit_cost refers to when the token budget cost was exhausted and the episode's
changes are automatically submitted (contrary to an intentional submit invoked by the agent)."

   ⟹ ⚠️⚠️ ★★★ 所以"掐断"这个说法是不完整的：

      ⚠️ 错误理解：花超预算 → 这题直接判 0 分，改动丢掉。
      ✅ 实际行为：花超预算 → 脚手架【把它当前已经改出来的东西
         原样交上去】，照常送进判卷器。

   ⟹ 🔑🔑 这个区别很重要，因为它意味着：
      ★★ 被掐断的那些题，仍然有一小部分能蒙对。
      ✅ 论文 Table 13 给了确切数字（SWE-agent w/ GPT-4 Turbo，
         SWE-bench 全量）：
         以 submit 结束的题目，14.3% 被判 resolved；
         以 exit_cost 结束的题目，只有 3.1% 被判 resolved。
      ⟹ ★★★ 3.1% 不是 0 —— 但它比 14.3% 低了 4.6 倍。

★★★ ✅ 论文 §B.9 把"一条轨迹到底有几种结束方式"逐个定义了（★ 这是比我上面那个五分法更硬的一手口径）：

✅ 论文的结束方式名 ✅ 论文定义（逐字要点） 中文
Submit "ends when the agent generates the submit command" 模型自己交卷
Exit Cost (Submit) "the cost limit was hit, and the changes so far are gathered and submitted as an edit" ★★ 钱用完了，把目前改出来的东西收起来交上去
Exit Cost (No Submit) "the cost limit was hit and no edit's were made, so there was nothing to submit. In this scenario, the instance is guaranteed to be unresolved." ★★★ 钱用完了，而且一次编辑都没做过 ⟹ 无东西可交 ⟹ 必然算失败
Early Exit "the task episode terminates because an agent issued too many malformed responses in a row. Any changes are submitted as an edit." 格式连续写错太多被强行结束；★ 已有的改动照样交上去

✅ 论文 Table 13 给了这四种结局的确切条数。★★ 下面取 SWE-bench Lite 那一组（★ 它加总正好是 300 和 54，可以自己核）：

结局 全部 300 道题里有几道这样结束 其中被判 resolved 的有几道 ⚠️ 我算的解决率
Submit（主动交卷） 203 50 24.6%
Exit Cost (Submit)（钱用完，有东西交） 95 4 ⚠️ 4.2%
Exit Cost (No Submit)（钱用完，没东西交） 2 0 0%（✅ 论文说这种必然失败）
Early Exit（格式连错） 0 0 ——
合计 300 ✅ 54 ✅（= 18.00%） 
   ⟹ ⚠️⚠️ ★★★ 所以"掐断"这个说法是不完整的：

      ⚠️ 错误理解：花超预算 → 这题直接判 0 分，改动丢掉。
      ✅ 实际行为：花超预算 → 脚手架【把它当前已经改出来的东西
         原样交上去】，照常送进判卷器。
      ★★ 只有"连一次编辑都没做过"的那 2 道题，才真的无东西可交。

   ⟹ 🔑🔑 这个区别很重要，因为它意味着：
      ★★ 被掐断的那些题，仍然有一小部分能蒙对（95 道里 4 道）。
      ✅ 论文正文也给了全量集上的同一对比（★ 逐字数字）：
         以 submit 结束的题目，14.3% 被判 resolved；
         以 exit_cost 结束的题目，只有 3.1% 被判 resolved。
      ⟹ ★★★ 3.1% 不是 0 —— 但它比 14.3% 低了 4.6 倍。

   ⚠️ 口径提醒：上表那三个"我算的解决率"（24.6% / 4.2% / 0%）是我用
      ✅ Table 13 的 Lite 计数相除得到的，★ 论文正文给的 14.3% / 3.1%
      是【全量 2,294 题】那一组。⟹ 两组口径不同，数值不该对得上。

   ⟹ ★★★ 这五个数字（$4 / 步数 / 窗口 / 重试次数 / 掐断后交不交），
      就是 [评测入门 08 章](../评测入门/08-ClaudeCode与Codex怎么被评.md) 说的"最常被隐藏的变量"。
      榜单上写"SWE-bench 65%"，从来不写"预算是每题 2 美元还是 20 美元"。
   ⟹ 🔑 完整的八项口径清单在 [01 章 §1.4b](01-两个harness不是一个东西.md)。

2.6 ✅ 一个很有意思的实测：成功的 agent 结束得早

★★★ SWE-agent 论文用一句标题总结了这个现象（★ 逐字）：

"Agents succeed quickly and fail slowly."

⟹ agent 成功得快，失败得慢。

✅ 支撑数字（论文 §5.2 正文 + Table 15，SWE-agent w/ GPT-4 Turbo）：

题目分组 花费 步数 ⚠️ 统计量
解决了的题目 $1.21 12 步 ★★ 中位数
没解决的题目 $2.52 21 步 ★★ 均值 
   ⚠️⚠️ ★★★ 这张表有两个口径陷阱，必须先说，否则会被当成"两倍关系"：

      ① ★★ 论文这一句是拿【中位数】和【均值】对比的，
         不是同一种统计量。
         ⟹ 均值被少数超长轨迹拉高，中位数不会。
         ⟹ 所以"$2.52 ÷ $1.21 ≈ 2.08 倍"这个算法【没有意义】。

      ② ★★★ ✅ 论文明说这张表"only including instances that did not
         exhaust their budget"（只统计【没有耗尽预算】的题目）。
         ⟹ ⚠️ 也就是说，最惨的那一批（烧光 $4 的）压根不在这张表里。
         ⟹ 🔑 真实的"失败有多慢"比表上显示的更极端。

✅ 另一组独立的数字（★ 逐字）：

"we find that 93.0% of resolved instances are submitted before exhausting their
cost budget, compared to 69.0% of instances overall."

   ⟹ 中文：**93.0% 的"已解决"题目，是在花完预算之前就交卷的；
      而全部题目里这个比例只有 69.0%。**

   ⚠️⚠️ 这两个数说的是【交卷早不早】，★★★ 不是【这一组的解决率】。
      ⚠️ 错读：「93% 的题被解决了」。
      ✅ 正确：「在被解决的题里，93% 没烧光预算；
                而不分组看，只有 69% 没烧光预算」。
   ⟹ ★★ 反过来推一个更直观的说法：
      全部题目里有 31% 是烧光预算（或格式连错）被自动交上去的，
      而在解决了的题里这个比例只有 7%。

★ 这两个数字可以用 §2.5 那张 Table 13 计数表自己验算一遍（★★ 这种交叉核对值得学一下）：

   ✅ 论文 Table 13 给的全量集（2,294 题）计数里：
      以 submit 结束且被判 resolved 的 = 266 道
      全部被判 resolved 的             = 286 道（= 12.47% × 2,294）

   ⟹ 266 / 286 = 93.006% ≈ ✅ 论文正文那个 93.0%。
   ⟹ ★★★ 完全对上了。所以"93.0%"的准确含义是：
      【286 道解决了的题里，有 266 道是模型自己 submit 的，
        剩下 20 道是烧光预算被自动交上去然后蒙对的。】

   ⚠️ 对应的 69.0% 我没有逐数核成：按 0.690 × 2,294 反推，
      以 submit 结束的总题数应该是 1,583 道左右；
      ★ 我从 PDF 里读到的那个计数和这个值差几道（可能是取字偏差），
      ⟹ 所以这里只引论文正文的 69.0%，不引我读到的计数。

   ⟹ 🔑🔑🔑 论文由此得出一个反直觉的结论（★ 逐字）：

      "we suspect that increasing the maximum budget or token limit are
       unlikely to substantially increase performance."

      ⟹ ★★★【单纯把预算调大，大概率不会明显提分。】
      ⚠️ 注意论文用的词是 "we suspect"（我们怀疑）——
         ★★ 这是一条【基于相关性的推测】，不是控制变量实验。
         论文没有真的把预算从 $4 调到 $8 再跑一遍。

   ⚠️ 我的解读：因为转了 20 步还没做完的，通常不是"差一点点"，
      而是【已经走进死胡同了】——它在原地打转，再给钱也是原地打转。
      ⟹ ★★ 这一点在 03 章会得到印证：✅ 失败模式里最大的一类是
         "改错了"（39.9%），而"预算用尽"只占 2.0%。

2.7 现代脚手架的循环，多了哪些格子

⚠️ 以下是我对 Claude Code / Codex 官方文档的归纳。标 ✅ 的是文档原文可查的名字；⚠️ 产品行为变化快，本节口径截至 2026-08-27，配置项名和模式数可能随版本变。

   ┌─ 基础循环（SWE-agent 那一版）
   │  想法 --> 工具调用 --> 执行 --> 结果 --> 想法 --> …
   └─
             ＋ 下面五格
# 多出来的格子 插在循环的哪一步 ✅ 文档可查的名字 详见
① ★★ 权限检查 执行之前先问一句"能动吗" ✅ Claude Code 有 六种许可模式（permission modes） 05 章 §5.4
② ★★ 沙箱 执行时限制它能碰到的文件和网络 ✅ Codex 有 read-only / workspace-write / danger-full-access 三档 05 章
③ ★★★ 自动压缩 拼下一轮上下文之前 ✅ Claude Code 叫 auto-compact；✅ Codex 的配置项叫 model_auto_compact_token_limit 04 章 §4.4
④ ★★ 子 agent 把脏活整段挪出主循环 ✅ Claude Code 官方文档原话："Each subagent runs in its own context window" 04 章 §4.5
⑤ ★ 钩子（hook） 在循环的固定位置插入你自己的脚本 ✅ 两家都有；Claude Code 有 PreToolUse，Codex 有 PreCompact / PostCompact 05 章、06 章 
   ⟹ 🔑🔑 ★★★ 注意这五项的共同点：
      【它们全都是在往循环里加"限制"和"删减"，不是加"能力"。】

   ⚠️ 我的判断，这是脚手架工程最反直觉的地方：
      ★★ 做一个能跑的 agent 循环，一个下午就够了。
      ★★★ 剩下 99% 的工作量，是让它在【上下文有限、钱有限、
           不能乱动用户文件】的约束下还能干成活。

★ 把 §2.2b 那五轮重走一遍，标出这五格会插在哪里，就很具体了：

   第 3 轮：模型说「edit 412:412」
      ├── ① 权限检查   --> "要改 pvlib/pvsystem.py，允许吗？"
      │                     （评测场景里全开；你公司里要问）
      ├── ② 沙箱       --> 真跑的时候，它只能写到工作区里
      ├──    linter 护栏 --> ⚠️ 这一格不是"现代产品才有"，
      │                     ✅ SWE-agent 2024 年就有了（03 章）
      └──    执行
   第 5 轮：模型说「pytest …」
      ├── ② 沙箱       --> 不许联网装包
      └──    执行 --> 如果输出 3,000 行：
             ├── ③ 自动压缩  --> 快撞窗口了，把前面总结掉
             └── ④ 子 agent  --> 或者：整段丢给一个独立上下文去看
   每一步之间
      └── ⑤ 钩子 --> 你可以在这里插 "每次编辑后自动跑 black 格式化"

2.8 本章总结

    🔑 七条带走：

    ① ★★★ 模型只会输出文字。把文字变成动作、再变回文字的，是脚手架。
       ⟹ ★★ 而且模型【没有记忆】：每轮都是把全部历史重发一遍。

    ② ★★ 一轮 = 工具声明 → 模型说要调用 → 脚手架执行 → 结果塞回对话。
       ⟹ ★★★ §2.2b 那张五轮表是全章骨架：
          上下文【只增不减】，第 4 轮之后同一行代码在上下文里有两个版本。

    ③ ★★ ✅ ReAct：强制每步先写想法再写命令。
       格式写错就回报错重来，★★ 重来的垃圾要从上下文里删掉
       （✅ 除第一条外全删）。效果：✅ 全部运行里只出现过 2 次 Early Exit。

    ④ ★★★ 环境反馈的写法本身是技术。
       ✅ 连"命令没有输出"都要专门写一句话，否则模型会死循环。
       ✅ 搜索命中超过 50 条就【一条都不给】，改为让它把查询写细。

    ⑤ ★★★ 循环有五种出口：主动交卷 / 成本 / 轮数 / 上下文 / 格式连错。
       ✅ 而 SWE-agent 实测只用到四种结局（论文 §B.9）：
          Submit / Exit Cost (Submit) / Exit Cost (No Submit) / Early Exit。
       ⟹ ⚠️⚠️ ✅ 关键纠正：成本超了【不是丢弃】，而是
          "把现有改动自动交上去"。
          ✅ Lite 300 题的计数：203 道主动交卷（解决 50）、
             95 道烧光预算后自动交（★★ 仍解决 4 道）、
             2 道烧光预算且一次编辑都没做过（✅ 论文说这种必然失败）。
       ⟹ ✅ 全量集上：以 submit 结束的 14.3% 被判 resolved，
          以 exit_cost 结束的只有 3.1%。★★ 不是 0，但低 4.6 倍。

    ⑥ ★★★ ✅「成功得快，失败得慢」——解决了的题中位 12 步 $1.21，
       没解决的均值 21 步 $2.52。
       ⚠️⚠️ 两个口径陷阱：① 中位数对均值，不能相除；
       ② ✅ 这张表只统计【没耗尽预算】的题，最惨那批不在里面。
       ⟹ 论文据此【推测】（"we suspect"）加预算不会明显提分，
          ⚠️ 不是控制变量实验。

    ⑦ ★★ 现代产品在这个圈上多了五格：权限 / 沙箱 / 自动压缩 /
       子 agent / 钩子。⟹ 🔑 全是"限制"和"删减"，不是"能力"。
