03 · 工具集与 ACI：界面本身就是能力

⭐⭐ 全目录数字最硬的一章。这里的每个结论都有 SWE-agent 论文的消融实验撑着。
结论提前说：★★★ 同一个模型，只改"给它用的界面"，
SWE-bench Lite 分数在 10.3 ~ 18.0 之间来回跑。

3.1 名词：ACI —— 为什么"给模型的界面"是一项技术

★★★ 这个词是 SWE-agent 论文提出来的，它的定义（★ 逐字）：

"an agent-computer interface (ACI), i.e., an abstraction layer between the LM
agent and computer, to enhance the LM agent's abilities in computer environments"

⟹ 智能体-计算机接口（ACI），即模型智能体与计算机之间的一个抽象层，用来增强模型在计算机环境中的能力。

   ★ 名词：ACI（Agent-Computer Interface，智能体-计算机接口）
     ⟹ 类比：★★ 人用计算机有 UI（User Interface，用户界面）——
        窗口、按钮、鼠标。那是为【人】设计的。
        ACI 就是为【模型】设计的那一套。

   ⟹ 🔑🔑 论文的核心主张：★★★
      【为人设计的界面，模型用起来是不顺手的。要专门为模型重做一套。】

✅ 论文用一句话点破了为什么（★ 逐字）：

"we posit that LM agents represent a new category of end users with their own
needs and abilities, and would benefit from specially-built interfaces"

⟹ 我们主张，模型智能体是一类全新的终端用户，有它自己的需求和能力，会从专门为它建造的界面中受益。

   ⟹ ⚠️ 我的翻译：★★ 把模型当成一个【新品种的用户】来做产品设计。
      它不会用鼠标，看不见颜色，记性有限（上下文窗口），
      但它读文本极快，且不会累。
      ⟹ ★★★ 界面得按这个特点重做。

★ 把"人用的界面"和"模型用的界面"摆在一起，这件事就很具体了：

同一个需求 ★ 人的界面（UI）怎么做 ★★ 模型的界面（ACI）怎么做 ⚠️ 为什么不能照搬
看一个文件 编辑器里滚动条随便拖，眼睛一扫就定位 ✅ open 命令，一次给最多 100 行，每行带行号，并标注"上面省略了 357 行、下面还有 1,436 行" ★★ 模型没有"眼睛扫一遍"这个动作，它必须把看到的每个字都读进上下文。给整个文件 = 把 1,893 行全塞进窗口
搜一个符号 搜索框里打字，结果列在侧边栏，点一个看一个 ✅ search_dir 返回汇总；✅ 超过 50 条就一条都不给，改为提示"把查询写细" ★★★ 人翻到第 5 页会放弃，模型会老老实实翻完 15 页 —— 然后预算就没了（§3.5）
改一行代码 鼠标点到那一行，直接敲字，所见即所得 ✅ edit <起始行> <结束行> <新内容>，一步换掉整段；改完自动回显改后的视窗 ★★ 模型没有"光标"。如果不回显，它不知道自己改成了什么样
发现自己敲错了 编辑器当场标红波浪线 ✅ 编辑命令内置 linter（语法检查器）；✅ 非法编辑直接丢弃不落盘，并把改前改后的片段给它看 ★★★ 人看到红线会立刻改；模型看不到颜色，必须把错误写成文字送给它

3.2 ✅ 论文给出的四条 ACI 设计原则

★★★ 这四条是论文正文明确编号列出的。下面每一条都是「✅ 英文逐字 + 中文 + 论文自己给的理由」。

# ✅ 原则（逐字） 中文 ✅ 论文给的理由 / 例子（逐字节选）
1 "Actions should be simple and easy to understand for agents." ★★ 动作要简单、模型容易理解 "Many bash commands have documentation that includes dozens of options. Simple commands with a few options and concise documentation are easier for agents to use, reducing the need for demonstrations or fine-tuning."
⟹ 很多 bash 命令的文档有几十个选项；参数少、文档短的命令模型更容易用对，还能少给示范、少做微调
2 "Actions should be compact and efficient." ★★★ 动作要紧凑高效 —— 重要操作要合并成尽量少的动作 "A poor design would therefore have many simple actions that must be composed across multiple turns for a higher order operation to take effect."
⟹ ★★ 糟糕的设计 = 一堆小动作，必须跨好几轮才能拼出一个有意义的操作
3 "Environment feedback should be informative but concise." ★★ 环境反馈要有信息量，但要简洁 "For instance, when editing a file, updating the agent about revised content is helpful."
⟹ 比如改完文件，把改后的内容回显给它，是有用的。（02 章 §2.4 讲过）
4 "Guardrails mitigate error propagation and hasten recovery." ★★★ 护栏能抑制错误蔓延、加快恢复 "Building in guardrails, such as a code syntax checker that automatically detects mistakes, can help agents recognize and quickly correct errors."
⟹ 在编辑命令里内置一个语法检查器，自动发现模型改出来的语法错误		 
   ★ 名词：guardrail（护栏）
     ⟹ 在工具内部加的自动检查：★★ 模型做了个明显错误的操作，
        工具【当场拦下来并告诉它错在哪】，而不是默默执行。
     ★★★ 关键在"当场"和"不落盘"这两件事上，见 §3.6。

   ★ 名词：linter（语法检查器 / 静态检查器）
     ⟹ 不运行代码、只靠读代码就能找出一类错误的程序。
        比如 Python 的 flake8 / pyflakes 能查出缩进错、变量名拼错、
        括号没闭合。⚠️ 它查不出【逻辑错】——参数传反了它不管。

   ⟹ 🔑🔑 ★★★ 四条原则里，第 2 条和第 4 条是最容易被忽略的：

      第 2 条反对的是【把工具切得太细】。
      ⚠️ 新手的直觉恰好相反：「工具拆得越细越灵活」。
      ⟹ ★★ 但"灵活"的代价是轮数，而轮数就是钱和上下文（§3.3b）。

      第 4 条说的是【工具要会说"不"】。
      ⚠️ 新手的直觉也相反：「工具就该老老实实执行」。
      ⟹ ★★★ 但默默执行一个错误操作，等于把错误写进了世界状态，
         后面每一轮都基于这个错误状态推理（02 章 §2.2b 第 ④ 条）。

3.3 ✅ SWE-agent 实际给了模型哪些工具

★★ 论文 §3 逐个描述了它的工具集。这不是猜的，是论文原文。

组 工具名 干什么 ✅ 关键设计（论文原文可查）

⟹ 超过 50 条就一条都不给，改为提示它"把查询写细"

search_dir 在一个目录里找字符串 同上

scroll_down / scroll_up 视窗上下挪 ★ 一次挪 100 行

设计二：★★★ 内置 linter。✅ 原话："Invalid edits are discarded, and the agent is asked to try editing the file again." ⟹【非法的编辑直接丢弃，不写进文件】，让它重改。✅ 并且 "Select errors from the linter are shown to the agent along with a snippet of the file contents before/after the error was introduced." ⟹ 报错时连改前改后的片段一起给它看

   ⟹ ★★ 除此之外，模型还能直接用普通 Linux 命令（python、pytest 等）。
      ✅ 论文原话："Built atop the Linux shell, SWE-agent also allows
         access to common Linux commands and utilities when needed."
      ✅ 旁证：论文 Figure 7 的动作频次图里，直接出现了
         python / python3 / pytest / find 这几个动作。

   ⟹ 🔑 所以数一数：★★ 专用工具 10 个 + 整个 Linux shell。
      ⚠️ 注意这和 DeepSeek-V4 跑分用的【2 个工具】是完全不同的取舍
         （bash + 文件编辑，见 07 章）—— 两家都拿到了好成绩。
      ⟹ ★★★ 所以"工具越多越好"也是错的。重点不是数量，是【顺不顺手】。

3.3b ⭐⭐⭐ 三种工具集设计，同一个任务各走一遍

★★★ 本章最该花时间的一节。用 02 章 §2.2b 的同一个任务，换三种工具集各走一遍。

① 任务与三种工具集

   ★ 任务（和 02 章完全一样）：
      issue: PVSystem.get_aoi returns wrong angles
      真正的 bug: pvlib/pvsystem.py 第 412 行，前两个参数顺序写反了
         改前: irradiance.aoi(self.surface_azimuth, self.surface_tilt, ...)
         改后: irradiance.aoi(self.surface_tilt, self.surface_azimuth, ...)
      ⚠️ 这一行在一个缩进 8 个空格的函数体里面。
         ★★ 记住这件事，三种工具集的差别全在它上面爆发。
方案 工具集 ✅ 对应论文消融表的哪一行 ✅ 实测分数
A ★ bash 一把梭：只给一个 shell，改文件靠 sed 或者整文件重定向覆盖 ✅ 论文的 Noedit 设定 10.3
B ★★ 细分 read / write / edit：有结构化的 edit <起始行> <结束行>、有带行号的视窗、改完自动回显，但没有 linter 护栏 ✅ 论文的 edit w/o linting 设定 15.0
C ★★★ 带 lint 的编辑器：B 的全部 ＋ 编辑命令内置 linter，非法编辑丢弃不落盘 ✅ SWE-agent 默认配置 18.0 
   ⚠️ 映射说明：A 和 C 是论文设定的原样。
      B 严格说是"把 C 的 linter 摘掉"，结构化 edit 和自动回显都还在。
      ★★ 我在下面的走查里按论文的口径来，不给 B 额外减配。

② 方案 A：只有 bash，走完要八轮，而且有一轮是静默失败

轮 模型输出 工具返回 ⚠️ 这一轮的麻烦在哪

2 sed -n '400,420p' pvlib/pvsystem.py 21 行纯代码，⚠️⚠️ 没有行号 ★★★ 模型必须自己数"从 400 开始往下第 13 行"。✅ 论文附录记录到了真实的这类行为：模型用 sed 看完前 100 行，然后要接着看下 100 行，得自己算区间
3 sed -i '412s/self.surface_azimuth, self.surface_tilt/self.surface_tilt, self.surface_azimuth/' pvlib/pvsystem.py （空输出） ⚠️⚠️⚠️ 本节最要命的一格。sed 没匹配上也是成功退出、无输出。⟹ 模型看到的"成功"和真的改了，长得一模一样（02 章 §2.4 那个"空输出有歧义"）
4 sed -n '410,414p' pvlib/pvsystem.py 5 行，412 行还是旧的 ★★ 得专门花一轮去验证，才发现第 3 轮白做了

★★★ 改一行要把 1,893 行全写一遍，写漏一段就是静默丢代码
6 sed -n '410,414p' pvlib/pvsystem.py 这次 412 行对了 ★ 又花一轮验证
7 python -m pytest pvlib/tests/test_pvsystem.py -k aoi 3 passed ——
8 交卷 —— —— 
   ⟹ 🔑🔑 ✅ 论文对这一套的评语是逐字的（★ 值得读两遍）：

      "In the Noedit setting, editing options are restrictive and prone to
       errors; the primary methods available are either replacing entire
       files through redirection and overwriting or using utilities like
       sed for single-line or search-and-replace edits. Both methods have
       significant drawbacks. ... Although sed can facilitate specific
       edits, executing multi-line edits is cumbersome and can lead to
       unintended consequences that are challenging to detect."

      ⟹ 中文：★★★ 两条路都有重大缺陷。整文件重定向：改一点点就要
         复制重写整个文件，既低效又容易出错。sed 虽然能做定点修改，
         但【多行编辑很别扭，而且会造成难以察觉的意外后果】。

   ⟹ ★★★ "难以察觉"（challenging to detect）这四个字就是方案 A 的
      全部问题：★★ 它的失败是【静默的】。

③ 方案 B：有结构化编辑器但没护栏，走完要七轮，第 3 轮把文件改坏了

轮 模型输出 工具返回 ⚠️ 这一轮的麻烦在哪
1 search_dir "def get_aoi" 汇总式命中：pvlib/pvsystem.py (line 408)、pvlib/tracking.py (line 173) ★★ 比 A 的 grep 干净，★ 而且直接给了行号
2 open pvlib/pvsystem.py 408 第 358–457 行，★★ 每行带行号，并标注总行数和上下省略行数 ★★★ 不用自己数行号，这一项就省掉了 A 的第 2 轮那种算术
3 edit 412:412 + 新内容（⚠️ 缩进写成 4 个空格，这个函数体要 8 个） ⚠️⚠️ 没有 linter，直接写进文件；自动回显改后的视窗 ★★★ 回显里 412 行的缩进其实"看着不太对"，但没有任何东西明确告诉它错了。⟹ 🔑 文件已经被改坏

7 pytest → 3 passed → 交卷 —— —— 
   ⟹ 🔑🔑 ★★★ B 比 A 好在哪、差在哪，要分开说：

      ★★ B 比 A 好：① 搜索结果带行号，省掉数行号那一轮；
         ② 改完自动回显，省掉"再发一条命令去验证"那一轮；
         ③ ★★★ 失败最终是【可见的】——pytest 会炸。
         ✅ 这就是 10.3 → 15.0 那 4.7 个点。

      ⚠️ B 比 C 差的地方只有一件事，但很致命：
         ★★★ 第 3 轮那次错误编辑【真的落盘了】。
         ⟹ 第 4、5 轮里，模型看到的是【已经被自己改坏的文件】。
         ⟹ 🔑 它现在要同时解决两个问题：原来的参数顺序 bug，
            和自己新引入的缩进错。
         ⚠️ 在这条顺利的走查里它解决了。✅ 论文的实测说：
            很多时候它解决不了 —— 一次失败编辑之后，
            最终改成功的概率从 90.5% 掉到 57.2%（§3.6）。

④ 方案 C：带 lint 的编辑器，走完六轮，第 3 轮当场被拦住且文件没动

★ 这一条就是 02 章 §2.2b 那张五轮表 ＋ 第 6 轮交卷，这里只重放最关键的第 3 轮：

   第 3 轮  模型输出：edit 412:412 + 新内容（缩进 4 个空格，错的）

   脚手架做的事（★★ 顺序很重要）：
   ├── ① 先在内存里算出"改完会是什么样"
   ├── ② 对这个结果跑 linter
   ├── ③ linter 报 E999 IndentationError at line 412
   ├── ④ ★★★ 把这次编辑【整个丢弃】—— 磁盘上的文件一个字没动
   └── ⑤ 把下面这段文字返回给模型：

         Your proposed edit has introduced new syntax error(s):
         - E999 IndentationError: unexpected indent (line 412)
         This is how your edit would have looked:
           (改前 3 行 / 改后 3 行 的并排片段)
         Your changes have NOT been applied. Please fix ... and try again.

   ⟹ 🔑🔑 ★★★ 对比 B 的第 3 轮，C 多做了三件事：
      ① 【当场】说错了，不等到第 4 轮跑测试才炸
      ② 【明确】说错在哪一行、是什么错，不用模型自己推
      ③ ★★★ 【文件没被改坏】—— 第 4 轮模型面对的还是干净代码

3.6 ✅ 护栏值多少钱：编辑失败的实测数据

★★ 论文 §5.2 给了一组非常具体的数字，说明"改错了之后能不能爬起来"有多要命。

✅ 口径：SWE-agent w/ GPT-4 Turbo 在 SWE-bench 全量 2,294 题上的轨迹（⚠️ 注意这一组不是 Lite 300 题）。

指标 ✅ 数值 ⚠️ 它到底在说什么
轨迹里出现过至少一次失败编辑的题目 51.7%（2,294 题里的 1,185 题） ★★ 一半以上的任务，模型都改错过
任何一次编辑尝试，最终改成功的概率 90.5% ⚠️⚠️ 这是【总体】成功率，不是"护栏拦下了 90.5% 的错误"
已经失败过一次之后，最终改成功的概率 57.2% ★★★ 掉 33.3 个百分点

✅ 论文原句（★ 逐字，避免再被转述错）：

"Any attempt at editing has a 90.5% chance of eventually being successful.
This probability drops off to 57.2% after a single failed edit."

   ⚠️ 顺便澄清两个容易混的词：
      ★ "最终改成功"（eventually successful）指的是
         ✅ 论文定义的 recovery：一连串失败编辑之后，紧接着来了一次成功编辑。
      ⚠️ 它【不是】"这道题最后解决了"。
         ★★ 编辑成功 ≠ 改对了 —— linter 只管语法，不管逻辑。

   ⟹ 🔑🔑🔑 ★★★ 这就是"护栏"存在的全部理由：

   没有 linter 护栏的因果链：
   ├── ① 错误的编辑被真写进文件
   ├── ② 模型下一步看到的是【已经被自己改坏的代码】
   ├── ③ 它基于错误的状态继续改
   ├── ④ 于是它现在要同时解决两个问题：原 bug ＋ 自己造的新错
   └── ⑤ ★★★ 错误滚雪球
          ✅ 论文的原词是 "cascading failed edits"（层叠的失败编辑）

   有 linter 护栏的因果链：
   ├── ① 先在内存里算出"改完会是什么样"，对它跑 linter
   ├── ② 非法 ⟹ ★★★ 【当场丢弃、不落盘】
   ├── ③ 把错误信息 ＋ 改前改后对比一起返回给它
   └── ④ ★★ 磁盘状态回到编辑前 ⟹ 它只需要解决原来那一个问题

   ✅ 代价换来的收益：15.0 → 18.0，值 3.0 个点（§3.4）。
   ⚠️ 这 3.0 个点在 300 题上等于 9 道题，刚刚压过噪声线（§3.4 ③）。

   ⟹ 🔑 一条很实用的推论，给要自己搭脚手架的人：

      ★★★ 【只报错、照样写进文件】的护栏，收益会显著缩水。
      ⚠️ 这是我的推断（论文没做这个中间档的消融），
         但机理很清楚：§3.3b 方案 B 的第 3 轮就是这种情况 ——
         ★★ 错误可见了，但磁盘已经脏了，模型要解决两个问题。
      ⟹ ★★★ "不落盘"这三个字，是这个护栏里最值钱的部分。

      ⟹ ⚠️ 第 9 类是 Table 9 里的 "Other"，在图上没有可见的占比
         （四舍五入后约 0.1%）。
      ⟹ ★ 另外 Figure 8 的标签和 Table 9 的类目名用词略有差异
         （Failed to Recover from Edit ↔ Failed Edit Recovery、
          Can't Reproduce ↔ Failed to Reproduce），指的是同一类。

   ⟹ 🔑🔑 读这张表要读三件事：

   ① ★★★ 52.0%（39.9 + 12.1）是【方案本身不对】。
      ✅ 论文原话确认了这个加总："about half (52.0%) of unresolved
         instances fall into the Incorrect Implementation or
         Overly Specific Implementation categories"
      ⟹ ★★ 这部分脚手架帮不上忙，是模型能力问题。

   ② ★★★ 但 23.4%（约 58 道题）是【编辑失败后爬不起来】——第二大类。
      ⟹ ★★ 这部分【纯粹是脚手架问题】。
      ⟹ 🔑 这就是为什么 §3.6 那个护栏值 3.0 个点。
      ⚠️ 注意这两个数不能直接相加换算：23.4% 是"未解决题里的占比"，
         而 3.0 个点是"全部 300 题里的解决率变化"。
         ★★ 口径不同，一个分母是 248，一个分母是 300。

   ③ ⚠️ 注意 "Ran Out of Budget" 只有 2.0% —— 约 5 道题。
      ★★★ 和 [02 章 §2.6](02-agent循环怎么转.md) 那句"加预算不会明显提分"完全对上了。
      ⚠️ 但也要诚实：5 道题 ÷ 248 的统计意义很弱，
         ★★ 这一行只能说"预算显然不是主要瓶颈"，不能说"正好 2.0%"。

3.9 本章总结

    🔑 八条带走：

    ① ★★★ ACI（Agent-Computer Interface，智能体-计算机接口）
       = 专门为模型（而不是为人）设计的操作界面。
       ⟹ 模型是一类新的终端用户，需要重做界面。

    ② ★★ ✅ 四条设计原则：动作简单 / 动作紧凑 / 反馈简洁有料 / 加护栏。
       ⟹ 🔑 最容易做错的是第 2 和第 4 条：
          【工具不能切太细】【工具要会说"不"】。

    ③ ★★★ ✅ §3.3b：同一个任务，三种工具集各走一遍 ——
       bash 一把梭 8 轮（且失败是静默的）／
       细分编辑器无护栏 7 轮（文件被改坏）／
       带 lint 的编辑器 6 轮（当场拦下、不落盘）。
       ⟹ ✅ 对应实测 10.3 / 15.0 / 18.0。

    ④ ★★★ ✅ 消融表：同一个 gpt-4-1106-preview，只换界面，10.3 ~ 18.0。
       ⚠️⚠️ 但 §3.4 ③ 必须一起看：前五行（↓7.7 / 6.0 / 5.3 / 3.7 / 3.0）
       是真结论；后两行（↓2.3 / 1.7）在噪声量级里，只能当方向性线索。

    ⑤ ★★★ ✅ 逐条翻页式搜索(12.0) 比【完全没搜索】(15.7) 还差。
       ⟹ 🔑 难用的工具，比没有工具更糟。
       ⟹ ★★ 它输在【没有上限】——汇总式搜索那个"超 50 条一条不给"
          的设计，本质也是一个护栏。

    ⑥ ★★★ ✅ 一次给 100 行(18.0) > 给 30 行(14.3) > 给整个文件(12.7)。
       ⟹ 🔑 给得越多越好是错的，两头都掉：
          视窗太小烧轮数，视窗太大每轮重发无关代码。
       ⚠️ 100 行是在 37 道 dev 题上扫出来的，不是普适常数。

    ⑦ ★★★ ✅ 编辑失败后，最终改成功的概率从 90.5% 掉到 57.2%
       （掉 33.3 个百分点）；51.7% 的题都至少改错过一次。
       ⟹ 护栏值 3.0 个点，而 🔑【"不落盘"是其中最值钱的部分】。

    ⑧ ★★ ✅ 失败模式（口径：Lite 的 248 道未解决题，GPT-4o 自动分类，
       与人工一致率 87%）：52.0% 是方案不对（帮不上忙），
       ★★★ 23.4% 是编辑失败后爬不起来（纯脚手架问题）。
       ⚠️⚠️ 校正："Ran Out of Time"（2.0%）在 Table 9 里的正式名字是
       Ran Out of Budget ⟹ 是【预算用尽】，不是【时钟超时】。
