03 · 工具集与 ACI：界面本身就是能力

⭐⭐ 全目录数字最硬的一章。这里的每个结论都有 SWE-agent 论文的消融实验撑着。
结论提前说：★★★ 同一个模型，只改"给它用的界面"，
SWE-bench Lite 分数在 10.3 ~ 18.0 之间来回跑。

3.1 名词：ACI —— 为什么"给模型的界面"是一项技术

★★★ 这个词是 SWE-agent 论文提出来的，它的定义（★ 逐字）：

"an agent-computer interface (ACI), i.e., an abstraction layer between the LM
agent and computer, to enhance the LM agent's abilities in computer environments"

⟹ 智能体-计算机接口（ACI），即模型智能体与计算机之间的一个抽象层，用来增强模型在计算机环境中的能力。

   ★ 名词：ACI（Agent-Computer Interface，智能体-计算机接口）
     ⟹ 类比：★★ 人用计算机有 UI（User Interface，用户界面）——
        窗口、按钮、鼠标。那是为【人】设计的。
        ACI 就是为【模型】设计的那一套。

   ⟹ 🔑🔑 论文的核心主张：★★★
      【为人设计的界面，模型用起来是不顺手的。要专门为模型重做一套。】

✅ 论文用一句话点破了为什么（★ 逐字）：

"we posit that LM agents represent a new category of end users with their own
needs and abilities, and would benefit from specially-built interfaces"

⟹ 我们主张，模型智能体是一类全新的终端用户，有它自己的需求和能力，会从专门为它建造的界面中受益。

   ⟹ ⚠️ 我的翻译：★★ 把模型当成一个【新品种的用户】来做产品设计。
      它不会用鼠标，看不见颜色，记性有限（上下文窗口），
      但它读文本极快，且不会累。
      ⟹ ★★★ 界面得按这个特点重做。

3.2 ✅ 论文给出的四条 ACI 设计原则

★★★ 这四条是论文正文明确编号列出的（★ 逐字节选 + 中文翻译）：

   ┌─ 原则 1 ────────────────────────────────────────────────┐
   │ "Actions should be simple and easy to understand         │
   │  for agents."                                            │
   │ ⟹ ★★ 动作要简单、模型容易理解。                        │
   │                                                          │
   │ ✅ 论文的理由：很多 bash 命令的文档有几十个选项。       │
   │    "Simple commands with a few options and concise      │
   │     documentation are easier for agents to use"          │
   │ ⟹ 参数少、文档短的命令，模型更容易用对。               │
   └──────────────────────────────────────────────────────────┘
   ┌─ 原则 2 ────────────────────────────────────────────────┐
   │ "Actions should be compact and efficient."               │
   │ ⟹ ★★★ 动作要紧凑高效——重要操作要合并成尽量少的动作。  │
   │                                                          │
   │ ✅ 论文的反面教材原话：                                  │
   │    "A poor design would therefore have many simple       │
   │     actions that must be composed across multiple turns" │
   │ ⟹ ★★ 糟糕的设计 = 一堆小动作，必须跨好几轮才能拼出     │
   │    一个有意义的操作。                                    │
   └──────────────────────────────────────────────────────────┘
   ┌─ 原则 3 ────────────────────────────────────────────────┐
   │ "Environment feedback should be informative but concise."│
   │ ⟹ ★★ 环境反馈要有信息量，但要简洁。（02 章讲过）        │
   └──────────────────────────────────────────────────────────┘
   ┌─ 原则 4 ────────────────────────────────────────────────┐
   │ "Guardrails mitigate error propagation and hasten        │
   │  recovery."                                              │
   │ ⟹ ★★★ 护栏能抑制错误蔓延、加快恢复。                   │
   │                                                          │
   │ ✅ 论文举的例子：在编辑命令里内置一个语法检查器，       │
   │    自动发现模型改出来的语法错误。                        │
   └──────────────────────────────────────────────────────────┘

   ★ 名词：guardrail（护栏）
     ⟹ 在工具内部加的自动检查：★★ 模型做了个明显错误的操作，
        工具【当场拦下来并告诉它错在哪】，而不是默默执行。

3.3 ✅ SWE-agent 实际给了模型哪些工具

★★ 论文 §3 逐个描述了它的工具集。这不是猜的，是论文原文：

   ┌─ 搜索与导航 ─────────────────────────────────────────┐
   │  find_file    ⟹ 按【文件名】在仓库里找               │
   │  search_file  ⟹ 在【一个文件】里找字符串             │
   │  search_dir   ⟹ 在【一个目录】里找字符串             │
   │                                                       │
   │  ✅ 关键设计：★★★ 搜索结果最多返回 50 条。            │
   │     论文原话："The search commands return at most 50  │
   │     results for each search query; if a search        │
   │     exceeds this number, we do not report the results │
   │     and instead suggest that the agent write a more   │
   │     specific query."                                  │
   │  ⟹ 超过 50 条就【一条都不给】，改为提示它"把查询写细"│
   └───────────────────────────────────────────────────────┘
   ┌─ 文件查看器（file viewer）───────────────────────────┐
   │  open         ⟹ 打开一个文件                         │
   │  scroll_down  ⟹ 视窗往下挪                           │
   │  scroll_up    ⟹ 视窗往上挪                           │
   │  goto         ⟹ 直接跳到某一行                       │
   │                                                       │
   │  ✅ 关键设计：★★★ 一次只显示【最多 100 行】。         │
   │  ✅ 每次显示还带上：完整文件路径、总行数、            │
   │     上面省略了多少行、下面省略了多少行、每行的行号。 │
   └───────────────────────────────────────────────────────┘
   ┌─ 文件编辑器（file editor）───────────────────────────┐
   │  create       ⟹ 新建文件                             │
   │  edit         ⟹ ★★★ 三个参数：起始行、结束行、新内容 │
   │                  一步把这段行整体换掉                │
   │                                                       │
   │  ✅ 关键设计一：改完【自动重新显示】改后的文件内容。  │
   │     论文原话："the file viewer automatically displays │
   │     the updated content, helping the agent observe    │
   │     the effects of its edit immediately without       │
   │     invoking additional commands."                    │
   │                                                       │
   │  ✅ 关键设计二：★★★ 内置语法检查（linter）。          │
   │     论文原话："Invalid edits are discarded, and the   │
   │     agent is asked to try editing the file again."    │
   │  ⟹【非法的编辑直接丢弃，不写进文件】，让它重改。      │
   └───────────────────────────────────────────────────────┘
   ┌─ 出口 ───────────────────────────────────────────────┐
   │  submit       ⟹ 交卷                                 │
   └───────────────────────────────────────────────────────┘

   ⟹ ★★ 除此之外，模型还能直接用普通 Linux 命令（python、pytest 等）。
      ✅ 论文原话："Built atop the Linux shell, SWE-agent also allows
         access to common Linux commands and utilities when needed."

3.4 ⭐⭐ 核心证据：消融实验表

★★★ 这是全目录最重要的一张表。✅ SWE-agent 论文 Table 3，
全部在 SWE-bench Lite（300 题）+ GPT-4 Turbo 上跑出来，
模型完全不变，只换界面。带 ★ 的是 SWE-agent 的默认配置。

   ┌───────────────┬────────────────────────┬────────┬────────┐
   │ 换掉哪一块     │ 换成什么                │ 分数   │ 变化   │
   ├───────────────┼────────────────────────┼────────┼────────┤
   │               │ ★ edit 带语法检查       │ 18.0   │ 基准   │
   │ 编辑器        │ edit 不带语法检查       │ 15.0   │ ↓ 3.0  │
   │               │ ★★★ 完全没有 edit 命令  │ 10.3   │ ↓ 7.7  │
   ├───────────────┼────────────────────────┼────────┼────────┤
   │               │ ★ 汇总式搜索            │ 18.0   │ 基准   │
   │ 搜索          │ ★★★ 逐条翻页式搜索      │ 12.0   │ ↓ 6.0  │
   │               │ 完全没有搜索命令        │ 15.7   │ ↓ 2.3  │
   ├───────────────┼────────────────────────┼────────┼────────┤
   │               │ 一次显示 30 行          │ 14.3   │ ↓ 3.7  │
   │ 文件视窗大小  │ ★ 一次显示 100 行       │ 18.0   │ 基准   │
   │               │ ★★★ 一次显示整个文件    │ 12.7   │ ↓ 5.3  │
   ├───────────────┼────────────────────────┼────────┼────────┤
   │               │ ★ 只保留最近 5 条观察   │ 18.0   │ 基准   │
   │ 上下文管理    │ ★★★ 保留全部历史        │ 15.0   │ ↓ 3.0  │
   │               │ 不给示范                │ 16.3   │ ↓ 1.7  │
   └───────────────┴────────────────────────┴────────┴────────┘

   ⟹ 🔑🔑🔑 ★★★ 请盯着这张表看三十秒。

      同一个 GPT-4 Turbo。同样 300 道题。同样的判卷方式。
      ★★ 只因为"给模型看的界面"不同，分数从 10.3 到 18.0。

      ⟹ 这个跨度（7.7 个点），比很多"新一代模型"的提升还大。

3.5 表里最反直觉的三行

① ★★★ 逐条翻页式搜索（12.0），比【完全没有搜索】（15.7）还差

✅ 论文解释得非常具体（★ 逐字）：

"when given a large number of search results, agents tend to look through every
match exhaustively, calling next until each result has been inspected. This
inefficient behavior can exhaust an agent's cost budget or context window"

⟹ 给了一大堆搜索结果时，agent 倾向于挨个看完，一直按 next 直到看完每一条。这种低效行为会耗尽它的成本预算或上下文窗口。

   ⟹ 🔑🔑 ★★★ 这条给新手的教训最大：
      【给模型一个"能用但用起来很笨"的工具，
        比不给它这个工具还糟。】

   ⚠️ 我的解读：因为模型没有"算了不看了"这种不耐烦。
      人翻到第 5 页会放弃，模型会老老实实翻完 15 页——
      ★★ 然后预算就没了。

② ★★★ 一次给整个文件（12.7），比一次只给 100 行（18.0）差 5.3

   ⟹ 🔑 "给它看得越多越好"是错的。
   ⚠️ 我的解读：整个文件动辄上千行，一次塞进去会
      ① 挤占上下文，② 让相关的那几行淹没在噪音里。
      ★★ 但也不能太少——30 行只有 14.3，比 100 行还差 3.7。
   ⟹ ★★★ 两头都掉。中间有个甜点区。

③ ★★★ 保留全部历史（15.0），比只留最近 5 条（18.0）差 3.0

   ⟹ 这一行留到 [04 章] 专门讲，那是整个上下文管理的立论依据。

3.6 ✅ 护栏值多少钱：编辑失败的实测数据

★★ 论文 §5.2 给了一组非常具体的数字，说明"改错了之后能不能爬起来"有多要命：

   ✅ 全部来自 SWE-agent w/ GPT-4 Turbo 在 SWE-bench 全量 2294 题上的轨迹：

   ① ★★ 2294 道题里，1185 道（51.7%）的轨迹中出现过至少一次失败的编辑。
      ⟹ 一半以上的任务，模型都改错过。

   ② ★★★ 任何一次编辑尝试，最终改成功的概率是 90.5%。
      ★★★ 但只要失败过一次，这个概率就掉到 57.2%。

   ⟹ 🔑🔑🔑 ★★★ 这就是"护栏"存在的全部理由：

      ┌────────────────────────────────────────────────────┐
      │ 没有语法检查 → 错误的编辑被真写进文件               │
      │   → 模型下一步看到的是【已经被自己改坏的代码】      │
      │   → 它基于错误的状态继续改                          │
      │   → ★★★ 错误滚雪球（论文叫 cascading errors）      │
      └────────────────────────────────────────────────────┘

      ⟹ 有了语法检查：非法编辑【当场丢弃、不落盘】，
         并把错误信息 + 改前改后对比一起给它看。
      ✅ 代价换来的收益：15.0 → 18.0，值 3 个点。

3.7 ✅ 失败到底失败在哪：失败模式分布

★★ 论文 Figure 8 用 GPT-4o 自动给"没解决"的轨迹分类
（✅ 论文说明：人工校验集上机器判断与作者判断的一致率是 87%）：

失败类型 占比
Incorrect Implementation（改错了） 39.9%
Failed to Recover from Edit（编辑失败后没爬起来） 23.4%
Failed to Find Edit Location（没找到该改哪一行） 12.9%
Overly Specific Implementation（改得太特化，只对这个例子有效） 12.1%
Gave Up Prematurely（过早放弃） 4.8%
Failed to Find Relevant File（没找到相关文件） 2.4%
Can't Reproduce（复现不出问题） 2.4%
Ran Out of Time（超时） 2.0% 
   ⟹ 🔑🔑 读这张表要读两件事：

   ① ★★★ 52.0%（39.9 + 12.1）是【方案本身不对】。
      ✅ 论文原话确认了这个加总："about half (52.0%) of unresolved
         instances fall into the Incorrect Implementation or
         Overly Specific Implementation categories"
      ⟹ ★★ 这部分脚手架帮不上忙，是模型能力问题。

   ② ★★★ 但 23.4% 是【编辑失败后爬不起来】——第二大类。
      ⟹ ★★ 这部分【纯粹是脚手架问题】。
      ⟹ 🔑 这就是为什么 §3.6 那个护栏值 3 个点。

   ③ ⚠️ 注意 "Ran Out of Time" 只有 2.0%。
      ★★★ 和 02 章那句"加预算不会明显提分"完全对上了。

   │ 搜索             │ ✅ 有           │ ✅ 有（Grep/Glob） │

   ⟹ ★★★ 多出来的四项，全都不是"更会写代码"，

   ⚠️ 这是我的判断：脚手架这三年的进化方向，
      是从"让模型能动手"变成"让模型能管好自己"。

3.9 本章总结

    🔑 七条带走：

    ① ★★★ ACI = 专门为模型（而不是为人）设计的操作界面。
       ⟹ 模型是一类新的终端用户，需要重做界面。
    ② ★★ ✅ 四条设计原则：动作简单 / 动作紧凑 / 反馈简洁有料 / 加护栏。
    ③ ★★★ ✅ 消融表：同一个模型，只换界面，10.3 ~ 18.0。
    ④ ★★★ ✅ 逐条翻页式搜索(12.0) 比【完全没搜索】(15.7) 还差。
       ⟹ 🔑 难用的工具，比没有工具更糟。
    ⑤ ★★★ ✅ 一次给 100 行(18.0) > 给 30 行(14.3) > 给整个文件(12.7)。
       ⟹ 🔑 给得越多越好是错的，两头都掉。
    ⑥ ★★★ ✅ 编辑失败后成功率从 90.5% 掉到 57.2%；
       失败模式里 23.4% 是"编辑失败后爬不起来"。⟹ 护栏值 3 个点。
    ⑦ ★★ ✅ 2026 年的工具集比 2024 年多的是【组织能力】：
       任务清单、子 agent、反问用户——不是更会写代码。
