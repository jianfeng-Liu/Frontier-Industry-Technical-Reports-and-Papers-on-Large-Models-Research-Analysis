04 · 上下文管理：主动扔东西是一项核心技术

⭐⭐ 这一章讲脚手架里最"不像功能"的一块。
结论提前说：★★★ ✅ 把全部历史留给模型，SWE-bench Lite 分数
从 18.0 掉到 15.0。留着不是免费的。

4.1 名词：上下文窗口，以及它为什么必然不够用

   ★ 名词：context window（上下文窗口）
     ⟹ 模型一次能"看见"的文字总量上限，按 token（词元）计。
     ★★ 超出这个量，最早的内容就必须被丢掉，否则请求会直接报错。

   ★ 名词：token（词元）
     ⟹ 模型处理文本的最小单位。⚠️ 粗略换算：
        英文约 1 个 token ≈ 0.75 个单词；中文约 1 个汉字 ≈ 1~2 个 token。

★★★ 为什么"窗口再大也不够"？✅ SWE-bench 论文 Table 1 给了原因（★ 逐字数据）：

SWE-bench 一道题里的仓库 均值 最大值
非测试文件数 3,010 个 5,890 个
非测试代码行数 438K 行 886K 行
issue（问题描述）长度 195.1 词 4,477 词
标准答案改了几行 32.8 行 5,888 行

✅ 论文自己下的结论（★ 逐字）：

"codebases consist of many more tokens (438K lines on average) than can typically
be fit into an LMs context window."

⟹ 代码库的 token 量（平均 438K 行）远超模型上下文窗口通常能装下的量。

   ⟹ 🔑🔑 ★★★ 请注意上表最刺眼的对比：

      仓库有 438,000 行  ──▶  但答案平均只改 32.8 行。

      ⟹ ★★ 也就是说，99.99% 的代码是【噪音】。
      ⟹ 🔑 上下文管理的全部任务就是：
         【在有限的窗口里，尽量装那 32.8 行附近的东西。】

4.2 ✅ SWE-agent 的做法：只保留最近 5 条观察

★★★ 论文 §3 "Context management" 一节，把做法写得很死（★ 逐字）：

"To further improve context relevance, observations preceding the last 5 are each
collapsed into a single line, shown in Figure 31. By removing most content from
prior observations, we maintain essential information about the plan and action
history while reducing unnecessary context, which allows for more interaction
cycles and avoids showing outdated file information."

⟹ 为进一步提升上下文相关性，最近 5 条之前的观察，每条都被折叠成一行。通过移除此前观察的大部分内容，我们保留了关于计划和动作历史的关键信息，同时减少了不必要的上下文，这让交互轮次可以更多，也避免了展示过时的文件信息。

   ⟹ ★★ 拆开看，这一句话里藏了三个理由：

   ┌──────────────────────────────────────────────────────────┐
   │ ① 省地方  ⟹ 腾出的空间可以多转几轮循环                   │
   │ ② ★★ 保留骨架 ⟹ 折叠成"一行"，不是删掉。               │
   │    模型仍知道"我第 3 步打开过 X 文件"，只是看不到内容了  │
   │ ③ ★★★ 避免过时信息 ⟹ 这一条最关键，见下方              │
   └──────────────────────────────────────────────────────────┘

   ⟹ 🔑🔑🔑 ★★★ 第 ③ 条为什么最关键：

      第 3 步：模型 open 了 foo.py，看到第 100 行是 `return None`
      第 7 步：模型 edit 了 foo.py，把第 100 行改成了 `return x`
      第 9 步：★★ 如果第 3 步的旧内容还留在上下文里——
              模型的"记忆"里，同一个文件的同一行有【两个互相矛盾的版本】。

      ⟹ ★★★ 这不是"浪费空间"，这是【喂给它错误信息】。

✅ 实测代价（论文 Table 3，SWE-bench Lite + GPT-4 Turbo）：

上下文策略 分数
★ 只保留最近 5 条观察 18.0
★★★ 保留全部历史 15.0（↓ 3.0） 
   ⟹ 🔑🔑 ★★★ 这就是本章的立论：
      【主动扔掉信息，比留着更好。而且值 3 个点。】

   ⚠️ 对新手最反直觉的一点：
      你会本能地觉得"多给模型一点信息总没坏处"。
      ★★ 这个实验说明不是——旧信息会【主动骗它】。

★★ 顺带，02 章讲过的那条也属于同一类设计：

   ✅ "Once received, all past error messages except the first are omitted."
   ⟹ 格式报错重试成功后，除第一条外的所有报错都从上下文里删掉。
   ⟹ ★★ 同一个思路：【已经没用的东西，主动清掉。】

4.3 三种上下文管理策略

⚠️ 这个三分法是我对公开实现的归纳，不是某篇论文的分类。但每一格都有 ✅ 实例。

   ┌─ 策略① 截断 / 折叠（truncate）───────────────────────┐
   │  ★ 做法：超过 N 条的旧内容，直接删或压成一行。        │
   │  ✅ 实例：SWE-agent 的"最近 5 条观察"                 │
   │  ✅ 实例：Codex 的 tool_output_token_limit            │
   │          （单条工具输出在历史里能占多少 token 的预算）│
   │  ⟹ ★★ 优点：便宜、确定。缺点：★★★ 信息真的没了。     │
   └───────────────────────────────────────────────────────┘
   ┌─ 策略② 压缩总结（compact）───────────────────────────┐
   │  ★★ 做法：快满时，【再调一次模型】，让它把前面的      │
   │     对话总结成一段短文，用总结替换掉原文。            │
   │  ✅ 实例：Claude Code 的 auto-compact（自动压缩）     │
   │  ✅ 实例：Codex 的 model_auto_compact_token_limit     │
   │  ⟹ ★★ 优点：保留语义。                               │
   │     缺点：★★★【压缩本身就是一次大请求，很贵】        │
   └───────────────────────────────────────────────────────┘
   ┌─ 策略③ 隔离（isolate）──────────────────────────────┐
   │  ★★★ 做法：把会产生大量垃圾输出的活，                │
   │     丢给一个【独立上下文】的子 agent 去做，           │
   │     只把它的结论拿回来。                              │
   │  ✅ 实例：Claude Code 的 subagent（子 agent）         │
   │  ⟹ ★★★ 优点：主对话完全不脏。                       │
   │     缺点：子 agent 看不到主对话的上下文。            │
   └───────────────────────────────────────────────────────┘

4.4 ✅ 策略②实例：Claude Code 的 auto-compact

★★ 以下全部来自 Claude Code 官方文档（costs 页），✅ 逐字引用：

"Claude Code automatically optimizes costs through prompt caching, which reduces
costs for repeated content like system prompts, and auto-compaction, which
summarizes conversation history when approaching context limits."

⟹ Claude Code 通过两个机制自动优化成本：提示词缓存（对系统提示词这类重复内容降费），以及自动压缩（在接近上下文上限时总结对话历史）。

   ★ 名词：auto-compact（自动压缩）
     ⟹ 上下文快满时，脚手架自动把前面的对话总结成一段短文，
        用总结替换原文，腾出空间继续干。

   ★ 名词：prompt caching（提示词缓存）
     ⟹ 每一轮都要把【整段对话】重新发给模型（模型没有记忆）。
        缓存的作用是：重复的那部分不必重新计算，按更便宜的价格算。
     ⚠️ 注意它不省 token，只省钱。

✅ 文档里还有一句，把"为什么长会话越来越贵"讲得很直白（★ 逐字）：

"Claude Code sends your full conversation with every request, and each time Claude
uses tools it sends another request carrying that batch of tool results."

⟹ Claude Code 每次请求都会把你的完整对话发过去；而且 Claude 每用一次工具，就会再发一次请求，把那批工具结果一起带上。

   ⟹ 🔑🔑 ★★★ 这句话解释了 agent 为什么这么贵：

      一个任务转 20 轮 = 发出 20 次请求，
      第 20 次请求里装着前 19 轮的【全部内容】。
      ⟹ ★★ 成本不是线性的，是【接近平方级】的。

   ⟹ 这也是为什么"折叠旧观察"能省这么多——
      省的不是一次，是【后面每一次请求都省】。

✅ 文档给的可操作项（★ 逐字工具名）：

手段 做什么
/clear 换不相干的任务时清空重开
/compact 手动触发压缩
/compact <指令> ★★ 压缩时告诉它保留什么。文档例子：/compact Focus on code samples and API usage
CLAUDE.md 里写 # Compact instructions ★★ 把压缩偏好固化到项目里
/context 看现在是什么占了地方

4.5 ✅ 策略③实例：Claude Code 的子 agent

★★★ 官方文档 sub-agents 页，把上下文隔离说得很明确（✅ 逐字）：

"Each subagent runs in its own context window with a custom system prompt,
specific tool access, and independent permissions."

⟹ 每个子 agent 在它自己的上下文窗口里运行，有自己的系统提示词、特定的工具权限和独立的许可设置。

"Each subagent starts with a fresh, isolated context window. It doesn't see your
conversation history, the skills you've already invoked, or the files Claude has
already read."

⟹ 每个子 agent 从一个全新的、隔离的上下文窗口开始。它看不到你的对话历史、你已经调用过的技能、或 Claude 已经读过的文件。

   ⟹ 🔑🔑 ★★★ 典型用法（✅ 文档原话的场景）：
      "Use one when a side task would flood your main conversation with search
       results, logs, or file contents you won't reference again"
      ⟹【当一个支线任务会用搜索结果、日志、或你不会再看的文件内容
         淹没你的主对话时，用一个子 agent。】

   ┌────────────────────────────────────────────────────────┐
   │ 不用子 agent：                                          │
   │   主对话 ──▶ 跑测试 ──▶ 3000 行日志涌进主上下文 💀      │
   │                                                        │
   │ 用子 agent：                                            │
   │   主对话 ──▶ 派一个子 agent ──▶ 它自己那边收 3000 行    │
   │           ◀── 只回来一句"有 2 个测试挂了，在 X 和 Y" ✅ │
   └────────────────────────────────────────────────────────┘

★★ 但文档也明确写了它的代价（✅ 逐字，文档里是一条 Warning）：

"When subagents complete, their results return to your main conversation. Running
many subagents that each return detailed results can consume significant context."

⟹ 子 agent 完成时，结果会回到你的主对话。如果跑很多子 agent、每个都返回详细结果，一样会吃掉大量上下文。

   ⟹ ★★ 🔑 隔离不是免费的：
      ① 返回值还是会进主上下文
      ② ★★★ 子 agent 看不到主对话，所以它可能【重复做已经做过的事】
      ③ ✅ 文档另一处："a subagent's context window is sized by its own
         model" ⟹ 派给小模型，窗口也跟着变小

4.6 ✅ Codex 这一块的配置面

★★ Codex 是把上下文管理做成配置项暴露出来的，这些名字在官方 config-reference 文档里可查：

配置项（config.toml 里） 类型 / 取值 作用
model_context_window 数字 当前模型可用的上下文 token 数
model_auto_compact_token_limit 数字 ★★★ 到多少 token 触发自动压缩；不设则用每个模型的默认值
model_auto_compact_token_limit_scope total | body_after_prefix ★★ 上面那个阈值是量【整个上下文】(total，默认) 还是只量【固定前缀之后新长出来的部分】
compact_prompt 字符串 ★★ 直接替换掉压缩用的提示词
experimental_compact_prompt_file 路径 同上，但从文件读（实验特性）
tool_output_token_limit 数字 ★★★ 单条工具输出在历史里能留多少 token

★★ 另外 Codex 的钩子（hook）事件里，有两个是专门给压缩用的：PreCompact（压缩前）和 PostCompact（压缩后）。

   ⟹ 🔑🔑 ★★★ 请特别注意 model_auto_compact_token_limit_scope 这一项。

      它区分【总量】和【前缀之后的增量】——
      ⚠️ 我的解读：因为系统提示词 + 工具定义 + 项目说明这一大坨"前缀"
      是每轮都一样的，它被提示词缓存住了，便宜。
      ★★ 真正在长的是后面那截。按哪个口径算阈值，
      直接决定【多久压缩一次】，也就直接决定成本和信息损失。

   ⟹ ★★★ 这就是本目录 README 说的"闭源产品公开的是【配置面】"：
      你看不到它压缩算法怎么写的，
      但你能看到它把哪些旋钮交到了你手上——
      ★★ 而这些旋钮，每一个都会动分数。

4.7 三家做法对照

   ┌────────────┬──────────────┬───────────────┬──────────────┐
   │            │ SWE-agent    │ Claude Code   │ Codex        │
   ├────────────┼──────────────┼───────────────┼──────────────┤
   │ 截断/折叠  │ ✅ 最近5条    │ ⚠️ 未公开细节 │ ✅ tool_output│
   │            │   其余折一行 │               │  _token_limit│
   ├────────────┼──────────────┼───────────────┼──────────────┤
   │ 压缩总结   │ ❌ 没有       │ ✅ auto-compact│ ✅ model_auto│
   │            │              │  + /compact   │  _compact_*  │
   ├────────────┼──────────────┼───────────────┼──────────────┤
   │ 子agent隔离│ ❌ 没有       │ ✅ subagent    │ ✅ 有 subagents│
   │            │              │  独立上下文窗口│  文档页      │
   ├────────────┼──────────────┼───────────────┼──────────────┤
   │ 可查证程度 │ ✅✅ 论文+源码│ ✅ 行为/⚠️实现 │ ✅ 配置面    │
   └────────────┴──────────────┴───────────────┴──────────────┘

   ⟹ ★★ 一句话看懂这张表：
      2024 年只有【截断】；2026 年的产品是【截断 + 压缩 + 隔离】三件套。

4.8 本章总结

    🔑 六条带走：

    ① ★★★ ✅ 仓库均 438K 行，答案均改 32.8 行。
       ⟹ 上下文管理的任务 = 在有限窗口里装那 32.8 行附近的东西。

    ② ★★★ ✅ SWE-agent：只留最近 5 条观察 = 18.0，
       留全部历史 = 15.0。⟹ 主动扔，值 3 个点。

    ③ ★★★ 🔑 扔的最大理由不是省地方，是【旧信息会骗它】——
       文件改过之后，旧版本还留在上下文里就是错误信息。

    ④ ★★ 三种策略：截断（便宜、真丢信息）/ 压缩（保语义、贵）/
       隔离（主对话干净、但子 agent 是瞎的）。

    ⑤ ★★★ ✅ "每次请求都发完整对话" ⟹ agent 成本接近平方级增长。
       ⟹ 折叠旧内容省的是【后面每一次请求】。

    ⑥ ★★ ✅ 闭源产品公开的是【旋钮】不是【算法】：
       Codex 的 model_auto_compact_token_limit_scope 这种配置项，
       名字和取值可查，实现查不到。
