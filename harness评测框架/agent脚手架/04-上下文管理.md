# 04 · 上下文管理：主动扔东西是一项核心技术

> ⭐⭐ 这一章讲脚手架里最"不像功能"的一块。
> 结论提前说：★★★ ✅ 把全部历史留给模型，SWE-bench Lite 分数
> 从 **18.0 掉到 15.0**。**留着不是免费的。**

## 4.1 名词：上下文窗口，以及它为什么必然不够用

```
   ★ 名词：context window（上下文窗口）
     ⟹ 模型一次能"看见"的文字总量上限，按 token（词元）计。
     ★★ 超出这个量，最早的内容就必须被丢掉，否则请求会直接报错。

   ★ 名词：token（词元）
     ⟹ 模型处理文本的最小单位。⚠️ 粗略换算：
        英文约 1 个 token ≈ 0.75 个单词；中文约 1 个汉字 ≈ 1~2 个 token；
        ⚠️ 一行 Python 代码大致 10~15 个 token。
     ⚠️⚠️ 不同模型用不同的分词器，token 数【互相不可比】。
        ✅ SWE-agent 论文专门加了一条脚注说这件事：
           "Token counts for different models are not directly comparable
            since they use different tokenizers."
```

★★★ 为什么"窗口再大也不够"？✅ SWE-bench 论文 Table 1 给了原因（★ 逐字数据）：

| SWE-bench 一道题里的仓库 | 均值 | 最大值 |
|---|---|---|
| 非测试文件数 | **3,010 个** | 5,890 个 |
| 非测试代码行数 | **438K 行** | 886K 行 |
| issue（问题描述）长度 | 195.1 词 | 4,477 词 |
| 标准答案改了几行 | **32.8 行** | 5,888 行 |

✅ 论文自己下的结论（★ 逐字）：

> "codebases consist of many more tokens (438K lines on average) than can typically
> be fit into an LMs context window."

⟹ **代码库的 token 量（平均 438K 行）远超模型上下文窗口通常能装下的量。**

```
   ⟹ 🔑🔑 ★★★ 请注意上表最刺眼的对比：

      仓库有 438,000 行  ──>  但答案平均只改 32.8 行。

      ⟹ ★★ 1 − 32.8/438000 = 99.9925%，
         也就是说 99.99% 的代码和这道题的改动无关。
      ⟹ 🔑 上下文管理的全部任务就是：
         【在有限的窗口里，尽量装那 32.8 行附近的东西。】
```

```
   ⚠️⚠️ 但"99.99% 是噪音"这句话是【修辞】，不能当工程指标用：

      ★★ 它不等于"只需要给模型看 32.8 行"。
      ⟹ 要【找到】那 32.8 行，模型得先看过调用方、看过类定义、
         看过测试、看过报错 —— 这些都不在那 32.8 行里。
      ✅ 旁证：论文 Table 11 发现 agent 交出来的补丁
         【比人写的标准答案更大】（加的行更多、改的区块更多），
         ★ 论文把主要原因归给"额外写的复现代码"。
      ⟹ ★★★ 所以准确的说法是：
         【要看的远多于 32.8 行，但远少于 438,000 行。
           上下文管理就是在这两个数之间找落点。】
```

★ 顺带把"窗口有多大"这件事量化一下，才知道这个矛盾有多硬：

| 口径 | 值 | ★ 折算 |
|---|---|---|
| ✅ GPT-4 Turbo 窗口（论文 §4 写明） | 128K token | 约 **9,800 行**代码 |
| ✅ Claude 3 Opus 窗口（同上） | 200K token | 约 15,400 行 |
| ✅ DeepSeek-V4 跑分时设的上限（07 章） | 512K token | 约 39,400 行 |
| **一个 SWE-bench 仓库（均值）** | ⚠️ 约 **5.7M token** | **438,000 行** |

```
   ⟹ ★★★ 就算 512K 的窗口，也只装得下一个平均仓库的 9%。
   ⚠️ 上面的"行 ↔ token"换算按 13 token/行 粗估，不是实测。
   ⟹ 🔑 结论：★★ 这不是"等窗口变大就解决了"的问题。
      窗口涨了 4 倍，差距还是两个数量级。
```

## 4.2 ✅ SWE-agent 的做法：只保留最近 5 条观察

★★★ 论文 §3 "Context management" 一节，把做法写得很死（★ 逐字）：

> "To further improve context relevance, observations preceding the last 5 are each
> collapsed into a single line, shown in Figure 31. By removing most content from
> prior observations, we maintain essential information about the plan and action
> history while reducing unnecessary context, which allows for more interaction
> cycles and avoids showing outdated file information."

⟹ **为进一步提升上下文相关性，最近 5 条之前的观察，每条都被折叠成一行。通过移除此前观察的大部分内容，我们保留了关于计划和动作历史的关键信息，同时减少了不必要的上下文，这让交互轮次可以更多，也避免了展示过时的文件信息。**

★★ 拆开看，这一句话里藏了三个理由，而且**它们的重要程度不一样**：

| # | 理由 | ✅ 论文的原词 | ★ 它在说什么 | 重要度 |
|---|---|---|---|---|
| ① | **省地方** | *"reducing unnecessary context, which allows for more interaction cycles"* | 腾出的空间可以多转几轮循环 | ★ 一般 |
| ② | **保留骨架** | *"we maintain essential information about the plan and action history"* | ★★ 折叠成"一行"，**不是删掉**。模型仍知道"我第 3 步打开过 X 文件"，只是看不到内容了 | ★★ 重要 |
| ③ | **避免过时信息** | *"avoids showing outdated file information"* | ★★★ 见下方 | ★★★ 最重要 |

```
   ⟹ 🔑🔑🔑 ★★★ 第 ③ 条为什么最关键 ——
      直接用 [02 章 §2.2b](02-agent循环怎么转.md) 那条轨迹来看：

      第 2 轮：模型 open 了 pvsystem.py，看到 412 行是
               irradiance.aoi(self.surface_azimuth, self.surface_tilt, ...)
      第 4 轮：模型 edit 了 412 行，自动回显里它已经是
               irradiance.aoi(self.surface_tilt, self.surface_azimuth, ...)
      第 5 轮：★★ 如果第 2 轮的旧内容还留在上下文里——
               模型的"记忆"里，同一个文件的同一行有【两个互相矛盾的版本】。

      ⟹ ★★★ 这不是"浪费空间"，这是【喂给它错误信息】。
      ⟹ 🔑 而折叠之后，第 2 轮那条观察变成一行
         "(Open file: pvlib/pvsystem.py)" ——
         ★★ 骨架留着（它知道自己看过这个文件），
         ★★★ 但那份【已经过时的内容】没了。
```

✅ **实测代价**（论文 Table 3，SWE-bench Lite 300 题 + GPT-4 Turbo，口径同 [03 章 §3.4](03-工具集与ACI.md)）：

| 上下文策略 | ✅ 论文里的设定名 | 分数 | ★ 约几道题（共 300） |
|---|---|---|---|
| ★ 只保留最近 5 条观察 | `Last 5 Obs.` | **18.0** | 54 道 |
| ★★★ 保留全部历史 | `Full history` | **15.0（↓ 3.0）** | 45 道（少 9 道） |

```
   ⟹ 🔑🔑 ★★★ 这就是本章的立论：
      【主动扔掉信息，比留着更好。而且值 3.0 个点。】

   ⚠️ 对新手最反直觉的一点：
      你会本能地觉得"多给模型一点信息总没坏处"。
      ★★ 这个实验说明不是——旧信息会【主动骗它】。

   ⚠️ 必须跟的限定（和 03 章 §3.4 ③ 是同一条）：
      ★★ 3.0 个点在 300 题上等于 9 道题，
      ✅ 而基线重跑 6 遍的极差是 4 道题（1.34 个百分点）。
      ⟹ ★ 所以这个差异压过了重跑噪声，但别把"3.0"当成精确值。
```

★★ 顺带，[02 章 §2.3](02-agent循环怎么转.md) 讲过的那条也属于同一类设计：

```
   ✅ "Once received, all past error messages except the first are omitted."
   ⟹ 格式报错重试成功后，除第一条外的所有报错都从上下文里删掉。
   ⟹ ★★ 同一个思路：【已经没用的东西，主动清掉。】
   ⟹ 🔑 注意这两条的共同点：★★★ 它们扔掉的都是
      【已经被后来的事实取代了的信息】，不是"不重要的信息"。
```

## 4.3 三种上下文管理策略

⚠️ 这个三分法是我对公开实现的归纳，不是某篇论文的分类。但每一格都有 ✅ 实例。

| 策略 | ★ 做法 | ✅ 实例 | ★★ 优点 | ★★★ 缺点 |
|---|---|---|---|---|
| **① 截断 / 折叠**<br>（truncate / fold） | 超过 N 条的旧内容，直接删或压成一行 | ✅ SWE-agent 的 `Last 5 Obs.`（最近 5 条之外每条折一行）<br>✅ Codex 的 `tool_output_token_limit`（单条工具输出在历史里能占多少 token） | 便宜、确定、不用再调一次模型 | ★★★ **信息真的没了**，而且**不可逆** |
| **② 压缩总结**<br>（compact / summarize） | 快满时**再调一次模型**，让它把前面的对话总结成一段短文，用总结替换原文 | ✅ Claude Code 的 **auto-compact** + `/compact`<br>✅ Codex 的 `model_auto_compact_token_limit` | 保留语义，比折叠记得多 | ★★★ **压缩本身就是一次大请求，很贵**；而且 ⚠️ 总结是模型写的，**可能写错或漏掉关键字符串** |
| **③ 隔离**<br>（isolate） | 把会产生大量垃圾输出的活，丢给一个**独立上下文**的子 agent 去做，只把它的结论拿回来 | ✅ Claude Code 的 **subagent**（子 agent） | ★★★ 主对话完全不脏 | 子 agent **看不到主对话的上下文**，⚠️ 可能重复做已经做过的事；⚠️ 它的返回值仍然会进主上下文 |

```
   ⟹ ★ 还有一个常被归进来的第四种，但它和上面三种不是一个层次：

   ④ 检索回填（retrieve / RAG-style）
      ★ 做法：不预先往上下文里塞，而是等模型说"我要看 X"时再去查。
      ⟹ ★★ 严格说这不是"管理已有的上下文"，而是"一开始就不放进来"。
      ✅ 实例：SWE-bench 的 RAG 基线（BM25 检索 + 一轮盲写）就是极端版。
      ⚠️ 而 agent 的搜索工具（search_dir / Grep）本质也是它 ——
         ★★★ 把"去仓库里查"这件事做成一个动作，交给模型自己决定什么时候用。
      ⟹ 🔑 这就是为什么 03 章说搜索界面值 6.0 个点：
         ★★ 搜索工具是上下文管理的【入口闸门】。
```

## 4.4 ✅ 策略②实例：Claude Code 的 auto-compact

★★ 以下全部来自 Claude Code 官方文档（`costs` 页），✅ 逐字引用。⚠️ 口径截至 **2026-08-27**，产品行为变化快，配置名和默认值可能随版本变。

> "Claude Code automatically optimizes costs through prompt caching, which reduces
> costs for repeated content like system prompts, and auto-compaction, which
> summarizes conversation history when approaching context limits."

⟹ **Claude Code 通过两个机制自动优化成本：提示词缓存（对系统提示词这类重复内容降费），以及自动压缩（在接近上下文上限时总结对话历史）。**

```
   ★ 名词：auto-compact（自动压缩）
     ⟹ 上下文快满时，脚手架自动把前面的对话总结成一段短文，
        用总结替换原文，腾出空间继续干。

   ★ 名词：prompt caching（提示词缓存）
     ⟹ 每一轮都要把【整段对话】重新发给模型（模型没有记忆，
        见 02 章 §2.1）。缓存的作用是：重复的那部分不必重新计算，
        按更便宜的价格算。
     ⚠️⚠️ ★★★ 注意它【不省 token，只省钱】。
        ⟹ 窗口该满照样满，撞上限照样撞。
        ⟹ 🔑 这是本章最容易被误解的一点：缓存解决的是【账单】，
           压缩和折叠解决的是【容量】。两件事，不能互相替代。
```

✅ 文档里还有一句，把"为什么长会话越来越贵"讲得很直白（★ 逐字）：

> "Claude Code sends your full conversation with every request, and each time Claude
> uses tools it sends another request carrying that batch of tool results."

⟹ **Claude Code 每次请求都会把你的完整对话发过去；而且 Claude 每用一次工具，就会再发一次请求，把那批工具结果一起带上。**

```
   ⟹ 🔑🔑 ★★★ 这句话解释了 agent 为什么这么贵：

      一个任务转 20 轮 = 发出 20 次请求，
      第 20 次请求里装着前 19 轮的【全部内容】。
      ⟹ ★★ 发出去的 token 总量不是线性的，是【接近平方级】的。

   ⚠️⚠️ 但"成本接近平方级"这个说法要加一个很重要的限定：

      ★★★ 【token 量】接近平方级 —— 这一条是确定的，
         §4.4b 会把它算出来。
      ⚠️ 【钱】不一定按平方涨 —— 因为那个一直在重发的"固定前缀"
         （系统提示 + 工具声明 + 项目说明）正好是缓存最擅长的部分。
      ⟹ ★★ 所以准确的说法是：
         【token 量平方级增长；钱的增长被缓存削平了一部分，
           削掉多少取决于缓存命中率和厂商折扣】。
      ⚠️ 具体折扣比例随厂商和时间变，这里不写死数字。

   ⟹ ★★ 这也是为什么"折叠旧观察"能省这么多——
      省的不是一次，是【后面每一次请求都省】。
```

✅ 文档给的可操作项（★ 逐字工具名）：

| 手段 | 做什么 |
|---|---|
| `/clear` | 换不相干的任务时清空重开 |
| `/compact` | 手动触发压缩 |
| `/compact <指令>` | ★★ 压缩时告诉它保留什么。文档例子：`/compact Focus on code samples and API usage` |
| `CLAUDE.md` 里写 `# Compact instructions` | ★★ 把压缩偏好固化到项目里 |
| `/context` | 看现在是什么占了地方 |

## 4.4b ⭐⭐⭐ 一个任务的逐轮 token 账：算到撞窗口

★★★ 本章最该花时间的一节。⚠️⚠️ **下面全部是我构造的算例，不是实测**：token 数按"英文 1 token ≈ 0.75 词、一行代码约 13 token"粗估，窗口刻意设得很小好算。★★ 用它看**结构和趋势**，不要引用任何绝对值。

### ① 设定

```
   ★ 任务：一个需要改两个文件、跑三次测试的 bug 修复，12 轮收工。

   ★ 固定前缀 P = 2,500 token（★★ 每一轮都要重发一遍）
   ├── 系统提示词          1,200
   ├── 工具声明（10 个工具）  800
   └── issue 文本            500

   ★ 上下文窗口 = 16,000 token
      ⚠️ 真实产品是 128K / 200K / 512K。
         ★★ 这里缩小到 16K，是为了让"撞墙"在 12 轮内发生、
         能手算出来。★★★ 结构和真实情况完全一样，只是刻度不同。

   ★ 三种策略并排比：
   ├── A  保留全部历史                （= 论文的 Full history）
   ├── B  折叠：最近 5 条观察留原文，更早的每条压成 25 token 一行
   │                                   （= 论文的 Last 5 Obs.）
   └── C  B ＋ 单条工具输出上限 2,000 token
                                       （= Codex 的 tool_output_token_limit）
```

### ② 这 12 轮各自产生了多少

| 轮 | 动作 | 模型输出<br>（想法+工具调用） | 工具返回（原始） | ⚠️ C 策略下截断成 |
|---|---|---|---|---|
| 1 | `search_dir` 定位 | 120 | 800 | 800 |
| 2 | `open` 文件 A（100 行） | 110 | 1,300 | 1,300 |
| 3 | `scroll_down` | 90 | 1,300 | 1,300 |
| 4 | `edit` + 自动回显 | 260 | 1,400 | 1,400 |
| **5** | **`pytest` 全量** | 100 | ⚠️ **4,000** | ★★ **2,000** |
| 6 | `open` 文件 B | 110 | 1,300 | 1,300 |
| 7 | `edit` + 自动回显 | 280 | 1,400 | 1,400 |
| **8** | **`pytest` 全量** | 100 | ⚠️ **4,000** | ★★ **2,000** |
| 9 | `search_file` | 100 | 500 | 500 |
| 10 | `edit` + 自动回显 | 260 | 1,400 | 1,400 |
| 11 | `pytest -k`（只跑相关） | 110 | 600 | 600 |
| 12 | `submit` | 80 | 40 | 40 |

### ③ ⭐⭐ 主表：每一轮那次请求要发出去多少 token

★★★ **「这一轮发出去多少」= 固定前缀 2,500 ＋ 到上一轮为止的可见历史。**

| 轮 | **A 全留**<br>发出 token | **B 折叠**<br>发出 token | **C 折叠+单条上限**<br>发出 token | ⚠️ 这一轮发生了什么 |
|---|---|---|---|---|
| 1 | 2,500 | 2,500 | 2,500 | ★ 只有固定前缀，它还没看过一行代码 |
| 2 | 3,420 | 3,420 | 3,420 | 三种策略还没分家 |
| 3 | 4,830 | 4,830 | 4,830 | |
| 4 | 6,220 | 6,220 | 6,220 | |
| 5 | 7,880 | 7,880 | 7,880 | ★ 前 5 轮的观察都在"最近 5 条"里，B 还没开始折 |
| 6 | 11,980 | 11,980 | **9,980** | ★★ 第 5 轮那 4,000 token 的 pytest 输出进来了。**C 在这里第一次省下 2,000** |
| 7 | 13,390 | 12,615 | 10,615 | ★★ B 开始折了（第 1 轮那条观察压成 25） |
| 8 | 15,070 | 13,020 | 11,020 | ⚠️ A 已经逼近 16,000 |
| **9** | ⚠️⚠️ **19,170** | **15,845** | **11,845** | ★★★ **A 在这一轮撞墙**（超窗口 3,170）。⚠️ B 只剩 **155 token** 余量 —— 因为第 5、8 轮两次 4,000 token 的 pytest 输出**同时落在"最近 5 条"里** |
| 10 | 19,770 | 15,070 | 11,070 | ★ B 缓过来了：第 5 轮那条被折掉了 |
| 11 | 21,430 | 12,755 | 10,755 | |
| 12 | 22,140 | 12,190 | 10,190 | ★★ B 和 C 都**反而在下降** |
| **12 轮合计发出** | ⚠️ **147,800** | **118,325** | ★★★ **100,325** | |
| **峰值** | ⚠️ **22,140**（撞墙） | 15,845（擦边过） | ★ **11,845**（宽裕） | |

★ 第 9 轮那三个数字可以自己验算，算式全在这里：

```
A（全留）第 9 轮 = 2,500 + 前 8 轮全部
  前 8 轮 = (120+800)+(110+1300)+(90+1300)+(260+1400)
          + (100+4000)+(110+1300)+(280+1400)+(100+4000)
          = 920+1410+1390+1660+4100+1410+1680+4100
          = 16,670
  ⟹ 2,500 + 16,670 = 19,170   ⚠️ 超出 16,000 窗口 3,170

B（折叠）第 9 轮 = 2,500 + 全部想法 + 最近 5 条观察原文 + 更早 3 条各 25
  全部想法 = 120+110+90+260+100+110+280+100 = 1,170
  最近 5 条观察 = 第 4~8 轮 = 1400+4000+1300+1400+4000 = 12,100
  更早 3 条（第 1~3 轮）= 3 × 25 = 75
  ⟹ 2,500 + 1,170 + 12,100 + 75 = 15,845   ★ 只剩 155 token

C（再加单条上限 2,000）第 9 轮
  最近 5 条观察 = 1400+2000+1300+1400+2000 = 8,100   ← 两次 pytest 各省 2,000
  ⟹ 2,500 + 1,170 + 8,100 + 75 = 11,845   ★ 宽裕
```

### ④ 🔑🔑🔑 从这张账里必须带走的六件事

```
   ① ★★★ 最终上下文很小，但【发出去的总量】大得离谱。
      A 策略最后一轮只装 19,640 token 的历史，
      但 12 轮一共发出 147,800 token —— ★★ 7.5 倍。
      ⟹ 🔑 这就是 agent 贵的全部原因。

   ② ★★★ 这个倍数随轮数【越来越大】，是平方级的。
      ★ 粗算：如果同样的节奏再走 12 轮（共 24 轮），
        A 的总量大约会到 51 万 token —— ★★ 轮数翻倍，总量变 3.5 倍。
      ⚠️ 为什么不是整 4 倍：因为固定前缀那部分（2,500 × 轮数）
         是【线性】的，它把平方项稍微拉平了一点。

   ③ ★★★ 撞墙不是"慢慢挤满"，是【某一轮突然跳上去】。
      ★★ 第 8 轮 A 还是 15,070（能过），第 9 轮直接 19,170（过不去）。
      ⟹ 🔑 原因是第 8 轮那次 pytest 吐了 4,000 token。
      ⟹ ★★★ 所以上下文爆掉的触发者，通常是【一条工具返回】，
         不是"对话太长"。⚠️ 这和直觉相反。

   ④ ★★ 折叠（B）救不了"短期内连着两次大输出"。
      ★★★ 第 9 轮 B 只剩 155 token 余量 ——
      因为第 5 轮和第 8 轮两次 4,000 token 的 pytest 输出
      【同时落在"最近 5 条"这个窗口里】。
      ⟹ 🔑 这就是为什么 Codex 除了折叠还要有
         tool_output_token_limit：★★ 两个旋钮管的是不同的事 ——
         折叠管【历史有多长】，单条上限管【单次有多大】。

   ⑤ ★★ B 和 C 的曲线在后半段是【下降】的。
      ⟹ 第 10~12 轮，发出的 token 在变少。
      ⟹ 🔑 因为大块观察陆续被折掉的速度，
         超过了新内容进来的速度。
      ⟹ ★★★ 这就是"折叠"真正的价值：它让上下文【有上界】，
         而不只是"长得慢一点"。

   ⑥ ⚠️ 固定前缀不可忽视，但它是最便宜的那部分。
      ★ 2,500 × 12 = 30,000，占 A 总量的 20%、占 C 总量的 30%。
      ⟹ ★★ 而它每轮一个字不变 ⟹ 正好是【提示词缓存】最擅长的部分。
      ⟹ 🔑 所以 §4.4 那句"钱不一定按平方涨"落在这里：
         ★★★ 平方增长的是【历史】那部分，而历史是最难缓存的
         （每轮都新增内容，前缀匹配每轮都在变长）。
```

### ⑤ ⚠️ 三种裁剪策略，各自到底丢了什么

★★★ 上面算的是"省了多少"。这一节算**代价** —— 每种策略丢掉的东西不一样，被咬的方式也不一样。

| 策略 | ★ 保留了什么 | ⚠️⚠️ 丢掉了什么 | ★★★ 什么时候会咬你 | 代价 |
|---|---|---|---|---|
| **① 截断 / 折叠** | ★★ 动作骨架：「我第 2 轮 open 过文件 A」 | 那条观察的**全部具体内容**：文件里的代码、报错全文、搜索命中列表。⚠️ **不可逆** | ★★★ 模型后来想回看文件 A 的**另一段**，但它已经看不见第 2 轮那 100 行了 ⟹ **得重新 `open` 一次，多烧一轮**<br>⚠️ 更坏的情况：它**不知道自己忘了**，于是基于那条"一行骨架"硬猜 | ★ 零（不用调模型） |
| **② 压缩总结** | ★★ 语义：「我改了 `get_aoi` 里的参数顺序，测试过了」 | ★★★ **精确的字符串**：行号 412、函数签名的确切拼写、报错码 `E999`、文件的确切路径。⚠️ 而且总结是**另一次模型调用写的**，它可能漏、可能写错 | ★★★ 模型需要精确值时：「刚才那个报错是哪一行？」—— 总结里写的是"有个缩进问题"，没有 412 这个数字 ⟹ 它只能重新去查<br>⚠️⚠️ 最坏情况：总结把一个**已经被否决的方案**写成了"我们决定这么做" ⟹ 模型照着错的方向继续 | ⚠️⚠️ **一次大请求**（要把被压缩的全部内容发过去） |
| **③ 隔离（子 agent）** | ★★ 子 agent 交回来的**结论**：「2 个测试挂了，在 X 和 Y」 | ★★★ 子 agent 看到的**全部中间过程**。主对话完全不知道它试过什么、排除过什么 | ★★ 主对话想追问"那个测试具体报什么错" ⟹ 结论里没有 ⟹ 要么再派一个（它又是瞎的），要么自己跑一遍<br>⚠️⚠️ ✅ 文档明说的坑：子 agent **看不到主对话**，所以它可能**重复做已经做过的事**（§4.5） | ★★ 一整条独立轨迹的钱 |
| **④ 检索回填** | ★ 什么都不预存，要什么现查 | ★★★ 「我该查什么」这个判断**本身**。⚠️ 检索召回不到就等于不存在 | ★★★ ✅ 实测证据最硬：SWE-bench 的 BM25 检索基线只有 **1.96%**，而把正确文件直接喂给它（oracle）是 **4.80%**（见 [评测入门 07 章 §7.9](../评测入门/07-agentic编码评测与SWE-bench.md)） | ★ 一次检索 |

```
   ⟹ 🔑🔑 ★★★ 把这张表压成一句话：

      ★★ 截断丢【细节】，压缩丢【精度】，
         隔离丢【过程】，检索丢【你不知道要查的东西】。

   ⟹ 🔑 所以现代产品是三件套一起用，不是挑一个：
      ① 截断 处理【每条工具返回别太大】
      ② 压缩 处理【历史别太长】
      ③ 隔离 处理【某一类活会产生一大堆你不想看的输出】
      ⟹ ★★ 而 ④ 检索 是入口闸门，决定【一开始放多少进来】。

   ⚠️ 一条很实用的取舍判据（这是我的归纳，不是论文结论）：
      ★★★ 后面还要【精确引用】的东西 ⟹ 不能交给压缩，
            要么留原文，要么让模型显式记到文件里。
      ★★ 后面只需要【知道做过】的东西 ⟹ 折叠就够了。
```

## 4.5 ✅ 策略③实例：Claude Code 的子 agent

★★★ 官方文档 `sub-agents` 页，把上下文隔离说得很明确（✅ 逐字）。⚠️ 口径截至 **2026-08-27**。

> "Each subagent runs in its own context window with a custom system prompt,
> specific tool access, and independent permissions."

⟹ **每个子 agent 在它自己的上下文窗口里运行，有自己的系统提示词、特定的工具权限和独立的许可设置。**

> "Each subagent starts with a fresh, isolated context window. It doesn't see your
> conversation history, the skills you've already invoked, or the files Claude has
> already read."

⟹ **每个子 agent 从一个全新的、隔离的上下文窗口开始。它看不到你的对话历史、你已经调用过的技能、或 Claude 已经读过的文件。**

```
   ⟹ 🔑🔑 ★★★ 典型用法（✅ 文档原话的场景）：
      "Use one when a side task would flood your main conversation with search
       results, logs, or file contents you won't reference again"
      ⟹【当一个支线任务会用搜索结果、日志、或你不会再看的文件内容
         淹没你的主对话时，用一个子 agent。】
```

★ 用 §4.4b 第 8 轮那次 pytest 当例子，把"用"和"不用"摆开：

```
   不用子 agent：
   ├── 主对话 --> 跑 pytest
   ├──        <-- 3,000 行日志全部涌进主上下文（约 4,000 token）
   └── ⚠️ 这 4,000 token 在接下来 5 轮里【每一轮都要重发一次】
          ⟹ ★★ 光这一条返回，就让后面 5 轮多发出约 20,000 token

   用子 agent：
   ├── 主对话 --> 派一个子 agent：「跑全量测试，只告诉我挂了哪几个」
   ├── 子 agent 那边 --> 自己收下 3,000 行日志（★★ 在它自己的窗口里）
   ├──               --> 自己读完、挑出结论
   └── 主对话 <-- 只回来一句「2 个测试挂了：test_aoi_tuple 和
                  test_aoi_scalar，都是 IndentationError at line 412」
          ⟹ ★★★ 约 40 token。主上下文【干净】
```

★★ 但文档也明确写了它的代价（✅ 逐字，文档里是一条 **Warning**）：

> "When subagents complete, their results return to your main conversation. Running
> many subagents that each return detailed results can consume significant context."

⟹ **子 agent 完成时，结果会回到你的主对话。如果跑很多子 agent、每个都返回详细结果，一样会吃掉大量上下文。**

| ⚠️ 隔离的三个代价 | 说的是什么 | ✅ / ⚠️ |
|---|---|---|
| ① **返回值还是会进主上下文** | 子 agent 返回一段 2,000 token 的"详细报告"，等于什么都没省 | ✅ 文档的 Warning 原文 |
| ② ★★★ **子 agent 是瞎的** | 它看不到主对话，所以它可能**重复做已经做过的事**（主对话第 2 轮已经 `open` 过文件 A，子 agent 会再 `open` 一次） | ✅ 文档原文："It doesn't see your conversation history..." |
| ③ **窗口大小跟着它自己的模型** | ✅ 文档另一处："a subagent's context window is sized by its own model" ⟹ 派给小模型，窗口也跟着变小 | ✅ 文档原文 |

```
   ⟹ 🔑 所以子 agent 用得好不好，全看【你让它返回什么】：

      ★★★ 好的用法：「只告诉我挂了哪几个测试，每个一行」
         ⟹ 返回 40 token，省下 4,000。
      ⚠️ 坏的用法：「把测试结果详细报告给我」
         ⟹ 返回 2,000 token，白跑一趟还多花一条轨迹的钱。

   ⟹ ★★ 这一条和 02 章 §2.4 那条设计原则是同一件事：
      ✅ "Environment feedback should be informative but concise."
      ⟹ 🔑 子 agent 的返回值，就是主对话眼里的"环境反馈"。
```

## 4.6 ✅ Codex 这一块的配置面

★★ Codex 是把上下文管理做成**配置项**暴露出来的，这些名字在官方 `config-reference` 文档里可查。⚠️⚠️ 口径截至 **2026-08-27**：★★ **配置项名、默认值、取值枚举都可能随版本变，照抄前请对一遍当前官网。**

| 配置项（写在 `config.toml` 里） | 类型 / 取值 | 作用 |
|---|---|---|
| `model_context_window` | 数字 | 当前模型可用的上下文 token 数 |
| `model_auto_compact_token_limit` | 数字 | ★★★ 到多少 token 触发自动压缩；不设则用每个模型的默认值 |
| `model_auto_compact_token_limit_scope` | `total` \| `body_after_prefix` | ★★ 上面那个阈值是量【整个上下文】(`total`，⚠️ 文档标为默认) 还是只量【固定前缀之后新长出来的部分】 |
| `compact_prompt` | 字符串 | ★★ 直接替换掉压缩用的提示词 |
| `experimental_compact_prompt_file` | 路径 | 同上，但从文件读（⚠️ 名字里带 `experimental`，★★ 实验特性最容易被改掉） |
| `tool_output_token_limit` | 数字 | ★★★ 单条工具输出在历史里能留多少 token |

★★ 另外 Codex 的钩子（hook）事件里，有两个是专门给压缩用的：`PreCompact`（压缩前）和 `PostCompact`（压缩后）。

```
   ⟹ 🔑🔑 ★★★ 请特别注意 model_auto_compact_token_limit_scope 这一项。

      它区分【总量】和【前缀之后的增量】——
      ⟹ 回到 §4.4b 第 ⑥ 条那笔账就很清楚了：
         固定前缀 2,500 token 每轮一字不变，占总量的 20%~30%，
         ★★ 而且正好是提示词缓存最擅长的部分，便宜。
         ★★★ 真正在长、真正贵、真正撑爆窗口的是【前缀之后那截】。

      ⟹ ★★ 按哪个口径算阈值，直接决定【多久压缩一次】：
         按 total 算 ⟹ 前缀越大，越早触发压缩（哪怕历史还很短）
         按 body_after_prefix 算 ⟹ 前缀不计入，压缩来得更晚
      ⟹ 🔑 也就直接决定成本和信息损失。

   ⟹ ★★★ 这就是本目录 README 说的"闭源产品公开的是【配置面】"：
      你看不到它压缩算法怎么写的，
      但你能看到它把哪些旋钮交到了你手上——
      ★★ 而这些旋钮，每一个都会动分数。
   ⟹ ⚠️ 所以报一个 agentic 分数时，这几个配置项的取值属于
      [01 章 §1.4b](01-两个harness不是一个东西.md) 第 ② 项「脚手架版本与配置」必须披露的内容。
```
