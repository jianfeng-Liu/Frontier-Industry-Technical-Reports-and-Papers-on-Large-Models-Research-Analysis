# 05 · 权限与沙箱：谁来拦住 `rm -rf /`

> ⭐ 这一章讲脚手架里唯一一块"不为了提分"的功能。
> ★★★ 但它决定了 agent 能不能【真的放出去自己跑】——
> 而"能不能自己跑"，反过来又决定了它能拿多少分。

---

## 5.1 先看问题本身

★★ 回到 02 章的循环：模型吐出一个命令，脚手架**真的去执行它**。

```
   ⟹ 🔑🔑 ★★★ 这一步是整个系统里最危险的地方。
      模型是【概率性】的，它可能吐出任何东西。
```

✅ SWE-agent 论文自己举的例子（★ 逐字，Broader Impacts 一节）：

> "running code generations on a personal computing device can have negative side
> effects, such as the unintentional removal of digital assets (e.g., `rm -rf asset/`)."

⟹ **在个人计算设备上运行代码生成结果，可能带来负面副作用，例如无意中删除数字资产（比如 `rm -rf asset/`）。**

```
   ★ 名词：rm -rf <路径>
     ⟹ Linux/macOS 上的删除命令。
        `-r` = 连子目录一起删；`-f` = 不确认、强制删。
     ⚠️ 它【不进回收站】。执行完就没了。

   ★★ 注意论文用的词是 "unintentional"（无意中）——
      不是说模型想搞破坏，是说它【好心办坏事】：
      它以为 asset/ 是构建产物，其实那是你的素材目录。
```

## 5.2 两道防线：许可 vs 沙箱

★★★ 这是本章最重要的一个区分。新手最容易把这两个混成一件事。

| 对比项 | 防线① **许可**（permission，许可/授权） | 防线② **沙箱**（sandbox） |
|---|---|---|
| 什么时候起作用 | ★ 在【执行之前】问一句："这条命令我能跑吗？" | ★ 在【执行的全过程】：让命令就算跑起来了，也够不着不该碰的东西 |
| 谁在拦 | ★ 规则 / 人 / 另一个模型 | ★★★ 操作系统内核 |
| 拦的是什么 | ⚠️ **命令文本**。命令写得花一点就可能绕过去 | ★★★ **系统调用**。不看命令长什么样，绕不过去 |
| 被拦时你看到什么 | 弹一个「允许 / 拒绝」等你点 | 命令真的跑了，但读写或联网被拒，返回一个权限错误 |
| 关掉它的后果 | 模型不再停下来问你，但还是碰不到边界外的东西 | ⚠️ 模型的每一条命令都拿到了你本人的全部权限 |
| 一句话 | 🔑 要不要**问**你 | 🔑 问不问都**够不着** |

✅ Claude Code 官方文档把这个分工写得非常清楚（★ 逐字）：

> "Permission modes decide whether Claude asks before an action, and the Bash sandbox
> and outer isolation boundaries decide what an action can reach once it runs."

⟹ **许可模式决定 Claude 在动作之前是否询问你；而 Bash 沙箱和外层隔离边界决定这个动作一旦跑起来能够到什么。**

```
   ⟹ 🔑🔑 ★★★ 一句口诀：
      【许可 = 要不要问你；沙箱 = 问不问都够不着。】

   ⟹ ★★ 所以它们是【正交】的，可以同时开。
      ✅ 文档原话："The Bash sandbox and auto mode work independently and combine"
      ⟹ Bash 沙箱和 auto 模式互相独立、可以叠加。
```

## 5.3 ✅ SWE-agent 的做法：整个跑在 Docker 容器里

★★ 2024 年的学术脚手架，做法很简单粗暴——**没有许可这一层，只有沙箱，而且是最重的那种**。

✅ 论文原话（★ 逐字）：

> "we design SWE-agent to use ephemeral containers for both inference and evaluation.
> SWE-agent's execution environment and the SWE-bench evaluation framework are both
> carried out in sand-boxed code environments, which is made possible with Docker."

⟹ **我们把 SWE-agent 设计成推理和评测都使用「一次性容器」。SWE-agent 的执行环境和 SWE-bench 评测框架都在沙箱化的代码环境里进行，这靠 Docker 实现。**

```
   ★ 名词：Docker（容器技术）
     ⟹ 把程序连同它需要的整套环境打包，跑在一个与主机隔离的
        "小盒子"里。盒子里的删改，碰不到盒子外面。

   ★ 名词：ephemeral container（一次性容器 / 临时容器）
     ⟹ 跑完就销毁的容器。⟹ ★★ 这意味着：
        模型在里面干了什么破坏，都随着容器一起消失。

   ⟹ 🔑 ★★ 这也顺便解决了【复现性】：
      每道题都从一个干净的、完全一样的盒子开始。
      ✅ 论文另一处："SWE-agent also uses Docker containers to ensure reproducible
         [environments]" ⟹ 确保环境可复现。
```

⚠️ 但论文自己也承认这不是绝对安全（✅ 逐字，这一句很诚实）：

> "While not considered as secure as virtualized hardware isolation, the namespace
> isolation provided by Docker containers is deemed sufficient for code that is not
> deliberately engineered to exploit recent container escape vulnerabilities."

⟹ **虽然不如硬件虚拟化隔离安全，但 Docker 容器提供的命名空间隔离，对于那些并非刻意针对近期容器逃逸漏洞而设计的代码，被认为已经足够。**

```
   ⟹ ★★ 请注意这句话的前提条件：
      "not deliberately engineered to exploit..."
      ⟹ 【只防意外，不防蓄意攻击。】
      ⚠️ 论文接下来还专门讨论了"如果有人在 issue 描述里
         写入恶意指令怎么办"——也就是提示词注入。
```

## 5.4 ✅ Claude Code：六种许可模式

★★ 这一节有一个数到底几种的问题，所以先把核实过程摆出来，再列表。

**✅ 核实结论（2026-10-01，在本机对 Claude Code `2.1.227` 一手核实）：是【六种】，不是五种。**

核实分三条，互相独立：

```
   ✅ ① 命令行可取值 —— claude --help 的 --permission-mode 一节逐字：
        (choices: "acceptEdits", "auto", "bypassPermissions",
                  "manual", "dontAsk", "plan")
      ⟹ 六个。

   ✅ ② 程序内部的取值枚举 —— 从 claude 可执行文件里抽到的字符串表，
        同一处连续出现两遍，紧跟着一句 "Cannot set permission mode: must be one of "：
        acceptEdits / auto / bypassPermissions / default / dontAsk / plan
      ⟹ 也是六个。

   🔑 ★★★ ③ 对上面两份清单的差异的解释：manual 和 default 是【同一档的两个名字】。
      ⟹ 命令行标志写 manual，设置文件 permissions.defaultMode 写 default，界面显示 Manual。
      ⚠️ 所以"五种"这个数很可能就是这么来的：
         把 manual 和 default 当成两档会数出七种，当成同一档又漏掉一档会数出五种。
      ⟹ ★★ 正确的数法：【六档，其中第一档有两个名字。】
```

✅ 而且程序里有一处把六档一次性描述完的字段说明（逐字，这是本节最硬的一条来源）：

> "Permission mode for controlling how tool executions are handled. `'default'` - Standard behavior, prompts for dangerous operations. `'acceptEdits'` - Auto-accept file edit operations. `'bypassPermissions'` - Bypass all permission checks (requires `allowDangerouslySkipPermissions`). `'plan'` - Planning mode, no actual tool execution. `'dontAsk'` - Don't prompt for permissions, deny if not pre-approved. `'auto'` - Use a model classifier to approve/deny permission prompts."

⟹ **用于控制工具执行如何被处理的许可模式。`default` —— 标准行为，对危险操作弹出询问。`acceptEdits` —— 自动接受文件编辑操作。`bypassPermissions` —— 绕过所有许可检查（需要 `allowDangerouslySkipPermissions`）。`plan` —— 计划模式，不实际执行工具。`dontAsk` —— 不弹许可询问，没有预先批准过就直接拒绝。`auto` —— 用一个模型分类器来批准/拒绝许可询问。**

```
   ⟹ 🔑 ★★★ 从这段逐字描述里额外捞到两条，都是前面漏掉的：
      ① bypassPermissions 不是改个配置就能用：
         ⚠️ 它还要求 allowDangerouslySkipPermissions 一起打开。
      ② dontAsk 的要点不是"不问"，是【不问 + 直接拒绝】。
         ⟹ ★★ 对照 default：default 是"不确定就问你"；
            dontAsk 是"不确定就当你说了不行"。
         ⟹ 🔑 所以 dontAsk 在无人值守的 CI 里是【安全】的那一档，
            auto / bypassPermissions 才是放开的那一档。别把它们记混。
```

⚠️ 一条使用层面的更正：**界面上的 `Shift+Tab` 不是在六档之间循环。** 本机 2.1.227 的提示文案逐字是 "to cycle between manual mode, auto-accept edit mode, and plan mode"（在手动模式、自动接受编辑模式、计划模式之间循环），只有三档。⟹ ★★ 剩下三档（`auto` / `dontAsk` / `bypassPermissions`）得走 `--permission-mode` 或 `permissions.defaultMode`。⚠️ 循环里含哪几档随版本变，这条只对 2.1.227 成立。

★★★ 下面这张表的模式名和"不问就能干的事"来自官方 `permission-modes` 文档（✅ 逐字表格），⚠️ 口径截至 2026-08-27：

| 模式（配置值） | ★ 不问就能干的事 | 适用场景 |
|---|---|---|
| `default`（界面显示 **Manual**，手动） | ★★ **只读** | 逐条审查、敏感工作 |
| `acceptEdits` | 读 + 改文件 + 常见文件系统命令（`mkdir` `touch` `mv` `cp` 等） | 你在旁边看着的迭代 |
| `plan` | 读；★★ 若 auto 模式可用，再加上分类器批准的命令 | 改之前先摸清代码库 |
| `auto` | ★★★ **全部**，但有后台安全检查 | 长任务、减少打断 |
| `dontAsk` | ★★ 只有【预先批准过】的工具 | 锁死的 CI 和脚本 |
| `bypassPermissions` | ★★★ **全部，无检查** | ⚠️ **只能用于隔离的容器和虚拟机** |

```
   ★ 名词：CI（Continuous Integration，持续集成）
     ⟹ 代码一提交就自动跑构建和测试的流水线。没有人在旁边看。

   ★ 名词：classifier（分类器）
     ⟹ ★★★ 这是 auto 模式的核心。✅ 文档原话：
        "a second model, the classifier, reviews actions instead of you"
        ⟹【另一个模型（分类器）替你审查动作。】
     ⟹ 🔑 也就是说：用模型来看住模型。
```

★★ 文档里有一句话，把这六种模式的排布逻辑讲透了（✅ 逐字）：

> "Each mode makes a different tradeoff between convenience and oversight."

⟹ **每种模式都在便利性和监督之间做了不同的取舍。**

```
   便利 ◀──────────────────────────────────────────▶ 监督
   bypassPermissions   auto   acceptEdits   plan   default
        ⚠️危险                                      🐢慢
```

⚠️ 注意这条轴上**少了 `dontAsk`**，因为它不在这条轴上：它既不便利也不监督，它是【不问 + 没批准就拒绝】。⟹ ★★ 一维的轴放不下它，所以下面换成矩阵。

### 5.4b ⭐⭐⭐ 矩阵：同一个操作，在六档里分别会发生什么

★★★ 这张表是本节最该存下来的东西。⚠️ 它是我按上面那段逐字字段说明 + 官方文档的"不问就能干的事"一列**推演**出来的，不是哪一份文档里现成的表格，所以通篇按推演读。

| 模型想干的事 | `default`<br>(=`manual`) | `plan` | `acceptEdits` | `auto` | `dontAsk` | `bypassPermissions` |
|---|---|---|---|---|---|---|
| **读文件**（Read/Glob/Grep） | ✅ 直接跑 | ✅ 直接跑 | ✅ 直接跑 | ✅ 直接跑 | ✅ 直接跑（注1） | ✅ 直接跑 |
| **写/改文件**（Edit/Write） | ❓ 问你 | ❌ 不执行（注2） | ✅ 直接跑 | 🤖 分类器判 | ⛔ 没预批就拒 | ✅ 直接跑 |
| **跑常见文件系统命令**（`mkdir` `cp` `mv`） | ❓ 问你 | ❌ 不执行 | ✅ 直接跑 | 🤖 分类器判 | ⛔ 没预批就拒 | ✅ 直接跑 |
| **跑任意 shell 命令**（Bash） | ❓ 问你 | ❌ 不执行 | ❓ 问你 | 🤖 分类器判 | ⛔ 没预批就拒 | ✅ 直接跑 |
| **联网**（WebFetch / `curl` / `pip install`） | ❓ 问你 | ❌ 不执行 | ❓ 问你 | 🤖 分类器判 | ⛔ 没预批就拒 | ✅ 直接跑 |
| **`rm` 打到关键路径** | ❓ 问你 | ❌ 不执行 | ❓ 问你 | ❓ **问你** | ⛔ 拒 | ❓ ★★★ **照样问你** |

注1：`dontAsk` 的"预先批准"在实践中通常把只读工具整类放行；⚠️ 但这取决于你写的 `permissions.allow`，不是这一档自带的性质。

注2：`plan` 档那句逐字说明是 "no actual tool execution"（不实际执行工具）；⚠️ 官方 `permission-modes` 文档另有一句说 plan 档在 auto 可用时还能跑分类器批准过的命令 —— 两处口径不完全一致，我没能在一次会话里把这条验到底，所以标 ⚠️。

```
   ★ 图例：✅ 不问就跑   ❓ 弹询问   ⛔ 直接拒绝不问   ❌ 这一档根本不执行
           🤖 交给分类器（另一个模型）判，判不下来才弹给你

   ⟹ 🔑🔑 ★★★ 把最后一行横着读一遍，这张表就讲完了：
      【只有最后一行，六档的结果几乎一致。】
      ⟹ ★★ 因为那一行不是许可档位管的，是【硬拦截】管的（见下）。

   ⟹ 🔑 ★★★ 再把"联网"那一行和"跑任意 shell 命令"那一行对比：
      ⚠️ 它们在许可层是【同一行】——因为 pip install 就是一条 bash 命令。
      ⟹ ★★★ 所以"能不能联网"这件事，许可档位其实管不住：
         你把 Bash 放行了，联网就跟着放行了。
      ⟹ 🔑 要单独管网络，必须下到【沙箱层】（5.5 的 allowedDomains）。
         这就是 5.2 那条"许可拦文本、沙箱拦系统调用"的实际后果。
```

### 5.4c ⭐⭐ 硬拦截：任何模式都不放行的那几件事

★★★ **有些事任何模式都不会自动放行**（✅ 文档 "Actions no mode auto-approves"，
包括 `bypassPermissions`）：

- ★★ 显式 ask 规则命中的工具
- 需要用户交互的工具（如 `AskUserQuestion`）
- ★★★ 针对**关键路径**（critical path）的 `rm` / `rmdir` ——
  ✅ 原话："which no allow rule or `PreToolUse` hook `"allow"` approves"
  ⟹ **没有任何 allow 规则、也没有任何 `PreToolUse` 钩子的 "allow" 能批准它。**

```
   ⟹ 🔑🔑 ★★★ 这一条很重要：
      连"跳过全部检查"的模式，都在 rm 关键路径上留了一道硬拦截。
   ⟹ ★★ 对照 5.1 论文那句 `rm -rf asset/`——
      两年之后，这个具体场景被【专门写进产品里】了。
```

**⭐ 而"关键路径"这四个字具体指哪些情况，可以在 2.1.227 的可执行文件里数清楚 —— 一共六类，每一类都带一句一模一样的尾巴（✅ 逐字，六句话里这一句重复出现）：**

> "This requires explicit approval and cannot be auto-allowed by permission rules."

⟹ **这需要显式批准，无法被许可规则自动放行。**

| # | 触发条件（✅ 程序里的提示文案逐字 ⟹ 中文） | 一个会踩中的例子 |
|---|---|---|
| ① | "This command would remove a critical system directory." ⟹ 这条命令会删除一个关键系统目录 | `rm -rf /usr` |
| ② | "This command would remove a workspace directory (the working directory, an additional working directory, or one of their parent directories)." ⟹ 会删除工作区目录本身：当前工作目录、附加工作目录，或它们的任一父目录 | 在 `~/proj` 里跑 `rm -rf ~/proj` |
| ③ | "This command changes directories before the removal, so the relative glob target cannot be statically resolved." ⟹ 删除之前先切了目录，于是相对路径通配符的目标没法静态确定 | `cd $X && rm -rf *` |
| ④ | "This command's removal target cannot be statically resolved to a directory." ⟹ 删除目标没法静态确定成一个目录 | `rm -rf $(cat list.txt)` |
| ⑤ | "This command's glob pattern traverses directories that cannot be statically enumerated." ⟹ 通配符要穿过没法静态枚举的目录 | `rm -rf build/*/*/tmp` |
| ⑥ | 变量没赋值时会展开成文件系统根或某个顶层目录 ⟹ ✅ 程序里给的例子逐字就是：``e.g. `rm -rf $UNSET/*` becomes `rm -rf /*` `` | `rm -rf $PREFIX/*`，而 `$PREFIX` 恰好是空的 |

```
   ⟹ 🔑🔑🔑 ★★★ 请注意这六类里只有 ①② 是"目标太重要"，
      ③④⑤⑥ 全是同一个判断：【我算不出来你到底要删哪儿】。

   ⟹ ★★★ 这是整章最值得学的一个设计思路，而且和模型无关：
      ┌─ 它不是在维护一张"危险路径黑名单"
      ├─ 而是在做一次【静态可解析性】检查
      └─ 算不出目标 ⟹ 当成危险处理，不赌。

   ⟹ ★★ 对照 5.1 论文的 "unintentional"（无意中）：
      🔑 模型"好心办坏事"的典型形态，正是写出一条
         【它自己也不知道会展开成什么】的命令。
      ⟹ 所以拦在"算不出来"这一层，比拦在"路径名"这一层有效得多。

   ⚠️ 版本提醒：以上六类来自 2.1.227 这一个版本的程序内文案。
      它不是公开 API，下个版本可能增删。要按它写策略请自己重验一遍。
```

## 5.5 ✅ Claude Code：Bash 沙箱

★★ 这是另一条腿。✅ 文档 `sandboxing` 页逐字：

> "The Bash sandbox lets Claude run most shell commands without stopping to ask
> permission. Instead of approving each command, you define which files and network
> domains commands can touch, and the operating system enforces that boundary for
> every Bash command and its child processes."

⟹ **Bash 沙箱让 Claude 不必停下来征求许可就能运行大多数 shell 命令。你不再逐条批准命令，而是定义命令能碰哪些文件和哪些网络域名，然后由操作系统对每一条 Bash 命令及其子进程强制执行这个边界。**

```
   ⟹ 🔑🔑 ★★★ 注意这句话的商业逻辑：
      沙箱不是为了"更安全"卖给你的，
      是为了【让你少点几百次"允许"按钮】。
      ⟹ ★★ 安全是手段，自动化程度才是目的。
```

**✅ 底层机制（逐字）：**

> "The sandbox is built into Claude Code and runs on macOS, Linux, and WSL2. Native
> Windows is not supported."
> "On macOS, there is nothing to install: sandboxing uses the built-in Seatbelt framework."

⟹ **沙箱内置于 Claude Code，运行在 macOS、Linux 和 WSL2 上，不支持原生 Windows。macOS 上无需安装任何东西：沙箱使用系统自带的 Seatbelt 框架。**

Linux/WSL2 上需要两个包（✅ 逐字）：

| 包 | 文档给的作用 |
|---|---|
| `bubblewrap` | "the unprivileged sandboxing tool that enforces filesystem isolation" ⟹ 强制文件系统隔离的**无特权**沙箱工具 |
| `socat` | "the relay used to route network traffic through the sandbox proxy" ⟹ 把网络流量路由到沙箱代理的中继 |

★★ 另有可选的 seccomp 过滤器，✅ "The seccomp filter is optional and adds Unix domain socket blocking."（可选，增加 Unix 域套接字阻断。）

```
   ★ 名词：Seatbelt ⟹ macOS 自带的进程沙箱框架（系统级）。
   ★ 名词：bubblewrap（命令名 bwrap）
     ⟹ Linux 上的沙箱工具。"unprivileged" = 不需要 root 权限就能用。
   ★ 名词：seccomp（secure computing mode）
     ⟹ Linux 内核特性，按【系统调用】粒度过滤。⟹ ★★ 粒度比文件路径更细。
   ★ 名词：WSL2（Windows Subsystem for Linux 2）
     ⟹ Windows 里跑 Linux 的官方方案。
```

**✅ 默认边界（逐字）：**

- 文件：`"read and write access to the current working directory and its subdirectories, plus the session temp directory"` ⟹ 只能读写当前工作目录及其子目录，加上会话临时目录。
- 网络：★★★ `"Claude Code pre-allows no domains by default."` ⟹ **默认一个域名都不放行。**第一次要访问新域名时才问你。

### 5.5b ⭐⭐⭐ 边界图：什么跑在沙箱里、什么跑在沙箱外、数据怎么进出

★★★ 新手对沙箱最大的误解是以为"Claude Code 整个跑在沙箱里"。**不是。** 沙箱只套住 Bash 命令那一截。

```
   你的真电脑（宿主机）  ← ★★★ Claude Code 本体跑在这里，不在沙箱里
   │
   ├── Claude Code 进程本体
   │     ├─ 和模型服务端通网络（这条连接不受沙箱的域名白名单约束）
   │     ├─ Read / Edit / Write 这些内置工具 ⟹ 走许可层
   │     │    ⚠️ 它们是否也受 sandbox.filesystem 的 deny 规则约束，
   │     │       我没有在 2.1.227 上验到底，所以这一格标 ⚠️
   │     └─ 许可层：5.4 那六档在这里做判断
   │
   └── 每一条 Bash 命令 + 它派生的所有子进程   ← ★★★ 只有这一截在沙箱里
         │
         ├─ 文件：✅ 可读写 = 当前工作目录及其子目录 + 会话临时目录
         │         ⚠️ 其余一切不可写（$HOME 的其他部分、/etc、/usr……）
         ├─ 网络：★★★ 默认放行 0 个域名；要访问新域名时才问你
         ├─ 失败时：违规细节被附加到命令输出里，交回模型看（见下）
         └─ 逃生舱：dangerouslyDisableSandbox 可以把这一条命令挪到沙箱外跑
```

★★ 把"数据怎么进出"单独列一遍，这是判断一个沙箱够不够用的唯一标准：

| 方向 | 走哪条路 | ⚠️ 要注意什么 |
|---|---|---|
| **代码/文件 进** | 直接就在工作目录里 —— 沙箱不是另一台机器，它只是在同一个文件系统上划了一圈可写范围 | ★★★ 所以沙箱里的进程看得见工作目录的**真实内容**，不是副本。改了就是真改了 |
| **文件 出** | 写回工作目录即可 | ⚠️ 想往工作目录外写，要 `sandbox.filesystem.allowWrite` 显式加 |
| **网络 出** | 经由一个沙箱代理转发，域名白名单在代理上判 | ✅ 这就是 Linux 上要装 `socat` 的原因：它是把流量路由到代理的中继 |
| **命令输出 回到模型** | 走 Claude Code 本体，不经沙箱 | 🔑 ★★★ 所以沙箱**不防提示词注入**：被污染的文本照样进上下文 |
| **凭据 进** | 继承宿主的环境变量 | ⚠️⚠️ 沙箱里的命令能读到你 shell 里的环境变量，`AWS_SECRET` 之类照样可见 |

```
   ⟹ 🔑🔑 ★★★ 最后两行是这张表存在的理由：
      ⚠️ 沙箱挡住的是【写坏文件】和【连错域名】。
      ⚠️ 它【没有】挡住：被注入的文本进上下文、环境变量里的密钥被读到。
   ⟹ ★★★ 对照 5.3 SWE-agent 论文那句坦白"只防意外、不防蓄意"——
      进程级沙箱的这条边界，比容器还要再松一点。
      🔑 真要防蓄意，得换成 [07 章](07-DeepSeek的脚手架.md) 讲的 microVM / fullVM 那一档。
```

### 5.5c ⭐⭐ 两种沙箱模式，和那个逃生舱

**✅ 两种沙箱模式（注意：和 5.4 的许可模式是两套东西）：**

| 沙箱模式 | 行为 | ✅ 2.1.227 里对应的配置键 |
|---|---|---|
| **auto-allow**（自动放行） | 能沙箱化的命令直接跑，不问 | `autoAllowBashIfSandboxed`（✅ 程序里的提示文案逐字："Auto-allowed with sandbox (autoAllowBashIfSandboxed enabled)"） |
| **regular permissions**（常规许可） | ★★ 即使沙箱化了，也照样走许可流程 | 把上面那个键关掉 |

⟹ 🔑 ★★ 这个键名本身就印证了 5.5 开头那条商业逻辑：这个开关的名字不叫 `enableSandbox`，叫 **`autoAllowBashIfSandboxed`** ——「**既然沙箱化了就自动放行**」。⟹ ★★★ 沙箱在产品里的定位，被写进了配置键名里：它是【自动放行的前提条件】，不是一个独立的安全开关。

★★★ 还有一个**逃生舱**（escape hatch），我认为设计上很值得注意（✅ 逐字）：

> "when a command fails because of sandbox restrictions, Claude analyzes the failure
> and may retry the command with the `dangerouslyDisableSandbox` parameter."

⟹ **当一条命令因为沙箱限制而失败时，Claude 会分析这次失败，并可能带上 `dangerouslyDisableSandbox` 参数重试。**

```
   ⟹ 🔑🔑 ★★★ 这一条直接回到 02 章讲的循环：
      ✅ 文档："Claude Code appends the violation details to the failed command's
         output, so Claude sees which file path or network host the sandbox blocked."
      ⟹【把违规细节附加到失败命令的输出里，让 Claude 看到沙箱挡了哪个路径或主机。】

   ⟹ ★★ 这就是 03 章讲的 ACI 思想在安全层的应用：
      【报错信息本身，是写给模型看的一条指令。】
      不是"拒绝执行"就完了，而是告诉它【为什么】，让它自己想办法。

   ⚠️ 但重试是要重新走许可流程的 —— ✅ 2.1.227 程序内文案逐字：
      "When a command fails due to sandbox restrictions, Claude can retry with
       dangerouslyDisableSandbox to run outside the sandbox
       (falling back to default permissions)."
      ⟹【…退回到默认许可。】⟹ ★★ 墙拆了，但"问不问你"这一层回来了。
```

**⭐ 而这个逃生舱可以整个焊死**（文档称之为 **Strict sandbox mode**，严格沙箱模式）。✅ 2.1.227 里 `sandbox.allowUnsandboxedCommands` 这个键的字段说明逐字：

> "Allow commands to run outside the sandbox via the `dangerouslyDisableSandbox` parameter. When false, the `dangerouslyDisableSandbox` parameter is completely ignored and all commands must run sandboxed. Default: `true`."

⟹ **允许命令通过 `dangerouslyDisableSandbox` 参数在沙箱外运行。当它为 false 时，`dangerouslyDisableSandbox` 参数被完全忽略，所有命令都必须沙箱化运行。默认值：`true`。**

```
   ⟹ 🔑🔑 ★★★ 请注意那个默认值：true。
      ⟹ ★★【逃生舱默认是开着的。】
      ⚠️ 也就是说开箱即用的沙箱，严格说是"一道可以被模型自己
         请求拆掉的墙"——拆之前要过许可层，但墙本身不是硬的。
      ⟹ 🔑 要硬，得自己把这个键设成 false。

   ⚠️ 还有一个相邻的口子：sandbox.excludedCommands。
      ✅ 程序内文案逐字："All bash commands invoked by the model must run in
         the sandbox unless they are explicitly listed in excludedCommands."
      ⟹【除了显式列在 excludedCommands 里的，模型调用的所有 bash 命令
         都必须在沙箱里跑。】
      ⟹ ★★ 这条清单是你自己写的 ⟹ 🔑 它是你自己给自己开的洞，
         写进去的每一条都该当成"这条命令以我的全部权限运行"来审。
```

## 5.6 ✅ Codex：三种沙箱 × 三种审批

★★★ Codex 把这两个维度做成了两个**独立的配置项**，正交组合。以下取值名来自官方 `sandboxing` 文档（✅ 逐字）：

**`sandbox_mode`（沙箱模式）**

| 取值 | 文档原文 ⟹ 中文 |
|---|---|
| `read-only` | "The agent can inspect files, but it can't edit files or run commands without approval." ⟹ 可以看文件，但不经批准不能改文件、不能跑命令 |
| `workspace-write` | ★★ "The agent can read files, edit within the workspace, and run routine local commands inside that boundary." ⟹ 可读、可在工作区内改、可在该边界内跑常规本地命令 |
| `danger-full-access` | ⚠️ "The agent runs without sandbox restrictions." ⟹ 无沙箱限制 |

**`approval_policy`（审批策略）**

| 取值 | 文档原文 ⟹ 中文 |
|---|---|
| `untrusted` | "The agent asks before running commands that aren't in its trusted set." ⟹ 跑不在可信集合里的命令前会问 |
| `on-request` | ★★ "The agent works inside the sandbox by default and asks when it needs to go beyond that boundary." ⟹ 默认在沙箱内干活，需要越界时才问 |
| `never` | ⚠️ "The agent doesn't stop for approval prompts." ⟹ 不为审批停下 |

**`approvals_reviewer`（谁来审批）** ★★ 这一项对应 Claude Code 的分类器：

| 取值 | 含义 |
|---|---|
| `user` | ✅ "approval prompts surface to the user. This is the default." ⟹ 弹给用户，默认值 |
| `auto_review` | ★★★ ✅ "eligible approval prompts go to a reviewer agent" ⟹ 够条件的审批请求交给一个**审查 agent** |

⚠️ 但文档有一句限定，很关键：**自动审查不改变沙箱边界，它只改变审批请求的路由。**

```
   ⟹ ★★ 换句话说：换个"审批员"，墙没动。
```

**✅ 底层机制：** macOS 用 Seatbelt（和 Claude Code 一样）；Linux/WSL2 用 bubblewrap ——
✅ 原话："Codex uses the first `bwrap` executable it finds on `PATH`."
⟹ Codex 使用它在 `PATH` 上找到的第一个 `bwrap` 可执行文件。
Windows 有原生沙箱（在 PowerShell 里），⚠️ 这一点和 Claude Code 不同。

**✅ 越界目录：** `sandbox_workspace_write.writable_roots` ——
✅ 原话：工作跨多个目录时，"writable roots let you extend the places it can modify
without removing the sandbox entirely"
⟹ **可写根目录让你扩展它能修改的位置，而不必整个把沙箱拿掉。**

✅ 文档给的两个预设组合：

```
   ⚠️ 全放开：  sandbox_mode = "danger-full-access"
                approval_policy = "never"

   ✅ 低风险本地自动化：
                sandbox_mode = "workspace-write"
                approval_policy = "on-request"
   ⟹ 命令行等价写法：
      codex --sandbox workspace-write --ask-for-approval on-request
```

### 5.6b ⭐⭐ 正交矩阵：3 × 3 一共九格，实际只有四格有意义

★★ 既然 Codex 把两个维度做成了独立配置项，就会有 9 种组合。⚠️ 下表是我按两组逐字定义**推演**的组合结果，不是文档里现成的表。

| | `approval_policy = untrusted`（不可信命令都问） | `approval_policy = on-request`（要越界才问） | `approval_policy = never`（永不问） |
|---|---|---|---|
| **`read-only`**（只能看） | 几乎每一步都问 ⟹ 🐢 最慢最稳 | ✅ 探索/审计代码的合理档：读不用问，想动手就问 | ⚠️ **哑档**：不问、又不许动 ⟹ 它只能看，看完没法改 |
| **`workspace-write`**（工作区内可改） | ⚠️ 沙箱内也照样被问 ⟹ 两层叠着，很啰嗦 | ✅ ★★★ **文档推荐的那一档**（低风险本地自动化） | ⚠️ 工作区内无人看管地改 ⟹ 代码能被改坏，但改不出工作区 |
| **`danger-full-access`**（无沙箱） | ⚠️ 墙拆了，靠"问你"当唯一防线 ⟹ 全押在你点得对 | ⚠️ 墙拆了，"越界"这个概念没了 ⟹ 几乎等于不问 | ⚠️⚠️⚠️ ★★★ **全放开**：没有墙，也不问 ⟹ 只能用在一次性容器/虚拟机里 |

```
   ⟹ 🔑🔑 ★★★ 这张表的看点是右上角和右下角两格：

   ⚠️ 右上角（read-only + never）是个【哑档】——
      两个旋钮各自都合法，组合起来却没有用。
      ⟹ ★★ 这是"正交设计"的代价：
         🔑 旋钮独立 = 你能拧出官方没设想过的组合，包括没意义的组合。

   ⟹ ★★★ 对照 Claude Code 的做法：它是【六个预设档位】。
      ┌─ 预设档位：不会拧出哑档，但你只能从菜单里挑
      └─ 正交旋钮：能精确拧到你要的那一点，但要自己负责组合有没有意义
   ⟹ 🔑 这不是谁对谁错，是【面向产品用户】和【面向脚本/CI】两种口味，
      和 06 章要讲的那条分界线是同一条。
```

## 5.7 三家对照

| | SWE-agent（2024 论文） | Claude Code（2026 产品） | Codex（2026 产品） |
|---|---|---|---|
| **许可层** | ❌ 没有（全自动跑） | ✅ **6 档**模式：`default`(=`manual`) … `bypassPermissions` | ✅ **3 档** `approval_policy`：`untrusted` / `on-request` / `never` |
| **谁来审** | — | ✅ 人 或 **分类器**（`auto` 模式） | ✅ 人 或 **reviewer agent**（`approvals_reviewer = "auto_review"`） |
| **沙箱层** | ✅ Docker 一次性容器 | ✅ Seatbelt（macOS）／`bwrap` + `socat`（Linux/WSL2） | ✅ Seatbelt／`bwrap`／⚠️ Windows 有原生方案 |
| **默认网络** | ⚠️ 容器内可联网（装依赖需要） | ✅ ★★★ 一个域名都不预先放行，首次访问才问 | ✅ 有允许清单机制 |
| **隔离粒度** | ★ 整个 agent 进程在盒子里 | ★★★ 单条 Bash 命令 + 它的子进程 | ★★ 工作区边界 |
| **沙箱起不来时** | ⚠️ 没有这个情形（起不来就跑不了） | ✅ `sandbox.failIfUnavailable` 可配成硬失败 | ⚠️ 我没核实到等价开关 |

```
   ⟹ 🔑 ★★★ 看出演进方向了吗：
      2024：【把整个 agent 关进盒子】——粗，但简单。
      2026：【盒子拆细到每条命令，再叠一层"要不要问你"】。
      ⟹ ★★ 因为产品要跑在【你的真电脑上】，不能整台机器关进容器。

   ⟹ ★★ 而代价就是 5.5b 那张"数据怎么进出"的表：
      🔑 盒子拆细 = 盒子变薄。单条命令的沙箱共享宿主内核、
         共享文件系统、共享环境变量。
      ⟹ ★★★ 2024 的粗办法在【隔离强度】上其实更强，
         它输在【不能跑在你的真电脑上】。
```

## 5.8 ★★ 这和分数有什么关系？

⚠️ 以下是我的分析，不是任何文档的原话。

```
   ⟹ 🔑🔑 ★★★ 论证链：

   ① 评测跑分时，人不可能在旁边逐条点"允许"。
      ⟹ 榜单成绩必然是在【最放开的档位】上跑出来的
        （Codex 的 approval_policy = never 那一档）。

   ② ★★★ 所以：【你日常用的档位 ≠ 榜单跑分的档位。】
      ⟹ 你开着许可提示用，它每一步都可能被你打断、被你拒绝；
         榜单上那个数字，是它一路畅通跑出来的。

   ③ ⚠️ 反过来说，如果一个产品【只能】在全放开档位下达到高分，
      那它的分数对"日常安全使用"没有参考价值。

   ⟹ ★★ 但这一点，榜单上是看不出来的。
      公开的 SWE-bench 提交记录里，通常不注明许可档位。
```

⚠️ 一条必须补上的限定：**上面④是论证，不是实测。** 我没有查到任何一份公开材料做过"同一个模型、同一批题，只换许可档位"的消融实验。⟹ ★★ 所以这一节能说的是【方向】（放开档位分数不会更低），不能说【量级】（差几个百分点）。🔑 [08 章 §8.1b](08-脚手架怎么影响榜单分数.md) 那张主表里，"许可档位"这一行的量级一栏写的就是 ⚠️ 未知 —— 本章是那一格为什么是空的原因。

## 5.9 本章总结

```
    🔑 七条带走：

    ① ★★★ 【许可】和【沙箱】是两件事：
       许可 = 执行前问不问你（拦命令文本）；
       沙箱 = 执行时够不够得着（操作系统内核拦）。
       ⟹ ✅ 官方原话："decide whether Claude asks" vs "decide what an action can reach"

    ② ★★ ✅ SWE-agent = 只有沙箱，没有许可。
       ephemeral Docker container（一次性容器），跑完即毁。
       ⚠️ 论文自己承认：只防意外，不防蓄意逃逸。

    ③ ★★★ ✅ Claude Code = 6 种许可模式 × 2 种沙箱模式。
       ✅ "6" 这个数已在本机 2.1.227 上一手核实（见 5.4 开头三条）：
          acceptEdits / auto / bypassPermissions / default(=manual) /
          dontAsk / plan。🔑 manual 和 default 是同一档的两个名字。
       ★★★ 且【任何模式都不放行 rm 的六类危险形态】，
          其中四类的判据是"算不出你要删哪儿"，不是路径黑名单。

    ④ ★★★ ✅ Codex = sandbox_mode(3) × approval_policy(3) × approvals_reviewer(2)，
       三个维度正交。⚠️ 但 approvals_reviewer 只改路由，不改边界。

    ⑤ ★★★ ✅ 两家都用【模型审模型】：
       Claude Code 的 classifier、Codex 的 auto_review。

    ⑥ ⚠️ ★★★ 我的推断：榜单分数必然出自最放开的档位。
       ⟹ 你日常用的档位和跑分档位不是同一个。
       ⚠️ 但【方向】可推、【量级】不可推：没有公开的
          "只换许可档位"消融实验。

    ⑦ ★★★ 🔑 沙箱不是把 Claude Code 整个关起来，
       它只套住【每一条 Bash 命令及其子进程】（5.5b 那张边界图）。
       ⚠️ 所以它不挡提示词注入，也不挡环境变量里的密钥被读到。
```
