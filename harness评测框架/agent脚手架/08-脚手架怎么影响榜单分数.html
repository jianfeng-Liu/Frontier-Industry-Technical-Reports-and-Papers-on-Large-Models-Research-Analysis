08 · 脚手架怎么影响榜单分数（收口章）

⭐⭐ ★★★ 这是本目录的收口章。前七章拆开讲了脚手架的每个部件，
这一章把它们折算成分数，并接回
评测入门 08 章 和
评测入门 11 章。

8.1 先把全目录的数字集中到一张表

★★★ 以下每一行都是 ✅ 同一个模型、同一批题目，只改脚手架的某一处。
来源：SWE-agent 论文 Table 3（GPT-4 Turbo，SWE-bench Lite，%Resolved 解决率）。

   ┌────────────────────────────┬────────┬──────────┐
   │ 改动                        │ 分数   │ 相对基线 │
   ├────────────────────────────┼────────┼──────────┤
   │ ★ SWE-agent 完整配置        │ 18.0   │  —       │
   ├────────────────────────────┼────────┼──────────┤
   │ 换掉文件编辑器界面          │ 10.3   │ ↓ 7.7 ★★★│
   │ 搜索改成迭代式（逐条翻）    │ 12.0   │ ↓ 6.0 ★★★│
   │ 上下文留全部历史            │ 15.0   │ ↓ 3.0 ★★★│
   │ 编辑器去掉 linter 护栏      │ 15.0   │ ↓ 3.0 ★★ │
   │ ★★ 完全不给搜索工具         │ 15.7   │ ↓ 2.3 ⚠️ │
   └────────────────────────────┴────────┴──────────┘

   ⟹ 🔑🔑🔑 ★★★ 请盯住这张表的量级：
      【最大单项差 7.7 分。而 18.0 是基线本身。】
      ⟹ ★★ 也就是说，脚手架里【一个部件】就能吃掉
         这套系统四成以上的成绩。

   ⚠️ 注意最后一行的反直觉：
      "完全不给搜索工具"(15.7) 反而【好过】
      "给了一个难用的搜索工具"(12.0)。
      ⟹ ★★★ 🔑 坏工具比没工具更糟。
         因为模型会去用它，然后被它带偏、被它填满上下文。

⚠️ 这张表的适用边界，必须说清楚：

   ⚠️ ① 它是 2024 年的 GPT-4 Turbo，不是今天的模型。
   ⚠️ ② 它是 SWE-bench Lite（300 题子集），不是 full。
   ⚠️ ③ 它证明的是【差异存在且量级很大】，
        不是"今天换编辑器还能差 7.7 分"。

   ⟹ ★★ 但 07 章给了一条 2026 年的旁证，量级同样惊人：
      ✅ 工具结果挂在 tool result 还是 user message 下，
      会决定模型的思考轨迹保不保留——
      官方直接说，后者的情况下【建议别用思考模型】。
      ⟹ 🔑 ★★★ 这不是掉几分，这是【换一个模型档位】。

8.2 那"模型分数"这四个字到底指什么

★★★ 把 01 章那条链重画一遍，标上谁贡献了什么：

   ┌──────────────────────────────────────────────────────────┐
   │                                                          │
   │   题目 ──▶ ┌─────────────────────────┐ ──▶ patch ──▶ 评测 │
   │            │      脚手架 scaffold     │              框架  │
   │            │  ┌───────────────────┐  │              (harness)│
   │            │  │      模型          │  │              ──▶ 分数│
   │            │  └───────────────────┘  │                     │
   │            │  循环/工具/上下文/权限   │                     │
   │            └─────────────────────────┘                     │
   └──────────────────────────────────────────────────────────┘

   ⟹ 🔑🔑 ★★★ 评测框架看到的只有最右边那个 patch。
      ✅ 这一点 评测入门 08.1 已经用 SWE-bench 源码证明过：
         预测结果的字段只有 model_name_or_path / model_patch /
         instance_id ——【没有一个字段描述脚手架】。

   ⟹ ★★★ 所以榜单上那一行，正确的读法是：

      ❌ 错：「GPT-4 Turbo 得 18.0 分」
      ✅ 对：「GPT-4 Turbo + SWE-agent 脚手架 + Lite 子集 +
              pass@1 + 某个成本上限，这【一整套系统】得 18.0 分」

8.3 ⭐⭐ 把评测入门那六件事的第②条展开

★★ 评测入门 08.7 给了看到 agentic 分数
要追问的六件事。其中第②条是"什么脚手架？"。

★★★ 学完本目录，你可以把这一条展开成七个子问题：

   ② 什么脚手架？ ⟹ 展开：

   ┌────┬────────────────────┬──────────────────────────────────┐
   │②a  │ 工具集是什么？      │ 几个工具？是通用 bash 还是专门   │
   │    │  ⟹ 见 03 章        │ 设计的 ACI？有没有 linter 护栏？ │
   ├────┼────────────────────┼──────────────────────────────────┤
   │②b  │ 上下文策略是什么？  │ 截断 / 压缩 / 隔离？留几条观察？ │
   │    │  ⟹ 见 04 章        │ 窗口多大？                       │
   ├────┼────────────────────┼──────────────────────────────────┤
   │②c  │ 步数上限多少？      │ ★★★ SWE-agent 约 12 步就成功，  │
   │    │  ⟹ 见 02 章        │ DeepSeek-V4 设了 500 步上限      │
   ├────┼────────────────────┼──────────────────────────────────┤
   │②d  │ 成本上限多少？      │ exit_cost 卡在几美元？           │
   │    │  ⟹ 见 02 章        │ ⚠️ 这直接决定 ②c 有没有意义     │
   ├────┼────────────────────┼──────────────────────────────────┤
   │②e  │ 许可档位是哪一档？  │ ★★★ 几乎没人披露。跑分必然是    │
   │    │  ⟹ 见 05 章        │ 全放开档（never / bypass）       │
   ├────┼────────────────────┼──────────────────────────────────┤
   │②f  │ 工具结果怎么回传？  │ ★★★ tool result 还是伪装成      │
   │    │  ⟹ 见 07 章        │ user message？会改变模型行为     │
   ├────┼────────────────────┼──────────────────────────────────┤
   │②g  │ 用没用子 agent？    │ 用了的话，总 token 消耗和         │
   │    │  ⟹ 见 06 章        │ 单 agent 不可比                  │
   └────┴────────────────────┴──────────────────────────────────┘

   ⟹ 🔑🔑 ★★★ 现实检查：
      在我为写本目录查过的所有公开材料里，
      【只有 DeepSeek-V4 报告同时回答了 ②a ②c ②b(部分)】。
      ⚠️ ②e 没有任何一家披露过。

8.4 三种常见的"不可比"，逐个认出来

⚠️ 不可比 A：两家用了不同的脚手架

   ✅ 实证（评测入门 10.6 已给过）：
      同一张表里，所有模型都跑 Agentless（无 agent 循环）时，
      Claude-3.5-Sonnet = 50.8。
      ⟹ ★★ 而 Anthropic 自家用 Claude Code 报出来的数字是另一回事。

   ⟹ 🔑 ★★★ 两个数都不假，但它们回答的是【不同问题】：
      ┌──────────────────┬────────────────────────┐
      │ 统一脚手架下的数  │ 这个【模型】有多强      │
      │ 各自产品报的数    │ 这套【产品】有多好用    │
      └──────────────────┴────────────────────────┘

   ⟹ ★★ 挑哪个数取决于你要做什么决定：
      要选【模型】接进自己的系统 ⟹ 看统一脚手架的数
      要选【产品】给团队用       ⟹ 看产品自己报的数
      ⚠️ 千万别用后者去推断前者。

⚠️ 不可比 B：改了脚手架又改了模型

   ✅ 实证（07 章）：
      DeepSeek V3（Agentless）= 42.0
      DeepSeek V4（自研 agent 框架，2 工具/500 步）= 80.6

   ⚠️⚠️ ★★★ 这 38.6 分的差，至少来自三个同时变化的变量：
      ① 模型换了（V3 → V4）
      ② 脚手架换了（Agentless → agent 循环）
      ③ 题目集是否完全一致，需回原文核对

   ⟹ 🔑 ★★★ 三变量同时变 ⟹ 这个差值【不能归因于任何单一原因】。
      ⚠️ 但宣传口径几乎总是把它说成"模型进步了"。

⚠️ 不可比 C：预算不同

   ✅ 实证（02 章，SWE-agent 论文）：
      成功案例：平均 $1.21 / 约 12 步
      失败案例：平均 $2.52 / 约 21 步
      ⟹ ★★ 论文原话概括为 "Agents succeed quickly and fail slowly"
         （agent 成功得快，失败得慢）。

   ⟹ 🔑🔑 ★★★ 这条规律有一个直接推论：
      【把预算上限调高，主要是在给"已经要失败的那些题"续命。】
      ⟹ ★★ 收益递减，但不是零——总有几题会在第 300 步做出来。

   ⟹ ⚠️ 所以：一个不写预算上限的 agentic 分数，
      在方法论上是【不完整】的。
      ⟹ ★★ 一个花 100 美元一题跑出来的 85%，
         和一个花 1 美元一题跑出来的 80%，不是同一件事。

8.5 ★★★ 一个必须承认的天花板

   ⚠️⚠️⚠️ 本目录做到最后，有一个问题是【结构性无解】的：

   ⟹ 对闭源产品，你能查到【配置面】（模式名、配置键、工具名），
      但查不到：
        ① 系统提示词
           ✅ Claude Code 文档明说 "Claude Code's system prompt
              isn't published."
        ② 每个工具的完整参数与内部实现
        ③ 压缩算法、分类器的判据
        ④ ★★★ 跑分那一次到底怎么配的

   ⟹ 🔑 ★★★ 而 8.1 那张表证明了：
      【这些查不到的东西，恰恰是分数差异的主要来源。】

   ⟹ ★★ 所以本目录能给你的，不是"算出各家真实水平"，
      而是【知道自己不知道什么，以及那个不知道有多大】。
      ⟹ 我认为这比一个假装精确的排名更有用。

8.6 那实际该怎么办

★★ 三条可操作的建议。⚠️ 这一节是我的建议，不是文档或论文内容。

   ┌─ 建议① 要比模型，就自己统一脚手架重跑 ─────────────┐
   │  ★★★ 用同一套【开源】脚手架（SWE-agent 是现成的，   │
   │     Codex CLI 也开源），把候选模型各跑一遍。        │
   │  ⟹ 这样 ②a~②g 全部固定，唯一变量是模型。          │
   │  ⚠️ 代价：要花钱，而且要花不少。                    │
   │  ⟹ 具体步骤见 评测入门 08.8 和 12 章。             │
   └─────────────────────────────────────────────────────┘
   ┌─ 建议② 要选产品，就用【你自己的仓库】试 ───────────┐
   │  ★★★ ✅ 评测入门 11.7 的"误读 B"已经讲过：          │
   │     "SWE-bench 70%" 不等于"你的仓库它能修好 70%"。  │
   │  ⟹ ★★ SWE-bench 的题全是【有人写好 issue、          │
   │     有人写好测试】的 Python 开源项目。              │
   │     你的仓库大概率三条都不满足。                    │
   └─────────────────────────────────────────────────────┘
   ┌─ 建议③ 看到一个数，先问它【回答的是哪个问题】 ─────┐
   │  ★★ 三类问题，三种数：                              │
   │   模型有多强 ⟹ 要统一脚手架的数                     │
   │   产品有多好用 ⟹ 要产品自己报的数 + 你自己试        │
   │   脚手架值不值 ⟹ ★★★ 要【消融实验】的数，          │
   │      也就是 8.1 那种"只改一处"的表                   │
   │  ⟹ 🔑 三者混着看，必然得到错误结论。               │
   └─────────────────────────────────────────────────────┘

8.7 全目录八条主结论

    🔑🔑🔑 ★★★ 如果只记八句话：

    ① 「harness」是同音异义词。
       评测框架 = 判卷的；agent 脚手架 = 让模型能动手的。
       ⟹ 本目录讲后者，评测入门讲前者。

    ② ★★★ 模型只会吐字。所有"动作"都是脚手架
       把那段字解析成命令、真的去执行、再把结果拼回对话。
       ⟹ 这个循环就是 agent 的全部。

    ③ ★★★ ✅ ACI（智能体-计算机接口）：给模型的界面
       是一项独立技术。换掉文件编辑器界面，掉 7.7 分。
       ⚠️ 且【坏工具比没工具更糟】（12.0 < 15.7）。

    ④ ★★★ ✅ 主动扔掉上下文比留着更好，值 3 分。
       🔑 最大理由不是省地方，是【旧信息会主动骗它】。

    ⑤ ★★ 许可 ≠ 沙箱。前者拦命令文本，后者靠操作系统内核。
       ⚠️ 榜单分数必然出自最放开的档位——但没人写出来。

    ⑥ ★★★ ✅ 两家产品的底层机制几乎相同
       （Seatbelt / bubblewrap），差异只在露出多少旋钮。
       Codex 的 CLI 开源，Claude Code 不开源。
       ⚠️ 但两家的【模型】都不开源。

    ⑦ ★★★ ✅ DeepSeek-V4 是唯一同时公开了脚手架规格和分数的：
       2 个工具、500 步、512K 上下文。
       🔑 且它明写了工具结果的【回传方式】会改变模型行为。

    ⑧ ★★★ 所以：榜单上从来没有"模型的分数"，
       只有【模型 + 脚手架 + 子集 + 预算 + 口径】这一整套系统的分数。
       ⟹ 🔑 少了任何一项，那个数字就不能横向比较。
