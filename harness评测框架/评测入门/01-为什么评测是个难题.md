
# 01 · 为什么"给模型打分"比想象中难得多

> 标记：✅ = 论文/源码原文可查证 ｜ ⚠️ = 我的推断 ｜ ★ = 重点 ｜ 🔑 = 关键结论

---

## 1.1 先破除一个直觉

**新手最自然的想法**：

```
    评测不就是考试吗？
    ⟹ 出一堆题 → 让模型答 → 数对了几道 → 算个百分比
    ⟹ ★ 这有什么难的？
```

**如果真这么简单，就不会有这份文档了。** 先看一个真实现象：

```
    ⚠️（演示用的典型情形，非某次具体披露的实测）
    ★★ 同一个模型、同一套题（MMLU），换一家机构去测：

        A 机构报：  68.2
        B 机构报：  74.5
        C 机构报：  61.9

    ⟹ 模型没变，题没变，★ 最高和最低差了 12.6 个百分点。
    ⟹ 这不是谁作弊，是【评测方法不同】。
```

> ⚠️ **先立一条贯穿全书的用词纪律**：上面只能说「差了 12.6 **个百分点**」，不能说「差了 12.6%」。⟹ 74.5 与 61.9 的**差**是 12.6 个百分点，而 74.5 相对 61.9 的**相对涨幅**是 12.6 ÷ 61.9 = **20.4%**。★ 这是两个数，混用会直接把结论说错。

> 🔑 **本章要建立的第一个认知**：**分数不是模型的属性，是「模型 + 评测方法」这个组合的属性。** ⟹ 脱离评测方法谈分数，等于没说。★★ §1.3b 会用一个能拿笔验算的例子，把这句话从口号变成算术。

## 1.2 名词先统一

因为后面会反复出现，这里一次讲清（这些词经常被混用，但**指的不是一回事**）：

| 词 | 英文全称 / 字面意思 | 中文 | 是什么 | 举例 |
|---|---|---|---|---|
| **benchmark** | benchmark（基准点、水准标记） | 基准 / 评测集 | ★ **一堆题目和标准答案** | MMLU、GSM8K、SWE-bench |
| **harness** | evaluation harness（马具、挽具） | 评测框架 / 评测台架 | ★★ **跑这些题的那套程序** | lm-evaluation-harness、OpenCompass |
| **metric** | metric（度量） | 指标 | 从模型输出算出的那个数 | 准确率 accuracy、pass@1 |
| **leaderboard** | leaderboard（领先者榜） | 榜单 | 把很多模型的分数排在一起的网页 | Open LLM Leaderboard |

顺手把本章会出现的几个评测集缩写也摊开，之后不再解释：

| 缩写 | 英文全称 | 中文 | 一句话 |
|---|---|---|---|
| **MMLU** | Massive Multitask Language Understanding | 大规模多任务语言理解 | ✅ 57 个科目的四选一知识题（论文 *Measuring Massive Multitask Language Understanding*，ICLR 2021，摘要原文 "covers 57 tasks"） |
| **GSM8K** | Grade School Math 8K（⚠️ 论文未拼写缩写，GSM 即 grade school math） | 小学数学 8 千题 | ✅ 8.5K 道小学应用题，切成 7.5K 训练 + 1K 测试（论文 *Training Verifiers to Solve Math Word Problems* 第 3 页原文 "We segmented these into 7.5K training problems and 1K test problems."） |
| **HumanEval** | ⚠️ 论文没给出缩写全称，字面是「human-written evaluation」（人工编写的评测集） | 人工手写评测集 | ✅ 164 道手写 Python 函数题，平均每题 7.7 个单元测试（Codex 论文 §2.2 原文） |
| **SWE-bench** | SWE = software engineering（软件工程），bench = benchmark | 软件工程基准 | 真实 GitHub 问题单，要模型改代码让测试通过（见 [07 章](07-agentic编码评测与SWE-bench.md)） |
| **LLM** | Large Language Model | 大语言模型 | 本文里「模型」默认指它 |
| **API** | Application Programming Interface | 应用程序接口 | 这里指「只能发请求、拿不到模型内部数据」的那种调用方式 |

```
    ★★ 打个比方，如果 benchmark 是【试卷】：

      harness  = 监考老师 + 阅卷规则
                 （怎么发卷、给不给草稿纸、答案写歪了算不算对）
      metric   = 计分方式（按题算还是按分算）
      leaderboard = 光荣榜

    ⟹ 🔑 同一张试卷，换个监考和阅卷规则，分数就能差十几个百分点。
       ★ 这就是 §1.1 那个现象的来源。
```

> ★ **"harness" 这个词的字面意思是"马具/挽具"**——套在马身上、把马和车连起来的那套皮带。引申到工程里，指**把被测对象套住、驱动它干活、并收集结果的那层外壳**。⟹ ★★ 记住这个意象：**harness 本身不产生智能，它只是"套子"。** 但套子怎么做，直接决定量出来的数是多少。

## 1.3 ★★ 难点一：模型的输出是【自由文本】

**这是所有困难的总根源。**

```
    传统机器学习的评测：
      模型输出 = 一个类别编号（比如 3）
      标准答案 = 3
      ⟹ ★ 相等就对，不等就错。★★ 没有任何歧义。

    大语言模型的评测：
      标准答案 = "72"
      模型输出 = "让我算一下。首先 12 × 6 = 72。所以答案是 72。"
      ⟹ ★★ 这算对吗？
```

**当然算对。但程序怎么知道？**

```
    ★ 要写一段代码，把 "72" 从那一大段话里【抠出来】。
      这段代码叫【答案抽取】（answer extraction）。

    ⟹ 然后问题就来了：

      模型输出 "答案是 72。"         ⟹ 抠出 72，成功
      模型输出 "答案是 72"           ⟹ 抠出 72，成功
      模型输出 "结果为 72 个"        ⟹ 抠得出来吗？取决于你的正则怎么写
      模型输出 "\\boxed{72}"          ⟹ 数学题常见格式，要单独处理
      模型输出 "是 72，不过如果..."   ⟹ 抠出 72，★ 但它其实在犹豫
      模型输出 "12 × 6 = 72"         ⟹ ⚠️ 有的抽取器会抠到【第一个数字 12】，判错！

    ⟹ 🔑 ★★★ 抽取规则写得不同，同一份模型输出能给出不同的分数。
```

> ★ 这不是假想。[05 章](05-答案抽取与打分.md) 会给你看 lm-evaluation-harness 里真实的抽取代码——**它的默认正则就是一行 `#### (\-?[0-9\.\,]+)`**，而这行正则只对某一种特定格式有效。

## 1.3b ★★★ 把这件事算一遍：同一批输出，三把尺子，三个分数

**上一节说"分数会不同"，这一节把它变成能拿笔验算的数。** 用的不是假想配置，是 lm-evaluation-harness v0.4.12 源码里 GSM8K 任务的**真实默认设置**。

### 第一个发现：框架自己就准备了两把尺子

```yaml
# ✅ lm_eval/tasks/gsm8k/gsm8k.yaml（原文照抄 filter_list 部分）
filter_list:
  - name: "strict-match"
    filter:
      - function: "regex"
        regex_pattern: "#### (\\-?[0-9\\.\\,]+)"
      - function: "take_first"
  - name: "flexible-extract"
    filter:
      - function: "regex"
        group_select: -1
        regex_pattern: "(-?[$0-9.,]{2,})|(-?[0-9]+)"
      - function: "take_first"
```

翻译成人话：

| 尺子名 | 它在找什么 | 找不到怎么办 |
|---|---|---|
| **strict-match**（严格匹配） | `####` 空格后面跟的那串数字——这是 GSM8K 标准答案的固有格式 | ✅ 返回字符串 `[invalid]`（源码默认 `fallback`，见 `lm_eval/filters/extraction.py:28`），而它和任何标准答案都不相等 ⟹ 判错 |
| **flexible-extract**（宽松抽取） | 输出里**所有**数字，然后 `group_select: -1` 取**最后一个** | ✅ 同样返回 `[invalid]`；取最后一个这行逻辑在 `extraction.py:49`：`match = match[self.group_select]` |

> 🔑🔑 **这件事本身就是本章的结论**：框架作者清楚一把尺子量不准，所以让 GSM8K **同时输出两个分数**。⟹ ★★★ 也就是说，"GSM8K 分数"这个说法本身是不完整的——你必须说清是 strict-match 还是 flexible-extract。

### 第二步：一个 4 题的迷你评测集

假设模型对这 4 道题给出了下面这些输出（⚠️ 输出是我为演示构造的，但下面所有抽取结果都是**用真实正则跑出来的**，你可以自己复现）：

| 题号 | 标准答案 | 模型这次的输出（一字不改） |
|---|---|---|
| Q1 | 66 | `12 × 6 = 72，送走 6 个，还剩 66 个。` |
| Q2 | 72 | `12 × 6 = 72` |
| Q3 | 15 | `#### 15` |
| Q4 | 8 | `答案是 8，不过含运费就是 9。` |

### 第三步：三把尺子各抠一遍

第三把尺子「取第一个匹配」不是 GSM8K 的默认配置，但只要把 `group_select` 从 `-1` 改成 `0` 就变成它——这是一行配置的差别。

| 题号 | 标准答案 | strict-match 抠到 | 判 | flexible-extract（取最后一个）抠到 | 判 | 取第一个匹配抠到 | 判 |
|---|---|---|---|---|---|---|---|
| Q1 | 66 | `[invalid]` | 错 | `66` | 对 | `12` | 错 |
| Q2 | 72 | `[invalid]` | 错 | `72` | 对 | `12` | 错 |
| Q3 | 15 | `15` | 对 | `15` | 对 | `15` | 对 |
| Q4 | 8 | `[invalid]` | 错 | `9` | **错** | `8` | 对 |

### 第四步：把准确率算出来

```
    strict-match        ：只有 Q3 对        ⟹ 1 ÷ 4 = 25.0%
    取第一个匹配         ：Q3、Q4 对         ⟹ 2 ÷ 4 = 50.0%
    flexible-extract    ：Q1、Q2、Q3 对     ⟹ 3 ÷ 4 = 75.0%

    ⟹ 🔑🔑 同一个模型、同一套题、同一批一个字都没改的输出：
       ★★★ 25.0% / 50.0% / 75.0%。
    ⟹ 最高和最低差 50.0 个百分点；75% 是 25% 的 3.0 倍。
```

### 三个必须盯住的细节

```
    ★★ ① 看 Q4：模型算对了（8），flexible-extract 却判错。
       ⟹ 它抠到的是"不过含运费就是 9"里的 9。
       ⟹ 🔑 【抽取失败 ≠ 模型答错】，但在最终那个百分比里，两者长得一模一样。
          ★ 这是 05 章的主题。

    ★★ ② 不能"哪把尺子分高就用哪把"。
       ⟹ flexible-extract 在这批题上分最高（75%），但它在 Q4 上判错了，
          错因是它的规则本身有缺陷——只会取最后一个数，不管那个数是不是结论；
          而"取第一个匹配"在 Q3、Q4 上是碰巧对的，也不说明它更好。
       ⟹ ⚠️ 挑一把让自己好看的尺子，叫【把口径调到出分最高】，不叫评测。
       ⟹ 🔑 正确做法是【口径先定、写进报告、之后不再动】。

    ★ ③ 抠出来之后还有一步【归一化】，它也会改分数。
       ✅ gsm8k.yaml 里 exact_match 带了 regexes_to_ignore = [",", "\$", "(?s).*#### ", "\.$"]
       ✅ 这些正则会同时作用在【模型输出】和【标准答案】上
          （lm_eval/api/metrics.py:220-221，两行 re.sub，一行作用在 predictions 一行作用在 references）
       ⟹ 所以模型写 "#### 1,000"、标准答案是 "1000" 时，逗号被两边同时去掉
          ⟹ ★ 判【对】。⚠️ 如果你的配置里少了去逗号这一条，同一份输出就判【错】。
```

> ⚠️ **一个容易被忽略的连带结论**：既然 `regexes_to_ignore` 里那条 `(?s).*#### ` 会把标准答案里 `#### ` 之前的全部解题过程都删掉，说明**框架比对的其实只是末尾那个数**。⟹ ★★ 也就是说 GSM8K 分数**完全不看模型的解题过程对不对**——中间步骤全错、最后碰巧写对数字，一样算对。

## 1.4 ★★ 难点二：怎么问，决定了答得怎么样

**同一道题，换个问法，模型的表现能差很多。** 这叫**提示词敏感性**（prompt sensitivity）。

```
    同一道 MMLU 题目，三种问法：

    ① 直接问：
       "以下哪个是哺乳动物？A.鲨鱼 B.鲸鱼 C.鳄鱼 D.企鹅"

    ② 加个身份设定：
       "你是一位生物学教授。以下哪个是哺乳动物？A.鲨鱼 B..."

    ③ 先给几个做过的例子（★ 这叫 few-shot，见 04 章）：
       "问：哪个是鸟类？A.猫 B.鸽子 ... 答：B
        问：以下哪个是哺乳动物？A.鲨鱼 B..."

    ⟹ ⚠️ 三种问法，同一个模型，分数可以差好几个百分点
       （⚠️ 具体差多少取决于模型和题目，我没有单一来源可引；04 章 §4.3 讲规律）。
```

### ★ "口径"到底指哪些东西：拿真实配置文件看一遍

**很多人以为口径是个虚词。它不是——它就是配置文件里那几行。** 下面是 GSM8K 在 lm-evaluation-harness 里的默认配置，一个分数背后要交代的东西，全在这里：

```yaml
# ✅ lm_eval/tasks/gsm8k/gsm8k.yaml（原文照抄，省略 filter_list 与 metric_list 细节）
task: gsm8k
dataset_path: openai/gsm8k
dataset_name: main
output_type: generate_until
test_split: test
doc_to_text: "Question: {{question}}\nAnswer:"
generation_kwargs:
  until:
    - "Question:"
    - "</s>"
    - "<|im_end|>"
  do_sample: false
  temperature: 0.0
repeats: 1
num_fewshot: 5
metadata:
  version: 3.0
```

| 口径字段 | 这份配置的取值 | 换掉它会发生什么 |
|---|---|---|
| 数据集版本 | `openai/gsm8k` 的 `main` 子集，配置版本 `3.0` | 换子集或版本 ⟹ 题目就不是同一批，分数不可比 |
| 取哪个划分 | `test_split: test`（1K 道） | 有人图快只跑 200 道 ⟹ 抽样噪声几个百分点起，见 11 章 |
| few-shot 数 | `num_fewshot: 5` | 改成 0 ⟹ 模型不知道要写成 `#### 66`，★★ strict-match 会大面积抠不到 |
| 示例怎么选 | 从 `train` 里**随机抽** 5 道，靠随机数种子定 | 换种子 ⟹ 换 5 道例题 ⟹ 分数变（✅ 源码宁可报错也要你传种子，见 04 章 §4.2） |
| 提问模板 | `doc_to_text` 那行 `Question: …\nAnswer:` | 换成对话模板 ⟹ 04 章 §4.4 的头号隐藏杀手 |
| 停在哪 | `until` 三个停止标记（见上方 yaml） | 不设 ⟹ ★ 模型会自己编下一道题，一直写下去（见 02 章 §2.3） |
| 采样方式 | `do_sample: false` + `temperature: 0.0` ⟹ 贪心解码 | 改成 `temperature: 0.8` ⟹ **每次跑分数都不一样**，必须报跑几遍、报方差 |
| 跑几遍 | `repeats: 1` | 改成多遍 ⟹ 就要交代是取平均还是取最好 |
| 抽取规则 | strict-match / flexible-extract 两把 | ★★★ 见 §1.3b：在那 4 道题上差 50.0 个百分点 |
| 判分与归一化 | `exact_match`，`ignore_case: true`，去逗号去美元号 | 少一条归一化 ⟹ `1,000` 对 `1000` 判错 |

> 🔑 **所以"严肃的评测报告"是个可操作的要求，不是态度问题**：上面这张表的每一行，报告里都该找得到。⟹ ⚠️ **只报一个数字、这十行一条都不交代的，那个数字的可比性接近零。** ★★ 11 章会把这张表压成一张七问速用卡。

## 1.5 ★★ 难点三：题目可能已经被模型"背过了"

这叫**数据污染**（data contamination），是评测领域最棘手的问题。

```
    ★ 事情是这样的：

      ① 评测集（比如 GSM8K）是公开的，挂在网上
      ② 训练大模型要抓【全网数据】
      ③ ⟹ ★★ 评测集的题目和答案，很可能【进了训练数据】

    ⟹ 于是模型不是在"解题"，是在"回忆"。
    ⟹ 🔑 分数虚高，而且【你无法从分数本身看出来】。
```

```
    ★ 一个直观的类比：
      期末考的题从往年真题里出，而学生正好把往年真题背熟了。
      ⟹ 他考 95 分。★ 但你不知道他到底会不会。
```

> ⚠️ **这个问题没有干净的解法**，只有一堆各有代价的缓解手段（[06 章](06-数据污染.md) 细讲，那一章还带一份 ✅ 论文实证）：

| 缓解手段 | 怎么做 | 代价 |
|---|---|---|
| 用**新出的**评测集 | 只用模型训练截止日之后才发布的题 | ⚠️ 题量小、噪声大；而且过几个月它也旧了 |
| 用**私有**评测集 | 题目不公开，只公开分数 | ★ 别人无法复现、无法核对，只能信你 |
| 用**动态生成**的题 | 每次考的具体数字/措辞都不一样 | ⚠️ 难度很难保持恒定 ⟹ 不同批次之间自己就不可比 |
| 做**污染检测** | 看模型对题目的"熟悉程度"是否异常高 | ★ 只能给出怀疑，给不出干净的"已污染/未污染"结论 |

> 🔑 **注意这四条的共同点**：它们都不是"消除污染"，而是"把污染的影响挪到一个你能大致估计的位置"。★★ 所以看到任何公开基准上的高分，正确的心态是"这里面有多少是背出来的，我不知道"，而不是"这个模型就这么强"。

## 1.6 ★★★ 难点四：现在的模型不只是"答题"了

**这是最近两年评测领域最大的变化，也是你问到 Claude Code / Codex 时的核心。**

```
    ★ 2020~2023 年的评测长这样：
      给一段文字 → 模型吐一段文字 → 比对答案
      ⟹ ★ 一问一答，一次结束

    ★★ 2024 年之后，要评的东西变成了这样：
      给一个【任务】："修复这个 GitHub issue"
      ⟹ 模型要：读代码库 → 想 → 改文件 → 跑测试 → 看报错 →
                 再改 → 再跑 → ... → 直到通过
      ⟹ ★★★ 可能来回几十轮，中间要【真的执行命令】
```

> 🔑 **这已经不是"考试"了，是"试用期"。**

★★ 评测框架也必须跟着变，两种 harness 要准备的东西完全不是一个量级：

| 要准备什么 | 传统 harness | ★★ agentic harness |
|---|---|---|
| 算力 | 一块 GPU（图形处理器） | GPU，而且要挂住几十轮生成 |
| 运行环境 | 不需要 | ★ 一个 **Docker 容器**（互相隔离的运行环境，一题一个） |
| 代码与数据 | 一份题目文件 | ★ 一份**能真的装起来、跑起来**的代码仓库 |
| 判对错靠什么 | 一个正则表达式 | ★ 一套**真实的测试用例**，真跑一遍看通过没有 |
| 模型与环境之间 | 一次请求一次响应 | ★ 一个能让模型**执行 shell 命令**并读到输出的通道 |
| 出了问题谁背 | 模型或正则 | ⚠️ 还可能是网络、上游依赖包、超时（见 02 章 §2.4） |

> ★ 名词解释：**agentic**（智能体式的）——指模型不是被动答题，而是**主动采取一系列行动、观察结果、再决定下一步**。**agent** 直译"代理人"，在这里就是"能自己干活的模型"。

**这就是为什么 [07 章](07-agentic编码评测与SWE-bench.md) 和 [08 章](08-ClaudeCode与Codex怎么被评.md) 要单独讲：评 Claude Code 和评一个模型答 MMLU，是两套完全不同的机制。**
