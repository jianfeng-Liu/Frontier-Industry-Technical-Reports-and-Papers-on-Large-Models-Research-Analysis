03 · 三个原语：lm-evaluation-harness 的核心抽象

★★ 这一章带你看真源码。它回答一个问题：
上百个评测集、几十种模型后端，怎么可能用一套代码全跑通？

3.1 先看问题有多大

    ★ lm-evaluation-harness 支持的东西：

      评测集：  MMLU、GSM8K、HellaSwag、ARC、TruthfulQA、
                HumanEval、MATH、BBH …… ★ 几百个

      模型后端：HuggingFace、vLLM、SGLang、OpenAI API、
                Anthropic API、llama.cpp、NeMo …… ★ 几十种

    ⟹ ★★ 如果每个评测集都要为每个后端写一遍适配，
       那是【几百 × 几十】次工作量。★★★ 显然不可能这么干。

它的解法，是软件工程里最经典的一招：找出【最小公共集合】。

3.2 ★★★ 答案：只有三个原语

源码里有一行 Literal，直接把答案写死了：

# ✅ lm_eval/api/instance.py:5-7  （原文照抄）
OutputType = Literal[
    "loglikelihood", "loglikelihood_rolling", "generate_until", "multiple_choice"
]

再看模型接口那边——只有三个抽象方法（@abc.abstractmethod 表示"子类必须实现"）：

# ✅ lm_eval/api/model.py
class LM(abc.ABC):                                                    # L25
    @abc.abstractmethod
    def loglikelihood(self, requests) -> list[tuple[float, bool]]:    # L40  ★
    @abc.abstractmethod
    def loglikelihood_rolling(self, requests) -> list[float]:         # L58
    @abc.abstractmethod
    def generate_until(self, requests) -> list[str]:                  # L100 ★

🔑🔑 ★★★ 这就是整个框架的地基。读懂这三个函数，你就读懂了 lm-eval-harness。

    ★★ 翻译成人话：

    ① loglikelihood(上文, 续写)
       "如果接着这段上文，写出这个续写，你觉得有多顺？"
       ⟹ 返回一个分数 + 一个布尔值（是不是贪心解码下最可能的续写）
       ⟹ ★ 这就是 02 章 §2.2 的【判别式评测】

    ② loglikelihood_rolling(一整段文本)
       "这一整段文字，你整体觉得有多顺？"
       ⟹ ★ 用来算【困惑度】（perplexity），衡量语言建模能力
       ⟹ 和 ① 的区别：① 只给续写部分打分，② 给全文打分

    ③ generate_until(上文, 停止条件)
       "接着这段上文写下去，写到遇见停止标记为止。"
       ⟹ ★ 这就是 02 章 §2.3 的【生成式评测】
       ⟹ ★★ 名字里的 until 就是 02 章讲的 stop sequence

★ 那 multiple_choice（多选题）为什么在 OutputType 里，却没有对应的模型方法？
⚠️ 因为它不是一个新能力，它是 ① 的批量版：
一道四选一 ⟹ ★ 拆成 4 次 loglikelihood 调用 ⟹ 比谁的分高 ⟹ 所以模型端不用实现它，任务端拆开就行。

3.3 ★★ 为什么这个设计这么值钱

    ★★★ 关键在于：这三个原语是【所有语言模型都天然具备的】。

      HuggingFace 的模型？   ⟹ 前向一次拿 logits，能算 ①②；能 generate，能 ③
      vLLM / SGLang？        ⟹ 同上
      OpenAI API？           ⟹ ⚠️ 只能 ③（见下方警告）
      llama.cpp？            ⟹ 都能

    ⟹ 于是工作量从【几百 × 几十】塌缩成【几百 + 几十】：
       ★ 评测集只需要说清"我要调哪个原语、参数是什么"
       ★ 模型后端只需要实现三个函数
       ⟹ ★★ 两边互不相识，通过这三个原语对接。

🔑 这在软件工程里叫窄腰设计（narrow waist）。
★ 像沙漏：上面很多（评测集），下面很多（模型后端）， ★★ 中间【故意做得极窄】（三个函数）。 ⟹ 互联网的 IP 协议、操作系统的系统调用，都是这个套路。

⚠️★★ 一个必须知道的现实约束

    ⚠️ 闭源 API 模型（GPT、Claude 等）【拿不到 loglikelihood】。
       ★ 因为服务商不返回逐 token 的概率。

    ⟹ 后果很直接：
       ★★ 对这些模型，判别式评测（②章的第①类）【做不了】，
          只能改用"让它直接输出 A/B/C/D"的生成式做法。

    ⟹ 🔑🔑 于是出现一个非常容易踩的陷阱：
       ★★★ 榜单上开源模型和闭源模型的 MMLU 分数，
            很可能【根本不是同一种测法测出来的】。
       ⟹ ⚠️ 严格来说不该直接比大小。

★ 这一点在 11 章 还会展开。它是最常见的误读来源之一。

3.4 一道题在框架里怎么流动

    ★ 以 GSM8K（小学数学应用题）一道题为例：

    ┌─ ① 任务加载 ─────────────────────────────────────┐
    │  Task 类读配置，拿到题目 doc                       │
    │  ✅ lm_eval/api/task.py:64  class Task(abc.ABC)   │
    └──────────────────────────────────────────────────┘
                          ↓
    ┌─ ② 拼提示词 ─────────────────────────────────────┐
    │  fewshot_context() 把【描述 + N 个示例 + 本题】拼起来│
    │  ✅ task.py:447  def fewshot_context(...)         │
    │  ⟹ ★ 04 章专门讲这一步                            │
    └──────────────────────────────────────────────────┘
                          ↓
    ┌─ ③ 造请求 ───────────────────────────────────────┐
    │  construct_requests() 生成 Instance 对象           │
    │  ✅ task.py:382                                   │
    │  ✅ Instance 定义在 api/instance.py:11            │
    │     request_type = "generate_until"   ★ 用哪个原语 │
    │     arguments    = (提示词, {"until": ["\n\n"]})   │
    └──────────────────────────────────────────────────┘
                          ↓
    ┌─ ④ 调模型 ───────────────────────────────────────┐
    │  ★ 框架把成千上万个 Instance 攒成批，一次性喂给模型 │
    │  model.generate_until(instances)                  │
    │  ⟹ ★★ 这里就接上了你的【推理框架】：               │
    │     vLLM / SGLang 在这一步发挥作用                 │
    └──────────────────────────────────────────────────┘
                          ↓
    ┌─ ⑤ 过滤/抽取 ────────────────────────────────────┐
    │  apply_filters() ★ 从生成的文字里抠出答案          │
    │  ✅ task.py:505                                   │
    │  ⟹ ★ 05 章专门讲这一步                            │
    └──────────────────────────────────────────────────┘
                          ↓
    ┌─ ⑥ 打分 ─────────────────────────────────────────┐
    │  process_results() 单题对错   ✅ task.py:403       │
    │  aggregation()     汇总成最终分数 ✅ task.py:416   │
    └──────────────────────────────────────────────────┘

★★ 注意第 ④ 步：这是你手上三份文档接起来的地方。
```
训练框架 ⟹ 把模型练出来
推理框架 ⟹ vLLM / SGLang 把模型跑起来
★ 评测框架 ⟹ 站在推理框架【上面】，反复调它，然后打分

⟹ 🔑 所以评测跑得快不快，很大程度上取决于你的推理后端。
   ★ 用 HuggingFace 原生跑 MMLU 要几小时，换 vLLM 可能十几分钟。

```

3.5 ★ Instance：贯穿全程的那个数据结构

# ✅ lm_eval/api/instance.py:11-27  （原文照抄，略去部分）
@dataclass
class Instance:
    request_type: OutputType     # ★ 用哪个原语
    doc: dict                    # 原始题目
    arguments: tuple             # ★ 传给原语的参数
    idx: int
    resps: list = ...            # ★ 模型的原始回答
    filtered_resps: dict = ...   # ★★ 抽取/过滤之后的答案
    task_name: ... ; doc_id: ... ; repeats: ...

    ★★ 盯住最后两个字段，它们是一对：

      resps          = 模型【原封不动】吐出来的东西
      filtered_resps = ★ 经过抽取规则处理后的东西

    ⟹ 🔑🔑 框架【两份都留着】，这个设计非常关键：
       ★★★ 出现分数异常时，你可以把 resps 打开看模型到底说了什么，
            判断是【模型答错了】还是【抽取规则没抠对】。

    ⟹ ⚠️ 这两种情况在最终分数上【长得一模一样】，
       但原因和解法完全相反。★ 12 章会讲怎么排查。

3.6 本章小结

    ★★ 三句话：

    ① 整个框架建立在【三个原语】上：
       loglikelihood / loglikelihood_rolling / generate_until
       ✅ lm_eval/api/model.py:40 / 58 / 100

    ② 这是【窄腰设计】：几百个评测集 + 几十个后端，
       ★ 靠三个函数解耦，工作量从相乘变成相加

    ③ ⚠️★★ 闭源 API 拿不到 loglikelihood
       ⟹ 开源模型和闭源模型的同名分数，★★★ 可能不是一种测法

    ⟹ 🔑 记住那条数据流：
       题目 → 拼提示词 → 造 Instance → 调原语 → 抽取 → 打分
       ★ 后面每一章，都是在放大其中某一步。
