
# 03 · 三个原语：lm-evaluation-harness 的核心抽象

> ★★ 这一章带你看真源码。它回答一个问题：
> **上百个评测集、几十种模型后端，怎么可能用一套代码全跑通？**

---

## 3.1 先看问题有多大

**先把"上百个""几十种"换成真实数字**，这样后面算工作量才有意义。下面三个数是从本地源码目录数出来的（✅ lm-evaluation-harness **v0.4.12**，`harness评测框架/源码/lm_eval-0.4.12/`）：

| 数出来的东西 | 怎么数的 | 数量 |
|---|---|---|
| **评测集家族** | `lm_eval/tasks` 下的**一级子目录**个数（mmlu、gsm8k、hellaswag……各算一个） | **213** 个 |
| （展开之后的配置文件） | `lm_eval/tasks` 下 `.yaml` 文件总数（每种语言、每个学科子集都是一个文件） | **13533** 个 |
| **模型后端** | `@register_model(...)` 里的注册名，去重后 | **35** 个 |

> ⚠️ **口径说明**：这三个数会随版本变；引用时必须带版本号。★ 下面所有算术都用"213 个评测集家族 × 35 个后端"这一组，不用 13533 那个数——因为同一个家族的几千个 yaml 共用同一套适配代码，拿它算会把工作量夸大几十倍。

```
    ⟹ ★★ 如果每个评测集家族都要为每个后端单独写一遍适配，
       那是【213 × 35】次工作量。★★★ 显然不可能这么干。
```

**它的解法，是软件工程里最经典的一招：找出【最小公共集合】。**

---

## 3.2 ★★★ 答案：只有三个原语

源码里有一行 `Literal`（"字面量类型"，把某个变量的取值范围写死成一份清单），直接把答案写死了：

```python
# ✅ lm_eval/api/instance.py:5-7  （原文照抄）
OutputType = Literal[
    "loglikelihood", "loglikelihood_rolling", "generate_until", "multiple_choice"
]
```

再看模型接口那边——**只有三个抽象方法**（`@abc.abstractmethod` 表示"子类必须实现"）：

```python
# ✅ lm_eval/api/model.py
class LM(abc.ABC):                                                    # L25
    @abc.abstractmethod
    def loglikelihood(self, requests) -> list[tuple[float, bool]]:    # L40  ★
    @abc.abstractmethod
    def loglikelihood_rolling(self, requests) -> list[float]:         # L58
    @abc.abstractmethod
    def generate_until(self, requests) -> list[str]:                  # L100 ★
```

> 🔑🔑 **★★★ 这就是整个框架的地基。读懂这三个函数，你就读懂了 lm-eval-harness。**

```
    ★★ 翻译成人话：

    ① loglikelihood(上文, 续写)
       "如果接着这段上文，写出这个续写，你觉得有多顺？"
       ⟹ 返回一个分数 + 一个布尔值（是不是贪心解码下最可能的续写）
       ⟹ ★ 这就是 02 章 §2.2 的【判别式评测】

    ② loglikelihood_rolling(一整段文本)
       "这一整段文字，你整体觉得有多顺？"
       ⟹ ★ 用来算【困惑度】（perplexity），衡量语言建模能力
       ⟹ 和 ① 的区别：① 只给续写部分打分，② 给全文打分

    ③ generate_until(上文, 停止条件)
       "接着这段上文写下去，写到遇见停止标记为止。"
       ⟹ ★ 这就是 02 章 §2.3 的【生成式评测】
       ⟹ ★★ 名字里的 until 就是 02 章讲的 stop sequence
```

**把 4 种 `OutputType`、3 个方法、02 章的 3 种范式对起来，一张表看完**：

| 配置里的 `output_type` | 模型端要实现什么 | 对应 02 章的范式 | 典型任务 |
|---|---|---|---|
| `loglikelihood` | `LM.loglikelihood`（✅ `model.py:40`） | ① 判别式 | 给单个续写打分 |
| `multiple_choice` | ★ **什么都不用实现**——任务端拆成 N 次 `loglikelihood` | ① 判别式 | MMLU、HellaSwag、ARC |
| `loglikelihood_rolling` | `LM.loglikelihood_rolling`（✅ `model.py:58`） | ⚠️ 不属于三种范式，它量的是语言建模能力 | wikitext 困惑度 |
| `generate_until` | `LM.generate_until`（✅ `model.py:100`） | ② 生成式 | GSM8K、MATH、HumanEval |
| ★★ （清单里根本没有） | — | ③ agentic | ⚠️ **lm-eval-harness 做不了这一类**，要另一套 harness（[07 章](07-agentic编码评测与SWE-bench.md)） |

> ★ **那 `multiple_choice`（多选题）为什么在 `OutputType` 里，却没有对应的模型方法？** ⚠️ 因为它不是一个新能力，**它是 ① 的批量版**：一道四选一 ⟹ ★ 拆成 4 次 `loglikelihood` 调用 ⟹ 比谁的分高。⟹ 所以模型端不用实现它，任务端拆开就行。✅ 拆开这件事在源码里是 `MultipleChoiceTask.construct_requests`（`lm_eval/api/task.py:1694-1705`），它对 `doc["choices"]` 里的每个选项各造一个 `Instance`。

> 🔑 **上面那张表最后一行值得单独记住**：★★★ 三个原语撑起了 02 章的 ① 和 ②，但**撑不起 ③**。⟹ 原因很直接：agentic 评测需要的不是"给我一段文字的概率"，而是"帮我在一个容器里执行这条命令并把输出还给我"——⚠️ 那是一个**完全不同的抽象**。⟹ ★ 所以你会看到 SWE-bench 有自己独立的一套 harness，不挂在 lm-eval-harness 下面。

## 3.3 ★★ 为什么这个设计这么值钱

```
    ★★★ 关键在于：这三个原语是【所有语言模型都天然具备的】。

      HuggingFace 的模型？   ⟹ 前向一次拿 logits，能算 ①②；能 generate，能 ③
      vLLM / SGLang？        ⟹ 同上
      llama.cpp / gguf？     ⟹ 都能
      闭源对话 API？          ⟹ ⚠️ 只能 ③（见本节后半的源码证据）

    ⟹ 于是工作量从【相乘】塌缩成【相加】：
       ★ 评测集只需要说清"我要调哪个原语、参数是什么"
       ★ 模型后端只需要实现三个函数
       ⟹ ★★ 两边互不相识，通过这三个原语对接。
```

### ★★★ 把这笔账算出来

用 §3.1 数出来的真实数字（213 个评测集家族、35 个后端）：

| | 不用窄腰：每个评测集为每个后端单独适配 | ★★ 用窄腰：两边只跟三个原语打交道 |
|---|---|---|
| **一共要写多少份适配** | 213 × 35 = **7455** 份 | 213 + 35 = **248** 份 |
| **新加 1 个评测集要动几处** | 35 处（每个后端都得改一遍） | **1 处**（写一个 yaml，声明用哪个原语） |
| **新加 1 个后端要动几处** | 213 处（每个评测集都得改一遍） | **1 处**（实现三个函数） |
| **两边要不要互相认识** | ⚠️ 要。评测集作者必须懂每个后端 | ★ 不要。互不相识 |

```
    ⟹ 7455 ÷ 248 ≈ 30.1 倍
    ⟹ 省掉的比例 = (7455 − 248) ÷ 7455 = 7207 ÷ 7455 = 96.7%

    ⟹ 🔑🔑 ★★★ 工作量从【相乘】变成【相加】——这就是窄腰值钱的地方。
```

> ⚠️ **一句话厘清这个 96.7% 到底是什么**：它是"**要写的适配份数**少了 96.7%"，★ **不是"代码量少了 96.7%"**。⟹ 每份适配的复杂度并不相等：实现一个 `generate_until` 后端可能上千行，写一个评测集 yaml 可能二十行。⟹ 🔑 报任何"减少 X%"的数字，都要说清分母是什么。

> 🔑 这在软件工程里叫**窄腰设计**（narrow waist，字面意思"窄的腰"）。★ 像沙漏：上面很多（213 个评测集），下面很多（35 个后端），★★ 中间【故意做得极窄】（3 个函数）。⟹ 互联网的 IP 协议（Internet Protocol，网际协议）、操作系统的系统调用，都是这个套路。

### ⚠️★★ 一个必须知道的现实约束

**结论先说**：★★★ 真正的分界线**不在"开源还是闭源"**，而在**你用的那个端点会不会把提示词的逐 token 概率还给你**。

源码里三处证据，都是原文照抄：

```python
# ✅ lm_eval/models/anthropic_llms.py:269-273
    def loglikelihood(self, requests, disable_tqdm: bool = False):
        raise NotImplementedError("No support for logits.")

    def loglikelihood_rolling(self, requests, disable_tqdm: bool = False):
        raise NotImplementedError("No support for logits.")
```

```python
# ✅ lm_eval/models/openai_completions.py:312-314（长字符串里的两个 GitHub 链接已省略）
    def loglikelihood(self, requests, **kwargs):
        raise NotImplementedError(
            "Loglikelihood (and therefore `multiple_choice`-type tasks) is not supported "
            "for chat completions as OpenAI does not provide prompt logprobs. ..."
        )
```

```python
# ✅ lm_eval/models/openai_completions.py:268-275（原文照抄）
    def loglikelihood(self, requests, **kwargs):
        assert self.model in [
            "babbage-002",
            "davinci-002",
        ], (
            f"Prompt loglikelihoods are only supported by OpenAI's API for {['babbage-002', 'davinci-002']}."
        )
        return super().loglikelihood(requests, **kwargs)
```

**把它整理成一张表**（`logprobs` = log probabilities，逐 token 的对数概率）：

| 后端 | `loglikelihood`（① 判别式） | `generate_until`（② 生成式） | 源码依据 |
|---|---|---|---|
| HuggingFace 本地权重 | 能 | 能 | 前向一次就有 logits |
| vLLM / SGLang 本地 | 能 | 能 | 同上 |
| llama.cpp / gguf | 能 | 能 | 同上 |
| 自己起的 OpenAI 兼容 `/v1/completions`（例如 vLLM 的 server） | 能 —— ★ 因为这个端点会把提示词的 logprobs 返回给你 | 能 | `LocalCompletionsAPI.parse_logprobs`（`openai_completions.py:16`、`:99`） |
| OpenAI 官方 `/v1/completions` | ⚠️ **只对 `babbage-002`、`davinci-002` 两个老模型能** | 能 | `openai_completions.py:268-275` 那句 `assert` |
| OpenAI 官方 `/v1/chat/completions` | **不能** | 能 | `openai_completions.py:312-314` 直接抛 `NotImplementedError` |
| Anthropic API | **不能** | 能 | `anthropic_llms.py:269-273`，理由写着 "No support for logits." |

```
    ⟹ 后果很直接：
       ★★ 对"只有对话端点"的模型，判别式评测（02 章的第 ① 类）【做不了】，
          只能改用"让它直接输出 A/B/C/D"的生成式做法。
       ⟹ 而那条路要过 01 章 §1.3b 的【答案抽取】这一关。

    ⟹ 🔑🔑 于是出现一个非常容易踩的陷阱：
       ★★★ 榜单上开源模型和闭源模型的 MMLU 分数，
            很可能【根本不是同一种测法测出来的】：
              开源模型：比 4 个选项的 loglikelihood，★ 瞎猜也有 25% 地板
              闭源模型：让它写出 "B"，再用正则抠，★ 抠不到就算错，没有地板
       ⟹ ⚠️ 严格来说不该直接比大小。
```

> ★ 这一点在 [11 章](11-怎么读懂一张榜单.md) 还会展开。**它是最常见的误读来源之一。**

## 3.4 一道题在框架里怎么流动

**以 GSM8K 一道题为例。六步，一条直线**：

```
    题目 doc（一道应用题 + 标准答案）
      |
      |  ① Task 读 yaml 配置，取出这道题
      v
    提示词字符串（5 个示例 + 本题）
      |
      |  ② fewshot_context()
      v
    Instance 对象（记着"用哪个原语、参数是什么"）
      |
      |  ③ construct_requests()
      v
    模型生成的原始文字
      |
      |  ④ model.generate_until()   <-- ★★ 推理框架在这一步发挥作用
      v
    抠出来的答案
      |
      |  ⑤ apply_filters()
      v
    单题对错  -->  全集平均分
      ⑥ process_results() / aggregation()
```

每一步的源码位置，以及跑 GSM8K 时这一步的**真实取值**：

| 步 | 干什么 | 源码位置（✅ v0.4.12） | 跑 GSM8K 时的真实值（✅ `gsm8k.yaml`） |
|---|---|---|---|
| **① 任务加载** | `Task` 类读 yaml 配置，拿到一道题 `doc` | `lm_eval/api/task.py:64` `class Task(abc.ABC)` | `dataset_path: openai/gsm8k`，`dataset_name: main`，`test_split: test`（1K 道题） |
| **② 拼提示词** | `fewshot_context()` 把【描述 + N 个示例 + 本题】拼成一个字符串 | `task.py:447` | `num_fewshot: 5`；每题按 `doc_to_text` 拼成 `Question: …` 换行 `Answer:` ⟹ ★ [04 章](04-few-shot与提示词.md) 专门讲这一步 |
| **③ 造请求** | `construct_requests()` 生成 `Instance` 对象 | `task.py:382`；`Instance` 定义在 `api/instance.py:11` | `request_type = "generate_until"`；参数里带上 `until` 三个停止标记、`do_sample: false`、`temperature: 0.0` |
| **④ 调模型** | ★ 框架把成千上万个 `Instance` 攒成批，一次性喂给模型 | 抽象方法在 `api/model.py:100`，调用形式 `model.generate_until(instances)` | ★★ 这里接上你的【推理框架】：vLLM / SGLang 在这一步发挥作用 |
| **⑤ 过滤/抽取** | `apply_filters()` ★ 从生成的文字里抠出答案 | `task.py:505` | ★★ **两条流水线并行**：`strict-match` 与 `flexible-extract` ⟹ ★ [05 章](05-答案抽取与打分.md) 专门讲这一步 |
| **⑥ 打分** | `process_results()` 判单题对错；`aggregation()` 汇总成最终分数 | `task.py:403` / `task.py:416` | `exact_match` 比对（带 `regexes_to_ignore` 归一化），`aggregation: mean` ⟹ ★★ 最终输出**两个**分数，一个 filter 一个 |

> ★★ **注意第 ④ 步**：这是你手上三份文档接起来的地方。训练框架 ⟹ 把模型练出来；推理框架 ⟹ vLLM / SGLang 把模型跑起来；★ 评测框架 ⟹ 站在推理框架**上面**，反复调它，然后打分。⟹ 🔑 所以评测跑得快不快，很大程度上取决于你的推理后端。

> ⚠️ **顺手纠一个到处被说错的算法**：假设某次评测从 **3 小时**降到 **15 分钟**（⚠️ 只是量级示意，不是实测；真要报这种数字，必须带上"哪块卡、几张、batch 多大、几 shot、多少道题"）。⟹ **时间减少了** (180 − 15) ÷ 180 = **91.7%**；**加速倍数是** 180 ÷ 15 = **12 倍**。★★★ "时间减少 91.7%"和"加速 91.7%"是两回事——后者会被理解成只快了不到一倍。🔑 **报性能只报一种：要么报"时间从 A 降到 B"，要么报"加速 N 倍"，别报百分比。**

## 3.4b ★★★ 换掉这条流水线上的一个零件，会发生什么

**§3.4 那六步，每一步都是一个可替换的零件。这张表回答一个很实际的问题：换掉其中一个，那个分数还能不能叫原来的名字？**

| 换掉哪一环 | 具体动作 | 分数会怎么变 | ★ 换完还能叫同一个分数吗 |
|---|---|---|---|
| **① 数据集版本** | `dataset_name` 换子集，或 yaml 里 `metadata.version` 升级 | 题目不是同一批 ⟹ ⚠️ 方向无法预测 | **不能**。必须把版本号一起报出来 |
| **① 题量** | 1K 道全跑 → 图快只抽 200 道 | ⚠️ 抽样噪声上来，几个百分点的差距变得没意义 | **不能**。必须报题量 |
| **② few-shot 数** | `num_fewshot: 5` → `0` | ★★ 模型不知道要写成 `#### 66` ⟹ strict-match 大面积抠不到 ⟹ 分数往低走 | **不能** |
| **② 示例的随机种子** | 换一个 `random.Random` 种子 | 换到另外 5 道例题 ⟹ ⚠️ 小幅变动，方向不定 | ⚠️ 勉强，但必须报种子 |
| **② 提问模板** | `doc_to_text` 从 `Question: …` 换成对话模板 | ★★ 对基座模型和对话模型的影响**方向相反**（见 04 章 §4.4） | **不能** |
| **③ 停止标记** | 删掉 `until` 里的 `"Question:"` | 模型自己编下一道题 ⟹ 抽取器抠到后面那道题的数 ⟹ 分数往低走 | **不能** |
| **③ 采样设置** | `temperature: 0.0` → `0.8` | ★ 每次跑都不一样 ⟹ 必须跑多遍、报均值和方差 | **不能**（口径变成了"采样 N 次的均值"） |
| **④ 推理后端** | `hf` → `vllm` | ⚠️ 原则上分数不该变，实际会有小差异（批处理顺序与数值精度不同） | ⚠️ 勉强，但要交代后端 |
| **⑤ 抽取规则** | `strict-match` ↔ `flexible-extract` | ✅ 01 章 §1.3b 那 4 道题：**25.0% 对 75.0%**，差 50.0 个百分点 | ★★★ **绝对不能**。这是最常见的偷换 |
| **⑥ 判分归一化** | 从 `regexes_to_ignore` 里删掉那条去逗号的规则 | 模型写 `1,000`、标准答案 `1000` ⟹ 判错 ⟹ 分数往低走 | **不能** |
| **⑥ 聚合方式** | `aggregation: mean`（按题平均）→ 按科目先平均再平均（MMLU 常见做法） | ★★ 各科题量不相等时，两种算法给出**不同的数** | **不能** |

```
    ⟹ 🔑🔑 数一下：11 行里，9 行的答案是"不能叫同一个分数"。

    ⟹ ★★★ 所以「MMLU 74.5」这个说法本身不构成一个可比的事实。
       它必须挂在一整套口径上，否则它就只是一个装饰数字。
    ⟹ ★ 反过来这也是好消息：这些零件都写在 yaml 里，
       ⟹ 🔑 【报口径】这件事在工程上等于【把那个 yaml 附上】。
```

## 3.5 ★ Instance：贯穿全程的那个数据结构

```python
# ✅ lm_eval/api/instance.py:11-25  （原文照抄，省略 field(...) 的默认值细节）
@dataclass
class Instance:
    request_type: OutputType     # ★ 用哪个原语
    doc: dict                    # 原始题目
    arguments: tuple             # ★ 传给原语的参数
    idx: int
    metadata: Tuple[...] = ...   # (task_name, doc_id, repeats) 三元组
    resps: list = ...            # ★ 模型的原始回答
    filtered_resps: dict = ...   # ★★ 抽取/过滤之后的答案
    # task_name / doc_id / repeats 由 __post_init__ 从 metadata 解包出来
```

```
    ★★ 盯住 resps 和 filtered_resps，它们是一对：

      resps          = 模型【原封不动】吐出来的东西
      filtered_resps = ★ 经过抽取规则处理后的东西

    ⟹ 🔑🔑 框架【两份都留着】，这个设计非常关键：
       ★★★ 出现分数异常时，你可以把 resps 打开看模型到底说了什么，
            判断是【模型答错了】还是【抽取规则没抠对】。

    ⟹ ⚠️ 这两种情况在最终分数上【长得一模一样】，
       但原因和解法完全相反。★ 12 章会讲怎么排查。
```

**用 01 章 §1.3b 的 Q4 对一遍，就知道这两个字段为什么必须都留着**：

| 字段 | Q4 里的值 | 你能从它读出什么 |
|---|---|---|
| `doc` 里的标准答案 | `8` | — |
| `resps`（原始回答） | `答案是 8，不过含运费就是 9。` | ★★ 模型**算对了**：它说了 8 |
| `filtered_resps`（flexible-extract 之后） | `9` | ★ 抽取器取了最后一个数字，抠错了 |
| 最终这道题的分 | `0` | ⚠️ **只看这个 0，你根本分不清是模型错还是抽取错** |

> 🔑 **所以排查分数异常的第一步永远是"打开 `resps` 看原文"**，而不是去怀疑模型。⟹ ★ `filtered_resps` 是 `dict` 而不是 `list`，正是因为一次运行可能挂着多个 filter（GSM8K 就挂了两个），★★ 每个 filter 的抽取结果都要单独存一份。
