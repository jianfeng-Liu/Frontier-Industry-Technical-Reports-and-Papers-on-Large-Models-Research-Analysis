04 · few-shot 与提示词：分数差异的第一大来源

★★ 这一章放大 03 章数据流的第 ② 步「拼提示词」。
它是"同模型同题目分数差十几分"的头号原因。

4.1 few-shot 是什么

先把词拆开：

    shot  = "一发"、"一次尝试"，这里指【给模型看的示例】
    few   = "少数几个"

    ⟹ few-shot = ★ 在正式提问之前，先给模型看几个做好的例题
    ⟹ zero-shot（零示例）= ★ 一个例题都不给，直接问

长什么样：

    ★ 5-shot 的 GSM8K 提示词，实际是这样一大坨：

    ┌────────────────────────────────────────────────┐
    │ 问：小红有 3 个苹果，又买了 5 个，一共几个？      │  ← 示例 1
    │ 答：3 + 5 = 8。答案是 8。                       │
    │                                                │
    │ 问：一支笔 4 元，买 6 支多少钱？                 │  ← 示例 2
    │ 答：4 × 6 = 24。答案是 24。                     │
    │                                                │
    │ ...（示例 3、4、5）...                          │
    │                                                │
    │ 问：小明有 12 盒饼干，每盒 6 块，一共几块？      │  ← ★ 真正要答的题
    │ 答：                                            │  ← ★★ 模型从这里开始写
    └────────────────────────────────────────────────┘

🔑 ★★ 为什么要给示例？两个作用，第二个才是关键：
```
① 让模型知道【题该怎么解】 —— ⚠️ 作用其实有限
② ★★★ 让模型知道【答案该怎么写】 —— ★ 这才是主要作用

⟹ 示例里都写"答案是 X"，模型就会照着写"答案是 X"
⟹ ★★ 于是 05 章的【答案抽取】才有稳定的格式可抠

⟹ 🔑🔑 few-shot 的本质是【格式对齐】，不是【教它做题】。

```

4.2 源码里的这一步

# ✅ lm_eval/api/task.py:447
def fewshot_context(self, doc, num_fewshot, rnd=None, description=None, **kwargs):
    """Returns a fewshot context string that is made up of a prepended description
    (if provided), the `num_fewshot` number of examples, and an appended prompt example.
    ...
    :param rnd: random.Random
        The pseudo-random number generator used to randomly sample examples.
        WARNING: This is currently a required arg although it's optionalized with a default `None`.
    """

    ★★ 注意源码注释里那句全大写的 WARNING，以及参数 rnd。

    ⟹ 🔑 它在说：★★★【示例是随机抽的，你必须给随机数种子】。
    ⟹ ⚠️ 换个种子 ⟹ 抽到不同的示例 ⟹ ★ 分数就变了。

紧接着的代码强制了这件事：

# ✅ lm_eval/api/task.py:462-469
if rnd is None:
    if self.fewshot_rnd is not None:
        rnd = self.fewshot_rnd
    else:
        raise ValueError(
            "A `random.Random` generator argument must be provided to `rnd`"
        )

★ 它宁可直接报错，也不给默认值。 这是很负责任的设计：
⟹ 强迫你意识到"这里有随机性"，而不是让你在不知情的情况下拿到不可复现的结果。

4.3 ★★ 到底能差多少

先说结论：⚠️ 差多少取决于模型和评测集，但足以颠倒榜单名次。

    ★ 三个已经形成共识的经验规律（⚠️ 我的归纳，非单一论文结论）：

    ① 模型越小，few-shot 影响越大
       ⟹ ★ 大模型 0-shot 也知道怎么答；小模型必须靠示例带格式

    ② ★★ 经过指令微调的模型，few-shot 反而可能【掉分】
       ⟹ 它已经被训练成"听懂人话直接答"，
          ★ 你塞一堆"问：...答：..."反而把它带跑偏

    ③ 数学/推理题受 few-shot 影响最大
       ⟹ ★ 因为示例还顺带演示了【要写解题步骤】
          （这就是 chain-of-thought，见 §4.5）

🔑 规律 ② 特别值得注意，因为它直接制造了一类误读：
⚠️ 场景：拿一套 5-shot 的老配置去测新的对话模型 ⟹ 分数偏低 ⟹ ★★ 你以为"新模型不行"，实际是【测法和模型不匹配】

4.4 ★★ 还有一个更隐蔽的变量：对话模板

这是新手最容易完全忽略、但影响巨大的一环。

    ★ 现在的模型分两种：

      基座模型（base model）：
        ⟹ 只会【续写】。你给它 "今天天气"，它接 "很好，适合出门"
        ⟹ ★ 适合 few-shot 那种"问：...答：..."的格式

      对话模型（chat / instruct model）：
        ⟹ 被训练成【听指令、按角色说话】
        ⟹ ★★ 它期待输入长这样（这叫【对话模板】chat template）：

           <|im_start|>system
           You are a helpful assistant.<|im_end|>
           <|im_start|>user
           12 盒饼干每盒 6 块，一共几块？<|im_end|>
           <|im_start|>assistant

    ⚠️★★★ 于是产生了评测里最经典的一个坑：

      用【不套模板】的方式去测【对话模型】
      ⟹ 模型收到的是它从没见过的格式
      ⟹ ★ 表现显著低于真实水平
      ⟹ 🔑 而这在分数上看不出来，只会显示"这个模型不行"

    ⟹ ⚠️ 反过来，给基座模型套对话模板，同样会掉分。

🔑 所以一份可信的评测报告，必须交代：
□ 测的是基座还是对话版本 □ ★ 有没有套 chat template □ 套的是哪个版本的模板（★★ 模型更新时模板也会改） □ 系统提示词写了什么
⚠️ 这四条任何一条不同，分数就不能直接比。

4.5 ★ 顺带说清 CoT

CoT = Chain-of-Thought（思维链），指让模型先写推理过程、再给答案。

    不用 CoT：
      问：12 盒饼干每盒 6 块，一共几块？
      答：72                              ← ★ 直接蹦答案

    ★ 用 CoT：
      问：12 盒饼干每盒 6 块，一共几块？
      答：每盒 6 块，共 12 盒，所以 6 × 12 = 72。答案是 72。
                                          ← ★★ 先算再答

    ★★ 怎么让它这么做？两种办法：

    ① few-shot 示例里就这么写 ⟹ ★ 模型照着学（04 章 §4.1 的作用 ②）
    ② 直接在提示词里说 "Let's think step by step"

    ⟹ ⚠️ 注意：现在的【推理模型】（如 DeepSeek-R1、o 系列）
       ★★ 是被【训练】成自动 CoT 的，不需要你提示。
       ⟹ 这又带来新的评测问题 —— 见 [10 章](10-DeepSeek的评测口径.md)。

⚠️ CoT 让分数变高，但也让评测变贵：
★ 输出从 3 个 token 变成 300 个 token ⟹ 慢 100 倍 ★★ 而且推理模型的思考过程可能有几千 token ⟹ 🔑 这是评测成本近两年暴涨的主要原因之一。

4.6 ★ 一份"可比"的最小信息清单

看到任何分数，缺了下面任何一条，就不该直接和别的分数比大小：

    ┌─────────────────────────────────────────────┐
    │  □ 模型的【精确版本】（不是"Llama-3"，       │
    │    ★ 是 "Llama-3-8B-Instruct" + 具体权重日期）│
    │  □ 用的哪个 harness、什么版本                │
    │  □ ★ few-shot 数（0 / 5 / 25）              │
    │  □ ★ 随机种子（示例是怎么抽的）              │
    │  □ ★★ 有没有套 chat template                │
    │  □ 系统提示词内容                            │
    │  □ ★ 判别式还是生成式（3 章 §3.3 的陷阱）    │
    │  □ 采样参数（temperature / top_p）          │
    │  □ 答案抽取规则（★ 05 章）                   │
    └─────────────────────────────────────────────┘

    ⟹ 🔑 九条。★★ 现实中大部分技术报告只写前两三条。
    ⟹ ⚠️ 这就是为什么「跨报告比分数」这件事基本不成立。

4.7 本章小结

    ★★ 四句话：

    ① few-shot 的本质是【格式对齐】，不是教它做题
    ② ✅ 源码强制你传随机种子（task.py:462-469 宁可报错也不给默认值）
       ⟹ ★ 因为示例是随机抽的，种子变则分数变
    ③ ★★ 对话模板是最隐蔽的变量：套错了，好模型也会显得很差
    ④ ★ 可比性需要九条信息，⚠️ 现实中很少有报告写全

    ⟹ 🔑 承接 01 章那句：分数是「模型 + 方法」的联合产物。
       ★★★ 本章讲的就是「方法」里最容易被忽略的那一半。
