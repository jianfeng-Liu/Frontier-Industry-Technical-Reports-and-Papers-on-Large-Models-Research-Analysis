05 · 答案抽取与打分：全书最脏的一章

★★ 放大 03 章数据流的第 ⑤ 步。
这里没有优雅的理论，只有一堆正则表达式和特例。但它直接决定分数。

5.1 先看真实的默认规则

lm-evaluation-harness 的抽取器，默认长这样：

# ✅ lm_eval/filters/extraction.py:16-37  （原文照抄，略去注释）
class RegexFilter(Filter):
    def __init__(
        self,
        regex_pattern: str = r"#### (\-?[0-9\.\,]+)",
        ...
        fallback: str = "[invalid]",
    ):
        self.regex_pattern = regex_pattern
        self.regex = re.compile(regex_pattern)
        self.fallback = fallback

两处值得盯住：

    ★ ① 默认正则是  #### (\-?[0-9\.\,]+)

      翻译：找 "####" 后面跟一个空格，再跟一串【数字/负号/小数点/逗号】。

      ⟹ 这不是通用规则，★★ 这是 GSM8K 数据集的【专属答案格式】：
         GSM8K 的标准答案就写成 "#### 72"
      ⟹ 🔑 换个数据集，这条正则【一个都抠不出来】。

    ★★ ② fallback = "[invalid]"

      ⟹ 抠不出来时，返回字符串 "[invalid]"
      ⟹ ★★★ 而 "[invalid]" 和标准答案永远不相等 ⟹ 判【错】

🔑🔑 这就是全章最重要的一句：
```
★★★ 抽取失败 ≠ 模型答错，但在分数上【完全等价】。

⟹ 一个模型可能算对了，只是没按 "#### 72" 的格式写，
   于是被记为错误。
⟹ ⚠️ 而你从最终的百分比里，【看不出来发生了这件事】。

```

5.2 ★★ 抽取失败长什么样

    ★ 同一道题，模型答对了，但因为格式问题被判错的几种典型情况：

    情况 A：换了写法
      标准格式：  "#### 72"
      模型输出：  "答案是 72。"
      ⟹ 正则找不到 "####" ⟹ [invalid] ⟹ ★ 判错

    情况 B：★★ 抠到了错的数字
      模型输出：  "12 × 6 = 72"
      某些"取第一个数字"的抽取器 ⟹ 抠到 12 ⟹ ★ 判错

    情况 C：格式对但多了东西
      模型输出：  "#### 72 块饼干"
      ⟹ 正则抠出 "72"（★ 这个反而没事，因为正则只吃数字）

    情况 D：⚠️ 单位/千分位
      标准答案：  "1000"
      模型输出：  "#### 1,000"
      ⟹ 抠出 "1,000" ⟹ ★★ 字符串比对 "1,000" ≠ "1000" ⟹ 判错！
      ⟹ 🔑 所以正经的抽取器后面还要接【归一化】（去逗号、去空格、去单位）

    情况 E：★★ 模型答对了但改口
      模型输出：  "#### 72 ... 等等，我重算一下 ... #### 68"
      ⟹ 取第一个还是最后一个？★★★ 两种实现，两种分数。

⚠️ 情况 E 在推理模型时代变得非常常见，因为它们会长篇自我检查、反复改口。
★ 一般约定是取最后一个（视为最终答案），但这是约定，不是标准。
⟹ 10 章 会讲这对 DeepSeek-R1 这类模型意味着什么。

5.3 ★ 框架提供的过滤器家族

    ✅ lm_eval/filters/ 目录：

      extraction.py      ★★ 抽取（正则、词性）
      selection.py       ★ 从多个候选里挑一个（比如多数投票）
      transformation.py  归一化（大小写、空白、标点）
      decontamination.py ★ 污染检测（06 章）
      custom.py          自定义

    ★★ 注意 selection.py 的存在，它对应一个重要玩法：

      让模型对同一题答 N 次（temperature > 0，每次不同）
      ⟹ 抽取出 N 个答案
      ⟹ ★ 取出现次数最多的那个作为最终答案

    ⟹ 这叫【自洽性投票】（self-consistency / majority voting）
    ⟹ ★★ 能显著提分，⚠️ 但成本是 N 倍
    ⟹ 🔑 看榜单时要注意：★★★ 有没有用投票，是不是同一条件下比的。

5.4 ★★ 三种"判对错"的方式，脏的程度递增

    ┌─ ① 精确匹配（exact match）───────────────────┐
    │  抽出来的字符串 == 标准答案                    │
    │  ★ 最干净，但最脆（情况 D 那种就挂了）         │
    └──────────────────────────────────────────────┘
                        ↓ 脏一点
    ┌─ ② 归一化后匹配 ─────────────────────────────┐
    │  先去空格/逗号/大小写/单位，再比               │
    │  ★★ 主流做法。⚠️ 但"归一化到什么程度"没有标准  │
    │     ⟹ 不同框架归一化不同 ⟹ ★ 分数不同         │
    └──────────────────────────────────────────────┘
                        ↓ 更脏
    ┌─ ③ ★ 语义判定 ───────────────────────────────┐
    │  两个答案文字不同但意思一样，算对吗？           │
    │  "72" vs "seventy-two" vs "72 块"             │
    │  ⟹ ★★ 只能靠【另一个模型来判】               │
    │  ⟹ 这就是 09 章的 LLM-as-a-Judge             │
    └──────────────────────────────────────────────┘

🔑 ★ 一个重要观察：
```
⟹ 越往下，★ 越贴近"人类会怎么判"，
⚠️ 但也越难复现（③ 的判定依赖裁判模型的版本和心情）

⟹ ★★ 这和 02 章那条主线是同一个规律：
   【越真实 ⟺ 越难复现】。★★★ 这个权衡贯穿整个评测领域。

```

5.5 ★★ 代码题为什么是个例外（也是个启发）

    ★★★ 写代码这类任务，完全绕开了本章所有的脏活。

      因为它不用【比对文字】，它可以【直接运行】：

      ① 把模型生成的函数抠出来
      ② 拼上测试用例
      ③ ★ 跑一遍
      ④ 跑通了 = 对，报错了 = 错

    ⟹ 🔑🔑 这叫【基于执行的验证】（execution-based verification）
    ⟹ ★★★ 判定是【客观的】，没有正则的模糊地带。

★ 这就是 02 章 §2.4 讲的第三类范式的思想源头，
也是 HumanEval → SWE-bench 这条演进路线的底层逻辑：
```
★ HumanEval（2021）：生成一个函数，跑单元测试
↓ 放大
★★ SWE-bench（2023）：在【真实代码库】里改多个文件，跑【真实测试套件】

⟹ 🔑 同一个思想，只是把"一个函数"换成了"一个项目"。

```

⚠️ 但执行验证也有它自己的坑（07 章 细讲）：
✗ 要真的跑代码 ⟹ ★ 必须隔离（不然模型可能删你文件） ✗ 测试本身可能有问题（不稳定测试 flaky test） ✗ ★★ 测试过了 ≠ 代码写得好（可能是绕过去的）

5.6 ★ 排查清单：分数异常时先看这里

这是本章最实用的部分。分数明显不对劲时，按顺序查：

    ① ★★ 打开原始输出（03 章的 resps 字段）
       ⟹ 模型到底说了什么？★★★ 这一步能解决一半的问题

    ② 看 [invalid] 的比例
       ⟹ ★ 如果超过 5%，问题几乎一定在抽取而不在模型

    ③ 检查 chat template 有没有套（04 章 §4.4）
       ⟹ ★ 对话模型不套模板，是最常见的低分原因

    ④ 检查 stop sequence
       ⟹ ★ 停太早 ⟹ 答案还没写完就被切断
          停太晚 ⟹ 模型开始自问自答，抽取器抠到下一题的答案

    ⑤ 检查 few-shot 数和示例（04 章）

    ⑥ 检查 max_tokens（生成长度上限）
       ⟹ ⚠️★★ 推理模型的坑：思考过程就几千 token，
          默认 512 的上限会把它【拦腰截断】⟹ 答案根本没出来

🔑 ⚠️ 第 ⑥ 条现在是最高频的翻车点。
★ 用测普通模型的老配置去测推理模型，分数会低得离谱，
而原因只是输出长度上限设小了。

5.7 本章小结

    ★★ 四句话：

    ① ✅ 默认正则 #### (\-?[0-9\.\,]+) 是 GSM8K 专属
       ⟹ ★ extraction.py:26，换数据集就失效

    ② 🔑🔑 抽取失败 ≠ 答错，但★★★ 在分数上完全等价，且看不出来

    ③ ★ 判定方式三级：精确匹配 → 归一化 → 语义判定（LLM 裁判）
       ⟹ 越往下越真实，⚠️ 越难复现

    ④ ★★ 代码题靠【执行】绕开全部脏活
       ⟹ 这是 SWE-bench 那条路线的思想起点

    ⟹ 🔑 排查口诀：★★★【先看原始输出，再看 invalid 比例，
       再看模板、停止符、长度上限。】
