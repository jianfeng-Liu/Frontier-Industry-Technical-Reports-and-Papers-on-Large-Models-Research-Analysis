## 5.1 先看真实的默认规则

lm-evaluation-harness 的抽取器，默认长这样：

```python
# ✅ lm_eval/filters/extraction.py:16-37  （原文照抄，略去注释行）
class RegexFilter(Filter):
    def __init__(
        self,
        regex_pattern: str = r"#### (\-?[0-9\.\,]+)",   # ← 第 26 行
        group_select: int = 0,                           # ← 第 27 行
        fallback: str = "[invalid]",                     # ← 第 28 行
    ) -> None:
        self.regex_pattern = regex_pattern
        self.regex = re.compile(regex_pattern)
        self.group_select = group_select
        self.fallback = fallback
```

**三个参数，每一个都决定分数**：

```
    ★ ① 默认正则是  #### (\-?[0-9\.\,]+)

      翻译：找字面的 "####"，紧跟【正好一个空格】，
            再跟一串【数字 / 负号 / 小数点 / 逗号】。

      ⟹ 这不是通用规则，★★ 这是 GSM8K 数据集的【专属答案格式】：
         ✅ GSM8K 的标准答案就写成 "#### 72"
            （GSM8K 论文 arXiv:2110.14168 附录 D 的每个样例都以 "####" 加最终数字收尾）
      ⟹ 🔑 换个数据集，这条正则【一个都抠不出来】。
      ⟹ ⚠️ 而且"正好一个空格"是写死的：模型多打一个空格就整条落空。

    ★★ ② group_select = 0

      ⟹ ★ 这个名字有误导性：它【不是】选正则的第几个捕获组，
         而是选 findall 结果里的【第几个匹配】。
      ⟹ 源码是 match = self.regex.findall(resp) 之后 match = match[self.group_select]
      ⟹ ★★★ 所以 0 = 取【第一个】匹配，-1 = 取【最后一个】匹配。
      ⟹ 🔑 这一个数字就是"模型改口了，算哪一个"的开关。见 §5.2 的 I 行。

    ★★ ③ fallback = "[invalid]"

      ⟹ 抠不出来时，返回字符串 "[invalid]"
      ⟹ ★★★ 而 "[invalid]" 和标准答案永远不相等 ⟹ 判【错】
```

> 🔑🔑 **这就是全章最重要的一句**：
> ```
>     ★★★ 抽取失败 ≠ 模型答错，但在分数上【完全等价】。
>
>     ⟹ 一个模型可能算对了，只是没按 "#### 72" 的格式写，
>        于是被记为错误。
>     ⟹ ⚠️ 而你从最终的百分比里，【看不出来发生了这件事】。
> ```

---
> 🔑 **本章和 01 章分工，别搞混**：[01 章 §1.3b](01-为什么评测是个难题.md) 已经用一个 4 题的干净算例回答了「**同一批输出，换把尺子，分数差多少**」（✅ strict-match 25.0% / 取第一个匹配 50.0% / flexible-extract 75.0%，最高最低差 **50 个百分点**）。★★ 本章**不重复那件事**，本章问的是另一个问题：

>          分别会【命中什么】、【漏掉什么】；

## 5.2 ★★★ 一张格式—命中表：抽取规则漏掉的，全是"答对了的题"

### 5.2.1 先把判分链条的四层摊开

★ 很多人以为"判分"就是一步字符串比对。实际是四层，**每一层都能单独改变判定**：

```
    ┌─ 第 1 层  生成  ── until（停止符）/ temperature / 最大生成长度
    │      ⟹ 决定模型【吐出什么文本】
    ├─ 第 2 层  抽取  ── regex_pattern + group_select（本章主角）
    │      ⟹ 从文本里【抠出一个字符串】，抠不到就给 "[invalid]"
    ├─ 第 3 层  归一化 ── regexes_to_ignore / ignore_case / ignore_punctuation
    │      ⟹ ★★ 对【抽出来的东西】和【标准答案】同时做删改
    └─ 第 4 层  比对  ── exact_match：两个字符串相等就 1 分，否则 0 分
```

✅ 第 1 层和第 3 层的真实配置（`lm_eval/tasks/gsm8k/gsm8k.yaml` 原文；第 2 层那两条 `filter_list` 已经在 [01 章 §1.3b](01-为什么评测是个难题.md) 逐字引过，这里不重复）：

```yaml
# ✅ lm_eval/tasks/gsm8k/gsm8k.yaml
metric_list:
  - metric: exact_match
    ignore_case: true
    ignore_punctuation: false
    regexes_to_ignore:
      - ","
      - "\\$"
      - "(?s).*#### "
      - "\\.$"
generation_kwargs:
  until: ["Question:", "</s>", "<|im_end|>"]
  do_sample: false
  temperature: 0.0
num_fewshot: 5
repeats: 1
```

### 5.2.1b ★★★ 归一化是【双向】的：它既救人，也放人

**这是本章最反直觉的一点。** ✅ `exact_match` 的实现里，那几条 `regexes_to_ignore` 是这么用的：

```python
# ✅ lm_eval/api/metrics.py:218-221
if regexes_to_ignore is not None:
    for s in regexes_to_ignore:
        predictions = np.array([re.sub(s, "", x) for x in predictions])
        references  = np.array([re.sub(s, "", x) for x in references])
```

```
    ⟹ 🔑🔑🔑 注意那是【两行】re.sub，一行作用在 predictions（模型输出），
       一行作用在 references（标准答案）——★ 就是源码第 220 和 221 行。

    ⟹ ★★★ 也就是说：归一化不是"把模型的输出洗干净去对答案"，
       而是【把两边一起洗】，洗完再比。
    ⟹ ⚠️ 于是它有两个方向的后果：
       ★ 救人：模型的格式差异被洗掉了 ⟹ 本该算对的题，算对了
       ⚠️ 放人：本该区分的差异也被洗掉了 ⟹ 本该算错的题，也算对了
```

✅ 四条规则逐条拆开，看各自的两个方向：

| 规则 | 它删什么 | ★ 救回什么（本该对，判对了） | ⚠️ 放过什么 / 边界在哪 |
|---|---|---|---|
| `","` | **所有**逗号（两边都删） | 千分位：模型写 `1,000`、标准答案 `1000` ⟹ 两边都变 `1000` ⟹ **判对** | ⚠️ 列表型答案会被搅乱：`1,2,3` 和 `123` 归一化后都是 `123` ⟹ **本该不同的两个答案变成同一个** |
| `"\\$"` | 所有美元符号 | `$36` vs `36` ⟹ 判对 | ⚠️ 只管美元；`￥36`、`36 元`、`36%` 一个都不删 |
| `"(?s).*#### "` | 贪婪地删掉"到**最后一个** `#### ` 为止"的全部内容 | 让标准答案从"整段解题过程 + `#### 72`"缩成 `72`，这样才比得动 | ⚠️★★★ **它等于宣布"解题过程不参与判分"**：中间步骤全错、最后碰巧写对数字，一样算对（这一点 [01 章 §1.3b](01-为什么评测是个难题.md) 末尾也点出来了） |
| `"\\.$"` | 只删**结尾**的一个句点 | `The answer is 72.` 抽出 `72.` ⟹ 删尾点 ⟹ 判对 | ⚠️ 只删结尾、只删 ASCII 句点：`72。`（中文句号）**删不掉** |
| `ignore_case: true` | 全转小写 | `Paris` vs `paris` ⟹ 判对 | ⚠️ 对纯数字题没有任何作用 |
| `ignore_punctuation: false` | ★ **不**统一删标点 | — | ⚠️ 所以中文全角标点、`\boxed{}` 的花括号、括号 `(A)`，全都原样留着 |

> ⚠️ **★★★ 最该记住的一句**：读者最容易以为 exact match（精确匹配）就是裸的字符串比对。**它不是。** 每个 harness 的 exact match 都自带一套**自己写的**归一化规则，而这套规则是**手写的特例清单**，不是标准。⟹ 🔑 **同一份模型输出，换个 harness、甚至换个任务 YAML，就可能判得不一样。**

## 5.3 ★ 框架提供的过滤器家族

✅ `lm_eval/filters/` 目录里**真正注册进 registry 的**过滤器（按 `@register_filter("...")` 的注册名列，这些名字就是你在 YAML 的 `function:` 字段里写的东西）：

| 文件 | 注册名 | 干什么 |
|---|---|---|
| `extraction.py` | `regex` | ★★ 正则抽取（本章主角） |
| `extraction.py` | `regex_pos` | ★ 带词性（part-of-speech，POS）约束的抽取 |
| `extraction.py` | `remove_whitespace` | 删空白 |
| `extraction.py` | `multi_choice_regex` | ★ 选择题专用：把模型说的话对回 A/B/C/D |
| `selection.py` | `take_first` | ★ N 次采样里只留第一次（⚠️ 注意：**不是**"取第一个正则匹配"，那是 `group_select`） |
| `selection.py` | `take_first_k` | 留前 k 次 |
| `selection.py` | `majority_vote` | ★★ 多数投票 |
| `transformation.py` | `lowercase` / `uppercase` | 大小写归一化 |
| `transformation.py` | `map` | 按字典映射（比如把 `"Yes"` 映成 `1`） |
| `transformation.py` | `format_span` | 命名实体识别（NER）任务专用的格式整理 |
| `custom.py` | `custom` | 自定义，塞你自己的函数 |

> ⚠️ **还有一个文件，但它不在上表里，这一点很重要**：`lm_eval/filters/decontamination.py` 里写着 `@register_filter("decontaminate")`，✅ 但 `lm_eval/filters/__init__.py` 的 import 行是 `from . import custom, extraction, selection, transformation`——**`decontamination` 不在里面**，全仓库也没有别处 import 它。⟹ ★★ 那个装饰器**从不执行**，这个过滤器**没有被注册**，YAML 里写 `function: "decontaminate"` 会直接报"找不到"。⟹ ⚠️ 而且它的 `apply()` 函数体就是一句 `pass`。🔑 **它是个空壳。** 详见 [06 章 §6.3.3](06-数据污染.md)。

```
    ★★ 注意 selection.py 的 majority_vote，它对应一个重要玩法：

      让模型对同一题答 N 次（temperature > 0，每次不同）
      ⟹ 抽取出 N 个答案
      ⟹ ★ 取出现次数最多的那个作为最终答案

    ⟹ 这叫【自洽性投票】（self-consistency / majority voting）
    ⟹ ★★ 能显著提分，⚠️ 但成本是 N 倍
    ⟹ ⚠️ 前提是 YAML 里 repeats > 1；默认 gsm8k.yaml 写的是 repeats: 1
    ⟹ 🔑 看榜单时要注意：★★★ 有没有用投票、投了几票，是不是同一条件下比的。
```

> ⚠️ **口径警告**：「GSM8K 92 分」如果是 `maj@64`（采样 64 次投票），和另一个「GSM8K 88 分」的 `pass@1`（只答一次）**根本不是同一件事**，前者的算力成本是后者的 64 倍。★★★ 拿这两个数比大小，是这个目录最容易犯的错。

## 5.4 ★★ 三种"判对错"的方式，脏的程度递增

| 层级 | 怎么判 | 一个例子 | 干净 / 脏 | 可复现性 |
|---|---|---|---|---|
| **① 精确匹配**<br>exact match | 抽出来的字符串 **完全等于** 标准答案 | `"1,000"` vs `"1000"` → 判**错** | ★ 最干净，但最脆 | ★ 完全可复现 |
| **② 归一化后匹配** | 先删空格 / 逗号 / 单位 / 统一大小写，再比（★★ 两边一起删，见 §5.2.1b） | `"1,000"` → `"1000"` → 判**对** | ★★ 主流做法。⚠️ 但"归一化到什么程度"没有标准 | ★ 可复现（前提是你知道归一化规则） |
| **②′ 数值容差** | 转成浮点数，`isclose(a, b, rel_tol=...)` | `"3.1416"` vs `π` → 判**对** | ★★ 数学题的主流，⚠️ 容差大小是个口径 | ★ 可复现 |
| **③ 语义判定** | 两个答案文字不同但意思一样，算对吗？<br>`"72"` vs `"seventy-two"` vs `"72 块"` | 只能靠**另一个模型来判** | ⚠️ 最脏 | ⚠️ **难复现**（依赖裁判模型的版本和采样） |

★★ ③ 就是 [09 章](09-LLM当裁判.md) 的 LLM-as-a-Judge（大语言模型当裁判）。

### 5.4.1 ★★★ 每一层各自会"误杀"什么、"放过"什么

**这张表是本节的重点。**「误杀」= 答对了被判错（分数虚低）；「放过」= 答错了被判对（分数虚高）。

| 判分器 | ⚠️ 会**误杀**（该对，判错） | ⚠️ 会**放过**（该错，判对） |
|---|---|---|
| **① 精确匹配** | 千分位 `1,000`；货币符号 `$36`；结尾句点 `72.`；大小写 `Paris` vs `paris`；全角半角 `７２`；多余空格；带单位 `72 块` | ★ 几乎不放过任何东西（这是它唯一的优点） |
| **② 归一化后匹配** | 归一化规则没覆盖到的写法：中文数字「七十二」、分数 `1/2` vs `0.5`、LaTeX `\frac{1}{2}`、`7.2e1` vs `72` | ⚠️ **删得过头**：`"(A)"` 里的括号被删成 `A`，而另一道题的标准答案恰好是 `A` 的情况下，模型胡乱输出括号也能蒙对 |
| **②′ 数值容差** | 容差太紧：✅ 实测 `isclose(0.333, 1/3, rel_tol=1e-4)` → **False**（判错），而 `isclose(0.3333, 1/3, rel_tol=1e-4)` → True。⟹ ⚠️ 模型少写一位小数就被判错 | ⚠️ **量级错误被放过**：✅ `math_grader.py` 的 `include_percentage=True` 会把标准答案扩成 `[ref/100, ref, ref*100]` 三个都算对。实测标准答案 `0.72` 时，模型答 `72`、`0.72`、`0.0072` **全判对**——★★★ 差 100 倍的答案也算对 |
| **③ 语义判定** | ⚠️ 裁判模型自己判错的那部分 | ⚠️ 裁判被"说得很有道理但结论错"的输出骗过去（09 章讲的各种偏差） |

> ✅ **②′ 那两行的依据**：`lm_eval/tasks/score/math/math_grader.py:378-384` 的函数签名是 `math_equal(prediction, reference, include_percentage: bool = True, tolerance: float = 1e-4, timeout: float = 10.0)`；第 420-426 行是 `gt_result = [reference / 100, reference, reference * 100]` 然后 `isclose(item, prediction, rel_tol=tolerance)`；符号等价的兜底在第 557 行（走 sympy）。★★ 上面那几个 `isclose` 的真假我都跑过一遍。

```
    ⟹ 🔑🔑 把整张表压成一句话：

      ★★★ 从 ① 到 ③，【误杀】越来越少，【放过】越来越多，
         而【可复现性】一路下降。

    ⟹ ★★ 这和 02 章那条主线是同一个规律：
       【越真实 ⟺ 越难复现】。★★★ 这个权衡贯穿整个评测领域。
    ⟹ ⚠️ 所以"用哪一层"不是技术优劣问题，是【你想要什么】的问题：
       要排行榜可复现 ⟹ 往 ① 靠；要贴近人类判断 ⟹ 往 ③ 靠。
```

> ⚠️ **报分数时，判分器和抽取规则必须一起报**。「GSM8K 88.0」这个数至少要写成：
> ```
>     GSM8K 88.0（5-shot，示例随机抽 / 种子 1234，
>                 strict-match，exact_match + 该任务默认的四条 regexes_to_ignore，
>                 temperature=0，repeats=1，lm-eval 0.4.12）
> ```
> ★★ 看起来很啰嗦，⟹ 🔑 但少了任何一项，它就不能和别人的数字比大小。

## 5.5 ★★ 代码题为什么是个例外（也是个启发）

```
    ★★★ 写代码这类任务，完全绕开了本章所有的脏活。

      因为它不用【比对文字】，它可以【直接运行】：

      ① 把模型生成的函数抠出来
      ② 拼上测试用例
      ③ ★ 跑一遍
      ④ 跑通了 = 对，报错了 = 错

    ⟹ 🔑🔑 这叫【基于执行的验证】（execution-based verification）
    ⟹ ★★★ 判定是【客观的】，没有正则的模糊地带。
```

★ 注意第 ① 步**还是抽取**——要从模型的回答里把代码块抠出来（通常靠三个反引号的围栏）。⚠️ 抠错了照样 0 分。🔑 **执行验证消掉的是"判对错"这一层的模糊性，不是"抽取"这一层。**

> ★ 这就是 [02 章 §2.4](02-三种评测范式.md) 讲的第三类范式的思想源头，
> 也是 HumanEval → SWE-bench 这条演进路线的底层逻辑：
> ```
>     ★ HumanEval（2021，arXiv:2107.03374）：生成一个函数，跑单元测试
>              ↓ 放大
>     ★★ SWE-bench（2023，arXiv:2310.06770）：在【真实代码库】里改多个文件，
>         跑【真实测试套件】
>
>     ⟹ 🔑 同一个思想，只是把"一个函数"换成了"一个项目"。
> ```

> ⚠️ **但执行验证也有它自己的坑**（[07 章](07-agentic编码评测与SWE-bench.md) 细讲）：
> ```
>     ✗ 要真的跑代码 ⟹ ★ 必须隔离（不然模型可能删你文件）
>     ✗ 测试本身可能有问题（不稳定测试 flaky test）
>     ✗ ★★ 测试过了 ≠ 代码写得好（可能是绕过去的）
> ```

## 5.6 ★ 排查清单：分数异常时先看这里

**这是本章最实用的部分。分数明显不对劲时，按顺序查**：

| 顺序 | 查什么 | 怎么查 | ⚠️ 典型症状 |
|---|---|---|---|
| **①** | ★★ 打开**原始输出** | 看 03 章那个 `resps` 字段，模型到底说了什么 | ★★★ 这一步能解决一半的问题 |
| **②** | 看 `[invalid]` 的**比例** | 数抽取结果里有多少个 `[invalid]` | ⚠️ 比例明显偏高 ⟹ 问题在抽取，不在模型（见 §5.2 那张表的 B–G 行） |
| **③** | 对比 `strict-match` 和 `flexible-extract` | lm-eval 会**同时报这两个分数** | ★★★ 两者差得很多 ⟹ 模型会做题，只是格式不对 |
| **④** | chat template 有没有套 | [04 章 §4.4](04-few-shot与提示词.md) | ★ 对话模型不套模板，是最常见的低分原因 |
| **⑤** | stop sequence（停止符） | ✅ gsm8k 的 `until` 默认是 `"Question:"` 加两个结束 token（原文见 §5.2.1 的 YAML） | ★ 停太早 ⟹ 答案还没写完就被切断<br>停太晚 ⟹ 模型自问自答，`group_select: -1` 抠到下一题的答案（[04 章 §4.3](04-few-shot与提示词.md) 的「改分隔符」那一段演示过） |
| **⑥** | few-shot 数、**示例选法和种子** | [04 章 §4.3](04-few-shot与提示词.md) 的「示例选法」表 | ⚠️ 随机选法换个种子分数就变 |
| **⑦** | **max_tokens**（生成长度上限） | 看配置里的生成长度 | ⚠️★★ 推理模型的思考过程就几千 token，几百的上限会把它**拦腰截断** |

> ⚠️ **第 ② 条的阈值别写死**：常见的经验说法是"`[invalid]` 超过 5% 就该怀疑抽取"，★ **这个 5% 是经验拍的，不是任何标准**（⚠️ 我没找到一手来源）。🔑 更可靠的做法是 **③**：直接看 `strict-match` 和 `flexible-extract` 这两个**同时产出**的分数差多少——差距大就一定是抽取问题，不需要任何阈值。

> 🔑 **⚠️ 第 ⑦ 条现在是最高频的翻车点。** ★ 用测普通模型的老配置去测推理模型，分数会低得离谱，而原因只是**输出长度上限设小了**——模型的思考被截断，`#### 答案` 那一行根本没机会写出来。★★ 这时抽取器拿到的是一段没有最终答案的推理片段：`strict-match` 给 `[invalid]`，`flexible-extract` 抠到推理中间的某个数字（✅ 我实测过一个截断片段，flexible 抠到的是中间量 `12`，不是答案 `72`）。⟹ ⚠️ **两条流水线都错，而且错得一点痕迹都不留。**

## 5.7 本章小结

```
    ★★ 六句话：

    ① ✅ 默认正则 #### (\-?[0-9\.\,]+) 是 GSM8K 专属
       ⟹ ★ extraction.py:26，换数据集就失效
       ⟹ ★★ 同一个类里还有 group_select（extraction.py:27）：
          0 = 取第一个匹配，-1 = 取最后一个。这一个数字就是一条口径。

    ② 🔑🔑 抽取失败 ≠ 答错，但★★★ 在分数上完全等价，且看不出来

    ③ ★★★ §5.2 那张 12 行命中表是本章的实感来源：
       ✅ 12 行里模型只有 3 行算错，而 strict-match 有【6 行是算对了却判 0 分】
       ⟹ ★★ 严格和宽松【各有各的误杀】，不是"越宽松越准"（E 行 vs I 行）
       ⟹ ⚠️ 那两个"命中行数"不是分数，别当分数引用；
          「换把尺子分数差多少」那件事在 [01 章 §1.3b](01-为什么评测是个难题.md)
          （25.0% / 50.0% / 75.0%，差 50 个百分点）

    ③b ★★★ 归一化是【双向】的（§5.2.1b）
       ✅ metrics.py:220-221 是两行 re.sub，一行洗模型输出、一行洗标准答案
       ⟹ ★ 它救回格式差异（1,000 == 1000）
       ⟹ ⚠️ 也放过该区分的差异（"(?s).*#### " 等于宣布解题过程不参与判分）
       ⟹ 🔑 所以 exact match【不是】裸字符串比对：
          ★★★ 每个 harness 自带一套手写的归一化特例，
          换个 harness、换个任务 YAML，同一份输出就可能判得不一样。

    ④ ★ 判定方式四级：精确匹配 → 归一化 → 数值容差 → 语义判定（LLM 裁判）
       ⟹ 往下走：★ 误杀越来越少，⚠️ 放过越来越多，可复现性一路下降
       ⟹ ✅ 一个真实的"放过"：math_grader 的 include_percentage 让
          标准答案 0.72 时，模型答 72 或 0.0072 都判对（差 100 倍也算对）

    ⑤ ★★ 代码题靠【执行】绕开"判对错"的脏活（⚠️ 但没绕开"抽取"）
       ⟹ 这是 SWE-bench 那条路线的思想起点

    ⟹ 🔑 排查口诀：★★★【先看原始输出，
       再比 strict 和 flexible 这两个同时产出的分数，
       再看模板、停止符、长度上限。】
```
