08 · Claude Code 和 Codex 到底是怎么被评的

⭐⭐ 这一章回答你最初问的那个问题。
结论提前说：★★★ 榜单上那个分数，评的不是模型，是【模型 + 脚手架】这一整套系统。
而这两样东西，★★ 榜单通常只报前者的名字。

8.1 先看一个源码事实：评测框架根本不知道 agent 长什么样

打开 SWE-bench 判卷入口 run_evaluation.py:699 的函数签名：

def main(
    dataset_name: str,
    split: str,
    instance_ids: list,
    predictions_path: str,     # ★★★ 就是这一行
    max_workers: int,
    ...
):
    """
    Run evaluation harness for the given dataset and predictions.
    """

它要的是一个文件路径。文件里每行一条预测，格式见 run_evaluation.py:244 的注释（★ 逐字）：

# pred (dict): Prediction w/ model_name_or_path, model_patch, instance_id

⟹ 🔑🔑 也就是说，SWE-bench 的判卷器只认三个字段：

字段 作用 判卷器拿它干什么
instance_id 哪道题 ★ 去数据集里找对应的题目和测试名单
model_patch ★★ 你交上来的补丁文本 ★★★ 写进容器、尝试 git apply
model_name_or_path ★ 一个【你自己随便填的字符串】 ⚠️ 只用来拼日志目录名

★★★ 注意最后一个。run_evaluation.py:253-254 里它的全部用途就是这两行（★ 逐字）：

model_name_or_path = pred.get("model_name_or_path", "None").replace("/", "__")
log_dir = RUN_EVALUATION_LOG_DIR / run_id / model_name_or_path / instance_id

    ⟹ 🔑🔑🔑 评测框架【完全不验证、也完全不关心】这个补丁是谁生成的、
       花了多少钱、跑了多少轮、用了什么工具、重试了几次。
    ⟹ ⚠️ 那个字段连"是不是一个真实存在的模型名"都不检查。
       ★ 默认值是字符串 "None"。

★★★ 这就是本章的全部要害：

SWE-bench 定义了什么 SWE-bench 不定义什么
★★ 题目：给哪个仓库、哪个 commit、哪段 issue 文字 ⚠️ 怎么把上下文喂给模型（07 章 §7.9：差 2.4–3.0 倍）
★★ 判卷：起容器、打补丁、跑测试、F2P × P2P（07 章 §7.4） ⚠️ 用什么工具、跑几轮、怎么纠错、怎么重试
★ 输出格式：三个字段的 JSONL ⚠️ 花了多少 token、多少钱、多少墙钟时间
— ⚠️ ★★★ 跑了一次还是五十次、怎么从多次里挑一份交 
    ⟹ ★★★ 中间"怎么把补丁做出来"那一段，是【完全开放】的。
    ⟹ 🔑 而 Claude Code、Codex 的绝大部分本事，全在那一段里。

★ 同一组源码事实的另一种讲法（逐函数、带上下文）在 SWE-bench拆解.md 第 3 节。本章不重复源码，只往下推它的后果。

8.2 名词：脚手架（scaffold）

    ★ 名词：scaffold（脚手架）
      ★ 同义词：agent harness（智能体挽具）、agent framework（智能体框架）

      ★★ 指【包在模型外面、让它能真的干活的那层程序】。
      盖楼时钢筋水泥是主体，脚手架是让工人上得去的架子——
      ★ 楼盖完脚手架就拆了，但没有它楼盖不起来。

    ⚠️⚠️ 注意 "harness" 这个词有两个意思，本书全程区分：
      ① 评测 harness：把模型接上题目和判分器的那套程序（01–06 章讲的那个）
      ② agent harness / 脚手架：把模型接上工具和环境的那套程序（本章讲的这个）
      ⟹ 🔑 它们是两个不同的东西，只是英文撞了名字。
         ★★ 姊妹目录 [agent脚手架/](../agent脚手架/README.md) 第 01 章专门拆这个歧义。

    ⟹ 🔑 07 章 §7.2b 那张流程图里"模型/agent 干活"的格子，装的就是它。

一个脚手架至少要做这些事（⚠️ 以下是我对公开实现的归纳，不是某篇论文的原文）：

# 部件 它要决定什么 ✅ 有没有实测数字
① 工具集（tools） 给模型哪几个能调用的动作：读文件、写文件、跑 shell、grep 搜索、跑测试 ✅ 有，而且很大。§8.4.2：去掉 edit 命令掉 7.7 个百分点
② 上下文管理 07 章说仓库平均 438K 行，装不进上下文窗口。★★ 什么时候塞什么进去、旧的怎么压缩掉 ✅ 有。§8.4.2：保留全历史 vs 只留最近 5 次观察，差 3.0 个百分点
③ 循环与停止条件 ★ 让模型跑多少轮？什么时候判定"它自己觉得做完了"？什么时候强行掐断？ ⚠️ 本章没有直接的消融数字，但预算上限是硬约束（§8.5）
④ 错误恢复 测试报错了怎么把报错喂回去、要不要回滚、重试几次 ✅ 有。§8.4.2：加 linting 护栏值 3.0 个百分点
⑤ 采样与挑选策略 ★★★ 只跑一遍？还是跑 6 遍挑最好的？怎么挑？ ✅ 有，而且是本章最大的一项。§8.5：pass@1 17.94% → pass@6 32.67%

★★★ 完整的变量清单（含"哪些会被算进模型能力、哪些不会"）在 §8.4.3。上面这张表只是把部件列出来。

★★ SWE-bench 自带的 swebench/inference/run_api.py 是最原始的一版脚手架，它的文件头注释（★ 逐字）：

"This python script is designed to run inference on a dataset using either the
OpenAI or Anthropic API, depending on the model specified."

★ 看它的做法就知道有多简陋：

步骤 run_api.py 干什么 ⚠️ 它没有的东西
1 把 issue + 检索到的文件拼成一个大 prompt —
2 ★★ 调一次 API ⚠️ 没有第二轮
3 用 extract_diff() 从回复里抠出补丁 ⚠️ 没有工具调用
4 完 ⚠️ 没有跑测试、没有看报错、没有改了再试 
    ⟹ 🔑 这就是 07 章那个【1.96%】的由来。
       ⚠️ 它衡量的是"模型盲写补丁"的能力，
       ★★★ 而不是"一个工程 agent 解决问题"的能力。

    ⟹ ⚠️ 顺手提醒一个容易被忽略的点：这一档连"抠补丁"都是
       ★★ 用 extract_diff() 正则做的 —— 05 章那套抽取脏活在这里还在。
       ⟹ 🔑 07 章 §7.5 的 % Apply 数字（ChatGPT-3.5 只有 26.33%）
          就是这个环节的直接后果。

8.3 所以 Claude Code / Codex 被评的是什么

    ★ 名词：Claude Code —— Anthropic 的命令行编码工具
    ★ 名词：Codex —— OpenAI 的编码 agent 产品线
      ★★ 它们【不是模型】，是【产品】：模型 + 脚手架 + 工具 + 提示词 + 策略。

    ⚠️ 顺带纠一个常见混淆：Codex 这个名字在历史上指过两样东西——
      ① 2021 年的 Codex 模型（HumanEval 论文那个，arXiv:2107.03374）
      ② 后来的 Codex 编码 agent 产品线
      ⟹ 🔑 看到"Codex 得了多少分"，★★ 先确认说的是哪一个。

⟹ 🔑🔑 当你看到"Claude Code 在 SWE-bench Verified 上 xx%"，这个数字的完整含义是：

这个分数其实等于…… 具体是什么 榜单一般说不说
某个具体模型版本 带日期的快照，不是"Claude" 三个字 ★ 通常说
＋ 某个具体脚手架版本 哪个 commit 的 agent 代码 ⚠️ 通常不说
＋ 某套工具定义 有没有 edit 工具、搜索长什么样 ⚠️ 几乎不说
＋ 某个上下文 / 轮数 / 超时预算 最多几轮、最多多少 token、多少钱 ⚠️ 几乎不说
＋ 某种采样与挑选策略 跑一遍还是 N 遍、怎么挑 ⚠️ 几乎不说
＝ 在 500 道人工校验题上的 RESOLVED_FULL 百分比 ★ 哪个子集 ★ 通常说 
    ⟹ ★★★ 换掉其中任何一项，分数都会动，而且可能动很多。
    ⟹ 🔑 这张表的上下两行（模型版本、题集）是榜单会说的；
       ★★★ 中间四行是决定性的，而它们通常不说。

⚠️ 这是我的判断，不是论文结论，但有源码支撑（§8.1）也有实测支撑（§8.4.1）：
★★ 同一个模型换一套脚手架，SWE-bench 分数的差距可以大过两代模型之间的差距。

    🔑 一个思想实验帮你记住：
       run_api.py 那套（一轮盲写）vs 一个能跑测试、看报错、改了再试的 agent。
       ★★ 模型一模一样。分数不可能一样。
       ⟹ 差的那部分，【全部记在了模型头上】。

★ 这件事一线团队自己是知道的。✅ DeepSeek-V3 技术报告 §5.3.1 原文：

"SWE-Bench verified is evaluated using the agentless framework (Xia et al., 2024)."

    ⟹ ★★ 一句话把脚手架披露掉了，这是正面样板。
    ⟹ 🔑 详见 10 章 §10.6，那一节把"同一张表里所有模型都跑 Agentless"
       这个设计的好处和局限都拆了。

8.4 名词：ACI —— 为什么"给模型的界面"本身是一项技术

    ★ 名词：ACI = Agent-Computer Interface（智能体-计算机界面）
      ★★ 由 SWE-agent 团队提出的说法（arXiv:2405.15793）。

      类比：UI = User Interface（用户界面）是给人用的，
           ★ ACI 是给模型用的。
      ⟹ 🔑 核心主张：给模型的工具，不该照搬给人用的工具。

    ✅ 论文摘要原文（逐字）：
    > "We show that ACIs tailored specifically for LMs **outperform existing user
    >  interfaces (UIs) designed for human users**, such as the Linux shell."

⚠️ 下面这张对照表是我的解释（不是论文原文），用来帮你理解为什么这件事重要：

场景 人用的 shell 是怎样 ★ 模型需要的是怎样 为什么
看一个 5000 行文件 cat 一下，一屏刷过去 ★ 分页显示，带行号 ⚠️ 人可以滚回去，模型没有"滚回去"这个动作
改文件 vim / sed，靠眼睛确认改对没有 ★★ 一个明确的 edit 工具，改完【自动回显改动结果】 ⚠️ 模型看不到屏幕，必须把结果写回对话里
看报错 几百行报错，人会跳着看 ★ 截断 + 只留关键行 ⚠️ 全塞进去会挤爆上下文
搜索 grep 吐出几百个匹配，人扫一眼就跳过 ★★★ 汇总式结果 + 结果太多时提示"缩小查询" ⚠️ ✅ 论文实测：模型会把列表一条一条走完（§8.4.2 ②） 
    ⟹ 🔑🔑 结论：★★★【工具设计是能力的一部分】。
       所以"评 Claude Code"这件事，评的相当大一块是【ACI 设计得好不好】，
       而不只是模型聪不聪明。

8.4.1 ✅ 论文原文：脚手架换一下，分数差多少

★★★ 这不是我的推断。SWE-agent 论文（arXiv:2405.15793，118 页，已校验）把"同一个模型、不同脚手架"的对照实验做完了，数字如下。

✅ 引言原文（关键的一句）：

"Using GPT-4 Turbo as a base LM, SWE-agent solves 12.47% of the
2,294 SWE-bench test tasks, substantially outperforming the previous best
resolve rate of 3.8% by a non-interactive, retrieval-augmented system."

   ⚠️⚠️ 【权重一个字节没改。】分数从 2.67 变成 18.00。

   ⟹ 🔑 ⚠️ 同一件事有两种说法，★★★ 千万别混（这是本章的第一个查错要点）：
      ★ 绝对差 = 18.00 − 2.67 = **15.33 个【百分点】**（percentage points）
      ★ 相对差 = 18.00 ÷ 2.67 = **6.74 【倍】**，也就是"高了 574%"
      ⟹ ⚠️ 说"高了 15.33%"是错的（那是百分点）；
         说"高了 6.7 倍"和"是 6.7 倍"也差一倍意思，★ 严谨的写法是"6.7 倍于"。
      ✅ 论文自己用的是倍数口径："a **6.7-fold** improved % Resolved rate"
         ⟹ ★★ 18.00 / 2.67 = 6.74 ✅ 对上了，说明论文这句话的对照组
            就是 Table 1 里 RAG w/ GPT-4 Turbo 那一行（不是 Claude 3 Opus 的 4.33）。

   ⟹ 🔑🔑 所以"GPT-4 Turbo 在 SWE-bench 上得几分"这句话，
      ★★★ 在没说脚手架之前，是【一个没有答案的问题】。

⚠️⚠️ 还有一处引用时极易出错的地方，必须点明。✅ 论文摘要里有这句：

"The results show that SWE-agent solves 10.7 percentage points more
instances than the baseline agent, which uses only the default Linux shell."

★ 但 Table 1 里"只给裸 Linux shell"有两行，于是这 10.7 对应的是哪一行？★★ 自己减一遍就知道：

拿 SWE-agent 的 18.00 减谁 差值（百分点） 对得上 10.7 吗
减 Shell-only w/ 示范 的 11.00 7.00 ❌
减 Shell-only w/o 示范 的 7.33 ★★ 10.67 ≈ 10.7 ✅ 就是这一行 
    ⟹ 🔑🔑 结论：★★★ 论文摘要那个 "10.7 percentage points"，
       比的是【裸 shell 且不给示范】那一档，不是"裸 shell"那一档。
    ⟹ ⚠️ 如果你引用成"SWE-agent 比裸 shell 高 10.7 个百分点"，就错了——
       ★ 正确说法是高 7.0 个百分点；10.7 那个数还额外包含了"给不给示范"的贡献。

    ⟹ ★★ 同一页论文还给了第三种说法：
       ✅ "SWE-agent's **64% relative increase** compared to Shell-only"
       ⟹ 18.00 ÷ 11.00 = 1.636 ⟹ +63.6% ≈ 64%。✅ 对上了。
    ⟹ 🔑🔑🔑 ★★★ 所以同一组数字有三种表达：
       「+7.0 个百分点」「+64%」「+10.7 个百分点（换了对照组）」。
       ⚠️⚠️ 百分点和百分比混用、对照组偷换，是这一类数字最常见的两种变形。

✅ 论文自己也点破了成本这一维（正文原文）：

"compared to RAG on Lite, SWE-agent is 8-13x more costly but yields a
6.7-fold improved % Resolved rate."

   ⟹ ★★ $0.13 → $1.67，正好落在论文说的 "8-13x" 区间里。
      🔑 这就是 02 章那条定律的又一次现身：
      ★★★【越真实 ⟺ 越贵 ⟺ 越难复现】。

   ⚠️ 还有一个藏在方法节里的预算约束，看分数时必须知道（✅ 原文）：
   > "Due to budget constraints, we set the **per-instance budget to $4**;
   >  if a run exceeded this budget, existing edits were submitted automatically."
   ⟹ ★★★ 所以 18.00% 这个数是【每题最多花 4 美元】条件下的成绩。
      🔑 把上限提到 $40 会怎样？★★ 论文没测，但这正是 §8.5 要讲的"隐藏变量"。

8.4.2 ✅ ACI 的每一个设计细节都值几个点

★★ 论文 Table 3 做了 ACI 的消融实验，全部在 SWE-bench Lite（300 题）上，基线是完整 SWE-agent 的 18.0%。

    ★ 名词：ablation study（消融实验）
      ★★ 把系统里某个部件拆掉或换掉，看分数掉多少。
      ⟹ 🔑 它是唯一能回答"这个部件值几分"的实验设计。

✅ Table 3 原文数值（↓ 列是论文自己标的，相对 18.0 掉了多少个百分点）：

部件 配置 % Resolved ✅ Δ（百分点） 读法
编辑器 edit 动作 + linting（语法检查）← 完整版 18.0 — ★ 基线
edit 动作，但不做 linting 15.0 ↓ 3.0 ★★ 护栏值 3 个点
完全没有 edit 命令（Noedit） 10.3 ↓ 7.7 ★★★ 单项最大
搜索 汇总式（Summarized）← 完整版 18.0 — ★ 基线
逐条翻页式（Iterative） 12.0 ↓ 6.0 ⚠️⚠️ 见下面 ②
完全没有搜索命令（No search） 15.7 ↓ 2.3 ⚠️ 比"有个难用的搜索"还高
文件查看器窗口 30 行 14.3 ↓ 3.7 ★ 太小也不行
100 行 ← 完整版 18.0 — ★ 基线
整个文件全塞进去（Full file） 12.7 ↓ 5.3 ⚠️⚠️ 见下面 ①
上下文管理 只保留最近 5 次观察 ← 完整版 18.0 — ★ 基线
保留完整历史（Full history） 15.0 ↓ 3.0 ⚠️ 给得多反而差
不给示范（w/o demo.） 16.3 ↓ 1.7 ★ 示范值 1.7 个点 
   ⟹ 🔑 这张表里有三个反直觉的地方，★★★ 每一个都值得记住：

   ① ★★★ 【给模型更多信息，反而更差】
      "整个文件全塞进去" 12.7 < "只给 100 行窗口" 18.0（↓ 5.3）
      "保留完整历史"     15.0 < "只留最近 5 次观察" 18.0（↓ 3.0）
      ⚠️ 因为上下文被无关内容挤满，模型反而定位不到关键行。
      ⟹ 这直接反驳了"上下文窗口越大越好"的朴素想法。
      ⟹ ★★ 而且这和 07 章 §7.9 那张表是【同一条规律的两次独立观测】：
         ✅ SWE-bench 论文：BM25 上限 13k → 50k，召回率 29.58 → 51.06 升了，
            Claude 2 的分数 1.96 → 1.22 掉了。
         🔑 两篇论文、不同系统、同一个结论。这比任何单篇的说法都可信。

   ② ★★★ 【设计得不好的工具，比没有这个工具还差】
      逐条翻页式搜索 12.0 < 完全没有搜索命令 15.7
      ✅ 论文原文解释：
      > "when given a large number of search results, agents tend to look
      > through **every match exhaustively**, calling next until each result
      > has been inspected. This inefficient behavior can **exhaust an
      > agent's cost budget or context window**, leading to even worse
      > performance than the not having additional search tools at all
      > (15.7% ↓ 2.3 for No search vs. 12.0% ↓ 6.0 with Iterative search)."
      ⟹ 🔑 模型不像人会"扫一眼觉得不对就跳过"，它倾向于把列表走完。
      ⟹ ★★ 注意它给出的机制：★★★ 不是"模型看不懂"，是【把预算烧光了】。
         这条机制把 §8.4.2 和 §8.5 的预算问题连到了一起。

   ③ ★★ 【护栏（guardrail）值 3 个点】
      `edit` 命令加上 linting（提交前先做语法检查，不通过就拒绝这次编辑）
      = 15.0 → 18.0。✅ 论文原文：
      > "This intervention improves performance considerably
      > (without linting, 15.0% ↓ 3.0)."
      ⟹ ★★ 不是让模型变聪明，而是【不让它把错误写进文件】。

✅ 补充一个很有实感的数字（论文正文「Editing remains challenging for agents」一节 + 附录 B.3「Editing Trends」，★ 逐字）：

"out of 2,294 task instances, 1,185 (51.7%) have at least one turn with an failed edit. ...
Of these trajectories, there is a median of 3 failed edits per trajectory, with a max of 33. ...
Any attempt at editing has a 90.5% chance of eventually being successful."

统计 数值 读法
至少写错过一次编辑的运行 1,185 / 2,294 = 51.7% ★★ 超过一半
这些运行里，写错次数的中位数 3 次 ★ 通常错几次就过去了
最多写错多少次 33 次 ⚠️ 有的题在编辑上死磕
任一次编辑尝试最终能成功的概率 90.5% ★ 恢复能力其实不差
⚠️ 最终解决了的那 286 条里，写错过的比例 113 / 286 = 31.5% ★★ 明显低于整体 51.7% 
   ⟹ ★★ 超过一半的运行过程里，模型至少写错过一次编辑。
      🔑 agentic 评测和 01-06 章的选择题最大的不同就在这里：
      ★★★ 它允许【中途犯错然后自己纠正】，最终只看结果。
      ⟹ 这也是为什么它贵——一道题要来回几十轮。
   ⟹ 🔑🔑 而最后一行说明了一件更微妙的事：★★★ "写错编辑"这件事和"最终失败"
      是强相关的（31.5% vs 51.7%）。⟹ 所以 ③ 那个 linting 护栏之所以值 3 个点，
      ★★ 不是玄学，是在直接削掉这条失败链。

   ⟹ 🔑🔑 §8.4 的最终结论，现在有了完整的证据链：

   ★★★ 一个 SWE-bench 分数 = 模型能力 × ACI 设计质量 × 尝试预算。
   ⚠️ 榜单只写第一项的名字。
   ⟹ 所以 §8.7 那张检查清单，不是吹毛求疵，是【读懂这个数的必要条件】。

   ⚠️⚠️ 这张表的适用边界，必须说清楚：
   ⚠️ ① 它是 2024 年的 GPT-4 Turbo（gpt-4-1106-preview），不是今天的模型。

8.5 最容易被误导的一点：一次尝试 vs 多次尝试

这是 02 章 pass@k 概念在 agentic 场景的翻版，★★★ 但危害大得多。★ pass@k 本身的三种算法和算术推演，在 07 章 §7.7b。

# 做法 诚实吗 ⚠️ 成本 它到底是什么指标
① pass@1 / 单次提交：跑一遍，交一份补丁 ✅ 诚实 1× ★ 这是榜单的默认口径
② 跑 N 遍，用 f2p 测试结果挑一份最好的交 ❌ 不诚实 N× ⚠️⚠️ ★★★ 【看着答案挑答案】——严重高估
③ 跑 N 遍，用自己写的测试挑一份交 ✅ 诚实 N× + 写测试的开销 ★★ 合法：模型自己造验收标准、自己筛。★ 但它显然比 ① 强 
    ⟹ 🔑🔑 ① 和 ③ 都是诚实的，但它们【不是同一个指标】。
       把 ③ 的分数和别人 ① 的分数放同一张表里比，就是在骗人。

    ⚠️ ② 在 SWE-bench 里技术上是做得到的——因为 f2p 测试名单
       就写在数据集里。★★★ 这是这个基准最需要靠自律来守住的地方。

    ⟹ ★★ 而且请注意：②这件事在 pass@k 的定义里【本来就是明说的】。
       ✅ HumanEval 论文原文（arXiv:2107.03374 §3）：
       > "Pass@k can also be interpreted as the result of evaluating the
       >  **best out of k samples**, where the best sample is picked by an
       >  **oracle with prior knowledge of the unit tests**."
       ⟹ 🔑🔑 ★★★ 所以 pass@k（k>1）在定义上就是"有先知帮你挑"的指标。
          ⚠️ 它不是错的，它只是【和 pass@1 回答的不是同一个问题】：
             pass@1  ：「一次交付，它能成吗」
             pass@k  ：「给它 k 次机会 + 一个完美筛子，天花板在哪」
       ⟹ ⚠️ 把 pass@k 的数写成 pass@1，或者不标 k，是最常见的一种虚报。

# 要问什么 ★★ 必须问到的粒度 为什么
① 哪个子集？ full / Lite / Verified；题数对不对（2,294 / 300 / 500）；有没有只跑子集的行（⚠️ 07 章那个 GPT-4 只跑了 25%） ★ 三个子集分数系统性不同（07 章 §7.8）

    ⟹ 🔑🔑 六项里【任何一项没说清，这个分数就不能横向比较】。
       ★★ 现实是：绝大多数宣传口径只说清了 ① 和 ⑥。

    ⟹ ★★★ 还有第 ⑦ 件事，严格说不属于"这个分数"而属于"这句话"：
       ⚠️ 这个数是【自己跑的】还是【从别人报告里抄的】？
       🔑 抄来的数往往连 ①–⑥ 都不一样。⟹ 11 章 §11.6 ② 专门讲这个。

② 脚手架 ② 工具集、③ 上下文管理、④ 重试与纠错

④ 挑选依据 ⑦ 采样与挑选、⑥ 权限与环境
⑤ 预算 ⑤ 超时与预算
⑥ 模型版本 ① 模型本身
⚠️ 没被覆盖的 ⑧ 的其余部分：swebench 包版本、镜像版本、判分器超时设置 
    ⟹ ⚠️ 最后那一行是个真实的盲区：★★ 同一份 predictions.jsonl，
       用不同版本的 swebench 包 / 不同版本的题目镜像去判，结果可以不同。
    ⟹ 🔑 所以严谨的报分还要加一句：★★★「用 swebench==x.y.z 判的」。
       ★ 本书引用的源码是 swebench-5.0.2。

8.8 如果你想自己评一次 Claude Code

⚠️ 这一节是操作建议，不是论文内容。

★ 好消息：因为 §8.1 那个设计，你完全做得到。★★ 你只要产出一个 predictions.jsonl，判卷器不问来路。

步骤 做什么 ★ 要点
① 取 SWE-bench Verified 的题目 每条含 repo + base_commit + problem_statement（issue 文本）
② 把仓库 checkout 到那个 base_commit ★★★ 见下面坑 ①
③ 把 issue 文本作为任务丢给 Claude Code，让它改 ★★ 见下面坑 ②
④ 它改完后 git diff 出补丁 ★ 注意排除掉它自己新建的临时文件
⑤ 写成一行 JSON 见下面的格式
⑥ 跑官方判卷器（需要 Docker） ★ 见下面坑 ③ 
{"instance_id": "django__django-11099", "model_patch": "<diff 文本>", "model_name_or_path": "claude-code-mysetup-v1"}

    ⚠️ 三个坑：
      ① ★★★ 必须切到题目指定的 base commit。
         切错了 = 仓库里已经有修好的代码，分数虚高到离谱。
         ⟹ 🔑 自检方法：切完之后先跑一遍 f2p 测试，★★ 它们应该【全是红的】。
            如果是绿的，说明你切错了 commit。
      ② ★★ 别让 agent 看 f2p 测试文件（数据集里带着）。
         看了就是抄答案（§8.7 ④）。
         ⟹ ★ 但注意这里有个两难：真实开发中人是会看测试的。
            🔑 所以这条限制是【为了让分数可比】，不是"更真实"。
      ③ ★ 起 Docker 会拉几十 GB 镜像，跑 500 题是【小时级】。
         ⟹ 建议先拿 20 题跑通链路，再放全量。

    ⚠️ 还有两件必须记在跑之前的事（否则跑完了没法写口径）：
      ④ ★★★ 把 §8.7 那六件事的答案先写进一个文件里。
         ⟹ 🔑 跑完再回忆"我当时轮数上限设了多少"是回忆不起来的。
      ⑤ ★★ 至少跑两遍全量（或者同一批 20 题跑三遍）。
         ⟹ ✅ Table 10 显示同配置重跑的极差有 1.34 个百分点。
         ⟹ ★★★ 不知道自己的噪声，就没法判断任何改动是不是真的有效。

    🔑 但说实话，★★★ 对你自己的业务来说，
       12 章那条路（自建小评测集）比复现榜单值钱得多。
