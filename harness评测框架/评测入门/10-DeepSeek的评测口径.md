## 10.1 第一个发现：他们的分类，就是 03 章那三个原语

✅ 论文 §4.4.1 原文（★ 这段值得逐字读）：

> "we adopt **perplexity-based evaluation** for datasets including HellaSwag, PIQA,
> WinoGrande, RACE-Middle, RACE-High, **MMLU**, MMLU-Redux, MMLU-Pro, MMMLU,
> ARC-Easy, ARC-Challenge, C-Eval, CMMLU, C3, and CCPM, and adopt
> **generation-based evaluation** for TriviaQA, NaturalQuestions, DROP, MATH,
> **GSM8K**, MGSM, HumanEval, MBPP, LiveCodeBench-Base, CRUXEval, BBH, AGIEval,
> CLUEWSC, CMRC, and CMath. In addition, we perform **language-modeling-based
> evaluation** for Pile-test and use **Bits-Per-Byte (BPB)** as the metric to
> **guarantee fair comparison among models using different tokenizers**."

★★ 把这段和 03 章那三个抽象方法并排放，🔑🔑 一字不差地对上了：

| DeepSeek 报告里的说法 | lm-eval-harness 的原语 | 模型实际在干什么 | 这份报告里用它测的数据集 |
|---|---|---|---|
| **perplexity-based** | ★★ `loglikelihood` | ★ 不说话，只给几个候选句子打分，比哪个更"顺" | MMLU、MMLU-Redux、MMLU-Pro、HellaSwag、PIQA、WinoGrande、ARC、C-Eval、CMMLU…… |
| **generation-based** | ★★ `generate_until` | ★ 自由生成一段文字，再从里面抽答案 | GSM8K、MATH、HumanEval、MBPP、DROP、BBH、TriviaQA、LiveCodeBench-Base…… |
| **language-modeling-based** | ★★ `loglikelihood_rolling` | ★ 对一整篇长文算"每个字节要多少比特"，不涉及题目和答案 | Pile-test（✅ 只有这一个，指标用 BPB） |

```
   ⟹ ★★★ 两个互不相干的团队，各自独立收敛到【同一个三分法】。
      🔑 说明 03 章讲的不是某个框架的实现细节，
         而是【这件事本身就只有这三种做法】。

   ⚠️ 顺带一个立刻能用的推论：
      ★★ 看到一份报告把 MMLU 和 HumanEval 的分数并排列在一张表里，
      ⟹ 这两个数【背后是两种不同的测量机制】，
         ★ 一个连"输出"都没有，另一个要经过抽取和比对。
      🔑 它们能放在一张表里，只是因为都被归一成了 0–100 的数。
```

```
    ★ 名词：perplexity（困惑度）
      衡量"模型对一段文本有多意外"的指标。★★ 越低说明模型越觉得这段话自然。
      ⟹ 它和 loglikelihood（对数似然）是同一个东西的两种写法。

    ★ 名词：BPB = Bits-Per-Byte（每字节比特数）
      ★★ 平均编码一个【字节】需要多少比特。

    ★ 名词：tokenizer（分词器）
      把一串文字切成模型能吃的基本单位（token）的那个程序。
      ⚠️ 每家模型的分词器都不一样，这就是下面那个问题的根源。
```

★★★ 那个 BPB 的理由值得单独说，因为它是全章第一个"口径对齐"的范例：

```
    ⚠️ 问题：不同模型的分词器不一样。
       同一句中文，A 模型切成 12 个 token，B 模型切成 20 个。
       ⟹ 🔑 那"每个 token 的困惑度"就【根本没法比】——
          分母都不是同一个东西。
```

★★ 用一个小算例把它算透（⚠️ token 数是我编的，只为演示分母问题）：

| | A 模型 | B 模型 | ⚠️ 结论 |
|---|---|---|---|
| 同一段中文，共多少字节 | 1200 字节 | 1200 字节 | ★★★ 字节数**相同** —— 这是物理事实 |
| 它的分词器切出多少 token | 400 个 | 600 个 | ⚠️ 差 1.5 倍 |
| 这段文本总共需要多少比特（假设值） | 3600 bit | 3600 bit | ★ 假设两个模型建模能力完全一样 |
| **每 token 多少比特** | 3600 ÷ 400 = **9.0** | 3600 ÷ 600 = **6.0** | ⚠️★★★ 看起来 B 好得多，**但这是假象** |
| **每字节多少比特（BPB）** | 3600 ÷ 1200 = **3.0** | 3600 ÷ 1200 = **3.0** | ✅ **相等** —— 这才是真相 |

```
    ⟹ ★★★ 所以解法是：换成【每字节】。
       字节是物理事实，谁的分词器都改变不了它。
       ✅ 论文原话就是 "to guarantee fair comparison among models
          using different tokenizers"。

    🔑🔑 记住这个思路：★★★ 当两个数不可比时，
       找一个【双方都无法影响的分母】。
    ⟹ ⚠️ 反过来，看到有人用"每 token 困惑度"横向比不同家的模型，
       ★★ 那个对比是无效的 —— 分母被各家的分词器掌控着。
```

## 10.2 第二个发现：他们自己承认分数会漂

✅ 论文 §4.4.2（★ 逐字）：

> "We evaluate all these models with **our internal evaluation framework**, and
> ensure that they share the **same evaluation setting**. Note that **due to the
> changes in our evaluation framework over the past months**, the performance of
> DeepSeek-V2-Base exhibits **a slight difference from our previously reported results**."

```
    ⟹ 🔑🔑🔑 读懂这句话：

    ★★★【同一个模型（V2-Base），同一个团队，只是评测框架改了几个月，
       分数就和自己上次公布的不一样了。】

    ⟹ 模型一个权重都没动。动的全是 harness。
```

★★ 这一句话，把 01 章的中心论点从"我的说法"变成了【一线团队的书面承认】：🔑🔑 分数是【模型 + 评测方法】的联合产物，不是模型的固有属性。

★★ 而且请注意他们的处理方式——他们做的是**两件事**，而第二件事是绝大多数技术报告不会做的：

| | 他们做了什么 | 为什么这件事重要 | ⚠️ 大多数报告的做法 |
|---|---|---|---|
| ① | ✅ 用**同一套框架重新跑了所有对比模型** | ★★ 保证一张表内部口径统一，横向比较才有意义 | ⚠️ 直接抄各家自己公布的数（口径全不同，见 [11 章 §11.6](11-怎么读懂一张榜单.md) ②） |
| ② | ✅ ★★★ 主动声明"**我们自己的历史数字对不上了**" | ★★ 这是一个**自我举证的负面信息**，没有任何宣传价值 | ⚠️ 不提。旧数字就让它留在旧报告里，没人会去对 |

```
    ⟹ ⚠️ 第 ② 条是判断一份报告可信度的最强信号之一：
       ★★★ 愿意公布对自己不利的信息，说明他们在意【正确】而不只是【好看】。
    ⟹ 🔑 看到有人这么写，可信度应该往上调。

    ⚠️ 也要注意 "slight"（轻微）这个词是他们自己的形容，没给数字。
       ★★ 所以严谨的说法是：【方向确定（会漂），量级未知】。
```

## 10.3 第三个发现：他们给出了噪声下限

✅ 论文 Table 3 表注（★ 逐字）：

> "**Scores with a gap not exceeding 0.3 are considered to be at the same level.**"

```
    ⟹ 🔑🔑 翻译：★★★【差 0.3 分以内，我们认为是平手。】

    ★★ 为什么必须有这么一条？因为评测本身有噪声：
       采样温度、题目顺序、浮点非确定性、few-shot 抽哪几条示例……
       ⟹ 同一个模型跑两遍，分数就可能差零点几。
```

★★★ 这条线是怎么定出来的？论文没说。**但它的量级可以自己算出来**——而且算出来的结果和 0.3 惊人地接近。⟹ 完整推演在 [11 章 §11.6](11-怎么读懂一张榜单.md) ①，这里只代一个数：

```
    ★ 把"答对一道题"看成抛一次硬币，正面概率 p，一共 n 道题。
      ⟹ 准确率的标准误（standard error，同一套设置重跑一遍会晃动多少）：

         ★★★ SE = √( p × (1 − p) ÷ n )

    ⟹ 代进 MMLU（✅ 测试集 14042 道题）和 87 分这个水平：
         p(1−p) = 0.87 × 0.13     = 0.1131
         ÷ n     = 0.1131 ÷ 14042 = 0.00000806
         开平方                    = ⚠️ 0.00284 = 【0.28 个百分点】
```

| 基准 | 题数 n | 取 p = | ⚠️ SE ≈ | 🔑 对照 DeepSeek 的 0.3 线 |
|---|---|---|---|---|
| **MMLU** | 14042 | 0.87 | **0.28 pp** | ✅ 几乎重合 ⟹ ★★★ 那条 0.3 是【一个标准误】的量级，不是拍脑袋 |
| MMLU-Pro | 12032 | 0.60 | ⚠️ 0.45 pp | ⚠️ 比 0.3 大 ⟹ 在 MMLU-Pro 上「差 0.3 算平手」还**偏严** |
| MATH-500 | 500 | 0.50 | ⚠️ 2.24 pp | ⚠️ 0.3 这条线在这里**完全不够用**，差 2 个百分点都是噪声 |
| AIME 2024 | **30** | 0.50 | ⚠️ 9.1 pp | ⚠️★★★ 30 题里多对 1 道 = 3.33 pp ⟹ 差几个百分点等于没差别 |

```
    ⟹ 🔑🔑 这张表解释了 §10.5 ② 那条规则为什么存在：
       ✅ 报告原话是「少于 1000 题的基准要多跑几遍」，
       ★★★ 因为题一少，SE 就大到能吞掉整个差距。

    ⟹ ★★★ 所以"我们比对手高 0.2 分"这种宣传，
       在 DeepSeek 自己的口径下，★★【等于没差别】。
    ⚠️ 而"我们 AIME 比对手高 3 分"这种宣传，
       ★★★ 在统计上同样【等于没差别】—— 只是多对了一道题。
```

```
    🔑 给你的行动项：
       ★★★ 以后看到任何两个模型的分数对比，先问两句：
          ①【这个基准有多少道题？】
          ②【这个差距，超过噪声了吗？】
       ⟹ 呼应 [09 章 §9.5](09-LLM当裁判.md) ③ 那个 Elo 的 bootstrap 置信区间
          ——同一个道理的两种表达。
```

## 10.4 第四个发现：few-shot 数量是逐题设置的，不是一刀切

✅ 论文 Table 3 的 "# Shots" 列（★ 摘录，⚠️ 第三列是我的解读，论文没给理由）：

| Benchmark | ✅ # Shots | ⚠️ 为什么可能是这个数（我的解读） |
|---|---|---|
| PIQA (EM) | **0-shot** | 常识判断题，不需要格式示范 |
| AGIEval (EM) | **0-shot** | 标准化考试题，题面自带格式 |
| BBH (EM) | **3-shot** | 推理题，★ 示例要顺带示范"怎么写推理过程" |
| DROP (F1) | **3-shot** | 阅读理解，要示范答案的粒度（抽一个词还是一句话） |
| **MMLU (EM)** | ★ **5-shot** | ★★ 领域惯例。⟹ 为了和别人报的数可比，**必须照抄** |
| MMLU-Redux | 5-shot | 同上（MMLU 的标注修正版） |
| MMLU-Pro | 5-shot | 同上（MMLU 的加难版） |
| WinoGrande | 5-shot | — |
| TriviaQA | 5-shot | — |
| HellaSwag (EM) | **10-shot** | — |
| ARC-Easy | ★ **25-shot** | ⚠️ 这个数字异常大，见下 |
| ARC-Challenge | ★ **25-shot** | ⚠️ 同上 |

```
    ⟹ 🔑 从 0 到 25，跨度极大。★★ 这印证了 04 章的核心论点：
       ★★★ few-shot 数量【不是一个可以随便定的超参数】，
       它是【这个基准的身份证的一部分】。

    ★ 名词：EM = Exact Match（精确匹配）—— 抽出来的答案和标准答案逐字相同才算对。
    ★ 名词：F1 —— 精确率和召回率的调和平均，⟹ 用于"答案是一小段文字、
      允许部分重叠"的题（DROP 这类抽取式阅读理解）。

    ⚠️ ARC 用 25-shot 是沿袭 HuggingFace Open LLM Leaderboard 的历史惯例
       （⚠️ 我的判断，论文未说明理由）。
       ⟹ ★★ 但这恰恰说明问题：★★★ 这些数字是【约定俗成】的，
          不是推导出来的。你必须照抄，否则分数不可比。

    🔑🔑 所以 04 章那句话要再强调一遍：
       ★★★ 报 MMLU 分数不说 shot 数，等于没报。
```

★★ 这张表还有一个容易被漏掉的读法：**同一份报告里，shot 数只出现在 base 模型表（Table 3）上**。

| | base 模型表（V3 报告 Table 3） | chat 模型表（V3 报告 Table 6） |
|---|---|---|
| 有没有 "# Shots" 列 | ✅ **有**，逐基准标注 | ⚠️ **没有** |
| ⟹ 所以 chat 那些分数的 shot 数 | — | ⚠️ 只能从「提示词用 simple-evals」去推它的默认值 |
| 🔑 读者该怎么处置 | ★★ 可以放心和别家的同 shot 数比 | ⚠️★★★ 当成「口径未完全披露」，**不要和别家的 MMLU 直接比大小** |

```
    ⟹ ⚠️ 这不是批评。★★ 它说明的是一个更普遍的事实：
       ★★★ 即便是全书里披露最详细的这份报告，
       chat 模型那一半的口径也没写全。
    ⟹ 🔑 所以 [11 章 §11.8](11-怎么读懂一张榜单.md) 那张清单里，
       「查不到」这一列才是常态，不是例外。
```

## 10.5 第五个发现：chat 模型的评法，和 base 模型完全不是一回事

★★★ 这是本章最重要的一节。

✅ 论文 §5.3.1 "Detailed Evaluation Configurations"（★ 逐字拆解）：

### ① 提示词直接借用别人的框架

> "For standard benchmarks including MMLU, DROP, GPQA, and SimpleQA, we adopt
> the evaluation prompts from the **simple-evals** framework."
> "We utilize the **Zero-Eval prompt format** for MMLU-Redux in a **zero-shot** setting."
> "For other datasets, we follow their **original evaluation protocols with default
> prompts as provided by the dataset creators**."

★★★ 注意这里的对比：**同一份报告里 MMLU 出现了两次，口径不同**。

| | V3-Base（Table 3） | V3-chat（Table 6） |
|---|---|---|
| **范式** | ① 判别式（perplexity-based，比四个选项的对数似然） | ② 生成式（让它写出来，再抽答案） |
| **提示词来源** | 数据集原始协议 | ✅ **simple-evals** 框架 |
| **shot 数** | ✅ 5-shot | ⚠️ 报告未写 |
| **报出来的分数** | ✅ **87.1** | ✅ **88.5** |

```
    ⟹ ★★★ 这两个 87.1 和 88.5【不能相减说"对齐带来 +1.4"】。
       ⚠️ 三重原因，任何一条都足以否掉这个减法：
          ① 连测量方式都换了（判别式 → 生成式）
          ② 模型也换了（base → chat，权重不同）
          ③ shot 数一个是 5、一个未披露

    🔑 这正是 01 章那个 12.6 分差示例的真实版本：
       ★★ 同一个基准名字底下，藏着完全不同的测法。
    ⟹ 🔑🔑 顺手记住一条通用规则：
       ★★★ 两个数能相减，前提是【除了你关心的那一项，其余口径全都相同】。
       ⚠️ 这个前提在公开榜单上几乎从不成立。
```

```
    ★ 名词：simple-evals
      ★★ OpenAI 开源的一套极简评测提示词集合。
      ⟹ 🔑 DeepSeek 直接借用它，是为了【和 OpenAI 报的数可比】。
      ★★★ 这是一个很清醒的工程决策：
         与其自己定一套更"合理"的口径，不如用对手用的那套。

    ★ 名词：Zero-Eval
      ★★ 一套专门做 zero-shot（零示例）评测的提示词格式。
      ⟹ ✅ 报告只在 MMLU-Redux 上用它，且明写是 zero-shot。
```

### ② 数学题：温度、跑几遍，全部写死

> "For mathematical assessments, **AIME and CNMO 2024 are evaluated with a
> temperature of 0.7, and the results are averaged over 16 runs**, while
> **MATH-500 employs greedy decoding**."

| 基准 | ✅ 题数 | ✅ 采样设置 | ✅ 怎么汇总 | ⚠️ 为什么这么设（结合 §10.3 的 SE） |
|---|---|---|---|---|
| **AIME 2024** | 30 | T = 0.7，**跑 16 次** | 取平均 | ⚠️ 题极少 ⟹ SE ≈ 9.1 pp，单次跑方差极大，**必须多跑** |
| **CNMO 2024** | 数十题量级 | T = 0.7，**跑 16 次** | 取平均 | ⚠️ 同上 |
| **MATH-500** | 500 | **greedy（T = 0）** | 单次结果 | ★★ 样本够（SE ≈ 2.2 pp），⟹ 直接贪心，**换来完全可复现** |

```
    ★ 名词：greedy decoding（贪心解码）
      每一步都选概率最高的那个 token。★★ 等价于 temperature = 0。
      ⟹ 🔑 同样输入必得同样输出 ⟹【逐次可复现】。

    ⟹ 🔑🔑 这条设置的价值在于它【解释了 why】：
       ★★★ 题目越少，越必须多跑取平均；题目够多，就该用贪心保复现。
    ⚠️ 但注意 §10.7b 会给出这条规则的例外：
       ★★★ 对长输出的推理模型，greedy 反而是坏选择。
```

★★ 表注里还有一句总纲（✅ 逐字）：

> "**Benchmarks containing fewer than 1000 samples are tested multiple times
> using varying temperature settings to derive robust final results.**"

```
    ⟹ ★★★【1000 题】是他们划的线。少于这个数就必须多跑。
    ⟹ 🔑 用 §10.3 那个公式验一下这条线合不合理：
       n = 1000、p = 0.5 ⟹ SE = √(0.25 ÷ 1000) = ⚠️ 1.58 个百分点。
       ★★ 也就是说：即便到了 1000 题，单个分数的抖动仍有 1.5 个百分点量级。
       ⟹ ⚠️ 所以这条线是个【工程折中】，不是"过了 1000 题就没噪声了"。
    ⚠️ 这条规则我在别的报告里很少见到写得这么明确。
```

### ③ 输出长度上限：一个数字定死全场

> "We allow all models to output a **maximum of 8192 tokens** for each benchmark."
> "All models are evaluated in a configuration that **limits the output length to 8K**."

```
    ⟹ 🔑 回看 05 章那个"最常见的坑"：

## 10.7 第七个发现：训练侧也在为"能抽取"服务

★★ 这是我认为最有意思的一条，它把 05 章和训练连起来了。

✅ 论文 §5.2.1 "Rule-Based RM"（★ 逐字）：

> "For questions that can be validated using specific rules, we adopt a rule-based
> reward system... certain math problems have deterministic results, and we
> **require the model to provide the final answer within a designated format
> (e.g., in a box)**, allowing us to **apply rules to verify the correctness**."

```
    ★ "in a box" 指数学界通用的 LaTeX 写法 \boxed{42}。
    ★ 名词：RM = Reward Model（奖励模型）—— 强化学习里给模型输出打分的那个部件。
      ★★ "Rule-Based RM" 就是【用规则代替模型来打分】。
```

★★★ 读懂这层含义，它是一个**双向的因果**：

```
   05 章的处境          DeepSeek 的做法             结果
   ──────────────────────────────────────────────────────────────
   评测端写正则去抠  →  ★★★ 在【训练阶段】就把    →  ⟹ 评测时那条正则
   答案，经常抠不准      格式教进去：强化学习的        【几乎不会失手】
   ⟹ 抽不到 = 判错      奖励规则本身就要求
                        "答案必须写在 \boxed{} 里"
```

| | 只在评测端努力（多数做法） | ★★★ DeepSeek 的做法：训练端也管 |
|---|---|---|
| **抽取规则** | 写越来越复杂的正则去兜住各种写法 | ★ 一条简单规则就够：抠 `\boxed{}` 里的东西 |
| **抽取失败率** | ⚠️ 高，且随模型改版波动 | ★★ 极低 |
| **谁在适应谁** | 评测适应模型 | ★★ **模型适应评测** |
| **副作用** | ★ 无 | ⚠️★★★ 模型的输出格式，一定程度上是【被评测方式塑造的】 |

```
    ⟹ ★★★ 这是一个双向的因果：
       评测方法 → 影响训练目标 → 塑造模型行为 → 让评测更准。

    ⚠️ 但也要看到硬币的另一面（⚠️ 我的判断，论文未讨论）：
       ★★ 好处很实在 —— 抽取这一层的噪声被基本消掉了。
       ⚠️ 代价是模型被训得"爱按评测喜欢的格式说话"。
       ⟹ 呼应 09 章冗长偏差那一节的推断：
          🔑 评测的偏好会顺着训练回流进模型行为。
    ⟹ 🔑🔑 更一般的结论：★★★ 当一个格式被写进奖励函数，
       它就不再只是"输出风格"，而变成了模型能力的一部分。
```

## 10.7b 第八个发现：R1 报告推翻了"greedy 最可复现"这条常识

⭐⭐ 前面 10.1–10.7 全部取自 **DeepSeek-V3 技术报告**（arXiv:2412.19437，53 页）。这一节换标本：**DeepSeek-R1 技术报告**（arXiv:2501.12948，86 页，已校验）。

★★ 为什么要单独看 R1？因为它是**推理模型**（reasoning model，会先输出一长段思考过程再给答案），⟹ 🔑 而推理模型的评测口径，和普通 chat 模型**有一处根本性的不同**。

### ✅ 原文：他们明确说「不用 greedy」

> "We set the maximum generation length to **32,768 tokens** for the models.
> We found that using **greedy decoding** to evaluate long-output reasoning models
> results in **higher repetition rates and significant variability across different
> checkpoints**. Therefore, we default to **pass@k** evaluation and report pass@1
> using a **non-zero temperature**. Specifically, we use a sampling temperature of
> **0.6** and a **top-p value of 0.95** to generate k responses (typically between
> 4 and 64, depending on the test set size) for each question. Specifically, we use
> **k = 64 for AIME and GPQA, k = 16 for MATH and CodeForces, and k = 8 for LCB**."

```
   ★ 名词补全：
   ★ greedy decoding（贪心解码）= 每一步都取概率最高的那个词。
     ⟹ 同一个输入永远给同一个输出，所以看起来【最可复现】。
   ★ temperature（温度）= 采样的随机程度。0 = greedy，越大越随机。
   ★ top-p（核采样，nucleus sampling）= 只在累计概率达到 p 的那批候选词里采样。
     ⟹ 0.95 表示：把概率最低的那 5% 尾巴直接砍掉，防止采到离谱的词。
   ★ LCB = LiveCodeBench（一个只用"训练截止日之后新发布"的编程题的基准）。
```

✅ 论文给出的公式原文：

> pass@1 = (1/k) · Σᵢ pᵢ ，where pᵢ denotes the correctness of the i-th response.
> "This method provides more reliable performance estimates."

### ⚠️⚠️ pass@k 至少有两种算法，数值不同、语义不同

★★★ 这是全章最容易误读、也最该讲透的一处。**光看"pass@1"这四个字符，你不知道对面用的是哪一种。**

| | 算法 ① 无偏估计量（Codex / HumanEval 那一系） | 算法 ② 多次采样取平均（DeepSeek-R1 这一系） |
|---|---|---|
| **公式** | ✅ pass@k = 1 − C(n−c, k) / C(n, k)<br>n = 这道题一共采了几个，c = 其中对了几个 | ✅ pass@1 = (1/k) · Σᵢ pᵢ<br>pᵢ = 第 i 个回答的对错（0 或 1） |
| **语义** | ★★「采 k 个里**至少有一个**对」的概率 | ★★「随便采**一个**」的期望正确率 |
| **k 变大会怎样** | ★★★ 分数**单调变高** | ★★★ 分数**不变高，只变稳** |
| **为什么要 n > k** | ✅ Codex 论文的理由：直接采 k 次去算「有没有对」是**无偏但方差极大**（原文 "can have **high variance**"）⟹ 先采 n ≥ k 个再用组合数换算，无偏且方差小 | — |
| **出处** | ✅ Codex 论文 arXiv:2107.03374 | ✅ R1 报告（本节引文） |
| **R1 用的 k** | — | ✅ AIME/GPQA k=64、MATH/CodeForces k=16、LiveCodeBench k=8 |

★★★ 拿一个具体例子把两种算法都算出来。⟹ 设某道题采样 **n = 10** 个答案，其中 **c = 3** 个正确：

| k | ① 无偏估计量 1 − C(10−3, k) / C(10, k) | ⚠️ 错误做法：把 ĉ/n = 0.3 直接代进 1 − (1−0.3)^k | ② R1 式：k 次取平均 |
|---|---|---|---|
| **1** | 1 − C(7,1)/C(10,1) = 1 − 7/10 = **0.300** | 1 − 0.7 = **0.300** | 3/10 = **0.300** ← ✅ **只有 k=1 时三者一致** |
| **2** | 1 − 21/45 = **0.533** | 1 − 0.7² = **0.510** | **0.300** |
| **5** | 1 − 21/252 = **0.917** | 1 − 0.7⁵ = **0.832** | **0.300** |
| **10** | 1 − 0/1 = **1.000** | 1 − 0.7¹⁰ = **0.972** | **0.300** |

```
   ⟹ 🔑🔑🔑 三条结论，逐条都值钱：

   ① ★★★ 算法 ① 和算法 ② 【只在 k = 1 时数值相同】。
      ⚠️ k ≥ 2 之后，一个冲向 1.0，一个死死停在 0.300。
      ⟹ 🔑 所以 "pass@10 = 92" 和 "pass@1 = 71" 不是"高 21 个百分点"，
         ★★ 它们是【两个不同的问题】：
            pass@10 问"给它十次机会能不能蒙对一次"，
            pass@1  问"一次就要对的概率"。
      ⟹ ★★★ 产品里用户通常只给一次机会，所以 pass@1 才是你该看的那个。

   ② ⚠️ 中间那一列是常见的偷懒写法（把 c/n 当概率直接代公式），
      ★★ 它系统性地【偏低】（本例 k=5 时 0.832 vs 0.917，差 8.5 个百分点）。
      ⟹ ✅ 这不是我的推断：Codex 论文 Appendix A 明说它 "is **biased**"。
      ⚠️⚠️ 顺带纠一个流传很广的误说：
         ★★★ 「直接采 k 次那种算法【有偏】」—— ✅ 论文说它是【无偏但方差大】，
         ⟹ 真正有偏的是这条插值法。🔑 两者要用完全不同的办法对付：
            方差大 ⟹ 多采样本就收敛；有偏 ⟹ 采再多也不收敛到真值，必须换公式。
      ⟹ ★★ 三种算法的完整对比和一个 n=2 的最小反例，见
         [07 章 §7.7b](07-agentic编码评测与SWE-bench.md)。

   ③ ★★★ R1 那个 pass@1 名字叫 pass@1，含义是"单次尝试的期望正确率"。
      ⟹ 🔑 采样 64 次只是为了把这个期望【估准】，不是为了刷高分。
      ⚠️ 如果你看到两张榜单都写 "pass@1"，
         ★★★ 它们可能一个是 greedy 跑一次，一个是采样 64 次取平均。
         ⟹ 这两个数【不能直接比】：前者含着那一次的运气，后者是期望值。
```

### 🔑 为什么"最可复现"的 greedy 反而被放弃

| | 普通 chat 模型（V3 的处境） | ★★ 长输出推理模型（R1 的处境） |
|---|---|---|
| **单次输出长度** | ★ 几百个 token | ★★ 上限 **32,768 token**（✅ 报告原文） |
| **greedy 会怎样** | ✅ 一次跑完，确定性强 ⟹ V3 的 MATH-500 就是 greedy | ⚠️ 长序列 + 每步都取最高概率 ⟹ 极易进入**复读循环**：「所以答案是……所以答案是……」✅ 论文原话 "higher repetition rates" |
| **checkpoint 之间稳不稳** | ★ 尚可 | ⚠️ ✅ 论文原话 "significant variability across different checkpoints" ⟹ 训练中相邻两个 checkpoint 的分数会**剧烈跳动** |
| **结论** | ✅ 用 greedy，换来逐次可复现 | ✅ 换成 T=0.6 / top-p 0.95 采样 k 次取平均 ⟹ **单次不确定了，但统计量稳定了** |

```
   ⟹ 🔑🔑🔑 这是全章最值得记住的一条方法论：
   ★★★【可复现】有两种，不要混为一谈：
      ① 逐次可复现（同输入 → 同输出）—— greedy 提供的是这个
      ② 统计可复现（同配置 → 同分数）—— 多次采样取平均提供的是这个
   ⚠️ 对长输出模型，★★★ ② 比 ① 重要得多，因为你要比的是分数，不是某一条输出。

   ⚠️ 但也别把多采样当万能药。用 [11 章 §11.6](11-怎么读懂一张榜单.md) ① 那个方差分解看：
      ★★ 采样 k 次只摊薄【同一道题反复采样的抖动】那一项，
      ★★★ 摊不薄【AIME 只有 30 道题】这一项。
      ⟹ 🔑 所以 R1 在 AIME 上采 64 次，解决的是"这次跑得稳"，
         ⚠️ 没解决"换一套 30 道新题分数还一样吗"。
```

### 10.7b.1 R1 报告里其余的口径披露

★★ 下面这张表里每一行都是 ✅ 报告原文的披露。⚠️ 最后一列是我标的「这一项为什么值得读者留心」。

| 口径维度 | ✅ R1 报告的原文披露 | ⚠️ 读者要留心什么 |
|---|---|---|
| **最大输出长度** | 32,768 tokens（"capped at a maximum of 32,768 tokens for each benchmark"） | ★★ 是 V3 的 **4 倍** ⟹ 反过来证明 8K 对推理模型不够 |
| **采样参数** | temperature **0.6**，top-p **0.95** | ★ 全场统一，没有逐基准调 |
| **采样次数 k** | AIME / GPQA **k=64**，MATH / Codeforces **k=16**，LiveCodeBench **k=8** | ★★ k 随题数反向调：题越少、采样越多（§10.3 那张 SE 表解释了为什么） |
| **pass@1 怎么算** | (1/k) · Σᵢ pᵢ ，即 k 次取平均 | ⚠️★★★ 和 HumanEval 那一系的 pass@k **不是一个算法**（见上一节那张表） |
| **AIME 额外指标** | **cons@64**（多数投票，consensus / majority vote） | ★★ 这是"给它 64 次机会再投票"的分数 ⟹ ⚠️ **不能和 pass@1 放在一起排名** |
| **提示词来源** | MMLU / DROP / GPQA / SimpleQA → **simple-evals** 框架；MMLU-Redux → **Zero-Eval** 格式、zero-shot | ★ 和 V3 一致 ⟹ 说明他们在两份报告之间保持了口径 |
| ★★ **特殊改动** | MMLU-Pro / C-Eval / CLUE-WSC 原本是 few-shot，他们**改成了 zero-shot** | ⚠️★★★ 这三个分数**不在通行口径下**，见下面 ① |
| **LiveCodeBench** | CoT 格式；数据窗口 **2024-08 ~ 2025-01** | ★★ 给了数据窗口，这是**少见的好披露** ⟹ 换个窗口就是另一个基准 |
| **Codeforces** | 10 场 **Div.2** 比赛 + 专家编写的测试用例 | ⚠️ 换成别的场次、别的难度档，分数不可比 |

## 10.9 那"为什么同一个模型能差十几分"

★ 回答开篇承诺的问题。把前面所有发现合起来，差异的来源是可以逐项列举的——**而且每一项的证据等级不一样，必须分开标**：

| 换动的那一项 | 从 → 到 | ⚠️ 方向与量级 | 证据等级与出处 |
|---|---|---|---|
| ★★★ **范式** | 判别式 → 生成式 | ⚠️ **最大的一项，可达十几个百分点** | ⚠️ 量级是我的估计；✅ 同向一手旁证：01 章同模型同题三家机构报 61.9 / 68.2 / 74.5，极差 **12.6 个百分点** |
| ★★★ **对话模板** | 不套 → 套（或反之） | ⚠️ 套错可以让分数**腰斩** | ⚠️ 我的判断（[04 章 §4.4](04-few-shot与提示词.md) 讲的对话模板）；无单一论文给出数字 |
| ★★ **shot 数** | 0 → 5 | ⚠️ 几个到十几个百分点，⚠️ **且对指令微调模型方向可能是负的** | ⚠️ 经验归纳（04 章 §4.3）；⚠️ 可验算的机理算例见 [04 章 §4.3](04-few-shot与提示词.md) 那个可验算的算例：能力一格没动，分数从 20% 走到 80%（**60 个百分点**，⚠️ 构造算例非实测）；✅ 反向一手证据：R1 把 MMLU-Pro/C-Eval/CLUE-WSC 改成 zero-shot，理由是"few-shot 里的 CoT 可能损害 R1 的表现" |
| ★★ **提示词模板** | 自己写 → simple-evals | ⚠️ 几个百分点 | ⚠️ 估计；✅ 旁证：DeepSeek 选择借用 simple-evals，正是为了和 OpenAI 的数可比 |
| ★★ **CoT 开关** | 非 CoT → CoT | ✅ **+2.9 个百分点**（⚠️ 换成相对量是 +7.7%） | ✅ **一手实数**：V3 报告 Table 6，LiveCodeBench 37.6 → 40.5 |
| ★★ **抽取规则** | 严格 → 宽松 | ✅ **41.7 个百分点** | ✅ **一手实数**：[05 章 §5.2](05-答案抽取与打分.md)，同一个官方 YAML 里并列的两条流水线（`strict-match` 33.3% vs `flexible-extract` 75.0%）跑同一批输出。⚠️ 那 12 行样本是为演示构造的，但两条流水线都来自官方任务文件。✅ 旁证：DeepSeek 在训练端用 `\boxed{}` 奖励，把这一项压到接近 0（§10.7） |
| ★★ **max_tokens** | 8192 → 32768 | ⚠️ 对长输出推理模型可以是**几十个百分点** | ⚠️ 量级估计；✅ 一手支撑：R1 把上限从 V3 的 8192 提到 **32768**，说明 8K 对它确实不够 |
| ★ **温度与采样** | greedy → T=0.6 × 64 取平均 | ⚠️ 小基准上几个百分点 | ✅ 一手：R1 报告 "higher repetition rates and significant variability across different checkpoints" |
| ★★★ **pass@1 的算法** | greedy 跑一次 → k 次取平均 | ⚠️ 期望值相同，但**单次结果的方差**完全不同 ⟹ 单个数字可以差好几个百分点 | ✅ 算法差异见 §10.7b 的公式；⚠️ 数值差异是我的推算（[11 章 §11.6](11-怎么读懂一张榜单.md) ①） |
| ★★★ **agentic 脚手架** | RAG → 裸 shell → 完整 ACI | ✅ **2.67% → 11.00% → 18.00%**，**6.7 倍** | ✅ **一手实数**：SWE-agent 论文 Table 1（arXiv:2405.15793），同一个 GPT-4 Turbo，SWE-bench Lite；转述见 [08 章 §8.4](08-ClaudeCode与Codex怎么被评.md) |
| ★ **harness 版本升级** | 旧版 → 新版 | ✅ 方向确定会变，⚠️ 量级未知（原文只说 "slight"） | ✅ 一手：V3 报告 §4.4.2 |

```
   ⟹ 🔑🔑🔑 这些【全部会叠加】。
      ★★ 所以"同一个模型在不同 harness 下差十几分"不是异常，是常态。
      ⟹ 异常的是【两个不同来源的分数恰好一样】——
         ★★★ 那通常意味着其中一个是抄来的（§10.7b.1 ②）。
```

⚠️⚠️ 最后做一个**叠加推演**。🔑 下表除起点那个 87.1 之外，**每一个数字都是我编的演示值**，任何真实模型都不该按它去推算。⟹ 唯一可信的是：**方向全部向下，合计量级是几十个百分点**。

| 步骤 | 换了什么 | ⚠️ 假设的影响 | ⚠️ 累计分数（演示值） |
|---|---|---|---|
| **起点** | V3-Base 的口径：判别式 + 5-shot + 数据集原始协议 | — | ✅ **87.1**（这一个数是报告原文） |
| ① | 判别式 → 生成式，用正则抽 A/B/C/D | ⚠️ −5 pp（抽取失败 + 输出格式不规范） | ⚠️ 82 |
| ② | 5-shot → 0-shot | ⚠️ −3 pp | ⚠️ 79 |
| ③ | ★★★ 忘了套对话模板 | ⚠️ **−15 pp**（这是最狠的一刀） | ⚠️ 64 |
| ④ | `max_tokens` 从 8192 改成 256，推理被截断 | ⚠️ −5 pp | ⚠️ 59 |
| **终点** | 四项口径全部换过 | ⚠️ 合计 **−28 个百分点** | ⚠️ **59** |

```
   ⟹ 🔑🔑 这张表要传达的只有一句话：
      ★★★ 【87 和 59 可以是同一个模型、同一套题。】
   ⟹ ⚠️ 顺手提醒两个换算，它们在这类对比里最常被写错
      （完整说明见 [11 章 §11.7](11-怎么读懂一张榜单.md) 误读 E）：
      ★★ ① 87 → 59 是降了【28 个百分点】，⟹ 相对降幅是 28 ÷ 87 ≈ 32%。
      ★★ ② 「耗时减少 40%」不等于「加速 40%」，
            ⟹ 🔑 加速比 = 1 ÷ (1 − 0.4) = **1.67 倍**，也就是"加速 67%"。
```

```
    🔑 十二条带走（✅ 全部来自 DeepSeek V3 / R1 报告原文，⚠️ 为我的推算）：

    ① ★★★ 他们的三分法 = 03 章的三个原语，一字不差
       ⟹ 说明这不是框架实现，是【问题本身的结构】
    ② ✅ 他们自承：框架改了几个月，自家旧模型分数就对不上了
       ⟹ ★★★ 01 章论点的书面证据
    ③ ✅ 差 0.3 分以内算平手
       ⟹ ⚠️ 而且这条线算得出来：MMLU（14042 题）的标准误 ≈ 0.28 个百分点
       ⟹ 🔑 任何对比先问两句：【这基准几道题】【这差距超过噪声了吗】
    ④ ✅ shot 数逐题设置，0 到 25 不等 ⟹ ★★ 它是基准身份证的一部分
       ⟹ ⚠️ 但 shot 列只存在于 base 模型表；chat 模型那半没有
    ⑤ ✅ base 用 perplexity、chat 用 simple-evals 提示词
       ⟹ ★★★ 同一份报告里的 87.1 和 88.5 不可相减（连模型都换了）
    ⑥ ✅ SWE-bench 用 Agentless ⟹ ★★★ 报的是"模型 + 脚手架"，08 章实锤
       ⟹ ⚠️ 顺带：42.0 vs 38.8 只差 1 个标准误，这个差距【不够结实】
    ⑦ ✅ 训练时用 \boxed{} 当奖励规则
       ⟹ ★★ 评测方式会反向塑造模型行为
    ⑧ ✅ R1 明说【不用 greedy】：长输出推理模型 greedy 会复读、
       且 checkpoint 之间剧烈跳动 ⟹ 改用 T=0.6 / top-p 0.95 采样多次取平均
       ⟹ ★★★【逐次可复现】和【统计可复现】是两回事，后者更重要
    ⑨ ⚠️⚠️ pass@k 至少有两种算法（无偏估计量 vs k 次取平均），
       ★★★ 只在 k=1 时数值相同；⟹ 两张榜都写 pass@1 也不代表能比

       ⟹ ★★★ 会说自己方法边界的报告，比宣称零污染的报告可信

       ⟹ 🔑 这是全行业的系统性空白，也是你自建评测时最容易做得更好的一项
