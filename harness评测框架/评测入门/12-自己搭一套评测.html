12 · 自己搭一套评测

⭐⭐ 全篇的落地章。
★★ 前十一章全是"别人的分数怎么读"。这一章是"你自己的分数怎么建"。

⟹ 🔑 先说结论：★★★ 50 条你自己业务的真实样本，比任何公开榜单都值钱。
因为榜单在答的是"这个模型有多强"，你真正要答的是"这个模型对我有没有用"。

12.1 为什么必须自建：四条理由

   ┌─ ① 题目形状不一样 ─────────────────────────────────┐
   │  ★ MMLU 是四选一知识题；SWE-bench 是 Python 开源仓库。│
   │  ★★ 你的业务可能是：从合同里抽关键条款、生成电商    │
   │     客服回复、给代码加中文注释、对话改写成 SQL……    │
   │  ⟹ 🔑 形状完全不同的题，榜单分数【没有迁移性】。   │
   └───────────────────────────────────────────────────┘
   ┌─ ② 领域词汇不一样 ────────────────────────────────┐
   │  ★★ 医疗报告的"肿物"≠普通"tumor"；                │
   │     金融里的"资产"和日常的"资产"语义不同。          │
   │  ⟹ 通用基准测不出【你的领域里表现如何】。          │
   └───────────────────────────────────────────────────┘
   ┌─ ③ 质量标准不一样 ────────────────────────────────┐
   │  ★★★ 你的用户在乎什么，公开榜单可能完全不在乎。   │
   │  有些业务要求【绝对不能杜撰名字（hallucination，幻觉）】；有些要求【字数   │
   │  必须在 X 之内】；有些要求【必须回绝敏感查询】。   │
   │  ⟹ 这些【没有一条在 MMLU 或 SWE-bench 里出现】。   │
   └───────────────────────────────────────────────────┘
   ┌─ ④ 污染问题你自己最好控制 ────────────────────────┐
   │  ★ 06 章讲了：公开基准会被训进下一代模型。         │
   │  ⚠️ 但你自己的内部样本，只要不公开，                │
   │     ★★★【物理上不可能进任何模型的训练集】。         │
   └───────────────────────────────────────────────────┘

12.2 样本从哪里来

    ⟹ 🔑 最好的来源是【真实发生的输入输出】，而不是精心构造的题目。

    ┌─ 首选：线上日志 ──────────────────────────────────┐
    │  ★★ 用户真实的输入 ⟹ 覆盖你没想到的边界情况。     │
    │  ⟹ 随机抽样，并由人工确认"期望输出是什么"。       │
    │  ⚠️ 注意脱敏（姓名/账号等 PII，Privacy-sensitive）。│
    └───────────────────────────────────────────────────┘
    ┌─ 次选：人工构造的典型 ─────────────────────────────┐
    │  ★ 业务人员列出"模型最常被问到的 20 类问题"，        │
    │    每类各造 2-3 条。                               │
    │  ⚠️ 缺点：覆盖不了你没预料到的情况。              │
    └───────────────────────────────────────────────────┘
    ┌─ 补充：边界与压力测试 ─────────────────────────────┐
    │  ★★ 你知道的【最难】的几类输入：                   │
    │    超长文档、含噪声的输入、刻意模糊的指令、         │
    │    ★★★ 应该被拒绝的敏感查询。                     │
    └───────────────────────────────────────────────────┘

    🔑 多少够？
    ★★ 50-100 条就能做第一轮决策。
    ★★★ 能反映「分布」比「多」更重要——
       50 条覆盖 10 类的比 500 条全是同一类有价值得多。
    ⚠️ 不要为了"数据量大"去构造相似题——那是在降低多样性，不是提高质量。

12.3 期望输出（gold answer）怎么定

    ★ 名词：gold answer / gold label（黄金答案）
      ★★ 评测时对照的"正确参考"。问题是：★★★ 谁来写它？

    ⟹ 按难度分三级：

① 有客观答案的题——最容易

    ★★ 实体抽取、分类、结构化信息提取、SQL 生成、代码正确性。
    ⟹ 可以直接写出期望的值，后续用【精确匹配或规则】判。
    ⟹ 🔑 如果你的任务属于这类，★★★ 一定用精确判，而不是 LLM 裁判。
       09 章 Table 4 证明了：直接用 LLM 判有客观答案的题，
       ★★ 失败率高达 70%。

② 有参考答案但允许变体的题

    ★★ 摘要、改写、翻译、总结。
    ⟹ 写出 1-3 个"满意答案样本"，再用 LLM 裁判打相似度。
    ★ 或者：定义【必须包含的要点清单】，用 LLM 裁判逐项核对
      （这比"打一个总分"更稳定）。
    ⟹ 🔑 09 章那套两遍法（交换顺序）仍然推荐用上。

③ 完全开放的生成题

    ★★★ "给这个产品写一段营销文案"——没有唯一正确答案。
    ⟹ 两条路：
      a) ★ 把"好"的标准分解成【可检查的维度】：
         字数范围 / 包含关键词 / 语气是否符合品牌指引 / 无拼写错误…
         ⟹ 每一维度单独判，拼成一个总分。
      b) ★★ 退而求其次：和已部署方案比较（A/B 模式）。
         ⟹ 不问"绝对好不好"，只问"比原来好不好"。

    ⚠️ ③ 是最难的一类。如果你能把它转成 ①②，
       ★★★ 就尽量转——更稳、更便宜、更可复现。

12.4 判卷：三档复杂度，按需选择

★★ 和 05 章的"三层裁判阶梯"一样，但换到你自己业务的视角。

   ┌─ 第一档：规则/正则 ───────────────────────────────┐
   │  ★★★ 优先用这个。                                │
   │  ① 精确匹配（分类标签、提取的实体）               │
   │  ② 正则（日期格式、金额区间、包含某个关键词）      │
   │  ③ 代码：真跑一遍（07-08 章的思想复用到你的场景）  │
   │  ⟹ 🔑 快、准、零成本、可复现。                    │
   └───────────────────────────────────────────────────┘
   ┌─ 第二档：模型打分（LLM 裁判） ─────────────────────┐
   │  ★★ 规则搞不定时才用。                            │
   │  ⟹ 复用 09 章的所有防范：                         │
   │    - ★ 用带参考答案的提示词模板（Reference-guided） │
   │    - ★★ 跑两遍，交换顺序，取平均                  │
   │    - ★★★ 记录【裁判模型版本】，否则历史对比失效    │
   └───────────────────────────────────────────────────┘
   ┌─ 第三档：人工打分 ─────────────────────────────────┐
   │  ★★★ 建立新场景时的黄金标准，之后可以用来"校准"   │
   │  前两档。                                          │
   │  ⟹ 🔑 不必全量：★ 随机抽 10-20 条人工复核，       │
   │     ★★★ 和自动打分的结论做一致率检查。            │
   │  ⚠️ 一致率 < 70% ⟹ 自动打分方案必须重做。         │
   └───────────────────────────────────────────────────┘

12.5 复用框架还是手写

★★ 简短的答案：先手写，等数量上去再考虑框架。

   ┌─ 手写（推荐起点） ────────────────────────────────┐
   │  JSONL 文件，每行一条样本：                        │
   │  {"input": "...", "gold": "...", "tags": [...]}   │
   │  ★★★ 加一个 tags 字段，记录题目类别和难度级别，   │
   │      ⟹ 以后能按类分析失败模式。                   │
   │                                                    │
   │  判卷脚本 100 行 Python 就够：                     │
   │    for 每条样本：                                  │
   │      resp = 调 API 得回答                          │
   │      score = 判卷(resp, gold)                      │
   │      记录(sample, resp, score)                    │
   │  然后 pd.DataFrame 算一下总分和按 tags 的分布。    │
   └───────────────────────────────────────────────────┘
   ┌─ 什么时候引入 lm-eval-harness / EvalScope ────────┐
   │  ★★ 满足这三条再考虑：                            │
   │    ① 你要测的基准在框架里已经有实现                │
   │    ② 你需要跑多个模型做横向比较                    │
   │    ③ 你需要 loglikelihood（判别式）能力            │
   │  ⟹ 🔑 如果只是"跑一个模型、用 generate_until 打分"│
   │     ★★ 手写脚本 + JSONL 比框架更灵活、更好调试。  │
   └───────────────────────────────────────────────────┘
   ┌─ 什么时候引入 SWE-bench 那套思路 ─────────────────┐
   │  ★★★ 只当你的任务是【修改/生成代码，且有测试】。  │
   │  ⟹ 07 章那套"起容器 → 打补丁 → 跑测试"的流水线   │
   │     可以被裁剪移植到你的场景。                     │
   │  ★ 最小化版本：                                   │
   │    ① 准备"初始仓库快照" + "需求描述"              │
   │    ② 模型产出 diff                                │
   │    ③ 本地（不用 Docker 也行）apply + 跑你自己的 CI │
   └───────────────────────────────────────────────────┘

12.6 跑起来之后：一个最小可行的分析流程

★★ 跑完评测得到一堆分数，然后呢？

   ┌─ Step 1: 先看整体通过率 ──────────────────────────┐
   │  ★ 基准在这里：如果没有这个数，后面所有比较没意义。│
   └───────────────────────────────────────────────────┘
   ┌─ Step 2: 按 tags 细分，找问题集中的类别 ───────────┐
   │  ★★ "总分 75%"掩盖了可能"合同类 40%、客服类 90%"  │
   │  ⟹ 🔑 找到差的那类，才能知道下一步改哪里。        │
   └───────────────────────────────────────────────────┘
   ┌─ Step 3: ★★ 手动看失败案例（必做，不能跳过）───────┐
   │  ★★★ 抽出分数最低的 10-20 条，人工读一遍：         │
   │    ① 模型真答错了，还是判卷脚本误判了？            │
   │    ② 失败是因为【模型不会】，还是【提示词没说清】？ │
   │    ③ 有没有系统性的错误模式（比如都在日期解析上）？ │
   │  ⟹ 这一步是最有信息量的，比跑 1000 条多 10% 有用。 │
   └───────────────────────────────────────────────────┘
   ┌─ Step 4: 决策 ─────────────────────────────────────┐
   │  ★★ 把错误模式归类：                              │
   │    A. 提示词问题  → 改提示词，立即重跑              │
   │    B. 上下文不够  → 改检索/上下文策略               │
   │    C. 模型能力瓶颈→ 换模型 or 微调                  │
   │    D. ★ 评测本身有问题 → 先修评测，再谈其他          │
   │  ⟹ 🔑 ★★★ D 经常出现，而且比你想象的出现得频繁。  │
   └───────────────────────────────────────────────────┘

12.7 版本管理：让结果可复现

★★★ 一个只能跑一次、无法复现的评测，和没跑区别不大。

   最少要记录的四件事：

   ① ★★★ 模型标识符（model ID + API 版本号或 checkpoint 路径）
          ⟹ 同名模型会静默升级（03 章讲的"闭源 API 陷阱"）

   ② ★★★ 提示词版本（用 git commit hash 或文件 md5）
          ⟹ "上次的提示词"很快变成"不记得了"

   ③ ★★ 测试集版本（文件 hash 或 git tag）
          ⟹ 加了新样本，分数变了，你不知道原因

   ④ ★★ 判卷方案版本（LLM 裁判用的话：裁判模型 + 提示词 + 版本）
          ⟹ 09 章说过：★★ 换裁判 = 换尺子，历史对比全部失效

   ⟹ 🔑🔑 最简单的实现：一个 JSON/YAML 配置文件，
      ★★★ 每次评测把这四个字段一起存进结果文件里。

12.8 一个完整的小示例

★ 场景：你想评估"根据用户输入，给产品打一个类别标签（A/B/C/D）"的效果。
★★ 这是最干净的一类，完全用规则判，不需要 LLM 裁判。

# 样本格式（jsonl 文件，每行一条）
# {"input": "这个洗发水洗完头发不干净", "gold": "C", "tags": ["personal_care", "complaint"]}

import json, os, re
from openai import OpenAI  # 或者 Anthropic 等任意 SDK

PROMPT = """你是一个产品评论分类助手。请将下面的评论分为 A/B/C/D 四类：
A = 正面好评  B = 中性/混合  C = 负面投诉  D = 无关/无意义
只输出一个字母，不要解释。

评论：{input}"""

client = OpenAI()

def run_eval(samples_path, model_id, output_path):
    results = []
    with open(samples_path) as f:
        samples = [json.loads(l) for l in f]

    for s in samples:
        resp = client.chat.completions.create(
            model=model_id,
            messages=[{"role": "user", "content": PROMPT.format(input=s["input"])}],
            temperature=0,      # ★ greedy，保证可复现
            max_tokens=4,       # ★ 只需要一个字母
        )
        pred = resp.choices[0].message.content.strip().upper()
        # 正则抽取：只要 A/B/C/D
        m = re.search(r'[ABCD]', pred)
        pred_label = m.group(0) if m else "[invalid]"  # ★ 呼应 05 章

        results.append({**s, "pred": pred_label,
                        "correct": pred_label == s["gold"]})

    # 存结果，含元数据（★ 12.7）
    with open(output_path, "w") as f:
        json.dump({"model": model_id,
                   "total": len(results),
                   "accuracy": sum(r["correct"] for r in results) / len(results),
                   "results": results}, f, ensure_ascii=False, indent=2)
    print(f"Accuracy: {sum(r['correct'] for r in results)/len(results):.1%}")

run_eval("samples.jsonl", "gpt-4o-mini", "eval_result.json")

    ⟹ 🔑 这段代码有几个"教训的具体化"：

    ★ temperature=0  ────────────── greedy，可复现（10 章 MATH-500 的做法）
    ★ max_tokens=4   ────────────── 不给它长篇大论，省 token 又避免被截断
    ★ "[invalid]"    ────────────── 05 章：抽取失败也要记录，不能丢掉
    ★ results 里保留 pred 原始值  ── 方便事后看失败案例（12.6 Step 3）
    ★ 元数据存进结果文件          ── 12.7 的最小化实现

12.9 两个常见误区

误区 A：「我先搭好框架，再收集样本」

    ⚠️ ★★★ 完全反了。
    ⟹ 先有 20 条真实样本 + 能跑通的最简判卷 ⟹ 再迭代框架。
    ★★ 没有样本的评测框架，就是一个空壳，测不出任何东西。

误区 B：「准确率 95% 就可以上线了」

    ⚠️ ★★ 95% 的含义完全取决于你的样本分布。
    ⟹ 如果那 5% 全在"拒绝敏感查询"这一类，★★★ 那是严重问题，
       ⚠️ 不是 "only 5% error rate" 这么轻巧。

    ⟹ 🔑 所以 12.6 Step 2 的"按 tags 细分"不可省略。
       ★★★ 某些类别的成功率你必须单独设定门槛，
       ⚠️ 加权平均会把关键失败掩盖掉。

12.10 本章总结，也是全篇总结

    🔑 这一章的五条：

    ① ★★★ 50 条自己业务的真实样本 > 任何公开榜单
       ⟹ 它们测的是"对你有没有用"，不是"模型有多强"
    ② ★★ 样本优先级：线上日志 > 业务人员构造 > 压力测试
    ③ ★★ 判卷优先级：规则/运行代码 > LLM 裁判（带参考答案）> 人工
    ④ ★★★ 手动看失败案例是最有信息量的一步，不能跳过
    ⑤ ★★ 版本管理（模型/提示词/测试集/裁判）让结果可复现
