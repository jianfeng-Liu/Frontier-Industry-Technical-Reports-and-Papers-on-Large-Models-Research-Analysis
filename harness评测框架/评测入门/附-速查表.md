## D. ⚠️⚠️ 三个"同名不同义"的陷阱

★★★ 这三个是全书最容易踩的坑，单独拎出来。

### ① pass@1 有两种完全不同的定义

| | **HumanEval 那一系**（取最大值语义） | **DeepSeek-R1 那一系**（取平均语义） |
|---|---|---|
| **pass@k 的含义** | 采样 k 个，★ 只要有一个对就算这题对 | `pass@1 = (1/k)·Σ pᵢ`，★★ k 次各自的对错取【平均】 |
| **pass@1 是什么** | 只采一个样本 | 采 k 个样本、每个单独判对错，再平均 |
| **k 变大会怎样** | 分数【变高】 | 分数【不变高，只变稳】 |
| **实际用的 k** | ✅ Codex 论文用 n=200、k≤100 | ✅ R1 用 k=64（AIME、GPQA）、16（MATH、CodeForces）、8（LiveCodeBench） |

⚠️ 🔑 两张榜单都写 "pass@1"，一个是 greedy 跑一次、一个是采样 64 次取平均 ⟹ ★★★【这两个数不能直接比】。

### ② "可复现"有两种

```
   ① 逐次可复现（同输入 → 同输出）   ← greedy 提供这个
   ② 统计可复现（同配置 → 同分数）   ← 多次采样取平均提供这个

   ✅ R1 报告的发现：长输出推理模型用 greedy 会
      "higher repetition rates and significant variability
       across different checkpoints"
   ⟹ 🔑 ★★★ 对长输出模型，② 比 ① 重要得多。
```

### ③ SWE-bench 有三个不同的题集

| 名字 | 题数 | 说明 |
|---|---|---|
| **SWE-bench**（全量 test） | 2,294 | ✅ 原论文的完整测试集，来自 12 个 Python 仓库 |
| **SWE-bench Lite** | 300 | ✅ 原论文 §2.4 给出的精简子集；只覆盖原来 12 个仓库里的 11 个 |
| **SWE-bench Verified** | 500 | ✅ OpenAI 在 2024-08 另行发布、经人工核验"题目确实做得出来"的子集，不在原论文里 |

⚠️ 🔑 ★★★ 三个数【绝对不能横向比较】。Verified 上的分数系统性高于全量，因为它剔除了描述不清、根本做不了的题。

⚠️ 原论文还有一个 dev split（225 题）用来调参，榜单上一般不报 —— 看到"SWE-bench 225"别以为是又出了个新子集。

## I. `pass@k` 的三种算法 —— 同一批采样结果能算出不同的数

★★ D① 讲的是 `pass@k` 这个**指标**有两种语义；这一节讲的是：就算语义相同，**算法**还有两种，算出来的数不一样。

前提：每道题采样 `n` 次，其中 `c` 次通过了测试。

| | **算法 A**（HumanEval 官方口径，无偏） | **算法 B**（图省事的算法，有偏） |
|---|---|---|
| **公式** | `pass@k = 1 − C(n−c, k) / C(n, k)` | `pass@k = 1 − (1 − c/n)^k` |
| **在算什么** | 从已采的 n 个样本里**不放回**地抽 k 个，算"这 k 个全失败"的概率 | 把 `c/n` 当成单次通过率，按独立重复试验算 |
| **对 n 的要求** | ★ 必须 `n ≥ k`。✅ Codex 论文用 `n=200`、`k≤100` | 只需要 `c/n` 这一个比例 |
| **偏与不偏** | ✅ 论文证明它**无偏** | ✅ 论文明说它**有偏**，而且是**系统性偏低** |

**还有算法 C**：干脆只采 k 次、看有没有一个对。

| | **算法 C**（直接法） |
|---|---|
| **公式** | 采 k 次，有一个通过就记 1，否则记 0 |
| **偏与不偏** | ⚠️ **也是无偏的** —— 这点反直觉，很多人以为「图省事」的做法就有偏 |
| **真正的问题** | ✅ 论文指出它**方差极大**（每道题只能得 0 或 1，就是一次伯努利试验） |

⚠️ 🔑 **三种算法里有偏的只有 B。** 常见的误说是把 B 的「有偏」安到 C 头上——**C 无偏、只是方差大；B 才系统性偏低**。只有 `k=1` 时三者一致。（出处：Codex 论文 arXiv:2107.03374 Appendix A。）

**一组小数字对照**（`n=10`、`c=3`；⚠️ `n=10` 正好是 LiveCodeBench 每题的实际采样数）：

| k | 算法 A（无偏） | 算法 B（有偏、偏低） | 差 |
|---|---|---|---|
| 1 | 30.00% | 30.00% | 0 |
| 5 | 91.67% | 83.19% | **低了 8.5 个百分点** |
| 10 | 100.00% | 97.18% | 低了 2.8 个百分点 |

⟹ 🔑 ★★★ `k=1` 时两者完全相同，所以 pass@1 不受这件事影响；**k 一变大就分叉**，算法 B 会把成绩压低。✅ Codex 论文 Figure 13 原话（★ 逐字）："While the top expression may look correct, it underestimates the true value by a considerable margin."（算法 B 看起来像是对的，但它把真实值低估了相当大的幅度。）

⚠️ 所以报 `pass@k`（k>1）时必须一起写清：用的是哪种算法、`n` 是多少。只写"pass@10"三个字，等于没写。

## J. 差多少才算真有差别 —— 一条能当场算的噪声下限

★★★ 榜单上两个模型差 1 个点，绝大多数情况下是噪声。这一节给你一条当场就能算的判据。

n 道题、准确率 p 时，这个分数自身的**标准误**（standard error，缩写 SE，指"同样的评测重跑一遍，分数典型的抖动幅度"）：

```
   SE ≈ sqrt( p * (1 - p) / n )

   代入 n=500、p=0.5：
   SE ≈ sqrt(0.25 / 500) ≈ 0.0224   =>  约 2.2 个百分点
```

⟹ 🔑 ★★★ **500 道题、成绩在五成上下时，单个分数自己就带着约 ±2.2 个百分点的抖动。** 所以榜单上差 1 个点，基本可以当没差别看。

**常见题量的噪声下限**（都按最坏情况 p=0.5 算；95% 区间 ≈ ±1.96×SE）：

| 题量 n | 典型例子 | SE | 95% 区间 | ⟹ 多大的差距才值得当真 |
|---|---|---|---|---|
| 100 | 自建的小评测集 | 5.0 pt | ±9.8 pt | 差 10 个点以下都别下结论 |
| 164 | HumanEval | 3.9 pt | ±7.7 pt | 差 8 个点以下要慎重 |
| 300 | SWE-bench Lite | 2.9 pt | ±5.7 pt | ★★★ Lite 上差 5 个点约等于噪声 |
| 500 | SWE-bench Verified | 2.2 pt | ±4.4 pt | 差 4 个点以下要慎重 |
| 1,000 | 中等规模基准 | 1.6 pt | ±3.1 pt | 差 3 个点以下要慎重 |
| 2,294 | SWE-bench 全量 | 1.0 pt | ±2.0 pt | 差 2 个点以下要慎重 |

⚠️ 四条必须一起记住的限制，否则这张表会被用歪：

- p 离 0.5 越远，SE 越小。SWE-bench 那种 p≈0.2 的量级：n=300 时 SE≈2.3 pt，n=500 时 SE≈1.8 pt。⟹ **上表是保守（偏大）的估计，可以直接拿来用。**
- 上表算的是**一个分数自己**的抖动。比较**两个模型**时，差值的误差原则上更大；但如果两个模型跑的是**同一批题**，题目难易这部分误差会互相抵消，实际比"两个 SE 相加"小得多。⚠️ 严格做法是做配对检验（McNemar 检验），不是把两个 SE 直接加起来。
- 这条只覆盖**采样噪声**。它管不了数据污染、抽取失败、脚手架差异 —— 那几项的影响比噪声大一个数量级。⟹ 也就是说，**过了噪声门槛只是最低要求，不等于差距是真的。**
- AIME 这种一年 30 题的基准，n=30 时 SE≈9.1 pt。⚠️ 单跑一遍的 AIME 分数几乎没有可比性 —— 这正是 ✅ R1 要在 AIME 上采 64 次取平均的原因。

⟹ ✅ 对照：DeepSeek-V3 报告给自己定的噪声下限是 **0.3**（分差不超过 0.3 视为同一水平），比上表严格得多 —— 因为他们的基准题量大，而且所有模型都在同一套框架、同一套设置里跑出来的。

## K. 两条最常被搞错的换算

### ① 百分比（%）和百分点（pt）不是一回事

| 说法 | 意思 | 同一件事的例子 |
|---|---|---|
| "提高了 10 **个百分点**" | 两个百分数**相减** | 40% → 50% |
| "提高了 10 **%**" | **相对**提升，即乘 1.10 | 40% → 44% |

⟹ 🔑 同一个变化（40% → 50%）既可以写成"+10 个百分点"，也可以写成"+25%"。⚠️ 宣传材料偏爱后者，因为数字更大。**看到带 % 的提升，先确认它是差值还是比值。**

### ② 「时间减少 X%」不等于「加速 X%」

```
   加速倍数     = 1 / (1 - 时间减少比例)
   时间减少比例 = 1 - 1 / 加速倍数
```

| 时间减少 | ⟹ 加速倍数 | | 加速倍数 | ⟹ 时间减少 |
|---|---|---|---|---|
| 10% | 1.11× | | 1.25× | 20.0% |
| 20% | 1.25× | | 1.5× | 33.3% |
| 30% | 1.43× | | 2× | 50.0% |
| 50% | 2.00× | | 3× | 66.7% |
| 80% | 5.00× | | 5× | 80.0% |
| 90% | 10.00× | | 10× | 90.0% |

⟹ 🔑 ★★★ "耗时减少 50%" 等于 "2 倍加速"，不是 "50% 加速"。⚠️ 反过来，"10 倍加速"听着惊人，其实只是把耗时压掉了 90%：**时间减少永远不可能超过 100%，而加速倍数没有上限** —— 所以同一份优化写成加速倍数总是更好看。
