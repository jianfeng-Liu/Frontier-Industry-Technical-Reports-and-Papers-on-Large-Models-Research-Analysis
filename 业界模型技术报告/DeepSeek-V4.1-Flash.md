## 一、先给结论：这篇报告只干一件事

标题就是主旨：**Pushing the Limits of KV Cache Compression**（把 KV cache 压缩推到极限）。

先解释这个词。**KV cache** 是模型在生成文字时，把「已经读过的每个 token 算出来的中间结果」存下来复用的缓存。不存就得每生成一个字重算一遍全文，慢到不能用；存了就要占显存。**上下文越长，这块缓存越大，大到成为部署成本的主要来源**。

V4.1-Flash 的全部设计，都是为了让这块缓存变小。

| | DeepSeek-V4-Flash | **DeepSeek-V4.1-Flash** |
|---|---|---|
| 骨干参数 | 284B | **552B**（另有 196B Engram 参数）|
| 每 token 激活 | 13B | **prefill 8B / decode 16B** |
| 上下文 | 1M | 1M |
| 预训练数据 | 32T tokens | **45T tokens（多模态）** |
| 运行时 KV（常驻显存）| —— | **890 字节/token，是 V4-Flash 的 1/4** |
| 持久化 KV（存 SSD）| —— | **V4-Flash 的 1/8** |
| 多模态 | 外挂 | **原生**（预训练一开始就有图）|

**一句话**：模型骨干大了近一倍，KV cache 却小了 4 倍，效果还更好。

**最直观的对比** ✅：跑满 1M 上下文时，每 token 全局 KV 只要 **890 字节**。报告给出的代际对比是相对 V4-Flash 降 4 倍、相对 **V1 降 437 倍**。⚠️ 按这个倍数反推，V1 存同样 1M 上下文约需 **389 GB**（十进制 GB；换算成 GiB 是 362 GiB），而 V4.1-Flash 只要 **890 MB**（= 849 MiB）—— 从「一台机器装不下」变成「一张卡的零头」。（389 GB 是我用 890×437×1M 算的，报告只给了倍数。）

### ★ 把 552B / 8B / 16B 这三个数字自己加出来

报告在第十二节给了完整的架构超参表，**所以这三个数字是可以一项一项加出来验的**，不用信任何二手解读。用到的输入全部来自那张表：`40 层 / hidden 5120 / 1 共享 + 384 路由、激活 6 / 专家中间维 2304 / 编码器 20 层 + 解码器 20 层`。

**第一步：一个专家多大。** 一个专家就是一个 SwiGLU，三个矩阵（gate / up / down），每个 `5120 × 2304`：

```
一个专家 = 3 x 5120 x 2304 = 35.39 M
```

**第二步：总参数。**

| 组件 | 算式 | 数值 | 占 552B |
|---|---|---|---|
| 40 层 × 384 个路由专家 | $40 \times 384 \times 35.39\,\text{M}$ | **543.6 B** | **98.5 %** |
| 40 层 × 1 个共享专家 | $40 \times 35.39\,\text{M}$ | 1.42 B | 0.26 % |
| **已披露项小计** | | **545.0 B** | — |
| **✅ 报告写的骨干参数** | | **552 B** | — |
| **差额**（注意力 + Embedding + mHC + RMSNorm） | | **7.0 B** | 1.3 % |

**第三步：那 7.0 B 能不能对上？** ⚠️ 这一步是本文的推算。报告给了注意力的各个维度，按标准参数化拆开：

```
W_DQ   Q 降维        5120 x 1280                    =  6.55 M
W_UQ   Q 升维        1280 x (64 头 x 512 头维)        = 41.94 M
W_DKV  KV 降到 512   5120 x 512                     =  2.62 M
输出投影（分 8 组，每组中间维 1024）
       组内          8 x (4096 x 1024)              = 33.55 M
       组外          8192 x 5120                    = 41.94 M
索引器 Q（32 头 x 128）  5120 x 4096                 = 20.97 M
索引器 K（从主 KV 投影） 512 x 4096                   =  2.10 M
--------------------------------------------------------------
每层合计                                            ≈ 149.7 M
40 层                                               ≈ 5.99 B
+ Embedding & LM Head（⚠️ 词表未在表里，按 DeepSeek 一贯的 12.9 万估）
                     2 x 129280 x 5120              =  1.32 B
==============================================================
合计 ≈ 7.31 B    vs   差额 7.0 B    ->   差 4.4%   ★ 对上了
```

**第四步：激活参数 —— 这一步直接验证了 CED。**

| | 每层 | prefill（只跑 20 层） | decode（跑满 40 层） |
|---|---|---|---|
| MoE（6 路由 + 1 共享） | $7 \times 35.39 = 247.7$ M | 4.95 B | 9.91 B |
| 注意力 | 149.7 M | 2.99 B | 5.99 B |
| **小计** | 397.4 M | **7.94 B** | **15.90 B** |
| **✅ 报告值** | | **8 B** | **16 B** |
| 误差 | | **0.7 %** | **0.6 %** |

> 🔑 **这张表最该带走的一句话**：**`8 = 16 / 2`，而 `20 = 40 / 2`。** "prefill 8B / decode 16B"这个乍看神秘的写法，**全部内容就是"prefill 只跑一半的层"**——也就是第三节要讲的 CED。两笔账误差都在 1% 以内，说明 CED 确实没有在别的地方偷偷加回成本。

### ★ 稀疏度、FLOPs、深宽比：四个派生量

```
❌ 常见说法："384 选 6，所以稀疏 64 倍"

✅ 四个数字，四个不同的问题：
   384 / 6         = 64.0 倍   <- 只是【路由专家】的选择比
   552 / 8         = 69.0 倍   <- prefill 时的 总参数/激活参数
   552 / 16        = 34.5 倍   <- ★ decode 时的 总参数/激活参数（显存 vs 算力的正确口径）
   (552+196) / 16  = 46.8 倍   <- ★ 把 196B 的 Engram 表也算进存储之后
```

| 派生量 | 通式 | V4.1-Flash | 对照：V4-Pro | 对照：Kimi K3 |
|---|---|---|---|---|
| 每 token **prefill** FLOPs | $2N_{\text{激活}}$ | **16** GFLOPs | — | — |
| 每 token **decode** FLOPs | $2N_{\text{激活}}$ | **32** GFLOPs | 98 GFLOPs | 208 GFLOPs |
| 每 token **训练** FLOPs | $6N_{\text{激活}}$ | **96** GFLOPs | 294 GFLOPs | 625 GFLOPs |
| **深宽比** $d/L$ | hidden ÷ 层数 | $5120/40 = \mathbf{128}$ | $7168/61 = 117.5$ | $7168/93 = 77.1$ |

> ⭐ **Engram 的 196B 在这张表里【一个 FLOP 都没贡献】**——它是查表，不是矩阵乘。所以 `2N_激活` 那个通式对它不适用：**它是"参数量涨、FLOPs 不涨"那一类加法里最彻底的一种**（加 MoE 专家也能做到 FLOPs 几乎不涨，但 all-to-all 通信会变贵；三条路的对照见第九节）。这也是为什么把 196B 算进"激活参数"是错的。
>
> ⚠️ 上面所有数字都是本文按通式算的；报告只给了 `8B / 16B` 两个激活参数，没有给 FLOPs 的绝对值。`6N = 2N 前向 + 4N 反向`，**不含优化器**；长上下文下还要加 `12·L·s·h` 那一项，而 CSA2 改的正是那一项（见 [01 章 §1.5](大模型架构入门/01-鸟瞰全景.md)）。

## 二、贯穿全文的一个例子

后面每个创新点都用这同一个场景讲：

> **你让 AI agent 读一个 10 万 token 的代码仓库，然后连续问 10 个问题。**

这是典型的 **agent 工作负载**：输入极长、输出很短、反复追问。报告反复强调的 `input-heavy`（输入密集）就是指这个。V4.1-Flash 的每一处设计都在优化它。

先记住两个阶段的名字：
- **prefill（预填充）**：模型把这 10 万 token 读进去，算出 KV cache。**又慢又费算力。**
- **decode（解码）**：一个字一个字往外吐答案。**每步都要读一遍 KV cache，费显存带宽。**

---

## 三、创新点 1：CED —— prefill 只跑一半的层 ★最核心

### 问题是什么

40 层的模型读 10 万 token，传统做法是**每一层都要过一遍所有 token**：

```
层  0   ----  处理 10 万 token  ---->  产出本层 KV
层  1   ----  处理 10 万 token  ---->  产出本层 KV
 ...
层 39   ----  处理 10 万 token  ---->  产出本层 KV

合计：40 层 x 10 万 = 400 万「层·token」
```

agent 每次调用工具都会产生新的 prompt，缓存一旦没命中，这 400 万就得重算一遍。**这是 agent 场景最大的一笔开销。**

### CED 的解法：把 40 层劈成两半

**CED = Causal Encoder-Decoder（因果编码器-解码器）**。40 层劈成：

- **前 20 层 = 因果编码器**（causal encoder）
- **后 20 层 = 解码器**（decoder）

关键在于 ✅：**后 20 层的全局 KV，不再由各自那层算，而是直接从第 20 层的输出「一次性投影」出来**。

```
prompt 10 万 token
   |
   v
【编码器 层 0~19】真的跑 10 万 token          <- 20 层 x 10 万 = 200 万「层·token」
   |
   +--> H20 = 第 20 层的输出
          |
          +--> 层 20 的全局 KV  =  H20 x W_20
          +--> 层 21 的全局 KV  =  H20 x W_21
          +--> 层 22 的全局 KV  =  H20 x W_22
          +--> ...
          +--> 层 39 的全局 KV  =  H20 x W_39
                  ^ 一次矩阵乘直接投影出来，这 20 层根本不用真的跑
```

报告的公式（式 1）写成大白话就是 `第 l 层的 KV = H₂₀ × 该层专属的投影矩阵 W_l`（对所有 l > 20 成立）。**每层的投影矩阵不同，所以各层 KV 仍然不一样**，只是都从同一个 H₂₀ 变出来 —— 省的是「跑那 20 层」的钱，不是「KV 的多样性」。

### 账怎么算

| | 传统 | CED |
|---|---|---|
| prefill 计算量 | 40 层 × 10 万 | **20 层 × 10 万 + 一点点** |
| 复杂度 | `O(N × L)` | **`O(N × L/2)`** ✅ |
| 每 token 激活参数 | 一样 | **prefill 8B / decode 16B** ✅ |

**prefill 只激活 8B，decode 才 16B** —— 这就是 CED 的直接结果。对「输入 10 万、输出 500 字」的 agent 来说，绝大部分成本花在 prefill，所以这一刀砍在了最疼的地方。

> 📖 **思想来源**：报告说 CED 受 **YoCo**（You Only Cache Once）启发 ✅，但做了改进以提升 KV 容量和 KV 生成的计算深度。

### 一个尾巴：SWA 怎么办

模型每层还有一条 **SWA（Sliding Window Attention，滑动窗口注意力）** 支路 —— 只看最近 128 个 token 的局部注意力。这条支路**没法投影**，必须每层老老实实算。

严格重建解码器的 SWA 状态，要重跑 `20 层 × 128 = 2560` 个「层·token」。报告用 **SWA Bounded Replay** 把它压到只重跑 **128 个 token 的一趟完整前向**（见第七节）。

> ⚠️ **这里的 2560 和第七节的 5120 不矛盾，但口径不同，本文统一一下**：`20 × 128 = 2560` 只算**解码器那一半**，`40 × 128 = 5120` 算的是**全模型 40 层**。两个数字都是「层·token」而不是「token」。Bounded Replay 之后只跑 **128 个 token × 40 层**，所以省的倍数是 **40 倍**（$5120/128$），按解码器单独算则是 20 倍。下文按**全模型 40 倍**的口径写。

## 四、创新点 2：CSA2 —— 三种模式，跨层借 KV

### 先复习：压缩 KV 有三个正交方向

报告把前人工作归纳成三个**可以相乘**的维度 ✅：

| 维度 | 做法 | 代表 |
|---|---|---|
| **条目大小** | 少存几个头 / 共享小 latent | GQA、MLA |
| **序列方向** | 每 `m` 个 token 压成 1 条 | V4 的 CSA、HCA |
| **层方向** | 某些层直接借别层的 | CLA、IndexCache、YOIO |

报告的原话是：**前人没有一个方法同时覆盖这三个维度** ✅。CSA2 就是要同时吃满三个。

### 三种模式

每个 CSA2 层被**静态指定**为三种模式之一。三种模式都自己算 Query 和 SWA KV，区别只在于「主 KV、索引器 K、Top-K 索引」从哪来：

| 模式 | 主 KV | 索引器 K | Top-K 索引 | 存不存 KV |
|---|---|---|---|---|
| **Full** | 自己算 | 自己算 | 自己选 | **存** |
| **Reindex** | 借前面的 | 借前面的 | **自己重新选** | 不存 |
| **Reuse** | 借前面的 | 借前面的 | 借前面的 | 不存 |

**Reuse 最省** —— 连索引器都不用跑。**Reindex 是折中** —— KV 借来，但允许「我关注的重点和上一层不一样」。

### 用例子看实际排布 ✅

报告给的真实配置（config.json 完全吻合）：

```
【编码器 20 层】
层 0, 1     纯 SWA，没有全局注意力
层 2 ~ 19   CSA2，压缩率 m=2，分 3 组每组 6 层：
            ┌─ 层 2  Full   ← 存 KV
            │  层 3  Reuse
            │  层 4  Reuse
            │  层 5  Reuse     6 层只存 1 层的 KV
            │  层 6  Reuse     ↓
            └─ 层 7  Reuse   省到 1/6
            （层 8~13、层 14~19 同样排布）

【解码器 20 层】
层 20~39    CSA2，压缩率 m=1，分 5 组每组 4 层：
            第 1 组：层 20 Full    + 层 21,22,23 Reuse
            第 2 组：层 24 Reindex + 层 25,26,27 Reuse
            第 3 组：层 28 Reindex + ...
            第 4 组：层 32 Reindex + ...
            第 5 组：层 36 Reindex + ...
```

**数一下：40 层里只有 4 层真正存全局 KV**（层 2、8、14 在编码器，层 20 在解码器）。这就是 4 倍压缩的来源。

> ⚠️ 我核对 config.json 时发现 `kv_source_layer_ids: [2, 8, 14, 20]`，和报告描述完全一致 —— 这条可以放心引用。

### 顺手做的简化

CSA2 相比 V4 的 CSA 还砍了两处 ✅：
1. **去掉重叠**：CSA 里压缩率 `m` 要用 `2m` 个原始条目、且相邻压缩条目的**源条目互相重叠**；CSA2 直接取消重叠，`m` 个进、1 个出。
2. **去掉绝对位置编码**：CSA 压缩时还要编码这 `2m` 条各自的位置，CSA2 不要了。
3. **索引器 K 改为从主 KV 投影**，不再单开一条从 hidden state 压缩的路径。

另外 ✅：**V4 用 CSA + HCA 混合，V4.1 用纯 CSA2** —— 架构反而更简单了。

## 五、创新点 3：分层稀疏索引器 —— 让索引成本与上下文长度脱钩

### 问题

跨层复用省下了「存」和「索引器的次数」，但**还在跑的那几个索引器，仍然要给全部 100 万个位置打分**。上下文越长这越贵。

### 解法：先划范围，再精选

**Hierarchical Sparse Indexer（分层稀疏索引器）**，只用在解码器里 ✅：

```
解码器第一个 Full 模式层（层 20）：
   ① 给全部 100 万个位置打分     ← 只有这一层扫全场
   ② 选出自己的 Top-512
   ③ 顺便做「块级筛选」：
      把位置按 8 个一块分组，每块取块内最高分作为块分
      选出分数最高的 2048 块
      → 2048 块 × 8 位置 = 16384 个候选位置，组成【候选池】

后面的 Reindex 层（层 24、28、32、36）：
   只在这 16384 个候选里打分，选自己的 Top-512
   → 从「扫 100 万」变成「扫 1.6 万」，省 61 倍 ⚠️（倍数是我算的）
```

**关键性质** ✅：候选池大小固定，所以后续索引器的每 query 成本**从「随上下文线性增长」变成「常数」**。

这也是为什么报告能说：**上下文从 4K 拉到 1M（256 倍），单 token decode FLOPs 只涨了 1/4** ✅。

> 📖 这个机制是**训练时就引入的**（在后训练阶段）✅ —— 训练和推理用同一套候选限制，所以深层索引器是在它实际会面对的搜索域上被优化的。这点很重要，不是推理时的事后 hack。

## 六、创新点 4：FP4 主 KV cache —— 每个数只用 4 个比特

**FP4** = 4 比特浮点数。V4 已经把**索引器**的 Q/K 用 FP4 了，V4.1 把**主 KV cache** 也压到 FP4 ✅ —— 相比 V4 的 FP8，存储直接**再砍一半**。

具体格式 ✅：**E2M1**（2 位指数 + 1 位尾数 + 1 位符号 = 4 比特），每 **16 个通道**配一个 **E4M3** 的缩放因子。这是 NVIDIA 的 NVFP4 格式，但**省掉了它的第二级全局缩放**。

### 为什么敢省掉全局缩放（这段推导很漂亮）✅

报告给了完整的数值论证：

```
① 训练出来的 RMSNorm 权重最大约 1
② RMS 归一化后，512 通道的 KV latent 的 L2 范数 ≤ √512
③ RoPE 是旋转，保范数 → 旋转后单通道最大绝对值也 ≤ √512 ≈ 22.6
④ 训练中实测最大值约 10
⑤ 而 E2M1 + E4M3 缩放能表示到 448 × 6 = 2688
   
   2688  vs  实测 10   →  余量 268 倍，全局缩放纯属多余
```

两个工程细节 ✅：
- **在 RoPE 之后量化**。之前量化精度只好一点点，却会给 decode 增加开销。
- **SWA 的 KV 仍用 FP8**，因为它对量化更敏感。

### ★ 把 890 字节/token 自己加出来

到这里，报告披露的超参已经足够把那个 890 算出来了。**⚠️⚠️ 先钉住一句话：CSA2 照样缓存 KV**，只不过缓存的是**压缩后的条目**、而且只有 4 层存。任何写成"压缩了所以不用存"的说法都是反的——那样 KV cache 一个字节都省不下来，整篇报告就白写了（这个坑在 MLA 上的孪生版本见 [07 章 §7.2](大模型架构入门/07-MHA到MLA.md)）。

**第一步：一个缓存条目多少字节。**

```
KV latent 512 个通道
   每个通道 E2M1（4 比特）             = 0.5    字节
   每 16 个通道配 1 个 E4M3 缩放因子    = 1/16 = 0.0625 字节/通道
   ---------------------------------------------------
   每通道 0.5625 字节  x  512 通道      = 288 字节/条目

⚠️ 有效位宽不是 4 比特，是 4.5 比特 —— 缩放因子不是免费的。
   （同一条纪律在 INT4 上是"有效位宽 4.15 而不是 4"，见 14 章 §14.5）
```

**第二步：哪几层存、每层每 token 摊到几条。**

| 层 | 位置 | 模式 | 压缩率 | 每 token 的条目数 | 每 token 字节 |
|---|---|---|---|---|---|

| 层 8 | 编码器 | Full | $m=2$ | 0.5 | 144 |
| 层 14 | 编码器 | Full | $m=2$ | 0.5 | 144 |
| 层 20 | 解码器 | Full | $m=1$ | 1.0 | 288 |
| **主 KV 合计** | | | | **2.5** | **720** |
| **✅ 报告写的运行时 KV** | | | | | **890** |
| **差额** | | | | | **170** |

> ⚠️ 另外注意 890 的**口径**：它是**常驻显存的运行时全局 KV**，**不含 SWA KV**（SWA KV 被挪进了宿主内存池，见第七节）。拿它和别家"每 token KV 字节数"直接比之前，先确认对方算没算滑窗那部分。

**第三步：用报告自己的"三个正交维度"把这 64 倍拆开。** 基线取"40 层每层都存一份 MLA-576 的 BF16 latent"，也就是 DeepSeek-V3 那种做法：$40 \times 576 \times 2 = 46080$ 字节/token。

```
① 层方向   ：40 层 -> 只有 4 层存                     省 10.0 倍
② 条目大小 ：576 维 BF16 (1152 B) -> 512 维 FP4 (288 B)  省  4.0 倍
③ 序列方向 ：4 个存 KV 的层里有 3 个是 m=2
             4 / (3 x 0.5 + 1) = 4 / 2.5              省  1.6 倍
   ---------------------------------------------------------------
   10.0 x 4.0 x 1.6 = 64.0 倍

   验算：46080 / 720 = 64.0   ✅ 严丝合缝
```

> 🔑 **这就是报告标题里"把 KV cache 压缩推到极限"的全部含义**：**三个维度是可乘的，而前人每次只吃一个维度。** 层方向那 10 倍是 CSA2 的 Full/Reuse/Reindex，条目大小那 4 倍是 FP4 + latent，序列方向那 1.6 倍是 $m=2$ 的块压缩。⚠️ 上面这三个因子是本文按披露超参算的，报告只给了 890 这个最终值和"相对 V4-Flash 降 4 倍"的倍数。

## 七、创新点 5：SWA Bounded Replay —— 用一点重算换掉一半硬盘

### 问题

SWA 的 KV 也得存。V4 的部署里，**SWA KV 占了持久化缓存的将近一半** ✅。

但 SWA KV 有个特点：**它只在一次会话内的几分钟窗口里被复用，会话一结束就是死数据**。而全局 KV 是长尾复用的（V4 的部署里保证存活 72 小时以上 ✅）。用同一套长期存储策略对待两者，很浪费。

V4 提过 **Zero SWA Caching**（干脆不存，要用时重算），但严格重建要跑 `层数 × 窗口` 个 token 的完整前向，**在生产环境里代价高到不可接受** ✅。

### 解法：只重放最近 128 个 token

```
  严格重建：窗口里【每一层】都要拿到自己那份精确的 SWA 状态，
            所以要为 40 层各重跑一遍 128 个 token  ->  5120「层·token」
  Bounded ：只重放最近 128 个 token 的【一趟】前向，
            让 40 层顺带都拿到（近似的）状态      ->   128 个 token

  ⟹ 省 5120 / 128 = 40 倍
```

代价是**拿到的是近似状态**：从位置 `s` 开始重放时，位置 `i` 的 query 只能看到 `max(s, i-127) ~ i` 这段键 —— 靠近重放起点的那几个 token，窗口比理论上的 128 短。报告的结论 ✅：**几乎不损失回答质量**。

配套的部署改动 ✅：
1. SWA KV **不再进持久化缓存**，改放在每台机器 **10% 宿主内存**组成的分布式内存池里，TTL 只有几分钟，靠高周转服务并发会话。
2. 全局 KV 留在持久化缓存，保证 ≥72 小时。
3. 万一「命中全局 KV 但没命中 SWA KV」，就用 bounded replay 兜底 —— 把灾难性的 miss 变成廉价的优雅降级。

报告把这个叫做**新的存储-计算权衡点** ✅。持久化缓存降到 1/8 的两个乘数就是：**不存 SWA（≈砍半）× 全局 KV 压到 1/4**。

## 八、创新点 6：Single-Pass mHC —— 把三个 kernel 合成一个

> 📖 **mHC** 是 V4 引入的残差连接改进，详见 [DeepSeek-V4.md](DeepSeek-V4.md) 的第三节。简单说：它在相邻 Transformer 块之间维持 `n` 条残差流（V4.1 里 `n = 4`），用 token 级系数 `A、B、C` 动态混合这几条流。

### 问题：一个数据依赖卡住了 kernel 融合

V4 的实现要跑三个 kernel，**因为有依赖必须串行**：

```
① X_l = B_{l-1}·X_{l-1} + C_{l-1}·Y_{l-1}     残差更新
② (A_l, B_l, C_l) = H(X_l)                    算系数    ← 需要对整个 hidden 维度归约
③ X̂_l = A_l · X_l                             输入混合  ← 必须等 ② 完成！
```

第 ③ 步要用 `A_l`，而 `A_l` 要等第 ② 步把整个 hidden 维度归约完才有。所以 `X_l` **必须被读两遍** —— 一遍算系数，一遍做混合。

总访存 `(4n+4)·d`，是理论下界 `(2n+2)·d` 的**两倍** ✅。

### 解法：把系数往后挪一个块

**Single-Pass mHC** 让每个块使用**上一个块**算出的混合系数 ✅：

```
原来： X_{l+1} = B_l·X_l + C_l·F_l( A_l   · X_l )
现在： X_{l+1} = B_l·X_l + C_l·F_l( A_{l-1} · X_l )
                                    ↑ 用上一块的，依赖消失了
```

依赖一断，`X_l` 的每个分块就能**同时**用于输入混合和系数预测，一次遍历搞定。配套的融合 kernel 叫 **Mega-mHC**，达到理论下界 `(2n+2)·d`，**访存砍半** ✅。

报告说这个改动的效果损失「可忽略」✅。注意 ✅：**预训练仍用原来的多 kernel 实现**，只在部署时用融合版 —— 因为这个改动只是换了「用谁的系数」，不影响训练语义。

**成果** ✅：绝大多数层（CSA2 处于 Reuse 模式的那些）**prefill 只要 15 个 kernel，decode 只要 11 个**。

## 九、创新点 7：Engram —— 196B 参数的「查表记忆」

**Engram** 是 DeepSeek 之前工作里的**条件记忆模块**，目的是**把「记忆」从「计算」里解耦出来** ✅。

### 它是什么

不是神经网络层，而是一张**巨大的查找表**。输入 token 序列 → 算出 n-gram（连续 n 个词的组合）→ 哈希成地址 → 查表取出向量 → 融进主干。

配置 ✅：

| 项 | 值 |
|---|---|
| 参数量 | **196B**（骨干之外另算）|
| 模块数 | 2 个，放在**层 1 和层 14** |
| n-gram 阶数 | {2, 3, 4} |
| 哈希头数 | 8 |
| 每阶总嵌入维度 | 2048 |
| 每个头的表大小 | 约 1600 万条，**表大小取互不相同的质数** |
| 精度 | 嵌入表和 K/V 投影都用 **FP8** |

> ⚠️ 我在报告出来前只凭 config.json 估算 Engram 约 197B 参数，报告给的是 **196B** —— 估得很准，但现在该用官方数字。

### ★ 这 196B 可以一步算出来（全表五个数字全都用上）

```
2 个模块 x 3 个 n-gram 阶（2/3/4 阶）x 8 个哈希头 x 1600 万条 x 每头 256 维
                                                          ^ 2048 / 8 = 256

= 2 x 3 x 8 x 16,000,000 x 256
= 196.6 B            vs   ✅ 报告写的 196 B   ->   差 0.3 %
```

> ✅ **这是本文里最干净的一次验算**：上面那张配置表里的**每一个数字都被用上了**，而且一次就撞到官方值。顺带也解释了第十五节那张总图里"每个模块 98B"是怎么来的——$196 / 2 = 98$。
>
> ⭐ **顺带看清一件事：Engram 的参数量是【纯乘法】堆出来的，和 hidden、和层数都无关。** MoE 的参数量还要乘 `层数 × 3 × hidden × 专家中间维`，跟着骨干一起长；Engram 只要把表调大就行。**这是"记忆"和"计算"被真正解耦的直接后果**——完整论证见 [18 章](大模型架构入门/18-Engram与条件记忆.md)。

### ⭐ 它到底换了什么：一笔要拆成四格看的交易

这一节我最初写成了「为什么它不拖慢推理」，**那个标题是错的**。Engram 是**拖慢**推理的，只是拖得很少。把它的账拆开：

```
    参数量    ↑  +196B
    FLOPs     ≈  不涨          ★ 这才是它真正的卖点
    推理吞吐  ↓  −1.9% ~ −2.8%   ← 它是【减速】的
    模型能力  ↑
```

Engram 论文 §6.4 Table 4 的实测（NVIDIA H800，512 条序列，长度 Uniform(100,1024)，100B 的 Engram 层塞在第 2 个 Transformer 块，推理框架 nano-vLLM）✅：

| 配置 | 吞吐 (tok/s) | 变化 |
|---|---|---|
| 4B-Dense 基线 | 9,031.62 | — |
| + 100B Engram（卸载到主机内存） | 8,858.28 | **−1.9%** |
| 8B-Dense 基线 | 6,315.52 | — |
| + 100B Engram（卸载到主机内存） | 6,140.02 | **−2.8%** |

> ⚠️ **必须和 V4.1 真正的提速组件分开算。** 这一版报告里让模型变快的是 CED、CSA2、分层稀疏索引器、FP4 主 KV cache、Single-Pass mHC、DSpark。**Engram 不在其中**——它是从那笔提速预算里**扣掉 2.8%** 的那一项，买回来的是能力。
>
> ⚠️ 反过来说，它也是三条「让模型更强」的路里**唯一一条 FLOPs 完全不涨**的：加层数/加宽是 FLOPs ↑↑、吞吐 ↓↓；加 MoE 专家是 FLOPs ≈ 不涨、但 all-to-all 通信变贵；Engram 只多一次查表 + 一次 PCIe 搬运。

### 为什么代价能压到 2% 量级 ✅

**n-gram 的地址只取决于输入 token 序列本身** —— 不依赖任何中间计算结果。所以**在模型开始算之前就能知道要查哪些格子**，可以从宿主内存**异步预取**，第一个模块的预取**被前面 Transformer 块的计算挡住**，大部分搬运延迟看不见。

报告称之为 **deterministic addressing（确定性寻址）** ✅。这是 Engram 相对 MoE 的结构性优势：MoE 要先算出隐状态才知道走哪个专家，地址是运行时才知道的，没法预取，所以专家必须常驻显存。

> ⚠️ 论文那个 −2.8% 还是**保守下界**：该实验强制**所有**检索都走 PCIe，没有用 §2.5 设计的 Zipf 局部性缓存（热的 n-gram 留在 HBM）。真实系统里应该更小——**但更小不等于零，更不等于提速**。
>
> ⚠️ 顺带把口径钉一下：**"吞吐 −2.8%" 不等于 "耗时 +2.8%"**。吞吐掉到 $97.2\%$，对应耗时变成 $1/0.972 = 102.9\%$，也就是**耗时 +2.9%**。倍数小时差别可以忽略，但这条换算纪律在读"提速 2 倍 / 时间减少 50%"这类句子时必须记住——**时间减少 50% = 提速 2 倍**，两者不是一回事。

> 📖 这个模块的完整原理（tokenizer 压缩 / 后缀 n-gram / 多头哈希 / 门控为什么是「只有一个 key 的注意力」/ MoE 与 Engram 的 U 形预算分配律）见 [大模型架构入门/18-Engram与条件记忆.md](大模型架构入门/18-Engram与条件记忆.md)。

### 相比原版的两处改动 ✅
1. **去掉短因果卷积** —— 收益不值得推理栈的复杂度。
2. **优化器换掉** —— 不用 Adam，改用「动量更新 + Sinkhorn 平衡」（见第十一节）。

## 十、创新点 8：DSpark —— 一次前向猜 5 个字

**投机解码**（speculative decoding）的意思是：用一个小模型先快速猜几个 token，再让大模型一次性验证，猜对就白赚。

**DSpark** 的配置 ✅：

```
草稿器 = 3 个 Transformer 块，滑窗 128
   ↓
一次前向 → 并行算出 5 个草稿位置的 base logits
   ↓
Markov 头  → 建模这 5 个草稿 token 之间的依赖
   ↓
置信度头  → 预测每个位置的条件接受概率 → 估计前缀存活概率
   ↓
调度器 → 结合实测的引擎吞吐曲线，动态决定这次验证多长
         目标：当前系统负载下最大化全系统 token 吞吐
```

**和 V3 的 MTP 有个重要区别** ✅：

| | V3 的 MTP | V4.1 的 DSpark |
|---|---|---|
| 何时训练 | 和骨干**联合**训练全程 | 骨干预训练**之后**单独训练 |
| 训练时骨干 | 一起更新 | **冻结** |
| 后训练阶段 | —— | 跟着骨干一起训，但**梯度不回传进骨干** |

这样做的好处 ✅：DSpark 始终跟得上不断演化的策略，**既加速线上服务，也加速 RL 和 OPD 的 rollout 生成**。

> ⚠️ 社区实测的 507 tokens/s 大概率主要来自 DSpark，但报告没有给这个数字，别混着引用。这类"实测"数字在没有标明硬件平台、batch size、上下文长度之前，**不具备可比性**。

### ⚠️ 读"一次猜 5 个"时，别把加速倍数算成 `α × 5`

报告没有公布 DSpark 的接受率 $\alpha$，所以**本文不给 V4.1-Flash 的加速倍数**。但这里要先把最高频的那个错法堵掉，因为它在解读投机解码时几乎必犯：

> ❓ 「接受率 70%，一次猜 5 个，那平均接受 $0.7 \times 5 = 3.5$ 个。」
> **错。正确值是 2.94**——高估了 19%。

错在哪：**草稿 token 是【串行依赖】的。** 第 2 个草稿是在"第 1 个已被接受"的前提下生成的；第 1 个一旦被拒，后面 4 个**就算内容碰巧对也全部作废**。所以这是一条"从头走、第一次失败就停"的链——**几何分布，不是二项分布**：

$$\mathbb{E}[\text{接受长度}] = \sum_{i=0}^{\gamma} \alpha^i = \frac{1-\alpha^{\gamma+1}}{1-\alpha}$$

**$\gamma = 5$（DSpark 的配置）时逐 $\alpha$ 的推演表**（末尾那个 bonus token 已含在内）：

| 接受率 $\alpha$ | ✗ 错法 $\alpha\times\gamma$ | ✅ 正确 $(1-\alpha^6)/(1-\alpha)$ | 天花板 $1/(1-\alpha)$ | 错法偏差 |
|---|---|---|---|---|
| 0.95 | 4.75 | **5.30** | 20.0 | −10 % |
| 0.90 | 4.50 | **4.69** | 10.0 | −4 % |
| 0.85 | 4.25 | **4.15** | 6.7 | +2 % |
| 0.80 | 4.00 | **3.69** | 5.0 | +8 % |
| 0.70 | 3.50 | **2.94** | 3.3 | +19 % |
| 0.60 | 3.00 | **2.38** | 2.5 | +26 % |

⚠️ **注意这张表的符号会翻转**：$\gamma = 5$ 时两条曲线大约在 $\alpha \approx 0.87$ 处交叉——**高接受率区间 `α×γ` 偏低（漏掉了末尾白送的 bonus token），低接受率区间它偏高（没算串行截断）**。所以"误差小"只是某个 $\alpha$ 上的巧合，**这个式子在任何区间都不是对的**。

```
两个可以直接带走的结论：
  ① 天花板 = 1/(1−α)，任凭你猜多长都突破不了
     ⟹ ★ 提高 α 的回报远大于加大 γ —— 这正是 DSpark 要加
        【Markov 头】和【置信度头】的原因，两个头都是在抬 α
  ② γ=5 时 α=0.8 已经吃掉天花板的 74%，再加 γ 收益很薄
     ⟹ 所以 DSpark 的【调度器】去动态决定"这次验证多长"才有意义
```

> ⚠️ **别把 E 当成实测加速比**：还要扣掉草稿器本身的开销，$\text{speedup} \approx \mathbb{E}/(1+\gamma c)$。作为量级参照，**DeepSeek-V3 的 MTP 官方口径是"第二个 token 接受率 85%~90%、TPS 提升 1.8×"**（✅ V3 报告披露，⚠️ **不是社区常传的 3×**）；那是 $\gamma=1$ 的配置，代进公式得 $1+\alpha = 1.85 \sim 1.90$，和 1.8× 吻合得很好。完整推导与"理论 2.75× / 实测 2.1×"的反例见 [12 章 §12.5](大模型架构入门/12-MTP与投机解码.md) 和 [推理框架 §8](../推理框架/推理优化入门/08-投机解码.md)。

阶段一 对比预训练：SigLIP sigmoid 对比损失，约 470 亿 图文对，分辨率限制 224×224
       （报告明说：更高分辨率在这阶段收益不大，白费算力）
阶段二 自回归微调：接一个 4B 的 MoE LLM，用 2360 亿 token 训练
       数据含 caption、alt text、图表、OCR；分辨率 544×544 ~ 1344×1344
       训完把 LLM 扔掉，只留视觉编码器
```

### 多模态专属的负载均衡 ✅

MoE 里图像 token 和文本 token 的**路由偏好不一样**，混在一起平衡会掩盖各自的失衡。解法：**给文本和图像各维护一套专家偏置**，路由时按自己模态的偏置选专家，但**打分权重仍用原始路由分数**。每步之后两套偏置**各自独立更新**。

### 数据 ✅

- 多模态数据**刻意不做大规模合成**，理由是「原始网页数据本身就富含多模态知识」，优先清洗和直接利用。
- 发现自己的爬虫**过于偏向文本网页**，因此**从 Common Crawl 重新自举**以改善多模态覆盖。
- 用 **SmolVLM** 做图文内容的严格质量打分。
- 最终语料 **文本:多模态 = 7:1** ✅。

### 优化器：三套并行 ✅

| 参数类型 | 优化器 |
|---|---|
| 线性层权重、Engram 投影、视觉投影器 | **Muon** |
| **Q 和 K 的权重** | **head-wise Muon**（按头切开再更新）|
| RMSNorm 权重、偏置、缩放因子等非矩阵参数 | AdamW |
| **Engram 表、token 嵌入、预测头** | **动量更新 + Sinkhorn 平衡** |

两个值得注意的点：

**① head-wise Muon** ✅：把 Muon 看作预条件梯度下降，原版对所有头用同一个预条件子，head-wise 给每个头单独的预条件子，**更好地处理注意力头之间的异质性**。报告特别提到 **GLM-5 和 Kimi-K3 也验证了这一点** —— 三家独立收敛到同一结论，可信度高。⚠️ **谁先做的不在本文讨论**（时间线在 [模型技术对比.md](模型技术对比.md) §6）；正交化"粒度"这个问题本身、以及三家的解法对照，见 [13 章 §13.7](大模型架构入门/13-优化器与Muon.md)。

**② 为什么 Engram 不用 Adam** ✅：196B 参数用 Adam，优化器状态的显存开销受不了。改用「只需要动量缓冲」的 Sinkhorn 平衡方案，**实测还比 Adam 好**。Sinkhorn 平衡做的事是：让更新矩阵的**行 RMS 和列 RMS 都约等于 1** —— 一行对应一个 token 或 n-gram 身份，一列对应一个隐藏特征，正好利用了这种 token-特征结构。

> ⚠️ Engram 的学习率被**放大 5 倍** ✅，这是沿用前作的设定。

API 里 `low / high / max` 分别对应 **50 / 75 / 100** ✅。

## 十四、代价与局限（报告自己说的）

✅ 报告在结论章明确列出：

1. **新架构的鲁棒性边界尚未完全刻画**。内部评测没发现系统性退化，但「没有任何有限测试集能覆盖所有极端输入」。
2. **两个具体风险点**：
   - **CSA2 可能选错**（潜在的 selection errors）
   - **SWA Bounded Replay 是近似重建**，在缓存恢复的边界处可能出问题
3. **后训练零算法创新** ✅ —— 报告罕见地直说：SFT → RL → OPD 完全沿用 V4 的既有实践，**所有实质变化都在数据管线上**。
4. **基准饱和问题**：报告呼吁社区重视 agent 基准被「刷分」（model gaming）的检测与缓解。
