一、先给结论：V4 到底改了什么

DeepSeek-V4 有两个型号，都原生 1M 上下文：

V4-Pro V4-Flash
总参数 / 激活 1.6T / 49B 284B / 13B
预训练数据 33T tokens 32T tokens
1M 上下文下单 token FLOPs（vs V3.2） 27% 10%
1M 上下文下 KV cache（vs V3.2） 10% 7%

整个 V4 的叙事只有一句话：不是"能跑到 1M"，而是"1M 便宜到可以当默认值"。 所有架构改动都是为这个目标服务的。

骨架仍然是 V3 那套 DeepSeekMoE + MTP，但在三个位置做了替换：

位置 V3.2 V4 解决什么问题
注意力 MLA + DSA CSA + HCA 混合 长上下文的算力和显存
残差连接 x + F(x) mHC（流形约束超连接） 1.6T 深层网络训练不稳定
优化器 AdamW Muon 收敛更快、更稳

下面逐个用最小例子讲。

⚠️ 先把上一代 V3 的基线数字钉死（本文后面多处拿它做对照）

读 V4 报告最容易出问题的地方，是拿一个记错的 V3 去当参照物。 下面这些是本仓库已核实的 ✅ 官方口径：

项 ✅ DeepSeek-V3 的官方数字 ❌ 常见错法
层数 61 层：前 3 层稠密 FFN + 58 层 MoE "61 层全是 MoE"
专家 256 个路由专家 + 1 个共享，每 token Top-8 "384 选 8"（那是 openPangu）／"896"（那是 Kimi K3）
训练并行 EP=64 / PP=16 / TP=1，2048 张 H800 写成用了 TP
丢 token 训练和推理都不丢 token（官方明确声明） "MoE 必然丢 token"
负载均衡 无辅助损失的偏置法：偏置训练时每 step 更新、推理时固定；⚠️ V3 并非完全不用辅助损失，它保留了一个极小的序列级 aux loss "V3 完全废除了辅助损失"
MTP 第二个 token 的接受率 85%~90%、TPS 提升 1.8× "提速 3×"

📘 这几条的出处与完整展开：层型分布和专家配置见 01 章 §1.6 与 10 章 §10.5，MTP 的 1.8× 见 12 章 §12.12，并行配置见 训练框架 §12。

★ 把 1.6T / 49B 这两个数字拆开：一笔你能自己按出来的账

报告给了总参数和激活参数，但没有给每个专家多大。好在这两个数字加上 MoE 配置就足够反解出来了。

关键观察：总参数和激活参数的差，只由"没被选中的那些路由专家"贡献——注意力、共享专家、Embedding、稠密层这些在两笔账里一模一样，相减就消掉了。于是（$M$ = MoE 层数、$E$ = 单个专家参数量）：

1600 B − 49 B = 1551 B = M x (384 − 6) x E

取 M = 61（V4 把原来的稠密层也换成了哈希路由的 MoE 层，所以 61 层全是 MoE）：
   E = 1551 B / (61 x 378) = 67.3 M
   一个专家 = 3 x 7168 x d_ff_e   ⟹   d_ff_e = 67.3 M / (3 x 7168) ≈ 3130

⚠️ 这是本文的反推，不是报告写的。 而且精度上限很低：报告给的 "1.6T" 只有两位有效数字，$\pm 0.05$T 的不确定度直接对应 $d_{ff}^{e}$ 上 $\pm 100$ 的摆幅——所以只能说专家中间维在 3100 上下，3072 和 3200 都落在误差里。

拿 $E = 67.3$ M 回代，两笔账同时列出来做一致性检查：

组件 算式 总参数 激活参数
61 层 × 384 个路由专家 $61 \times 384 \times 67.3\,\text{M}$ ／ 激活 $61 \times 6 \times 67.3\,\text{M}$ 1576 B 24.6 B
61 层 × 1 个共享专家 $61 \times 67.3\,\text{M}$ 4.1 B 4.1 B
小计 1580 B 28.7 B
✅ 报告值 1600 B 49 B
差额（注意力 + Embedding + RMSNorm + mHC 的 A/B/C） 20.0 B 20.3 B

✅ 这张表真正的价值在最后一行：两个差额是 20.0 B 和 20.3 B，几乎相等——本来就该相等，因为注意力和 Embedding 一点都不稀疏。两条独立路径撞到同一个数，说明前面那个 $E \approx 67.3$ M 的反推没错得离谱。平摊下来 每层注意力 ≈ 3.3 亿参数（⚠️ 推算；V4 每层同时挂着 CSA、HCA 和 Lightning Indexer 三套投影，这个量级合理）。

★ 稀疏度：384 / 6 = 64× 这个说法要小心

❌ 常见说法："384 选 6，所以 V4-Pro 稀疏 64 倍"

✅ 三个数字，三个不同的问题：
   384 / 6     = 64.0 倍   <- 只是【路由专家】的选择比
   385 / 7     = 55.0 倍   <- 算上共享专家后的 FFN 稀疏比
   1600 / 49   = 32.7 倍   <- ★ V4-Pro 全模型 总参数/激活参数（正确口径）
   284  / 13   = 21.8 倍   <- ★ V4-Flash 同口径

⟹ 显存按【总参数】付钱，算力按【激活参数】付钱。
   只有第三行那个口径才回答"这两笔账差多少"。

同一个陷阱在 01 章 §1.4.4 拿 openPangu 演示过（那里是「384/8 = 48×」应为「505/18 = 28.1×」）。

★ 算力与显存：三个可以直接算的数

量 通式 V4-Pro 代入 说明
每 token 前向 FLOPs $2N_{\text{激活}}$ $2 \times 49\,\text{B} = \mathbf{98}$ GFLOPs 不含注意力打分项
每 token 训练 FLOPs $6N_{\text{激活}}$ $6 \times 49\,\text{B} = \mathbf{294}$ GFLOPs ⚠️ 6N = 2N 前向 + 4N 反向，不含优化器
预训练总算力 $6N \times D$ $6 \times 49\,\text{B} \times 33\,\text{T} = \mathbf{9.7 \times 10^{24}}$ FLOPs $D$ = 33T tokens
训练态显存 16 字节/参数 $1.6\,\text{T} \times 16 = \mathbf{25.6}$ TB FP32 主权重 4 + 梯度 4 + Adam 的 $m$、$v$ 各 4

⚠️ "9.7e24 FLOPs 等于多少卡时"必须带硬件平台，否则这个数字没有意义。 用 V3 反过来标定一次：V3 是 $6 \times 37\,\text{B} \times 14.8\,\text{T} = 3.29\times10^{24}$ FLOPs，官方公布 2.788 M H800 卡时；H800 的 BF16 稠密峰值是 989 TFLOPS（⚠️ 另一个常见数字 1979 是 2:4 稀疏值，不能拿来算 MFU），于是
V3 的 MFU = 3.29e24 / (2.788e6 x 3600 s x 989e12) = 33.1% <- H800 / BF16 口径 V4-Pro 按同一 MFU： 9.7e24 / (0.331 x 989e12) ≈ 8.2e6 卡时 <- 约等于 V3 的 2.9 倍
⚠️ 这 8.2 M 卡时是本文的推算，报告没有公布训练卡时。 而且它只算了 6N 那一项：V4 训到 1M 上下文，注意力打分那一项 12·L·s·h 在稠密基线下是 $12 \times 61 \times 10^6 \times 7168 = 5247$ GFLOPs/token，是 6N(294) 的 17.8 倍——这恰恰就是 CSA + HCA 要解决的那个问题，也是"1M 上下文下单 token FLOPs 只有 V3.2 的 27%"这句话的来源。

那 25.6 TB 的训练显存也值得停一下：按 H800 每卡 80 GB 算，光是放下权重和优化器状态就要 320 张卡，一个样本都还没跑。显存都去哪了、ZeRO 怎么切，见 训练框架 §2 / §5。

二、改进点 1：混合注意力 CSA + HCA（最核心）

问题是什么

假设上下文有 100 万个 token。传统注意力（哪怕是 MLA）要为每个 token 存一份 KV，生成第 1000001 个 token 时，要和前面 100 万个逐一算相似度。这就是 1M 上下文贵的根源。

V4 的思路很朴素：先把序列"压缩"成更短的序列，再在压缩后的序列上做注意力。

CSA：压缩稀疏注意力（"精读"）

最小例子

假设序列只有 16 个 token，压缩率 m = 4：

原始 KV:  [t0 t1 t2 t3] [t4 t5 t6 t7] [t8 t9 t10 t11] [t12 t13 t14 t15]
              ↓              ↓              ↓                ↓
压缩条目:     c0             c1             c2               c3

16 个 token → 4 个压缩条目，序列长度直接砍到 1/4。

压缩不是简单平均池化，而是学出来的加权求和：模型另外算一路"压缩权重" Z，加上可学习的位置偏置后做 softmax，再和 KV 做加权和。

一个关键小设计——重叠压缩：如果硬切成块，t3 和 t4 明明相邻却被切进不同块。所以 V4 用了两路 KV（Ca、Cb），Cb 取的是前一块的区间：

c1 的信息来源 = [t4 t5 t6 t7]（来自 Ca）+ [t0 t1 t2 t3]（来自 Cb）
                → softmax 在这 2m=8 个元素上统一归一化

所以每个压缩条目实际看到 2m = 8 个 token，但序列长度仍然只压到 1/4。相邻条目共享信息，块边界的硬切断被抹平了。

压完之后：只挑重要的看

压缩之后 1M token → 25 万条目，还是多。于是用 Lightning Indexer（V3.2 就有，V4 沿用）打分：

I(t,s) = Σ_h  w_h · ReLU( q_h · K_s )

给每个压缩条目打个分，取 top-k（k 比 V3.2 更小，因为条目本身已经短了 4 倍），只对这 k 条做真正的注意力。

再加两个补丁：

  • 滑动窗口：最近 128 个 token 保留不压缩的原始 KV（因为最近的内容需要看细节，且同一块内因果关系被压掉了）
  • Attention sink：每个头有个可学习的 sink logit，加在 softmax 分母上，允许某个头的注意力总和 < 1，甚至接近 0（"这一层我不想看任何东西"）

HCA：重度压缩注意力（"泛读"）

同样的压缩思路，但压缩率拉到 m′ = 128，而且不重叠、不做稀疏筛选：

100 万 token / 128 ≈ 7800 个条目 → 全部都看（稠密注意力）

7800 条已经很便宜了，直接全量注意力，保证全局连贯性不丢。

两者交替 = 精读 + 泛读

CSA 层：看得细（1/4 压缩），但只挑 top-k 看 → 局部精度
HCA 层：看得糙（1/128 压缩），但全都看   → 全局视野

层与层之间交错排列。这就是 1M 上下文能被"扛住"的全部秘密——没有一层同时既看得细又看得全，但堆起来两者都有。

还有几个工程细节

  • QK-RMSNorm：对 query 和压缩 KV 条目直接做 RMSNorm，防止 attention logits 爆炸。副作用是 Muon 里不需要 QK-Clip 了。
  • Partial RoPE + 反向 RoPE：只在最后 64 维加 RoPE。但因为压缩条目同时充当 key 和 value，输出会带上绝对位置信息；于是对输出 o_i 的最后 64 维再施加一次位置为 −i 的 RoPE，把绝对位置抵消掉，恢复相对位置性质。这个 trick 挺巧。
  • KV 存储混合精度：RoPE 维度用 BF16，其余用 FP8，KV cache 再砍一半。Indexer 的注意力计算用 FP4。
  • 最终效果：以 BF16 / GQA-8 / head_dim=128 为基线，1M 上下文下 KV cache 只有约 2%。

⚠️⚠️ 讲压缩注意力时最容易写反的一句话

❌ "CSA 把 KV 压缩掉了，所以不用缓存 KV 了。"

★ 这是反的，而且是把整个设计讲没的那种反。 CSA 和 HCA 照样要缓存——只不过缓存的是压缩后的条目（1M / 4 = 25 万条、1M / 128 ≈ 7800 条），不是原始的 100 万份 KV。省显存的全部来源正是"缓存的是压缩条目"这件事本身。

同一个坑在 MLA 上有个孪生版本：MLA 的"矩阵吸收"吸的是上投影矩阵（吸到 Q 侧和输出侧），它照样缓存压缩后的潜向量 $c_{KV}$。任何推出"不用存了"的说法都一定错了。两个坑的完整对照见 07 章 §7.2 / §7.4。

判断口诀：压缩注意力省的是"缓存里有几条"，不是"要不要缓存"。

★ 把那个 "2%" 拆成三个可乘的因子

报告只给了一个百分比。百分比最容易骗人——它取决于拿谁当基线。这里把它拆开，顺便把 §一 那张表里的 "vs V3.2 的 10%" 和这里的 "vs GQA-8 的 2%" 对齐。

先把两条基线的绝对值算出来（通式 每 token 每层 = 2 × n_kv_heads × head_dim × 字节数，61 层）：

基线 算式 每 token 1M 上下文
报告用的 GQA-8 / head_dim 128 / BF16 $61 \times 2 \times 8 \times 128 \times 2$ 244 KiB（249,856 字节） 250 GB（= 233 GiB）
V3 / V3.2 的 MLA-576 / BF16（⚠️ MLA 那行不乘 2、也没有头数） $61 \times 576 \times 2$ 68.6 KiB（70,272 字节） 70.3 GB（= 65.4 GiB）

⚠️ 注意这两条基线本身就差 3.56 倍（$249856 / 70272$；⚠️ 顺带提醒 GB 和 GiB 差 7.4%，1M 这里按 $10^6$ 个 token 算）——所以"降到 2%"和"降到 10%"根本不是同一个陈述，不能互相印证。

再把 V4 相对 MLA-BF16 省的那部分拆成三个正交方向（这个"三维度"的分法是 V4.1-Flash 报告里明确写出来的，见 DeepSeek-V4.1-Flash.md 第四节）：

     两种层各占一半 ⟹ 平均 = (0.250 + 0.0078)/2 = 0.129  →  省 7.76 倍

② 条目大小方向：主体 FP8（1 字节）+ RoPE 那 64 维 BF16，相对全 BF16
                                                       →  省 约 2 倍

③ 层方向：V4 没动（61 层每层都有自己的 KV）            →  省 1 倍

合计 ≈ 7.76 x 2 = 15.5 倍   （相对同规模的 MLA-576 / BF16）

最后对账（⚠️ 以下是本文的推算，报告只给了百分比）：

相对 GQA-8 基线 = 15.5 x 3.56 = 55.2 倍  →  1/55.2 = 1.81%   ≈ 报告的"约 2%"  ★ 对上了
相对 MLA 基线   = 1/15.5 = 6.4%                             ⚠️ 报告说的是 10%，差 1.6 倍

⟹ 两条口径换算到绝对值：4.4 ~ 6.9 KiB/token，1M 上下文约 4.5 ~ 7 GB。
   差的那 1.6 倍本文对不齐 —— V3.2 的 DSA 本身也改了缓存内容，
   而且 CSA 层还要额外存 128 个滑动窗口位置的【未压缩】原始 KV。
   ⚠️ 这一处如实标出，不替报告圆。

🔑 不管取哪一端，结论是同一个：1M 上下文的 KV cache 从"250 GB，得拿 4 张 80 GB 的卡只用来装它"变成"5~7 GB，一张卡的零头"。这就是"1M 便宜到可以当默认值"这句话的全部含金量。KV cache 为什么是长上下文的第一成本项，见 06 章 §6.3；压缩注意力这条路的隐藏代价（它依然是平方复杂度，只是常数小了）见 08 章 §8.4。

三、改进点 2：mHC —— 把残差连接换掉

问题：残差为什么会炸

标准残差：x_{l+1} = x_l + F(x_l)。只有一条"车道"，信号一路加上去。层数一深、参数量一大，数值就容易爆。

Hyper-Connections (HC) 的想法是把这一条车道加宽成 n 条：

x_{l+1} = B_l · x_l  +  C_l · F(A_l · x_l)
  • A：把 n 条车道汇成 1 条，喂给这一层（所以层内部结构完全不用改）
  • B：n×n 矩阵，让 n 条车道互相混合
  • C：把这一层的输出再分发回 n 条车道

问题出在 B：如果它的谱范数 > 1，每过一层信号就放大一点，60 层叠下来能放大 3000 倍，训练直接崩。

mHC 的解法：把 B 关进 Birkhoff 多胞体

V4 强制 B 是双随机矩阵（行和 = 1、列和 = 1、元素非负）。

最简单的例子：把 B 想成"往 4 条车道分水"。

        到车道0  到车道1  到车道2  到车道3   行和
车道0     0.5     0.2     0.2     0.1   = 1.0
车道1     0.2     0.4     0.3     0.1   = 1.0
车道2     0.2     0.3     0.4     0.1   = 1.0
车道3     0.1     0.1     0.1     0.7   = 1.0
列和      1.0     1.0     1.0     1.0

行和为 1 ⇒ 每条车道的水全部流出去、一滴不多；列和为 1 ⇒ 每条车道收到的水总量不变。水的总量守恒 → 谱范数 ‖B‖₂ ≤ 1 → 永远不放大。

而且双随机矩阵集合对乘法封闭，所以 61 层连乘下来仍然不放大。这就把 3000× 的放大压到了 2× 以内。

实现上：先 exp() 保证元素为正，再用 Sinkhorn-Knopp 交替归一化行和列 20 次，逼近双随机。A = σ(Ã) ∈ (0,1)，C = 2σ(C̃) ∈ (0,2)，都用 Sigmoid 卡住范围。

A/B/C 还是动态的（由当前 token 的 hidden state 算出来）+ 静态偏置 + 一个初始化为很小值的门控 α，让训练早期约等于普通残差，再慢慢学。

代价：mHC 让墙钟时间多了 6.7%（✅ V4 报告实测；已经通过融合 kernel、选择性重计算、调 DualPipe 优化过了）。

⚠️ "时间 +6.7%" 不等于 "吞吐 −6.7%"，这两个数不是同一个。 换算一次：吞吐变成 $1/1.067 = 93.7\%$，也就是降速 6.3%，不是 6.7%。倍数小的时候差别不大，但这条换算纪律在读"提速 1.5 倍 / 时间减少 50%"这类句子时会救命——时间减少 50% = 提速 2 倍，不是 1.5 倍。

⚠️ 还要注意这 6.7% 的归属：它是 mHC 一个组件的开销，不是 V4 整体的。V4 那些"更快"的结论来自 CSA/HCA、MegaMoE、FP4，mHC 是从那笔提速预算里扣掉的一项，买回来的是 1.6T 规模下的训练稳定性。⚠️ mHC 为什么贵在访存和串行而不在 FLOP（Sinkhorn 20 次迭代是 20 个串行的小 kernel），见 03 章 §3.5.5。

四、改进点 3：Muon 优化器

Adam 的逻辑：对每个参数单独看历史梯度大小，梯度大的方向步子迈小点。

Muon 的逻辑：把梯度当成矩阵 G，做 SVD 得 G = UΣVᵀ，然后把所有奇异值都强制设为 1，用 UVᵀ 去更新。

用大白话讲：Adam 是"逐个方向调音量"，Muon 是"把所有方向的音量拉平"——不让某几个主导方向吃掉全部更新量，更新更均衡，收敛更快。

真做 SVD 太贵，所以用 Newton-Schulz 迭代近似。V4 用了个混合系数方案，共 10 步：

  • 前 8 步：(3.4445, −4.7750, 2.0315) —— 激进，快速把奇异值推向 1

  • 后 2 步：(2, −1.5, 0.5) —— 温和，把奇异值稳稳收在 1

  • 哪些参数用 Muon：矩阵形参数（MoE 专家、注意力投影）全用。

  • 哪些不用：embedding、预测头、mHC 的静态偏置和门控、所有 RMSNorm 权重 —— 这些继续用 AdamW。

⚠️ "embedding 不用 Muon"不是工程偷懒，是有硬理由的：Muon 的整个论证建立在"把梯度矩阵的奇异值全部拉平"上，而 embedding 的两个维度性质完全不同（一边是词表、一边是特征），它更像 $V$ 个独立的向量而不是一个矩阵，谱范数那套几何在它身上讲不通。完整推导见 13 章 §13.6。

工程上有个坑：Muon 需要完整的梯度矩阵，而 ZeRO（Zero Redundancy Optimizer，零冗余优化器）会把参数切碎。V4 为此设计了混合 ZeRO 分桶（背包算法分配矩阵、保证不切分逻辑独立矩阵、padding 开销 < 10% 显存）。ZeRO 三个阶段各切什么、为什么会和 Muon 冲突，见 训练框架 §5。

五、改进点 4：MoE 的三处小调整（沿用 DeepSeekMoE）

V4-Pro 配置：61 层、hidden 7168、384 个路由专家 + 1 共享专家、每 token 激活 6 个。

和 V3 并排看，改的是"更多更细的专家、每次选更少"：

✅ DeepSeek-V3 ✅ DeepSeek-V4-Pro 方向
层数 61（前 3 层稠密 + 58 层 MoE） 61（全部 MoE，浅层改哈希路由） 稠密层消失
路由专家 256 384 +50%
每 token 激活 Top-8 Top-6 −25%
共享专家 1 1 =
每个专家多大 — ⚠️ 反推 ≈ 67 M（见 §一） —
路由节点数上限 每 token 最多 4 个节点 取消 靠新并行策略兜
负载均衡 无辅助损失偏置法（⚠️ 仍保留极小的序列级 aux loss） 沿用 =

📌 "更多更细的专家 + 每次选更少"是这一代的共同方向，背后是一个组合数论证：$\binom{384}{6} \approx 5.6\times10^{12}$ 种组合，而 $\binom{256}{8} \approx 4.1\times10^{14}$——⚠️ 注意 V4 的组合数其实更少，所以这次的动机不是组合数，而是单个专家更小 ⟹ 激活参数更少 ⟹ 每 token 更便宜。细粒度专家的完整论证在 10 章 §10.7.2。

  1. 亲和度打分函数：Sigmoid → Sqrt(Softplus(·))
    Sigmoid 在分数很高时会饱和（输出贴近 1，导数≈0），"很想要这个专家"和"极其想要这个专家"梯度都消失了。Sqrt(Softplus) 不饱和，梯度一直有。

  2. 浅层改用哈希路由
    前几层原本是 dense FFN，V4 换成按 token ID 哈希决定专家的 MoE 层。哈希是确定性的 → 天然负载均衡、零路由开销，还白赚了参数量。

  3. 取消路由目标节点数限制
    V3 限制每个 token 最多路由到 4 个节点（省通信），V4 直接取消，靠新的并行策略解决。

MTP 完全没改（MTP = Multi-Token Prediction，多 token 预测），原文说 "we adopt the same strategy for DeepSeek-V4 series without modification"，深度为 1，用于投机解码。

⚠️ 既然"完全没改"，那 V3 的官方口径就可以直接搬过来用：第二个 token 的接受率 85%~90%、TPS 提升 1.8×（✅ V3 报告披露）。不是社区常传的 3×。 深度为 1 意味着 $\gamma = 1$，代进期望接受长度的公式可以对一下：
E = (1 − α^(γ+1)) / (1 − α) = 1 + α (γ = 1) α = 0.85 → E = 1.85 α = 0.90 → E = 1.90 ⟹ 和官方的"TPS 提升 1.8×"几乎完全吻合 ✅（差的那一点是草稿层本身的开销）
⚠️ 别写成 α × γ：草稿 token 是串行依赖的（第 2 个建立在"第 1 个被接受"的前提上），期望接受长度是几何求和 $\frac{1-\alpha^{\gamma+1}}{1-\alpha}$，$\gamma$ 越大这个错法错得越离谱。逐 $\gamma$ 的完整推演表见 12 章 §12.5，工程实现见 推理框架 §8。

六、训练稳定性的两个"土办法"

报告很坦诚，这两个是经验性的、没有理论解释：

  • 前瞻路由（Look-ahead Routing）：第 t 步计算特征用 θ_t，但路由索引用 θ_{t−Δt}（一个稍旧的快照）。打破"路由决策"和"骨干网络"的同步耦合，几乎零开销地消除 loss spike。
  • SwiGLU 截断：线性分量强行限制在 [−10, 10]，gate 上限也是 10。

七、Infra 层：为什么便宜

  • MegaMoE 融合 kernel：把专家切成多个 wave 流水，做到「算当前 wave + 发上一 wave + 收下一 wave」三者并行，相比非融合基线加速 1.50~1.73×，RL rollout 场景最高 1.96×。
  • FP4 QAT（QAT = Quantization-Aware Training，量化感知训练）：MoE 专家权重走 FP32 主权重 → FP4 存储 → FP8 计算。关键点是 FP4→FP8 反量化是无损的（E2M1 只能表示 $\pm{0, 0.5, 1, 1.5, 2, 3, 4, 6}$ 这 15 个值，E4M3 全都能精确表示），所以能直接复用现有 FP8 训练框架。

⚠️⚠️ "复用现有 FP8 训练框架"指的是 V3 那一套，而 V3 的 FP8 方案在中文资料里有四处几乎总被写反。 V4 篇里只要提到 FP8，就该按下面这个口径（✅ 全部按 DeepSeek-V3 报告 §3.3 / §3.5.2 原文）：

# ❌ 常见错法 ✅ 论文原文
① 注意力计算也走 FP8 注意力算子保持原精度；走 FP8 的只有 Fprop / Dgrad / Wgrad 三个 GEMM
② 前向 E4M3、梯度 E5M2 所有张量统一用 E4M3（这正是 V3 和前人混合格式方案最大的区别）
③ scale 用历史最大值的 EMA 延迟更新 在线逐 tile / 逐 block 现场算 max，论文明说就是为了避开延迟缩放
④ "PPL < 0.02% / 提速 1.6 倍 / 省显存 30%" ⚠️ 这三个数字论文里都没有。 唯一的结论是相对 BF16 基线的 loss 相对误差 < 0.25%

逐条还原与那条"scale 沿内维变 ⟹ 标准 FP8 GEMM 不支持 ⟹ 所以有了 DeepGEMM"的因果链，见 14 章 §14.11 和 大模型算子开发 §6。
- TileLang：自研 kernel DSL，把 kernel 启动的 CPU 侧开销从几十~几百微秒压到 < 1 微秒，还集成 Z3 SMT 求解器做索引约束的形式化验证。
- 逐位确定性：注意力用双 kernel 替代 split-KV，矩阵乘用 DeepGEMM 替代 cuBLAS，反向传播给每个 SM 独立累加 buffer 消除 atomicAdd 不确定性 —— 训练/推理 bitwise 可复现。
- 推理侧缓存：把滑动窗口和未压缩尾部视为"状态空间模型"（大小固定、只取决于当前位置），可以预分配固定大小缓存池；共享前缀（如同一套 system prompt）的 KV cache 存到磁盘复用。这就是 cache hit 价格能做到 $0.0036/M 的原因。分页与前缀缓存的工程实现见 推理框架 §5。
- 给硬件厂商的建议（报告专门写了一节）：算力/带宽比 C/B ≤ 6144 FLOPs/Byte 比绝对带宽更重要；预留功耗余量；提供低延迟信令支持 push 模式；设计比 SwiGLU 更简单的激活函数。

★ 那个 C/B ≤ 6144 值得代进真实硬件看一眼（这正是屋脊线模型里的"屋脊点"，见 06 章 §6.4 与 大模型算子开发 §2）：
```
H100 SXM5：HBM3 80 GB / 3.35 TB/s
BF16 稠密 989 TFLOPS -> 屋脊点 = 989e12 / 3.35e12 = 295 FLOPs/Byte
FP8 稠密 1979 TFLOPS -> 屋脊点 = 1979e12 / 3.35e12 = 591 FLOPs/Byte
⚠️ BF16 那一栏另一个常见数字 1979 是【2:4 稀疏】值，不是稠密峰值，别混用

⟹ 现役硬件的屋脊点是 295 / 591，DeepSeek 要求的上限是 6144。
它不是在说"现在太高了"，而是在说"★ 别再往上飙了" ——
算力涨得比带宽快，屋脊点就会一路右移，
decode 这种算术强度只有个位数的负载会被越甩越远。
```
⚠️ 顺带把两个常被写错的带宽数字也钉住：NVLink 的 900 GB/s 是双向聚合，单向是 450；InfiniBand 400 Gb/s ÷ 8 = 50 GB/s（是 Gb 不是 GB，差 8 倍）。见 训练框架 §3。

八、后训练：领域专家 → on-policy 蒸馏合并

这块和 on-policy distillation survey 正好对上（该综述在本仓库上一级目录）。

两阶段范式：

阶段 1：分领域各练各的
  数学专家   ← SFT + GRPO（数学专用奖励）
  代码专家   ← SFT + GRPO（代码专用奖励）
  Agent 专家 ← SFT + GRPO（Agent 专用奖励）
  指令专家   ← ...

阶段 2：用 on-policy distillation 合并成一个模型
  学生自己采样 → 各领域教师给出分布 → 最小化 Σ w_i · D_KL(π_student ‖ π_teacher_i)

为什么不用别的办法：权重合并会因为参数空间不对齐而失效；混合 RL 会让不同领域的奖励互相冲突。OPD 成本高，但效果最好。

两个关键设计：

  • 逆 KL（D_KL(学生 ‖ 教师)）而非正向 KL —— 逆 KL 是 mode-seeking（学一个模式学得像），正向 KL 是 mode-covering（把所有模式糊在一起）。蒸馏要的是前者。
  • 全词表 logit 计算 KL，而不是 token 级采样估计 —— 梯度方差小得多，多教师场景下尤其必要。

另外几个后训练亮点：

  • GRM（生成式奖励模型）：不训标量奖励模型，让模型生成一段评估判断，并对 GRM 本身也做 RL。信息量远超一个分数。
  • 三档推理力度：Non-think（8K）、Think High（128K）、Think Max（384K），每一档单独训练专家。
  • 交错思考：V3.2 每轮丢弃思考痕迹，V4 在工具调用场景保留并跨轮累积（1M 窗口才撑得住）。
  • Quick Instruction：把意图识别、搜索触发等辅助任务编码成特殊 token 附加到输入，复用 KV cache，避免重新 prefill。
  • RL Infra：可抢占 rollout 服务 + token 粒度 WAL 日志（被抢占后从最后完成的 token 恢复）；Rust 写的 DSec 沙箱平台管理数十万并发沙箱。

九、效果与代价

强的地方（V4-Pro-Max）：

  • Codeforces Rating 3206（开源首次匹敌闭源，约等于人类第 23 名）
  • LiveCodeBench 93.5、HMMT 2026 Feb 95.2
  • 长上下文 MRCR 1M 83.5 > Gemini-3.1-Pro 的 76.3（但 < Opus 4.6 的 92.9）
  • 中文功能写作胜率 62.7% vs Gemini-3.1-Pro 34.1%

弱的地方：

  • SimpleQA-Verified 57.9 vs Gemini-3.1-Pro 75.6，差 17.7 分
  • MMLU-Pro 87.5 vs 91.0

报告自己给的结论很值得记：推理能力更依赖架构与训练方法，知识能力更依赖数据。 差距主要在训练语料的质量与知识密度上，落后前沿约"3 到 6 个月"。

报告承认的局限：组件堆叠导致架构"不够优雅"；前瞻路由和 SwiGLU 截断缺乏理论解释；事实性知识仍落后顶尖闭源模型。
