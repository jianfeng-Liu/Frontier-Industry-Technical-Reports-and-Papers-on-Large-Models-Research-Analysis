06 · KV cache：为什么长上下文这么贵

这一章的目标：这是全教程第二关键的一章。五份技术报告里那些看起来五花八门的注意力改造，动机全部来自本章的两个事实。
读完你应该能回答：KV cache 是什么、有多大？为什么"生成第 10001 个字"比"读完 10000 个字"更贵？为什么省 KV cache 几乎等于直接提速？

6.1 先看一个反直觉的事实

    你给模型一个 10 万字的文档，让它总结。

    阶段 A：模型"读完"这 10 万字        ← 大概 3 秒
    阶段 B：模型吐出 500 字的总结        ← 大概 5 秒

    读 10 万字用了 3 秒，写 500 字用了 5 秒。
    ★ 写字比读字慢了【400 倍】（按每字算）

这不是模型"思考"得慢。这是两个阶段的硬件瓶颈完全不同。

┌─── Prefill（预填充）：处理你的输入 ────────────────────┐
│  一次前向，【并行】处理全部 L 个 token                   │
│  每个权重矩阵读进来一次，要给 L 个 token 用              │
│  → 计算多、访存少  → 【算力受限 compute-bound】          │
└────────────────────────────────────────────────────────┘

┌─── Decode（解码）：一个一个吐字 ──────────────────────┐
│  每次前向只处理【1 个】token                            │
│  每个权重矩阵还是要完整读进来一次，但只给 1 个 token 用   │
│  → 计算少、访存多  → 【访存受限 memory-bound】           │
└────────────────────────────────────────────────────────┘

★ 先把四个缩写认清楚（后面各章会反复出现）

这两个阶段各自对应一个延迟指标，业界几乎只用缩写称呼它们。本教程从这里开始也会用，所以先在这里讲清楚：

┌─ TTFT ─ Time To First Token ─「首字延迟」──────────────────┐
│                                                            │
│  你按下回车  →  屏幕上蹦出【第一个字】，中间等了多久        │
│                                                            │
│  由 Prefill 决定 → 算力受限 → 只有【减少 FLOPs】才有用      │
│  单位：秒（s）。上面例子里那「3 秒」就是 TTFT               │
└────────────────────────────────────────────────────────────┘

┌─ TPOT ─ Time Per Output Token ─「每字延迟」────────────────┐
│                                                            │
│  第一个字出来【之后】，每多蹦一个字要等多久                 │
│  （有些论文写作 ITL = Inter-Token Latency，是同一个东西）   │
│                                                            │
│  由 Decode 决定 → 访存受限 → 只有【减少字节数】才有用       │
│  单位：毫秒（ms）                                           │
│  ★ 它就是你肉眼看到的「打字速度」：                         │
│    TPOT = 10 ms  →  每秒 100 个字，比人读得快，体感流畅      │
│    TPOT = 100 ms →  每秒 10 个字，明显一顿一顿              │
└────────────────────────────────────────────────────────────┘

  一次完整对话的耗时  ≈  TTFT  +  TPOT × 输出字数
                         └首字┘   └──── 后续每个字 ────┘

还有两个描述"量"而不是"延迟"的缩写：

TPS   Tokens Per Second「吞吐量」—— 一块卡每秒总共吐出多少字
      ★★ 和 TPOT 不是一回事，这是最容易混的一对：
         TPOT 问的是「我这一个用户要等多久」        ← 延迟，越小越好
         TPS  问的是「这块卡一共干了多少活」        ← 产能，越大越好
      两者靠 batch（同时服务几个用户）联系起来：
         TPS ≈ batch ÷ TPOT
      ⚠️ 而且它们【互相打架】：batch 开大 → TPS 涨，但每个用户的 TPOT 也变长
         （openPangu 的实测就是这样：TPOT 9.53 ms 那一档和
           1727 TPS 那一档【不是同一个配置】，见 §6.7）

ISL   Input Sequence Length  —— 输入有多少 token（报告表格里常见）
OSL   Output Sequence Length —— 输出有多少 token
      「8K+1K」就是 ISL=8192、OSL=1024 的意思

📌 为什么要专门强调这四个词：五份技术报告在"推理性能"一节几乎只报这几个数。看不懂缩写，那一整节就等于没读。

🔑 一句必须记住的话：
Decode 阶段，GPU 的算力几乎是闲置的。它 99% 的时间在等数据从显存搬到计算单元。

这句话是理解这一代所有推理优化的钥匙。

6.2 为什么需要 cache

回忆 05 章：生成第 $t$ 个 token 时，它的 Query 要和前面所有 token 的 Key 做内积。

生成第 1 个：Q1 · [K1]                       V: [V1]
生成第 2 个：Q2 · [K1, K2]                   V: [V1, V2]
生成第 3 个：Q3 · [K1, K2, K3]               V: [V1, V2, V3]
                    ↑↑↑↑↑↑
              这些每次都完全一样！

K1 是从 token 1 算出来的，token 1 不会变，所以 K1 永远不变。

❌ 不 cache：每生成一个 token，重算前面所有 K、V     → O(L²) 重复计算
✅ cache：  算过就存下来，只算新 token 的 K、V       → O(L)

所以 KV cache 是必须的。问题是它太大了。

⚠️ 为什么不 cache Q：因为 $Q_t$ 只在生成第 $t$ 个 token 时用一次，用完就没用了。K 和 V 要被后面所有 token 反复用，Q 不会。

6.3 KV cache 到底有多大：算一笔账

$$\text{KV cache 大小} = 2 \times N \times H_{kv} \times d_h \times L \times B \times \text{bytes}$$

符号 含义
2 K 和 V 各一份
$N$ 层数（每层都有自己的 KV）
$H_{kv}$ KV 头数
$d_h$ 每个头的维度
$L$ 当前序列长度
$B$ batch size（同时服务几个用户）

代入真实数字

用一个 openPangu 规模的假想 MHA 模型（$N=50$，$d=5120$，即 $H\cdot d_h = 5120$），BF16（2 字节）：

每个 token 每层：  2 × 5120 × 2 字节 = 20,480 字节 = 20 KB
每个 token 全模型：20 KB × 50 层 = 1,024,000 字节 ≈ 1 MB   ★

    L = 8K：      8 GB
    L = 128K：  128 GB      ← 已经超过单卡显存
    L = 512K：  512 GB      ← 需要 7 张 80GB 卡【只放 cache】
    L = 1M：   1024 GB

🔑 记住这个量级：一个 500B 级模型，MHA 下大约 1 MB / token。

而这还只是 batch=1。真实服务要同时服务几十上百个用户：
B = 32，L = 128K：128 GB × 32 = 4 TB ← 完全不可能

对比：模型权重本身多大

openPangu-2.0-Pro：505B 参数
    BF16：  505B × 2 字节 = 1010 GB     ← 报告实测 1009 GB ✅
    W8A8：  505B × 1 字节 ≈ 505 GB      ← 报告实测 517 GB ✅（1.95× 压缩）

    权重（固定）    ████████████████████  1009 GB
    KV cache 128K   ██                     128 GB   ← MHA 假想值
    KV cache 512K   ██████████             512 GB   ← 和权重同一量级了！

🔑 这就是问题的全貌：短上下文时 KV cache 可以忽略，长上下文时它会追上甚至超过模型权重本身。而它还随用户数线性增长。

✅ 对照真实数据：DeepSeek-V4 报告称在 1M 上下文下，KV cache 只占约 2%。这不是 MHA 能做到的——是 07 章 的压缩技术做到的。

6.4 Roofline：为什么"省显存"就等于"提速"

这一节是本章的技术核心。它解释了为什么所有厂商都在省 KV cache，而不是省计算。

算术强度（arithmetic intensity）

对任何一段计算，定义：

$$I = \frac{\text{做了多少次浮点运算 (FLOPs)}}{\text{从显存搬了多少字节 (bytes)}}$$

硬件有一个"脊点"（ridge point）：

$$I_{\text{ridge}} = \frac{\text{峰值算力 (FLOP/s)}}{\text{显存带宽 (byte/s)}}$$

以 H100 SXM（BF16 稠密约 989 TFLOPS，HBM3 带宽约 3.35 TB/s）为例：

$$I_{\text{ridge}} \approx \frac{989\times10^{12}}{3.35\times10^{12}} \approx \mathbf{295\ \text{FLOP/byte}}$$

      性能
        ▲
 峰值算力├──────────────────────  ← 算力受限区（compute-bound）
        │                ╱
        │              ╱  斜率 = 显存带宽
        │            ╱
        │          ╱  ← 访存受限区（memory-bound）
        │        ╱     性能完全由带宽决定，算力再强也没用
        └──────╱────────────────────────→ 算术强度 I
                     ↑
                I_ridge ≈ 295 FLOP/byte

要跑满 H100 的算力，每从显存读 1 个字节，必须做 295 次浮点运算。 达不到，就是在浪费算力。

Decode 的算术强度是多少

对一个权重矩阵 $W\in\mathbb{R}^{m\times n}$，BF16 存储：

搬运：m × n × 2 字节
计算：每个 batch 元素做 2mn FLOPs（乘 + 加），共 B 个

    I = (2mn × B) / (2mn) = B

$$\boxed{I_{\text{decode}} \approx B\ \text{（batch size）}}$$

B = 1：    I = 1        vs   I_ridge = 295
                             → 算力利用率 【1/295 ≈ 0.3%】
B = 32：   I = 32       →  利用率 ~11%
B = 295：  I = 295      →  刚好跑满

★ 但 B=295 意味着 KV cache 要 ×295 —— 显存根本放不下

🔑 这就是完整的因果链，请仔细看：

① decode 每次只处理 1 个 token → 算术强度 ≈ batch size ② 要跑满算力，需要 batch ≈ 295 ③ 但 batch 越大，KV cache 越大（线性） ④ 显存被 KV cache 占满 → batch 开不大 → 算力浪费 99% ↓ ⑤ ★★ 省下 KV cache = 能开更大 batch = 直接换成吞吐量 ★★

"省显存"和"提速"在 decode 阶段是【同一件事】。这就是五家全都在死磕 KV cache 的原因。

换个角度：单次 decode 的时间下界

即使 batch=1，每生成一个 token 也必须至少把所有激活的权重读一遍：

openPangu-2.0-Pro 激活参数 18B，W8A8（1 字节）：
    每 token 至少搬运 18 GB
    在 3 TB/s 带宽下：18 / 3000 ≈ 6 ms

✅ 报告实测 TPOT = 9.53 ms @ 8K，9.55 ms @ 128K
   （TPOT = 每吐一个字的间隔，见 §6.1；8K/128K 是 ISL 输入长度）
   → 和这个量级完全吻合（差的部分是 KV cache 读取 + 通信 + 非理想效率）

📌 注意 openPangu 那两个数字：8K 和 128K 的 TPOT 几乎一样（9.53 vs 9.55 ms）。
这说明它的 KV cache 读取开销在 128K 下依然没有成为主导项——正是 MLA + SWA + DSA 组合起来的效果（07/08 章）。

反过来说：如果一个模型用朴素 MHA，128K 的 TPOT 会明显高于 8K，因为每步都要多读 128 GB 的 cache。

6.5 三个可以下手的方向

现在你有了完整的问题定义，解法只有三个方向，五家全部落在这三格里：

    KV cache 大小 = 2 × N × H_kv × d_h × L × B × bytes
                        ↑    ↑↑↑↑↑↑↑↑↑↑    ↑        ↑
                        │        │          │        │
                     ① 层数    ② 每层存多少  ③ 存几个  ④ 每个几字节
                                                token
方向 怎么做 在哪章
② 每层存多少 MQA / GQA / MLA（低秩压缩） 07 章
③ 存几个 token 滑动窗口 / 稀疏选择 / 线性注意力（根本不存） 08 章
④ 每个几字节 KV cache 量化（BF16 → FP8 → INT4） 14 章 §14.10
① 层数 只在部分层保留全量 KV（跨层共享） 08 章（GLM 的 IndexShare 是相关思路）

这就是 06→07→08 三章的分工，也是 ../模型技术对比.md §3.1 那张表的组织逻辑。

6.6 Prefill 侧的账：TTFT（首字延迟）

Prefill 是算力受限的，所以它的账完全不同。

$$\text{prefill FLOPs} \approx 2 \times N_{\text{active}} \times L + \underbrace{\text{注意力的 } L^2 \text{ 项}}_{\text{长序列时主导}}$$

回忆 01 章 §1.5：

L = 4K：   注意力项占 ~12%，可忽略
L = 1M：   注意力项占 ~97%，【完全主导】

    而且它是【平方】的：128K → 1M 是 8 倍长度，这一项涨 64 倍

✅ openPangu 报告实测：TTFT = 3.0 s @ 128K 输入、单 batch
   （TTFT = Time To First Token = 首字延迟，见 §6.1）
   → 读 12.8 万字要等 3 秒才开始出字，这 3 秒【全部花在 Prefill 上】

🔑 两个阶段要用完全不同的手段优化：
```
Prefill 慢 → 是【算力】问题 → 要减少 FLOPs → 稀疏注意力、滑窗
Decode 慢 → 是【访存】问题 → 要减少字节数 → 压缩 KV cache、量化

★ 稀疏注意力同时帮两边：既少算，又少存
这就是为什么 DSA / MSA / SWA 这类技术是五家的主流选择
```

6.7 还有一个方向：一次多吐几个字

如果 decode 的瓶颈是"每步都要把 18 GB 权重读一遍"，那么——

    读一遍权重，只吐 1 个 token   →  每 token 成本 = 18 GB
    读一遍权重，吐出 5 个 token   →  每 token 成本 = 3.6 GB    ★ 5 倍

权重只读一次，能多产出几个 token，就等于直接提速几倍。

这正是 MTP + 投机解码的全部动机，见 12 章。五家全部上了 MTP，一个不落，因为它是在不改主模型的前提下最直接的 decode 加速手段。

📌 注意这和"省 KV cache"是两条独立的路：
省 KV cache → 能开更大 batch → 提【吞吐量 TPS】（这块卡每秒总共吐多少字） MTP → 每次多吐几个字 → 降【单用户延迟 TPOT】（我这一个人要等多久）
✅ openPangu 报告的 1727 TPS/NPU 是吞吐量指标，9.53 ms TPOT 是延迟指标——回到 §6.1 那组定义。

⚠️ 但这两个数字不能凑在一起吹，它们来自报告里两张不同的表、两个不同的配置：
```
「超低延迟」那档： TPOT 9.53 ms ← 牺牲吞吐换延迟
「低延迟吞吐」那档：TPOT 23.2 ms，batch 40，1727 TPS ← 牺牲延迟换吞吐

验算一下这组数是否自洽（⚠️ 我的推算，不是报告写的）：
40 个用户 ÷ 0.0232 秒 ≈ 1724 tokens/s ✅ 和 1727 对得上
—— 正好印证 §6.1 那条 TPS ≈ batch ÷ TPOT
```
同一个模型，batch 从小调到 40，TPOT 从 9.53 ms 变成 23.2 ms（慢了 2.4 倍），换来吞吐量大涨。这就是延迟与吞吐的取舍。

6.8 本章小结

① Prefill（读输入）是【算力受限】，Decode（吐字）是【访存受限】
   → decode 时 GPU 算力利用率可能只有 0.3%，全在等数据
② KV cache = 2·N·H_kv·d_h·L·B·bytes
   500B 级 MHA 模型 ≈ 1 MB / token
   → 128K 就是 128 GB，512K 追上模型权重本身，且随用户数线性增长
③ ★ Roofline：decode 的算术强度 ≈ batch size，而脊点是 ~295
   → KV cache 占满显存 → batch 开不大 → 算力浪费
   → 【省 KV cache 就是直接提吞吐】，这两件事在 decode 阶段是同一件事
④ 只有四个下手点：改层数 / 改每层存多少 / 改存几个 token / 改每个几字节
   → 分别对应 08 / 07 / 08 / 14 章
⑤ Prefill 慢是 FLOPs 问题（L² 项），Decode 慢是字节数问题，手段不同
   稀疏注意力是少数【两边都帮】的技术
⑥ 另一条独立的路：MTP —— 权重只读一次，多吐几个字（12 章）
