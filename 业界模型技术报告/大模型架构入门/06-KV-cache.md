# 06 · KV cache：为什么长上下文这么贵

> **这一章的目标**：这是全教程**第二关键**的一章。五份技术报告里那些看起来五花八门的注意力改造，**动机全部来自本章的两个事实**。
> 读完你应该能回答：KV cache 是什么、有多大？为什么"生成第 10001 个字"比"读完 10000 个字"更贵？**为什么省 KV cache 几乎等于直接提速**？

> 📌 **本章的定位**：这里讲的是**模型架构侧**的账——为什么结构非得这么设计。同一笔账在推理服务侧还有一份更细的版本（vLLM 怎么分块、一张卡的显存怎么逐行扣、Paged KV 怎么管），在 [推理框架 02 章](../../推理框架/推理优化入门/02-KV-Cache与显存账.md)；算子实现侧（FlashAttention 的在线 softmax、三代 kernel 改了什么）在 [大模型算子开发 04 章](../../大模型算子开发/04-FlashAttention全系.md)。**本章不重复那两份，需要深入时直接跳过去。**

## 6.1 先看一个反直觉的事实

```
    你给模型一个 10 万字的文档，让它总结。

    阶段 A：模型"读完"这 10 万字        ← 大概 3 秒
    阶段 B：模型吐出 500 字的总结       ← 大概 5 秒

    读 10 万字用了 3 秒 → 每个字 0.03 毫秒
    写   500 字用了 5 秒 → 每个字 10   毫秒
    ★ 按每个字算，写字比读字慢了【约 330 倍】
```

**这不是模型"思考"得慢。这是两个阶段的硬件瓶颈完全不同。**

| | **Prefill（预填充）** | **Decode（解码）** |
|---|---|---|
| 在干什么 | 处理你输入的提示词 | 一个一个往外吐字 |
| 一次前向处理几个 token | **并行处理全部 L 个** | ★ **只有 1 个** |
| 权重矩阵读几遍 | 每个读 1 遍，摊给 L 个 token | 每个还是读 1 遍，**只摊给 1 个 token** |
| 计算 : 访存 | 计算多、访存少 | 计算少、访存多 |
| **瓶颈** | **算力受限（compute-bound）** | **访存受限（memory-bound）** |
| 对应的延迟指标 | TTFT（首字延迟） | TPOT（每字延迟） |
| 唯一有效的优化方向 | **减少 FLOPs** | **减少搬运的字节数** |

> 📌 **FLOPs**（**FL**oating-point **OP**eration**s**，浮点运算次数）—— 一次乘法或一次加法各算 1 次。注意它和 **FLOPS**（每秒浮点运算次数，带 /s 的那个）只差一个大小写，前者是"活有多少"，后者是"干活的速度"。本教程一律写成 `FLOPs`（活）和 `FLOP/s` 或 `TFLOPS`（速度）。

### ★ 先把五个缩写认清楚（后面各章会反复出现）

**五份技术报告在"推理性能"一节几乎只报这几个数。看不懂缩写，那一整节就等于没读。**

| 缩写 | 全称 | 中文 | 单位 | 由哪个阶段决定 | 怎么才能改善 |
|---|---|---|---|---|---|
| **TTFT** | **T**ime **T**o **F**irst **T**oken | **首字延迟** | 秒（s） | Prefill | 减少 FLOPs |
| **TPOT** | **T**ime **P**er **O**utput **T**oken | **每字延迟** | 毫秒（ms） | Decode | 减少字节数 |
| **TPS** | **T**okens **P**er **S**econd | **吞吐量** | token/s | 两个阶段合起来 | 省显存 → 开大 batch |
| **ISL** | **I**nput **S**equence **L**ength | 输入长度 | token | — | — |
| **OSL** | **O**utput **S**equence **L**ength | 输出长度 | token | — | — |

**TTFT 是"你按下回车，到屏幕上蹦出第一个字"等的时间**。上面例子里那 3 秒就是它。有些论文把 TPOT 写作 **ITL**（**I**nter-**T**oken **L**atency，字间延迟），是同一个东西的另一个名字。报告表格里的"8K+1K"就是 `ISL=8192、OSL=1024` 的意思。

**TPOT 就是你肉眼看到的「打字速度」**：`TPOT = 10 ms` → 每秒 100 个字，比人读得快，体感是流畅地淌出来；`TPOT = 100 ms` → 每秒 10 个字，明显一顿一顿。

```
    一次完整对话的耗时  ≈  TTFT（等第一个字）  +  TPOT × 输出字数（后面每个字）
```

> ⚠️ **TPOT 和 TPS 是最容易混的一对**，务必分开：
> ```
>     TPOT 问的是「我这一个用户要等多久」   ← 延迟指标，越小越好
>     TPS  问的是「这块卡一共干了多少活」   ← 产能指标，越大越好
>
>     两者靠 batch（同时服务几个用户）联系起来：   TPS ≈ batch / TPOT
> ```
> **而且它们互相打架**：batch 开大 → TPS 涨，但每个用户排队等的时间变长，TPOT 也跟着变长。
> 所以看到一家报"TPOT 9.53 ms"又报"1727 TPS"，第一件事是去确认这两个数是不是同一个配置测出来的——openPangu 那两个数就**不是**，见 §6.7。

---

> 🔑 **一句必须记住的话**：
> **Decode 阶段，GPU 的算力几乎是闲置的。它 99% 的时间在等数据从显存搬到计算单元。**
>
> 这句话是理解这一代所有推理优化的钥匙。§6.4 会把这个 99% 算出来。

## 6.2 为什么需要 cache

回忆 [05 章](05-注意力机制.md)：生成第 $t$ 个 token 时，它的 Query 要和**前面所有** token 的 Key 做内积。

```
生成第 1 个：Q1 · [K1]                       V: [V1]
生成第 2 个：Q2 · [K1, K2]                   V: [V1, V2]
生成第 3 个：Q3 · [K1, K2, K3]               V: [V1, V2, V3]
                    ^^^^^^^^
              这些每次都完全一样！
```

**K1 是从 token 1 算出来的，token 1 不会变，所以 K1 永远不变。** 于是只有两种做法：

```
❌ 不 cache：每生成一个 token，把前面所有 K、V 全部重算一遍
✅ 会 cache：算过就存下来，每步只算【新来这一个 token】的 K、V
```

> ⚠️ **为什么不 cache Q**：因为 $Q_t$ 只在生成第 $t$ 个 token 时用一次，用完就没用了。**K 和 V 要被后面所有 token 反复用，Q 不会。** 这个不对称是 KV cache 这个名字里只有 K 和 V 的全部原因。

### ★ 把这笔交易算出来：cache 到底换掉了什么

**这一节是本章的第一个推演。** 很多材料只说"不 cache 是 $O(L^2)$，cache 是 $O(L)$"就结束了，但**大 O 记号会把最重要的东西藏起来**：cache 并不是凭空变快的，它是**用访存换算力**——省下的是计算，多付的是显存和搬运。把两边的绝对值都算出来，才能看懂 §6.4 为什么说"省 KV cache 等于提速"。

**设定一个具体场景**（用 openPangu-2.0-Pro 的规模：$N=50$ 层、$d=5120$，MHA，BF16）：

```
    prompt 有 1000 个 token，要生成 1000 个字。
    ★ 只算「K、V 两个投影」这一项，不含 FFN、不含注意力本身——
      这样两边的差别才是干净的，看的就是"重算 vs 存下来"这一件事。
```

**先算单价**。一个 token、一层的 K 投影是 `[1,d] × [d,d]`，乘加各一次记 2 FLOPs：

| 算什么 | 式子（乘加各记 1 FLOP） | FLOPs |
|---|---|---|
| 一层的 K 投影 | `2 × d × d = 2 × 5120 × 5120` | 52.4 M |
| 一层的 K + V | 再 `× 2` | 104.9 M |
| **全模型 50 层** | 再 `× 50` | ★ **5.24 G** —— 每个 token 的 K/V 投影单价 |

**再数要算几个 token**：

| 生成到第几个字 | ❌ 不 cache：本步要算 K/V 的 token 数 | ✅ 有 cache：本步要算的 token 数 |
|---|---|---|
| 第 1 个 | 1001 | 1 |
| 第 2 个 | 1002 | 1 |
| 第 500 个 | 1500 | 1 |
| 第 1000 个 | 2000 | 1 |
| **1000 步累计** | **1,500,500** | **1,000** |

（累计公式：不 cache 是 $\sum_{t=1}^{1000}(1000+t) = 1000\times1000 + \frac{1000\times1001}{2} = 1{,}500{,}500$；有 cache 就是 1000。）

**★ 把两边的 FLOPs 和字节数并排列出来**（⚠️ 我的推演，用于建立量级感，不是任何一家的官方数字）：

| | ❌ 不 cache | ✅ 有 cache | 倍数 |
|---|---|---|---|
| K/V 投影总 FLOPs | 5.24 G × 1,500,500 = **7.87 PFLOPs** | 5.24 G × 1000 = **5.24 TFLOPs** | ★ **1500×** |
| 跑完这些计算的理想耗时（H100 BF16 满算力 989 TFLOP/s） | **约 8.0 秒** | 约 5.3 毫秒 | 1500× |
| 额外要从显存读回的 KV 字节 | **0**（重算，不读） | 每步读整份 cache，累计 **约 1.54 TB** | — |
| 搬这些字节的理想耗时（H100 HBM3 3.35 TB/s） | 0 | **约 0.46 秒** | — |
| 峰值显存占用（KV） | **0** | 2000 token × 1 MB ≈ **2.0 GB** | — |
| **★ 两项相加的下界** | **约 8.0 秒** | **约 0.46 秒** | ★ **约 17×** |

> 🔑 **三个结论，逐条看**：
> ```
> ① FLOPs 差了 1500 倍，墙钟时间只差 17 倍 —— 差距被"吃掉"了
>    因为重算那条路是【算力受限】的（算得多但不搬数据），
>    而 cache 那条路是【访存受限】的（几乎不算，全在搬 1.54 TB）。
>    ★ 这两条路撞在硬件的两面墙上，这就是 §6.4 屋顶线的雏形。
>
> ② cache 换掉的不是"计算"，是把计算【换成了搬运】
>    5.24 GFLOPs/token 的重算  →  1 MB/token 的读回
>    这笔交易在任何长度上都划算（17×），所以 KV cache 不是优化，是前提。
>
> ③ ★ 但注意那 1.54 TB 是【随长度平方增长】的：
>    第 t 步要读 t 个 token 的 cache，累计就是 ΣL ∝ L²。
>    ⟹ cache 把"平方的计算"换成了"平方的搬运"。
>    ⟹ 长上下文下，搬运这一项会重新变成瓶颈 —— 这就是 07、08 两章要解决的事。
> ```

> ⚠️ **上表的口径说明**：① 两边都还要读权重矩阵（$2d^2$ 个数，两条路一样多），我把它约掉了，只看差异项；② "理想耗时"假设满算力、满带宽，真实效率远低于此（FlashAttention-2 在 H100 上只跑到峰值的 **35% 左右**，见 [大模型算子开发 §4.4.6](../../大模型算子开发/04-FlashAttention全系.md)），所以这两个数只能互相比，不能当成实测值；③ 这里只数了 K/V 投影，**整个前向**的重算代价还要大得多——那份"每步要前向几个 token"的完整账（同样的场景差 509 倍）在 [推理框架 §2.1](../../推理框架/推理优化入门/02-KV-Cache与显存账.md)。

**所以 KV cache 是必须的，没有任何生产框架提供"关掉它"的选项。问题只在于它太大了。**

## 6.3 KV cache 到底有多大：算一笔账

$$\text{KV cache 字节数} = 2 \times N \times H_{kv} \times d_h \times L \times B \times \text{bytes}$$

| 符号 | 含义 | 常见取值 |
|---|---|---|
| 2 | K 和 V 各存一份 | 固定 |
| $N$ | 层数（每层都有自己独立的 KV） | 32 ~ 93 |
| $H_{kv}$ | ★ **KV 头数**（不是 Q 头数！） | MHA 等于 Q 头数；GQA 少几倍；MQA = 1 |
| $d_h$ | 每个头的维度（head_dim） | 通常 64 / 80 / 128 |
| $L$ | 当前序列长度 | 8K ~ 1M |
| $B$ | batch size（同时服务几个用户） | 1 ~ 几百 |
| bytes | 每个数占几字节 | BF16 = 2，FP8 = 1，INT4 = 0.5 |

> ⚠️⚠️ **本教程最高频的一个算错点，先说在这里。** 很多文章会把公式简写成 **「每 token 每层 = $4\times d_{\text{model}}$ 字节」**（BF16 下）。这个简写**只对 MHA 成立**——因为只有 MHA 才有 $H_{kv}\times d_h = d_{\text{model}}$。拿它去套 GQA / MQA / MLA 模型，会高估很多倍：
>
> | 模型 | 真实配置 | ✅ 正确算法 | ❌ 用 $4d_{\text{model}}$ 硬套 | 高估 |
> |---|---|---|---|---|
> | **Llama-3-70B**（GQA） | 80 层，64 Q 头 / **8 KV 头**，$d_h$=128，$d_{\text{model}}$=8192 | $2\times8\times128\times2\times80$ = **320 KiB / token** | $4\times8192\times80$ = 2560 KiB | ★ **8 倍** |
> | 同规模改成 **MQA** | **1 KV 头** | $2\times1\times128\times2\times80$ = **40 KiB / token** | 同上 2560 KiB | ★ **64 倍** |
> | **DeepSeek-V3**（MLA） | 61 层，latent 512 + 解耦 RoPE 64，$d_{\text{model}}$=7168 | $(512{+}64)\times2\times61$ = **68.6 KiB / token** | $4\times7168\times61$ = 1708 KiB | ★ **25 倍** |
>
> ★ **判断法则：公式里那个头数必须是 `n_kv_heads`，不是 `n_heads`。** 看到任何 KV cache 估算，第一件事是去模型的 `config.json` 里确认 `num_key_value_heads`。这条口径与 [推理框架 §2.2](../../推理框架/推理优化入门/02-KV-Cache与显存账.md) 一致，那边还逐行演示了 Llama-3-8B 的七步累乘。

> ⚠️ **单位口径，全章统一**：算**容量**一律用 **GiB / KiB**（$1\ \text{GiB}=2^{30}$ 字节），因为显存的一切数字都是 2 的幂；算**带宽**才用十进制 GB/TB（3.35 TB/s 是十进制）。两套差 7%，**混着用是这个主题最常见的错账来源**。厂商报告里的权重占用（1009 GB、517 GB）是**十进制 GB**，本章引用时会标出来。

### 代入真实数字

**用一个 openPangu-2.0-Pro 规模的假想 MHA 模型**（✅ 报告披露：$N=50$ 层、$d_{\text{model}}=5120$、64 个注意力头，所以 $d_h = 5120/64 = 80$；这里**假设它是 MHA**，即 $H_{kv}=64$），BF16：

```
每 token、每层    ：2 × 64 × 80 × 2 字节 = 20,480 字节 = 20 KiB
每 token、全部 50 层：20 KiB × 50 = 1,024,000 字节 = 1000 KiB      ★ 记住这个数
```

**1000 KiB 换成别的单位**：$= 1.024$ MB（十进制）$\approx 0.98$ MiB。后文一律简称「**约 1 MB / token**」。

**★ 随序列长度怎么涨**（batch = 1，一张 H100 的可用显存是 79.6 GiB）：

| 序列长度 $L$ | KV cache | 占一张 H100 | 只装 cache 要几张卡 |
|---|---|---|---|
| 8K（8192） | 7.81 GiB | 9.8% | 不到 1 张 |
| 32K | 31.25 GiB | 39% | 不到 1 张 |
| **128K** | **125 GiB** | ★ **157%** | **2 张** |
| **512K** | **500 GiB** | 628% | **7 张** |
| **1M** | **1000 GiB** | 1256% | **13 张** |

> 🔑 **记住这个量级：一个 500B 级模型，MHA 下大约 1 MB / token。** 于是 128K 上下文的 KV cache 就已经**装不进一张卡**了。
>
> 而这还只是 **batch = 1**。真实服务要同时服务几十上百个用户，而 KV cache 是**随用户数线性增长**的：
> ```
>     B = 32，L = 128K：125 GiB × 32 = 4000 GiB ≈ 3.9 TiB    ← 完全不可能
> ```

### 对比：模型权重本身多大

**openPangu-2.0-Pro 是 505B 总参数**，权重占用按参数量直接乘就行：

| | 算式 | 结果 | 报告实测 |
|---|---|---|---|
| **BF16 权重** | $505\times10^9\times2$ 字节 | 1010 GB（十进制） | ✅ **1009 GB** |
| **W8A8 权重** | $505\times10^9\times1$ 字节 | 约 505 GB | ✅ **517 GB**（压缩 1.95×） |

**把权重和 cache 画在同一把尺子上**（⚠️ 为了可比，全部换算成 GiB；KV 那两行是上面那个假想 MHA 的推演值）：

| 项目 | 大小（GiB） | 相对长度 |
|---|---|---|
| 模型权重 BF16（✅ 报告 1009 GB） | 940 GiB | `####################` |
| 模型权重 W8A8（✅ 报告 517 GB） | 482 GiB | `##########` |
| KV cache @ 128K（⚠️ 假想 MHA） | 125 GiB | `###` |
| KV cache @ 512K（⚠️ 假想 MHA） | 500 GiB | `###########` |

> 🔑 **这就是问题的全貌**：短上下文时 KV cache 可以忽略，**长上下文时它会追上甚至超过模型权重本身**。而权重是**固定的一份**，KV cache 却**随用户数线性增长**。
>
> ✅ **对照真实数据**：DeepSeek-V4 报告称在 **1M 上下文下，KV cache 只占约 2%**。这不是 MHA 能做到的——是 [07 章](07-MHA到MLA.md) 的低秩压缩加上 [08 章](08-高效注意力.md) 的稀疏化一起做到的。

## 6.4 Roofline：为什么"省显存"就等于"提速"

这一节是本章的技术核心。**它解释了为什么所有厂商都在省 KV cache，而不是省计算。**

### 算术强度（arithmetic intensity）

> 📌 **算术强度**（arithmetic intensity，也叫计算访存比）—— 一段计算里「做了多少次浮点运算」除以「从显存搬了多少字节」，单位 FLOP/byte。它衡量的是**这段计算有多"值得"搬数据**。

$$I = \frac{\text{做了多少次浮点运算 (FLOPs)}}{\text{从显存搬了多少字节 (bytes)}}$$

**硬件有一个"屋脊点"（ridge point，也译脊点）**，它只由硬件决定，和跑什么模型无关：

$$I_{\text{ridge}} = \frac{\text{峰值算力 (FLOP/s)}}{\text{显存带宽 (byte/s)}}$$

以 **H100 SXM5** 为例：

| 项目 | 数值 |
|---|---|
| BF16 **稠密**峰值算力 | **989 TFLOP/s** |
| HBM3 容量 / 带宽 | 80 GB（实际可用 79.6 GiB）/ **3.35 TB/s** |
| **屋脊点** | $989 / 3.35 \approx$ ★ **295 FLOP/byte** |

> ⚠️ **一个到处流传的错数**：H100 的 BF16 峰值**不是 1979 TFLOPS**。1979 是 **2:4 结构化稀疏**下的值（要求权重里每 4 个数有 2 个是 0），**稠密只有 989**。用 1979 去算屋脊点会得到 591，把后面所有的判断全部带偏一倍。看到任何算力数字，先问：稠密还是稀疏？

```
       性能 (FLOP/s)
        ^
  989 --|--------+------------------------------   <- 算力受限区（compute-bound）
        |       /|                                     性能已贴在天花板上
        |      / |                                     再加带宽也没用
        |     /  |
        |    /   |     斜率 = 显存带宽（3.35 TB/s）
        |   /    |
        |  /     |
        | /      |     <- 访存受限区（memory-bound）
      0 +--------+------------------------------>  算术强度 I（FLOP/byte）
                 |
            I_ridge = 989 / 3.35 ≈ 295 FLOP/byte
```

> **要跑满 H100 的算力，每从显存读 1 个字节，必须做 295 次浮点运算。** 达不到，性能就被那条斜线按住了——这时算力再强也没用，**你买的是带宽，不是 TFLOPS**。
>
> 📌 屋顶线模型的完整用法（怎么测算术强度、它有哪三个盲区、昇腾上屋脊点是多少）在 [大模型算子开发 02 章](../../大模型算子开发/02-屋顶线与性能剖析.md)。

### Decode 的算术强度是多少

对一个权重矩阵 $W\in\mathbb{R}^{m\times n}$，BF16 存储，batch 里有 $B$ 个 token 要过它：

| | 量 | 和 batch $B$ 的关系 |
|---|---|---|
| **搬运** | $m\times n\times 2$ 字节 | ❌ **无关**——矩阵只搬一次，来几个 token 都一样 |
| **计算** | 每个 token 做 $2mn$ FLOPs，共 $B$ 个 | ✅ **正比** |

$$I = \frac{2mn\times B}{2mn} = B$$

$$\boxed{I_{\text{decode}} \approx B\ \text{（batch size）}}$$

**这个结论简单到有点可疑，但它就是对的**：权重只搬一次，来几个 token 就摊薄几倍。

| batch $B$ | 算术强度 $I$ | 对比 $I_{\text{ridge}}=295$ | 算力利用率 |
|---|---|---|---|
| **1** | 1 | 差 295 倍 | ★ **约 0.3%** |
| 8 | 8 | 差 37 倍 | 约 2.7% |
| 32 | 32 | 差 9 倍 | 约 11% |
| 128 | 128 | 差 2.3 倍 | 约 43% |
| **295** | 295 | ★ 刚好相等 | **100%（跑满）** |

```
★ 但 B = 295 意味着 KV cache 也要 ×295。
  回到 §6.3 那张表：L = 8K 时单用户 7.81 GiB，×295 = 2304 GiB。
  ⟹ 显存根本放不下，batch 被【KV cache 的体积】卡死了。
```

> 🔑 **这就是完整的因果链，请仔细看**：
>
> ```
> ① decode 每次只处理 1 个 token   →  算术强度 ≈ batch size
> ② 要跑满算力，需要 batch ≈ 295
> ③ 但 batch 越大，KV cache 越大（线性）
> ④ 显存被 KV cache 占满  →  batch 开不大  →  算力浪费 99%
>              |
>              v
> ⑤ ★★ 省下 KV cache = 能开更大 batch = 直接换成吞吐量 ★★
> ```
>
> **"省显存"和"提速"在 decode 阶段是【同一件事】。这就是五家全都在死磕 KV cache 的原因。**

### 换个角度：单次 decode 的时间下界

即使 batch=1，每生成一个 token 也**必须至少把所有激活的权重完整读一遍**——不读完就算不出结果。这给出一个谁都绕不过去的下界：

```
一个「18B 激活参数、W8A8（1 字节/参数）」的模型，权重全放在一张 H100 上：

    每 token 至少搬运 18 GB
    18 GB ÷ 3.35 TB/s ≈ ★ 5.4 ms     ← 延迟下界，再怎么优化也快不过它

    ⟹ 这也解释了 MoE 为什么流行：总参数 505B 但只激活 18B，
       搬运量按【激活参数】算，不按总参数算（见 10 章 MoE）。
```

> ✅ **openPangu-2.0-Pro 报告实测 TPOT = 9.53 ms @ 8K、9.55 ms @ 128K**（超低延迟档）。
>
> ⚠️ **但不要拿上面那个 5.4 ms 当它的下界——两个口径都对不上**：
> ```
> ① 它跑在昇腾 NPU 上，不是 H100。910B3 的 HBM 带宽约 1.6 TB/s
>    （⚠️ 推断值，见 大模型算子开发 12 章 §12.4.1），只有 H100 的一半。
> ② 更关键：它是 MoE，报告的部署是 2P1D 八节点、MoE 走 EP（专家并行）。
>    那 18 GB 激活权重被【摊到几十张卡上并行读】，每卡只读自己那一份。
>    ⟹ 「18 GB ÷ 单卡带宽」既不是它的下界也不是上界，这个除法做不成。
> ```
> 📌 **那这两个数还能读出什么？** 能安全读出的只有一条，而且恰好是最重要的那条 ↓

> 🔑 **注意 openPangu 那两个数字的【差值】**：**8K 和 128K 的 TPOT 几乎一样**（9.53 vs 9.55 ms，只差 0.02 ms）。
> 差值不受带宽口径和并行方式影响——**它说明 KV cache 的读取开销在 128K 下依然没有成为主导项**。这正是 MLA + SWA + DSA 组合起来的效果（[07](07-MHA到MLA.md) / [08](08-高效注意力.md) 章）。
>
> **反过来说**：如果这个模型用的是朴素 MHA，按 §6.3 的表，128K 时每步要多读 125 GiB 的 cache，TPOT 会明显高于 8K。**"TPOT 与上下文长度脱钩"本身就是注意力改造成功的标志。**
>
> 📌 想看"KV 读取什么时候会反超权重读取"的逐行表格（Llama-3-8B，从 1.8% 一路到 70%），在 [推理框架 §7.6](../../推理框架/推理优化入门/07-注意力变体MQA-GQA-MLA.md)。

## 6.5 四个可以下手的方向

现在你有了完整的问题定义。**公式里只有四个乘数可以动，五家的所有方案全部落在这四格里**：

```
    KV cache 字节数 = 2 × N × H_kv × d_h × L × B × bytes

    ① 动 N            —— 有几层要存
    ② 动 H_kv × d_h   —— 每层每 token 存多宽
    ③ 动 L × B        —— 一共要存几个 token
    ④ 动 bytes        —— 每个数占几字节
```

| 方向 | 怎么做 | 代表技术 | 在哪章 |
|---|---|---|---|
| **② 每层存多宽** | 让多个 Q 头共用一份 KV，或把 KV 压成低维潜向量 | MQA / GQA / **MLA** | ★ **[07 章](07-MHA到MLA.md)** |
| **③ 存几个 token** | 只看最近的 / 只看最相关的 / 打包成摘要 / 根本不存 | 滑动窗口、稀疏选择、压缩、线性注意力 | ★ **[08 章](08-高效注意力.md)** |
| **④ 每个几字节** | KV cache 量化 | BF16 → FP8 → INT4 | **[14 章 §14.10](14-量化.md)** |
| **① 有几层** | 只在部分层保留全量 KV，其余层跨层共享或用廉价注意力 | GLM 的 IndexShare、K3 的 KDA/MLA 3:1 交错 | [08 章](08-高效注意力.md) |

> 📌 **注意 ③ 里的 $B$（batch）是个例外**：它不是"架构可以改小"的东西，而是**服务端想开大**的东西。所以 ①②④ 和"改 $L$"是**架构侧**的活（本教程），"把省下来的显存换成更大 $B$"是**推理服务侧**的活（[推理框架 §2.3~2.5](../../推理框架/推理优化入门/02-KV-Cache与显存账.md) 逐行扣了一张 H100 的显存账，并给出三个能改变这笔账的旋钮）。

**这就是 06 → 07 → 08 三章的分工，也是 [../模型技术对比.md](../模型技术对比.md) §3.1 那张表的组织逻辑。**

## 6.6 Prefill 侧的账：TTFT（首字延迟）

Prefill 是**算力受限**的，所以它的账和 decode 完全不同——**这里要数的是 FLOPs，不是字节。**

### 先把注意力的 FLOPs 写准

对序列长 $s$、$d = d_{\text{model}}$ 的**一层**，注意力里有两个跟 $s^2$ 相关的矩阵乘：

$$\underbrace{QK^\top}_{2s^2d} \;+\; \underbrace{PV}_{2s^2d} \;=\; 4s^2d \qquad\xrightarrow{\ \text{因果掩码只算下三角}\ }\qquad \approx 2s^2d$$

> ⚠️ **那个"约一半"极容易被漏掉，是估算长序列 prefill 时最常见的 2 倍误差来源。** 因果掩码下第 $i$ 个 query 只和 $j\le i$ 的 key 配对，配对总数是 $s^2/2$ 而不是 $s^2$。
> （$QK^\top$ 是 `[s,d]×[d,s]`，$PV$ 是 `[s,s]×[s,d]`，两者都是 $s^2 d$ 次乘加 = $2s^2d$ FLOPs。跨头求和已经包含在 $d = H\cdot d_h$ 里了。）

**其余部分和 $s$ 只是线性关系**：四个投影 $QKVO$ 合计 $8sd^2$，FFN 约 $6\,s\,d\,d_{ff}$。所以每层每 token 的非注意力项是常数 $8d^2 + 6d\,d_{ff}$——代入 $d=5120$、$d_{ff}=16128$（openPangu 的激活 FFN 宽度）得 **约 $7.05\times10^8$ FLOPs**。

### 交叉点在哪

| 序列长度 $s$ | 注意力项（每 token 每层） | 占一层总 FLOPs 的比例 |
|---|---|---|
| **4K** | $2sd = 4.2\times10^7$ | 约 **6%**，可以忽略 |
| 32K | $3.4\times10^8$ | 约 **32%** |
| **128K** | $1.34\times10^9$ | 约 **66%**，已经过半 |
| **1M** | $1.07\times10^{10}$ | ★ 约 **94%**，完全主导 |

```
    ★ 而且它是【平方】的：128K → 1M 是 8 倍长度，这一项涨 64 倍。
      这就是为什么"把上下文从 128K 拉到 1M"不是把机器多开 8 台就能解决的事。
```

> ⚠️ **和 [01 章 §1.5](01-鸟瞰全景.md) 的口径差异**：01 章给的是 **12% / 97%**，因为它用的是**未计因果掩码**的 $4sd$。两套数字的结论完全一样（长序列时注意力唯一主导），但**绝对值差一倍**——做容量规划、估 TTFT 的时候，记得那约一半的折扣。

```
✅ openPangu 报告实测：TTFT = 3.0 s @ 128K 输入、单 batch
   （Flash 版是 2.6 s）
   → 读 12.8 万 token 要等 3 秒才开始出字，这 3 秒【全部花在 Prefill 上】
```

> 🔑 **两个阶段要用完全不同的手段优化**：
> ```
> Prefill 慢  ->  是【算力】问题  ->  要减少 FLOPs   ->  稀疏注意力、滑窗、压缩
> Decode 慢   ->  是【访存】问题  ->  要减少字节数   ->  压缩 KV cache、量化
>
> ★ 稀疏注意力是少数【两边都帮】的技术：既少算，又少存
>   这就是为什么 DSA / MSA / SWA 这类技术是五家的主流选择（[08 章](08-高效注意力.md)）
> ```
>
> 📌 **还有一类手段两边都不改数学，只改 kernel 怎么写**：FlashAttention 把 $[s,s]$ 那张大表按块吃掉，从不落 HBM——它把注意力的**显存**从 $O(s^2)$ 降到 $O(s)$、把**搬运量**降了一个量级，但 **FLOPs 一个都没少**。三代 kernel 各改了哪一层（在线 softmax、循环顺序、split-Q、Hopper 异步流水），在 [大模型算子开发 04 章](../../大模型算子开发/04-FlashAttention全系.md)。

## 6.7 还有一个方向：一次多吐几个字

**如果 decode 的瓶颈是"每步都要把 18 GB 权重读一遍"，那么——**

```
    读一遍权重，只吐 1 个 token   →  每 token 的搬运成本 = 18 GB
    读一遍权重，吐出 5 个 token   →  每 token 的搬运成本 = 3.6 GB    ★ 5 倍
```

**权重只读一次，能多产出几个 token，就等于直接提速几倍。**

这正是 **MTP**（**M**ulti-**T**oken **P**rediction，多 token 预测）**+ 投机解码**的全部动机，见 [12 章](12-MTP与投机解码.md)。**五家全部上了 MTP，一个不落**，因为它是在不改主模型的前提下最直接的 decode 加速手段。

> ⚠️ **上面那个"5 倍"是理想值**，实际拿不到：投机出来的 5 个候选 token **不一定全被主模型接受**，一旦某个位置被否，它后面的全部作废。真实加速比等于**平均接受长度**——✅ DeepSeek-V3.2 是 **2.55**，GLM-5.2 自己的消融里从 4.56 提到 5.47（见 [12 章](12-MTP与投机解码.md)）。

> 📌 **注意这和"省 KV cache"是两条独立的路，改善的指标都不一样**：
> ```
> 省 KV cache  ->  能开更大 batch  ->  提【吞吐量 TPS】（这块卡每秒总共吐多少字）
> MTP          ->  每次多吐几个字  ->  降【单用户延迟 TPOT】（我这一个人要等多久）
> ```
> ✅ openPangu 报告的 **1727 TPS/NPU** 是**吞吐量**指标，**9.53 ms TPOT** 是**延迟**指标——回到 §6.1 那组定义。

> ⚠️ **而这两个数字不能凑在一起吹**，它们来自报告里**两张不同的表、两个不同的配置**：
>
> | 报告里的档位 | TPOT | Batch | TPS/NPU | 取舍 |
> |---|---|---|---|---|
> | **超低延迟** | **9.53 ms** | 报告未给 | 报告未给 | 牺牲吞吐换延迟 |
> | **低延迟吞吐** | 23.2 ms | 40 | **1727** | 牺牲延迟换吞吐 |
>
> ```
> ★ 同一个模型，batch 调到 40 之后 TPOT 从 9.53 ms 变成 23.2 ms（慢 2.4 倍），
>   换来吞吐量大涨。这就是延迟与吞吐的取舍，也是 §6.1 说它们"互相打架"的实证。
>
> 验算一下这组数是否自洽（⚠️ 我的推算，不是报告写的）：
>     40 ÷ 0.0232 秒 ≈ 1724 tokens/s   ← 和 1727 只差 0.2%
> ⚠️ 但这个吻合要打个问号：报告那一列的表头写的是「per NPU」，
>    而 batch 40 是【整个部署】（2P1D 八节点）的并发数。
>    严格来说这两个数不该直接相除，吻合得这么好可能是巧合。
>    ★ 能确定的是趋势方向，不是这个等式。
> ```

## 6.8 本章小结

```
① Prefill（读输入）是【算力受限】，Decode（吐字）是【访存受限】
   -> decode 时 GPU 算力利用率可能只有 0.3%，99% 的时间在等数据

② KV cache 不是"优化"而是"前提"：它把 O(L²) 的重算换成 O(L) 的读回
   ★ 但换来的是搬运，而搬运量累计同样 ∝ L² —— 长上下文下它会重新变成瓶颈

③ KV cache 字节数 = 2 · N · H_kv · d_h · L · B · bytes
   ⚠️ 那个头数必须是 H_kv（KV 头数），不是 Q 头数
      用 4·d_model 硬套 GQA 模型高估 8 倍，套 MQA 高估 64 倍，套 MLA 高估 25 倍
   500B 级 MHA 模型 ≈ 1 MB / token
   -> 128K 就装不进一张卡，512K 追上模型权重本身，且随用户数线性增长

④ ★ Roofline：decode 的算术强度 ≈ batch size，H100 的屋脊点是 295
   （989 TFLOP/s ÷ 3.35 TB/s；⚠️ 别用 1979，那是 2:4 稀疏值）
   -> KV cache 占满显存 -> batch 开不大 -> 算力浪费 99%
   -> 【省 KV cache 就是直接提吞吐】，这两件事在 decode 阶段是同一件事

⑤ 公式里只有四个乘数可动：层数 / 每层多宽 / 存几个 token / 每个几字节
   -> 分别对应 08 / 07 / 08 / 14 章

⑥ Prefill 慢是 FLOPs 问题（注意力项 ≈ 2s²d，⚠️ 因果掩码下只有一半）
   Decode 慢是字节数问题，两边手段不同
   稀疏注意力是少数【两边都帮】的技术

⑦ 另一条独立的路：MTP —— 权重只读一次，多吐几个字（12 章）
   ⚠️ 实际加速 = 平均接受长度（2.5~5.5），不是候选个数
```
