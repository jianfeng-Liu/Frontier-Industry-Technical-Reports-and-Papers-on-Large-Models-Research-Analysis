## 7.1 问题重述

回忆 [05 章](05-注意力机制.md)的多头注意力：$H$ 个 query 头，每个头有自己的 $K^i, V^i$，都是 $d_h$ 维。

$$\text{每 token 每层要存：}\quad 2\times H_{kv} \times d_h \quad\text{个数}$$

**MHA 的特点是 $H_{kv} = H$，而且通常 $H\cdot d_h = d_{\text{model}}$**，所以 MHA 下这个式子刚好等于 $2\,d_{\text{model}}$：

```
d_model = 5120，BF16：  2 × 5120 × 2 字节 = 20,480 字节 = 20 KiB / token / 层
```

> ⚠️ **但 $2d_{\text{model}}$ 这个简写只对 MHA 成立**，这是 [06 章 §6.3](06-KV-cache.md) 反复强调的那个坑。下面三种方案要动的恰恰是 $H_{kv}$ 和 $d_h$ 这两个符号，**一旦动了，$H_{kv}\cdot d_h$ 就不再等于 $d_{\text{model}}$**，简写式立刻失效。本章往后一律写 $H_{kv}$，不写 $d_{\text{model}}$。

**这一章的四种方案，就是把 $2\times H_{kv}\times d_h$ 变小的四种办法。**

## 7.2 演化的四步

**四步的核心区别只有一句话：几个 query 头去共用一份 KV。** 先看图，再看表。

```
MHA（2017）—— 一对一，谁都不共用
    Q:   q1   q2   q3   q4   q5   q6   q7   q8       8 个 query 头
         |    |    |    |    |    |    |    |
    K:   k1   k2   k3   k4   k5   k6   k7   k8       8 个 KV 头
    V:   v1   v2   v3   v4   v5   v6   v7   v8

GQA（2023）—— 分 4 组，组内共用（图上画的是 GQA-2，每 2 个 q 共享一组）
    Q:   q1   q2   q3   q4   q5   q6   q7   q8
         +--+-+    +--+-+    +--+-+    +--+-+
            |         |         |         |
    K:      k1        k2        k3        k4        4 个 KV 头
    V:      v1        v2        v3        v4

MQA（2019）—— 全部共用一份，最省
    Q:   q1   q2   q3   q4   q5   q6   q7   q8
         +----+----+----+--+-+----+----+----+
                          |
    K:                    k                        1 个 KV 头
    V:                    v

MLA（2024，DeepSeek）—— 不共用，改成"存之前先压缩"
    x（5120 维）
     |
     +--> W^DKV 向下投影 --> c（512 维）   ★ cache 里只放这个
                              |
                              +--> W^UK 向上投影 --> K（各头不同）
                              +--> W^UV 向上投影 --> V（各头不同）
```

**★ 四者并排**（存储倍数按 8 个头、$d_h$ 相同来算）：

| 方案 | $H_{kv}$ | 每 token 每层存多少个数 | 相对 MHA 的存储 | 头的表达多样性 | 一句话 |
|---|---|---|---|---|---|
| **MHA** | 8 | $2\times8\times d_h = 2d$ | ×1（基准） | ★★★★★ 完整 | 最准也最贵 |
| **GQA**（这里画 4 组） | 4 | $2\times4\times d_h = d$ | **×1/2** | ★★★★ 略降 | 开源生态的事实标准 |
| **MQA** | 1 | $2\times1\times d_h = d/4$ | **×1/8** | ★★★ 明显降 | 最省，但掉点 |
| **MLA** | 没有这个概念 | latent 维度（例如 576） | **×1/17.8** | ★★★★★ 完整保留 | ★ 唯一"存得更少、效果不掉"的 |

> 📌 **GQA-n 的 n 是什么**：业界写法不统一，本教程一律用 **"n 个 query 头共享一组 KV"**。所以 MiniMax M3 的 **64 个 q 头 / 4 个 kv 头** 记作 **GQA-16**（64÷4），Llama-3 的 32 q / 8 kv 记作 **GQA-4**。看到别处的 "GQA-8" 要先确认它指的是"8 个组"还是"8 个 q 共享"。

### MQA/GQA 为什么会掉效果

回忆 [05 章 §5.6](05-注意力机制.md)：多头的价值在于**不同的头可以关注不同的模式**。

```
MHA：  头 3 的 K 专门编码"我是主语"，头 17 的 K 专门编码"我是物品"
       -> 每个头有【自己的一套语义空间】

MQA：  所有 8 个头共用同一份 K
       -> 这份 K 必须同时满足所有头的需求
       -> 被迫编码一个"通用"的、模糊的表示
       -> 头之间的【专业化被削弱了】★ 这是掉效果的机制

GQA：  折中，组内共享。组数越多越接近 MHA，组数越少越接近 MQA
```

> ✅ **MiniMax M3 是五家里唯一还在用 GQA 的**：**64 个 query 头 / 4 个 KV 头**（即 GQA-16，16 个 query 共享一组 KV）。
>
> ⚠️ 这不是"落后"。M3 只有 230B 总参 / 10B 激活，走的是**小而快**的路线，而 GQA 的**工程成熟度和算子支持是最好的**——FlashAttention 从 v2 起就原生支持 GQA/MQA（让共享同一份 KV 的多个 Q 头排进同一个线程块，K/V 只搬一次，见 [大模型算子开发 §4.4.5](../../大模型算子开发/04-FlashAttention全系.md)），而 **MLA 需要重写一整套推理核函数**。
>
> 📌 还有一条更硬的工程理由：**GQA 可以给已经训好的 MHA 模型"改装"上去**（uptraining，用少量语料微调），**MLA 不行——它必须从预训练就用**。这解释了为什么开源生态里 GQA 一统天下。这条对比的完整版在 [推理框架 §7.5](../../推理框架/推理优化入门/07-注意力变体MQA-GQA-MLA.md)。

### ★ 四者用同一个配置，把每 token 的 KV 字节数逐个算出来

**这一节是本章的数值核心。** 上面那些"×1/8"、"×1/17.8"都是相对倍数，**相对倍数最容易骗人**——真正要做判断，得看绝对字节。

**固定一个配置**（✅ 取 openPangu-2.0-Pro 报告披露的真实规模，这样各行之间才真的可比）：

| 配置项 | 取值 | 来源 |
|---|---|---|
| 层数 $N$ | **50** | ✅ 报告 |
| query 头数 $H$ | **64** | ✅ 报告 |
| $d_h$ = head_dim | **80**（$= 5120/64$） | 推算 |
| $d_{\text{model}}$ | **5120** | ✅ 报告 |
| MLA 的 latent 维 + 解耦 RoPE 维 | **512 + 64 = 576** | ✅ 报告 |
| 精度 | BF16 = **2 字节** | ✅ 报告 |
| 上下文 | 512K = 524,288 token，batch = 1 | ✅ 报告的上下文上限 |

套通式 `每 token 每层 = 2 × H_kv × d_h × 字节数`（MLA 那行是例外，下面单独解释）：

| 方案 | $H_{kv}$ | 每 token **每层** | 每 token **全部 50 层** | 相对 MHA | **512K 上下文的 KV cache** | 装得进一张 H100（79.6 GiB）吗 |
|---|---|---|---|---|---|---|
| **MHA** | 64 | $2{\times}64{\times}80{\times}2$ = **20 KiB** | **1000 KiB** | ×1（基准） | ★ **500 GiB** | ❌ 要 7 张卡只放 cache |
| **GQA-8**（8 个 q 共享） | 8 | $2{\times}8{\times}80{\times}2$ = **2.5 KiB** | **125 KiB** | **8×** | **62.5 GiB** | ⚠️ 勉强，但卡里还得放权重 |
| **GQA-16**（M3 的比例） | 4 | $2{\times}4{\times}80{\times}2$ = **1.25 KiB** | **62.5 KiB** | **16×** | **31.25 GiB** | ✅ |
| **MQA** | 1 | $2{\times}1{\times}80{\times}2$ = **0.3125 KiB** | **15.625 KiB** | **64×** | **7.81 GiB** | ✅ 绰绰有余 |
| **MLA-576** | 不适用 | $(512{+}64){\times}2$ = **1.125 KiB** | **56.25 KiB** | ★ **17.8×** | ★ **28.125 GiB** | ✅ |

> ⚠️ **口径声明**：**配置来自 openPangu 报告，但只有 MHA→MLA 那一行的 MLA 数字是它的真实方案**——GQA / MQA / MHA 那三行是**把同一个规模换成那些方案会怎样**的推演，不是任何一家的实际配置。用途是建立"同规模下差多少"的量级感。

**★ 三个值得停下来看的地方**：

```
① MQA 比 MLA 还省（15.6 KiB vs 56.25 KiB，省 3.6 倍）
   ⟹ 所以 MLA 不是"最省的"，它是【省得够多 + 效果不掉】的那个。
      如果只看字节数，MQA 才是冠军 —— 但没人敢用，因为它掉点。

② GQA-16 的 62.5 KiB 和 MLA-576 的 56.25 KiB 几乎一样
   ⟹ ★ 这解释了 MiniMax M3 为什么"敢"不上 MLA：
      在这个规模上，GQA-16 已经把 KV 压到和 MLA 同一个量级了，
      而它换来的是成熟得多的算子生态。M3 换的是【工程确定性】。

③ MHA 的 500 GiB 和 openPangu 权重的 940 GiB（BF16）是同一个量级
   ⟹ 回到 06 章 §6.3：长上下文时 KV cache 会追上模型权重本身。
```

### ⚠️⚠️ MLA 那一行为什么不乘 2、也没有头数——以及一个必须避开的反向错误

**先说式子为什么长这样**：

```
    MHA / GQA / MQA：要存 K 和 V 【两份】       ⟹ 式子前面那个 × 2
                     KV 按头切开，每头一套      ⟹ 式子里有 H_kv

    MLA：           只存【一个】潜向量 c_KV     ⟹ 不乘 2
                    （K 和 V 都从同一个 c_KV 解压出来）
                    c_KV 【不分头】，全部头共用 ⟹ 没有 H_kv 这一项
                    再加一个 64 维的解耦 RoPE 分量（§7.5 会讲它为什么必须单列）
```

> ⚠️⚠️ **这里有一个极高频的反向错误，本仓库在 [大模型算子开发 §11.7.1](../../大模型算子开发/11-训推一致性算子层.md) 查出过一次，务必躲开**：
>
> ```
> ❌ 错误写法：「矩阵吸收把上投影合并进 K 投影，得到 W_K_eff = W^DKV · W^UK，
>              于是 K = x · W_K_eff 直接算出来，不用存 c_KV 了」
>
> ★ 这是【反的】。那样做会得到【全尺寸的 K】（5120 维），
>   KV cache 一个字节都没压缩 —— MLA 就白做了，上面那 17.8× 全部归零。
>
> ✅ 正确：吸收式【照样把 c_KV 缓存起来】（这正是 MLA 省显存的全部来源）。
>   被"吸收"的是【上投影矩阵 W^UK / W^UV】，
>   吸收的方向是【吸到 Q 侧和输出投影侧】，不是吸到 K 侧。
> ```
>
> **判断口诀：MLA 的 cache 里放的永远是 576 维的 `c_KV` 加 `k^R`，不是 K 和 V。** 任何说法只要推出"不用存 c_KV"，就一定错了。§7.4 会把正确的推导走一遍。

> 📌 **换一个真实模型验一下这个式子**：DeepSeek-V3（⚠️ 按公开配置推算：**61 层**——前 3 层稠密 FFN + 58 层 MoE，latent 512，解耦 RoPE 64，$d_{\text{model}}=7168$，BF16）：
> ```
>     每 token = 61 层 × (512 + 64) × 2 字节 = 70,272 字节 = ★ 68.6 KiB
>
>     对照：Llama-3-8B（GQA-4）是 128 KiB / token。
>     ⟹ ★★ 一个 671B 的模型，每 token 的 KV cache 比一个 8B 模型还小一半。
> ```
> 这句话值得停三秒——它解释了 DeepSeek 为什么敢把上下文开到 128K 以上。这条账的推理服务侧版本（以及它怎么反过来改变了并行策略）在 [推理框架 §7.5 / §7.7](../../推理框架/推理优化入门/07-注意力变体MQA-GQA-MLA.md)。

## 7.3 MLA：核心思路是低秩压缩

### 直觉

**观察**：MHA 存的 $2d$ 个数里有大量冗余——$K$ 和 $V$ 都是从同一个 $x$（$d$ 维）线性投影出来的，**信息量的上限就是 $d$ 维**，却存了 $2d$。

**那就不存 $K$ 和 $V$，存一个能重建出它们的【压缩表示】。**

$$c^{KV} = W^{DKV}x \in \mathbb{R}^{512},\qquad K = W^{UK}c^{KV},\qquad V = W^{UV}c^{KV}$$

> 📌 **三个上标是缩写，第一次出现给全称**：**DKV** = **D**own-projection for **KV**（KV 的向下投影，把 5120 压到 512）；**UK** / **UV** = **U**p-projection for **K** / **V**（向上投影，把 512 还原回各头的 K / V）。

### 为什么这不是"有损压缩导致效果下降"

**关键在于：$W^{UK}$ 和 $W^{UV}$ 是【可学习的】，而且训练时它们和 $W^{DKV}$ 一起学。**

```
❌ 错误理解：先有一个完整的 K，然后把它压缩，丢失了信息
✅ 正确理解：K 从来就【不是】独立存在的。
             整个 x -> c -> K 的通路是端到端学出来的，
             模型自己决定"什么信息值得留在这 512 维里"

    这等价于给 W_K 这个矩阵加了一个【低秩约束】：
        W_K = W^UK · W^DKV      rank ≤ 512

    而实践发现：注意力的 K/V 投影矩阵【本来就近似低秩】
    -> 这个约束几乎没有代价
```

> 📌 **"低秩"是什么意思**（术语，第一次出现）：一个矩阵的**秩**（rank）是它"真正独立的方向"有多少个。$5120\times5120$ 的矩阵最多有 5120 个独立方向，但如果实际上只有 512 个方向承载了几乎全部信息，剩下 4608 个方向的贡献接近 0，就说它**近似低秩**。这时把它写成两个瘦矩阵相乘（$5120\times512$ 乘 $512\times5120$）几乎不丢东西，**而参数量和中间结果都小了 10 倍**。

> 🔑 **这就是 MLA 优于 MQA/GQA 的机制性理由**：
> ```
> MQA/GQA：削减【头的数量】 -> 直接损失表达的多样性，不可恢复
> MLA：    削减【秩】       -> 只要真实秩本来就低，就几乎没有损失
>
> 而且 MLA 解压出来的每个头【依然是不同的】（各头有各自的 W^UK 分块）
> -> ★ 头的专业化被完整保留了，这是它和 MQA/GQA 的本质分野
> ```

## 7.4 矩阵吸收：MLA 真正的杀手锏（以及它到底吸了什么）

上面有个明显的问题：**每次用都要解压，那不是白省了吗？**

```
    存 512 维，但每次计算前要展开成 5120 维
    -> 显存省了，计算量没省，还多了解压的开销
```

**答案：解码时根本不用解压。**

### 推导

注意力分数是 $q^\top k$。代入 MLA 的定义（$q = W^{UQ}c^Q$，$k = W^{UK}c^{KV}$）：

$$q^\top k = \left(W^{UQ}c^{Q}\right)^\top\left(W^{UK}c^{KV}\right) = c^{Q\top}\underbrace{\left(W^{UQ\top}W^{UK}\right)}_{\text{★ 这一坨与输入无关}}c^{KV}$$

$$\boxed{\ q^\top k = c^{Q\top}\,\widetilde{W}\,c^{KV},\qquad \widetilde{W} = W^{UQ\top}W^{UK}\ \text{（训练完就固定，可在加载时预先算好）}\ }$$

```
    ★★★ 全程在【512 维的压缩空间】里做内积，从来没有展开到 5120 维 ★★★

    W^UQᵀ W^UK  在模型加载时算一次，融进权重里
    -> cache 里存的还是 512 维的 c_KV，一个字节都没多存
```

**输出侧同理**：$o = \sum_j A_j v_j = \sum_j A_j W^{UV}c_j^{KV} = W^{UV}\left(\sum_j A_j c_j^{KV}\right)$，所以 $W^{UV}$ 可以吸收进后面的输出投影 $W_O$。

> 🔑 **这就是"矩阵吸收"（matrix absorption）。把它吸的方向记清楚**：
> ```
>   W^UK  ->  吸到【Q 侧】     （先把 q 变成 512 维，再和 c_KV 点积）
>   W^UV  ->  吸到【输出侧】   （先在 512 维里加权求和，最后再一次性上投影）
>
>   ★★ cache 里躺着的永远是 c_KV（512 维）+ k^R（64 维）。
>      吸收【不改变 cache 里存什么】，只改变"乘法按什么顺序做"。
> ```
> ⚠️ 再强调一次 §7.2 那个反向错误：**说成"吸收之后 K 直接算出来、不用存 c_KV"就全错了**——那样 cache 里躺的是 5120 维的 K，压缩率归零。

### ⚠️ 但"吸收之后计算量也变小了"这句话只有一半对

**这是本章第二个高频错误。** 吸收式确实让 decode 快得多，**但它让注意力本身的 FLOPs 变大了 4 倍**——赚的是别的地方。

```
★ 吸收式把注意力的 head_dim 从 128 变成了 512（潜向量的维度）
   -> 分数矩阵乘的 FLOPs 直接 ×4
★ 但它省掉了一件更贵的事：不用把 L 个位置的 K、V 全部物化出来
   -> 省掉的那一项 ∝ L × 512 × (头数 × head_dim)，在长上下文下大得多
```

**把两条路径的账算出来**（⚠️ 我的推演，配置用 DeepSeek-V3 公开的 MLA 维度：$d_{\text{model}}=7168$、128 个头、head_dim 128、latent 512，只看**一层**）：

| 场景 | 路径 | 主要开销 | 每层 FLOPs | 谁赢 |
|---|---|---|---|---|
| **Decode**（1 个 query，$L$ = 128K） | 非吸收式 | 每步把 128K 个位置的 K、V 全物化一遍 | **约 4.4 TFLOPs** | — |
| | **吸收式** | 只对 1 个 token 做 $q\,W^{UK\top}$，然后在 512 维里点积 | ★ **约 34 GFLOPs** | ★ **吸收式快约 128×** |
| **Prefill**（$S = L$ = 4K） | **非吸收式** | 物化 K、V 一次，被 4096 个 query 摊薄 | ★ **约 1.24 TFLOPs** | ★ **非吸收式快约 3.6×** |
| | 吸收式 | head_dim 128 → 512，注意力 FLOPs ×4，而且没人帮它摊薄 | 约 4.47 TFLOPs | — |

> 🔑 **所以 MLA 在训练/prefill 和 decode 走的是【两条不同的 kernel 路径】**：
> ```
>   训练 / Prefill  ->  非吸收式（Non-Absorptive）：把 K、V 真的算出来，形态像 MHA
>   Decode          ->  吸收式（Absorptive）  ：在 512 维潜空间里算，形态像 MQA
> ```
> ✅ **这不是推测，是报告原文**：openPangu 报告写的是 *"MLA switching between Absorptive (MQA, decode) and Non-Absorptive (MHA, training/prefill) modes"*（见 [../openPangu-2.0-Pro.md](../openPangu-2.0-Pro.md) §十「训推不一致解剖」）。
>
> ⚠️ **这件事有一个不明显的代价**：同一份权重走两条不同顺序的矩阵乘，**浮点加法不满足结合律**，两条路会算出**略微不同**的数（量级约 1–2 ULP / 层）。单层看不出来，几十层累起来就进了可观测区间，在强化学习里会被放大成训练崩掉。这是 MLA **训推不一致的根源，而且它是"设计出来的"**——完整分析见 [大模型算子开发 §11.7.1](../../大模型算子开发/11-训推一致性算子层.md)。

> ★ **另外记住吸收式的一个副产品，它会在 [08 章](08-高效注意力.md) 变得极其重要**：
> ```
>   吸收式下，全部 128 个头读的是【同一份 512 维 c_KV】
>   -> 等价于 MQA 的访存形态
>   -> 做稀疏选择时，一次 gather（按下标去显存里抓 KV）就服务了全部头 ★
> ```
> 这是 DSA（DeepSeek Sparse Attention）敢用最激进的 **token 级 top-k** 的底层原因，见 [08 章 §8.3](08-高效注意力.md)。

> 🔑 **三者的最终对比**：
> ```
> MQA/GQA：省了存储，注意力的计算量【不变】
> MLA：    ★ decode 时存储和计算【同时】变小
>          ⚠️ 但 prefill 时要换另一条路径，而且 MLA 的参数量比 MHA 略多
>            （多了 W^DKV / W^UK / W^UV 三组矩阵）
> ```
> **"decode 大幅变快 + 效果不掉"这个组合，是 MLA 成为主流的真正原因。**

## 7.5 ⚠️ RoPE 和 MLA 的天然冲突

**这是很多人讲不清、但极其关键的一点。理解了它，才能理解 DeepSeek 为什么要在 cache 里多放那 64 维。**

### 冲突在哪

[11 章](11-位置编码RoPE.md)会详讲 **RoPE**（**Ro**tary **P**osition **E**mbedding，旋转位置编码），这里只需要一个性质：**RoPE 是在 $q$ 和 $k$ 上各乘一个依赖位置的旋转矩阵**：

$$q_m \leftarrow R_m q_m,\qquad k_n \leftarrow R_n k_n$$

现在把 RoPE 加进 §7.4 的推导：

$$q_m^\top k_n = \left(R_m W^{UQ}c^{Q}_m\right)^\top\left(R_n W^{UK}c^{KV}_n\right) = c_m^{Q\top}\,W^{UQ\top}\underbrace{R_m^\top R_n}_{\text{★ 依赖 } m, n}W^{UK}\,c_n^{KV}$$

```
    ★ 问题来了：R_mᵀ R_n = R_{n−m}，它【夹在两个上投影矩阵中间】，
      而且依赖具体的位置对 (m, n)。

    -> W^UQᵀ · R_{n−m} · W^UK 无法预先算好，因为 (n−m) 每对位置都不同
    -> ★★ 矩阵吸收失效了 ★★
    -> 只能真的把 c 解压成全尺寸、加 RoPE、再算内积
    -> 于是 decode 又变回上面那个"4.4 TFLOPs / 层"的非吸收式
    -> MLA 的全部速度优势消失（显存还是省的，速度不省了）
```

> 🔑 **一句话说清冲突**：
> **矩阵吸收要求"$W^{UQ\top}W^{UK}$ 是一个常数矩阵"，而 RoPE 恰好在这两者之间插入了一个"随位置变化"的矩阵。二者不可兼得。**

### 解法：Decoupled RoPE（解耦 RoPE）

**DeepSeek 的方案：把 K 拆成两部分——一部分不加 RoPE（可吸收），一部分专门承载位置信息（不可吸收，但做得很小）。**

$$k = \Big[\ \underbrace{W^{UK}c^{KV}}_{\text{压缩部分，无 RoPE，可吸收}}\ ;\ \underbrace{\text{RoPE}(W^{KR}x)}_{\text{解耦部分，有 RoPE，直接存}}\ \Big]$$

**于是分数变成两项相加**：

$$q^\top k = \underbrace{c^{Q\top}\widetilde{W}c^{KV}}_{\text{在 512 维压缩空间算，吸收生效}} \;+\; \underbrace{q^{R\top}k^{R}}_{\text{在 64 维小空间算，带位置信息}}$$

```
    ★ 为什么这样就成了：
      把"不能吸收"的那部分【隔离】到一个独立的小通道里，
      让它自己算自己的内积，不去污染可以吸收的那条大通道。

      代价 = cache 里要多存那 64 维（因为它带了 RoPE，没法从 c_KV 重建）
      收益 = 主通道的矩阵吸收完好无损

    ⟹ 这是一个非常典型的"把麻烦隔离而不是消灭"的工程设计。
```

### ✅ openPangu-2.0-Pro 的真实配置

| cache 里放什么 | 怎么算出来的 | 维度 | 加 RoPE 吗 | 能吸收吗 |
|---|---|---|---|---|
| $c^{KV}$ | $W^{DKV}\cdot x$ | **512** | ❌ 不加 | ✅ 能 |
| $k^{R}$ | $\text{RoPE}(W^{KR}\cdot x)$ | **64** | ✅ 加 | ❌ 不能，直接存 |
| **合计入 cache** | — | ★ **576** | — | — |

**注意 $k^R$ 只有 64 维，而且它是【所有头共享的】**（像 MQA 那样）——因为位置信息本身不需要每个头各有一套。**如果它按头存**（64 个头 × 64 维），cache 立刻从 576 涨到 $512 + 4096 = 4608$ 维，压缩率从 17.8× 掉到 2.2×，MLA 基本白做。**"共享"这个细节是 decoupled RoPE 能成立的前提，不是可选项。**

### 省了多少

§7.2 那张大表已经算过了，这里只把关键那一行拎出来，并加上一个"每层能省多少"的直观量：

| | 每 token 每层入 cache | 每 token 全 50 层 | 512K 上下文 | 相对 MHA |
|---|---|---|---|---|
| MHA（$d$=5120） | $2\times5120$ = 10240 个数 = **20 KiB** | 1000 KiB | **500 GiB** | ×1 |
| **MLA-576** | $512+64$ = **576 个数 = 1.125 KiB** | **56.25 KiB** | ★ **28.125 GiB** | ★ **压缩 17.8×** |
| | | | **省下 472 GiB** | |

> 🔑 **这就是 [06 章](06-KV-cache.md) 那个"约 1 MB / token"变成"56 KiB / token"的过程。**
> 而再结合 [08 章](08-高效注意力.md) 的稀疏化（不是每个 token 都要看），才有了 DeepSeek-V4 报告的"**1M 上下文下 KV cache 仅约 2%**"。
>
> ⚠️ **注意这两步是【乘】起来的，不是加起来的**：MLA 砍的是"每个 token 存多宽"（特征维度方向），稀疏砍的是"一共看多少个 token"（序列长度方向），两个方向正交。这条正交性是 [08 章 §8.3](08-高效注意力.md) 的起点。

## 7.7 numpy 走一遍

**把三件事写成能跑的代码**：MHA 的 cache 存什么、MLA 的 cache 存什么、吸收之后分数怎么算。

```python
import numpy as np

# ---------- 标准 MHA 的 KV cache ----------
class MHACache:
    """每步 append 一个 [H, d_h] 的 K 和一个 [H, d_h] 的 V。"""
    def __init__(self):
        self.K, self.V = [], []
    def step(self, x, W_K, W_V):
        self.K.append(x @ W_K)          # 存 H*d_h 个数
        self.V.append(x @ W_V)          # 再存 H*d_h 个数
        # 本例配置下：2 × 64 × 80 = 10240 个数 / token / 层

# ---------- MLA 的 KV cache ----------
class MLACache:
    """★ 只存 c_KV（512）和 k^R（64），【不存 K、也不存 V】。"""
    def __init__(self):
        self.C, self.KR = [], []
    def step(self, x, W_DKV, W_KR, pos):
        self.C.append(x @ W_DKV)                 # 512 维，K/V 共用这一份
        self.KR.append(rope(x @ W_KR, pos))      # 64 维，全部头共享
        # ★ 一共只存 576 个数，而不是 10240 个 —— 压缩 17.8×

# ---------- 吸收式（decode 路径）的分数计算 ----------
def mla_scores_absorbed(cQ, qR, cache, W_absorbed, d_h):
    """W_absorbed = W_UQ.T @ W_UK，在模型【加载时】算一次就固定了。"""
    C  = np.stack(cache.C)                  # [L, 512]   ← cache 里真实躺着的东西
    KR = np.stack(cache.KR)                 # [L, 64]
    part1 = cQ @ W_absorbed @ C.T           # ★ 全程 512 维，K 从未被物化
    part2 = qR @ KR.T                       # 64 维的位置项，单独算
    return (part1 + part2) / np.sqrt(d_h)

# ---------- 非吸收式（训练 / prefill 路径）：对照着看差别 ----------
def mla_scores_materialized(Q, cache, W_UK, d_h):
    """★ 这条路把 K 真的算出来 —— 注意它【也是从 cache 里的 C 算的】，
       cache 内容完全一样，区别只在乘法顺序。"""
    C = np.stack(cache.C)                   # [L, 512]
    K = C @ W_UK                            # [L, H*d_h]  ← 物化，开销 ∝ L
    return (Q @ K.T) / np.sqrt(d_h)
```

> 🔑 **对着这两个函数再看一遍 §7.4 的结论**：
> ```
> ① 两条路径【读的是同一个 cache】（都是 cache.C），
>    所以"吸收之后不用存 c_KV"这句话在代码层面根本写不出来。
> ② 区别只在 (cQ @ W_absorbed) @ C.T   与   Q @ (C @ W_UK).T 的括号位置。
>    ★ 数学上相等，浮点上不等 —— 这就是训推不一致的全部来源。
> ```

## 7.8 本章小结

```
① 问题：MHA 每 token 每层要存 2 × H_kv × d_h 个数
   ⚠️ 它等于 2·d_model 只在 MHA 下成立，别拿这个简写去套 GQA/MQA/MLA
   openPangu 规模（50 层、64 头、d_h=80）下是 20 KiB / token / 层

② MQA（全部共用 1 组 KV）/ GQA（分组共用）省存储，但削弱头的专业化 -> 掉效果
   而且【注意力的计算量一点没省】
   ★ 同规模推演（512K 上下文）：MHA 500 GiB、GQA-8 62.5 GiB、
     GQA-16 31.25 GiB、MQA 7.81 GiB、MLA-576 28.125 GiB
   -> MQA 其实最省，但没人敢用；GQA-16 已经和 MLA 同量级，这是 M3 的底气

③ MLA 换了思路：不共享，而是【低秩压缩】
   x -> c_KV(512 维) -> 用的时候解压出 K、V
   因为 W^UK/W^UV 是端到端学出来的，等价于给 W_K 加低秩约束，几乎无损
   ★ 头的专业化被完整保留，这是它区别于 MQA/GQA 的本质

④ ★ 矩阵吸收：qᵀk = c^Qᵀ (W^UQᵀ W^UK) c^KV
   括号里与输入无关，可预先算好 -> decode 全程在 512 维算
   ⚠️⚠️ 吸的是【上投影矩阵】，吸到【Q 侧和输出侧】；
        cache 里【照样存 c_KV】。写成"不用存 c_KV"就把 MLA 作废了
   ⚠️ 而且"计算也变小"只在 decode 成立：吸收让 head_dim 128→512，
      注意力 FLOPs ×4，所以 prefill / 训练走的是【非吸收式】另一条路
      -> 两条路径浮点结果不同，这是 MLA 训推不一致的根源

⑤ ★ RoPE 与 MLA 天然冲突：R_mᵀR_n = R_{n−m} 夹在两个上投影中间，
   随位置变化 -> 吸收失效
   解法 = decoupled RoPE：K 拆成【可吸收的压缩部分】+【带 RoPE 的 64 维小部分】
   ★ 那 64 维必须【所有头共享】，否则压缩率从 17.8× 掉到 2.2×
   openPangu：512 + 64 = 576 维入 cache，相比 MHA 压缩 17.8×，512K 下省 472 GiB

⑥ 五家四家用 MLA 系，只有 M3 用 GQA -> MLA 已形成共识
   ⚠️ 但 DeepSeek 自己的 V4 已经不用 MLA，改走压缩注意力（08 章）
```
