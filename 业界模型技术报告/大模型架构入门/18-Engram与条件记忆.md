# 18 · Engram 与条件记忆：MoE 之外的第二根稀疏轴

> **这是一章加餐**（2026-09 增补）。内容上它是 [10 章 MoE](10-MoE.md) 的姊妹章——MoE 是**条件计算**（conditional computation），Engram 是**条件记忆**（conditional memory），两者是同一个问题的两种解法。读完 10 章可以直接跳到这里。
>
> **这一章的目标**：讲清 DeepSeek-V4.1-Flash 里那个 **196B 参数、却几乎不产生任何 FLOPs** 的模块到底在干什么。
> 读完你应该能回答：一张查找表怎么可能有用？为什么必须哈希、为什么必须门控？它换来了什么、又付出了什么代价？"等效于加深模型"这个说法有多硬？
>
> **术语先摆这里**（本教程惯例，缩写第一次出现必须给全称）：
> **Engram** —— 论文自造的模块名，词源是神经科学的"记忆痕迹"，没有缩写展开。
> **MoE** —— Mixture of Experts，混合专家，见 [10 章](10-MoE.md)。
> **n-gram** —— 连续 n 个 token 组成的片段，如 3-gram = 相邻三个 token。
> **FLOPs** —— Floating Point Operations，浮点运算次数，衡量"算了多少"。
> **HBM** —— High Bandwidth Memory，显卡上的高带宽显存。
> **DRAM** —— Dynamic Random Access Memory，主板上的普通内存（比 HBM 大得多、慢得多）。
> **PCIe** —— Peripheral Component Interconnect express，显卡和主板之间的那条总线。
> **FP8** —— 8 位浮点数格式，一个参数只占 **1 字节**。Engram 的表和投影全用它。

> 📌 **这一章的边界**：本章讲**结构**——Engram 怎么设计、为什么这么设计、它的账怎么算。它挂在 DeepSeek-V4.1-Flash 上的完整上下文（和其他六个创新点怎么配合）见 [../DeepSeek-V4.1-Flash.md](../DeepSeek-V4.1-Flash.md) 第九节；MoE 那一侧的对照见 [10 章](10-MoE.md)。

## 18.0 ⚠️ 先纠正一个最容易犯的错误

很多介绍（包括我最初的讲法）会说 Engram"几乎免费"。**这句话是错的，或者至少是误导的。**

"免费"描述的是**代价小**，不是**有收益**。Engram 这笔交易必须拆成**四个独立的格子**来看，四格的方向并不一致：

| 这一格 | 方向 | 数字（V4.1-Flash 实测配置） | 说明 |
|---|---|---|---|
| 参数量 | ↑ | **+196B** | 骨干之外另算 |
| **FLOPs** | **≈ 不涨** | 见 §18.8 的账：+0.63 GFLOPs / token，约 **+2%** | ★ 这才是它真正的卖点 |
| **推理吞吐** | **↓** | **−1.9% ~ −2.8%** | ← 它是**减速**的 |
| 模型能力 | ↑ | 多项基准 **+2 ~ +5 分** | 见 §18.11 |

对比一下另外两条"让模型更强"的路：

| 路线 | 参数量 | FLOPs | 推理吞吐 | 备注 |
|---|---|---|---|---|
| 加层数 / 加宽（Dense） | ↑ | **↑↑** | **↓↓** | 每 token 都要多算一遍 |
| 加 MoE 专家（[10 章](10-MoE.md)） | ↑↑ | ≈ 不涨 | ↓ | all-to-all 通信变贵 |
| **Engram** | ↑ | **≈ 不涨** | ↓ 一点点 | 只多一次查表 + 一次 PCIe 搬运 |

> 🔑 **Engram 是三条路里唯一一条"FLOPs 几乎完全不涨"的**。它的 −2.8% 不是算力开销，是**数据搬运**开销（把查到的向量从主机内存搬到显卡）。
>
> ⚠️ **所以：Engram 属于"能力"侧，不属于"提速"侧。** V4.1-Flash 真正提速的组件是另外一批（CED、CSA2、分层稀疏索引器、FP4 主 KV cache、Single-Pass mHC、DSpark），Engram 反而是从那笔提速预算里**扣掉 2.8%** 的那一项。见 [../DeepSeek-V4.1-Flash.md](../DeepSeek-V4.1-Flash.md) 第九节。

## 18.1 出发点：模型认一个人名，要烧掉六层

论文 §6.1 引了 Ghandeharioun et al. (2024) 的一个可解释性实验。用 LogitLens / PatchScope 这类工具，把模型每一层的中间状态**翻译回人话**，看它在读到"Diana, Princess of Wales"这串 token 时，脑子里想的是什么：✅

```
    层 1-2   ->  "Wales：英国的一个组成国"
    层 3     ->  "Wales：欧洲的一个国家"
    层 4     ->  "Princess of Wales：女性君主的头衔"（还没定位到人）
    层 5     ->  "Princess of Wales：威尔士亲王的妻子"（还是没定位到人）
    层 6     ->  ★ "Diana, Princess of Wales (1961-1997)，查尔斯的第一任妻子……"
```

读一遍这张表，你会有一个很直接的感受：**模型花了六层的注意力 + FFN，做的事情本质上是一次查字典。**

> 🔑 **把这件事拆开看**：
>
> "Diana / Princess / of / Wales" 这四个 token 连在一起，**指向一个固定的实体**。
>
> 这是一条**静态的、和上下文无关的**事实。它不需要"推理"，它只需要"记住"。
>
> ★ **但今天的 Transformer 没有"查表"这个原语。** 它手上只有 Attention 和 FFN 两把工具，只能用**计算**去模拟**记忆**——用六层的参数和算力，硬凑出一个本来一次寻址就能拿到的结果。

Engram 的全部想法就一句话：

> 🔑 **给 Transformer 补上一个"查表"原语，把那些本来靠算力硬凑出来的静态模式，改成直接查出来。**

省下来的层数和算力，让模型拿去做真正需要推理的事。

## 18.2 结构：五步

先看整体，再逐步拆。

```
  输入 token 序列  x_1 ... x_t
        │
        ① tokenizer 压缩       Apple / ␣apple / APPLE  ->  归成同一个 id
        │
        ② 取后缀 n-gram        以当前 token 结尾的 2/3/4 元组
        │                       ("princess","of","wales")
        │
        ③ 多头哈希 -> 查表      每个元组算出 8 个不同的行号，查 8 张表
        │                       得到一个拼起来的向量 e_t
        │
        ④ 上下文门控           拿主干当前的隐状态 h_t 去"审一遍" e_t
        │                       算出一个 0~1 的标量 α_t
        │
        ⑤ 加回残差流           H <- H + α_t · (e_t 投影后的值)
        v
   继续走后面的层
```

第 ①②③ 步**只依赖输入 token 本身**，和模型算到哪一步无关——这一点后面 §18.8 会变成一个巨大的系统优势，先记住。

第 ④ 步是唯一依赖上下文的地方，也是这个模块和"普通 n-gram 查表"的本质区别。

> 📌 **想直接看一个 token 走完这五步的完整数字**，跳到 §18.7 末尾的「走完全程」。下面三节先把每一步单独讲清楚。

## 18.3 第①步：tokenizer 压缩

一个直接的麻烦：同一个词在 tokenizer 里有很多长相。

```
    "Apple"        ->  id 12345
    " apple"       ->  id 67890      （前面带空格）
    "APPLE"        ->  id 24680
    "Apple"（句首） ->  又一个 id
```

对"查表"来说这是纯浪费——它们指向同一个语义，却占了四个不同的地址，把表撑大了四倍，还把统计量摊薄了。

Engram 的做法：定义一个**满射**（surjective，多对一）映射 `P: V → V'`，做 NFKC 规范化（Normalization Form Compatibility Composition，Unicode 的一种标准化形式，把全角/半角、组合字符等归一）+ 转小写，把它们合并成同一个 id。✅

```
    P("Apple") = P(" apple") = P("APPLE") = P(" Apple") = "apple"
```

> ✅ 论文实测：对一个 **128k 词表**，有效词表大小**减少 23%**。
>
> ⚠️ 注意这是**只用于查表寻址**的压缩。模型正常的输入 embedding 和输出 LM head 还是用原始 tokenizer，没被改。丢掉大小写信息在"查静态模式"这件事上不要紧，在"预测下一个 token"上会要命。

**为什么减 23% 这么值钱？** 因为 3-gram 的组合数是**立方**关系。词表少 23%，3-gram 的地址空间就少 `1 − 0.77³ = 54%`——同样大的表，碰撞率直接砍掉一半还多。

消融实验里，去掉这一步（`w/o token compress`）是**损失最大的三个改动之一**。✅

---

## 18.4 第②步：后缀 n-gram

在位置 `t`，取**以 t 结尾**的 n 元组：

```
    g_{t,n} = ( x'_{t-n+1}, ..., x'_{t-1}, x'_t )        （x' 是压缩后的 id）
```

对 n = 2, 3, ..., N 各取一个。V4.1 用的是 **n ∈ {2, 3, 4}**。✅

```
    句子：  ... the  media  impact  of  Diana ,  Princess  of  Wales
                                                              ^ t

    2-gram：           ("of", "wales")
    3-gram：  ("princess", "of", "wales")
    4-gram：  (",", "princess", "of", "wales")
```

**为什么是"后缀"而不是"窗口"？** 因为语言模型是因果的（causal，只能看左边）。后缀 n-gram 保证不偷看未来的 token，可以直接用在自回归生成里。

**为什么要同时取 2/3/4 三个阶数？** 因为你事先不知道一个模式有多长。"of wales"这个 2-gram 信息量很低（到处都是），"princess of wales"这个 3-gram 就非常specific。三个阶数一起查、一起拼，等于让模型自己在门控那一步决定信哪一个。

> ⚠️ 也正因为是后缀，Engram 天然擅长的是**"这个短语在这里结束了"**这种模式：它在短语的**最后一个 token** 上信号最强，因为只有到那里，完整的 n 元组才凑齐。§18.6 的门控正是靠这一点来判断该不该开火。

---

## 18.5 第③步：多头哈希——表放不下怎么办

一个 3-gram 的可能组合数是 `V'³`。就算压缩后 V' ≈ 98k，也是 `9.4 × 10^14` 种。**不可能给每种组合都开一行。**

标准解法：**哈希**。把任意长度的元组，压成一个固定范围内的行号。

```
    z_{t,n,k} = φ_{n,k}( g_{t,n} )        φ 是轻量的乘法-异或哈希
    e_{t,n,k} = E_{n,k}[ z_{t,n,k} ]      去第 k 张表的第 z 行取一个向量
```

然后把所有阶数 n、所有头 k 的结果**拼接**（‖ 表示 concat）：

```
             N     K
    e_t  =   ‖     ‖   e_{t,n,k}
            n=2   k=1
```

**为什么要"多头"？** 因为哈希一定会撞（collision）——两个不相干的短语算出同一个行号，查出同一个向量。

| | 会发生什么 | 后果 |
|---|---|---|
| **单头**（1 个哈希 + 1 张表） | 撞了就是撞了，"红烧肉"和"薛定谔"拿到**完全相同**的向量 | 模型没有任何办法把它们分开 |
| **8 头**（8 个不同的哈希 + 8 张不同的表） | 要 8 个哈希**同时**把这两个短语撞到一起，概率 ≈ 0 | 拼起来的 `e_t` 仍然能把它们区分开 |

> 🔑 **这就是 Bloom filter（布隆过滤器）/ count-min sketch 的老套路**：用**多个独立哈希**把碰撞概率压到可以忽略。单头撞一次的概率是 p，八头同时撞的概率是 p⁸；p 就算高到 1%，p⁸ 也是 10⁻¹⁶。

**把碰撞率算出来**（⚠️ 我的推演，用生日问题的近似）：

```
    每张表 M = 1600 万行
    一段 1 万 token 的文本，产生约 1 万个 3-gram（大量重复，去重后假设 5000 个不同的）

    单张表上，任意两个不同 3-gram 撞到同一行的概率 ≈ 1 / 1.6e7 = 6.25e-8
    5000 个里出现【至少一对】碰撞的概率 ≈ 5000² / 2 / 1.6e7 = 78%   ← 单头必撞

    但要求【同一对】在 8 张表上全撞：(6.25e-8)^8 ≈ 2.3e-58            ← 8 头不可能
```

> ✅ V4.1 的配置：**8 个哈希头**，每张表约 **1600 万行**，而且**各张表的行数取互不相同的质数**。
>
> ⚠️ 取质数是哈希表的标准工程手段：表长互质能让不同表的碰撞模式尽量不相关，避免"在 A 表撞了的，在 B 表也倾向于撞"。上面那个 p⁸ 的独立性假设，靠的就是这一条。

**numpy 伪代码**（整个检索过程）：

```python
def engram_lookup(ids, t, tables, orders=(2, 3, 4), K=8):
    """tables[n][k] 是第 n 阶、第 k 头的嵌入表，形状 [M_{n,k}, d_sub]"""
    ids = normalize(ids)                       # ① tokenizer 压缩
    parts = []
    for n in orders:
        gram = tuple(ids[t - n + 1 : t + 1])   # ② 后缀 n-gram
        for k in range(K):
            M = tables[n][k].shape[0]          # 表长，取质数
            z = mul_xor_hash(gram, seed=(n, k)) % M   # ③ 第 k 个哈希
            parts.append(tables[n][k][z])      #    查一行
    return np.concatenate(parts)               # e_t
```

注意这段代码里**一次矩阵乘法都没有**。全是取地址 + 读内存。这就是"FLOPs ≈ 0"的来源。

## 18.6 第④步：门控——只有一个 key 的注意力

到这里为止，Engram 还只是个查字典的。**但直接把 `e_t` 加进残差流是危险的**，因为 `e_t` 有三个毛病：

| # | 毛病 | 具体例子 |
|---|---|---|
| ① | 它是**上下文无关**的先验 | "苹果"查出来的向量分不清水果和公司 |
| ② | 它可能是**哈希撞出来**的垃圾 | 8 头同时撞概率极低，但单头撞很常见（§18.5） |
| ③ | 大多数位置根本**没有**静态模式可查 | "的"、"了"、随机组合的三元组 —— 查出来是噪声 |

> ★ **所以必须有个开关：让主干说了算。**

做法（论文 Eq. 3–4）✅：

```
    k_t = W_K · e_t                                  <- 把查出来的东西变成一个"key"
    v_t = W_V · e_t                                  <- 和一个"value"

              /  RMSNorm(h_t)ᵀ · RMSNorm(k_t)  \
    α_t = σ  | ------------------------------- |     σ 是 sigmoid
              \              √d                /

    ṽ_t = α_t · v_t
```

**这个式子你其实已经见过了。** 把它和 [05 章](05-注意力机制.md) 的注意力对照：

```
    标准注意力：  softmax( q·Kᵀ / √d ) · V        K 有 L 行（L 个 token）
    Engram 门控： sigmoid( h·kᵀ / √d ) · v        K 只有【1 行】
```

> 🔑 **当 key 只有一个的时候，softmax 退化成 sigmoid。**
> softmax 在多个候选之间分配权重（一行加起来 = 1）；只有一个候选时"分配"没有意义，剩下的唯一问题是"要不要"，那就是一个 0~1 的开关。
>
> 所以 Engram 的门控**不是新机制**，它就是一次"只有一个候选的注意力"。查询是主干的 `h_t`（有上下文），被查的是 `k_t`（没上下文）。**如果查出来的东西和当前上下文对不上，α_t → 0，这次查表就当没发生过。**

这解决了上面三个毛病：语义对不上 → 关掉；哈希撞出垃圾 → 对不上 → 关掉；没有模式可查 → 查出来的东西和 h_t 无关 → 关掉。

消融里去掉门控（`w/o gating`）同样是**三个最大退化之一**。✅

## 18.7 第⑤步：加回残差流

```
    H <- H + Attn(H) + MoE(H) + α_t · ( W_V · e_t )
                                ^^^^^^^^^^^^^^^^^^
                                    Engram 的贡献
```

就是 [03 章](03-残差流.md) 讲的那条总线，多接了一路旁支。**不改变任何形状，不影响任何其他模块**——这也是它能被塞进一个已有架构的原因。

**多分支（multi-branch）**：V4.1 用的 mHC（Manifold-Constrained Hyper-Connections，流形约束超连接，见 [03 章](03-残差流.md)）把残差流拆成 M = 4 条并行的流。Engram 的做法是：✅

```
    嵌入表          ->  所有分支【共享】     （最贵的部分只存一份）
    W_V（值投影）   ->  所有分支【共享】
    W_K（键投影）   ->  每个分支【各有一个】 -> 每个分支算自己的 α_t
```

> ⚠️ 这个设计有个很实际的动机：一个共享的 `W_V` 加 M 个 `W_K` 可以**融合成一次 FP8 稠密矩阵乘法**，对 GPU 友好。同时又保留了"不同分支对同一条记忆有不同取舍"的自由度。
>
> 消融里 `w/o multi branch` 也是三个最大退化之一。✅

### ★ 走完全程：一个 token 的完整数值走查

把五步用**能手算的小数字**跑一遍。为了看得清，这里把配置缩小到：阶数 n ∈ {2, 3}、哈希头 K = 2、每行维度 d_sub = 2、主干维度 d = 4、分支数 M = 1。真实配置在这一节末尾对照。

**输入**：`... the media impact of Diana , princess of wales`，当前位置 t 落在 `wales` 上。

**① tokenizer 压缩**：`"Princess" / " princess" / "PRINCESS"` 全部归成 `princess`。压缩后的 id：`princess = 41`、`of = 7`、`wales = 88`。

**② 取后缀 n-gram**：

```
    2-gram：  g_{t,2} = (7, 88)
    3-gram：  g_{t,3} = (41, 7, 88)
```

**③ 多头哈希 → 查表**。哈希用 `φ_{n,k}(g) = ( Σ_i id_i · A_k^i ) mod M_{n,k}`，两个头分别取 `A_1 = 5`、`A_2 = 7`，四张表的行数取四个不同的质数。**这一步你可以自己按计算器验算**：

| 表 | 阶 n | 头 k | 表长 M（质数） | 算式 | 行号 z | 取到的行（d_sub = 2） |
|---|---|---|---|---|---|---|
| E₂,₁ | 2 | 1 | 13 | (7·5 + 88·5²) mod 13 = 2235 mod 13 | **12** | [ 0.5, −0.2 ] |
| E₂,₂ | 2 | 2 | 17 | (7·7 + 88·7²) mod 17 = 4361 mod 17 | **9** | [ 0.1, 0.3 ] |
| E₃,₁ | 3 | 1 | 19 | (41·5 + 7·5² + 88·5³) mod 19 = 11380 mod 19 | **18** | [ 1.2, 0.8 ] |
| E₃,₂ | 3 | 2 | 23 | (41·7 + 7·7² + 88·7³) mod 23 = 30814 mod 23 | **17** | [ 1.0, 0.9 ] |

拼接得到：`e_t = [0.5, −0.2, 0.1, 0.3, 1.2, 0.8, 1.0, 0.9]`（8 维）。

> 🔑 **注意这四行的量级差别**：3-gram 那两行（`princess of wales`）数值明显更大，2-gram 那两行（`of wales`）接近 0。这正是训练想要的结果——`of wales` 这个 2-gram 到处都是、没信息量，表里就学成了接近零向量；`princess of wales` 是一条真实的实体线索，表里存了强信号。**同时查 2/3/4 阶，让模型自己选信哪一阶。**

**④ 上下文门控**。设 `W_K · e_t = k_t = [0.9, 0.2, −0.1, 1.1]`，`W_V · e_t = v_t = [0.4, −0.3, 0.7, 0.2]`。现在看两种上下文下 α_t 的差别：

| | 上下文 A：正在谈英国王室 | 上下文 B：正在谈南威尔士的煤矿 |
|---|---|---|
| 主干隐状态 `h_t` | [1.0, 0.1, 0.0, 0.8] | [−0.9, 0.3, 1.0, −0.8] |
| RMSNorm(h_t) | [1.557, 0.156, 0, 1.246] | [−1.129, 0.376, 1.255, −1.004] |
| RMSNorm(k_t) | [1.251, 0.278, −0.139, 1.529] | 同左（k_t 与上下文无关） |
| 点积 | **+3.896** | **−3.016** |
| ÷ √d（d = 4） | +1.948 | −1.508 |
| **α_t = sigmoid(·)** | **0.875 → 门开着** | **0.181 → 门基本关上** |

**⑤ 加回残差流**（用上下文 A）：

```
    ṽ_t = α_t · v_t = 0.875 × [0.4, −0.3, 0.7, 0.2] = [0.350, −0.263, 0.613, 0.175]

    H <- h_t + ṽ_t = [1.0, 0.1, 0.0, 0.8] + [0.350, −0.263, 0.613, 0.175]
                   = [1.350, −0.163, 0.613, 0.975]
```

> 🔑 **整段走完，一次矩阵乘法只出现在第 ④ 步的 `W_K` / `W_V` 两个小投影上。** ①②③ 全是取模、取地址、读内存，⑤ 是一次向量加法。**这就是"196B 参数、FLOPs 几乎不涨"的字面含义**——参数躺在表里，只有被查到的那几行才被读出来，而且读出来也不参与任何大矩阵乘。

## 常见问题：Engram 训练哪些参数、在哪个模块起作用？

**训练的参数**共三类，全部用 FP8 存储：

1. **嵌入表**（embedding tables）——主体，196B 参数的来源。每张表的每一行是一个 d_sub 维向量，对应一条 n-gram 的"记忆"。V4.1-Flash 配置：2 个模块 × 8 个哈希头 × 3 个阶数（n=2,3,4）= 48 张表，每表约 1600 万行。

2. **W_K（键投影）**：把查表结果 `e_t` 投影成门控所用的 key 向量 `k_t`，是一个小的线性层。多分支时**每个分支各有一个**。

3. **W_V（值投影）**：把 `e_t` 投影成门控输出的 value 向量 `v_t`。**所有分支共享一个**（最贵的部分只存一份）。

> ⚠️ 门控的 **query 不是独立参数**——它直接复用主干的隐状态 `h_t`，查询侧没有额外权重。这正是 Engram 的门控"只是一次单 key 注意力"的含义（见 §18.6）。

**起作用的位置**：Engram 不修改任何现有模块，它是**挂在残差流上的一条旁支**：

```
   残差流 h_t
     │
     ├─ 恒等直连（什么都不做，原样带下去）
     │
     ├─ 主路：      Attn(H)  ->  MoE(H)
     │
     └─ Engram 旁支：查表 ①②③ -> e_t -> 门控 ④ -> α_t · W_V · e_t
     │
     v
   三路相加，写回残差流：
       H <- H + Attn(H) + MoE(H) + α_t · W_V · e_t
```

V4.1-Flash 把 Engram 插在第 **1** 层和第 **14** 层。放在第 0 层不行——门控需要 `h_t` 已经过至少一轮注意力才有上下文；放太靠后效果下降（详见 §18.9）。

## 18.8 系统：为什么 196B 参数能放在主机内存里

这是 Engram 和 MoE 最大的结构性差别，值得单独一节。

| | **MoE 路由** | **Engram 检索** |
|---|---|---|
| 地址由什么决定 | 隐状态 `h_t`（要先算出来） | ⭐ **输入 token 序列**，仅此而已 |
| 什么时候知道地址 | **运行时**，算到这一层才知道 | ⭐ **token 一进来就知道**，可以提前几层算好 |
| 权重能放哪 | 必须**提前把所有专家摆在 HBM 里**等着 | ⭐ 可以放**主机 DRAM**，用到时再取 |
| 能不能预取 | ✗ | ⭐ ✅ 可以，而且能被前面几层的计算挡住 |

论文管这个叫 **deterministic addressing**（确定性寻址）。它直接换来两件事：✅

**训练时**：表按 GPU 切片（模型并行），前向用 All-to-All 收集需要的行，反向用 All-to-All 发回梯度。总容量随卡数**线性增长**。

**推理时**：整张表放在**主机 DRAM**（比 HBM 便宜、大几十倍），需要的行**异步预取**。因为地址提前知道，可以在前面几层还在算的时候，就把 PCIe 搬运做完：

```
    时间 -->
    GPU ：  [ 第 0 层计算 ][ 第 1 层计算 ][ 第 2 层 = Engram，e_t 已到齐 ]
    PCIe：  [ 预取 e_t ............ ] 完成
            \___ 整段搬运被第 0~1 层的计算盖住，端到端看不见 ___/
```

这就是为什么 Engram 模块**必须放在靠前但不是第一层**——放太靠前，前面没有足够的计算量来挡住搬运延迟；放太靠后，见下一节，效果会掉。

> ✅ 论文还指出：n-gram 的频率服从 **Zipf 分布**（Zipfian distribution，少数模式占绝大多数访问）。所以可以做**多级缓存**：热的行缓存在 HBM，温的在 DRAM，冷的长尾放 NVMe SSD。
>
> ⚠️ 但 §6.4 的实测**没有**用这个优化——它把**所有**检索都强制走 PCIe，属于最保守的下界。所以 §18.12 那个 −2.8%，是**悲观值**。

### ★ 把显存和计算的账算出来

上面说了半天"便宜"，到底多便宜？把 V4.1-Flash 的配置逐项代进去。⚠️ **下面除了配置本身，算术都是我的推演**，报告没有逐项列出。

**第一笔：表有多大**

```
    48 张表 × 1600 万行 × 256 维 × 1 字节（FP8）
      = 1.966 × 10^11 字节
      = 196.6 GB   （= 183.1 GiB）      ✔ 和报告给的 196B 参数对得上
```

> ⚠️ **注意 GB 和 GiB**：196.6 GB 是十进制，183.1 GiB 是二进制。一张 H800 的 HBM 是 80 GB——**这张表塞不进任何单张卡**，要么切到 3 张卡以上，要么放主机内存。而一台 8 卡服务器通常配 1~2 TB 主机 DRAM，**一台机器放一整份表绰绰有余**。这才是"卸载"这个方案成立的物理前提。

**第二笔：每个 token 要搬多少字节**

```
    每模块查的行数 = 3 个阶数 × 8 个哈希头            = 24 行
    两个模块                                          = 48 行
    每行字节数     = 256 维 × 1 字节（FP8）           = 256 B

    每 token 搬运量 = 48 × 256 = 12,288 B = 12 KiB
```

**第三笔：这 12 KiB 走 PCIe 占多少带宽**

```
    PCIe Gen5 ×16 单向带宽 ≈ 64 GB/s
    按论文实测那档吞吐 6,140 tok/s 算：
        12,288 B × 6,140 /s = 75.4 MB/s
        75.4 MB/s ÷ 64 GB/s = 0.12%
```

> 🔑 **这个 0.12% 是本节最重要的一个数**。它说明 §18.12 那个 −2.8% 的吞吐损失**根本不是 PCIe 带宽被打满**造成的。
>
> ⚠️ 那是什么造成的？我的推断是三件事：**(a) 延迟**——一次主机内存往返是百纳秒到微秒量级，如果预取窗口没盖住就要干等；**(b) 随机访问**——48 行落在 196 GB 里的 48 个随机位置，DRAM 的随机小块读远达不到标称带宽；**(c) 描述符开销**——每 token 48 个不连续的 256 B 片段，要攒成 scatter-gather DMA 请求，CPU 侧和 DMA 引擎都有固定成本。**⚠️ 这三条是我的推断，论文没有做归因分解。**
>
> 🔑 **实践含义**：既然瓶颈不是带宽，那么"加宽 PCIe"没用，有用的是**加大预取提前量**（往后挪一层）和**提高 HBM 缓存命中率**（Zipf 局部性）。如果热点行的命中率做到 90%，走 PCIe 的随机请求数直接降一个数量级。

**第四笔：门控到底花了多少 FLOPs**

这是唯一真正产生浮点运算的地方。⚠️ 这里假设 `k_t` 的维度等于主干维度 5120（点积要求两者同维），报告没有明写这一条：

```
    每模块：
        W_V：6144 × 5120 = 31.5 M 参数    （4 个分支共享 1 份）
        W_K：6144 × 5120 = 31.5 M 参数    × 4 个分支 = 125.8 M
        小计                              = 157.3 M

    两个模块合计 ≈ 314.6 M 参数 ≈ 0.31 B
    每 token 前向 FLOPs = 2 × 3.146e8 = 0.63 GFLOPs
```

**第五笔（收口）：同样 196B 参数，放在三个不同位置，账完全不一样**

| 把这 196B 参数放到哪 | 必须占的 HBM | 每 token 新增 FLOPs | 每 token 新增搬运 | 能不能卸载到主机 |
|---|---|---|---|---|
| **稠密 FFN**（加宽或加深） | **+196 GB** | **+392 GFLOPs** ≈ 骨干（decode 32 GFLOPs）的 **12 倍** | 0（权重常驻 HBM） | ✗ |
| **MoE 专家**（384 选 6 = 1/64） | **+196 GB**（没被选中的也得在 HBM 里等着） | +6.1 GFLOPs（约 +19%） | + All-to-All 通信 | ✗ 地址运行时才知道 |
| ⭐ **Engram** | **0** | **+0.63 GFLOPs**（约 +2%，全在门控投影上） | **+12 KiB** 走 PCIe | ✅ 确定性寻址，可预取 |

> ⚠️ **这张表顺手纠正了一个说法**：严格讲 Engram 的 FLOPs **不是零**，是骨干的约 **2%**（decode 口径；prefill 激活 8B 时约 4%）。但和"同样参数塞进 FFN 要多算 12 倍"相比，这 2% 确实可以叫"不涨"。**本章说"FLOPs ≈ 0"时，指的是这个对比，不是字面的零。**
>
> 🔑 **三行里真正决定性的是第二列**：稠密和 MoE 都必须把 196 GB 摆进 HBM，Engram 是 0。**这不是"优化得好"，是结构性的——寻址方式不同，所以能放的位置不同。**

## 18.9 放在哪一层：一个真实的取舍

论文 §6.2 做了一个很干净的实验：在一个 **3B MoE** 的小模型上，固定 1.6B 的 Engram 预算，把它整块塞进第 1~12 层里的某一层，扫一遍。✅

```
    3B MoE 基线                      Val Loss = 1.808
    ----------------------------------------------------
    单块塞在第 2 层  ★ 最优           Val Loss = 1.770
    单块塞在第 1 层                   略差
    往深了塞（3, 4, ..., 12）         持续变差
    ----------------------------------------------------
    拆成两小块，放第 2 层 + 第 6 层    Val Loss = 1.768   <- 这个小模型上的最终选择
```

**为什么早比晚好，但第 1 层又不如第 2 层？** 两股力量在打架：

| 方向 | 理由 | 谁在推 |
|---|---|---|
| 往**早**放 | 静态模式的重建**本来就发生在底层**（§18.1 那张表：层 1–6）。要替它省事，就得赶在它开始费劲之前。 | 收益侧 |
| 往**晚**放 | 门控要用 `h_t` 当查询。第 1 层的 `h_t` 还没经过任何注意力，几乎不含上下文 → **α_t 判断不准**，该关的关不掉。 | 质量侧 |

> 🔑 **第 2 层是这两股力的平衡点**：已经过了一轮注意力（`h_t` 有上下文了），但还没轮到主干去硬凑那些静态模式。
>
> 🔑 **拆成两块比一块更好，是因为两块各吃一头的红利**：第一块放在最早的位置吃"早"的红利，第二块放在中层，那里的 `h_t` 上下文最充分，门控判得最准。

> ✅ 论文实测配置：Engram-27B 放在第 **2** 层和第 **15** 层。
> ✅ V4.1-Flash（40 层）放在第 **1** 层和第 **14** 层。
>
> ⚠️ **别把"第 2 + 第 6"和"第 2 + 第 15"当成互相矛盾**：前者是上面那个 **3B 小模型**的扫层结果（它只有十几层，第 6 层已经是中层了），后者是 **27B 模型**的配置。**两块的相对位置（一块极浅、一块中层）在两个规模上是一致的，绝对层号不一致。**
>
> ⚠️ V4.1 比论文更靠前一层（第 1 而不是第 2），报告没解释原因。可能和它的主干层数（40 层）、mHC 结构不同有关，也可能只是重新调过。

另外还有一层系统上的理由：拆成两块，正好对应 §18.8 的多级缓存——两块的预取窗口可以分别安排，第一块靠前面几层的计算挡住搬运，第二块有整整十几层的时间可以慢慢取。

## 18.10 稀疏度分配：MoE 和 Engram 怎么分预算

这是论文最有价值的一节（§3），也是它敢叫 "a new axis of sparsity"（一根新的稀疏轴）的底气。

先定义三个量：✅

```
    P_tot     总参数量（不含词表 embedding 和 LM head）
    P_act     每个 token 实际激活的参数量  ->  决定 FLOPs
    P_sparse  = P_tot − P_act
              ★ "不花算力的参数预算"：没被选中的专家 + 没被查到的嵌入行
```

然后问：**这笔 P_sparse，该分给 MoE 还是分给 Engram？**

```
    分配比 ρ ∈ [0,1]：
        P_MoE     = ρ · P_sparse
        P_Engram  = (1 − ρ) · P_sparse

        ρ = 1     ->  纯 MoE（今天所有模型的做法）
        ρ = 0     ->  纯 Engram
```

固定 `P_tot` 和 `P_act`（所以**参数量相同、FLOPs 也相同**），只调 ρ，扫一遍：

| ρ（分给 MoE 的比例） | 分给 Engram | Val Loss | 相对纯 MoE |
|---|---|---|---|
| **100%**（纯 MoE，今天所有模型的做法） | 0 | **1.7248** | 基线 |
| ⭐ **75~80%**（最优） | 20~25% | ⭐ **1.7109** | **−0.0139** |
| **40%**（专家从 106 个砍到 46 个） | 60% | ≈ 1.725 | ≈ **追平**基线 |
| 0%（纯 Engram） | 100% | 明显更差 | 需要动态推理的任务垮掉 |

画成图就是一条 **U 形曲线**：

```
 Val Loss（越低越好）
        ^
  1.725 |  o                                                 o   <- 两端都差
        |   \                                               /
  1.720 |    \                                             /
        |     \                                           /
  1.715 |      \                                         /
        |       \____                             ______/
  1.711 |            \_____________o_____________/             <- ★ 谷底 rho = 75~80%
        |
        +-----+---------+---------+---------+---------+------> rho
             40%       55%       70%       85%      100%
```

三个结论，每一条都值得单独记住：✅

```
① 纯 MoE 【不是最优的】。
   把 20~25% 的稀疏预算挪给 Engram，loss 更低（Δ = 0.0139）。

② 挪得很狠也不塌。
   ρ 降到 40%（专家从 106 个砍到 46 个），性能仍然【追平】纯 MoE。

③ 最优点很稳。
   2e20 和 6e20 两个算力量级下，最优 ρ 都在 75~80%。
```

**这条 U 形曲线的两端在说什么：**

```
   ρ -> 100%（纯 MoE）：  没有专门的记忆，只能用深度和算力去【重建】静态模式  -> 浪费
   ρ -> 0%（纯 Engram）： 没有条件计算，需要动态推理的任务垮掉  -> 记忆替代不了计算
```

> 🔑 **记忆和计算是互补的两根轴，不是互相替代。** 这是全篇论文的核心主张，U 形曲线是它的直接证据。

另一个方向的实验（§3.2，"无限内存"）：固定主干，只把嵌入槽位从 2.58×10⁵ 扫到 1.0×10⁷（加了约 13B 参数），loss 在 log 坐标下**是一条直线**——严格的幂律。✅ 也就是说 Engram 提供了一个**可预测的、不花算力的**扩展旋钮。

> ⚠️ 幂律直线意味着**收益是递减的**：槽位每翻十倍，loss 降一个固定的量。所以"再加一万倍的表"并不会带来一万倍的好处——这也是为什么 ρ 的最优点停在 75~80%，而不是一路滑向 0。

|---|---|---|---|

> ⭐ **最反直觉的一点**：涨得最多的**不是知识题**，是**推理题**（BBH +5.0、ARC-Challenge +3.7），连代码和数学也涨了。

> 一张查找表，为什么能提升推理？论文的解释就是 §18.1 那件事——**把底层用来拼凑静态模式的算力省下来了，主干可以拿去做别的**。TriviaQA（纯记忆题）只涨 1.9，反倒是涨得最少的之一。
>
> ⚠️ **这张表要连着"对照组是什么"一起读**：MoE-27B 不是一个更弱的模型，它是**同参数量、同激活量、同数据、同步数**的对照。所以这几分不是"堆上去的"，是**同一笔预算换了个花法换来的**。这也是为什么 §18.10 那条 U 形曲线才是本章最重要的结论——它说的就是"怎么花"。

**长上下文（§5，RULER 32k）** 更夸张：✅

| | MoE-27B (50k 步) | Engram-27B (46k 步，**同 loss**) |
|---|---|---|
| Multi-Query NIAH | 84.2 | **97.0** |
| 多跳变量追踪 VT | 77.0 | **87.2** |
| 高频词抽取 FWE | 73.0 | **98.6** |

> ✅ 这里的对照做得很讲究：Engram-27B 取的是**预训练 loss 和满训 MoE 相同**的那个中间检查点（46k 步 vs 50k 步），所以差异只能归因于架构，不能归因于"底座更强"。
>
> 论文的解释：Engram 把**局部依赖**的建模卸载掉了，注意力的容量就腾出来给**全局上下文**了。这和 §18.4 说的"后缀 n-gram 天然擅长'这个短语在这里结束了'"是同一件事的两面——短语级的局部模式交给查表，注意力只管跨越几万 token 的长程关联。

## 18.12 它到底付出了什么：也要摆数字

### ① 吞吐是负的（§6.4，Table 4）✅

| 配置 | 吞吐 (tok/s) | 变化 |
|---|---|---|
| 4B-Dense 基线 | 9,031.62 | — |
| + 100B Engram（卸载到主机内存） | 8,858.28 | **−1.9%** |
| 8B-Dense 基线 | 6,315.52 | — |
| + 100B Engram（卸载到主机内存） | 6,140.02 | **−2.8%** |

测试条件：NVIDIA H800，512 条序列，长度 Uniform(100, 1024)，100B 的 Engram 层塞在第 2 个 Transformer block，推理框架是 nano-vLLM。

> ⚠️ **这 2.8% 是数据搬运，不是计算。** 而且如 §18.8 所说，这个实验强制所有检索都走 PCIe，没用 Zipf 缓存，是**保守下界**——真实系统里应该更小。
>
> ⚠️ 同时留意 §18.8 第三笔账：PCIe 带宽只被用掉 **0.12%**。所以这 2.8% 的来源是**延迟和随机访问**，不是带宽。想把它压下去，加宽 PCIe 没用，要靠预取提前量和 HBM 热点缓存。
>
> ⚠️ 还有一条口径要注意：**"吞吐掉 2.8%" 和 "变慢 2.8%" 不是同一句话。** 吞吐从 6,315.52 掉到 6,140.02 是 −2.78%；反过来看单 token 耗时，是 `6315.52/6140.02 − 1 = +2.86%`。两个数很接近只是因为百分比小，量级大了就会明显分叉——**引用时说清楚是哪一侧**。
>
> ⚠️ 但"更小"不等于"零"，更不等于"提速"。**任何把 Engram 归到"推理加速技术"那一栏的说法都是错的。**

### ② 它承担了知识，也就成了单点（§6.3）✅

论文做了个压力测试：推理时**把 Engram 的输出整个掐掉**，主干不变，看还剩多少：

```
    事实知识类：
        TriviaQA        只剩 29%   <- 塌了
        PopQA           只剩 44%
        TriviaQA-ZH     只剩 44%

    阅读理解类：
        C3              还有 93%   <- 几乎没事
        RACE-Middle     还有 89%
        DROP            还有 81%
```

> 🔑 **一个非常干净的功能分工**：Engram 是**参数化知识的主仓库**，注意力主干负责**上下文里的东西**。掐掉记忆，模型立刻"失忆"，但"看着材料回答问题"的能力还在。
>
> ⚠️ 这个实验有训练-推理不一致的问题（模型训的时候有 Engram，测的时候没有），论文自己也承认，所以只挑了信噪比最高的两端来分析。别把中间那些 60~80% 的数字当精确结论。
>
> ⚠️ **工程上的言外之意**：Engram 那 196 GB 的表是**不能降级、不能裁剪、不能"先不加载"**的。它不像一个可选的加速插件，它是模型知识的主体。部署时"主机内存不够就先不开 Engram"这条路走不通——模型会直接变傻。

### ③ "等效于加深模型"——这个说法有多硬

论文 §6.1 用两个可解释性工具论证 Engram "effectively increases the model's depth"：✅

- **LogitLens**（逻辑透镜）：把每层的中间状态用最终的 LM head 投影出来，算它和最终输出分布的 KL 散度（Kullback-Leibler divergence，衡量两个概率分布差多远）。Engram 版本在**早期层**的 KL 明显更低 → 更早"想清楚"。
- **CKA**（Centered Kernel Alignment，中心化核对齐，一种比较两组表示相似度的指标）：Engram-27B 的第 5 层，表示上最接近 MoE 基线的**第 12 层**。热力图的高相似对角线整体**向上偏移**。

> ⚠️ **这是我要给这一节打的最大一个问号。**
> LogitLens 和 CKA 都是**观察性**证据，说明"表示看起来像更深的层"。它**不等于**一个受控实验——论文**没有**做"Engram 版本砍掉 k 层、分数仍然打平"这种直接验证。
>
> 所以"等效加深"目前应该读作：**一个有可解释性证据支持的、合理的解释**，而不是一个已经量化的结论。真要说"能省几层"，现在没有数字。

| 家 | 用了吗 | 说明 |
|---|---|---|
| **DeepSeek-V4** | ✗ | Engram 是独立论文（arXiv:2601.07372），**没有进 V4**。见 [../模型技术对比.md](../模型技术对比.md) §2.9（V4 的原始数字保留在那里；[../DeepSeek-V4.md](../DeepSeek-V4.md) 用的是中文序号，没有 §2.9） |
| **DeepSeek-V4.1-Flash** | ⭐ ✅ **用了** | 196B 参数，第 1 和第 14 层，n ∈ {2,3,4}，8 头，每阶总维度 2048，每表约 1600 万行（质数），嵌入表和 K/V 投影全 FP8 |

| GLM-5.x | ✗ | 同上 |
| MiniMax-M3 | ✗ | 同上 |
| openPangu | ✗ | 同上 |

> 🔑 **六家里只有一家用了，这件事本身是信息**：Engram 需要的不只是一个新模块，还需要**推理栈配合**（主机内存里放一份 196 GB 的表、算好地址、异步预取、多级缓存）。这是一个**架构决策连带系统改造**的典型例子，不是改几行模型代码就能加上的。

**V4.1 相比原论文的两处改动** ✅：
1. **去掉了短因果卷积**——论文消融里这一项本来就"影响很小"（`w/o short conv` 几乎不掉），去掉合理。
2. **优化器从 Adam 换成动量 + Sinkhorn 平衡**（γ=0.18 / K=11 / τ=1e-3）。见 [13 章](13-优化器与Muon.md)。

> ⚠️ **第 2 条不是口味问题，是被显存逼出来的**：196B 参数如果用 Adam，光优化器状态（一阶动量 + 二阶动量）就是参数量的好几倍。改成"只需要一个动量缓冲"的方案，把这笔开销砍掉了大部分。✅ 报告还说这么换**实测比 Adam 更好**，另外 Engram 的学习率被**放大 5 倍**（沿用前作设定）。

**参数量能对上吗？** 自己算一遍：

```
    2 个模块 × 8 个哈希头 × 3 个阶数(n=2,3,4)  =  48 张表
    每张表 ≈ 1600 万行
    每行维度 = 2048 / 8 = 256

    48 × 16e6 × 256  =  1.966e11  ≈  196B    ✔ 和报告一致
```

> ✅ 这个数和 DeepSeek-V4.1-Flash 报告给出的 196B 对得上。
> ⚠️ 其中"每行维度 = 每阶总维度 / 头数"是我的推断（拼接式多头的标准做法），报告没有逐字写明。
> ⚠️ 另有一处公开数字的出入：Hugging Face 模型页标的是 **485B**，报告写的是 **552B 骨干 + 196B Engram**。我推测 HF 的数字是按 FP8/FP4 存储的实际权重文件统计的，但报告没有解释这个差异。见 [../DeepSeek-V4.1-Flash.md](../DeepSeek-V4.1-Flash.md) 末节。

## 18.14 和 MoE 的对照（一张表收口）

| | **MoE**（[10 章](10-MoE.md)） | **Engram**（本章） |
|---|---|---|
| 中文叫法 | 条件**计算** | 条件**记忆** |
| 稀疏的是什么 | 哪几个专家被算 | 哪几行嵌入被查 |
| 地址什么时候知道 | 运行时（要先算 h_t） | ⭐ **输入一给定就知道** |
| 能不能卸载到主机内存 | 很难 | ⭐ **可以**（靠确定性寻址预取） |
| 每 token 的 FLOPs | 有（k 个专家的前向） | ≈ 0（只有取址 + 一次小投影，约骨干的 2%） |
| 主要成本 | all-to-all 通信 | PCIe 上的**随机小块延迟**（不是带宽，见 §18.8） |
| 负载均衡问题 | ★ 严重，要专门治 | 哈希天然均匀，靠多头压碰撞 |
| 擅长 | 动态、依赖上下文的推理 | 静态、和上下文无关的模式 |
| 单独用行不行 | 行（今天都这么干） | 不行（ρ→0 时推理垮掉） |

> 🔑 **最优解是混合**：把 20~25% 的稀疏预算给记忆，剩下给计算。

## 18.15 本章小结

```
    ① Engram 给 Transformer 补了一个它一直没有的原语：【查表】。
      模型认出 "Diana, Princess of Wales" 本来要烧六层，
      现在可以查出来。                              -> §18.1

    ② 五步：tokenizer 压缩 -> 后缀 n-gram -> 多头哈希查表
            -> 上下文门控 -> 加回残差流。
      前三步不依赖上下文，第四步才依赖。
      一个 token 走完全程的数值走查在 §18.7 末尾。  -> §18.2 / §18.7

    ③ ★ 门控就是【只有一个 key 的注意力】。
      softmax 在唯一候选上退化成 sigmoid。
      查出来的东西和上下文对不上，α_t -> 0，当没查过。-> §18.6

    ④ ★★ 地址只由输入 token 决定（确定性寻址）。
      这一条换来了：表可以放主机内存 + 异步预取藏在
      前面几层的计算里。这是 MoE 做不到的。          -> §18.8

    ⑤ ★★ 同样 196B 参数，放三个地方账完全不同：
      稠密 FFN  -> +196 GB HBM，+392 GFLOPs/token（骨干的 12 倍）
      MoE 专家  -> +196 GB HBM，+6.1 GFLOPs/token
      Engram    -> 0 HBM，+0.63 GFLOPs/token，+12 KiB PCIe
      ⚠️ 而且 PCIe 带宽只用掉 0.12%，2.8% 的损失来自
         【延迟和随机访问】，不是带宽。               -> §18.8

    ⑥ 放在极浅层最好，拆成两块（一块极浅 + 一块中层）更好。
      早放能替主干省事，但太早门控又判断不准。
      ⚠️ 3B 小模型是第 2+6 层，27B 是第 2+15 层，
         V4.1-Flash（40 层）是第 1+14 层——相对位置一致。-> §18.9

    ⑦ ★★ U 形分配律：纯 MoE 不是最优。
      把 20~25% 的稀疏预算挪给记忆，loss 最低（−0.0139）；
      挪走 60%（ρ=40%，专家 106→46）都还能追平。
      记忆和计算互补，不互相替代。                    -> §18.10

    ⑧ 同参数量同 FLOPs 下，涨得最多的是【推理题】
      （BBH +5.0、ARC-C +3.7），不是知识题。
      长上下文 Multi-Query NIAH 84.2 -> 97.0。       -> §18.11

    ⑨ ⚠️ 代价一：推理吞吐【掉】1.9% ~ 2.8%。
      Engram 是【能力】技术，不是【提速】技术。
      任何把它归到加速那一栏的说法都是错的。         -> §18.0 / §18.12

    ⑩ ⚠️ 代价二：掐掉 Engram，TriviaQA 只剩 29%。
      它是知识的主仓库，不是可选插件，部署时不能省。
      ⚠️ "等效于加深模型" 目前只有 LogitLens + CKA 这类
      观察性证据，没有"砍掉 k 层仍打平"的受控实验。
      当解释读，别当结论引用。                       -> §18.12

    ⑪ 六家里目前只有 DeepSeek-V4.1-Flash 用了（196B，
      第 1 和第 14 层）。V4 没用。                   -> §18.13
```

**回到 [15 章的总装图](15-五家总装图.md)**：Engram 是那张图上**第 ⑭ 个可改的位置**——一条从残差流旁边接出去、通向一张巨大查找表的支路。它是这一代架构里，除了注意力和 FFN 之外，**第三种能吃掉参数预算的结构**。
