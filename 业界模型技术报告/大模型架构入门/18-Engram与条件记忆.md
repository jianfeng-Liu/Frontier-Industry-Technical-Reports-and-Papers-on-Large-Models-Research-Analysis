# 18 · Engram 与条件记忆：MoE 之外的第二根稀疏轴

> **这是一章加餐**（2026-09 增补）。内容上它是 [10 章 MoE](10-MoE.md) 的姊妹章——MoE 是**条件计算**（conditional computation），Engram 是**条件记忆**（conditional memory），两者是同一个问题的两种解法。读完 10 章可以直接跳到这里。
>
> **这一章的目标**：讲清 DeepSeek-V4.1-Flash 里那个 **196B 参数、却几乎不产生任何 FLOPs** 的模块到底在干什么。
> 读完你应该能回答：一张查找表怎么可能有用？为什么必须哈希、为什么必须门控？它换来了什么、又付出了什么代价？"等效于加深模型"这个说法有多硬？
>
> **术语先摆这里**（本教程惯例，缩写第一次出现必须给全称）：
> **Engram** —— 论文自造的模块名，词源是神经科学的"记忆痕迹"，没有缩写展开。
> **n-gram** —— 连续 n 个 token 组成的片段，如 3-gram = 相邻三个 token。
> **FLOPs** —— Floating Point Operations，浮点运算次数，衡量"算了多少"。
> **HBM** —— High Bandwidth Memory，显卡上的高带宽显存。
> **DRAM** —— Dynamic Random Access Memory，主板上的普通内存（比 HBM 大得多、慢得多）。
> **PCIe** —— Peripheral Component Interconnect express，显卡和主板之间的那条总线。

## 18.0 ⚠️ 先纠正一个最容易犯的错误

很多介绍（包括我最初的讲法）会说 Engram"几乎免费"。**这句话是错的，或者至少是误导的。**

"免费"描述的是**代价小**，不是**有收益**。Engram 在推理吞吐这一格上是**负的**：

```
┌──────────────────────────────────────────────────────────────┐
│  Engram 这笔交易，必须拆成【四个独立的格子】来看：             │
│                                                               │
│      参数量    ↑  +196B      （V4.1 的实测配置）              │
│      FLOPs     ≈  不涨        ★ 这才是它真正的卖点            │
│      推理吞吐  ↓  −1.9% ~ −2.8%   ← 它是【减速】的           │
│      模型能力  ↑  多项基准 +2 ~ +5 分                         │
└──────────────────────────────────────────────────────────────┘
```

对比一下另外两条"让模型更强"的路：

| 路线 | 参数量 | FLOPs | 推理吞吐 | 备注 |
|---|---|---|---|---|
| 加层数 / 加宽（Dense） | ↑ | **↑↑** | **↓↓** | 每 token 都要多算一遍 |
| 加 MoE 专家（[10 章](10-MoE.md)） | ↑↑ | ≈ 不涨 | ↓ | all-to-all 通信变贵 |
| **Engram** | ↑ | **≈ 不涨** | ↓ 一点点 | 只多一次查表 + 一次 PCIe 搬运 |

> 🔑 **Engram 是三条路里唯一一条"FLOPs 完全不涨"的**。它的 −2.8% 不是算力开销，是**数据搬运**开销（把查到的向量从主机内存搬到显卡）。
>
> ⚠️ **所以：Engram 属于"能力"侧，不属于"提速"侧。** V4.1-Flash 真正提速的组件是另外一批（CED、CSA2、分层稀疏索引器、FP4 主 KV cache、Single-Pass mHC、DSpark），Engram 反而是从那笔提速预算里**扣掉 2.8%** 的那一项。见 [../DeepSeek-V4.1-Flash.md](../DeepSeek-V4.1-Flash.md) 第九节。

## 18.1 出发点：模型认一个人名，要烧掉六层

论文 §6.1 引了 Ghandeharioun et al. (2024) 的一个可解释性实验。用 LogitLens / PatchScope 这类工具，把模型每一层的中间状态**翻译回人话**，看它在读到"Diana, Princess of Wales"这串 token 时，脑子里想的是什么：✅

```
    层 1-2   →  "Wales：英国的一个组成国"
    层 3     →  "Wales：欧洲的一个国家"
    层 4     →  "Princess of Wales：女性君主的头衔"（还没定位到人）
    层 5     →  "Princess of Wales：威尔士亲王的妻子"（还是没定位到人）
    层 6     →  ★ "Diana, Princess of Wales (1961-1997)，查尔斯的第一任妻子……"
```

**读一遍这张表，你会有一个很直接的感受：**

```
┌──────────────────────────────────────────────────────────────┐
│  模型花了【六层的注意力 + FFN】，                              │
│  做的事情本质上是一次【查字典】。                              │
│                                                               │
│  "Diana / Princess / of / Wales" 这四个 token 连在一起        │
│   → 指向一个固定的实体                                        │
│                                                               │
│  这是一条【静态的、和上下文无关的】事实。                       │
│  它不需要"推理"，它只需要"记住"。                              │
│                                                               │
│  ★ 但今天的 Transformer 【没有查表这个原语】。                 │
│    它只有 Attention 和 FFN，只能用【计算】去模拟【记忆】。      │
└──────────────────────────────────────────────────────────────┘
```

Engram 的全部想法就一句话：

> 🔑 **给 Transformer 补上一个"查表"原语，把那些本来靠算力硬凑出来的静态模式，改成直接查出来。**

省下来的层数和算力，让模型拿去做真正需要推理的事。

## 18.2 结构：五步

先看整体，再逐步拆。

```
  输入 token 序列  x_1 ... x_t
        │
        ① tokenizer 压缩       Apple / ␣apple / APPLE  →  归成同一个 id
        │
        ② 取后缀 n-gram        以当前 token 结尾的 2/3/4 元组
        │                       ("princess","of","wales")
        ③ 多头哈希 → 查表      每个元组算出 8 个不同的行号，查 8 张表
        │                       得到一个拼起来的向量 e_t
        │
        ④ 上下文门控           拿主干当前的隐状态 h_t 去"审一遍" e_t
        │                       算出一个 0~1 的标量 α_t
        │
        ⑤ 加回残差流           H ← H + α_t · (e_t 投影后的值)
        ▼
   继续走后面的层
```

第 ①②③ 步**只依赖输入 token 本身**，和模型算到哪一步无关——这一点后面 §18.8 会变成一个巨大的系统优势，先记住。
第 ④ 步是唯一依赖上下文的地方，也是这个模块和"普通 n-gram 查表"的本质区别。

---

## 18.3 第①步：tokenizer 压缩

一个直接的麻烦：同一个词在 tokenizer 里有很多长相。

```
    "Apple"      → id 12345
    " apple"     → id 67890      （前面带空格）
    "APPLE"      → id 24680
    "Apple"（句首）→ 又一个 id
```

对"查表"来说这是纯浪费——它们指向同一个语义，却占了四个不同的地址，把表撑大了四倍，还把统计量摊薄了。

Engram 的做法：定义一个**满射**（surjective，多对一）映射 `P: V → V'`，做 NFKC 规范化（Unicode 的一种标准化形式，把全角/半角、组合字符等归一）+ 转小写，把它们合并成同一个 id。✅

```
    P("Apple") = P(" apple") = P("APPLE") = P(" Apple") = "apple"
```

> ✅ 论文实测：对一个 **128k 词表**，有效词表大小**减少 23%**。
>
> ⚠️ 注意这是**只用于查表寻址**的压缩。模型正常的输入 embedding 和输出 LM head 还是用原始 tokenizer，没被改。丢掉大小写信息在"查静态模式"这件事上不要紧，在"预测下一个 token"上会要命。

消融实验里，去掉这一步（`w/o token compress`）是**损失最大的三个改动之一**。✅

---

## 18.4 第②步：后缀 n-gram

在位置 `t`，取**以 t 结尾**的 n 元组：

```
    g_{t,n} = ( x'_{t-n+1}, ..., x'_{t-1}, x'_t )        （x' 是压缩后的 id）
```

对 n = 2, 3, ..., N 各取一个。V4.1 用的是 **n ∈ {2, 3, 4}**。✅

```
    句子：  ... the  media  impact  of  Diana ,  Princess  of  Wales
                                                              ↑ t

    2-gram：           ("of", "wales")
    3-gram：  ("princess", "of", "wales")
    4-gram：  (",", "princess", "of", "wales")
```

**为什么是"后缀"而不是"窗口"？**
因为语言模型是因果的（causal，只能看左边）。后缀 n-gram 保证不偷看未来的 token，可以直接用在自回归生成里。

> ⚠️ 也正因为是后缀，Engram 天然擅长的是**"这个短语在这里结束了"**这种模式。§18.11 的门控可视化会看到，它确实是在短语的**最后一个 token** 上开火。

---

## 18.5 第③步：多头哈希——表放不下怎么办

一个 3-gram 的可能组合数是 `V'³`。就算压缩后 V' ≈ 98k，也是 `9.4 × 10^14` 种。**不可能给每种组合都开一行。**

标准解法：**哈希**。把任意长度的元组，压成一个固定范围内的行号。

```
    z_{t,n,k} = φ_{n,k}( g_{t,n} )        φ 是轻量的乘法-异或哈希
    e_{t,n,k} = E_{n,k}[ z_{t,n,k} ]      去第 k 张表的第 z 行取一个向量
```

然后把所有阶数 n、所有头 k 的结果**拼接**（‖ 表示 concat）：

```
             N     K
    e_t  =   ‖     ‖   e_{t,n,k}
            n=2   k=1
```

**为什么要"多头"？** 因为哈希一定会撞（collision）——两个不相干的短语算出同一个行号，查出同一个向量。

```
┌──────────────────────────────────────────────────────────────┐
│  单头：撞了就是撞了，"红烧肉" 和 "薛定谔" 拿到同一个向量。      │
│                                                               │
│  8 头（8 个不同的哈希函数 + 8 张不同的表）：                   │
│      要 8 个哈希【同时】把这两个短语撞到一起，概率 ≈ 0         │
│      → 拼起来的 e_t 仍然能把它们区分开                        │
│                                                               │
│  ★ 这就是 Bloom filter / count-min sketch 的老套路：          │
│    用【多个独立哈希】把碰撞概率压到可以忽略。                   │
└──────────────────────────────────────────────────────────────┘
```

> ✅ V4.1 的配置：**8 个哈希头**，每张表约 **1600 万行**，而且**各张表的行数取互不相同的质数**。
>
> ⚠️ 取质数是哈希表的标准工程手段：表长互质能让不同表的碰撞模式尽量不相关，避免"在 A 表撞了的，在 B 表也倾向于撞"。

**numpy 伪代码**（整个检索过程）：

```python
def engram_lookup(ids, t, tables, orders=(2, 3, 4), K=8):
    """tables[n][k] 是第 n 阶、第 k 头的嵌入表，形状 [M_{n,k}, d_sub]"""
    ids = normalize(ids)                       # ① tokenizer 压缩
    parts = []
    for n in orders:
        gram = tuple(ids[t - n + 1 : t + 1])   # ② 后缀 n-gram
        for k in range(K):
            M = tables[n][k].shape[0]          # 表长，取质数
            z = mul_xor_hash(gram, seed=(n, k)) % M   # ③ 第 k 个哈希
            parts.append(tables[n][k][z])      #    查一行
    return np.concatenate(parts)               # e_t
```

注意这段代码里**一次矩阵乘法都没有**。全是取地址 + 读内存。这就是"FLOPs ≈ 0"的来源。

## 18.6 第④步：门控——只有一个 key 的注意力

到这里为止，Engram 还只是个查字典的。**但直接把 `e_t` 加进残差流是危险的**：

```
┌──────────────────────────────────────────────────────────────┐
│  e_t 有三个毛病：                                              │
│                                                               │
│  ① 它是【上下文无关】的先验。                                  │
│     "苹果" 查出来的向量分不清水果和公司。                       │
│                                                               │
│  ② 它可能是【哈希撞出来】的垃圾。                              │
│                                                               │
│  ③ 大多数位置根本【没有】静态模式可查。                        │
│     "的"、"了"、随机组合的三元组 —— 查出来是噪声。             │
│                                                               │
│  ★ 所以必须有个开关：让主干说了算。                            │
└──────────────────────────────────────────────────────────────┘
```

做法（论文 Eq. 3–4）✅：

```
    k_t = W_K · e_t                                  ← 把查出来的东西变成一个"key"
    v_t = W_V · e_t                                  ← 和一个"value"

              ⎛  RMSNorm(h_t)ᵀ · RMSNorm(k_t)  ⎞
    α_t = σ ⎜ ────────────────────────────── ⎟      σ 是 sigmoid
              ⎝              √d                ⎠

    ṽ_t = α_t · v_t
```

**这个式子你其实已经见过了。** 把它和 [05 章](05-注意力机制.md) 的注意力对照：

```
    标准注意力：  softmax( q·Kᵀ / √d ) · V        K 有 L 行（L 个 token）
    Engram 门控： sigmoid( h·kᵀ / √d ) · v        K 只有【1 行】
```

> 🔑 **当 key 只有一个的时候，softmax 退化成 sigmoid。**
> softmax 在多个候选之间分配权重（一行加起来 = 1）；只有一个候选时"分配"没有意义，剩下的唯一问题是"要不要"，那就是一个 0~1 的开关。
>
> 所以 Engram 的门控**不是新机制**，它就是一次"只有一个候选的注意力"。查询是主干的 `h_t`（有上下文），被查的是 `k_t`（没上下文）。**如果查出来的东西和当前上下文对不上，α_t → 0，这次查表就当没发生过。**

这解决了上面三个毛病：语义对不上→关掉；哈希撞出垃圾→对不上→关掉；没有模式可查→查出来的东西和 h_t 无关→关掉。

消融里去掉门控（`w/o gating`）同样是**三个最大退化之一**。✅

## 18.7 第⑤步：加回残差流

```
    H ← H + Attn(H) + MoE(H) + α_t · ( W_V · e_t )
                                └─────────────────┘
                                    Engram 的贡献
```

就是 [03 章](03-残差流.md) 讲的那条总线，多接了一路旁支。**不改变任何形状，不影响任何其他模块**——这也是它能被塞进一个已有架构的原因。

**多分支（multi-branch）**：V4.1 用的 mHC（Manifold-Constrained Hyper-Connections，见 [03 章](03-残差流.md)）把残差流拆成 M = 4 条并行的流。Engram 的做法是：✅

```
    嵌入表          →  所有分支【共享】     （最贵的部分只存一份）
    W_V（值投影）   →  所有分支【共享】
    W_K（键投影）   →  每个分支【各有一个】 → 每个分支算自己的 α_t
```

> ⚠️ 这个设计有个很实际的动机：一个共享的 `W_V` 加 M 个 `W_K` 可以**融合成一次 FP8 稠密矩阵乘法**，对 GPU 友好。同时又保留了"不同分支对同一条记忆有不同取舍"的自由度。
>
> 消融里 `w/o multi branch` 也是三个最大退化之一。✅

## 18.8 系统：为什么 196B 参数能放在主机内存里

这是 Engram 和 MoE 最大的结构性差别，值得单独一节。

```
┌──────────────────────────────────────────────────────────────┐
│  MoE 路由：   要先算出 h_t，才知道走哪几个专家                 │
│               → 【运行时才知道地址】                          │
│               → 必须提前把所有专家都摆在 HBM 里等着            │
│                                                               │
│  Engram 检索：地址只由【输入 token 序列】决定                  │
│               → token 一定，地址就定了                        │
│               → ★ 可以在这一层执行【之前】就把地址算出来       │
└──────────────────────────────────────────────────────────────┘
```

论文管这个叫 **deterministic addressing**（确定性寻址）。它直接换来两件事：✅

**训练时**：表按 GPU 切片（模型并行），前向用 All-to-All 收集需要的行，反向用 All-to-All 发回梯度。总容量随卡数**线性增长**。

**推理时**：整张表放在**主机 DRAM**（比 HBM 便宜、大几十倍），需要的行**异步预取**。因为地址提前知道，可以在前面几层还在算的时候，就把 PCIe 搬运做完：

```
    时间 →
    GPU：  [ 第 0 层计算 ][ 第 1 层计算 ][ 第 2 层（Engram）]
    PCIe：      [ 预取 e_t ........ ]  ✔ 到齐
                └─── 被第 0~1 层的计算【挡住了】，看不见 ───┘
```

这就是为什么 Engram 模块**必须放在靠前但不是第一层**——放太靠前，前面没有足够的计算量来挡住搬运延迟；放太靠后，见下一节，效果会掉。

> ✅ 论文还指出：n-gram 的频率服从 **Zipf 分布**（Zipfian distribution，少数模式占绝大多数访问）。所以可以做**多级缓存**：热的行缓存在 HBM，温的在 DRAM，冷的长尾放 NVMe SSD。
>
> ⚠️ 但 §6.4 的实测**没有**用这个优化——它把**所有**检索都强制走 PCIe，属于最保守的下界。所以下一节那个 −2.8%，是**悲观值**。

## 18.9 放在哪一层：一个真实的取舍

论文 §6.2 做了一个很干净的实验：固定 1.6B 的 Engram 预算，把它整块塞进第 1~12 层里的某一层，扫一遍。✅

```
    3B MoE 基线                    Val Loss = 1.808
    ────────────────────────────────────────────────
    单块塞在第 2 层  ★ 最优         Val Loss = 1.770
    单块塞在第 1 层                 略差
    往深了塞（3,4,...,12）          持续变差
    ────────────────────────────────────────────────
    拆成两小块，放第 2 层 + 第 6 层  Val Loss = 1.768   ← 最终采用
```

**为什么早比晚好，但第 1 层又不如第 2 层？** 两股力量在打架：

```
┌──────────────────────────────────────────────────────────────┐
│  往【早】放的理由：                                            │
│    静态模式的重建本来就发生在底层（§18.1 那张表：层 1-6）。     │
│    要替它省事，就得赶在它开始费劲之前。                        │
│                                                               │
│  往【晚】放的理由：                                            │
│    门控要用 h_t 当查询。第 1 层的 h_t 还没经过任何注意力，      │
│    几乎不含上下文 → α_t 判断不准。                            │
│                                                               │
│  ★ 第 2 层是平衡点：已经过了一轮注意力（h_t 有上下文了），      │
│    但还没轮到主干去硬凑那些静态模式。                          │
│                                                               │
│  ★ 拆成两块更好：第一块吃"早"的红利，第二块吃"上下文准"的红利。 │
└──────────────────────────────────────────────────────────────┘
```

> ✅ 论文实测配置：Engram-27B 放在第 **2** 层和第 **15** 层。
> ✅ V4.1-Flash 放在第 **1** 层和第 **14** 层。
> ⚠️ V4.1 比论文更靠前一层，报告没解释原因。可能和它的主干层数、mHC 结构不同有关，也可能只是重新调过。

另外还有一层系统上的理由：拆成两块，正好对应 §18.8 的多级缓存——两块的预取窗口可以分别安排。

## 18.10 稀疏度分配：MoE 和 Engram 怎么分预算

这是论文最有价值的一节（§3），也是它敢叫"a new axis of sparsity"（一根新的稀疏轴）的底气。

先定义三个量：✅

```
    P_tot     总参数量（不含词表 embedding 和 LM head）
    P_act     每个 token 实际激活的参数量  →  决定 FLOPs
    P_sparse  = P_tot − P_act
              ★ "不花算力的参数预算"：没被选中的专家 + 没被查到的嵌入行
```

然后问：**这笔 P_sparse，该分给 MoE 还是分给 Engram？**

```
    分配比 ρ ∈ [0,1]：
        P_MoE     = ρ · P_sparse
        P_Engram  = (1 − ρ) · P_sparse

        ρ = 1     →  纯 MoE（今天所有模型的做法）
        ρ = 0     →  纯 Engram
```

固定 `P_tot` 和 `P_act`（所以**参数量相同、FLOPs 也相同**），只调 ρ，扫一遍：

```
   Val Loss
      │
  1.725│●  ρ=100%（纯 MoE，1.7248）
      │ ╲
      │  ╲
      │   ╲___
  1.711│       ●___●  ★ ρ ≈ 75~80% 最优（1.7109）
      │      ╱
      │  ___╱
      │ ╱                        ← ρ 再小，推理能力开始崩
      └──┬────┬────┬────┬────┬──→  ρ
        40%  60%  80%  100%
```

三个结论，每一条都值得单独记住：✅

```
① 纯 MoE 【不是最优的】。
   把 20~25% 的稀疏预算挪给 Engram，loss 更低（Δ = 0.0139）。

② 挪得很狠也不塌。
   ρ 降到 40%（专家从 106 个砍到 46 个），性能仍然【追平】纯 MoE。

③ 最优点很稳。
   2e20 和 6e20 两个算力量级下，最优 ρ 都在 75~80%。
```

**这条 U 形曲线的两端在说什么：**

```
   ρ → 100%（纯 MoE）：  没有专门的记忆，只能用深度和算力去【重建】静态模式  → 浪费
   ρ → 0%（纯 Engram）： 没有条件计算，需要动态推理的任务垮掉  → 记忆替代不了计算
```

> 🔑 **记忆和计算是互补的两根轴，不是互相替代。** 这是全篇论文的核心主张，U 形曲线是它的直接证据。

另一个方向的实验（§3.2，"无限内存"）：固定主干，只把嵌入槽位从 2.58×10⁵ 扫到 1.0×10⁷（加了约 13B 参数），loss 在 log 坐标下**是一条直线**——严格的幂律。✅ 也就是说 Engram 提供了一个**可预测的、不花算力的**扩展旋钮。

## 18.11 它到底带来了什么：数字

论文 §4 的主实验很规矩：**同参数量 + 同激活参数量 + 同数据 + 同训练步数**，只把 72 个专家砍到 55 个，省下的参数换成 5.7B 的 Engram（ρ = 74.3%）。✅

| 基准 | MoE-27B | Engram-27B | Δ |
|---|---|---|---|
| Pile (loss ↓) | 1.960 | 1.950 | −0.010 |
| MMLU | 57.4 | 60.4 | **+3.0** |
| CMMLU | 57.9 | 61.9 | **+4.0** |
| **BBH** | 50.9 | 55.9 | **★ +5.0** |
| **ARC-Challenge** | 70.1 | 73.8 | **★ +3.7** |
| DROP | 55.7 | 59.0 | +3.3 |
| HumanEval | 37.8 | 40.8 | +3.0 |
| GSM8K | 58.4 | 60.6 | +2.2 |
| MATH | 28.3 | 30.7 | +2.4 |
| TriviaQA (EM) | 48.8 | 50.7 | +1.9 |

> ⭐ **最反直觉的一点**：涨得最多的**不是知识题**，是**推理题**（BBH +5.0、ARC-Challenge +3.7），连代码和数学也涨了。
>
> 一张查找表，为什么能提升推理？论文的解释就是 §18.1 那件事——**把底层用来拼凑静态模式的算力省下来了，主干可以拿去做别的**。TriviaQA（纯记忆题）只涨 1.9，反倒是涨得最少的之一。

**长上下文（§5，RULER 32k）** 更夸张：✅

| | MoE-27B (50k 步) | Engram-27B (46k 步，**同 loss**) |
|---|---|---|
| Multi-Query NIAH | 84.2 | **97.0** |
| 多跳变量追踪 VT | 77.0 | **87.2** |
| 高频词抽取 FWE | 73.0 | **98.6** |

> ✅ 这里的对照做得很讲究：Engram-27B 取的是**预训练 loss 和满训 MoE 相同**的那个中间检查点（46k 步 vs 50k 步），所以差异只能归因于架构，不能归因于"底座更强"。
>
> 论文的解释：Engram 把**局部依赖**的建模卸载掉了，注意力的容量就腾出来给**全局上下文**了。

## 18.12 它到底付出了什么：也要摆数字

### ① 吞吐是负的（§6.4，Table 4）✅

| 配置 | 吞吐 (tok/s) | 变化 |
|---|---|---|
| 4B-Dense 基线 | 9,031.62 | — |
| + 100B Engram（卸载到主机内存） | 8,858.28 | **−1.9%** |
| 8B-Dense 基线 | 6,315.52 | — |
| + 100B Engram（卸载到主机内存） | 6,140.02 | **−2.8%** |

测试条件：NVIDIA H800，512 条序列，长度 Uniform(100, 1024)，100B 的 Engram 层塞在第 2 个 Transformer block，推理框架是 nano-vLLM。

> ⚠️ **这 2.8% 是 PCIe 搬运，不是计算。** 而且如 §18.8 所说，这个实验强制所有检索都走 PCIe，没用 Zipf 缓存，是**保守下界**——真实系统里应该更小。
>
> ⚠️ 但"更小"不等于"零"，更不等于"提速"。**任何把 Engram 归到"推理加速技术"那一栏的说法都是错的。**

### ② 它承担了知识，也就成了单点（§6.3）✅

论文做了个压力测试：推理时**把 Engram 的输出整个掐掉**，主干不变，看还剩多少：

```
    事实知识类：
        TriviaQA        只剩 29%   ← 塌了
        PopQA           只剩 44%
        TriviaQA-ZH     只剩 44%

    阅读理解类：
        C3              还有 93%   ← 几乎没事
        RACE-Middle     还有 89%
        DROP            还有 81%
```

> 🔑 **一个非常干净的功能分工**：Engram 是**参数化知识的主仓库**，注意力主干负责**上下文里的东西**。掐掉记忆，模型立刻"失忆"，但"看着材料回答问题"的能力还在。
>
> ⚠️ 这个实验有训练-推理不一致的问题（模型训的时候有 Engram，测的时候没有），论文自己也承认，所以只挑了信噪比最高的两端来分析。别把中间那些 60~80% 的数字当精确结论。

### ③ "等效于加深模型"——这个说法有多硬

论文 §6.1 用两个可解释性工具论证 Engram "effectively increases the model's depth"：✅

- **LogitLens**：把每层的中间状态用最终的 LM head 投影出来，算它和最终输出分布的 KL 散度。Engram 版本在**早期层**的 KL 明显更低 → 更早"想清楚"。
- **CKA**（Centered Kernel Alignment，中心化核对齐，一种比较两组表示相似度的指标）：Engram-27B 的第 5 层，表示上最接近 MoE 基线的**第 12 层**。热力图的高相似对角线整体**向上偏移**。

> ⚠️ **这是我要给这一节打的最大一个问号。**
> LogitLens 和 CKA 都是**观察性**证据，说明"表示看起来像更深的层"。它**不等于**一个受控实验——论文**没有**做"Engram 版本砍掉 k 层、分数仍然打平"这种直接验证。
>
> 所以"等效加深"目前应该读作：**一个有可解释性证据支持的、合理的解释**，而不是一个已经量化的结论。真要说"能省几层"，现在没有数字。

| **DeepSeek-V4.1-Flash** | ⭐ ✅ **用了** | 196B 参数，第 1 和第 14 层，n ∈ {2,3,4}，8 头，每阶总维度 2048，每表约 1600 万行（质数），嵌入表和 K/V 投影全 FP8 |

**V4.1 相比原论文的两处改动** ✅：
1. **去掉了短因果卷积**——论文消融里这一项本来就"影响很小"（`w/o short conv` 几乎不掉），去掉合理。
2. **优化器从 Adam 换成动量 + Sinkhorn 平衡**（γ=0.18 / K=11 / τ=1e-3）。见 [13 章](13-优化器与Muon.md)。

**参数量能对上吗？** 自己算一遍：

```
    2 个模块 × 8 个哈希头 × 3 个阶数(n=2,3,4)  =  48 张表
    每张表 ≈ 1600 万行
    每行维度 = 2048 / 8 = 256

    48 × 16e6 × 256  =  1.966e11  ≈  196B    ✔ 和报告一致
```

> ✅ 这个数和 DeepSeek-V4.1-Flash 报告给出的 196B 对得上。
> ⚠️ 其中"每行维度 = 每阶总维度 / 头数"是我的推断（拼接式多头的标准做法），报告没有逐字写明。

## 18.14 和 MoE 的对照（一张表收口）

| | **MoE**（[10 章](10-MoE.md)） | **Engram**（本章） |
|---|---|---|
| 中文叫法 | 条件**计算** | 条件**记忆** |
| 稀疏的是什么 | 哪几个专家被算 | 哪几行嵌入被查 |
| 地址什么时候知道 | 运行时（要先算 h_t） | ⭐ **输入一给定就知道** |
| 能不能卸载到主机内存 | 很难 | ⭐ **可以**（靠确定性寻址预取） |
| 每 token 的 FLOPs | 有（k 个专家的前向） | ≈ 0（只有取址 + 一次小投影） |
| 主要成本 | all-to-all 通信 | PCIe 搬运 |
| 负载均衡问题 | ★ 严重，要专门治 | 哈希天然均匀，靠多头压碰撞 |
| 擅长 | 动态、依赖上下文的推理 | 静态、和上下文无关的模式 |
| 单独用行不行 | 行（今天都这么干） | 不行（ρ→0 时推理垮掉） |

> 🔑 **最优解是混合**：把 20~25% 的稀疏预算给记忆，剩下给计算。

## 18.15 本章小结

```
    ① Engram 给 Transformer 补了一个它一直没有的原语：【查表】。
      模型认出 "Diana, Princess of Wales" 本来要烧六层，
      现在可以查出来。                              → §18.1

    ② 五步：tokenizer 压缩 → 后缀 n-gram → 多头哈希查表
            → 上下文门控 → 加回残差流。
      前三步不依赖上下文，第四步才依赖。            → §18.2

    ③ ★ 门控就是【只有一个 key 的注意力】。
      softmax 在唯一候选上退化成 sigmoid。
      查出来的东西和上下文对不上，α_t → 0，当没查过。→ §18.6

    ④ ★★ 地址只由输入 token 决定（确定性寻址）。
      这一条换来了：表可以放主机内存 + 异步预取藏在
      前面几层的计算里。这是 MoE 做不到的。          → §18.8

    ⑤ 放在第 2 层最好，拆成两块（第 2 + 第 6）更好。
      早放能替主干省事，但太早门控又判断不准。       → §18.9

    ⑥ ★★ U 形分配律：纯 MoE 不是最优。
      把 20~25% 的稀疏预算挪给记忆，loss 最低；
      挪走 60%（ρ=40%，专家 106→46）都还能追平。
      记忆和计算互补，不互相替代。                    → §18.10

    ⑦ 同参数量同 FLOPs 下，涨得最多的是【推理题】
      （BBH +5.0、ARC-C +3.7），不是知识题。
      长上下文 Multi-Query NIAH 84.2 → 97.0。       → §18.11

    ⑧ ⚠️ 代价：推理吞吐【掉】1.9% ~ 2.8%（PCIe 搬运）。
      Engram 是【能力】技术，不是【提速】技术。
      任何把它归到加速那一栏的说法都是错的。         → §18.0 / §18.12

    ⑨ ⚠️ "等效于加深模型" 目前只有 LogitLens + CKA 这类
      观察性证据，没有"砍掉 k 层仍打平"的受控实验。
      当解释读，别当结论引用。                       → §18.12

    ⑩ 五家里目前只有 DeepSeek-V4.1-Flash 用了（196B，
      第 1 和第 14 层）。V4 没用。                   → §18.13
```

**回到 [15 章的总装图](15-五家总装图.md)**：Engram 是那张图上**第 ⑭ 个可改的位置**——一条从残差流旁边接出去、通向一张巨大查找表的支路。它是这一代架构里，除了注意力和 FFN 之外，**第三种能吃掉参数预算的结构**。
