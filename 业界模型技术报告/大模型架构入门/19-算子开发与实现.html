19 · 算子开发与实现：架构决策落到 GPU 上会变成什么

这是一章加餐（2026-09 增补，2026-09 重写）。前面十八章讲的是模型结构长什么样，这一章讲这些结构落到 GPU 上之后会遇到什么。读完 05 章（注意力机制）、07 章（MHA 到 MLA）、10 章（MoE） 可以直接跳到这里。

这一章的目标：让你在看到一个架构决策（head_dim 选 128、KV 头数砍到 8、Top-K 从 2 调到 8、精度改成 FP8）的时候，能立刻说出它在算子层会变成什么——多一个 kernel、少一次搬运、通信量翻四倍、还是逼出两套不同的实现。

读完你应该能回答：为什么几乎所有模型的 head_dim 都是 128？MLA 的"矩阵吸收"到底改变了什么、又没有改变什么？MoE 的 Top-K 是怎么同时造出两个完全不同的算子问题的？为什么 RMSNorm 这种 FLOPs 可以忽略的算子，反而会决定推理延迟？

术语先摆这里（本教程惯例，缩写第一次出现必须给中英文全称）：
算子 / kernel（内核）—— 一次可以在 GPU 上独立发起执行的函数，比如一次矩阵乘、一次归一化。它是"计算图"落到硬件上的最小执行单元。
GEMM —— General Matrix Multiply，通用矩阵乘法。大模型九成以上的浮点运算是它。
FLOPs —— Floating Point Operations，浮点运算次数。全教程按一次"乘加"算 2 FLOP（即 2·m·n·k）。
HBM —— High Bandwidth Memory，高带宽显存。GPU 的"主内存"，大但相对慢。
SRAM —— Static Random-Access Memory，片上静态存储。极快但极小，是算子优化里所有"分块"手段的舞台。
Tensor Core（张量核心）—— 专做矩阵乘累加的硬件单元，比通用的 CUDA Core 快约 15 倍。
MMA —— Matrix Multiply-Accumulate，矩阵乘累加。Tensor Core 的硬件指令，形状固定（如 m16n8k16）。
wgmma —— Warpgroup MMA，线程束组矩阵乘累加。Hopper（H100）新增的 MMA 指令，由 128 个线程协同发射。
TMA —— Tensor Memory Accelerator，张量内存加速器。Hopper 新增的异步搬运引擎。
SFU —— Special Function Unit，特殊函数单元。算 exp、sin 这类超越函数的硬件，和 Tensor Core 是两套单元。
Roofline（屋顶线）—— 判断一个算子受限于算力还是受限于带宽的模型，本章唯一的分析工具。
算术强度 —— Arithmetic Intensity，每搬运一个字节能做多少次浮点运算（FLOP/Byte）。
屋脊点（ridge point）—— 屋顶线上那个拐点 = 峰值算力 ÷ 内存带宽。H100 的 BF16 屋脊点是 295。
EP —— Expert Parallelism，专家并行。把 MoE 的专家切到多张卡上。
All-to-All（全交换）—— 每张卡都要给其他每张卡发一份数据的通信原语，MoE 的主要开销。
MFU —— Model FLOPs Utilization，模型算力利用率 = 实际达到的 FLOPs/s ÷ 硬件峰值。
ULP —— Unit in the Last Place，最后一位的单位。衡量两个浮点数差多少个"最小可表示的刻度"。
epilogue（尾声）—— GEMM 算完、结果还在寄存器里时顺手做掉的那一小段计算（加偏置、激活、归一化等）。

19.1 本章的问题：一个方框，落到 GPU 上是几个 kernel

15 章的总装图 里，一层 Transformer 是几个方框。但 GPU 不认识"方框"，GPU 只认识 kernel（内核，一次可以在 GPU 上独立发起执行的函数）。把一层 decode 摊开数一遍：

架构图上的一个方框 GPU 上实际发起的 kernel
RMSNorm 1 个（逐元素 + 一次行归约）
QKV 投影 1 个 GEMM（gate/up 常合并成一个）
RoPE 1 个（逐元素旋转，常融进上一步的尾巴）
Attention 1 个（FlashAttention / PagedAttention）
输出投影 1 个 GEMM
残差加 1 个（常融进上一步）
RMSNorm 1 个
MoE 路由（打分 + TopK + 排序） 3~5 个（含一次非规则的 gather）
All-to-All dispatch 1 次通信
专家 FFN 1 个 Grouped GEMM（或 3 个：gate / up / down）
All-to-All combine 1 次通信
残差加 1 个
合计 ⭐ 约 12 ~ 18 个 kernel / 层

一个 60~80 层的模型，一次 decode 步要发起上千个 kernel。这件事本身就会变成瓶颈——§19.6 会把这笔账算出来。

🔑 本章的整个视角就一句话：架构图上改一个数字，下面这三件事至少有一件会跟着变。

变的是什么 典型例子
① 形状 head_dim 从 128 改成 64 → Tensor Core 利用率的天花板直接掉一半
② kernel 的数量和边界 MLA 加了矩阵吸收 → 同一个注意力模块变成两套 kernel
③ 搬运/通信的量 MoE 的 Top-K 从 2 调到 8 → All-to-All 通信量直接 ×4

⚠️ 注意这三件事里没有"FLOPs"。 大模型时代绝大多数性能问题不是"算不过来"，是"数据供不上"或者"kernel 发不完"。下一节把这句话变成一个数字。

19.2 全章唯一一把尺：屋脊点 295

本章所有数字统一用 H100 SXM5（H800 是它的削减版，算力相同、互联带宽被限）。这组数请背下来，全系列笔记通用：

量 值 备注
BF16 稠密峰值 989 TFLOPS ⚠️ 官方表里那个 1979 是"带 2:4 稀疏"的，常规算子用不上
FP8 稠密峰值 1979 TFLOPS 正好是 BF16 的两倍
FP32（CUDA Core） 67 TFLOPS —
HBM3 80 GB / 3.35 TB/s —
屋脊点（BF16） 295 FLOP/Byte = 989 ÷ 3.35
屋脊点（FP8） 591 FLOP/Byte = 1979 ÷ 3.35
Tensor Core vs CUDA Core ⭐ 约 15 倍 = 989 ÷ 67

⚠️ 这里埋着本章第一个高频错误：BF16 和 FP8 的峰值表里都有 1979 这个数，但含义完全不同——BF16 的 1979 是稀疏值，FP8 的 1979 才是稠密值。拿 BF16 的 1979 去除 3.35，会算出 591，把 BF16 的屋脊点错记成 FP8 的。这一错，下面所有"这个算子是 Compute Bound 还是 Memory Bound"的判断就全反了。

📌 屋顶线的完整推导、六个真实算子的算术强度逐项计算、MFU 怎么算，在 ../../大模型算子开发/02-屋顶线与性能剖析.md §2.2–§2.6。本章只用结论。

怎么用这把尺：算出一个算子的算术强度 I = FLOP ÷ 搬运字节数，和 295 比。

    I < 295   ->  Memory Bound（访存受限）：算力在等数据，优化方向是【少搬】
    I > 295   ->  Compute Bound（算力受限）：数据够用，优化方向是【算得更快】

⚠️ 一个必须纠正的流行说法："Prefill 是算力受限，Decode 是访存受限"

这句话只有下半句无条件成立。上半句有前提。

拿 09 章 讲的那个 FFN 的 up 投影做例子（形状取 LLaMA-3-8B 的配置，和 ../../大模型算子开发/09-推理侧算子.md 全章保持一致），形状 (M, 4096) × (4096, 14336)，BF16。M 就是"这一步同时处理多少个 token"：

    FLOP  = 2 · M · K · N
    Byte  = 2 · (M·K + K·N + M·N)

                 M · K · N
    I  =  ----------------------------
           M·K  +  K·N  +  M·N

代进去扫一遍 M：

M（这一步处理几个 token） 算术强度 I 和屋脊点 295 比 结论
1（Decode） 1.0 差 295 倍 Memory Bound
6（一个"你好"级别的短 prompt） 约 6 差 49 倍 ⚠️ 照样 Memory Bound
64 约 61 差 4.8 倍 还是 Memory Bound
⭐ 325 ⭐ 295 正好持平 ★ 临界点
2048（一段正常长度的 prompt） 1247 超出 4.2 倍 Compute Bound

🔑 规律一眼就看出来了：在 K·N 这一项占主导的区间里，算术强度约等于 M，也就是约等于 prompt 长度。

⚠️ 所以"Prefill 是 Compute Bound"要加个前提：prompt 得够长。临界点在这个形状下是 325 个 token，工程上记"约 300~400"。 一个 6 token 的 Prefill 和 Decode 一样是访存受限，给它上一堆算力侧的优化不会有任何效果。

⚠️ 这一条对架构讨论很要命：agent 类应用动辄十万 token 的 prompt，Prefill 确实是 Compute Bound；但一个聊天应用里大量的"嗯""继续""再说说"，Prefill 短得可怜，走的是完全不同的性能路径。任何"我们的模型 Prefill 提速了 X%"的说法，都必须先问 prompt 多长。

📌 完整推导（含临界点 M = 325 的解方程过程）在 ../../大模型算子开发/09-推理侧算子.md §9.1 和 §9.8.3。

19.3 决策① head_dim = 128：一个被 Tensor Core 钉死的数字

翻一遍 15 章 的五家配置，head_dim（每个注意力头的维度，见 05 章 §5.6）几乎全是 128。这不是巧合，也不完全是"效果好"——它是被硬件形状钉住的。

三条互相独立的理由，全都指向 128

理由一：Tensor Core 的指令形状是固定的。

    Ampere / Hopper 的 BF16 硬件指令：
        mma.m16n8k16
            ^^^ ^^ ^^^
            |   |  +--- K = 16
            |   +------ N = 8
            +---------- M = 16      一条指令一次只处理这么大一小块

    Hopper 新增的 Warpgroup（线程束组）指令：
        wgmma.m64nNk16              M = 64，N 可取 8 / 16 / ... / 256，K = 16

所有维度都得对齐到 16，否则最后那一块要补零（padding），补的部分照样占满 Tensor Core 的时间，算出来的结果扔掉。128 = 8 × 16 ✓；64 = 4 × 16 ✓；但 100、96、80 这些数就会让分块变得难看。

理由二：128 个 BF16 正好是两条缓存行。

    head_dim 128 × 2 字节（BF16） = 256 字节 = 2 × 128 字节缓存行  ✓ 完美对齐
    head_dim 96  × 2 字节         = 192 字节 = 1.5 条缓存行        ✗ 每次都跨行

这直接决定合并访存（memory coalescing）能不能满速，也决定共享内存的 swizzle（交错排布，用来避开 bank conflict）好不好设计。📌 这两件事的机制在 ../../大模型算子开发/01-GPU硬件基础.md §1.4 和 §1.5。

理由三（最反直觉的一条）：head_dim 越小，注意力算子的 Tensor Core 利用率上限越低。

这条只有在算子层才看得见。注意力 kernel 里有两类操作：矩阵乘（走 Tensor Core）和 exp（走 SFU，Special Function Unit，特殊函数单元）。H100 上一次 exp 比一次等价的矩阵乘慢约 254 倍（✅ FA3 论文的实测比值）。两者的时间比是：

    exp 时间 / 矩阵乘时间  =  254 / (4 · d)        d = head_dim

        d = 128  ->  254 / 512  = 50%     exp 占矩阵乘的一半时间
        d = 64   ->  254 / 256  = 99%     ★ exp 和矩阵乘【一样贵】

🔑 换句话说：head_dim 砍一半，注意力里那些"不是矩阵乘的部分"占比翻倍。 d=64 时，就算 Tensor Core 无限快，整个 kernel 也快不过 SFU 那一半——这和 Tensor Core 有多强完全无关，是架构选的那个数字决定的天花板。

⚠️ 所以"把 head_dim 调小、多开几个头"这个看起来很中性的决策，在算子层是有代价的，而这个代价在架构图上完全看不见。

📌 254 这个比值的来源、以及 FA3 怎么把 SFU 和 Tensor Core 重叠起来，见 ../../大模型算子开发/04-FlashAttention全系.md §4.5.1–§4.5.3。

顺带说清楚 FlashAttention 的真实水平

架构讨论里经常引用 FlashAttention 的性能数字，而这些数字被传错的频率极高：

版本 H100 前向 FP16 吞吐 占 989 TFLOPS 峰值 说明
朴素实现 约 100~200 TFLOPS 10~20% 中间的 N×N 矩阵要落 HBM
FA2（2023） ⭐ 约 350 TFLOPS ⭐ 约 35% ✅ FA3 官方博客
FA3（2024） ⭐ 约 740 TFLOPS ⭐ 约 75% ✅ FA3 论文
FA3 + FP8 约 1200 TFLOPS — ✅ 官方，接近 1.2 PFLOPS

⚠️ 别写成 540 / 810。 540~570 是 FA3 开发过程中"只把指令换成 wgmma + TMA、还没做 SFU 重叠"的中间态，不是发布水平。

⚠️ FA2 在 H100 上只有 35%，不是因为 FA2 退步了，是因为它用的是 Ampere 的 mma.sync 指令，在 Hopper 上最多摸到峰值的约三分之二。A100 上 FA2 能到 50~73%——百分比的分母是不同卡的峰值，不能横向比。

19.4 决策② GQA / MLA：省的是字节，改的是算子边界

07 章 已经把"每 token 存多少字节"算得很细，本节不重复那张表，只讲这些方案落到算子上带来了什么。

先把那个公式钉死（因为它被套错的频率极高）

    KV cache 每 token 每层 = 2 × n_kv_heads × head_dim × 每元素字节数
                             ^                ^
                          K 和 V 两份     ⚠️ 是【KV 头数】，不是 query 头数

拿 LLaMA-3-8B（32 层，32 个 query 头，8 个 KV 头，head_dim 128，BF16）验一遍：

算法 每层每 token 全部 32 层 对不对
✅ 正确：2 × 8 × 128 × 2 4,096 B 128 KiB ✓
❌ 错误：2 × d_model × 2 = 2 × 4096 × 2 16,384 B 512 KiB ✗ 高估 4 倍

⚠️ 为什么错得这么整齐地是 4 倍？ 因为 d_model = n_q_heads × head_dim。用 d_model 套公式，等于偷偷把 KV 头数换成了 query 头数——算出来的是 MHA 的答案。高估的倍数正好等于 GQA 的分组数（这里 32÷8 = 4）。模型分组越狠，这个错就越离谱。

⚠️ MLA 的行更不能套这个公式：它不乘 2（K 和 V 从同一个潜向量解压）、也没有头数（所有头共用一份）。⭐ 而且——MLA 照样要缓存压缩后的 c_KV。 "矩阵吸收"吸的是上投影矩阵（W^UK 吸到 Q 侧、W^UV 吸到输出侧），不是把 K 直接算出来。任何说法只要推出"吸收之后就不用存 c_KV 了"，就一定错了——那样 cache 里躺的是全尺寸的 K，压缩率归零。完整推导见 07 章 §7.4。

算子后果①：GQA 让注意力 kernel 多了一步"广播"

MHA 里 query 头和 KV 头一一对应，kernel 读 KV 直接按头索引。GQA 下 8 个 query 头共享 1 个 KV 头，kernel 里要做一次头维度的广播：

    朴素做法（FA1 时代）：把 KV 在显存里【物理复制】4 份，凑成 32 个头
        -> KV cache 的显存优势【当场还回去】，白省了

    正确做法（FA2 起原生支持）：不复制，让 4 个 query 头的分块
        【共用同一块搬进 SRAM 的 KV】
        -> ★ 反而比 MHA 更快：同一份 KV 被复用 4 次，算术强度上升

🔑 这是"架构决策 → 算子后果"最干净的一个例子：GQA 在架构上只是"少存点 KV"，但它在算子层带来了额外的收益——注意力 kernel 里 KV 的复用率随分组数线性上升。⚠️ 前提是 kernel 支持，否则就是额外的损失。

📌 FA2 的 GQA 原生支持怎么实现的，见 ../../大模型算子开发/04-FlashAttention全系.md §4.4.5。

算子后果②：MLA 把一个注意力模块变成了两套 kernel

这是本章最重要的一个例子，因为它显示了架构决策可以改变的不只是性能，还有算子的边界。

非吸收式（Non-Absorptive） 吸收式（Absorptive）
做法 把 c_KV 真的上投影成 K、V，再走标准注意力 把 W^UK 吸到 Q 侧、W^UV 吸到输出侧，全程在 512 维潜空间里算
形态像 MHA MQA（所有头读同一份 c_KV）
有效 head_dim 128 ⭐ 512
用在哪 训练 / Prefill Decode
为什么 K、V 物化一次，被几千个 query 摊薄，划算 只有 1 个 query，物化 12.8 万个位置的 K、V 是纯浪费

✅ 这不是推测：openPangu 报告原文就写了 "MLA switching between Absorptive (MQA, decode) and Non-Absorptive (MHA, training/prefill) modes"。

🔑 注意 head_dim 从 128 变成 512，对 §19.3 那个 exp 比值是【好事】：254 / (4 × 512) = 12.4%，非矩阵乘的开销占比从 50% 降到 12%。但代价是注意力本身的 FLOPs ×4——吸收式在 Decode 里赢，是因为它省掉了物化 K、V 这件更贵的事，不是因为它算得少。

⚠️ 这个设计有一个不明显的、而且相当严重的代价：同一份权重走两条不同顺序的矩阵乘，浮点加法不满足结合律，两条路必然算出略微不同的数（量级约 1–2 ULP / 层）。单层看不出来，几十层累起来就进了可观测区间，在强化学习里会被放大成训练崩掉。这是 MLA 训推不一致的根源，而且它是"设计出来的"，不是 bug。 完整分析见 ../../大模型算子开发/11-训推一致性算子层.md §11.7。

算子后果③：吸收式的一个副产品，反过来又催生了新架构

    吸收式下，全部 128 个头读的是【同一份 512 维 c_KV】
        -> 访存形态等价于 MQA
        -> 做稀疏注意力选 top-k 时，【一次 gather 就服务了全部头】

🔑 这条因果链值得完整念一遍：架构上选了 MLA（为了省 KV）→ 算子上出现了吸收式（为了 Decode 快）→ 吸收式的访存形态像 MQA → 稀疏选择的 gather 成本降到 1/128 → DSA（DeepSeek Sparse Attention）才敢用最激进的 token 级 top-k。

架构 → 算子 → 再回到架构。 这一章想让你看见的就是这个回路。见 08 章 §8.3。

19.5 决策③ MoE 的 Top-K：一刀同时切出两个算子问题

10 章 讲清了 MoE 为什么能"参数多但算得少"。落到算子上，"每个 token 只走 K 个专家"这一条设计，同时制造了两个完全不同性质的麻烦：

    Top-K 路由
        │
        ├── ① 每个专家拿到的 token 数【不一样多】
        │      -> 形状参差不齐（ragged）-> 普通 GEMM 用不了 -> Grouped GEMM
        │      -> 而且每个专家的 M 很小 -> ★ 从 Compute Bound 掉进 Memory Bound
        │
        └── ② token 要被送到专家所在的那张卡上
               -> All-to-All 通信 -> ★ 通信量和 K 成正比

麻烦①：形状参差不齐，而且每一块都太小

为什么不能用普通的 batched GEMM：批量矩阵乘要求批里每一个矩阵形状完全相同。但路由的结果是"专家 3 分到 97 个 token、专家 7 分到 211 个"——形状对不齐。补零到最大值的话，浪费的算力和不均衡程度成正比。解法是 Grouped GEMM（分组矩阵乘法）：一次 kernel 调用里处理一组形状不同的矩阵乘。

更麻烦的是第二件事。把 DeepSeek-V3 规模的数字代进 §19.2 那把尺（H = 7168，专家中间维 2048，每卡 4096 token，256 个路由专家，Top-8）：

    每张卡的 token-专家配对数 = 4096 × 8 = 32,768
    平摊到 256 个专家          = 每个专家约 128 个 token       ->  M = 128
GEMM M 算术强度 I 对比屋脊点 295 结论
稠密 FFN（不分专家） 4096 1147 超出 3.9 倍 Compute Bound ✓
⚠️ MoE 单个专家的 GEMM 128 ⚠️ 118 只有 0.4 倍 ⚠️ Memory Bound

🔑 这是"细粒度专家"这个架构决策最贵的一笔隐藏成本：专家切得越细、数量越多，每个专家分到的 M 越小，专家 GEMM 就越往访存受限那一侧掉。掉过去之后，Tensor Core 再快也没用——时间全花在把专家权重从 HBM 读进来上。

⚠️ 注意这和"MoE 省 FLOPs"完全不矛盾，但它让"省下来的 FLOPs"换不成等比例的时间。 架构报告里说"激活参数只有 1/20 所以快 20 倍"，在算子层几乎从来不成立。

📌 Grouped GEMM 的接口长什么样、三条实现路线各浪费多少、重排（gather/scatter）本身的开销，见 ../../大模型算子开发/08-MoE算子与通信.md §8.2。

麻烦②：All-to-All 的账，以及那个最常被漏掉的 × K

单向通信量的公式：

    每张卡 Dispatch 要发出的字节数  =  t × K × H × b × (1 − 1/EP)

    Combine（回程）的量和 Dispatch 一样，所以一层 MoE 的总量 ≈ 这个数的 2 倍
符号 含义
t 本卡本地的 token 数
K ⚠️⚠️ Top-K——每个 token 要复制 K 份发出去。这一项最常被漏掉
H 隐藏维度
b 每个元素的字节数（BF16 = 2，FP8 = 1）
(1 − 1/EP) 减掉恰好落在自己这张卡上、不用发出去的那一部分

⚠️⚠️ × K 是全仓库被漏掉次数最多的一项。 漏掉它，Top-8 的模型通信量会被算成实际的 1/8——从"通信是主要瓶颈"直接变成"通信可以忽略"，结论完全翻转。

代进 DeepSeek-V3 规模（t = 4096，K = 8，H = 7168，FP8 b = 1，EP = 32）：

    Dispatch = 4096 × 8 × 7168 × 1 × (1 − 1/32)
             = 234.9 MB × 0.96875
             = 227.5 MB     （每卡、每层、单向）

    一层合计（Dispatch + Combine） ≈ 455 MB

换成时间，先把带宽单位弄对（⚠️ 这里是第二个高频错误区）：

链路 标称 ⚠️ 真正该用的分母 455 MB 要多久
NVLink（机内卡间） 900 GB/s ⚠️ 这是双向聚合，单向是 450 GB/s 约 1.0 ms
InfiniBand（机间） 400 Gb/s ⚠️ Gb 是比特，÷ 8 = 50 GB/s 约 9.1 ms

⚠️ 两个单位陷阱，各自会让你乐观一倍和八倍：把 900 当单向用，结果乐观 2 倍；把 400 Gb/s 当 400 GB/s 用，结果乐观 8 倍。两个一起犯，乐观 16 倍。凡是看到"通信量 ÷ 带宽"的式子，第一件事是确认两边是不是同一个方向、同一个单位。

🔑 机内 450 GB/s 和机间 50 GB/s 差 9 倍——这一条直接决定了架构侧的一个设计：节点受限路由（Node-Limited Routing，限制一个 token 最多只能去 M 台机器，✅ DeepSeek-V3 取 M = 4）。这不是通信优化的技巧，这是写进模型路由逻辑里的架构约束。

🔑 回到架构决策：把 Top-K 从 2 调到 8（细粒度专家的标准做法），All-to-All 的通信量原样 ×4。在架构图上，"Top-K: 8"只是一个数字；在算子层，它是每层每卡多出来的几百兆通信。这就是本章想让你建立的那种条件反射。

📌 完整的三笔账（含 DeepSeek-V3 真实配置）、三种把通信藏起来的办法、All-to-All 和 AllReduce 的区别，见 ../../大模型算子开发/08-MoE算子与通信.md §8.3；训练侧的 EP 切分见 ../../训练框架/分布式训练入门/09-专家并行EP.md；推理侧的负载不均和 EPLB 见 ../../推理框架/推理优化入门/11-MoE推理与专家并行.md。

麻烦③（顺带）：不均衡的代价是"最慢那张卡说了算"

All-to-All 是一次同步操作：所有卡都发完、收完，专家 FFN 才能开始。所以一张卡上的专家如果分到了 2 倍的 token，整个 EP 组都要等它。这就是为什么 10 章 §10.5 那一整节的负载均衡不是"锦上添花"，而是 MoE 能不能用的前提。

19.6 决策④ RMSNorm / SwiGLU / RoPE：FLOPs 可忽略，时间不可忽略

这三个模块在 04 章、09 章、11 章 各讲过。它们的共同点是：FLOPs 占比小到可以忽略，但它们决定了推理延迟。

为什么"FLOPs 可忽略"不等于"时间可忽略"

拿 §19.2 那把尺量一遍：

算子 典型算术强度 对比 295 时间由什么决定
大批量 GEMM 300 ~ 1200 > 算力
RMSNorm 1 ~ 5 ⚠️ 远小于 搬运字节数（读一遍、写一遍）
SiLU / GeLU 激活 1 ~ 3 ⚠️ 远小于 同上
RoPE 1 ~ 3 ⚠️ 远小于 同上
残差加 约 1 ⚠️ 远小于 同上

🔑 对一个 Memory Bound 的算子，它花的时间只和"读写了多少字节"有关，和它算了几次浮点运算基本无关。 一个只做 x * sigmoid(x) 的激活函数，和一个做 20 次浮点运算的复杂激活，耗时几乎一样——因为两者都是读一遍、写一遍。

🔑 所以对这一类算子，唯一有效的优化是【融合】：让中间结果留在寄存器/SRAM 里，不落 HBM。 📌 融合能省多少、什么时候不能融（⚠️ 两个都是 Compute Bound 的算子融合不一定更快，因为算力已经打满了），见 ../../大模型算子开发/05-算子融合.md §5.3–§5.4。

三个架构选择各自送了算子一份礼物（或一份债）

① RMSNorm 比 LayerNorm 省一遍归约。 LayerNorm 要先求均值再求方差，RMSNorm 只求平方均值（04 章）。FLOPs 上这点差别可以忽略，但在算子层：

    LayerNorm：  需要均值和方差两个统计量
                 -> 朴素实现要扫两遍（或用 Welford 一遍搞定，但寄存器压力更大）
    RMSNorm：    只要一个统计量
                 -> ★ 稳稳地一遍读完，循环体更短，寄存器更省

② SwiGLU 的三矩阵结构，反而送了一个合并 GEMM 的机会。

    SwiGLU：  out = W_down · ( SiLU(W_gate · x)  *  (W_up · x) )
                                ^^^^^^^^^^^^        ^^^^^^^^
                              两个投影，输入是【同一个 x】

    ★ 算子上：把 W_gate 和 W_up 【按列拼成一个大矩阵】，做【一次】GEMM
       -> 少一次 kernel 启动
       -> 输入 x 只从 HBM 读一遍，不是两遍
       -> 拼出来的 N 维度翻倍，对 Tensor Core 的分块更友好

③ RoPE 是纯逐元素操作，它的唯一正确位置是别人的"尾巴"。

RoPE 对 Q、K 做旋转（11 章），算术强度约等于 1。如果单独起一个 kernel，就要把整个 Q、K 张量读一遍写一遍；融进 QKV 投影那个 GEMM 的 epilogue（尾声，GEMM 算完结果还在寄存器里时顺手做的那一段）里，这一读一写就完全消失了。

⚠️ 反过来说，架构上任何"在 QK 之间插一个新的逐元素操作"的想法，都要先问一句：它能不能融进 epilogue？ 融不进去，就意味着每层多一次全量的 Q、K 读写——在长上下文下这不是小数目。

⭐ kernel 数量本身就是一笔账（而且不能简单相加）

§19.1 数过：一层 12~18 个 kernel，60~80 层的模型，一次 decode 步要发起 上千个 kernel。每个 kernel 从 CPU 侧下发到 GPU 有一个固定成本，⚠️ 约 2 µs。

⚠️⚠️ 但这里有一个极容易犯的错：不能把"kernel 数 × 2 µs"当成额外增加的时间加到 GPU 执行时间上。 下发是流水化的——CPU 在下发第 n 个 kernel 的时候，GPU 正在执行第 n−5 个。正确的判据是取最大值：

    每步耗时 ≈ max( kernel 数 × 单个下发成本(⚠️ 约 2 µs) ,  GPU 执行时间 )
                    \___________ CPU 侧 ___________/      \___ GPU 侧 ___/

代两组数进去，结论完全不同：

场景 kernel 数 CPU 侧 = 数 × 2 µs GPU 侧执行 ⚠️ 谁是瓶颈 该做什么
大 batch decode 800 1.6 ms 6.0 ms GPU 优化 kernel 本身
⚠️ 小 batch decode 800 1.6 ms 1.0 ms ⚠️ CPU 下发 ⭐ 上 CUDA Graph

🔑 CUDA Graph 做的事就是把这上千次下发预先录成一张静态图，运行时一次提交，把 CPU 侧那一列直接压到接近零。它对大 batch 几乎没用，对小 batch / 低延迟场景收益显著——因为它治的是那个 max 里的另一项。

⚠️ 这也解释了一个架构层面的取舍：那些"每层多插一个小模块"的设计（额外的门控、额外的归一化、额外的旁支），FLOPs 上可能只有千分之几，但每层多一个 kernel，80 层就是多 80 个，在小 batch 下是实打实的延迟。18 章 的 Engram 只插了 2 层而不是每层都插，这一条也是理由之一。

📌 CUDA Graph 的限制（形状必须固定、不能有数据依赖的控制流）见 ../../大模型算子开发/05-算子融合.md §5.5；下发开销的完整测算见 ../../大模型算子开发/09-推理侧算子.md §9.9；推理框架侧的图编译见 ../../推理框架/推理优化入门/12-CUDA-Graph与图编译.md。

19.7 决策⑤ FP8：精度是架构决策，不是部署后处理

14 章 讲的是量化的三个维度（格式 / 粒度 / 离群值）。这里只说一件事：为什么 FP8 训练属于架构决策，而不是训练完再做的一道工序。

它改的是那把尺本身

    BF16：  峰值 989 TFLOPS，屋脊点 = 989 ÷ 3.35 = 295 FLOP/Byte
    FP8 ：  峰值 1979 TFLOPS，屋脊点 = 1979 ÷ 3.35 = 591 FLOP/Byte
            ^^^^ 算力翻倍，同时每个元素只占 1 字节，搬运量减半

⚠️⚠️ 这里是全章最容易出错的一处数字：官方规格表里 BF16 和 FP8 都有 1979 这个数，但含义完全不同。

精度 989 1979
BF16 ✅ 稠密峰值（常规算子用这个） ⚠️ 2:4 稀疏峰值（要求权重满足稀疏模式，常规算子用不上）
FP8 — ✅ 稠密峰值

拿 BF16 的 1979 去算屋脊点，会得到 591——正好是 FP8 的屋脊点，错得毫无破绽。 之后所有 Memory Bound / Compute Bound 的判断都会偏。

为什么它必须在架构阶段决定

    ★ 量化不是"训练完把权重压小"这么简单。DeepSeek-V3/V4 是【全程 FP8 训练】，
      这要求模型设计时就回答三个问题：

      ① 哪些模块【不能】用 FP8？
         -> 残差流、归一化、嵌入层、LM head 保持 BF16；梯度累加用 FP32
         -> 这些位置的数值范围跨度太大，8 位放不下

      ② scaling（缩放因子）的粒度定多细？
         -> per-tensor 太粗（一个离群值毁掉整个张量）
         -> per-tile / per-block 才够用，但这要求 GEMM kernel 原生支持
         -> ★ 这是【模型格式】和【kernel 实现】必须一起定的东西

      ③ 训练和推理两边的量化路径一致吗？
         -> 不一致就会出现训推不一致，在强化学习阶段会被放大

🔑 ①②③ 里没有一条是"训练完再补"能解决的。 这就是"精度属于架构决策"的含义。

📌 FP8 的两种格式（E4M3 / E5M2）怎么选、per-tile scaling 怎么做、离群值为什么是真正的敌人，见 ../../大模型算子开发/06-量化算子.md §6.3 和 §6.5；训练侧的混合精度流程见 ../../训练框架/分布式训练入门/10-混合精度与FP8.md。

顺带把训练算力的口径钉死

讨论"这个架构训起来要多少卡"的时候，几乎所有人都用 6N 这个经验式（N = 参数量，单位是"每 token 的 FLOPs"）。它的来历是：

    6N  =  2N（前向）  +  4N（反向）
           ^^            ^^
      每个参数一次乘加   反向要算两份梯度（对输入、对权重），所以是前向的两倍

    ⚠️ 6N 【不含】优化器更新，也【不含】激活重计算带来的额外前向。
    ⚠️ 6N 还【不含】注意力里那部分随序列长度平方增长的计算 —— 它和参数量无关。

把缺的那一项补上：

    每 token 总 FLOPs ≈ 6N  +  12 · L · s · h
                              ^^^^^^^^^^^^^^^
                          注意力的 QK^T 和 AV 两个矩阵乘
                          （前向 4·s·h/层，反向 8·s·h/层，合计 12）

代一组真实量级的数（L = 80 层，h = 8192，N = 70B）：

序列长度 s 6N 12·L·s·h 占比 说明
4,096 4.20e11 3.22e10 +7.7% 可以忽略吗？勉强
8,192 4.20e11 6.44e10 ⚠️ +15.3% ⚠️ 不能忽略了

⚠️ 序列长度翻倍，这一项就翻倍。 所以"长上下文训练"的成本估算，光用 6N 会系统性低估——而且是越长越低估。

⚠️ MFU（Model FLOPs Utilization，模型算力利用率）= 实际达到的 FLOPs/s ÷ 硬件峰值。 分母是硬件峰值，所以报 MFU 必须同时说清楚是哪张卡、什么精度。"我们做到了 45% 的 MFU"这句话在 A100 上和在 H100 上是两个完全不同的成绩。📌 MFU 的完整算法见 ../../大模型算子开发/02-屋顶线与性能剖析.md §2.6。

19.8 决策⑥ MTP 与投机解码：把 Decode 的 M 从 1 变成 k

12 章 讲了 MTP（Multi-Token Prediction，多 token 预测）和投机解码的原理和正确性证明。从算子视角看，它们做的其实是同一件事：

    普通 Decode：  M = 1        ->  算术强度 ≈ 1.0     ->  ⚠️ 权重读了一整遍，只产出 1 个 token
    投机解码  ：  M = k        ->  算术强度 ≈ k       ->  ★ 同一遍权重读，验证 k 个 token

🔑 这是本章最简洁的一条因果：Decode 慢，是因为它的算术强度是 1.0——权重从 HBM 读一遍的成本，被摊在了唯一一个 token 上。投机解码没有让 GPU 算得更快，它只是把摊薄的分母从 1 变成了 k。

⚠️ 也正因为如此，投机解码的收益只在 Memory Bound 区间存在。batch 大到 M 已经越过 §19.2 那个临界点（约 325）之后，再叠投机解码不但不赚，还要多算被拒绝的那些 token。这是一个只在低 batch / 低延迟场景成立的优化。

它在算子层要求什么

要求 为什么 谁来实现
注意力 kernel 支持非标准掩码 草稿是一棵树（一个位置有多个候选），不是一条链，普通因果掩码套不上 FlashAttention 的 varlen / 自定义 mask 变体
KV cache 支持回滚 被拒绝的草稿 token 写进去的 K、V 必须撤掉 PagedAttention 的块管理天然适合（丢掉几个块即可）
一步之内两次模型调用 草稿模型 + 主模型验证 调度器；MTP 把草稿头做进主模型，省掉一次调度

🔑 MTP 相对于"外挂一个小草稿模型"的架构优势，正好在最后一行：草稿头和主干共享同一份前向计算，不需要额外加载和调度另一个模型。这是把一个系统问题（调度两个模型）用架构手段（多加一个预测头）解决掉了。

📌 接受率怎么换算成加速比、树形草稿的具体 mask、EAGLE / Medusa 的差别，见 ../../大模型算子开发/09-推理侧算子.md §9.6 和 ../../推理框架/推理优化入门/08-投机解码.md。

⚠️ 报加速比的时候有一个口径陷阱，这里一次说清楚：

```
"单 token 耗时从 10 ms 降到 8 ms"

时间减少  =  (10 − 8) / 10  =  20%
加速比    =  10 / 8         =  1.25×，也就是【快了 25%】

⚠️ 这两个数【永远不相等】，而且差距随收益变大而变大：
   时间减少 50%  ->  加速 2.00×（快 100%）
   时间减少 90%  ->  加速 10.0×（快 900%）

```

"减少 X%"和"加速 X%"是两句不同的话，引用别人的数字前先确认是哪一句。

19.9 收口总表：架构位置 → 算子后果 → 去哪读

把 15 章总装图 上那些"可改的位置"逐个过一遍，每一行回答同一个问题：改了它，算子层会发生什么。

架构上的位置 典型改动 ⭐ 算子层的后果 深入读哪一份
词表 / Embedding 词表放大到 15 万+ LM head 变成一个又大又薄的 GEMM；vocab × hidden 的梯度是显存大头 02 章；../../训练框架/分布式训练入门/02-显存去哪了.md
残差流 mHC 把残差拆成 M 条并行流 每层的逐元素算子数 × M；融合机会变多也变复杂 03 章
归一化 LayerNorm → RMSNorm 少一个统计量 → 少一遍归约；更容易融进相邻 GEMM 的尾巴 04 章；../../大模型算子开发/05-算子融合.md
head_dim 128 → 64 ⚠️ 注意力里非矩阵乘部分的占比从 50% 涨到 99%，Tensor Core 利用率天花板腰斩 ★ §19.3；../../大模型算子开发/04-FlashAttention全系.md §4.5.1
KV 头数 MHA → GQA-8 KV 字节 ÷ 8；注意力 kernel 里 KV 复用率 × 8（⚠️ 前提是 kernel 原生支持，否则要物理复制，白省） ★ §19.4；07 章
注意力形式 GQA → MLA ⭐ 同一个模块变成两套 kernel（训练/prefill 非吸收式，decode 吸收式）；⚠️ 两条路数值不同，是训推不一致的根源 ★ §19.4；../../大模型算子开发/11-训推一致性算子层.md §11.7
稀疏注意力 全注意力 → token 级 top-k 多一个索引器 kernel + 一次非规则 gather；⭐ MLA 吸收式让这次 gather 一次服务全部头 08 章
位置编码 绝对位置 → RoPE 纯逐元素算子，⚠️ 不融进 QKV 投影的 epilogue 就白白多一次全量读写 ★ §19.6；11 章
FFN 激活 ReLU-FFN → SwiGLU 三个矩阵而不是两个；⭐ gate 和 up 可按列拼成一次 GEMM，输入只读一遍 ★ §19.6；09 章
FFN → MoE 稠密 → 256 专家 Top-8 ⭐ 形状 ragged → Grouped GEMM；⚠️ 每专家 M 掉到约 128，从 Compute Bound 掉进 Memory Bound ★ §19.5；../../大模型算子开发/08-MoE算子与通信.md §8.2
Top-K 2 → 8 ⚠️ All-to-All 通信量原样 × 4（公式里那个 × K） ★ §19.5；同上 §8.3
精度 BF16 → FP8 屋脊点 295 → 591，搬运减半；⚠️ 要求 GEMM kernel 原生支持 per-tile scaling，某些模块必须留 BF16 ★ §19.7；14 章；../../大模型算子开发/06-量化算子.md
多 token 预测 单头 → MTP ⭐ Decode 的 M 从 1 变成 k，算术强度同倍数上升；⚠️ 需要非标准掩码 + KV 回滚 ★ §19.8；12 章
条件记忆 挂一个 Engram 旁支 几乎不产生 FLOPs，但多两个 kernel + 一条 PCIe 预取链路；⚠️ 瓶颈是随机小块延迟，不是带宽 18 章 §18.8
优化器 AdamW → Muon 多一个 Newton-Schulz 迭代（一串小矩阵乘）；优化器状态显存减少 13 章

19.10 ⚠️ 八个最常被写错的口径

这一节是查错清单。下面每一条，本仓库都在某份笔记里实际踩过或纠正过。

# ❌ 常见的错误说法 ✅ 正确口径 错多少
1 "H100 的 BF16 算力是 1979 TFLOPS" 989 TFLOPS 是稠密值；1979 是 2:4 稀疏值。FP8 的 1979 才是稠密的 屋脊点会从 295 错成 591
2 "Prefill 是算力受限" ⚠️ 只有 prompt 够长才成立。算术强度约等于 prompt 长度，临界点约 300~400 token 6 token 的 Prefill 照样访存受限
3 "KV cache = 2 × d_model × 层数 × 字节数" 2 × n_kv_heads × head_dim × 字节数，用的是 KV 头数 GQA-4 会高估 4 倍，GQA-8 高估 8 倍
4 "MLA 吸收之后就不用存 c_KV 了" ⚠️ 照样存 c_KV。吸的是上投影矩阵（W^UK→Q 侧、W^UV→输出侧） 压缩率直接归零（17.8× → 1×）
5 "FA2 在 H100 上能跑 540 TFLOPS" FA2 约 350（35%）、FA3 约 740（75%），FA3 FP8 约 1200 540~570 是 FA3 的中间态，不是 FA2
6 "Tensor Core 比 CUDA Core 快 8 倍" 约 15 倍（989 ÷ 67） 少算一半
7 "All-to-All 量 = tokens × H × 字节数" ⚠️ 漏了 × Top-K，还要乘 (1 − 1/EP) Top-8 会少算 8 倍
8 "1000 个 kernel × 2 µs = 多出 2 ms" ⚠️ 下发是流水化的，判据是 max(kernel 数 × 约 2 µs, GPU 执行时间) 大 batch 下这 2 ms 根本不存在

另外三条单位与口径上的纪律：

项 纪律
NVLink 900 GB/s ⚠️ 这是双向聚合。算"我要发出 X 字节要多久"，分母用单向 450 GB/s
InfiniBand 400 Gb/s ⚠️ Gb 是比特。÷ 8 = 50 GB/s。和 GB 混用会乐观 8 倍
"时间减少 X%" vs "加速 X%" ⚠️ 永远不相等。时间减少 50% = 加速 2.0×（快 100%）

⚠️ 还有两条写作纪律，本教程全程遵守：(a) 报 MFU 必须带硬件平台和精度，否则数字没有意义；(b) 十进制 GB 和二进制 GiB 要分清（1 GiB ≈ 1.074 GB），显存容量按 GB 标、实际可用按 GiB 算，长上下文的显存账里这 7.4% 足以让"刚好装得下"变成"装不下"。

19.11 本章小结

    ① 本章不讲 kernel 怎么写，只讲【架构决策 -> 算子后果】。
      实现细节全在 ../../大模型算子开发/ 那 17 章里，本章一律链接过去。

    ② 一把尺：H100 屋脊点 BF16 = 295、FP8 = 591 FLOP/Byte。
      ⚠️ BF16 的 1979 是稀疏值，别拿它算屋脊点。        -> §19.2

    ③ ⚠️ "Prefill 算力受限"有前提：算术强度约等于 prompt
      长度，临界点约 300~400 token。短 prompt 照样访存受限。-> §19.2

    ④ head_dim = 128 是被硬件钉死的：MMA 形状要对齐 16、
      256 字节正好两条缓存行、而且 d 越小注意力里
      exp 的占比越高（d=128 是 50%，d=64 就到 99%）。      -> §19.3

    ⑤ ★ GQA 让 KV 复用率上升（前提是 kernel 原生支持）；
      MLA 把一个注意力模块变成【两套 kernel】，
      ⚠️ 而这正是训推不一致的设计级根源。
      ⚠️ 吸收吸的是上投影矩阵，c_KV 照样要存。            -> §19.4

    ⑥ ★ MoE 的 Top-K 一刀切出两个问题：
        形状 ragged -> Grouped GEMM，而且每专家 M 太小
                      -> 从 Compute Bound 掉进 Memory Bound
        token 要跨卡 -> All-to-All，⚠️ 通信量里那个 × K
                      最容易被漏掉，Top-8 漏掉就少算 8 倍   -> §19.5

    ⑦ RMSNorm / SwiGLU / RoPE 的 FLOPs 可以忽略，时间不能。
      它们是 Memory Bound，唯一有效的优化是【融合】。
      ⚠️ kernel 下发是流水化的，判据是
         max(kernel 数 × 约 2 µs, GPU 执行时间)。         -> §19.6

    ⑧ FP8 是架构决策不是后处理：哪些模块必须留 BF16、
      scaling 粒度多细、训推路径一不一致，
      三个问题都得在设计阶段回答。
      ⚠️ 训练算力 6N 不含优化器，也不含注意力的 O(s²) 项：
         补全式 6N + 12·L·s·h（s=8192 时那一项占 +15.3%）。 -> §19.7

    ⑨ ★ 投机解码 / MTP 的本质是把 Decode 的 M 从 1 变成 k，
      让同一遍权重读服务 k 个 token。
      ⚠️ 只在 Memory Bound 区间有收益，大 batch 下会亏。   -> §19.8

    ⑩ ⚠️ 八条最常写错的口径 + 三条单位纪律，见查错清单。  -> §19.10
