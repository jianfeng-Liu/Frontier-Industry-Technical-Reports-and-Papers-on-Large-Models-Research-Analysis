# 19 · 算子开发与实现：大模型的算力引擎

> **这是一章加餐**（2026-09 增补）。它和前面讲架构、注意力、MoE 的章节是同一套系统，只是视角切换到了"代码实际怎么跑在 GPU 上"。读完 [05 章（注意力机制）](05-注意力机制.md) 和 [10 章（MoE）](10-MoE.md) 可以直接跳到这里。

**这一章的目标**：讲清楚"算子"这个词到底是什么、为什么 GPU 上跑一个矩阵乘法会慢、业界用什么手段让它快起来，以及 FlashAttention、算子融合、量化、Triton、All-to-All 这些名字背后在解决什么具体问题。

---

**本章关键词**

**算子**（operator / kernel）—— 一个可以在 GPU 上独立执行的数学运算的实现，比如矩阵乘法、Softmax、LayerNorm。  
**GEMM**（General Matrix Multiply，通用矩阵乘法）—— 算子里最核心的一个，大模型 90% 以上的计算量是它。  
**HBM**（High Bandwidth Memory，高带宽内存）—— GPU 上的"主内存"，读写快但容量有限。  
**SRAM**（Static Random-Access Memory，静态随机存取内存）—— GPU 片上的"缓存"，极快但极小（A100 约 40 MB）。  
**Roofline**（屋顶线）—— 分析算子性能瓶颈在算力还是内存的模型，本章核心工具。  
**Triton** —— OpenAI 开源的 GPU 内核编程语言，比 CUDA 更易写，比 PyTorch 更快。  
**All-to-All** —— MoE 里 token 分配到各专家时用的通信原语，分布式训练的主要瓶颈之一。

## 19.1 一个算子是什么——先祛魅 {#191}

你在 PyTorch 里写 `torch.matmul(A, B)`，这背后发生了什么？

```
Python 层:  torch.matmul(A, B)
         ↓ 调度
C++ 层:   at::matmul(A, B)
         ↓ 选择实现
CUDA 层:  cublasSgemm(...)   ← 这就是一个【算子】（kernel）
         ↓ 执行
GPU 硬件: 数以千计的线程同时运算
```

**算子 = "在 GPU 上实际运行的那段 C++/CUDA 代码"**。它接收输入张量，输出结果张量，是整个计算图的最小执行单元。

大模型推理/训练的一次前向传播，会调用几百到上千个算子：矩阵乘法、RoPE 位置编码、LayerNorm、Softmax、激活函数、KV Cache 的读写……

**为什么需要专门优化？**  
同一个数学公式，不同的实现方式在 H100 上可以相差 **10 倍甚至 50 倍**的速度。这个差距完全来自"硬件资源有没有被高效使用"，不是数学问题，是工程问题。

## 19.2 为什么算子会慢：屋顶线模型 {#192}

在分析为什么慢之前，先搞清楚 GPU 有哪些资源：

```
┌──────────────────────────────────────────────────────────┐
│                     GPU（以 H100 为例）                   │
│                                                          │
│  算力（Compute）:  约 2000 TFLOPS（BF16 Tensor Core）     │
│  内存带宽（BW）:   约 3.35 TB/s（HBM3）                   │
│  片上缓存（SRAM）: 约 50 MB（L2），每个 SM 约 256 KB       │
│                                                          │
│  类比：一个工厂                                          │
│    算力  ≈ 工人的操作速度                                 │
│    带宽  ≈ 传送带（从仓库取货的速度）                     │
│    SRAM  ≈ 工人手边的货架（极小但极快）                   │
└──────────────────────────────────────────────────────────┘
```

### 算术强度：判断瓶颈在哪

**算术强度**（Arithmetic Intensity）= 每读一个字节的数据，能做多少次浮点运算（FLOP/Byte）。

```
算术强度 = 总 FLOPs / 总内存读写字节数
```

H100 的**硬件峰值强度** = 2000 TFLOPS / 3.35 TB/s ≈ **600 FLOP/Byte**。

这就是"屋顶线"（Roofline）的含义：

```
性能 (TFLOPS)
    ↑
2000│─────────────────────────────── ← 算力屋顶（Compute Bound）
    │                               /
    │                              /
    │                             /
    │                            /
    │                           /  ← 带宽线（Memory Bound）
    │                          /
    │─────────────────────────/
    └───────────────────────────────→ 算术强度
                         600
```

- **算术强度 < 600**：算子是**内存瓶颈**（Memory Bound），GPU 的计算单元在等数据。
- **算术强度 > 600**：算子是**算力瓶颈**（Compute Bound），计算单元全力运转，带宽够用。

### 大模型算子落在哪里？

| 算子 | 算术强度（典型值） | 瓶颈 |
|---|---|---|
| 大批量 GEMM（训练） | ~300–2000 | 算力为主 |
| 小批量 GEMM（推理，batch=1） | ~1–10 | ★ 内存瓶颈 |
| Softmax / LayerNorm | ~1–5 | ★ 内存瓶颈 |
| Flash Attention（融合后） | ~40–200 | 内存为主，改善明显 |
| 激活函数（SiLU、GeLU） | ~1–3 | ★ 严重内存瓶颈 |

**结论**：推理时大量算子是内存瓶颈，优化算子就是"减少 HBM 读写次数"。

## 19.3 最核心的算子：矩阵乘法 GEMM {#193}

**大模型里 90% 以上的 FLOPs 是矩阵乘法**。每一个注意力的 Q/K/V 投影、FFN 的两层线性变换、最终的 LM head，全是 GEMM。

### 最朴素的实现为什么慢？

```python
# 朴素实现：C = A @ B，A 是 (M,K)，B 是 (K,N)
for i in range(M):
    for j in range(N):
        for k in range(K):
            C[i,j] += A[i,k] * B[k,j]
```

问题：每次算 `A[i,k] * B[k,j]` 都要从 HBM 取一次数据。A 矩阵的每一行要被读 N 次，B 矩阵的每一列要被读 M 次。数据搬运量 = O(M×K + K×N) × N 或 M，完全在浪费带宽。

### 分块（Tiling）：让数据"住"在 SRAM 里

核心思路：把 A、B 分成小块（tile），每块加载进 SRAM 一次，反复使用，算完再换下一块：

```
┌──────────────────────────────────────────┐
│              矩阵 B                       │
│         [ B₀₀ | B₀₁ | B₀₂ ]             │
└──────────────────────────────────────────┘
      ×
┌──────────────────────────────────────────┐
│ [ A₀₀ ] [ A₀₁ ] [ A₀₂ ]  矩阵 A        │
└──────────────────────────────────────────┘
      ↓
   ★ 把 A₀₀ 和 B₀₀ 同时搬进 SRAM
   ★ 算 C₀₀ 的一部分（局部累加）
   ★ A₀₀、B₀₀ 在 SRAM 里可以被反复使用
   ★ 算完了再搬 A₀₁、B₁₀，继续累加
```

分块后，同一份数据被复用 `tile_size` 次，算术强度从 O(1) 提升到 O(tile_size)。tile 越大，复用率越高，越接近算力上限。

### Tensor Core：矩阵乘法的专用硬件

从 Volta 架构（V100）开始，NVIDIA GPU 内置了 **Tensor Core**，一个时钟周期内可以做一个 4×4 的矩阵乘累加（或更大的 16×16 Warp 级别）。

```
普通 CUDA Core（FP32）：每周期 1 次乘加
Tensor Core（BF16）：   每周期 16×16=256 次乘加，快 256 倍
```

要用上 Tensor Core，矩阵的维度必须是 16（或 8、32）的倍数。这就是为什么模型的隐藏维度通常是 128 的倍数。

### cuBLAS vs. CUTLASS vs. 自定义

| 选项 | 适用场景 | 优点 | 限制 |
|---|---|---|---|
| **cuBLAS** | 标准 GEMM | 极度优化，开箱即用 | 只支持标准形状，无法融合 |
| **CUTLASS** | 需要定制的 GEMM | 模板化，可融合 Epilogue | C++ 模板，学习成本高 |
| **Triton** | 快速原型 + 实验 | Python 语法，易迭代 | 不如 CUTLASS 极致 |
| **自写 CUDA** | 极端优化 | 完全控制 | 开发周期长，维护难 |

> ✅ DeepSeek-V3/V4 系列训练时大量使用了自定义 GEMM 内核，专门针对 FP8 精度和 H800 的 SM 数量做了分块参数调优。这是它们在训练成本上做到极致的原因之一。

## 19.4 Flash Attention：重写历史的内存优化 {#194}

注意力机制（Attention）的朴素实现是大模型里最大的内存杀手，没有之一。FlashAttention（Dao et al., 2022）通过一个算法上的技巧，把它的内存复杂度从 O(N²) 砍到 O(N)，同时速度也快了 2–4 倍。

### 朴素 Attention 的问题

对于序列长度 N = 8192，隐藏维度 d = 128，标准 Attention 的中间矩阵 S = QKᵀ 大小是 8192 × 8192 = 64M 个元素，占 128 MB（BF16）。这只是一个头，32 头就是 4 GB。

```
Q (N×d)  ×  Kᵀ (d×N)  →  S (N×N)  →  softmax(S)  →  ×V  →  O
                          ↑
                   ★ 这个 N×N 的矩阵要写进 HBM 再读出来
                   ★ 序列越长，它越大，带宽代价是平方级
```

### FlashAttention 的核心思路：分块 + 在线 Softmax

Softmax 有一个问题：计算 `softmax(x)` 时需要先知道所有 `x` 的最大值，才能做数值稳定的指数运算。所以朴素实现必须先把整个 N×N 的 S 矩阵算出来再做 Softmax。

**在线 Softmax**（Online Softmax，Milakov & Gimelshein, 2018）解决了这个问题：

```
只需要维护两个标量：
  m = 当前见过的最大值
  ℓ = 当前 exp(x - m) 的累加和

每来一个新的 x_new：
  m_new = max(m, x_new)
  ℓ_new = ℓ × exp(m - m_new) + exp(x_new - m_new)

最终 softmax(x_i) = exp(x_i - m_final) / ℓ_final
```

有了在线 Softmax，就可以**按块处理 K、V**，不需要把整个 N×N 矩阵存下来：

```
FlashAttention 算法（简化）：

按块读 Q：
  for i in range(0, N, BLOCK_Q):        ← Q 的一个块
    加载 Q_i 进 SRAM
    初始化 O_i = 0, m_i = -∞, ℓ_i = 0
    for j in range(0, N, BLOCK_KV):     ← 逐块扫 K、V
      加载 K_j, V_j 进 SRAM
      S_ij = Q_i × K_jᵀ                ← 小块矩阵乘，留在 SRAM
      更新 m_i, ℓ_i（在线 Softmax）
      更新 O_i += softmax_block × V_j
    写回 O_i 到 HBM                     ← 只写一次！
```

**关键点**：S 矩阵从未完整出现在 HBM 里，它以小块的形式生存在 SRAM，用完即抛。

### 三代 FlashAttention 的演进

| 版本 | 年份 | 核心改进 | 速度提升（vs 朴素） |
|---|---|---|---|
| **FA1** | 2022 | 分块 + 在线 Softmax，消除 N×N 矩阵 | 2–4× |
| **FA2** | 2023 | 减少非矩阵乘运算，更好的并行划分，GQA 支持 | 2× (vs FA1) |
| **FA3** | 2024 | 针对 H100 的 Tensor Core Warpgroup，异步流水线 | 1.5–2× (vs FA2) |

> ✅ FA3 在 H100 上能跑到理论峰值的 75%，而朴素实现通常只有 10–20%。

### 反向传播：重计算换显存

FlashAttention 的反向传播用了一个巧妙的权衡：**不保存 softmax(S) 矩阵**（节省显存），反向时**重新计算它**（多花一点算力）。这让显存从 O(N²) 降到 O(N)，训练 100K 序列成为可能。

## 19.5 算子融合：把多张单曲合成一首 {#195}

### 问题：算子之间的搬运税

即使每个算子内部是高效的，两个算子串联仍然会浪费带宽：

```
LayerNorm(x) → Linear(x)

实现 A（不融合）：
  x → [读 HBM] → LayerNorm → [写 HBM] → [读 HBM] → Linear → [写 HBM]
                               ↑
                       这里的写和下一步的读是冗余的！

实现 B（融合）：
  x → [读 HBM] → LayerNorm → Linear → [写 HBM]
                               ↑
                  LayerNorm 的结果留在 SRAM/寄存器，直接喂给 Linear
```

融合后节省了一次 HBM 写 + 一次 HBM 读，数据量等于中间激活值的大小。

### 常见的融合模式

**1. 点对点融合**（最简单）

```
ReLU(x + bias)
GeLU(Linear(x))
SiLU(x) * Linear(x)    ← SwiGLU 的门控，一次 kernel 搞定
```

**2. Softmax + 矩阵乘（Attention 里的融合）**

FlashAttention 本质上是把 `QKᵀ → Softmax → ×V` 三步融合成一个 kernel。

**3. LayerNorm + GEMM**

LayerNorm 是 Memory Bound，GEMM 是 Compute Bound，融合后 LayerNorm 的输出直接进入 GEMM 的 Epilogue 计算，不落盘。

**4. GEMM + 激活 + GEMM（Flash-FFN）**

FFN 层通常是 Linear → SiLU/GeLU → Linear。把前两步融合，激活结果不写 HBM：

```
正常 FFN：  x → W₁ → [HBM] → SiLU → [HBM] → W₂ → out
融合 FFN：  x → W₁ → SiLU → W₂ → out
                        ↑
                  留在 SRAM，不经过 HBM
```

> ⚠️ 融合并非总有收益。两个都是 Compute Bound 的算子融合后不一定更快，因为计算资源已经打满了；只有 Memory Bound 的算子融合才能节省带宽。

### CUDA Graph：消除 kernel 启动开销

每次调用一个 CUDA kernel，都有一个固定的启动延迟（约 5–10 µs）。模型有上千个算子，启动开销累计起来很可观。

**CUDA Graph**：提前把所有算子的调用关系录制成一张静态图，推理时一次提交给 GPU，消除每次单独启动的开销。对推理延迟有 5–20% 的提升。

## 19.6 量化算子：用更小的数节省带宽 {#196}

### 为什么量化可以提速

用 FP16（16 bit）存一个数，用 INT8 存同一个数只需要 8 bit——带宽需求减半。用 FP4 只需要 4 bit——带宽减少 4 倍。

对于 Memory Bound 的算子（推理时大多数都是），带宽减半直接等于速度翻倍。

### 量化的基本原理

浮点数 → 整数的过程：

```
量化公式：  q = round( x / scale ) + zero_point
反量化：    x̂ = (q - zero_point) × scale

其中 scale 和 zero_point 是量化参数，每个张量或每行/每列可以各有一组。
```

量化精度越低，scale 管的范围越大，误差就越大。所以量化有一个**精度-速度权衡**。

### 主流量化方案

**INT8 权重量化（W8A16）**：权重存 INT8，激活值保持 FP16。读权重时省带宽，但矩阵乘法前需要反量化到 FP16，计算强度没变。主要收益是模型加载快、显存省。

**INT8 激活量化（W8A8）**：权重和激活都是 INT8，可以用 INT8 Tensor Core，算力也提升。难点是激活值的分布不像权重那样稳定（有异常值），直接量化精度损失大。

**SmoothQuant**（2022）：激活值里有少数"刺"（异常大的值），量化误差全集中在这几个数上。SmoothQuant 把激活值的"刺"转移到权重侧，让两边都更好量化：

```
Y = (X diag(s)⁻¹) (diag(s) W)   ← s 是平滑因子向量
      ↑                  ↑
   平滑后的激活值      吸收了刺的权重
```

**FP8 量化**：用 8 位浮点（E4M3 或 E5M2 格式）代替 FP16/BF16。H100 原生支持 FP8 Tensor Core，吞吐是 FP16 的 2 倍。DeepSeek-V3 训练全程用 FP8，是目前最激进的量化实践之一。

> ✅ DeepSeek-V3/V4 的训练用了**混合精度 FP8**：主要 GEMM 用 FP8，残差、LayerNorm、嵌入层保持 BF16，梯度累加用 FP32。实测精度损失可以忽略不计，训练速度提升约 1.6 倍。

**GPTQ**（2022）：只量化权重，不量化激活，精度更好。用二阶梯度信息（Hessian 近似）来调整量化误差，可以把 LLaMA 70B 压缩到 4 bit 而精度损失很小。

| 方案 | 权重 | 激活 | 优点 | 缺点 |
|---|---|---|---|---|
| W8A16 | INT8 | FP16 | 部署简单 | 计算不加速 |
| W8A8 (SmoothQuant) | INT8 | INT8 | 算力+带宽都省 | 需要校准数据 |
| FP8 训练 (DeepSeek) | FP8 | FP8 | 原生硬件支持 | 需要 H100+ |
| GPTQ W4 | INT4 | FP16 | 模型极小 | 精度有损失 |

## 19.7 用 Triton 写自定义算子 {#197}

CUDA 是写 GPU kernel 的"官方语言"，但学习曲线陡峭：线程组织、共享内存、bank conflict……一个 kernel 动辄几百行。

**Triton**（OpenAI, 2019，现已广泛用于生产）提供了更高层的抽象：你在"块"（block）级别写逻辑，Triton 负责把它翻译成高效的 CUDA。

### 一个 Triton 算子的骨架

```python
import triton
import triton.language as tl

@triton.jit
def add_kernel(
    x_ptr, y_ptr, out_ptr,
    n_elements,
    BLOCK_SIZE: tl.constexpr,   # 编译时常量，决定分块大小
):
    # 每个"程序"（相当于 CUDA 的 thread block）处理一个块
    pid = tl.program_id(axis=0)
    
    # 计算这个块负责的元素范围
    block_start = pid * BLOCK_SIZE
    offsets = block_start + tl.arange(0, BLOCK_SIZE)
    
    # 越界保护
    mask = offsets < n_elements
    
    # 从 HBM 加载数据
    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)
    
    # 计算
    output = x + y
    
    # 写回 HBM
    tl.store(out_ptr + offsets, output, mask=mask)

# 调用
add_kernel[grid](x, y, out, n_elements, BLOCK_SIZE=1024)
```

Triton 自动处理了：共享内存的声明、线程内的向量化、部分内存访问合并（memory coalescing）优化。

### Triton 适合写什么

Triton 最适合这类场景：
- **Memory Bound 的算子融合**（LayerNorm、RMSNorm、SiLU、RoPE）
- **FlashAttention 变体**（FA2 的官方实现就是 Triton 写的）
- **自定义激活函数**
- **量化/反量化 kernel**

不适合的场景：
- 极致优化的 GEMM（cuBLAS/CUTLASS 更成熟）
- 需要精细控制 warp-level 原语的算子（FA3 就放弃了 Triton，转回 CUDA PTX）

> ✅ PyTorch 2.0 的 `torch.compile` 后端（Inductor）的 GPU codegen 核心就是 Triton，说明 Triton 已经足够成熟进入生产工具链。

## 19.8 MoE 专属算子：All-to-All 与专家并行 {#198}

MoE（混合专家模型）引入了一种普通 Transformer 没有的计算模式：每个 token 要被路由到不同的专家，而这些专家可能分布在不同的 GPU 上。

### Expert Parallelism（专家并行）下的通信模式

假设有 8 个 GPU，每个 GPU 放 8 个专家（共 64 个专家），序列里的每个 token 激活其中 K=2 个：

```
GPU 0 里的 token                  各 GPU 的专家
[tok₀ → 专家2,5]                  GPU 0: 专家 0–7
[tok₁ → 专家3,11]    All-to-All  GPU 1: 专家 8–15
[tok₂ → 专家7,14]    ─────────→  GPU 2: 专家 16–23
[tok₃ → 专家0,19]                 ...
```

**All-to-All**：每个 GPU 把自己负责的 token 发给对应专家所在的 GPU，同时接收其他 GPU 发来的 token。完成后，每个专家都拿到了自己应该处理的 token。

这个操作在大规模训练中是主要的通信瓶颈，因为：
- 每个 token 都可能被发往任意 GPU
- 通信量随 GPU 数目和 token 数线性增长
- 无法轻易被计算"遮住"（All-to-All 完成前，专家 FFN 无法开始）

### DeepSeek 的 All-to-All 优化

DeepSeek-V3 的技术报告给出了具体数字：在 64 节点（512 GPU）的集群上，EP=32（32 路专家并行），每次 All-to-All 需要传输约 1.6 GB 数据，用 NVLink（节点内）+ InfiniBand（跨节点）完成，延迟约 2–5 ms。

两个关键优化：

**1. 限制 Token 跨节点路由**：允许 token 在节点内自由路由，但限制跨节点的专家激活数（比如每个 token 最多跨 2 个节点），大幅降低 InfiniBand 流量。

**2. All-to-All 与计算流水线**：在等 All-to-All 完成时，把其他层的计算（比如 Attention）填进去，用计算遮住通信延迟：

```
时间 →
层 L：   [All-to-All 发送] [等待] [All-to-All 接收]
层 L+1：             [Attention 计算 ←────────────覆盖等待时间]
```

### TopK 路由的算子实现

路由器（Router）计算 `softmax(W_r × h_t)`，选出 TopK 的专家 id。这本身是个简单的操作，但 **gathering**（把 token 按路由结果重新排列）是个非规则的内存访问模式，需要专门优化：

```python
# token 重排（gathering）：按专家 id 把 token 分组
# indices[i] = token i 应该去的专家
# 要求：把同一专家的 token 连续排列

sorted_tokens = tokens[argsort(indices)]   ← 这步是瓶颈
```

NVIDIA 的 [Grouped GEMM](https://github.com/tgale96/grouped_gemm)（分组矩阵乘法）库专门处理这种场景：把不同专家的 token 组分别做矩阵乘，批次大小不一，在一次 kernel 调用内完成，避免多次 kernel 启动开销。

## 19.9 推理侧：PagedAttention 与连续批处理 {#199}

推理场景有两个 GEMM 不好解决的问题：**KV Cache 的内存管理**和**不同长度请求的批处理**。

### KV Cache 的问题

推理时每生成一个新 token，都要保存该 token 在所有层的 K、V 向量（这就是 KV Cache），用于后续 token 的 Attention 计算。

问题：请求的最大长度事先不知道，必须预留最坏情况的内存——导致大量内存**内部碎片**（Fragmentation）。

**PagedAttention**（vLLM, 2023）：借鉴操作系统的虚拟内存分页思想。KV Cache 不再是连续的大块，而是被分成固定大小的"页"（block），按需分配：

```
传统 KV Cache（预分配）：
  请求 A（最大 512 token）：[ K₀K₁K₂K₃___________预留空间___ ]
                              ↑ 实际只用了 4 个 token，浪费 508 个位置

PagedAttention：
  物理块池: [ Block 0 ][ Block 1 ][ Block 2 ][ Block 3 ][ Block 4 ]...
  请求 A（已生成 4 token）: 块指针 → [Block 2][Block 5]
  请求 B（已生成 100 token）: 块指针 → [Block 0][Block 3][Block 1]...
```

每页固定 16 或 32 个 token，用完再申请一页，显存利用率从 20–40% 提升到 90%+。

### 连续批处理（Continuous Batching）

传统批处理：把一批请求打包，等最长的那条生成完，整批才算完。短请求一直等长请求。

**连续批处理**（也叫 Iteration-level batching）：每次生成一个 token 后，检查哪些序列已经完成，立刻把完成的槽位让给新请求，不等：

```
时间步 →   t=0  t=1  t=2  t=3  t=4
请求 A：   [生成][生成][生成][✓完成]
请求 B：   [生成][生成][✓完成]
请求 C：             [←立刻插入][生成][生成]
请求 D：                  [←插入  ][生成]
```

GPU 利用率从传统的 30–50% 提升到 70–90%。

## 19.11 本章小结 {#1911}

```
这一章的几条主线：

① GPU 的核心矛盾是【算力】和【带宽】的不匹配。
  Roofline 模型告诉你一个算子在哪边受限，这决定了该怎么优化。

② 大模型推理几乎全是 Memory Bound。
  优化的核心手段是：减少 HBM 读写次数。

③ GEMM 是主力算子，关键技术是分块（Tiling）和 Tensor Core。
  批量小时 GEMM 也变成 Memory Bound，是推理速度的主要瓶颈。

④ FlashAttention 用分块 + 在线 Softmax，
  把注意力的中间矩阵从 HBM 消除，序列越长收益越大。

⑤ 算子融合 = 减少算子间的数据搬运税。
  LayerNorm、激活函数、GEMM 的 Epilogue 都是融合的好目标。

⑥ 量化 = 用更小的数表示权重/激活，主要收益来自带宽的节省。
  FP8 是 H100 时代的主流选择，DeepSeek-V3 是最激进的落地案例。

⑦ Triton 提供了写自定义 kernel 的"中间道路"：
  比 CUDA 容易写，比 PyTorch 自定义 op 更快，够覆盖大部分场景。

⑧ MoE 的 All-to-All 是分布式训练的主要通信瓶颈，
  解法是：限制跨节点路由 + 用计算流水线遮住通信延迟。

⑨ 推理服务层：PagedAttention 解决 KV Cache 碎片，
  连续批处理解决 GPU 利用率低的问题。
```
