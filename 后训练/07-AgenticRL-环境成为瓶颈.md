# 07 · ⭐ Agentic RL：环境成为新瓶颈

> **这是 2026 年后训练的主战场。** 这一代的几份一手技术报告里，有几家把**一半以上的篇幅**砸在这一章讲的东西上。
>
> 读完你应该能回答：agent 的强化学习和做数学题的强化学习差在哪？为什么"环境"会变成比模型更难的问题？以及——**"环境成为瓶颈"用数字说出来，到底是什么形状。**
>
> **⚠️ 本章的分工**：这里讲**为什么环境是瓶颈**（算法和数据层面）。**工程上怎么解**（异步 rollout、partial rollout、权重同步、引擎解耦）在隔壁目录 [../强化学习训练框架/](../强化学习训练框架/)，本章只链过去，不重写。

---

**本章关键词**（每个缩写第一次出现都给中英文全称）

**Agentic RL**（智能体强化学习）—— 奖励来自"模型真的去操作一个系统，看它成没成"的强化学习。

**环境**（Environment）—— 一个能让模型**真的动手**、并且能**自动判分**的沙盒。本章的主角。

**rollout**（采样 / 轨迹生成）—— 让模型跑一遍完整任务，产出一条轨迹。

**轨迹**（Trajectory）—— 一次 rollout 的产物。在 Agentic RL 里它是"调工具 → 看结果 → 再调"的一长串。

**同步 RL**（Synchronous RL）—— 一批 rollout 全部跑完，才更新一次权重。

**长尾**（Long tail）—— 耗时分布里那一小撮极慢的样本。本章所有工程问题的源头。

**horizon**（时间跨度 / 步数）—— 一条轨迹有多少步。长 horizon 是本章的难点来源。

**信用分配**（Credit assignment）—— 一条 40 步的轨迹失败了，到底该罚哪一步。

**QAT**（Quantization-Aware Training，量化感知训练）—— 训练时就模拟量化误差，让模型提前适应低精度。

**microVM**（微虚拟机）—— 比容器隔离性更强、比传统虚拟机启动更快的沙盒形态。

## 7.1 先看清楚"一条数据"变成了什么

```
【RLVR 的一条训练样本】
   输入：一道数学题
   模型输出：一段 2,000 token 的推理
   奖励：答案对不对（一次字符串比对，微秒级）
   耗时：几十秒，且【可预测】


【Agentic RL 的一条训练样本】
   输入："这个仓库的 CI 挂了，修好它"
   模型输出：
      读 README            → 环境返回文件内容
      跑 pytest            → 环境返回 37 个失败
      读 traceback         → 环境返回堆栈
      改 utils.py          → 环境返回 diff 已应用
      再跑 pytest          → 环境返回 3 个失败
      ...（可能 40 轮）
   奖励：最后测试全过了吗（0 或 1）
   耗时：★ 几分钟到几十分钟，且【完全不可预测】
```

> ★★★ **这一节只要记住一件事**：**"一条数据"从"一段文本"变成了"一次与真实系统的交互过程"。**
> 后面所有的工程灾难，都是这一句话的直接后果。

### ★★ 环境的成本结构表：把每一项成本都摊开

**这张表是本章的地基。** 它解释了为什么同一套 RL 算法，换个任务就从"几秒一条"变成"半小时一条"：

| 成本维度 | 数学题（RLVR） | 代码仓修 bug（Agentic） | 浏览器找信息（Agentic） |
|---|---|---|---|
| **一条 rollout 几步** | **1 步**（生成一段就结束） | **20 ~ 50 步**工具调用 | **10 ~ 100 步** |
| **每步要不要调外部工具** | ✗ 不要 | ✅ 要（读文件、改文件、跑测试） | ✅ 要（发 HTTP 请求） |
| **有没有网络延迟** | ✗ 没有 | ⚠️ 装依赖时有 | ★ **有，而且不受你控制** |
| **单步的环境耗时** | — | 0.1 s（读文件）~ 120 s（跑全量测试） | 0.3 ~ 10 s（看目标站点） |
| **一条轨迹的环境总耗时** | ≈ 0 | **几十秒 ~ 几十分钟** | 几十秒 ~ 几分钟 |
| **判分本身要多久** | 微秒 | ★ **要再跑一遍全量测试**：几十秒 ~ 几分钟 | 答案比对（快）+ 来源核查（慢） |
| **能不能并行** | ✅ 完全能 | ✅ 能，但每条要一个**独立容器**，内存和磁盘是上限 | ⚠️ 受**目标站点限流**，并行度不由你定 |
| **失败怎么重置** | 不需要重置 | 丢掉容器重建（几秒 ~ 几分钟，看镜像大小） | ⚠️ **外部状态可能已被改掉**，重置不彻底 |
| **耗时可不可预测** | ✅ 可预测 | ✗ **完全不可预测** | ✗ **完全不可预测** |

```
★★ 这张表里最该盯住的是【最后两行】，不是耗时那几行。

   "能不能并行" + "耗时可不可预测" 这两格，
   决定了你的 GPU 利用率 —— 而不是"单步多慢"。
   ⟹ 7.3 节会把这件事算成一个具体的百分比。
```

## 7.2 ★★ 官方原话：难点从模型转移到了环境

✅ **GLM-5.3 官方博客**（2026-08-14，见 [../业界模型技术报告/GLM-5.3.md](../业界模型技术报告/GLM-5.3.md)）的原话：

> *"As agent capability improves, much of the difficulty in scaling post-training moves from the model to the environment."*
> （随着智能体能力提升，后训练规模化的难点**从模型转移到了环境上**。）

**"环境"到底是什么**（这个词必须讲清楚）：

```
监督学习需要：  题目 + 标准答案
强化学习需要：★ 一个能让模型【真的动手】、并且能【自动判分】的沙盒

一个"写代码"的环境，必须同时有：
   · 一个能跑的容器（依赖装好、能联网装包）
   · 一份真实的代码仓库和它的 git 历史
   · 一套能执行的测试
   · 一个判定"任务完成没有"的规则
   · ★ 而且要保证这套东西【没有洞】（6.4 节那个问题）
```

### ⚠️ "工程量比造一条 SFT 数据大多少"：把这笔账算出来

```
⚠️ 这一段原来写的是"大三到四个数量级"，我算不出那个数，已经下调。
   下面是能算出来的版本：

造一条 SFT 数据：
   人写：     约 5 分钟  = 300 秒
   模型合成： 几秒

造一个 RL 环境（容器 + 仓库 + 测试 + 判分规则）：
   顺的情况： 约 4 小时  = 14,400 秒
   不顺的情况：约 3 天   = 259,200 秒

⟹ 比值：14,400 / 300 = 48 倍     （1.7 个数量级）
         259,200 / 300 = 864 倍   （2.9 个数量级）

⟹ ⚠️ 所以可以说的是【2 ~ 3 个数量级】。这是本文的估算，无一手出处。

★ 而且这笔账只算了"造"，没算"验"。
  6.4 节那个数字（代码 RL 环境的门禁检查里 65/105 项 FAIL）说明：
  【验证一个环境没有洞，可能比造出来更贵】。
```

## 7.3 ★★★ 长尾：把"环境成为瓶颈"算成一个百分比

**这一节是本章的核心。** 光说"环境慢"没用，要算出它慢成什么形状。

### 第一层：单条轨迹的时间账

```
设定（⚠️ 示意数值，不是实测，但每个数都落在真实量级内）：
   一条轨迹 50 步工具调用
   每一步：模型生成 200 个 token 来决定"调什么工具、传什么参数"
          然后环境执行 2 秒
   单路解码速度按 50 token/s 估（⚠️ 一个常见量级，取决于模型和硬件）
```

| 每一步的时间构成 | 耗时 | 这段时间 GPU 在干什么 |
|---|---|---|
| 模型生成 200 token | 200 ÷ 50 = **4 s** | ✅ **在算** |
| 环境执行这一次工具调用 | **2 s** | ✗ **在等** |
| **单步合计** | **6 s** | **33% 的时间在干等** |

```
一条轨迹 = 50 步 × 6 s = 300 秒 = 5 分钟
   其中 GPU 真正在算 = 50 × 4 = 200 秒
        GPU 纯等待   = 50 × 2 = 100 秒
   ⟹ 单条轨迹的 GPU 空转比例 = 100 / 300 = 33.3%

★★ 但 33% 还【不是】"环境成为瓶颈"的真正形态。
   因为单条轨迹的空转是可以用批处理填掉的：
   一张卡上同时跑 64 条轨迹，这条在等工具的 2 秒里，
   另外 63 条正在生成。⟹ 这一层的损失，工程上是有解的。

⟹ 真正要命的是下面第二层，它【填不掉】。
```

### 第二层：同步 RL 必须等最慢那一条

```
同步 RL 的规则（这是算法要求，不是实现偷懒）：
   一批 128 条 rollout 【全部跑完】，才能算优势、才能更新一次权重。

   ★ 为什么必须等全部？因为 GRPO 的优势要用【组内均值】当基线
     （5.2 节第二步）。少一条，均值就不对，优势就算错。

⟹ 整批的墙钟时间 = 最慢那一条的时间。
```

**把一批 128 条的耗时分布写出来，然后算利用率**：

| 这一批里的 128 条 | 条数 | 单条耗时 | 这些条真正消耗的算力 |
|---|---|---|---|
| 简单任务，几轮就做完 | 64 | 60 s | 64 × 60 = **3,840 卡·秒** |
| 正常长度 | 51 | 180 s | 51 × 180 = **9,180 卡·秒** |
| 反复试错的 | 12 | 600 s | 12 × 600 = **7,200 卡·秒** |
| ★ **最慢的那 1 条**（装依赖卡住 / 死循环） | 1 | **1,800 s** | 1 × 1,800 = **1,800 卡·秒** |
| **合计** | **128** | 最慢 = **1,800 s** | **22,020 卡·秒** |

```
① 这一批【真正有用】的算力  = 22,020 卡·秒
② 这一批【占住】的算力      = 128 张卡 × 1,800 秒 = 230,400 卡·秒
   （同步 RL 下，先做完的卡不能释放，必须在那儿等那一条）
③ ⟹ GPU 利用率 = 22,020 ÷ 230,400 = 9.6%

★★★ 这就是"GPU 利用率可以低到个位数百分比"的具体算法。
   注意它的成因：【不是代码慢】，是【耗时分布有长尾 + 算法要求同步】。
   —— 这两个条件缺一个，这个数字就不成立。
```

**再算一个最能说明问题的对照：丢掉最慢的那一条会怎样**

```
把超时上限设成 600 秒，超时就丢弃：
   墙钟      = 600 秒
   占住算力  = 128 × 600 = 76,800 卡·秒
   有用算力  = 22,020 − 1,800 = 20,220 卡·秒
   利用率    = 20,220 ÷ 76,800 = 26.3%

⟹ ★ 丢掉 128 条里的 1 条（0.8% 的数据），
   利用率从 9.6% 提到 26.3% —— 提升了【2.7 倍】。

⚠️ 措辞纪律：这里是"利用率提升 2.7 倍"，
   不要写成"耗时减少 2.7 倍"（那句话没有意义）。
   对应的墙钟是从 1,800 秒降到 600 秒，即【减少 66.7%】，
   等价于【快了 3 倍】（1 / (1 − 0.667) = 3）。

⚠️ 这个耗时分布是我构造的示意，不是实测。但"丢弃长尾能换来数倍
   利用率"这个结论对任何重尾分布都成立，不依赖具体数值。

⚠️⚠️ 而且丢弃【不是免费的】：被丢掉的恰恰是【最难的那些题】。
   长期这么丢下去，训练分布会系统性地偏向简单任务 ——
   ★ 这是一个很隐蔽的数据问题，而不只是工程取舍。
```

### 解法家族：全都在"打破同步"

| 手段 | 一句话 | 谁在用（✅ 一手报告） |
|---|---|---|
| **异步 RL** | 训练引擎和推理引擎完全解耦，各跑各的，不再等齐 | GLM-5（每次权重同步后**重置优化器**） |
| **Partial rollout** | 一批里完成了 λ 比例就暂停，剩下的下一轮接着跑 | Kimi-K3 |
| **可抢占 rollout** | 长任务可以被打断，用 token 粒度的 WAL 日志恢复 | DeepSeek-V4（Rust 写的 DSec 沙箱平台） |
| **动态过滤** | 把"永远能解出来"的题踢出训练池 | openPangu-2.0（✅ 报告原文叫 **Online Dynamic Filtering**：持续跟踪每条样本的通过率，一直能解出来的样本动态踢出训练循环，让模型"永远停在它的学习前沿"） |

```
★★ 注意这四条和 5.2 节那张采样成本表是同一件事的两面：
   「动态过滤」踢掉的正是 p 太高的题 —— 也就是 5.2 节算出的
   "G = 8 时有 66% 概率整组白跑"的那种题。
   ⟹ 算法侧省采样，系统侧省等待，两边指向同一个动作。
```

## 7.4 异步带来的新病：训推不一致（算法侧只需要懂这一点）

**打破同步解决了利用率，但引入了一个新问题。** ⚠️ 这是一个**系统问题**，完整内容在 [../强化学习训练框架/04-训推一致性.md](../强化学习训练框架/04-训推一致性.md)；本节只讲**算法为什么会被它搞崩**。

```
RL 系统里永远有两套东西在跑：
   训练引擎（更新权重，Megatron 系）
   推理引擎（生成轨迹，vLLM / SGLang 系）

⚠️ 同一份权重，在两个引擎里【算出来的概率不完全一样】
   —— 算子实现不同、并行策略不同、量化方案不同，
      甚至 atomicAdd 的求和顺序不确定都会造成差异。
```

**为什么这对算法是致命的**（接 5.2 节第四步那张 clip 表）：

```
RL 的更新里有一项：  比值 = 【训练引擎算的当前概率】 ÷ 【推理引擎采样时的概率】

★ 这个比值本该【只反映"策略更新了多少"】。
  但现在它混进了"两个引擎实现不一样"的噪声。

⟹ 后果一：clip 误判。5.2 那张表里"比值 1.40 → 被截断"，
          如果这个 1.40 里有 0.3 是引擎差异带来的，
          那就是在【截一个本来不该截的 token】。
⟹ 后果二：噪声大到一定程度，梯度方向就是错的，训练直接崩。

★★ 一句话：异步 RL 把"比值"这个量的信噪比搞坏了，
   而整个 PPO / GRPO 家族的安全机制全都建立在这个量上。
```

**各家的解法**（✅ 各家一手报告，⚠️ 实现细节与取舍见隔壁目录）：

| 模型 | 做法 |
|---|---|
| **DeepSeek-V4** | 追求**逐位确定性**（双 kernel / DeepGEMM / 消除 atomicAdd 的非确定性） |
| **Kimi-K3** | ★ **SFT → RL 全程 QAT**，rollout 和训练用同一套量化方案——**从根上让两边"错得一样"** |
| **GLM-5** | INT4 量化 kernel，训推 **bitwise 一致** |
| **openPangu-2.0** | ⚠️ 这一批报告里唯一做了完整根因解剖的（显式定义 / 计算图重排 / 硬件调度非确定性），外加两阶段白盒逐层对齐方法论。✅ 报告还披露了一条很实用的运维规则：**当训练-rollout 的皮尔逊相关系数低于 0.99 时用更严的掩码，高于 0.99 时放松，以保留探索能力** |

> **QAT** = **Quantization-Aware Training**（量化感知训练），训练时就模拟量化误差，让模型提前适应低精度。

## 7.5 环境从哪来：2026 年真正的数据问题

```
2024 年的问题："哪儿找一百万条高质量 SFT 数据"
2026 年的问题："哪儿找一万个能跑、能判分、且【没有洞】的环境"
```

| 路线 | 做法 | ✅ 好处 | ⚠️ 代价 |
|---|---|---|---|
| **① 真实仓库改造** | 从 GitHub 上挑有测试的项目，把一个真实 commit 反向变成任务 | **最真实**，分布和线上一致 | 数量有限、清洗麻烦、**容易和评测集污染**（见 9.6） |
| **② 程序化合成** | 自动生成任务 + 自动生成验证器 | 可以**无限造** | ★ 门禁检查的失败率很高（见下） |
| **③ 自演化 / 自对弈** | 让模型自己出题、自己加难度 | **不会被榨干** | ⚠️ 难度曲线不好控；可能自己绕进一个小圈子 |

**路线 ③ 的核心动机值得单独讲**：

```
✅ DeepMind 的 Evolving Alignment via Asymmetric Self-Play
   （[arXiv:2411.00062](https://arxiv.org/abs/2411.00062)，Ziyu Ye 等，2024-10）指出：
   静态 prompt 集会被【榨干】—— 模型一旦刷满，学习就停止了。

★ 把这件事和 5.2 节那张表接起来就很清楚了：
  "被榨干"的精确含义就是【这些题的 p 全都接近 1】，
  于是每一组都退化（全对），优势全是 0，梯度为 0。
⟹ 所以模型应该【自己生成自己的训练题目分布】，
   让题目难度跟着模型能力一起往上走。
```

### ⚠️ 路线 ② 那个著名的数字，口径必须先掰清

```
✅ Auditing Reward Hackability in Code RL Training Environments
   （[arXiv:2606.16062](https://arxiv.org/abs/2606.16062)，Shreshth Rajan，2026-06）：
   对自动生成的代码 RL 环境做完整性门禁检查，
   【105 项检查中 65 项 FAIL / 40 项 PASS】→ 65 / 105 = 61.9%

⚠️⚠️ 61.9% 是【检查项】的失败率，分母是"检查项"，不是"环境"。
   它【不等于】"61.9% 的环境是漏的"——
   一个环境可能同时 FAIL 五项，也可能只 FAIL 一项。

⟹ 所以"自动合成一万个环境，一大半是漏的"这句话是
   【本文做的一次口径跳跃】，不是论文的结论。
   方向性判断我仍然认为成立（门禁失败率这么高，环境级缺陷率很难低），
   但它是推断，不是数据。完整讨论在 6.4 节。
```

⚠️ 一个二手但很有信息量的产业数据点：Scale AI 公开表示，**其新增数据项目中近一半涉及 RL 环境**。⚠️ **厂商自述，当趋势看，别当精确统计。**

## 7.6 ★★ 长程信用分配：还没解决的那个问题

```
一条 40 轮的轨迹，最后失败了，结果奖励 = 0。

   问题：★ 是哪一轮错的？

   结果奖励只告诉你"整体失败"。
   而 5.2 节第三步那张表说过：优势 A 是【按轨迹】算的，
   一条轨迹里的每个 token 用同一个 A。
   ⟹ 40 轮里正确的那 35 轮，也拿到了同一个负优势。
```

### 把"被错误惩罚的比例"算出来

```
设定：一条 40 轮的轨迹，其中 35 轮动作是对的、5 轮是错的。
     对的 35 轮共写了 7,000 token，错的 5 轮共 1,000 token，合计 8,000。
     轨迹失败 ⟹ 这 8,000 个 token 全部拿到同一个负优势。

⟹ 7,000 / 8,000 = 【87.5% 的 token，拿到了和它自身质量相反的信号】。

★ 对照一下 5.2 节那条数学题：一条 2,000 token 的推理错在第 3 步，
  被错误惩罚的大概只是开头那一小段。
  ⟹ 轨迹越长，这个比例越接近 100%。
```

**⚠️ 但这里有一个很容易讲错的地方，必须说准**：

```
⚠️ 常见的错误说法是"所以梯度方向是错的"。不对。

   5.2 节验算过：组内所有优势之和恒等于 0。
   所以在【期望】上，这些错误惩罚会被成功轨迹里的正优势抵消掉 ——
   一个在成功和失败轨迹里出现频率相当的动作，净梯度接近 0。

★★ 真正的代价不是"方向错"，是【信噪比】：
   要分辨出一个动作到底好不好，必须让它在足够多的成功轨迹
   和失败轨迹里都出现过，两边抵消之后剩下的那一点差值才是真实信号。
   而这个差值相对于噪声极小。

⟹ 所以结论是：【需要的样本数随轨迹长度快速增长】。
   不是梯度错了，是【样本效率塌了】。
   ★ 而 Agentic RL 里一条样本要几分钟 —— 这两件事撞在一起才是墙。

⚠️ 以上这段机制解释是本文的推演，不是哪篇论文的原话。
```

**目前的缓解手段（都不完美）**：

| 手段 | 做法 | ⚠️ 代价 |
|---|---|---|
| **① 分段奖励** | 给中间里程碑打分（"测试从 37 个失败降到 3 个"给部分分） | ⚠️ 里程碑要人设计，且**极易被 hack**——模型学会"制造进度假象"（6.4 节的钻法） |
| **② 优势整形** | 用轨迹之间的对比来近似逐步信用 | ⚠️ 只是把问题从"逐步"降到"逐段"，没消除 |
| **③ 缩短 horizon** | 把长任务拆成若干短任务分别训 | ⚠️ 模型学不到**全局规划**——而那恰恰是长任务的价值 |
| **④ 上下文压缩**（compaction） | 轨迹太长塞不下时，中途压缩历史 | ✅ GLM-5.2/5.3 用的 SAO with compaction 属于这一类。⚠️ 压掉的信息可能正是后面要用的 |

> 🔮 **这是本教程里我认为最重要的未解问题之一**，[12 章](12-研究热点与开放问题.md)会再讲。

## 7.7 一条 Agentic RL 训练轨迹的完整生命周期

```
① 调度器发任务         "修好 repo X 的 CI"
        ↓
② 拉起沙箱             microVM / 容器，装好依赖
   ✅ Kimi-K3：可恢复的 microVM
   ✅ DeepSeek-V4：Rust 写的 DSec 平台，数十万并发沙箱
        ↓
③ rollout 循环         推理引擎生成动作 → 沙箱执行 → 结果回填上下文
   ⚠️ 这里要处理：超时、崩溃、死循环、模型调一个不存在的工具
   ✅ GLM-5 的 TITO Gateway：拦截所有生成请求，记录 token ID 和元数据，
      把繁琐的 token ID 处理从 agent 逻辑里隔离出来
   ✅ openPangu-2.0 也用了 TITO（Token-in-Token-out），
      目的是消除"生成"和"更新"之间的分词不一致（接 7.4 节）
        ↓
④ 判分                 跑最终测试 / 调 GRM / 规则检查
   ⚠️ 别忘了这一步【自己也要几十秒到几分钟】（7.1 那张表）
        ↓
⑤ 轨迹回传训练引擎     ⚠️ 一条轨迹可能几万 token，回传本身也是带宽问题
        ↓
⑥ 权重更新 → 同步给推理引擎
   ⚠️ 几百 GB 的权重要在几秒内同步到几百个推理副本
   → ../强化学习训练框架/03-权重同步.md
```

★ **看这个循环最大的收获**：**后训练团队的一半人力，花在了 ①②⑤⑥ 这些"和算法无关"的地方。** 这也是本章和隔壁目录分工的由来——那边讲的就是 ①②⑤⑥。

## 7.8 这一章的四句话总结

```
① Agentic RL 把"一条数据"从一段文本变成了一次真实交互，
   这一句话解释了这一章所有的工程复杂度。

② ★ "环境成为瓶颈"的具体形状是一个百分比：
   一批 128 条，耗时有长尾（最慢 1,800 秒 vs 多数 60 秒），
   而同步 RL 必须等齐 ⟹ GPU 利用率 22,020 / 230,400 = 9.6%。
   ⟹ 丢掉最慢的 1 条（0.8% 的数据），利用率升到 26.3%。
   ⚠️ 代价是训练分布会系统性地偏向简单任务。

③ 瓶颈已经从模型转移到环境：
   2026 年缺的不是数据，是【能跑、能判分、且没有洞的环境】。
   ⚠️ 而"没有洞"这一条可能比"能跑"更贵（6.4 节那个 61.9%）。

④ 长程信用分配（40 轮里到底哪轮错了）目前没有好答案。
   ★ 而它的要害不是"梯度方向错了"（期望上会抵消），
     是【信噪比太低、需要的样本数随轨迹长度暴涨】——
     而一条样本要几分钟。这两件事撞在一起，才是把 RL
     推向更长任务时最先撞到的那面墙。
```
