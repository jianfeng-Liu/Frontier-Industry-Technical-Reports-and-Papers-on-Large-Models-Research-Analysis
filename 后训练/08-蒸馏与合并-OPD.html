08 · ⭐ On-Policy 蒸馏（OPD）：四家共同的收口

OPD = On-Policy Distillation（在策略蒸馏）

2026 年后训练最清晰的一次收敛：四家一手技术报告，在流水线的最后一步收敛到了两类几乎等价的数学形式。⚠️ 为什么是四家而不是五家，8.3 节会说清——这件事本身有信息量。
读完你应该能回答：on-policy 蒸馏和普通蒸馏差在哪、为什么这个差别是机制性的而不是程度上的、以及为什么它同时解决了"合并专家"和"找回被遗忘的能力"两个看起来无关的问题。

读法：8.1 和 8.4 各有一张能自己按计算器验算的推演表。8.4 那一节的理论部分⚠️可靠性最低，我会标出来。

本章关键词（每个缩写第一次出现都给中英文全称）

OPD（On-Policy Distillation，在策略蒸馏）—— 让学生自己采样，老师在学生写的每个 token 上给方向。本章主角。

MOPD（Multi-teacher On-Policy Distillation，多教师在策略蒸馏）—— 多个老师版本的 OPD。⚠️ 注意不是 "Multi-domain"。✅ openPangu-2.0 报告里自己那一节的标题用的是 Multi-Expert On-Policy Distillation（多专家在策略蒸馏），⚠️ 两个名字指的是同一类做法。

off-policy 蒸馏（离策略蒸馏）—— 传统蒸馏：老师先做题存下答案，学生对着答案做 SFT。

logits（对数几率）—— 模型在输出层给每个词的原始分数，过 softmax 之后就是概率分布。白盒蒸馏要的就是这个。

KL 散度（Kullback-Leibler divergence）—— 衡量两个概率分布差多远的量。

逆 KL（reverse KL）—— 指 KL(学生 ‖ 老师)。和 KL(老师 ‖ 学生)（正向 KL）的行为不一样，⚠️ 两者谁更好要看任务。

sg[·]（stop-gradient，停止梯度）—— 这一项只当数值用，不往回传梯度。

exposure bias（曝光偏差）—— 训练时只见过完美前缀，一旦自己写歪就进入没训练过的状态。8.1 节的主题。

Task vector（任务向量）—— 微调后的权重 − base 权重，也就是"这次训练到底改了什么"的差分。

TIES（TrIm, Elect Sign & Merge，裁剪-选符号-合并）—— 一种参数空间合并方法。

DARE（Drop And REscale，随机丢弃并重新放缩）—— 另一种参数空间合并方法。

8.1 三种蒸馏，一张表说清

"蒸馏"这个词下面至少有三种完全不同的东西。 先把它们摊开：

黑盒蒸馏（只用输出文本） 白盒蒸馏（用 logits） on-policy 蒸馏（OPD）
数据从谁的分布来 老师的 老师的 ★ 学生自己的
要老师给什么 只要输出的文本 要每个位置的完整概率分布 要每个位置的完整概率分布
学生在学什么 "这道题的答案长这样" "这个位置老师认为每个词有多可能" "我刚才走的这一步，老师会怎么走"
本质上是什么 就是 SFT，只是标准答案由老师写 带软标签的 SFT ★ 是 RL（8.2 节讲为什么）
用闭源 API 当老师 ✅ 可以 ✗ 不行（拿不到完整分布） ✗ 不行
tokenizer 必须一致吗 ✗ 不必 ✅ 必须 ✅ 必须
成本 ✅ 最便宜。老师跑一次，数据可以反复用 N 个 epoch ⚠️ 老师跑一次，但要存全词表分布（存储量暴涨） ✗ 最贵。学生每轮都要重新 rollout，老师每轮都要重新前向
典型失效模式 曝光偏差（见下） 曝光偏差（同上，只是软标签缓解了一点） 多样性坍缩（8.6 节）

★★★ 为什么 on-policy 的那个差别是机制性的：把曝光偏差算出来

这是本章最值得讲透的一件事。 很多介绍把 OPD 说成"效果更好一点"，其实不是程度问题，是训练分布和使用分布重不重叠的问题。

off-policy 蒸馏在干什么：
   ① 老师做 10 万道题，把老师的完整解法存下来
   ② 学生对着这些解法做 SFT

   老师的解法是：  A → B → C → D
   学生被训练的是："看到前缀 A，输出 B"
                  "看到前缀 A→B，输出 C"
                  "看到前缀 A→B→C，输出 D"

★ 注意：学生只在【以老师的正确前缀开头】的状态上被训练过。

问题出在学生自己上考场的时候：

   第 1 步学生写成了 A'（一个老师从来不会写的东西）
   ⟹ 现在学生处在状态 "A'"
   ⟹ 训练集里【没有任何一条数据以 A' 开头】
   ⟹ 学生在这里的行为【完全没有被训练过】，只能靠泛化瞎猜
   ⟹ 猜歪一点，下一步就更偏，误差一步一步累积
   ★ 这就是 exposure bias（曝光偏差），也叫复合误差（compounding error）。

把它算成一个概率。 设学生每一步"走出老师分布之外"的概率是 ε，那么一条 L 步的轨迹至少走歪一次的概率是 1 − (1 − ε)^L：

每步走歪的概率 ε L = 10 步 L = 100 步 L = 1,000 步
0.01（百步一歪） 9.6% 63.4% 99.996%
0.001（千步一歪） 1.0% 9.5% 63.2%
0.0001（万步一歪） 0.1% 1.0% 9.5% 
自己验一格：ε = 0.01、L = 100
   (1 − 0.01)^100 = 0.99^100 = 0.3660
   1 − 0.3660 = 0.6340 = 63.4%   ← 和表里一致

★★★ 现在把 L 换成真实数字：
   长思维链的一条推理轨迹是【几千个 token】。
   就算学生每一步只有千分之一的概率走偏，
   1,000 步下来"至少走偏一次"的概率也有 63%。
   ⟹ 在长输出场景下，"学生走到一个老师没示范过的状态"
      几乎是一个【必然事件】。

⟹ ★★ 所以 off-policy 蒸馏的训练分布和学生的实际使用分布，
   在长输出上【几乎没有重叠】。
   这不是"效果差一点"，是【训练的东西和用的东西不是一回事】。

⚠️ 这里的 ε 是一个概念上的量，不是可直接测量的指标；
   上表是为了把"长度放大错配"这个机制量化出来，不是实验数据。

on-policy 蒸馏怎么从机制上消掉这个缺口

OPD 的三步：
   ① 让【学生自己】做题（学生 rollout）—— 所以数据来自学生当前的分布
   ② 在学生写出的【每一个 token 上】，问老师：
      "这个位置，你会给每个词多少概率？"
   ③ 让学生的分布向老师的分布靠拢

★★★ 关键差别一句话：
   老师不是在【给出答案】，老师是在【对学生自己走的路做点评】。

★★ 为什么这从机制上解决了问题：
   训练数据【定义上】就是学生当前会去的那些状态。
   学生走到 A' 了？那下一条训练数据就是在 A' 上的点评。
   ⟹ 训练分布 ≡ 使用分布。缺口不是"被缩小了"，是【不存在】。

   类比：
   off-policy = 看名师的标准解题录像
   on-policy  = 自己做题，老师在旁边逐步说"这步偏了，我会这么走"

   ⟹ 第二种更有效，因为点评发生在【学生真的会犯错的那些位置上】。

成本：OPD 贵在哪，以及工业界怎么省

off-policy：老师跑一次（离线），结果可以反复用 N 个 epoch。便宜。

on-policy ：★ 学生要 rollout（贵）
            + 老师要对学生的【每一条新轨迹】做前向（贵）
            + 如果有 N 个老师，就是 N 次前向
            ⟹ 而且这些都【不能复用】：学生一更新，轨迹就全变了。

⟹ 这就是 DeepSeek-V4 报告那句"OPD 成本高，但效果最好"的来源。

✅ 一个很实际的省法（openPangu-2.0 报告原文的 Compute Optimization 一节）：

问题：4 个领域专家，如果每个专家都占一个专属 NPU 池，显存要 4 份。
      ⚠️ 本文按 BF16 粗算：505B 参数 × 2 字节 ≈ 1.01 TB / 个专家
         ⟹ 4 个同时驻留 ≈ 4.04 TB，光放权重就吃掉整个超节点。

✅ openPangu 的做法：【顺序载入到一个共享 NPU 池】
   rollout 之后，把样本按"该用哪个专家打分"分组；
   然后一组一组来：载入专家 1 的权重 → 算完它那组样本的 log 概率
                 → 换成专家 2 的权重 → 算它那组 → ...

⟹ 把"同时驻留 4 个专家"压成"同时驻留 1 个"，
   代价是多了 4 次权重载入的时间。
★ 这是一笔很典型的【显存换时间】，而且能换，
  正是因为 OPD 的打分可以按专家分批、不需要同时进行。

8.2 ★★ 它和 RL 的关系：其实是"有密集奖励的 RL"

这是理解 2026 年这批报告的关键一跃。

普通 RL：一整条轨迹跑完，才拿到【一个】0/1 的分数
         ⟹ 信号极其稀疏（7.6 节算过：40 轮的轨迹只有 1 个数）

OPD ：学生写的【每一个 token】都能立刻拿到一个数
      （= 老师和学生在这个位置的概率差）
      ⟹ 信号密集到不能再密集

★★ 所以 OPD 可以看成："把老师当成一个逐 token 的稠密奖励模型"。

这个视角一旦建立，那几份报告的公式就不神秘了：

它们都在做同一件事 —— 把"老师和学生的 log 概率之差"
                       塞进已有的 RL 框架里当 advantage 或 reward：

        Â  =  sg[ log( π_teacher / π_student ) ]
                ↑
          stop-gradient（这一项只当数值用，不回传梯度）

把这个式子按计算器算一遍

挑 5 个 token，看老师的"点评"长什么样（ε 这里不涉及，纯算 log 比）：

学生写的 token 老师给它的概率 π_t 学生给它的概率 π_s 比值 π_t / π_s Â = ln(比值) 优化器会做什么
Wait 0.30 0.05 6.00 +1.792 ★ 大幅提高（老师觉得这里该停下来重想，学生几乎没想到）
let 0.12 0.10 1.20 +0.182 略微提高
42 0.60 0.60 1.00 0.000 不动（两人一致）
the 0.20 0.25 0.80 −0.223 略微压低
obviously 0.01 0.20 0.05 −2.996 ★ 大幅压低（学生的口头禅，老师基本不说） 
验算：ln(6) = 1.7918，ln(1.2) = 0.1823，ln(1) = 0，
      ln(0.8) = −0.2231，ln(0.05) = −2.9957     ← 和表里一致

翻译成人话：
   老师觉得这个词比学生觉得的【更可能】 → 正的优势 → 提高它
   老师觉得这个词比学生觉得的【更不可能】 → 负的优势 → 压低它

这个式子有两个很漂亮的性质，和两个代价：

✅ 性质一：自带停止准则。
   学生完全追上老师时，每个 token 的 Â 都是 0 ⟹ 梯度自然归零。
   ★ 不需要额外设一个"什么时候停"的判据。

✅ 性质二：幅值自动分配注意力。
   差得越远（比值离 1 越远），|Â| 越大，学得越狠。
   ⟹ 学生已经会的地方几乎不花算力，不会的地方信号很强。

⚠️ 代价一：老师也不确定的地方，信号接近 0。
   如果老师在某个位置也是 0.1/0.1/0.1 地纠结，
   它给不出方向 —— 而那往往正是最难的位置。

⚠️ 代价二：比值可以爆炸。
   学生给某个词 1e-6、老师给 0.3，那 ln(比值) ≈ 12.6。
   ⟹ ✅ 所以 Kimi-K3 的公式里明确带了裁剪：
      r = clip( sg[log(π_t/π_θ)], ±R_max )
      ✅ openPangu 也做了同一件事（报告原话：clipping outlying
         log-ratio values），并额外【掩掉接近零优势的 token】
         —— 把算力集中在信息量大的位置上。

🔑 为什么各家宁可写成 RL 的 advantage，而不写成一个 KL loss（数学上近似等价）？
✅ Kimi-K3 报告给了很实际的理由：这样一来，为长周期任务做的 RL 基建（partial rollout 等）原封不动就能复用。
★ 这是一个典型的"为了复用系统而选择数学形式"的决策，很值得记住——同一个数学内容，写成不同形式，接的工程管线完全不同。

⚠️ 另一个副产品（✅ GLM-5 报告发现，K3 和 openPangu 的报告都没提）：既然 advantage 直接来自与老师的差距，就不再需要靠组内比较来估基线了——于是 GRPO 的 group size 可以设成 1，batch size 拉到 1024，吞吐直接拉满。

★★ 为什么这一条很值钱，对照 5.2 节就看明白了：
   GRPO 要 G = 8 ~ 16 条采样，唯一目的就是【算那个组内均值当基线】。
   而 OPD 的基线是老师给的，不需要靠同组样本估。
   ⟹ G 从 16 降到 1，同样的卡能跑 16 倍的唯一 prompt 数。
   ⟹ ★ 而且 5.2 节那张"退化组概率"表里的问题全部消失 ——
      group size = 1 根本不存在"全对/全错导致优势归零"这回事。

   不能拿来代表 M3。

★★ 所以这一格要读成【未披露】，而不是【没做】。
   ⚠️ "未披露 ≠ 没做" 是读技术报告时最容易犯的一类错误：
      把"报告里没写"推成"这家没干这件事"。
   ⟹ 这张表能说的只有一句：
      有后训练报告的四家，在这一步上高度趋同。

★★ 形式上其实只有两类，不是四类

① 写成 loss：       DeepSeek-V4 —— 全词表逆 KL loss
                    min Σ w_i · D_KL(π_student ‖ π_teacher_i)

② 写成 RL 的优势/奖励： Kimi-K3 / GLM-5 / openPangu-2.0
                    Â = sg[ log( π_teacher / π_student ) ]

★★★ 第 ② 类这三家是【各自独立收敛】到同一个式子的：
   GLM-5 报告    2026-02   ← 最早，早了五个月
   Kimi-K3 报告  2026-07
   openPangu     2026-07-31

⟹ 三家互不相同的团队、不同的硬件（NVIDIA / NVIDIA / 昇腾 NPU）、
   不同的目的（纵向修复 / 横向合并 / 横向合并），
   写出了同一个形式。
   ★ 这种独立收敛，比任何单家的"我们效果最好"都更有说服力 ——
     它说明这个形式基本可以当成这一代的事实标准。

⟹ 所以"四种用法"更准确的说法是：【两类形式，四种用途】。

★★★ 这张表最值得注意的一格是 GLM-5：
   它的老师不是"领域专家"，而是【自己前面几个阶段的 checkpoint】。

GLM-5 的做法画出来是这样（它不是在合并专家，是在做时间上的修复）：

训练阶段本来是顺序走的，一步接一步：

   base  ──→  SFT  ──→  Reasoning RL  ──→  Agentic RL  ──→  最终学生

⚠️ 问题：后面每一段 RL 都会【部分冲掉】前面学到的东西（灾难性遗忘）。

GLM-5 的解法：把前面每个阶段【存下来的那份 ckpt】都请回来当老师。

   SFT ckpt        ─┐
   Reasoning ckpt  ─┼──→  三个一起当老师  ──→  蒸给最终的学生
   Agentic ckpt    ─┘

⟹ 它不是在"合并专家"，是在【把被后续训练冲掉的自己找回来】。

★ 两种完全不同的用途，用的是同一个式子：
   【横向合并】把不同领域的能力捏到一起
                （DeepSeek-V4 / Kimi-K3 / openPangu-2.0）
   【纵向修复】把被后续阶段冲掉的自己捞回来（GLM-5）

★★ 能看出这个区别，说明你真的读懂了这批报告。
   而且注意：纵向修复这件事只有在"多阶段顺序 RL"成为标配之后才会出现 ——
   它是一个【新流水线长出来的新问题】，不是一个老问题的新解法。

⭐ 一个值得注意的细节差异（✅ 两家报告直接对话）：GLM-5 承认自己是从推理后端取老师的概率，并把"迁到训练引擎"列为未来工作；openPangu-2.0 直接用训练引擎的前向算老师概率，并在报告里主动点名 GLM-5 做对比。

★ 这个差异为什么要紧：接 7.4 节。
  推理后端和训练引擎算出来的概率【本来就不完全一样】。
  如果老师概率来自推理后端、学生概率来自训练引擎，
  那 log(π_t / π_s) 这个差里就混进了【引擎实现差异】的噪声 ——
  而它本该只反映"老师和学生的能力差"。
  ⟹ 所以 openPangu 那一步不是洁癖，是在修一个真实的偏置。

8.4 ★★ 对照：模型合并是怎么算的，为什么它在跨域时不行

这一节把"参数空间合并"的几种方法逐个算出来。 ⚠️ 本节后半段的理论解释是整章可靠性最低的部分，我会明确标出。

📎 "把多个专家变成一个模型"有三条路线（数据空间 / 参数空间 / 函数空间），框架性的分类在 03 章 3.6。本节只深挖参数空间那条路具体怎么算，以及它为什么在跨域时失效。

四种参数空间合并方法的算式

记号：W_base 是 base 权重；W_i 是第 i 个专家微调后的权重。

① 权重平均 / Model Soup
      W_合 = Σ w_i · W_i          （权重 w_i 加起来等于 1）

② 任务向量 / Task Arithmetic（"任务算术"）
      先定义任务向量：  τ_i = W_i − W_base
         ★ 它就是"这次微调到底改了什么"的差分。
      再合并：          W_合 = W_base + λ · Σ τ_i

   ★★ 这两个式子在 λ = 1/n 时【完全等价】，可以自己展开验：
      W_base + (1/n)·Σ(W_i − W_base)
    = W_base + (1/n)·ΣW_i − W_base
    = (1/n)·ΣW_i                     ← 就是简单平均

   ⟹ 所以 task vector 不是一个新算法，是一个【改写方式】。
      它把"合并权重"改写成"合并改动量"，于是可以对每个改动量
      单独【加权、裁剪、投票】—— 这才是下面两个方法的立足点。

③ TIES（TrIm, Elect Sign & Merge：裁剪 → 选符号 → 合并）三步：
      第一步 Trim        每个 τ_i 只保留幅值最大的 top-k%，其余置 0
      第二步 Elect Sign  对每个参数位，比较"所有正分量的幅值之和"
                         和"所有负分量的幅值之和"，大的那一方定符号
      第三步 Merge       只平均【和选中符号一致】的那些分量

④ DARE（Drop And REscale：随机丢弃并重新放缩）：
      以概率 p 把 τ 的分量随机置 0，剩下的除以 (1 − p)
      ★ 为什么要除以 (1−p)：让期望不变。
        E[τ'] = (1−p) · τ/(1−p) = τ    —— 自己验一下就懂这一步的用意

✅ 出处说明（四个编号已逐个核对「编号 ↔ 标题 ↔ 第一作者 ↔ 会议」，2026-10-08）：

方法 arXiv 论文标题 第一作者 / 会议
Model Soups 2203.05482 Model soups: averaging weights of multiple fine-tuned models improves accuracy without increasing inference time Wortsman 等 / ICML 2022
Task Arithmetic 2212.04089 Editing Models with Task Arithmetic Ilharco 等 / ICLR 2023
TIES-Merging 2306.01708 TIES-Merging: Resolving Interference When Merging Models Yadav 等 / NeurIPS 2023
DARE 2311.03099 ⚠️ 标题其实是 Language Models are Super Mario: Absorbing Abilities from Homologous Models as a Free Lunch —— DARE（Drop And REscale）是文中的方法名，不是标题，按标题搜是搜不到的 Yu 等（阿里）/ ICML 2024

一个 4 维的手算例子：看符号冲突怎么被处理

假设模型只有 4 个参数（真实模型有几千亿个，但机制完全一样）。两个专家的任务向量：

τ_数学 = [ +0.80,  −0.10,  +0.30,  +0.02 ]
τ_代码 = [ −0.60,  +0.05,  +0.40,  −0.01 ]

方法 ①/②（简单平均，各占一半）：逐位算 (τ_数学 + τ_代码) / 2

方法 ③（TIES，取 top-50% 也就是每个向量留 2 个分量）：

第一步 Trim：
   τ_数学 的幅值排序：0.80 > 0.30 > 0.10 > 0.02 → 留第 1、3 位
      ⟹ [ +0.80,  0,  +0.30,  0 ]
   τ_代码 的幅值排序：0.60 > 0.40 > 0.05 > 0.01 → 留第 1、3 位
      ⟹ [ −0.60,  0,  +0.40,  0 ]

第二步 Elect Sign：
   第 1 位：正方总幅值 = 0.80，负方总幅值 = 0.60  →  0.80 > 0.60  →  选 "+"
   第 3 位：两边都是正的                          →  选 "+"
   第 2、4 位：都被裁掉了                          →  0

第三步 Merge（只平均和选中符号一致的分量）：
   第 1 位：只有 +0.80 和 "+" 一致   →  结果 = 0.80
   第 3 位：+0.30 和 +0.40 都一致     →  结果 = (0.30 + 0.40) / 2 = 0.35
参数位 τ_数学 想要 τ_代码 想要 简单平均的结果 TIES 的结果
第 1 位（★ 符号冲突） +0.80 −0.60 +0.10 +0.80
第 2 位（都很小） −0.10 +0.05 −0.025 0（被裁掉）
第 3 位（两边同号） +0.30 +0.40 +0.35 +0.35
第 4 位（都很小） +0.02 −0.01 +0.005 0（被裁掉） 
★★★ 这张表要横着读第 1 行和第 3 行的对比：

第 3 位（两边同号，没冲突）：
   简单平均 = 0.35，TIES = 0.35 —— 【完全一样】。
   ★ 这说明：参数平均在"没有冲突"的地方本来就工作得好好的。

第 1 位（符号冲突）：
   数学专家想 +0.80，代码专家想 −0.60。
   · 简单平均给 +0.10 —— 数学专家要的 0.80 只剩下 12.5%，
     代码专家要的 −0.60 直接变成了正数。【两边都不满意】。
     ★★ 这就是【跷跷板效应（seesaw effect）】在单个参数上的样子。
   · TIES 给 +0.80 —— 保住了数学专家，
     代价是代码专家在这一维的要求被【完全无视】。

⟹ ★★ 所以 TIES 并没有"解决"冲突，它只是换了一种处理方式：
   从"两边都砍一半"变成"赢家通吃"。
   ⟹ 哪种更好，取决于这些冲突是"真冲突"还是"噪声"。
      如果大部分冲突来自噪声，赢家通吃就赢；
      如果是真冲突（两个任务真的要求相反的方向），两种都救不了。

什么时候参数合并有效（这张表比任何理论都实用）

场景 参数平均有效吗 为什么
同一次训练、相邻几个 step 的 ckpt 平均 ✅ 有效 它们在同一个"盆地"里，差异主要是优化噪声
同一个 base、不同随机种子跑同一个训练 ✅ 常常有效（降方差，涨零点几分） 同上。★ 这是参数平均最常见的成功用法
同一个 base、短距离微调（LoRA / 少量 SFT 步） ⚠️ 经常有效 τ 的幅值小，"线性近似"还成立
同一个 base、各自做完整 RL 的领域专家 ✗ 基本不行 τ 幅值大、方向冲突多，线性近似破了
不同 base / 不同架构 ✗ 完全不行 参数位根本不对应，第 i 个神经元在两边编码的东西不一样

⚠️⚠️ 为什么它跨域失效：有现象，但理论不牢

✅ 现象层面有一手出处。KAT-Coder-V2.5 报告
   （[arXiv:2607.05471](https://arxiv.org/abs/2607.05471)）的原话大意：
   参数平均 / Task Arithmetic / 顺序多域 SFT 都会出现【跷跷板效应】，
   因为【参数空间的合并破坏了专家特有的结构】，
   而离线监督又引入了训推不匹配。
   ⟹ 所以 MOPD 改在【函数空间】做融合。

✅ DeepSeek-V4 报告也给了同样的判断：权重合并会因为参数空间不对齐
   而失效；混合 RL 会让不同领域的奖励互相冲突。所以选 OPD ——
   成本高，但效果最好。
   （见 [03 章](03-分训与合训.md) 3.6 的引用）

⚠️⚠️ 但"为什么符号投票应该赢""为什么跨域就不行"这一层，
   目前只有几个启发式说法，没有一个能【在合并之前预测结果】的理论：
   · "线性模式连通性"（linear mode connectivity）：
     同一个 base 的两次微调，如果中间的插值路径上损失不升高，
     那它们就"在同一个盆地里"，可以平均。
     ⚠️ 这是一个【事后能测、事前不能算】的性质。
   · "参数不干涉"（parameter interference）：
     假设不同任务用到的参数子集大致不重叠，所以裁剪掉小分量不损失能力。
     ⚠️ 这个假设在真实大模型上没有被严格验证过。
   · TIES 的 top-k% 比例、DARE 的丢弃率 p，都是【调出来的超参】，
     没有原则性的取法。

⟹ ★★ 所以这一节的正确态度是：
   【把它当一套经验手段用，别当一套理论用。】
   上面那张"什么时候有效"的表，可靠性远高于任何机制解释。

★★ 为什么函数空间是良定义的，而参数空间不是

参数空间合并在要求什么：
   "几个专家的参数可以线性插值。"
   ⚠️ 这个要求的问题是：它【依赖参数的排列方式】。
      神经网络有置换对称性 —— 把一层里的神经元重新编号、
      同时把下一层的权重相应重排，得到的是【同一个函数】，
      但参数向量完全不同。
   ⟹ 两个专家各自训远了之后，它们可能是"同一个功能、不同编号"，
      这时按位平均在数学上就是在做一件【没有意义】的事。

函数空间合并（OPD）在要求什么：
   "给同样的输入，学生的输出分布 ≈ 老师的输出分布。"
   ✅ 这个要求【完全不涉及参数长什么样】。
      它对置换对称性是不变的，对架构差异也宽容得多。

★★★ 一句话：
   "输出分布要接近"是一个良定义的要求；
   "参数要接近"不是 —— 因为参数本来就不唯一。
   ⟹ 这是 OPD 比参数平均好的【最根本的那条理由】，
      而且它不需要任何实验来支持，是一个结构性的事实。

常识：蒸馏的天花板是老师。学生最多追平老师。

8.6 失败模式：OPD 不是万能的

⚠️ 下面这些来自 OPD 综述（arXiv:2604.00626，Mingyang Song 等，2026-04）和社区整理，⚠️ 本目录未归档 PDF。

失败模式 机制 后果
① 多样性坍缩 学生一味模仿老师的分布，输出多样性下降 ⟹ 后续如果还要做 RL，探索空间已经被压扁了（和 02 章 2.5 的病三、5.3 的熵坍缩同源）
② tokenizer 不匹配 ★ 老师和学生分词器不同时，"逐 token 对齐"根本无从谈起（见下） ⟹ 这是跨家族蒸馏（用别家模型当老师）最硬的一道墙
③ 思维模式不兼容 老师习惯长思维链、学生是 non-thinking 模式 ⟹ 蒸不动。两边在同一个位置想做的事根本不一样
④ 老师没有"新东西"可给 老师的能力学生已经有了 ⟹ 每个位置的 Â 都接近 0，OPD 只是在浪费算力。✅ 成功条件之一就是【老师具备学生没有的能力】

② 为什么 tokenizer 不一致就彻底做不了：一个具体例子

假设老师的词表 15 万，学生的词表 12.8 万。同一个单词 "unbelievable"：

   老师切成： [ "unbeliev", "able" ]            →  2 个 token
   学生切成： [ "un", "believ", "able" ]        →  3 个 token

⟹ "在第 2 个 token 上，老师会给每个词多少概率" 这句话【没有定义】：
   两边的"第 2 个 token"指的不是同一段文本。
   老师的第 2 个 token 覆盖 "able"，学生的第 2 个覆盖 "believ"。

★★ 注意这不是"误差大一点"，是【对齐关系不存在】。
   OPD 的整个式子建立在"学生写的第 t 个 token"这个位置上，
   位置对不上，式子就无从计算。

⚠️ 有一些工作尝试用"最小公共子串对齐 / 字节级重映射"来桥接，
   ⚠️ 但都会引入额外的近似误差，且未见一手工业报告采用。

★ 一条工程硬门槛：闭源 API 当老师做不了标准 OPD

OPD 需要老师的【完整输出分布】（logits）。

   用开源模型当老师：可以 —— logits 拿得到。
   用闭源 API 当老师：做不了 —— API 通常只返回 top-k 个 logprob。

把这件事量化一下：
   一个 15 万词表的模型，API 给 top-20 的 logprob，
   覆盖的词表位置比例 = 20 / 150,000 = 0.013%

⚠️ 要说公平：头部几个词往往占了大部分概率质量，
   所以"概率质量的覆盖率"远高于 0.013%。
   ★ 但逆 KL 这类目标要对【整个词表】求和，
     尾部那些小概率项全部丢失 —— 而学生犯的错恰恰常常在尾部
     （学生给某个词 0.2、老师给 0.001，这一项的 Â 是 −5.3，
      信息量极大，而它根本不在 top-20 里）。

⟹ 所以结论是：闭源 API 只能退回【黑盒蒸馏】（拿它的输出文本做 SFT），
   也就回到了 8.1 那张表最左边一列，连带回到曝光偏差。

8.7 这一章的四句话总结

① on-policy 蒸馏 = 学生自己走路，老师在每一步旁边点评。
   它把老师变成了一个逐 token 的稠密奖励模型 ——
   所以它其实是 RL，不是 SFT。

② ★ 它比普通蒸馏好的理由是【机制性的，不是程度上的】：
   off-policy 蒸馏只在"老师的正确前缀"上训练过学生，
   而学生每步只要有千分之一的概率走偏，1,000 步下来
   "至少走偏一次"的概率就是 63% —— 训练分布和使用分布
   在长输出上几乎没有重叠。
   OPD 的数据【定义上】来自学生自己的分布，这个缺口不存在。

③ 2026 年四家一手报告用【两类形式】做了【四种用途】：
   形式上分两类：DeepSeek 写成全词表逆 KL loss；
                K3 / GLM / openPangu 写成 sg[log(教师/学生)] 当 advantage。
   用途上分两类：【合并多个专家】（DeepSeek / K3 / openPangu）
                【找回被后续阶段遗忘的能力】（GLM-5）
   ⚠️ MiniMax M3 在这张对照里缺席 —— 因为它没有技术报告，
      不是因为它不做 OPD。【未披露 ≠ 没做】。

④ 它比参数平均好，根子在【函数空间的要求是良定义的，参数空间的不是】：
   神经网络有置换对称性，"同一个功能、不同神经元编号"的两份权重
   按位平均是没有意义的；而"给同样输入、输出分布接近"
   完全不依赖参数长什么样。
   ★ 它的硬门槛是：老师要能给出 logits，且 tokenizer 必须一致。
