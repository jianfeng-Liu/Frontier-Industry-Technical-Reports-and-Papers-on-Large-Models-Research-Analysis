00 · 一个例子讲清：你发一张图，模型里到底发生了什么

这一章只讲一件事：一张图片是怎么"变成模型能读的东西"的。
读完这一章，后面 01~14 章都只是在给这条链路的每一节做放大。
不需要任何背景，只需要知道"大模型是一个吃 token、吐 token 的东西"。

0.1 先看现场

你在对话框里拖进一张手机截图，配一句话：

    [截图.png]  +  「这个报错怎么修？」

几秒后模型说："你的 config.yaml 第 12 行缩进用了 tab，YAML 只认空格。"

它没有"看见"任何东西。 它收到的，从头到尾都是一串数字向量。这一章讲这串向量是怎么造出来的。

0.2 ★★ 卡住一切的那个约束

先记住这句话，它是整个多模态领域的总起点：

🔑 大语言模型（LLM）的输入只有一种东西：一串向量。
每个向量长得都一样（比如 4096 维），谁也不知道它原来是文字、是图、还是声音。

文本是怎么变成向量的？两步，中间隔着一本词典：

    「猫」 ──[tokenizer 查词典]──→ 编号 27364 ──[查 embedding 表]──→ 4096 维向量
             ★ 离散的：全世界只有 15 万种可能                 ★ 连续的：一行浮点数

图片没有词典。没有人能说清一张照片对应词表里的第几号。 于是问题变成：

    ⚠️ 怎么在【不查词典】的情况下，把一张图直接变成一串 4096 维向量，
       并且要让 LLM 觉得这些向量"和文字向量是一路货"？

🔑 多模态大模型的全部工程，几乎都是在回答这一个问题。

0.3 四步走完全程

    ┌─────────────┐
    │  原图        │  1092 × 1092 像素，3 个颜色通道
    └──────┬──────┘
           │  ① 切块（patchify）
           ▼
    ┌─────────────┐
    │ 6084 个小块  │  每块 14×14 像素，78 × 78 = 6084 块
    └──────┬──────┘
           │  ② 视觉编码器（ViT）：让每块"看看邻居"，理解自己是什么
           ▼
    ┌─────────────┐
    │ 6084 个向量  │  每个 1152 维（视觉塔自己的宽度）
    └──────┬──────┘
           │  ③ 合并 + 连接器：4 块并 1 块，再把 1152 维→ 4096 维
           ▼
    ┌─────────────┐
    │ 1521 个向量  │  每个 4096 维 ← ★ 现在它们"长得和文字向量一模一样"了
    └──────┬──────┘
           │  ④ 和文字向量拼成一条序列，喂进 LLM
           ▼
    [<img> v1 v2 ... v1521 </img>] [这][个][报][错][怎][么][修]
    └──────── 1521 个 ────────┘   └──── 7 个 ────┘

然后 LLM 就照常干活了——它根本不在乎前面那 1521 个向量是从哪来的，
就像你读一本书时不在乎某一页是激光打印还是喷墨打印。

★★ 这就是为什么这类模型的通用名字叫 "视觉语言模型"，而不是"看图模型"：
它 90% 的身体还是那个语言模型，前面只是多接了一个"翻译器"。

0.4 📖 三个新名词，一次讲完

名词 英文 干什么 在哪讲
视觉编码器 / 视觉塔 vision encoder / vision tower 把像素块变成"有语义的向量"，比如认出这块是"字母 t" 02
连接器 / 投影层 connector / projector / adapter 把视觉塔的向量"翻译"成 LLM 认识的形状和风格 03
视觉 token visual token 上面那 1521 个向量，一个就叫一个视觉 token 全书

⚠️ "视觉 token"这个叫法有点骗人：文本 token 是整数编号（27364），视觉 token 是一行浮点数，
它不在词表里，也没有编号。之所以也叫 token，只因为它在序列里占一个位置、参与同一套注意力计算。
★ 这个区别在 09 章讲图像生成时会突然变得极其重要——
因为"要模型吐出一张图"的时候，你就不得不给图像发明一本词典了。

0.5 ★★ 现在算一笔账：一张图值多少钱

上面那张 1092×1092 的图，最后占了 1521 个 token。做个对照：

    1521 个 token  ≈  1100 个汉字   ≈  一页半 A4 纸的中文
                   ≈  1150 个英文单词

🔑 一张普通截图 ≈ 一篇短文的成本。 这一句话解释了这个领域一大半的技术动作。

再看几个真实型号的口径（✅ 数字来自本仓库已核对的一手报告）：

型号 输入尺寸 patch 切出多少块 合并后 token 数
Kimi K3 / MoonViT-V2 3584 × 3584 14 256×256 = 65536 2×2 pixel shuffle → 16384
MiniMax M3 2016 × 2016 14 144×144 = 20736 2×2 merge → 5184

✅ 出处：../业界模型技术报告/Kimi-K3.md §六、../业界模型技术报告/MiniMax-M3.md §架构表。
⚠️ "合并后 token 数"是我按 边长÷patch 再除以 4 算的，两家报告都没有直接列这个数字。

视频更夸张。按 GLM-5.3 报告里提到的 1 fps 抽帧口径 ✅：

    一段 5 分钟的视频  →  300 帧
    每帧按 448×448 编码  →  每帧 (448/14)² = 1024 块  →  2×2 合并后 256 token
    ⟹ 300 × 256 = 76,800 token
    ⟹ ⚠️ 一段五分钟的视频，比一本《活着》还长

★★ 所以你会看到本领域到处都在做同一件事：想尽办法砍 token 数。
2×2 合并、时间维池化、动态分辨率、token 剪枝……04 和 05 两整章都在讲这个。
不是为了省显存那么简单——注意力的开销是 token 数的平方。 token 数翻倍，算力翻四倍。

0.6 ★ 三个反直觉的点

① 模型看到的画面，分辨率比你想的低得多

一张图被切成 14×14 的块之后，块内部的细节就被压成一个向量了。

    ⟹ 这就是为什么早期模型看不清图里的小字：
       224×224 的输入，一个 14×14 的块里可能糊了两三个字符
    ⟹ 这也是为什么"提高分辨率"是过去两年多模态最大的性能来源之一（04 章）

② 图像 token 的"信息密度"和文字完全不对等

    一段文字里，去掉 10% 的 token → 句子基本读不懂了
    一张图里，去掉 10% 的 patch  → 你多半看不出差别
    ⟹ 图像 token 冗余度极高 ⟹ 才敢做 2×2 合并、token 剪枝这些暴力操作
    ⟹ ⚠️ 但"冗余"是对**普通照片**说的；对**密集文档**（表格、公式、小字）就不成立
       —— 这是 04 章那些"动态分辨率"方案的根本动机

③ 同一张图，喂给两个模型，token 数可以差 10 倍

因为切法不同（patch 大小、分辨率策略、合并倍数全都不一样）。

⟹ 两家模型的"多模态价格"根本没法直接比，得先问清楚"你这张图算几个 token"。
⟹ 同理，两家的多模态评测分数也没法直接比（11 章会展开，
本仓库的 模型技术对比 已经点破过这件事：
✅ K3 与 M3 之间"零个共享的视觉 benchmark"）。

0.7 那声音、视频、图像生成呢？

同一套骨架，换一个前端：

    图片  →  ViT 视觉塔      →  连接器  →┐
    视频  →  ViT + 时间维处理  →  连接器  →┤
    音频  →  音频编码器        →  连接器  →┼→  [一串 4096 维向量]  →  LLM
    文字  →  tokenizer + 查表                →┘

输出侧则是另一个故事，也是这两年真正在变的地方：

    只输出文字      →  "理解型"多模态模型（本教程 01~08 章）
    还要输出图/音   →  ⚠️ 麻烦大了：LLM 只会从词表里挑编号，怎么"挑"出一张图？
                       →  两条路：外挂一个扩散模型 / 给图像造一本词典
                       →  [09 章](09-生成侧-图像与统一模型.md) 专门讲这个

0.8 🔑 这一章的四句话

  1. LLM 只吃向量。多模态的全部难点，是在没有词典的情况下把图/音变成"像文字一样的向量"。
  2. 链路是四步：切块 → 视觉编码器 → 连接器 → 拼进文本序列。三大件对应 0203 两章。
  3. 一张图 ≈ 一千多个 token，一段五分钟视频 ≈ 七八万个 token。 这个账决定了后面所有的设计取舍。
  4. ⚠️ "多模态"其实是两个方向的问题：让模型看懂（01~08 章）和让模型画出来/说出来（09、10 章），
    它们的技术栈差别，比很多人以为的大得多。
