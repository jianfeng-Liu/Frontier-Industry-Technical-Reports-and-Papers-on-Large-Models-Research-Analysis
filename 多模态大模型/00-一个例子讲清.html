00 · 一个例子讲清：你发一张图，模型里到底发生了什么

这一章只讲一件事：一张图片是怎么"变成模型能读的东西"的。
读完这一章，后面 01~14 章都只是在给这条链路的每一节做放大。
不需要任何背景，只需要知道"大模型是一个吃 token、吐 token 的东西"。
读法：0.3 和 0.5 两节各有一张可以自己验算的表，里面每个数字都给了来路。建议拿纸笔跟着除一遍 —— 算过的数字才会变成直觉。

0.1 先看现场

你在对话框里拖进一张手机截图，配一句话：

    [截图.png]  +  「这个报错怎么修？」

几秒后模型说："你的 config.yaml 第 12 行缩进用了 tab，YAML 只认空格。"

它没有"看见"任何东西。 它收到的，从头到尾都是一串数字向量。这一章讲这串向量是怎么造出来的。

0.2 ★★ 卡住一切的那个约束

先记住这句话，它是整个多模态领域的总起点：

🔑 大语言模型（LLM = Large Language Model，大语言模型）的输入只有一种东西：一串向量。 每个向量长得都一样（比如 4096 维），谁也不知道它原来是文字、是图、还是声音。

文本是怎么变成向量的？两步，中间隔着一本词典：

    「猫」 --[tokenizer 查词典]--> 编号 27364 --[查 embedding 表]--> 4096 维向量
             ★ 离散的：全世界只有 15 万种可能                 ★ 连续的：一行浮点数

📖 tokenizer（分词器） = 把一段文字切成若干"词片"并查出各自编号的那个程序。embedding 表（词嵌入表） = 一张 15 万行 × 4096 列的大矩阵，第 27364 行就是「猫」这个编号对应的向量。

图片没有词典。没有人能说清一张照片对应词表里的第几号。 于是问题变成：

    ⚠️ 怎么在【不查词典】的情况下，把一张图直接变成一串 4096 维向量，
       并且要让 LLM 觉得这些向量"和文字向量是一路货"？

🔑 多模态大模型的全部工程，几乎都是在回答这一个问题。

0.3 ★★ 四步走完全程：把一张图的形状一路算下来

先看链路的样子（每一步的数字在下面那张表里逐行验算）：

   原图  [3, 1092, 1092]
     |
     |  (1) 切块 patchify：每 14x14 像素切一块
     v
   6084 个小块，每块 588 个数         <- 588 = 14 x 14 x 3(RGB)
     |
     |  (2) 视觉编码器 ViT：27 层，让每块"看看邻居"，弄明白自己是什么
     v
   6084 个向量，每个 1152 维          <- 1152 是视觉塔自己的宽度
     |
     |  (3) 2x2 空间合并 + 连接器：4 块并 1 块，再把 4608 维换成 4096 维
     v
   1521 个向量，每个 4096 维          <- 现在它们"长得和文字向量一模一样"
     |
     |  (4) 和文字向量拼成一条序列，喂进 LLM
     v
   最终序列 = <|image_start|> + 1521 个视觉向量 + <|image_end|> + 7 个文本 token

现在把每一步的形状逐行算出来。 假设配置是业界最常见的那一套：视觉塔用 SigLIP-SO400M 的形状（27 层 / 宽 1152 / patch 14，02 章讲它），LLM 主干 hidden dim = 4096，输入是一张 1092×1092 的截图。

步骤 做什么 出来的形状 每个数怎么来的
⓪ 原图 解码成像素矩阵 [3, 1092, 1092] 3 = RGB 三个颜色通道
① 切块 每 14×14 像素切一块，拉平 [6084, 588] 6084 = (1092÷14)² = 78²
588 = 14×14×3
② 线性投影 过一个 588×1152 的矩阵 [6084, 1152] 1152 = 视觉塔的宽度
这一个矩阵 588×1152 ≈ 68 万参数
③ 加位置编码 形状不变，数值变 [6084, 1152] 告诉模型"哪块在左上角"
④ 过 27 层 Transformer 形状不变，语义变 [6084, 1152] 每块"看过"其余 6083 块
★ 理解发生在这一步
⑤ 2×2 空间合并 相邻 4 块的向量拼起来 [1521, 4608] 1521 = 6084÷4
4608 = 4×1152
⑥ 连接器（两层 MLP） 换成 LLM 的宽度 [1521, 4096] 4096 = LLM 的 hidden dim
⑦ 和文本拼接 直接首尾相接 [1521+2+7, 4096] 2 = 两个图像边界标记
7 = 「这个报错怎么修」
⑧ 过 LLM，自回归吐字 和纯文本一模一样 — LLM 不知道前 1521 个是图

★★ 这张表里只有第 ⑤ 行把 token 数变少了，其余每一行 token 数都不动。 整条链路的 token 预算，就是在第 ① 行（切多细）和第 ⑤ 行（合并多少）这两处定下来的 —— 这也正是 03 和 04 两章的全部内容。

⚠️ 第 ⑤ 行容易被误读成"丢信息"：4 个 patch 并成 1 个，但 4×1152 = 4608 个数一个没少，只是换了个装法，由第 ⑥ 行那个 MLP 自己决定留什么。真正把信息硬压掉的是 Q-Former 那一类做法（03 章 做法③），它会把 6084 个向量压成固定的 32 个。

然后 LLM 就照常干活了 —— 它根本不在乎前面那 1521 个向量是从哪来的，就像你读一本书时不在乎某一页是激光打印还是喷墨打印。

★★ 这就是为什么这类模型的通用名字叫 "视觉语言模型"，而不是"看图模型"：它 90% 的身体还是那个语言模型，前面只是多接了一个"翻译器"。

0.4 📖 三个新名词，一次讲完

名词 英文全称 干什么 在哪讲
视觉编码器 / 视觉塔 vision encoder / vision tower 把像素块变成"有语义的向量"，比如认出这块是"字母 t" 02
连接器 / 投影层 connector / projector / adapter 把视觉塔的向量"翻译"成 LLM 认识的形状和风格 03
视觉 token visual token 上面那 1521 个向量，一个就叫一个视觉 token 全书
patch（图块） patch 第 ① 步切出来的那 6084 个 14×14 小方块 全书

⚠️ "视觉 token"这个叫法有点骗人：文本 token 是整数编号（27364），视觉 token 是一行浮点数，它不在词表里，也没有编号。之所以也叫 token，只因为它在序列里占一个位置、参与同一套注意力计算。

⚠️ 更要紧的是别把这三个数混成一个（本目录最高频的误读）：

别混 本例的值 关系
像素数 1092² = 1,192,464 —
patch 数 6084 = 像素数 ÷ 14²
视觉 token 数 1521 = patch 数 ÷ 压缩倍数（本例 4）
视觉 token 占上下文的比例 1521 ÷ (1521+9) ≈ 99.4% 还要和文本 token 一起算，不是单看图

patch 数 ≠ token 数（中间隔着连接器的压缩），token 数 ≠ 占上下文的比例（分母里还有文字和模型输出）。04 章会反复用到这三层区分。

★ 这个"视觉 token 没有编号"的区别，在 09 章讲图像生成时会突然变得极其重要 —— 因为"要模型吐出一张图"的时候，你就不得不给图像发明一本词典了。

0.5 ★★ 现在算一笔账：一张图值多少钱

上面那张 1092×1092 的图，最后占了 1521 个 token。要把它换算成"相当于多少文字"，得先把换算口径说清楚：

⚠️ 汉字和 token 的比例完全取决于 tokenizer，两档之间差一倍多：
中文优化过的（Qwen / DeepSeek / GLM 一类）约 1 token ≈ 1.5 个汉字；
没优化过的（早期 GPT / Llama 一类）约 1 token ≈ 0.7 个汉字。
本目录统一取保守的 0.7 这一档，和 附-速查表 的数字速查一致。换到 1.5 那一档，下面所有"文本当量"都要再乘 2.1 倍。

    1521 个 token  x 0.7  ≈  1065 个汉字   ≈  一页半 A4 纸的中文
                   x 0.75 ≈  1140 个英文单词

🔑 一张普通截图 ≈ 一篇短文的成本。 这一句话解释了这个领域一大半的技术动作。

再看四个真实型号的口径。 下表前五列全部有一手出处，最后一列（视觉 token 数）是我自己除出来的：

型号 / 视觉塔 层数 最大输入 patch patch 数 压缩法 视觉 token
Kimi K3 / MoonViT-V2 27 ✅ 3584² ✅ 14 ✅ 256² = 65536 2×2 pixel shuffle ✅ ⚠️ 16384
MiniMax M3 的 ViT 32 ✅ 2016² ✅ 14 ✅ 144² = 20736 2×2 空间 + 2 帧时间 ✅ ⚠️ 5184（单图）
DeepSeek-V4.1-Flash / DeepSeek-ViT 32 ✅ ≈1344² ✅ 14 ✅ 96² = 9216 3×3 pixel-unshuffle（÷9）✅ ⚠️ 1024
GLM-5.3-Flash 的视觉塔 24 ✅ 未披露 未披露 — 未披露 —

✅ 出处：../业界模型技术报告/Kimi-K3.md 报告 §六；../业界模型技术报告/DeepSeek-V4.1-Flash.md 报告 §十一；M3 的输入尺寸与合并方式在 ../业界模型技术报告/模型技术对比.md 报告 §二 的多模态行（⚠️ 不在 MiniMax-M3.md 里 —— 那份只写了"32 层 ViT，patch 14，3D RoPE，2×2 patch merge"）；GLM 的 24 层来自 ../业界模型技术报告/GLM-5.3.md 报告 §5.2 按 config.json 做的参数推演。
⚠️ 最后一列是我按"patch 数 ÷ 压缩倍数"算的，四家报告都没有直接列这个数字。

★★ 这张表里最值得停一下的是 DeepSeek 那一行：同样一张 1344×1344 的图，走业界通行的 2×2 四合一要花 9216÷4 = 2304 个 token，走 DeepSeek 的 9 合 1 只要 1024 个 —— 省了 56%。⚠️ 代价当然也有（压得更狠，细节更可能糊掉），但报告没给对照实验，这个代价有多大目前无法核对。

视频更夸张。 按 GLM-5.3 报告披露的评测口径（⚠️ 注意这是它评测别家模型时的抽帧规则，不是某个模型的推理默认值）：原生支持视频的直接喂原视频，不支持的按 1 fps 抽帧、超限则均匀采样 ✅：

    一段 5 分钟的视频，按 1 fps  ->  300 帧
    每帧 448x448 编码            ->  每帧 (448/14)^2 = 32^2 = 1024 个 patch
    2x2 合并                     ->  每帧 256 个 token
    ==> 300 x 256 = 76,800 token
    ==> ⚠️ 一段五分钟的视频，比一本《活着》还长

★★ 所以你会看到本领域到处都在做同一件事：想尽办法砍 token 数。 2×2 合并、9 合 1、时间维池化、动态分辨率、token 剪枝…… 04 和 05 两整章都在讲这个。

⚠️ 而且不是为了省显存那么简单 —— 注意力的开销是 token 数的平方。 token 数翻倍，注意力那部分的算力翻四倍。02 章 2.7 节会把这笔账算到具体 FLOPs。

0.6 ★ 三个反直觉的点

① 模型看到的画面，分辨率比你想的低得多

一张图被切成 14×14 的块之后，块内部的细节就被压成一个向量了。

    ==> 这就是为什么早期模型看不清图里的小字：
        224x224 的输入只有 16x16 = 256 个 patch，
        一个 14x14 的块里可能糊了两三个字符
    ==> 这也是为什么"提高分辨率"是过去两年多模态最大的性能来源之一（04 章）

② 图像 token 的"信息密度"和文字完全不对等

    一段文字里，去掉 10% 的 token -> 句子基本读不懂了
    一张图里，去掉 10% 的 patch   -> 你多半看不出差别
    ==> 图像 token 冗余度极高 ==> 才敢做 2x2 合并、9 合 1、token 剪枝这些暴力操作
    ==> ⚠️ 但"冗余"是对【普通照片】说的；对【密集文档】（表格、公式、小字）就不成立
        —— 这是 04 章那些"动态分辨率"方案的根本动机

③ 同一张图，喂给两个模型，token 数可以差 10 倍

这一条现在有一手数字可以验算了。 拿同一张 1344×1344 的图过三家的切法：

切法 patch 数 压缩 视觉 token 相对最省的那家
不压缩（2023 年做法） 9216 1× 9216 9.0 倍
2×2 四合一（业界通行） 9216 ÷4 2304 2.3 倍
3×3 九合一（DeepSeek-ViT ✅） 9216 ÷9 1024 1 倍（基准）

⟹ 两家模型的"多模态价格"根本没法直接比，得先问清楚"你这张图算几个 token"。
⟹ 同理，两家的多模态评测分数也没法直接比（11 章会展开）。本仓库的 模型技术对比 已经实证过这件事：✅ K3 与 M3 之间"零个共享的视觉 benchmark" —— K3 报告用 OmniDocBench / Video-MME / PerceptionBench，M3 模型卡用 MMMU_Pro / Video-MME-v2 / claw-eval。

0.7 那声音、视频、图像生成呢？

同一套骨架，换一个前端：

    图片  ->  ViT 视觉塔         --> 连接器 --+
    视频  ->  ViT + 时间维处理    --> 连接器 --+
    音频  ->  音频编码器          --> 连接器 --+--> [一串 4096 维向量] -> LLM
    文字  ->  tokenizer + 查表 ----------------+

输出侧则是另一个故事，也是这两年真正在变的地方：

    只输出文字      ->  "理解型"多模态模型（本教程 01~08 章）
    还要输出图/音   ->  ⚠️ 麻烦大了：LLM 只会从词表里挑编号，怎么"挑"出一张图？
                       ->  两条路：外挂一个扩散模型 / 给图像造一本词典
                       ->  09 章专门讲这个

更多见 09 生成侧 和 10 语音与实时全双工。

0.8 🔑 这一章的四句话

  1. LLM 只吃向量。多模态的全部难点，是在没有词典的情况下把图/音变成"像文字一样的向量"。
  2. 链路是四步：切块 → 视觉编码器 → 连接器 → 拼进文本序列。0.3 那张形状表里，只有"2×2 合并"那一行会改变 token 数。
  3. 一张 1092² 的图 ≈ 1521 个 token ≈ 1000 个汉字；一段五分钟视频 ≈ 7.7 万个 token。 这个账决定了后面所有的设计取舍。
  4. ⚠️ patch 数、token 数、"占上下文的比例"是三个不同的数，差着连接器的压缩倍数和文本 token 的分母。混用这三个数，是读多模态报告时最容易算错账的地方。
