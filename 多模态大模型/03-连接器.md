# 03 · 连接器：怎么把视觉向量"翻译"给语言模型

> 三大件的第二件，**也是最小的一件**（两三千万参数），
> 但它决定了两件大事：**视觉 token 占多少上下文**、**信息在这里丢多少**。

---

## 3.1 它到底要解决什么

视觉塔吐出来的是 6084 个 **1152 维**向量，LLM 要的是 **4096 维**向量。所以最起码得做一次形状转换。但真正的问题有三个：

```
    问题① 形状不对    1152 维  ==>  4096 维              <- 一个矩阵就能解决
    问题② 数量太多    6084 个 token 塞进上下文太贵       <- ★ 真正的难点
    问题③ 分布不对    视觉塔的向量【长得不像】文字 embedding
                     ==> LLM 会"读不懂"，需要学一个映射把它拉进同一片空间
```

> 🔑 **连接器 = 一个降数量 + 换形状 + 对齐分布的小模块。**
> ⚠️ 它参数很少，但它是**唯一一个必须从零训练的部件**（视觉塔和 LLM 都可以拿现成的）。

---

## 3.2 ★★ 两大流派：塞进去 vs 挂旁边

这是本章最重要的一张图。**所有连接器方案都属于这两类之一。**

### 流派 A：输入端拼接（prefix / decoder-only 式）

```
    视觉 token 直接【混进输入序列】，和文字 token 平起平坐

    序列 = [视觉 1..1521] + [这][个][报][错][怎][么][修]
                 |
                 v
           一个标准 LLM，什么都不用改

    ✅ 优点：LLM 一个字都不用改；图文可以任意交错；实现极简
    ⚠️ 缺点：★ 视觉 token 吃掉上下文预算，而且参与全部注意力计算（平方开销）
```

**代表**：LLaVA 系列、Qwen-VL 系列、InternVL，以及**本仓库里 K3 / M3 / GLM-5.3-Flash / DeepSeek-V4.1-Flash 四家 2026 年模型**（⚠️ 后四家是我从"合并后投影进主干"这个描述反推的流派归属，报告没有明说）。

### 流派 B：交叉注意力（cross-attention 式）

```
    视觉 token 【不进序列】，而是挂在旁边当"资料库"
    在 LLM 的某些层之间，插入新的一层：让文字 token 去【查阅】视觉 token

    序列里只有文字：  [这][个][报][错]...
                        ^
                        |  在第 4、12、20... 层插入 cross-attention
                        |
    视觉在"外面"：    [视觉 1..6084]

    ✅ 优点：★ 视觉 token 不占上下文；6084 个也无所谓
             开销是 n_text x n_image（线性，不是平方）
    ⚠️ 缺点：必须【改 LLM 结构、加新层】==> 新层要从零训 ==> 需要多得多的训练数据
             图文交错的位置关系表达起来别扭
```

**代表**：Flamingo（2022，arXiv 2204.14198，这条路的开创者）、Llama 3.2 Vision。

### 一张对照表

| | 流派 A 拼接 | 流派 B 交叉注意力 |
|---|---|---|
| LLM 要不要改 | **不用** | 要加层 |
| 视觉 token 占上下文吗 | **占** | 不占 |
| 计算量随图像 token 数 | **平方** | 线性 |
| 训练数据需求 | 小（60 万条就能起步） | 大 |
| 图文交错灵活度 | **高** | 低 |
| 2024 年后的主流 | **★ 是** | 少数派 |

> ⚠️ **为什么流派 A 赢了？** 我的判断是三条：
> ① **生态惯性** —— 不用改 LLM，意味着能直接蹭所有现成的推理框架（vLLM / SGLang）和训练框架；
> ② **数据效率** —— 学术界和创业公司拿不出 Flamingo 那个量级的数据；
> ③ **长上下文变便宜了** —— 2023 年 4K 上下文时"视觉 token 占位置"是致命的，2026 年动辄 1M 上下文，**这个缺点被硬件和算法进步稀释掉了**。
>
> ⟹ 🔑 **一个通用规律：当某个资源变便宜时，为省它而设计的复杂架构就会被淘汰。** 这和 [../推理框架/](../推理框架/) 里 KV cache 相关设计的演化是同一个逻辑。

## 3.3 ★★ 四种具体做法，以及它们的 scaling 完全不同

### 3.3.1 先看四种做法本身

**做法① 线性层 / MLP —— ★ 现在的主流**

```
    每个视觉向量【独立地】过一个小网络：
      1152 --[Linear]--> 4096 --[GELU]--> [Linear] --> 4096

    参数量：1152x4096 + 4096x4096 = 4,718,592 + 16,777,216 ≈ 2150 万
    token 数：★ 【不变】。进来几个，出去几个
```

**LLaVA（2023）用的是单个线性层；LLaVA-1.5 换成两层 MLP，分数明显上涨。** 就这么简单的改动 ⟹ ⚠️ 说明这一层的**表达能力确实是瓶颈之一**，但也就到两层为止，再深收益很小。

**做法② 空间合并（pixel shuffle / patch merge）—— ★ 2026 年标配**

```
    把相邻 2x2 = 4 个 patch 的向量【直接拼起来】，当成一个 token

      [a][b]          a,b,c,d 各 1152 维
      [c][d]   ==>  拼接成 4608 维 ==> 过 MLP ==> 4096 维

    参数量：4608x4096 + 4096x4096 ≈ 3570 万
    ==> token 数除以 4
    ==> ★★ 注意力开销直接除以 16
```

> ✅ **四家 2026 年模型全用了这一招，但压缩倍数不同**（本仓库一手报告）：
>
> | 模型 | 压缩法 | token 数 | 报告原话 / 出处 |
> |---|---|---|---|
> | **Kimi K3** | **2×2 pixel shuffle** | ÷4 | *"让 3584×3584 的输入在 1M 上下文里放得下"*，报告 §六 |
> | **MiniMax M3** | **2×2 空间 + 2 帧时间** | ÷4（图）/ ÷8（视频） | [模型技术对比.md](../业界模型技术报告/模型技术对比.md) 报告 §二 多模态行 |
> | **GLM-5.3-Flash** | ⚠️ 未披露 | — | 只披露了视觉塔 24 层 / 0.30 B |
> | **DeepSeek-V4.1-Flash** | ★ **3×3 pixel-unshuffle** | **÷9** | 报告 §十一，支持到约 1344×1344 |
>
> 🔑 **"2×2 合并"在 2026 年已经不算技术，算常识了。** 看到某个模型没做，反而要问为什么。
> ★ 而 **DeepSeek 的 3×3 是目前公开模型里压得最狠的一档** ✅ —— 业界常见 4 合 1，它做 9 合 1。

**做法③ Q-Former / Perceiver Resampler —— ★ 已退潮，但必须认识**

> 📖 **Q-Former**（BLIP-2，2023，arXiv 2301.12597）/ **Perceiver Resampler**（Flamingo）：准备 **固定数量**（比如 32 个）的"提问向量"（learnable query，可学习查询），让它们用交叉注意力去"采访"那 6084 个视觉 token，最后只输出这 32 个。

```
    32 个 query  --cross-attn-->  6084 个视觉 token
         |
         v
    输出【永远是 32 个】token —— 不管原图多大

    参数量：⚠️ 1 亿量级（BLIP-2 的 Q-Former 大致是 BERT-base 规模 + 交叉注意力层）
            ★ 注意它比前两种做法大 3~5 倍，是连接器里最重的一种
    ✅ 优点：token 数【完全可控且极小】，一张图只占 32 个位置
    ⚠️ 致命缺点：★ 6084 -> 32 是一个【硬信息瓶颈】
                 普通照片够用，但文档、表格、小字直接死掉
    ⚠️ 缺点二：这个模块要单独训，训练不稳定、收敛慢
```

**做法④ 交叉注意力插层（流派 B）** —— 3.2 节已经讲过，这里只补一句参数量：它要在 LLM 的若干层里各加一套交叉注意力，**参数量跟着 LLM 的宽度和层数走，是四种做法里唯一会随 LLM 一起变大的**。

### 3.3.2 ★★ 关键区别：token 数是"正比"还是"常数"

**这是本章最该算一遍的一张表。** 同一座视觉塔（patch 14），把输入分辨率一档一档往上推，看四种做法分别输出多少个 token：

| 输入边长 | patch 数 | ① MLP 直通 | ② 2×2 合并 | ② 3×3 合并 | ③ Q-Former |
|---|---|---|---|---|---|
| 224² | 256 | 256 | 64 | 28 | **32** |
| 336² | 576 | 576 | 144 | 64 | **32** |
| 672² | 2304 | 2304 | 576 | 256 | **32** |
| 1024² | 5329 | 5329 | 1332 | 592 | **32** |
| 1344² | 9216 | 9216 | 2304 | 1024 | **32** |
| 2016² | 20736 | 20736 | 5184 | 2304 | **32** |
| 3584² | 65536 | 65536 | 16384 | 7281 | **32** |
| **随分辨率怎么长** | — | **线性正比** | 正比（÷4） | 正比（÷9） | ★ **常数** |

> ⚠️ **表里的除法是理想值**：要整齐地做 2×2 或 3×3 合并，patch 网格的边长必须能被 2 或 3 整除。`224÷14 = 16` 不是 3 的倍数，`1024÷14 ≈ 73` 既不是 2 也不是 3 的倍数 —— 真实实现会先把图**垫（pad）到合适的尺寸**再切，所以实际 token 数会比表里略多几个。**量级不受影响，但别拿表里的数去对账单。**

> ★★ **这两种 scaling 根本不是一回事**：①②是"**正比**"（边长翻倍 → token 数 ×4），③是"**常数**"。从 224² 到 3584²，①的 token 数涨了 **256 倍**，③**一个都没涨**。
>
> ⚠️ **"③ 不涨"听起来是优点，实际上是它的死因。** 下一小节把这件事换成数字。

### 3.3.3 ★ 把"信息损失"算成一个数

**信息能丢多少，看"每个输出 token 要替多少个 patch 说话"，以及"进来多少个数、出去多少个数"：**

| 做法 | 每个输出 token 背后有几个 patch | 进来多少个数 | 出去多少个数 | **信息通道宽度** |
|---|---|---|---|---|
| ① MLP 直通 | 1 | 1 × 1152 = 1152 | 4096 | **356 %**（升维，无损） |
| ② 2×2 合并 + MLP | 4 | 4 × 1152 = 4608 | 4096 | **89 %** |
| ② 3×3 合并 + MLP | 9 | 9 × 1152 = 10368 | 4096 | **40 %** |
| ③ Q-Former（**224²** 输入） | 256 ÷ 32 = 8 | 8 × 1152 = 9216 | 4096 | **44 %** |
| ③ Q-Former（**3584²** 输入） | 65536 ÷ 32 = **2048** | 2048 × 1152 = 2,359,296 | 4096 | ★ **0.17 %** |

> ★★ **看③的两行**：**同一个 Q-Former，什么都没改，只是输入分辨率从 224² 换到 3584²，信息通道就从 44% 掉到 0.17% —— 窄了 256 倍。**
>
> 🔑 **这就是 Q-Former 退潮的机制层面的原因**，而不是"感觉它不好"：**它的输出容量是写死的，而输入容量随分辨率平方增长。** 分辨率一进入 2024 年的高清时代，这个模块就必然被挤爆。

> ⚠️ **顺手纠正一个本目录早先版本的错误说法**：我以前写过"2×2 合并**信息一点没丢**"。**严格说不对。** 拼接（concat）那一步确实是纯 reshape、一个数都没少，**但紧跟的那个 MLP 把 4608 维压成 4096 维，这是一次降维，一般来说是有损的**（上表第二行的 89%）。**真正"无损"的只有 concat 本身。** 对 3×3 来说这件事更明显：10368 → 4096，**通道只剩 40%** —— DeepSeek 那条路线省 token 不是白省的，⚠️ 但报告没给对照实验，**代价有多大目前无法核对。**

> ★★ **为什么业界还是选了②而不是③**：2024 年之后，**文档 / 截图 / 表格成了主要应用场景**，而这些场景恰恰是"32 个 token 装不下"的。
> ⟹ 🔑 **业界的选择是：宁可多花 token，也不要丢信息。**
> ⟹ 这个转折是理解 2023→2026 多模态演进的一条关键线索（[14 章](14-演进主线与开放问题.md)）。

## 3.4 ★ 一个容易被忽略的细节：特殊标记

视觉 token 塞进序列时，两边要加标记：

```
    ... 用户说：<|image_start|> v1 v2 ... v1521 <|image_end|> 这个报错怎么修？ ...
                ^^^^^^^^^^^^^^^                 ^^^^^^^^^^^^^
                这两个是【真正的文本 token】，在词表里有编号
```

**为什么需要**：

```
    ① 让模型知道"这一段是图，不是文字"
    ② 多图时能分清哪些 token 属于哪张图
    ③ ★ 有的模型还会插入行分隔符（每行 patch 结束插一个 <|row_end|>）
       ==> 帮助模型建立【二维空间感】—— 因为序列本身是一维的（05 章）
```

**第 ③ 条的代价要算一下**，它不是可以忽略的零头：

| 做法 | 视觉 token | 额外标记 | 合计 | 多花 |
|---|---|---|---|---|
| 只加首尾两个标记 | 1521 | 2 | 1523 | 0.1 % |
| **再给每行 patch 加一个行尾标记** | 1521 | 2 + **39 行** | 1562 | **2.7 %** |

> ⚠️ 1521 个 token 是 39×39 的网格（78÷2 = 39），所以行尾标记是 39 个，不是 78 个 —— **合并之后行数也减半了**，这一步很容易算错。

> ⚠️ **实操陷阱**：这些特殊 token 的数量会被算进你的账单，而且不同模型的模板完全不同。**自己拼 prompt 时把模板拼错，是多模态调用最常见的低级错误。**

## 3.5 训练时谁冻谁

连接器是唯一必须从零训的部件，所以训练流程一般这样安排（细节见 [06 章](06-训练流程三阶段.md)）：

| 阶段 | 视觉塔 | 连接器 | LLM | 数据量级 | 这么安排的理由 |
|---|---|---|---|---|---|
| **一 · 对齐** | 冻结 | **训** | 冻结 | 几百万图文对<br>几十卡·天 | ★ 冻住 LLM 是为了**不破坏它的语言能力**；只学"翻译"这一件事 |
| **二 · 联合训练** | 训 | 训 | 训 | 真正长本事的阶段<br>**也是最贵的阶段** | 视觉要变成模型世界观的一部分 |
| **三 · 指令微调** | 冻结 或 很小的学习率 | 训 | 训 | 几十万~几百万条指令 | 保住已经长出来的视觉能力，别被少量指令数据带偏 |

> ⚠️ **"阶段一必须冻住 LLM"是 LLaVA 时代的经验**，前提是**数据少**。
> **原生多模态路线根本没有"阶段一"这回事** —— 它从第 0 步就是全部一起训的。✅ DeepSeek-V4.1-Flash 的报告把这件事说得最明白：**"预训练一开始就有图"**，而它的视觉塔是在**另一条独立的两阶段流程**里单独训好的（对比预训练 → 接一个 4 B 的 MoE LLM 做自回归微调 → **把那个 LLM 扔掉只留编码器**），然后才进主干的预训练。
>
> ⚠️ **一处必须更正的旧说法**：本目录早先版本写过"GLM-5.3-Flash 的 30T 多模态语料"。**这个数字在 GLM-5.3 报告里只出现在一句归档者自己的概括里，原文紧跟着就标了"⚠️ 但没有可核对的数字支撑"。** 官方博客只有一句定性的 *"a richer multimodal pre-training corpus"*。⟹ **别把"本文的推断"写成"报告的结论"。**
>
> 🔑 **别把小规模微调的经验直接套到大规模预训练上。**

## 3.6 🔑 这一章的五句话

1. 连接器要干三件事：**换形状、降数量、对齐分布**。参数只有两三千万，但它是信息瓶颈的所在。
2. **两大流派：拼进序列（主流）vs 挂旁边做交叉注意力（少数派）。** 主流赢在生态和数据效率，而不是赢在原理更优。
3. ★★ **两种 scaling 必须分清**：MLP / patch merge 的输出 token 数**正比于 patch 数**，Q-Former 的输出 token 数是**写死的常数**。从 224² 到 3584²，前者涨 256 倍，后者一个不涨。
4. ⚠️ **而"一个不涨"正是 Q-Former 的死因**：它的信息通道宽度从 44% 掉到 **0.17%**（3.3.3 节那张表）。**业界的取向是"宁可贵也不丢信息"。**
5. ✅ **2026 年的标配组合是"空间合并 + 两层 MLP"**：K3 / M3 做 2×2（÷4），**DeepSeek-V4.1-Flash 做 3×3（÷9）**。⚠️ 但"合并无损"只对 concat 那一步成立，紧跟的降维是有损的 —— 3×3 的通道只剩 40%。
