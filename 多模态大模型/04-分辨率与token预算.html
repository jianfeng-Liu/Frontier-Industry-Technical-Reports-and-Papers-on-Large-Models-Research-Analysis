04 · ⭐ 分辨率与 token 预算：这个领域一半的工程量

如果你只读本教程的一章，读这一章。
2023→2026 年多模态能力的提升，来自"看得更清"的部分，很可能大于来自"想得更明白"的部分。
读法：4.3 节是一张从分辨率一路算到"128K 窗口塞得下几张图"的扫描表，本章其余每一节都在解释那张表里的某一行为什么长这样。

4.1 病根：一个 2021 年留下的历史包袱

CLIP 是在 224×224 上训练的。ViT 的位置编码是为固定块数写死的：

    224 / 14 = 16  ==>  16x16 = 256 个 patch  ==>  位置编码表就只有 256 行
    ==> 你喂一张 1000x1000 的图进去？位置编码表不够用，直接报错
    ==> 所以只能【先把图缩小到 224x224】

这意味着什么，看一眼就懂：

    你的 1920x1080 截图  --缩到 336x336-->  一张糊得看不清任何字的小图

    ==> 🔑 2023 年多模态模型"看不懂截图、读不了 PDF"，
        ★ 根本原因不是模型笨，是【它压根没看见】。

4.2 ★★ 三代解法

第一代：插值 + 高分辨率微调（2023）

把 256 行的位置编码表插值成 576 行（对应 336×336），然后在高分辨率数据上微调。

    ✅ 简单，直接有效
    ⚠️ 但 336x336 依然不够看 PDF

而且代价涨得比直觉快，这一条必须说清楚：

    边长 x2  ==>  patch 数 x4  ==>  视觉 token 数 x4
                              ==>  线性部分（矩阵乘）开销 x4
                              ==>  ★ 注意力部分开销 x16   <- token 数的平方

    ⚠️ 所以"支持 2 倍分辨率"在 token 预算上是【4 倍代价】，
       在注意力算力上是【16 倍代价】。02 章 2.7 节把这笔账算到了具体 FLOPs。
输入边长 视觉 token（2×2 合并后） 线性部分相对开销 注意力部分相对开销
336² 144 1× 1×
672² 576 4× 16×
1344² 2304 16× 256×
2688² 9216 64× 4096×

⚠️ 这张表只是"边长每翻一倍"的四级阶梯，用来建立量级感。边长从 336 涨到 2688 是 8 倍，注意力开销涨了 4096 倍。

第二代：★ AnyRes / 动态切图（2024，主流）

📖 AnyRes / dynamic tiling / 动态切图：把大图切成若干块标准尺寸的小图，每块分别过视觉塔，再把结果拼起来；另外额外过一张缩略图保留全局视野。

    原图 1920x1080
      |
      +--> 切成 4x2 = 8 块，每块 448x448    <- 局部细节：小字能看清了
      |      每块过塔 -> (448/14)^2 = 1024 patch -> 2x2 合并 -> 256 token
      |      8 块 x 256 = 2048 token
      |
      +--> 整图缩略成一张 448x448           <- ★ 全局视野：不然看不出整体布局
             -> 1024 patch -> 256 token

    ==> 合计 2304 token

★★ 那张缩略图（thumbnail）是这个方案的灵魂。没有它，模型只能看到八块碎片，"这个按钮在页面的哪个位置"这类问题会全错。

    ✅ 优点：复用 224/448 训好的视觉塔，不用改位置编码 ==> 工程代价极小
    ⚠️ 缺点①：★ 切块的边界会把一个字、一个表格单元格【切成两半】
    ⚠️ 缺点②：块与块之间【看不见彼此】（各自独立过塔），跨块的表格关系要靠 LLM 去缝
    ⚠️ 缺点③：长宽比被强行凑成网格，会有形变或留白

代表：LLaVA-NeXT（LLaVA-1.6）、InternVL 的 dynamic tiling。

第三代：★ 原生分辨率 / 变长（2024 末～，前沿路线）

📖 原生分辨率（native resolution）：不切、不缩，图多大就切多少块，视觉塔直接处理变长的 patch 序列。位置编码换成能外推的形式（05 章的 2D RoPE）。

    1920x1080 直接切：(1920/14) x (1080/14) = 137 x 77 = 10549 patch
                      -> 2x2 合并 -> 2637 token

    ✅ 优点：★ 无切块伪影、无形变、全图 patch 互相可见（一趟注意力全看到）
    ⚠️ 代价：视觉塔必须支持【变长 batch】—— 每张图 token 数都不同
             ==> 训练时要做 patch packing（把多张图打包成一条长序列 + 掩码隔开）
             ==> ★ 这正是纯文本训练里"样本打包"的同一套技术
                见 ../数据格式和数据处理/13-打包与文档掩码.md

思想源头：NaViT / Patch n' Pack（Google，2023，arXiv 2307.06304）；工程落地：Qwen2-VL 的"naive dynamic resolution"（arXiv 2409.12191）等。

✅ 2026 年的一手证据（三家都走到第三代，但支持上限差 7 倍）：

模型 最大输入 patch 数 压缩 视觉 token 出处
Kimi K3 / MoonViT-V2 3584² 65536 2×2 ⚠️ 16384 Kimi-K3.md 报告 §六
MiniMax M3 的 ViT 2016² 20736 2×2 ⚠️ 5184 模型技术对比.md 报告 §二 多模态行 ⚠️ 不在 MiniMax-M3.md 里
DeepSeek-V4.1-Flash ≈1344² 9216 ★ 3×3 ⚠️ 1024 DeepSeek-V4.1-Flash.md 报告 §十一

3584² 这个量级已经不是"能看清字"，而是"能看清一整页 PDF 的字"。
★ 而 DeepSeek 那一行是另一种取舍：分辨率上限只有 K3 的 3/8，但用 9 合 1 把 token 压到 1024 —— 它要的是"便宜"，不是"看得最清"。✅ 它的视觉塔还明说第一阶段对比预训练只在 224×224 上做，理由是"更高分辨率在这阶段收益不大，白费算力"，高分辨率留给第二阶段（544² ~ 1344²）。

4.3 ★★ 核心：把 token 账一档一档算出来

4.3.1 从分辨率一路算到"相当于多少汉字"

全部用一套固定口径：patch 14 × 14，视觉塔宽 1152，之后做 2×2 或 3×3 空间合并。每一列都能自己验算：

输入边长 patch 网格 patch 数 2×2 合并 → token 3×3 合并 → token 文本当量（汉字） 占 128K 窗口 占 1M 窗口
336² 24 × 24 576 144 64 ≈100 0.11 % 0.014 %
448² 32 × 32 1024 256 113 ≈180 0.20 % 0.024 %
672² 48 × 48 2304 576 256 ≈400 0.44 % 0.055 %
1024² 73 × 73 5329 1332 592 ≈930 1.0 % 0.13 %
1092² 78 × 78 6084 1521 676 ≈1070 1.2 % 0.15 %
1344² 96 × 96 9216 2304 1024 ≈1610 1.8 % 0.22 %
2016² 144 × 144 20736 5184 2304 ≈3630 4.0 % 0.49 %
3584² 256 × 256 65536 16384 7281 ≈11470 12.5 % 1.6 %

每一列是怎么来的：

    patch 网格  = floor(边长 / 14)                   例：1024 / 14 = 73.1 -> 73
    patch 数    = 网格边长的平方                     例：73^2 = 5329
    2x2 后token = patch 数 / 4                       例：5329 / 4 = 1332
    3x3 后token = patch 数 / 9                       例：5329 / 9 = 592
    汉字当量    = token 数 x 0.7                     例：1332 x 0.7 = 932
    占窗口      = token 数 / 131072（128K）或 1048576（1M）

⚠️ 三处口径必须记住，不然这张表会被误用：
① floor 不是四舍五入：1024 ÷ 14 = 73.14，取 73，所以最右边那 2 个像素列被丢掉了。真实实现一般会先 pad 或 resize 到 14 的整数倍。
② 2×2 / 3×3 的除法同样需要整除：73 既不是 2 也不是 3 的倍数，真实实现会再垫一圈，所以实际 token 数会比表里略多几个（03 章 3.3.2 节同样的提醒）。
③ 汉字当量那一列的 0.7 是一档保守值。换成中文优化过的 tokenizer（约 1 token ≈ 1.5 汉字），整列要再乘 2.1 倍。口径说明见 00 章 0.5 节。

★★ 这张表最该带走的两行是 1024² 和 3584²：
一张 1024×1024 的普通截图 = 5329 个 patch = 1332 个视觉 token ≈ 930 个汉字 ≈ 一页半 A4 纸。
一张 3584×3584 的高清 PDF 页 = 16384 个视觉 token ≈ 11470 个汉字 ≈ 16 页 A4 纸。

🔑 "一张图 ≈ 一篇短文"这句话，在最高档上变成"一张图 ≈ 一个章节"。

4.3.2 ★ 接到上下文窗口：塞得下几张图

把上表的 token 数去除窗口大小，得到本章最有工程意义的一张表：

输入边长 每张图 token（2×2） 128K 窗口塞几张 1M 窗口塞几张 不压缩（1×1）1M 能塞几张
336² 144 910 7281 1820
448² 256 512 4096 1024
672² 576 227 1820 455
1024² 1332 98 787 196
1344² 2304 56 455 113
2016² 5184 25 202 50
3584² 16384 ★ 8 ★ 64 ★ 16

⚠️ 这是理论上限，实际要打折：窗口里还得装系统提示、用户问题、模型输出，以及每张图的边界标记。留 10%~20% 给文字是常识，所以上表的数字实际要乘 0.8 左右。

★★ 看最后一行，三个数字连起来读：
3584×3584 的输入，1M 上下文不压缩只能放 16 张图；做了 2×2 合并就能放 64 张。 ⟹ 这正好解释了 K3 报告那句话的分量：✅ "投影前用 2×2 pixel shuffle 把视觉 token 数降 4 倍，让 3584×3584 的输入在 1M 上下文里放得下"。
⟹ 🔑 "放得下"不是修辞。16 张 vs 64 张，是"勉强能用"和"真的能用"的差别。

★ 反过来读这张表，就得到多模态产品的一条硬约束：128K 窗口（2024 年的主流规格）配 1024² 输入，最多 98 张图 —— 而一份 100 页的 PDF 正好就是 100 张图。⟹ "把一份 PDF 整本喂进去"这件事，在 128K 时代刚好差一点，在 1M 时代才真正成立。

4.3.3 同一张 1080p 截图，五种方案的账

这是 4.2 三代解法的对账单。 1920×1080 的截图：

方案 年代 实际看到的分辨率 做空间合并吗 视觉 token 能读小字吗
固定 336 2023 336×336（严重形变+模糊） ❌ 当时还没这招 576 ❌ 完全不行
AnyRes 2 块 + 缩略 2024 初 672×336 + 全局 ❌ 1728 ⚠️ 大字可以
动态切图 8 块 + 缩略 2024 ≈1792×896 + 全局 ✅ 2×2 2304 ✅ 可以
原生分辨率 2025~ 1920×1080（真分辨率） ✅ 2×2 ≈2637 ✅ 且无切块伪影
原生分辨率 + 9 合 1 2026（DeepSeek 式） 1920×1080 ✅ 3×3 ≈1172 ⚠️ 未有公开对照实验

⚠️ 表中数字是我按"patch 14 + 对应合并倍数"算的，具体模型会有出入。原生分辨率 那两行的算法是 137 × 77 = 10549 patch，再 ÷4 = 2637 或 ÷9 = 1172。

四条结论：

 ① 从 576 -> 2637，token 涨了 4.58 倍 ==> ★ 钱和延迟也涨了这么多
 ② 但"能不能读小字"是【0 或 1】的差别 —— 这钱必须花
 ③ ★★ 最后一行最值得看：同样是看【真 1080p】，9 合 1 把 token 压到 1172，
    比 2024 年那个只看 672x336 的 AnyRes 方案（1728）还便宜 32%。
    ==> ⚠️ 代价是信息通道从 89% 掉到 40%（03 章 3.3.3 节），
       但 DeepSeek 报告没给对照实验，这个代价有多大【目前无法核对】。
 ④ ==> 🔑 所以真正的战场不是"要不要高分辨率"，而是
    ★★【怎么在同样的 token 预算下，把预算花在真正有信息的地方】

4.4 于是有了 token 预算控制

生产环境里，模型一般会暴露两个参数（Qwen-VL 系列的 min_pixels / max_pixels 是典型）：

    max_pixels = 1,003,520   （约 1024x980）
      ==> 图片超过这个像素数就等比缩小，保证 token 数有上限
      ==> ★ 这是你控制多模态成本最直接的旋钮

    min_pixels = 3,136       （= 56x56）
      ==> 太小的图也垫到这个尺寸，否则 token 太少模型看不出东西

★ 把这两个像素数换算成 token 数，就看出它们为什么是这两个值了（patch 14×14 = 196 像素，之后 2×2 合并）：

设置 像素数 ÷196 → patch 数 ÷4 → 视觉 token
min_pixels 默认 3,136 16 4
max_pixels 默认 1,003,520 5,120 1,280
把 max_pixels 调到 1/4 250,880 1,280 320
把 max_pixels 调到 4 倍 4,014,080 20,480 5,120

★★ 这两个数字不是随手填的：1,003,520 = 1280 × 4 × 196，3,136 = 4 × 4 × 196。⟹ 这个旋钮的真实含义是"每张图最多 1280 个视觉 token、最少 4 个"，像素数只是它换算过去的样子。⟹ 🔑 调这个参数时，心里默算的应该是 token 数，不是像素数。

🔑 实操建议（⚠️ 我的经验判断，不是论文结论）：
- 看图说话、判断氛围 → 低分辨率足够，别浪费钱
- 读表格、发票、PDF、代码截图 → 一定要拉满，这是省不得的钱
- 一张大图不如裁成关键区域的小图 —— 你自己知道该看哪，模型不知道
- ⚠️ 按量计费时先拿一张典型图量一下 token 数：4.3.1 那张表能给你量级，但各家的 patch 大小和合并倍数不同，账单会差 2~9 倍（03 章 3.3.2 节那张表）。

4.5 推理侧的另一条路：把已经生成的视觉 token 扔掉

前面都是"进模型前"少生成一点。还有一条路是"进了模型后再扔"：

    观察（有多篇工作报告过类似现象）：
      在 LLM 的【前几层】之后，绝大多数视觉 token 得到的注意力已经极低
      ==> ⚠️ 意味着信息已经被"吸收"进少数几个 token 和文本 token 里了
      ==> 那就在第 K 层之后，把注意力最低的一大半视觉 token 直接【删掉】

    ✅ 收益：后续所有层的开销直接砍半，几乎不掉分
    ⚠️ 风险：删错了就是永久性失明，而且【你无法从输出看出它删错了】

和前面那些手段的根本区别：

手段 在哪一步省 省掉的是什么 可逆吗
降分辨率 进视觉塔之前 视觉塔 + LLM 的开销都省 不可逆（信息根本没进来）
2×2 / 3×3 合并 视觉塔之后、LLM 之前 只省 LLM 的开销 不可逆（但 concat 那步无损）
token 剪枝 LLM 的第 K 层之后 只省第 K 层以后的开销 不可逆，且是推理期的动态决策

⚠️ 第三行那个"K 层之后"是它所有麻烦的来源：前 K 层的钱已经花了，而且哪些 token 该删是按当前这个问题的注意力分布临时决定的 —— 同一张图，换个问题，删掉的就是另一批。

⚠️ 这条路线（FastV 等一类工作）在学术上很热，在生产上要谨慎：它对"通用看图问答"友好，对"找图里那一行小字"是灾难 —— 因为那一行小字对应的 token，在早期层的注意力可能恰好就很低。

4.6 ⚠️ 一个反直觉的现象：分辨率不是越高越好

    实践中常见的一条曲线：
      分辨率 ↑  ==>  分数 ↑↑  ==>  分数 ↑  ==>  ★ 分数【持平甚至下降】

    ⚠️ 可能的原因（我的解读，不同工作给的归因不完全一致）：
      ① token 太多，稀释了注意力：真正有用的那几个 token 被淹没
      ② 训练数据里根本没有那么高分辨率的样本 ==> 推理时超出了训练分布
      ③ 高分辨率下的位置编码要外推，外推得不好就乱（05 章）

✅ 第②条有一手证据支持：DeepSeek-ViT 的两阶段训练里，对比预训练阶段把分辨率限死在 224×224，报告明说"更高分辨率在这阶段收益不大，白费算力"；高分辨率（544² ~ 1344²）只在第二阶段的自回归微调里出现。⟹ 这说明"在什么分辨率上训过"是厂商自己也在精确控制的变量，不是开到最大就好。

🔑 所以"支持 4K 输入"这种宣传要打个问号：问它是不是真的在 4K 数据上训过。 支持 ≠ 训过 ≠ 有效。

4.7 🔑 这一章的六句话

  1. 2023 年多模态"看不懂文档"的根因是 CLIP 224×224 的历史包袱，不是模型笨。
  2. 三代解法：插值高清 → 切块 AnyRes（+缩略图）→ 原生变长分辨率。2026 年的旗舰走的是第三代，上限从 1344² 到 3584² ✅。
  3. ★★ 4.3.1 那张扫描表是本章的全部：一张 1024² 的图 = 5329 个 patch = 1332 个视觉 token ≈ 930 个汉字；一张 3584² 的图 = 16384 个 token ≈ 16 页 A4。
  4. ★★ 接到上下文窗口就得到硬约束：3584² 的图，1M 窗口不压缩只放 16 张，2×2 合并后放 64 张 —— 这就是 K3 那句"让 3584² 在 1M 上下文里放得下" ✅ 的实际含义。128K 窗口配 1024² 输入，上限是 98 张。
  5. ⚠️ 边长翻倍 = patch 数 4 倍 = token 数 4 倍 = 注意力开销 16 倍。 "支持 2 倍分辨率"在预算上从来不是 2 倍代价。
  6. ⚠️ 分辨率不是越高越好，也不要相信"支持 XX 分辨率"的宣传 —— 要问它在什么分辨率上训过。✅ DeepSeek 自己的两阶段训练就是这条规律的反面教材式证据：它的对比预训练阶段故意只用 224²。
