# 04 · ⭐ 分辨率与 token 预算：这个领域一半的工程量

> **如果你只读本教程的一章，读这一章。**
> 2023→2026 年多模态能力的提升，**来自"看得更清"的部分，很可能大于来自"想得更明白"的部分。**

---

## 4.1 病根：一个 2021 年留下的历史包袱

CLIP 是在 **224×224** 上训练的。ViT 的位置编码是**为固定块数写死的**：

```
    224 ÷ 14 = 16  ⟹  16×16 = 256 个 patch  ⟹  位置编码表就只有 256 行
    ⟹ 你喂一张 1000×1000 的图进去？位置编码表不够用，直接报错
    ⟹ 所以只能【先把图缩小到 224×224】
```

**这意味着什么，看一眼就懂**：

```
    你的 1920×1080 截图  ──缩到 336×336──→  一张糊得看不清任何字的小图

    ⟹ 🔑 2023 年多模态模型"看不懂截图、读不了 PDF"，
       ★ 根本原因不是模型笨，是【它压根没看见】。
```

---

## 4.2 ★★ 三代解法

### 第一代：插值 + 高分辨率微调（2023）

把 256 行的位置编码表**插值**成 576 行（对应 336×336），然后在高分辨率数据上微调。

```
    ✅ 简单，直接有效
    ⚠️ 但 336×336 依然不够看 PDF；而且分辨率每提一档，
       token 数按【平方】涨、注意力按【四次方】涨（02.7 节那笔账）
```

### 第二代：★ AnyRes / 动态切图（2024，主流）

> 📖 **AnyRes / dynamic tiling / 动态切图**：把大图切成若干块**标准尺寸的小图**，
> 每块**分别**过视觉塔，再把结果拼起来；另外**额外过一张缩略图**保留全局视野。

```
    原图 1920×1080
      │
      ├─→ 切成 4×2 = 8 块，每块 448×448    ← 局部细节：小字能看清了
      │      每块过塔 → (448/14)² = 1024 patch → 2×2 合并 → 256 token
      │      8 块 × 256 = 2048 token
      │
      └─→ 整图缩略成一张 448×448           ← ★ 全局视野：不然模型看不出整体布局
             → 256 token

    ⟹ 合计 2304 token
```

> ★★ **那张缩略图（thumbnail）是这个方案的灵魂**。没有它，模型只能看到八块碎片，
> **"这个按钮在页面的哪个位置"这类问题会全错。**

```
    ✅ 优点：复用 224/448 训好的视觉塔，不用改位置编码 ⟹ 工程代价极小
    ⚠️ 缺点①：★ 切块的边界会把一个字、一个表格单元格【切成两半】
    ⚠️ 缺点②：块与块之间【看不见彼此】（各自独立过塔），跨块的表格关系要靠 LLM 去缝
    ⚠️ 缺点③：长宽比被强行凑成网格，会有形变或留白
```

**代表**：LLaVA-NeXT（LLaVA-1.6）、InternVL 的 dynamic tiling。

### 第三代：★ 原生分辨率 / 变长（2024 末～，前沿路线）

> 📖 **原生分辨率（native resolution）**：不切、不缩，**图多大就切多少块**，
> 视觉塔直接处理**变长**的 patch 序列。位置编码换成能外推的形式（05 章的 2D RoPE）。

```
    1920×1080 直接切：(1920/14) × (1080/14) ≈ 137 × 77 = 10549 patch
                      → 2×2 合并 → ≈ 2637 token

    ✅ 优点：★ 无切块伪影、无形变、全图 patch 互相可见（一趟注意力全看到）
    ⚠️ 代价：视觉塔必须支持【变长 batch】——每张图 token 数都不同
             ⟹ 训练时要做 patch packing（把多张图打包成一条长序列 + 掩码隔开）
             ⟹ ★ 这正是纯文本训练里"样本打包"的同一套技术
                见 ../数据格式和数据处理/13-打包与文档掩码.md
```

**思想源头**：NaViT / *Patch n' Pack*（Google，2023，arXiv 2307.06304）；
**工程落地**：Qwen2-VL 的"naive dynamic resolution"（arXiv 2409.12191）等。

> ✅ **2026 年的一手证据**：Kimi K3 的 MoonViT-V2 支持到 **3584×3584** 输入
> （65536 个 patch → pixel shuffle 后 16384 token），MiniMax M3 的 ViT 输入尺寸为 **2016²**。
> **这个量级已经不是"能看清字"，而是"能看清一整页 PDF 的字"。**
> ⟹ 出处：[../业界模型技术报告/Kimi-K3.md](../业界模型技术报告/Kimi-K3.md)、[../业界模型技术报告/MiniMax-M3.md](../业界模型技术报告/MiniMax-M3.md)

## 4.3 ★ 同一张截图，四种方案的 token 账

**这张表是本章的核心。** 1920×1080 的截图：

| 方案 | 实际看到的分辨率 | 视觉 token 数 | 能读小字吗 |
|---|---|---|---|
| 固定 336（2023） | 336×336（严重形变+模糊） | **576** | ❌ 完全不行 |
| AnyRes 2 块 + 缩略 | 672×336 + 全局 | **1728** | ⚠️ 大字可以 |
| 动态切图 8 块 + 缩略 | ≈1792×896 + 全局 | **2304** | ✅ 可以 |
| 原生分辨率 | 1920×1080 | **≈2637** | ✅ 可以，且无切块伪影 |

> ⚠️ 表中数字是我按"patch 14 + 2×2 合并"这一组常见口径算的，**具体模型会有出入**。

**三条结论**：

```
 ① 从 576 → 2637，token 涨了 4.6 倍 ⟹ ★ 钱和延迟也涨了这么多
 ② 但"能不能读小字"是【0 或 1】的差别 —— 这钱必须花
 ③ ⟹ 🔑 所以真正的战场不是"要不要高分辨率"，而是
    ★★【怎么在同样的 token 预算下，把预算花在真正有信息的地方】
```

## 4.4 于是有了 token 预算控制

生产环境里，模型一般会暴露两个参数（Qwen-VL 系列的 `min_pixels` / `max_pixels` 是典型）：

```
    max_pixels = 1,003,520   （≈ 1024×980）
      ⟹ 图片超过这个像素数就等比缩小，保证 token 数有上限
      ⟹ ★ 这是你控制多模态成本最直接的旋钮

    min_pixels = 3,136       （= 56×56）
      ⟹ 太小的图也垫到这个尺寸，否则 token 太少模型看不出东西
```

> 🔑 **实操建议（⚠️ 我的经验判断，不是论文结论）**：
> - **看图说话、判断氛围** → 低分辨率足够，别浪费钱
> - **读表格、发票、PDF、代码截图** → 一定要拉满，**这是省不得的钱**
> - **一张大图不如裁成关键区域的小图**——你自己知道该看哪，模型不知道

## 4.5 推理侧的另一条路：把已经生成的视觉 token 扔掉

前面都是"进模型前"少生成一点。还有一条路是**"进了模型后再扔"**：

```
    观察（有多篇工作报告过类似现象）：
      在 LLM 的【前几层】之后，绝大多数视觉 token 得到的注意力已经极低
      ⟹ ⚠️ 意味着信息已经被"吸收"进少数几个 token 和文本 token 里了
      ⟹ 那就在第 K 层之后，把注意力最低的一大半视觉 token 直接【删掉】

    ✅ 收益：后续所有层的开销直接砍半，几乎不掉分
    ⚠️ 风险：删错了就是永久性失明，而且【你无法从输出看出它删错了】
```

> ⚠️ **这条路线（FastV 等一类工作）在学术上很热，在生产上要谨慎**：
> 它对"通用看图问答"友好，对"找图里那一行小字"是灾难——
> **因为那一行小字对应的 token，在早期层的注意力可能恰好就很低。**

---

## 4.6 ⚠️ 一个反直觉的现象：分辨率不是越高越好

```
    实践中常见的一条曲线：
      分辨率 ↑  ⟹  分数 ↑↑  ⟹  分数 ↑  ⟹  ★ 分数【持平甚至下降】

    ⚠️ 可能的原因（我的解读，不同工作给的归因不完全一致）：
      ① token 太多，稀释了注意力：真正有用的那几个 token 被淹没
      ② 训练数据里根本没有那么高分辨率的样本 ⟹ 推理时超出了训练分布
      ③ 高分辨率下的位置编码要外推，外推得不好就乱（05 章）
```

> 🔑 **所以"支持 4K 输入"这种宣传要打个问号**：**问它是不是真的在 4K 数据上训过。**
> 支持 ≠ 训过 ≠ 有效。

---

## 4.7 🔑 这一章的五句话

1. 2023 年多模态"看不懂文档"的根因是 **CLIP 224×224 的历史包袱**，不是模型笨。
2. 三代解法：**插值高清 → 切块 AnyRes（+缩略图）→ 原生变长分辨率**。2026 年的旗舰走的是第三代。
3. **一张 1080p 截图，从 576 token 涨到 2600+ token**——**贵了 4.6 倍，但"能不能读字"是 0/1 的差别。**
4. ✅ **"2×2 合并"是所有方案的公共底座**（K3、M3 都用），因为它无损、便宜、直接把注意力开销除以 16。
5. ⚠️ **分辨率不是越高越好**，也**不要相信"支持 XX 分辨率"的宣传**——要问它在什么分辨率上**训过**。
