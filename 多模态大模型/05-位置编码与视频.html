05 · 位置编码与视频：一维的序列，怎么装下二维的图、三维的视频

上一章解决了"看得够不够清"，这一章解决"知不知道东西在哪、什么时候发生"。
📖 前置：如果你不知道 RoPE 是什么，先看 ../业界模型技术报告/大模型架构入门/11-位置编码RoPE.md。
这里只需要记住一句：RoPE 让模型感知到两个 token"隔了多远"。

5.1 问题：拉平一张图，就把上下关系拉断了

视觉 patch 进入序列时，必须拉成一条线（按行扫描，raster order）：

    二维网格（78 列）              一维序列
    ┌────┬────┬────┐
    │ 0  │ 1  │ 2  │ ...        [0][1][2] ... [77][78][79] ...
    ├────┼────┼────┤                          ↑    ↑
    │ 78 │ 79 │ 80 │ ...                   行末  下一行行首
    └────┴────┴────┘

    ★★ 看这两个 patch：
       #1（第 0 行第 1 列）和 #79（第 1 行第 1 列）在图上是【上下相邻】的
       但在序列里，它们的距离是 【78】

    ⟹ ⚠️ 用普通的一维 RoPE，模型会认为它们"隔得很远"
    ⟹ 这就是 02 章说的"分不清空间关系"的机制层面的原因之一

5.2 ★ 解法：把位置拆成几个维度

RoPE 的做法是把注意力头的维度分成若干组，每组转不同的角度。
多模态的技巧是：不同组编码不同的坐标轴。

    纯文本 1D RoPE：
        所有维度 ← 位置 t（第几个 token）

    ★ 图像 2D RoPE：
        一半维度 ← 行号 h
        一半维度 ← 列号 w
        ⟹ 上下相邻的 patch：h 差 1、w 差 0  ⟹ 模型直接感知到"它们上下相邻"

    ★★ 视频 3D RoPE：
        维度分三组 ← 时间 t / 行 h / 列 w
        ⟹ 模型同时知道"这块在画面哪、在第几帧"

✅ 一手证据：MiniMax M3 的 32 层 ViT 用的就是 3D RoPE
（出处：../业界模型技术报告/MiniMax-M3.md 架构表 ✅）。
学术上这一族方案常叫 M-RoPE / multimodal RoPE（Qwen2-VL，arXiv 2409.12191）。

5.3 ⚠️ 一个很少被讲清楚的细节：图文混排时位置号怎么发

假设序列是：「看这张图」+ [图 6×4=24 个 patch] + 「里面有什么」

    ⚠️ 天真做法：图像 token 也按 1,2,3... 顺序发号
       ⟹ 一张图占掉 24 个位置号，一段 3 分钟视频占掉几万个
       ⟹ ★ 后面的文字被推到"很远的位置"，长上下文能力被图像吃掉

    ★ M-RoPE 类做法：
       文本 token：t=h=w，三个坐标一起 +1（退化成普通 RoPE）
       图像 token：t 固定，只有 h、w 在动
       图之后的文本：从【图的最大坐标 + 1】接着数

    ⟹ 🔑 一张图无论多少 patch，在【时间轴】上只占很少的位置号
    ⟹ ⟹ 这让"1M 上下文里塞几十张图"这件事在位置编码上仍然成立

⚠️ 这是我对这类设计动机的解读，不同实现的坐标分配规则有差异，
用的时候请以具体模型的实现为准。

5.4 视频：三个新问题一起来

视频 = 一堆图 + 时间。听起来简单，实际上它把 04 章那笔 token 账彻底引爆：

    5 分钟视频，1 fps 抽帧 = 300 帧
    每帧 448×448 → 1024 patch → 2×2 空间合并 → 256 token
    ⟹ 300 × 256 = 76,800 token

    ⚠️ 而这只是【5 分钟】、【每秒 1 帧】、【中等分辨率】
       换成 30 分钟、2 fps ⟹ 92 万 token ⟹ 塞不进任何模型

于是有三个必须做的决定：

决定① 抽多少帧（时间采样）

    ✅ GLM-5.3 报告披露的评测口径：
       原生支持视频的模型【直接喂原视频】；不支持的按 【1 fps 抽帧】，
       超过上限则【均匀采样】。
       出处：../业界模型技术报告/GLM-5.3.md §六

    ⚠️ 均匀采样的代价：一个 0.5 秒的关键动作（比如"他把杯子打翻了"）
       可能【正好落在两帧之间】⟹ 模型永远看不到
    ⟹ 所以有一类工作在做【自适应采样】：先粗看，再对可疑段落密集抽帧

决定② 时间维怎么压

    ✅ MiniMax M3：2×2 空间 + 【2 帧时间】patch merge  ⟹ token 再除以 2
    ✅ Kimi K3  ：注意力【分解】成"帧内空间"+"帧间时间"两趟，
                  时间维再做【池化压缩】；★ 图像和视频【完全共享参数】
       出处：../业界模型技术报告/Kimi-K3.md §六、MiniMax-M3.md

    ⟹ ★ "分解注意力"这一招很关键：
       300 帧 × 256 token = 76800，若做全序列注意力 ⟹ 76800² ≈ 59 亿对
       分解后：帧内 300×256² + 帧间 256×300² ≈ 0.2 亿 + 0.23 亿 ≈ 0.43 亿对
       ⟹ ★★ 差了 137 倍

⚠️ 上面这个倍数是我按公式算的，不是报告里的数字。
但它解释了为什么"帧内 + 帧间分解"是所有视频模型的标配——不分解根本算不起。

决定③ 模型怎么知道"这是第几秒"

    ⚠️ 只喂 300 张图，模型知道顺序，但【不知道时间刻度】
       —— 它分不出"这 300 帧是 5 分钟还是 5 小时"
    ★ 常见做法：在帧之间插入时间戳文本 token，比如 <00:03:12>
    ⟹ "视频里第几分钟发生了 X" 这类问题才答得出来

5.5 长视频的三条路（都还没走通）

 路线① 硬塞      靠超长上下文（1M）+ 激进压缩
                 ✅ K3/M3 都是 1M 上下文，这条路现在是主流
                 ⚠️ 但 1M 上下文里塞满视频，attention 成本极高，且长程召回未必好
                 ⟹ 见 ../业界模型技术报告/模型技术对比.md 里的长上下文召回讨论

 路线② 分段+记忆  把视频切段，每段生成文字摘要，再用摘要做推理
                 ✅ 便宜、可扩展到几小时
                 ⚠️ 摘要一旦漏了细节就永远找不回来；本质是有损压缩

 路线③ 检索      先用轻量模型定位"可能相关的几十秒"，只把那几十秒喂进去
                 ✅ ★ 这是我认为最像最终形态的一条（和文本 RAG 同构）
                 ⚠️ 需要一个好的"视频检索"模块，而这个模块本身就不好做

🔑 一句话：长视频理解目前没有干净的解法，三条路都在用，且经常混用。
⚠️ 这是我的判断，不是某篇论文的结论。

5.6 🔑 这一章的四句话

  1. 拉平一张图会拉断上下关系，所以要把位置编码拆成 2D（图）/ 3D（视频） 的坐标。✅ M3 用的就是 3D RoPE。
  2. 图文混排时，图像在时间轴上只占很少的位置号——否则一张图就能把长上下文吃光。
  3. 视频的核心矛盾是 token 账：5 分钟 ≈ 7.7 万 token。所以必抽帧、必做时间维压缩、必做帧内/帧间分解注意力（✅ K3 的做法）。
  4. ⚠️ 长视频没有标准答案：硬塞 / 摘要 / 检索三条路并存。看到"支持 2 小时视频"的宣传，先问它是怎么抽帧的。
