# 09 · 生成侧：让模型不只是看懂，还要画出来

> ⚠️ **换战场提醒**：前八章讲的是"理解"，主干是 Transformer 自回归。
> 这一章讲"生成"，它的主流技术**原本和 LLM 完全无关**，是另一套数学（扩散）。
> **这两拨人是最近两年才开始合流的，而且合得并不彻底。**

---

## 9.1 卡住一切的那个问题

回到 [06 章 6.3 节](06-训练流程三阶段.md) 那条结论：

```
LLM 的输出头 = 一个 [hidden_dim × 词表大小] 的矩阵
⟹ 它只会做一件事：★ 从 15 万个词里【挑一个编号】

⚠️ 而一张图是 1024×1024×3 ≈ 300 万个连续的数
⟹ 你怎么"挑"出这 300 万个数？
```

**三条路，对应三个学派**：

```
路线① 不自己画，叫人画     → LLM 写提示词，交给外挂的扩散模型     （9.3）
路线② 给图像造一本词典     → 把图变成离散编号，就能"挑"了         （9.4）
路线③ 一个身体两套输出头   → 文本用自回归，图像用扩散，共享主干     （9.5）
```

---

## 9.2 📖 先花三分钟搞懂扩散模型

不懂扩散模型，后面三节都读不下去。**它只有一个想法**：

```
正向（训练时人为做的）：
   清晰的图 → 加一点噪 → 再加一点 → ... → 纯噪声
   ★ 这一步不需要学，是拿随机数硬加的

反向（模型要学的）：
   给模型一张【加了噪的图】，让它预测【加进去的噪声是什么】
   ⟹ 学会了这个，就能从纯噪声开始，一步步"减掉噪声"
   ⟹ ★★ 最后减出一张原本不存在的清晰图
```

**三个必须知道的名词**：

| 名词 | 解释 | 为什么重要 |
|---|---|---|
| **潜空间扩散**<br>latent diffusion | 先用一个 **VAE**（Variational Auto-Encoder，变分自编码器）把 1024×1024 的图压成 128×128 的"潜图"，**在潜空间里做扩散**，最后再解码回像素 | ★ **这是文生图能跑起来的关键**（Stable Diffusion 的核心，arXiv 2112.10752），省了多少见下面那笔账 |
| **DiT** | Diffusion **Transformer**：把扩散模型里的 U-Net 换成 Transformer（arXiv 2212.09748） | ★★ **这一步让扩散和 LLM 用上了同一套架构和基建**，是后来能"统一"的前提 |
| **流匹配**<br>flow matching | 扩散的一个更简洁的数学表述，走直线而不是曲线 | 步数更少、更快。⟹ 隔壁 [具身智能](../具身智能与世界模型/01-具身智能与VLA.md) 里 π0 输出机器人动作用的是同一个东西 |

### ⚠️ "潜空间省了 64 倍"这句话要分两种情况说

```
边长     1024 → 128      ★ 降 8 倍
元素数   1024² = 1048576 → 128² = 16384
                          ★ 降 8² = 64 倍      ← 平方关系，不是 8 倍

⟹ 如果那一层的开销和【元素数成正比】（卷积、逐元素运算）：省 64 倍
⟹ ⚠️ 如果那一层是【自注意力】，开销和元素数的平方成正比：
     (1024²)² ÷ (128²)² = 8⁴ = ★★ 省 4096 倍

⟹ 🔑 所以"省 64 倍"是个保守说法。DiT 把 U-Net 换成全注意力之后，
   潜空间这一步省下来的其实是四个数量级 —— 这才是 DiT 可行的真正原因。
```

> 🔑 **和 LLM 的根本差异**：
> **LLM 是"从左到右一个字一个字往下写"；扩散是"整张图一起，从模糊到清晰刷很多遍"。**
> ⟹ ⚠️ 这个差异导致两者的**并行方式、KV cache、推理优化全都不通用**——
> 这也是"统一"这件事在工程上难的根本原因。

## 9.3 路线①：外挂——LLM 当甲方

```
用户：「画一只戴帽子的柯基，赛博朋克风」
  ↓
LLM：把它扩写成一段详细提示词（这是 LLM 的强项）
  ↓
扩散模型：照着画
```

```
✅ 优点：★ 极其实用。两边各自用最强的模型，独立升级，工程解耦
⚠️ 缺点：★★ 两个模型之间【只有一根文本细管子】
         ⟹ "把这张图里的猫换成狗，其它一模一样"这类【编辑】任务做不好
            因为"其它一模一样"这个信息，文字描述不出来
         ⟹ 多轮修改时上下文对不齐："再红一点" —— 扩散模型不记得上一张
```

```
★ 把"文本细管子"的带宽算一下，就知道这个缺点有多硬：
  一段详细提示词         约 100 个文本 token
  一张 512×512 的图     512 × 512 × 3 = 786432 个数

⟹ ⚠️ 你在用 100 个 token 去指定 78 万个数该长什么样。
⟹ 🔑 所以"其它一模一样"这件事在原理上就不可能通过文字传达 ——
  不是提示词写得不够好，是这根管子根本装不下那么多信息。
```

> 🔑 **这就是"统一模型"要解决的核心痛点：不是"画得更好看"，而是【可控和可编辑】。**

## 9.4 路线②：给图像造一本词典（全自回归）

> 📖 **VQ（Vector Quantization，向量量化）**：准备一本 codebook（码本，比如 8192 个"视觉单词"），
> 把每个图像块的向量**替换成码本里最接近的那一个的编号**。
> ⟹ **一张图就变成了一串整数** ⟹ 和文本 token 完全同构 ⟹ LLM 可以直接"挑"了。

```
图 ──VQ 编码器──→ [3021][887][1204]...[5566]   ← 1024 个整数
                   ★ 这些编号直接【加进 LLM 的词表】

序列：「画一只柯基」<image_start> [3021][887]... <image_end>
⟹ ★★ 训练目标、架构、推理代码，和纯文本 LLM 【完全一样】
```

**代表**：Chameleon（Meta，arXiv 2405.09818）、Emu3、Janus 系列。

> ✅ **Chameleon 论文给的具体参数**（这是本节所有算账的基础）：图像 tokenizer 把一张 **512×512** 的图编成 **1024 个离散 token**，**码本大小 8192**，码本维度 256，等效下采样 16 倍（512/16 = 32，32² = 1024）。它的文本 BPE 词表是 **65536**，其中 **8192 个就是图像 token**——⟹ ★ 图像 token 占词表的 8192/65536 = **12.5%**，**真的和文字共用同一个输出头**。

```
✅ 优点：架构极简、真正的"一个模型"，图文可以任意交错生成
         ⟹ "画一步、解释一步、再画一步"天然支持
⚠️ 缺点①：★ 量化必然【丢信息】—— 下面把这个损失算成数字
⚠️ 缺点②：★★ 一张图 1024 个 token，要【一个一个串行生成】
           ⟹ 比扩散的几十步去噪慢得多（9.7 节有串行步数对照）
⚠️ 缺点③：训练不稳定（Chameleon 论文花了大量篇幅讲怎么稳住）
```

### ★★ 离散化到底丢了多少：把信息量算出来

**这是本章最值得自己算一遍的一笔账。** 用 Chameleon 的真实参数：

```
原图能承载的信息量：
   512 × 512 像素 × 3 通道 × 8 bit = 6,291,456 bit = 786,432 字节 = 768 KiB

VQ 之后剩下的信息量：
   1024 个 token × log₂(8192) bit/token = 1024 × 13 = 13,312 bit
                                        = 1,664 字节 = 1.625 KiB

⟹ ★★ 压缩比 = 786,432 ÷ 1,664 ≈ 473 倍
```

**473 倍是个什么概念**：⚠️ 一张 512×512 的 JPEG，在肉眼几乎看不出损失的质量下大约 100~200 KB（**这是经验量级，不是测量值**）。而 VQ 把同一张图压到 **1.6 KB** —— **比一张高质量 JPEG 还小 60~120 倍**。⟹ 🔑 **这 1.6 KB 里装不下细毛发、装不下小字、装不下渐变色的精确过渡。这不是工程没做好，这是信息论的硬下限。**

> ✅ **Chameleon 论文自己承认了这个损失落在哪**：tokenizer 的一个核心弱点是**重建含大量文字的图像**，这**直接给模型在 OCR 类任务上设了一个上限**。⟹ ★ 注意这个弱点的方向：**丢掉的恰好是高频细节，而文字就是纯高频**。这和 [08 章](08-幻觉与多模态后训练.md) 8.1 表里的 ⑤ OCR 幻觉是同一个问题的两端——那边是"看不清"，这边是"画不出"。

### ⚠️ 为什么"把码本做大"这条路基本是死的

**直觉上，码本越大信息量越多。但它是对数关系。** 固定 1024 个 token，看码本大小的影响：

| 码本大小 | 每个 token 携带 | 1024 个 token 共计 | 相对 Chameleon 的信息量 | 压缩比 |
|---|---|---|---|---|
| 1,024 = 2¹⁰ | 10 bit | 1.25 KiB | 77% | 614 倍 |
| **8,192 = 2¹³**（Chameleon） | **13 bit** | **1.625 KiB** | **100%** | **473 倍** |
| 65,536 = 2¹⁶ | 16 bit | 2.00 KiB | 123% | 384 倍 |
| 262,144 = 2¹⁸ | 18 bit | 2.25 KiB | 138% | 341 倍 |
| ≈ 6,700 万 = 2²⁶ | 26 bit | 3.25 KiB | ★ 200% | 236 倍 |

```
⟹ ★★ 读最后一行：码本要从 8192 涨到 6700 万（★ 8192 倍！）
   才能让每张图的信息量【仅仅翻一倍】。

⟹ 对比另一个旋钮：token 数从 1024 涨到 2048（★ 只要 2 倍）
   信息量就直接翻倍。

⟹ 🔑 【码本大小是对数杠杆，token 数量是线性杠杆。】
   想多装信息，加 token 才是唯一有效的路。
```

```
⚠️ 但加 token 的代价也要算清（和 04 章、06 章同一个平方关系）：
   token 数    1024 → 2048      ★ 2 倍
   注意力开销  1024² → 2048²    ★★ 4 倍
   串行步数    1024 → 2048      ★ 2 倍 ⟹ 延迟直接翻倍

⟹ ★ 这就是路线②的根本困境：
  画质要靠 token 数，token 数要靠延迟和算力换，而它的延迟本来就是三条路里最差的。
```

> ⚠️ **"加大码本"还有一个比对数关系更糟的问题：码本坍缩（codebook collapse）。** 码本做大之后，**很多码字从训练开始到结束一次都没被用到**，于是"有效码本"远小于名义码本——名义上 65536，实际可能只用到几千个，**那 16 bit 是账面数字，不是真实携带的信息量**。⟹ 后来有工作（MAGVIT-v2 一路的 **LFQ**，Lookup-Free Quantization，免查表量化）用"不维护嵌入表"的办法把码本推到 2¹⁸ 这个量级来绕开坍缩。⚠️ **坍缩的具体利用率数字本文没有核对到一手来源，这里只说它存在、方向对不对。**

## 9.5 路线③：一个主干，两套输出（混合）

**这是 2024 年后最被看好的一条**，代表是 Transfusion（arXiv 2408.11039）、Show-o（arXiv 2408.12528）。

```
一个 Transformer，一条序列，里面有三段：

  段 1  文本：「画」「猫」
  段 2  图像：patch_1  patch_2  ...  patch_N     ← ★ 连续向量，不量化
  段 3  文本：「再」「解」「释」

★★ 三段跑在同一个主干上，但 loss、注意力掩码、推理方式【各不相同】。
```

**三段的待遇逐项排开**：

| 序列里的段 | 内容是什么 | 算什么 loss | 注意力掩码 | 推理时怎么出来 |
|---|---|---|---|---|
| 段 1 文本 | 词表里的编号 | 自回归 CE（Cross Entropy，交叉熵） | 因果：只能看左边 | 一个 token 一个 token 往下写 |
| **段 2 图像** | ★ **连续向量（patch），不量化** | ★ **扩散 loss（预测噪声）** | ★★ **段内双向**：图的左边可以看右边 | ★ **整块一起，多步去噪** |
| 段 3 文本 | 词表里的编号 | 自回归 CE | 因果：能看到前面整张图 | 一个 token 一个 token 往下写 |

```
★★ 两个关键点，和上表一一对应：
  ① 图像部分【不量化】，保留连续向量 ⟹ 没有 9.4 节那 473 倍的量化损失
  ② 图像内部用【双向注意力】，文本仍然是因果的
     ⟹ 为什么？因为画图不是"从左到右"的过程 ——
       一张图的构图是整体决定的，左上角的内容依赖右下角
```

```
✅ 优点：画质接近纯扩散，同时保留 LLM 的语言与推理能力
⚠️ 缺点：★ 工程复杂度高 —— 一个模型里跑两种 loss、两种注意力掩码、
         两种推理模式（自回归 vs 多步去噪），
         ⟹ 现成的推理框架（vLLM / SGLang）不直接支持
         ⟹ ★ 具体卡在哪：KV cache 是为"因果 + 一次一个 token"设计的，
           而图像段是"双向 + 整块反复刷 50 遍"，这两种访存模式对不上
```

## 9.6 ★★ 一个深层矛盾：理解要的和生成要的不是一个东西

这是本章最值得记住的一条洞见：

```
★ 理解任务需要的编码：  丢掉细节，保留语义
    "这是一只猫"——毛发的具体纹理是噪声，压掉才好

★ 生成任务需要的编码：  保留一切像素细节
    少一根毛都画不回来

⟹ ⚠️ 同一个视觉编码器要同时服务这两个目标，是在【自相矛盾】
⟹ ⟹ 这就是"统一模型的理解能力通常打不过同规模纯理解模型"的原因
```

> ★ **9.4 节那笔账正好给这个矛盾标了刻度**：理解一张图需要的信息量可以压到 1.6 KB 还够用（"这是一只猫"根本不需要知道每根毛的位置）；而生成一张图需要的信息量，1.6 KB 远远不够。**同一个编码器要同时满足"压到 1.6 KB"和"不能压到 1.6 KB"，这不是调参能解决的。**

**Janus 系列给的解法很直白：干脆用两个编码器。** 理解走一个语义编码器，生成走一个像素编码器，**只共享 LLM 主干**（arXiv 2410.13848 / 2501.17811）。

> 🔑 **"解耦编码、共享主干"很可能是这条路的正确答案**——
> ⚠️ 这是我的判断。它的代价是"统一"的成色打了折：**统一的是大脑，不是眼睛。**

## 9.7 三条路线对照

### 表一：机制层面（怎么表示图像、训练什么、串行几步、共享不共享参数）

| | ① 外挂扩散 | ② 全自回归（VQ） | ③ 混合（Transfusion 式） |
|---|---|---|---|
| **图像在模型里长什么样** | 根本不进 LLM，只有一段提示词文本 | ★ **离散编号**（码本里的 index），和文字 token 同构 | ★ **连续向量**（patch），不量化 |
| **图像进不进词表** | 不进 | ★★ **进**。✅ Chameleon：词表 65536 里有 8192 个是图像 token | 不进词表，走单独的输入 / 输出通道 |
| **训练目标** | 两个模型分开训：LLM 用 CE，扩散模型学预测噪声 | ★ **只有一个目标**：next-token CE | ★ 同一条序列上两个 loss：文本 CE + 图像扩散 |
| **注意力掩码** | 各自独立，不互通 | 全因果 | ⚠️ 混合掩码：文本因果 + 图像段内双向 |
| **和文本共享参数** | ❌ **完全不共享**（只共享一根文本细管子，9.3 节） | ★★ **100% 共享**：同一个主干、同一个输出头、同一个词表 | 共享主干，**不共享输入 / 输出头** |
| **出一张图的串行步数** | ≈ 50（去噪步数） | ⚠️ ≈ **1024**（token 数，一个一个来） | ≈ 50（去噪步数） |
| **有没有量化信息损失** | 无（VAE 有少量） | ⚠️ ★★ **有，约 473 倍压缩**（9.4 节） | ★ 无量化损失 |

```
★ 把"串行步数"这一行单独说清楚，因为它最容易被误读：
  路线② 的 1024 ÷ 路线① 的 50 ≈ ★ 20 倍的串行步数

⚠️ 但【串行步数 ≠ 总计算量】：
   扩散的一步   = 整张潜图过一遍完整的 UNet / DiT        ← 单步很贵
   自回归的一步 = 只算 1 个新 token（有 KV cache 兜着）  ← 单步很便宜

⟹ ⚠️ 所以路线② 的【总 FLOPs 可能反而更少，但延迟一定更差】。
⟹ 🔑 这是"延迟和吞吐是两件事"的教科书案例：
     · 看【单张图的延迟】⟹ 路线② 最差，1024 次串行前向一步都省不掉
     · 看【批处理吞吐】 ⟹ 路线② 可以攒大 batch 把 GPU 填满，吞吐未必差
   ⟹ ★ 做实时交互产品看第一行，做离线批量出图看第二行，结论相反。
```

### 表二：工程与产品后果

| | ① 外挂扩散 | ② 全自回归（VQ） | ③ 混合（Transfusion 式） |
|---|---|---|---|
| 画质 | ★ 最好 | ⚠️ 一般（量化损失是根因） | 接近① |
| 单张图延迟 | 快 | ⚠️ 慢 | 中 |
| 图文交错生成 | ❌ 做不了 | ★ 天然支持 | ★ 支持 |
| 精细编辑 / 多轮一致性 | ⚠️ 差（细管子） | 好 | 好 |
| 工程复杂度 | ★ 最低 | 低 | ⚠️ 最高 |
| 推理框架支持 | 成熟 | 成熟 | ⚠️ 要自己改（KV cache 对不上，9.5 节） |
| 现在谁在用 | ★ 绝大多数产品 | 研究为主 | 研究 + 少数产品 |

> ⚠️ **这两张表里的分级（"最好 / 一般 / 快 / 慢"）是我按机制归纳的定性判断，不含任何具体产品的实测数据**；表一里带 ✅ 的两格（Chameleon 的词表和 token 数）和 9.4 节所有算术，才是有一手出处的。
> ⚠️ 另外：本仓库归档的五份 2026 年一手报告**都是理解型多模态**（K3 / M3 / GLM-5.3-Flash），
> **没有一份涉及图像生成** ⟹ **本章无法用本仓库的一手材料交叉验证**，请特别注意。

## 9.8 ⚠️ 一个还没有答案的问题：统一到底值不值

```
支持方的论证：
  "会画画的模型才真的理解世界"——能画出来说明真的懂结构
  ⟹ 类比：人学会画一个东西，才算真看懂了它

⚠️ 怀疑方的论证（我倾向这一边）：
  ① 至今【没有公开证据】表明"加了生成能力，理解分数会提升"
  ② 理解和生成对编码的要求相反（9.6 节）⟹ 统一是在付出代价
  ③ 产品上，用户要的是"画得好"和"答得准"，
     ★ 而不是"这两件事由同一堆参数完成"

🔑 目前"统一"的真实好处是【交互形态】：多轮编辑、图文混排输出、
   一致性维持 —— 这些是外挂路线做不到的。
   ⟹ 这是产品价值，不是智能价值。这个区分很重要。
```

## 9.9 🔑 这一章的六句话

1. 生成的根本障碍是：**LLM 的输出头只会从词表里挑编号，而图片是几百万个连续数。**
2. **扩散模型 = 学会预测"加进去的噪声"**。潜空间把边长压 8 倍，**元素数就降 64 倍，自注意力的开销降 4096 倍**（平方关系），这才是 DiT 可行的原因；**DiT 又是后来能统一的技术前提**。
3. 三条路：**外挂（最实用）/ 给图像造词典（最简洁）/ 混合双 loss（画质与统一兼顾，最复杂）**。只有路线② 真正和文本共享全部参数（✅ Chameleon 的 65536 词表里有 8192 个图像 token）。
4. ★★ **离散化的代价是可以算出来的**：Chameleon 把 768 KiB 的图压成 **1.625 KiB，压缩比 473 倍**，比高质量 JPEG 还小两个数量级。✅ 论文自己承认它在"含大量文字的图"上重建不行，**给 OCR 能力设了上限**。
5. ★★ **码本大小是对数杠杆，token 数量是线性杠杆**：码本要涨 8192 倍才能让信息量翻倍，token 数只要涨 2 倍。⚠️ 但 token 翻倍 = 注意力 4 倍 + 延迟 2 倍。
6. ⚠️ **"统一能提升理解"至今没有公开证据**；**理解要压掉细节、生成要保住细节**是统一模型的天花板，Janus 的解法是"两只眼睛、一个大脑"。统一目前买到的是**交互形态**，不是智能。
