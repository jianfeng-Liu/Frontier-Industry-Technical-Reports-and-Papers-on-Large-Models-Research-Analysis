# 10 · 语音与实时全双工：难点根本不在智能

> 这一章讲第三个战场。**它的技术含量常被低估**：
> 一个能考满分的模型，做成语音助手照样难用——因为**这里的敌人是毫秒，不是智商**。

---

## 10.1 老办法：三段式级联

```
    你说话 ──→ [ASR 语音识别] ──→ 文字 ──→ [LLM] ──→ 文字 ──→ [TTS 语音合成] ──→ 声音
              📖 Automatic          📖 Text-to-Speech
              Speech Recognition
```

**✅ 优点**：三段各自独立、可替换、可调试，**至今仍是绝大多数产品的做法**。

**⚠️ 但有两个致命伤：**

### 伤口① 延迟账

```
    ① 判断"你说完了"（VAD 静音检测）     500 ~ 800 ms   ← ★ 最大的一块，且无法压缩
    ② ASR 出最终文本                      100 ~ 300 ms
    ③ LLM 首 token（TTFT）                300 ~ 800 ms
    ④ TTS 出第一段音频                    100 ~ 300 ms
    ─────────────────────────────────────────────────
      合计首声延迟                        ★ 1.0 ~ 2.2 秒

    ⚠️ 参照：人和人对话的轮次间隔约 200 毫秒
    ⟹ 1.5 秒的停顿，在人类感受里就是【这人反应好慢 / 是不是没听见】
```

> ★★ **注意第①项**：它是**架构性**的——**因为你必须先确定他说完了，才能开始想**。
> ⟹ 这一条单独就决定了级联方案**永远做不到自然对话的节奏**。

### 伤口② 信息在 ASR 那一步被丢光了

```
    语音里有：文字内容 + 语气 + 情绪 + 音量 + 重音 + 谁在说 + 背景声 + 停顿
    ASR 输出：★ 只有文字

    ⟹ 「你行啊。」这句话，是夸奖还是嘲讽？ ⚠️ 转成文字后，模型永远无法知道
    ⟹ 反过来，TTS 那一端也只拿到文字 ⟹ 它不知道这句话该用什么情绪念
```

## 10.2 ★ 新办法：端到端语音

**思路和视觉完全同构**（这就是为什么它属于多模态）：

```
    输入侧：声音 → [音频编码器] → 音频 token → 和文本 token 拼进同一条序列
                   📖 通常是 Whisper（arXiv 2212.04356）那一类的编码器
                   ⟹ ★ 和 02 章的视觉塔是同一个位置、同一个角色

    输出侧：★ 这里是新问题 —— 怎么让 LLM "吐"出声音？
            ⟹ 和 09 章图像生成【一模一样的困境】，也用了同一个解法：
              给声音造一本词典（音频 codec）
```

> 📖 **音频 codec / 声学 token**：用 **RVQ（残差矢量量化）** 把每 80 毫秒的声音
> 编码成几个整数（比如 8 层码本、每层一个编号）。
> ⟹ **声音就变成了一串"词"** ⟹ LLM 可以像写字一样"写"出声音。
> ⟹ ⚠️ 注意它是**多层**的：第一层管内容，后面几层管音色和细节 ——
> 所以输出时要**同时预测好几个流**，这是语音生成比文本生成复杂的地方。

```
    ✅ 收益①：★★ 延迟直接砍到 300 毫秒以内 —— 因为不需要等 ASR、TTS 两次转换
    ✅ 收益②：情绪、语气、说话人信息【全程保留】，模型能听出嘲讽、能带情绪回答
    ⚠️ 代价①：音频 token 很占位置（每秒几十到上百个 token）
    ⚠️ 代价②：★ 语音数据远比图文数据稀缺，尤其是【带情绪、多轮、真实对话】的
    ⚠️ 代价③：文本能力会掉——和 06 章"加视觉会让文本变笨"是同一个病
```

## 10.3 ★★ 真正的分水岭：全双工

> 📖 **半双工**：像对讲机，一次只能一个人说（你说完 → 它说 → 你说）。
> 📖 **全双工（full-duplex）**：像真人对话，**双方随时可以同时说、可以打断、可以"嗯嗯"附和**。

```
    ⚠️ 半双工模型在架构上是"回合制"的：
       听（收集 token）→ 想 → 说（生成 token）→ 停 → 再听
       ★ 在它"说"的时候，它【根本没在听】
       ⟹ 你想打断它？它听不见。只能靠外面的程序检测到你出声、然后掐掉它

    ★ 全双工的做法（Moshi，arXiv 2410.00037 是最出名的公开工作）：
       模型【每 80 毫秒一拍】，每一拍同时做两件事：
         · 读入这一拍你说的声音
         · 输出这一拍它要说的声音（可以是"静音"）
       ⟹ ★★ 于是"听"和"说"变成【两条永远并行的流】
       ⟹ 打断不再需要外部逻辑 —— 它听见你出声，自己就会停
       ⟹ 它甚至可以在你说话时插一句"嗯"（📖 backchannel，附和音）
```

> 🔑 **这是一个架构级的差别，不是调参能达到的。**
> ⟹ **判断一个语音产品是不是真全双工，只要试一件事：在它说话时插一句"等一下"。**
> 半双工的会说完那一句才反应，或者被硬生生掐断（听起来像卡带）。

## 10.4 流式：所有东西都要"边来边算"

```
    ⚠️ 视觉可以等图片完整了再编码；语音不行 —— 你不能等他说完
    ⟹ 音频编码器必须【流式】：来一小段算一小段
    ⟹ 注意力要限制成【只看过去 + 一小段未来】（chunk-wise / 因果注意力）
    ⟹ ⚠️ 代价：模型损失了"回头听"的能力，识别准确率比离线模式低一截
```

**推理侧的连锁反应**（可对照 [../推理框架/推理优化入门/](../推理框架/推理优化入门/)）：

```
    · 语音的 KV cache 是【持续增长】的 —— 一通 10 分钟的电话，
      按每秒 50 个音频 token 算 ⟹ ⚠️ 3 万个 token 的 KV，全程占着显存
    · 必须严格控制【每一拍的计算量】：80 毫秒一拍，你就只有 80 毫秒
      ⟹ ★ 这是【硬实时】约束，和聊天场景"平均延迟低就行"完全不同
    · ⟹ 和隔壁 ../具身智能与世界模型/ 里机器人控制的实时性约束是同一类问题
```

## 10.5 ⚠️ 这个方向的三个真实困难

```
 ① 数据       ★ 最大的坎。真实的、多轮的、带打断和情绪的对话录音，
              既稀缺又有隐私和版权问题
              ⟹ 合成数据在这里很难造：★ 合成对话没有真实的【打断和重叠】

 ② 评测       ⚠️ 几乎无解。"这个语音助手好不好用"该怎么打分？
              延迟能测，打断响应能测，但【对话的自然度】只能靠人听
              ⟹ 见 11 章：这是多模态评测困境里最严重的一格

 ③ 智能倒退   ★ 端到端语音模型的【推理能力普遍弱于同源文本模型】
              ⚠️ 原因我认为有两条：语音数据量小得多；
                 以及"实时"这个约束不允许它做长思维链——
                 ★★ 你不能让用户等它想 30 秒
              ⟹ 🔑 这是【延迟和智能的直接对立】，目前无解，
                 只能靠"简单问题端到端答、复杂问题转给文本模型"这类工程折中
```

## 10.6 "omni / 全模态"这个词该怎么理解

```
    宣传里的 omni：文/图/音/视频，全都能进、全都能出
    ⚠️ 实际拆开看，通常是：
       · 文、图、音【进】     ← 这个一般是真的
       · 文【出】             ← 一定是真的
       · 音【出】             ← 可能是端到端，也可能是外挂 TTS ★ 差别巨大
       · 图【出】             ← 大概率是外挂扩散（09 章路线①）

    🔑 三个问题看穿一个"全模态"模型：
       ① 语音输出是端到端的，还是接了 TTS？
       ② 是不是全双工？（在它说话时打断试试）
       ③ 图像输出是同一个模型出的，还是调了另一个模型？
```

## 10.7 🔑 这一章的五句话

1. **级联（ASR→LLM→TTS）的两个致命伤：1.5 秒起步的延迟，和 ASR 那一步把语气情绪全丢光。**
2. **端到端语音 = 音频编码器（对应视觉塔）+ 音频 codec 输出（对应图像词典）**——结构和前面九章完全同构。
3. ★★ **全双工是架构级差别**：听和说是两条并行的流。**试着打断它，就知道是不是真的。**
4. ⚠️ **实时约束和智能直接对立**：不能让用户等你想 30 秒 ⟹ 端到端语音模型的推理能力普遍弱一截。
5. ⚠️ **"全模态"是营销词**，拆开问四个模态各自"进还是出、端到端还是外挂"，宣传就现形了。
