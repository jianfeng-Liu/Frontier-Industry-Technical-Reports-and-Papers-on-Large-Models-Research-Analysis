# 12 · 推理与训练工程：多模态是怎么把系统搞乱的

> 📖 **前置**：[../推理框架/推理优化入门/](../推理框架/推理优化入门/) 和
> [../训练框架/分布式训练入门/](../训练框架/分布式训练入门/)。
> **本章只讲"加了视觉之后，那些干净的假设是怎么被打破的"。**

---

## 12.1 ★★ 推理：从两段变三段

纯文本推理只有两个阶段（见 [../推理框架/推理优化入门/03-Prefill与Decode两阶段.md](../推理框架/推理优化入门/03-Prefill与Decode两阶段.md)）：

```
    Prefill（吃进 prompt，算力密集）  →  Decode（一个一个吐字，访存密集）
```

**多模态凭空多出一段，而且它的性格和前两段都不一样**：

```
 ┌────────────┬──────────────┬──────────────┬─────────────────┐
 │            │   Encode     │   Prefill    │    Decode       │
 │            │  （视觉编码） │              │                 │
 ├────────────┼──────────────┼──────────────┼─────────────────┤
 │ 瓶颈       │ ★ 纯算力     │ 算力，且产 KV │ ★ 访存带宽      │
 │ 要不要 KV  │ 不要         │ 要写          │ 要读            │
 │ batch 特性 │ 图多才划算   │ 长序列        │ 大 batch 才划算 │
 │ 时长       │ 每图 ~25 ms  │ 长            │ 每 token 几十 ms │
 └────────────┴──────────────┴──────────────┴─────────────────┘
```

> ✅ **一手证据（GLM-5.3 的 EPD 分离）**：
> *"视觉编码是纯计算密集的（过 24 层 ViT），prefill 是计算密集但要 KV，decode 是访存密集。
> **三者的硬件需求完全不同。挤在一起的话，一张图片的编码会把 decode 的卡堵住。**
> 拆开后每一段可以独立扩缩容。"*
> 出处：[../业界模型技术报告/GLM-5.3.md](../业界模型技术报告/GLM-5.3.md) §7.2
>
> ```
>     GLM-5.3-Flash 的 EPD：Encode 池 → Prefill 池 → Decode 池
>                             ↑
>                        多模态编码（图/视频过视觉塔）单独成池
> ```

> 🔑 **这是纯文本世界 PD 分离（Prefill/Decode）的直接延伸**：
> 见 [../推理框架/推理优化入门/10-PD分离.md](../推理框架/推理优化入门/10-PD分离.md)。
> ⟹ **规律：只要一类负载的瓶颈资源和别人不同，它迟早会被拆成独立的池。**

## 12.2 算一笔显存账：一张图的 KV 有多大

```
    ⚠️ 我的估算（假设：60 层、GQA 4 个 KV 头、head_dim 128、bf16）：

      每 token 每层 KV = 2(K和V) × 4 × 128 × 2 字节 = 2048 字节
      每 token 全模型  = 2048 × 60 层 ≈ 120 KB

      一张图 1521 个视觉 token ⟹ ★ 约 178 MB 的 KV cache
      ⟹ 一个 80GB 的卡，光是【450 张图】的 KV 就满了
      ⟹ 而这还没算模型权重
```

> ★★ **这就是为什么多模态服务的并发数远低于纯文本服务。**
> ⟹ 也是为什么 [MLA 这类压缩 KV 的注意力](../业界模型技术报告/大模型架构入门/07-MHA到MLA.md)
> 在多模态场景下**收益比纯文本更大**——⚠️ 这一条是我的推断，报告里没有直接对比。

## 12.3 ★ 一个立刻能用的优化：缓存视觉编码结果

```
    典型场景：用户上传一张图，然后连问五个问题
    ⚠️ 天真实现：每一轮都把图重新过一遍视觉塔 ⟹ 每轮白烧 25 毫秒 + 算力

    ★ 正确做法：用图片的哈希做 key，把【连接器输出的那 1521 个向量】缓存起来
      ⟹ 第 2~5 轮直接命中，Encode 阶段耗时归零

    ⟹ ★★ 更进一步：如果 prompt 的前缀（含图）完全一样，
       连 KV cache 都可以复用 —— 这就是普通的前缀缓存
       见 ../推理框架/推理优化入门/05-PagedAttention与前缀缓存.md
```

> ⚠️ **陷阱**：前缀缓存的 key 通常是**文本 token 序列的哈希**。
> 图像走的是"占位符 token + 外部向量"这条路，**如果实现时没有把图片内容一起算进 key，
> 就会出现"换了图但命中了旧缓存"的严重 bug**。
> ⟹ 这类 bug 的表现是"模型回答的是上一张图的内容"——**看起来像幻觉，其实是缓存错了**。

## 12.4 变长：多模态把 batching 搞乱了

```
    纯文本的连续批处理（continuous batching）假设：
      每个请求每一步生成 1 个 token ⟹ 步长整齐 ⟹ 可以随时插拔请求
      见 ../推理框架/推理优化入门/04-连续批处理与调度.md

    ⚠️ 多模态打破了它：
      · 请求 A：纯文本，prompt 50 token
      · 请求 B：带 1 张图，prompt 1571 token
      · 请求 C：带 1 段视频，prompt 76800 token   ← ★ 这一个能把整批卡住
      ⟹ 调度器要处理【三个数量级】的 prompt 长度差异
      ⟹ 一个视频请求进来，其它请求的 TTFT（首字延迟）全被拖垮
```

**常见对策**：

```
    ① ★ EPD 分离（12.1）—— 从架构上隔离
    ② 分块 prefill（chunked prefill）：把超长 prompt 切成小块，
       和别人的 decode 交错着算 ⟹ 不让一个巨型请求独占
    ③ 按"带不带图 / 带不带视频"分队列，甚至分集群
```

## 12.5 训练侧的三个麻烦

### 麻烦① 变长样本 → 负载不均

```
    一个 batch 里：样本 1 有 0 张图、样本 2 有 3 张图、样本 3 有 1 段视频
    ⟹ 各个 DP rank 的实际计算量差好几倍
    ⟹ ★ 快的 rank 干等慢的 rank（木桶效应）⟹ MFU 掉

    对策：按【总 token 数】而不是【样本数】来组 batch（token-based batching）
         + patch packing（把多张图打包进一条序列，用掩码隔开）
    ⟹ 和纯文本的样本打包是同一套技术：
       ../数据格式和数据处理/13-打包与文档掩码.md
```

### 麻烦② 视觉塔不好切

```
    LLM：2.78T 参数，必须切（TP + PP + EP）
    视觉塔：0.4B 参数 ⟹ ★ 太小了，切了通信开销比计算还大
    ⟹ 常见做法：视觉塔【每个 rank 各存一份（DP 复制）】，只切 LLM
    ⟹ ⚠️ 但这样一来，流水线并行（PP）的第一段就多背了一个 ViT
       ⟹ ★ PP 的各段负载又不均了，需要手工调整层的划分
    ⟹ 并行策略基础见 ../训练框架/分布式训练入门/12-并行策略组合与MFU.md
```

### 麻烦③ 两个部件的"训练性格"不一样

```
    ✅ K3 的实证：SigLIP 初始化的视觉塔【梯度范数持续更高且频繁 spike】
    ⟹ 混合精度、梯度裁剪的阈值，对视觉塔和 LLM【应该不一样】
    ⟹ ⚠️ 但多数框架是全局设一个阈值 ⟹ 要么裁得太狠、要么防不住 spike
    ⟹ K3 的应对是【从零训 + 移除视觉塔所有 bias 项】（见 02、06 章）
```

---

## 12.6 🔑 这一章的四句话

1. ✅ **多模态推理从两段变三段：Encode / Prefill / Decode，性格完全不同 ⟹ 必然被拆成独立的池**（GLM-5.3 的 EPD）。
2. ⚠️ **一张图约 178 MB 的 KV cache**（我的估算）⟹ 多模态服务的并发天然远低于纯文本。
3. ★ **最容易拿到的优化是缓存视觉编码结果**；但要小心"缓存 key 没算图片内容"这个会伪装成幻觉的 bug。
4. **训练侧的核心矛盾是"变长"和"两个部件性格不同"**：token-based batching + packing 解决前者，分别调优解决后者。
