13.2 ★★ 把五家的视觉 token 预算放到同一个刻度上

主表里"输入尺寸"和"token 压缩"两行是分开看的，合起来算才有意义。 下面每一格都能自己验算（算法见 12.2）：

模型 输入边长 patch 数 = (边长/14)² 压缩 一张满分辨率图的视觉 token ⚠️ ≈多少汉字
GLM-5.3-Flash 448 32×32 = 1024 ÷4 256 ≈180
DeepSeek-V4.1-Flash ≈1344 96×96 = 9216 ÷9 1024 ≈730
MiniMax M3 2016 144×144 = 20736 ÷4 5184 ≈3700
Kimi K3 3584 256×256 = 65536 ÷4 16384 ≈1.2 万 
    ⟹ 🔑🔑 ★★ 最高和最低【差 64 倍】（16384 ÷ 256）
    ⟹ 而这四家的视觉塔【部件清单几乎一样】：patch 都是 14，
       层数都在 24~32，hidden 都在 1024~1280

    ⟹ ★★ 所以"架构收敛了"这个说法只对了一半：
       部件收敛了，【预算完全没收敛】

⚠️ 两条口径提醒，不看会读错这张表：
① GLM 的 448 是 config.json 里的 image_size，很可能是"一块"的尺寸。如果它在上面叠了动态切图（AnyRes），一张大图的总 token 会是 256 的若干倍。⚠️ config 看不出有没有叠，报告也没说，所以这一格的真实含义是"每块 256 token"，不是"一张图最多 256 token"。
② K3 的 16384 是上限，不是常用值。真实请求里大多数图远小于 3584²，算出来的是"最坏情况的预算"。

🔑 这张表解释了两件原本看不懂的事（⚠️ 以下两条是我的读法，报告没有这样表述）：
⟹ ★ GLM-5.3-Flash 的单块预算是四家最小的（256 token），而 ✅ 它的设计目标本来就写着"为极低成本推理重新设计"——两件事是一致的。
⟹ ★ 只有 DeepSeek 选 3×3（÷9），而 ✅ 它整篇报告的主题是"把 KV cache 压到极限"。在一个全力压 KV 的模型里，视觉 token 正是最大的一块 KV（12.3 那 90%），所以压它是同一个目标的延伸。

13.4 ★ 从这几张表能读出的四件事

① ⚠️ 原来的招牌结论错了：现在是四家做、一家不做

    做了：V4.1-Flash、K3、GLM-5.3-Flash、M3
    没做：openPangu-2.0-Pro（报告明说 Claw-Eval 只评非多模态子集）

    ★ 而且两家是【一代之内翻的】：
      · DeepSeek：V4 外挂/纯文本  ->  V4.1-Flash 原生多模态
      · GLM：     5.2 纯文本      ->  5.3-Flash 原生多模态

⚠️⚠️ 这里要把一条被推翻的推断原样留着，因为它的教训比结论值钱。
本章原来写的是："多模态尚未被证明能提升纯文本智能……如果多模态能提升推理，V4 这种把宝全押在推理上的模型没有理由不做。"
⟹ ★★ V4.1-Flash 直接推翻了它的前半截推理过程：V4.1 比 V4 更推理导向（总参砍到约 1/3、激活砍到约 1/4），却反而把多模态从外挂改成了原生。
⟹ 🔑 教训很具体：从"谁没做一件事"反推"这件事没用"是不可靠的。 厂商不做某件事的原因可能只是数据管线还没准备好，和这件事有没有用无关。

⚠️ 但别过度纠正："多模态能提升纯文本智能"仍然没有被证明。 ✅ V4.1 给的理由不是能力，是语料——报告说爬虫"过于偏向文本网页"，所以从 Common Crawl 重新自举。★ 它把多模态当成语料工程问题而不是能力问题，这是五家里独一份的动机。
⟹ 🔑 所以正确的更新是：失效的是"推理导向的模型不做多模态"这条经验规律，不是"多模态提不提升智能"这个开放问题（后者见 14.3 ①）。

② ⚠️ "架构已经收敛"说过头了：部件收敛，预算没有

    ✅ 真的收敛的部分：
       · patch 边长 14：四家全是 14
       · 中等 ViT：层数 24~32、hidden 1024~1280、参数 0.4B 量级
       · 空间 2×2 合并：K3 ✅、GLM ✅、M3 ✅（三家）

    ⚠️ 明显没收敛的部分：
       · 压缩倍数：V4.1 用 3×3（÷9），其余三家 2×2（÷4）
       · 一张图的 token 预算：256 vs 1024 vs 5184 vs 16384 —— ★★ 差 64 倍
       · 位置编码：V4.1 是 2D-RoPE，M3 是 3D RoPE，另两家没说

    ⟹ 🔑 更准确的说法：
       ★★ 【部件清单收敛了，预算策略完全没收敛】
       而预算策略恰好是决定"成本"和"能不能读小字"的那一项

⚠️ 顺带撤回一个归因：本章原来写过"这是 SigLIP-SO400M（27 层 / patch 14 / 400M）成了事实标准之后的行业惯性"。证据不足，降级为猜测——✅ 只有 K3 的 27 层对得上 SO400M，而 GLM 是 24 层、V4.1 和 M3 都是 32 层，三家都不是那个形状。
⟹ 能站得住的只有一句：patch 14 这一个参数四家一致；其余"趋同"更像同一个尺寸区间里各自调参，不是抄同一份配置。

③ ✅ 只有 GLM-5.3 认真回答了"为什么"

其它几家都在讲怎么做，只有 GLM 讲了为什么值得做，而且论证是产品级的：

✅ "For tasks such as frontend development, game development, and 3D simulation, the final output is not code alone, but an interface, an interaction, or a world experienced by the user. Many failures only surface through rendering, interaction, or playtesting."

✅ "Vision therefore needs to be natively integrated into the model, enabling it to decide when to observe and use visual feedback to guide subsequent actions."

    ⟹ 🔑 这个论证的关键在于：★★ 它把视觉从【一个输入模态】
       重新定义成了【agent 的验证器】。
    ⟹ 在这个框架下，"多模态能不能提升智能"这个问题被换掉了：
       ★ 视觉不是让模型更聪明，而是让模型【能看见自己干得对不对】。
    ⟹ ⚠️ 我认为这是目前为止多模态最有说服力的一个存在理由，
       比"让模型能看图说话"强得多。

★ 现在它还多了一个对照：✅ V4.1-Flash 给的理由是语料覆盖（13.4 ①）。⟹ 🔑 于是五家里唯一给了理由的两家，给的是两个完全不同的理由：一个是"视觉让 agent 能自检"，一个是"不吃图就少吃了一批网页"。⚠️ 两个理由都不是"多模态让模型更聪明"。

④ 评测各说各话（11.7 已详述）

    ✅ K3 和 M3 之间【零个共享的视觉 benchmark】
    ⚠️ 而唯一一组同名的（M3 的 MMMU_Pro 78.1 vs V4.1 的 MMMU-Pro 56.5）
       一个是后训练模型、一个是 Base 模型 ⟹ ★ 恰好也不能比

上面四家是本仓库有一手材料的。开源多模态生态还有另外一批玩家，它们才是大多数人真正会用到的：

⚠️⚠️ 下表为背景性介绍，时效性和细节未经本轮核实，仅用于建立方位感。★ 任何一条都不要当作可引用的事实。

🔑 一条选型经验（⚠️ 我的判断，不是实测结论）：
做通用看图问答，挑一个主流开源 VLM（Vision-Language Model，视觉语言模型）微调即可；做文档/表格/发票，一定要看它的"最大支持分辨率"和"是否有 OCR（Optical Character Recognition，光学字符识别）专项训练"，这两项比它的 MMMU 分数重要得多。
⟹ ★ 13.2 那张表就是这条经验的量化版：256 token 和 16384 token 是两种完全不同的产品，而 MMMU 分数不会告诉你这件事。

  2. ★★ 教训比结论重要：V4.1-Flash 比 V4 更推理导向却反而做了原生多模态 ⟹ 从"谁没做"反推"做了没用"是不可靠的推理。而 V4.1 给的理由是语料工程，所以"多模态能不能提升智能"这个问题仍然开放。
  3. ★★ "架构收敛"只对了一半：patch 14 四家一致、ViT 都在 24~32 层，但一张图的 token 预算从 256 到 16384，差 64 倍 ⟹ 部件收敛，预算策略完全没收敛。
  4. ★ 披露程度本身就是信息：能从 config.json 算出来的形状，四家全给；能决定效果的训练决策（初始化、冻不冻、语料配比），最多两家给。 ⚠️ 形状藏不住，训练决策是唯一还能保密的东西。
  5. ⚠️ 我们知道他们做了什么，但不知道谁做得更好——分数是图片、只有 Base、口径不通用、benchmark 零重叠。
