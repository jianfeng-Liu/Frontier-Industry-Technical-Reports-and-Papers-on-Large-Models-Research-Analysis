00 · 总纲：所有算子优化都在解同一个问题

前置：无。这是全系列的入口，建议在读任何一章之前先读完。
目标：给你一个平台无关的骨架——算子优化到底在优化什么、一共有哪几种手段、两类硬件为什么长得不一样、性能出问题时按什么顺序查。有了这个骨架，后面每一章都是在往上挂具体技术。
读法：本章不讲任何一种具体实现，但每个抽象说法后面都跟一个带真实数字的小例子，例子里的算术都能自己验算。建议拿纸笔跟着算——本章的四个例子分别是后面第 03、05、03、06 章的缩微版，先在这里算一遍，进正文时就不会迷路。

本章关键词

算子（Operator / Kernel，核函数）—— 在加速卡上执行的一个计算单元，如矩阵乘、Softmax、LayerNorm。PyTorch 里一行 torch.matmul 对应底层一个或多个算子。
FLOP（Floating Point Operation，浮点运算次数）与 FLOPS（Floating Point Operations Per Second，每秒浮点运算次数）—— 前者是"总工作量"，后者是"干活速度"，只差一个大小写的 S，混了后面全错。
HBM（High Bandwidth Memory，高带宽显存）—— 加速卡的主内存，大（几十到上百 GB）但相对慢。本系列说"搬数据"，默认指 HBM 和芯片之间的往返。
片上存储（On-chip Memory）—— SRAM（Static Random-Access Memory，静态随机存储器）级的高速存储，容量以 KB 计，速度比片外 HBM 快一到两个数量级。
带宽墙（Memory Wall，内存墙）—— 算力增长长期快于内存带宽增长，导致越来越多的计算被"喂数据"的速度卡住。
算术强度（Arithmetic Intensity，简称 I）—— 每从 HBM 搬运 1 字节，能做多少次浮点运算，单位 FLOP/Byte。判断算子瓶颈的核心指标。
屋脊点（Ridge Point）—— 屋顶线模型上算力屋顶与带宽斜线的交点，是"算力受限"和"带宽受限"的分界算术强度。H100 的 BF16 屋脊点是 295 FLOP/Byte。
Memory Bound（带宽受限）/ Compute Bound（算力受限）—— 算术强度低于 / 高于屋脊点的两种状态。
Host Bound（下发受限）—— CPU 把命令发给加速卡的速度跟不上加速卡执行的速度，卡在饿着等命令。屋顶线模型看不见这一类。
SIMT（Single Instruction Multiple Threads，单指令多线程）—— NVIDIA GPU 的并行模型：一条指令同时驱动 32 个线程处理不同数据。
DSA（Domain-Specific Architecture，领域专用架构）—— 为特定领域定制的芯片架构，华为昇腾属于此类。
SM（Streaming Multiprocessor，流式多处理器）—— NVIDIA GPU 的基本计算单元，一块 H100 有 132 个。昇腾的对应物叫 AI Core。
MTE（Memory Transfer Engine，存储转换引擎）—— 昇腾上专门负责各级存储之间搬运的独立硬件单元。GPU 上没有对应的独立硬件，只有 cp.async 这类异步指令。
Cache vs Scratchpad（缓存 vs 便签存储）—— 片上存储的两种管理方式：Cache 由硬件自动填充，Scratchpad 由软件显式搬运。这是 GPU 和 NPU 最根本的分歧之一。
MFU（Model FLOPs Utilization，模型算力利用率）—— 模型必须完成的运算量 ÷ 硬件在同样时间内能提供的运算量，衡量一次训练"钱花得值不值"。

0.1 一个根本事实：算力涨得比带宽快

0.1.1 先算一笔账：从 V100 换到 H100，为什么没快 8 倍

不讲概念，先做一道算术题。任务是推理 Decode（逐 token 生成）阶段的一个矩阵向量乘：权重矩阵 4096 × 4096，FP16（2 字节），一次只算 1 个 token。

计算量 = 2 × 1 × 4096 × 4096 = 33.55 MFLOP
搬运量 = 权重 4096 × 4096 × 2 B = 33.55 MB      ← 输入输出各 8 KB，忽略

把这个算子分别放到 V100 和 H100 上，两笔账各算一遍：

V100 SXM2（2017） H100 SXM5（2022） 倍数
FP16 稠密算力 125 TFLOPS 989 TFLOPS 7.9 ×
HBM 带宽 900 GB/s 3350 GB/s 3.7 ×
算完这 33.55 MFLOP 要多久 33.55 M ÷ 125 T = 0.27 µs 33.55 M ÷ 989 T = 0.034 µs 7.9 ×
搬完这 33.55 MB 要多久 33.55 MB ÷ 900 GB/s = 37.3 µs 33.55 MB ÷ 3350 GB/s = 10.0 µs 3.7 ×
实际耗时 ≈ max(两者) 37.3 µs 10.0 µs 3.7 ×
算力利用率 = 算 ÷ 实际 0.27 ÷ 37.3 = 0.72% 0.034 ÷ 10.0 = 0.34% 掉了一半

买了一张算力 7.9 倍的卡，这个算子只快了 3.7 倍，而且算力利用率还从 0.72% 掉到了 0.34%。

再看同一代硬件上的另一个算子作对照——4096×4096×4096 的大方阵乘法（FP16）：

计算量 = 2 × 4096³ = 137.44 GFLOP
搬运量 = 3 × 4096² × 2 B = 100.66 MB     ← 读 A、读 B、写 C 各一遍

V100：算 137.44 G ÷ 125 T = 1100 µs ；搬 100.66 MB ÷ 900 GB/s = 112 µs → 耗时 1100 µs
H100：算 137.44 G ÷ 989 T =  139 µs ；搬 100.66 MB ÷ 3350 GB/s = 30 µs → 耗时  139 µs

1100 ÷ 139 = 7.9 倍   ← 算力那 7.9 倍，一分不少地吃到了

★ 同一次换卡，两个算子拿到的红利差一倍。 差别不在算子写得好不好，而在它每搬 1 字节能算几次：Decode 那个算子是 1 次，大方阵那个是 1365 次。这个比值就叫算术强度，它决定了你这张卡的两个峰值——算力和带宽——哪一个会先见底。整个系列所有技术，都是在把这个比值往上推，或者把分母（字节数）往下压。

0.1.2 跨代际数字表：比值是怎么一步步恶化的

把五代硬件的两个峰值摆在一起（NVIDIA 侧 ✅ 均为厂商公开规格；屋脊点 = 算力 ÷ 带宽，可自行验算）：

硬件 发布 BF16/FP16 稠密算力 HBM 带宽 相对 V100 算力 相对 V100 带宽 屋脊点
V100 SXM2 (16 GB) 2017 125 TFLOPS 900 GB/s 1.0 × 1.0 × 139 FLOP/Byte
A100 SXM (80 GB) 2020 312 TFLOPS 2039 GB/s 2.5 × 2.3 × 153 FLOP/Byte
H100 SXM5 (80 GB) 2022 989 TFLOPS 3350 GB/s 7.9 × 3.7 × 295 FLOP/Byte
H200 SXM (141 GB) 2024 989 TFLOPS 4800 GB/s 7.9 × 5.3 × 206 FLOP/Byte
B200 (192 GB) 2025 ⚠️ ~2250 TFLOPS ~8000 GB/s ~18 × ~8.9 × ⚠️ ~281 FLOP/Byte
昇腾 910B3 2023 ⚠️ ~320 TFLOPS ⚠️ ~1.6 TB/s — — ⚠️ ~200 FLOP/Byte

V100 到 H100 这五年，算力涨了 7.9 倍，带宽只涨了 3.7 倍，屋脊点从 139 抬到 295。

屋脊点变大的物理含义只有一句话：同一个算子，一行代码都不改，在新卡上更容易变成带宽受限。你买的是算力，吃到的是带宽。

屋脊点走势（数字越大，越难喂饱算力）

  V100  139  ████████████
  A100  153  █████████████
  H100  295  █████████████████████████
  H200  206  █████████████████
  B200  281  ████████████████████████
  910B3 200  █████████████████  (⚠️ 基于推断数字)

⚠️ 趋势不是单调的，也不该被讲成"末日论"。 H200 靠 HBM3e 把带宽拉到 4.8 TB/s、屋脊点回落到 206，B200 又用更高的算力把它推回 281。快慢交替，但"算力和带宽赛跑、且带宽长期落后"这个结构性矛盾一直在。这个系列讲的所有技术，在屋脊点 139 的卡上和 295 的卡上都成立，只是收益大小不同。

⚠️ B200 那一行标 ⚠️ 的原因：Blackwell 的规格在发布后经历过修订，且官方口径里稀疏值和稠密值、单 die 和双 die 混着报。本系列一律用稠密值，和 附-速查表 §A 一致。昇腾那两行标 ⚠️ 的原因见本章 §0.7。

0.1.3 算术强度：一把尺子，一条分界线

算术强度 I = 总浮点运算次数 (FLOP) ÷ 从 HBM 搬运的总字节数 (Byte)

I > 屋脊点  →  Compute Bound（算力受限），硬件在满负荷算，带宽有富余
I < 屋脊点  →  Memory Bound（带宽受限），算力在空转等数据

把大模型里几个真实算子的 I 算出来，摆到同一条数轴上（全部按 H100，详细推导见 02 章 §2.3）：

算术强度数轴（对数刻度）

  0.125      1        2                62      124        295         1365
    A        B        C                 D       F        屋脊点         E
    |        |        |                 |       |          |             |
    +--------+--------+-----------------+-------+----------+-------------+
    <--------------- Memory Bound（带宽受限）------------->  <- Compute ->
点 算子 精度 I 屋顶线上界 占对应峰值
A 逐元素乘 y = x * 2 FP32 0.125 0.42 TFLOPS 0.63%（峰值 67）
B SiLU 激活 / Decode 的矩阵向量乘 BF16 1.0 3.35 TFLOPS 0.34%（峰值 989）
C LayerNorm BF16 2.0 6.7 TFLOPS 0.68%
D 训练 GEMM，M = 64 BF16 62 208 TFLOPS 21%
F FlashAttention-2 前向 BF16 ⚠️ 124 415 TFLOPS 42%
E 大方阵 GEMM 4096³ BF16 1365 989 TFLOPS（屋顶） 100%（理论）

看这张表最该注意的一件事：六个算子里有五个在屋脊点左边，而它们占了大模型训练和推理 90% 的时间。 大方阵 GEMM 那一个 Compute Bound 的点，是整个列表里的少数派。

★ 所以这个系列从头到尾只在做一件事：想办法让数据少搬，或者搬的时候别让算力闲着。 后面所有的技术——分块、融合、双缓冲、量化、FlashAttention、PagedAttention、投机解码——全都是这一件事的不同侧面。下一节把"这一件事"拆成四个手段。

0.2 四个通用手段

不管在什么硬件上，减少"搬运税"的办法就这么四种。这四个手段是平台无关的，变的只是实现方式。 下面每一个都配一个带数字的最小例子，说清它到底在省什么。

0.2.1 手段一：分块（Tiling）—— 省的是"同一份数据被搬进来的次数"

朴素的矩阵乘，每算一个输出元素，就把 A 的一整行和 B 的一整列从 HBM 读一遍。同一行 A 会被重复读 N 次。

不分块：
  C[0][0] ← 读 A 第 0 行 + B 第 0 列
  C[0][1] ← 又读 A 第 0 行 + B 第 1 列      ← A 第 0 行第二次进城
  C[0][2] ← 又读 A 第 0 行 + B 第 2 列      ← 第三次
   ...                                      ← 一共 N 次

分块（把 C 切成 128×128 的块，一个块负责 16384 个输出元素）：
  C 的 (0,0) 块 ← 读 A 的第 0 条横条（128 行）+ B 的第 0 条竖条（128 列）
                  搬进片上之后，这两条数据被这 16384 个输出元素共用
                  → 同一份数据只进城 1 次，在城里被用 128 次

把数字算出来（M = N = K = 1024，FP32 4 字节，H100：HBM 3.35 TB/s，FP32 峰值 67 TFLOPS）：

从 HBM 读 A+B HBM 搬运时间 纯计算时间 实际耗时 ≈ max 算力利用率
不分块 1024³ × 2 × 4 B = 8590 MB 2564 µs 32 µs 2564 µs 1.25%
128×128 分块 64 块 × 1.049 MB = 67.1 MB 20 µs 32 µs 32 µs 100%（理论）

HBM 流量降到 1/128，瓶颈从"访存把计算卡死 80 倍"翻成了"计算把访存盖住"。 那个 128 不是巧合，它就是你选的块边长——完整推导见 03 章 §3.3。

★ 分块省的是次数，不是总量。 要读的原始数据（A 和 B 各 4 MB）一个字节都没少，省掉的是"同一份数据被重复搬进来"的那 8523 MB。代价是你得自己算块开多大、怎么切、边界怎么处理——这是四个手段里收益最大、也最费脑子的一个。

在哪一章展开：GEMM 的三级分块（03 章）、FlashAttention 的 K/V 分块（04 章）、PagedAttention 对显存的分块（09 章）、昇腾的 Host 侧 Tiling 函数（13 章 §13.5）。

0.2.2 手段二：融合（Fusion）—— 省的是"中间结果往 HBM 跑的那一趟"

Transformer 每层都有这样一段：n = layer_norm(x) → g = gelu(n) → y = x + g。三个算子分开跑，n 和 g 这两个中间张量会各自完整地写进 HBM、再完整地读回来。

融合前：3 个 kernel，中间结果两次落地

  HBM: x ──读 T──→ [LayerNorm] ──写 T──→ HBM: n
                                            │ 读 T   ← 这一读一写纯属浪费
  HBM: n ──读 T──→ [GELU]      ──写 T──→ HBM: g
                                            │ 读 T   ← 同上
  HBM: g + x ──读 2T──→ [残差加] ──写 T──→ HBM: y

融合后：1 个 kernel，中间结果全程待在寄存器里

  HBM: x ──读 T──→ [LayerNorm → GELU → 残差加] ──写 T──→ HBM: y
                    n 和 g 一个字节都没进过 HBM
                    x 读进来后也一直留着，残差加直接取用，不必二次读

把字节数算出来（token 数 8192、隐藏维度 4096、BF16，一个张量 T = 64 MiB）：

kernel 数 HBM 读 HBM 写 合计 时间（÷ 3.35 TB/s）
融合前 3 5 T 2 T 7 T = 448 MiB 140.2 µs
融合后 1 1 T 1 T 2 T = 128 MiB 40.1 µs

加速 7 ÷ 2 = 3.5 倍，而浮点运算量一个 FLOP 都没变。 完整推导见 05 章 §5.2。

★ 注意这个 3.5 倍和张量多大无关。 换成别的形状、别的精度，7 T ÷ 2 T 的比值不变。决定加速比的是链的结构（几个算子、每个读写几份），张量大小只决定省下来的绝对时间是多少微秒。

⚠️ 融合的收益依赖于一个前提：中间结果真的能留在片上。 这个前提在 GPU 上基本成立，在昇腾 910B 上因为 Cube（矩阵单元）和 Vector（向量单元）被拆成了两个独立的核、之间必须绕一趟全局内存，并不总是成立（12 章 §12.2.3）。同一个手段，在两个平台上收益来源不同——这正是本系列要讲清楚的那类差异。

在哪一章展开：三种融合模式与判据（05 章）、FlashAttention 把整个注意力融成一个 kernel（04 章）、昇腾的 CV 流水并行（13 章、14 章）。

0.2.3 手段三：流水重叠（Pipelining）—— 省的是"等待的时间"，一个字节都不少搬

前两个手段都在减少字节。这一个不减字节，它只是让搬运和计算同时发生。

单缓冲（一块片上缓冲区：搬完才能算，算完才能覆盖）

  时间 →
  搬运单元  [搬 t0]        [搬 t1]        [搬 t2]
  计算单元         [算 t0]        [算 t1]        [算 t2]
            └ 算的时候搬运单元全空，搬的时候计算单元全空
            每轮 = T搬 + T算

双缓冲（两块缓冲区 buf0 / buf1 交替：搬下一块的同时算这一块）

  时间 →
  搬运单元  [搬 t0][搬 t1][搬 t2][搬 t3][搬 t4]
  计算单元         [算 t0][算 t1][算 t2][算 t3]
            └ 两行同时在动。预热一轮之后，每轮 = max(T搬, T算)

把周期数算出来（沿用 03 章 §3.5 的配置：块 128×128×8，FP32，K = 1024 所以要循环 128 轮）：

T搬 = 570 周期（8 KB ÷ 单 SM 分到的带宽，并受 HBM 延迟约束）
T算 = 1024 周期（262144 FLOP ÷ 单 SM 每周期 256 FLOP）

单缓冲：每轮 570 + 1024 = 1594 周期，总计 570 + 128 × 1594 ≈ 204,600 周期
双缓冲：每轮 max(570, 1024) = 1024 周期，总计 570 + 128 × 1024 ≈ 131,600 周期

204600 ÷ 131600 = 1.55 倍

算法没改、字节没少，快了 1.55 倍，省下来的正好是那 128 轮 × 570 周期的干等。

★ 这个手段的收益有一个硬上限：2 倍，而且只在 T搬 恰好等于 T算 时取到。 因为 (T搬 + T算) ÷ max(T搬, T算) ≤ 2。上例是 1594 ÷ 1024 = 1.56，已经接近这个配置能拿到的全部。如果搬运本身就远大于计算（T搬 ≫ T算），重叠之后 HBM 依然满负荷，这条路走到头了——这时必须回去用分块、融合或降精度把字节数真的减下来。

⚠️ 前提是硬件上搬运和计算有各自独立的执行单元。GPU 上靠 cp.async 异步拷贝指令或 Hopper 的 TMA（Tensor Memory Accelerator，张量内存加速器）配合双缓冲实现；昇腾上靠 MTE 这个真正独立的硬件流水线实现（13 章 §13.4）。在 GPU 上这是一种优化技巧，在昇腾上这是基本写法——原因见本章 §0.3。

0.2.4 手段四：降精度（Quantization）—— 省的是"每个数占的字节"

最直白的一个：数还是那么多个，只是每个占的位数变少了。

以 LLaMA-3-8B（80.3 亿参数）的 Decode 为例。Decode 每生成 1 个 token，都必须把整个模型的权重从 HBM 完整读一遍，所以每步耗时的下界就是"读权重的时间"：

权重格式 每权重位数 权重总大小 每 token 下界（÷ 3.35 TB/s） 吞吐上界 相对 BF16
BF16 16 16.06 GB 4.79 ms 209 token/s 1.00 ×
INT8 8 8.03 GB 2.40 ms 417 token/s 2.00 ×
INT4（group = 128） 4.156 4.17 GB 1.25 ms 803 token/s 3.85 ×

★ 注意 INT4 是 3.85 倍而不是 4 倍。 差的那 0.15 是 scale（缩放系数）占的空间：每 128 个权重要额外存一个 FP16 的 scale 和一个 zero-point，摊下来每个权重实际是 4.156 位而不是 4 位。这笔账在 06 章 §6.2.6 里算得很细。

⚠️ 这里有一个流传极广的错误推论，必须在总纲就掐掉：「INT8 Tensor Core 的算力是 BF16 的 2 倍，所以 W8A8 量化能快 2 倍」。这个推论只在 Compute Bound 的场景（大 batch 训练、长序列 Prefill）下成立。在 Decode 这种 Memory Bound 的场景里，算力根本没在用，那 2 倍算力是白送的，一分钱都兑现不了——上表里的 2 倍，100% 来自"字节少了一半"，和 INT8 算得快不快毫无关系。同一个量化动作，收益来源随场景完全不同，详见 06 章 §6.1.2。

在哪一章展开：INT8 / FP8 / GPTQ / AWQ 与精度取舍（06 章）、KV Cache 量化（06 章 §6.8.5、09 章）、昇腾没有 FP8 时怎么办（06 章 §6.10）。

0.2.5 四个手段并排：它们动的是同一张账单的不同行

一个算子的耗时可以写成这样一张账单，四个手段各改其中一项：

耗时 ≈ max( 搬运时间 , 计算时间 ) + 等待时间

  搬运时间 = (数据份数 × 每份被搬的次数 × 每个数的字节数) ÷ 带宽
              ↑ 融合动这里      ↑ 分块动这里      ↑ 降精度动这里

  等待时间 = 搬运和计算没能重叠上的那部分
              ↑ 流水重叠动这里
手段 动账单的哪一项 本节例子的收益 收益上限 GPU 上怎么做 昇腾上怎么做 章节
分块 每份数据被搬的次数 128 × 受片上容量限制，可以很大 共享内存三级分块；FA 的 K/V 分块 L1/L0/UB 分块 + Host 侧 Tiling 函数 03 04 · 13
融合 中间结果的份数 3.5 × = 链上字节数的比值 手写融合 kernel；torch.compile cann-ops-adv 现成算子；CV 流水并行 05 · 13 14
流水重叠 等待时间 1.55 × 严格 < 2 × cp.async / TMA + 双缓冲；Warp Specialization BUFFER_NUM=2 + MTE 独立流水 03 §3.5 · 13 §13.4
降精度 每个数的字节数 2.0 × / 3.85 × = 位宽的比值 FP8 / INT8 / GPTQ / AWQ INT8 W8A8（无 FP8）；HiF8 06
（通信层） 卡与卡之间的传输 — — NCCL + 计算通信重叠；DeepEP HCCL + 通算融合；超节点 08

★ 四个手段里只有"流水重叠"有一个硬性的 2 倍天花板，另外三个的收益取决于你能把字节压到多少。所以排优化顺序时，先用前面三个把字节数压下去，最后才用流水重叠把残留的等待抹平。

0.2.6 读法建议：遇到新技术，先归类

绝大多数"新算子"都是这四种手段的重新组合。先问它属于哪一类，再看它的具体实现：

技术 拆成四个手段
FlashAttention 分块（K/V 切块）+ 融合（N×N 的分数矩阵从不落 HBM）+ 重计算（反向时重算而不是存）→ 04 章 §4.3.3
PagedAttention 分块，但切的是显存而不是计算——目标是消除碎片，不是提高算术强度 → 09 章 §9.3
连续批处理 提高算术强度的第五条路：把更多 token 塞进同一次权重读取 → 09 章 §9.4.2
投机解码 把 Memory Bound 的逐 token Decode，换成 Compute Bound 的批量验证 → 09 章 §9.6
CUDA Graph 都不属于——它治的是 Host Bound，不在这四个手段的射程内 → 05 章 §5.5

最后一行值得停一下：有一整类性能问题，四个手段一个都治不了。那就是下一节要说的诊断漏斗里的第一步。

0.3 两种硬件哲学：延迟怎么掩盖

这是理解 GPU 和 NPU 一切差异的总开关。

0.3.1 共同的问题：500 个周期的空档

两类硬件面对的是同一个物理事实：从 HBM 取一次数据要几百个时钟周期，而一次浮点运算只要 1 个周期。

⚠️ H100 上的实测量级（随代际和缓存命中情况浮动，见 01 章 §1.3）：

  寄存器      ~1 周期
  共享内存   ~25 周期
  L2 缓存   ~250 周期
  HBM 显存  ~500 周期      ← 就是这个数字，逼出了两种完全不同的架构

500 个周期里，如果计算单元干等着，就是 500 个周期的浪费。怎么把这 500 个周期填满，是两类硬件分岔的起点。

0.3.2 同一个算子，两种执行方式

拿一个最简单的算子做对照：把 4 块数据从 HBM 搬进来、各做一点计算、再写回去。

━━━ SIMT（NVIDIA GPU）：超额订阅 —— 多找几个人排队，总有一个能上 ━━━

  一个 SM 上同时挂着最多 64 个 Warp（每个 Warp = 32 个线程）。
  哪个 Warp 在等内存，硬件调度器立刻切到下一个就绪的 Warp。

  时间 →     0        1        2      ...     500      520      540
  Warp 0   [发读请求]···························等···[算 20]
  Warp 1      [发读请求]························等········[算 20]
  Warp 2         [发读请求]·····················等·············[算 20]
   ...
  Warp 24           [发读请求]··················等
  ─────────────────────────────────────────────────────────────────
  SM 在干嘛   发   发   发  ...（24 个 Warp 陆续发完）...   算 算 算 算

  ★ 一个 Warp 等的那 500 个周期，被其他 23 个 Warp 的工作填满了。
    需要多少个 Warp 才填得满？500 ÷ 20 = 25 个。这就是 occupancy 的来历。

  你写的代码：只描述"一个线程怎么处理一个元素"。
  谁上场、什么时候切：硬件调度器决定，代码里看不到、也控制不了。


━━━ DSA（华为昇腾）：流水重叠 —— 一个人不换，但把三条流水线同时排满 ━━━

  一个 AI Core 里，搬入（MTE2）、计算（Vector/Cube）、搬出（MTE3）
  是三套真正独立的硬件单元，可以同时工作。

  时间 →   ├─ t0 ─┼─ t1 ─┼─ t2 ─┼─ t3 ─┼─ t4 ─→
  MTE2     [搬入 0][搬入 1][搬入 2][搬入 3]
  Vector           [计算 0][计算 1][计算 2][计算 3]
  MTE3                    [搬出 0][搬出 1][搬出 2]

  ★ 三行同时在动 = 流水排满了。任何一行出现空格，就是一个"气泡"。
    没有"切换到别的任务"这回事，只有"把自己的流水排紧"。

  你写的代码：显式写 DataCopy（搬入）→ Compute → DataCopy（搬出），
              并显式开 BUFFER_NUM = 2，好让三行能在时间上错开。

把这两张图叠在一起看，差别只有一句话：GPU 用"换人"填空档，昇腾用"同一个人同时做三件事"填空档。

0.3.3 由此推出的两串后果

SIMT 由此推出
  ├── 需要 occupancy（占用率）这个概念 —— 手上得有足够多的 Warp 可换
  ├── 切换由硬件负责，程序员写"一个线程"的代码就行
  ├── 片上存储可以做成 Cache（硬件自动填充），不必显式搬
  ├── 编译器能替你做很多事 → Triton 这种"七行写一个算子"的语言可行
  └── 代价：巨大的寄存器文件 + 调度硬件，吃芯片面积和功耗

DSA 由此推出
  ├── 没有 occupancy 这个概念 —— 根本不存在"换一个 Warp 上"这件事
  ├── 流水靠软件排，程序员必须显式写每一次搬运
  ├── 片上存储是 Scratchpad（便签存储，软件显式搬运），没有自动填充
  ├── 编译器帮不上忙 → Ascend C 代码量必然大
  └── 代价：软件复杂度，以及"忘了开双缓冲性能直接腰斩"

0.3.4 这一张图解释了后面所有的"为什么"

现象 根因 在哪一章
为什么 GPU 有 occupancy、bank conflict，昇腾完全没有这两个概念 超额订阅 vs 流水重叠 01 §1.5–1.6 vs 12 §12.1
为什么昇腾要手写 DataCopy，GPU 上一句访存就完事 Scratchpad vs Cache 12 §12.3
为什么 Triton 七行能写完的算子，Ascend C 要七十行 编译器能不能替你排流水 07 vs 13 §13.3
为什么昇腾上双缓冲是"基本功"而不是"优化项" 流水重叠是它唯一的延迟掩盖手段 13 §13.4
为什么昇腾多一类 GPU 上没有的 MTE Bound 瓶颈 搬运有独立硬件单元，它自己会先成为瓶颈 12 §12.6
为什么 GPU 上的"融合"在昇腾上有时候不省事 Cube 和 Vector 是两个独立的核，中间结果得绕全局内存 12 §12.2.3

★ 不要把这理解成"谁更好"。 超额订阅的代价是大量寄存器和调度硬件（面积、功耗）；流水重叠的代价是软件复杂度（每一次搬运都得你自己写）。两者是在不同约束下的合理选择。真正要记住的是：换平台时作废的不是某几个 API，而是"延迟怎么被掩盖"这个底层假设——你脑子里那张图要整个重画。

0.4.3 为什么第 ① 步不能跳过：把账算出来

第 ① 步最容易被跳过，也最容易中招。 用一个具体的数字说明代价。

假设 nsys 显示：所有 kernel 耗时之和只占 wall time 的 60%，另外 40% 是加速卡在空转等命令。现在有两个方案：

方案 做了什么 新的 wall time 整体加速比 工作量
A · 只优化 kernel 把所有 kernel 都提速 1.5 倍 0.60 ÷ 1.5 + 0.40 = 0.80 1.25 × 通常按周算
B · 只治空转 开 CUDA Graph，把 40% 空转压掉四分之三 0.60 + 0.10 = 0.70 1.43 × 通常按天算
A + B 两件都做 0.40 + 0.10 = 0.50 2.00 × —
理论上限（只做 A） 把 kernel 时间优化到 0 0 + 0.40 = 0.40 2.50 × 不可能达到

花几天做 B，比花几周做 A 收益还大。 而且注意最后一行：只要那 40% 的空转还在，无论你把 kernel 优化到多完美，整体加速比都不可能超过 2.5 倍。先看整体，再看单个，这个顺序不能颠倒。

⚠️ Host Bound 的判据经常被算错，这里说清楚。 一个 kernel 的启动延迟是 3–10 µs（从 CPU 调用到 GPU 第一个线程开跑），但这不是每个 kernel 都要串行付一遍的成本——连续启动时，CPU 发第 2 个 kernel 和 GPU 执行第 1 个是同时进行的，启动是流水化的。所以正确的判据是：

```
每步耗时 ≈ max( kernel 数 × 单个下发成本(⚠️ 约 2 µs) , 加速卡执行总时间 )

CPU 侧 > GPU 侧 → Host Bound，GPU 在饿着等命令，该开 CUDA Graph
CPU 侧 ≤ GPU 侧 → 开了也白开，收益是零
```

把启动开销按 kernel 数简单相加，会把 Host Bound 严重高估。 详见 01 章 §1.8.2 和 05 章 §5.5.1。

★ 屋顶线模型（第 ③ 步）是跨平台通用的，只是屋脊点要换成对应硬件的（昇腾 910B3 ⚠️ ≈ 200）。但它是一个"kernel 内部"的模型：它看不见 kernel 之间的空隙（第 ① 步），也看不见通信（第 ② 步），还看不见昇腾那类 MTE Bound（第 ④ 步）。漏斗的存在，就是为了把屋顶线看不见的三类问题先筛掉。 屋顶线自己的三个盲区见 02 章 §2.5。

0.4.4 把漏斗完整跑一遍

⚠️ 本节的耗时和百分比是为演示流程构造的自洽数字，不是某次真实测量。但每一步的算术都是真的，可以自己验算。

现象：8 卡 H100 训练一个 13B 稠密模型，整机吞吐 20000 tokens/s。先算 MFU（口径见 02 章 §2.6）：

分子 = 20000 × 6 × 13 × 10⁹ = 1.56 × 10¹⁵ FLOP/s
分母 = 8 × 989 × 10¹²       = 7.912 × 10¹⁵ FLOP/s
MFU = 1.56 ÷ 7.912 = 19.7%      ← 低于 30%，一定有系统性问题（02 §2.6.4）

第 ① 步 · 加速卡在不在干活

nsys stats：所有 kernel 耗时之和 ÷ wall time = 71%   → 29% 在空转
时间线上：top-10 kernel 里有 6 个是几微秒的逐元素小算子

→ 命中第 ① 步。先用 torch.compile 把这些小算子融掉（05 章）。
   顺带一个副作用：融合同时也减少了 HBM 流量，两头都赚。

复测：20000 → 26000 tokens/s，MFU = 26000 × 6 × 13e9 ÷ 7.912e15 = 25.6%

第 ② 步 · 是不是通信

nccl 开头的算子占 7%，且在时间线上和计算 kernel 重叠良好
→ 不是瓶颈，跳过。（单机 8 卡走 NVLink，本来就不容易在这里出问题。）

第 ③ 步 · 算力还是带宽

主力 GEMM：M = 2048（每卡 micro-batch 的 token 数），K = N = 5120

  FLOP = 2 × 2048 × 5120 × 5120 = 1.074 × 10¹¹
  Byte = 2 × (2048×5120 + 5120×5120 + 2048×5120) = 9.44 × 10⁷
  I    = 1.074e11 ÷ 9.44e7 = 1138 FLOP/Byte    ≫ 屋脊点 295

→ Compute Bound。ncu 验证：Compute Throughput 68%、DRAM 24%，对得上。
   68% 对一个真实训练 GEMM 来说已经不差，这里没有大空间了。

第 ④ 步 · 那剩下的差距在哪

MFU 25.6%，但训练开了全量重计算（Activation Recomputation，梯度检查点）。
全量重计算意味着硬件实际执行的是 8N 而不是 6N（多一遍前向）：

  HFU = MFU × 8 ÷ 6 = 25.6% × 1.333 = 34.1%

→ 8.5 个百分点的缺口，是重计算烧掉的，不是 kernel 写得差（02 §2.6.3）。
   下一步不该继续调 kernel，而该问："显存够不够关掉一部分重计算？"

★ 这个走查的结论是"问题不在算子层"，而这恰恰是漏斗最大的价值。 如果一上来就抓着主力 GEMM 用 ncu 猛看，会在一个 Compute Throughput 已经 68% 的 kernel 上耗掉两周，而真正的 6000 tokens/s 在第 ① 步、剩下的空间在第 ④ 步。先定位在哪一层，再决定花力气。

0.7 关于数字的可信度约定

NVIDIA 侧的规格有完整白皮书，本系列直接引用，统一用稠密峰值（不是稀疏），并和 附-速查表 §A 保持一致。

华为昇腾侧没有公开的完整数据手册，公开数字彼此矛盾的地方很多（同一款 910B 的 FP16 算力，公开资料里有 256 和 320 两种说法；HBM 带宽从 400 GB/s 到 2.4 TB/s 都有人写）。凡涉及昇腾规格，本系列标注：

  • ✅ 披露 —— 华为官方产品页 / CANN 官方文档明确写出
  • ⚠️ 推断 —— 第三方分析、芯片拆解、学术论文或社区实测，仅供量级参考

另外三类数字也一律标 ⚠️，请勿当作规格引用：

类型 举例 为什么要标
实测量级 "HBM 延迟约 500 周期"、"有效带宽通常是峰值的 80–90%" 随代际、时钟、功耗墙、缓存命中浮动
推算值 "单 SM 每周期约 4096 FLOP"、"DeepSeek-V3 的 MFU 约 34.6%" 由几个官方数字反推，误差会叠加
演示构造值 本章 §0.4.4、02 章 §2.7.4 的走查 为了让流程自洽而编的，算术是真的、数字不是

任何要写进方案、用于容量规划的数字，请在自己的卡上实测（NVIDIA 侧用 nsys / ncu；昇腾侧用 npu-smi info + CANN 的 platform_config/*.ini，方法见 12 章 §12.4.3），不要引用本系列。

0.8 本章小结

一个根本事实

V100（2017） H100（2022） 倍数
BF16/FP16 稠密算力 125 TFLOPS 989 TFLOPS 7.9 ×
HBM 带宽 900 GB/s 3350 GB/s 3.7 ×
屋脊点 139 FLOP/Byte 295 FLOP/Byte 2.1 ×

→ 同一个算子，一行不改，在新卡上更容易变成带宽受限。数据搬运是根本瓶颈，整个系列都在绕这一件事。

四个通用手段（平台无关，变的只是实现方式）

手段 省的是 最小例子 收益 上限
分块 Tiling 同一份数据被搬进来的次数 1024³ GEMM：8590 MB → 67.1 MB 128 × 受片上容量限制
融合 Fusion 中间结果的份数 LayerNorm→GELU→残差：7T → 2T 3.5 × = 字节数的比值
流水重叠 等待时间（字节一个不少） 单缓冲 1594 → 双缓冲 1024 周期/轮 1.55 × 严格 < 2 ×
降精度 每个数的字节数 8B 模型 Decode：16.06 → 8.03 GB 2.0 × = 位宽的比值

→ 遇到任何新技术，先问它属于这四类中的哪一类。绝大多数"新算子"都是这四种的重新组合。

两种硬件哲学（解释后面一切差异的总开关）

共同的问题：从 HBM 取一次数据要 ⚠️ 约 500 个周期，计算单元不能干等

  SIMT（GPU）   超额订阅：挂 64 个 Warp，谁等内存就换谁上
                → 有 occupancy / Cache 自动填充 / 编译器能帮忙（Triton 可行）

  DSA（昇腾）   流水重叠：搬入、计算、搬出三条独立硬件流水线同时跑满
                → 无 occupancy / Scratchpad 手动搬 / 双缓冲是基本功不是优化

诊断漏斗（从外往里剥，别跳第一步）

步 问题 判据 解法
① 加速卡在空转吗 kernel 总时长 ÷ wall time < 60% CUDA Graph / 融合 / 图模式
② 是通信吗 通信占比 > 20% 且未重叠 计算通信重叠、改并行策略
③ 带宽还是算力 算术强度 I 对比屋脊点；ncu 四象限 四个手段挑一个
④ 平台特有 算力带宽都 < 40% Stall Reason / 指令流水图

→ 第 ① 步跳过的代价：如果 40% 的时间在空转，无论 kernel 优化到多完美，整体加速比也超不过 2.5 倍。

自测三题（答案在对应小节，建议先自己算）

  1. 某张卡的 BF16 稠密算力是 400 TFLOPS、HBM 带宽 2.0 TB/s，INT8 稠密算力 800 TOPS。(a) 它的 BF16 屋脊点是多少？(b) 一个算术强度 I = 8 的算子在这张卡上的理论性能上界是多少 TFLOPS，占峰值百分之多少？(c) 把这个算子的权重从 BF16 换成 INT8，理论耗时变成原来的几分之几？它在屋顶线图上的相对位置变了吗？
  2. 下面四件事各属于四个通用手段中的哪一个，各省的是账单上的哪一项？(a) 把 KV Cache 从 FP16 存成 FP8；(b) 把 RMSNorm 融进后面那个 GEMM 的 Prologue（前置段）；(c) FlashAttention 不把 N×N 的注意力分数矩阵写回 HBM；(d) 用 cp.async 在算第 k 块的同时把第 k+1 块搬进来。
  3. 某 8 卡训练，nsys 显示所有 kernel 耗时之和只占 wall time 的 55%，其中最耗时的单个 kernel 占 wall time 的 20%。你手上有两个方案：(A) 花两周把那个最耗时的 kernel 优化到快 1.5 倍；(B) 花一天开 CUDA Graph，把空转时间压掉一半。分别算出两者的整体加速比，说明该先做哪个。

参考答案

  1. (a) 屋脊点 = 400 × 10¹² ÷ 2.0 × 10¹² = 200 FLOP/Byte。(b) 上界 P = 带宽 × I = 2000 GB/s × 8 FLOP/Byte = 16 TFLOPS，占峰值 16 ÷ 400 = 4%——深陷 Memory Bound。(c) 字节数减半，而耗时 = 字节数 ÷ 带宽，所以耗时变成原来的 1/2。但相对位置没变：I 从 8 翻到 16，INT8 的屋脊点也从 200 翻到 800 ÷ 2.0 = 400，I ÷ 屋脊点 前后都是 0.04。收益 100% 来自字节变少，和 INT8 算得快没有关系。 参见 §0.1.3、§0.2.4。
  2. (a) 降精度，省的是"每个数的字节数"——KV Cache 的读取量减半。(b) 融合，省的是"中间结果的份数"——RMSNorm 的输出不再写进 HBM 又读回来，省掉一次完整的往返（一写一读）。(c) 融合 + 分块两者都是：中间结果不落 HBM 是融合，把 K/V 切成块让 N×N 的分数矩阵从来没有完整存在过是分块——这也是为什么 FlashAttention 的收益比单纯融合大得多。(d) 流水重叠，省的是"等待时间"，搬运的字节数一个都没少。参见 §0.2.1–§0.2.5。
  3. 设 wall time = 1.0，kernel 合计 0.55，空转 0.45。方案 A：那个 kernel 从 0.20 降到 0.20 ÷ 1.5 = 0.133，新 wall = 1.0 − 0.067 = 0.933，加速比 = 1 ÷ 0.933 = 1.07 倍。方案 B：空转从 0.45 降到 0.225，新 wall = 1.0 − 0.225 = 0.775，加速比 = 1 ÷ 0.775 = 1.29 倍。B 的收益是 A 的四倍，工作量却是十四分之一，必须先做 B。 这正是漏斗第 ① 步要放在最前面的原因。参见 §0.4.3。
