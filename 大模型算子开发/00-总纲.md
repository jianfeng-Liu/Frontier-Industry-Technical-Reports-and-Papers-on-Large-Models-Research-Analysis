# 00 · 总纲：所有算子优化都在解同一个问题

> **前置**：无。这是全系列的入口，建议在读任何一章之前先读完。
> **目标**：给你一个平台无关的骨架——算子优化到底在优化什么、有哪几种手段、两类硬件为什么长得不一样。有了这个骨架，后面每一章都是在往上挂具体技术。

---

**本章关键词**

**算子**（Operator / Kernel）—— 在加速卡上执行的一个计算单元，如矩阵乘、Softmax、LayerNorm。PyTorch 里一行 `torch.matmul` 对应底层一个或多个算子。
**带宽墙**（Memory Wall）—— 算力增长长期快于内存带宽增长，导致越来越多的计算被"喂数据"的速度卡住。
**算术强度**（Arithmetic Intensity）—— 每搬运 1 字节数据能做多少次浮点运算，单位 FLOP/Byte。判断算子瓶颈的核心指标。
**屋脊点**（Ridge Point）—— 屋顶线模型上算力与带宽两条限制线的交点，是"算力受限"和"带宽受限"的分界算术强度。
**SIMT**（Single Instruction Multiple Threads，单指令多线程）—— NVIDIA GPU 的并行模型。
**DSA**（Domain Specific Architecture，特定域架构）—— 为特定领域定制的芯片架构，华为昇腾属于此类。
**片上存储**（On-chip Memory）—— SRAM 级的高速存储，容量以 KB 计，速度比片外 HBM 快两个数量级。
**Cache vs Scratchpad** —— 片上存储的两种管理方式：Cache 由硬件自动填充，Scratchpad 由软件显式搬运。这是 GPU 和 NPU 最根本的分歧之一。

## 0.1 一个根本事实：算力涨得比带宽快

整个系列要解决的问题，可以压缩成一张表（✅ 均为厂商公开规格）：

| | 发布 | FP16 算力 | HBM 带宽 | 屋脊点 |
|---|---|---|---|---|
| V100 | 2017 | 125 TFLOPS | 900 GB/s | 139 FLOP/Byte |
| A100 | 2020 | 312 TFLOPS | 2039 GB/s | 153 FLOP/Byte |
| H100 | 2022 | 989 TFLOPS | 3350 GB/s | **295 FLOP/Byte** |
| 昇腾 910B3 | 2023 | ~320 TFLOPS ⚠️ | ~1.6 TB/s ⚠️ | ~200 FLOP/Byte ⚠️ |

五年里**算力涨了 7.9 倍，带宽只涨了 3.7 倍**。

屋脊点从 139 涨到 295 的含义是：**同一个算子，什么都不改，在新卡上更容易变成带宽受限**。你买了算力 8 倍的卡，但如果算子的算术强度没跟上，实际只能吃到带宽那 3.7 倍的红利。

```
算术强度 I = FLOPs / Bytes

I > 屋脊点  →  Compute Bound（算力受限），硬件在满负荷算
I < 屋脊点  →  Memory Bound（带宽受限），算力在空转等数据

大模型里的真实情况：
  训练时的大 GEMM        I ≈ 数百～上千   → Compute Bound ✅
  推理 Decode 的矩阵向量乘 I ≈ 1          → Memory Bound ❌❌
  LayerNorm / Softmax    I ≈ 2～5         → Memory Bound ❌❌
  逐元素加法              I ≈ 0.25        → Memory Bound ❌❌
```

**所以这个系列从头到尾只在做一件事：想办法让数据少搬、或者搬的时候别让算力闲着。** 后面所有的技术——分块、融合、双缓冲、量化、FlashAttention、PagedAttention——全都是这一件事的不同侧面。

> ⚠️ 趋势不是单调的。H200（4.8 TB/s）和 B200 把带宽拉了上来，屋脊点回落。但"算力和带宽赛跑"这个结构性矛盾没有消失，只是快慢交替。

## 0.2 四个通用手段

不管在什么硬件上，减少"搬运税"的办法就这么四种。**这四个手段是平台无关的，变的只是实现方式**。

### 手段一：分块（Tiling）—— 用片上容量换搬运次数

```
朴素做法：每算一个结果元素，就去 HBM 取一次数据
          → 同一份数据被反复搬运 N 次

分块做法：把数据切成片上放得下的小块，搬一次，在片上反复用
          → 搬运次数降到 1/N

代价：要自己算块多大、怎么切、边界怎么处理
```

这是**收益最大、也最费脑子**的手段。GEMM 的三级分块（[03 章](03-GEMM深度剖析.md)）、FlashAttention 的 KV 分块（[04 章](04-FlashAttention全系.md)）、Ascend C 的 Tiling 函数（[13 章](13-AscendC编程.md)）本质是同一件事。

### 手段二：融合（Fusion）—— 消灭中间结果的落盘

```
不融合：  GEMM → 写回 HBM → 读出 → Bias → 写回 → 读出 → GeLU → 写回
          三个算子，六次 HBM 往返

融合：    GEMM → (片上) Bias → (片上) GeLU → 写回
          一个算子，两次 HBM 往返
```

细节见 [05 章](05-算子融合.md)。这里要先埋一个伏笔：**融合的收益依赖于"中间结果真的能留在片上"**。这个前提在 GPU 上基本成立，在昇腾 910B 上因为 Cube 和 Vector 是两个独立的核，**并不总是成立**（[12 章 §12.2.3](12-昇腾硬件基础.md)）。同一个手段，在两个平台上收益来源不同——这正是本系列要讲清楚的那类差异。

### 手段三：流水重叠（Pipelining）—— 让搬运和计算同时发生

```
串行：  [搬块0][算块0][搬块1][算块1][搬块2][算块2]
        总耗时 = (T搬 + T算) × N

流水：  [搬块0][搬块1][搬块2][搬块3]
              [算块0][算块1][算块2]
        总耗时 ≈ max(T搬, T算) × N
```

前提是硬件上**搬运和计算有独立的执行单元**。GPU 上靠 `cp.async` 异步拷贝指令加双缓冲，昇腾上靠独立的 MTE（存储转换引擎）硬件流水线。见 [03 章 §3.5](03-GEMM深度剖析.md) 和 [13 章 §13.4](13-AscendC编程.md)。

### 手段四：降精度（Quantization）—— 直接减少要搬的字节

```
BF16 → INT8：要搬的字节直接减半 → 带宽受限的算子直接快一倍
              同时 INT8 算力通常是 BF16 的 2 倍
```

见 [06 章](06-量化算子.md)。代价是精度，所以整章都在讲怎么在精度和速度之间取舍。

### 四个手段的全局索引

| 手段 | 本质 | GPU 上怎么做 | 昇腾上怎么做 | 章节 |
|---|---|---|---|---|
| **分块** | 片上容量换搬运次数 | 共享内存三级分块；FA 的 KV 分块 | L1/L0/UB 分块 + **Host 侧 Tiling 函数** | [03](03-GEMM深度剖析.md) [04](04-FlashAttention全系.md) · [13](13-AscendC编程.md) |
| **融合** | 消灭中间结果落盘 | 手写融合 kernel；`torch.compile` | `cann-ops-adv` 现成算子；**CV 流水并行** | [05](05-算子融合.md) · [13](13-AscendC编程.md) [14](14-GPU到NPU迁移实战.md) |
| **流水重叠** | 搬运与计算并行 | `cp.async` + 双缓冲；Warp Specialization | **`BUFFER_NUM=2` + MTE 独立流水** | [03](03-GEMM深度剖析.md) · [13](13-AscendC编程.md) |
| **降精度** | 减少字节数 | FP8 / INT8 / GPTQ / AWQ | **INT8 W8A8**（无 FP8）；HiF8 | [06](06-量化算子.md) |
| （通信层）| 减少或重叠传输 | NCCL + 计算通信重叠；DeepEP | HCCL + **通算融合**；超节点 | [08](08-MoE算子与通信.md) |

**读法建议**：遇到任何一个新技术，先问它属于这四类中的哪一类。绝大多数"新算子"都是这四种手段的重新组合。FlashAttention = 分块 + 融合 + 重计算；PagedAttention = 分块（针对显存碎片）；投机采样 = 把 Memory Bound 的 Decode 变成 Compute Bound 的批量验证。

## 0.3 两种硬件哲学：延迟怎么掩盖

这是理解 GPU 和 NPU 一切差异的总开关。

**共同的问题**：访存很慢。从 HBM 取一次数据要 ~400 个时钟周期，这期间计算单元干等着就是浪费。

**两种截然不同的答案**：

```
━━━ SIMT（NVIDIA GPU）：超额订阅 ━━━

  一个 SM 上同时挂 64 个 Warp。
  Warp A 等内存 → 硬件立刻切到 Warp B → B 也等 → 切到 C……
  只要挂的 Warp 足够多，总有一个能跑。

  ┌─ 由此推出 ─────────────────────────────────┐
  │ · 需要 occupancy（占用率）这个概念          │
  │ · 切换由硬件调度，程序员写单线程代码即可    │
  │ · 片上存储可以是 Cache（硬件自动填充）      │
  │ · 编译器能自动做很多优化 → Triton 可行      │
  └─────────────────────────────────────────────┘

━━━ DSA（华为昇腾）：流水重叠 ━━━

  搬运交给独立的硬件单元（MTE），它和计算单元真正并行。
  MTE 搬第 k+1 块的同时，Cube 在算第 k 块。
  没有"切换到别的任务"，只有"把自己的流水排满"。

  ┌─ 由此推出 ─────────────────────────────────┐
  │ · 没有 occupancy 这个概念                   │
  │ · 流水靠软件排，程序员必须显式写搬运        │
  │ · 片上存储是 Scratchpad（软件显式搬运）     │
  │ · 编译器帮不上忙 → Ascend C 代码量必然大    │
  └─────────────────────────────────────────────┘
```

**这一张图解释了后面所有的"为什么"**：

| 现象 | 根因 |
|---|---|
| 为什么 GPU 有 occupancy、bank conflict，昇腾没有 | 超额订阅 vs 流水重叠 |
| 为什么昇腾要手写 `DataCopy`，GPU 不用 | Scratchpad vs Cache |
| 为什么 Triton 七行能写完的算子，Ascend C 要七十行 | 编译器能不能替你排流水 |
| 为什么昇腾上双缓冲是"基本功"而非"优化" | 流水重叠是唯一的延迟掩盖手段 |
| 为什么昇腾多一类 MTE Bound 瓶颈 | 搬运有独立硬件单元，它自己会成为瓶颈 |

> **不要把这理解成"谁更好"**。超额订阅的代价是大量寄存器和调度硬件（面积、功耗）；流水重叠的代价是软件复杂度。两者是在不同约束下的合理选择。

## 0.4 性能诊断的通用漏斗

不管什么平台，定位性能问题都按这个顺序，**从外往里剥**：

```
① Host 下发够快吗？
   现象：Device 利用率低，但每个算子本身都不慢
   查：时间线视图里 kernel 之间有大片空隙
   解：CUDA Graph（GPU）/ ACLGraph 或图模式（昇腾）；合并小算子
   ↓ 排除后

② 通信是瓶颈吗？
   现象：多卡时慢，单卡时不慢
   查：通信算子耗时占比
   解：计算通信重叠、换通信算法、调并行策略  → 08 章
   ↓ 排除后

③ 算力受限还是带宽受限？
   查：算术强度 vs 屋脊点  → 屋顶线模型，02 章
   解：Memory Bound → 分块/融合/量化
       Compute Bound → 已接近上界，换更好的 kernel 或更低精度
   ↓ 定位后

④ 平台特有的瓶颈
   GPU：occupancy 不足、bank conflict、寄存器溢出   → 01/02 章
   昇腾：MTE Bound、CV 流水不均衡、核间负载不均     → 12/13 章
```

**第 ① 步最容易被跳过，也最容易中招**。尤其在推理 Decode 阶段：每步只算一个 token，算子多而小，Host 侧一个一个发，Device 算得比发得快。这类问题在昇腾上格外突出（[13 章 §13.8](13-AscendC编程.md)），但 GPU 上同样存在——这也是 CUDA Graph 存在的理由（[05 章 §5.5](05-算子融合.md)）。

屋顶线模型（第 ③ 步）是**跨平台通用的**，只是屋脊点要换成对应硬件的。昇腾多了第 ④ 步里的 MTE Bound，是因为它把搬运做成了独立硬件单元——屋顶线模型不覆盖这一类。

## 0.7 关于数字的可信度约定

NVIDIA 侧的规格有完整白皮书，本系列直接引用。

**华为昇腾侧没有公开的完整数据手册**，公开数字彼此矛盾的地方很多（同一款 910B 的 FP16 算力，公开资料里有 256 和 320 两种说法；HBM 带宽从 400 GB/s 到 2.4 TB/s 都有人写）。凡涉及昇腾规格，本系列标注：

- **✅ 披露** —— 华为官方产品页 / CANN 官方文档明确写出
- **⚠️ 推断** —— 第三方分析、芯片拆解、学术论文或社区实测，仅供量级参考

**任何要写进方案、用于容量规划的数字，请在自己的卡上实测**（`npu-smi info` + CANN 的 `platform_config/*.ini`，方法见 [12 章 §12.4.3](12-昇腾硬件基础.md)），不要引用本系列。

