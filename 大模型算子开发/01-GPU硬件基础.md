# 01 · GPU 硬件基础：在写第一行 CUDA 之前必须搞清楚的事

> **前置**：无。这是本系列的起点，后面所有章节都建立在这里。  
> **目标**：让你在脑子里有一张清晰的 GPU 硬件地图，知道"一个线程在哪里运行、数据在哪里存、为什么快、为什么会慢"。  
> **读法**：本章每个概念后面都跟一个带真实数字的小例子，例子里的算术都能自己验算。**建议拿纸笔跟着算一遍**，算过一遍的数字才会变成直觉。

---

**本章关键词**

**SM**（Streaming Multiprocessor，流式多处理器）—— GPU 的基本计算单元，一块 H100 有 132 个 SM。  
**SIMT**（Single Instruction Multiple Threads，单指令多线程）—— GPU 的执行模型：一条指令同时驱动 32 个线程处理不同数据。  
**Warp**（线程束）—— SM 内部同时执行的 32 个线程，是 GPU 调度的最小单位。  
**Thread / Block / Grid**（线程 / 线程块 / 网格）—— CUDA 的三级线程组织结构，对应 GPU 的物理执行层次。  
**寄存器**（Register）—— 每个线程私有的最快存储，容量极小（H100 共 256 KB/SM）。  
**共享内存**（Shared Memory / SRAM，静态随机存储器）—— 一个 Block 内所有线程共享的片上存储，和 L1 缓存共用同一块物理 SRAM。  
**HBM**（High Bandwidth Memory，高带宽显存）—— GPU 的主内存，大（80 GB）但相对慢。  
**Coalescing**（合并访存）—— 让同一个 Warp 的 32 个线程访问连续地址，是**新手第一大坑**。  
**Sector**（扇区）—— 显存访问的最小粒度，32 字节；理解合并访存的关键单位。  
**Bank Conflict**（存储体冲突）—— 共享内存访问的经典性能杀手，**新手第二大坑**。  
**Occupancy**（占用率）—— SM 上实际运行的 Warp 数量 / 理论最大值，影响延迟隐藏能力。  
**Wave**（波次）—— 一批能同时驻留在整块 GPU 上的 Block；Block 数量不是波次整数倍时会产生"尾巴效应"。  
**Tensor Core**（张量核心）—— 专门做矩阵乘累加的硬件单元，从 V100 开始出现，是现代深度学习的算力来源。

## 1.1 先算一笔账：GPU 到底快在哪

先不讲架构，做一道算术题。

**任务**：给 1 亿个 `float`（32 位浮点数）每个乘 2，即 `y[i] = x[i] * 2`。

数据量：读 1 亿 × 4 字节 = 400 MB，写 400 MB，**共搬 800 MB**。计算量：1 亿次乘法 = 1 亿 FLOP（浮点运算）。

| 硬件 | 内存带宽 | 搬完 800 MB 的时间 |
|---|---|---|
| 服务器 CPU（一颗，8 通道 DDR5） | ⚠️ 实测约 200 GB/s | 800 MB ÷ 200 GB/s = **4 ms** |
| H100 SXM5 | 3.35 TB/s | 800 MB ÷ 3350 GB/s = **239 µs** |

GPU 快 4 ms ÷ 239 µs ≈ **17 倍**。

> ★ **注意这 17 倍是从哪来的**：不是因为 H100 有 16896 个核而 CPU 只有 32 个（那是 528 倍的差距），而是因为**带宽差了 17 倍**。这个任务里每个数只用一次，核再多也只能干等数据。核的数量决定"有多少人能同时干活"，带宽决定"活能以多快的速度喂进来"——这两件事经常不是同一个瓶颈，而对大模型算子来说，**瓶颈通常在带宽**。整个第 02 章就在讲怎么判断瓶颈在哪一边。

再换一个任务，结论会翻过来：

**任务 B**：把这 1 亿个数**依次累加**，`s = ((x[0] + x[1]) + x[2]) + ...`，每一步依赖上一步的结果。

这时 GPU 一点便宜都占不到，甚至比 CPU 慢——因为每一步都必须等上一步，16896 个核里只有 1 个在干活，而 GPU 的单核频率和单核效率都不如 CPU。（实践中会用**树形归约**把它改成能并行的形式，但那是改算法，不是硬件占便宜。）

**两个任务的差别，就是 GPU 的适用边界**：

```
CPU（比喻）：
  [超级厨师] [超级厨师] [超级厨师] [超级厨师]
   能做任何菜    独立运作    快速思考    灵活应变
   适合：一道工序复杂、步步相扣的菜

GPU（比喻）：
  [普工][普工][普工]...[普工]   ← 16896 个
   只会切菜    只会切菜   只会切菜
   适合：同时切 16896 根胡萝卜
   不适合：熬一锅必须一步步来的高汤
```

> ★ **一句话**：GPU 快的前提是"同一件事有很多份互不依赖的活"。深度学习恰好满足——矩阵里每个元素的计算相互独立。这个前提贯穿全书，后面每一次优化，本质上都是在"凑出更多互不依赖的活"或者"让搬进来的数据被多用几次"。

## 1.2 硬件地图：从一整块芯片到一个线程

### 1.2.1 三层物理结构

```
第 1 层  一整块 GPU（H100 SXM5）
           ├── 132 个 SM
           ├── L2 缓存 50 MB        ← 全芯片共享
           └── HBM3 显存 80 GB / 3.35 TB/s

第 2 层  一个 SM
           ├── 4 个处理块（Processing Block，也叫 SM 分区）
           ├── 寄存器文件 256 KB
           └── L1 / 共享内存 256 KB  ← 本 SM 独占，其他 SM 看不到

第 3 层  一个处理块
           ├── 32 个 FP32 CUDA Core
           ├── 1 个 Tensor Core（第四代）
           └── 1 个 Warp 调度器      ← 每周期发射 1 条指令
```

两个容易搞混的点，先说清楚：

- **L2 是全芯片共享的，L1/共享内存是每个 SM 独占的。** 所以两个 Block 想交换数据，只能绕到 L2 或 HBM，不能走共享内存。
- **一个 SM 有 4 个 Warp 调度器**，所以一个 SM 每周期最多发射 4 条指令——这 4 条指令来自 4 个**不同的** Warp，不是同一个 Warp。

### 1.2.2 一个 SM 里面有什么

```
一个 SM（Hopper 架构）内部：

  ├── 处理块 0 ──┬── FP32 CUDA Core × 32    ← 普通浮点计算
  │              ├── Tensor Core × 1        ← 矩阵乘累加专用
  │              ├── SFU × 4                ← 特殊函数单元，算 exp/sin/rsqrt
  │              ├── LD/ST × 8              ← 访存单元，发射读写请求
  │              └── Warp 调度器 × 1
  ├── 处理块 1 ──（同上）
  ├── 处理块 2 ──（同上）
  ├── 处理块 3 ──（同上）
  │
  ├── 寄存器文件      65536 × 32-bit = 256 KB   ← 四个处理块各分 1/4
  ├── L1 / 共享内存   统一 256 KB，最多 228 KB 可配为共享内存
  └── TMA                                    ← Hopper 新增的异步搬数引擎
      （Tensor Memory Accelerator，张量内存加速器，
        能在后台把 HBM 的一块数据搬进共享内存，不占用计算线程）

  一个 SM 合计：128 个 FP32 CUDA Core + 4 个 Tensor Core + 4 个 Warp 调度器
```

H100 SXM5 的关键数字（来源：NVIDIA H100 架构白皮书 + CUDA C++ Programming Guide 计算能力 9.0 表）：

| 参数 | 数值 | 说明 |
|---|---|---|
| SM 数量 | 132 | PCIe 版本是 114，注意区分 |
| FP32 CUDA Core 总数 | 16896 | = 132 × 128 |
| 每 SM 最大驻留 Warp | 64 | = 2048 个线程 |
| 每 SM 最大驻留 Block | 32 | 所以 Block 太小会先撞这个上限 |
| 每 Block 最大线程数 | 1024 | 硬上限，不可超 |
| 每 SM 寄存器 | 65536 个 32-bit | = 256 KB |
| 每线程最大寄存器 | 255 | 超了就溢出到显存 |
| 每 SM 共享内存（最大） | 228 KB | 与 L1 共用 256 KB，比例可配 |
| L2 缓存 | 50 MB | 全芯片共享 |
| HBM3 | 80 GB / 3.35 TB/s | — |

### 1.2.3 软件侧的三级组织：Thread / Block / Grid

CUDA 把线程组织成三级，和上面的物理结构一一对应：

```
软件概念                     跑在哪                      能共享什么
─────────────────────────────────────────────────────────────────────
Grid（网格）        →  一整块 GPU             →  只能通过 HBM
  └ Block（线程块）  →  一个 SM（不会跨 SM）   →  该 SM 的共享内存
      └ Warp（32 线程）→ 一个处理块            →  可用 warp shuffle 直接交换寄存器
          └ Thread（线程）→ 一条 CUDA Core 通道 →  自己的寄存器（私有）
```

**关键约束**：一个 Block 一旦被分配给某个 SM，就**终身待在那个 SM 上**，不会迁移。这是"Block 内可以用共享内存和 `__syncthreads()` 同步、Block 之间不行"的物理原因——共享内存是 SM 独占的，跨 SM 根本没有一块共同的片上存储。

**用一个具体例子走一遍索引怎么算**。任务：`y[i] = x[i] * 2`，N = 1000。

```c
// 选择：每个 Block 256 个线程
int threads_per_block = 256;
int blocks = (1000 + 256 - 1) / 256;   // = 4，向上取整
kernel<<<4, 256>>>(x, y, 1000);
```

启动了 4 × 256 = **1024 个线程**，但只有 1000 个数要处理。每个线程怎么知道自己该处理哪一个？

```c
__global__ void kernel(float* x, float* y, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    //      ↑第几个Block   ↑每Block多少线程  ↑本Block内第几个线程
    if (i < N) y[i] = x[i] * 2.0f;   // ← 这个 if 不是可选的！
}
```

把 4 个 Block 的索引范围列出来：

| Block | `blockIdx.x` | `threadIdx.x` 范围 | 全局索引 `i` 范围 | 情况 |
|---|---|---|---|---|
| 0 | 0 | 0 – 255 | 0 – 255 | 全部有效 |
| 1 | 1 | 0 – 255 | 256 – 511 | 全部有效 |
| 2 | 2 | 0 – 255 | 512 – 767 | 全部有效 |
| 3 | 3 | 0 – 255 | 768 – 1023 | **后 24 个越界** |

Block 3 的线程 232–255 算出的 `i` 是 1000–1023，超出了数组范围。`if (i < N)` 就是拦住它们的——**漏掉这一行会越界写显存**，这是 CUDA 新手最高频的 bug，而且它经常不报错，只是安静地写坏别的数据。

> ★ 这里有个副产品：1024 个线程里有 24 个（2.3%）什么都没干。N 和 Block 大小不整除时，总会浪费一点。N = 1000、Block = 256 时浪费 2.3%；如果 Block 开成 1024，那就是 1024 个线程处理 1000 个数，浪费仍然只有 2.3%——但如果 N = 1030、Block = 1024，就要启动 2 个 Block = 2048 个线程，**浪费近 50%**。Block 大小的选择不是随手填的。

### 1.2.4 Block 是怎么落到 SM 上的：波次与尾巴效应

Grid 里可能有几千个 Block，但 GPU 只有 132 个 SM，每个 SM 同时能装的 Block 数量也有限。硬件的做法是：**先装满，谁先做完谁接下一个**。

能同时驻留在整块 GPU 上的那一批 Block，叫一个**波次（Wave）**。

**一个极端例子说明为什么这件事要紧**。假设某个 kernel 的每个 Block 占用资源很大，一个 SM 只放得下 1 个 Block：

```
情况 A：Grid = 132 个 Block
  波次 1：132 个 Block 同时上机，132 个 SM 全满
  总时间 = 1 个 Block 的时间 = 1T
  机器利用率 = 100% ✓

情况 B：Grid = 140 个 Block   ← 只比 A 多了 6% 的活
  波次 1：132 个 Block，全满
  波次 2：只剩 8 个 Block，124 个 SM 空转
  总时间 = 2T                 ← 时间翻倍！
  机器利用率 = 140 / (132 × 2) = 53% ✗
```

**多 6% 的工作量，耗时翻了一倍。** 这叫**尾巴效应**（Tail Effect）或**波次量化**（Wave Quantization）。

诊断和应对：

- **看 Grid 大小是不是 SM 数的整数倍附近**。132 个 SM，Grid 开 133 个 Block 是最糟的选择之一。
- **让分块更细**：Block 数量远大于波次容量时（比如几千个），尾巴只占总时间的一小部分，影响可以忽略。上面的例子之所以致命，是因为总共只有 1–2 个波次。
- **Persistent Kernel（常驻 kernel）**：干脆只启动"刚好填满一个波次"的 Block，每个 Block 内部用循环去领取多份活（Grid-Stride Loop，网格跨步循环）。这是第 03、07 章会反复用到的写法。

> ⚠️ 上面的"波次"是一个简化模型。真实硬件不是同步地一波做完再放下一波，而是某个 Block 结束就立刻补一个新的进去。但在预估尾巴效应时，这个模型够用，NVIDIA 官方性能文档也用它。

### 1.2.5 Warp：调度的真正最小单位

Block 里连续的 32 个线程构成一个 **Warp**。GPU 调度器**以 Warp 为单位发射指令**——同一个 Warp 里的 32 个线程永远执行同一条指令，只是数据不同。这就是 **SIMT**（单指令多线程）模型。

一个重要推论：**你写的 `if` 不是免费的**。

```c
// 反例：同一 Warp 里的线程走了不同分支
if (threadIdx.x % 2 == 0) {
    A();   // 假设需要 100 个周期
} else {
    B();   // 假设需要 60 个周期
}
```

同一个 Warp 里，偶数线程要走 A，奇数线程要走 B，但硬件只能发一条指令。它的做法是**两条路都走，各走一遍，不该干活的线程用掩码屏蔽掉**：

| 周期 | 执行什么 | 活跃的通道（lane） | 空转的通道 |
|---|---|---|---|
| 0 – 99 | `A()` | 16 个（偶数 lane） | 16 个（奇数 lane 被掩码屏蔽） |
| 100 – 159 | `B()` | 16 个（奇数 lane） | 16 个（偶数 lane 空转） |

算一下账：

```
总耗时     = 100 + 60 = 160 个周期     ← 不是 max(100, 60) = 100！
有效工作量 = 16×100 + 16×60 = 2560 通道·周期
硬件产能   = 32 × 160      = 5120 通道·周期
通道利用率 = 2560 / 5120   = 50%      ← 一半的硬件在空转
```

**改法：把分支的粒度提到 Warp 以上。**

```c
// 正例：同一个 Warp 必然整体走同一条路
int warp_id = (blockIdx.x * blockDim.x + threadIdx.x) / 32;
if (warp_id % 2 == 0) { A(); } else { B(); }
```

现在 Warp 0 整体走 A（100 周期，32 通道全活跃），Warp 1 整体走 B（60 周期，全活跃），而且它们在不同的 Warp 调度器上**并发**执行。通道利用率 100%，总耗时约 100 周期而不是 160。

> ★ 设计 kernel 时的判断标准不是"能不能有分支"，而是"**分歧发生在哪一层**"。Warp 内分歧要命；Warp 之间、Block 之间的分歧几乎免费。

> ⚠️ 从 Volta（V100）开始，硬件支持**独立线程调度**（Independent Thread Scheduling），分歧的线程可以各自推进程序计数器，不再严格"先全部 A 再全部 B"。但**代价没有消失**：两条路径的执行时间仍然要相加，掩码屏蔽造成的通道空转仍然存在。上面的账依然成立。

## 1.3 内存层级：五级台阶和它们的真实代价

GPU 的存储是一个金字塔，越快越小：

```
     ▲ 快                                                   小 ▲
     │   寄存器      每线程最多 255 个，SM 共 256 KB
     │   共享内存    每 SM 最多 228 KB
     │   L2 缓存     全芯片 50 MB
     │   HBM 显存    80 GB
     ▼ 慢           主机内存   几百 GB（要过 PCIe）          大 ▼
```

配上真实数字，差距的量级才看得清：

| 层级 | 容量 | 延迟（⚠️ 实测量级，随代际浮动） | 作用域 | 谁控制 |
|---|---|---|---|---|
| 寄存器 | 256 KB / SM | ~1 周期（相当于免费） | 单个线程私有 | 编译器 |
| 共享内存 | ≤228 KB / SM | 约 20–30 周期 | 一个 Block | **程序员手动** |
| L1 缓存 | 与共享内存共用 256 KB | 约 30–40 周期 | 一个 SM | 硬件 |
| L2 缓存 | 50 MB | 约 200–300 周期 | 全芯片 | 硬件 |
| HBM 显存 | 80 GB | 约 450–600 周期 | 全芯片 | 硬件（可用 TMA 预取） |
| 主机内存 | 几百 GB | µs 级（过 PCIe，约 64 GB/s） | — | 程序员（`cudaMemcpy`） |

**先把这一行读三遍**：共享内存和 HBM 的延迟差 **20 倍以上**。这就是为什么"手动把数据搬进共享内存、在片上反复用"是 GPU 算子优化的第一招——第 03 章的 GEMM 分块、第 04 章的 FlashAttention，本质上都是这一招的不同形态。

### 寄存器与寄存器溢出

每个线程独享，访问速度等同于计算速度。**限制在于总量**：一个 SM 只有 65536 个 32-bit 寄存器，线程越多，每个线程分到的就越少。

具体算一下：一个 SM 要塞满 2048 个线程（64 个 Warp），那么每个线程只能用 65536 ÷ 2048 = **32 个寄存器**。想用 64 个寄存器？那这个 SM 最多只能装 1024 个线程。

如果一个线程要用的寄存器超过了编译器分配的额度，编译器会把放不下的变量挪到 **Local Memory**（本地内存）——名字听起来像片上存储，**但它物理上就在 HBM 里**。这叫**寄存器溢出**（Register Spilling）。

```
溢出的代价：原本 1 个周期的变量访问，变成 450–600 个周期
后果：一个本来算得很快的 kernel，性能塌到 1/10 都有可能
怎么发现：编译时加 -Xptxas -v，看输出里的 "spill stores / spill loads"
          非 0 就要警惕；配合 Nsight Compute 看 Local Memory 的流量
```

> ★ 寄存器溢出是"kernel 莫名其妙很慢"的头号嫌疑犯，而且它在源码里完全看不出来——必须看编译器输出。

### 共享内存

Block 内所有线程共享，生命周期等同于 Block（Block 结束就没了）。它和 L1 共用同一块 256 KB 的物理 SRAM，比例可配。

```c
__shared__ float tile[32][32];                      // 声明：32×32×4 B = 4 KB
tile[threadIdx.y][threadIdx.x] = A[row * K + col];  // ① 每个线程搬一个元素进来
__syncthreads();                                    // ② 等本 Block 所有线程都搬完
float val = tile[threadIdx.y][k];                   // ③ 现在可以放心反复读了
```

第 ② 步的 `__syncthreads()` 不能省：没有它，线程 0 可能在线程 500 还没写完的时候就去读 `tile`，读到垃圾值。**而且这个 bug 具有随机性**——同样的代码有时对有时错，取决于调度顺序，极难排查。

**为什么值得这么麻烦**：一块 4 KB 的 tile 从 HBM 搬进来要付一次约 500 周期的代价，但搬进来之后，Block 里的 1024 个线程可以各读它几十次，每次只要 20 多个周期。**搬一次、用很多次**，这是 GPU 算子优化的核心经济学。

### HBM（高带宽显存）

GPU 的主内存。H100 SXM5 是 80 GB HBM3，带宽 3.35 TB/s——听起来很高，但和算力比就不够看了：

```
BF16 峰值算力（稠密）   = 989 TFLOPS  = 989 × 10¹² FLOP/s
HBM 带宽                = 3.35 TB/s   = 3.35 × 10¹² Byte/s

要让算力和带宽同时打满，每搬 1 字节必须算：
    989 × 10¹² ÷ (3.35 × 10¹²) ≈ 295 FLOP/Byte    ← 这叫"屋脊点"
```

回头看 §1.1 那个 `y[i] = x[i] * 2`：每个元素搬 8 字节（读 4 写 4）、算 1 次乘法，算术强度 = 1 ÷ 8 = **0.125 FLOP/Byte**。离 295 差了 **2360 倍**。

这个 kernel 实际能跑多快：

```
性能 = 带宽 × 算术强度 = 3350 GB/s × 0.125 FLOP/Byte = 419 GFLOPS
占 FP32 峰值（67 TFLOPS）的比例 = 419 / 67000 = 0.63%
```

**算力用了 0.6%，而且这已经是这个 kernel 的理论最优。** 再怎么优化计算部分都没用——瓶颈完全在搬数据上。绝大多数深度学习算子（激活函数、归一化、逐元素运算）都在这个区间，这就是**算子融合**（第 05 章）存在的全部理由：既然搬一次数据的成本这么高，那就在搬进来的这一趟里把能算的都算完。

> ⚠️ 注意别用错算力数字。NVIDIA 官方表里 BF16 有 989 和 1979 两个数，**1979 是"带稀疏"的**（要求权重满足 2:4 稀疏模式），常规稠密算子用不上。本系列统一用稠密值 989 TFLOPS，屋脊点 295 FLOP/Byte，和 [02 章](02-屋顶线与性能剖析.md)、[附-速查表](附-速查表.md) 保持一致。

## 1.4 合并访存：新手踩的第一个坑

这一节讲的东西，在源码里**长得和正确写法几乎一样**，但性能能差 8 倍。

### 1.4.1 先理解"扇区"

GPU 读显存不是按字节读的，而是按 **32 字节的扇区（Sector）** 为最小单位。你只要碰到某个扇区里的 1 个字节，硬件就得把整整 32 字节都搬上来。（L1 的缓存行是 128 字节 = 4 个扇区。）

于是问题变成：**同一个 Warp 的 32 个线程发出的这一批访问，一共碰到了几个扇区？**

一个 Warp 读 32 个 `float` = 128 字节。最好的情况是这 128 字节正好落在 4 个扇区里；最坏的情况是它们散落在 32 个不同扇区里。

### 1.4.2 四种情况，把扇区数算出来

假设数组 `x` 起始地址按 128 字节对齐，元素是 `float`（4 字节），`tid` 是 Warp 内的通道号 0–31。

**情况 A：`x[tid]` —— 完美合并**

```
线程:   0    1    2    3   ...   30    31
地址:   0    4    8   12   ...  120   124     ← 连续 128 字节
扇区: └──0──┘└──1──┘└──2──┘└──3──┘           ← 每个扇区装 8 个 float

搬入 4 × 32 = 128 字节，用掉 128 字节 → 效率 100% ✓
```

**情况 B：`x[tid * 32]` —— 跨步访问，最糟**

```
线程:   0      1      2      3    ...    31
地址:   0    128    256    384   ...   3968    ← 每个相隔 128 字节
扇区:   0      4      8     12    ...   124    ← 32 个互不相同的扇区！

搬入 32 × 32 = 1024 字节，只用掉 128 字节 → 效率 12.5%
带宽浪费 8 倍，等于把 3.35 TB/s 当 0.42 TB/s 用 ✗
```

**情况 C：`x[tid + 1]` —— 只错了一个元素**

```
地址: 4 ... 128（跨过了 128 字节边界）
扇区: 0, 1, 2, 3, 4  ← 5 个，多了一个

搬入 5 × 32 = 160 字节，用掉 128 → 效率 80%
```

**情况 D：`x[0]` —— 所有线程读同一个地址**

```
扇区: 只有 1 个。硬件识别出这是广播，搬 32 字节分发给 32 个线程
效率没问题 ✓  ← 反直觉但正确：读同一个地址不是冲突，是广播
```

汇总：

| 访问模式 | 碰到的扇区数 | 搬入字节 | 有效字节 | 效率 |
|---|---|---|---|---|
| A `x[tid]` | 4 | 128 | 128 | **100%** |
| B `x[tid*32]` | 32 | 1024 | 128 | **12.5%** |
| C `x[tid+1]` | 5 | 160 | 128 | 80% |
| D `x[0]`（广播） | 1 | 32 | 128（复用） | 正常 |

### 1.4.3 落到真实代码：矩阵的两种遍历

这才是这一节真正要命的地方。设 `float A[1024][1024]`，C 语言是**行优先**存储，即 `A[r][c]` 的实际地址是 `A + (r*1024 + c) * 4`。

```c
// 写法 ①：让 threadIdx.x 走列方向
float v = A[blockIdx.x][threadIdx.x];
// 相邻线程 → 相邻的 c → 地址相差 4 字节 → 连续 → 情况 A，效率 100% ✓

// 写法 ②：让 threadIdx.x 走行方向
float v = A[threadIdx.x][blockIdx.x];
// 相邻线程 → 相邻的 r → 地址相差 1024×4 = 4096 字节 → 情况 B，效率 12.5% ✗
```

**两行代码只是把下标换了个位置，访存效率差 8 倍。** 而且写法 ② 在语法上、逻辑上都完全正确，跑出来的结果一模一样——它只是慢。

> ★ **记住这条判断法则**：让 `threadIdx.x` 对应内存里**变化最快的那一维**（行优先存储中就是最后一维）。这条法则在 CUDA、Triton（第 07 章）里都成立，在昇腾上换了形式但思想相同（第 13 章的对齐搬运）。

### 1.4.4 那如果我就是必须按列访问呢

比如矩阵转置，输入按行读、输出按行写，两边不可能同时合并。标准解法是**借共享内存中转**：

```
① 按行（合并）从 HBM 读入一块 32×32 的 tile   → 效率 100%
② 在共享内存里完成转置（片上，延迟只有 20-30 周期，随便怎么访问）
③ 按行（合并）把 tile 写回 HBM                → 效率 100%
```

把"不合并的访问"从 HBM 挪到了共享内存里去做。但这样做会立刻撞上下一个坑——**共享内存也有自己的访问冲突规则**。下一节就是它。

## 1.5 Bank Conflict：共享内存里的第二个坑

### 1.5.1 规则

共享内存物理上被切成 **32 个存储体（Bank）**，编号 0–31，每个 Bank 宽 4 字节。地址是**轮流**分配给各个 Bank 的：

```
4 字节编号:  0   1   2   3  ...  30  31  32  33  ...  63  64
落在 Bank:   0   1   2   3  ...  30  31   0   1  ...  31   0
                                          ↑ 绕回来了

规则：第 n 个 4 字节 → Bank (n % 32)
```

**Bank Conflict（存储体冲突）**：同一个 Warp 内，如果多个线程访问**同一个 Bank 里的不同地址**，硬件只能一个一个来，把并行访问串行化了。

三种情况必须分清（第三种最容易被误判）：

| 情况 | 结果 |
|---|---|
| 32 个线程访问 32 个**不同的 Bank** | 一个周期全部完成 ✓ |
| 多个线程访问**同一 Bank 的不同地址** | 串行化，k 个线程撞一起就是 k 倍延迟 ✗ |
| 多个线程访问**同一 Bank 的同一地址** | 广播，一个周期完成 ✓ **不是冲突** |

### 1.5.2 把 Bank 编号一个个算出来

声明 `__shared__ float tile[32][32]`。元素 `tile[r][c]` 的线性下标是 `r * 32 + c`，所以它在 **Bank `(r * 32 + c) % 32`**。

**按行读**（`tile[0][tid]`，32 个线程读第 0 行）：

| 线程 | 访问 | 线性下标 | Bank |
|---|---|---|---|
| 0 | `tile[0][0]` | 0 | 0 |
| 1 | `tile[0][1]` | 1 | 1 |
| 2 | `tile[0][2]` | 2 | 2 |
| … | … | … | … |
| 31 | `tile[0][31]` | 31 | 31 |

32 个不同的 Bank，**一个周期搞定** ✓

**按列读**（`tile[tid][0]`，32 个线程读第 0 列）：

| 线程 | 访问 | 线性下标 | Bank = 下标 % 32 |
|---|---|---|---|
| 0 | `tile[0][0]` | 0 | **0** |
| 1 | `tile[1][0]` | 32 | **0** |
| 2 | `tile[2][0]` | 64 | **0** |
| 3 | `tile[3][0]` | 96 | **0** |
| … | … | … | … |
| 31 | `tile[31][0]` | 992 | **0** |

**32 个线程全部撞在 Bank 0 上。** 下标都是 32 的倍数，除以 32 余数当然都是 0。这是最坏的 **32 路冲突**，本该 1 个周期的访问变成 32 个周期，**共享内存的速度优势被抹掉 32 倍**——比直接读 HBM 强不了多少。

而 §1.4.4 说的矩阵转置，第 ② 步恰恰就是按列读。坑就是这么连在一起的。

### 1.5.3 解法一：加一列 Padding

改成 `__shared__ float tile[32][33]`，每行多留一个 float 不用。现在 `tile[r][c]` 的线性下标是 `r * 33 + c`：

| 线程 | 访问 | 线性下标 | Bank = 下标 % 32 |
|---|---|---|---|
| 0 | `tile[0][0]` | 0 | **0** |
| 1 | `tile[1][0]` | 33 | **1** |
| 2 | `tile[2][0]` | 66 | **2** |
| 3 | `tile[3][0]` | 99 | **3** |
| … | … | … | … |
| 31 | `tile[31][0]` | 1023 | **31** |

**32 个不同的 Bank，冲突完全消除** ✓

为什么这么巧？一行算术就能看明白：

```
(r × 33) % 32 = (r × (32 + 1)) % 32 = (r×32 + r) % 32 = r % 32
                                                          ↑
                    r = 0..31 时，这正好是 0..31，互不相同
```

**每行多一个 float，就让每一列整体斜着错开一个 Bank。** 代价是多用 32 × 4 = 128 字节共享内存（4 KB 的 tile 变 4.125 KB，涨 3%），换来 32 倍的访问加速。

```c
__shared__ float tile[32][32];   // ✗ 按列访问 = 32 路冲突
__shared__ float tile[32][33];   // ✓ 加一列 padding，冲突消除，多花 3% 空间
```

### 1.5.4 解法二：Swizzle（了解即可）

Padding 的毛病是浪费了空间，而且破坏了对齐——TMA 和 Tensor Core 都喜欢整齐的 128 字节边界，多出来的那一列会让地址不对齐。

现代高性能库（CUTLASS、Triton）用的是 **Swizzle（异或置换）**：不加 padding，而是把访问地址按位异或一个模式，把落点打散到不同 Bank。

```
padding：    改变数据布局（多占空间，破坏对齐）
swizzle：    改变访问地址的映射（不占额外空间，保持对齐）
             addr' = addr XOR ((addr >> k) & mask)
```

现在只要知道"有这么个东西、它比 padding 更现代"就够了，具体用法在 [第 03 章](03-GEMM深度剖析.md)（GEMM 的共享内存布局）和 [第 07 章](07-Triton编程.md) 展开。

## 1.6 Occupancy：延迟隐藏，以及为什么它不是越高越好

### 1.6.1 GPU 靠什么掩盖 500 周期的访存延迟

**Occupancy（占用率）** = SM 上实际驻留的 Warp 数 ÷ SM 支持的最大 Warp 数（H100 是 64）。

GPU 掩盖延迟的方式不是"让访存变快"，而是**切换 Warp**：某个 Warp 在等 HBM 数据时，调度器立刻换一个已就绪的 Warp 去执行。前提是——**手上得有牌可换**。

**用具体周期数算一遍**。假设每个 Warp 干的活是：发一次 HBM 读（延迟 500 周期），数据回来后算 20 个周期。

```
只有 1 个 Warp：
  周期 0        发出读请求
  周期 1-500    ███████████████████ SM 完全空转，无牌可打
  周期 501-520  计算 20 周期
  总计 520 周期，其中有效计算 20 周期 → SM 利用率 3.8%  ✗

有 25 个 Warp：
  周期 0-24     25 个 Warp 依次发出读请求（每周期 1 个）
  周期 25-499   等待中，但此时……第 1 个 Warp 的数据即将返回
  周期 500      Warp 0 数据到，开始算 20 周期
  周期 520      Warp 1 数据到（它晚 1 周期发的请求），接着算
  ...           25 个 Warp × 20 周期 = 500 周期的计算量，
                恰好填满 500 周期的等待窗口
  → 延迟被完全掩盖，SM 一直有活干 ✓
```

**掩盖延迟需要多少 Warp，是可以算出来的**：

```
需要的 Warp 数 ≈ 访存延迟 ÷ 每个 Warp 的计算时间 = 500 ÷ 20 = 25 个
对应 Occupancy = 25 / 64 ≈ 39%
```

> ★ 这就解释了那句经验之谈"50–75% 的 Occupancy 通常就够了"——**够不够取决于"每搬一次数据能算多久"**。计算密集的算子（每次访存算 100 周期）只需要 5 个 Warp、8% 的 Occupancy 就够；纯访存的算子（几乎不算）则怎么堆 Warp 都填不满。Occupancy 不是一个越高越好的分数，它是"你需要多少张牌"的答案。

> ⚠️ 上面是简化模型：忽略了 4 个 Warp 调度器的并发发射、指令级并行（同一个 Warp 内也能有多个未完成的读请求）、以及 L2 命中会大幅缩短延迟。真实情况用 Nsight Compute 看，别手算。

### 1.6.2 Occupancy 是怎么被资源卡住的：完整推演

Occupancy 不是你能直接设定的，它是三种资源**互相挤压后的结果**。走一个完整的例子。

**给定一个 kernel**：

```
Block 大小      = 256 个线程 = 8 个 Warp
每线程寄存器    = 40 个
每 Block 共享内存 = 32 KB
```

**逐个算三条限制**（H100，SM 上限：65536 寄存器 / 228 KB 共享内存 / 64 Warp / 32 Block）：

```
① 寄存器限制
   每个 Warp 需要的寄存器 = 40 × 32 = 1280 个
   （寄存器按 Warp 为单位、以 256 个为粒度分配；1280 = 256 × 5，正好整齐）
   一个 SM 能装的 Warp  = 65536 ÷ 1280 = 51.2 → 向下取整 51 个 Warp
   换算成 Block         = 51 ÷ 8 = 6.375 → 向下取整  6 个 Block

② 共享内存限制
   228 KB ÷ 32 KB = 7.125 → 向下取整               7 个 Block

③ Warp / Block 数量限制
   64 个 Warp ÷ 8 = 8 个 Block（Block 上限 32，不是瓶颈） 8 个 Block

取三者最小值：min(6, 7, 8) = 6 个 Block
                ↑ 寄存器是瓶颈

实际驻留 Warp = 6 × 8 = 48 个
Occupancy    = 48 / 64 = 75%
```

**现在把寄存器从 40 个加到 48 个**（比如多了几个中间变量），重算 ①：

```
每 Warp 寄存器 = 48 × 32 = 1536 = 256 × 6   ✓ 仍然整齐
Warp 数 = 65536 ÷ 1536 = 42.67 → 42 个
Block 数 = 42 ÷ 8 = 5.25 → 5 个 Block
驻留 Warp = 5 × 8 = 40 个
Occupancy = 40 / 64 = 62.5%     ← 掉了 12.5 个百分点
```

**每个线程多用 8 个寄存器，Occupancy 掉 12.5 个百分点。** 而且这个变化在源码里几乎看不出来——可能只是多写了一个临时变量。这也解释了为什么 Occupancy 曲线是**阶梯状**的：只要还没跨过取整的台阶，多用几个寄存器完全免费；一跨过去就断崖式下跌。

三条限制的实用含义：

| 资源 | 拧哪个旋钮 | 副作用 |
|---|---|---|
| 寄存器用量 | `__launch_bounds__`、`-maxrregcount` | 压太狠会**寄存器溢出**，比低 Occupancy 更糟 |
| 共享内存用量 | 减小 tile 尺寸 | tile 小了，数据复用就少了，HBM 流量上升 |
| Block 大小 | 128 / 256 / 512 | 太小撞 32-Block 上限；太大则资源被一个 Block 独占，取整浪费更大 |

### 1.6.3 高 Occupancy ≠ 高性能

> ⚠️ **这是本节最重要的一句话。** Occupancy 是"延迟掩盖的手段"，不是目标。三种常见的反例：
>
> 1. **计算密集的算子**已经把计算单元打满了，再提 Occupancy 一点收益都没有。
> 2. **主动降低 Occupancy 反而更快**：让每个线程多用寄存器、多处理几个输出元素（Thread Tiling，线程级分块），虽然驻留 Warp 少了，但寄存器里的数据复用暴涨、访存次数骤减。第 03 章高性能 GEMM 用的就是这招，Occupancy 常常只有 25–50%。
> 3. **压寄存器换 Occupancy，换来了溢出**：把 `-maxrregcount` 拧得太小，Occupancy 数字上去了，但溢出的变量跑到 HBM，每次访问 500 周期，净亏。
>
> 判断标准永远是**实测时间**，不是 Occupancy 的百分比。Nsight Compute 会同时给出 Occupancy 和"Occupancy 是否是当前瓶颈"的结论，看后者。

## 1.7 Tensor Core：矩阵乘法的专用加速器

### 1.7.1 快多少

从 Volta（V100）开始，每个 SM 内置了 **Tensor Core**——专门执行**小矩阵乘累加**（Matrix Multiply-Accumulate，MMA，即 `D = A × B + C`）的硬件单元。

普通 CUDA Core 一个周期做 1 次乘加（2 FLOP），Tensor Core 一个周期做一整块小矩阵的乘加。

```
一个 SM 每周期的浮点运算量：

  FP32 CUDA Core:  128 个核 × 2 FLOP =  256 FLOP/周期   （架构定义，精确）
  BF16 Tensor Core:                  ≈ 4096 FLOP/周期   （⚠️ 推算，见下）

  比例约 16 倍
```

用官方峰值表交叉验证：

```
BF16 Tensor Core（稠密） 989 TFLOPS
FP32 CUDA Core            67 TFLOPS
                    ────────────────
                    989 / 67 ≈ 15 倍   ✓ 和架构推算的 16 倍吻合
```

> ⚠️ 上面 4096 FLOP/周期 是推算值：A100 的官方数字能精确反推出 2048 FLOP/SM/周期（312 TFLOPS ÷ 108 SM ÷ 1.41 GHz ≈ 2048），Hopper 每 SM 的 Tensor 吞吐翻倍即 4096。但 H100 官方峰值表里 FP32 和 BF16 两个数字似乎不是按同一个时钟频率标定的，所以逐周期推算和峰值表会有几个百分点的出入。**结论只用记"约 15 倍"这个量级**，别把逐周期的数字当精确值引用。
>
> （顺带修正：本章旧版写的"快 8 倍"是错的，那个数对不上任何一组官方数字。）

**15 倍意味着什么**：矩阵乘法只要能用上 Tensor Core，性能就有一个数量级的跨越；用不上就等于把 15/16 的算力扔了。所以"这个算子走没走 Tensor Core"是性能分析里第一个要确认的问题。

### 1.7.2 用上它的条件：维度对齐

Tensor Core 执行的是固定形状的指令。以 Ampere/Hopper 的 BF16 为例，硬件指令是 `mma.m16n8k16`——一次处理 M=16、N=8、K=16 的小块。

| 精度 | 典型 MMA 形状 | 实践上的维度要求 | H100 稠密峰值 |
|---|---|---|---|
| FP32 | 无（走 CUDA Core） | 无 | ~67 TFLOPS |
| TF32 | m16n8k8 | M,N,K 对齐到 16 | ~494 TFLOPS |
| BF16 / FP16 | m16n8k16 | M,N,K 对齐到 16 | ~989 TFLOPS |
| FP8 | m16n8k32 | M,N,K 对齐到 16 | ~1979 TFLOPS |
| INT8 | m16n8k32 | M,N,K 对齐到 16 | ~1979 TOPS |

严格说硬件只要求 N 对齐到 8，但 cuBLAS / CUTLASS 为了走上最快的那条 kernel 路径，还要求**指针 16 字节对齐**、维度对齐到 8 或 16 个元素。实践中统一记"**对齐到 16**"就不会错。

**对不齐会怎样**：库会悄悄退回到慢速路径（要么补零到对齐、要么直接用 CUDA Core），不报错，只是慢——可能慢 5 倍以上。

### 1.7.3 为什么大模型的隐藏维度总是 128 的倍数

这个到处能看到的约定，背后是三个条件叠起来的：

```
① 硬件 MMA 形状：      要对齐到 16
② 张量并行（TP）切分： 隐藏维度要被均分到 8 张卡上
                       → 每张卡拿到 128 ÷ 8 = 16，仍然是 16 的倍数 ✓
③ 合并访存与对齐：     128 个 BF16 = 256 字节 = 2 个完整的 128 字节缓存行 ✓

如果隐藏维度取 100（不是 16 的倍数）：
  → Tensor Core 用不上，退回 CUDA Core，慢一个数量级
如果取 144（是 16 的倍数，但 144 ÷ 8 = 18，不是 16 的倍数）：
  → 单卡能用 Tensor Core，8 卡 TP 切分后每卡 18，对不齐了，又变慢
```

**128 是同时满足这三件事的最小值**。所以你看到的 hidden_size 4096、5120、8192，除以 8 卡还是 512、640、1024，全都整齐。

### 1.7.4 怎么调用

Tensor Core 是**在 Warp 层面协作**的：一个 Warp 的 32 个线程共同完成一次 MMA，每个线程持有结果矩阵的一小部分（这叫 Fragment，片段）。Hopper 更进一步，引入 `wgmma` 指令，需要 4 个 Warp（128 线程，称为一个 Warpgroup，线程束组）协同发射。

这意味着**你没法用普通的 `for` 循环调用 Tensor Core**，必须走专门的接口：

```
抽象层从低到高：

  PTX 汇编        mma / wgmma 指令        ← 最底层，手写极难
  CUDA C++        wmma API               ← 能用，但性能一般，只支持部分形状
  CUTLASS         模板库                  ← NVIDIA 官方，性能接近极限，学习曲线陡
  Triton          tl.dot()               ← 编译器自动选 MMA 指令，最省事（第 07 章）
  cuBLAS / PyTorch  torch.matmul()       ← 最省事，但只能用现成的算子
```

绝大多数情况下用 Triton 或 cuBLAS 就够了。手写 MMA 的场合和方法在 [第 03 章](03-GEMM深度剖析.md) 展开。

## 1.8 全流程串一遍：一次 kernel 调用的完整旅程

### 1.8.1 从 Python 到 HBM 的完整路径

```
CPU 侧（主机）
─────────────────────────────────────────────────────────────
① Python:  y = torch.mul(x, 2.0)
              ↓
② PyTorch 调度：查 dispatch 表，选中 CUDA 后端的逐元素乘 kernel
              ↓
③ 计算启动配置：grid = ceil(N/256)，block = 256
              ↓
④ 把"启动命令"推进 CUDA Stream（流）的队列
              ↓
   ★ CPU 到这里就返回了，不等 GPU！这叫异步启动
     ——所以想计时必须先 torch.cuda.synchronize()，
       否则你测到的只是"把命令塞进队列"的时间
              ↓
═══════════ PCIe / 命令队列 ═══════════  约 3–10 µs 的启动开销
              ↓
GPU 侧（设备）
─────────────────────────────────────────────────────────────
⑤ GigaThread Engine（全局工作分配器）把 Grid 里的 Block 发给各个 SM
      ↓   按 §1.2.4 的波次规则，先填满，谁空了补谁
⑥ 每个 SM 接收若干 Block，为它们分配寄存器和共享内存
      ↓   分配不下就少收 Block —— 这就是 §1.6 的 Occupancy
⑦ 每个 Block 被切成 Warp（32 线程一组），挂到 4 个 Warp 调度器上
      ↓
⑧ 调度器每周期挑一个"就绪"的 Warp 发射指令
      ↓
⑨ 遇到访存指令：查 L1 → 查 L2 → 去 HBM（§1.3 的阶梯）
      ↓   这个 Warp 转为"等待"状态，调度器立刻换下一个 Warp（§1.6 延迟掩盖）
      ↓   访问是否合并，决定了这一步搬 128 字节还是 1024 字节（§1.4）
⑩ 数据返回 → Warp 重新就绪 → 被再次调度 → 计算 → 写回
      ↓
⑪ 全部 Block 完成 → kernel 结束 → 向 Stream 发完成信号
      ↓
⑫ CPU 在下一个同步点（synchronize / 读取结果）看到它完成了
```

### 1.8.2 把全章数字用到同一个 kernel 上

最后用一个完整的例子，把前面所有概念的数字串起来。

**任务**：`y[i] = x[i] * 2`，N = 1,000,000（100 万个 float），H100 SXM5。

**第一步：启动配置**

```
Block 大小 = 256 线程 = 8 个 Warp
Grid 大小  = ceil(1000000 / 256) = 3907 个 Block
总线程数   = 3907 × 256 = 1,000,192
空转线程   = 192 个（0.02%，靠 if (i < N) 拦住）← §1.2.3
```

**第二步：能同时驻留多少（假设每线程 16 个寄存器，不用共享内存）**

```
寄存器限制：每 Warp 16×32 = 512 个 → 65536 ÷ 512 = 128 个 Warp，超过上限 64
Warp 限制： 64 ÷ 8 = 8 个 Block
Block 限制：32 个 Block
→ min 后为 8 个 Block/SM，驻留 64 个 Warp，Occupancy = 100%   ← §1.6

全 GPU 一个波次 = 132 SM × 8 = 1056 个 Block          ← §1.2.4
总波次 = ceil(3907 ÷ 1056) = 4 个
最后一个波次只有 3907 − 3×1056 = 739 个 Block（装了 70%）
机器利用率 = 3907 ÷ (4 × 1056) = 92.5%，浪费 7.5%，可以接受

  ★ 对比 §1.2.4 那个 140 Block 的例子（利用率 53%）：
    这里 Block 数量多、波次数也多，尾巴被摊薄了。
    尾巴效应只在"总共就一两个波次"的时候致命。
```

**第三步：访存分析**

```
访问模式 x[i]，i = blockIdx.x*256 + threadIdx.x
→ 同一 Warp 内地址连续 → 完美合并，效率 100%   ← §1.4 情况 A
数据量 = 读 4 MB + 写 4 MB = 8 MB
```

**第四步：理论耗时**

```
HBM 时间 = 8 MB ÷ 3350 GB/s = 2.39 µs
算术强度 = 1 FLOP ÷ 8 Byte = 0.125 FLOP/Byte  ≪ 295（屋脊点）
→ 彻底的 Memory Bound，算力只用到 0.63%       ← §1.3
```

**第五步：和启动开销比一比 —— 本章最后一个反直觉结论**

```
kernel 执行时间 ≈ 2.39 µs
kernel 启动开销 ≈ 3–10 µs
                  ────────────
启动开销比 kernel 本身还长！
```

**这个 kernel 一半以上的时间花在"启动"上，而不是"计算"上。** 而真实模型里这种小算子（激活、缩放、加偏置、归一化）动辄几百个，每个都要付一遍启动开销。

于是两条优化路线自然浮现：

- **算子融合**（[第 05 章](05-算子融合.md)）：把 10 个小 kernel 合成 1 个，省掉 9 次启动开销，顺带省掉 9 趟 HBM 往返。
- **CUDA Graph**（[第 09 章](09-推理侧算子.md)）：把整串 kernel 启动命令预先录制成一张图，一次提交，把每次 3–10 µs 的开销压到接近零。

> ★ 到这里，本章所有概念都在同一个例子上用过一遍了。**如果你能自己把这五步重算一遍（换成 N = 1000 万，或者换成 BF16），这一章就算过了。**

## 1.9 本章小结

**硬件与线程**

| 概念 | 一句话 | 关键数字（H100） |
|---|---|---|
| SM | GPU 的基本计算单元 | 132 个 |
| Block | 一组协作线程，终身绑定在一个 SM 上 | ≤1024 线程，每 SM ≤32 个 |
| Warp | 32 个线程，调度的最小单位，同步执行同一条指令 | 每 SM ≤64 个 |
| Thread | 最小执行单元，有私有寄存器 | 每线程 ≤255 个寄存器 |
| Wave（波次） | 一批能同时驻留的 Block | 132 × 每 SM 可驻留 Block 数 |

**内存层级（延迟为 ⚠️ 实测量级）**

```
寄存器 ~1 周期  →  共享内存 ~25 周期  →  L2 ~250 周期  →  HBM ~500 周期
  256 KB/SM        ≤228 KB/SM           50 MB 全芯片     80 GB / 3.35 TB/s

★ 共享内存比 HBM 快 20 倍以上 —— 这是全书所有"分块 + 片上复用"优化的根源
```

**四个坑，四个数字**

| 坑 | 症状 | 代价 | 解法 |
|---|---|---|---|
| Warp 分歧 | 同一 Warp 走不同分支 | 两条路耗时相加，通道利用率腰斩 | 把分支粒度提到 Warp 以上 |
| 未合并访存 | 相邻线程访问不连续地址 | 跨步 32 时浪费 **8 倍**带宽 | 让 `threadIdx.x` 对应变化最快的维度 |
| Bank Conflict | 同 Warp 撞同一 Bank 的不同地址 | 按列访问 32×32 tile = **32 倍**延迟 | Padding（`[32][33]`）或 Swizzle |
| 寄存器溢出 | 寄存器不够，变量挪到 HBM | 1 周期变 **500 周期** | `-Xptxas -v` 看 spill，调整 tile 大小 |

**两个不要误解的概念**

- **Occupancy 不是越高越好**：它是延迟掩盖的手段。需要多少，取决于"每搬一次数据能算多久"（`延迟 ÷ 单 Warp 计算时间`）。高性能 GEMM 常常只有 25–50%。
- **Tensor Core 不是自动生效的**：维度对不齐到 16 就会静默退回慢速路径。这也是大模型隐藏维度总是 128 倍数的原因。

**自测三题**（答案在本章对应小节）

1. `__shared__ float t[64][64]`，一个 Warp 执行 `t[threadIdx.x][0]`，是几路 Bank Conflict？改成 `t[64][65]` 之后呢？
2. 某 kernel 的 Grid 是 133 个 Block，每 SM 只放得下 1 个 Block。它的耗时大约是 132 个 Block 版本的几倍？机器利用率多少？
3. 一个 kernel 每线程用 64 个寄存器、Block 开 512 线程、不用共享内存。它在 H100 上的 Occupancy 是多少？瓶颈是哪个资源？

#### 参考答案

1. `t[r][0]` 的线性下标是 `r × 64`，对 32 取余恒为 0 → **32 路冲突**（一个 Warp 只有 32 个线程，所以是 32 路，不是 64 路）。改成 `t[64][65]` 后下标是 `r × 65`，而 `(r × 65) % 32 = (r × 64 + r) % 32 = r % 32`，r = 0…31 各不相同 → **冲突消除**。参见 §1.5.2–§1.5.3。
2. 两个波次（132 + 1），耗时 ≈ **2 倍**；利用率 = 133 ÷ (132 × 2) ≈ **50%**。多 1 个 Block，时间翻倍。参见 §1.2.4。
3. 每 Warp 需要 64 × 32 = 2048 个寄存器 → 65536 ÷ 2048 = **32 个 Warp**；Block 是 512 线程 = 16 个 Warp → 32 ÷ 16 = **2 个 Block** → 驻留 32 个 Warp → Occupancy = 32 ÷ 64 = **50%**，瓶颈是**寄存器**。参见 §1.6.2。
