02 · 屋顶线与性能剖析：判断一个算子"该有多快"

前置：01 章（GPU 硬件基础）
目标：学会用一个简单的模型判断任何算子的瓶颈在哪里，以及怎么用 Nsight 工具验证判断。
更具体地说：读完这一章，拿到任何一个算子，你应该能在不跑代码的情况下先算出"它最快能多快"，再用 profiler 去验证实测和这个上界差多少、差在哪。
读法：本章每个概念后面都跟一个带真实数字的小例子，例子里的算术都能自己验算。建议拿纸笔跟着算一遍——这一章的全部价值就在"能自己把那个数算出来"。

本章关键词

FLOP（Floating Point Operation，浮点运算次数）—— 一次浮点加或一次浮点乘记 1 FLOP。FLOPS（Floating Point Operations Per Second，每秒浮点运算次数）—— 速度单位。两者只差一个大小写的 S，一个是"总工作量"、一个是"干活速度"，混了后面全错。
算术强度（Arithmetic Intensity，简称 I）—— 每从显存搬运 1 字节，能完成多少次浮点运算，单位 FLOP/Byte。刻画算子"体质"的唯一核心数字。
Roofline Model（屋顶线模型）—— 用算术强度和硬件峰值推导理论性能上界的分析框架，2009 年由 Williams 等人提出。
屋脊点（Ridge Point）—— 算力屋顶和带宽斜线的交点，对应"算力和带宽恰好同时打满"的算术强度。H100 的 BF16 屋脊点是 295 FLOP/Byte。
Memory Bound（带宽受限）—— 算术强度低于屋脊点，算力空转等数据。
Compute Bound（算力受限）—— 算术强度高于屋脊点，带宽够用，算力打满。
Latency Bound（延迟受限）—— 算力和带宽都没打满，卡在依赖链或并行度不足上。屋顶线模型不覆盖这一类，是最容易误判的情况。
GEMM（General Matrix Multiply，通用矩阵乘）—— C = A × B，深度学习里最重要的算子。
GEMV（General Matrix-Vector multiply，通用矩阵向量乘）—— GEMM 在 M=1 时的退化形式，推理 Decode 阶段的主力，也是最典型的 Memory Bound 算子。
MFU（Model FLOPs Utilization，模型算力利用率）—— 模型必须完成的运算量 ÷ 硬件在同样时间内能提供的运算量。衡量一次训练"钱花得值不值"。
HFU（Hardware FLOPs Utilization，硬件算力利用率）—— 硬件实际执行的运算量 ÷ 峰值。和 MFU 的差额主要来自重计算。
Nsight Systems（简称 nsys）—— NVIDIA 官方的全局时间线剖析器，看"整体长什么样"。
Nsight Compute（简称 ncu）—— NVIDIA 官方的单 kernel 深度剖析器，看"这一个 kernel 内部发生了什么"。
Speed Of Light（SOL，"光速"）—— ncu 报告里最重要的一屏，直接给出算力和带宽各用了峰值的百分之多少。
有效带宽（Effective Bandwidth）—— 手算出来的字节数 ÷ 实测时间。没有 profiler 时唯一能自己算的诊断指标。

2.1 先算一笔账：batch=1 和 batch=64 的矩阵乘，为什么一样快

先不讲模型，做一道算术题。

import torch
W = torch.randn(4096, 4096, dtype=torch.float16, device='cuda')   # 一层的权重

x1  = torch.randn(1,  4096, dtype=torch.float16, device='cuda')   # 推理 Decode：一次一个 token
x64 = torch.randn(64, 4096, dtype=torch.float16, device='cuda')   # 训练 / 批量推理：一次 64 个

torch.matmul(x1,  W)    # 计算量 = 2 × 1  × 4096 × 4096 = 33.6 MFLOP
torch.matmul(x64, W)    # 计算量 = 2 × 64 × 4096 × 4096 = 2.15 GFLOP，是上面的 64 倍

第二行的计算量是第一行的 64 倍。直觉会说：第二行慢 64 倍。把两边的账都算一遍：

x1 @ W（M=1） x64 @ W（M=64）
计算量 FLOP 2×1×4096×4096 = 33.6 M 2×64×4096×4096 = 2147 M
读权重 W 4096×4096×2 B = 33.55 MB 4096×4096×2 B = 33.55 MB（一模一样）
读输入 x 1×4096×2 B = 0.008 MB 64×4096×2 B = 0.52 MB
写输出 y 1×4096×2 B = 0.008 MB 64×4096×2 B = 0.52 MB
搬运总量 33.57 MB 34.60 MB
搬完要多久（÷3350 GB/s） 10.02 µs 10.33 µs
这段时间里的有效算力 33.6 M ÷ 10.02 µs = 3.35 TFLOPS 2147 M ÷ 10.33 µs = 208 TFLOPS
占 FP16 峰值 989 TFLOPS 0.34% 21.0%

计算量多了 64 倍，时间只多了 3%。

原因只有一句话：两种情况都必须把同一份 33.55 MB 的权重从 HBM（高带宽显存）完整读一遍，而这件事就要 10 µs。M=1 时，读进来的每个权重只被用了 1 次（乘 1 个输入元素）就扔掉了；M=64 时，同一个权重被用了 64 次。搬运成本一样，摊到的计算量差 64 倍。

★ 这就是本章要反复用的那把尺子：一个算子快不快，不取决于它算得多，而取决于"每搬 1 字节，能算几次"。这个比值就叫算术强度。M=1 时它是 1，M=64 时它是 62。整个屋顶线模型，就是把这个比值和硬件的两个峰值放在一起比。

⚠️ 上表里的时间是理论下界（假设带宽 100% 打满、没有启动开销）。实测会更大：H100 上这两个 kernel 大约都在 15–25 µs（⚠️ 实测量级，随 cuBLAS 版本和时钟浮动），因为实际有效带宽通常只有峰值的 80–90%，还要加 3–10 µs 的 kernel 启动开销（01 章 §1.8.2）。但"两者几乎一样快"这个结论非常稳健——实测比值同样在 1.0–1.1 之间。

⚠️ 顺带纠正一个常见的误读：不能因为 x1 @ W 只花 10 µs 就说"推理很快"。它快得毫无意义——花了 10 µs 只算出 4096 个数，GPU 有 99.66% 的算力在空转。真实的推理 Decode 要把这件事在几十层 × 几百个 token 上重复做，累积起来就是延迟。

2.2 算术强度：唯一需要记住的那个数字

2.2.1 定义和最小的例子

算术强度 I = 总浮点运算次数 (FLOP) ÷ 总显存搬运字节数 (Byte)

单位：FLOP/Byte

最简单的例子，y[i] = x[i] * 2，float（FP32，4 字节）：

每个元素：
  算 ——  1 次乘法                      = 1 FLOP
  搬 ——  读 x[i] 4 字节 + 写 y[i] 4 字节 = 8 Byte

I = 1 ÷ 8 = 0.125 FLOP/Byte

注意 I 是一个和数组多大无关的数：N = 1000 还是 N = 10 亿，每个元素的账都是"1 FLOP / 8 Byte"。算术强度刻画的是算子的形状，不是它的规模。 这正是它有用的地方——你在写代码之前就能算出来。

2.2.2 数 Byte 的三条规矩（比数 FLOP 难得多）

数 FLOP 一般不会错（加和乘各算 1 次，矩阵乘是 2MKN）。出错基本都出在数 Byte 上。 三条规矩：

数据从显存到计算单元，要过三道门：

  HBM 显存 (80 GB, 3.35 TB/s)
    │
    │  第 1 道门：HBM <-> 芯片          ★ 屋顶线的分母只数这一道
    ↓
  L2 缓存 (50 MB, 全芯片共享)
    │
    │  第 2 道门：L2 <-> SM             流量再大也不进分母
    ↓
  共享内存 / 寄存器 (<=228 KB/SM)
    │
    │  第 3 道门：片上 <-> 计算单元      同上，不进分母
    ↓
  CUDA Core / Tensor Core

把访问从第 1 道门挪到第 2、3 道门，就是「片上复用」，
也是提高算术强度的全部机制。

规矩一：只数 HBM 的往返，不数片上的读写。 一块数据搬进共享内存后被读 100 次，那 100 次不算。GEMM 分块（03 章）、FlashAttention（04 章）提高算术强度，靠的就是把访问从 ① 挪到 ②③。

规矩二：默认口径是"每份数据从 HBM 读一次、写一次"。 这是乐观口径，给出的是 I 的上界、时间的下界。如果实现得不好（比如同一个数组读了两遍），实际字节数会更大，实际 I 更低——§2.7.4 的走查里就抓到了这样一个 bug。

规矩三：中间结果如果没落回 HBM，就不进分母。 这是算子融合（05 章）提高 I 的机制：两个算子串联，中间那个张量本来要写出去再读回来（2 次往返），融合后它只在寄存器里存在（0 次往返）。

⚠️ 最常见的两个数错：

① 忘了权重每次都要重读。 "权重是常量，应该会被缓存吧？"——一层权重 33.55 MB，L2 只有 50 MB，整个模型有几十层几百个权重矩阵，等你转回来这一层的权重早被挤出去了。Decode 阶段每生成一个 token，都要把全部权重从 HBM 完整读一遍。 这是大模型推理速度的物理上限，也是 §2.1 那道题的本质。

② 把中间张量漏掉。 朴素 Attention 的 S = QKᵀ 矩阵大小是 B×H×N×N，序列长 8192 时单是这一个中间结果就 4 GB（见 附-速查表 §B.4），写出去再读回来是 8 GB 的流量。只数 Q、K、V、O 会把算术强度算高一个数量级。

2.2.3 GEMM 的通式

矩阵乘 C = A × B，A 是 M×K，B 是 K×N，C 是 M×N，元素 s 字节（FP16/BF16 时 s = 2）：

FLOP  = 2 · M · K · N          （每个输出元素要 K 次乘 + K 次加）
Byte  = s · (M·K + K·N + M·N)  （读 A + 读 B + 写 C，各一遍）

           2 · M · K · N                    2 · M · K · N
I  =  ───────────────────────────  =  ─────────────────────────
       s · (M·K + K·N + M·N)           2 · (M·K + K·N + M·N)      ← s=2 时

把三种典型形状代进去（全部 FP16，s = 2）：

场景 M K N FLOP Byte I 相对 295
推理 Decode（GEMV） 1 4096 4096 33.6 M 33.57 MB 1.0 差 295 倍
小批量训练 64 4096 4096 2147 M 34.60 MB 62 差 4.8 倍
大方阵 4096 4096 4096 137.4 G 100.66 MB 1365 超出 4.6 倍

从中能读出一条通用规律：当 M ≪ K, N 时，分母被 K·N（读 B）主导，分子是 2MKN，所以 I ≈ 2M。 M=1 → I≈2（实测 1，因为还要读 A 写 C）；M=64 → I≈128（实测 62，因为 M 还不够小，M·K 和 M·N 项开始起作用）。推理想变快，最直接的旋钮就是把 M 变大，这就是连续批处理（Continuous Batching，09 章）存在的理由。

★ 一句话记住：GEMM 的算术强度大约是 min(M, N, K) 的量级。三个维度里最小的那个决定了数据能被复用几次。

2.3 把六个真实算子的算术强度算出来

下面六个算子，覆盖了大模型训练和推理里 90% 的时间。每一个都把 FLOP 和 Byte 逐项列出来，你可以自己验算。硬件统一按 H100 SXM5（BF16 稠密峰值 989 TFLOPS，HBM3 带宽 3350 GB/s）。

A · 逐元素乘 y = x * 2（FP32）

每元素 FLOP = 1（一次乘法）
每元素 Byte = 4（读 x）+ 4（写 y）= 8

I = 1 / 8 = 0.125 FLOP/Byte
屋顶线上界 P = 3350 GB/s × 0.125 FLOP/Byte = 419 GFLOPS = 0.42 TFLOPS

这是整本书里算术强度最低的算子。它的上界 0.42 TFLOPS，只占 FP32 峰值（67 TFLOPS）的 0.63%——而且这已经是理论最优，再怎么优化计算部分都不会更快。

B · SiLU 激活 与 Decode GEMV（BF16）—— 两个毫不相干的算子，落在同一个点

SiLU（y = x · sigmoid(x)，LLaMA 系列的激活函数）：

每元素 FLOP ⚠️ ≈ 4  （exp 按 1 条 SFU 指令记 1 FLOP，再加 1 加、1 除、1 乘）
每元素 Byte = 2（读 x，BF16）+ 2（写 y）= 4

I ≈ 4 / 4 = 1.0 FLOP/Byte

Decode GEMV（§2.1 的 M=1 情形）：

FLOP = 33.55 M，Byte = 33.57 MB
I = 1.0 FLOP/Byte

一个是矩阵乘法的退化形式，一个是一行标量运算，算术强度完全一样 = 1.0。

→ 在屋顶线上它们是同一个点，理论上界都是 3350 × 1 = 3.35 TFLOPS。
→ 但绝对耗时天差地别：
     SiLU 在 [8192, 4096] 上要搬 33.55M × 4 B = 134.2 MB，耗时 40 µs
     Decode GEMV 要搬 33.6 MB，耗时 10 µs

★ 算术强度只告诉你"效率"，不告诉你"耗时"。 耗时 = 字节数 ÷ 带宽。判断"该不该优化这个算子"要看 nsys 里它占总时间的百分比；判断"优化它还有多少空间"才看算术强度。两件事不能混。

⚠️ 超越函数（exp / tanh / rsqrt）的 FLOP 该记 1 还是记 10，业界没有统一口径——它在硬件上是 SFU（Special Function Unit，特殊函数单元）的一条指令，但等价的软件实现要十几次运算。本书统一按 1 条指令 = 1 FLOP 记，并标 ⚠️。好在这类算子都深陷 Memory Bound，分子记 1 还是 10 都改不了结论。

C · LayerNorm（BF16，形状 [T, H]）

把每个元素上发生的运算数出来：

步骤 做什么 每元素 FLOP
① 求均值 sum += x 1（加）
② 求方差 sum2 += (x - mean)² 3（减、乘、加）
③ 归一化输出 y = (x - mean) × inv_std × γ + β 4（减、乘、乘、加）
合计 8

（每行另有 2 次除法和 1 次 rsqrt，被 H 个元素摊薄，忽略。）

每元素 Byte = 2（读 x）+ 2（写 y）= 4
              γ、β 各 H 个元素，被 T 行摊薄，忽略

I = 8 / 4 = 2.0 FLOP/Byte
屋顶线上界 P = 3350 × 2.0 = 6.7 TFLOPS  ← 占 989 峰值的 0.68%

RMSNorm 省掉了减均值和加 β：每元素 = 1（平方）+ 1（累加）+ 1（乘 inv_rms）+ 1（乘 γ）= 4 FLOP，Byte 不变，所以 I = 1.0。RMSNorm 计算更省，但算术强度反而更低——因为省掉的是分子，分母一点没变。

★ 这条规律很反直觉，值得单独记：在 Memory Bound 区里，"减少计算量"的优化一点用都没有，甚至会让算术强度变得更难看。 唯一有用的是减少字节数。

D · 训练 GEMM，M=64（BF16）

§2.1 已经算过：

FLOP = 2147 M，Byte = 34.60 MB
I = 62 FLOP/Byte
屋顶线上界 P = 3350 × 62 = 208 TFLOPS  ← 占 989 峰值的 21.0%

注意这个数：一个"看起来像训练主力"的 GEMM，理论天花板只有峰值的 21%。这就是为什么大模型训练要把 batch 堆到几百上千，而不是 64。

E · 大方阵 GEMM，4096×4096×4096（BF16）

FLOP = 2 × 4096³ = 137.44 GFLOP
Byte = 3 × 4096² × 2 = 100.66 MB

I = 137.44e9 / 100.66e6 = 1365 FLOP/Byte    ← 远超屋脊点 295

→ Compute Bound。上界 = 989 TFLOPS（算力屋顶），不再受带宽约束。
  理论最短时间 = 137.44 GFLOP ÷ 989 TFLOPS = 139 µs
  （带宽侧只需要 100.66 MB ÷ 3350 GB/s = 30 µs，绰绰有余）

⚠️ 实测量级：cuBLAS 在 H100 上跑这个形状大约 600–750 TFLOPS（随库版本、时钟、功耗墙浮动），对应 183–229 µs。离 989 的差距不是带宽造成的，是 Tensor Core 的流水线、尾巴效应、功耗降频造成的——这类问题屋顶线模型看不见，要靠 03 章。

F · FlashAttention-2 前向（BF16，单头，N=4096，d=128，Q 块边长 Br=128）

FLOP = 4·N²·d               （QKᵀ 是 2N²d，PV 又是 2N²d）
     = 4 × 4096² × 128 = 8.59 GFLOP

Byte（悲观口径：每个 Q 块都把完整的 K、V 从 HBM 读一遍）
  Q 读一遍 + O 写一遍 = 2 × 4096 × 128 × 2 = 2.10 MB
  Q 块数 = 4096 / 128 = 32
  每块读一遍 K+V     = 2 × 4096 × 128 × 2 = 2.10 MB
  K/V 总流量         = 32 × 2.10 = 67.1 MB
  合计               = 69.2 MB

I = 8.59e9 / 69.2e6 = 124 FLOP/Byte
屋顶线上界 P = 3350 × 124 = 415 TFLOPS   ← 占 989 峰值的 42%

把上面的式子化简一下，会得到一个漂亮的结论：

I = 4N²d / (4Nd + 4N²d/Br) = N / (1 + N/Br) ≈ Br     （N ≫ Br 时）

→ FlashAttention 的算术强度 ≈ Q 分块的边长 Br。
   Br=128 → I≈128；Br=64 → I≈64。分块开多大，算术强度就是多少。

⚠️ 这个 415 TFLOPS 的"上界"会被实测打脸：FlashAttention-3 在 H100 上实测约 810 TFLOPS（附-速查表 §D），是"上界"的两倍。不是测错了，是模型的口径错了——单头的 K、V 一共只有 2.1 MB，远小于 50 MB 的 L2 缓存，那 32 遍重读绝大部分命中 L2，根本没走 HBM。屋顶线的分母只数 HBM，L2 命中的流量是"免费"的。这是屋顶线模型的第一个盲区，§2.5 详细讲。

2.4 屋顶线模型：把六个点画在同一张图上

2.4.1 两条限制线

任何算子的性能都同时受两个上限约束：

① 算力上限：再快也不可能超过硬件峰值算力
     P ≤ 989 TFLOPS                         ← 一条水平线，和 I 无关

② 带宽上限：每秒最多搬 3350 GB，每字节最多算 I 次
     P ≤ 3350 GB/s × I FLOP/Byte            ← 一条过原点的斜线，斜率 = 带宽

合起来：  P ≤ min(989 TFLOPS,  3350 × I)

两条线的交点就是屋脊点：

989 × 10¹² FLOP/s  ÷  3.35 × 10¹² Byte/s  =  295 FLOP/Byte

屋脊点的物理含义：每搬 1 字节必须算满 295 次浮点运算，才能让算力和带宽同时打满。少于 295，算力必然有空转；多于 295，带宽必然有富余。

2.4.3 读图的三条规则

规则一：在斜线上，性能和算术强度严格成正比。 想让一个 Memory Bound 算子快一倍，只有三条路：

① 把 I 翻倍  →  减少字节数（融合、量化）或提高片上复用（分块）
② 换带宽更大的卡（斜线更陡）
③ 没有第三条路

★ 优化计算部分（换更快的指令、减少运算次数）在斜线区完全无效 ——
  这就是 §2.3 里 RMSNorm 比 LayerNorm 少算一半、却一点不更快的原因。

规则二：上了屋顶之后，再提高 I 没有任何收益。 点 E 的 I 是 1365，屋脊点是 295，富余 4.6 倍。就算把 I 提到 3000，性能还是 989 封顶。这时唯一的方向是把屋顶抬高：换更低的精度。

规则三：屋脊点不是一个数，是每种计算单元一个数。 H100 上至少有四条屋顶线：

计算单元 峰值算力（稠密） 屋脊点 = 峰值 ÷ 3350 GB/s
FP32 CUDA Core 67 TFLOPS 20 FLOP/Byte
TF32 Tensor Core 494 TFLOPS 147 FLOP/Byte
BF16 / FP16 Tensor Core 989 TFLOPS 295 FLOP/Byte
FP8 Tensor Core 1979 TFLOPS 591 FLOP/Byte

★ 这张表解释了一个容易踩的坑：同一个算子，换个精度，Memory/Compute Bound 的结论可能就反过来了。 点 D（I=62）在 BF16 Tensor Core 上是 Memory Bound（62 < 295），但如果它跑在 FP32 CUDA Core 上，I 会变成 31（字节数翻倍），而 FP32 的屋脊点只有 20——31 > 20，它变成 Compute Bound 了。所以"这个算子是 Memory Bound"这句话不完整，必须说"在哪个计算单元上"。

⚠️ 1979 TFLOPS 是 FP8 的稠密值。 NVIDIA 官方表里每个精度都有"稠密/稀疏"两列，稀疏值是稠密的 2 倍（BF16 稀疏 1979、FP8 稀疏 3958），但要求权重满足 2:4 稀疏模式，常规算子用不上。本系列统一用稠密值，和 01 章、附-速查表 §A 一致。把 BF16 的稀疏值 1979 当稠密用，会把屋脊点算成 591，所有结论都要错。

2.4.4 量化为什么总是有用：一次完整的推演

把点 B（Decode GEMV，权重 BF16）的权重量化成 FP8，重算一遍：

                        BF16 权重              FP8 权重
  FLOP                  33.55 M                33.55 M        （不变）
  读权重                33.55 MB               16.78 MB       （减半）
  算术强度 I            1.0                    2.0            （翻倍）
  该单元的屋脊点        295                    591            （也翻倍！）
  I / 屋脊点            0.0034                 0.0034         （相对位置没变）
  ────────────────────────────────────────────────────────────
  屋顶线上界 P          3350 × 1 = 3.35        3350 × 2 = 6.70 TFLOPS
  搬完要多久            10.0 µs                5.0 µs         ← 时间减半 ✓

看清楚这里发生了什么：量化把算术强度翻倍，同时把屋脊点也翻倍，所以算子在屋顶线图上的相对位置一点没变——它仍然一样"贫瘠"。但绝对时间减半了，因为要搬的字节少了一半。

★ 在 Memory Bound 区里，量化的收益 100% 来自"字节变少"，和"FP8 算得更快"没有半点关系。 这也解释了为什么推理量化通常只量化权重（W8A16）就能拿到大部分收益：Decode 的字节数几乎全是权重。详见 06 章。

2.5 屋顶线的三个盲区

屋顶线模型极其好用，但它是个极简模型，有三类问题它根本看不见。不知道这三个盲区，就会对着一个"明明在屋顶线附近"的算子束手无策。

盲区一：L2 缓存 —— 实测可以超过"上界"

§2.3 的点 F 已经撞上了：按"K/V 每个 Q 块重读一遍"算出 I=124、上界 415 TFLOPS，但 FlashAttention-3 实测 810 TFLOPS。

原因：单头的 K、V 一共只有 2.1 MB，而 H100 的 L2 有 50 MB。
      那 32 遍"重读"里，绝大多数命中 L2，根本没经过 HBM。

屋顶线的分母只数 HBM 往返。命中 L2 的流量在这个模型里是免费的。

→ 同一个算子有两个算术强度：
    悲观口径，每次重读都算 HBM     ： I = 124，上界 415 TFLOPS
    乐观口径，Q/K/V/O 各读写一遍   ： I = N/2 = 2048，Compute Bound
  真相在两者之间，而且更靠近乐观那一侧。

怎么处理：先用悲观口径算一个保守上界。如果实测已经超过它，说明 L2 在帮忙，直接换乐观口径重算。永远不要因为"实测超过了我算的上界"就怀疑测量出错——先怀疑自己的 Byte 数错了。

同样的事也发生在 GEMM 上：只做一级分块、分块边长 T 时，算术强度大约是 T/2（推导见 03 章），T=128 → I=64，上界只有 214 TFLOPS。但实测大方阵 GEMM 能跑到 700 TFLOPS，因为真实的 GEMM 有三级分块 + L2 复用，实际 HBM 流量接近"每个元素只读一遍"的理想值（I=1365）。

盲区二：延迟受限（Latency Bound）—— 算力和带宽都没打满

屋顶线假设"要么算力满、要么带宽满"。但现实中最常见的状态是两个都不满：

典型症状（ncu 里看到）：
    Compute (SM) Throughput   8%
    Memory   Throughput      15%     ← 两个都低，屋顶线解释不了

常见成因：
    ① kernel 太小，启动开销（3–10 µs）占了大头 —— 01 章 §1.8.2
    ② Occupancy 太低，没有足够的 Warp 掩盖访存延迟 —— 01 章 §1.6
    ③ 依赖链太长（归约、串行循环），并行度不足
    ④ 同步点太多（__syncthreads / 原子操作排队）
    ⑤ Warp 分歧，一半通道空转 —— 01 章 §1.2.5

判据很简单：两个 Throughput 都低于 40%，就别看屋顶线了，去看 ncu 的 Warp State / Stall Reasons。

盲区三：kernel 之间的空隙 —— 屋顶线是"kernel 内部"的模型

屋顶线预测：这个 kernel 要 2.4 µs
实测：      12 µs

差距在哪？kernel 启动就要 5 µs，前一个 kernel 结束到这个开始之间还有
CPU 侧的调度间隙。屋顶线画的是「kernel 跑起来之后」的事，
完全看不见 kernel 之间的空白。

这对应 00 章 §0.4 诊断漏斗的第 ① 步，而屋顶线是第 ③ 步。顺序不能颠倒：如果 GPU 有 40% 的时间在空转，你把每个 kernel 都优化到屋顶线上，整体也只能快 60%。先看整体，再看单个。

⚠️ 还有一个"打折"因素，严格说不算盲区但一定要记住：峰值带宽是跑不满的。实际能达到的最高有效带宽通常是峰值的 80–90%（⚠️ 实测量级）。所以判断"这个 Memory Bound 算子到顶了没有"，标准是有效带宽 ≥ 峰值的 80%，不是 100%。

2.6 MFU：把一个训练任务的效率算出来

算术强度衡量单个算子。MFU（Model FLOPs Utilization，模型算力利用率）衡量整个训练任务。

          模型必须完成的浮点运算总量
MFU  =  ────────────────────────────────────
         硬件在同样时间内能提供的运算总量

2.6.1 分子里的 6N 是从哪来的

几乎所有 MFU 计算都写成 每 token 的 FLOPs ≈ 6N（N = 参数量）。这个 6 不是经验常数，是能数出来的。

拿一个 Linear 层：权重 W 的形状是 [H_in, H_out]，参数量 n = H_in × H_out。对 1 个 token：

阶段 算什么 矩阵形状 FLOP
前向 y = x·W (1×H_in) × (H_in×H_out) 2·H_in·H_out = 2n
反向 · 传给上一层 dx = dy·Wᵀ (1×H_out) × (H_out×H_in) 2n
反向 · 算权重梯度 dW = xᵀ·dy (H_in×1) × (1×H_out) 2n
合计 6n

把模型里所有带参数的层加起来，就是每 token 6N FLOP。

⚠️ 三条必须知道的说明：

① 优化器更新不算在里面。 AdamW 更新是 per-step、per-parameter 的，不随 token 数增长；batch 大的时候它被完全摊薄。（附-速查表 §B.3 写的"包含前向 + 反向 × 2 + 优化器"里的"+ 优化器"是不准确的，6N 就是 2N 前向 + 4N 反向。）

② Attention 的 QKᵀ 和 PV 不含参数，6N 漏算了它们。 补全的式子是 每 token FLOPs ≈ 6N + 12·L·s·H（L = 层数，s = 序列长，H = 隐藏维度）。拿 LLaMA-3 8B、s=8192 代一下：6N = 4.8e10，12 × 32 × 8192 × 4096 = 1.29e10——漏算了 27%。序列越长漏得越多。

③ 尽管如此，业界统一用 6N 这个保守口径，因为它只依赖参数量，不依赖序列长和实现细节，横向可比。引用任何 MFU 数字时，先确认对方用的是不是 6N。

2.6.2 一次完整代入：DeepSeek-V3

DeepSeek-V3 技术报告（arXiv:2412.19437）✅ 官方披露了三个数：

总参数 671 B，每 token 激活 37 B          ← MoE 模型，N 取「激活参数量」
预训练 token 数        14.8 T
预训练 GPU 小时        2.664 M H800 GPU·小时

再加一个硬件常数：H800 的 BF16 稠密峰值 = 989 TFLOPS（和 H100 SXM5 完全相同——H800 被限制的是 NVLink 互联带宽，不是算力）。

分子：模型必须完成的 FLOP

= token 数 × 6 × 激活参数量
= 14.8 × 10¹²  ×  6  ×  37 × 10⁹
= 14.8 × 10¹²  ×  2.22 × 10¹¹
= 3.286 × 10²⁴ FLOP

分母：硬件提供的 FLOP 预算

= GPU 小时 × 3600 秒/小时 × 峰值 FLOPS

= 9.590 × 10⁹ GPU·秒  ×  9.89 × 10¹⁴
= 9.485 × 10²⁴ FLOP

MFU

MFU = 3.286 × 10²⁴ ÷ 9.485 × 10²⁴ = 34.6%

换算成更直观的说法：

每卡每秒的有效算力 = 3.286e24 ÷ 9.590e9 = 3.43 × 10¹⁴ = 343 TFLOPS/卡
                                            （峰值 989 的 34.6%）

⚠️ 34.6% 是我们用三个官方数字推算的，DeepSeek 报告本身没有直接给 MFU。

⚠️ 更要紧的一句：DeepSeek-V3 的大部分 GEMM 跑在 FP8 上，FP8 峰值是 1979 TFLOPS。如果分母换成 FP8 峰值，MFU 只有 17.3%。同一次训练，分母不同，MFU 差一倍。 业界惯例是按 BF16 稠密峰值报（否则不同精度之间没法比），但引用任何 MFU 数字之前都要先问一句"分母是哪个峰值"。

2.6.3 MFU vs HFU：重计算造成的那个缺口

MFU（模型算力利用率）= 模型「必须做」的 FLOP ÷ 峰值
HFU（硬件算力利用率）= 硬件「实际做了」的 FLOP ÷ 峰值

HFU ≥ MFU，差额主要来自「重计算」

重计算（Activation Recomputation / Gradient Checkpointing，梯度检查点）：为了省显存，前向时不保存中间激活值，反向需要时重新跑一遍前向。这部分 FLOP 硬件确实执行了（计入 HFU），但模型本来不需要它们（不计入 MFU）。

PaLM 论文 ✅ 同时报了两个数，缺口一目了然：

PaLM 540B（6144 块 TPU v4）：
    MFU = 46.2%
    HFU = 57.8%
    ──────────────
    缺口 11.6 个百分点  ← 这就是重计算烧掉的算力

★ 两个指标各回答一个问题：想知道"这笔训练预算花得值不值"，看 MFU；想知道"kernel 写得好不好、硬件用得满不满"，看 HFU。一个 MFU 只有 35% 的训练，如果 HFU 已经有 55%，那问题不在 kernel 上，而在"要不要少开点重计算、多用点显存"。

2.7 Nsight 工作流：从一条命令到一个结论

2.7.1 三步漏斗，顺序不能换

第 1 步 · 用 nsys 看全局：整个训练步长什么样？
  ├── GPU 有没有空着？
  │     有大片空白 → 下发问题，先解决它，不用往下走
  ├── 通信占多少？
  │     占比高 → 去 08 章做通信-计算重叠，不用往下走
  └── 哪 10 个 kernel 最耗时？
        按耗时排序，只处理前几名
              ↓ 选中一个 kernel

第 2 步 · 用纸笔算：这个 kernel 理论上最快能多快？
  ├── 数 FLOP、数 Byte，算出算术强度 I
  ├── 查屋顶线，得到理论时间下界
  └── 实测 ÷ 理论 = 几倍？
        小于 1.5 倍 → 到顶了，停手，换个层次（融合掉它、改算法）
        大于 2 倍   → 有东西可挖，继续
              ↓

第 3 步 · 用 ncu 深挖：这个差距从哪来？
  ├── Memory 高、Compute 低      → Memory Bound，走 2.8 节的四条路
  ├── Compute 高、Memory 低      → Compute Bound，只能换 kernel 或降精度
  ├── 两个都高                   → 健康，别动
  ├── 两个都低                   → 延迟受限，查 Warp State / Stall Reason
  └── 实际 DRAM 字节和手算对不上  → 是你数错了，回第 2 步重数

★ 第 ② 步是最容易被跳过的一步，也是最省时间的一步。 不先算出"应该多快"，profiler 甩给你几十个百分比，你也不知道 63% 算好还是算坏。先有基准，再看报告。

  ① compute 行上有大片空白   —— Host 下发跟不上，用 CUDA Graph 或算子融合

  ③ compute 行全是又短又密的小块 —— 大量小 kernel，融合，见 05 章

⚠️ nsys 的时间线按 Stream（流）分行，不按 SM 分行。它看不到 GPU 内部 132 个 SM 各自在干什么——那是 ncu 的活。想知道"kernel 之间有没有空隙"看 nsys，想知道"kernel 内部 SM 忙不忙"看 ncu。

2.7.4 一次完整走查：从 18% 的耗时到 45 µs

⚠️ 本节所有耗时都是为演示流程构造的自洽数字，不是某次真实测量。但每一步的算术都是真的，可以自己验算。

背景：某 7B 模型训练，nsys 显示 rms_norm_kernel 占 GPU 时间 18%，单次 95 µs。输入形状 [8192 tokens, 4096 hidden]，BF16。

第 ① 步 · 纸笔算下界

元素数 = 8192 × 4096 = 33.55 M

Byte = 读 x   33.55 M × 2 = 67.1 MB
     + 写 y   33.55 M × 2 = 67.1 MB
     + 读 γ   4096   × 2 = 8 KB（忽略）
     = 134.2 MB

理论最短时间 = 134.2 MB ÷ 3350 GB/s = 40.1 µs

实测 95 µs ÷ 理论 40.1 µs = 2.37 倍       ← 超过 2 倍，值得查

第 ② 步 · ncu 看 Speed Of Light

Compute (SM) Throughput    5.1%      ← 符合预期，RMSNorm 的 I 只有 1
DRAM Throughput           63.4%      ← 带宽只用了 63%，不该这么低
dram__bytes_read.sum     201.3 MB    ← ★ 手算是 67.1 MB，实际读了 201.3 MB！
dram__bytes_write.sum     67.1 MB    ← 写的对得上

★ dram__bytes_read.sum 这一行就是整个诊断的转折点。 实际从 HBM 读进来的字节是手算的 3 倍。这种事靠盯代码是看不出来的，只有 profiler 能告诉你。

第 ③ 步 · 找原因

67.1 MB → 201.3 MB，正好 3 倍。x 被读了 3 遍？数一下 kernel 干了什么：

  第 1 遍读 x：算 Σx²（求均方根）
  第 2 遍读 x：算 y = x × inv_rms × γ
  第 3 遍？   → 检查发现每个 Block 只处理 1/3 行，同一行被 3 个 Block
                各读了一遍 —— 分块策略和行长对不上

根因：① 中间没把 x 留在片上，第二遍又去 HBM 取
      ② 一行 4096 个元素被拆给了 3 个 Block，重复读

第 ④ 步 · 改法

一行 = 4096 个 BF16 = 8 KB
一个 Block 的共享内存上限 228 KB（01 章 §1.2.2）—— 一行完全装得下

改成「一个 Block 处理一整行」：
    读 x → 存进共享内存 → 算 Σx² → 从共享内存里再读 x → 写 y

HBM 流量：201.3 MB → 134.2 MB

第 ⑤ 步 · 复测

95 µs → 63 µs

有效带宽 = 134.2 MB ÷ 63 µs = 2130 GB/s = 峰值的 64%
还差 63 ÷ 40.1 = 1.57 倍                     ← 还没到 1.5 倍以内，再来一轮

第 ⑥ 步 · 第二轮，ncu 看 Memory Workload Analysis

现象：字节数对了，但请求数（sectors / requests）异常高

原因：每个线程只读 1 个 BF16 = 2 字节
      一个 Warp（32 线程）一次只请求 64 字节，而扇区是 32 字节
      → 访存指令发射次数是「每线程读 8 个 BF16」写法的 8 倍
      → 瓶颈从带宽转移到了指令发射

改法：向量化。每线程用 float4（16 字节 = 8 个 BF16）
      一个 Warp 一次请求 512 字节 = 16 个完整扇区

第 ⑦ 步 · 再复测，然后停手

63 µs → 45 µs

有效带宽 = 134.2 MB ÷ 45 µs = 2980 GB/s = 峰值的 89%   ← 到 80–90% 区间了
45 µs ÷ 40.1 µs = 1.12 倍                              ← < 1.5 倍，停手

第 ⑧ 步 · 真正的大头在下一个层次

这个 kernel 本身已经榨干了。但它可以整个消失 ——
把 RMSNorm 融进后面那个 GEMM 的 Prologue（前置段），
或者和前面的残差加融在一起：134.2 MB 的 HBM 往返直接归零。

95 µs → 63 µs → 45 µs → 0 µs
   └────── kernel 内优化，2.1 倍 ──────┘   └─ 换层次，∞ ─┘

★ 这就是屋顶线最大的价值：它不只告诉你天花板在哪，还告诉你什么时候该停下来换个层次想问题。 一个已经跑到有效带宽 89% 的 kernel，再花一周也顶多再快 10%；而把它融掉是 100%。详见 05 章。

2.7.5 没有 Nsight 时的穷人版

开发机上没装 Nsight、或者只想快速看一眼时，两行代码就够：

import torch, time

def bench(fn, warmup=20, iters=100):
    for _ in range(warmup):
        fn()                     # ① 必须预热：第一次调用含 JIT 编译 / cuBLAS 选 kernel
    torch.cuda.synchronize()     # ② 必须同步：不加这行测到的是「往队列里塞命令」的时间
    t0 = time.perf_counter()
    for _ in range(iters):
        fn()
    torch.cuda.synchronize()     # ③ 结束也要同步
    return (time.perf_counter() - t0) / iters

拿到时间之后，两个手算数字就能下结论：

有效带宽 (GB/s)  = 手算 Byte  ÷ 实测时间
有效算力 (TFLOPS) = 手算 FLOP ÷ 实测时间

有效带宽 ÷ 3350  ≥ 0.8   →  Memory Bound 且已到顶，去 §2.8 换思路
有效算力 ÷ 989   ≥ 0.8   →  Compute Bound 且已到顶，只能降精度
两个都 < 0.3            →  延迟受限，查启动开销 / Occupancy / 分歧

拿 §2.7.4 的例子走一遍：

版本 实测 有效带宽 ÷ 3350 结论
初版 95 µs 1413 GB/s 0.42 远没到顶，继续查
修完重复读 63 µs 2130 GB/s 0.64 还有余量
向量化之后 45 µs 2980 GB/s 0.89 到顶，停手

⚠️ 穷人版的两个坑，都会让你测出一个好得离谱的数字：① 不 synchronize，测到的只是 CPU 把命令塞进 CUDA Stream 的时间（01 章 §1.8.1），可能只有 5 µs；② 不 warmup，第一次调用包含 kernel 编译、cuBLAS 算法选择、显存分配的开销，会测出一个坏得离谱的数字。

2.8 确认 Memory Bound 之后：四条路，各能省多少

前面所有分析，最后都收敛到同一件事：把算术强度提上去，或者把字节数降下来。 只有四条路，每条都在后面有专门的一章。

方向 手段 用 §2.3 的例子算一遍收益 去哪一章
减少字节 算子融合：LayerNorm + SiLU 串联 → 合成一个 kernel 不融合：134.2 + 134.2 = 268.4 MB；融合后中间张量不落 HBM：134.2 MB。I 从 1.5 提到 3.0，时间减半 05 章
减少字节 量化：Decode 的权重 BF16 → FP8 读权重 33.55 MB → 16.78 MB，I 从 1.0 提到 2.0，时间从 10.0 µs 降到 5.0 µs 06 章
提高复用 分块：把 tile 搬进共享内存反复用 朴素 GEMM 每个输出元素都从 HBM 读 2K 个数，I ≈ 0.5；分块边长 T 之后 I ≈ T/2，T=128 → I=64（128 倍） 03 章、04 章
增大 batch 让更多计算共享同一份权重读取 Decode batch 1 → 64：时间 10.02 → 10.33 µs（+3%），吞吐 62 倍 09 章

（融合那一行的 I：LayerNorm 8 FLOP/元素 + SiLU 4 FLOP/元素 = 12 FLOP/元素 × 33.55 M = 402.7 MFLOP。不融合 402.7 M ÷ 268.4 MB = 1.5；融合后 402.7 M ÷ 134.2 MB = 3.0。）

★ 注意这四条路都在动分母（字节数），没有一条在动分子（计算量）。 这是整章最该带走的一句话：Memory Bound 的算子，减少计算量毫无收益；只有减少搬运才有收益。

什么时候不该优化：实测 ÷ 理论下界 < 1.5 倍，就别在这个 kernel 上继续花时间了。要么它在 nsys 里占比本来就小，要么该换层次（融合掉它、或者改算法）。

2.9 本章小结

四个公式，能推出本章全部结论

① 算术强度   I = FLOP ÷ Byte（只数 HBM ↔ 芯片的往返）
② 性能上界   P = min(峰值算力, 峰值带宽 × I)
③ 屋脊点     R = 峰值算力 ÷ 峰值带宽    （H100 BF16：989 ÷ 3.35 = 295）
④ MFU        = (tokens × 6N) ÷ (GPU 秒数 × 峰值 FLOPS)

H100 SXM5 的四条屋顶线

三个盲区（屋顶线看不见的）

盲区 现象 怎么办
L2 缓存命中 实测超过你算的上界 不是测错了，是 Byte 数错了；换乐观口径重算
延迟受限 算力和带宽都低于 40% 别看屋顶线，去查 Stall Reason / Occupancy / 启动开销
kernel 之间的空隙 单个 kernel 都到顶，整体还是慢 屋顶线是 kernel 内部的模型；先用 nsys 看整体

三条最容易记错的结论

  • 减少计算量对 Memory Bound 算子毫无帮助：RMSNorm 比 LayerNorm 少算一半，一点不更快，算术强度还更低。
  • "Memory Bound" 不完整：必须说"在哪个计算单元上"。点 D 那个 GEMM 在 BF16 Tensor Core 上 I=62、屋脊点 295，是 Memory Bound；换成 FP32 跑，字节翻倍使 I 降到 31，但 FP32 的屋脊点只有 20，它反而变成 Compute Bound 了。
  • MFU 数字必须带着"硬件 + 分母精度"引用：DeepSeek-V3 按 BF16 峰值是 34.6%，按 FP8 峰值是 17.3%，同一次训练差一倍。

自测三题（答案在本章对应小节）

  1. 对形状 [2048, 8192] 的 BF16 张量做 RMSNorm，实现上 x 只读一遍、y 只写一遍。算出它的算术强度、屋顶线上界、H100 上的理论最短时间。如果实测是 60 µs，该不该继续优化？
  2. 一个 GEMM，M = N = K = 1024。分别在 (a) BF16 Tensor Core 和 (b) FP32 CUDA Core 上跑，各自的算术强度是多少？各自是 Memory Bound 还是 Compute Bound？两者的理论最短时间差几倍？
  3. 某 8 卡 H100 整机训练一个 13B 稠密模型，整机吞吐 12000 tokens/s。它的 MFU 是多少？如果目标是 45%，吞吐要提到多少？这个数字说明问题最可能出在哪一层（提示：对照 §2.6.4 的水位表和 §2.6.5 的清单）。

参考答案

  1. 元素数 = 2048 × 8192 = 16.78 M。RMSNorm 每元素 4 FLOP（平方、累加、乘 inv_rms、乘 γ），每元素 4 Byte（读 2 + 写 2）→ I = 1.0 FLOP/Byte，上界 P = 3350 × 1.0 = 3.35 TFLOPS。字节总数 = 16.78 M × 4 = 67.1 MB，理论最短时间 = 67.1 MB ÷ 3350 GB/s = 20.0 µs。实测 60 µs ÷ 20.0 µs = 3.0 倍，远超 1.5 倍的停手线，应该继续查——按 §2.7.4 的流程，第一件事是用 ncu 看 dram__bytes_read.sum 是不是超过 33.55 MB（即 x 有没有被读两遍）。参见 §2.3 C、§2.7.4。
  2. FLOP 两种精度下都是 2 × 1024³ = 2.147 GFLOP。(a) BF16：Byte = 3 × 1024² × 2 = 6.29 MB → I = 341，BF16 屋脊点 295，341 > 295 → Compute Bound（勉强越过），理论最短时间 = 2.147 G ÷ 989 T = 2.17 µs。(b) FP32：Byte = 3 × 1024² × 4 = 12.58 MB → I = 171，FP32 屋脊点只有 20，171 ≫ 20 → 也是 Compute Bound，而且更深；理论最短时间 = 2.147 G ÷ 67 T = 32.0 µs。差 14.8 倍，差距全部来自屋顶高度（989 vs 67），和带宽无关。参见 §2.4.3。
  3. 分子 = 12000 tokens/s × 6 × 13 × 10⁹ = 9.36 × 10¹⁴ FLOP/s = 936 TFLOPS（整机）。分母 = 8 × 989 = 7912 TFLOPS。MFU = 936 ÷ 7912 = 11.8%。要达到 45%，吞吐 = 0.45 × 7912 × 10¹² ÷ (6 × 13 × 10⁹) ≈ 45600 tokens/s（约 3.8 倍）。11.8% 远低于 §2.6.4 表里"低于 30% 一定有系统性问题"的线，而且是单机 8 卡、通信走 NVLink，通信不太可能是主因——按 §2.6.5 的清单，最可能是 batch 太小（主力 GEMM 的 M 不够大）或大量小算子导致的下发开销，先用 nsys 看 GPU 空闲比例和 top-10 kernel。参见 §2.6.2、§2.6.4、§2.6.5。
