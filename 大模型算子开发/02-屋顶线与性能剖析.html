02 · 屋顶线与性能剖析：诊断算子瓶颈的唯一正确姿势

前置：01 章（GPU 硬件基础）
目标：学会用一个简单的模型判断任何算子的瓶颈在哪里，以及怎么用 Nsight 工具验证判断。

本章关键词

算术强度（Arithmetic Intensity）—— 每读写一个字节完成的浮点运算次数（FLOP/Byte），是刻画算子特征的最重要数字。
Roofline Model（屋顶线模型）—— 用算术强度和硬件峰值推导理论性能上界的分析框架。
Memory Bound（内存瓶颈）—— 算子的瓶颈在于内存带宽，算力空转等数据。
Compute Bound（算力瓶颈）—— 算子的瓶颈在于浮点运算，内存带宽够用但算力打满。
MFU（Model FLOP Utilization，模型算力利用率）—— 实际吞吐 / 峰值算力，衡量 GPU 被利用了多少。
Nsight Systems / Compute —— NVIDIA 官方性能分析工具，前者看整体时间线，后者深挖单个 kernel。
roofline ridge point（屋脊点）—— 算力屋顶和带宽线的交点，对应的算术强度是"算力和带宽恰好同时打满"的临界值。

2.1 一个经典的困惑：矩阵乘法为什么有时快有时慢

先从一个具体案例进入。

import torch
A = torch.randn(4096, 4096, dtype=torch.float16, device='cuda')
B = torch.randn(4096, 4096, dtype=torch.float16, device='cuda')

# 训练场景：batch_size = 64
X_train = torch.randn(64, 4096, dtype=torch.float16, device='cuda')

# 推理场景：batch_size = 1
X_infer = torch.randn(1, 4096, dtype=torch.float16, device='cuda')

# 两种场景的矩阵乘法
torch.matmul(X_train, A)   # 64×4096 × 4096×4096
torch.matmul(X_infer, A)   # 1×4096  × 4096×4096

实测结果（H100 SXM5）：

场景 矩阵形状 (M×K × K×N) 时间 TFLOPS GPU 利用率
训练 batch=64 64×4096 × 4096×4096 ~0.15 ms ~1800 TFLOPS 90%+
推理 batch=1 1×4096 × 4096×4096 ~0.08 ms ~5 TFLOPS ~0.3%

推理场景花了 0.08 ms，看起来更快。但是有效算力只有 5 TFLOPS——GPU 99.7% 的时间在空转。

为什么？这就是算术强度不同导致的结果，Roofline 模型解释这一切。

2.2 算术强度：算子的"体质"

算术强度 = 总浮点运算量（FLOPs）/ 总内存读写量（Bytes）

矩阵乘法的算术强度

对于 GEMM：C = A × B，其中 A 是 M×K，B 是 K×N：

FLOPs  = 2 × M × K × N   （每对 (i,j) 需要 K 次乘 + K 次加，简化为 2MKN）

内存读写：
  读 A：M × K × 2 Bytes（FP16 = 2 Bytes）
  读 B：K × N × 2 Bytes
  写 C：M × N × 2 Bytes
  总计 = 2(MK + KN + MN) Bytes

算术强度 I = 2MKN / (2(MK + KN + MN))
           ≈ MKN / (MK + KN + MN)

当 M 很小（推理 batch=1），分子 MKN 很小但分母 KN 项很大（要读完整的 B 矩阵）：

M=1, K=4096, N=4096:
  FLOPs  = 2 × 1 × 4096 × 4096 ≈ 33.5 M FLOP
  读 B   = 4096 × 4096 × 2 = 33.5 MB
  算术强度 ≈ 33.5 M / 33.5 M = 1 FLOP/Byte   ← 极低！

M=64, K=4096, N=4096:
  FLOPs  = 2 × 64 × 4096 × 4096 ≈ 2.15 G FLOP
  读 B   = 4096 × 4096 × 2 = 33.5 MB         ← B 一样大
  算术强度 ≈ 2150 M / 33.5 M ≈ 64 FLOP/Byte  ← 高 64 倍

关键洞察：无论 batch size 是 1 还是 64，都要把完整的权重矩阵 B 从 HBM 读一遍。batch=64 把这份读的成本分摊到了 64 倍更多的计算上，batch=1 则完全浪费了算力。

2.3 屋顶线模型：画出性能上界

建立 Roofline 图

X 轴是算术强度（FLOP/Byte），Y 轴是性能（TFLOPS）。

H100 SXM5 的两个硬件常数：
- 峰值算力（Compute Roof）：BF16 约 989 TFLOPS
- 峰值带宽（Memory Bandwidth）：约 3.35 TB/s = 3350 GB/s

屋顶线由两段组成：

性能 (TFLOPS)
    ↑
989 │════════════════════════════ Compute Roof（算力屋顶）
    │                          /
    │                        /
    │                      /   带宽线：Performance = BW × I
    │                    /          = 3350 GB/s × I FLOP/Byte
    │                  /
    │                /
    │              /
    └─────────────┼──────────────→ 算术强度 I (FLOP/Byte)
                 295
                屋脊点 = 989 TFLOPS / 3350 GB/s ≈ 295 FLOP/Byte

屋脊点（Ridge Point）= 989 / 3.35 ≈ 295 FLOP/Byte。

  • 算术强度 < 295：Memory Bound，性能 = 带宽 × 算术强度（斜线区域）
  • 算术强度 > 295：Compute Bound，性能 ≤ 989 TFLOPS（水平屋顶）

常见算子落在哪里

算子 典型算术强度 区域 优化方向
GEMM（batch=1，推理） 1–10 Memory Bound 批量化、量化降带宽
GEMM（batch≥32，训练） 64–512 Memory → Compute 接近屋脊点，相对高效
GEMM（大 batch，大矩阵） 512+ Compute Bound 分块调优，用满 Tensor Core
LayerNorm / RMSNorm 2–8 Memory Bound 融合进相邻算子
Softmax 2–5 Memory Bound 融合、FlashAttention 消掉它
朴素 Attention ~10–20 Memory Bound FlashAttention（下一章）
FlashAttention（融合后） ~60–200 接近屋脊点 已大幅改善
激活函数（SiLU、GeLU） 1–3 严重 Memory Bound 必须融合，不能单独跑

★ 推理慢的根本原因：大模型推理几乎所有算子都是 Memory Bound。GPU 绝大多数时间在等 HBM 数据，算力大量空转。优化推理 = 减少 HBM 读写。

2.4 MFU：衡量你的训练效率

MFU（Model FLOP Utilization）= 实际吞吐 / 峰值算力

实际吞吐：每秒处理多少 token，乘以每个 token 的 FLOPs（= 6 × N，N 是参数量，仅计 Forward + Backward 的近似值）。

MFU = (tokens/s × 6N) / peak_TFLOPS

PaLM 论文（2022）报告 H100 集群的 MFU 约 46%——这是当时的顶级水平。DeepSeek-V3（2024）报告 MFU 约 42%（使用 FP8，实际有效算力更高）。

MFU 低的常见原因：

  1. 通信瓶颈（AllReduce / All-to-All 成为瓶颈，GPU 等通信）
  2. 小 batch 导致 Memory Bound（尤其是 Attention 和小矩阵 GEMM）
  3. 算子启动开销（大量小算子，kernel launch 延迟累积）
  4. 内存碎片 / OOM 后的重分配（动态显存管理导致暂停）
  5. 未启用 Flash Attention / 算子融合

2.5 用 Nsight 验证你的分析

理论是理论，实测是实测。要确认一个算子是否真的在 Memory Bound，需要用 NVIDIA 的 profiler 工具。

Nsight Systems：看全局时间线

nsys profile --trace=cuda,nvtx \
             --output=profile_result \
             python your_script.py

打开 profile_result.nsys-rep，看 CUDA 时间线：

时间轴 →
 CPU 线程：  [kernel launch][kernel launch][kernel launch]...
 GPU SM 0：  [─kernel─][等待][─kernel─][等待]...
 GPU SM 1：  [等待][─kernel─][等待][─kernel─]...
 内存复制：  [H2D: inputs]              [D2H: outputs]

要注意的信号：
- GPU 有大量空白（idle）：kernel 之间有延迟，可能是 CPU launch overhead 或同步点
- 内存复制时 GPU 空转：数据准备和计算没有重叠
- kernel 很短但很密集：大量小 kernel，融合机会多

Nsight Compute：深挖单个 kernel

ncu --set full \
    --kernel-name "my_kernel_name" \
    --launch-count 1 \
    python your_script.py

关键指标：

Memory Throughput（内存吞吐）：

DRAM Bandwidth Utilization = 实际带宽 / 峰值带宽
如果这个数字 > 80%，确认 Memory Bound

Compute Throughput（算力吞吐）：

SM Throughput = 实际 FLOPS / 峰值 FLOPS
如果这个数字 > 80%，确认 Compute Bound

两个数字同时高 → 好，算子很高效。
两个数字都低 → 有其他瓶颈（Warp Divergence、同步点、Bank Conflict）。
只有内存高 → Memory Bound，考虑融合/量化。
只有算力高 → Compute Bound，考虑分块调优/降精度。

一个实际的诊断流程

1. nsys 看全局时间线，找出耗时最长的 10 个 kernel
2. ncu 对这些 kernel 逐个分析
3. 对每个 kernel：
   a. 读出算术强度（ncu 会直接给你算好）
   b. 和屋顶线比较，确认瓶颈
   c. 看具体的 Stall Reasons（内存等待？同步？指令流水线空泡？）
4. 按照瓶颈类型选优化手段（下面的章节逐一讲）

2.6 算术强度不够高，能怎么办

总结一下：确认 Memory Bound 之后，可以选择的方向：

方向 手段 适用场景 章节
减少读写量 算子融合（把多个 Memory Bound 算子合并为一个） LayerNorm、激活函数、残差 05 章
减少读写量 量化（FP16→INT8→FP4，每字节装更多数据） 权重、KV Cache 06 章
提高复用率 分块（把数据装进 SRAM，反复使用） GEMM、Attention 03 章、04 章
增大 batch 让更多计算共享同一份权重读取 推理服务 09 章

2.7 本章小结

核心概念速查：

算术强度 = FLOPs / Bytes         ← 算子的"体质"，越高越好
屋脊点   = 峰值算力 / 峰值带宽   ← H100 约 295 FLOP/Byte

低于屋脊点：Memory Bound，优化方向是减少 HBM 读写
高于屋脊点：Compute Bound，优化方向是充分利用 Tensor Core

推理场景的绝大多数算子：算术强度 1–20，严重 Memory Bound
训练场景的大矩阵 GEMM：算术强度 64–512，接近或超过屋脊点

MFU = 实际吞吐 / 峰值算力，业界顶级水平约 40–50%

诊断工具：nsys（看时间线）→ ncu（看单 kernel 的内存/算力利用率）
