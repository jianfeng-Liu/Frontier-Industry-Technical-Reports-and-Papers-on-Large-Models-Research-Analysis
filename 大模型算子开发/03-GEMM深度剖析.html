03 · GEMM 深度剖析：大模型 90% 算力的来源

前置：01 章（GPU 硬件基础）、02 章（屋顶线与性能剖析）
目标：彻底搞清楚矩阵乘法在 GPU 上如何从朴素实现一步步优化到接近硬件峰值，以及 cuBLAS / CUTLASS 的架构思路。
读法：本章的核心是分块，而分块能省多少是可以一位一位算出来的。§3.3 那道 M=N=K=1024 的算术题请一定拿纸笔跟着算一遍——算完你会发现"省 128 倍"不是玄学，那个 128 就是你选的块边长。

本章关键词

GEMM（General Matrix Multiply，通用矩阵乘法）—— C = α·A·B + β·C，深度学习里最核心的算子。
FLOP（Floating Point Operation，浮点运算次数）—— 一次 GEMM 的 FLOP 数是 2·M·N·K，那个 2 是因为每次乘加算两次运算（1 乘 + 1 加），千万别漏。
算术强度（Arithmetic Intensity）—— FLOP 数 ÷ 搬运字节数，单位 FLOP/Byte。H100 的分水岭（屋脊点）是 295，见 02 章。
分块（Tiling）—— 把大矩阵切成小块装进片上存储，提高数据复用率的核心手段，本章的灵魂。
三级分块（3-Level Tiling）—— Block Tile → Warp Tile → Thread Tile，分别对应"HBM→共享内存""共享内存→寄存器""寄存器内部"三段路的流量。
HBM（High Bandwidth Memory，高带宽显存）—— GPU 主存，H100 是 80 GB / 3.35 TB/s。
SRAM / 共享内存（Shared Memory，Static Random Access Memory 静态随机存储器）—— 片上存储，每 SM 最多 228 KB，比 HBM 快 20 倍以上。
SM（Streaming Multiprocessor，流式多处理器）—— GPU 的基本计算单元，H100 有 132 个。
外积（Outer Product）—— 一列乘一行得到一个小矩阵的计算模式，线程级分块的基础。
双缓冲（Double Buffering）—— 用两块共享内存缓冲区交替，让数据加载和计算在时间上重叠。
MMA（Matrix Multiply-Accumulate，矩阵乘累加）—— Tensor Core 的硬件指令，形如 D = A×B + C。
wgmma（Warpgroup MMA，线程束组矩阵乘累加）—— Hopper 新增的指令，由 4 个 Warp（128 线程）协同发射，是 H100 上跑满 Tensor Core 的必需品。
Swizzle（异或置换）—— 不加 padding 就消除 bank conflict 的共享内存布局技巧，兑现 01 章 §1.5.4 留的坑。
Epilogue（收尾计算）—— GEMM 算完、写出 C 之前顺手做掉的融合操作，如加 bias、激活、量化。
cuBLAS（CUDA Basic Linear Algebra Subprograms，CUDA 基础线性代数子程序库）—— NVIDIA 官方闭源库，最优化但不可定制。
CUTLASS（CUDA Templates for Linear Algebra Subroutines and Solvers，CUDA 线性代数模板库）—— NVIDIA 开源的 GEMM 模板库，可定制 Epilogue，是 TensorRT 和 FlashAttention 的底层。
TMA（Tensor Memory Accelerator，张量内存加速器）—— Hopper 新增的异步搬数引擎，可以在后台把 HBM 的一块数据搬进共享内存。
Stream-K —— 按"总工作量 ÷ SM 数"切分而不是按输出块切分的调度方式，解决 SM 之间负载不均（CUTLASS 3.x 引入）。

3.1 为什么 GEMM 是大模型的核心：把 FLOP 账算出来

"大模型 90% 的算力花在矩阵乘上"这句话到处都能看到。它的准确版本是什么？拿 LLaMA-2 7B 逐项算一遍就知道了。

模型参数：隐藏维度 H = 4096，FFN（Feed-Forward Network，前馈网络）中间维度 11008，层数 32，词表 32000，序列长度 S = 2048。下面算的是一个 token 走过一层的浮点运算量。

算子 形状（M × K × N） FLOP = 2·M·K·N 类型
Q 投影 1 × 4096 × 4096 33.55 M GEMM
K 投影 1 × 4096 × 4096 33.55 M GEMM
V 投影 1 × 4096 × 4096 33.55 M GEMM
QKᵀ（对 2048 个 key） 1 × 4096 × 2048 16.78 M GEMM（批量）
注意力 · V 1 × 2048 × 4096 16.78 M GEMM（批量）
O 投影 1 × 4096 × 4096 33.55 M GEMM
FFN gate 1 × 4096 × 11008 90.18 M GEMM
FFN up 1 × 4096 × 11008 90.18 M GEMM
FFN down 1 × 11008 × 4096 90.18 M GEMM
GEMM 小计（9 次） 438.3 M
RMSNorm × 2、RoPE、SiLU、Softmax、两次残差加 — ⚠️ 约 0.45 M 逐元素 / 归约

算一下比例：GEMM 占 438.3 ÷ (438.3 + 0.45) = 99.9% 的 FLOP。

★ "90%" 其实是个保守说法。 按 FLOP 数算，矩阵乘占的不是 90% 而是 99% 以上——Softmax、LayerNorm、激活函数这些算子的运算量小到可以忽略。但它们在时间上远不止 0.1%，因为它们是访存密集型（02 章的 Memory Bound），每个 FLOP 都要拖着几十字节的搬运。⚠️ 实践中 GEMM 大约占 60–80% 的墙钟时间，剩下 20–40% 被那些"几乎不算东西"的小算子吃掉——这正是 05 章 算子融合存在的理由。FLOP 分布和时间分布是两回事，这一章讲前者的优化，05 章讲后者。

整个模型一次前向的 FLOP：32 层 × 438.3 M + LM head（2 × 4096 × 32000 = 262.1 M）= 14.3 GFLOP / token。用业界的 2N 经验公式交叉验证（N = 6.74 B 参数）：2 × 6.74e9 = 13.5 GFLOP，两者差 6%，差在注意力那两次批量 GEMM 上（2N 公式不含它们）。✓ 对得上。

所以：把 GEMM 从 30% 的硬件利用率优化到 80%，整个模型就快 2 倍以上。这是全书投入产出比最高的一件事。

3.2 朴素实现：把浪费掉的字节数算出来

最直观的写法是"一个线程负责 C 的一个元素"：

// 最朴素的 CUDA 实现：每个线程负责 C 的一个元素
__global__ void naive_gemm(const float* A, const float* B, float* C,
                           int M, int K, int N) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;  // C 的行
    int col = blockIdx.x * blockDim.x + threadIdx.x;  // C 的列
    if (row < M && col < N) {
        float sum = 0.0f;
        for (int k = 0; k < K; k++) {
            sum += A[row * K + k] * B[k * N + col];   // ← 每次都从 HBM 读
        }
        C[row * N + col] = sum;
    }
}

代码本身没错，结果也对。问题全在同一份数据被从 HBM 反复搬了多少次。

3.2.1 用一个 4×4 的例子看清重复

取 M = N = K = 4，一共启动 16 个线程。把每个线程读了什么列出来：

线程 (row, col) 读 A 的元素 读 B 的元素
(0, 0) A[0][0..3]（第 0 行） B[0..3][0]（第 0 列）
(0, 1) A[0][0..3] ← 和上面一模一样 B[0..3][1]
(0, 2) A[0][0..3] ← 又一遍 B[0..3][2]
(0, 3) A[0][0..3] ← 再一遍 B[0..3][3]
(1, 0) A[1][0..3] B[0..3][0] ← 和 (0,0) 一模一样
… … …
(3, 3) A[3][0..3] B[0..3][3]

数一数：

A 只有 16 个元素，却被读了 16 线程 × 4 = 64 次   → 每个元素读了 4 次 = N 次
B 只有 16 个元素，也被读了 64 次                 → 每个元素读了 4 次 = M 次
一共发生了 128 次元素读取，但真正不同的元素只有 32 个
                                    ↓
                   (128 − 32) / 128 = 75% 的搬运是纯粹的重复

规律：A 的每一行被读 N 次，B 的每一列被读 M 次。矩阵越大，浪费越离谱。

3.2.2 换成真实尺寸：0.25 FLOP/Byte

取 M = N = K = 4096，FP32（4 字节/元素）：

计算量   = 2 × M × N × K = 2 × 4096³ = 137.4 GFLOP
                            ↑ 别漏这个 2

读 A     = M × N × K 个元素（每个 C 元素读 K 个）= 4096³ 个 = 68.72 G 个 × 4 B = 274.9 GB
读 B     = 同上                                                             = 274.9 GB
写 C     = 4096² × 4 B = 16.8 MB   ← 可忽略
搬运总量 ≈ 549.8 GB

算术强度 = 137.4e9 FLOP ÷ 549.8e9 Byte = 0.25 FLOP/Byte

这个 0.25 不是巧合，它是精确值：2MNK ÷ (2·MNK·4 Byte) = 1/4。对 FP32 的朴素 GEMM，算术强度恒等于 0.25，和矩阵多大完全无关。

放到屋顶线上看：

对照 屋脊点 朴素 GEMM 的 0.25 差多少 理论性能上界
FP32（CUDA Core，67 TFLOPS） 67 ÷ 3.35 = 20 FLOP/Byte 差 80 倍 3350 GB/s × 0.25 = 838 GFLOPS，占 FP32 峰值 1.25%
BF16（Tensor Core，989 TFLOPS） 295 FLOP/Byte 差 1180 倍 —

⚠️ 注意别拿错屋脊点。 这一节的例子是 FP32、走 CUDA Core，该比的是 FP32 的屋脊点 20，不是 BF16 的 295。同一块卡在不同精度下有不同的屋脊点：屋脊点 = 该精度的峰值算力 ÷ 带宽。本章后面讲 Tensor Core 时才切到 295。

⚠️ 上面 549.8 GB 是"完全不命中缓存"的上界。真机上 L1/L2 会拦下一部分——B 的同一列被同一个 Block 里的线程连着读，L1 命中率不低。所以朴素 kernel 的实测大约是理论下界的 3–10 倍，而不是 80 倍。⚠️ 这个倍数是量级估计，不是实测值。但结论不变：绝大部分带宽花在了重复搬运上，而且这件事完全由缓存碰运气决定，程序员一点控制权都没有。

分块要解决的就是这件事：把"碰运气的复用"变成"程序员写死的复用"。

3.3 分块（Tiling）：本章的灵魂

3.3.1 先做一道纯算术题

这道题请一定自己算一遍。M = N = K = 1024，FP32（4 字节）。

情况一：不分块（§3.2 的写法）

读 A = M × N × K 个元素 = 1024³ = 1,073,741,824 个 × 4 B = 4.295 GB
读 B = 同上                                                = 4.295 GB
                                                    ──────────────
                                        A + B 合计   = 8.590 GB
写 C = 1024² × 4 B = 4.19 MB

情况二：把 C 切成 128×128 的块，每个 Block 负责一块

C 是 1024×1024，切成 128×128 的块 → 1024/128 × 1024/128 = 8 × 8 = 64 个块

要算 C 的第 (i, j) 块，需要什么数据？
  A 的第 i 条横条：128 行 × 1024 列 = 131,072 个元素 × 4 B = 524.3 KB
  B 的第 j 条竖条：1024 行 × 128 列 = 131,072 个元素 × 4 B = 524.3 KB
  一个 Block 从 HBM 读进 1.049 MB

64 个 Block × 1.049 MB = 67.1 MB

对比：

不分块：8590 MB
分  块：  67.1 MB
         ─────────
8590 ÷ 67.1 = 128.0 倍

HBM 流量降到 1/128。 而且这个 128 不是巧合——它就是你选的块边长。

换算成时间（H100，3.35 TB/s，FP32 峰值 67 TFLOPS）：

HBM 搬运时间 纯计算时间 实际耗时 ≈ max(两者) 算力利用率
不分块 8.590 GB ÷ 3350 GB/s = 2564 µs 2.147 GFLOP ÷ 67 TFLOPS = 32 µs 2564 µs 32/2564 = 1.25%
128×128 分块 67.1 MB ÷ 3350 GB/s = 20 µs 32 µs 32 µs 100%（理论）

从"访存把计算卡死 80 倍"变成"计算把访存盖住"。瓶颈换了一边，这就是分块的全部意义。

3.3.2 为什么正好是 128 倍：一个能背下来的公式

把上面的算术抽象一步。设块尺寸 BM × BN，元素 s 字节：

A 的每一条横条（M×K）被读的次数 = C 横向有几列块 = N / BN
B 的每一条竖条（K×N）被读的次数 = C 纵向有几行块 = M / BM

HBM 读量 = M·K·s·(N/BN) + K·N·s·(M/BM)
         = M·N·K·s·(1/BN + 1/BM)

算术强度 = 2·M·N·K ÷ [M·N·K·s·(1/BM + 1/BN)]
         = 2 / [s·(1/BM + 1/BN)]
         = 调和平均(BM, BN) ÷ s

★ 一句话记住整章：Block Tile 的算术强度 = 两条边的调和平均 ÷ 每个元素的字节数。比朴素实现省下的倍数，正好等于那个调和平均值。

验算一遍：BM = BN = 128 时，调和平均 = 2 ÷ (1/128 + 1/128) = 128；除以 s = 4 得算术强度 32 FLOP/Byte；省下的倍数 = 128 ✓，和 §3.3.1 一位不差。

把几种块尺寸列成表（仍取 M=N=K=1024，FP32）：

BM × BN C 被切成几块 HBM 读量 (A+B) 比不分块省 算术强度 累加器占的寄存器 = BM×BN
1 × 1（即朴素） 1024 × 1024 8590 MB 1× 0.25 1
32 × 32 32 × 32 268.4 MB 32× 8 1024（占 SM 寄存器文件 1.6%）
64 × 64 16 × 16 134.2 MB 64× 16 4096（6.3%）
128 × 128 8 × 8 67.1 MB 128× 32 16384（25%）
256 × 256 4 × 4 33.6 MB 256× 64 65536（100%，装不下）

3.3.3 块为什么不能无限大：天花板在寄存器，不在共享内存

看上表最后一行。块越大越省带宽，那为什么不开 256×256？

因为 C 的累加器必须全程待在寄存器里。 一个 Block 负责 BM×BN 个输出元素，每个元素在整个 k 循环期间都要维持一个 FP32 累加值，所以这个 Block 需要 BM × BN 个寄存器——无论你把它们怎么分给线程，总数不变。

H100 一个 SM 的寄存器文件 = 65536 个 32-bit = 65536 个 float

BM×BN = 128×128 = 16384 个累加器  → 占 25%，剩下 75% 给操作数、地址、循环变量 ✓
BM×BN = 256×256 = 65536 个累加器  → 正好把整个寄存器文件吃光，
                                     连一个操作数寄存器都放不下 ✗

★ 这是新手最容易搞反的一点：限制 Block Tile 大小的第一约束是寄存器，不是共享内存。上表里 128×128 配 BK=8 时共享内存才用 (128+128)×8×4 = 8 KB，离 228 KB 的上限远得很。真正先撞墙的是寄存器。这也解释了 01 章 §1.6.3 那句"高性能 GEMM 的 Occupancy 常常只有 25–50%"——寄存器被累加器吃掉了，一个 SM 只放得下一两个 Block。

3.3.4 分块 kernel 长什么样

Thread Block 负责 C[i:i+BM, j:j+BN]：

  在寄存器里开一个 BM×BN 的累加器，清零

  for k_tile in 0, BK, 2·BK, ... , K-BK:      ← 沿 K 方向一块一块推进
      ① 全 Block 的线程协作，从 HBM 搬两块小矩阵进共享内存
           A[i:i+BM, k_tile:k_tile+BK]  → smem_A   (BM × BK)
           B[k_tile:k_tile+BK, j:j+BN]  → smem_B   (BK × BN)
      ② __syncthreads()                          ← 等所有人搬完
      ③ for k in 0..BK-1:
             累加器 += smem_A[:, k] 外积 smem_B[k, :]
      ④ __syncthreads()                          ← 等所有人用完再覆盖

  把累加器写回 C

配一张图看数据是怎么流的（注意 smem_A 沿 K 方向滑动，smem_B 沿 K 方向向下滑动）：

                     B 矩阵 (K x N)
                     +----------------------------
          k_tile     |            BBBB
            |        |            BBBB
            |        |            BBBB
            v        |            BBBB

  A 矩阵 (M x K)                  C 矩阵 (M x N)
  +--------------------          +----------------------------
  | AAAA  ---- k_tile --->       |            CCCC
  |                              |            CCCC
  |                              |            CCCC
  |                              |            CCCC

  AAAA = A_tile，BM x BK，搬进共享内存，沿 K 方向向右滑动
  BBBB = B_tile，BK x BN，搬进共享内存，沿 K 方向向下滑动
  CCCC = C_tile，BM x BN，全程待在寄存器里，k 循环结束才写回 HBM

⚠️ 两个 __syncthreads() 一个都不能省。少了 ② 会读到还没搬完的垃圾数据；少了 ④ 会有跑得快的线程把还在被别人读的 tile 覆盖掉。这两个 bug 都是随机出现的，跑十次错一次，极难排查。参见 01 章 §1.3。

3.3.5 BK 的作用：一个反直觉的结论

注意 §3.3.2 的公式里没有 BK。

★ BK 完全不影响 HBM 总流量。 无论 BK 取 8 还是 64，一个 Block 最终都要把 A 的那条完整横条（BM × K）和 B 的那条完整竖条（K × BN）读完一遍，只是分成了 K/BK 批。总量是 BM×K + K×BN，和 BK 无关。

那 BK 决定什么？三件事：

BK 变大 影响
共享内存占用 (BM+BN)·BK·s 线性增加 BK=8 时 8 KB，BK=64 时 64 KB（FP32、128×128、单缓冲）
循环轮数 K/BK 减少 同步次数、循环开销、地址计算都按比例减少
一次发出的 HBM 请求变长 更容易把 HBM 延迟摊薄（01 章 §1.6 的延迟隐藏），也更利于 TMA 一次搬一大块

所以 BK 是个纯粹的"流水线调节旋钮"：小了循环开销大、延迟藏不住；大了共享内存放不下、双缓冲（§3.5）翻倍后更放不下。FP32 时代典型值 8，BF16 + Tensor Core 时代典型值 32–64。

3.3.6 一次分块够不够：FP32 够了，BF16 不够

上面 FP32 的账很漂亮：分块后算术强度 32 > FP32 屋脊点 20，变成 Compute Bound，收工。

但换成 BF16 + Tensor Core，账立刻不成立了，因为屋脊点从 20 跳到 295：

配置 算术强度 = 调和平均 ÷ s 对比屋脊点 295 理论上界
BM=BN=128，BF16（s=2） 128 ÷ 2 = 64 差 4.6 倍 3350 × 64 = 214 TFLOPS，占峰值 22%
BM=128, BN=256，BF16 170.7 ÷ 2 = 85.3 差 3.5 倍 286 TFLOPS，占峰值 29%
BM=BN=256，BF16 256 ÷ 2 = 128 差 2.3 倍 429 TFLOPS，占峰值 43%（但寄存器装不下）

把块开到寄存器装不下，算术强度还是够不到 295。 那 cuBLAS 凭什么能跑到 88%？

答案是 L2 缓存。上面的账假设"每个 Block 都老老实实从 HBM 把自己那条横条竖条读一遍"，但 A 的同一条横条会被同一行上的 8 个 Block 都读一次——如果这 8 个 Block 在时间上挨得近，后 7 次就命中 L2（50 MB），根本没走 HBM。

算一下理想情况下的下界（M=N=K=4096，BF16）：

理想最小流量 = (A + B + C 各读写一遍) = 3 × 4096² × 2 B = 100.7 MB
理想算术强度 = 137.4 GFLOP ÷ 100.7 MB = 1365 FLOP/Byte  ≫ 295 ✓

理想下界远在屋脊点之上，说明"够到峰值"在物理上是可能的，差的只是缓存命中率。 所以真实 GEMM 库还有第四件事要做：控制 Block 的执行顺序，让同时在跑的那批 Block 尽量共享 A/B 的同一条带。这叫 Threadblock Swizzle / Rasterization（分块光栅化顺序）——不是按行扫描地发 Block，而是按 Z 字形或分组扫描，让一个波次内的 Block 挤在 C 的一个方块区域里。

按行扫描（差）：一个波次覆盖 C 的很宽很扁的一条
   0  1  2  3  4  5  6  7   ← 波次里的 8 个 Block 用到 A 的 1 条横条、B 的 8 条竖条
   8  9 10 11 12 13 14 15      L2 要装 1 + 8 = 9 条带

按 4×2 分组扫描（好）：一个波次挤在一个方块里
   0  1  4  5  8  9 12 13   ← 前 8 个 Block 用到 A 的 4 条横条、B 的 2 条竖条
   2  3  6  7 10 11 14 15      L2 只要装 4 + 2 = 6 条带，命中率更高

⚠️ L2 能补多少是实测问题，不同 shape 差别很大，手算不出来。这里要记住的结论只有一条：分块把算术强度从 0.25 拉到 60–130，L2 再把剩下的缺口补上，两者缺一不可。 具体命中率用 Nsight Compute 的 lts__t_sectors_hit_rate 看，见 02 章。

3.4 三级分块：每一级省的是哪一段路的流量

§3.3 解决了 HBM 这一段。但数据搬进共享内存之后，还要再搬进寄存器才能算——那一段路同样会堵。三级分块就是把三段路分别治一遍。

3.4.1 一张从大到小的嵌套图

下面这套参数是完全自洽的，每个数字都能对上（FP32，Block 开 256 线程）：

C 矩阵  (M × N，比如 4096 × 4096)
│
├── 切成 Block Tile：128 × 128
│     → 共 32 × 32 = 1024 个 Block
│     → 每个 Block 要的 A/B 数据放【共享内存】
│     → 这一级决定：HBM ↔ 共享内存 的流量        （§3.3 算过：省 128 倍）
│     │
│     ├── 再切成 Warp Tile：64 × 32
│     │     → 一个 Block 里 128/64 × 128/32 = 2 × 4 = 8 个 Warp ✓
│     │     → 每个 Warp 把自己那块的数据从【共享内存】读进【寄存器】
│     │     → 这一级决定：共享内存 ↔ 寄存器 的流量，以及 bank conflict
│     │     │
│     │     └── 再切成 Thread Tile：8 × 8
│     │           → 一个 Warp 里 64/8 × 32/8 = 8 × 4 = 32 个线程 ✓（正好一个 Warp）
│     │           → 这 8×8 = 64 个累加值全程待在【寄存器】里，只做乘加
│     │           → 这一级决定：每读一个操作数能做几次乘加

自洽性检查：
  Block 线程数 = 8 Warp × 32 = 256 ✓
  累加器总数   = 256 线程 × 64 = 16384 = 128 × 128 ✓  正好覆盖整个 Block Tile

和 01 章 §1.3 的存储金字塔一一对应：

分块级别 对应 01 章的哪一层存储 管住哪一段搬运 容量约束
Block Tile（BM×BN×BK） 共享内存（≤228 KB/SM，约 25 周期） HBM → 共享内存 (BM+BN)·BK·s 字节
Warp Tile（WM×WN） 寄存器文件（256 KB/SM，~1 周期） 共享内存 → 寄存器 决定每个 Warp 读多少共享内存
Thread Tile（TM×TN） 单个线程的寄存器（≤255 个） 寄存器内部的复用 TM×TN 个累加器 + TM+TN 个操作数

★ 三级分块不是"分三次同一件事"，而是三段不同的路各修一遍。 只做 Block Tile，HBM 不堵了但共享内存会堵；只做 Thread Tile，共享内存不堵了但 HBM 照样堵死。这也是 §3.9 小结里要重点记的一条。

3.4.2 Thread Tile 为什么正好是 8×8：从共享内存带宽推出来

这是本章最值得亲手算的一笔账。

先算供给侧：H100 的共享内存有 32 个 bank，每个 bank 每周期吐 4 字节，所以一个 SM 每周期最多从共享内存读出 ⚠️ 约 128 字节（这个数是按"32 bank × 4 字节"的架构定义推算的，实际受 LSU 访存单元发射率影响会略低）。

再算需求侧：一个 SM 有 128 个 FP32 CUDA Core，每周期能做 128 次乘加（FMA）。每次 FMA 要两个操作数（一个来自 A，一个来自 B）。如果每次都从共享内存新读：

需求 = 128 FMA × 2 个操作数 × 4 字节 = 1024 字节/周期
供给 = 128 字节/周期
                ↓
      缺 8 倍。计算单元有 7/8 的时间在等共享内存。

所以每个从共享内存读进寄存器的操作数，必须被复用至少 8 次。 这正是 Thread Tile 干的事：

每个线程负责 TM × TN 个输出，每推进一个 k：
    从共享内存读 A 的 TM 个元素 → a_reg[TM]
    从共享内存读 B 的 TN 个元素 → b_reg[TN]
    做外积：for i in TM: for j in TN: c_reg[i][j] += a_reg[i] * b_reg[j]

  → 读了 (TM + TN) 个元素，做了 TM × TN 次 FMA
  → 每次 FMA 平均读 4·(TM+TN) / (TM·TN) 字节

逐个 TM/TN 算出来：

TM × TN 每次 FMA 读的字节 需要的共享内存带宽 对比 128 B/周期的预算 累加器寄存器/线程
1 × 1（点积，即朴素） 8.0 1024 B/周期 超 8 倍 ✗ 1
2 × 2 4.0 512 B/周期 超 4 倍 ✗ 4
4 × 4 2.0 256 B/周期 超 2 倍 ✗ 16
8 × 8 1.0 128 B/周期 正好用满 ✓ 64
16 × 16 0.5 64 B/周期 富余一半 256 → 超过 255 的硬上限 ✗

★ 8×8 是被两头夹出来的唯一解：比 8 小，共享内存带宽不够；比 8 大，寄存器放不下（16×16 需要 256 个累加器，超过每线程 255 个的硬件上限）。所以你在所有 FP32 手写 GEMM 教程里看到的都是 TM=TN=8，不是抄来的习惯，是算出来的。

外积 vs 点积，一句话说清区别：

点积模式（朴素）：c[i][j] = Σ_k a[i][k] · b[k][j]
                  内层循环固定 i、j，扫 k       → 一次 FMA 要读 2 个新操作数

外积模式：        固定 k，一次更新整个 TM×TN 的小块
                  c_reg[i][j] += a_reg[i] · b_reg[j]
                  内层是 i、j 双重循环，k 在外层 → 读 TM+TN 个，做 TM×TN 次 FMA

  循环顺序从 (i, j, k) 换成 (k, i, j)，一行代码都没多，
  共享内存流量降到 1/8。

3.4.3 共享内存布局：padding 还是 swizzle

Warp Tile 这一级还有一个坑：数据在共享内存里怎么摆。

A 在 HBM 里是行优先的 M×K，但外积循环每一步要取 A 的一整列（固定 k，取 TM 个不同的行）。所以搬进共享内存时通常要转置成 smem_A[BK][BM]。而"按列写入"正是 01 章 §1.5.2 那个 32 路 bank conflict 的现场。

01 章 §1.5.3 给的解法是 padding（[32][33]），但它在 Hopper 上有个致命问题：TMA 要求共享内存里的一块是 128 字节对齐、连续、无 padding 的，多出来的那一列会让 TMA 直接用不了。所以 CUTLASS 用的是 Swizzle（异或置换）。

Swizzle 的原理，用 01 章同一个例子演示。 声明 __shared__ float tile[32][32]，但存取时把列下标异或行下标：把逻辑上的 tile[r][c] 实际存到物理位置 tile[r][c XOR r]。

现在一个 Warp 按列读 tile[tid][0]：

线程 tid 想读 实际落点 tile[r][0 XOR r] 线性下标 r×32 + r Bank = 下标 % 32
0 tile[0][0] tile[0][0] 0 0
1 tile[1][0] tile[1][1] 33 1
2 tile[2][0] tile[2][2] 66 2
3 tile[3][0] tile[3][3] 99 3
… … … … …
31 tile[31][0] tile[31][31] 1023 31

32 个不同的 Bank，冲突完全消除，而且一个字节的额外空间都没用。

按行读也不会坏掉：读 tile[0][c]，落点是 tile[0][c XOR 0] = tile[0][c]，banks 0–31 ✓。读第 r 行，落点的列下标是 c XOR r，当 c 跑遍 0–31 时 c XOR r 也恰好跑遍 0–31（异或是个双射），所以仍然是 32 个不同 bank ✓。

padding：  tile[32][33]   多花 128 字节，破坏 128 B 对齐，TMA 用不了
swizzle：  tile[r][c^r]   零额外空间，对齐不变，TMA 可用
           代价：地址计算多一条 XOR 指令（几乎免费）

★ 这就是 01 章 §1.5.4 说的"比 padding 更现代"的东西。CUTLASS 里对应 Swizzle<B, M, S> 三个模板参数（分别控制异或几位、每个单元多大、跨几行），常见的是 32B/64B/128B 三档 swizzle 模式。07 章 的 Triton 编译器会自动选布局，不用手写。

3.4.4 一套完整自洽的配置

把前面所有约束凑在一起，得到经典的 FP32 SGEMM 配置：

Block Tile        BM=128, BN=128, BK=8
Warp  Tile        WM=64,  WN=32
Thread Tile       TM=8,   TN=8
Block 线程数      256（= 8 个 Warp）

逐项验算：
  Warp 数        = (128/64) × (128/32) = 2 × 4 = 8 ✓
  每 Warp 线程数 = (64/8)   × (32/8)   = 8 × 4 = 32 ✓   ← 必须正好 32
  Block 线程数   = 8 × 32 = 256 ✓
  累加器总数     = 256 × 64 = 16384 = 128 × 128 ✓

共享内存（单缓冲）= (128 + 128) × 8 × 4 B = 8 KB / Block
                    双缓冲翻倍 = 16 KB，离 228 KB 上限还很远 ✓

寄存器 / 线程     = 64（累加器）+ 16（a_reg + b_reg）+ ⚠️ 约 20（地址、循环、预取）
                  ≈ 100 个
  一个 SM 能放几个 Block：65536 ÷ (100 × 256) = 2.56 → 2 个 Block
  驻留 Warp = 2 × 8 = 16 个，Occupancy = 16/64 = 25%

★ Occupancy 只有 25%，但这是对的。 对照 01 章 §1.6.3：GEMM 是计算密集型，每个 Warp 一次访存后能算上千个周期，根本不需要很多 Warp 来掩盖延迟。用寄存器换复用率是划算的买卖。看见 GEMM kernel 的 Occupancy 低不要慌，看实测时间。

3.5 双缓冲：让搬运和计算在时间上重叠

§3.3 和 §3.4 解决的是"搬多少"，这一节解决"搬的时候在不在干活"。

3.5.1 单缓冲的问题：一半时间在等

回看 §3.3.4 的伪代码：搬 → 同步 → 算 → 同步 → 搬 → 同步 → 算……搬的时候计算单元全空，算的时候访存单元全空。

把周期数算出来（沿用 §3.4.4 的配置：BM=BN=128，BK=8，FP32，M=N=K=1024，H100 时钟 ⚠️ 按 1.755 GHz boost 计）：

每一轮 k 循环要搬多少：(128×8 + 8×128) × 4 B = 8192 B = 8 KB

搬运耗时（两个上界取大的）：
  按带宽算：每个 SM 分到的 HBM 带宽 = 3350 GB/s ÷ 132 SM = 25.4 GB/s
            = 25.4e9 ÷ 1.755e9 = 14.5 字节/周期
            8192 B ÷ 14.5 = 566 周期
  按延迟算：HBM 延迟约 500 周期（01 章 §1.3）
  → T_load ≈ 570 周期

计算耗时：
  每轮 FLOP = 2 × 128 × 128 × 8 = 262,144 FLOP
  一个 SM 每周期 128 FMA = 256 FLOP（01 章 §1.7.1）
  → T_comp = 262144 ÷ 256 = 1024 周期

循环轮数 = K / BK = 1024 / 8 = 128 轮

3.5.2 时间线：单缓冲 vs 双缓冲

单缓冲（一块共享内存缓冲区，搬完才能算，算完才能覆盖）
周期  0        570      1594     2164     3188     3758
      ├─搬 t0──┼──算 t0─┼─搬 t1──┼──算 t1─┼─搬 t2──┼ ...
        570      1024     570      1024     570
      每轮 = 570 + 1024 = 1594 周期
      访存单元在算的那 1024 周期里全空 ✗
      计算单元在搬的那  570 周期里全空 ✗


双缓冲（两块缓冲区 buf0 / buf1 交替，搬下一块的同时算这一块）

      上排 = 计算（用 buf0 / buf1 交替），下排 = 同时在后台搬下一块
      预热一次 570 周期，之后每轮 = max(570, 1024) = 1024 周期

算总账：

一行代码没改算法，快 1.55 倍。 省下来的正好是那 128 轮 × 570 周期的等待。

3.5.3 靠什么实现：cp.async 和 TMA

普通的 smem[x] = global[y] 是同步的：数据先进寄存器，再写共享内存，这条指令不返回线程就没法往下走，没法重叠。

Ampere 开始提供 cp.async（异步拷贝）指令：HBM 直接搬到共享内存，不经过寄存器，发出后线程立刻继续执行，之后用 cp.async.wait_group 等它完成。这才是双缓冲的硬件基础。

// 概念示意（真实代码要用 cuda::memcpy_async 或内联 PTX）
__pipeline_memcpy_async(&smem[buf_next], &gmem[tile_next], bytes);  // 发出，不阻塞
__pipeline_commit();

compute_on(smem[buf_cur]);        // ← 在这里干活，搬运在后台跑

__pipeline_wait_prior(0);         // 等上面那次搬运落地
__syncthreads();
swap(buf_cur, buf_next);

Hopper 更进一步，用 TMA（Tensor Memory Accelerator，张量内存加速器）：整块 tile 的搬运交给一个独立的硬件引擎，只需要一个线程发一条指令，剩下 255 个线程完全不用参与搬运，全去算。配合 Warp Specialization（线程束专业化）——把 Block 里的 Warp 分成"生产者"（只管发 TMA 指令）和"消费者"（只管发 MMA 指令）两组——这是 H100 上 CUTLASS 3.x 的标准做法。

真实的 CUTLASS 不止两级缓冲，而是 N 级流水（模板参数 Stages，常用 3–8 级）：同时有好几块 tile 在路上，进一步掩盖抖动。

3.5.4 什么时候双缓冲救不了你

⚠️ 双缓冲藏的是"延迟"，藏不掉"带宽不够"。

把 §3.5.1 的账换成 BF16 + Tensor Core（BM=128, BN=128, BK=64）再算一遍：

每轮搬运 = (128×64 + 64×128) × 2 B = 32,768 B
         ÷ 14.5 字节/周期 = 2260 周期

每轮计算 = 2 × 128 × 128 × 64 = 2,097,152 FLOP
         ÷ 4096 FLOP/周期（BF16 Tensor Core，01 章 §1.7.1）= 512 周期

双缓冲后每轮 = max(2260, 512) = 2260 周期
                    ↑ 搬运是计算的 4.4 倍，重叠之后仍然被搬运卡死

Tensor Core 把计算快了 16 倍，搬运一点没变，于是瓶颈整个翻到了访存侧。 这个 4.4 倍和 §3.3.6 算出的"算术强度 64 差屋脊点 295 的 4.6 倍"是同一件事的两种说法 ✓。

这时候唯一的出路不是改流水线，而是回到 §3.3：把 tile 开大（提高算术强度）+ 靠 L2 把重复读吃掉。双缓冲是必要条件，不是充分条件。

3.6 Tensor Core 的接入：从 mma 到 wgmma

前面所有讨论都是用 CUDA Core 做乘加。要摸到 989 TFLOPS，必须换成 Tensor Core。

3.6.1 MMA 指令的真实形状

H100 的 BF16 MMA（Matrix Multiply-Accumulate，矩阵乘累加）指令是 mma.sync.aligned.m16n8k16。名字里的三个数字就是它一次处理的形状：

  M = 16    N = 8     K = 16        <-- 是 16x8x16，不是 16x16x16！

                       B 操作数：K=16 行 x N=8 列，BF16
                       BBBBBBBB
                       BBBBBBBB
                       BBBBBBBB
                       BBBBBBBB

  A 操作数                          D / C 累加器
  M=16 行 x K=16 列，BF16           M=16 行 x N=8 列，FP32
  AAAAAAAAAAAAAAAA         x        DDDDDDDD
  AAAAAAAAAAAAAAAA                  DDDDDDDD        D = A x B + C
  AAAAAAAAAAAAAAAA                  DDDDDDDD
  AAAAAAAAAAAAAAAA                  DDDDDDDD

  一条指令的运算量 = 2 x 16 x 8 x 16 = 4096 FLOP

32 个线程各持一片。这是 Tensor Core 最反直觉的地方：操作数不在某个线程手里，而是分布在整个 Warp 的寄存器里，每个线程只拿一小块碎片（Fragment，片段）：

操作数 总元素数 每线程分到 占几个 32-bit 寄存器
A（16×16 BF16） 256 8 个 BF16 4 个（1 个寄存器装 2 个 BF16）
B（16×8 BF16） 128 4 个 BF16 2 个
C / D（16×8 FP32） 128 4 个 FP32 4 个

★ 这就是为什么你不能用普通 for 循环调用 Tensor Core：碎片在哪个线程的哪个寄存器里，是硬件写死的一张布局表。你必须用 wmma API、内联 PTX（Parallel Thread Execution，并行线程执行汇编）、或者让 CUTLASS / Triton 替你生成。参见 01 章 §1.7.4。

3.6.2 为什么 H100 上光有 mma 还不够

算一笔发射率的账：

一个 SM 的 BF16 峰值 = 4096 FLOP/周期（01 章 §1.7.1，⚠️ 推算值）
一条 mma.m16n8k16   = 4096 FLOP

→ 要跑满峰值，一个 SM 必须【每个周期完成一条 mma】，一个气泡都不能有

一个 SM 有 4 个 Warp 调度器，每周期各发一条指令。但 MMA 指令之间还夹着地址计算、共享内存读取、循环控制、同步——指令发射槽根本不够。实践中靠 mma.sync 通常只能跑到峰值的一部分（⚠️ 经验量级，具体看 shape 和实现）。

Hopper 的解法是 wgmma（Warpgroup MMA，线程束组矩阵乘累加）：

mma.sync.aligned.m16n8k16          由  1 个 Warp（32 线程）发射
                                   一条指令 = 2×16×8×16 = 4,096 FLOP

wgmma.mma_async.sync.aligned.m64n256k16
                                   由  4 个 Warp（128 线程，一个 Warpgroup）协同发射
                                   一条指令 = 2×64×256×16 = 524,288 FLOP
                                              ↓
                                   一条顶 128 条，发射压力降到 1/128

wgmma 还有第二个关键改进：A 操作数可以直接从共享内存喂给 Tensor Core，不用先搬进寄存器。这省掉了大量 ldmatrix 指令，也省掉了 A fragment 占的寄存器——正好把 §3.3.3 说的寄存器天花板往上抬了一截。

mma.sync wgmma.mma_async
发射单位 1 Warp（32 线程） 1 Warpgroup（128 线程）
典型形状 m16n8k16 m64n{8…256}k16
单条 FLOP（BF16） 4,096 最大 524,288
A 操作数来源 必须先进寄存器 可直接读共享内存
执行方式 同步 异步，可与其他指令重叠
引入 Ampere Hopper（H100）

★ 一条实用结论：在 H100 上手写 GEMM，如果只用 wmma API 或 mma.sync，天花板会明显低于 cuBLAS。想接近峰值就得用 wgmma + TMA + Warp Specialization，而这三件事一起写的复杂度极高——这正是 CUTLASS 存在的理由（§3.7）。日常工作中的正确选择是 Triton 或 cuBLAS。

3.6.3 维度对齐：用不上 Tensor Core 的静默陷阱

MMA 的形状是硬件写死的，所以矩阵维度必须对得上：

精度 MMA 形状 实践上的维度要求 H100 稠密峰值
FP32 无（走 CUDA Core） 无 ~67 TFLOPS
TF32 m16n8k8 对齐到 16 ~494 TFLOPS
BF16 / FP16 m16n8k16 对齐到 16 ~989 TFLOPS
FP8 m16n8k32 对齐到 16 ~1979 TFLOPS

⚠️ 别把稀疏算力当稠密用。 NVIDIA 的表里 BF16 还有一个 1979 TFLOPS 的数字，那是要求权重满足 2:4 结构化稀疏才能达到的。常规稠密 GEMM 用不上。本系列统一用 989 TFLOPS / 屋脊点 295 FLOP/Byte，和 01 章、02 章、附-速查表 §A 一致。

⚠️ 对不齐不会报错，只会变慢。 cuBLAS 会静默退回到补零路径或 CUDA Core 路径，结果完全正确，就是慢好几倍。这是"模型改了个 hidden_size 之后突然慢了"的头号原因。为什么大模型的隐藏维度总是 128 的倍数，见 01 章 §1.7.3。

3.7 CUTLASS：为什么一个矩阵乘要分这么多层

3.7.1 cuBLAS 的两个不够用

cuBLAS 的 GEMM 极度优化，但它只会算 C = α·A·B + β·C。大模型里实际需要的是：

  • C = GEMM(A, B) + bias —— 加偏置
  • C = SiLU(GEMM(A, B)) —— 融合激活
  • C = quantize_int8(GEMM(A, B)) —— 融合量化（06 章）
  • C = GEMM(A, B) ⊙ gate —— SwiGLU 的门控

如果 cuBLAS 算完把 C 写回 HBM，再启动一个 kernel 读回来加 bias 再写回去，那就白白多搬了 2 遍 C。以 M=4096、N=11008、BF16 为例：4096 × 11008 × 2 B = 90 MB，一来一回 180 MB，在 3.35 TB/s 上是 54 µs——而这层 GEMM 本身的计算只要 2×4096×4096×11008 ÷ 989e12 = 374 µs，等于凭空多付 14%。整个模型几百个这样的点，代价可观（详见 05 章）。

这些"写出 C 之前顺手做掉"的计算，统称 Epilogue（收尾）。cuBLAS 不支持自定义 Epilogue，CUTLASS 就是为这件事设计的。

3.7.2 为什么必须分层：加法 vs 乘法

一个高性能 GEMM 要同时决定一堆互相正交的选择。粗略数一下：

维度 大致有几种选择
数据类型组合（A/B/C/累加器） FP16、BF16、TF32、FP8、INT8… ≈ 6
布局（A 行/列 × B 行/列） 4
Block Tile 形状 64×128、128×128、128×256、256×128… ≈ 8
流水级数 Stages 3–8 ≈ 5
Epilogue 无、bias、bias+激活、量化、门控… ≈ 6
调度策略 Data-Parallel、Split-K、Stream-K ≈ 3 
如果每种组合手写一个 kernel：
    6 × 4 × 8 × 5 × 6 × 3 = 17,280 个 kernel     ← 乘法，不可能

如果把它切成 6 个正交的层，每层各写几个零件：
    6 + 4 + 8 + 5 + 6 + 3 =     32 个零件        ← 加法，一个团队能维护
    再用 C++ 模板在编译期把零件拼成具体 kernel

★ CUTLASS 那一堆吓人的模板参数，本质上就是把"乘法"变成"加法"。 理解了这一点，再看它的分层就顺了：每一层只负责一个正交的决策，层与层之间靠模板参数拼接。

3.7.3 分层结构

Device Level     GemmUniversalAdapter
                 └ 管：算 grid 大小、分配 workspace、启动 kernel
                   （唯一面向用户的那一层）
   │
Kernel Level     GemmUniversal<Mainloop, Epilogue, TileScheduler>
                 └ 管：把 Block 映射到 C 的哪一块、Split-K / Stream-K 怎么切
                   （§3.7.5 的调度策略换在这一层）
   │
Collective       CollectiveMainloop + CollectiveEpilogue
                 └ 管：整个 Block 的主循环（搬运 + 流水 + MMA）和收尾
                   （双缓冲级数、TMA、Warp Specialization 换在这一层）
   │
Tile Level       TiledMMA + TiledCopy + SmemLayout
                 └ 管：Warp 怎么分工、共享内存怎么摆（§3.4.3 的 swizzle 在这里）
   │
Atom Level       MMA_Atom（一条 mma / wgmma）+ Copy_Atom（一条 cp.async / TMA）
                 └ 管：包装单条 PTX 指令，屏蔽各代硬件的差异

自下而上读一遍就懂了：Atom 层把"这代硬件有哪条指令"这件事封起来，往上每一层都不用关心自己跑在 Ampere 还是 Hopper 上。 这是 CUTLASS 能同时支持五代 GPU 的原因，也是它模板嵌套这么深的代价来源。

3.7.4 自定义 Epilogue

// CUTLASS 的 Epilogue 支持"访问者模式"（EVT：Epilogue Visitor Tree，收尾访问者树）
// 可以把任意逐元素操作串在 GEMM 后面，全程不落 HBM

// 示例：GEMM + bias + ReLU，输出量化为 INT8
using EpilogueOp = cutlass::epilogue::thread::LinearCombinationRelu<
    ElementOutput,                     // 输出类型：INT8
    128 / cutlass::sizeof_bits<ElementOutput>::value,  // 向量化宽度（一次存 128 bit）
    ElementAccumulator,                // 累加器类型：FP32
    ElementComputeEpilogue,            // 中间计算精度：FP32
    cutlass::epilogue::thread::ScaleType::NoBetaScaling
>;

关键是累加器还在寄存器里的时候就把 bias、激活、量化全做完，只把最终的 INT8 结果写回 HBM。省下的不只是一趟往返，输出字节数还从 FP32 的 4 字节降到 1 字节。

3.7.5 Stream-K：解决 SM 吃不饱

先把问题定位准。 标准的 Data-Parallel 调度把 C 切成 Block Tile，一个 Block 一块。它的毛病不是"矩阵大小不能整除"，而是输出块的数量和 SM 数量对不上（01 章 §1.2.4 的波次量化）。

反例一：块数还不到 SM 数（注意 1024 能被 128 整除得干干净净）

M = N = 1024，BM = BN = 128
  输出块数 = (1024/128) × (1024/128) = 8 × 8 = 64 个
  H100 有 132 个 SM
  → 只有 64 个 SM 拿到活，68 个 SM 从头空到尾
  → 机器利用率 = 64 / 132 = 48%

反例二：块数刚过一个波次

M = N = 1536，BM = BN = 128
  输出块数 = 12 × 12 = 144 个
  波次 1：132 个块   波次 2：只剩 12 个块，120 个 SM 空转
  → 总耗时 2 个波次的时间
  → 机器利用率 = 144 / (132 × 2) = 55%

Stream-K 的做法：不按输出块分活，而是把总乘加工作量（所有块的 k 循环加起来）平均切成 132 份（或它的整数倍），一个 SM 一份。

Data-Parallel：      按 C 的块分活
                     SM0: [块0 的全部 K]   SM1: [块1 的全部 K]  ...  SM64~131: 空
                                                                      ↑ 浪费

Stream-K：           按总工作量分活
                     SM0: [块0 的 K 前半]  SM1: [块0 的 K 后半 + 块1 的 K 前段] ...
                     每个 SM 都拿到 64/132 = 0.485 个块的工作量

                     代价：一个输出块的部分和可能散在 2 个 SM 手里
                          → 需要一次跨 SM 的归约（通过全局内存的 workspace 汇总）

对反例一，理论上从 48% 提到接近 100%，约 2 倍加速（⚠️ 扣掉归约开销后实际略低）。矩阵越小、块数越接近 SM 数的非整数倍，Stream-K 收益越大；大方阵（几千个块）本来利用率就高，收益很小。

★ 顺带一提，Stream-K 的前身是 Split-K：固定把 K 维切成 k 份，块数 ×k，然后归约。Split-K 的问题是 k 是个要手调的常数，切多了归约开销大，切少了还是喂不饱。Stream-K 是"自动算出最优切法"的版本。

3.8 实测数字与选型建议

3.8.1 先算理论上界，再看实测

M=1 是推理的常态，也是最惨的形状。 先把它的理论上界算出来（BF16，N=K=4096）：

FLOP  = 2 × 1 × 4096 × 4096 = 33.55 MFLOP
Bytes = 读 A(1×4096) + 读 B(4096×4096) + 写 C(1×4096)，全部 ×2 B
      = (4096 + 16,777,216 + 4096) × 2 = 33.57 MB
                  ↑ B 矩阵占了 99.95%，这本质上是一次"把权重整个读一遍"

算术强度 = 33.55e6 ÷ 33.57e6 = 1.0 FLOP/Byte     ← 和附录 §B.2 一致 ✓
HBM 屋顶线上界 = 3350 GB/s × 1.0 = 3.35 TFLOPS
                 占 BF16 峰值的 3350/989000 = 0.34%

batch=1 的 GEMM 在物理上就跑不过 3.35 TFLOPS，和 kernel 写得多好完全无关。 这不是优化问题，是屋顶线问题——出路只有量化（06 章，权重字节数减半就快一倍）和攒 batch（09 章）。

顺便解一个有用的方程：M 要多大才能摆脱访存瓶颈？

I(M) = M·K·N / (M·K + K·N + M·N)，取 K = N = 4096
     = 4096M / (2M + 4096)
令 I = 295（屋脊点）：4096M = 590M + 1,208,320 → M ≈ 345

★ batch × seq 要大于约 345，GEMM 才有可能碰到算力上限。 这个数字解释了训练（batch×seq 动辄几万）和推理（batch=1）为什么是完全不同的两个优化问题。⚠️ 这是理想缓存假设下的下界，真机上要更大。

3.9 本章小结

一条主线：GEMM 优化 = 提高算术强度 = 让每个搬进来的字节多算几次

阶段 做了什么 算术强度（FP32） 在 H100 上的结果
朴素 一线程一元素，全从 HBM 读 0.25 差 FP32 屋脊点（20）80 倍
Block Tile 128×128 把 A/B 的块搬进共享内存 32 超过屋脊点，变 Compute Bound ✓
Thread Tile 8×8 外积，把操作数留在寄存器 共享内存流量降到 1/8 共享内存带宽刚好够用 ✓
双缓冲 搬运躲到计算背后 — 1.55×
Tensor Core 换 MMA 指令 — 算力 ×15，但瓶颈翻回访存侧
更大 tile + L2 + swizzle 把 BF16 的算术强度从 64 推上去 目标 295 cuBLAS 88–93%

三级分块：三段不同的路，各修一遍

级别 典型尺寸 对应存储（01 章） 管住哪段流量 卡住它的是什么
Block Tile 128×128×8 共享内存 HBM → 共享内存 寄存器（BM×BN 个累加器），不是共享内存
Warp Tile 64×32 寄存器文件 共享内存 → 寄存器 bank conflict（用 swizzle 解）
Thread Tile 8×8 线程私有寄存器 寄存器内部复用 共享内存带宽（下界 8）+ 255 寄存器上限（上界 8）

四条能背下来的结论

① 算术强度 = Block Tile 两条边的调和平均 ÷ 元素字节数
   128×128 的 FP32 tile → 128/4 = 32；BF16 → 128/2 = 64

② BK 不影响 HBM 总流量，它只影响共享内存占用和流水线粒度

③ tile 开不大的原因是寄存器（BM×BN 个累加器），不是共享内存

④ 双缓冲藏延迟，藏不掉带宽不够。带宽不够只能靠更大的 tile 和 L2

两个容易搞错的数字

  • 屋脊点分精度：FP32 是 20 FLOP/Byte（67 ÷ 3.35），BF16 是 295（989 ÷ 3.35）。拿 FP32 的例子去比 295 会得出荒谬的结论。
  • 989 不是 1979：1979 TFLOPS 是 2:4 结构化稀疏才有的数字，稠密 GEMM 用不上。

自测三题

  1. M = N = K = 2048，BF16（2 字节）。用 BM=BN=256 的 Block Tile，从 HBM 读 A 和 B 一共多少字节？算术强度是多少？比不分块省了几倍？
  2. 某 GEMM 的 Block Tile 是 BM=128、BN=64，Warp Tile 是 WM=32、WN=32，Thread Tile 是 TM=8、TN=4。这个配置自洽吗？每个 Block 有几个 Warp？每个 Warp 有几个线程？
  3. 一个 BF16 GEMM 的形状是 M=2048、N=K=4096，用 BM=BN=128 的分块。它需要多少个 Block？在 132 个 SM 的 H100 上会跑几个波次？机器利用率多少？换成 Stream-K 大约能快多少？

参考答案

  1. 调和平均 = 2 ÷ (1/256 + 1/256) = 256，算术强度 = 256 ÷ 2 = 128 FLOP/Byte。HBM 读量 = M·N·K·s·(1/BM + 1/BN) = 2048³ × 2 × (1/256 + 1/256) = 8.59e9 × 2 × 0.0078125 = 134.2 MB。不分块时是 2 × 2048³ × 2 B = 34.36 GB，省 256 倍（正好等于调和平均值 ✓）。顺带一提，128 仍然小于屋脊点 295，所以即使开到 256×256 这个形状还是 Memory Bound，要靠 L2 补——和 §3.3.6 的结论一致。参见 §3.3.2。
  2. 自洽 ✓。Warp 数 = (128/32) × (64/32) = 4 × 2 = 8 个 Warp。每 Warp 线程数 = (32/8) × (32/4) = 4 × 8 = 32 个 ✓（这一步必须正好是 32，否则配置就是错的——原稿里 WM=WN=64 配 TM=TN=8 会算出 64 个线程，那是一个不成立的配置）。Block 线程数 = 8 × 32 = 256，累加器总数 = 256 × 32 = 8192 = 128 × 64 ✓。参见 §3.4.1、§3.4.4。
  3. Block 数 = (2048/128) × (4096/128) = 16 × 32 = 512 个。波次数 = ceil(512 / 132) = 4 个波次，最后一波只有 512 − 3×132 = 116 个 Block。利用率 = 512 ÷ (132 × 4) = 97%。Stream-K 在这里几乎没有收益（最多 3%）——它只在块数少、波次少的时候才值钱，比如 §3.7.5 那个 64 个块的例子。参见 §3.7.5 和 01 章 §1.2.4。
