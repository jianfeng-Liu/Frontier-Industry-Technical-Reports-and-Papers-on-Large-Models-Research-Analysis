05 · 算子融合：消灭算子间的"搬运税"

前置：02 章（屋顶线）、03 章（GEMM）
目标：搞懂算子融合的分类、实现路径、以及 CUDA Graph 和 torch.compile 怎么自动帮你做这件事。

本章关键词

算子融合（Operator Fusion / Kernel Fusion）—— 把多个算子合并成一个 kernel，消除中间结果写入 HBM 再读出的往返开销。
搬运税（Memory Traffic Tax）—— 两个算子串联时，中间激活值必须经过 HBM 的写入和读出，这部分带宽消耗是纯粹的浪费。
CUDA Graph —— 把一批 kernel 调用录制成静态图，一次提交给 GPU，消除逐 kernel 的 CPU 启动延迟。
torch.compile —— PyTorch 2.0 引入的编译接口，后端 TorchInductor 自动发现融合机会并生成 Triton kernel。
Epilogue Fusion（收尾融合）—— GEMM 完成后，把 bias 加法、激活函数等 element-wise 操作在 GEMM 的写出阶段顺带完成，不增加额外的内存往返。
水平融合（Horizontal Fusion）—— 把多个形状相同的独立 kernel 合并成一个，减少 kernel 启动次数。
垂直融合（Vertical Fusion）—— 把前后依赖的多个 kernel 串联成一个，消除中间数据落盘。

5.1 搬运税：为什么相邻算子之间存在浪费

以最简单的例子说明：

# 两步操作
x = layer_norm(x)   # kernel 1
x = linear(x)       # kernel 2

不融合时的数据路径：

HBM                SRAM/寄存器
  x_input  ──读──→  [ LayerNorm 计算 ]  ──写──→  x_normed（HBM）
  x_normed ──读──→  [ Linear 计算    ]  ──写──→  x_output（HBM）

每个 kernel 都要把输入从 HBM 读进来，把输出写回 HBM。中间的 x_normed 经历了一次写 + 一次读，而这份数据只被下一步用了一次——这就是搬运税。

对于 Hidden Size = 8192，Batch=64，一次 LayerNorm 的输出是 64 × 8192 × 2 Bytes = 1 MB。
这 1 MB 写进 HBM 再读出来，浪费了 2 MB 的带宽。H100 带宽 3.35 TB/s，乍看不多，但模型有几百个这样的点，累积起来占比可达 20–40%。

5.2 融合的三种模式

模式一：垂直融合（最常见，效果最好）

把前后依赖的 kernel 串联，中间结果留在寄存器 / SRAM，不落 HBM。

例1：LayerNorm + Linear（GEMM 的 Epilogue 融合）
  未融合：HBM→LayerNorm→HBM→Linear→HBM
  融合后：HBM→[LayerNorm→Linear]→HBM   中间结果从不离开 SRAM

例2：Linear + Activation（SiLU、GeLU）
  未融合：HBM→Linear→HBM→SiLU→HBM
  融合后：HBM→[Linear→SiLU]→HBM

例3：FlashAttention（QK^T → Softmax → ×V）
  未融合：三步各写一次 HBM，中间 N×N 矩阵占 GB 级别
  融合后：一个 kernel，N×N 矩阵从未写进 HBM

模式二：水平融合

把多个形状相同、逻辑独立的 kernel 合并，减少 kernel 启动次数和调度开销。

例：MHA 里三个 QKV 投影矩阵
  未融合：linear(x, W_Q), linear(x, W_K), linear(x, W_V)  → 3 次 GEMM，3 次 kernel 启动

  融合后：把 W_Q, W_K, W_V 按列拼成 [W_Q|W_K|W_V]（shape: H × 3H）
          linear(x, W_QKV)  → 1 次 GEMM，一次性算出 Q、K、V

  收益：kernel 启动次数 3→1，同时 GEMM 形状更大，Tensor Core 利用率更高

模式三：Epilogue 融合（GEMM 收尾融合）

GEMM 的最后一步是把结果写回 HBM。在写之前插入额外操作，不增加额外的内存读写：

标准 GEMM：  C = A × B → [写 HBM]
Epilogue 融合：C = activation(A × B + bias) → [写 HBM]
              └── bias 加法和激活函数在寄存器里完成，不多一次 HBM 来回 ──┘

CUTLASS 的 Epilogue Visitor Tree（EVT）支持把任意 element-wise 操作链接在 GEMM 后面，第 03 章已介绍。

5.3 融合的收益量化

以 H100 + LLaMA-70B 规模的 FFN 层为例：

FFN 结构（SwiGLU）：
  gate = linear(x, W_gate)   # (B×S, H) → (B×S, 4H)
  up   = linear(x, W_up)     # (B×S, H) → (B×S, 4H)
  h    = silu(gate) * up     # element-wise
  out  = linear(h, W_down)   # (B×S, 4H) → (B×S, H)

B=4, S=2048, H=8192, 4H=28672（FFN 扩展比）

未融合：
  W_gate 结果：4 × 2048 × 28672 × 2 = 470 MB → 写 HBM
  W_up 结果：  470 MB → 写 HBM
  silu(gate) * up：470 MB → 读写 HBM
  合计额外 HBM 流量 ≈ 1.4 GB

融合后（gate 和 up 并成 W_gate_up，结果直接在 Epilogue 里做 SiLU + 乘法）：
  额外 HBM 流量 ≈ 0

时间节省（H100 3.35 TB/s）：1.4 GB / 3350 GB/s ≈ 0.42 ms / FFN 层
32 层模型：32 × 0.42 = 13.4 ms（仅 FFN 部分，batch=4, seq=2048）

5.5 CUDA Graph：消除 kernel 启动开销

问题：kernel 启动延迟累积

每次通过 CUDA API 启动一个 kernel，CPU 需要：
1. 打包参数（~1 µs）
2. 提交给 GPU 驱动（~2–5 µs）
3. GPU 的 Command Queue 解析并调度（~1–2 µs）

合计约 5–10 µs / kernel。

一个 32 层 Transformer，每层约 20 个 kernel，共 640 个 kernel：

640 × 7 µs = 4.5 ms 仅用于 kernel 启动

对于推理延迟 10–30 ms 的场景，这是 15–45% 的额外开销。

CUDA Graph 的解决方式

录制阶段（一次性，通常在第一次推理时）：

import torch

# 准备固定形状的输入
x = torch.randn(batch, seq_len, hidden, device='cuda')

# 录制图
g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    y = model(x)   # 所有 kernel 调用都被录制下来

# 之后每次推理只需：
g.replay()         # 一次 GPU 命令提交，所有 kernel 按图执行

限制：
- 输入形状必须固定（动态 shape 不支持，或需要多套图）
- 不支持 Python 控制流（if/for 内部不能动态决定 kernel）
- KV Cache 增长时指针会变，需要特殊处理（vLLM 用 CUDA Graph + 固定最大长度的 KV buffer）

典型收益：推理延迟减少 10–25%，对短序列、小 batch 效果更明显（因为 kernel 启动开销占比更高）。

5.6 torch.compile：自动算子融合

PyTorch 2.0 引入 torch.compile，让你用一行代码获得自动算子融合：

import torch

model = MyModel().cuda()
model = torch.compile(model)   # ← 一行搞定

# 第一次调用时编译（约 10–60 秒），之后都用编译版
output = model(input)

torch.compile 的内部流程

Python 模型代码
      ↓  TorchDynamo（Python 字节码捕获）
计算图（FX Graph）
      ↓  AOTAutograd（提前展开 Autograd）
前向 + 反向的联合图
      ↓  TorchInductor（后端代码生成）
      ├─→ Triton kernel（GPU，自动融合）
      └─→ C++ kernel（CPU）

TorchInductor 的融合策略：

  1. Pointwise 融合：连续的 element-wise 算子（加法、乘法、激活函数）自动融合成一个 Triton kernel
  2. Reduction 融合：连续的 reduction（sum、mean、LayerNorm 内部）合并
  3. GEMM + Epilogue：线性层后面跟着 element-wise 操作，自动融合进 GEMM 的 Epilogue

实测收益（LLaMA 系列，H100）

场景 原生 PyTorch torch.compile 提升
训练前向+反向，batch=8 100% 115–130% 15–30%
推理，batch=1 100% 120–140% 20–40%
推理，batch=32 100% 110–120% 10–20%

⚠️ 第一次调用会触发编译，有 30–120 秒延迟。生产环境需要提前 warm-up 或使用 torch.compile 的 AOT（Ahead-of-Time）导出模式。

5.7 哪些融合值得做，哪些不值得

融合目标 值得做 原因
LayerNorm / RMSNorm + 后续 Linear ✅ 非常值得 LN 是强 Memory Bound，融合节省 100% 的中间 HBM 流量
激活函数（SiLU、GeLU）融合进 Linear ✅ 非常值得 激活函数算术强度 ~1，单独跑是纯浪费
QKV 投影合并 ✅ 值得 三合一 GEMM 更大，Tensor Core 利用率更高
FlashAttention（QK^T + Softmax + ×V） ✅ 必须做 中间 N×N 矩阵不能存 HBM
两个 Compute Bound 的大 GEMM 融合 ⚠️ 谨慎 两个都打满算力，融合后可能因 SRAM 不够反而更慢
带控制流的算子（条件路由、动态 shape） ❌ 难做 CUDA Graph 不支持，torch.compile 降级为图模式

5.8 本章小结

算子融合的本质：减少 HBM 往返次数

三种模式：
  垂直融合：串联算子合并，中间结果留在 SRAM/寄存器
  水平融合：同形状独立算子合并，减少 kernel 启动
  Epilogue 融合：GEMM 写出阶段顺带做 element-wise 操作

实现路径（优先级从高到低）：
  1. torch.compile  ← 零代码，自动融合 pointwise 和 reduction
  2. CUDA Graph     ← 消除启动延迟，推理场景标配
  3. 已有融合库（flash-attn, xformers）← 高频 pattern 直接用
  4. Triton 自定义  ← 需要定制逻辑
  5. CUDA + CUTLASS ← 极致性能，开发成本高

Memory Bound 的算子融合收益最大；
两个 Compute Bound 的 GEMM 融合不一定更快。
