05 · 算子融合：消灭算子间的"搬运税"

前置：01 章（GPU 硬件基础）、02 章（屋顶线）、03 章（GEMM）
目标：把"融合能省多少"从一句口号变成一笔你自己能算出来的账；搞清楚哪些算子能融、哪些不能融、判据是什么；知道 CUDA Graph 和 torch.compile 各自解决的是哪一半问题。
读法：本章的骨架是一条真实的小算子链，从 §5.2 开始一路算到章末。建议拿纸笔跟着算，所有数字都能自己验算。

本章关键词

算子融合（Operator Fusion / Kernel Fusion）—— 把多个算子合并成一个 kernel（核函数），让中间结果留在片上，不写回显存再读出来。
搬运税（Memory Traffic Tax）—— 两个算子串联时，中间结果必须经过一次"写显存 + 读显存"的往返，这部分带宽消耗不产生任何新信息，是纯浪费。
HBM（High Bandwidth Memory，高带宽显存）—— GPU 的主内存，H100 SXM5 是 80 GB / 3.35 TB/s。本章所有"落地""往返"说的都是它。
SRAM（Static Random-Access Memory，静态随机存储器）—— 片上存储的统称，在 CUDA 里表现为共享内存（Shared Memory，每个 SM 最多 228 KB）和寄存器（Register，每个 SM 256 KB）。
SM（Streaming Multiprocessor，流式多处理器）—— GPU 的基本计算单元，H100 有 132 个。
垂直融合（Vertical Fusion）—— 把前后有依赖的算子串成一个 kernel，消除中间结果落地。收益最大的一类。
水平融合（Horizontal Fusion）—— 把彼此独立、形状相同的算子合并成一个 kernel，减少启动次数、增大计算规模。
Epilogue 融合（Epilogue Fusion，收尾融合）—— 在 GEMM 把结果写回 HBM 之前，顺手把加偏置、激活函数等逐元素操作做完。
Prologue 融合（Prologue Fusion，前置融合）—— 在 GEMM 从 HBM 读入数据的那一刻顺手做预处理（如反量化）。比 Epilogue 难得多，原因见 §5.4。
GEMM（General Matrix Multiply，通用矩阵乘）—— C = A × B，深度学习里算力消耗的绝对主体。
算术强度（Arithmetic Intensity，记作 I）—— 每搬运 1 字节能做多少次浮点运算，单位 FLOP/Byte。屋顶线模型的横轴，见 02 章。
kernel 启动开销（Kernel Launch Overhead）—— CPU 发起一次 kernel 调用到 GPU 真正开跑之间的代价，约 3–10 µs。
Host Bound（下发受限）—— GPU 算得比 CPU 发得快，硬件在饿着等命令。这是小算子场景真正的敌人，融合只能解决一半，另一半靠 CUDA Graph。
CUDA Graph —— 把一整串 kernel 调用录成一张静态图，之后每次只用一次 API 调用整体重放。
torch.compile / TorchInductor —— PyTorch 2.0 的编译接口和它的 GPU 后端，自动发现融合机会并生成 Triton kernel。

5.1 接住上一章的结尾：一个 kernel 的成本由三部分组成

01 章 §1.8.2 最后算了一笔账，结论很扎心：y[i] = x[i] * 2，N = 100 万，在 H100 上——

kernel 真正执行时间  ≈ 2.39 µs   （8 MB ÷ 3.35 TB/s）
kernel 启动开销      ≈ 3–10 µs   （CPU 打包参数 + 提交驱动 + GPU 命令队列解析）

启动开销比 kernel 本身还长。

把这个观察推广一下：跑一个算子的总成本 = 启动开销 + 搬数据的时间 + 真正算的时间。对深度学习里那一大堆逐元素算子（激活函数、归一化、残差加、缩放、类型转换），这三项的量级是：

成本项 典型量级 由什么决定
启动开销 3–10 µs 和数据量完全无关，每次都要付
搬数据 张量字节数 ÷ 3.35 TB/s 和数据量成正比
真正算 几乎为零 算术强度只有 1–3 FLOP/Byte，离屋脊点 295 差两个数量级

第三项基本可以忽略——附-速查表 §C 里那些算子的算术强度全在个位数，意思是算力利用率不到 1%，GPU 的绝大部分时间在等数据。

于是优化方向只剩两个，而且它们对应两种不同的武器：

敌人 ①：中间结果反复进出 HBM        →  武器：算子融合   （§5.2 – §5.4、§5.6、§5.7）
敌人 ②：kernel 太多，每个都要付启动费 →  武器：CUDA Graph（§5.5）

这两件事是正交的：
  融合    减少 kernel 数量 和 HBM 流量，但剩下的每个 kernel 还是要启动
  CUDA Graph 不减少 kernel 数量、不减少一个字节的 HBM 流量，只把每次启动的代价压到接近零

★ 本章最容易被混淆的一点，先在这里说清楚：很多材料把"融合"和"CUDA Graph"当成同一件事的两种说法，其实它们解决的是完全不同的瓶颈。融合攻的是带宽，CUDA Graph 攻的是下发。判断你该用哪个，看 §5.5 末尾那条判据。生产环境里通常两个都要开。

5.2 把账算出来：x → LayerNorm → GELU → 残差加

这一节是全章的骨架。后面所有结论，都是这笔账的推论。

5.2.1 设定：一条真实的残差支路

Transformer 的每一层里都有这样一段（这里用最朴素的写法，先不管它在 PyTorch 里长什么样）：

n = layer_norm(x)      # 归一化
g = gelu(n)            # 激活函数
y = x + g              # 残差加（注意：这里第二次用到了 x）

给定形状（取 LLaMA-3-8B 的配置，batch = 4、序列长 2048）：

量 值 说明
token 数 M 8192 = batch 4 × 序列长 2048
隐藏维度 H 4096 LLaMA-3-8B 的 hidden_size
数据类型 BF16 2 字节/元素
一个张量的大小 T 67,108,864 字节 = 64 MiB = 8192 × 4096 × 2

后面所有账都用 T = 64 MiB 这一个单位来数，这样不用反复乘除。硬件按 附-速查表 §A：H100 SXM5，HBM3 带宽 3.35 TB/s。

5.2.2 融合前：数据在 HBM 和片上之间弹三个来回

融合前：3 个 kernel，中间结果两次落地 HBM

  HBM: x
    │  读 T
    ▼
  片上: LayerNorm 计算
    │  写 T   ← 中间结果 n 落地。这次写是纯浪费：n 只有下一个 kernel 会用
    ▼
  HBM: n
    │  读 T   ← 又得原样读回来。这次读同样是纯浪费
    ▼
  片上: GELU 计算
    │  写 T   ← 中间结果 g 落地，同样浪费
    ▼
  HBM: g
    │  读 T + 再读一遍 x（共 2T）
    ▼
  片上: 残差加
    │  写 T
    ▼
  HBM: y

逐个 kernel 把字节数列出来：

# kernel 从 HBM 读 写回 HBM 小计 时间（÷ 3.35 TB/s）
① LayerNorm x（1 T） n（1 T） 2 T = 128 MiB 40.1 µs
② GELU n（1 T） g（1 T） 2 T = 128 MiB 40.1 µs
③ 残差加 g（1 T）+ x（1 T） y（1 T） 3 T = 192 MiB 60.1 µs
合计 5 T 2 T 7 T = 448 MiB 140.2 µs

（LayerNorm 还要读 gamma、beta 两个长度 4096 的向量，共 16 KB，占总量的 0.003%，忽略。）

kernel 启动次数：3 次。

5.2.3 融合后：只进出一次

融合后：1 个 kernel，中间结果从不出片

  HBM: x
    │  读 T   ← 全流程唯一一次读
    ▼
  片上: LayerNorm ─→ GELU ─→ 残差加
        n 和 g 全程活在寄存器里，一个字节都没进过 HBM
        x 读进来之后也一直留在寄存器里，残差加直接取用，不需要第二次读
    │  写 T   ← 全流程唯一一次写
    ▼
  HBM: y
从 HBM 读 写回 HBM 合计 时间
融合 kernel x（1 T） y（1 T） 2 T = 128 MiB 40.1 µs

kernel 启动次数：1 次。

5.2.4 对比

HBM 流量：  448 MiB  →  128 MiB      省掉 320 MiB（71%）
理论耗时：  140.2 µs →  40.1 µs      加速比 7 / 2 = 3.5 倍
启动次数：      3    →      1

★ 加速比 3.5 倍是怎么来的，值得盯着看一眼：融合前后做的浮点运算一模一样，一个 FLOP 都没省。省下来的全部是"往返字节数"——从 7 T 降到 2 T。而这类算子的耗时完全由字节数决定，所以字节数降到 2/7，时间就降到 2/7。融合的收益 = 字节数的比值，这个公式贯穿全章。

★ 顺便注意：这个 3.5 倍和形状无关。换成 M = 4096、H = 8192，或者换成 FP16，7 T / 2 T 的比值不变，加速比还是 3.5 倍。决定加速比的是链的结构（几个算子、每个读写几份），不是张量多大。张量大小只决定省下来的绝对时间是多少微秒。

5.2.5 在屋顶线上看这件事

按 02 章 的框架再看一遍。这条链的浮点运算量：LayerNorm 每元素约 7 FLOP，GELU（tanh 近似）每元素约 18 FLOP，残差加 1 FLOP，合计 ⚠️ 约 25 FLOP/元素（估算值，依据是把每条算式的乘加逐个数出来，tanh 按 10 FLOP 计）。

元素总数 = 8192 × 4096 = 33,554,432
总 FLOP  = 33,554,432 × 25 ≈ 8.39 × 10⁸ = 0.84 GFLOP

融合前算术强度 I = 8.39e8 FLOP ÷ 4.698e8 Byte = 1.79 FLOP/Byte
融合后算术强度 I = 8.39e8 FLOP ÷ 1.342e8 Byte = 6.25 FLOP/Byte

H100 屋脊点 = 295 FLOP/Byte（BF16 稠密 989 TFLOPS ÷ 3.35 TB/s）
→ 融合前后都远在屋脊点左边，都是彻底的 Memory Bound（内存受限）

性能（TFLOPS，纵轴）
                                          ┌─────────  BF16 稠密峰值 989
   989 ┤                                 ╱
       │                               ╱
       │                             ╱
       │                           ╱      斜边上的点：性能 = 3350 GB/s × I
  20.9 ┤              B          ╱
   6.0 ┤      A                ╱
       └──────┴───────┴──────────────────────────→  算术强度 I（FLOP/Byte）
            1.79    6.25              295

   A = 融合前（6.0 TFLOPS，占峰值 0.6%）
   B = 融合后（20.9 TFLOPS，占峰值 2.1%）
   295 = 屋脊点，两个点都远在它左边

★ 融合是在屋顶线上"向右平移"，不是"向上抬升"。 融合后算力利用率从 0.6% 涨到 2.1%，依然惨不忍睹——但这不重要，因为时间确实降到了 2/7。对 Memory Bound 的算子，唯一有意义的优化目标是减少字节，不是提高算力利用率。反过来说，如果你把两个已经 Compute Bound（算力受限）的算子融在一起，它们本来就在屋顶的水平段上，向右平移毫无意义——这正是 §5.4 判据④要讲的事。

5.2.6 换个场景，结论会翻过来：Decode 的小形状

同一条链，换成推理的 Decode（逐 token 生成）阶段：batch = 32 个序列，每步每个序列只算 1 个 token，所以 M = 32（而不是 8192），H 还是 4096。

T = 32 × 4096 × 2 = 262,144 字节 = 256 KiB

融合前 HBM 时间 = 7 T = 1.75 MiB ÷ 3.35 TB/s = 0.55 µs
融合后 HBM 时间 = 2 T = 0.50 MiB ÷ 3.35 TB/s = 0.16 µs
省下的搬运时间  = 0.39 µs

融合前启动开销 = 3 × (3–10 µs) = 9–30 µs
融合后启动开销 = 1 × (3–10 µs) = 3–10 µs
省下的启动开销 = 6–20 µs

省下的启动开销是省下的搬运时间的 15–50 倍。 场景一换，同一个融合动作的收益来源完全变了：训练的大形状下，融合省的是带宽；Decode 的小形状下，融合省的是启动次数。

更要命的是最后那一行：融合完之后，这个 kernel 执行 0.16 µs，启动却要 3–10 µs——启动开销是 kernel 本身的 20–60 倍。融合已经把 kernel 数从 3 压到 1，没法再压了，但每个 kernel 的固定启动费还在。这就是 CUDA Graph（§5.5）存在的全部理由。

训练（M = 8192） Decode（M = 32）
融合前耗时主体 HBM 搬运 140 µs kernel 启动 9–30 µs
融合的主要收益 带宽：140 → 40 µs 启动次数：3 → 1
融合后还剩什么问题 基本解决了 启动开销仍是执行时间的几十倍
下一步该上什么 继续找别的融合点 CUDA Graph

5.2.7 摊到整个模型：别高估，也别低估

把上面的方法套到 LLaMA-3-8B 一整层（H = 4096，FFN 中间维度 I = 14336，M = 8192 token，BF16）。逐元素算子的 HBM 流量（T = 64 MiB，T_I = M × I × 2 = 234.9 MB）：

位置 流量
Attention 前的 RMSNorm 2 T
Attention 后的残差加 3 T
FFN 前的 RMSNorm 2 T
SwiGLU 的 silu(gate) * up 3 T_I（读 gate、读 up、写 h）
FFN 后的残差加 3 T
合计 10 T + 3 T_I = 671 MB + 705 MB = 1376 MB 
逐元素部分理论耗时 = 1.376 GB ÷ 3.35 TB/s = 411 µs / 层

同一层的 GEMM 算力消耗（QKVO 投影 + FFN 三个矩阵）：
  ≈ 29 × M × H² = 29 × 8192 × 4096² ≈ 3.99 TFLOP
  ⚠️ 按实测可达 600 TFLOPS 估算（约为 989 峰值的 60%）→ 6.64 ms / 层

逐元素部分占比 = 411 µs ÷ (6640 + 411) µs ≈ 5.8%

⚠️ 本章旧版这里写的是"累积起来占比可达 20–40%"，这个数字对大 batch 训练是明显高估的，已改正。 按上面的推演，大 batch 训练前向里逐元素算子约占 6% 量级；把它们全部融掉，整体加速约 3–4%（因为融合只能消掉其中一部分，不是全部）。听起来不多，但这是几乎零风险、零精度损失的 3–4%，而且 torch.compile 一行代码就能拿到大半。

真正的大头在另外两个地方，它们才是"融合"这件事的高光时刻：

  • FlashAttention：把 QK^T → Softmax → ×V 融成一个 kernel，避免 N×N 的中间矩阵落地。按 附-速查表 §B.4，N = 8192、32 个 head 时这个矩阵就有 4 GB，N = 32768 时 64 GB——超过 H100 的 80 GB 显存。这里融合不是提速手段，是可行性前提。见 04 章。
  • Decode / 小 batch 推理：如 §5.2.6，逐元素算子和启动开销加起来能占到大半。这里融合 + CUDA Graph 通常能拿到 20–40% 的延迟下降（⚠️ 量级，随模型大小和并行策略浮动）。原文那个 20–40% 放在这个场景才成立。

5.3 三种融合模式，每种算一笔账

5.3.1 垂直融合：串联的算子合并（收益最大）

就是 §5.2 讲的那件事：把前后有数据依赖的算子串成一个 kernel，中间结果留在寄存器 / 共享内存。

例子 融合前 融合后 收益来源
LayerNorm → GELU → 残差加 7 T 2 T 3.5×，见 §5.2
Linear → SiLU GEMM 写出 + SiLU 读写 GEMM 的 Epilogue 里做 SiLU 省 2 次 T 的往返
QK^T → Softmax → ×V 中间矩阵 N×N 落地（GB 级） 从不落地 从"跑不动"变成"跑得动"

垂直融合的判断口诀：如果算子 B 的输入就是算子 A 的输出，而且这份中间结果除了 B 没人用，那它进出 HBM 的那一趟就是纯浪费，值得融。

5.3.2 水平融合：独立的同形算子合并

把彼此没有依赖、形状相同的多个算子合并成一个更大的 kernel。最经典的例子是 Attention 的 Q、K、V 三个投影矩阵：

融合前（MHA，32 个 head × head_dim 128，所以 Q/K/V 各是 4096 × 4096）：
    Q = x @ W_Q      ← GEMM 1，读 x
    K = x @ W_K      ← GEMM 2，又读一遍 x
    V = x @ W_V      ← GEMM 3，再读一遍 x

融合后：把三个权重按列拼成一个 4096 × 12288 的大矩阵
    QKV = x @ [W_Q | W_K | W_V]     ← 1 个 GEMM，x 只读一遍
    再把结果沿列切三刀，拿到 Q、K、V

训练形状（M = 8192）下算账：

读 x 读权重 写输出 合计
三个独立 GEMM 3 × 67.1 MB 3 × 33.6 MB 3 × 67.1 MB 503.3 MB
合并成一个 GEMM 1 × 67.1 MB 100.7 MB 201.3 MB 369.1 MB
省下 134.2 MB（27%） — — —

但是这 27% 换不来时间。算一下这个 GEMM 的算术强度：

FLOP  = 2 × 8192 × 4096 × 12288 = 8.25 × 10¹¹
Byte  = 3.69 × 10⁸
I     = 8.25e11 ÷ 3.69e8 ≈ 2234 FLOP/Byte  ≫ 295（屋脊点）
→ 这是彻底的 Compute Bound，时间由算力决定，和字节数无关

★ 省字节只在 Memory Bound 的一侧才能兑现成时间。 这条判断在整章反复出现：同一个融合动作，放在 Memory Bound 的算子上是赚的，放在 Compute Bound 的算子上是白忙。

那 QKV 水平融合到底赚在哪？赚在 Decode。 同样的三个 GEMM，M 从 8192 降到 32：

GEMM 常见的分块是 BLOCK_M × BLOCK_N = 64 × 128（一个 Block 算输出的一小块）

单个 QKV GEMM（M=32, N=4096）：
  M 方向只需要 1 个行块（32 < 64，一个块就吃下了）
  N 方向 4096 ÷ 128 = 32 个列块
  → 总共只有 32 个 Block！而 H100 有 132 个 SM
  → 100 个 SM 完全空转，机器利用率 24%     ← 01 章 §1.2.4 的尾巴效应

合并后（M=32, N=12288）：
  N 方向 12288 ÷ 128 = 96 个列块 → 96 个 Block
  → 机器利用率 73%，比之前好 3 倍
  → 启动次数也从 3 降到 1

所以水平融合的三条收益，在不同场景下权重完全不同：

收益 训练大 batch Decode 小 batch
输入只读一遍 省 27% 字节，但 Compute Bound，白省 字节本来就少，可忽略
kernel 启动次数 3 → 1 占比极小 显著
GEMM 规模变大、SM 利用率提高 本来就够大，提升有限 24% → 73%，最主要的收益

⚠️ 一个常见的错误说法要纠正：很多材料（包括本章旧版）说"QKV 拼成 H × 3H"。这只在 MHA（Multi-Head Attention，多头注意力）下成立。现在主流模型用的是 GQA（Grouped-Query Attention，分组查询注意力），K 和 V 的 head 数远少于 Q。LLaMA-3-8B 是 32 个 Q head、8 个 KV head，head_dim = 128，所以合并后的矩阵是 4096 × (4096 + 2×8×128) = 4096 × 6144，不是 4096 × 12288。拼错了会静默产生错误结果——切分偏移量全乱，但不报错。

5.3.3 Epilogue 融合：GEMM 写出前顺手做完

GEMM 算完一个输出块之后，这个块正躺在寄存器里，马上要写回 HBM。在写之前插进去一段逐元素运算，是完全免费的——数据本来就在手上。

标准 GEMM：
    寄存器里的 C 块  ──写──→  HBM
    然后另起一个 kernel：HBM ──读──→ 加 bias、算激活 ──写──→ HBM

Epilogue 融合：
    寄存器里的 C 块 ──→ 加 bias ──→ 算激活 ──→ 写 HBM
                      └── 这一段全程在寄存器里，一次 HBM 往返都不多

用 LLaMA-3-8B 的 FFN（SwiGLU）算一笔完整的账。结构是：

gate = x @ W_gate        # (8192, 4096) → (8192, 14336)
up   = x @ W_up          # (8192, 4096) → (8192, 14336)
h    = silu(gate) * up   # 逐元素
out  = h @ W_down        # (8192, 14336) → (8192, 4096)

记 T_I = 8192 × 14336 × 2 = 234,881,024 字节 ≈ 234.9 MB（中间张量的大小）。只数"从 gate/up 算出来"到"被 W_down 读走"这段的流量：

步骤 未融合 Epilogue 融合后
写出 gate 1 T_I —
写出 up 1 T_I —
SiLU-乘法 kernel 读 gate 1 T_I —
SiLU-乘法 kernel 读 up 1 T_I —
写出 h 1 T_I 1 T_I
W_down 的 GEMM 读 h 1 T_I 1 T_I
合计 6 T_I = 1.41 GB 2 T_I = 470 MB 
省下 4 T_I = 939.5 MB
时间收益 = 939.5 MB ÷ 3.35 TB/s = 280 µs / 层
32 层    = 9.0 ms（对照：整个前向 ⚠️ 约 213 ms，即约 4.2%）

⚠️ 本章旧版这里有三处错误，逐条改正：① 旧版写"B=4, S=2048, H=8192, 4H=28672"——4 × 8192 = 32768，28672 根本不是 4H，它是 LLaMA-70B 的 intermediate_size，比值是 3.5 不是 4（SwiGLU 有三个矩阵，所以中间维度按 8/3 × H 再向上取整对齐，不是 4H）。② 旧版只数了 3 份流量（1.4 GB），漏掉了 gate 和 up 的读回，实际是 6 份。③ 旧版说"融合后额外 HBM 流量 ≈ 0"，这是错的——h 必须落地，因为下一步 W_down 要沿着 14336 这一维做归约，而一个 Block 拿不到完整的一行 h（原因见 §5.4 反例 2）。④ 旧版说"32 层模型"却用的是 LLaMA-70B 的维度，70B 是 80 层。本节改用 LLaMA-3-8B 全套自洽的配置。

CUTLASS 的 EVT（Epilogue Visitor Tree，收尾访问者树）可以把任意一串逐元素操作挂在 GEMM 后面，细节见 03 章。

5.3.4 三种模式对照

合并的对象 省掉的是 典型收益 难度
垂直融合 前后有依赖的算子 中间结果的 HBM 往返 3–5× （对 Memory Bound 链） 中
水平融合 彼此独立的同形算子 启动次数 + 输入重复读 + SM 空转 Decode 下 2–3× 低
Epilogue 融合 GEMM + 它后面的逐元素算子 中间结果的 HBM 往返 省 2/3 的中间流量 低（库已支持）
Prologue 融合 GEMM + 它前面的逐元素算子 同上 通常做不到，见 §5.4 反例 1 高

5.4 能不能融：五条判据和四个反例

到这里为止都在讲"融合有多好"。这一节讲反面：什么时候融不了，什么时候融了反而更慢。这比记住一张"可融算子清单"有用得多——清单会过时，判据不会。

5.4.1 五条判据

判据①：消费者的每个输出，依赖生产者输出的哪些元素？

这是最根本的一条。三种情况，难度天差地别：

一对一（逐元素）      消费者的第 i 个输出只依赖生产者的第 i 个输出
                      例：GELU 之后接残差加
                      → 随便融，中间值放寄存器就行            【最容易】

行内归约              消费者的一个输出依赖生产者的一整行
                      例：LayerNorm、Softmax（要整行求和）
                      → 能融，但要求"一整行装得进片上"，见判据②

跨块归约 / 转置       消费者要的元素由别的 Block 产出
                      例：矩阵转置、沿 batch 维的归约
                      → 一个 kernel 里做不到（Block 之间不能同步，
                        原因见 01 章 §1.2.3：Block 终身绑定在一个 SM 上，
                        没有共同的片上存储）                  【基本不能融】

判据②：需要同时留在片上的中间结果，装得下吗？

片上预算（H100，每个 SM）：
    共享内存  最多 228 KB
    寄存器    256 KB

但这是一个 SM 的总量，要分给同时驻留的多个 Block。
实际给一个 Block 的预算 ⚠️ 通常按 100 KB 上下估（留出双缓冲和 Occupancy 的余地）。
预算超了会发生什么：Occupancy 掉（01 章 §1.6）或寄存器溢出到 HBM（01 章 §1.3），
两种都可能让"融合版"比"不融版"还慢。

判据③：这份中间结果被几个消费者用？

被 k 个消费者用，融进每个消费者就要重算 k 遍。划算的条件是：(k−1) × 重算成本 < (k−1) × 一次 HBM 往返，也就是重算比搬运便宜。对逐元素算子，重算几乎免费，所以通常划算；对一个大 GEMM，重算贵得离谱，绝不能这么干。

★ FlashAttention 的反向传播用的正是这一招：不保存前向的 N×N 注意力矩阵，反向时重新算一遍。因为"重算一个 GEMM"比"从 HBM 读 4 GB"还快。这是判据③的极端应用，见 04 章。

判据④：两边各自的瓶颈类型是什么？

生产者 消费者 融合是否值得 原因
Memory Bound Memory Bound ✅ 几乎必赚 两边都靠减字节提速，字节减了时间就减
Compute Bound Memory Bound ✅ 赚 把小的"藏"进大的执行时间里，相当于白送
Memory Bound Compute Bound ✅ 赚 同上
Compute Bound Compute Bound ⚠️ 通常不赚，可能亏 两边本来就在屋顶的水平段，减字节不改变时间；而融合会同时占用两份寄存器和共享内存，把 Occupancy 压下去，反而变慢

判据⑤：形状和控制流稳定吗？

融合 kernel 是针对特定形状编译出来的。如果形状每步都变（变长序列、动态 batch）、或者中间有依赖数据的分支（MoE 的专家路由、早退），融合 kernel 要么退化成一堆特化版本，要么根本编不出来。

5.4.2 四个反例（都带数字）

反例 1：把 LayerNorm 融进后面 Linear 的输入端（Prologue）——做不到

直觉上"LayerNorm 之后马上是 Linear，应该能融"。算一下就知道为什么不行：

Linear 就是 GEMM：out = LayerNorm(x) @ W，x 是 (M, K)，K = 4096

GEMM 的一个 Block 负责算 out 的一个 128 × 128 块。
它的做法是沿 K 方向分块，一次只读 x 的 128 × 32 一小片（01 章说的分块复用）。

但 LayerNorm 要算一整行（K = 4096 个元素）的均值和方差，才能归一化任何一个元素。
一个 Block 要缓存 128 行 × 4096 列 × 2 字节 = 1,048,576 字节 = 1 MiB
                                              ▲
                              共享内存上限 228 KB，超了 4.6 倍   ✗ 判据② 不过

实践中的做法：LayerNorm 单独跑一个 kernel（它本来就便宜，2 T 而已），或者——更聪明的办法——把它融到前一个算子的 Epilogue 里。在 Transformer 里，LayerNorm 前面正好是残差加，两者融成一个 AddRMSNorm kernel 是标准操作。

⚠️ 本章旧版把"LayerNorm + Linear"叫做"GEMM 的 Epilogue 融合"，这是错的。 Epilogue 是"收尾"，指 GEMM 算完之后的位置；LayerNorm 在 Linear 之前，那是 Prologue（前置） 位置。这两个位置的难度完全不对称：Epilogue 时结果已经在寄存器里，随便加东西；Prologue 时数据是分块读进来的，任何需要"看到完整一行"的操作都做不了。记住这个不对称，比记住术语重要。

反例 2：两个大 GEMM 串联——一般不能融

要算 out = (A @ B) @ D
    A: M × K，B: K × N，C = A@B 是 M × N，D: N × P

第二个 GEMM 要沿 N 做归约：out[i][p] = Σ_n C[i][n] × D[n][p]
也就是说，算 out 的任何一个元素，都需要 C 的一整行（N 个元素）。

而第一个 GEMM 的一个 Block 只算出 C 的一个 128 × 128 小块，
只覆盖 N 方向的 128/N。要凑齐一整行，得等别的 Block —— 跨 Block，
一个 kernel 里没法同步。                          ✗ 判据① 第三类

那 FlashAttention 为什么能融？它明明也是"GEMM → Softmax → GEMM"。 因为它同时满足两个特殊条件：

① 累加器足够小
   FA 的第二个 GEMM 输出的是 O，形状是 (BLOCK_M, head_dim) = (128, 128)
   FP32 累加器 = 128 × 128 × 4 = 65,536 字节 = 64 KiB   ✓ 放得进寄存器

   对比：如果 head_dim 是 1024，累加器 = 128 × 1024 × 4 = 512 KiB
         → 片上放不下，FlashAttention 这条路就走不通了。
         这就是为什么主流模型的 head_dim 一直卡在 64 / 128，很少更大。

② 归约可以"增量"做
   普通 Softmax 要先扫完一整行找最大值和总和，才能归一化 —— 属于判据①第二类。
   FlashAttention 用"在线 Softmax"（Online Softmax）：每处理一块 K/V，
   就更新一次运行中的最大值 m 和求和值 l，同时把已经累加好的 O 按比例修正。
   这样就把"整行归约"降级成了"可以边走边做的归约"。

FA 一个 Block 的片上占用（BLOCK_M = BLOCK_N = 128，head_dim = 128）：
    Q 块  128 × 128 × 2 (BF16) =  32 KiB
    K 块  128 × 128 × 2        =  32 KiB
    V 块  128 × 128 × 2        =  32 KiB
    S 块  128 × 128 × 4 (FP32) =  64 KiB
    O 累加器 128 × 128 × 4     =  64 KiB
                              ───────────
                               约 224 KiB   ← 顶到 H100 片上预算的天花板

★ FlashAttention 不是"发现了一个能融的地方"，而是"改造了算法，让它变得能融"（在线 Softmax 就是那个改造）。这是融合的最高形态：判据不满足时，改算法去满足它。详见 04 章。

反例 3：中间结果被多个消费者用——要先做水平融合

Transformer 里：
    n = RMSNorm(x)
    Q = n @ W_Q
    K = n @ W_K
    V = n @ W_V        ← n 被 3 个消费者用

如果硬把 RMSNorm 垂直融进三个 GEMM，那就要算 3 遍 RMSNorm，x 也要读 3 遍。
                                                  ✗ 判据③ k=3，不划算

正确做法：先水平融合（QKV 合成一个 GEMM，把 3 个消费者变成 1 个），
          再考虑垂直融合。

★ 两种融合模式是配合使用的，不是二选一。 水平融合常常是垂直融合的前置步骤——它把"一对多"的依赖图压成"一对一"，判据③就通过了。

反例 4：转置 / reshape 打断了融合

Attention 输出的布局是 (B, n_heads, S, head_dim)，
下一步 O 投影需要的是 (B, S, n_heads × head_dim)。
中间隔着一次转置。

转置的特点：消费者要的元素 (j, i) 由拥有 (i, j) 的那个 Block 产出。
            → 跨 Block                            ✗ 判据① 第三类

两种解法（都是 01 章 §1.4.4 那一招的变体）：
  ① 借共享内存中转：在一个 Block 内部完成局部转置（注意 Bank Conflict，01 章 §1.5）
  ② 让生产者直接按目标布局写出：FlashAttention 就是这么做的，
     它的 kernel 直接把 O 写成下一步要的形状，转置消失了

5.4.3 判据速查

写融合 kernel 之前，按顺序过一遍这五问：

① 消费者依赖生产者的哪些元素？  一对一 → 继续；行内归约 → 看 ②；跨块 → 放弃或改算法
② 中间结果片上装得下吗？        > 100 KB / Block 就危险
③ 中间结果被几个消费者用？      k > 1 时先考虑水平融合把 k 压到 1
④ 两边的瓶颈类型？              都是 Compute Bound → 别融
⑤ 形状和控制流稳定吗？          不稳定 → 融合 kernel 会爆炸成一堆特化版本

5.5 CUDA Graph：消除 kernel 启动开销

§5.2.6 留了一个尾巴：融合已经把 kernel 数压到最少，但剩下的每个 kernel 还是要付 3–10 µs 的启动费，而 Decode 场景下这笔费用是 kernel 执行时间的几十倍。CUDA Graph 就是来收这一刀的。

5.5.1 先把"启动开销"这件事说准确

先纠正一个几乎所有材料都含糊带过、本章旧版也算错了的地方。

旧版的算法：32 层 × 每层 20 个 kernel = 640 个 kernel
           640 × 7 µs = 4.5 ms，"全是启动开销"

这个算法把两个不同的东西混成了一个。

3–10 µs 是启动延迟（latency）：从 CPU 调用 cudaLaunchKernel 到 GPU 上第一个线程开始跑，中间隔了这么久。但连续启动时，CPU 发第 2 个 kernel 和 GPU 执行第 1 个 kernel 是并行发生的——启动是流水化的，不是串行相加的。

真正决定成败的是另一个量：CPU 端每提交一个 kernel 要占用多少 CPU 时间（吞吐成本，⚠️ 实测量级 1.5–3 µs/kernel，取决于参数个数、是否走 PyTorch 的 Python 层、驱动版本）。于是：

每一步的实际耗时 ≈ max( CPU 下发总时间 , GPU 执行总时间 )
                    ▲                      ▲
            kernel 数 × 单个下发成本      真正干活的时间

  CPU 侧 < GPU 侧  →  正常，GPU 是瓶颈，启动开销被完全掩盖，不用管
  CPU 侧 > GPU 侧  →  Host Bound（下发受限），GPU 在饿着等命令   ← CUDA Graph 的战场

时间线示意（每格 1 µs，K = kernel）

正常情况（GPU 慢，CPU 快）：
  CPU: [发K1][发K2][发K3]........................（发完就闲着）
  GPU: ....[====== K1 ======][===== K2 =====][===== K3 =====]
       └ GPU 一直有活干，启动开销完全被掩盖

Host Bound（GPU 快，CPU 慢）：
  CPU: [--发K1--][--发K2--][--发K3--][--发K4--]
  GPU: ....[K1]......[K2]......[K3]......[K4]
              ▲空闲     ▲空闲     ▲空闲
       └ GPU 每次都要等 CPU，总时间由 CPU 决定

一个具体场景：LLaMA-3-8B，BF16，8 卡张量并行（TP = 8，Tensor Parallel），Decode 阶段。

GPU 侧每步执行时间 ≈ 每卡权重量 ÷ 带宽
                   = (16 GB ÷ 8) ÷ 3.35 TB/s = 2 GB ÷ 3.35 TB/s ≈ 0.6 ms
                   （Decode 是 Memory Bound，时间几乎等于"把权重读一遍"）

CPU 侧每步下发成本 ≈ kernel 数 × 单个下发成本
                   ⚠️ 约 500 个 kernel × 2 µs ≈ 1.0 ms

每步耗时 = max(1.0, 0.6) = 1.0 ms     ← CPU 是瓶颈，GPU 有 40% 时间在空转

注意这里的关键：切了 TP 之后，GPU 侧的活变少了（权重被 8 张卡分摊），但 kernel 数量一点没少——每张卡还是要发那 500 个 kernel。并行度越高、模型越小、batch 越小，就越容易滑进 Host Bound。这也是为什么 vLLM、SGLang、TensorRT-LLM 这些推理框架把 CUDA Graph 当成默认必开项。

5.5.2 录制—重放：CUDA Graph 怎么工作

CUDA Graph 的思路很直白：既然每一步要发的 kernel 序列都一模一样，那就录一次，以后重放。

① 录制阶段（一次性，在 warm-up 时做，通常跑 1–3 次预热后录）

   CPU:  cudaStreamBeginCapture(stream)     ← 打开"录音"
           │
           │   照常调用 kernel_1、kernel_2、……、kernel_500
           │   但这些调用不会真的送到 GPU 执行，
           │   而是被记录成图里的节点
           ▼
         kernel_1   ──→  节点 1
         kernel_2   ──→  节点 2（依赖节点 1）
           ……
         kernel_500 ──→  节点 500
           │
           ▼
         cudaStreamEndCapture     ──→  得到一张 Graph（有向无环图，
           │                            节点是 kernel，边是依赖关系）
           ▼
         cudaGraphInstantiate     ──→  得到 GraphExec（可执行实例）
                                        此时参数地址、grid/block 配置
                                        全部固化进去，不能再改

② 重放阶段（之后每一步都走这条路）

   CPU:  把这一步的新数据拷进"录制时用的那几块固定 buffer"
           │
           ▼
         cudaGraphLaunch(graphExec)     ← 全程只有这一次 API 调用
           │
           ▼
   GPU:  硬件按图的依赖顺序依次调度 500 个节点
         中间不再回头问 CPU 要命令

在 PyTorch 里长这样：

import torch

# ① 准备固定形状、固定地址的输入输出 buffer
static_input = torch.randn(batch, seq_len, hidden, device='cuda')

# ② 预热：必须先正常跑几次，让 cuBLAS 选好算法、内存池稳定下来
s = torch.cuda.Stream()
s.wait_stream(torch.cuda.current_stream())
with torch.cuda.stream(s):
    for _ in range(3):
        _ = model(static_input)
torch.cuda.current_stream().wait_stream(s)

# ③ 录制
g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    static_output = model(static_input)   # 所有 kernel 调用被录进 g

# ④ 之后每一步：把新数据写进同一块 buffer，然后重放
static_input.copy_(new_data)   # 必须是 copy_，不能是重新赋值！地址不能变
g.replay()
result = static_output.clone() # static_output 会被下次 replay 覆盖，要用就先拷走

⚠️ 第 ④ 步那行 copy_ 是最高频的坑。写成 static_input = new_data 会让变量指向一块新显存，而图里固化的还是老地址——不报错，结果是用旧数据算出来的。这是典型的静默错误。同理，static_output 必须在下一次 replay() 之前拷走。

5.5.3 省下多少：把两笔账并排放

沿用 §5.5.1 那个场景（500 个 kernel，GPU 侧 0.6 ms）：

每步开销 Eager（逐个下发） CUDA Graph 重放
CPU 侧 API 调用次数 500 次 1 次
CPU 侧总耗时 ⚠️ 500 × 2 µs ≈ 1.0 ms ⚠️ 约 5–10 µs
GPU 侧节点间调度 每个节点都有间隙 硬件直连，⚠️ 亚微秒级
HBM 流量 1× 完全不变
kernel 数量 500 完全不变
每步实际耗时 max(1.0, 0.6) = 1.0 ms max(0.01, 0.6) = 0.6 ms 
加速比 = 1.0 ÷ 0.6 ≈ 1.67 倍
延迟下降 = (1.0 − 0.6) ÷ 1.0 = 40%

注意加速的上限在哪：CUDA Graph 最多只能把耗时从 CPU 侧 拉回到 GPU 侧。上面这个例子的天花板就是 0.6 ms，再开十张图也快不了。如果本来就不是 Host Bound，CUDA Graph 的收益是零。

★ 判断该不该开 CUDA Graph，一条不等式就够：

kernel 数 × 单个下发成本（⚠️ 约 2 µs） > GPU 侧执行时间 → 开，收益 = 两者之差 kernel 数 × 单个下发成本 ≤ GPU 侧执行时间 → 不开也一样

怎么量：用 Nsight Systems 看时间线，如果 GPU 那条泳道上 kernel 之间有肉眼可见的密集空隙、而 CPU 那条泳道是满的，就是 Host Bound。02 章 有具体操作。

输入形状必须固定 图里固化了 grid 配置和参数地址 预先录制多套图（如 batch = 1/2/4/8/16/32），运行时选最接近的那张并 padding
显存地址必须固定 同上 用静态 buffer + copy_；PyTorch 的 CUDA 内存池在图捕获期间会切到专用池
不支持依赖数据的控制流 图是静态的，录的时候走哪条分支就永远走哪条 把分支拆到图外面，或分别录多张图
KV Cache 长度在增长 Cache 的有效长度每步变化 按最大长度分配固定 buffer，用 mask 或 seq_len 张量控制有效范围（vLLM 的做法）
CPU 端同步会破坏捕获 捕获期间不能有 .item()、.cpu()、print() 等同步操作 把所有 host 侧逻辑挪出捕获区
录制本身要花时间和显存 每张图要预留自己的中间 buffer 图的套数别开太多；⚠️ 一套图的额外显存通常在几百 MB 量级

典型收益：⚠️ 推理延迟下降 10–25%（一般情况），Host Bound 严重时（小模型、高 TP、小 batch）可达 40% 以上。batch 越大、序列越长，GPU 侧的活越多，CUDA Graph 的收益越小。

5.6 torch.compile：让编译器替你做融合

手写融合 kernel 成本高。torch.compile 能自动吃掉其中最简单也最琐碎的那一大类——逐元素算子链。

import torch

model = MyModel().cuda()
model = torch.compile(model)   # ← 一行

output = model(x)              # 第一次调用触发编译

5.6.1 内部流程

Python 模型代码
      │  TorchDynamo：改写 Python 字节码，把张量操作抽出来
      ▼
FX Graph（计算图）
      │  AOTAutograd：提前把反向传播也展开成图
      ▼
前向图 + 反向图
      │  TorchInductor：后端代码生成
      ├──→  Triton kernel（GPU）   ← 融合发生在这里
      └──→  C++ / OpenMP（CPU）

TorchInductor 的三类融合，正好对应 §5.3 的三种模式：

Inductor 的叫法 对应本章 做什么
Pointwise 融合 垂直融合 连续的逐元素算子（加、乘、激活、类型转换）合成一个 kernel
Reduction 融合 垂直融合（行内归约） 归约算子和它前后的逐元素算子合并，如 LayerNorm 的内部三步
模板 + Epilogue Epilogue 融合 用 GEMM 模板，把后面的逐元素算子挂进 Epilogue

5.6.2 怎么确认它真的融了

这是最实用的一招：看生成的 kernel 名字。

TORCH_LOGS="output_code" python your_script.py

Inductor 生成的 Triton kernel 会被命名成这样：

triton_poi_fused_add_gelu_native_layer_norm_0
        │   │     └─ 融进去的算子列表：add、gelu、layer_norm
        │   └─ fused：确实发生了融合
        └─ poi = pointwise（另有 red = reduction，per = persistent reduction）

看到 add_gelu_native_layer_norm 三个算子出现在同一个 kernel 名字里，就说明 §5.2 那条链被完整融成了一个 kernel。如果它们分散在三个 kernel 里，融合就没发生，通常是被"图断裂"（Graph Break）打断了。

查图断裂：

TORCH_LOGS="graph_breaks" python your_script.py

常见的断裂原因：print()、.item()、tensor.cpu()、依赖张量值的 if、调用了 Dynamo 看不懂的第三方库。每断一次，两侧的算子就不可能融在一起。

5.6.3 和 CUDA Graph 的关系

model = torch.compile(model, mode="reduce-overhead")

mode="reduce-overhead" 会在编译之后自动套一层 CUDA Graph。也就是说这一个参数同时用上了本章的两把武器：Inductor 负责减少 kernel 数和 HBM 流量，CUDA Graph 负责压掉剩下那些 kernel 的下发成本。Decode 场景优先试这个模式。

场景 ⚠️ 典型加速（社区量级，随模型/版本浮动大）
训练前向 + 反向，大 batch 1.1–1.3×
推理，batch = 1 1.2–1.4×
推理，batch = 32 1.1–1.2×

⚠️ 编译耗时：首次调用会触发编译，⚠️ 典型 30–120 秒（大模型可能更久），而且每遇到一个新形状就要重编一次。生产环境必须在服务起来之前用代表性形状 warm-up 完；或者用 torch.export / AOTInductor 做提前编译。（旧版这里前后写了"10–60 秒"和"30–120 秒"两个互相矛盾的数字，已统一。）

5.7 手写融合 kernel：把 §5.2 那条链真的写出来

torch.compile 覆盖不到的场合（需要定制归约逻辑、需要特殊的片上布局、需要极致性能），就得自己写。这里用 Triton 把 §5.2 那条 LayerNorm → GELU → 残差加 完整实现一遍——这段代码的每一行都对应前面账本里的一行。

import torch
import triton
import triton.language as tl


@triton.jit
def fused_ln_gelu_res_kernel(
    x_ptr, gamma_ptr, beta_ptr, y_ptr,
    stride_row,               # 相邻两行之间隔多少个元素（这里就是 H）
    H,                        # 隐藏维度
    eps,
    BLOCK_H: tl.constexpr,    # 必须 >= H：一整行要一次装进片上
):
    row = tl.program_id(0)              # 一个 Block 负责一整行（一个 token）
    cols = tl.arange(0, BLOCK_H)
    mask = cols < H                     # H 不是 2 的幂时，尾部用 mask 屏蔽

    # ① 全流程唯一一次从 HBM 读 x —— 对应账本里的那 1 个 T
    x = tl.load(x_ptr + row * stride_row + cols, mask=mask, other=0.0).to(tl.float32)

    # ② LayerNorm：整行归约，全部在寄存器里完成
    mean = tl.sum(x, axis=0) / H
    xc = tl.where(mask, x - mean, 0.0)              # 被 mask 掉的位置必须清零
    var = tl.sum(xc * xc, axis=0) / H
    n = xc / tl.sqrt(var + eps)
    gamma = tl.load(gamma_ptr + cols, mask=mask, other=0.0).to(tl.float32)
    beta = tl.load(beta_ptr + cols, mask=mask, other=0.0).to(tl.float32)
    n = n * gamma + beta
    # ↑ n 到此为止只存在于寄存器里。未融合版本会在这里写 1 个 T 到 HBM。

    # ③ GELU（tanh 近似版，和 PyTorch 的 approximate='tanh' 一致）
    inner = 0.7978845608 * (n + 0.044715 * n * n * n)   # sqrt(2/pi) ≈ 0.7978845608
    g = 0.5 * n * (1.0 + tl.math.tanh(inner))
    # ↑ g 同样只在寄存器里。未融合版本会在这里再写 1 个 T。

    # ④ 残差加：x 从第 ① 行起就一直在寄存器里，不需要第二次读 HBM
    y = x + g

    # ⑤ 全流程唯一一次写 HBM —— 对应账本里的那 1 个 T
    tl.store(y_ptr + row * stride_row + cols, y.to(tl.bfloat16), mask=mask)


def fused_ln_gelu_res(x, gamma, beta, eps=1e-5):
    assert x.is_contiguous()
    M, H = x.shape
    y = torch.empty_like(x)
    BLOCK_H = triton.next_power_of_2(H)        # 4096 -> 4096
    fused_ln_gelu_res_kernel[(M,)](            # Grid = M，一行一个 Block
        x, gamma, beta, y,
        x.stride(0), H, eps,
        BLOCK_H=BLOCK_H, num_warps=8,
    )
    return y

对着账本读这段代码：整个 kernel 里只有一次 tl.load(x_ptr...) 和一次 tl.store(y_ptr...)。n 和 g 从头到尾没有任何一条指令把它们写向 HBM。这就是"7 T 变 2 T"在源码层面的样子——融合不是什么高深技巧，就是"别把中间变量写出去"。

片上占用核对（判据②）：

H = 4096，读进来转成 FP32 = 4096 × 4 = 16 KB
同时活着的 FP32 中间量：x、xc、n、g、gamma、beta 大约 5–6 份
→ ⚠️ 约 80–96 KB / Block（估算，编译器会复用寄存器，实际更少）

寄存器文件 256 KB/SM，所以一个 SM 大概只能驻留 2–3 个这样的 Block。
Occupancy 不高，但这类 kernel 本来就是纯带宽受限，
只要能把 HBM 打满就够了（01 章 §1.6.3：Occupancy 不是越高越好）。

H 再大会怎样：H = 32768 时，一行 FP32 就是 128 KB，加上中间量直接爆掉片上预算——判据②不过。这时只能退回两趟方案：第一趟扫一遍算出 mean 和 var（或用 Welford 在线算法），第二趟再扫一遍做归一化。代价是 x 要读两遍，融合收益从 3.5× 降到约 2.3×（7 T → 3 T）。

★ 生产环境里不要什么都自己写。Flash-Linear-Attention、unsloth、xformers、Apex 已经提供了大量调好的融合 kernel（FusedRMSNorm、AddRMSNorm、SwiGLU、各种 Fused Optimizer）。自己写的场合是：① 你的算子链是独有的；② 现成库的形状约束不满足；③ 你要在 Epilogue 里塞进量化、通信之类的非标准操作。Triton 的完整写法见 07 章。

5.8 决策表：先做什么，后做什么

5.8.1 哪些融合值得做

融合目标 判断 理由（对照 §5.4 的判据）
残差加 + RMSNorm（AddRMSNorm） ✅ 必做 判据① 一对一 + 行内归约，一行 8 KB 装得下；两边都 Memory Bound（判据④）；现成库有
激活函数融进前面的 GEMM（Epilogue） ✅ 必做 判据① 一对一，结果就在寄存器里；省 2/3 中间流量（§5.3.3 算过）
逐元素链（cast / scale / add / mul / 激活） ✅ 必做 全是判据① 一对一，torch.compile 自动搞定，零成本
QKV / gate-up 投影合并 ✅ 值得 水平融合；Decode 下 SM 利用率 24% → 73%（§5.3.2）。注意 GQA 下不是 3H
QK^T + Softmax + ×V（FlashAttention） ✅ 必须 不是提速，是可行性前提：中间矩阵 4–64 GB（§5.2.7）
LayerNorm 融进后面 Linear 的 Prologue ❌ 做不到 判据② 不过：一个 Block 要 1 MiB，上限 228 KB（§5.4 反例 1）
两个大 GEMM 串联 ❌ 一般不行 判据① 第三类：第二个 GEMM 要沿第一个的 N 维归约，跨 Block（§5.4 反例 2）
两个都 Compute Bound 的算子 ⚠️ 通常亏 判据④：减字节不改变时间，还会挤压 Occupancy
带数据依赖控制流的算子（MoE 路由、早退） ⚠️ 难 判据⑤：形状不稳定；CUDA Graph 也用不了，只能录多套图

5.8.2 实施顺序（投入产出比从高到低）

① torch.compile（必要时加 mode="reduce-overhead"）
     零代码。先跑一遍，用 TORCH_LOGS="output_code" 看融了哪些。
     这一步通常能拿到全部收益的 50–70%。

② CUDA Graph
     只在 Host Bound 时有用。先用 Nsight Systems 确认 GPU 泳道有空隙，
     再按 §5.5.3 那条不等式估一下能省多少。推理场景基本是标配。

③ 换用现成的融合库
     FlashAttention、Apex FusedLayerNorm、xformers、unsloth。
     成熟、正确性有保障，比自己写快得多。

④ Triton 自定义融合 kernel
     前三步覆盖不到的定制逻辑。开发 + 调试 ⚠️ 通常按天计。

⑤ CUDA / CUTLASS 手写
     极致性能或需要定制 Epilogue（量化、通信重叠）。⚠️ 按周计。

⚠️ 每一步之后都要实测，不要连着做完再测。 融合有可能变慢（判据②③④任意一条不过就可能），而且慢下来的原因往往藏在 Occupancy 和寄存器溢出里，源码上看不出来——必须用 Nsight Compute 看（01 章 §1.6.3、02 章）。

5.9 本章小结

一句话：融合减少的是字节和kernel 数量，CUDA Graph 减少的是每个 kernel 的下发成本。两个瓶颈，两把武器，都要配。

核心账本（§5.2，全章骨架）

HBM 流量 时间 启动次数
x → LayerNorm → GELU → 残差加 融合前 7 T = 448 MiB 140.2 µs 3
融合后 2 T = 128 MiB 40.1 µs 1
省 71% 3.5× — 
★ 加速比 = 融合前字节数 ÷ 融合后字节数。
  只取决于链的结构（几个算子、每个读写几份），和张量大小、数据类型都无关。

三种模式

合并谁 省什么
垂直融合 前后有依赖的算子 中间结果的 HBM 往返
水平融合 彼此独立的同形算子 启动次数 + 输入重复读 + SM 空转
Epilogue 融合 GEMM + 它后面的逐元素算子 中间结果的 HBM 往返（FFN 里省 2/3）

五条判据（§5.4）

① 依赖粒度：一对一 → 随便融；行内归约 → 看 ②；跨块/转置 → 融不了
② 片上容量：中间结果 > ⚠️100 KB/Block 就危险（H100 共享内存 228 KB）
③ 消费者个数：k > 1 要重算 k 遍，先用水平融合把 k 压到 1
④ 瓶颈类型：都是 Compute Bound → 别融，省字节换不来时间
⑤ 形状稳定性：形状/控制流一变，融合 kernel 就失效

CUDA Graph 的判据（§5.5）

每步耗时 ≈ max( kernel 数 × 单个下发成本(⚠️约 2 µs) , GPU 执行时间 )

CPU 侧 > GPU 侧  →  Host Bound，开图，收益 = 两者之差
CPU 侧 ≤ GPU 侧  →  开了也白开，收益为零

上限：CUDA Graph 最多把耗时从 CPU 侧拉回到 GPU 侧，一点也不会更快。

收益的真实量级（别被夸大的数字骗了）

场景 融合的收益
大 batch 训练前向 逐元素算子约占 6%，全融掉整体提速 ⚠️ 3–4%
FlashAttention 不是提速，是可行性——不融就放不下（4–64 GB 中间矩阵）
Decode / 小 batch 推理 ⚠️ 20–40%，且其中大半来自 CUDA Graph 而非融合本身

自测三题

  1. 形状换成 M = 4096 个 token、H = 8192、FP16，算子链换成 x → RMSNorm → SiLU → 残差加。融合前后各搬多少字节？加速比是多少？和 §5.2 的 3.5× 一样吗，为什么？
  2. 某 Decode 场景，每卡每步要发 420 个 kernel，GPU 侧总执行时间 0.35 ms，CPU 端单个 kernel 下发成本按 2 µs 算。这一步是不是 Host Bound？开 CUDA Graph 后每步耗时变成多少，延迟下降几个百分点？
  3. 想把 Softmax 融进它前面的 GEMM。行长 N = 65536（长上下文），中间值用 FP32。一个 Block 要缓存一整行需要多少片上空间？按判据②能不能融？如果不能，有什么办法绕过去？

参考答案

  1. T = 4096 × 8192 × 2 = 67,108,864 字节 = 64 MiB（和 §5.2 的 T 恰好相同）。RMSNorm 读写 2 T，SiLU 读写 2 T，残差加读 g 和 x、写 y 共 3 T，融合前 7 T = 448 MiB（140.2 µs）；融合后只读 x、只写 y，2 T = 128 MiB（40.1 µs）。加速比 7 ÷ 2 = 3.5×，和 §5.2 完全一样——因为加速比只由链的结构决定（三个算子、读写份数相同），与形状和数据类型无关。形状只决定省下来的绝对时间。参见 §5.2.4。
  2. CPU 侧 = 420 × 2 µs = 0.84 ms > GPU 侧 0.35 ms → 是 Host Bound，眼下每步耗时 0.84 ms，GPU 有 (0.84−0.35)/0.84 ≈ 58% 的时间在空转。开图后 CPU 侧降到约 0.01 ms，每步耗时 = max(0.01, 0.35) = 0.35 ms，加速 0.84 ÷ 0.35 = 2.4 倍，延迟下降 58%。参见 §5.5.1、§5.5.3。
  3. 一行 = 65536 × 4 字节 = 262,144 字节 = 256 KiB，已经超过 H100 每 SM 228 KB 的共享内存上限（更别说还要留给 Q/K/V 分块和双缓冲）→ 判据② 不过，按朴素写法融不了。绕过去的办法是改算法：用在线 Softmax（Online Softmax）把"必须先扫完整行"的归约改成"边走边更新最大值 m 和求和值 l"的增量归约，这样片上只需要留一个 tile 加两个标量，判据①也从"行内归约"降级成"可增量归约"。这正是 FlashAttention 的做法。参见 §5.4 反例 2 与 04 章。

下一章：融合是"让同样的字节被多用几次"。还有一条更直接的路——让字节本身变少：同样一个数，用 8 位甚至 4 位来存。见 06 · 量化算子。

昇腾对照：910B 起 Cube 和 Vector 是两个独立的核，中间结果必须绕 Global Memory —— 本章「消灭中间结果落盘」这个收益来源在昇腾上部分失效，融合要改用 CV 流水并行，见 12 章 §12.2.3 与 04 章 §4.9.1。CUDA Graph 在昇腾上的对应物是 ACLGraph，见 14 章 §14.5；昇腾单算子下发路径比 GPU 更长，§5.5 那条 Host Bound 判据在昇腾上更容易成立。
