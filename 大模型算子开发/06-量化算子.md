# 06 · 量化算子：让每个数占的字节变少

> **前置**：[02 章（屋顶线）](02-屋顶线与性能剖析.md)、[03 章（GEMM）](03-GEMM深度剖析.md)、[05 章（算子融合）](05-算子融合.md)  
> **目标**：搞清楚量化到底在做什么算术、误差从哪来、每种方案（INT8 / FP8 / GPTQ / AWQ）各自用什么信息做取舍，以及量化 kernel 在工程上要处理哪些事。  
> **读法**：本章有一个贯穿全章的数值例子——**8 个浮点数**，从 §6.2 开始一路被反复量化：对称一遍、非对称一遍、三种粒度各一遍、掺进离群值再来一遍。**所有数字都能用计算器验算，建议拿纸笔跟着算。**

---

**本章关键词**

**量化**（Quantization）—— 用位宽更低的数据类型（INT8、FP8、INT4）表示原本是 FP16/BF16 的张量，减少显存占用和 HBM 带宽消耗。  
**PTQ**（Post-Training Quantization，训练后量化）—— 模型训练完之后再量化，不改训练流程，本章讲的绝大部分方案都属于这一类。  
**QAT**（Quantization-Aware Training，量化感知训练）—— 在训练过程中就模拟量化误差，让权重自己适应，精度更好但要改训练，见 [11 章 §11.2.2](11-训推一致性算子层.md)。  
**scale（缩放因子）/ zero-point（零点）** —— 量化的两个参数：`scale` 决定一个整数刻度代表多大的实数，`zero-point` 决定实数 0 落在哪个整数上。  
**对称量化 / 非对称量化** —— 是否带 zero-point。对称：`q = round(x / scale)`；非对称：`q = round(x / scale) + zero_point`。  
**RTN**（Round-To-Nearest，就近取整）—— 最朴素的量化方法：直接四舍五入，不做任何补偿。本章所有高级方案都是在跟它比。  
**Per-tensor / Per-channel / Per-token / Per-group 量化** —— 量化粒度，指"多少个数共用一个 scale"。粒度越细越准，但 scale 本身也要占空间。  
**离群值**（Outlier，也叫"刺"）—— 张量里少数几个远大于其余元素的值。它撑大 scale，把其余元素的精度全部拖垮，是激活值量化的头号敌人。  
**W8A8 / W8A16 / W4A16** —— 权重（Weight）和激活值（Activation）各用几位的简写。W8A16 = 权重 INT8、激活 FP16。  
**SmoothQuant** —— 用一组逐通道的缩放因子，把激活的离群值"难度"等价地搬到权重上，让 W8A8 变得可行。  
**FP8（E4M3 / E5M2）** —— 8 位浮点格式，E4M3 = 1 符号位 + 4 指数位 + 3 尾数位，E5M2 = 1 + 5 + 2。H100 的 Tensor Core 原生支持。  
**GPTQ**（Generative Pre-trained Transformer Quantization）—— Frantar 等人提出的训练后权重量化方案，用**二阶信息（Hessian 矩阵）**做逐列误差补偿，支持 INT4/INT3。  
**AWQ**（Activation-aware Weight Quantization，激活感知权重量化）—— 用**激活值的逐通道幅度**决定哪些权重通道重要，通过等价缩放保护它们，不做反向传播。  
**Hessian 矩阵**（海森矩阵）—— 损失函数对参数的二阶导数矩阵。GPTQ 用它来判断"改动哪个权重对输出影响最小"。  
**PPL**（Perplexity，困惑度）—— 语言模型的标准评测指标，越低越好。量化论文几乎都用它衡量精度损失。  
**SQNR**（Signal-to-Quantization-Noise Ratio，信号量化噪声比）—— 另一个衡量量化误差的指标，单位 dB，越高越好。  
**MSE / RMSE**（Mean Squared Error / Root Mean Squared Error，均方误差 / 均方根误差）—— 本章用 RMSE 横向比较各种量化方案的误差。  
**校准**（Calibration）—— 用一小批真实数据跑一遍模型，统计出每层激活的取值范围，从而确定 scale。  
**屋脊点**（Ridge Point）—— 峰值算力 ÷ 峰值带宽，见 [02 章](02-屋顶线与性能剖析.md)。**量化会让屋脊点也跟着变，这是本章最容易被忽略的一点。**

## 6.1 先算一笔账：量化到底买到了什么

### 6.1.1 两样东西：显存和带宽

量化省的从来不是"计算量"——FLOP（浮点运算次数）一次都没少。它省的是**字节数**，而字节数买到两样东西。

**第一样：显存装得下。** 以 LLaMA-3-8B（80.3 亿参数）为例：

| 权重格式 | 每个权重占的位数 | 权重总大小 | 能否装进一块 24 GB 消费卡 |
|---|---|---|---|
| BF16 | 16 | 8.03e9 × 2 = **16.06 GB** | 勉强（剩不下 KV Cache） |
| INT8 | 8 | **8.03 GB** | 可以 |
| INT4（group = 128） | **4.156**（见 §6.2.6） | **4.17 GB** | 绰绰有余 |

**第二样：Decode 跑得快。** [02 章 §2.4.4](02-屋顶线与性能剖析.md) 已经证明过：自回归生成（Decode）阶段是彻底的 Memory Bound（内存受限），每生成一个 token 都要把**整个模型的权重从 HBM 读一遍**，时间几乎完全等于"读权重的时间"。

```
Decode 每步的理论下界 = 权重总字节数 ÷ HBM 带宽

H100 SXM5，HBM3 带宽 3.35 TB/s：
  BF16   16.06 GB ÷ 3350 GB/s = 4.79 ms/token  →  209 token/s
  INT8    8.03 GB ÷ 3350 GB/s = 2.40 ms/token  →  417 token/s
  INT4    4.17 GB ÷ 3350 GB/s = 1.25 ms/token  →  803 token/s
```

> ⚠️ 上面三个数字是**理论上界**，不是实测：它假定 batch = 1、忽略 KV Cache 和激活值的流量、忽略反量化开销、假定 HBM 带宽 100% 打满。真机上能拿到其中的 60–80% 就算不错了。但**三者之间的比值（1 : 2 : 3.85）是可靠的**，因为分母是同一个带宽。

> ★ **注意 INT4 的加速比是 3.85 倍而不是 4 倍。** 差的那 0.15 就是 scale 参数占的空间——每 128 个权重要额外存一个 FP16 的 scale 和一个 INT4 的 zero-point。§6.2.6 会把这笔账算清楚。

### 6.1.2 在屋顶线上看：算术强度和屋脊点同时翻倍

这是本章和 [02 章](02-屋顶线与性能剖析.md) 最要紧的联动，也是最容易搞错的地方。

取 Decode 阶段的一个 GEMV（矩阵-向量乘，即 batch = 1 的 GEMM），权重矩阵 4096 × 4096：

```
                             BF16 权重          INT8 权重（W8A8）
  运算量                     33.55 MFLOP        33.55 MOP       （完全不变）
  读权重字节                 33.55 MB           16.78 MB        （减半）
  ─────────────────────────────────────────────────────────────
  算术强度 I                 1.0 FLOP/Byte      2.0 OP/Byte     （翻倍 ↑）
  该计算单元的屋脊点         295（BF16）        591（INT8）     （也翻倍 ↑）
  I ÷ 屋脊点                 0.0034             0.0034          （一点没变）
  ─────────────────────────────────────────────────────────────
  搬完权重要多久             10.0 µs            5.0 µs          （减半 ✓）
```

（屋脊点的来源：BF16 稠密 989 TFLOPS ÷ 3.35 TB/s ≈ 295；INT8 稠密 1979 TOPS ÷ 3.35 TB/s ≈ 591。见 [附-速查表 §A](附-速查表.md)。）

> ★ **看清楚这里发生了什么**：量化把算术强度翻了一倍，但也把屋脊点翻了一倍，所以这个算子在屋顶线图上的**相对位置一点没动**——它还是一样"贫瘠"，算力利用率还是 0.34%。**但绝对时间减半了**，因为要搬的字节少了一半。**在 Memory Bound 区里，量化的全部收益来自"字节变少"，和"INT8 算得更快"没有一分钱关系。**

> ⚠️ **一个常见的错误推论**：既然 INT8 Tensor Core 是 BF16 的 2 倍算力，那 W8A8 应该快 2 倍。这个推论只在 **Compute Bound**（算力受限）的场景下成立——大 batch 训练、长序列 Prefill。Decode 场景下算力根本没在用，INT8 Tensor Core 那 2 倍算力是白送的，一点也兑现不了。**同一个量化动作，收益来源随场景完全不同**，这和 [05 章 §5.2.6](05-算子融合.md) 讲融合时是同一个道理。

### 6.1.3 量化的收益会随 batch 消失：算出临界点

既然收益来自"减少字节"，那当算子本身变成 Compute Bound 的时候，收益就该归零。这个临界点可以算出来。

设权重矩阵 K × N = 4096 × 4096，batch（token 数）为 M，H100：

```
运算量 = 2 × M × 4096 × 4096 = 3.355e7 × M  FLOP
        → 在 BF16 Tensor Core（989 TFLOPS）上耗时 = 0.0339 × M  µs

字节数 = 权重 + 激活进出
        BF16 权重：33.55 MB           → 10.02 µs
        INT4 权重：8.39 + 0.33 = 8.72 MB → 2.60 µs       （0.33 是 scale/zero-point）
        激活进出：2 × M × 4096 × 2 = 16384 × M Byte → 0.00489 × M µs
```

令"算的时间"= "搬的时间"，解出临界 M：

| 权重格式 | 方程 | 临界 M | 含义 |
|---|---|---|---|
| BF16 | 0.0339 M = 10.02 + 0.00489 M | **M ≈ 345** | 超过 345 个 token 后，BF16 GEMM 本身就已是 Compute Bound |
| INT4（激活仍 FP16） | 0.0339 M = 2.60 + 0.00489 M | **M ≈ 90** | 超过 90 个 token 后，INT4 的带宽优势开始兑现不出时间 |

```
M = 1    （Decode，batch=1）        INT4 相对 BF16 提速 ≈ 10.02 / 2.60 = 3.85 倍  ★收益最大
M = 90                              INT4 刚好触顶，再大就被算力卡住
M = 345                             BF16 自己也触顶，两者时间相同，量化只剩显存收益
M = 2048（Prefill / 训练）          两者都是 Compute Bound，W4A16 的加速比 ≈ 1.0
```

> ⚠️ 上面是**单个 GEMM 的理论模型**，忽略了 Attention、通信、kernel 启动，也假定 INT4 权重反量化后仍走 FP16 Tensor Core。真实系统的临界点会更模糊。但**趋势是可靠的**：**batch 越大，权重量化的收益越小。** 这解释了一个现象——端侧和单用户场景（batch = 1）大量用 W4A16，而高吞吐服务集群（batch 上百）更愿意用 W8A8 或 FP8，因为那边要的是算力，不只是带宽。

### 6.1.4 三条路线：W8A16、W8A8、W4A16 各省在哪

| | 权重 | 激活 | 省带宽 | 省算力 | 需要校准数据 | 精度风险 |
|---|---|---|---|---|---|---|
| **W8A16** | INT8 | FP16/BF16 | 权重减半 | ❌ 无（仍走 FP16 Tensor Core） | ❌ 不需要 | 极低 |
| **W8A8** | INT8 | INT8 | 权重和激活都减半 | ✅ INT8 Tensor Core 2× | ✅ 需要（激活范围要统计） | **中，卡在激活离群值** |
| **W4A16** | INT4 | FP16/BF16 | 权重减 3.85× | ❌ 无 | ✅ 需要（GPTQ/AWQ 都要） | 中 |
| **FP8（W8A8 的浮点版）** | FP8 | FP8 | 都减半 | ✅ FP8 Tensor Core 2× | 通常需要（或在线算 scale） | 低（见 §6.5） |

**W8A16 是"最保守"的一档**：只动权重，不动激活，因此不需要校准数据、不会踩激活离群值的坑、任何现成的 FP16 GEMM kernel 稍加改造就能用。代价是 Tensor Core 吞吐一点没涨，纯粹是带宽/显存的收益。

> ★ **为什么 W8A16 这么"弱"的方案仍然值得用**：因为 Decode 的字节数里，权重占了绝大部分。LLaMA-3-8B，batch = 1、序列长 2048 时，每步要读 16 GB 权重，而 KV Cache 只有几十 MB 量级。**只量化权重就能拿走 Decode 大部分的收益**，而激活量化那部分风险高、收益小。这也是 [02 章 §2.4.4](02-屋顶线与性能剖析.md) 那句"推理量化通常只量化权重就够"的完整理由。

> ⚠️ 本章旧版写"W8A16 反量化的开销约占 5–10%"，**这个数字没有来源，已删除**。真实情况取决于 batch：batch = 1 时计算单元几乎全空着，反量化基本白送；batch 大到一定程度后，反量化本身会变成瓶颈（这正是 Marlin、Machete 这类 W4A16 专用 kernel 要解决的问题，见 §6.8）。

## 6.2 量化的数学基础：8 个数走完全程

这一节是全章的骨架。我们只用 8 个数，但要把它们量化 5 遍。

**这就是那 8 个数**（可以理解成一层权重里连续的 8 个元素）：

```
x = [ -0.80,  0.25,  1.50, -2.10,  0.05,  3.81, -0.40,  1.00 ]
      索引0   索引1  索引2  索引3   索引4  索引5  索引6   索引7
```

（挑 3.81 这个数是为了让算术干净：`3.81 ÷ 127 = 0.03` 整。真实张量当然不会这么配合，但流程完全一样。）

### 6.2.1 对称量化：完整走一遍

**三步公式**（b = 位宽，这里 b = 8）：

```
① 定 scale：      scale = max(|x|) / (2^(b-1) - 1)       分母对 INT8 是 127
② 量化：          q = clamp( round(x / scale), -127, 127 )
③ 反量化：        x̂ = q × scale
```

代进去：`max(|x|) = 3.81`，所以 **scale = 3.81 ÷ 127 = 0.03**。

| 索引 | 原值 x | x / scale | 取整后 q（INT8） | 反量化 x̂ = q × 0.03 | 绝对误差 x̂ − x | 相对误差 |
|---|---|---|---|---|---|---|
| 0 | −0.80 | −26.667 | **−27** | −0.81 | −0.01 | 1.3% |
| 1 | 0.25 | 8.333 | **8** | 0.24 | −0.01 | 4.0% |
| 2 | 1.50 | 50.000 | **50** | 1.50 | 0.00 | 0% |
| 3 | −2.10 | −70.000 | **−70** | −2.10 | 0.00 | 0% |
| 4 | 0.05 | 1.667 | **2** | 0.06 | +0.01 | **20.0%** |
| 5 | 3.81 | 127.000 | **127** | 3.81 | 0.00 | 0% |
| 6 | −0.40 | −13.333 | **−13** | −0.39 | +0.01 | 2.5% |
| 7 | 1.00 | 33.333 | **33** | 0.99 | −0.01 | 1.0% |

误差汇总：

```
最大绝对误差 = 0.01              ← 理论上界是 scale/2 = 0.015，实际没到顶
RMSE（均方根误差）：
    平方和 = 5 × (0.01)² = 5.0e-4
    MSE    = 5.0e-4 / 8 = 6.25e-5
    RMSE   = 0.00791
```

> ★ **这张表里最该盯住的是索引 4**：真值 0.05，量化回来变成 0.06，**相对误差 20%**。而索引 5（3.81）的相对误差是 0。这不是偶然——**均匀量化的绝对误差处处相同（都不超过 scale/2），所以数值越小，相对误差越大。** 这条性质贯穿整章：它是离群值为什么致命（§6.3）的原因，也是 FP8 为什么和 INT8 不同（§6.5）的原因。

> ⚠️ **`round` 的实现细节会影响结果。** `0.5` 这种正好卡在中间的情况，C/CUDA 的 `roundf` 是"远离零"（0.5 → 1，−0.5 → −1），而 IEEE-754 默认和 PyTorch 的 `torch.round` 是"就近取偶"（0.5 → 0，1.5 → 2）。两种实现对同一个张量会给出不同的整数，训练端和推理端用了不同实现就会引入无端的数值差异——这正是 [11 章](11-训推一致性算子层.md) 讲的训推不一致的来源之一。

### 6.2.2 非对称量化：同样 8 个数再走一遍

对称量化默认"正负范围一样宽"。如果分布偏向一侧，对称量化会白白浪费掉一半档位。非对称量化多引入一个 **zero-point（零点）**，把整个区间平移到无符号整数 `[0, 255]` 上。

```
① scale      = ( max(x) − min(x) ) / (2^b − 1)          分母对 INT8 是 255
② zero_point = round( −min(x) / scale )                  实数 0 落在哪个整数上
③ q          = clamp( round(x / scale) + zero_point, 0, 255 )
④ x̂          = (q − zero_point) × scale
```

代进去：`max = 3.81`，`min = −2.10`，range = 5.91。

```
scale      = 5.91 / 255 = 0.0231765
zero_point = round( 2.10 / 0.0231765 ) = round(90.61) = 91
```

| 索引 | 原值 x | x / scale | round | + zp = q（UINT8） | 反量化 x̂ | 绝对误差 |
|---|---|---|---|---|---|---|
| 0 | −0.80 | −34.517 | −35 | **56** | −0.8112 | −0.0112 |
| 1 | 0.25 | 10.787 | 11 | **102** | 0.2549 | +0.0049 |
| 2 | 1.50 | 64.720 | 65 | **156** | 1.5065 | +0.0065 |
| 3 | −2.10 | −90.609 | −91 | **0** | −2.1091 | −0.0091 |
| 4 | 0.05 | 2.157 | 2 | **93** | 0.0464 | −0.0036 |
| 5 | 3.81 | 164.391 | 164 | **255** | 3.8009 | −0.0091 |
| 6 | −0.40 | −17.259 | −17 | **74** | −0.3940 | +0.0060 |
| 7 | 1.00 | 43.147 | 43 | **134** | 0.9966 | −0.0034 |

```
RMSE = 0.00721      （对称量化是 0.00791）
改善 = 8.8%
```

注意两个细节：**最小值恰好落到 q = 0，最大值恰好落到 q = 255**——非对称量化的整个 256 个档位被完整用满了，这就是它的优势来源。而对称量化实际只用到了 `[−70, 127]` 这 198 个档位，剩下 57 个（`[−127, −71]`）全空着。

### 6.2.3 什么时候非对称才真的有用

上面只改善了 8.6%，看起来不值得多存一个 zero-point。因为**这组数本来就大致对称**（−2.10 到 3.81）。

换一组**单边分布**的数——这是激活值的常态，因为 ReLU/GELU/SiLU 之后的值几乎都非负：

```
a = [ 0.00,  0.40,  1.20,  2.00,  0.10,  3.20,  0.00,  0.80 ]     全部 ≥ 0
```

| | 对称量化 | 非对称量化 |
|---|---|---|
| scale | 3.20 / 127 = **0.025197** | (3.20 − 0.00) / 255 = **0.012549** |
| zero_point | — | round(0 / 0.012549) = **0** |
| 实际用到的档位 | q ∈ [0, 127]，**128 个** | q ∈ [0, 255]，**256 个** |
| 白白浪费的档位 | q ∈ [−127, −1]，**127 个** | 0 个 |
| 每一档代表多大 | 0.0252 | **0.0125** |
| 最大量化误差 | 0.0126 | **0.0063** |

**步长正好减半，误差正好减半，等价于多了 1 个比特。** 这就是"非对称量化用于激活值、对称量化用于权重"这条经验法则的全部内容——**权重的分布大致以 0 为中心，用不着 zero-point；激活值经常是单边的，用了就白赚 1 bit。**

> ⚠️ **非对称量化在 GEMM（矩阵乘）里是有代价的，不只是多存一个数。** 展开看：
>
> ```
> Y = Σ ( (q_x − zp_x) · s_x ) × ( (q_w − zp_w) · s_w )
>   = s_x · s_w · [ Σ q_x·q_w − zp_w·Σ q_x − zp_x·Σ q_w + K·zp_x·zp_w ]
>                   ▲主项，INT8 Tensor Core 干这个   ▲三个额外的修正项
> ```
>
> 后面三项都得单独算：`Σ q_x` 要沿 K 方向对激活求和，`Σ q_w` 要对权重求和（可以离线预计算）。**这就是为什么权重几乎一律用对称量化**——`zp_w = 0` 时后两项直接消失，只剩一个可以在 Epilogue 里顺手算掉的修正项。

### 6.2.4 量化粒度：同一组数走三遍

"多少个数共用一个 scale"就是粒度。把那 8 个数摆成一个 **2 × 4 的权重矩阵**（2 个输出通道 × 4 个输入维度）：

```
                 输入维度 0   输入维度 1   输入维度 2   输入维度 3      该行的 max|.|
  输出通道 0        -0.80        0.25        1.50       -2.10            2.10
  输出通道 1         0.05        3.81       -0.40        1.00            3.81
```

四种粒度在这个矩阵上分别是：

```
Per-tensor（逐张量）        整个 2 × 4 共用 1 个 scale

    所有 8 个数 ──  -0.80   0.25   1.50  -2.10
                     0.05   3.81  -0.40   1.00      共用 scale = 3.81/127


Per-channel（逐输出通道）   每一行一个 scale   ← 权重量化的标准做法

    ├── 行 0   -0.80   0.25   1.50  -2.10           scale_0 = 2.10/127
    └── 行 1    0.05   3.81  -0.40   1.00           scale_1 = 3.81/127


Per-group（逐组，这里 g=2） 每行内再切成 2 段，共 4 个 scale

    ├── 行 0 段 0   -0.80   0.25                    scale = 0.80/127
    ├── 行 0 段 1    1.50  -2.10                    scale = 2.10/127
    ├── 行 1 段 0    0.05   3.81                    scale = 3.81/127
    └── 行 1 段 1   -0.40   1.00                    scale = 1.00/127


Per-token（逐 token）       用于激活矩阵：每一行（每个 token）一个 scale
                            形状上和 per-channel 一样，只是切的是另一个张量
```

**三种粒度的完整数值对比**（都用对称量化）：

| 索引 | 原值 | per-tensor q / x̂ | 误差 | per-channel q / x̂ | 误差 | per-group(2) q / x̂ | 误差 |
|---|---|---|---|---|---|---|---|
| 0 | −0.80 | −27 / −0.8100 | −0.0100 | −48 / −0.7937 | +0.0063 | −127 / −0.8000 | **0** |
| 1 | 0.25 | 8 / 0.2400 | −0.0100 | 15 / 0.2480 | −0.0020 | 40 / 0.2520 | +0.0020 |
| 2 | 1.50 | 50 / 1.5000 | 0 | 91 / 1.5047 | +0.0047 | 91 / 1.5047 | +0.0047 |
| 3 | −2.10 | −70 / −2.1000 | 0 | −127 / −2.1000 | 0 | −127 / −2.1000 | 0 |
| 4 | 0.05 | 2 / 0.0600 | +0.0100 | 2 / 0.0600 | +0.0100 | 2 / 0.0600 | **+0.0100** |
| 5 | 3.81 | 127 / 3.8100 | 0 | 127 / 3.8100 | 0 | 127 / 3.8100 | 0 |
| 6 | −0.40 | −13 / −0.3900 | +0.0100 | −13 / −0.3900 | +0.0100 | −51 / −0.4016 | −0.0016 |
| 7 | 1.00 | 33 / 0.9900 | −0.0100 | 33 / 0.9900 | −0.0100 | 127 / 1.0000 | **0** |

```
                    scale 个数     RMSE        相对 per-tensor
  per-tensor            1         0.00791          基准
  per-channel           2         0.00676          好 14%
  per-group (g=2)       4         0.00401          好 49%
```

> ★ **粒度的收益完全取决于"离群值被隔离进多小的组"。** 看索引 4（真值 0.05）：三种粒度下它的误差**一模一样，都是 +0.01**。因为它和 3.81 在同一行、同一组里，无论怎么切，那个最大值都跟它绑在一起。而索引 0 和索引 7 的误差被细粒度彻底消掉了，因为它们所在的小组最大值只有 0.80 和 1.00。**细粒度不是万能药，它只能把"被离群值污染的范围"缩小，缩不到 0。**

> ⚠️ **per-channel 切哪一维不能搞错。** 权重矩阵 `W[out, in]`，per-channel 指的是**按输出通道（行）** 切，因为 GEMM 输出 `Y[:, j] = X @ W[j, :]` 的第 j 列只由 W 的第 j 行决定——scale 可以整列提到 Epilogue 外面乘。如果按输入维度切，scale 会卡在 K 方向的归约里面，Tensor Core 累加到一半就得停下来乘 scale，工程上麻烦得多（DeepSeek 的 FP8 方案正是硬啃了这个麻烦，见 §6.5.3）。

### 6.2.5 激活值为什么用 per-token 而不是 per-channel

激活矩阵 `X[token, channel]`，同样有两个方向可切，但答案和权重相反：

```
X 的形状：M 个 token × K 个通道

  per-token（切行）     每个 token 一个 scale     ✅ 常用
      → 推理时 token 是一个一个来的，来一个算一个 scale，不需要提前知道范围
      → scale 是 GEMM 输出的"行方向"缩放，可以在 Epilogue 里乘，免费

  per-channel（切列）   每个通道一个 scale        ❌ 通常不用
      → 这个方向正好是 GEMM 归约的 K 方向，scale 混在累加里面，
        标准 INT8 Tensor Core 干不了这件事
      → 但激活的离群值恰恰是"逐通道"的（§6.3.2），
        所以这正是最想要却最难要的那个粒度 —— SmoothQuant（§6.4）就是绕过它的办法
```

> ★ **这是本章最关键的一个结构性事实**：激活的离群值沿**通道**分布，而 GEMM 允许的廉价 scale 方向是 **token**。要的和能给的正好错开一个维度。SmoothQuant 之所以有效，不是因为它发明了更好的量化算法，而是因为它把"逐通道的难度"提前搬到了权重上——权重的 per-channel 是廉价的。

### 6.2.6 scale 本身要占多少空间：算出"有效位宽"

粒度越细，scale 越多。这些 scale 不是免费的。

以一个 4096 × 4096 的权重矩阵（16,777,216 个元素）为例：

| 粒度 | scale 个数 | scale 占用（FP16，每个 2 B） | 权重本体（INT8） | 额外开销 |
|---|---|---|---|---|
| per-tensor | 1 | 2 B | 16.78 MB | 0.00001% |
| per-channel（4096 行） | 4096 | 8 KB | 16.78 MB | **0.05%** |
| per-group，g = 128 | 4096 × 32 = 131072 | 256 KB | 16.78 MB | **1.5%** |

INT8 下这点开销可以忽略。但 **INT4 下就不能忽略了**，因为权重本体缩小了一半而 scale 没变：

```
INT4，group = 128，非对称（scale 用 FP16，zero-point 用 INT4）：

  每 128 个权重需要存：
      权重  128 × 4 bit  = 64 字节
      scale 1 个 FP16    =  2 字节
      zp    1 个 INT4    =  0.5 字节
                        ──────────
      合计               = 66.5 字节

  平均每个权重 = 66.5 × 8 ÷ 128 = 4.15625 bit      ← 不是 4 bit！
```

拿它回头验算 §6.1.1 那个"4.17 GB"：

```
8.03e9 个参数 × 4.15625 bit ÷ 8 = 4.172e9 字节 = 4.17 GB      ✓ 对上了
相对 BF16 的压缩比 = 16 ÷ 4.15625 = 3.85 倍                   ✓ 就是 §6.1.1 那个 3.85
```

> ★ **group size 的取舍就是这张表**：g = 128 时多付 3.9% 的体积换更细的粒度；g = 32 时 scale 开销涨到 15.6%（每 32 个权重要 2.5 字节，平均 4.625 bit），精度确实更好但体积优势被吃掉一大截。**g = 128 是社区收敛下来的默认值**，它落在"精度还行、开销还小"的甜点上。

## 6.3 离群值：一个数怎么毁掉整个张量

### 6.3.1 把它算出来

回到 §6.2.1 那 8 个数，只改一个元素：把索引 5 的 `3.81` 换成 **`100.0`**（大约是其余元素典型量级的 100 倍）。其他 7 个数一字未动。

```
x' = [ -0.80,  0.25,  1.50, -2.10,  0.05,  100.0, -0.40,  1.00 ]
                                            ▲ 就改了这一个
```

`max(|x'|) = 100.0`，所以 **scale 从 0.03 暴涨到 100 / 127 = 0.7874**——大了 26 倍。

| 索引 | 原值 | 新 q | 反量化 x̂ | 新误差 | 对照：§6.2.1 的误差 | 恶化倍数 |
|---|---|---|---|---|---|---|
| 0 | −0.80 | −1 | −0.7874 | +0.0126 | −0.01 | 1.3× |
| 1 | 0.25 | **0** | **0.0000** | −0.2500 | −0.01 | **25×** |
| 2 | 1.50 | 2 | 1.5748 | +0.0748 | 0.00 | — |
| 3 | −2.10 | −3 | −2.3622 | −0.2622 | 0.00 | — |
| 4 | 0.05 | **0** | **0.0000** | −0.0500 | +0.01 | 5× |
| 5 | 100.0 | 127 | 100.0000 | 0.0000 | — | — |
| 6 | −0.40 | −1 | −0.7874 | −0.3874 | +0.01 | **39×** |
| 7 | 1.00 | 1 | 0.7874 | −0.2126 | −0.01 | **21×** |

```
7 个"正常"元素的 RMSE：
    量化前（无离群值）  0.00845
    量化后（有离群值）  0.21868
    恶化 26 倍 —— 恰好等于 scale 涨大的倍数
```

三个具体的灾难：

```
① 索引 1（0.25）和索引 4（0.05）被直接抹成了 0
   —— 它们的真值小于 scale/2 = 0.394，四舍五入后什么都不剩。信息完全丢失。

② 索引 6（−0.40）被"放大"到 −0.79，误差比它本身还大（0.39 > 0.40 的 97%）
   —— 反量化后的值几乎和真值无关了。

③ 8 个数原本用满了 [−70, 127] 这 198 个档位，
   现在 7 个正常值全挤在 q ∈ {−3, −1, 0, 1, 2} 这 6 个档位里：
       log₂(6) ≈ 2.6 bit
   —— 花了 8 bit 的存储，正常值实际只拿到不到 3 bit 的精度。
```

> ★ **"一个离群值毁掉整个张量"不是修辞，是算术。** scale 由 `max(|x|)` 单点决定，这个最大值涨多少倍，其余所有元素的绝对误差就涨多少倍。**一个元素，全员买单。**

### 6.3.2 为什么激活有离群值而权重没有

这是两类张量最根本的区别，也决定了"权重好量化、激活难量化"这个基本事实。

```
权重 W                          激活 X
  ├── 训练时被 weight decay 和     ├── 是 GEMM 的输出，
  │   梯度更新反复约束             │   由上千个数累加而来
  ├── 分布接近高斯，尾巴很短       ├── 残差流会把每一层的输出累加起来，
  ├── max / median 通常 < 20 倍   │   某些通道的幅度会一层层堆积
  └── 静态的，离线看一眼就知道     ├── 分布是长尾的，max / median 可达 数百倍
                                   └── 动态的，换一批输入就变
```

**离群值有一个关键的结构性质：它们集中在固定的少数几个通道里。** 同一个通道，对几乎所有 token 都是大的；其余通道对几乎所有 token 都是小的。这个现象在 6B 参数以上的模型里稳定出现，是 SmoothQuant 和 AWQ 共同的立论基础。

```
一个典型的激活矩阵（示意，行 = token，列 = 通道）：

              c0     c1     c2     c3  ...  c1847  ...  c4095
  token 0    0.3    0.5   -0.2    0.8       92.1        0.4
  token 1   -0.4    0.2    0.6   -0.1       88.7       -0.3
  token 2    0.1   -0.6    0.3    0.5       95.4        0.2
  token 3    0.5    0.4   -0.5    0.2       90.8       -0.6
                                              ▲
                              这一整列都很大，而且每个 token 都大
```

### 6.3.3 为什么细粒度救不了它

把 §6.3.1 那 8 个数按 per-group（g = 4）切成两组再试一次：

```
组 0 = [-0.80,  0.25,  1.50, -2.10]    max = 2.10，scale = 0.016535
组 1 = [ 0.05, 100.0, -0.40,  1.00]    max = 100 ，scale = 0.787402
```

| 索引 | 原值 | 所在组 | 反量化 x̂ | 误差 |
|---|---|---|---|---|
| 0 | −0.80 | 组 0 | −0.7937 | +0.0063 |
| 1 | 0.25 | 组 0 | 0.2480 | −0.0020 |
| 2 | 1.50 | 组 0 | 1.5047 | +0.0047 |
| 3 | −2.10 | 组 0 | −2.1000 | 0.0000 |
| 4 | 0.05 | 组 1 | **0.0000** | **−0.0500** |
| 5 | 100.0 | 组 1 | 100.0000 | 0.0000 |
| 6 | −0.40 | 组 1 | **−0.7874** | **−0.3874** |
| 7 | 1.00 | 组 1 | **0.7874** | **−0.2126** |

**组 0 完全恢复了正常**（RMSE 0.0043，和没有离群值时一样好）；**组 1 照旧被毁**。

> ★ **细粒度量化只能给离群值"划隔离区"，不能治它。** 隔离区里的元素照样陪葬。对权重来说这够用了（离群值稀疏、组小、影响范围有限），但对激活不够——因为激活的离群值是**逐通道**的（§6.3.2），而 GEMM 里逐通道那个方向的 scale 恰恰是最贵的（§6.2.5）。**所以激活离群值必须用结构性手段解决，这就是 §6.4 SmoothQuant 存在的理由。**

### 6.3.4 三类通用对策

| 对策 | 做法 | 代价 | 代表 |
|---|---|---|---|
| **截断（Clipping）** | 不用 `max`，用分位数（如 99.9%）定 scale，超出的直接钳到边界 | 离群值本身被算错，但其余 99.9% 精度大涨 | 几乎所有 PTQ 校准工具的默认选项 |
| **迁移（Migration）** | 用一组等价变换，把幅度从难量化的一侧搬到好量化的一侧 | 要额外存一组缩放因子；变换要严格等价 | **SmoothQuant**（§6.4）、**AWQ**（§6.7） |
| **旋转 / 混合精度** | 用哈达玛变换把离群值"打散"到所有通道；或把离群通道单独留 FP16 | 前者多一次变换开销；后者 kernel 复杂、硬件不友好 | QuaRot、SpinQuant；FA3 的非相干处理（[04 章 §4.6](04-FlashAttention全系.md)）；LLM.int8() |

> ⚠️ **截断的分位数不能照抄别人的数。** 99.9% 对一个模型合适，对另一个可能就切掉了真正重要的信号。实践中用一小批校准数据扫几个候选值（99.0 / 99.9 / 99.99 / max），拿量化后的 MSE 或 PPL 挑最好的那个。这个搜索本身就是校准工具的主要工作量。

## 6.4 W8A8 与 SmoothQuant：把难度从激活搬到权重

### 6.4.1 W8A8 的诱惑与障碍

W8A8 是唯一能同时拿到"带宽减半"和"算力翻倍"的 INT8 方案：H100 的 INT8 Tensor Core 是 1979 TOPS，BF16 是 989 TFLOPS，正好 2 倍（[附-速查表 §A](附-速查表.md)）。

障碍只有一个，就是 §6.3 讲的激活离群值。用 §6.3.1 的话说：**权重侧 INT8 是送分题，激活侧 INT8 是送命题。**

### 6.4.2 SmoothQuant 的核心恒等式

SmoothQuant 的想法出奇地简单：既然一侧太难、另一侧太容易，那就**把难度分一部分过去**。

矩阵乘法有一个平凡的恒等式——中间插一对互逆的对角矩阵，结果不变：

```
Y = X · W
  = X · diag(s)⁻¹ · diag(s) · W
  = ( X / s ) · ( s · W )
     ▲ 逐通道除    ▲ 逐输入通道乘
        X̃              W̃

  X̃ = X / s  →  每一列（通道）除以对应的 s_j
  W̃ = s · W  →  每一行（输入通道）乘以对应的 s_j
```

**因为 s 沿的是同一个维度（X 的列 = W 的行 = GEMM 的 K 维），这个变换严格等价，一个 FLOP 都没多。**

### 6.4.3 把它算出来：一个 2 通道的完整例子

设一个 token 的激活和一个 2×2 的权重：

```
X = [ 0.5 , 60.0 ]        ← 通道 1 是离群通道，比通道 0 大 120 倍

W = [ 0.9  -0.7 ]         ← 第 0 行 = 输入通道 0 的权重
    [ 0.6   0.4 ]         ← 第 1 行 = 输入通道 1 的权重
```

**第一步：看看不做任何处理会有多糟。** 激活 per-tensor 对称 INT8：

```
scale_X = 60.0 / 127 = 0.472441
  通道 0：0.5 / 0.472441 = 1.058 → round = 1 → 0.4724
          误差 −0.0276，相对误差 5.5%
  通道 1：60.0 → 127 → 60.0，误差 0
```

**第二步：算平滑因子。** 公式是

```
s_j = max|X[:, j]|^α  ÷  max|W[j, :]|^(1−α)          α ∈ [0, 1]，通常取 0.5
```

α = 0.5 时：

```
s_0 = √0.5  ÷ √0.9 = 0.70711 ÷ 0.94868 = 0.745356
s_1 = √60.0 ÷ √0.6 = 7.74597 ÷ 0.77460 = 10.000000
```

**第三步：应用变换。**

```
X̃ = X / s = [ 0.5 / 0.745356 ,  60.0 / 10.0 ] = [ 0.670820 ,  6.000000 ]

W̃ = s · W（第 j 行乘 s_j）：
    行 0 × 0.745356 = [ 0.670820 , −0.521749 ]
    行 1 × 10.0     = [ 6.000000 ,  4.000000 ]
```

**第四步：验算等价性**（这一步一定要自己算一遍）：

```
原式  X · W  = [ 0.5×0.9 + 60×0.6 ,  0.5×(−0.7) + 60×0.4 ]
             = [ 0.45 + 36.0     ,  −0.35 + 24.0        ]
             = [ 36.45           ,   23.65              ]

新式  X̃ · W̃ = [ 0.670820×0.670820 + 6.0×6.0 ,  0.670820×(−0.521749) + 6.0×4.0 ]
             = [ 0.45 + 36.0                 ,  −0.35 + 24.0                   ]
             = [ 36.45                       ,   23.65                         ]     ✓ 完全一致
```

**第五步：看难度怎么移动的。**

```
                    激活 X 的逐通道最大值        权重 W 的逐输入通道最大值

  迁移前              c0: 0.5   c1: 60.0          r0: 0.9   r1: 0.6
                      通道间落差 120 倍            通道间落差 1.5 倍，本来就平

                           ▼ 每个通道除以 s_j           ▼ 每个输入通道乘以 s_j
                             s = [0.745, 10.0]

  迁移后              c0: 0.671  c1: 6.0          r0: 0.671  r1: 6.0
                      通道间落差 8.9 倍            通道间落差 8.9 倍

                      两边的最大值一模一样（都是 6.0），难度被均分了
```

**第六步：量化误差改善了多少。** 激活 per-tensor 对称 INT8，新的 `max = 6.0`：

```
scale_X̃ = 6.0 / 127 = 0.047244
  通道 0：0.670820 / 0.047244 = 14.199 → round = 14 → 0.661417
          误差 −0.009403，相对误差 1.4%       （迁移前是 5.5%，好了 3.9 倍）
  通道 1：6.0 → 127 → 6.0，误差 0
```

代价在权重侧：`max|W|` 从 0.9 涨到 6.0，权重的 scale 大了 6.67 倍。但权重侧本来就有大量余量——它是静态的、分布平滑的、可以用 per-channel 的（§6.2.4），所以吃得下。

### 6.4.4 α 到底在调什么

α = 0.5 有一个漂亮的性质：**迁移后两边的最大值完全相等，都等于两者的几何平均数。**

```
迁移后激活的最大值 = max|X_j| / s_j = max|X_j|^(1−α) · max|W_j|^(1−α)
迁移后权重的最大值 = max|W_j| · s_j = max|X_j|^α     · max|W_j|^α

α = 0.5 时两式相等 = √( max|X_j| × max|W_j| )

验算：√(0.5 × 0.9) = √0.45 = 0.670820   ✓ 和上面算出来的一样
      √(60 × 0.6)  = √36   = 6.0        ✓
```

把 α 从 0 扫到 1，看本例通道 1（`max|X| = 60`，`max|W| = 0.6`）上发生什么：

| α | s_1 = 60^α ÷ 0.6^(1−α) | 迁移后激活 max | 迁移后权重 max | 两者乘积 |
|---|---|---|---|---|
| 不做迁移（s = 1） | 1.00 | 60.0 | 0.6 | **36** |
| 0 | 1 ÷ 0.6 = 1.667 | 36.0 | 1.0 | **36** |
| 0.5 | 10.00 | **6.0** | **6.0** | **36** |
| 0.75 | 21.564 ÷ 0.880 = 24.49 | 2.45 | 14.70 | **36** |
| 1.0 | 60.00 | 1.0 | 36.0 | **36** |

> ★ **最后一列是全表最重要的信息：乘积恒等于 36，怎么调 α 都不变。** 因为 `(max|X| / s) × (max|W| × s) = max|X| × max|W|`，s 直接约掉了。**迁移只能在两边之间分配难度，分不掉总量。** α = 0.5 之所以是默认值，是因为在总量固定的前提下，把 36 拆成 6 × 6 比拆成 36 × 1 或 1 × 36 更"均衡"——两边都落在 INT8 吃得下的范围里。

> ⚠️ **注意 α = 0 不等于"什么都不做"。** 公式在 α = 0 时取 `s_j = 1 / max|W_j|`，效果是把权重归一化到 1、把几乎全部难度留给激活（表里第二行，激活 max 仍高达 36）。真正的"什么都不做"是 s = 1，那是表的第一行。

> ★ **α 是一个旋钮，不是一个常数。** 离群值特别凶的模型（论文里 OPT-175B 这类）需要更大的 α 把更多难度推给权重；离群值温和的模型 α = 0.5 甚至更小就够。**调 α 的判据是量化后的端到端精度，不是任何一侧的最大值本身。**

### 6.4.5 工程上它是免费的

`X / s` 这个除法看起来要多跑一遍逐元素 kernel，但实际上**一次都不用跑**：

```
Transformer 里 Linear 前面必然是 LayerNorm / RMSNorm，而归一化层自带一个逐通道的
仿射参数 gamma（有的还有 beta）。于是：

    把  gamma ← gamma / s，  beta ← beta / s   离线改一次
    归一化层的输出就自动是 X̃ 了，运行时零开销

  权重侧同理：W̃ = s · W 离线算好存下来，运行时就是普通的 INT8 权重
```

**所以 SmoothQuant 在推理时的额外开销确实是 0**——所有工作都在离线的校准阶段完成。它需要的只是一批校准数据，用来统计每个通道的 `max|X[:, j]|`。

> ⚠️ **上一段的前提是"前面是归一化层"。** 如果 Linear 前面直接跟着另一个 Linear 的输出、或者跟着 Attention 的输出投影，就没有现成的 gamma 可以吸收，得插一个真的逐元素乘法 kernel。这时它的成本就是一次 Memory Bound 的逐元素算子（[05 章](05-算子融合.md) 的账），通常还是能融进上一个 kernel 的 Epilogue。

### 6.4.6 效果

> ⚠️ **本章旧版这里写的是"LLaMA-65B，W8A8 无 SmoothQuant 时 PPL 上升 2–5"，这个数字没有出处，已删除。** SmoothQuant 论文（Xiao et al., ICML 2023）自己的口径是：**在 OPT、BLOOM、GLM、MT-NLG、Llama-1/2、Falcon、Mistral、Mixtral 上做 W8A8，精度损失可忽略；相对 FP16 最多 1.56 倍加速、2 倍显存节省**；并且使得 530B 模型能在单节点上服务。

论文里最有说服力的定性结论是：**模型越大，朴素 W8A8 崩得越厉害，SmoothQuant 的价值越大。** 因为离群值的幅度随模型规模增长——小模型（1B 量级）直接做 W8A8 往往也没事，到 100B 量级就会看到精度断崖。

> ★ **所以"要不要上 SmoothQuant"这个问题，答案取决于模型规模而不是取决于口味。** 判断方法很直接：统计一下各层激活的 `max / median`，如果有层超过 50 倍，朴素 W8A8 基本无望。

## 6.5 FP8：把精度按数量级分配

### 6.5.1 两种格式，先把位数摆出来

```
E4M3（1 符号 + 4 指数 + 3 尾数）          E5M2（1 符号 + 5 指数 + 2 尾数）

  S │ E E E E │ M M M                      S │ E E E E E │ M M
  ▲     ▲         ▲                        ▲       ▲        ▲
  │     │         └ 3 位尾数               │       │        └ 2 位尾数
  │     └ 指数偏置 7                       │       └ 指数偏置 15
  └ 符号                                   └ 符号

  每个二进制数量级内有 2³ = 8 个刻度        每个数量级内有 2² = 4 个刻度
  没有 Inf（省下来给数值范围）              有 Inf 和 NaN，和 IEEE-754 一样
```

| 指标 | E4M3 | E5M2 | 对照：INT8 | 对照：BF16 |
|---|---|---|---|---|
| 最大正规数 | **448** | **57344** | 127 × scale | 3.39e38 |
| 最小正规数 | 2⁻⁶ = 0.015625 | 2⁻¹⁴ ≈ 6.10e−5 | 1 × scale | 1.18e−38 |
| 最小次正规数 | 2⁻⁹ ≈ 0.00195 | 2⁻¹⁶ ≈ 1.53e−5 | — | — |
| 动态范围（最大 ÷ 最小正规） | ≈ 2¹⁵ | ≈ 2³⁰ | 127（= 2⁷） | ≈ 2²⁷⁷ |
| 最大相对舍入误差 | 2⁻⁴ = **6.25%** | 2⁻³ = **12.5%** | 随数值大小变，见下 | 2⁻⁸ = 0.39% |
| 十进制有效位 | ≈ 1.2 位 | ≈ 0.9 位 | 随数值大小变 | ≈ 2.4 位 |

验算一下 448 这个数是怎么来的（可以自己推）：

```
E4M3 指数字段最大可用值 = 1111₂ = 15，偏置 7 → 实际指数 = 15 − 7 = 8
尾数最大（排除 111₂，那是 NaN）= 110₂ → 有效数 = 1.110₂ = 1.75
          最大值 = 1.75 × 2⁸ = 1.75 × 256 = 448      ✓

E5M2 指数字段最大可用值 = 11110₂ = 30（11111 留给 Inf/NaN），偏置 15 → 指数 = 15
尾数最大 = 11₂ → 有效数 = 1.75
          最大值 = 1.75 × 2¹⁵ = 1.75 × 32768 = 57344  ✓
```

> ⚠️ **[附-速查表 §B.6](附-速查表.md) 写的"E4M3 精度 ~3 有效位、E5M2 ~2 有效位"是按十进制理解的话偏高。** 按比特算：E4M3 的有效数只有 4 bit（3 显式 + 1 隐含），`log₁₀(2⁴) ≈ 1.2` 位十进制；E5M2 是 3 bit，约 0.9 位。速查表那两个数更像是把"尾数位数"当成了"十进制有效位"。本章用上面这张按比特推导的表。

### 6.5.2 FP8 和 INT8 的本质区别：精度怎么分配

这才是 FP8 值得单独讲一节的原因。**INT8 的绝对误差处处相同；FP8 的相对误差处处相同。**

用一个具体的张量对比：假设某张量最大值是 448（这样 E4M3 的范围刚好用满），INT8 per-tensor 对称量化的 `scale = 448 / 127 = 3.52756`。

| 真实值 x | INT8 的 q | INT8 反量化 | INT8 相对误差 | E4M3 最近可表示值 | E4M3 相对误差 |
|---|---|---|---|---|---|
| 448 | 127 | 448.0 | 0% | 448 | 0% |
| 100 | 28 | 98.77 | −1.2% | 96（128 以下步长 8） | −4.0% |
| 10 | 3 | 10.58 | +5.8% | **10（精确）** | **0%** |
| 1 | **0** | **0** | **−100%** | **1（精确）** | **0%** |
| 0.1 | **0** | **0** | **−100%** | 0.1015625 | +1.6% |
| 0.01 | **0** | **0** | **−100%** | 0.009765625（次正规） | −2.3% |

> ★ **两条曲线在这里交叉了**：大数上 INT8 更准（1.2% vs 4.0%），因为 INT8 的 255 个档位全堆在最大值附近；小数上 INT8 彻底失效（全部变 0），而 E4M3 保持约 4% 的相对误差不变。**FP8 用"牺牲大数的精度"换"覆盖整个动态范围"。**

> ⚠️ **别把这张表当成"FP8 总是比 INT8 好"。** 这个对比对 INT8 不公平，因为它用了最差的 per-tensor 粒度和最坏的 `max = 448`。真实部署里 INT8 用 per-channel / per-group 把每组的 `max` 压得很小，动态范围问题就大幅缓解了。**§6.10.2 会给出一个反例：华为在 openPangu-7B 权重量化上的实测，INT8 per-channel 的 SQNR 排在所有 FP8 变体之前。** FP8 的真正优势是**训练**——梯度的动态范围能跨好几个数量级，那是 INT8 无论怎么细粒度都搞不定的。

### 6.5.3 DeepSeek-V3 的 FP8 训练：本章旧版这里错得最多

> ⚠️ **本章旧版这一节有四处事实错误，逐条改正**：① 旧版说"注意力计算（QKᵀ、PV）用 FP8 E4M3"——**错**，DeepSeek-V3 明确把 attention 算子留在原精度。② 旧版说"梯度用 E5M2"——**错**，DeepSeek-V3 的特点恰恰是**所有张量都用 E4M3**，这是它和前人（Micikevicius 等 2022 的 E4M3/E5M2 混合方案）最大的区别。③ 旧版说"每隔几步更新一次 scale（历史最大值的指数移动平均）"——**错**，论文明确用的是**在线（online）** 计算，每个 tile/block 当场算 max，正是为了避免延迟缩放（delayed scaling）的问题。④ 旧版写"PPL 差异 < 0.02%、训练速度提升约 1.6 倍、显存减少约 30%"——**这三个数字论文里都没有**，已删除；论文给的是**相对 loss 误差始终低于 0.25%**。另外旧版写"DeepSeek-V3/V4 技术报告"，V4 不存在，已改。

以下全部按 [DeepSeek-V3 技术报告](https://arxiv.org/abs/2412.19437) §3.3 与 §3.5.2 的口径（✅ 论文披露）：

**（1）哪些算 FP8，哪些不算**

```
走 FP8（E4M3）的：
  ├── 所有主要 GEMM：Fprop（前向）、Dgrad（对输入求梯度）、Wgrad（对权重求梯度）
  └── 这三个 GEMM 占了训练算力的绝大部分

保持原精度（BF16 / FP32）的：
  ├── 嵌入层（embedding）
  ├── 输出头（output head）
  ├── MoE 门控（gating）           ← 路由是离散决策，一点噪声就会翻转，见 11 章
  ├── 归一化算子（LayerNorm / RMSNorm）
  └── 注意力算子（attention）      ← 不是 FP8！旧版这里写错了
  另外：主权重、权重梯度、优化器状态全部保持高精度（靠 DP 切分摊薄显存）

特例：
  └── attention 之后那个 Linear 的输入用自定义的 E5M6 格式
      （因为这份激活还要参与反向，对精度特别敏感）
```

**（2）量化粒度：两种，都是在线算的**

```
激活：1 × 128 的 tile     —— 每个 token 的每 128 个通道一个 scale
权重：128 × 128 的 block  —— 每 128 个输入通道 × 128 个输出通道一个 scale

  ┌──────────── 权重 W（K × N）────────────
  │ ┌─────┬─────┬─────┬─────
  │ │128× │128× │128× │  ...     每个小方块一个独立 scale
  │ │128  │128  │128  │
  │ ├─────┼─────┼─────┼─────
  │ │     │     │     │  ...
  │ └─────┴─────┴─────┴─────

  激活 X（M × K）
  │ token 0 │ 128 通道 │ 128 通道 │ ...     每一小段一个独立 scale
  │ token 1 │ 128 通道 │ 128 通道 │ ...
```

注意这个粒度的方向：**scale 沿着 GEMM 的内维（K 方向）在变。** 按 §6.2.4 说过的，这正是最贵的那个方向——标准 FP8 GEMM 不支持它，得自己写 kernel。DeepSeek 为此开源了 **DeepGEMM**。

**（3）为什么必须自己做累加：Hopper 的 FP8 累加只有 14 bit**

这是整节最硬核也最实用的一个硬件事实：

```
H800/H100 的 FP8 Tensor Core 做累加时：
  ① 把 32 个尾数乘积按最大指数右移对齐
  ② 只取每个乘积最高的 14 bit 相加，其余截断
  ③ 累加寄存器也只有 14 bit 精度

  论文的 toy 实验：两个随机矩阵相乘，内维 K = 4096，
  只靠 Tensor Core 累加的最大相对误差接近 2%     ← ✅ 论文口径
```

DeepSeek 的解法：**每累加 N_C = 128 个元素（约 4 条 WGMMA 指令），就把部分和搬到 CUDA Core 上用 FP32 累加一次。** 128 是"能显著改善精度、又不至于太贵"的最小间隔；而 Hopper 允许两条 WGMMA 并发，所以搬运和矩阵乘可以重叠，Tensor Core 不会闲着。

> ★ **这个细节值得记住，它是"低精度 GEMM 的精度不只取决于输入格式"的最好例子。** 同样是 FP8 输入，累加用 14 bit 还是 FP32，K = 4096 时结果能差 2%。很多"FP8 训练发散了"的案例，根子在累加而不在格式。

**（4）结果**

```
在两个规模（对标 DeepSeek-V2-Lite 和 DeepSeek-V2）上、约 1T token 的验证：
    相对 BF16 基线的 loss 相对误差始终 < 0.25%     ← ✅ 论文口径
    论文的评价是：这在正常训练噪声范围之内
```

> ⚠️ **论文没有给出"FP8 让训练快了多少倍"的独立数字。** 网上流传的各种倍数（1.6×、2× 之类）都找不到一手出处，**不要引用**。可以肯定的只有：FP8 GEMM 的理论算力是 BF16 的 2 倍（1979 vs 989 TFLOPS，[附-速查表 §A](附-速查表.md)），而训练里 GEMM 不是 100% 的时间，所以端到端的提升必然明显低于 2 倍。

## 6.6 GPTQ：用二阶信息决定怎么取舍

### 6.6.1 RTN 的问题：它在优化错的东西

朴素的 RTN（Round-To-Nearest，就近取整）做的是：**让量化后的权重尽量靠近原权重**。

但我们真正在乎的不是权重像不像，而是**这一层的输出像不像**。这两件事在权重之间有相关性时会分岔——而校准数据里的输入通道几乎总是相关的。

GPTQ 的目标函数因此写成：

```
min  ‖ X·W − X·Ŵ ‖²        ← 输出的差，不是权重的差
 Ŵ
其中 X 是一小批校准数据（约 128 条样本）跑出来的该层输入
```

### 6.6.2 用 2 个权重把差别算出来

这是本节的核心例子，**建议一定自己算一遍**。

**设定**：某一层的某个输出神经元，只有 2 个输入通道，权重 `w = [1.40, 0.45]`。量化格点粗一点好看清楚：允许的取值是 `{0, 1, 2}`（步长 1.0）。

**校准数据**（3 条样本，2 个通道）：

```
x⁽¹⁾ = (1, 0)
x⁽²⁾ = (1, 1)
x⁽³⁾ = (0, 1)

Hessian 矩阵 H = XᵀX = [ 2  1 ]
                       [ 1  2 ]         ← 非对角元 1 ≠ 0，说明两个通道是相关的

H⁻¹ = (1/3) [  2  -1 ]
            [ -1   2 ]
```

**方法 A：RTN。** 各自四舍五入：

```
w₀ = 1.40 → 1
w₁ = 0.45 → 0
结果 ŵ_RTN = [1, 0]
```

**方法 B：GPTQ。** 逐列量化 + 误差补偿：

```
第 1 列：
  量化    q₀   = round(1.40) = 1
  误差    err₀ = 1.40 − 1 = 0.40
  补偿    w₁ ← w₁ − err₀ × H⁻¹[0,1] / H⁻¹[0,0]
              = 0.45 − 0.40 × (−1/3) / (2/3)
              = 0.45 − 0.40 × (−0.5)
              = 0.45 + 0.20 = 0.65        ← 把第 1 列丢掉的东西"补"给第 2 列

第 2 列：
  量化    q₁   = round(0.65) = 1

结果 ŵ_GPTQ = [1, 1]
```

**两种结果谁好？用真实的输出误差判。**

真值输出：`y = x·w`

```
y⁽¹⁾ = 1×1.40 + 0×0.45 = 1.40
y⁽²⁾ = 1×1.40 + 1×0.45 = 1.85
y⁽³⁾ = 0×1.40 + 1×0.45 = 0.45
```

| 样本 | 真值 y | RTN `[1,0]` 的 ŷ | RTN 误差 | GPTQ `[1,1]` 的 ŷ | GPTQ 误差 |
|---|---|---|---|---|---|
| x⁽¹⁾ = (1,0) | 1.40 | 1.00 | −0.40 | 1.00 | −0.40 |
| x⁽²⁾ = (1,1) | 1.85 | 1.00 | **−0.85** | 2.00 | +0.15 |
| x⁽³⁾ = (0,1) | 0.45 | 0.00 | −0.45 | 1.00 | +0.55 |
| | | **误差平方和** | **1.085** | **误差平方和** | **0.485** |

**GPTQ 的输出误差是 RTN 的 45%，好了 2.2 倍。**

而且可以穷举验证 `[1,1]` 确实是最优的：`{0,1,2}²` 一共 9 种组合，`[1,1]` = 0.485，`[2,0]` = 0.585，`[1,0]` = 1.085，其余更差。**GPTQ 找到了最优解，RTN 没有。**

> ★ **最反直觉的一点在这里**：在**权重空间**里，RTN 的 `[1,0]` 离真值 `[1.40, 0.45]` 更近（距离² = 0.40² + 0.45² = 0.3625），GPTQ 的 `[1,1]` 更远（0.40² + 0.55² = 0.4625）。**GPTQ 故意选了一个"看起来更差"的权重，因为它在输出空间里更近。** 这就是"用二阶信息做取舍"的具体含义——Hessian 告诉你哪些权重的改动会互相抵消。

### 6.6.3 完整算法与它要付的代价

```
对权重矩阵 W 的每一行（或整块），按列从左到右：

  for i in 0 .. K-1:
      q[i]   = quantize(w[i])                                    量化第 i 列
      err    = (w[i] − q[i]) / H⁻¹[i, i]                          归一化的误差
      w[i+1:] -= err × H⁻¹[i, i+1:]                               补偿给右边所有未量化的列

  H = 2·XᵀX + λI，用约 128 条校准样本算出来；λ 是阻尼项，防止 H 不可逆
```

| 维度 | GPTQ |
|---|---|
| 需要什么信息 | **校准数据的二阶统计量**（Hessian = XᵀX） |
| 计算成本 | 要对 H 求逆（Cholesky 分解），⚠️ 7B 模型典型 10–30 分钟量级（单卡，随实现差异大） |
| 需要反向传播吗 | 不需要，但需要逐层跑前向收集 X |
| 是否可能过拟合校准集 | **会**，因为它在显式最小化校准集上的重构误差 |
| 典型配置 | INT4，group = 128，对称或非对称都行 |

> ⚠️ **GPTQ 有一个著名的"顺序"敏感性。** 严格按列从左到右量化时，误差全往右边堆，最右边那几列会被补偿得面目全非。实践中用 `act_order`（也叫 desc_act）选项：**按激活幅度从大到小排序再量化**，让重要的列先被量化、后面的列去承担补偿。开了它精度更好，但权重在内存里就不再连续，推理 kernel 要多一层索引，速度会掉一些。这是部署时的一个真实取舍。

### 6.6.4 实测效果

| 模型 | FP16 基线 PPL | INT4 / group=128 PPL | PPL 上升 | 权重大小 |
|---|---|---|---|---|
| Llama-2 7B | 5.47 | ⚠️ ≈ 5.6 | ≈ +0.15 | 13.5 GB → **3.5 GB** |
| Llama-2 13B | 4.88 | ⚠️ ≈ 5.0 | ≈ +0.12 | 26.0 GB → **6.8 GB** |
| Llama-2 70B | 3.32 | ⚠️ ≈ 3.43 | ≈ +0.11 | 138 GB → **35.8 GB** |

> ⚠️ **PPL 数字标了 ⚠️，原因要说清楚。** ① 旧版表里的 5.68 / 5.02 / 3.44 找不到一手出处，已换成第三方汇总复现的量级值。② 更重要的是：**不同论文的绝对 PPL 不可混用**。同一个 Llama-2 7B，评测序列长度取 2048 还是 4096，FP16 基线就能从 5.47 变到 5.12。**只有同一张表内的差值才有意义。** 引用任何量化论文的 PPL 时，必须连着评测脚本、序列长度、数据集（通常是 WikiText-2）一起引。③ 权重大小是按 §6.2.6 的 4.15625 bit 精确算出来的，不是估的。

> ★ **INT4 GPTQ 的 70B 模型（35.8 GB 权重）能装进一块 40 GB A100，FP16 需要 4 块。** 但注意"装得进"和"跑得好"是两回事：40 GB 里减掉 35.8 GB 权重只剩 4.2 GB 给 KV Cache 和激活，batch 和上下文长度都会被卡死。实际部署通常还是会选 48 GB 或 80 GB 的卡。

## 6.7 AWQ：和 GPTQ 用的是完全不同的信息

### 6.7.1 先纠正一个流传很广的误解

> ⚠️ **本章旧版说"AWQ 把 1% 的重要权重保持 FP16、其余量化为 INT4"，这是错的，而且错得很典型。** 保留 1% 权重为 FP16 是 AWQ 论文用来**论证动机**的对照实验（"只保护 1% 的显著权重就能大幅降低量化误差"），论文紧接着就**明确否定了这条路**，理由是混合精度对硬件不友好——kernel 要同时处理两种格式，实现复杂且跑不快。**AWQ 的实际做法是：所有权重统一量化为 INT4，通过一个等价的逐通道缩放来保护显著通道。**

### 6.7.2 核心洞察：用激活的幅度判断权重重不重要

```
一个输出元素：  y[j] = Σᵢ w[i, j] · x[i]

如果 w[i, j] 有量化误差 Δ，它对输出的贡献误差是   Δ · x[i]
                                                       ▲
                                    被激活的幅度放大了 |x[i]| 倍
```

所以**权重重不重要，不取决于权重自己有多大，取决于跟它相乘的那个激活通道有多大。** 而激活的大通道是固定的少数几个（§6.3.2），于是：

```
GPTQ 用的信息：校准数据的 Hessian（XᵀX），是二阶的、带通道间相关性的
AWQ  用的信息：校准数据的逐通道平均幅度 mean|x[i]|，是一阶的、逐通道独立的
```

### 6.7.3 把它算出来

**设定**：某输出通道的 4 个权重，以及它们对应的 4 个输入通道的激活平均幅度：

```
w   = [ 0.20 ,  0.31 , −0.24 ,  0.40 ]
|x| = [ 30.0 ,   0.8 ,   0.5 ,   0.6 ]
        ▲ 通道 0 是显著通道，比其余大 40 倍以上
```

量化设定：INT4 对称，一组 4 个共用一个 scale，`scale = max|w| / 7 = 0.40 / 7 = 0.0571429`。

**基准（RTN，不做任何保护）**：

| i | w[i] | w/scale | q | 反量化 ŵ | 误差 Δ | 加权输出误差 = \|Δ\| × \|x[i]\| |
|---|---|---|---|---|---|---|
| 0 | 0.20 | 3.500 | 4 | 0.228571 | +0.028571 | **0.8571** |
| 1 | 0.31 | 5.425 | 5 | 0.285714 | −0.024286 | 0.0194 |
| 2 | −0.24 | −4.200 | −4 | −0.228571 | +0.011429 | 0.0057 |
| 3 | 0.40 | 7.000 | 7 | 0.400000 | 0 | 0 |
| | | | | | **合计** | **0.8822** |

（`3.500` 是一个标准的"最坏情况"：正好卡在两个格点中间，按就近取偶进到 4，误差达到 scale/2 的上限。）

**AWQ：把通道 0 放大 s = 1.75 倍**（同时激活侧除以 1.75，和 SmoothQuant 一样是等价变换）：

```
w′ = [ 0.20 × 1.75 , 0.31 , −0.24 , 0.40 ] = [ 0.35 , 0.31 , −0.24 , 0.40 ]

关键检查：max|w′| = 0.40，没变！   ← 0.35 < 0.40，所以 scale 保持 0.0571429
                                      其余三个通道一点也没受影响
```

| i | w′[i] | w′/scale | q | 反量化 | 除回 s 后的 ŵ | 误差 Δ | 加权输出误差 |
|---|---|---|---|---|---|---|---|
| 0 | 0.35 | 6.125 | 6 | 0.342857 | 0.342857/1.75 = **0.195918** | −0.004082 | **0.1224** |
| 1 | 0.31 | 5.425 | 5 | 0.285714 | 0.285714 | −0.024286 | 0.0194 |
| 2 | −0.24 | −4.200 | −4 | −0.228571 | −0.228571 | +0.011429 | 0.0057 |
| 3 | 0.40 | 7.000 | 7 | 0.400000 | 0.400000 | 0 | 0 |
| | | | | | | **合计** | **0.1475** |

```
加权输出误差：  0.8822  →  0.1475        好了 6.0 倍
而且：其余三个通道的误差一个字节都没变 —— 因为组内最大值没被顶上去
```

> ★ **AWQ 的"免费午餐"是这么来的**：把一个权重乘以 s，它在量化格子里占据的格数从 3.5 变成 6.125，**舍入时丢掉的那个零头相对它自己就小了**；反量化后再除以 s，误差也跟着缩小到 1/s 附近。**只要放大后的值没有成为组内新的最大值，这件事就是纯赚的。** 一旦顶上去了，整组的 scale 就变大，所有通道一起变差——这就是 s 不能随便取大的原因。

> ⚠️ **本例的 6 倍改善偏乐观**，因为 `w[0] = 0.20` 恰好卡在最坏的半格点上。论文里的 s 是按 `s = (逐通道平均 |x|)^α` 生成、α 在 `[0, 1]` 上网格搜索、以**真实的层输出误差**为目标选出来的，典型改善没这么夸张。但**方向和机理是对的**：显著通道的误差降到约 1/s。

### 6.7.4 AWQ vs GPTQ：一张对照表

| | GPTQ | AWQ |
|---|---|---|
| 用什么信息决策 | Hessian（XᵀX），**二阶 + 通道间相关** | 逐通道 mean\|x\|，**一阶 + 通道独立** |
| 怎么改权重 | **逐列误差补偿**：改变权重的数值 | **等价缩放**：数学上不改变这一层的函数 |
| 是否需要重构/反传 | 需要逐层最小化重构误差 | **不需要**，只要一遍前向统计 |
| 是否会过拟合校准集 | **会**（在显式拟合校准集） | 不太会（论文强调跨域/跨模态泛化好） |
| 量化速度 | 慢（要求 Hessian 的逆） | 快 |
| 权重排布 | 开 act_order 后不连续，kernel 要多一层索引 | 保持连续，kernel 友好 |
| INT4 精度（同 group size） | 相当 | 略好，小模型上更明显 |

> ★ **一句话概括两者的分工**：**GPTQ 问的是"改动这个权重会让输出错多少，能不能用别的权重补回来"；AWQ 问的是"这个权重会被多大的激活放大，要不要事先把它放大保护起来"。** 前者是修正，后者是预防。两者不冲突，工程上也有把 AWQ 的缩放和 GPTQ 的补偿叠在一起用的做法。

## 6.8 量化 kernel：工程上要处理的四件事

### 6.8.1 W8A8 INT8 GEMM：scale 在哪一步乘

```
从 HBM 读进来
  ├── X_int8   激活，已量化
  ├── W_int8   权重，已量化（离线做好）
  ├── s_X      每个 token 一个标量（per-token）
  └── s_W      每个输出通道一个标量（per-channel）
       │
       ▼
片上：① INT8 Tensor Core 做 MMA，累加器是 INT32
       │
       ▼
片上：② Epilogue（收尾，见 05 章 §5.3.3）里做反量化
       │     Y_fp16[i,j] = Y_int32[i,j] * s_X[i] * s_W[j]
       │     s_X[i] 只跟行有关，s_W[j] 只跟列有关
       │     → 这是一个外积形式，等累加全部结束之后乘一次就行，几乎免费
       ▼
写回 HBM：③ 转成 BF16/FP16 写出 Y
```

> ★ **"per-token 激活 scale × per-channel 权重 scale"这个组合之所以是业界标配，是因为它在 Epilogue 里退化成一个外积。** `s_X` 只跟行有关、`s_W` 只跟列有关，两者都在累加**结束之后**才参与，一次乘法搞定。这也回答了 §6.2.5 那个问题：为什么廉价的粒度偏偏是 per-token 和 per-channel。

> ⚠️ **INT32 累加器不会溢出，但要会算。** 最坏情况：`|q| ≤ 127`，K = 4096，那么 `|Σ q_x·q_w| ≤ 127 × 127 × 4096 = 6.6e7`，而 INT32 的上限是 2.1e9 —— 有 32 倍余量，安全。但如果 K 达到 13 万以上就有风险了，这在超长序列的某些归约里真的会出现。

### 6.8.2 per-group scale 的麻烦：它在 K 循环里面

```
per-tensor / per-channel scale：   scale 只跟输出位置有关
      → 整个 K 循环跑完再乘一次       ✓ Epilogue 就够了

per-group scale（沿 K 方向分组）：  scale 在 K 循环中途就变了
      → for k_block in range(K // 128):
            acc_partial = mma(X[:, k_block], W[k_block, :])   ← INT8/FP8 Tensor Core
            acc += acc_partial × s_X[k_block] × s_W[k_block]  ← 每 128 步就要乘一次
        ▲ 这一行必须在 CUDA Core 上做，Tensor Core 干不了
```

这正是 DeepSeek 的 FP8 方案（§6.5.3）要自己写 GEMM（DeepGEMM）的原因，也正好和它的"每 128 个元素提升到 FP32 累加一次"合并成同一次操作——**两个需求撞在同一个位置，所以代价可以共享。**

### 6.8.3 W4A16：反量化放在 Prologue

W4A16（GPTQ / AWQ 的标准部署形态）的计算图和 W8A8 完全不同：

```
从 HBM 读进来
  ├── W_int4   两个 INT4 挤在一个字节里（packed）
  ├── scale    每 128 个权重一个
  └── zp       每 128 个权重一个
       │        ★ 全部收益都在这一步：读进来的字节少了 3.85 倍
       ▼
片上：② Prologue（前置）反量化
       │     unpack 出 INT4 → 减 zp → 乘 scale → 转成 BF16
       │     只涉及位运算和逐元素乘加，跑在 CUDA Core 上
       ▼
片上：③ BF16 Tensor Core 做 MMA（和普通 GEMM 一模一样）
       │     激活全程是 BF16，从没量化过
       ▼
写回 HBM：④ 正常写出 Y_bf16
```

> ★ **这里和 [05 章 §5.4 反例 1](05-算子融合.md) 表面矛盾，实际不矛盾，值得对照着看。** 05 章说"Prologue 融合通常做不到"，因为 LayerNorm 需要**看到完整的一行**才能算均值，而 GEMM 是分块读数据的。但**反量化是纯逐元素的**——一个权重的反量化只需要它自己和它那一组的 scale，不需要看见任何别的元素。按 05 章判据①，它属于"一对一"那一类，**最容易融的一类**。

**unpack 的位运算长这样**（两个 INT4 挤在一个字节里）：

```
  一个 uint8:   [ b7 b6 b5 b4 | b3 b2 b1 b0 ]
                 ▲ 高 4 位      ▲ 低 4 位
                 = 权重 2i+1     = 权重 2i

  lo = (byte     ) & 0x0F        取低 4 位
  hi = (byte >> 4) & 0x0F        取高 4 位
  值 = (lo − zero_point) × scale
```

> ⚠️ **W4A16 的加速比取决于反量化能不能被藏起来。** batch = 1 时 Tensor Core 几乎全空着，反量化在 CUDA Core 上跑完全不占用它，是免费的；batch 一大，反量化的工作量（正比于权重个数，和 batch 无关）被摊薄的同时 GEMM 的时间在涨，反而可能变成新瓶颈。**Marlin、Machete 这类 W4A16 专用 kernel 的全部技巧，就是把 unpack 和反量化用最少的指令做完、并和 Tensor Core 流水重叠起来。**

### 6.8.4 INT4 在 H100 上没有硬件：一个会静默变慢的坑

```
Turing / Ampere（sm_75 / sm_80）：
    有原生 INT4 MMA，PTX 的 mma.s4 会编译成真正的 IMMA.16832.S4.S4 指令

Hopper（sm_90）：
    ✅ 已在 CUDA 文档中弃用并移除 —— wmma 的 experimental::precision::s4 / u4 / b1
    ⚠️ 但 PTX 的 mma.s4 为了前向兼容仍然能编译通过，
       只是被翻译成一串 IMAD（跑在 CUDA Core 上）或用 INT8 MMA 模拟
    ⚠️ wgmma 指令（Hopper 的主力矩阵指令）压根不支持 INT4

Blackwell（sm_100）：
    重新引入了低精度浮点 FP4 / FP6（NVFP4、MXFP4），走的是块缩放（block-scaled）路线，
    不是回到 INT4
```

> ⚠️ **这是一个静默性能坑**：在 H100 上跑一个依赖 `mma.s4` 的 kernel，**不会报错、不会拒绝编译**，只会悄悄失去 Tensor Core 加速。所以在 Hopper 上，**INT4 的价值 100% 在"权重存储和带宽"，0% 在"算力"**——W4A16 的名字本身就说明了这一点：A 那一侧是 16 位，因为计算一定要回到 FP16/BF16。

### 6.8.5 KV Cache 量化：另一个战场

Decode 阶段除了权重，KV Cache 也在 HBM 里反复读。长上下文时它甚至会超过权重：

```
LLaMA-3-70B（80 层，8 个 KV head，head_dim = 128），FP16 KV Cache：
    每 token 每层 = 2（K 和 V）× 8 × 128 × 2 字节 = 4096 字节 = 4 KB
    每 token 全模型 = 4 KB × 80 = 320 KB
    32K 上下文、batch = 8：320 KB × 32768 × 8 = 84 GB       ← 比权重（138 GB FP16）同量级

    量化成 INT8：42 GB，量化成 INT4：21 GB
```

KV Cache 量化和权重量化的关键差别：**它是在线产生的，没有离线校准的机会。** 所以通常用最简单的 per-token（甚至 per-head-per-token）对称量化，量化和反量化都融进 Attention kernel 里。细节见 [09 章 §9.2](09-推理侧算子.md)。

## 6.9 量化方案选型速查

| 方案 | 权重 | 激活 | 带宽收益 | 算力收益 | 校准 | 精度损失 | 最适合的场景 |
|---|---|---|---|---|---|---|---|
| BF16 基准 | 16 bit | 16 bit | 1× | 1× | 不需要 | 无 | 训练、精度优先 |
| **FP8 E4M3** | 8 bit | 8 bit | 2× | **2×** | 在线或少量 | 极小 | **H100 训练**、高吞吐推理 |
| **W8A8 + SmoothQuant** | INT8 | INT8 | 2× | **2×** | 需要（小量） | 小 | 生产推理，大 batch，A100/H100 |
| **W8A16** | INT8 | 16 bit | 权重 2× | 1× | **不需要** | 极小 | 显存受限、最保守、最快落地 |
| **W4A16 GPTQ** | INT4 g128 | 16 bit | 权重 **3.85×** | 1× | 需要 | 中 | 端侧 / 单卡 / batch 小 |
| **W4A16 AWQ** | INT4 g128 | 16 bit | 权重 **3.85×** | 1× | 需要 | 中（略优于 GPTQ） | 同上，尤其是小模型和多模态 |

**决策流程**：

```
① 你的 batch 大不大？
     batch ≲ 90（Decode / 端侧 / 单用户）
         → 瓶颈是带宽，优先选位宽最低的：W4A16（AWQ 或 GPTQ）
     batch ≳ 345（Prefill / 训练 / 高吞吐服务）
         → 瓶颈是算力，只有 FP8 / W8A8 有用；W4A16 只剩显存收益
     中间地带
         → 两条都试，实测定夺
     （90 和 345 的来历见 §6.1.3，是按 4096×4096 GEMM 算出来的，换形状要重算）

② 有没有 FP8 硬件？
     H100 / H200 / B200      → FP8 优先，尤其是训练
     A100 / V100 / 昇腾 910B → 没有 FP8，走 INT8 路线（昇腾见 §6.10）

③ 要不要量化激活？
     不要（W8A16 / W4A16）   → 简单、无校准、风险低，拿走 Decode 大部分收益
     要（W8A8 / FP8）        → 必须先处理离群值（SmoothQuant 或等价手段），
                               且必须用业务相关的真实数据校准

④ 精度掉了怎么办（按投入从低到高）
     a. 把敏感层排除（lm_head、首尾各若干层）—— 最有效、最便宜的一招
     b. 细化粒度：per-tensor → per-channel → per-group(128) → per-group(32)
     c. 换算法：RTN → AWQ → GPTQ（或叠加）
     d. 加 SmoothQuant / 提高 α
     e. 上 QAT（要改训练流程，见 11 章 §11.2.2）
```

> ★ **步骤 ④ 的 a 永远先试。** `lm_head` 和头尾几层贡献了绝大部分的量化敏感度，把它们留在 BF16 只多占几百 MB，却常常能把掉下去的精度救回来大半。所有量化工具都提供这个开关（HuggingFace 系叫 `modules_to_not_convert`，昇腾 msModelSlim 叫 `disable_names`）。

## 6.10 在昇腾上：一条没有 FP8 的量化路线

> 本节需要 [12 章](12-昇腾硬件基础.md) 的硬件背景。只关心 GPU 可以跳过。

§6.5 讲的 FP8 是 H100 时代的主流答案：Hopper 的 Tensor Core 原生支持 E4M3/E5M2，DeepSeek-V3 用它做了 FP8 训练。**昇腾 910B/910C 这一代没有 FP8 硬件支持**（✅），于是整条技术路线不同：

```
NVIDIA 路线：BF16 训练 → FP8 训练/推理 → 更低比特
             硬件原生支持，配 per-tensor / per-block scale

昇腾 910B/C： BF16 训练（不变）
             推理走 INT8（W8A8）  ← 主力
             FP8 要等下一代硬件（HiF8）
```

这意味着 §6.5 的 FP8 方案在昇腾上**不可直接迁移**，要退回 §6.4 的 W8A8（SmoothQuant 路线）或 BF16。这是迁移时最先撞上的硬约束之一。

### 6.10.1 W8A8：昇腾推理量化的主力

工具是 **msModelSlim**（MindStudio ModelSlim，昇腾的模型压缩工具链）。它做的事和 §6.4 的 SmoothQuant + §6.6 的 PTQ 校准是同一套思路：

```python
from msmodelslim.pytorch.llm_ptq.anti_outlier import AntiOutlierConfig, AntiOutlier
from msmodelslim.pytorch.llm_ptq.llm_ptq_tools import Calibrator, QuantConfig

# ① 异常值抑制 —— 对应 §6.4 讲的 SmoothQuant
#    激活里的离群值会把量化 scale 撑大（§6.3 算过：一个 100 倍的值能让误差恶化 26 倍），
#    先把"难度"从激活等价地搬到权重上
anti_cfg = AntiOutlierConfig(anti_method="m2")      # 工具提供 6 种算法
anti = AntiOutlier(model, calib_data=calib_data, cfg=anti_cfg)
anti.process()

# ② 量化配置
quant_cfg = QuantConfig(
    w_bit=8, a_bit=8,
    disable_names=[...],      # 敏感层排除，通常是 lm_head 和首尾若干层（§6.9 步骤 ④a）
    dev_type="cpu",
    act_method=3,             # 激活量化的校准方法
    mm_tensor=False,          # False = per-channel（对应 §6.2.4 的粒度选择）
)

# ③ 校准并保存
calibrator = Calibrator(model, quant_cfg, disable_level="L0")
calibrator.run()
calibrator.save(save_path)
```

三个实践要点：

- **校准数据量极小（10～50 条），但必须是业务相关的真实数据。** 用通用语料校准、上线跑专业领域，精度会掉。这一点和 §6.6 讲的 GPTQ 校准集选择是同一个道理（GPTQ 会过拟合校准集），但昇腾工具链对数据量的要求更低。
- **`disable_names` 是主要调参旋钮。** 哪些层不量化，直接决定精度-性能的取舍。和 §6.9 的选型表配合使用。
- **CANN 版本决定安装方式**：8.0.RC3 及之前，msModelSlim 内置在 CANN 包里；之后的版本要单独装开源版。用新 CANN 却按老文档调内置模块会找不到，这是高频踩坑点。

除 W8A8 外，昇腾还提供 W8A8SC（稀疏量化）、KV Cache 量化（对应 §6.8.5 和 [09 章 §9.2](09-推理侧算子.md) 的 KV Cache 显存压力）、W8A16 / W4A8 等组合。

### 6.10.2 HiFloat8：一个值得关注的不同答案

§6.5.1 摆出过 FP8 的核心矛盾：E4M3 精度高但动态范围只有约 2¹⁵，E5M2 范围大到 2³⁰ 但每个数量级只剩 4 个刻度。二选一都不够用，所以必须配缩放因子（scale），而 scale 的管理本身就是工程负担——DeepSeek-V3 的 FP8 方案（§6.5.3）有相当一部分复杂度花在这上面。

华为的 **HiF8**（HiFloat8，华为自研的 8 位浮点格式）换了个思路（⚠️ 以下为华为技术材料口径）：

```
传统 FP8：指数位/尾数位的划分固定（E4M3 或 E5M2 二选一）

HiF8：引入「点位域（Dot）」，用即时可译的变长前缀码编码
  → 同一种格式内，不同数量级的数自动采用不同的指数/尾数划分
  → 单一格式覆盖更宽的动态范围
  → 推理时可用 Per-Tensor 甚至 Scale-Free 的粗粒度量化
  → 省掉 Per-Token / Per-Channel / Per-Block 的 scale 管理开销
```

**但华为自己公布的精度对比值得注意**（⚠️ 华为技术博客，openPangu-7B 权重量化的 SQNR 排序）：

```
INT8 (per-channel) > HiF8 (scaled) ≈ MXFP8 (E4M3) > E4M3 > E5M2 > HiF8 (裸格式)
       ▲ 排第一                                                    ↑ 垫底
```

华为给出的解释是：HiF8 的设计初衷是捕捉**训练中跨数量级波动的梯度**，而静态权重呈类高斯的集中分布，HiF8 在密集区间可用的量化阶反而更少。

> ★ **这个排序正好印证了 §6.5.2 的那条 ⚠️：FP8 不是"总是比 INT8 准"。** 权重是静态的、分布集中的、可以慢慢做 per-channel 校准的——这正是 INT8 的主场。FP8 的主场是**动态范围跨数量级的量**（梯度、某些激活），那里 INT8 无论怎么细粒度都救不回来。**选格式看的是张量的分布形状，不是位宽数字谁更时髦。**

这个坦率的自评很有参考价值：**HiF8 的定位是训练侧（梯度），不是推理侧的权重量化**。如果你的场景是推理部署，回到 §6.10.1 的 W8A8 per-channel 仍是昇腾上的稳妥选择。

HiF8 算法已在 CANN 社区开源（AMCT 工具链），并提供跨平台伪量化仿真库——**可以在 GPU 上先验证精度再上昇腾**，这对评估阶段很实用。

## 6.11 本章小结

**一句话**：量化减少的是**字节**，不是 FLOP。它买到的是显存和带宽；只有在硬件有对应低精度算力、且算子确实是 Compute Bound 的时候，才顺带买到算力。

**核心账本（§6.1，全章骨架）**

| | 权重位宽 | LLaMA-3-8B 权重 | Decode 理论上界 | 相对 BF16 |
|---|---|---|---|---|
| BF16 | 16 | 16.06 GB | ⚠️ 4.79 ms/token | 1× |
| INT8 | 8 | 8.03 GB | ⚠️ 2.40 ms/token | 2× |
| INT4 g128 | **4.156** | 4.17 GB | ⚠️ 1.25 ms/token | **3.85×** |

```
★ 量化把算术强度翻倍，但也把屋脊点翻倍 —— 算子在屋顶线上的相对位置不变，
  只是搬的字节少了，所以时间变短。收益 100% 来自字节，0% 来自"算得更快"。

★ 收益随 batch 消失：4096×4096 的 GEMM，M ≳ 90 时 INT4 触顶，
  M ≳ 345 时连 BF16 都是 Compute Bound，量化只剩显存收益。
```

**误差的三个来源和它们的量级（§6.2–§6.3，那 8 个数的结论）**

| 来源 | 机理 | 本章的数值证据 |
|---|---|---|
| **小数值的相对误差** | 绝对误差恒为 scale/2，数越小相对误差越大 | 0.05 的相对误差 20%，3.81 的是 0% |
| **离群值** | scale 由单点 max 决定，它涨多少倍误差就涨多少倍 | 一个 100 倍的值让其余元素 RMSE 恶化 **26 倍**，8 bit 退化成 2.6 bit |
| **粒度太粗** | 一组里的最大值绑架整组 | per-tensor 0.0079 → per-channel 0.0068 → per-group(2) 0.0040 |

**两个结构性事实（本章最该带走的）**

```
① 激活的离群值沿【通道】分布，而 GEMM 里廉价的 scale 方向是【token】。
   要的和能给的错开一个维度 —— 这是 SmoothQuant 存在的全部理由。

② 权重的 per-channel 是廉价的（scale 提到 Epilogue 外面就行）。
   所以"把难度从激活搬到权重"总是划算的。
```

**四种方案，各自用什么信息**

| | 用什么信息 | 怎么用 | 改不改函数 |
|---|---|---|---|
| RTN | 什么都不用 | 直接四舍五入 | 改（有误差） |
| **SmoothQuant** | 激活的逐通道 max | 等价缩放，把难度移给权重 | **不改（数学等价）** |
| **GPTQ** | 校准数据的 Hessian（二阶） | 逐列量化 + 误差补偿给后面的列 | 改（但输出更准） |
| **AWQ** | 激活的逐通道平均幅度（一阶） | 等价缩放，放大显著通道 | **不改（数学等价）** |

**工程要点（§6.8）**

```
per-token × per-channel 的 scale = Epilogue 里一个外积，几乎免费
per-group（沿 K）的 scale       = 必须进 K 循环，得自己写 GEMM（DeepGEMM）
W4A16 的反量化                  = Prologue，逐元素，好融（和 05 章反例 1 不矛盾）
INT4 在 Hopper 上没有 Tensor Core = 静默退化成 CUDA Core，别指望算力收益
FP8 在 Hopper 上累加只有 14 bit  = K=4096 时误差可达 2%，必须周期性提升到 FP32
```

**自测三题**

1. 对 `x = [−1.20, 0.35, 2.54, −0.07]` 做 per-tensor 对称 INT8 量化（round 用"就近取偶"）。① 算出 scale、每个元素的 q、反量化值、绝对误差和相对误差。② 把 `2.54` 换成 `254.0`（其余不变）重算一遍，指出哪些元素被抹成了 0，以及正常元素的最大绝对误差变成了原来的多少倍。
2. 某模型 76.2 亿参数，权重用 INT4 / group = 128，scale 存 FP16、zero-point 存 INT4。① 实际平均位宽是多少？② 权重占多少 GB？③ 在 H100（HBM 3.35 TB/s）上，Decode 每步的理论下界是多少毫秒、对应多少 token/s？④ 相对 BF16 是几倍？
3. 某层的某个输入通道 j，校准后 `max|X[:, j]| = 128`，`max|W[j, :]| = 0.5`。① 取 α = 0.5，算出 SmoothQuant 的 `s_j`，以及迁移后激活和权重在该通道上的最大值各是多少。② 改成 α = 0.75 再算一遍。③ 用一句话说明 α 从 0.5 调到 0.75 意味着什么。

#### 参考答案

1. **① 基准**：`max|x| = 2.54`，`scale = 2.54 / 127 = 0.02`。`−1.20/0.02 = −60 → q = −60 → −1.20`，误差 0；`0.35/0.02 = 17.5`，就近取偶进到 **18** → `0.36`，误差 **+0.01（相对 2.9%）**；`2.54/0.02 = 127 → q = 127 → 2.54`，误差 0；`−0.07/0.02 = −3.5`，就近取偶到 **−4** → `−0.08`，误差 **−0.01（相对 14.3%）**。注意同样是 0.01 的绝对误差，在 0.07 上就是 14.3%，在 2.54 上是 0——这就是 §6.2.1 那条结论。**② 加离群值**：`max = 254`，`scale = 2.0`。`−1.20/2 = −0.6 → q = −1 → −2.00`，误差 **−0.80**；`0.35/2 = 0.175 → q = 0 → 0`，**被抹成 0**，误差 −0.35；`254 → 127 → 254`，误差 0；`−0.07/2 = −0.035 → q = 0 → 0`，**被抹成 0**，误差 +0.07。正常元素的最大绝对误差从 0.01 涨到 0.80，**80 倍**（scale 从 0.02 涨到 2.0 也正好是 100 倍的量级）。参见 §6.2.1、§6.3.1。
2. **①** 每 128 个权重存 `128 × 4 bit = 64 B` 权重 + `2 B` scale + `0.5 B` zero-point = **66.5 B**，平均 `66.5 × 8 ÷ 128 = **4.15625 bit**`。**②** `7.62e9 × 4.15625 ÷ 8 = 3.959e9 字节 = **3.96 GB**`。**③** `3.959e9 ÷ 3.35e12 = 1.182e−3 s = **1.18 ms/token**`，对应 `1 ÷ 0.001182 ≈ **846 token/s**`（⚠️ 理论上界，忽略 KV Cache、激活、反量化和带宽利用率）。**④** BF16 权重 `7.62e9 × 2 = 15.24 GB`，耗时 `4.55 ms`，比值 `4.55 ÷ 1.18 = **3.85 倍**`——也等于 `16 ÷ 4.15625`，和模型大小无关。参见 §6.1.1、§6.2.6。
3. **① α = 0.5**：`s_j = √128 ÷ √0.5 = 11.3137 ÷ 0.70711 = **16.0**`。迁移后激活最大值 `128 ÷ 16 = **8**`，权重最大值 `0.5 × 16 = **8**`——两者相等，等于几何平均数 `√(128 × 0.5) = √64 = 8` ✓。**② α = 0.75**：`s_j = 128^0.75 ÷ 0.5^0.25 = 2^5.25 ÷ 2^(−0.25) = 38.055 ÷ 0.8409 = **45.25**`。激活最大值 `128 ÷ 45.25 = **2.83**（= 2^1.5）`，权重最大值 `0.5 × 45.25 = **22.63**（= 2^4.5）`。**③** α 调大 = **把更多量化难度推给权重**：激活变得更好量化（8 → 2.83），代价是权重的动态范围被撑大 2.8 倍（8 → 22.63）。顺手验证一下守恒律：`8 × 8 = 64`，`2.83 × 22.63 = 64` ✓——难度只是在两边之间挪，总量不变。离群值特别凶的模型需要更大的 α；但推过头会把权重也搞崩，判据是端到端精度而不是任何一侧的最大值。参见 §6.4.3、§6.4.4。

> **下一章**：本章的 kernel 都是"概念上写得出来、工程上很难写好"的——per-group scale 要塞进 K 循环、反量化要和 MMA 流水重叠、INT4 要 unpack。用 CUDA 写这些要几百行，用 Triton 写要几十行。见 [07 · Triton 编程](07-Triton编程.md)。

> **昇腾对照**：910B/910C 没有 FP8 硬件，整条低精度路线要退回 INT8 W8A8，工具是 msModelSlim；华为的 HiF8 是另一条思路但定位在训练侧。见本章 §6.10，以及 [12 章](12-昇腾硬件基础.md)（硬件）、[14 章](14-GPU到NPU迁移实战.md)（迁移 checklist：量化产物不能直接搬，必须在昇腾上重新校准）。
