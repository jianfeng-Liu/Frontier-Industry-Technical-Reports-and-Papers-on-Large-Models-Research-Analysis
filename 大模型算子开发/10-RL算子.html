10 · RL 算子：训练循环里的推理算子与训练算子如何共存

前置：03 章（GEMM）、04 章（FlashAttention）、09 章（推理侧算子）
目标：搞清楚 PPO/GRPO 的计算图里有哪些算子、每个算子的形状特征和性能瓶颈，以及为什么同一个 GPU 上同时跑推理算子和训练算子会带来独特的工程难题。

本章关键词

Rollout（展开采样）—— RL 训练的数据生成阶段，用当前策略模型（Actor）自回归生成回答序列，算子形态和推理 Decode 完全相同。
LogProb（对数概率）—— 对生成序列里每个 token 计算模型输出的对数概率，PPO loss 的核心输入，比 Decode 时的 argmax 代价高。
GAE（Generalized Advantage Estimation，广义优势估计）—— 沿时间步做带折扣的 TD 误差累加，估计每步动作的相对价值，有顺序依赖，难以并行。
PPO clip（近端策略优化裁剪）—— min(ratio·A, clip(ratio, 1±ε)·A)，element-wise 操作，算力开销极小但实现细节影响训练稳定性。
GRPO（Group Relative Policy Optimization，组内相对策略优化）—— 去掉 Value Model，用同一个 prompt 生成多个回答的相对奖励代替 GAE，减少一个模型但改变了批次形状。
Weight Offload（权重卸载）—— 把暂时不用的模型权重从 GPU HBM 搬到 CPU DRAM，释放显存给当前阶段使用，代价是 PCIe 传输延迟。
重要性采样（Importance Sampling, IS）—— 用推理时的概率和训练时的概率之比修正离策略偏差，当两者相差太大时裁剪比值防止梯度爆炸。

10.1 RL 训练循环的两阶段结构

标准 PPO 的训练循环由两个截然不同的阶段交替组成：

┌─────────────────────────────────────────────────────────┐
│                    一个 PPO Iteration                    │
│                                                         │
│  阶段一：Rollout（数据生成）                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │  Actor 模型          推理 Decode × N steps      │   │
│  │  Reference 模型      推理 Prefill（算 log_prob）  │   │
│  │  Reward/Value 模型   推理 Prefill（打分）         │   │
│  └─────────────────────────────────────────────────┘   │
│           ↓ 收集 (token_ids, logprobs, rewards, values) │
│                                                         │
│  阶段二：Policy Update（参数更新）                       │
│  ┌─────────────────────────────────────────────────┐   │
│  │  Actor 模型   训练 Prefill + Backward + Optimizer│   │
│  │  Value 模型   训练 Prefill + Backward（可选）     │   │
│  └─────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘

关键矛盾：Rollout 阶段要用推理引擎（追求低延迟、高吞吐、KV Cache），Policy Update 阶段要用训练引擎（追求高 GPU 利用率、激活存储、梯度计算）。两者对显存的需求模式完全不同，必须通过 weight offload 或 worker 分离来协调。

10.2 Rollout 阶段的算子图

Rollout 的核心是 Actor 模型的自回归 Decode，算子形态和第 09 章的推理 Decode 完全相同，但额外需要：

10.2.1 LogProb 收集

普通推理只做 argmax，不需要完整的 softmax 概率。但 PPO 需要知道每个已生成 token 的精确对数概率：

# 普通推理（Greedy Decode）
logits = model(x)           # (batch, vocab_size)
token = logits.argmax(-1)   # 只取最大值，O(V) 比较

# RL Rollout 需要的 LogProb
logits = model(x)           # (batch, vocab_size)，V ≈ 128K
log_probs = F.log_softmax(logits, dim=-1)   # ← 全词表 softmax！
token_logprob = log_probs[range(batch), token_ids]  # 取生成 token 的概率

# 代价差异：
#   argmax：O(V) 比较，不需要 exp，延迟极低
#   log_softmax：O(V) 的 exp + sum + log，内存读写量是 argmax 的 3-4×
#   V=128K 时，logits 矩阵 = 128K × sizeof(BF16) = 256 KB / token

性能影响：LogProb 收集把 Decode 的内存带宽需求提高了约 3-4 倍。对于批量处理，每个 token 生成后都需要完整读写一遍词表，词表越大（LLaMA-3 128K、Qwen 152K）这个开销越显著。

10.2.2 Reference Model 的 LogProb

PPO 需要同时知道 Actor 和 Reference Model 对同一序列的 log_prob，用于计算 KL 散度。Reference Model 不需要 Decode，只做 Prefill Forward（把已生成序列一次性过一遍）：

Reference Model 的计算模式：
  输入：完整生成序列 (B, T)，T = prompt_len + response_len
  模式：Prefill（T 步一次性），不是逐 token Decode
  形状：M = B × T，当 T=512 时 M=512，接近 Compute Bound

  相比 Actor 的 Decode（M=1）：
  Reference Prefill 的算术强度高约 T 倍，GPU 利用率好得多

如果 Actor 和 Reference 共享同一个 GPU，通常的策略是：
- Actor 做 Decode 时，Reference 等待（显存冲突）
- Actor Decode 完一批序列后，Reference 对整批序列做 Prefill

10.2.3 Reward/Value Model

和 Reference 类似，也是 Prefill 模式，但可能是不同大小的模型（Value Model 通常比 Policy 小）。

10.3 Policy Update 阶段的算子图

Policy Update 的算子流：

① Re-forward（重新前向）
   输入：Rollout 生成的序列 (B × T_max, H)
   模式：Prefill，Compute Bound（如果 B×T 够大）
   注意：这是第二次跑 Actor 的前向，用于精确计算 π_new 的 log_prob

② Log_prob 差值 → ratio 计算（element-wise）
   ratio = exp(log_prob_new - log_prob_old)   ← log_prob_old 是 Rollout 时存的
   代价：O(B × T)，极小

③ GAE 计算（CPU 或 GPU sequential）
   advantage[t] = δ_t + γλ·advantage[t+1]
   δ_t = reward[t] + γ·value[t+1] - value[t]
   注意：这个递推有时间步顺序依赖，不能并行化！
   实践上：在 GPU 上用 for 循环或 scan 算，或者搬到 CPU 做

④ PPO Loss（element-wise）
   loss = -min(ratio·A, clip(ratio, 1-ε, 1+ε)·A)
   再加 Value Loss 和 KL 惩罚项

⑤ Backward
   和标准训练 Backward 相同，但 loss 形状是 (B × T)
   GEMM 形状同 Forward，梯度 dW 的形状是 (B × T, H)

⑥ AdamW 更新
   读 grad + m + v，写 param + m + v
   4 × param_count × 4 Bytes（FP32 状态）

GAE 的串行性问题

GAE 是 Policy Update 里最难并行化的算子：

# 正向写法（不能并行）：
advantages = torch.zeros(T, batch_size)
last_gae = 0
for t in reversed(range(T)):
    delta = rewards[t] + gamma * values[t+1] - values[t]
    advantages[t] = last_gae = delta + gamma * lam * last_gae

# 等价的 parallel scan 写法（可以 GPU 并行，但实现复杂）：
# 本质是把递推关系写成 (a[t], b[t]) 的仿射变换，用 prefix scan 并行
# advantages[t] = sum_{k=t}^{T-1} (γλ)^{k-t} * delta[k]
# 展开成 parallel prefix sum 后可以 O(log T) 并行

实际工程里大多数框架直接在 CPU 上跑 GAE（序列长度通常 ≤ 2048，CPU 速度够用），避免实现 GPU scan。veRL 和 OpenRLHF 都是这样处理的。

10.4 GRPO 对算子图的影响

GRPO（DeepSeekMath、DeepSeek-R1 使用）去掉了 Value Model，改变了批次结构：

PPO 的 batch 形状：
  (B prompts) × (1 response per prompt)
  GAE 需要 Value Model 的输出

GRPO 的 batch 形状：
  (B prompts) × (G responses per prompt)，G 通常为 8-16
  优势估计 = (reward - mean(rewards)) / std(rewards)，组内归一化
  不需要 Value Model，不需要 GAE

算子层变化：

方面 PPO GRPO
模型数量 Actor + Reference + Reward + Value = 4 个 Actor + Reference + Reward = 3 个
Batch 形状 (B, T) (B×G, T)，G 倍扩展
GAE 需要，有顺序依赖 不需要，换成组内 mean/std
GEMM M 维 B×T B×G×T（G=8 时 8 倍）
优势估计算子 递推，串行 mean + std + element-wise，完全并行
Value loss 需要，多一次 Backward 没有

GRPO 的最大算子层优势是把串行的 GAE 换成了全并行的组内统计，而且批次更大，GEMM 形状更接近 Compute Bound。缺点是每个 prompt 要生成 G 个回答，Rollout 阶段的计算量是 PPO 的 G 倍。

10.5 多模型显存竞争

RL 训练里同时需要多个模型，是推理和训练里都没有的场景：

PPO 四模型的显存需求（以 LLaMA-3 70B 为例，BF16）：

Actor（要做 Backward）：
  权重  = 70B × 2B = 140 GB
  激活存储（序列长 T=1024）≈ 40 GB（含 KV cache 和 attention 中间值）
  梯度 ≈ 140 GB（和权重等大）
  Adam 状态（FP32）≈ 280 GB（m + v）
  合计：~600 GB

Reference（只做 Prefill，不需要梯度）：
  权重 = 140 GB
  无梯度，无 Adam 状态

Reward Model（通常较小，如 7B）：
  权重 ≈ 14 GB

Value Model（通常和 Actor 同大）：
  权重 = 140 GB + 梯度 + Adam ≈ 420 GB

H100 单卡 80 GB，8 卡合计 640 GB → 还是不够！

解法分三层：

① Rollout/Update 时间分离 + Weight Offload

Rollout 阶段：
  - Actor 权重在 GPU（Decode 用）
  - Reference 权重在 GPU（Prefill 用）
  - Value/Critic 权重 offload 到 CPU DRAM
  - Actor 的 Adam 状态 offload 到 CPU

Policy Update 阶段：
  - Actor 权重 + 梯度 + Adam 状态 全部在 GPU
  - Reference 权重 offload 到 CPU
  - Reward/Value 用完即卸载

Offload 带宽成本：
  PCIe 4.0 × 16 双向约 32 GB/s
  70B × 2B = 140 GB 上传/下载约需 4–5 秒
  → 每次权重切换会暂停 ~5 秒，这是 RL 训练吞吐低的直接原因之一

② Worker 分离（推理 Worker + 训练 Worker）

把 Rollout 和 Policy Update 放到不同的 GPU 组：

Rollout Workers（N 卡）：
  专跑 Actor Decode + Reference Prefill
  用 vLLM/SGLang，追求推理吞吐
  KV Cache 常驻

Training Workers（M 卡）：
  专跑 Policy Update
  用 Megatron/FSDP，追求训练 MFU

权重同步：
  Policy Update 完后，Training Workers 把新权重广播给 Rollout Workers
  同步量 = 模型大小，每次约 140 GB（分布在 NVLink 上）

这是 OpenRLHF、veRL、Slime 等框架的主流架构，代价是需要更多 GPU 和更复杂的调度逻辑。

③ 参数共享（Reference = frozen Actor）

Reference Model 权重和 Actor 完全相同，只是冻结不更新。可以通过权重共享节省一份显存：

# Reference 不保存单独副本，直接共享 Actor 的参数
with torch.no_grad():
    ref_logprobs = actor_model(input_ids)  # 用 no_grad 包住，当 Reference 用

这只在 Actor 权重变化不大（训练初期）时近似有效，不是精确的 Reference。DeepSeek-R1 的 GRPO 实现就是这样，因为它没有单独的 Reference Model。

10.6 LogProb 的批量计算优化

Rollout 结束后，Policy Update 的第一步是对整批生成序列重算 log_prob（Re-forward）。这是一个 Prefill 形状的 GEMM，批次较大，相对 Compute Bound。但有一个坑：

10.6.1 序列长度不均匀

Rollout 生成的序列长度各不相同（有的回答长，有的短）。直接 padding 到最大长度会浪费大量计算：

假设 batch=16，序列长度分布：
  2 条：512 tokens
  8 条：1024 tokens  
  4 条：2048 tokens
  2 条：4096 tokens

Padding 到 4096：
  实际计算量 = (2×512 + 8×1024 + 4×2048 + 2×4096) × H GEMM = ~30K 有效 tokens
  Padded 计算量 = 16 × 4096 × H GEMM = 65K tokens
  浪费 = 55%

varlen Prefill（FA2 的 varlen 模式）：
  把所有序列拼接成一条长序列，cu_seqlens 记录边界
  实际计算量 = 30K tokens，无浪费

最佳实践：Re-forward 阶段用 varlen Attention（flash_attn_varlen），按实际长度排序并打包，同时配合 Grouped GEMM 或 bucket 化策略处理不均匀的 FFN 形状。

10.6.2 Cross-Entropy 在大词表下的瓶颈

计算训练 loss 时需要对 logits 做 cross-entropy：

loss = F.cross_entropy(logits.view(-1, vocab_size), labels.view(-1))
# logits: (B×T, V)，V=128K 时是个 (B×T) × 128K 的矩阵

# 内存分析：
#   logits 读入：B×T × 128K × 2B = 当 B×T=16K 时 ≈ 4 GB
#   softmax exp：需要同样大小的中间矩阵
#   写出 loss：标量
#   实际上是 Memory Bound 的 element-wise 操作

解法：使用 Chunked Cross-Entropy，把词表维度分块计算，每次只把一块 logits 读入 SRAM：

# 分块，每次处理 vocab_chunk_size 个词
def chunked_cross_entropy(logits, labels, chunk_size=4096):
    batch_size, seq_len, vocab_size = logits.shape
    loss = 0
    max_logit = logits.max(dim=-1, keepdim=True)[0]  # 数值稳定

    for start in range(0, vocab_size, chunk_size):
        end = min(start + chunk_size, vocab_size)
        chunk = logits[..., start:end] - max_logit
        # 只计算这个块的 softmax 分母贡献
        ...

    # HBM 读取量从 B×T×V 降低到分块后的大小
    # 每个 chunk 复用 SRAM 里的 max_logit，减少重复读取

实际项目里常用 Flash Cross-Entropy（lm-cross-entropy 库），原理和 FlashAttention 类似：把词表维度分块，在 SRAM 里完成 exp+sum，不写中间矩阵到 HBM。

10.7 KL 散度的算子实现

PPO 的 KL 惩罚项：

# 精确 KL（需要完整 softmax）
kl = (prob_actor * (log_prob_actor - log_prob_ref)).sum(-1)  # 对词表求和

# 近似 KL（只用已生成 token 的 logprob，实践中更常用）
# 对每个已生成 token：
kl_approx = log_prob_actor - log_prob_ref  # element-wise，形状 (B, T)
kl_penalty = kl_approx.mean()

# 两者差别：
#   精确 KL：需要完整词表的概率分布，内存开销高
#   近似 KL：只用 token 级别的 log_prob 差，对 PPO 来说够用
#   Schulman 的近似：kl ≈ (ratio - 1) - log(ratio)，可以进一步避免 log 运算

在 RL 框架里，KL 散度本身是个 element-wise 算子，计算开销可忽略。真正的开销在于获取 log_prob_ref——这需要 Reference Model 的完整前向传播。

10.8 实测数字：PPO 各阶段耗时分布

以 LLaMA-3 8B，8×H100，batch=64 prompt，response=512 tokens 为例的粗略分布：

阶段 典型耗时占比 瓶颈
Actor Rollout（Decode） 45–55% Memory Bound（M=1 GEMM）
Reference LogProb（Prefill） 10–15% Compute Bound（M=512）
Reward 评分 5–10% Compute Bound
GAE 计算 <1% CPU 串行
Re-forward（Policy Update） 15–20% Compute Bound
Backward + Optimizer 10–15% Compute + Memory
权重同步（Worker 分离模式） 5–10% NVLink/PCIe 带宽

⚠️ Rollout（Decode）占了将近一半时间，而它的 GPU 利用率只有 1–5%。这是 RL 训练整体 MFU 远低于监督训练的根本原因。
提升 Rollout 吞吐是 RL 框架优化的第一优先级，主要手段是增大 Rollout batch size 和使用推理优化框架（vLLM/SGLang）。

10.9 本章小结

RL 训练的算子特征：

Rollout 阶段：
  = 推理 Decode（M=1，Memory Bound）
  + LogProb 收集（全词表 softmax，额外 3-4× 带宽）
  + Reference Prefill（M=T，Compute Bound，同时或串行）
  内存压力 = 3-4 个模型同时或轮流在 GPU 上

Policy Update 阶段：
  = Prefill Forward（Re-forward，Compute Bound）
  + GAE（CPU 串行递推，或 GPU parallel scan）
  + PPO clip（element-wise，可忽略）
  + Backward + AdamW（和标准训练相同）

GRPO vs PPO：
  去掉 Value Model，GAE → 组内 mean/std（完全并行）
  Batch 变 G 倍，GEMM 形状更 Compute Bound

显存管理：
  Weight Offload：阶段切换时搬权重，PCIe 延迟是痛点
  Worker 分离：推理 Worker + 训练 Worker，需要权重同步

RL 的整体 MFU 低（通常 5–15%）
原因：Rollout Decode 占 50% 时间但 GPU 利用率 1–5%
优化方向：用推理框架跑 Rollout，增大 batch size，异步流水线
