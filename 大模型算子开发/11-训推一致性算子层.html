11 · 训推一致性：算子层的数值对齐问题

前置：06 章（量化算子）、10 章（RL 算子）
关联：强化学习训练框架 04-训推一致性（该篇讲系统架构层；本章专注 kernel 和数值层）
目标：搞清楚同一份权重在训练和推理两端为什么会算出不同的数，每种差异的来源在哪一层，以及各层对应的 kernel 级解法。

本章关键词

浮点非结合性（Floating-point Non-associativity）—— (a+b)+c ≠ a+(b+c)，浮点加法不满足结合律，累加顺序不同结果就不同，是训推数值差异的底层根源。
QAT（Quantization-Aware Training，量化感知训练）—— 在训练前向传播里插入 FakeQuantize 算子，让模型在训练期间就"见到"推理时的量化噪声，从而自适应。
STE（Straight-Through Estimator，直通估计器）—— QAT 中量化操作的梯度近似：前向做量化，反向当量化不存在，梯度直通。
Absorptive MLA（吸收式多头潜在注意力）—— MLA 在 Decode 阶段把低秩 KV 压缩矩阵吸收进 W_Q/W_K/W_V，等价于 MQA，改变了算子计算路径。
Keep Routing / R3（路由重放）—— MoE 推理时记录每个 token 的 Expert 路由决策，训练时按原路由重放，避免训练和推理的 Expert 累加顺序不同。
路由跳变（Routing Flip）—— MoE 的 top-k 专家选择是离散决策，微小数值扰动可能让 token 换一批专家，把连续的小误差整流成 O(1) 量级的输出差异，是 MoE 独有的误差放大机制。
EP（Expert Parallel，专家并行）—— MoE 的并行方式，把不同专家放到不同卡上，卡间用 all-to-all 通信收发 token。训推 EP 度不同会改变累加与通信顺序。
capacity factor（专家容量因子）—— 单个专家在一个批次里最多接收多少 token，超额的被丢弃（drop）。训练常设上限、推理常用 dropless（不丢），这是 MoE 的 A 类失配。
bitwise reproducibility（逐位可复现）—— 训练和推理对同一输入产生完全相同的二进制结果，是最严格的一致性标准，实现代价极高。
TITO（Token-In-Token-Out，令牌级输入输出）—— 推理引擎直接把 token 序列传给训练引擎，不经过 detokenize → retokenize，消除分词边界引入的差异。

11.1 问题的本质

训练和推理用的是同一份权重，理论上对同一个输入应该得到完全相同的输出。实际上它们不同，而且这个差异会直接影响 RL 训练的 loss：

PPO loss 中的 ratio：
  ratio = exp(log_prob_new - log_prob_old)
         ↑ 训练引擎算的     ↑ 推理引擎算的

ratio 本该等于 1（同样的权重，同样的输入）
实际上 ratio ∈ [0.85, 1.15] 是很常见的
  → 梯度被无端放大或缩小 15%
  → 不是策略变了，是数值噪声

这个问题不会报错，不会触发 NaN，只是悄悄让训练效果变差，或者某一步梯度爆炸。

openPangu 的技术报告里把不一致的来源分成三类（A：定义失配，B：计算图重排，C：硬件非确定性），本章从算子层把每类的具体表现和 kernel 级解法展开。

11.2 精度格式差异（A 类：定义失配）

最直接的来源：训练用 BF16，推理用量化格式（INT8、FP8、INT4）。

11.2.1 量化误差的累积

训练时：y = x @ W.to(bf16)
推理时：y = x @ dequant(W_int8, scale)

单层误差：
  相对误差 ~ 2^{-(bits-1)} = 1/127 ≈ 0.8%（INT8）

N 层 Transformer 后的累积：
  误差不独立，方向可能对齐，累积到约 0.8% × √N（随机游走近似）
  N=32 层：累积误差 ~ 4.5%  → ratio 偏移可达 1.045，梯度放大 4.5%
  N=80 层（LLaMA-3 70B）：~ 7%  → ratio 偏移可达 1.07

11.2.2 QAT：在训练里插入量化噪声

解法是让模型在训练时就见到推理的量化误差，参数自动适应：

class FakeQuantizeINT8(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x, scale):
        # 前向：模拟 INT8 量化的四舍五入误差
        x_scaled = x / scale
        x_clamp = torch.clamp(x_scaled, -128, 127)
        x_round = torch.round(x_clamp)          # ← 引入量化误差
        return x_round * scale                   # 反量化回 FP16

    @staticmethod
    def backward(ctx, grad_output):
        # 反向：STE，梯度直通，当量化不存在
        return grad_output, None                 # ← 梯度不经过 round

# 在每层 Linear 的权重上包一层 FakeQuantize
class QATLinear(nn.Linear):
    def forward(self, x):
        scale = self.weight.abs().max() / 127.0
        w_fq = FakeQuantizeINT8.apply(self.weight, scale)
        return F.linear(x, w_fq, self.bias)

训练完成后，权重已经"习惯"了 INT8 的噪声，用真正的 INT8 做推理时误差更小，ratio 偏移也更小。

11.2.3 FP8 端到端训练（最彻底的对齐方式）

DeepSeek-V3 采用的路线：把训练前向也换成 FP8，使训练和推理用完全相同的数值格式：

训练阶段：
  前向 GEMM：FP8（E4M3）← 和推理完全一致
  反向 GEMM：BF16（梯度精度不降）
  权重更新：FP32 Master Weight

推理阶段：
  GEMM：FP8（E4M3）← 和训练前向一致

数值差异：0（两端同一个 kernel，同一种精度）

代价：需要精细管理每层的动态 scale factor（权重 scale、激活 scale 分开维护），以及处理 FP8 溢出（E4M3 动态范围只有 ±448）。

11.3 算子计算路径差异（B 类：计算图重排）

即使精度相同，计算图的不同也会导致浮点结果不同。

11.3.1 MLA 的 Absorptive 路径

MLA（Multi-head Latent Attention，多头潜在注意力）是 DeepSeek 提出的 KV Cache 压缩方案。它的核心是把 K/V 投影分解为低秩矩阵：

标准 MHA：
  K = X @ W_K，V = X @ W_V
  KV Cache 存 K, V，大小 = 2 × d_model × L tokens

MLA（Non-Absorptive，训练/Prefill 模式）：
  c_KV = X @ W_down    ← 压缩到低秩 r << d_model
  K = c_KV @ W_K_up    ← 从低秩还原
  V = c_KV @ W_V_up
  KV Cache 只存 c_KV，大小 = r × L tokens（r/d_model ≈ 1/8 的压缩比）

MLA（Absorptive，Decode 推理模式）：
  把两次矩阵乘合并：W_K_eff = W_down @ W_K_up
  K = X @ W_K_eff       ← 一次 GEMM，等价于 MQA
  不需要存 c_KV，直接存等效的低秩 K

关键问题：Non-Absorptive 是 (X @ W_down) @ W_K_up，Absorptive 是 X @ (W_down @ W_K_up)。

矩阵乘法满足结合律，数学上完全等价。但 FP16/BF16 的矩阵乘法不完全满足结合律：

Non-Absorptive：
  step 1: c = X @ W_down      ← X: (B,S,H) × W_down: (H,r)，中间有 r 个数
  step 2: K = c @ W_K_up      ← c: (B,S,r) × W_K_up: (r,H')

Absorptive：
  W_K_eff = W_down @ W_K_up   ← 预计算合并后的权重 (H,H')
  K = X @ W_K_eff              ← 一次 GEMM

两条路的浮点累加序列不同 → K 的末位不同 → Attention 分数不同 → 输出不同
差异量级：约 1–2 ULP（最低有效位），看起来极小，但累积 80 层后会可见

这不是 bug，而是性能优化的必然代价：Decode 时必须用 Absorptive 路径才能用 MQA 的 KV Cache，训练时用 Non-Absorptive 路径才能正确优化低秩矩阵。解决方法是接受这个差异，在 IS 修正层（见 11.6 节）兜底，而不是强制两端走同一路径。

11.3.2 MoE Expert 累加顺序

MoE 的输出是多个 Expert 输出的加权和：

output = sum(gate_score[i] * expert_output[i] for i in top_k_experts)

问题：Expert 选出后以什么顺序累加？

训练侧（常见实现）：按 Expert-ID 升序排列后累加
  output = g[2] * e[2] + g[5] * e[5] + g[7] * e[7]  （Expert 2,5,7 按序）

推理侧（性能优化后）：按 gate_score 降序排列后累加（分数高的先加）
  output = g[5] * e[5] + g[7] * e[7] + g[2] * e[2]  （分数 5>7>2）

浮点加法不满足交换律（严格说来），加法顺序不同 → 结果不同
对 BF16：差异约在 10^{-3} 量级（相对误差）

11.3.3 并行切分对累加顺序的影响

训练用 TP=8（张量并行，8 路切分），推理用 TP=4，两者的 AllReduce 通信方式不同：

TP=8 时的 GEMM 后 AllReduce：
  每卡算 1/8 的矩阵乘结果，然后 sum across 8 卡
  累加顺序：由 Ring-AllReduce 的环形顺序决定

TP=4 时：
  每卡算 1/4，然后 sum across 4 卡
  累加的中间值和顺序完全不同

→ 即使权重一样，TP 不同就会引入数值差异

11.4 硬件非确定性（C 类）

最难处理的一类：即使代码完全一样，不同运行之间结果也可能不同。

11.4.1 SplitK GEMM

GEMM 可以沿 K 轴并行化（多个 SM 分别计算部分和，再 Reduce 合并）。问题在于 SM 完成的顺序是不确定的，AtomicAdd 收集结果时的累加顺序因此随机：

SplitK=4 时：
  SM 0 算 A[:,0:K/4] @ B[0:K/4,:]
  SM 1 算 A[:,K/4:K/2] @ B[K/4:K/2,:]
  SM 2 算 A[:,K/2:3K/4] @ ...
  SM 3 算 A[:,3K/4:K] @ ...

AtomicAdd 汇总：
  假设 SM 3 先完成 → 先加 SM 3 的结果
  下次运行 SM 1 先完成 → 先加 SM 1 的结果

→ 相同的输入，相同的代码，每次运行结果不同（最后几位差异）

解法：使用 deterministic GEMM 模式，禁用 SplitK 的 AtomicAdd，改用 reduction tree（确定性的树形累加）。代价是性能降低约 10–30%（取决于矩阵大小）。

# PyTorch 的确定性模式
torch.use_deterministic_algorithms(True)
torch.backends.cudnn.deterministic = True

# 这会强制 CUDA 后端选择确定性的 GEMM 实现
# 某些情况下会触发 RuntimeError，需要检查哪些算子不支持确定性模式

11.4.2 Flash Attention 的确定性问题

FA2/FA3 的反向传播用了 AtomicAdd 来汇总多个 Block 对 dK、dV 的梯度贡献，默认是非确定性的：

# flash_attn 的确定性反向（flash-attn >= 2.3）
from flash_attn import flash_attn_func

output = flash_attn_func(q, k, v, deterministic=True)
# deterministic=True：用确定性的 reduction，不用 AtomicAdd
# 代价：反向传播速度降低约 10–15%

11.4.3 AllReduce 拓扑选择

在分布式训练中，AllReduce 的结果取决于通信拓扑（Ring / Tree / Recursive Halving-Doubling），而框架可能根据当前网络状态动态选择拓扑：

Ring AllReduce（8 卡）：
  累加顺序固定为环形，结果确定

Tree AllReduce：
  二叉树归约，不同根节点分配导致累加顺序变化

动态选择 → 两次运行可能用不同拓扑 → 累加顺序不同 → 结果不同

解法：固定 AllReduce 算法，禁用 NCCL 的自动算法选择：

export NCCL_ALGO=Ring          # 固定使用 Ring 算法
export NCCL_PROTO=Simple       # 禁用 LL128 等低延迟协议（这些改变累加顺序）

11.5 算子融合带来的差异

训练和推理对同一组算子可能使用不同的融合策略，融合策略改变了中间值的精度。

11.5.1 LayerNorm / RMSNorm 的融合

不融合（分两步）：
  hidden = linear(x)    ← BF16 输出
  out = rms_norm(hidden) ← 读入 BF16，内部转 FP32 做 sum，写出 BF16

融合版本（一个 kernel 里完成）：
  linear 的输出直接在寄存器里（不写回 HBM），以 FP32 传给 norm
  整个 linear + rms_norm 共享一个 FP32 累加器

差异：中间 hidden 的精度不同（BF16 vs FP32）→ norm 的输入精度不同 → 输出有差异

解法：训练和推理使用完全相同的融合 kernel。torch.compile 可以做到这一点：同一段 Python 代码，TorchInductor 对训练和推理生成同一个 Triton kernel，融合策略一致。

11.5.2 Attention Bias 的处理位置

causal mask 可以在 softmax 之前加（训练端常见），也可以在 FlashAttention kernel 内部处理（推理端）：

训练端（单独 kernel）：
  S = Q @ K^T / sqrt(d)
  S += causal_mask          ← 单独一次 element-wise 写 HBM
  out = softmax(S) @ V

FlashAttention（fused kernel）：
  在 SRAM 里做 S = Q_tile @ K_tile^T / sqrt(d)
  立即加 mask（不写 HBM）
  立即做在线 softmax
  立即乘 V_tile

差异来源：mask 加法发生在 BF16 还是 FP32 累加器里，以及是否有中间写回
量级：极小（< 1e-4），通常可忽略，但严格 bitwise 一致性时要处理

11.6 MoE 为什么特殊：离散路由把误差整流成跳变

前面五节讲的 A / B / C 三类差异，对 dense（稠密）模型和 MoE（Mixture of Experts，混合专家）模型都成立。但 MoE 多了一个 dense 没有的结构，它会把上面所有的小误差放大成大差异。

11.6.1 误差放大器：top-k 是一个离散决策

dense 模型里误差是连续传播的：输入扰动 1e-3，输出扰动也在 1e-3 量级，可控、可估。

MoE 在每一层多了一步 router（路由器）：

scores  = softmax(x @ W_router)                       # 对 E 个专家打分
experts = topk(scores, k)                             # ← 离散决策：选出 k 个
output  = sum(scores[i] * expert_i(x) for i in experts)

topk 是不连续的。当两个专家的分数接近时，1e-4 的扰动就足以让排序翻转：

推理侧：scores[17] = 0.1032,  scores[21] = 0.1029   → top-2 选中 {3, 17}
训练侧：scores[17] = 0.1030,  scores[21] = 0.1031   → top-2 选中 {3, 21}
        ↑ 分数差异只有 2e-4，但选出的专家换了一个

输出差异不是 2e-4，而是 |expert_17(x) - expert_21(x)|  → O(1) 量级

这就是 MoE 的特殊之处：它把连续的数值噪声整流（rectify）成了离散的跳变。同样一份 kernel 噪声，dense 模型能忍，MoE 忍不了。

三个会放大这个效应的因素：

  • 专家数 E 越大，分数分布越密集，相邻专家的分数间隔越小，翻转概率越高。E=256（DeepSeek-V3）比 E=8（Mixtral）敏感得多
  • 层数越深，前面层的跳变会改变隐状态，下一层的输入差异更大，跳变概率进一步升高——误差沿深度自我放大
  • 序列越长，逐 token 推进时同理累积

这一项是可以直接测的：统计训练侧与推理侧 top-k 专家集合的重合度。它比 PCC（Pearson Correlation Coefficient，皮尔逊相关系数）更早暴露问题——重合度已经在掉的时候，PCC 可能还很好看。

11.6.2 MoE 独有的失配源清单

除 11.3.2 讲过的 Expert 累加顺序外，MoE 还有三个 dense 不存在的来源：

来源 类别 说明
Expert 累加顺序 B 类 见 11.3.2：训练按 Expert-ID 升序累加，推理按 gate 分数降序累加
EP 度不同 B 类 训练 EP=8、推理 EP=64，all-to-all 的分组、通信顺序、累加顺序全部改变
capacity factor A 类 训练设专家容量上限、超额 token 被丢弃；推理多用 dropless。数学上就不等价，不是数值误差
路由跳变 B 类的放大 见 11.6.1。本身不产生误差，是把已有误差放大的机制

⚠️ capacity factor 这条最容易被漏掉：它是 A 类（定义失配），靠任何 kernel 对齐都修不掉，必须改配置——训练侧也用 dropless，或者推理侧也设同样的容量上限。改配置的代价很小，收益却是消掉一整类失配，性价比排在很前面。

⚠️ EP 度对齐的代价远大于 TP 度对齐：大 EP 正是 MoE 推理部署的核心优化（每张卡只放少量专家，显存才装得下）。要求训推同 EP，等于放弃这条优化，对大规模 MoE 基本不可行。

11.6.3 R3 / Keep Routing 的天花板

针对路由跳变，openPangu 的 R3（Rollout Routing Replay，回放推理侧路由）和 DeepSeek 的 Keep Routing 是同一个思路：推理时把每个 token 选中的专家记下来，训练时强制走同一套。

这确实消掉了跳变，但方案本身有天花板。openPangu 的 Masked R3 记录了这个坑：

现象：隐状态随 MoE 层加深而累积发散
     此时在深层强制全量重放推理侧路由
       → logits 被严重扭曲
       → PCC 骤降
       → 可能梯度爆炸

原因：训练侧这一层的输入 x_train 已经和推理侧的 x_infer 不一样了
     强行让 x_train 走 x_infer 选的专家
     = 用错的专家算错的输入，比不对齐更糟

解法：自适应阈值——只有训练侧自己算出的 top-k 与录制值重合度超过阈值时，
     才对该 token 重放

⚠️ 这是「一致性」和「正确性」的一次直接冲突，不是实现粗糙。全量重放不是越多越好。Masked R3 把这个矛盾挪到了一个可接受的位置，但没有消除它——这是 R3 路线不能称为「根治」的根本原因。

R3 的另一重成本在接口层。推理引擎交给训练引擎的契约要扩展：

(token_ids, logprobs, finish_reason)
    → (token_ids, logprobs, finish_reason, routing_records, sampling_mask, ...)

所有推理引擎要吐出路由、所有传输层要传路由、所有训练引擎要吃路由。这是生态成本，比技术成本更难推动。系统架构层的展开见 强化学习训练框架 04-训推一致性 §4.4。

11.6.4 一条边界：不该被「修掉」的那一半差异

在异步 RL（Reinforcement Learning，强化学习）里，rollout 用的是 N 步之前的旧权重，训练用的是当前权重。此时 ratio ≠ 1 是设计使然，不是数值 bug——这叫 off-policy（离策略）偏移。

ratio 的偏离 = 数值失配（A / B / C 三类，该修）
             + off-policy 偏移（异步设计的固有属性，只能用 IS 修正，不该修）

把 kernel 做到 bitwise 一致，只能消掉第一项。所以「训推一致性」这个词其实混装了两件事——判断一个方案有没有「根治」之前，先要分清在谈哪一半。

11.6.5 所以 MoE 训推一致性能不能根治

能，但代价是放弃推理侧的全部性能优化。这里有一条近似守恒律：

差异的来源，恰恰就是推理侧的优化本身。

Absorptive MLA、量化、SplitK、批次相关的 kernel 选择、大 EP 部署——每一项都是拿「改变计算路径」换吞吐。要求 bitwise 一致，等价于要求推理引擎按训练引擎的方式算，rollout 就慢回去了。所以「不根治」在工程上是主动取舍，不是能力不足。

现实的验收标准不是「差异为零」，而是「差异已经小到不伤训练」：

可接受区间：
  PCC(log_prob_train, log_prob_rollout) > 0.99
  ratio 标准差 < 0.1
  top-k 专家重合度 > 95%        ← MoE 特有，要单独看，不要只看前两项

11.7 分层解法汇总

不同层次的解法有不同的代价和效果：

算法层（最便宜，但不根治）
  ↓
接口层（中等代价，消除分词边界问题）
  ↓
数值格式层（中等代价，消除大部分精度差异）
  ↓
Kernel 层（最昂贵，但可以做到 bitwise 一致）

11.7.1 算法层：IS 修正（兜底）

承认 ratio ≠ 1，用重要性采样（Importance Sampling）修正：

# PPO with IS correction
ratio = torch.exp(log_prob_new - log_prob_old)

# 截断式 IS（TIS）：限制单个 token 的权重
ratio_clipped = torch.clamp(ratio, 1 - epsilon, 1 + epsilon)

# CISPO：裁剪重要性权重本身，而不是 ratio × advantage
# 当 ratio 偏离 1 超过阈值时，直接 mask 掉该 token
mask = (ratio > 1.0 / (1 + delta)) & (ratio < (1 + delta))
loss = -(ratio_clipped * advantage * mask).mean()

IS 修正能兜住数值差异带来的梯度放大问题，但不消除差异本身。当差异系统性地偏向一个方向时（比如 MLA 的 Absorptive 路径始终让 ratio < 1），IS 会系统性地降低某类 token 的学习信号。

11.7.2 接口层：TITO

把 tokenize/detokenize 从训推接口里去掉，直接传 token ID 序列：

# 错误做法（Text-In-Text-Out）
response_text = inference_engine.generate(prompt_text)
token_ids = tokenizer.encode(response_text)      # ← 可能和原来的 token_ids 不同！
log_probs_train = policy.forward(token_ids)

# 正确做法（Token-In-Token-Out，TITO）
token_ids, log_probs_rollout = inference_engine.generate_with_logprobs(prompt_ids)
log_probs_train = policy.forward(token_ids)      # ← 同一份 token_ids，无分词差异

TITO 不需要修改任何 kernel，是最便宜的一条改进，消除了分词边界引入的序列差异。

11.7.3 数值格式层：FP8 端到端 / QAT

见 11.2 节，FP8 训练是最彻底的格式对齐方式。

11.7.4 Kernel 层：确定性 kernel 库

DeepSeek 的解法：构建一套 批次不变（batch-invariant）且确定性的 kernel 库，保证：
- 同一个输入，批次大小改变，结果不变（不用 SplitK 这类依赖批次的优化）
- 同一个输入，两次运行结果完全相同（不用 AtomicAdd）

实现代价：需要为每个关键算子（GEMM、Attention、AllReduce）维护两套实现：一套高性能的（训练用），一套确定性的（用于需要 bitwise 对齐的场景）。

批次不变性要求：
  GEMM 的分块参数（BM, BN, BK）不随 batch 变化
  SplitK 的切分数固定，或完全不用 SplitK
  Reduction 用确定性的树形结构

确定性要求：
  禁用所有 AtomicAdd
  AllReduce 固定算法和拓扑
  Flash Attention 用 deterministic=True

代价：性能下降约 10–25%（和"不惜代价高性能"模式相比）
适用场景：专门用于生成 log_prob_old 的 Rollout 路径

11.9 实践中的优先级

不是所有不一致都值得修，按实际收益排序：

第一优先级（几乎总是值得做）：
- TITO —— 零代价，消除分词差异

第二优先级（RL 训练有明显收益）：
- IS 修正（CISPO/TIS）—— 在 loss 层面兜住所有剩余差异
- 禁用 SplitK（或启用 deterministic GEMM）—— 消除随机性，让训练可复现

第三优先级（有精度要求时）：
- QAT —— 如果推理用 INT8/FP4，训练时加 FakeQuantize
- FP8 端到端训练 —— 如果训练本身就在 FP8 下进行（DeepSeek 路线）

模型是 MoE 时，额外的两条（见 11.6）：
- 对齐 capacity factor（训推都用 dropless）—— 改配置即可，消掉一整类 A 类失配
- 先测 top-k 专家重合度，再决定上不上 Masked R3 —— 专家数多、层数深时几乎是必做项；注意用带阈值的 Masked R3，不要全量重放

只在极端场景需要：
- 全量 bitwise 确定性 kernel 库 —— 性能代价大，只有超大规模 MoE + 异步 RL 才值得
- 训推对齐 EP 度 —— 等于放弃大 EP 部署，一般不可行

11.10 本章小结

训推数值差异的三层根源：

A 类（定义失配）：精度格式不同
  → QAT 或 FP8 端到端训练

B 类（计算图重排）：浮点非结合性
  → MLA：结构性，IS 修正兜底
  → MoE：Keep Routing 重放累加顺序
  → 融合策略：torch.compile 统一代码路径

MoE 独有的放大机制（11.6）：
  top-k 路由是离散决策 → 把连续小误差整流成 O(1) 跳变
  capacity factor 属 A 类，靠 kernel 对齐修不掉，改配置即可
  R3 重放有天花板：深层强制重放 = 用错的专家算错的输入
  → 用带阈值的 Masked R3，不要全量重放

C 类（硬件非确定性）：AtomicAdd 顺序随机
  → deterministic GEMM + FA deterministic=True
  → 固定 NCCL_ALGO=Ring

接口层快赢：
  TITO：零代价，消除分词边界引起的序列差异
  IS 修正：算法层兜底，不消除差异，但限制梯度放大

一条守恒律：
  差异的来源，恰恰就是推理侧的优化本身
  要 bitwise 一致 = 要放弃推理优化 → 是取舍，不是能力问题
  另外 ratio 的偏离里还混着 off-policy 偏移，那一半不该修，只能 IS 修正

严格性层次：
  IS 修正 < TITO < QAT < deterministic kernel < FP8 端到端
  越往右越彻底，代价也越高

实践建议：
  先上 TITO + IS 修正，观察 ratio 分布
  ratio 标准差 > 0.1 时考虑下一层解法
  PCC(log_prob_train, log_prob_rollout) > 0.99 时已经足够
  MoE 额外看一项：top-k 专家重合度 > 95%

昇腾对照：本章的逐层比对方法论在 GPU→NPU 迁移中直接适用 —— 只不过比的是「GPU vs NPU」而非「训练 vs 推理」，见 14 章 §14.4。TorchAir 的精度 dump 是昇腾侧的主力比对工具，见 14 章 §14.5。
