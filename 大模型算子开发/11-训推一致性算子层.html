11 · 训推一致性：算子层的数值对齐问题

前置：06 章（量化算子）、10 章（RL 算子）。本章会反复用到 10 章 §10.5 的 clip 边界 ±0.1823，建议先把那一节看完。
关联：强化学习训练框架 04-训推一致性（该篇讲系统架构层；本章专注 kernel 和数值层）
目标：搞清楚同一份权重在训练和推理两端为什么会算出不同的数，这个差异从哪一行浮点加法长出来，怎么被指数函数放大到能掀翻训练，以及每一层对应的 kernel 级解法各要付什么代价。
读法：本章 §11.2 的所有浮点例子都是真的算过的（BF16 按 IEEE 规则舍入），数字全是 2 的幂，拿纸笔就能验。强烈建议自己把 §11.2.3 那张表重算一遍——全章后面所有结论都从那张表里长出来。

本章关键词

logprob（log probability，对数概率）—— 模型给某个 token 打的概率取自然对数。RL 里训练端和推理端各算一份，两份对不上就是本章的全部问题。
浮点非结合性（Floating-point Non-associativity）—— (a+b)+c ≠ a+(b+c)，浮点加法不满足结合律（但满足交换律，见 §11.2.4），累加顺序不同结果就不同，是训推数值差异的物理根源。
归约（Reduction）—— 把一串数加成一个数的操作。求和、求最大值、softmax 的分母、GEMM 沿 K 轴的累加，全是归约。归约就意味着有顺序，有顺序就有分歧。
Split-K（K 轴切分）—— GEMM 把 K 维切成若干段并行算，各段算出部分和再合并。切几段由 kernel 根据矩阵形状和 batch 大小自动选，切法一变结果就变。
batch 不变性（Batch Invariance）—— 同一条序列，无论它是单独送进去（batch=1）还是和别人拼在一起（batch=32），输出完全相同。现代推理引擎默认不满足这条性质。
ratio（重要性采样比）—— exp(logprob_train − logprob_infer)，PPO/GRPO loss 的核心系数。本该是 1，实际不是。
IS（Importance Sampling，重要性采样）—— 用旧策略采的数据估计新策略的期望，需要乘上 ratio 做修正。
TIS（Truncated Importance Sampling，截断重要性采样）—— 给 IS 权重加一个上限 C（常取 1~2），承认训练端和推理端是两个不同的分布，用一个带截断的权重把它修回来。
CISPO（Clipped IS-weight Policy Optimization，截断重要性权重策略优化）—— MiniMax-M1 提出的目标函数：裁剪 IS 权重本身并对它 stop-gradient，所有 token 的梯度都保留，不像 PPO 的 clip 那样把越界 token 的梯度归零。
behavior policy（行为策略）—— 实际产生数据的那个策略。RL 理论要求 logprob_old 必须来自真正产生数据的策略；rollout 是推理引擎跑的，所以推理引擎才是 behavior policy，这一条被违反是训推不一致的理论核心。
QAT（Quantization-Aware Training，量化感知训练）—— 在训练前向里插入 FakeQuantize 算子，让模型在训练期间就"见到"推理时的量化噪声，从而自适应。
STE（Straight-Through Estimator，直通估计器）—— QAT 中量化操作的梯度近似：前向做量化，反向当量化不存在，梯度直通。
MLA（Multi-head Latent Attention，多头潜在注意力）—— DeepSeek 的 KV Cache 压缩方案，Decode 时会把上投影矩阵"吸收"进 Q 侧（Absorptive，吸收式），改变了算子计算路径。
Keep Routing / R3（Rollout Routing Replay，路由重放）—— MoE 推理时记录每个 token 的 Expert 路由决策，训练时按原路由重放，避免训练和推理选出不同的专家。
路由跳变（Routing Flip）—— MoE 的 top-k 专家选择是离散决策，微小数值扰动可能让 token 换一批专家，把连续的小误差整流成 O(1) 量级的输出差异，是 MoE 独有的误差放大机制。
EP（Expert Parallel，专家并行）—— MoE 的并行方式，把不同专家放到不同卡上，卡间用 all-to-all 通信收发 token。训推 EP 度不同会改变累加与通信顺序。
TP（Tensor Parallel，张量并行）—— 把一个矩阵乘沿某一维切到多张卡上算，算完 AllReduce 求和。切几刀决定了求和的顺序。
capacity factor（专家容量因子）—— 单个专家在一个批次里最多接收多少 token，超额的被丢弃（drop）。训练常设上限、推理常用 dropless（不丢），这是 MoE 的 A 类失配。
bitwise reproducibility（逐位可复现）—— 训练和推理对同一输入产生完全相同的二进制结果，是最严格的一致性标准，实现代价极高。
TITO（Token-In-Token-Out，令牌级输入输出）—— 推理引擎直接把 token 序列传给训练引擎，不经过 detokenize（反分词）→ retokenize（重分词），消除分词边界引入的差异。
ULP（Unit in the Last Place，末位单位）—— 浮点数在当前量级上相邻两个可表示值的间距，是衡量数值误差的自然单位。BF16 在 1.0 附近的 1 ULP = 2⁻⁷ = 0.0078125。

11.1 先看见它：同一份权重，两个引擎，两个数

在讲任何原理之前，先把这件事摆到桌面上。

实验：拿一个模型的同一份权重文件，同一个 prompt，让推理引擎（vLLM / SGLang）生成一小段回答；然后把这段回答原封不动喂给训练引擎（Megatron / FSDP）做一次前向，让它算同样这些 token 的 logprob。两边用的是同一份权重、同一段 token、同一种精度（都是 BF16）。

两边给出的 logprob 应该一模一样。实际长这样：

# token 推理引擎 logp_infer 训练引擎 logp_train Δ = train − infer ratio = exp(Δ)
1 The −0.4512 −0.4500 +0.0012 1.0012
2 capital −1.2034 −1.2068 −0.0034 0.9966
3 of −0.0891 −0.0681 +0.0210 1.0212
4 France −0.3320 −0.3328 −0.0008 0.9992
5 is −2.7710 −2.5760 +0.1950 1.2153
6 Paris −0.0155 −0.0576 −0.0421 0.9588

（⚠️ 这张表的 logprob 是构造的示意数据，用来演示量级和换算关系；Δ 列的分布形态——大部分在 1e-3 量级、少数 token 蹦到 1e-1——是各家 RL 框架里普遍报告的现象。ratio 列是真的按 exp(Δ) 算的，可以自己验。）

三件事已经能看出来了：

  • 大部分 token 差得很小：Δ 在 1e-3 量级，ratio 在 1.00x，无害。
  • 少数 token 差得很大：第 5 个 token 的 Δ = 0.195，ratio = 1.2153。
  • 第 5 个 token 已经越界了。 10 章 §10.5 算过：PPO 取 ε = 0.2 时，clip 边界对应的 log-prob 偏移正好是 ±0.1823（因为 ln 1.2 = 0.1823）。这个 token 的 Δ = 0.195 > 0.1823，它会被 PPO 的 clip 裁掉，梯度精确归零。

★ 这就是本章要解决的问题的全貌：权重没变、策略没变、什么都没变，纯粹因为两个引擎的 kernel 写法不同，就有 token 被判定成"策略变化过大"而丢掉梯度。10 章 §10.5 的那句话在这里落地了——clip 的全部预算只有 ±0.1823 个自然对数单位，而训推数值失配一个人就能吃掉它。

11.1.1 为什么这件事在 RL 里才致命

同样的数值差异，在预训练和普通推理里都无所谓，唯独 RL 受不了。原因是 RL 的 loss 里有一个 exp()：

预训练 loss:   L = −logp(target)
               logp 差 0.195  →  loss 差 0.195      ← 线性，小扰动就是小扰动

RL 的 PPO loss: L = −min(ratio·A, clip(ratio)·A),  ratio = exp(logp_train − logp_infer)
               logp 差 0.195  →  ratio = 1.2153    ← 指数放大
                              →  越过 clip 边界 1.2
                              →  梯度【从 A·1.2153 直接掉到 0】
                                 不是变小，是断崖

再加上 RL 的第二个放大器：这个差异不是随机噪声，它有系统性方向。量化让推理端的 logprob 系统性偏高或偏低，MLA 的吸收路径让某一类 token 的 ratio 稳定小于 1。系统性偏差不会在一个 batch 里互相抵消，而是每一步都往同一个方向推梯度。

11.1.2 顺着往下推：训练是怎么崩的

把上面两条串起来，就是一条完整的因果链：

① 两个引擎的 kernel 归约顺序不同
        ↓  （§11.2：浮点加法不满足结合律）
② 同一个 logit 算出来差几个 ULP
        ↓  （§11.3：一次前向有上万次归约，误差累积）
③ 单个 token 的 logprob 差 1e-3 ~ 1e-1
        ↓  （ratio = exp(Δ)，指数放大）
④ ratio 偏离 1，少数 token 冲出 [0.8, 1.2]
        ↓
⑤ 这些 token 被 clip 掉，梯度归零 —— 数据被白采了
        ↓  （而且被裁掉的往往是【模型最不确定的那些 token】，
        ↓    也就是最有学习价值的那些）
⑥ 有效样本量下降 + 梯度方向被系统性偏置
        ↓
⑦ 表现：reward 涨一段后卡住不动，或者某一步 loss 突然尖刺、
        entropy（熵）塌缩，训练直接发散

⚠️ 这条链上的每一步都不报错、不产生 NaN、不触发任何告警。 你在日志里看到的只有第 ⑦ 步——reward 曲线不涨了。这是 RL 训练最难排查的一类问题，因为它的症状和"超参没调好""数据质量差""reward 设计有问题"长得一模一样。所以必须把 ①~⑥ 每一步都变成能直接观测的指标，这是 §11.11 要给的东西。

11.2 物理根源：浮点加法不满足结合律

这一节是全章的地基。只有一个定理，但它解释后面所有现象。

11.2.1 最小的例子：三个数，两种加法，两个答案

先约定：本节所有例子用 BF16（Brain Float 16），因为它是大模型训练和推理最常用的精度。BF16 的位布局是：

BF16 = 1 位符号 + 8 位指数 + 7 位尾数
                              └─ 加上隐含的前导 1，共【8 位有效数字（二进制）】

在 1.0 附近，相邻两个可表示的数相差 2⁻⁷ = 0.0078125   ← 这就是 1 ULP
换句话说：1.0 之后下一个能表示的数是 1.0078125，中间什么都没有

现在取三个数，全都在 BF16 里精确可表示（是 2 的整数次幂，不存在"输入就有误差"的干扰）：

a = 1.0
b = 2⁻⁸ = 0.00390625
c = 2⁻⁸ = 0.00390625

算法一：(a + b) + c

第 1 步：1.0 + 0.00390625 = 1.00390625（真值）
         但 BF16 在 1.0 附近只能表示 1.0 和 1.0078125
         1.00390625 正好卡在两者【正中间】
         → IEEE 的"就近舍入，平局取偶"规则：取尾数为偶数的那个 = 1.0
         结果：1.0     ← b 被整个吃掉了，什么都没留下

第 2 步：1.0 + 0.00390625 = 同上 → 1.0

(a + b) + c = 1.0

算法二：a + (b + c)

第 1 步：0.00390625 + 0.00390625 = 0.0078125
         这个数在 BF16 里精确可表示（= 2⁻⁷）
         结果：0.0078125   ← 没有任何损失

第 2 步：1.0 + 0.0078125 = 1.0078125
         这个数也精确可表示（正好是 1.0 的下一个）
         结果：1.0078125

a + (b + c) = 1.0078125

两个答案不一样：

算法 结果 与真值 1.0078125 的差
(a + b) + c 1.0 差 1 个完整 ULP，相对误差 −0.78%
a + (b + c) 1.0078125 精确

★ 一行字总结整章的物理根源：(1.0 + 2⁻⁸) + 2⁻⁸ = 1.0，而 1.0 + (2⁻⁸ + 2⁻⁸) = 1.0078125。只是加括号的位置变了，结果就差了一个 ULP。 没有人写错代码，没有 bug，两边都严格遵守了 IEEE 754。

11.2.2 为什么会这样：浮点加法必须先"对阶"

机理只有一句话：浮点加法要先把两个数对齐到同一个指数，小的那个数会被右移，移出尾数范围的位直接丢掉。

1.0          的二进制 = 1.0000000 × 2⁰       （尾数 8 位有效）
0.00390625   的二进制 = 1.0000000 × 2⁻⁸

对阶：把小的那个右移 8 位，对齐到 2⁰
      1.0000000 × 2⁰
    + 0.0000000|1  × 2⁰       ← 竖线右边这一位超出了 8 位有效数字
      ─────────────────
      1.0000000|1  × 2⁰       ← 这一位必须扔掉

舍入：扔掉的部分正好是 0.5 ULP（平局）→ 平局取偶 → 1.0000000 × 2⁰ = 1.0

结论：0.00390625 对 1.0 来说【太小了】，加不进去。这叫【吞噬】（swamping）。

反过来，先把两个小数加在一起，它们量级相同、不需要对阶、一位都不丢；等它们长成 0.0078125（刚好 1 ULP）之后再去加 1.0，就加得进去了。

★ "先把小的加在一起"永远更准。 这不是巧合，是所有归约算法的基本原理：树形归约（配对相加）的误差是 O(log n)·ε，串行累加是 O(n)·ε。这条规律在下一小节会直接量化出来。

11.2.3 归约顺序：一个数组，四种加法，四个答案

上一节是三个数的玩具。现在把它放大到一个真实 kernel 会遇到的场景：一个 GEMM 沿 K 轴归约。

设 K = 9，要把这 9 个数加起来（全部 BF16 精确可表示）：

x = [ 1.0 ,  2⁻⁸ ,  2⁻⁸ ,  2⁻⁸ ,  2⁻⁸ ,  2⁻⁸ ,  2⁻⁸ ,  2⁻⁸ ,  2⁻⁸ ]
      ↑      └──────────────── 8 个 0.00390625 ────────────────┘
    一个大的

数学真值 = 1.0 + 8 × 0.00390625 = 1.0 + 0.03125 = 1.03125

（这个"一个大值 + 一堆小值"的分布不是我编的极端情况——它正是 Transformer 里 K 轴归约的典型形态：少数几个维度贡献了大部分数值，其余维度贡献微小。massive activation 现象就是它的极端版本。）

方式一：串行累加（Split-K = 1，单个线程从头加到尾）

步骤 累加器加之前 加上 真值 BF16 舍入后
1 0 1.0 1.0 1.0
2 1.0 0.00390625 1.00390625 1.0（平局取偶）
3 1.0 0.00390625 1.00390625 1.0
4–9 1.0 0.00390625 1.00390625 1.0

结果 = 1.0。8 个小数一个都没加进去，全被吞掉了。误差 −3.03%。

方式二：Split-K = 2（K 轴切成两段，两段并行，最后合并）

段 A = x[0:5] = [1.0, 2⁻⁸, 2⁻⁸, 2⁻⁸, 2⁻⁸]  → 串行累加 → 1.0        （同样被吞）
段 B = x[5:9] = [2⁻⁸, 2⁻⁸, 2⁻⁸, 2⁻⁸]        → 串行累加 → 0.015625   （量级相同，无损）

合并：1.0 + 0.015625 = 1.015625   ← BF16 精确可表示（= 1.0 + 2 ULP）

结果 = 1.015625。误差 −1.52%。

方式三：Split-K = 4（切成 4 段）

段 0 = x[0:3] = [1.0, 2⁻⁸, 2⁻⁸]  → 1.0
段 1 = x[3:5] = [2⁻⁸, 2⁻⁸]       → 0.0078125
段 2 = x[5:7] = [2⁻⁸, 2⁻⁸]       → 0.0078125
段 3 = x[7:9] = [2⁻⁸, 2⁻⁸]       → 0.0078125

两两合并（树形）：
  (段0 + 段1) = 1.0 + 0.0078125     = 1.0078125
  (段2 + 段3) = 0.0078125+0.0078125 = 0.015625
  最终        = 1.0078125 + 0.015625 = 1.0234375

结果 = 1.0234375。误差 −0.76%。

方式四：完整二叉树归约

第 0 层  1.0   2⁻⁸   2⁻⁸   2⁻⁸   2⁻⁸   2⁻⁸   2⁻⁸   2⁻⁸   2⁻⁸
          └──┬──┘     └──┬──┘     └──┬──┘     └──┬──┘     │
第 1 层    1.0       0.0078125  0.0078125  0.0078125   0.00390625
             └────┬────┘            └────┬────┘            │
第 2 层       1.0078125              0.015625         0.00390625
                  └───────────┬───────────┘                │
第 3 层                   1.0234375                    0.00390625
                               └──────────────┬─────────────┘
第 4 层                              1.03125     ← 精确！

四种归约方式，四个不同的答案：

归约方式 谁会这么算 结果 相对误差
串行（Split-K = 1） 小 batch 时的 GEMM kernel 1.0 −3.03%
Split-K = 2 中等 batch 1.015625 −1.52%
Split-K = 4 大 K、小 M/N 时的 kernel 1.0234375 −0.76%
完整二叉树 warp shuffle 归约、确定性 kernel 1.03125 0（精确）

★ 这张表是全章的核心。 四行结果都不同，但没有一行是 bug——它们都在正确地做浮点加法，只是加的顺序不同。训练引擎和推理引擎恰恰会选中不同的行：训练端 batch 大（M 大），GEMM kernel 倾向不切 K；推理 Decode 端 M = 1（§10.3.1 那张形状表），K 很大，kernel 必须切 K 才能填满 GPU。于是同一个矩阵乘，两端走了表里的不同行。

⚠️ 别把这个例子当成"误差上界只有 3%"。 这里 K 只有 9。真实 GEMM 的 K 是 4096~16384，归约链长几千倍；而且 Tensor Core 内部用 FP32 累加器（比 BF16 好得多），所以单次 GEMM 的实际相对误差远小于 3%，通常在 1e-4~1e-3 量级（⚠️ 量级估计）。这个例子要说明的是"顺序改变结果"这个事实本身，不是误差的具体大小。

11.2.4 一个必须澄清的说法：交换律是成立的

网上（也包括本章的旧版）经常写成"浮点加法不满足交换律"。这是错的，必须纠正：

定律 数学写法 浮点是否满足
交换律（commutative） a + b = b + a ✅ 满足（除 NaN 的符号位等边角情况外，IEEE 754 保证 a+b 和 b+a 逐位相同）
结合律（associative） (a+b)+c = a+(b+c) ❌ 不满足 —— 就是 §11.2.1 那个例子
分配律（distributive） a×(b+c) = a×b + a×c ❌ 不满足

为什么这个区别要紧：它决定了"改变顺序"到底哪一种会出问题。

把加法的【操作数左右对调】     → 安全，结果不变
把加法的【结合方式改掉】       → 不安全，结果会变
  ├── 切成几段并行算再合并（Split-K）          ← 改的是结合方式 ✗
  ├── 树形归约 vs 串行累加                      ← 改的是结合方式 ✗
  ├── AtomicAdd 到达顺序随机                    ← 改的是结合方式 ✗
  └── AllReduce 用 Ring 还是 Tree               ← 改的是结合方式 ✗

也就是说：你在真实 kernel 里遇到的所有顺序问题，全都是结合律问题，没有一个是交换律问题。（顺带一提：AtomicAdd 看起来像"顺序随机的交换"，其实它是"每次和当前累加器的值结合"，改的还是结合方式。）

11.2.5 小结：一条规则解释一切

只要一个算子里有【归约】，它的结果就依赖【归约的结合方式】。
而结合方式由 kernel 的并行策略决定，并行策略又由【张量形状】和【硬件】决定。

         张量形状（batch、seq_len、K）
              ↓  决定
         kernel 选哪套分块/切分参数（Split-K、tile 大小、线程数）
              ↓  决定
         归约的结合方式（先加谁后加谁）
              ↓  决定
         浮点结果的末几位
              ↓  经过 exp() 放大
         ratio 偏离 1

后面所有章节都是这条链的具体展开：§11.3 讲第四步怎么被放大，§11.4 讲第一步（形状）在推理引擎里为什么天然不稳定，§11.5–11.8 讲这条链在真实系统里的各个入口。

11.3 从几个 ULP 到训练崩掉：放大链的四级台阶

§11.2 证明了"末位会不一样"。但末位差几个 ULP，怎么就能把训练搞崩？这一节把中间的四级放大一级一级算出来。

11.3.1 第一级：一次前向里有多少次归约

先建立量感。取一个 32 层、hidden = 4096、词表 128k 的模型，看一个 token 走一遍前向要做多少次归约：

位置 每层的归约次数 每次归约的长度 K 说明
RMSNorm（2 个） 2 4096 求平方和，纯归约
QKV / O 投影 GEMM 4 × 4096 个输出元素 4096 每个输出元素是一次长度 4096 的归约
Attention 的 QKᵀ 每个 score 一次 128（head_dim）
Attention 的 ·V 每个输出一次 seq_len 长度随序列变，是 batch 敏感的重灾区
MLP 的两个 GEMM 2 × (4096 + 11008) 个输出 4096 / 11008
合计（粗算） 约 3 万次 / 层 — 32 层 ≈ 百万量级
最后的 LM Head 128000 个输出 4096 算 logits
logsumexp 1 128000 算 logprob 的分母

★ 一个 token 的 logprob，背后是上百万次归约的结果。 每一次归约的结合方式都可能在两个引擎之间不同。§11.2.3 那张表不是发生一次，是发生一百万次，而且层与层之间会接力——第 1 层的输出误差是第 2 层的输入误差。

误差怎么长大，有一个粗糙但够用的模型：

假设每层引入的相对误差 δ ≈ 1e-4，方向随机、层间独立：
   N 层后累积  ≈ δ × √N          （随机游走）
   N = 32:   1e-4 × 5.66 = 5.7e-4
   N = 80:   1e-4 × 8.94 = 8.9e-4

假设误差有【系统性方向】（比如推理端始终用 Split-K=4、训练端始终不切）：
   N 层后累积  ≈ δ × N            （线性累积，最坏情况）
   N = 32:   1e-4 × 32 = 3.2e-3   ← 比随机游走大 5.7 倍
   N = 80:   1e-4 × 80 = 8.0e-3   ← 大 9 倍

⚠️ 上面两行都是 量级模型，不是实测。真实情况在两者之间，而且更接近线性那一行——因为 kernel 选择是确定的、不是随机的，推理引擎在整个前向里会系统性地用同一套策略。这正是"训推差异"比"同一引擎跑两次的差异"大得多的原因：后者是真随机游走，前者是系统性偏置。判断你的系统落在哪一行，唯一办法是实测逐层 PCC 曲线（§11.11 给方法）。

11.3.2 第二级：hidden state 的误差怎么变成 logprob 的误差

logprob 不是 hidden state，中间还隔着 LM Head 和 softmax。这一步的传递关系值得单独算，因为它不是 1:1 的。

用一个 4 词的玩具词表，把整个过程走完：

logits       = [ 2.000, 1.0, 0.5, 0.0 ]      ← 原始
logits'      = [ 2.004, 1.0, 0.5, 0.0 ]      ← 第 0 个 logit 被扰动了 +0.004

算第 0 个 token 的 logprob（logprob = logit_0 − logsumexp(logits)）：

logits logsumexp logprob_0 prob_0
原始 [2.000, 1.0, 0.5, 0.0] 2.546006 −0.546006 0.579259
扰动后 [2.004, 1.0, 0.5, 0.0] 2.548325 −0.544325 0.580233
差 +0.004 +0.002319 +0.001681 +0.000974

关键在于衰减比：logit 动了 0.004，logprob 只动了 0.001681，只有 42% 传过去了。

为什么会衰减，一行微分就看明白：

logprob_i = logit_i − logsumexp(logits)
∂(logprob_i) / ∂(logit_i) = 1 − softmax(logits)_i = 1 − p_i

本例：p_0 = 0.5793  →  衰减系数 = 1 − 0.5793 = 0.4207
验证：0.004 × 0.4207 = 0.001683   ✓ 和上表的 0.001681 对得上（差在高阶项）

★ 1 − p 这个系数决定了哪些 token 最危险，而结论是反直觉的：

模型很确定的 token（p ≈ 0.99）：衰减系数 = 0.01 → logit 误差被【压掉 99%】，安全 模型很不确定的 token（p ≈ 0.01）：衰减系数 = 0.99 → logit 误差【几乎全部透传】，危险

也就是说：数值失配专挑模型犹豫的 token 下手。而 RL 要学的恰恰就是这些犹豫的 token——确定的 token 没什么可学的。§11.1.2 第 ⑤ 步说"被裁掉的往往是最有学习价值的 token"，物理原因就在这个 1 − p 上。

11.3.3 第三级：exp() 把 logprob 差变成 ratio 偏离

这一级是纯换算，但必须有量感。记住 ±0.1823 这条线（10 章 §10.5，ε = 0.2 时的 clip 边界）：

Δ = logp_train − logp_infer ratio = exp(Δ) 相对 clip 边界
0.001 1.0010 0.5% 的预算
0.01 1.0101 5.5% 的预算
0.05 1.0513 27% 的预算
0.10 1.1052 55% 的预算
0.1823 1.2000 100% —— 正好触线
0.30 1.3499 超出，梯度归零

★ clip 的全部预算只有 0.1823。 而 §11.3.1 的线性累积模型给出 N = 80 层时 hidden state 相对误差约 8e-3，经 §11.3.2 的 1−p 传递到 logprob……对低概率 token 几乎不衰减。这就是为什么少数 token 能蹦到 Δ = 0.195（§11.1 那张表的第 5 行）。

11.3.4 第四级：多少 token 会被裁掉，训练受多大损失

现在把它量化成"损失了多少数据"。假设每个 token 的 Δ 服从均值 0、标准差 σ 的正态分布（⚠️ 高斯假设是简化，真实分布是重尾的，实际被裁比例会比下表更高），那么被裁掉的 token 比例就是落在 ±0.1823 之外的概率：

Δ 的标准差 σ ratio 的 ±1σ 区间 被 clip 的 token 比例 这个训练还能跑吗
0.01 [0.990, 1.010] ~0% 完全健康
0.02 [0.980, 1.020] ~0% 健康
0.05 [0.951, 1.051] 0.03% 可以接受
0.08 [0.923, 1.083] 2.3% 开始要盯着
0.10 [0.905, 1.105] 6.8% 明显浪费数据
0.15 [0.861, 1.162] 22.4% 五分之一的数据白采了

（这一列是 2 × (1 − Φ(0.1823/σ)) 算出来的，可以用任何统计工具复算。）

★ 这张表给出了"ratio 标准差 < 0.1"这条经验阈值的来源。 σ = 0.1 对应 6.8% 的 token 被无谓裁掉，勉强能忍；σ = 0.15 就是 22%，等于每采 5 条数据扔掉 1 条，而且扔掉的是最该学的那批。旧版本章里写的"ratio ∈ [0.85, 1.15] 很常见"，换算过来正是 σ ≈ 0.1 ~ 0.15 这个危险区间。

还有一个更糟的用法必须警告：有些实现用序列级 ratio（把整条序列的 Δ 加起来再 exp），这会把问题放大到不可用：

序列长度 n = 512，每个 token 的 Δ 标准差 σ = 0.05（上表里"可以接受"的那档）

序列级 Δ 的标准差 = σ × √n = 0.05 × √512 = 0.05 × 22.63 = 1.131
序列级 ratio 的 ±1σ 区间 = [exp(−1.131), exp(+1.131)] = [0.32, 3.10]
                                                           ↑
                                  token 级完全健康的配置，序列级已经彻底失控

n = 4096 时： 0.05 × 64 = 3.2  →  ratio ∈ [0.041, 24.5]

⚠️ token 级看起来完全健康的数值失配，换成序列级 IS 就会直接炸。 原因是误差沿序列长度按 √n 累积，而 exp() 对这个累积量做指数放大。做训推一致性诊断时，永远看 token 级 ratio 的分布，不要只看序列级的均值——序列级均值可能正好是 1，因为正负抵消了，而分布已经宽到没法用。

11.4 batch 不变性：同一条序列，放在 batch=1 和 batch=32 里结果不同

这是本章最反直觉、也最容易被忽略的一节。它是 §11.2 那条规律在推理引擎里的必然结果。

11.4.1 现象

实验：同一份权重、同一条 prompt。

跑法 A：单独送进去                  batch = 1     → logprob = −2.7710
跑法 B：和另外 31 条 prompt 拼一起    batch = 32    → logprob = −2.7706
                                                       ↑
                                这【一条序列自己】的输出变了。
                                它和另外 31 条序列在数学上毫无关系
                                （attention 有 mask，不会互相看到），
                                但结果就是不一样。

"同一条序列的结果不受同批次其他序列影响"这条性质叫 batch 不变性（batch invariance）。几乎所有高性能推理引擎默认都不满足它。

11.4.2 为什么：batch 大小会改变 kernel 的并行策略

根子在 §11.2.5 那条链的第一步——形状决定 kernel 选择。batch 一变，形状就变，kernel 就换一套参数，归约的结合方式就变了。

batch = 1 时的一个 GEMM:   M=1,  N=4096, K=4096
    → M 太小，只有 4096 个输出元素，撑不满 132 个 SM（§1.2.4 的波次问题）
    → kernel 启发式：【必须切 K】才能造出更多并行任务 → Split-K = 8

batch = 32 时的同一个 GEMM: M=32, N=4096, K=4096
    → 输出元素 32 倍多了，SM 已经喂饱
    → kernel 启发式：【不切 K】，切 K 反而要多付一次归约开销 → Split-K = 1

同一个矩阵乘，同一份权重，走了 §11.2.3 表里的【不同两行】。

具体到哪几类 kernel，有三个惯犯：

# kernel 类别 为什么 batch 敏感 典型算子
① 纯归约类 每个线程块处理几行、归约用几个线程，都随总行数变。行少时用"一个 block 处理多行"的布局，行多时用"一个 block 一行"，两种布局的树形结构不同 RMSNorm、LayerNorm、Softmax、逐元素求和
② Split-K 的 GEMM 见上面的推演：M 小就切 K，M 大就不切 所有 Linear 层
③ FlashAttention 的 split-KV / split-Q Decode 时 Q 只有 1 行，必须沿 KV 长度切块并行（FlashDecoding），切几块取决于"还剩多少 SM 空着"——而这取决于同批次其他序列占了多少 SM Attention

第 ③ 类最阴险，值得单独画一下：

batch = 1，序列长 8192：
    只有 1 个 query，132 个 SM 全空着
    → FlashDecoding 把 8192 长的 KV 切成 32 块，32 个 SM 各算一块
    → 32 个部分 softmax 结果，用 log-sum-exp 合并（树形，32 个叶子）

batch = 32，每条序列长 8192：
    32 个 query，SM 已经被别的序列占掉大半
    → 每条序列只分到 4 块
    → 4 个部分结果合并（树形，4 个叶子）

           ↓  同一条序列，同一份 KV Cache
    32 叶子的树 和 4 叶子的树，结合方式完全不同 → 结果不同

★ 注意这里发生了什么：这条序列的输出，取决于同批次里还有谁。而在连续批处理（continuous batching）的推理引擎里，"同批次里还有谁"是由请求到达时间决定的——完全不可控、每次都不一样。这就是为什么同一个 prompt 连着问 vLLM 两次，temperature=0 也可能得到不同的回答：不是采样随机，是 kernel 不是 batch 不变的。

11.4.3 为什么推理引擎不肯放弃这件事

因为 batch 可变的 kernel 选择正是推理引擎的性能来源。

推理引擎的两大命根子：
  ① 连续批处理（continuous batching）：谁来了就插进当前 batch，谁完了就踢出去
     → batch 大小【每一步都在变】（§10.2.1 讲过 rollout 的长尾衰减，就是这个）
  ② 按当前形状挑最快的 kernel（cuBLAS/CUTLASS 的启发式、Triton 的 autotune）
     → 形状变了就换 kernel

要 batch 不变性 = 要求【任何 batch 下都用同一套切分参数】
               = 小 batch 时用不上 Split-K，Decode 的 GEMM 直接慢一大截
               = 放弃 ① 或放弃 ②

★ 这里出现了本章反复会遇到的守恒律的第一个实例：差异的来源，恰恰就是推理侧的优化本身（§11.9.5 会把它说完整）。batch 不变性不是"没人去修的 bug"，是一个明码标价的性能取舍。

11.4.4 怎么测：一个 20 行的自检脚本

这件事的好处是极易验证，不需要跑 RL，不需要训练引擎：

import torch

# 把同一条 prompt 复制 N 份，只看【第 0 条】的 logprob 变化
prompt_ids = tokenizer("……你的 prompt……").input_ids
ref = None
for bs in [1, 2, 4, 8, 16, 32, 64]:
    batch = [prompt_ids] * bs
    out = engine.forward_logprobs(batch)      # 各引擎接口名不同，取 batch[0] 的结果
    lp0 = out[0]                              # 第 0 条序列的 per-token logprob
    if ref is None:
        ref = lp0
    else:
        d = (lp0 - ref).abs()
        print(f"bs={bs:3d}  max|Δ|={d.max():.3e}  mean|Δ|={d.mean():.3e}  "
              f"bitwise_equal={torch.equal(lp0, ref)}")

判读：
  bitwise_equal 全部为 True         → 这个引擎是 batch 不变的（罕见，通常是开了确定性开关）
  max|Δ| 在 1e-6 ~ 1e-3 且随 bs 变   → 典型的 batch-variant，符合预期
  max|Δ| > 1e-2                      → 偏大，八成还叠加了别的问题（量化？Split-K 太激进？）

★ 这个脚本应该是任何 RL 项目排查训推一致性的第一步，因为它把问题关在推理引擎内部了——不涉及训练引擎、不涉及两套代码的对比。如果一个引擎连"自己和自己"都对不齐，那它和训练引擎对不齐就毫不意外。先把单边的不确定性压下去，再去谈两边的对齐。

⚠️ 顺带澄清一个常见误解：batch 不变性 ≠ 确定性（determinism）。确定性是"同样的输入跑两次结果一样"；batch 不变性是"同样的序列在不同批次里结果一样"。一个引擎可以是确定性的但不是 batch 不变的（固定 batch 下每次都一样，换个 batch 就变），这恰恰是最常见的情况。想做到训推一致，两条都要。

11.5 一张定位图：三类失配

到这里，机理讲完了。接下来要做的是分类——因为不同来源的差异，解法和代价完全不同，混在一起谈就没法做决策。

openPangu 的技术报告给了一套好用的三分类。先看这张图，后面三节（§11.6 / §11.7 / §11.8）分别展开一类：

训练端算出的 logprob  ≠  推理端算出的 logprob
  │
  ├── A 类：定义失配 —— 两边算的【根本不是同一个函数】
  │     ├── 精度格式不同（BF16 训练 vs INT8/FP8 推理）
  │     ├── MoE capacity factor（训练丢 token、推理 dropless）
  │     ├── 分词边界（detokenize → retokenize 改变了序列）
  │     └── position_id / mask / BOS 定义不同
  │     ·
  │     ├── 特征：差异【稳定复现】，量级【大】，可到 O(1)
  │     ├── 修法：改配置或改模型定义 ——【不是 kernel 问题】
  │     └── 代价：通常很小，但【最容易被漏掉】
  │
  ├── B 类：计算图重排 —— 同一个数学函数，【算法路径不同】
  │     ├── Split-K 切法不同（§11.2.3）
  │     ├── batch 不变性（§11.4）
  │     ├── MLA 吸收式 vs 非吸收式路径
  │     ├── MoE expert 累加顺序
  │     ├── TP / EP 度不同 → AllReduce 归约顺序不同
  │     └── 算子融合策略不同
  │     ·
  │     ├── 特征：差异【稳定复现】（同配置下每次一样），
  │     │         量级【小】（1e-4 ~ 1e-3）但沿层累积
  │     ├── 修法：强制两端走同一条算子路径
  │     └── 代价：牺牲推理性能
  │
  └── C 类：硬件非确定性 —— 两边【代码都一样】，调度顺序本身不定
        ├── AtomicAdd 到达顺序随机
        ├── NCCL 动态选 AllReduce 算法/拓扑
        └── FlashAttention 反向的原子累加
        ·
        ├── 特征：差异【不可复现】，同一进程跑两次都不同
        ├── 修法：打开确定性开关（三行配置）
        └── 代价：⚠️ 性能 −10% ~ −30%

怎么判断手上的问题属于哪一类，有一个干净的决策流程：

① 同一个引擎、同一个 batch、跑两次，结果 bitwise 一样吗？
      否  → 有 C 类问题。先关掉非确定性（§11.8），否则后面什么都测不准。
      是  → 往下

② 同一个引擎，把 batch 从 1 改到 32，同一条序列结果一样吗？（§11.4.4 的脚本）
      否  → 有 batch 不变性问题（B 类）。
      是  → 往下

③ 两个引擎的差异随层数【线性增长】还是【突然跳变】？
      逐层平滑增长  → B 类累积，去 §11.7 找是哪条路径
      某一层突然跳  → 要么是 A 类（那一层的定义不同），
                      要么是 MoE 路由跳变（§11.9）。看那一层是不是 MoE 层。

④ 差异大到 O(1)（logprob 差超过 1.0、甚至 token 都不一样）？
      → 几乎必然是 A 类。优先查：分词、mask、position_id、capacity factor。
        这一类【不要用 kernel 手段去修】，修不动的。

★ 这个顺序不能乱。 很多团队一上来就去抠 kernel（B 类），结果 C 类的随机性还在，测出来的每个数字都在跳，根本判断不了改动有没有效果。先消灭随机性，再消灭路径差异，最后才谈精度。

11.6 A 类：两边算的根本不是同一个函数

A 类的特点是数学上就不等价，跟浮点无关。好消息是它通常最好修，坏消息是它最容易被当成"数值噪声"漏掉。

11.6.1 最便宜的一条：分词边界与 TITO

先讲代价为零的那一条。

推理引擎生成完之后，如果接口传的是文本，训练引擎拿到文本还要重新分词，这一来一回可能得到不同的 token 序列：

推理引擎生成的 token id 序列:   [ 1734 , 29889 , 29871 ]
                                 "hello"   "."    " "

detokenize → 字符串:            "hello. "

训练引擎 retokenize:            [ 1734 , 29889 ]        ← 变成 2 个 token！
                                 "hello"  ". "           尾部空格被并进去了

→ 序列长度都不一样，逐 token 对齐的 logprob 直接错位
→ 这不是"差几个 ULP"，是【对错了位置】，差异 O(1)

BPE（Byte-Pair Encoding，字节对编码）分词器不保证 encode(decode(x)) == x，尤其在空格、emoji、不完整的 UTF-8 多字节序列、以及被采样中途截断的 token 上。

解法（TITO，Token-In-Token-Out）：接口层只传 token id，永远不经过文本。

# ✗ 错误做法（Text-In-Text-Out）
response_text = inference_engine.generate(prompt_text)
token_ids = tokenizer.encode(response_text)        # ← 可能和引擎内部的 token_ids 不同
logp_train = policy.forward(token_ids)

# ✓ 正确做法（Token-In-Token-Out，TITO）
token_ids, logp_infer = inference_engine.generate_with_logprobs(prompt_ids)
logp_train = policy.forward(token_ids)             # ← 同一份 token_ids，无分词差异

★ TITO 是全章唯一一条"零代价、纯赚"的改动：不改任何 kernel、不损失任何性能、消掉一整类 O(1) 量级的失配。如果你的系统还没做 TITO，别的什么都不用看，先做这个。

11.6.2 精度格式不同：量化

最常见的 A 类：训练用 BF16，推理用 INT8 / FP8 / INT4 权重。这时两端算的确实是两个不同的函数。

训练:  y = x @ W                        （W 是 BF16）
推理:  y = x @ dequant(quantize(W))     （W 先量化再反量化，已经不是同一个 W 了）

单层误差有多大，可以算出来。以 INT8 per-tensor 对称量化为例：

① 量化步长（scale）
      step = amax / 127
   其中 amax 是这个权重张量的绝对值最大值。
   对一个大的高斯分布权重张量（σ 是标准差），amax ≈ 4σ（⚠️ 经验近似，
   取决于张量大小；4096×4096 的张量最大值大约在 4~5 个 σ）
      → step ≈ 4σ / 127 = σ / 31.75

② 舍入误差
      round() 的误差在 ±step/2 内均匀分布，其标准差 = step / √12
      → 误差标准差 ≈ (σ/31.75) / 3.464 = σ / 110 = 0.91% × σ

③ 传到 GEMM 输出
      y = Σₖ xₖ wₖ。信号项和噪声项都沿 K 累积，都按 √K 增长，
      所以【相对误差不随 K 变化】，仍然是 ≈ 0.91%

所以 INT8 权重量化的单层相对误差约 0.9%（⚠️ 这是上面这个高斯模型推出来的量级，不是实测值；实际取决于权重分布、是否 per-channel、有无异常值）。

累积到整个模型：

层数 N 随机游走 0.9% × √N 线性累积 0.9% × N（最坏） 对应 ratio 偏移的量级
32 层 5.1% 29% ratio ≈ 1.05（若全部透传到 logprob）
80 层（LLaMA-3 70B） 8.1% 72% ratio ≈ 1.08

⚠️ 上表两列都要打折看。左列假设误差方向层间独立（对量化噪声基本成立，因为每层权重的舍入方向是无关的），右列假设完全同向（不现实）。而且 hidden state 的相对误差不等于 logprob 的绝对误差——中间还要过 §11.3.2 的 1 − p 衰减。这张表用来判断"量级是百分之几还是千分之几"，不要拿去做精确预算。

⚠️ 顺带修正旧版的一个笔误：2^{-(bits-1)} 对 INT8 是 2⁻⁷ = 1/128 = 0.78%，不是 1/127。两个数很接近，但 1/127 来自 amax/127 这个步长公式，和 2^{-(bits-1)} 不是一回事，混用会在推 INT4（amax/7）时出错。

解法一：QAT（量化感知训练） —— 让训练时就见到量化噪声，参数自己适应：

class FakeQuantizeINT8(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x, scale):
        # 前向：真的做一遍"量化→反量化"，把舍入误差引进来
        x_round = torch.round(torch.clamp(x / scale, -128, 127))
        return x_round * scale

    @staticmethod
    def backward(ctx, grad_output):
        # 反向：STE（直通估计器），当 round 不存在，梯度原样穿过
        # 理由：round 的导数几乎处处为 0，照实算的话梯度全没了
        return grad_output, None

class QATLinear(nn.Linear):
    def forward(self, x):
        scale = self.weight.abs().max() / 127.0
        w_fq = FakeQuantizeINT8.apply(self.weight, scale)
        return F.linear(x, w_fq, self.bias)

⚠️ QAT 缩小的是"量化带来的精度损失"，但它并不能让训推 bitwise 一致。 训练里的 FakeQuantize 走的是 BF16 乘法，推理里走的是真正的 INT8 GEMM，两者的累加器和归约顺序仍然不同（B 类问题原封不动地还在）。QAT 让模型对噪声更鲁棒，但噪声本身没消失。这一点经常被误解。

解法二：FP8 端到端 —— DeepSeek-V3 的路线，把训练前向也换成推理用的格式：

训练阶段：
  前向 GEMM：FP8（E4M3）      ← 和推理【完全相同】的格式
  反向 GEMM：BF16             ← 梯度不降精度，否则训不动
  权重更新：FP32 Master Weight

推理阶段：
  GEMM：FP8（E4M3）           ← 和训练前向相同

A 类失配：消除（同一种数值格式）
B 类失配：仍然存在（kernel 路径还是两套）

代价：要给每层维护动态的 scale factor（权重 scale、激活 scale 分开），并处理 FP8 溢出——E4M3 的动态范围只有 ±448，一个异常激活就能打穿。细节见 06 章。

11.6.3 MoE 的 capacity factor：最容易被漏掉的一条

这一条值得单独列，因为它看起来像 B 类，实际是 A 类。

训练侧（常见配置）：capacity_factor = 1.25
   每个专家在一个批次里最多接收  1.25 × (总 token 数 / 专家数) 个 token
   超额的 token【被丢弃】—— 它那一层的 MoE 输出直接变成 0（或只走残差）

推理侧（常见配置）：dropless（不丢）
   每个专家来多少收多少，用 grouped GEMM 处理变长分组

→ 同一个 token，训练时可能【被丢了】，推理时【没被丢】
→ 这一层的输出差异不是 1e-3，是 O(1)
→ 而且这个差异【和浮点毫无关系】，两边算的就不是同一个函数

⚠️ 靠任何 kernel 对齐都修不掉 capacity factor 失配，因为问题不在 kernel 里，在配置里。修法极其简单：训练侧也改成 dropless（或推理侧也设同样的容量上限）。代价很小（训练吞吐略降，因为要处理变长分组），收益是消掉一整类 O(1) 失配——这是全章性价比最高的改动之一，仅次于 TITO。

11.6.4 A 类的隐蔽成员：mask 与 position_id

最后一类容易漏的 A 类失配，是两端对"这个 token 在第几个位置"的理解不同：

失配点 典型表现 后果
position_id 起点 推理端从 prompt 长度开始计，训练端从 0 开始重新计 RoPE 旋转角不同 → attention 分数全变 → O(1) 差异
prompt 是否参与 loss 训练端算了 prompt token 的 logprob，推理端只给了 response 部分 对齐时整体错位
causal mask 的对角线 一端 mask = tril(ones)，另一端 mask = tril(ones, diagonal=-1) 每个 token 少看/多看自己
padding 方向 一端左 padding，一端右 padding，而 position_id 没跟着调整 有 padding 的序列全错
special token BOS/EOS 一端加了一端没加 序列整体偏移一位

★ 这五条的共同特征是"差异大到不像数值问题"：logprob 差 1.0 以上、PCC 掉到 0.9 以下、甚至肉眼能看出两边的 token 概率分布完全对不上。看到这种量级的差异，不要去查 kernel，先把这张表过一遍。一个立等可取的自查方法：把 temperature 设成 0、让推理引擎贪心解码一小段，然后让训练引擎对同一段做 teacher forcing 前向，看训练引擎给出的 argmax 是不是逐个 token 都和推理引擎选的一样。如果连 argmax 都对不上，问题一定在这张表里，不在浮点里。

11.7 B 类：同一个数学函数，两条算法路径

B 类的定义：两端算的是同一个数学式子，但算法路径不同，于是落到了 §11.2.3 那张表的不同行上。特征是差异小（1e-4 ~ 1e-3）但稳定复现、方向一致、沿层累积。

11.7.1 MLA 的吸收式路径：一次矩阵乘的重新结合

MLA（Multi-head Latent Attention，多头潜在注意力）把 K/V 投影拆成低秩两段，KV Cache 只存中间那个低维的 c_KV：

下投影（两端都做，结果都进 KV Cache）：
    c_KV = X @ W_DKV            X:(S, 7168) → c_KV:(S, 512)        ← DeepSeek-V3 的维度
                                              ↑ 缓存的就是它，两端一致

上投影（两端都需要，但【做的时机不同】）：
    K = c_KV @ W_UK             (S,512) → (S, n_head × 128)
    V = c_KV @ W_UV

注意力分数 score = Q · Kᵀ = Q · (c_KV @ W_UK)ᵀ。这里有两种算法：

路径 ①  非吸收式（Non-Absorptive）—— 训练 / Prefill 用
    第 1 步：K = c_KV @ W_UK           把 K 真的算出来（物化）
    第 2 步：score = Q @ Kᵀ            按普通 MHA 做，head_dim = 128

路径 ②  吸收式（Absorptive）—— Decode 用
    利用结合律改写：Q · (c_KV @ W_UK)ᵀ = Q · W_UKᵀ · c_KVᵀ = (Q @ W_UKᵀ) · c_KVᵀ
    第 1 步：Q' = Q @ W_UKᵀ            把上投影【吸收进 Q 侧】，只对 1 个 query token 做
    第 2 步：score = Q' @ c_KVᵀ        直接和缓存的 c_KV 点积，head_dim = 512
                                       所有 head 共享同一份 c_KV → 等价于 MQA
    （输出侧同理：attn @ V = attn @ (c_KV @ W_UV) = (attn @ c_KV) @ W_UV，
      W_UV 被吸收进输出投影）

为什么非要分两条路，一句话：谁的活少就走谁。

Prefill（S 个 query） Decode（1 个 query，缓存长 L）
非吸收式的额外开销 物化 K 一次，被 S 个 query 摊薄 每步都要把 L 个位置的 K 全物化一遍，开销 ∝ L
吸收式的额外开销 head_dim 从 128 变 512，注意力 FLOPs ×4 Q @ W_UKᵀ 只对 1 个 token 做，几乎免费
谁赢 非吸收式 吸收式

★ 这就是 MLA 训推不一致的根源，而且它是"设计出来的"：(c_KV @ W_UK) · Qᵀ 和 c_KV · (W_UKᵀ @ Q)ᵀ 数学上完全相等（矩阵乘满足结合律），但浮点乘加不满足——两条路的归约链长度、中间值量级、舍入次数全都不同。差异量级约 1–2 ULP / 层（⚠️ 量级估计），单层看不出来，80 层累下来就进了 §11.3.3 那张表的可见区间。

⚠️ 这一条基本上没法修。要求两端走同一条路，等于要么让 Decode 每一步物化整条 KV（Decode 直接慢几倍），要么让 Prefill 用 head_dim=512（FLOPs ×4）。正确的应对是承认它、在 §11.8 的 IS 修正层兜底，而不是去对齐 kernel。

⚠️ 顺带纠正旧版本章的一处硬错：旧版写"吸收式把 W_down @ W_K_up 合并成 W_K_eff，K = X @ W_K_eff，不需要存 c_KV"。这是反的——那样做会得到全尺寸的 K，KV Cache 一点都没压缩，MLA 就白做了。吸收式照样缓存 c_KV（这正是 MLA 省显存的全部来源），被吸收的是上投影矩阵，吸收方向是 Q 侧和输出侧，不是把两个投影合成一个更大的 K 投影。

11.7.2 MoE：专家输出的累加顺序

MoE 的输出是被选中的 k 个专家输出的加权和，这是一次归约，所以有顺序：

output = sum(gate[i] * expert_output[i] for i in selected_experts)

两端为什么会选不同顺序：

训练侧（典型实现）：按 Expert-ID 升序
    先把 token 按专家分组（sort by expert_id），各组做 grouped GEMM，
    结果按 expert_id 顺序写回并累加
    output = g[2]·e[2] + g[5]·e[5] + g[7]·e[7]

推理侧（典型实现）：按 gate 分数降序，或按【专家所在 GPU 的返回顺序】
    大 EP 部署下，token 被 all-to-all 发到不同卡上算，
    谁先回来先累加 —— 顺序由网络决定
    output = g[5]·e[5] + g[7]·e[7] + g[2]·e[2]

三个数相加，顺序不同 → §11.2.1 的老问题 → 结果差 1 ULP 量级
⚠️ BF16 下差异约 1e-3 相对量级（量级估计，取决于 gate 分数的分布）

这一条是可以修的，而且便宜：把两端都规定成"按 expert_id 升序累加"。代价是推理侧要多一次排序（对 k=8 的小数组，开销可以忽略），或者在 all-to-all 回收后加一次按 id 的重排。在 B 类里属于性价比最高的一条。

11.7.3 TP / EP 度不同：AllReduce 把顺序问题搬到了卡间

张量并行（TP）把一个 GEMM 沿 K 维切到多张卡，每卡算一个部分和，最后 AllReduce 求和。切几刀，就决定了这个和分几段来加——这就是 §11.2.3 的 Split-K，只不过切分发生在卡之间而不是 SM 之间。

K = 8192 的一个 GEMM：

训练 TP=8：   每卡算 K 的 1/8 = 1024 个乘加，得 8 个部分和
              Ring-AllReduce 按环形顺序两两相加 → 8 段的归约树

推理 TP=4：   每卡算 K 的 1/4 = 2048 个乘加，得 4 个部分和
              4 段的归约树

推理 TP=1（小模型单卡部署）：  1 段，一路串行加到底

           三种切法 = §11.2.3 表里的三行 = 三个不同的答案

⚠️ TP 度对齐的代价是"中等"：训练常用 TP=8，推理为了降低通信开销常用 TP=2 或 4（甚至纯数据并行）。强行对齐会让推理多付 AllReduce 的通信量，Decode 阶段本来就是访存瓶颈（§10.3.1），多一次 AllReduce 影响明显但不致命。能对齐就对齐，是 B 类里第二划算的一条。

⚠️ EP 度对齐的代价则大到不可行。大 EP（推理 EP=64 甚至更高）是 MoE 推理部署的命根子——每张卡只放少量专家，显存才装得下、grouped GEMM 才有足够的 token 打满 Tensor Core。要求训推同 EP，等于放弃这条优化。对大规模 MoE，这条直接划掉，别浪费时间。

11.7.4 算子融合策略不同

同一段数学，融不融合，中间值的精度就不一样：

不融合（训练侧常见，两个 kernel）：
    hidden = linear(x)          → 结果【写回 HBM】，写的是 BF16
    out    = rms_norm(hidden)   → 从 HBM 读回 BF16，内部转 FP32 求平方和

融合（推理侧常见，一个 kernel）：
    linear 的结果留在【寄存器/共享内存】里，是 FP32 累加器的原值
    直接喂给 norm，全程 FP32，一次都没降到 BF16

差异来源：中间那一次【BF16 舍入】做了还是没做
量级：< 1e-4（⚠️ 量级估计），是 B 类里最小的一项

同类的还有：causal mask 是在 softmax 前单独加（一次 BF16 element-wise），还是在 FlashAttention kernel 内部的 FP32 累加器上加；bias 是单独一个 kernel 还是 epilogue（GEMM 尾部）里顺手加完。

解法：让两端用同一套融合 kernel。torch.compile 能做到这一点——同一段 Python 代码，TorchInductor 对训练和推理生成同一个 Triton kernel（前提是输入形状也一样，否则又回到 §11.4 的 batch 不变性问题）。融合本身的原理见 05 章。

★ B 类四条的性价比排序（从高到低）：MoE 累加顺序（几乎免费）→ 融合策略统一（用 torch.compile）→ TP 度对齐（中等代价）→ MLA 路径 / EP 度（不可行，只能兜底）。照这个顺序修，别一上来就啃最难的那条。

11.8 C 类：连"自己和自己"都对不齐

C 类最讨厌的地方在于：代码完全一样、形状完全一样、batch 完全一样，同一个进程跑两次，结果还是不同。 它必须第一个被消灭，否则后面所有测量都在噪声里（§11.5 的决策流程第 ① 步）。

11.8.1 AtomicAdd：顺序由"谁先跑完"决定

C 类的来源几乎全是 AtomicAdd（原子加）。原子加保证"不丢更新"，但不保证顺序——哪个线程块先到就先加谁。

Split-K = 4 的 GEMM，4 个 SM 各算一段部分和，用 AtomicAdd 汇总到同一块显存：

第 1 次运行：SM 3 先完成 → acc = ((0 + p3) + p1) + p0) + p2
第 2 次运行：SM 1 先完成 → acc = ((0 + p1) + p2) + p3) + p0
                              ↑ 两次的【结合方式不同】→ §11.2.1 的老问题

到达顺序取决于：SM 的调度、L2 命中情况、同时在跑的其他 kernel、
                GPU 温度导致的时钟抖动 …… 全都不可控

★ 注意这和 §11.4 的 batch 不变性是两件事：batch 不变性是"形状变了 → kernel 选择变了"，是确定的函数关系（同样的 batch 每次结果一样）；AtomicAdd 是"同一个 kernel 内部的到达顺序随机"，同样的输入每次都可能不同。前者是 B 类，后者是 C 类。

11.8.2 三个惯犯与对应的开关

# 来源 什么时候出现 关掉的方法 代价
① Split-K GEMM 的原子归约 K 很大、M/N 很小（Decode、小 batch 训练） torch.use_deterministic_algorithms(True) ⚠️ 约 −10% ~ −30%（视形状）
② FlashAttention 反向的 dK/dV 累加 反向传播，多个 Q block 对同一个 KV block 贡献梯度 flash_attn_func(..., deterministic=True) ⚠️ 反向约 −10% ~ −15%

11.8.3 一个容易踩的坑：cudnn.benchmark

torch.backends.cudnn.benchmark = True 的行为：

  第一次遇到某个形状 → 把所有候选 kernel 都跑一遍计时 → 选最快的那个 → 缓存
                        ↑
            "最快的那个"取决于【当时机器的状态】：
            别的进程在不在跑、GPU 温度多少、时钟降没降频

  → 同一份代码，在两台机器上（甚至同一台机器的两次运行）可能选中【不同的 kernel】
  → 不同的 kernel = 不同的归约顺序 = §11.2.3 表里的不同行

⚠️ cudnn.benchmark = True 是很多人默认打开的性能选项，它会把一个本该是 C 类的随机性固化成 B 类的稳定差异——更隐蔽，因为单次运行内部完全可复现，你会以为一切正常，直到换台机器发现对不上了。做训推一致性对比时必须关掉它。

11.8.4 C 类的性价比：为什么它应该第一个修

C 类的特点：
  ✓ 修法【极其简单】—— 三个开关，几行代码，不用改任何 kernel
  ✓ 代价【明确可预估】—— 10~30% 的性能，而且只需要在【生成 logp_old 的那条路径】上付
  ✓ 收益【是后续一切工作的前提】—— 没有它，你测不出任何改动的效果

一个实用的折中：
  【不要】给整个训练开确定性模式（反向传播那 10~15% 太贵）
  【只给】Rollout 路径 + 算 logp_old 的那次前向开确定性
      → 这条路径本来就不做反向，FlashAttention 反向的代价根本不产生
      → GEMM 的 10~30% 只落在前向上，而 Rollout 阶段的瓶颈是访存不是算力
        （§10.2、§10.8 都算过），实际端到端损失远小于 10%

★ 这是全章一条很重要的工程判断：确定性开关的代价被普遍高估了，因为大家默认要"全程确定性"。实际上只有 behavior policy 那条路径需要确定性——它产出的 logp_old 要被后面所有梯度步反复引用，它必须稳；训练侧的前反向传播是一次性消费，稍有抖动无所谓。按路径开，不要按进程开。

11.9 MoE 为什么特殊：离散路由把小误差整流成大跳变

A / B / C 三类对 dense（稠密）模型和 MoE（Mixture of Experts，混合专家）模型都成立。但 MoE 多了一个 dense 没有的结构，它会把上面所有的小误差放大成 O(1) 的差异。

11.9.1 误差放大器：topk 是一个不连续函数

dense 模型里误差是连续传播的：输入扰动 1e-3，输出扰动也在 1e-3 量级，可控、可估、可用 §11.3 的模型预算。

MoE 在每一层多了一步 router（路由器）：

scores  = softmax(x @ W_router)                        # 给 E 个专家打分
experts = topk(scores, k)                              # ← 离散决策：选出 k 个
output  = sum(scores[i] * expert_i(x) for i in experts)

topk 是不连续的。当两个专家的分数接近时，1e-4 的扰动就足以让排序翻转。把数代进去看：

scores[3] scores[17] scores[21] top-2 选中
推理侧 0.2500 0.1032 0.1029 {3, 17}
训练侧 0.2500 0.1030 0.1031 {3, 21}
差 0 −0.0002 +0.0002 换了一个专家 
输入端的差异：  2e-4          ← 微不足道
输出端的差异：  |expert_17(x) − expert_21(x)|
                这是【两个完全不同的 FFN】的输出之差
                两个独立训练出来的专家，输出根本不相关
                → 差异是 O(1)，和隐状态本身同一个量级

★ 这就是 MoE 的特殊之处：它把连续的数值噪声整流（rectify）成了离散的跳变。 同样一份 kernel 噪声，dense 模型能忍（误差按 §11.3 的模型线性传递），MoE 忍不了（误差被一个阶跃函数放大了几个数量级）。

三个会放大这个效应的因素：

因素 为什么放大 举例
专家数 E 越大 E 个分数挤在总和为 1 的区间里，E 越大相邻分数的间隔越小，翻转所需的扰动越小 E=256（DeepSeek-V3）比 E=8（Mixtral）敏感得多
层数越深 前面层的跳变改变了隐状态 → 下一层的输入差异更大 → 跳变概率更高 误差沿深度自我放大，不是线性累积而是正反馈
序列越长 Decode 逐 token 推进，前面 token 的跳变污染 KV Cache，影响后面所有 token 长 CoT（思维链）的 RL 尤其严重

⚠️ 第二条是 MoE 最恶劣的性质：dense 模型的误差累积是 §11.3.1 的 δ×√N 或 δ×N，最坏线性；MoE 的路由跳变是正反馈回路——跳变让隐状态偏得更多，偏得更多又让下一层更容易跳变。实践中的表现是逐层 PCC 曲线在某一层之后断崖下跌，而不是平滑下降。

11.9.2 一个比 PCC 更早报警的指标：top-k 重合度

因为路由跳变是离散的，它有一个直接可测的指标：

top-k 重合度 = (训练侧选出的专家集合 ∩ 推理侧选出的专家集合) 的大小 / k
              对每个 token、每一层分别算，然后取平均

例：k=8，某 token 训练侧选 {2,5,7,11,19,33,40,88}
             推理侧选 {2,5,7,11,19,33,40,91}
    交集 7 个 → 重合度 = 7/8 = 87.5%

★ top-k 重合度比 PCC 更早暴露问题。 PCC（Pearson Correlation Coefficient，皮尔逊相关系数）算的是两组 logprob 的线性相关性——少数 token 跳变时，PCC 仍然可能有 0.995 的好看数字（因为绝大多数 token 好好的），而重合度已经掉到 90% 了。MoE 的训推一致性监控必须单独看这一项，不能只看 PCC 和 ratio。经验阈值：重合度 > 95%。

11.9.3 MoE 独有的失配源清单

来源 类别 量级 怎么修 代价
capacity factor（训练丢 token / 推理 dropless） A 类 O(1) 两端统一用 dropless 小 —— 性价比最高
Expert 累加顺序 B 类 ~1e-3 两端都按 expert_id 升序累加 几乎为零
EP 度不同 B 类 ~1e-3 / 层 训推同 EP 大到不可行（见 §11.7.3）
路由跳变 B 类的放大器 O(1) R3 / Masked R3（下一节） 接口契约改造 + 调参

⚠️ 注意"路由跳变"那一行的定语：它本身不产生任何误差，它是把已有误差放大的机制。所以修它的正确做法是先修上游——先把 A 类、C 类清掉，把进入 router 的隐状态误差压下去，跳变率自然就降了。上游不清干净就直接上 R3，是在用一个重药去压一个本可以便宜解决的症状。

11.9.4 R3 / Keep Routing 的天花板

针对路由跳变，最直接的想法是：推理时把每个 token 选中的专家记下来，训练时强制走同一套。openPangu 的 R3（Rollout Routing Replay，回放推理侧路由）就是这个思路。

这确实消掉了跳变，但方案本身有天花板。openPangu 的 Masked R3 记录了这个坑：

现象：隐状态随 MoE 层加深而累积发散（§11.9.1 的正反馈）
      此时在【深层】强制全量重放推理侧的路由
        → logits 被严重扭曲
        → PCC 骤降
        → 可能梯度爆炸

原因：训练侧这一层的输入 x_train 已经和推理侧的 x_infer 不一样了。
      强行让 x_train 走 x_infer 选的专家，
      = 用【错的专家】算【错的输入】
      —— 比不对齐【更糟】

解法（Masked R3）：自适应阈值。
      只有当训练侧自己算出的 top-k 与录制值【重合度超过阈值】时，
      才对该 token 重放；否则放它自己走。

⚠️ 这是「一致性」和「正确性」的一次直接冲突，不是实现粗糙。 全量重放不是越多越好：一致性要求"和推理侧一样"，正确性要求"给定这个输入，选对的专家"，当输入已经偏了，这两个要求就指向不同的答案。Masked R3 把这个矛盾挪到了一个可接受的位置，但没有消除它——这是 R3 路线不能称为「根治」的根本原因。

R3 的另一重成本在接口层。推理引擎交给训练引擎的契约要扩展：

现在的契约：   (token_ids, logprobs, finish_reason)
                     ↓
R3 需要的契约： (token_ids, logprobs, finish_reason,
                 routing_records,      ← 每 token 每层选了哪 k 个专家
                 sampling_mask, ...)

数据量：  L 层 × k 个专家 id × 每个 token
          80 层 × 8 个 × 1 字节 = 640 B/token
          一条 4096 token 的序列 → 2.6 MB 的额外路由数据
          （对比 §10.1.3：rollout 上行本来只有 3 MB 量级，这一下翻倍）

⚠️ 所有推理引擎要吐出路由、所有传输层要传路由、所有训练引擎要吃路由。 这是生态成本，比技术成本更难推动——你改得动自己的代码，改不动 vLLM 的上游接口。系统架构层的展开见 强化学习训练框架 04-训推一致性 §4.4。

11.9.5 一条守恒律，和一条不该越过的边界

守恒律：

★ 差异的来源，恰恰就是推理侧的优化本身。

把前面几节的对策一字排开就看得很清楚：

Absorptive MLA   ← 为了 Decode 不物化 KV        （§11.7.1）
Split-K / 变 batch 的 kernel 选择 ← 为了小 batch 打满 SM  （§11.4）
量化              ← 为了显存和带宽              （§11.6.2）
大 EP 部署        ← 为了 MoE 装得下              （§11.7.3）
dropless          ← 为了不丢 token              （§11.6.3，这条反而是推理更"对"）
AtomicAdd         ← 为了不做额外一趟归约         （§11.8.1）

每一项都是拿【改变计算路径】换吞吐。
要求 bitwise 一致 = 要求推理引擎按训练引擎的方式算 = rollout 慢回去。
而 §10.8 算过：RL 的时间【绝大部分花在 rollout 上】。

所以「不根治」在工程上是主动取舍，不是能力不足。

边界：还有一半的 ratio 偏离根本不该被修掉。

在异步 RL 里，rollout 用的是 N 步之前的旧权重，训练用的是当前权重：

ratio 的偏离 = 数值失配（A / B / C 三类）          ← 该修，本章讲的全是它
             + off-policy 偏移（异步设计的固有属性）  ← 【不该修】，只能用 IS 修正

把 kernel 做到 bitwise 一致，只能消掉第一项。
第二项是算法要的：它正是 PPO 的 clip 机制存在的理由（10 章 §10.5.4）。

★ 「训推一致性」这个词混装了两件事。 判断一个方案有没有「根治」之前，先要分清在谈哪一半。一个干净的诊断办法（10 章 §10.5.4 给过）：把配置改成「一批数据只做一次更新 + logp_old 由训练引擎自己算」，此时 ratio 应当精确等于 1。如果不是，剩下的偏离 100% 是数值失配，和 off-policy 没有半点关系——这是把两半分开的唯一可靠手段。

11.10 五条对策，各自的代价

到这里所有机理都讲完了。这一节回答工程上的那个问题：手上这个系统，到底该上哪一条？

先把选项摆开。它们不是互斥的，但第一步必须先在 ① 和 ② 之间选边——这是一个理论立场问题，不是调参问题。

11.10.1 ①：重算 logprob（让 ratio 恒等于 1）

最常见的做法：丢掉推理引擎给的 logprob，用训练引擎重新跑一次前向算 logp_old。

rollout 产出:  (token_ids, logp_infer)
                              ↑ 【扔掉不用】

训练引擎:  logp_old = policy.forward(token_ids)    ← 额外一次前向，no_grad
           logp_new = policy.forward(token_ids)    ← 带梯度那次

第 1 个 inner epoch：两次前向用的是【同一份权重、同一套 kernel、同一个 batch】
                     → Δ ≡ 0，ratio ≡ 1（浮点意义上精确）
第 2 个 inner epoch 起：权重确实变了，ratio 才开始偏离 —— 而这部分是算法要的

代价：多一次完整前向。按 10 章 §10.3.1 的账，Update 阶段前向:反向 ≈ 1:2，多一次前向等于 Update 阶段 +33%；而 Update 阶段只占端到端一小部分（§10.8 说时间大头在 rollout），⚠️ 端到端大约 +5%~10%（量级估计，取决于 rollout 占比）。

⚠️ 这条路的真正问题不是算力，是理论上它错了。 IS 修正的前提是 logp_old 必须来自真正产生这批数据的那个策略（behavior policy，行为策略）。数据是推理引擎采出来的，所以推理引擎才是 behavior policy。用训练引擎重算的 logp_old 顶替它，等于在假装"数据是训练引擎采的"——训推失配没有被消除，只是被藏进了"梯度估计的偏差"里，从监控上彻底消失了。你的 ratio 会很漂亮地贴着 1，clip fraction 会很低，而偏差照样在每一步推着梯度走。它让问题不可观测，这比问题本身更危险。

11.10.2 ②：老实用推理引擎的 logprob 做 behavior policy

理论正确的做法：logp_old := logp_infer，直接用推理引擎给的那份。

好处：① 理论上对 —— behavior policy 就是它
      ② 零额外算力 —— 推理引擎生成时顺手就算出来了
      ③ 【失配变得可观测】—— ratio 的偏离就是失配本身，
         clip fraction、ratio 标准差直接反映数值健康度

坏处：失配不再被隐藏，于是 §11.3.4 那张表变成现实：
      σ = 0.10 → 6.8% 的 token 被 clip 掉，梯度归零
      σ = 0.15 → 22.4% 被 clip，数据白采五分之一

★ ②是"把病显出来"，①是"把病盖住"。 选 ② 意味着你必须真的去治（③④⑤），但至少你能看见治得怎么样。推荐路径是选 ②，然后配 ③ 或 ④ 兜底。

11.10.3 ③：TIS —— 承认这是两个分布，加一个截断权重

TIS（Truncated Importance Sampling，截断重要性采样）的思路：既然训练引擎的分布 π_train 和推理引擎的分布 π_infer 确实是两个不同的分布，那就老老实实再做一次重要性采样修正，把这个偏差补回来。

# 在原有 PPO / GRPO 的 loss 之外，再乘一个 TIS 权重
# logp_infer：推理引擎给的（真正的 behavior policy）
# logp_old  ：训练引擎算的 logp_old（策略更新起点）
tis_w = torch.exp(logp_old - logp_infer).clamp(max=C)   # C 常取 1.0 ~ 2.0
                #   ↑ 这个比值【就是训推失配本身】

ratio = torch.exp(logp_new - logp_old)                  # 原来的 PPO ratio 不变
obj   = torch.min(ratio * adv, ratio.clamp(1-eps, 1+eps) * adv)
loss  = -(tis_w.detach() * obj).mean()                  # ★ tis_w 必须 detach

它在做什么（一句话）：
  给"训练引擎和推理引擎分歧大"的那些 token 【降权】，
  给分歧小的 token 保持原权重。
  截断上限 C 防止个别 token 的权重飙到天上（§10.5.3 那个 exp 爆炸问题）。

它【不】做什么：
  不消除差异，不改 kernel，不改推理引擎。
  它是【统计层的修正】，不是【数值层的修复】。

代价：几乎为零的算力（一次 exp 和一次 clamp），但要求接口把 logp_infer 传过来（TITO 的自然扩展），外加一个超参 C 要调。

11.10.4 ④：CISPO —— 裁权重而不是裁梯度

CISPO（Clipped IS-weight Policy Optimization，截断重要性权重策略优化，MiniMax-M1 提出）针对的是 PPO clip 的一个具体毛病：被 clip 的 token 梯度精确归零（10 章 §10.5.2 那张表），而被 clip 的恰恰是最有信息量的 token（§11.3.2 的 1−p 分析）。

PPO 的做法：objective = min(r·A, clip(r,1−ε,1+ε)·A)
            r 越界 → 取常数支 → 【梯度为 0】→ 这个 token 白采了

CISPO 的做法：objective = sg(clip(r, 1−ε_lo, 1+ε_hi)) · A · log π(a|s)
                          ↑ stop-gradient：权重只当系数，不参与求导
              r 越界 → 权重被夹住，但 log π 那一项的【梯度照常流】
              → 【所有 token 都贡献梯度】，只是贡献的大小被限住了
PPO clip CISPO
ratio 越界的 token 梯度 = 0，完全丢弃 梯度 ≠ 0，权重被夹到边界值
有效样本利用率 σ=0.15 时损失 22%（§11.3.4） 100%
对训推失配的鲁棒性 差 —— 失配直接吃掉样本 好 —— 失配只影响权重大小
代价 — 换目标函数，需要重新调 ε_lo / ε_hi

⚠️ 旧版本章把 CISPO 写成"当 ratio 偏离超过阈值时直接 mask 掉该 token"。这正好说反了——CISPO 的全部卖点就是不丢弃 token。丢 token 是 PPO clip 的行为，CISPO 是来救这个的。

11.10.5 ⑤：确定性 + batch 不变的 kernel 库（真正的根治）

唯一从物理上消除差异的路线：给关键算子准备一套"归约方式固定、不随形状变化"的实现。

batch 不变性要求（§11.4）：
  ├── GEMM 的分块参数（BM, BN, BK）【不随 batch 变化】
  ├── Split-K 的切分数【固定】，或干脆不用 Split-K
  ├── Norm / Softmax 的线程布局固定，归约树形状固定
  └── FlashAttention 的 split-KV 块数固定（不按剩余 SM 动态分）

确定性要求（§11.8）：
  ├── 禁用所有 AtomicAdd，改确定性归约
  ├── AllReduce 固定算法和拓扑（NCCL_ALGO=Ring, NCCL_PROTO=Simple）
  └── 关掉 cudnn.benchmark 和所有 autotune

⚠️ 代价：约 −10% ~ −30%（相对"不惜代价高性能"模式，随形状波动）
适用范围：只给【生成 logp_old 的 rollout 路径】用，不给训练路径用（§11.8.4）

★ 这条路线的公开参考实现是 Thinking Machines Lab 的 batch-invariant-ops（挂在 vLLM 上），它给出的正是本章 §11.4.2 那三类惯犯的确定性替代：RMSNorm、matmul、attention。如果你要自己做，那三个算子就是全部工作量的 90%。

一条因果链，五级放大

环节 发生了什么 量级 在哪一节

三类失配，三种修法

类别 判据 典型成员 修法 代价
A 定义失配 差异 O(1)、稳定复现、连 argmax 都对不上 分词、capacity factor、position_id、量化 改配置或改定义，不是 kernel 问题 通常很小
B 计算图重排 差异 1e-4~1e-3、稳定复现、沿层平滑累积 Split-K、batch 不变性、MLA 吸收、TP/EP、融合 强制两端同一条算子路径 牺牲推理性能

两个必须澄清的说法

  • 浮点加法满足交换律（a+b = b+a），不满足结合律（(a+b)+c ≠ a+(b+c)）。 真实 kernel 里遇到的所有顺序问题全是结合律问题（§11.2.4）。
  • batch 不变性 ≠ 确定性。 前者是"换个批次结果不变"（B 类），后者是"跑两次结果不变"（C 类）。一个引擎可以是确定性的却不是 batch 不变的——这恰恰是最常见的情况（§11.4.4）。

MoE 的额外一层

top-k 是【离散决策】→ 把连续的 1e-4 噪声整流成 O(1) 的输出跳变
                    → 且沿深度【正反馈】（跳变改变隐状态 → 更容易跳变）
                    → 表现为逐层 PCC 曲线【断崖】而非平滑下降

必测指标：top-k 专家重合度 > 95%（PCC 还好看的时候它已经在掉了）
必做改动：capacity factor 两端统一 dropless（A 类，改配置即可，最划算）
最后一招：Masked R3 —— 且【必须带阈值】，全量重放 = 用错的专家算错的输入

一条守恒律，一条边界

守恒律：差异的来源，恰恰就是推理侧的优化本身。
        bitwise 一致 = 放弃推理优化 = rollout 慢回去
        → 「不根治」是主动取舍，不是能力不足

自测三题（答案在下面，都能拿纸笔算）

  1. BF16 下把 x = [1.0, 2⁻⁸, 2⁻⁸, 2⁻⁸, 2⁻⁸] 这 5 个数加起来。（a）一个线程从头串到尾（Split-K = 1）得到多少？（b）切成两段——段 A 只含 x[0]，段 B 含后 4 个——再合并，得到多少？（c）数学真值是多少？提示：BF16 在 1.0 附近的相邻可表示值是 1.0 和 1.0078125，中间那个点按"平局取偶"处理。
  2. 某 RL 任务序列长 n = 256，每个 token 的 Δ = logp_train − logp_infer 标准差 σ = 0.05（按 §11.3.4 的表，这一档"可以接受"）。如果框架用的是序列级 ratio（把整条序列的 Δ 求和再取 exp），序列级 ratio 的 ±1σ 区间是多少？还能用吗？
  3. 某层的 logit 因为归约顺序不同产生了 0.01 的误差。对于一个模型很确定的 token（p = 0.9）和一个模型很犹豫的 token（p = 0.02），各自的 logprob 误差是多少？对应的 ratio 是多少？哪一个更危险，为什么这件事对 RL 特别糟糕？

参考答案

  1. （a）1.0。 第一步累加器 = 1.0；之后每一步都是 1.0 + 0.00390625 = 1.00390625，而这个值正好卡在 1.0 和 1.0078125 的正中间，IEEE 的"就近舍入、平局取偶"选尾数为偶的 1.0——4 个小数一个都没加进去。（b）1.015625。 段 A = 1.0；段 B 是 4 个同量级的数相加，4 × 2⁻⁸ = 0.015625，全程无损；合并 1.0 + 0.015625 = 1.015625，这个值在 BF16 里精确可表示（= 1.0 + 2 ULP）。（c）真值 = 1.0 + 4 × 0.00390625 = 1.015625，也就是说（b）精确、（a）差了 2 个完整 ULP（相对误差 −1.54%）。两边都严格遵守 IEEE 754，没有 bug——这就是 §11.2.3 的全部内容。
  2. 序列级 Δ 的标准差 = σ × √n = 0.05 × √256 = 0.05 × 16 = 0.8。序列级 ratio 的 ±1σ 区间 = [exp(−0.8), exp(0.8)] = [0.449, 2.226]。完全不能用——有相当一部分序列的 ratio 会落在 2 倍以上或 0.5 倍以下，PPO 的 clip 区间 [0.8, 1.2] 会把绝大多数序列裁掉。结论：token 级完全健康的配置，换成序列级 IS 就直接失控，因为误差按 √n 累积而 exp() 对它做指数放大。做诊断永远看 token 级分布（§11.3.4 末尾）。
  3. 用 ∂logprob/∂logit = 1 − p（§11.3.2）：p = 0.9 的 token：误差 = 0.01 × (1 − 0.9) = 0.001，ratio = exp(0.001) = 1.0010；p = 0.02 的 token：误差 = 0.01 × (1 − 0.02) = 0.0098，ratio = exp(0.0098) = 1.00985。后者的偏离量（0.985%）是前者（0.100%）的约 9.8 倍，犹豫的 token 更危险。对 RL 特别糟糕的原因是：模型犹豫的 token 恰恰是最有学习价值的那些（确定的 token 没什么可学），所以数值失配是在定向破坏最重要的训练信号——它不是均匀地加噪声，而是专挑要害。这也解释了 §11.1.2 第 ⑤ 步"被裁掉的往往是最该学的 token"。
