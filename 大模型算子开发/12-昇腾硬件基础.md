**本章关键词**

**NPU**（Neural Processing Unit，神经网络处理器）—— 相对 GPU 的通用并行架构，NPU 指为神经网络定制的专用芯片。昇腾属于此类。  
**DSA**（Domain Specific Architecture，特定域架构）—— 只为一类负载设计的芯片架构，代价是通用性。  
**达芬奇架构**（DaVinci Architecture）—— 华为自研的 AI 计算架构，属于 DSA。  
**AI Core** —— 达芬奇架构的基本计算单元，地位相当于 NVIDIA 的 SM（Streaming Multiprocessor，流式多处理器）。  
**Cube / Vector / Scalar**（矩阵单元 / 向量单元 / 标量单元）—— AI Core 内部三类计算单元，分别做矩阵乘、向量运算、流程控制。  
**AIC / AIV**（AI Cube / AI Vector，矩阵核 / 向量核）—— 910B 起 Cube 和 Vector 被拆成两种独立的核，AIC 指矩阵核，AIV 指向量核，数量比 1 : 2。  
**GM**（Global Memory，全局内存）—— 昇腾对片外主存（HBM，高带宽显存）的称呼，相当于 GPU 的 HBM / Global Memory。  
**UB**（Unified Buffer，统一缓冲区）—— Vector 单元唯一的片上工作区，相当于 GPU 共享内存的一部分角色。  
**L1 Buffer** —— AIC 侧的片上中转缓冲，GM 和 L0 之间的那一跳落在这里。**它是 scratchpad（便笺存储）不是 cache**，名字带 L1 极易误解。  
**L0A / L0B / L0C** —— Cube 单元专用的三块片上缓冲：左矩阵、右矩阵、结果累加。GPU 上没有对应物。  
**Scratchpad**（便笺存储）—— 容量由程序员显式管理的片上存储，**不会自动填充**，和 cache 的根本区别就在这里。  
**MTE**（Memory Transfer Engine，存储转换引擎）—— 专门负责各级存储之间搬运和格式转换的**独立硬件流水线**。MTE1 管 L1→L0A/L0B，MTE2 管搬入（GM→L1/UB），MTE3 管搬出（UB→GM）。  
**FixPipe**（Fixed Pipe，随路后处理流水）—— 把 Cube 的结果从 L0C 搬出去的通路，顺路做量化、ReLU、精度转换。  
**五级流水** —— Scalar / MTE1 / MTE2 / MTE3 / Cube-Vector 这几条能同时干活的硬件流水线。昇腾掩盖延迟的**唯一**手段就是把它们错开排满。  
**MTE Bound**（搬运受限）—— 算力没打满、HBM 带宽也没打满，但 MTE 流水占满了。屋顶线模型不覆盖的第三类瓶颈，见 §12.6。  
**FRACTAL_NZ**（分形 NZ 格式）—— 昇腾片上矩阵的摆放格式：先切 16×16 小块，块内行优先、块间列优先。  
**HCCS**（Huawei Cache Coherence System，华为缓存一致性互联）—— 华为自研的片间高速互联，地位相当于 NVLink。  
**UB 总线**（Unified Bus，统一总线）—— CloudMatrix 超节点使用的全互联总线。注意：**和上面的 Unified Buffer 是两个完全不同的东西，昇腾体系里这个缩写撞车了**，看到 UB 要先判断语境。  
**CANN**（Compute Architecture for Neural Networks，神经网络计算架构）—— 昇腾的软件栈总称，地位相当于 CUDA。  
**soc_version**（芯片型号标识）—— 如 `Ascend910B3`。昇腾的算子和硬件参数都按它区分，**同一个"910B"下面的子型号差异可以很大**。

## 12.1 一句话说清两者的分歧

### 12.1.1 两条技术路线

第 01 章讲过，GPU 的哲学是 **SIMT**（Single Instruction Multiple Threads，单指令多线程）：堆一万多个弱核，让它们用同一条指令处理不同数据。矩阵乘不是 GPU 的专属任务，它只是"恰好很适合"GPU 的一类任务——所以 NVIDIA 后来才要额外加 Tensor Core 这种专用单元打补丁。

昇腾反过来：**先认定矩阵乘是主要任务，再围绕它造芯片**。

```
NVIDIA（通用 → 专用）：
  一堆通用 CUDA Core  →  发现 AI 火了  →  加装 Tensor Core
  结果：一个 SM 里，通用单元和专用单元并存，靠编译器决定用哪个
       用不上 Tensor Core 的时候，还有 CUDA Core 兜底（慢一档，但能跑）

华为昇腾（一开始就专用）：
  先问"AI 负载是什么"  →  答：矩阵乘 + 向量运算 + 少量控制
  →  直接造三种专门的硬件单元：Cube / Vector / Scalar
  结果：一个 AI Core 里【没有通用核】，每种运算有且只有一条硬件通路
       用不上 Cube 的时候，【没有兜底】——只能改数据布局让它用得上
```

最后那两行括号里的对比，是本章后面所有内容的根源。**"没有兜底"会在三个地方反复出现**：维度对不齐没有慢速通用路径可退（§12.2.2）、延迟没有 warp 轮转可掩盖（§12.3.2）、搬运有自己的独立流水线因而会自己先成为瓶颈（§12.6）。

### 12.1.2 概念存废清单：第 01 章有一半要作废

先把结论摆出来，细节和逐条理由在 §12.3.2：

| | NVIDIA GPU | 昇腾 NPU |
|---|---|---|
| 设计出发点 | 通用并行，AI 是应用之一 | AI 专用（DSA） |
| 并行模型 | SIMT，你写单线程代码，硬件管 32 个 | 显式多核 + 核内流水，你自己切数据 |
| 片上存储 | Cache 为主（L1/L2 自动填充） | **Scratchpad 为主（L1/L0/UB 全靠你手动搬）** |
| 数据搬运 | 访存指令触发，硬件透明 | **MTE 显式搬运，要写代码** |
| 矩阵乘单元 | Tensor Core，warp 级接口 | Cube，核级接口 |
| 最小调度单位 | Warp（32 线程） | 无对应物——**昇腾没有 warp** |
| 延迟怎么掩盖 | **超额订阅**：一个 SM 挂 64 个 warp 轮转 | **手工排流水**：五条流水线错开 |
| 计算核的数量级 | 132 个 SM | ⚠️ 20 个 AIC + 40 个 AIV（910B3 口径） |

最后两行是全章的主轴。**132 对 20，差了将近 7 倍**——这不是"昇腾核少所以慢"（单核的 Cube 比一个 SM 的 Tensor Core 强），而是**调度弹性完全不同**：GPU 上几千个 Block 去填 132 个 SM，某个 Block 慢一点会被别的 Block 填上；昇腾只有 20 个核，一个核慢就整个算子慢，没有任何弹性。

> ★ **一句话记住这一章**：GPU 用"人多"掩盖延迟，昇腾用"排班"掩盖延迟。人多是硬件自动的，排班要你手写。

## 12.2 达芬奇架构：AI Core 内部长什么样

### 12.2.1 三类计算单元，加一类搬运单元

一个 AI Core 内部的分工是这样的（✅ CANN 官方文档）：

```
一个 AI Core（达芬奇）内部
  │
  ├── Cube    矩阵单元   只做一件事：16×16×16 的矩阵乘累加
  │                       大模型 90% 以上的 FLOP 都在这里产生
  │
  ├── Vector  向量单元   除矩阵乘以外的一切：激活、归一化、逐元素
  │                       加减乘除、类型转换、规约。指令集非常丰富
  │
  ├── Scalar  标量单元   一个小 CPU：循环控制、分支判断、算地址
  │                       它不干活，它指挥干活
  │
  └── MTE ×3  搬运引擎   各级存储之间搬数据，顺手做格式转换
                          ★ 独立硬件流水线，能和计算【真正同时】发生
```

抽象的分工看不出份量，**把一层 Transformer 的算子摊开点名**，就清楚了：

| 这个算子 | 谁来算 | 在一层里占的 FLOP（⚠️ 量级，随模型结构浮动） |
|---|---|---|
| QKV 投影、Attention 输出投影 | **Cube** | 大头 |
| Attention 内部的 `Q×Kᵀ` 和 `P×V` | **Cube** | 大头 |
| FFN 的两个（或三个）矩阵乘 | **Cube** | 最大头 |
| Softmax、RMSNorm、SiLU、残差加、RoPE | **Vector** | 合计通常 < 10% |
| 量化 / 反量化、精度转换（Cast） | **Vector** | 很小 |
| 循环控制、tiling 参数、每一块的地址计算 | **Scalar** | 0（它不产生 FLOP） |
| 上面每一步的数据进出片上 | **MTE** | 0（它也不产生 FLOP，但常常是瓶颈） |

这张表解释了两件事。

**第一，为什么 Vector 单元不能砍。** Vector 算子只占不到 10% 的 FLOP，但它们的**个数**远多于 Cube 算子——一层里矩阵乘大概 6～7 个，Vector 算子二三十个。而且它们全是 [02 章 §2.3](02-屋顶线与性能剖析.md) 里那种算术强度 0.1 量级的 Memory Bound 算子，耗时占比远高于 FLOP 占比。

**第二，为什么 AIV 的数量是 AIC 的两倍**（§12.2.3）。⚠️ 这是一个合理的解释而非官方说法：Cube 的 FLOP 效率太高了，一个 AIC 几微秒就能算完的 GEMM，后面跟着的那一串 Vector 算子要花掉可观的时间。配两个 AIV 是在平衡这条产线。

> ★ **请特别记住 MTE 是独立的硬件流水线**。这意味着"搬数据"和"算数据"可以真正同时发生——这正是 [13 章 §13.4](13-AscendC编程.md) 双缓冲的物理基础。GPU 上你也做类似的事（`cp.async` 异步拷贝、TMA、软件流水），但 GPU 上那是一种**优化技巧**；在昇腾上**这是基本写法，不这么写性能直接腰斩**。为什么会腰斩，§12.3.4 会用时间线算给你看。

### 12.2.2 Cube：16×16×16 的立方体，以及"对不齐没有退路"

Cube 单元一条指令完成 `C[16×16] += A[16×16] × B[16×16]`（✅ CANN 文档口径，FP16）：

```
16 × 16 × 16 = 4096 次乘累加 / 指令 = 8192 FLOP / 指令
```

**代进一个具体的块算一遍。** 假设 tiling 把 GEMM 切成 256×256×256 的块（这个尺寸只是为了手算好看，真实值由 L1/L0 容量决定，见 §12.4.3）：

```
一个 256×256×256 的块要发多少条 Cube 指令？
  M 方向 256 / 16 = 16
  N 方向 256 / 16 = 16
  K 方向 256 / 16 = 16
  合计 16 × 16 × 16 = 4096 条 Mmad 指令

校验：4096 条 × 8192 FLOP/条 = 33.55 MFLOP
      直接算：2 × 256³ = 33.55 MFLOP   ✓ 对上了
```

对照 [01 章 §1.7](01-GPU硬件基础.md) 的 Tensor Core：Hopper 的 Tensor Core 也是做 MMA（Matrix Multiply-Accumulate，矩阵乘累加），但接口是 **warp 级**的——需要一个 warp 的 32 个线程协同持有数据碎片（Fragment）。Cube 是**核级**的：你不用操心线程怎么分数据，只要把数据按规定格式摆进 L0A / L0B 就行。**这是昇腾比 CUDA 省事的少数几个地方之一。**

> ⚠️ 推断：社区资料称达芬奇核分 Max / Lite / Tiny 三档，Max 核单周期 8192 次 MAC（可能是 FP16 口径下计入了两个 Cube 或双发射），Tiny 核仅 512 次。这组数字和"16×16×16 = 4096"对不上，公开资料没有解释差异来源，**请勿据此推算峰值算力**。另外不同数据类型下 K 方向的长度不一样（INT8 比 FP16 长），具体值以你的型号文档为准，本章不给。

**现在说对齐，这里和 GPU 的差别比想象中大。** 第 01 章说 Tensor Core 要求维度是 16 的倍数，否则退化。昇腾这边的措辞要换：**不是"退化"，是"必须补齐"**。

```
例：一个 M = 250 的 GEMM（N = K = 256），在 Cube 上怎么算？

  M 方向需要 250 / 16 = 15.625 个 16 行的分形块
  → 只能补到 16 个块 = 256 行，最后一个块里只有 10 行是真数据、6 行是填充

  ① 多算的 FLOP：(256 − 250) / 256 = 2.3%     ← 这部分其实无所谓
  ② 真正的代价在搬运：GM 上那 250 行本来是连续的，
     要摆成 16 行一组的分形块（§12.3.3），最后一组凑不满，
     MTE 要么多搬一段、要么走非对齐的慢路径
  ③ 而且【没有退路】：GPU 上对不齐可以退回 CUDA Core 慢慢算，
     昇腾的 AI Core 里根本没有通用核，Cube 只吃 16×16 的块
```

> ★ 这就是 §12.1.1 那句"没有兜底"的第一次兑现。GPU 上维度不对齐是**性能问题**（慢 5 倍，但能跑）；昇腾上是**格式问题**（必须补齐到 16，代价落在 MTE 上）。所以昇腾侧的对齐建议比 GPU 更硬：见 [附-速查表 §L.7](附-速查表.md)。

### 12.2.3 AIC / AIV 分离：910B 最重要的架构变化

**分离架构本身是 ✅ 的**：CANN 官方文档在 Atlas A2 训练系列上明确区分 AIC（矩阵核）和 AIV（向量核），并据此定义了 AIV Only / AIC Only / MIX 三种算子模式（[13 章 §13.5.6](13-AscendC编程.md)）。⚠️ **推断的部分是"从 910A 的耦合形态演进而来"这个叙述**——官方文档没有系统说明代际演进，下面这张对比图里 910A 那一半来自社区与学术资料。

```
910A（耦合架构，⚠️ 推断）
  一个 AI Core
    ├── Cube 和 Vector 同核部署，共享 Scalar、共享指令流
    └── Cube 算完的结果留在 L0C，Vector 直接取走接着算
        → 中间结果不出片

910B / 910C（分离架构，✅ 架构存在）

  AIC（矩阵核）
    ├── Cube
    ├── 自己的 Scalar、自己的指令流
    └── 自己的片上存储：L1 / L0A / L0B / L0C

  AIV（向量核）
    ├── Vector
    ├── 自己的 Scalar、自己的指令流
    └── 自己的片上存储：UB

  两者要交换数据，只有这一条路：
    AIC  ──►  Global Memory（经 L2 中转）  ──►  AIV
    ⚠️ 推断：硬件上没有 AIC↔AIV 的片上直连通道
```

**AIC : AIV = 1 : 2**（✅ CANN 官方文档）——一个矩阵核配两个向量核，理由见 §12.2.1 那张点名表。

分离的好处是矩阵计算和向量计算能各自独立调度、互不阻塞；代价是**AIC 和 AIV 之间的数据必须绕 Global Memory**（在 Ascend C 里就是绕 GM 上的 workspace，✅ 这一点在高阶 Matmul API 的用法里是明写的）。

**把这个代价算成数字。** 这是本节最该慢慢看的一段，因为它直接改写了"融合"这个词在昇腾上的含义。

```
任务：GEMM（4096×4096×4096，BF16）后面跟一个激活函数
⚠️ 用到的硬件数字全部是推断值：910B3 FP16 ~320 TFLOPS、HBM ~1.6 TB/s（§12.4.1）

【不融合，两个独立算子】
  GEMM  写 C 到 GM            4096×4096×2 B = 33.55 MB
  激活  读 C                                   33.55 MB
        写 Y                                   33.55 MB
  比"理想情况"多出来的 GM 流量 = 读 C + 写 C = 67.1 MB
  多花的时间 = 67.1 MB ÷ 1.6 TB/s ≈ 42 µs

【GPU 上融合（05 章的 Epilogue 融合）】
  GEMM 算完一块 C，结果还在寄存器/共享内存里，顺手做激活，直接写 Y
  多出来的 GM 流量 = 0     ★ 这 42 µs 是【消除】掉的

【910B 上"融合"】
  GEMM 在 AIC、激活在 AIV，中间结果仍然要经 GM
  多出来的 GM 流量 = 67.1 MB   ★ 一个字节都没省
```

那昇腾的融合算子还有什么意义？意义在**掩盖**，不在消除。把数据切成 8 块做 CV 流水并行（Cube-Vector 流水并行）：

```
GEMM 本身的 Cube 时间 = 2 × 4096³ ÷ 320 TFLOPS ≈ 429 µs
切成 8 块后，每块：T_AIC ≈ 429/8 ≈ 53.6 µs，T_AIV ≈ 42/8 ≈ 5.3 µs

不流水（AIC 全算完，AIV 再全算）：429 + 42 = 471 µs
                                   AIC 忙 429/471 = 91%，AIV 忙 8.9%

流水（AIC 算第 k+1 块时，AIV 在处理第 k 块）：
  用 13 章 §13.4.3 那个公式：(ΣT − maxT) + N × maxT
                           = (53.6 + 5.3 − 53.6) + 8 × 53.6
                           = 5.3 + 429 ≈ 434 µs

省下 471 − 434 = 37 µs，占 7.9%
```

> ★ **同样叫"融合"，两边省的不是同一笔钱**：GPU 上省的是 67 MB 的 GM 流量（消除），昇腾上省的是 42 µs 里被流水盖住的那部分（掩盖），而且**必须先做分块才有得掩盖**——不分块就是 0 收益。这就是为什么昇腾上 FlashAttention 类算子的优化文章，通篇在讲"核间负载均衡""CV 流水并行""MTE2 流水优化"，而不像 GPU 那边讲"把 softmax 留在 SRAM 里"。物理约束不同，优化的着力点就不同。详见 [04 章 §4.9.1](04-FlashAttention全系.md)、[05 章](05-算子融合.md) 章末与 [13 章 §13.6](13-AscendC编程.md) 陷阱 3。

> ⚠️ 上面这笔账里有一个容易被放大的误读：**7.9% 不是"昇腾融合没用"**。它是这个特定形状（大方阵 GEMM，Cube 时间压倒性地长）下的结果。换成 Decode 阶段的小 shape，Cube 时间坍缩到微秒级，Vector 和搬运的占比会完全反过来——那时候融合与否的差距远不止 8%。**形状变了要重算，别记这个百分比，记那个公式。**

> ⚠️ 推断：下一代昇腾 950 据称针对性地补了这个短板——AIC 与两个 AIV 共享 L1，且新增小容量直通缓冲供 AIC↔AIV 小数据交互，不必绕 GM。若属实，未来几代的融合算子写法会再变一次。

### 12.2.4 五级流水线：先认全这五条腿

前面说"MTE 是独立硬件流水线"，现在把话说完整：**一个 AI Core 内部有多条能并发推进的指令流水线，每条管一类事。** 经典说法是五级：

| 流水线 | Ascend C 里的枚举名 | 干什么 | 对应的典型 API |
|---|---|---|---|
| **Scalar** | `PIPE_S` | 循环控制、分支、算地址、发射其他指令 | 普通 C++ 语句、`GetValue` |
| **MTE2**（搬入） | `PIPE_MTE2` | GM → L1 / UB / L0（顺路 ND→NZ 格式转换） | `DataCopy`（搬进来的那次） |
| **MTE1**（转存） | `PIPE_MTE1` | L1 → L0A / L0B（顺路 NZ→ZZ/ZN） | `LoadData`，或高阶 `Matmul` 内部 |
| **MTE3**（搬出） | `PIPE_MTE3` | UB → GM / UB → L1 | `DataCopy`（搬出去的那次） |
| **Cube / Vector** | `PIPE_M` / `PIPE_V` | 真正算数 | `Mmad` / `Add`、`Exp`… |

> ⚠️ 两点补充。① **Cube 和 Vector 在 Ascend C 的事件枚举里是两条（`PIPE_M` / `PIPE_V`），"五级"是把它们合并成"计算级"的一种口径**；910B 的分离架构下它们本来就在不同的核上，更不可能是同一条。看到"五级""六级""七级"不同说法，先确认对方在数哪几条。② CANN 的枚举里还有 `PIPE_FIX`（FixPipe，把 L0C 的结果搬出去，顺路做量化 / ReLU / 精度转换），**版本相关**，老文档里没有。以你所装 CANN 版本的文档为准。

**为什么要认全这几条？** 因为昇腾的性能分析工具（msprof 的指令流水图）就是按这几行画的，看哪一行最满就是看瓶颈在哪一级（[13 章 §13.8.3](13-AscendC编程.md)）。而在此之前，你得先知道一块数据从 GM 到 Cube 途中会踩到哪几条线——这就是下一节。

## 12.3 内存层级：Cache 世界 → Scratchpad 世界

这是 GPU 工程师转昇腾最容易摔跤的地方。**一句话概括差别**：GPU 上你写 `a = x[i]`，硬件自动把数据从 HBM 经 L2、L1 送到寄存器，你什么都不用管；昇腾上**每一跳都要你写一行代码**，没写就没搬，没搬就读到垃圾。

### 12.3.1 完整层级，以及一块数据要走几跳

先看静态的层级图：

```
片外
  GM / HBM        64 GB 级，最慢。所有输入输出的起点和终点
    │
片上·全芯片共享
  L2 Cache        多核共享，硬件自动管理。★ 这是昇腾唯一"像 cache"的一级
    │
    ├──────────────── AIC（矩阵核）侧 ────────────────
    │     L1 Buffer     片上中转 / 复用暂存（scratchpad）
    │       ├── L0A     Cube 的左矩阵取料口
    │       ├── L0B     Cube 的右矩阵取料口
    │       ├── L0C     Cube 的结果累加器
    │       ├── BT Buffer    Bias 表
    │       └── FP Buffer    量化 / ReLU 参数
    │
    └──────────────── AIV（向量核）侧 ────────────────
          UB            Unified Buffer，Vector 单元【唯一】的工作区
```

**现在加上"谁搬"，看两条数据流**（✅ CANN 官方文档）：

```
Cube 路径（矩阵算子）
  GM ──MTE2──► L1 ──MTE1──► L0A / L0B ──► [Cube] ──► L0C ──FixPipe──► GM（或回 L1 / UB）
     ①            ②                ③          ④              ⑤

Vector 路径（向量算子）
  GM ──MTE2──► UB ──► [Vector] ──► UB ──MTE3──► GM
     ①               ②                    ③
```

逐跳点名，这张表是本节的核心：

| 跳 | 从 → 到 | 执行者 | 顺路做什么 | 你要写的代码 |
|---|---|---|---|---|
| ① | GM → L1（或 → UB） | **MTE2** | ND → FRACTAL_NZ 格式转换 | `DataCopy` |
| ② | L1 → L0A / L0B | **MTE1** | NZ → ZZ / ZN 格式转换 | `LoadData`，或高阶 `Matmul` API 内部代劳 |
| ③ | L0A / L0B → Cube | 硬件（指令操作数） | — | `Mmad`（或高阶 API） |
| ④ | Cube → L0C | 硬件（累加） | 多个 K 块在 L0C 上累加 | — |
| ⑤ | L0C → GM / L1 / UB | **FixPipe** | 随路量化、ReLU、精度转换 | `DataCopy` / Fixpipe 相关 API |

**Cube 路径 5 跳，Vector 路径 3 跳。** 这个数字本身就是一条结论：

> ★ **为什么在昇腾上写矩阵算子比写向量算子难得多**——不是因为矩阵乘的数学难，是因为数据要多走两跳，而这两跳都要你显式安排，还要顺路处理两次格式转换。这也是为什么 [13 章](13-AscendC编程.md) 建议矩阵算子尽量用高阶 `Matmul` API 而不是自己摆 L0A/L0B。

和 GPU 的同一条路径并排看一下，差别在"谁负责"而不在"几跳"：

```
GPU（Tensor Core 路径）
  HBM ──硬件自动（经 L2/L1）──► 共享内存 ──ldmatrix──► 寄存器 ──► Tensor Core
       ↑ 你写一句访存就行         ↑ 这一跳你要写      ↑ 编译器/CUTLASS 代劳

昇腾（Cube 路径）
  GM ──MTE2，你写──► L1 ──MTE1，你写──► L0A/L0B ──► Cube
       ↑ 不写就没有       ↑ 不写就没有
```

> ⚠️ **L1 Buffer 这个名字是个陷阱**。它叫 L1，但**它不是 cache**，不会因为你"访问了 GM 上某个地址"就自动被填充。它是 scratchpad（便笺存储）：容量是你的，内容是你搬进去的，你不搬它就是空的。昇腾这一层里唯一真正像 cache 的只有 **L2**。UB 同理。**看到 L1 就想起共享内存（`__shared__`），不要想起 CPU 的 L1 cache。**

### 12.3.2 第 01 章那套概念，逐条清点存废

**这是全章最重要的一节。** 第 01 章你辛苦建立的那套词汇，有一半在昇腾上不是"改了个名字"，而是**根本不存在**。先看对照表，再看它们为什么不存在。

**存储层的对照：**

| 昇腾 | GPU 上最接近的东西 | 关键差异 |
|---|---|---|
| GM | HBM / Global Memory | 基本一致 |
| L2 Cache | L2 Cache | 基本一致，都是硬件自动管理 |
| L1 Buffer | 共享内存（Shared Memory） | **L1 是 scratchpad 不是 cache**：不会自动填充，必须显式 `DataCopy` |
| UB | 共享内存 | 同上，且**只有 Vector 能用** |
| L0A / L0B / L0C | **无对应物** | Tensor Core 的操作数来自寄存器，昇腾有三块专用缓冲 |
| BT / FP Buffer | **无对应物** | 分离架构新增，专存 Bias 和量化 / ReLU 参数 |
| MTE | `cp.async` / TMA | GPU 上是**指令**，昇腾上是**独立硬件单元**，有自己的流水线编号 |
| 寄存器文件 | 寄存器文件 | 昇腾这层对开发者基本不可见 |

**编程概念的存废清单——这张表才是重点：**

| 第 01 章的概念 | 它在 GPU 上解决什么问题 | 昇腾上还在吗 | 取而代之的是什么 |
|---|---|---|---|
| Thread / Block / Grid | 把元素摊到硬件上 | **没有** | 只有"核"这一层。⚠️ `blockDim` 在昇腾指**核数**，撞名了 |
| Warp（32 线程）、SIMT | 调度的最小单位 | **没有** | 一条 Cube/Vector 指令直接处理一整块数据 |
| Warp 分歧（§1.2.5） | 同 warp 走不同分支要两条路都走 | **没有** | 没有 warp 就没有分歧；分支由 Scalar 单元统一做 |
| 合并访存 / 扇区（§1.4） | 让 32 个线程的地址连续 | **没有** | 换成 **32 字节对齐 + 连续搬运**（`DataCopy` 的硬要求） |
| Bank Conflict（§1.5） | 共享内存的存储体冲突 | **没有** | padding `[32][33]`、swizzle 这些技巧全部作废 |
| Occupancy（§1.6） | 靠多 warp 轮转掩盖延迟 | **没有** | 换成**手工排流水**（§12.3.4） |
| 寄存器溢出（§1.3） | 寄存器不够，静默掉到 HBM | **基本没有** | 换成 UB / L1 / L0 超分配，而且它**会报错**，不是静默变慢 |
| 尾巴效应 / 波次（§1.2.4） | Block 数不是波次整数倍就浪费 | **还在，而且更严重** | 只有 20～40 个核，尾巴摊不薄，见下 |
| Tensor Core 对齐到 16（§1.7） | 对不齐就退回慢路径 | **还在，而且更硬** | 没有慢路径可退，必须补齐（§12.2.2） |

三条要单独展开。

**① 尾巴效应不但还在，而且比 GPU 严重。** 第 01 章 §1.2.4 说"Block 数量多的时候尾巴会被摊薄，影响可以忽略"——那个结论的前提是 GPU 有几千个 Block 去填 132 个 SM。昇腾没有这个前提：

```
GPU：Grid = 3907 个 Block，132 个 SM，一波装 1056 个
     → 4 个波次，最后一波装 70%，整体利用率 92.5%（01 章 §1.8.2 算过）

昇腾：⚠️ 910B3 有 40 个 AIV。假设一个算子切成 45 块
     → 第 1 轮 40 块，第 2 轮只有 5 块，35 个核空转
     → 耗时 = 2 轮，利用率 = 45 / (40 × 2) = 56%

  多 12.5% 的工作量，耗时翻倍。
  ★ 而且你【没法靠"多切几块"来摊薄】——核就这么多，
    块数每跨过 40 的整数倍一次，就多一轮。
```

这就是为什么昇腾算子的调优文章总在讲"核间负载均衡"（[13 章 §13.5.4](13-AscendC编程.md) 给了变长序列场景的完整例子）。**GPU 的调度弹性来自"Block 数远多于 SM 数"，昇腾没有这个缓冲垫。**

**② Bank Conflict 为什么消失了。** GPU 的共享内存被切成 32 个 bank，是为了让**一个 warp 的 32 个线程**在一个周期内各取各的数——bank 数等于 warp 宽度不是巧合。昇腾没有 warp，也就没有"32 个并发的独立地址"这回事：Vector 指令一次处理的是**一整段连续数据**，UB 的取数模式是顺序的、批量的。于是 §1.5 那一整套算 bank 编号、加 padding、做 swizzle 的技巧，在昇腾上**连问题都不存在**。取而代之的约束是"搬运长度和起始地址都要 32 字节对齐"——形式完全不同，但同属"你得照着硬件喜欢的方式摆数据"这一类。

**③ Occupancy 为什么消失了，以及这才是真正的分岔。**

回想 [01 章 §1.6.1](01-GPU硬件基础.md) 算过的那笔账：一次 HBM 访存 500 个周期，每个 warp 拿到数据后算 20 个周期，所以需要 `500 ÷ 20 = 25` 个 warp 才能把延迟填满。**关键在于，这 25 个 warp 的轮转是硬件自动做的**——你只要别把寄存器用超，调度器自己会在 warp 之间切换。

昇腾一个核只有**一条指令流**，没有"另外 24 个 warp"可以切过去。同样的 500 周期，如果没别的活干，就是 500 周期的纯等待。唯一的办法是：**在发起第 k 块的搬运之后，立刻让计算单元去处理第 k−1 块**——也就是让不同的流水线在时间上错开。而要错开，就必须有**两份缓冲**（一份正在被搬，一份正在被算）。

```
GPU 的延迟掩盖               昇腾的延迟掩盖
────────────────────────    ────────────────────────
资源        64 个 warp 槽位   资源        每个缓冲的份数（BUFFER_NUM）
上限        64（硬件给的）     上限        2～3（受 UB / L1 容量限制）
谁来调度    硬件调度器         谁来调度    你，写在代码里
不做会怎样  仍有部分自动轮转    不做会怎样  【硬件直接空转】
调优旋钮    寄存器用量、Block   调优旋钮    tileLength、BUFFER_NUM
诊断指标    Occupancy 百分比    诊断指标    指令流水图各级占比
```

> ★ **`BUFFER_NUM` 就是昇腾版的 Occupancy**——都是"手上有几张牌可以换"。区别有两个，而且都很致命：**它的上限是 2～3 而不是 64**（片上容量装不下更多份），**而且它不是硬件给的，是你写出来的**。这一句话解释了 [13 章](13-AscendC编程.md) 为什么要花整整一节讲"`BUFFER_NUM = 2` 不是优化而是基本功"。

> ★ **所以昇腾算子调优的核心问题不是"occupancy 够不够"，而是"流水排没排满、哪一级是瓶颈"。** 下一节把这句话画成图。

### 12.3.3 FRACTAL_NZ：一个躲不掉的数据格式

昇腾片上的矩阵不按你熟悉的行优先（Row Major，昇腾叫 **ND** 格式）摆放，而是按**分形格式** FRACTAL_NZ：

```
规则两句话：
  ① 把大矩阵切成 16×16 的小块
  ② 块内按行优先存，块间按列优先排
```

**用一个 4×4 矩阵手推一遍。** 为了画得下，把"16×16 的小块"缩成"2×2 的小块"，规则完全一样：

```
原矩阵（4×4）
  a00 a01 a02 a03
  a10 a11 a12 a13
  a20 a21 a22 a23
  a30 a31 a32 a33

切成 4 个 2×2 小块
  B00 = a00 a01     B01 = a02 a03
        a10 a11           a12 a13
  B10 = a20 a21     B11 = a22 a23
        a30 a31           a32 a33

ND（行优先）在内存里的顺序：
  a00 a01 a02 a03 | a10 a11 a12 a13 | a20 a21 a22 a23 | a30 a31 a32 a33

NZ（块内行优先、块间列优先）在内存里的顺序：
  块的走法：先竖着走完第 0 列的两个块（B00 → B10），再走第 1 列（B01 → B11）

     B00              B10              B01              B11
  a00 a01 a10 a11 | a20 a21 a30 a31 | a02 a03 a12 a13 | a22 a23 a32 a33
```

**为什么要这么摆？把搬运次数算出来就明白了。**

```
Cube 一次吃一个 16×16 的块（FP16，512 字节）。要把这个块搬进片上：

  NZ 格式：这 256 个元素在内存里【连续】
           → 1 次连续搬运，512 字节

  ND 格式：这 256 个元素分散在 16 行里，每行 16 个（32 字节），
           相邻两行相隔一整个 row stride（比如 4096 × 2 = 8192 字节）
           → 16 次跨步搬运，每次只搬 32 字节

  ★ 同样的 512 字节，一次搬完 vs 分 16 次搬。
    §12.6 会告诉你，"小而多的搬运"正是 MTE Bound 的头号成因。
```

实践后果三条：

- **L1 Buffer 里推荐用 NZ 格式**，这样搬到 L0A / L0B 时（两者还要分别转成 ZZ / ZN 格式）格式转换开销最小（✅ CANN 文档）。
- **从 GPU 迁移过来的代码里，那些手工算 stride 的逻辑基本都要重写。** 你在 GPU 上精心设计的 tile 布局，在这里是另一套规则。
- **`torch_npu` 里有 `npu_format_cast` 这类接口在 ND 和 NZ 之间转换，而转换本身是有成本的。**

最后这一条值得算一笔账，因为它是昇腾上一类典型的**隐性**性能损失：

```
⚠️ 用推断数字：910B3 HBM ~1.6 TB/s

一次 ND ↔ NZ 转换 = 把整个张量读一遍、写一遍
  4096×4096 的 BF16 权重 = 33.55 MB
  读 + 写 = 67.1 MB ÷ 1.6 TB/s ≈ 42 µs

如果模型里某一层的输入输出在 ND 和 NZ 之间横跳两次，
80 层的模型一次前向就是 80 × 2 × 42 µs ≈ 6.7 ms

  ★ 这 6.7 ms 不产生任何 FLOP，在算子耗时表上还会被摊到
    一堆叫 TransData / Cast 的小算子头上，很容易看漏。
```

> ⚠️ **排查动作**：在 msprof 的算子耗时列表里 grep `TransData`、`Cast`、`Format`。它们的总耗时如果超过端到端的 5%，说明模型里有 ND↔NZ 横跳，值得回去看是哪个算子的输入输出格式没对上。具体操作见 [14 章 §14.5.4](14-GPU到NPU迁移实战.md)。

### 12.3.4 把时间轴加上：一次分块矩阵乘的错位流水

§12.3.2 说"延迟靠手工排流水掩盖"，§12.3.1 说"数据要走五跳"。**把这两件事画在同一张图上，就是昇腾性能的全部秘密。** 这一节请拿纸笔跟着算。

**设定。** 一个 AIC 要算 6 个输出块，每块走 §12.3.1 的 Cube 路径。每一跳的耗时**全部是 ⚠️ 假设值，仅为演示流水机理**（真机数字要用 msprof 测，见 [13 章 §13.8](13-AscendC编程.md)）：

```
⚠️ 假设（仅为演示）：

  T_MTE2  = 2 个时间单位   GM → L1，把 A 块和 B 块搬进片上
  T_MTE1  = 1 个时间单位   L1 → L0A / L0B
  T_Cube  = 3 个时间单位   4096 条 Mmad（§12.2.2 那个 256³ 的块）
  T_MTE3  = 1 个时间单位   L0C → GM（走 FixPipe）

  N = 6 个块
  Σ T = 2 + 1 + 3 + 1 = 7      max T = 3（Cube）

  ★ Cube 最重，是合理的形态：矩阵算子本来就该 Cube Bound（§12.6）。
```

**情况 A：不排流水，一块走完再走下一块。**

```
数字 = 正在处理第几块；'.' = 这条流水线空转。只画前 14 个时间单位

              11111
     12345678901234
MTE2 00.....11.....
MTE1 ..0......1....
CUBE ...000....111.
MTE3 ......0......1
```

看出来了吗：**任意一列里，最多只有一行是数字。** 四条流水线，永远只有一条在动。

```
总耗时 = N × Σ T = 6 × 7 = 42 个时间单位

各流水线占用率：
  MTE2  6×2 = 12 / 42 = 29%
  MTE1  6×1 =  6 / 42 = 14%
  Cube  6×3 = 18 / 42 = 43%     ← 最贵的硬件，只用了不到一半
  MTE3  6×1 =  6 / 42 = 14%
```

**情况 B：排好流水，每一级各干各的。**

```
              1111111111222
     1234567890123456789012
MTE2 00.11.22.33.44.55.....
MTE1 ..0..1..2..3..4..5....
CUBE ...000111222333444555.
MTE3 ......0..1..2..3..4..5
```

**把第 10 个时间单位那一列竖着读一遍**——这一列就是这一章要你记住的那张图：

```
时间单位 10 这一瞬间，一个 AI Core 里同时在发生：

  MTE2  正在把【第 3 块】从 GM 搬进 L1
  MTE1  空转（它刚在第 9 单位把第 2 块转完）
  Cube  正在算【第 2 块】
  MTE3  正在把【第 1 块】的结果从 L0C 写回 GM

  ★ 三块数据，同时在三条不同的硬件流水线上，彼此错开一格。
    这就是昇腾掩盖延迟的【唯一】机制。
```

算账：

```
总耗时 = 22 个时间单位

  通用公式（和 13 章 §13.4.3 是同一个）：
    不排流水 = N × Σ T
    排好流水 = (Σ T − max T) + N × max T

  代入：不排 = 6 × 7             = 42   ✓ 和情况 A 一致
        排好 = (7 − 3) + 6 × 3   = 22   ✓ 和上图一致

加速比 = 42 / 22 = 1.91 倍

各流水线占用率：
  MTE2  12 / 22 = 55%
  MTE1   6 / 22 = 27%
  Cube  18 / 22 = 82%     ← 从 43% 提到 82%，翻了一倍
  MTE3   6 / 22 = 27%
```

**开头那 4 个单位（Cube 还没开工）和结尾那 1 个单位（Cube 已经收工）是流水线的填充和排空**，正好等于公式里的 `Σ T − max T = 4`。块数 N 越多，这 4 个单位摊得越薄：

| 块数 N | 不排流水 | 排好流水 | 加速比 | Cube 占用率 |
|---|---|---|---|---|
| 2 | 14 | 10 | 1.40× | 60% |
| 6 | 42 | 22 | 1.91× | 82% |
| 20 | 140 | 64 | 2.19× | 94% |
| N → ∞ | 7N | 3N + 4 | **→ 7/3 = 2.33×** | → 100% |

> ★ **上限是 `Σ T / max T`，不是"无限快"。** 排流水能做到的极限是"只剩最慢的那一级在累加"，其余三级完全被藏起来。本例是 `7 / 3 = 2.33` 倍。**想再快，只能去优化 Cube 那一级本身**（更大的 tiling、更高的 Cube 利用率）——这就是 §12.6 里"Cube Bound 是理想终点"的含义。

**这张图还顺带回答了两个问题。**

**问题一：为什么必须有两份缓冲？** 看第 4 个时间单位：MTE2 正在往 L1 里搬第 1 块，而 MTE1 在第 3 单位刚把第 0 块从 L1 取走、Cube 从第 4 单位开始用它。如果 L1 上只给 A 块留了**一份**空间，MTE2 就必须等 Cube 彻底用完第 0 块才能搬第 1 块——时间线立刻塌回情况 A。**所以"排流水"和"双缓冲"是同一件事的两个说法**：错开时间的前提是错开空间。L1 要两份，L0A/L0B 也要两份。

**问题二：为什么昇腾的 tiling 不能随便切大？** 块切得越大，Cube 每块算得越久（`max T` 变大），流水填充占比越小——听起来该切大。但块越大，L1 和 L0 上放两份就放不下了，双缓冲开不起来，直接退回情况 A。**"块大小"这一个参数同时被两个相反的力拉扯**，这就是 [13 章 §13.5.2](13-AscendC编程.md) 要花一整节反推 tiling 上界的原因。

> ⚠️ 这套推演是**理想模型**，至少忽略了四件事：① 流水线之间的同步事件本身有开销；② MTE2 和 MTE3 虽是两条流水线，但可能争抢同一条通向 GM 的总线，不完全独立；③ Scalar 单元要给每一块算地址，它自己也可能成为瓶颈（尤其是块很小、循环次数很多的时候）；④ 真实算子里 Cube 和 Vector 还跨在 AIC / AIV 两个核上（§12.2.3），中间要过 GM。**真实加速比会低于 1.91，具体多少只能实测。这里要记住的是量级和机理，不是那个数。**

## 12.4 规格：910B 与 910C，以及为什么本节最该被怀疑

### 12.4.1 910B：先搞清楚你手上是哪一款

**"910B" 不是一款芯片，是一个系列**。B1 / B2 / B3 / B4 的 AI Core 数量、HBM 容量和带宽差异巨大，笼统说"910B"会导致严重的性能预估偏差，甚至会让一份部署方案在另一个子型号上**根本起不来**（[14 章 §14.3.3](14-GPU到NPU迁移实战.md) 算过这笔显存账）。

| 型号 | AIC | AIV | HBM 容量 | HBM 带宽 | FP16 算力 | 可信度 |
|---|---|---|---|---|---|---|
| 910B2 | 24 | 48 | 64 GB | — | — | ⚠️ 推断（学术论文口径） |
| 910B3 | 20 @ 1.8 GHz | 40 | 64 GB | ~1.6 TB/s | ~320 TFLOPS | ⚠️ 推断 |
| 910B4 | 20 | 40 | 32 GB | ~800 GB/s | 280 TFLOPS | ✅ 部分（见下） |

唯一的厂商一手口径是**整机 / 板卡产品页**：

- **Atlas 300T A2**（采用 910B4 die）：20 个 AI Core、280 TFLOPS FP16、75 TFLOPS FP32 —— ✅ 披露
- **Atlas 800T A2** 训练服务器（8 卡）：整机 2.56 PFLOPS FP16 —— ✅ 披露；反推单卡 320 TFLOPS —— ⚠️ 推断
- **AIC : AIV = 1 : 2** —— ✅ CANN 文档（所以表里的 AIV 列是由 AIC 列算出来的，不是独立来源）

> ⚠️ 流传最广的两组数字是「320 TFLOPS FP16 / 640 TOPS INT8」和「256 TFLOPS FP16 / 512 TOPS INT8」，**都无官方出处**。带宽数字更乱，从 400 GB/s 到 2.4 TB/s 的说法都有人写，大概率是混淆了不同子型号和不同口径（单 die / 单卡、单向 / 双向）。**看到一个昇腾算力数字，第一件事是问它是哪个子型号、哪个精度、稠密还是稀疏。**

粗略量级感知（⚠️ 全部为推断，仅用于建立直觉，**不可用于选型**）：

```
910B3 ≈ A100 的算力量级（FP16 ~320 vs 312 TFLOPS）
       但 HBM 带宽（~1.6 TB/s）大约是 H100（3.35 TB/s）的一半
       且没有 FP8 Tensor Core 的对应物
       （见 06 章 §6.10：昇腾走的是 INT8 和 HiF8 路线）
```

**把这组数字接到第 02 章的屋顶线上，会得到一个有意思的结论。**

```
屋脊点 = 峰值算力 ÷ 峰值带宽

  H100  ：989 TFLOPS ÷ 3.35 TB/s ≈ 295 FLOP/Byte   （✅ 官方数字）
  910B3 ：320 TFLOPS ÷ 1.6  TB/s ≈ 200 FLOP/Byte   （⚠️ 基于推断数字）
```

屋脊点低意味着**同一个算子在昇腾上更容易落到 Compute Bound 一侧**。这不是抽象的，能找到具体落在中间那一段的算子：

```
例：训练里的一个 GEMM，M = 256，N = K = 4096，BF16

  FLOP  = 2 × 256 × 4096 × 4096 = 8.59 GFLOP
  Byte  = (M×K + K×N + M×N) × 2
        = (1,048,576 + 16,777,216 + 1,048,576) × 2 = 37.75 MB
  算术强度 I = 8.59e9 ÷ 3.775e7 ≈ 228 FLOP/Byte

  在 H100  上：228 < 295  →  Memory Bound，该做的是减少搬运（融合、量化）
  在 910B3 上：228 > 200  →  Compute Bound，该做的是提高 Cube 利用率

  ★ 同一个算子，两台机器上优化方向【相反】。
```

> ★ **第 02 章的诊断流程照用，但屋脊点必须换成你这张卡的**。而且注意上面那个 200 是拿两个 ⚠️ 推断值相除得到的，误差会叠加——把它当成"比 H100 低、大概在 200 这个量级"来用，不要当成 200.0。

### 12.4.2 910C：双 die 封装

⚠️ 以下全部为第三方分析（SemiAnalysis 等）估算，华为未发布数据手册：

```
910C = 两颗 910B 级的 die 封装在一起
  ├─ 稠密 BF16 算力   ~780 TFLOPS
  ├─ HBM              ~128 GB
  └─ HBM 带宽         ~3.2 TB/s
```

工程上最要紧的一点不是算力数字，而是：**双 die 意味着卡内也存在 NUMA（Non-Uniform Memory Access，非统一内存访问）效应**。一张 910C 上两个 die 之间的通信代价，和 die 内部不同。

```
把一张 910C 当成"一个均匀的加速器"会怎样：

  ✗ 按"一张卡 = 一个单元"做 TP 切分
    → 一半的通信悄悄跨了 die，比你估算的慢

  ✓ 按"一张卡 = 2 个单元"做切分和通信编排
    → 让高频通信尽量留在 die 内
```

这一条直接影响 [14 章 §14.3.3](14-GPU到NPU迁移实战.md) 的 TP 规模决策。

### 12.4.3 别信本节，去查你自己的卡

**这是本章最有用的一段，也是唯一一段你应该原样照抄的内容。** 三个办法，可信度从低到高：

```bash
# 1) 看硬件实况：型号、HBM 容量、AICore 使用率、HBM 带宽占用
npu-smi info
npu-smi info -t usages -i 0

# 2) 看 CANN 眼中的芯片参数（最权威的本地来源）
#    CANN 安装目录下有 platform_config/，每个文件对应一款芯片子产品
#    里面写着真实的 AI Core 数、各级 Buffer 容量、频率
find /usr/local/Ascend -type d -name "platform_config" 2>/dev/null
#    然后查看对应 soc_version 的 .ini 文件，如 Ascend910B3.ini

# 3) 代码里查（算子里唯一正确的做法）
python3 -c "import torch, torch_npu; print(torch_npu.npu.get_device_name(0), torch_npu.npu.get_device_properties(0))"
```

Host 侧写 Tiling 函数时，还有一组必须**在代码里查、绝不能写死**的数字——各级 Buffer 的容量（✅ CANN 平台 API）：

```cpp
auto platform = platform_ascendc::PlatformAscendC(context->GetPlatformInfo());
uint64_t ubSize, l1Size;
platform.GetCoreMemSize(platform_ascendc::CoreMemType::UB, ubSize);
platform.GetCoreMemSize(platform_ascendc::CoreMemType::L1, l1Size);
uint32_t aicNum = platform.GetCoreNumAic();
uint32_t aivNum = platform.GetCoreNumAiv();
```

> ⚠️ `CoreMemType::UB` 这个枚举是核实过的（[13 章 §13.5.2](13-AscendC编程.md) 有出处），但 `CoreMemType::L1` 的**字面量**我没找到一手文档确认——各级 Buffer 在不同 CANN 版本里的枚举名改过。用之前先在你装的版本的头文件里 grep 一下 `CoreMemType`，别照抄。这一节要你记住的是「**查，不要写死**」这个做法，不是这两行代码的确切拼写。

> ⚠️ **这不是洁癖，是踩过的坑。** 一个真实例子：UB 容量的社区常见口径在 910B 上是 ≈192 KB，而 310B 上是 ≈248 KB——**同一个昇腾家族，差了 30%**。把 192 KB 写死在 tiling 里，换一张卡要么白白浪费四分之一的片上空间，要么直接超分配报错。L1 / L0A / L0B / L0C 的情况只会更乱，所以 §12.1 开头就说了：**本章干脆不给这几个数。** 完整的推导流程见 [13 章 §13.5.2](13-AscendC编程.md)。

> ★ `platform_config` 里的 `.ini` 文件是写 Ascend C 算子时的必备参照。**如果你只记住本章一件事，记住这个路径。**

## 12.5 互联：HCCS、UB 总线与超节点

### 12.5.1 单机内：HCCS

**HCCS**（Huawei Cache Coherence System，华为缓存一致性互联）是华为自研的片间高速互联，地位等同 NVLink，支持硬件级缓存一致性。

- 服务器内基础拓扑是 **Full Mesh 全互联**（✅ HCCL 文档），8 卡两两直连，和 NVSwitch 的效果类似但实现路径不同。
- 服务器之间走 **RoCE**（RDMA over Converged Ethernet，融合以太网上的远程直接内存访问）组成 Fat Tree。
- ⚠️ 推断：单链路约 100 GB/s 双向，社区常引用的卡间互联带宽为 392 GB/s。

**这个短板有多短，算一次 TP 通信就知道了**（⚠️ 全部基于推断带宽，仅演示量级）：

```
场景：TP = 8 的一层 AllReduce
  激活形状 [seq 4096, hidden 8192]，BF16 → 4096 × 8192 × 2 = 67.1 MB

  Ring AllReduce 每张卡要收发的量 ≈ 2 × D × (n−1)/n
                                  = 2 × 67.1 × 7/8 ≈ 117 MB

  在昇腾上：117 MB ÷ 392 GB/s  ≈ 0.30 ms   （⚠️ 社区口径带宽）
  在 H100 上：117 MB ÷ 900 GB/s ≈ 0.13 ms   （NVLink 4.0）

  慢 2.3 倍。
  ★ 而 TP 的 AllReduce 在每一层都要做两次，80 层就是 160 次。
```

> ★ **这是昇腾集群侧最明显的短板之一，直接影响可行的 TP（Tensor Parallel，张量并行）规模**——TP 度越高，每层的 AllReduce 越频繁，互联带宽越容易变成瓶颈。它同样影响 [08 章](08-MoE算子与通信.md) 讲的 MoE All-to-All。缓解手段有两条：一是少用 TP 多用其他并行维度，二是下一节的超节点。

### 12.5.2 CloudMatrix 384 超节点：把短板换个方向解决

华为云 2025 年 4 月发布的 CM384（✅ 配置为官方发布）：

```
384 颗 Ascend 910C + 192 颗鲲鹏 CPU
  └─ 全部经 UB（Unified Bus，统一总线）全互联，无阻塞 all-to-all

约 300 PFLOPS 稠密 BF16 算力（⚠️ SemiAnalysis 估算）
约 48 TB HBM 总容量
四层结构：计算节点（48 节点 × 8 NPU）→ L1 板级交换 → L2 机柜级交换 → RDMA 横向扩展
光互联：6912 个 400G 硅光 LPO 光模块
```

**对算子开发者的意义**，用一句对比说清：

```
GPU 集群（NVLink 域 = 8 卡，域外走 InfiniBand，慢一个量级）
  → MoE 的专家并行要费尽心思把通信【塞进 8 卡的 NVLink 域内】
  → 于是有了分层 All-to-All：域内一种算法，域外另一种（08 章 §8.3.6）

CloudMatrix 384（一个平坦的 384 卡通信域）
  → ⚠️ 官方宣称跨节点带宽劣化 <3%、时延增加 <1 μs
  → "域内 / 域外"这个区分在很大程度上消失了
  → 分层 All-to-All 的必要性下降（08 章 §8.9.3）
```

> ★ **同一个 MoE 模型，在两种硬件上的最优通信策略不一样**，因为"通信域的边界在哪"这个前提变了。华为的思路不是把单链路做得比 NVLink 快，而是**把边界推到 384 卡之外**。

代价是能效：SemiAnalysis 的评价是 CM384 用封装、光互联和系统设计弥补了制程劣势，代价是显著更高的功耗。

> ⚠️ 单 NPU 的 UB 带宽数字在公开资料里有 196 GB/s、~390 GB/s、2.8 Tbps 三种说法，量纲和口径（单 die / 单封装、单向 / 双向）都不统一，**本章不给结论**。

> ⚠️ 再提醒一次：这一节的 **UB 是 Unified Bus（总线）**，和 §12.3.1 里 Vector 单元用的 **UB = Unified Buffer（片上缓冲）**完全无关。昇腾体系里这个缩写撞车了，看到 UB 先判断语境——在讲互联就是总线，在讲算子就是缓冲区。

## 12.6 那么第 02 章的屋顶线还能用吗

能用，但要换三样东西，而且要加一类它根本不覆盖的瓶颈。

### 12.6.1 三处要换

```
第 02 章的 GPU 屋顶线：
  P = min(峰值算力, 峰值带宽 × 算术强度 I)
  瓶颈二选一：Compute Bound / Memory Bound

昇腾的屋顶线：公式一模一样，但——

  ① 屋脊点换成你这张卡的（910B3 ⚠️ ≈ 200 FLOP/Byte，§12.4.1）

  ② "峰值算力"要分开问：是 Cube 的还是 Vector 的？
     一个算子如果全是 Vector 运算（LayerNorm、Softmax、SiLU），
     它一条 Cube 指令都不会发——那个 320 TFLOPS 对它【毫无意义】，
     拿它当分母算出来的"算力利用率 0.3%"是个假指标

  ③ 多一类瓶颈：MTE Bound（搬运受限）
```

第 ② 条值得多说一句，因为它是昇腾性能报告里最常见的一种误读。GPU 上 CUDA Core 和 Tensor Core 虽然峰值差 15 倍，但**一个 LayerNorm 至少还在 CUDA Core 上跑，用的是同一张芯片的浮点单元**。昇腾上 Vector 算子跑在 AIV、Cube 算子跑在 AIC，**是两组物理上分开的核**。给一个纯 Vector 算子算"占 Cube 峰值算力的百分之几"，就像用卡车的载重量去衡量一辆摩托车。

### 12.6.2 MTE Bound：屋顶线看不见的第三类瓶颈

**先说现象。** 在 GPU 上，访存受限就是访存受限：HBM 带宽跑满了，你在 Nsight 里能看到 DRAM Throughput 接近 100%。在昇腾上，你会遇到一种新形态：

```
指令流水图（13 章 §13.8.3 的读法）：
  MTE2   占比 88%      ← 满了
  Cube   占比  4%      ← 闲着
  Vector 占比 22%      ← 也闲着

同时 msprof 报的 HBM 实测带宽：只有峰值的 20%

  → 算力没打满，带宽也没打满，但算子就是慢。
     屋顶线上这个点离两条线都很远，模型解释不了。
```

**为什么会这样？把搬运次数的账算出来。** 关键在于 **MTE 的每一次搬运都有固定开销**（发起、地址计算、格式转换的启动），这个开销和搬多少字节无关。

```
⚠️ 假设（仅为演示机理）：一次 DataCopy 的固定开销 ≈ 搬 2 KB 数据所需的时间。
   真值随型号、方向、是否对齐而变，要用 msprof 实测。

任务：把 1 MB 数据从 GM 搬进 UB

  方案 A：tileLength 对应 512 字节
    搬运次数 = 1 MB ÷ 512 B = 2048 次
    每次等效代价 = 2 KB（固定） + 0.5 KB（数据） = 2.5 KB
    总等效代价 = 2048 × 2.5 KB = 5120 KB = 5 MB
    ★ MTE2 的有效利用率 = 0.5 / 2.5 = 20%

  方案 B：tileLength 对应 16 KB
    搬运次数 = 1 MB ÷ 16 KB = 64 次
    每次等效代价 = 2 KB + 16 KB = 18 KB
    总等效代价 = 64 × 18 KB = 1152 KB ≈ 1.125 MB
    ★ MTE2 的有效利用率 = 16 / 18 = 89%

  两者搬的【真实数据量都是 1 MB】，HBM 侧看到的流量一模一样，
  但 MTE2 上的耗时差 5120 / 1152 = 4.4 倍。
```

**这就是屋顶线看不见它的原因**：屋顶线只有两根资源轴——每秒多少 FLOP、每秒多少 Byte。MTE 是第三种资源，它的容量单位既不是 FLOPS 也不是 GB/s，而是**每秒能完成多少次搬运事务**。当瓶颈是"事务次数"而不是"字节数"时，这个算子在屋顶线图上会落在两条线的下方很远的地方——**长得很像 [02 章 §2.5 盲区二](02-屋顶线与性能剖析.md) 的"延迟受限"，但成因和对策都不同**。

**判据（三条同时成立才是 MTE Bound）：**

```
① 指令流水图里 MTE2 或 MTE3 的占比 > 85%
② 实测 HBM 带宽 < 峰值的 50%        ← 关键的一条，区别于真正的 Memory Bound
③ Cube 和 Vector 的占比都不高

  如果 ① 成立但 ② 不成立（带宽也跑满了），那是普通的 Memory Bound，
  对策是减少搬运【总量】（融合、量化），不是调 tile 大小。
```

**四类常见成因，按排查顺序：**

| 成因 | 为什么会造成 MTE Bound | 怎么确认 | 对策 |
|---|---|---|---|
| **没开双缓冲** | 流水塌回 §12.3.4 情况 A，四条线轮流空转 | 各级占比都不高、总耗时却长 | `BUFFER_NUM = 2`（[13 章 §13.4](13-AscendC编程.md)） |
| **单次搬运太小** | 固定开销摊不薄，就是上面那笔账 | 搬运次数 × 单次大小 ≈ 总量，且单次 < 几 KB | 调大 tileLength（上界见 [13 章 §13.5.2](13-AscendC编程.md)） |
| **没对齐到 32 字节** | 退到非对齐的慢路径 | 尾块长度不是 32 B 的整数倍 | tiling 里保证整除，或尾块单独处理 |
| **ND ↔ NZ 隐式转换** | 一次转换 = 整个张量读一遍写一遍（§12.3.3） | 算子列表里有 `TransData` / `Cast` | 统一格式，减少横跳 |

### 12.6.3 四类瓶颈速查

所以昇腾的算子瓶颈分类是**四选一**，不是 GPU 那样的二选一：

| 瓶颈 | 流水图现象 | 屋顶线覆盖吗 | 对策 |
|---|---|---|---|
| **Cube Bound** | Cube 占比高 | ✓ Compute Bound | 已接近最优；剩余收益在更大 tiling、更高 Cube 利用率 |
| **Vector Bound** | AIV 占比高，AIC 空转 | ✓（但要用 Vector 的峰值算） | CV 流水并行；把能挪的计算挪给 Cube |
| **MTE Bound** | MTE2 / MTE3 高，带宽却没满 | **✗ 不覆盖** | 双缓冲 → 调大 tile → 查对齐 → 查 ND↔NZ |
| **下发 Bound** | 三级都不满，Host 侧下发密 | ✗ 不覆盖（[02 章 §2.5 盲区三](02-屋顶线与性能剖析.md)） | 开图模式（[14 章 §14.5](14-GPU到NPU迁移实战.md)）、合并小算子 |

判断工具是 MindStudio Insight 的**指令流水图**，完整的采集命令、读图方法和四个案例在 [13 章 §13.8](13-AscendC编程.md)。

> ⚠️ **排查顺序不能换：先确认瓶颈在不在算子里。** 昇腾单算子的下发开销相对更显眼，推理 Decode 阶段算子又多又小，**很大比例的"昇腾算子慢"最后查出来根本不是算子慢**。第 0 步永远是"所有算子耗时之和 ≈ 端到端耗时吗"。

## 12.7 本章小结

**一句话**

```
GPU 用"人多"掩盖延迟（64 个 warp 轮转，硬件自动）
昇腾用"排班"掩盖延迟（五条流水线错开，你手写）

  ★ 这一个分岔，衍生出本章所有的"没有对应物"
```

**硬件地图**

| 层次 | 昇腾 | GPU 对应物 | 关键差异 |
|---|---|---|---|
| 芯片 | ⚠️ 20 AIC + 40 AIV（910B3） | 132 个 SM | 核少 7 倍 → **调度没有弹性**，尾巴效应更致命 |
| 核内计算 | Cube / Vector / Scalar | Tensor Core / CUDA Core / — | Cube 是**核级**接口，不用管线程分数据 |
| 核内搬运 | MTE1 / MTE2 / MTE3 / FixPipe | `cp.async` / TMA 指令 | 昇腾是**独立硬件流水线**，所以能真正重叠 |
| 片上存储 | L1 / L0A / L0B / L0C / UB | 共享内存 / 寄存器 | **Scratchpad 不是 Cache**，不搬就是空的 |
| 片上唯一的 cache | L2 | L2 | 这一级两边一致 |
| 卡间 | HCCS Full Mesh | NVLink / NVSwitch | ⚠️ ~392 vs 900 GB/s，TP 规模受限 |
| 超节点 | CloudMatrix 384（UB 总线） | 无对应物 | 把通信域边界推到 384 卡外 |

**数据要走几跳，谁负责**

```
Cube 路径（5 跳）
  GM ──MTE2──► L1 ──MTE1──► L0A/L0B ──► [Cube] ──► L0C ──FixPipe──► GM

Vector 路径（3 跳）
  GM ──MTE2──► UB ──► [Vector] ──► UB ──MTE3──► GM

  ★ 每一跳都要你写一行 DataCopy。不写就没搬，没搬就读到垃圾。
```

**核心公式，全章就这两个**

```
① 流水加速（§12.3.4，和 13 章 §13.4.3 同一个公式）
     不排流水 = N × Σ T
     排好流水 = (Σ T − max T) + N × max T
     N 大时加速比上限 → Σ T / max T
   ★ 排流水的前提是每级至少两份缓冲——错开时间必须先错开空间

② 屋脊点（§12.4.1）
     910B3 ⚠️ ≈ 320 TFLOPS ÷ 1.6 TB/s ≈ 200 FLOP/Byte
     H100     ≈ 989 TFLOPS ÷ 3.35 TB/s ≈ 295 FLOP/Byte
   ★ 屋脊点低 → 同一算子在昇腾上更容易落到 Compute Bound 一侧
```

**第 01 章里作废的概念（完整版见 §12.3.2）**

| 作废的 | 因为 | 换成了 |
|---|---|---|
| Thread / Block / Grid / Warp / SIMT | 昇腾没有线程这一层 | 核 + 核内流水。⚠️ `blockDim` 撞名，在昇腾指核数 |
| 合并访存、扇区 | 没有 warp 就没有"32 个地址凑一起" | 32 字节对齐 + 连续搬运 |
| Bank Conflict | 32 个 bank 是为 32 线程的 warp 设计的 | 不存在这个问题，padding / swizzle 全作废 |
| Occupancy | 没有多 warp 可轮转 | **`BUFFER_NUM`，上限只有 2～3，而且要你自己写** |
| 寄存器溢出 | 这一层对开发者不可见 | 片上 Buffer 超分配，而且**会报错**不是静默变慢 |

**没作废、反而更严重的**

- **尾巴效应**：只有 20～40 个核，块数每跨过核数的整数倍一次就多一轮，摊不薄（§12.3.2）。
- **维度对齐**：Cube 只吃 16×16 的块，**没有通用核可以退回去**，不对齐就必须补齐（§12.2.2）。

**多出来的一类瓶颈**

```
MTE Bound：Cube 没满、HBM 带宽也没满，但 MTE 流水满了
  成因：搬运【次数】太多，而不是搬运【字节】太多
  判据：MTE 占比 >85% ＋ 实测带宽 <50% 峰值 ＋ 计算单元都闲着
  对策顺序：双缓冲 → 调大 tile → 查 32B 对齐 → 查 ND↔NZ 横跳
```

**关于数字**

```
华为没有公开 910B/910C 的数据手册。本章的算力、带宽、互联数字
大部分是 ⚠️ 推断，时间单位和固定开销全部是 ⚠️ 为举例而设的假设值。

★ 唯一可信的数字来源是你手上那张卡：
    npu-smi info
    $ASCEND_HOME/.../platform_config/Ascend910B3.ini
    GetCoreMemSize() / GetCoreNumAic() / GetCoreNumAiv()
  本章连 L1 / L0 / UB 的容量都不给，就是因为它们跨型号差异太大（§12.4.3）。
```

**自测三题**（答案在本章对应小节）

1. 某矩阵算子每块的四段耗时是 `T_MTE2 = 3`、`T_MTE1 = 1`、`T_Cube = 2`、`T_MTE3 = 1`（⚠️ 假设值），一个核处理 5 个块。不排流水和排好流水各耗时多少？加速比是多少？瓶颈是哪一级、占用率多少？块数趋于无穷时加速比的上限是多少？按 §12.6.3，这算哪一类瓶颈？
2. 要把 512 KB 数据从 GM 搬进 UB，⚠️ 假设一次搬运的固定开销等效于搬 2 KB。`tileLength` 对应 1 KB 和 8 KB 两种方案，各需要多少次搬运？MTE2 的有效利用率各是多少？两者的等效耗时差几倍？如果流水图显示 MTE2 占 90%、Cube 占 5%、实测 HBM 带宽只有峰值的 18%，判成哪类瓶颈？第一个该做的动作是什么？
3. 某算子的算术强度 `I = 150 FLOP/Byte`。在 910B3（⚠️ 320 TFLOPS / 1.6 TB/s）和 H100（989 TFLOPS / 3.35 TB/s）上分别属于哪类瓶颈？各自能达到的性能上限是多少？各占本机峰值算力的百分之几？这个对比说明了什么？

#### 参考答案

1. `Σ T = 3 + 1 + 2 + 1 = 7`，`max T = 3`（**MTE2**）。不排流水 = `5 × 7` = **35 个时间单位**；排好流水 = `(7 − 3) + 5 × 3` = `4 + 15` = **19 个时间单位**；加速比 = `35 ÷ 19` ≈ **1.84 倍**。瓶颈是 **MTE2**，占用率 = `15 ÷ 19` ≈ **79%**。上限 = `Σ T ÷ max T` = `7 ÷ 3` ≈ **2.33 倍**。注意 Cube 只占 `10 ÷ 19` ≈ 53%——**最贵的硬件有一半时间在等搬运**，所以这是 **MTE Bound**，对策按 §12.6.3 走（先确认双缓冲、再调大 tile）。参见 §12.3.4 与 §12.6。
2. 1 KB 方案：`512 ÷ 1` = **512 次**，每次等效 `2 + 1 = 3 KB`，总计 `512 × 3` = 1536 KB，有效利用率 = `1 ÷ 3` ≈ **33%**。8 KB 方案：`512 ÷ 8` = **64 次**，每次等效 `2 + 8 = 10 KB`，总计 `64 × 10` = 640 KB，有效利用率 = `8 ÷ 10` = **80%**。等效耗时差 `1536 ÷ 640` = **2.4 倍**——而两者搬的真实数据量完全相同。给出的三个观测量同时满足 §12.6.2 的三条判据（MTE 占比 > 85%、带宽 < 50% 峰值、计算单元闲着），判成 **MTE Bound**。第一个动作**不是**调大 tile，而是**先确认 `BUFFER_NUM = 2` 真的生效了**——它代价最低，而且双缓冲没开时的表现会和这一模一样。参见 §12.6.2 那张成因表。
3. 910B3 屋脊点 ⚠️ ≈ 200，`150 < 200` → **Memory Bound**；性能上限 = `1.6 TB/s × 150` = **240 TFLOPS**，占峰值 `240 ÷ 320` = **75%**。H100 屋脊点 295，`150 < 295` → 也是 **Memory Bound**；上限 = `3.35 TB/s × 150` = **502 TFLOPS**，占峰值 `502 ÷ 989` ≈ **51%**。对比说明：**屋脊点低的机器更容易"把算力用满"，但那是因为它的算力本来就配得少**——绝对性能 240 vs 502 TFLOPS，昇腾仍然慢一半多。所以"算力利用率高"从来不是目标，绝对耗时才是（[02 章 §2.6](02-屋顶线与性能剖析.md) 讲 MFU 时是同一个道理）。参见 §12.4.1 与 §12.6.1。
