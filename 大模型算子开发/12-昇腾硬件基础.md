# 12 · 昇腾硬件基础：从 SIMT 换到达芬奇，脑子里那张图要重画

> **前置**：[01 · GPU 硬件基础](01-GPU硬件基础.md)、[02 · 屋顶线与性能剖析](02-屋顶线与性能剖析.md)。本章处处和它们对照，先读完那两章再来。
> **目标**：把前 11 章建立的 NVIDIA 心智模型平移到华为昇腾上——哪些概念一一对应，哪些**根本没有对应物**。后者才是真正的坑。

---

**本章关键词**

**NPU**（Neural Processing Unit，神经网络处理器）—— 相对 GPU 的通用并行架构，NPU 指为神经网络定制的专用芯片。昇腾属于此类。
**达芬奇架构**（DaVinci Architecture）—— 华为自研的 AI 计算架构，属于 DSA（Domain Specific Architecture，特定域架构）。
**AI Core** —— 达芬奇架构的基本计算单元，地位相当于 NVIDIA 的 SM（Streaming Multiprocessor）。
**Cube / Vector / Scalar** —— AI Core 内部三类计算单元，分别做矩阵乘、向量运算、流程控制。
**AIC / AIV**（AI Cube / AI Vector）—— 910B 起 Cube 和 Vector 被拆成两种独立的核，AIC 指矩阵核，AIV 指向量核。
**GM**（Global Memory，全局内存）—— 昇腾对片外主存（HBM）的称呼，相当于 GPU 的 HBM/Global Memory。
**UB**（Unified Buffer，统一缓冲区）—— Vector 单元专用的片上高速存储，相当于 GPU 共享内存的一部分角色。
**L0A / L0B / L0C** —— Cube 单元专用的三块片上缓冲：左矩阵、右矩阵、结果累加。GPU 上没有对应物。
**MTE**（Memory Transfer Engine，存储转换引擎）—— 专门负责各级存储之间搬运和格式转换的硬件单元。
**HCCS**（Huawei Cache Coherent System）—— 华为自研的片间高速互联，地位相当于 NVLink。
**UB 总线**（Unified Bus，统一总线）—— CloudMatrix 超节点使用的全互联总线。注意：**和上面的 Unified Buffer 是两个完全不同的东西，昇腾体系里这个缩写撞车了**，看到 UB 要先判断语境。
**CANN**（Compute Architecture for Neural Networks，神经网络计算架构）—— 昇腾的软件栈总称，地位相当于 CUDA。

> **关于本章数字的可信度标记**
> 华为**没有发布过昇腾 910B/910C 的完整数据手册**，公开数字来自产品页、拆解报告和社区实测，彼此矛盾的地方很多。本章沿用本仓库的核对纪律：
> **✅ 披露** = 华为官方产品页 / CANN 官方文档明确写出的；
> **⚠️ 推断** = 第三方分析、芯片拆解、学术论文或社区实测，仅供量级参考。
> 凡是要写进方案、拿去做容量规划的数字，**请用 §12.4.3 的方法在自己手上的卡上实测**，不要引用本章。

## 12.1 一句话说清两者的分歧

第 01 章讲过，GPU 的哲学是 **SIMT**（Single Instruction Multiple Threads，单指令多线程）：堆一万多个弱核，让它们用同一条指令处理不同数据。矩阵乘不是 GPU 的专属任务，它只是"恰好很适合"GPU 的一类任务——所以 NVIDIA 后来才要额外加 Tensor Core 这种专用单元打补丁。

昇腾反过来：**先认定矩阵乘是主要任务，再围绕它造芯片**。

```
NVIDIA（通用 → 专用）：
  一堆通用 CUDA Core  →  发现 AI 火了  →  加装 Tensor Core
  结果：一个 SM 里，通用单元和专用单元并存，靠编译器决定用哪个

华为昇腾（一开始就专用）：
  先问"AI 负载是什么"  →  答：矩阵乘 + 向量运算 + 少量控制
  →  直接造三种专门的硬件单元：Cube / Vector / Scalar
  结果：一个 AI Core 里没有"通用核"，每种运算有且只有一条硬件通路
```

这个差别带来的直接后果，是本章后面所有内容的根源：

| | NVIDIA GPU | 昇腾 NPU |
|---|---|---|
| 设计出发点 | 通用并行，AI 是应用之一 | AI 专用（DSA） |
| 并行模型 | SIMT，你写单线程代码，硬件管 32 个 | 显式多核 + 核内流水，你自己切数据 |
| 片上存储 | Cache 为主（L1/L2 自动管理） | **Scratchpad 为主（L1/L0/UB 全靠你手动搬）** |
| 数据搬运 | 访存指令触发，硬件透明 | **MTE 显式搬运，要写代码** |
| 矩阵乘单元 | Tensor Core，warp 级接口 | Cube，核级接口 |
| 最小调度单位 | Warp（32 线程） | 无对应物——**昇腾没有 warp** |

最后一行要单独强调：**昇腾没有 warp、没有 thread、没有 block、没有 bank conflict、没有 occupancy**。第 01 章里你辛苦建立的那套概念，有一半在这里直接作废。取而代之的是"多核切分 + 核内五级流水 + 手动双缓冲"，见 [13 · Ascend C 编程](13-AscendC编程.md)。

## 12.2 达芬奇架构：AI Core 内部长什么样

### 12.2.1 三类计算单元

一个 AI Core 内部有三种计算单元，各管一摊（✅ CANN 官方文档）：

```
┌─────────────────── 一个 AI Core（达芬奇） ───────────────────┐
│                                                              │
│  ┌────────────┐   矩阵乘。16×16×16 的三维立方体，            │
│  │   Cube     │   一条指令完成 4096 次乘累加。               │
│  │  矩阵单元  │   大模型 90% 的算力在这里。                  │
│  └────────────┘                                              │
│                                                              │
│  ┌────────────┐   除矩阵乘以外的一切：激活、归一化、         │
│  │  Vector    │   逐元素加减乘除、类型转换、规约……          │
│  │  向量单元  │   指令集非常丰富。                           │
│  └────────────┘                                              │
│                                                              │
│  ┌────────────┐   一个小 CPU：循环控制、分支判断、           │
│  │  Scalar    │   给 Cube/Vector 算地址和参数。              │
│  │  标量单元  │   它不干活，它指挥干活。                     │
│  └────────────┘                                              │
│                                                              │
│  ┌────────────┐   各级存储之间搬数据 + 顺手做格式转换。      │
│  │  MTE ×N    │   MTE1/MTE2/MTE3 分管不同方向。              │
│  │  搬运引擎  │   **它是独立流水线，能和计算重叠**。         │
│  └────────────┘                                              │
└──────────────────────────────────────────────────────────────┘
```

请特别记住 MTE 是**独立的硬件流水线**。这意味着"搬数据"和"算数据"可以真正同时发生——这正是第 13 章双缓冲（Double Buffer）的物理基础。在 GPU 上你也做类似的事（`cp.async` 异步拷贝、软件流水），但 GPU 上那是一种优化技巧，在昇腾上**这是基本写法，不这么写性能直接腰斩**。

### 12.2.2 Cube：16×16×16 的立方体

Cube 单元一条指令完成 `C[16×16] += A[16×16] × B[16×16]`：

```
16 × 16 × 16 = 4096 次乘累加 / 指令
```

对照第 03 章讲的 Tensor Core：Hopper 的 Tensor Core 也是做 MMA（Matrix Multiply-Accumulate，矩阵乘累加），但接口是 **warp 级**的——需要一个 warp 的 32 个线程协同持有数据碎片。Cube 是**核级**的，你不用操心线程怎么分数据，只要把数据按规定格式搬进 L0A/L0B 就行。

> ⚠️ 推断：社区资料称达芬奇核分 Max / Lite / Tiny 三档，Max 核单周期 8192 次 MAC（可能是 FP16 口径下计入了两个 Cube 或双发射），Tiny 核仅 512 次。这组数字和"16×16×16 = 4096"对不上，公开资料没有解释差异来源，请勿据此推算峰值算力。

**维度对齐的要求比 GPU 更硬**。第 03 章说 Tensor Core 要求维度是 16 的倍数，否则退化；昇腾这边不是"退化"，而是数据在片上就必须按分形格式摆放（见 §12.3.3），不对齐会触发额外的补齐搬运，代价明显更大。

### 12.2.3 AIC / AIV 分离：910B 最重要的架构变化

这是从 910A 到 910B 最需要知道的一件事（⚠️ 推断，来自社区与学术资料，官方文档未系统说明演进）：

```
910A（耦合架构）：
  ┌──────── 一个 AI Core ────────┐
  │  Cube  +  Vector  同核部署   │   Cube 算完的结果留在 L0C，
  │  共享 Scalar、共享指令流     │   Vector 直接从 L0C 取走接着算
  └──────────────────────────────┘   → 中间结果不出片

910B / 910C（分离架构）：
  ┌─── AIC（矩阵核）───┐      ┌─── AIV（向量核）───┐
  │ Cube + 自己的      │      │ Vector + 自己的     │
  │ Scalar + 自己的    │      │ Scalar + 自己的     │
  │ 指令流             │      │ 指令流              │
  └────────┬───────────┘      └──────────┬─────────┘
           │                              │
           └──────► Global Memory ◄───────┘
                   （经 L2 中转）
                 ↑ 两者之间没有直连通道
```

**AIC : AIV = 1 : 2**（✅ CANN 官方文档）——一个矩阵核配两个向量核。

分离架构的好处是矩阵计算和向量计算能各自独立调度、互不阻塞；代价是**AIC 和 AIV 之间的数据必须绕 Global Memory（经 L2）**，不能像 910A 那样在片上直接交棒。

这一条直接决定了昇腾上融合算子的写法。回想第 05 章讲的算子融合：GPU 上把 GEMM（General Matrix Multiply，通用矩阵乘）和后面的激活函数融合，收益来自"中间结果不写回 HBM"。在 910B 上，如果 GEMM 跑在 AIC、激活跑在 AIV，那中间结果**照样要过 GM**，融合收益被削掉一大截。于是昇腾的融合算子必须在 tiling（分块）层面做**CV 流水并行**：把数据切成块，让 AIV 处理第 k 块的同时 AIC 已经在算第 k+1 块，用流水重叠掩盖搬运，而不是靠"消除搬运"。

> 这也解释了一个常见困惑：为什么昇腾上 FlashAttention 类算子的优化文章，通篇在讲"核间负载均衡""CV 流水并行""MTE2 流水优化"，而不像 GPU 那边讲"把 softmax 留在 SRAM 里"。物理约束不同，优化的着力点就不同。详见 [04 章 §4.9](04-FlashAttention全系.md)。

> ⚠️ 推断：下一代昇腾 950 据称针对性地补了这个短板——AIC 与两个 AIV 共享 L1，且新增小容量直通缓冲供 AIC↔AIV 小数据交互，不必绕 GM。若属实，未来几代的融合算子写法会再变一次。

## 12.3 内存层级：Cache 世界 → Scratchpad 世界

这是 GPU 工程师转昇腾最容易摔跤的地方。

### 12.3.1 完整层级

```
                    ┌──────────────────────┐
                    │   GM / HBM（片外）    │  64 GB 级，最慢
                    └───────────┬──────────┘
                                │  MTE2 搬入 / MTE3 搬出
                    ┌───────────┴──────────┐
                    │   L2 Cache（片上）    │  多核共享，硬件管理
                    └───────────┬──────────┘
                                │
            ┌───────────────────┴──────────────────┐
            │                                      │
   ┌────────┴────────┐                   ┌─────────┴─────────┐
   │  AIC（矩阵核）   │                   │  AIV（向量核）     │
   │                 │                   │                   │
   │  L1 Buffer      │  中转/复用暂存     │   UB              │
   │      ↓          │                   │  Unified Buffer   │
   │  L0A  L0B       │  左矩阵 / 右矩阵   │  Vector 的唯一    │
   │    ↘   ↙        │                   │  工作区           │
   │    [Cube]       │                   │      ↓            │
   │      ↓          │                   │   [Vector]        │
   │    L0C          │  结果 + 累加       │                   │
   │      ↓          │                   │                   │
   │  BT Buffer      │  Bias 表           │                   │
   │  FP Buffer      │  量化/Relu 参数    │                   │
   └─────────────────┘                   └───────────────────┘
```

典型数据流（✅ CANN 官方文档）：

```
Cube 计算：  GM → L1 → L0A/L0B → [Cube] → L0C → FixPipe → GM（或回写 L1）
Vector 计算：GM → UB → [Vector] → UB → GM
```

### 12.3.2 和 GPU 的对照，以及"没有对应物"的部分

| 昇腾 | GPU 上最接近的东西 | 关键差异 |
|---|---|---|
| GM | HBM / Global Memory | 基本一致 |
| L2 Cache | L2 Cache | 基本一致，都是硬件自动管理 |
| L1 Buffer | 共享内存（Shared Memory） | **L1 是 scratchpad，不是 cache**：不会自动填充，必须显式 `DataCopy` 搬进来 |
| UB | 共享内存 | 同上，且**只有 Vector 能用** |
| L0A / L0B / L0C | **无对应物** | Tensor Core 的操作数直接来自寄存器，昇腾则有三块专用缓冲 |
| BT / FP Buffer | **无对应物** | 910B 分离架构新增，专存 Bias 和量化参数 |
| MTE | `cp.async` / LDGSTS 指令 | GPU 上是指令，昇腾上是**独立硬件单元**，有自己的流水线编号 |
| 寄存器文件 | 寄存器文件 | 昇腾这层对开发者基本不可见 |
| **无对应物** | Bank Conflict | 昇腾片上存储的冲突模型不同，第 01 章那套 padding 技巧用不上 |
| **无对应物** | Occupancy | 昇腾没有"多个 warp 轮转掩盖延迟"这回事，延迟靠**流水线重叠**掩盖 |

最后两行值得停下来想一想。GPU 隐藏访存延迟的办法是**超额订阅**：一个 SM 上挂 64 个 warp，这个 warp 等内存时就切到那个 warp，所以第 01 章要讲 occupancy。昇腾的办法是**流水线**：MTE2 搬第 k+1 块的同时，Cube 在算第 k 块，Vector 在处理第 k-1 块的结果，MTE3 在写第 k-2 块。延迟靠"手工排流水"掩盖，不是靠"多开线程"掩盖。

**所以昇腾算子调优的核心问题不是"occupancy 够不够"，而是"流水排没排满、哪一级是瓶颈"**。判断方法见第 13 章讲的 msprof 指令流水图。

### 12.3.3 FRACTAL_NZ：一个躲不掉的数据格式

昇腾片上的矩阵不按你熟悉的行优先（Row Major）摆放，而是按**分形格式**：

```
NZ 格式（FRACTAL_NZ）直觉：
  把一个大矩阵先切成 16×16 的小块，
  块内按行优先存，块间按列优先排。

为什么：Cube 一次吃 16×16，按这个格式摆好，
        搬运时不需要跨步（stride）访问，MTE 效率最高。
```

实践后果：

- L1 Buffer 里推荐用 NZ 格式，这样搬到 L0A / L0B 时（两者还要分别转成 ZZ / ZN 格式）格式转换开销最小（✅ CANN 文档）。
- 从 GPU 迁移过来的代码里，那些手工算 stride 的逻辑基本都要重写。
- `torch_npu` 里有 `npu_format_cast` 这类接口在 ND（普通格式）和 NZ 之间转换。**转换本身是有成本的**，模型里反复 ND↔NZ 横跳是昇腾上一类典型的隐性性能损失。

## 12.4 规格：910B 与 910C

### 12.4.1 910B：先搞清楚你手上是哪一款

**"910B" 不是一款芯片，是一个系列**。B1/B2/B3/B4 的 AI Core 数量和 HBM 带宽差异巨大，笼统说"910B"会导致严重的性能预估偏差。

| 型号 | AI Core | HBM 容量 | HBM 带宽 | FP16 算力 | 可信度 |
|---|---|---|---|---|---|
| 910B2 | 24 AIC + 48 AIV | 64 GB | — | — | ⚠️ 推断（学术论文口径） |
| 910B3 | 20 AIC @ 1.8 GHz | 64 GB | ~1.6 TB/s | ~320 TFLOPS | ⚠️ 推断 |
| 910B4 | 20 AIC + 40 AIV | 32 GB | ~800 GB/s | 280 TFLOPS | ✅ 部分（见下） |

唯一的厂商一手口径是**整机/板卡产品页**：

- **Atlas 300T A2**（采用 910B4 die）：20 个 AI Core、280 TFLOPS FP16、75 TFLOPS FP32 —— ✅ 披露
- **Atlas 800T A2** 训练服务器（8 卡）：整机 2.56 PFLOPS FP16 —— ✅ 披露，反推单卡 320 TFLOPS —— ⚠️ 推断

流传最广的两组数字是「320 TFLOPS FP16 / 640 TOPS INT8」和「256 TFLOPS FP16 / 512 TOPS INT8」，**都无官方出处**。带宽数字更乱，从 400 GB/s 到 2.4 TB/s 的说法都有人写，大概率是混淆了不同子型号和不同口径（单 die / 单卡、单向 / 双向）。

粗略量级感知（⚠️ 全部为推断，仅用于建立直觉，**不可用于选型**）：

```
910B3 ≈ A100 的算力量级（FP16 ~320 vs 312 TFLOPS）
       但 HBM 带宽（~1.6 TB/s）低于 H100（3.35 TB/s）约一半
       且没有 FP8 Tensor Core 对应物（见第 06 章：昇腾走的是 INT8 和 HiF8 路线）
```

对照第 02 章的屋顶线：昇腾 910B3 的屋脊点 ≈ 320e12 / 1.6e12 ≈ **200 FLOP/Byte**（⚠️ 基于推断数字计算），比 H100 的 295 低。这意味着**同一个算子，在昇腾上更容易落在 Compute Bound 一侧**——第 02 章的诊断流程照用，但屋脊点要换。

### 12.4.2 910C：双 die 封装

⚠️ 以下全部为第三方分析（SemiAnalysis 等）估算，华为未发布数据手册：

```
910C = 两颗 910B 级的 die 封装在一起
  ├─ 稠密 BF16 算力   ~780 TFLOPS
  ├─ HBM              ~128 GB
  └─ HBM 带宽         ~3.2 TB/s
```

工程上最要紧的一点不是算力数字，而是：**双 die 意味着卡内也存在 NUMA 效应**。一张 910C 上的两个 die 之间通信，和 die 内通信的代价不同。做算子切分和通信编排时，把一张 910C 当成"一个均匀的加速器"会踩坑。

### 12.4.3 别信本节，去查你自己的卡

这是本章最有用的一段。三个办法：

```bash
# 1) 看硬件实况：型号、HBM 容量、AICore 使用率、HBM 带宽占用
npu-smi info
npu-smi info -t usages -i 0

# 2) 看 CANN 眼中的芯片参数（最权威的本地来源）
#    CANN 安装目录下有 platform_config/，每个文件对应一款芯片子产品
#    里面写着真实的 AI Core 数、各级 Buffer 容量、频率
find /usr/local/Ascend -type d -name "platform_config" 2>/dev/null
#    然后查看对应 soc_version 的 .ini 文件，如 Ascend910B3.ini

# 3) 代码里查
python3 -c "import torch, torch_npu; print(torch_npu.npu.get_device_name(0), torch_npu.npu.get_device_properties(0))"
```

`platform_config` 里的 `.ini` 文件是写 Ascend C 算子时的必备参照——L1/L0/UB 的实际容量都在里面，第 13 章做 tiling 时要按它算。

## 12.5 互联：HCCS、UB 总线与超节点

### 12.5.1 单机内

**HCCS**（Huawei Cache Coherent System）是华为自研的片间高速互联，地位等同 NVLink，支持硬件级缓存一致性。

- 服务器内基础拓扑是 **Full Mesh 全互联**（✅ HCCL 文档），8 卡两两直连，和 NVSwitch 的效果类似但实现路径不同。
- 服务器间走 **RoCE**（RDMA over Converged Ethernet）组成 Fat Tree。
- ⚠️ 推断：单链路约 100 GB/s 双向，社区常引用的卡间互联带宽为 392 GB/s。对比 H100 NVLink 的 900 GB/s，这是昇腾集群侧最明显的短板之一——直接影响第 08 章讲的 MoE All-to-All 和 TP（Tensor Parallel，张量并行）的可行规模。

### 12.5.2 CloudMatrix 384 超节点

华为云 2025 年 4 月发布的 CM384（✅ 配置为官方发布）：

```
384 颗 Ascend 910C + 192 颗鲲鹏 CPU
    ↓ 全部经 UB（Unified Bus，统一总线）全互联，无阻塞 all-to-all
约 300 PFLOPS 稠密 BF16 算力（⚠️ SemiAnalysis 估算）
约 48 TB HBM 总容量
四层结构：计算节点（48 节点 × 8 NPU）→ L1 板级交换 → L2 机柜级交换 → RDMA 横向扩展
光互联：6912 个 400G 硅光 LPO 光模块
```

**对算子开发者的意义**：超节点把"跨机通信"变成了"节点内通信"级别的延迟（⚠️ 官方宣称跨节点带宽劣化 <3%、时延增加 <1 μs）。这改变了 MoE 专家并行的设计空间——在 GPU 集群上你要费尽心思把专家塞进 NVLink 域内，在超节点上 384 卡是一个平坦的通信域。第 08 章讲的分层 All-to-All 策略，在这里的最优解不一样。

代价是能效：SemiAnalysis 的评价是 CM384 用封装、光互联和系统设计弥补了制程劣势，代价是显著更高的功耗。

> ⚠️ 单 NPU 的 UB 带宽数字在公开资料里有 196 GB/s、~390 GB/s、2.8 Tbps 三种说法，量纲和口径（单 die / 单封装、单向 / 双向）都不统一，本章不给结论。

## 12.6 那么第 02 章的屋顶线还能用吗

能用，但要换三样东西。

```
第 02 章的 GPU 屋顶线：
  P = min(峰值算力, 峰值带宽 × 算术强度 I)
  瓶颈二选一：Compute Bound / Memory Bound

昇腾的屋顶线：公式一样，但——
  ① 屋脊点换成昇腾的（910B3 ⚠️ ≈ 200 FLOP/Byte）
  ② 峰值算力要区分 Cube 和 Vector：
     一个算子如果全是 Vector 运算（如 LayerNorm、Softmax），
     它根本用不到 Cube，"峰值算力"对它毫无意义
  ③ 多一类瓶颈：MTE Bound（搬运受限）
```

第三条是昇腾独有的。在 GPU 上，访存受限就是访存受限；在昇腾上，因为搬运由独立的 MTE 流水线执行，你会遇到"HBM 带宽没跑满、Cube 也没跑满，但 MTE2 流水占满了"的情况——数据在 GM→L1→L0 的路上堵住了。

所以昇腾的算子瓶颈分类是**四选一**：

| 瓶颈 | 现象 | 对策 |
|---|---|---|
| Cube Bound | Cube 流水占比高 | 已经最优，或换更大 tiling |
| Vector Bound | AIV 流水占比高，AIC 空转 | CV 流水并行；或把部分计算挪给 Cube |
| MTE Bound | MTE2/MTE3 占比高 | 开双缓冲、调 tiling 块大小、改数据格式（ND→NZ） |
| Scalar / 下发 Bound | 三个流水都不满，host 侧下发密 | 开图模式（见 [14 章 §14.5](14-GPU到NPU迁移实战.md)），减少算子下发次数 |

判断工具是 MindStudio Insight 的**指令流水图**，第 13 章会给完整的排查路径。

## 12.7 小结

```
达芬奇 = DSA，不是 SIMT
  AI Core ≈ SM，但内部是 Cube / Vector / Scalar 三类专用单元
  910B 起 Cube 和 Vector 拆成独立的核：AIC : AIV = 1 : 2
  两者之间必须绕 GM 交换数据 → 融合算子要靠 CV 流水并行，不是靠"不落盘"

内存是 Scratchpad 不是 Cache
  GM → L2 → L1 → L0A/L0B/L0C（Cube）
                → UB（Vector）
  每一级都要显式 DataCopy 搬，MTE 是独立硬件流水线
  L0A/L0B/L0C、BT/FP Buffer、MTE 在 GPU 上没有对应物
  warp、bank conflict、occupancy 在昇腾上没有对应物

规格：查你自己的卡，别信任何二手数字
  npu-smi info + CANN 的 platform_config/*.ini
  910B 分 B1/B2/B3/B4，AI Core 数和带宽差异巨大
  910C 是双 die，卡内有 NUMA 效应

屋顶线照用，但屋脊点要换，且多一类 MTE Bound

下一章：知道了硬件长什么样，开始用 Ascend C 写第一个算子。
```
