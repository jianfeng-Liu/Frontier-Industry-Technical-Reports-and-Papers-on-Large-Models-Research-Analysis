B. 关键公式速查

B.1 算术强度与屋顶线

算术强度 I = FLOPs / Bytes（读写总字节数）

屋顶线性能上界：
  P = min(峰值算力, 峰值带宽 × I)
  H100 屋脊点 = 989 TFLOPS / 3350 GB/s ≈ 295 FLOP/Byte

  I < 295：Memory Bound，P ≈ 3350 × I (GFLOPS，I 单位 FLOP/Byte)
  I ≥ 295：Compute Bound，P → 989 TFLOPS

B.2 GEMM 算术强度

A: M×K，B: K×N，C: M×N（FP16，2 Bytes/元素）

FLOPs  = 2·M·K·N
Bytes  = 2·(M·K + K·N + M·N)

I ≈ M·K·N / (M·K + K·N + M·N)

特殊情形：
  M=1（推理 batch=1）：I ≈ 1 FLOP/Byte
  M=64：              I ≈ 64 FLOP/Byte（近似，K=N 时）
  M=N=K=大数：        I ≈ M/2 FLOP/Byte → Compute Bound

B.3 MFU（Model FLOPs Utilization，模型算力利用率）

MFU = (tokens/s × 6N) / 峰值算力      ← 分母单位是 FLOP/s，不是 TFLOPS

N = 参数量。6N ≈ 训练时每个 token 每个参数的 FLOP 数，构成是：
      2N  前向
    + 2N  反向：算输入的梯度
    + 2N  反向：算权重的梯度
    ─────
      6N
  ⚠️ 不含优化器。优化器是 per-step per-parameter 的开销，
     不随 token 数增长，不进这个式子。

⚠️ 6N 漏算了 Attention 的 QKᵀ 和 PV（它们不是参数矩阵乘）。
   补全式：6N + 12·L·s·H   （L 层数，s 序列长度，H 隐藏维度）
   长序列下漏算可观：LLaMA-3 8B 在 s=8192 时漏算约 27%。

业界顶级：MFU ≈ 40–50%（单机 8×H100）
⚠️ 引用任何 MFU 数字都必须带硬件平台——PaLM 那个 46.2% 是 6144 块
   TPU v4 上的结果，不是 GPU。

推导过程、DeepSeek-V3 的完整代入（34.6%）、以及 MFU 与 HFU 的区别见 02 章 §2.6。

B.4 注意力内存开销

朴素 Attention 中间矩阵 S = QK^T：
  大小 = B × H × N × N × 2 Bytes（FP16）
  N=8192, H=32, B=1：≈ 4 GB
  N=32768：≈ 64 GB（超出 H100 80 GB 显存！）

FlashAttention 重计算后：
  保存量 = O(N)，与序列长度线性

B.5 KV Cache 大小

通式（唯一该记的那个）：
  每 token 每层 = 2 × n_kv_heads × head_dim × 字节数
                  ↑ K 和 V 两份

  MHA（n_kv_heads × head_dim = d_model）时退化为：
    FP16 下 = 2 × d_model × 2 = 4 × d_model Bytes

⚠️ 本表此前写的是 8 × d_model，多乘了一个 2，所有下游数字都翻倍了。

LLaMA-3 70B 实际值（80 层，GQA：8 个 KV head × head_dim 128）：
  每 token = 80 × 2 × (8 × 128) × 2 = 327680 Bytes = 320 KiB

  ⚠️ 别用 d_model=8192 硬套 MHA 公式——那会算出 2.56 MB/token，
     整整高估 8 倍。70B 是 GQA，KV head 只有 8 个不是 64 个。
     GQA 省下的正是这 8 倍。

  80 GB 卡装得下多少：(80 − 权重 141/TP8 ≈ 17.6 − 开销 4) ≈ 58 GiB
                      ÷ 320 KiB ≈ 190K token

B.6 量化误差与位宽

对称量化（scale-only）：
  x_q = round(x / s)，x_dq = x_q × s
  s = max(|x|) / (2^(b-1) - 1)

FP8 E4M3：动态范围 ±448，    尾数 3 bit（+ 隐含位 = 4 bit 有效数）→ ≈1.2 位十进制
FP8 E5M2：动态范围 ±57344，  尾数 2 bit（+ 隐含位 = 3 bit 有效数）→ ≈0.9 位十进制
INT8：   动态范围 [-128, 127]，8 bit                            → ≈2.4 位十进制
INT4：   动态范围 [-8, 7]，    4 bit                             → ≈1.2 位十进制

⚠️ 本表此前把 FP8 两行写成「~3 / ~2 有效位（十进制）」，那是把
   尾数的二进制位数当成了十进制有效位。换算是 log10(2^有效位数)。

★ 记这个对比就够：E4M3 和 INT4 的十进制精度是同一量级（都 ≈1.2 位），
  但 E4M3 的动态范围宽了几个数量级 —— 这正是 FP8 在有离群值时
  比 INT8/INT4 稳的原因，而不是因为它「更准」。
  ⚠️ 没有离群值、分布均匀时，INT8（2.4 位）反而比 E4M3 更准。

G. MoE 关键数字（DeepSeek-V3 规模参考）

模型规模：671B 参数，37B 激活
专家配置：256 路由专家 + 1 共享专家，Top-8 路由
隐藏维度：H = 7168

EP 配置随场景不同（都是官方口径，别混用）：
  训练        EP=64（跨 8 机），PP=16，TP=1，2048 张 H800
  推理 Prefill EP=32（含 32 个冗余专家）
  推理 Decode  EP=144（⚠️ 技术报告写 EP=320，开源周博客写 EP=144，时期不同）

All-to-All 通信量（每层）：
  单向 = tokens × Top-K × H × sizeof(dtype) × (1 − 1/EP)
                    ↑ 别漏这一项：每个 token 要发给 K 个专家
  Dispatch + Combine = 上式 × 2

  例：tokens=4096，K=8，H=7168，BF16，EP=64
    单向 = 4096 × 8 × 7168 × 2 × 63/64 ≈ 462 MB
    往返 ≈ 924 MB

Grouped GEMM 的不规则性：
  每专家平均 tokens = tokens × K / 256 = tokens / 32
  tokens=4096 → 每专家约 128 个（实际按 Poisson 分布，有专家空 / 过载）
  ⚠️ 每专家须 ≥ 约 362 个 token 才跨得过屋脊点 295，128 个远不够
     → 专家 GEMM 在训练时通常仍是 Memory Bound

⚠️ 本表此前的算式漏了 × Top-K，且把 56.9 MB 写成了 1.76 GB（差 30 倍），已修正。带宽单位、逐卡推演、以及 EP 与 TP 通信量之比 K/p 的推导见 08 章 §8.3。NVLink 900 GB/s 是双向聚合值，算单向发送要用 450 GB/s。

迁移四坑（详见 04 章 §4.9.3）：

按性质分三类，排查优先级完全不同：

【静默精度错误】不报错、只是结果不对 —— 必须逐层比对才发现，优先级最高
  ① atten_mask 语义相反 —— NPU 侧 True = 屏蔽，要 torch.logical_not()
     自检：causal attention 下 out[0] 必须等于 V[0]
  ② sparse_mode：替换 flash-attn ≤2.0 用 2，≥2.1 用 3
     S_q ≠ S_kv 时左上/右下对齐差 (S_kv − S_q) 列；方阵下两者重合，
     ⚠️ 所以用方阵测试测不出这个坑

【会报错】跑不起来，反而是最省事的一类
  ③ 定长 kernel 要求序列长 128 的倍数 —— 直接触发 kernel 错误
     变长场景改用 input_layout="TND" + actual_seq_qlen

【静默性能损失】结果对、就是慢 —— 不是精度问题，别混进精度排查
  ④ head_dim 对齐要求比 GPU 严（FRACTAL_NZ 分形格式）
     padding 到 128 的浪费是平方级的：序列 [10,37,512,8] 补齐到 512
     → 4×512² / (10²+37²+512²+8²) ≈ 4.0 倍计算浪费

⚠️ 本表此前把四条并列并写「①② 都是静默错误」，读者容易把 ③（会报错）和 ④（静默性能损失）也当成精度问题。三类的排查方法不同：精度类走 msprobe 逐层比对（见 §L.8），性能类走 msprof 流水图（见 §L.4–L.5）。详见 14 章 §14.4。

L.2 Ascend C 三段式骨架

CopyIn  (MTE2)  →  Compute (Vector/Cube)  →  CopyOut (MTE3)
   AllocTensor        DeQue                    DeQue
   DataCopy           计算 API                 DataCopy
   EnQue              EnQue + FreeTensor       FreeTensor

TPipe  管片上内存      pipe.InitBuffer(que, BUFFER_NUM, bytes)
TQue   管传递 + 同步   EnQue / DeQue
TBuf   管临时变量      tmpBuf.Get<T>()
BUFFER_NUM = 2         开启双缓冲 —— 不是优化，是基本功

A2 / B2 L0A / L0B 矩阵第二级（Cube 直接吃）

L.4 四类瓶颈与对策

瓶颈 流水图现象 对策
Cube Bound Cube 占比高 理想状态，剩余收益在换更大 tiling
Vector Bound AIV 高、AIC 空转 CV 流水并行；部分计算挪给 Cube
MTE Bound MTE2/MTE3 占比高 ① 确认 BUFFER_NUM=2 ② 调大 tileLength ③ 32 Byte 对齐 ④ 查 ND↔NZ 隐式转换
下发 Bound 三级都不满但总耗时长 开 ACLGraph 或 TorchAir 图模式；合并小算子

L.7 昇腾维度对齐（对照 §I 的 GPU 版）

Cube 基本块：16×16×16
DataCopy 对齐：32 Byte
定长 FA kernel：序列长度须为 128 的倍数（变长请改用 TND 布局）
片上矩阵格式：FRACTAL_NZ（L1 推荐 NZ，搬到 L0A/L0B 再转 ZZ/ZN）
昇腾没有 warp、没有 bank —— §I 的 32 线程/32 bank 规则全部不适用

非对齐搬运的出路：DataCopyPad（CANN 7.0+，⚠️ 310 推理卡不支持）
  ⚠️ blockLen 的单位是【字节】不是元素个数 —— 最高频踩坑点
  ⚠️ GM→UB 方向，为凑对齐多搬进来的 dummy 区【不保证为 0】：
       padding 全为 0 时 → 填的是待搬数据块的第一个元素值
       padding 非 0 且 isPad=false 时 → 填随机值
     直接接 ReduceSum 会把它算进和里，且【只在 shape 不整除时才出现】
     → 传 isPad=true + paddingValue=0，或算完再把尾巴清掉
  ✓ UB→GM 方向是安全的（框架自动补齐后丢弃）

UB 容量不要写死：用 GetCoreMemSize(CoreMemType::UB, ubSize) 查
  ⚠️ 跨型号差异很大（社区口径 910B ≈192 KB、310B ≈248 KB）

⚠️ 本表此前把尾块 bug 归因为「昇腾没有 mask」，归因是错的。矢量计算 API 是有 mask 的（见 §K.3），真正的成因是上面那条 DataCopyPad 的 dummy 填充值不为 0。详见 13 章 §13.5.3。

L.8 精度比对速查（迁移必用）

迁移时「结果不对」的排查主路径。⚠️ 官方文档只说按阈值过滤、没给数值门槛，下面的阈值是工具源码常量口径，标 ⚠️。

pip install mindstudio-probe          # 工具名 msprobe（mstt 仓库）

# 比对（-s 生成汇总）
msprobe -f pytorch compare -i ./compare.json -o ./output -s

# 计算图可视化比对
msprobe -f pytorch graph_visualize -tp ./gpu_dump -gp ./npu_dump

采集粒度：先粗后细，别一上来就 dump 全部张量
  level = "L0"          只采 module 级（层粒度）      ← 先跑这个定位到层
  level = "L1"          采 API 级（算子粒度）          ← 再在可疑层内细查
  task  = "statistics"  只存统计量，快、占空间小       ← 先跑这个
  task  = "tensor"      存完整张量，慢、占空间巨大     ← 确认可疑点后再开

五个指标与判读（⚠️ 阈值为工具常量口径，非官方门槛）：
  Cosine（余弦相似度）        ≥ 0.9999 视为一致
  MaxAbsErr（最大绝对误差）    < 0.001
  MaxRelativeErr（最大相对误差）
  单千分之一 / 双千分之一      ≥ 0.99
  ⚠️ 阈值要结合量级看：MaxAbsErr 0.001 对 RMSNorm 输出是问题，
     对 logits（量级 10）是噪声

二分定位三步法：
  ① 只看比对表里【第一个】变红的条目 —— 后面的红都是它传染的
  ② 在该层内把 level 切到 L1，逐算子看
  ③ 写 20 行脚本最小复现该算子，脱离模型调试

性能类问题不走这条路，走 msprof 流水图（§L.4–§L.5）。两类问题的区分见 §K.4。

M. 访存效率速查（GPU）

对应 01 章 §1.4–§1.6。昇腾没有 warp / bank / occupancy 这套概念，本节整节不适用，对照见 12 章。

M.1 合并访存：一个 Warp 碰到几个扇区

扇区（Sector）= 显存访问的最小粒度 = 32 Bytes
一个 Warp 读 32 个 float = 128 Bytes = 最好情况下 4 个扇区
判据：同一 Warp 的 32 个线程，地址落进了几个不同的 32B 扇区？
访问模式（float，tid = Warp 内通道号 0–31） 扇区数 搬入 有效 效率
x[tid] 连续且 128B 对齐 4 128 B 128 B 100%
x[tid + 1] 连续但错位 5 160 B 128 B 80%
x[tid * 2] 跨步 2 8 256 B 128 B 50%
x[tid * 8] 跨步 8 32 1024 B 128 B 12.5%
x[tid * 32] 跨步 ≥8 均同此 32 1024 B 128 B 12.5%
x[0] 全员同址 1 32 B 广播 正常 ✓ 
★ 法则：让 threadIdx.x 对应内存里变化最快的那一维
        （C 行优先存储中 = 最后一维）

行优先 float A[M][N]：
  A[blockIdx.x][threadIdx.x]   → 相邻线程差 4 B    → 合并  ✓
  A[threadIdx.x][blockIdx.x]   → 相邻线程差 N×4 B  → 12.5% ✗

⚠️ 跨步 ≥ 8 个 float 之后效率就锁死在 12.5%，不会继续恶化
   （每个线程已各占一个独立扇区，再跨也是 32 个扇区）

M.2 Bank Conflict：算 Bank 编号

共享内存 = 32 个 bank × 4 Bytes
第 n 个 4 字节 → Bank (n % 32)

float tile[R][C] 中 tile[r][c] 的 bank = (r × C + c) % 32
情形 结果
32 个线程 → 32 个不同 bank 1 个周期 ✓
k 个线程 → 同一 bank 的不同地址 k 路冲突，k 倍延迟 ✗
多个线程 → 同一 bank 的同一地址 广播，1 个周期 ✓ 不是冲突 
按列访问 float tile[32][32]：下标 r×32，(r×32)%32 ≡ 0
  → 32 个线程全撞 Bank 0 → 32 路冲突，32 倍延迟

Padding 修复：float tile[32][33]
  (r×33) % 32 = (r×32 + r) % 32 = r % 32 → r=0..31 各不相同 → 无冲突 ✓
  代价：每行多 1 个 float（4 KB 的 tile 涨到 4.125 KB，+3%）

通用 padding 规则（元素宽 4 B）：列数 C 若满足 C % 32 == 0，按列访问必冲突
  取 C' = C + 1 即可错开；C 为奇数时本就无冲突

⚠️ Swizzle（异或置换）是更现代的替代：不占额外空间、不破坏 128B 对齐，
   CUTLASS / Triton 用的是它。见 03、07 章

M.3 Occupancy：三条限制取最小

Occupancy = 驻留 Warp 数 / 64（H100 每 SM 上限）

每 SM 可驻留 Block 数 = min(①, ②, ③)

① 寄存器限制：每 Warp 寄存器 = 每线程寄存器 × 32，向上取整到 256 的倍数
                可驻留 Warp = floor(65536 / 每 Warp 寄存器)
                可驻留 Block = floor(可驻留 Warp / 每 Block Warp 数)
② 共享内存限制：floor(228 KB / 每 Block 共享内存)
③ 数量限制：    min(floor(64 / 每 Block Warp 数), 32)

代入示例：Block = 256 线程（8 Warp），每线程 40 寄存器，每 Block 32 KB 共享内存

限制 计算 得出 Block 数
① 寄存器 40×32 = 1280；65536/1280 = 51.2 → 51 Warp；51/8 = 6.375 6 ← 瓶颈
② 共享内存 228/32 = 7.125 7
③ 数量 64/8 = 8 8

→ 6 个 Block × 8 Warp = 48 Warp → Occupancy = 48/64 = 75%

掩盖延迟需要多少 Warp（⚠️ 简化模型）：
    需要的 Warp 数 ≈ 访存延迟 / 单 Warp 的计算时间
    例：HBM 500 周期 / 每 Warp 算 20 周期 = 25 个 Warp → 39% 就够

★ Occupancy 不是越高越好。高性能 GEMM 常只有 25–50%——
  让每线程多占寄存器、多算几个输出，复用率的收益大于驻留数的损失。
  判据永远是实测时间，不是百分比。

⚠️ 压寄存器换 Occupancy 要小心：一旦触发寄存器溢出（spill），
   变量落到 HBM，1 周期变 500 周期，净亏。
   查法：nvcc -Xptxas -v，看 "spill stores / spill loads" 是否非 0

M.4 延迟量级（⚠️ 实测量级，随代际浮动）

寄存器 ~1  →  共享内存 ~25  →  L1 ~35  →  L2 ~250  →  HBM ~500   （周期）
                  ↑ 比 HBM 快 20 倍以上 —— 所有「分块 + 片上复用」优化的根源
