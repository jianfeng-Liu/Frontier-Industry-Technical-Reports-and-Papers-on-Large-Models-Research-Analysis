## 1.1 先复述五个模块（不重写，只对齐词汇）

任何一个 RL 训练框架，拆开都是这五块。这个拆法在 [14 章 §14.4](../训练框架/分布式训练入门/14-RL训练框架.md) 已经讲过，这里只把名字对齐，方便后面几章引用：

```
┌──────────────────────────────────────────────────────────┐
│                    ① Controller（控制器）                │
│         决定「现在该生成还是该训练」的那段主循环         │
└───────────────┬──────────────────────────┬───────────────┘
                │                          │
       ┌────────▼────────┐        ┌────────▼────────┐
       │  ② Rollout      │        │  ④ Trainer      │
       │  生成引擎       │        │  训练引擎       │
       │  vLLM / SGLang  │        │  Megatron/FSDP  │
       └────────┬────────┘        └────────┬────────┘
                │                          │
                │   ③ Data Buffer          │
                └──────►（样本队列）───────┘
                             │
                ⑤ Weight Sync（权重同步）
                训练完的新权重，怎么塞回生成引擎
```

| 模块 | 干什么 | 本目录哪一章展开 |
|---|---|---|
| ① Controller | 主循环：什么时候生成、什么时候更新、允不允许并行 | [02](02-架构主轴-同步到全异步.md) |
| ② Rollout | 让模型生成答案。RL 里 ~80% 时间在这 | [02](02-架构主轴-同步到全异步.md) |
| ③ Data Buffer | 生成好的样本排队等训练。**队列有多深，就决定了架构有多异步** | [02](02-架构主轴-同步到全异步.md) |
| ④ Trainer | 算梯度、更新参数 | [05](05-算法与框架的接口.md) |
| ⑤ Weight Sync | 新权重搬回生成引擎，中间要 resharding（重切分） | [03](03-权重同步.md) |

> 🌐 HuggingFace 那篇 16 框架横评把这五块进一步展开成**七条轴**（编排原语 / buffer 深度 / 权重同步协议 / 陈旧度管理 / partial rollout 处理 / LoRA 支持 / 训练后端与并行）。本目录把其中最吃架构的三条——**buffer 深度**、**权重同步**、**陈旧度管理**——分别放进 [02](02-架构主轴-同步到全异步.md)、[03](03-权重同步.md)、[04](04-训推一致性.md)。
> 来源：[Keep the Tokens Flowing: Lessons from 16 Open-Source RL Libraries](https://huggingface.co/blog/async-rl-training-landscape)，访问于 2026-08。

## 1.2 🌐 开源框架总表

> ⚠️ **这张表会过时。** 开源 RL 框架的迭代速度远快于训练框架，star 数只用于表达量级（数量级对了就行，别当精确数字）。以官方仓库现状为准。
> star 数与能力描述来源同上（HF 横评，访问于 2026-08）+ 各仓库 README。

| 框架 | 出品方 | 编排原语 | 训练后端 | 推理后端 | 异步档位 | 量级 |
|---|---|---|---|---|---|---|
| **veRL** | 字节跳动 | Ray | Megatron / FSDP / TorchTitan / VeOmni / MindSpeed | vLLM / SGLang / TRT-LLM | 同步 → 一步离策略 → 全异步（**三档都有**） | ~2 万 star |
| **slime** | 智谱 THUDM | Ray | **只有** Megatron | **只有** SGLang | 同步 + 全异步 | ~5 千 star |
| **OpenRLHF** | 社区 | Ray | DeepSpeed | vLLM | 同步 + 异步 | — |
| **verifiers-rl** | — | 原生 Python | — | — | — | ~4 千 star |
| **AReaL** | inclusionAI | 原生 Python | — | — | **全异步**为主打 | ~4 千 star |
| **open-instruct** | AI2 | Ray | — | vLLM | 一步离策略 | ~4 千 star |
| **ROLL** | 阿里 | Ray | Megatron / DeepSpeed | vLLM / SGLang | 同步 + 异步 | ~3 千 star |
| **Tunix** | Google | — | JAX / TPU | — | — | ~2 千 star |
| **SkyRL** | NovaSky（伯克利） | Ray | FSDP / Megatron | vLLM / SGLang | 一步离策略 | ~2 千 star |
| **NeMo-RL** | NVIDIA | Ray | Megatron / DTensor | vLLM | 同步 + 异步 | ~1 千 star |
| **PRIME-RL** | Prime Intellect | 原生 Python | **FSDP2 + EP** | vLLM | 异步 | ~1 千 star |
| **MILES** | radixark | Ray | — | — | — | ~1 千 star |
| **ART** | CoreWeave | 原生 Python | — | vLLM | — | ~9 千 star |
| **Atropos** | Nous Research | **HTTP 微服务** | 不含（只做环境侧） | — | — | ~900 star |
| **OAT** | SAIL-SG | Ray | — | vLLM | — | ~600 star |
| **TorchForge** | Meta | **Monarch**（非 Ray） | PyTorch 原生 | vLLM | 异步 | ~600 star |
| **PipelineRL** | ServiceNow | **pub/sub** | — | vLLM | **权重同步不打断生成** | ~400 star |
| **TRL** | HuggingFace | 无（单进程为主） | Accelerate / DeepSpeed | vLLM（可选） | 同步 | 生态最广 |

### 从这张表能直接读出三件事

**① 🌐 Ray 占了绝对多数。**
18 家里有 8 家明确用 [Ray](https://github.com/ray-project/ray)（一个 Python 分布式计算框架）做编排：veRL、SkyRL、NeMo-RL、slime、MILES、ROLL、OAT、open-instruct。

⚠️ 我的理解：这不是巧合。RL 训练需要的恰好是 Ray 最擅长的东西——**异构角色**（训练进程和推理进程完全不同）、**动态生命周期**（推理引擎要能睡眠、唤醒、重启）、**跨进程对象传递**（样本要从生成侧流到训练侧）。用 `torchrun` 那套「所有进程跑同一份代码」的模型，表达不了这种拓扑。

剩下的几家是有意识地不用 Ray：TorchForge 用 Meta 自己的 Monarch，Atropos 干脆把环境做成 HTTP 微服务，PipelineRL 用发布/订阅，AReaL 和 PRIME-RL 直接写原生 Python。

**② 🌐 「多后端」是少数派，而且是奢侈品。**
只有 veRL、ROLL、NeMo-RL、SkyRL 支持多个训练后端。veRL 一家就接了 6 个训练引擎和 4 个推理引擎（✅ 见 [训练框架对比.md §7.5–7.6](../训练框架/训练框架对比.md)）。

而 slime 明确走了反方向：**只支持 Megatron 一个训练后端、SGLang 一个推理后端**。
🌐 slime README 给的理由是拒绝「为了兼容多后端而把抽象降到最小公分母」——多后端抽象层意味着任何一家的新特性都要等抽象层跟上。
详见 [slime拆解.md](slime拆解.md)。

**③ ⚠️ 代码量差了一个数量级，但不代表能力差一个数量级。**

| 框架 | 行数（✅ 本地实测） | commit |
|---|---|---|
| veRL | **171,584** 行 / 649 文件 | `b256ebf` |
| slime | **72,468** 行 / 332 个 `.py` | `3778dbf`（v0.3.2） |
| OpenRLHF | **13,411** 行 / 65 个 `.py` | `3c3be62`（v0.11.0） |

veRL 是 OpenRLHF 的 **12.8 倍**。但这 12.8 倍里，绝大部分不是「RL 算法更强」，而是**后端适配**——6 个训练引擎 × 4 个推理引擎 × 6 个 checkpoint 后端的排列组合。

OpenRLHF 只认 DeepSpeed + vLLM 一条路，所以 13,411 行就够了。**如果你的目的是读懂 RL 框架的骨架，OpenRLHF 是最好的入口**，见 [OpenRLHF拆解.md](OpenRLHF拆解.md)。

## 1.3 ✅ 五套自研系统

开源榜单之外，五份前沿模型技术报告各自披露了一套自研的 RL 基建。这是本仓库的独特材料——**这五家从来没有被横向对齐过**。

| 模型 | 系统名 | 是否开源 | 一句话定位 | ✅ 报告出处 |
|---|---|---|---|---|
| **GLM-5** | **slime** | ✅ 开源 | 全异步、训推分离，「统一的后训练基础设施」 | §3.6 The slime Framework · §4.1.1 |
| **MiniMax-M2** | **Forge** | ❌ 未开源 | Agent 侧 / 中间件 / 训推侧三层解耦，为 agentic RL 设计 | §6.2 |
| **Kimi-K3** | 未命名 | ❌ | **同置（co-located）** + partial rollout + 外部 KV 池 | §5.3 Infra for 1M Agentic RL |
| **DeepSeek-V4** | 未命名 | ❌ | Keep Routing / Keep Sampling Mask，主攻训推一致性 | 见 [04](04-训推一致性.md) |
| **openPangu-2.0-Pro** | 未命名 | ❌ | 唯一给出训推失配**诊断框架**的（三分类） | §10 |

### ★★ 最值得注意的一点：GLM-5 和 Kimi-K3 给出了相反的答案

同一个问题——「训练和推理该不该放在同一批 GPU 上」——两家顶级团队给出了**完全相反**的选择：

> ✅ **GLM-5**：*"we implement a new asynchronous reinforcement learning infrastructure that drastically improves post-training efficiency by **decoupling generation from training**"*
> ——彻底分离。

> ✅ **Kimi-K3**：*"We adopt **co-located** RL training to keep each 1M-context Kimi K3 RL experiment within a few hundred GPUs, and use partial rollouts to reduce tail latency from ultra-long trajectories."*
> ——反而同置。

⚠️ 我的解读：**这不是谁对谁错，是约束不同。** Kimi 那句话自己写出了约束——*"within a few hundred GPUs"*（把每次实验控制在几百张卡内）。分离部署要求训练侧和推理侧各自独占一批卡，卡少的时候这笔账划不来。而 GLM-5 是 744B 参数、28.5T token 的规模，分离带来的重叠收益足以覆盖额外的卡。

这条线是 [02-架构主轴](02-架构主轴-同步到全异步.md) 的主题，那一篇会把 MiniMax 的第三条路（Windowed FIFO，在两个极端之间插值）也放进来。

## 1.4 ⚠️ 开源与自研在同一坐标系里的位置

把上面两张表叠起来看，能看到一个位置差：

```
    分布式程度
        ▲
  全异步 │   AReaL     PipelineRL          ★ GLM-5 / slime
        │   TorchForge  PRIME-RL
        │
一步离策略│   SkyRL   open-instruct    veRL(experimental)
        │                              ★ MiniMax Forge (Windowed FIFO)
        │
    同步 │   TRL      OpenRLHF(默认)   veRL(默认)   ★ Kimi-K3(co-located)
        │
        └────────────────────────────────────────────────► 工程复杂度
           单机可跑         需要 Ray 集群        需要专门的基建团队
```

⚠️ 三点归纳：

1. **开源框架把「异步档位」做成了可选项，自研系统把它做成了架构前提。**
   veRL 在 `experimental/` 下同时放了同步、一步离策略、全异步三套实现（✅ 实测：`one_step_off_policy/` 553 行、`fully_async_policy/` 4,335 行、`separation/` 1,040 行）——它在**同时探索**。而 GLM-5 直接把全异步写进了架构定义。

2. **自研系统普遍比开源框架更「窄」，但更深。**
   Forge 只服务 MiniMax 自己的 agentic 场景，但为此做了 prefix tree merging、全局 L3 KV 池这些开源框架里没有的东西。反过来，开源框架为了通用性必须留抽象层，深度优化就难做。

3. **slime 是唯一一个「既是自研又是开源」的样本。**
   它既在 GLM-5 报告里被当作生产基建描述（✅ *"the unified post-training infrastructure for GLM-5"*），又是一个能 clone 下来读的开源仓库。这让它成为本目录唯一可以**报告与源码互相印证**的对象——[slime拆解.md](slime拆解.md) 就是干这个的。
