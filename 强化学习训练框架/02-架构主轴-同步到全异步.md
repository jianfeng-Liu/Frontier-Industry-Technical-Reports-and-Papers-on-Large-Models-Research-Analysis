# 02 · 架构主轴：从同步到全异步

> **这一篇干什么**：讲清楚 RL 训练框架**唯一的核心矛盾**，以及业界在这条轴上的四个位置。

> **前置**：[01-格局全景.md](01-格局全景.md)、[14 章 §14.3](../训练框架/分布式训练入门/14-RL训练框架.md)

## 2.1 先看清楚问题有多严重

RL 的一步训练长这样：

```
生成 512 个答案  ────►  算奖励  ────►  算梯度更新参数  ────►  权重同步回去
     ~80% 时间          ~5%            ~10%                  ~5%
```

大部分人对「生成占 80%」是有概念的。但真正致命的不是**平均**耗时，是**长尾**。

### 🌐 一组能把问题量化的数字

单张 H100 上用 vLLM 做离线推理（bf16 精度）的吞吐大致是：

| 模型规模 | 输出吞吐 |
|---|---|
| 7B | ~6,300 token/s |
| 32B | ~1,200 token/s |

拿这个算一步 RL 要多久。设定：64 道题 × 每题生成 8 个答案（G=8）= **512 个 rollout**：

| 每个答案的输出长度 | 7B 单卡耗时 | 32B 单卡耗时 |
|---|---|---|
| 2K token | ~3 分钟 | ~14 分钟 |
| 8K token | ~11 分钟 | ~56 分钟 |
| **32K token** | **~45 分钟** | **~3.7 小时** |

就算把生成摊到 8 张推理卡上并行，32B 模型生成 32K 长度的一步仍要 **~28 分钟**。

> 来源：[Keep the Tokens Flowing: Lessons from 16 Open-Source RL Libraries](https://huggingface.co/blog/async-rl-training-landscape)，访问于 2026-08。

⚠️ 这组数字要读出的**不是**「生成很慢」，而是：**在同步架构下，训练 GPU 在这 28 分钟里完全空转。** 而且 512 个答案不是同时结束的——有的 500 token 就写完了，有的写满 32K 才停。同步架构必须**等最慢的那一个**。这就是长尾。

✅ GLM-5 报告把这件事说得很直接：

> *"the optimization target is not aggregate throughput but **end-to-end latency, dominated by the slowest (long-tail) sample in each step**"*
> （优化目标不是总吞吐，而是端到端延迟——它由每一步里最慢的那个样本决定。）
> —— GLM-5 §3.6.2 Scaling Up: Tail-Latency Optimization

## 2.2 唯一的解法方向：让训练不等生成

所有架构分歧，都是这一句话的不同实现。而实现的关键，就落在**五模块里的第 ③ 块：data buffer 有多深**。

### 🌐 Buffer 深度四档

```
深度 0（同步）
  生成一批 ──► 训完 ──► 生成下一批 ──► ...
  训练卡在生成时空转，生成卡在训练时空转
  样本 100% on-policy（在策略）

深度 1（一步离策略 / one-step-off-policy）
  生成第 N+1 批  ┐
                 ├─ 同时进行
  训练第 N 批    ┘
  样本落后 1 个版本。这是"最便宜的异步"——只多一个缓冲区

深度 2~K（有界队列）
  生成 ────► [ 队列，最多 K 批 ] ────► 训练
  队列满了才阻塞生成。K 越大越不容易卡，但样本越陈旧

深度 ∞（无界流 / fully async）
  生成永不停 ────► [ 流 ] ────► 训练按自己的节奏取
  吞吐最高，陈旧度完全靠算法侧修正兜底
```

| 深度 | 名称 | 训练卡空转 | 样本陈旧度 | 谁在用 |
|---|---|---|---|---|
| 0 | 同步 | **严重** | 0（完全 on-policy） | TRL、OpenRLHF 默认、veRL 默认 |
| 1 | 一步离策略 | 小 | 落后 1 版 | SkyRL、open-instruct、veRL `one_step_off_policy/` |
| 2~K | 有界队列 | 很小 | 落后 ≤K 版 | ROLL、NeMo-RL、MiniMax Forge |
| ∞ | 全异步 | 几乎没有 | 不确定 | AReaL、PipelineRL、TorchForge、**GLM-5 / slime** |

⚠️ 这张表最重要的是**第 3 列和第 4 列此消彼长**。你没法两头都要：训练卡不空转，就意味着它在用旧样本训练。这是 RL 系统设计的**根本权衡**，后面所有东西都是在这条曲线上找位置。

## 2.3 ✅ veRL 的 `experimental/` 就是这条谱系的源码实证

最有意思的证据是：veRL 把这条轴上的**几乎每一档都实现了一遍**，全部放在 `experimental/` 目录下。

✅ 本地实测（commit `b256ebf`）：

| 目录 | 文件数 | 行数 | 对应档位 |
|---|---|---|---|
| `verl/experimental/one_step_off_policy/` | 3 | **553** | 深度 1 |
| `verl/experimental/separation/` | 4 | **1,040** | 训推分离的基础设施 |
| `verl/experimental/fully_async_policy/` | 14 | **4,335** | 深度 ∞ |
| `verl/experimental/agent_loop/` | 6 | **2,831** | agentic rollout（见 [06](06-AgenticRL-环境与沙箱.md)） |
| `verl/experimental/reward_loop/` | 14 | 1,961 | 奖励计算异步化 |
| `verl/experimental/teacher_loop/` | 3 | 373 | 在策略蒸馏（见 [05](05-算法与框架的接口.md)） |

✅ `fully_async_policy/` 里的文件名把架构直接写在脸上：

```
fully_async_main.py        主入口
fully_async_rollouter.py   生成侧，独立进程
fully_async_trainer.py     训练侧，独立进程
message_queue.py           ★ 两者之间的队列——就是「深度 ∞」的那个流
detach_utils.py            解耦工具
dynamic_schedule/          动态调度
config/  shell/  unittest/
```

而 `one_step_off_policy/` 只有 3 个文件、553 行：`main_ppo.py` + `ray_trainer.py` + `__init__.py`。

⚠️ 我的解读：**553 行 vs 4,335 行，差 7.8 倍，这个比例本身就是结论。**
从同步走到「一步离策略」，你只需要多开一个缓冲区、把两个阶段并行起来——改动很小，收益却拿走了大半。而从「一步离策略」走到「全异步」，你要额外处理：独立的生成进程生命周期、消息队列、动态调度、陈旧度追踪、失败恢复……复杂度陡增。

**这是选型上最实用的一条经验：如果你不是在做超长上下文或 agentic 任务，一步离策略往往是性价比最高的位置。** 见 [07-选型与实践.md](07-选型与实践.md)。

## 2.4 ★★ 三家前沿模型，三个不同的位置

这一节是全篇的核心。三份技术报告，在同一条轴上选了三个不同的点。

### ① GLM-5：走到最右边，彻底分离

✅ 原文（§4.1.1 Asynchronous RL Design）：

> *"we **decouple the training engine and the inference engine onto different GPU devices**. The inference engine **continuously generates** trajectories. Once the number of generated trajectories reaches a predefined threshold, the batch is sent to the training engine to update the model... The training engine updates the model parameters and **pushes the new weights back to the inference engine every K gradient updates**."*

拆开看这段话，四个设计决策：

| 原文短语 | 意思 | 对应的架构选择 |
|---|---|---|
| decouple ... onto different GPU devices | 训练和推理用不同的卡 | **disaggregated（分离部署）** |
| continuously generates | 生成永不停 | **buffer 深度 = ∞** |
| reaches a predefined threshold | 攒够阈值才发一批 | 用「攒批」而不是「等对齐」来切分训练步 |
| every K gradient updates | 每 K 步才推一次权重 | 权重同步频率是**可调参数**，不是每步必做 |

✅ 还有一句容易被漏掉但很关键的：

> *"we also **reset the optimizer** after each weight update of the inference engine."*

⚠️ 我的理解：优化器状态（Adam 的一阶、二阶动量）是「对过去梯度的记忆」。异步 RL 里数据分布一直在漂，旧动量可能反而是噪声。每次推权重就重置一次优化器，等于**主动放弃跨版本的动量累积**，换取每一段训练内部的稳定性。这是个反直觉但很实在的工程选择——正常训练里没人会这么干。

✅ 配套的还有一个 **Multi-Task Rollout Orchestrator**（多任务 rollout 编排器）：每个任务是一个独立的微服务，向中央编排器注册；编排器控制每个任务的 rollout 配比和生成速度；所有任务用统一的 message list 表示；**支持超过 1000 路并发 rollout**。

### ② Kimi-K3：留在最左边，同置

✅ 原文（§5.3 Infra for 1M Agentic RL）：

> *"We adopt **co-located RL training** to keep each 1M-context Kimi K3 RL experiment **within a few hundred GPUs**, and use **partial rollouts** to reduce tail latency from ultra-long trajectories."*

⚠️ 注意这句话的因果方向：**同置是结论，不是前提。** 前提是「每次实验要控制在几百张卡内」。K3 是 1M（一百万 token）上下文，分离部署要给训练侧和推理侧各留一整套卡，几百张的预算下这笔账划不来。

那长尾怎么办？Kimi 不靠分离，靠另外三招：

| 手段 | ✅ 原文 | 解决什么 |
|---|---|---|
| **partial rollout**（部分 rollout） | *"use partial rollouts to reduce tail latency from ultra-long trajectories"* | 超长样本不必一次生成完，下一轮接着生成 |
| **外部 KV cache 池** | *"external KV-cache retention"*，write-back 设计：正在解码的块留在 GPU 显存，可复用但闲置的前缀在被驱逐时才写回 CPU 内存，下次复用前预取 | partial rollout 的前缀不用重算 |
| **可恢复 microVM 沙箱** | *"resumable microVM sandboxes to preserve long-lived model and environment state"* | agent 任务中断后环境状态还在（见 [06](06-AgenticRL-环境与沙箱.md)） |

⚠️ 这三招合起来，本质是**把「异步」从系统层挪到了样本层**：系统仍然是同步的，但单个样本可以跨步继续。这是一条被低估的路径。

### ③ MiniMax Forge：在中间插值

✅ Forge（§6.2）的架构是三层解耦：

```
┌─────────────────────────────────────────────┐
│  Agent Side（agent 侧）                     │
│  纯粹的轨迹生产者，对训练/推理完全无感知    │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│  Middleware Abstraction Layer（中间件层）   │
│  · Gateway Server：路由所有补全请求         │
│  · Data Pool：分布式轨迹存储，异步收集      │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│  Training / Inference Side（训推侧）        │
│  · Rollout Engine 扮演 π_θ                  │
│  · Train Engine 算 CISPO 梯度，同步权重回去 │
└─────────────────────────────────────────────┘
```

真正有意思的是它的调度策略——**Windowed FIFO（窗口化先进先出）**：

✅ 队列 `Q = [T_0, T_1, ..., T_{N-1}]`，维护一个头指针 `i`，窗口是 `[T_i, T_{i+W-1}]`。**窗口内**谁先完成用谁（贪心，不等顺序），**跨窗口边界**必须严格按序。实践取 **`W = 0.3N`**。

⚠️ 这就是在两个极端之间**显式插值**：

```
W = 1  ──────────────────► 严格 FIFO：完全按顺序，长尾全暴露
                              ↑
                        W = 0.3N（Forge 实际取值）
                              ↓
W = N  ──────────────────► 完全贪心：谁快用谁，但陈旧度不可控
```

W 越大，吞吐越高、陈旧度越不可控；W 越小，越接近同步。**把一个架构选择变成了一个可调旋钮**，这是三家里最工程化的做法。

✅ 另外两个 Forge 的加速手段值得单独记：

- **Prefix Tree Merging（前缀树合并）**：同一道题的 G 个答案共享同一段前缀，前缀只算一次然后分叉。报告称「**数学上等价于独立样本训练**」「**零近似误差**」，带来 **最高 40× 的训练加速**。
- **全局 L3 KV Cache 池**：由分布式文件系统托底，配一个成本感知的请求路由器。

### 三家放在一起

| | GLM-5 | Kimi-K3 | MiniMax Forge |
|---|---|---|---|
| 训推放置 | **分离** | **同置** | 分离（三层解耦） |
| buffer 深度 | ∞（连续生成） | 0（但样本可跨步） | 有界，窗口 `W=0.3N` |
| 长尾怎么解 | 靠异步吸收 + PD 分离 + FP8 | **partial rollout + 外部 KV 池** | **窗口内贪心 + 前缀树合并** |
| 明说的约束 | 744B / 28.5T token 规模 | *"within a few hundred GPUs"* | 10 万+ agent 脚手架 |

⚠️ **我的综合判断：这三个点在同一条「吞吐 ↔ 分布一致性」的权衡曲线上，谁也没有推翻谁。**

```
分布一致性（样本越新越好）
   ▲
   │  ★ Kimi-K3（同置）
   │      同置 → 样本永远是最新权重生成的
   │      代价：训练卡要等生成
   │
   │           ★ MiniMax（W=0.3N）
   │               显式旋钮，可调
   │
   │                        ★ GLM-5（全异步）
   │                            吞吐拉满，一致性交给算法侧兜底
   └────────────────────────────────────────► 吞吐
```

选哪个点，取决于三个约束：**卡够不够**（Kimi 明说不够）、**上下文多长**（越长长尾越致命）、**有没有算法侧的一致性兜底手段**（见 [04](04-训推一致性.md)）。

## 2.5 陈旧度怎么管：三种正交的手段

一旦离开深度 0，样本就带上了「版本落后」这个属性。🌐 业界的处理手段有三种，而且它们是**正交的**——可以同时用：

| 手段 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **① 逐样本版本拒绝** | 每个样本带一个版本号，太旧的直接丢 | 精确，粒度到单个样本 | 丢掉的是已经花掉的算力 |
| **② 深度限制** | 队列最多 K 层，满了就阻塞生成 | 简单，硬保证上界 | 阻塞生成 = 部分退回同步 |
| **③ IS 加权修正** | 不丢样本，在 loss 里乘一个重要性采样比值来纠偏 | 不浪费算力 | 比值方差大时反而更不稳（见 [04](04-训推一致性.md)） |

🌐 HF 横评的结论是：**生产环境的趋势是三种混用**，而不是只靠一种。

⚠️ 这里有个容易踩的坑，值得单独拎出来：

> **非对称过滤会让「存活的正样本」系统性地更陈旧。**

很多 RL 训练会做动态过滤——把全对或全错的组丢掉（因为组内没有区分度，梯度是零）。但难题的 rollout 通常**更长**，所以完成得更晚。结果是：难题的样本天然更旧，而难题恰恰是训练最需要的那部分。

**batch 级的陈旧度门控看不见这个偏差**——整批的平均陈旧度可能很正常，但真正贡献梯度的那些样本全都是最旧的。🌐 HF 横评据此认为**逐样本打版本号是必需的**，不能只在 batch 级别管。
