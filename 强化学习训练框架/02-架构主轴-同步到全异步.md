# 02 · 架构主轴：从同步到全异步

> **这一篇干什么**：讲清楚 RL 训练框架**唯一的核心矛盾**，以及业界在这条轴上的四个位置。
> **难度** ★★★ · **这是全目录最重要的一篇**
> **前置**：[01-格局全景.md](01-格局全景.md)、[14 章 §14.3](../训练框架/分布式训练入门/14-RL训练框架.md)
> **读法**：本章 §2.1 和 §2.2 的每个数字都能自己验算，而且**后面所有章节都复用这两节的那批数字**。⚠️ 强烈建议拿纸笔跟着算一遍——「气泡」这个词只有变成 GPU·秒之后才有意义。
> **分工**：RL 的算法与数据在 [../后训练/](../后训练/README.md)，推理引擎本身在 [../推理框架/](../推理框架/README.md)。本章只讲系统编排。

---

**本章关键词**

**气泡**（bubble）—— GPU 占着没干活的那段时间。本章把它统一换算成 **GPU·秒**（卡数 × 秒数）来结账，否则「利用率低」是一句说不清的话。
**长尾**（long tail）—— 一批样本里极少数特别长的那几条，它们决定整批什么时候结束。
**buffer 深度**—— 生成好的样本在队列里最多能攒几批。**这个整数就是「有多异步」的全部定义**。
**陈旧度**（staleness）—— 一个样本生成时用的权重，落后当前权重几个训练步。
**on-policy / off-policy**（在策略 / 离策略）—— 样本是不是当前这版权重生成的。
**IS**（Importance Sampling，重要性采样）—— 承认样本来自旧策略，在 loss 里乘一个比值把偏差纠回来。展开在 [04 章 §4.6](04-训推一致性.md)。
**partial rollout**（部分 rollout）—— 长样本不必一次写完，到预算就存盘，下一轮接着写。
**PD 分离**（Prefill-Decode Disaggregation，预填充-解码分离）—— 推理的两个阶段拆到不同机器上，见 [../推理框架/推理优化入门/10-PD分离.md](../推理框架/推理优化入门/10-PD分离.md)。

## 2.1 先看清楚问题有多严重

RL 的一步训练，拆成四个阶段：

| 阶段 | 做什么 | 🌐 常见的占比说法 | ⚠️ 本章 §2.2 实际算出来的 |
|---|---|---|---|
| ① rollout | 生成 512 个答案 | ~80% | **82.9%** |
| ② 奖励 | 判对错、算优势 | ~5% | 5.3% |
| ③ 训练 | 前向 + 反向 + 优化器 | ~10% | 10.5% |
| ④ 权重同步 | 新权重搬回生成引擎 | ~5% | 1.3% |

大部分人对「生成占 80%」是有概念的。但真正致命的不是**平均**耗时，是**长尾**。下面把长尾算成数字。

### 🌐 一组能把问题量化的数字

单张 H100 上用 vLLM 做离线推理（BF16 精度）的**聚合输出吞吐**大致是：

| 模型规模 | 聚合输出吞吐 |
|---|---|
| 7B | ~6,300 token/s |
| 32B | ~1,200 token/s |

> 来源：[Keep the Tokens Flowing: Lessons from 16 Open-Source RL Libraries](https://huggingface.co/blog/async-rl-training-landscape)，访问于 2026-08。**只有这两个吞吐数字是 🌐 来源的，下面所有分钟数都是 ⚠️ 本文按它们算出来的**，不是博客直接给的。

拿这个算一步 RL 要多久。设定：**64 道题 × 每题生成 8 个答案（G=8）= 512 个 rollout**。算式一律是 `总 token ÷ 聚合吞吐`：

| 每个答案的长度 | 总输出 token = 512 × 长度 | 7B 单卡：÷ 6,300 | 32B 单卡：÷ 1,200 |
|---|---|---|---|
| 2K = 2,048 | 1,048,576 | 166 s = **2.8 分钟** | 874 s = **14.6 分钟** |
| 8K = 8,192 | 4,194,304 | 666 s = **11.1 分钟** | 3,495 s = **58.3 分钟** |
| **32K = 32,768** | **16,777,216** | 2,663 s = **44.4 分钟** | 13,981 s = **3.9 小时** |

就算把生成摊到 **8 张**推理卡上并行，32B 模型生成 32K 长度的一步仍要 `13,981 ÷ 8 = 1,748 s` ≈ **29 分钟**。

⚠️ 这组数字要读出的**不是**「生成很慢」，而是：**在同步架构下，训练 GPU 在这 29 分钟里完全空转。**

### ★ 长尾的账：为什么「平均」是个骗人的口径

上面那张表假设 512 条答案**一样长**。真实情况不是——有的 500 个 token 就写完了，有的写满 32K 才停。同步架构必须**等最慢的那一个**。这一段把这笔账算出来，它是 partial rollout 存在的**全部**理由。

**第一步：单条序列到底能跑多快。**

聚合吞吐（1,200 token/s）是靠**很多条序列同时跑**堆出来的，单条序列没这么快。单条的速度由屋顶线决定——decode 阶段每吐一个 token，都必须把**整个模型的权重**从显存读一遍：

| 量 | 数值 | 算式 |
|---|---|---|
| 32B 模型的 BF16 权重 | 64 GB | 32 × 10⁹ 参数 × 2 字节 |
| H100 SXM5 的 HBM3 带宽 | 3.35 TB/s | 规格值 |
| 读完一遍权重的时间 | **19.1 ms** | 64 GB ÷ 3,350 GB/s |
| ⟹ 单条序列的解码速度上限 | **52 token/s** | 1 ÷ 0.0191 s |

> ⚠️ 52 token/s 是**屋顶线上限**，实测通常只有它的 60–70%。下面一律按 52 算，**结论只会比算出来的更糟，不会更好**。屋顶线怎么用见 [../大模型算子开发/02-屋顶线与性能剖析.md](../大模型算子开发/02-屋顶线与性能剖析.md)，decode 为什么卡在带宽上见 [../推理框架/推理优化入门/03-Prefill与Decode两阶段.md](../推理框架/推理优化入门/03-Prefill与Decode两阶段.md)。

★ 顺便得到一个有用的换算：**聚合 1,200 ÷ 单条 52 ≈ 23**，也就是这张卡上大约能同时跑 23 条序列。记住这个 23，下面要用。

**第二步：给 512 条样本一个长度分布。**

⚠️ 下面这个分布是**示意分布，不是实测**，形状取自「推理类任务上极少数样本特别长」这个公认经验。关键不是具体分位，是**比例关系**：

| 分位段 | 条数 | 输出长度 | 单条耗时 = 长度 ÷ 52 | 该段总 token |
|---|---|---|---|---|
| p0–p50 | 256 | 2,048 | **39.4 s** | 524,288 |
| p50–p90 | 205 | 8,192 | 158 s | 1,679,360 |
| p90–p99 | 46 | 16,384 | 315 s | 753,664 |
| p99–p100 | **5** | **32,768** | **630 s** | 163,840 |
| 合计 | 512 | — | — | **3,121,152** |

**最慢的那条 ÷ 中位数 = 630 s ÷ 39.4 s = 16 倍。** ⚠️ 这正好等于长度比 `32,768 ÷ 2,048 = 16`，**不是巧合**：单条序列的解码速度几乎与 batch 里有多少条无关（它被权重读取带宽卡住，而这一遍权重是全 batch 共享的），所以**耗时比 = 长度比**，一比一。

**第三步：两笔账一起算。**

| | 算式 | 结果 |
|---|---|---|
| **理想**：完美打包，按聚合吞吐算 | 3,121,152 token ÷ 1,200 token/s | **2,601 GPU·秒**（单卡口径） |
| 摊到 8 张推理卡 | 2,601 ÷ 8 | 325 s = 5.4 分钟 |
| **实际**：同步架构，必须等最慢那条 | 那 5 条 32K 样本各自要 630 s | **墙钟 ≥ 630 s = 10.5 分钟** |

为什么 8 张卡救不了最后那 630 秒？因为**一条序列没法拆给两张卡去写**——第 n 个 token 必须等第 n−1 个 token 出来。加卡能提高并发度，提不高单条的速度。

⟹ **推理侧利用率 = 2,601 ÷ (8 × 630) = 2,601 ÷ 5,040 = 51.6%。** 近一半的推理机时被长尾吃掉了。而训练侧那 8 张卡，在整整 630 秒里利用率是 **0%**。

**第四步：长尾还有第二笔隐性账——它占着 KV cache 的槽位。**

到 t = 315 秒之后，队列里只剩 5 条活着的序列，而这张卡本来能同时跑 23 条（第一步算的）。**并发度掉到 5 ÷ 23 ≈ 22%**，聚合吞吐随之掉到 `5 × 52 = 260 token/s`——只剩峰值的 21.7%。上面那个 51.6% 的物理来源就是这个。KV cache 怎么占显存见 [../推理框架/推理优化入门/02-KV-Cache与显存账.md](../推理框架/推理优化入门/02-KV-Cache与显存账.md)。

**第五步：partial rollout 能救回多少。**

把那 5 条超长样本在 t = 325 秒处**切断、存进 buffer、下一轮接着写**，这一轮的工作量变成：

```
  2,957,312 token   <-- 其余 507 条本来就要写完的
+    84,500 token   <-- 5 条超长样本只写了 325 s x 52 token/s 那一段
= 3,041,812 token
/ 1,200 token/s / 8 张卡 = 317 s
```

| | 墙钟 | 推理侧利用率 |
|---|---|---|
| 不做 partial rollout | 630 s | 51.6% |
| 做 partial rollout | **317 s** | ~100% |

> ⚠️ 317 s 比「完美打包」的 325 s 还小一点，不是算错了：partial rollout **把那 5 条样本剩下的一半 token 推迟到了下一轮**，这一轮的工作量本来就少了。它不是凭空变快，是**把工作摊平**——这正是它和「加卡」的本质区别。

⚠️ **这里有个最高频的算术陷阱，必须拎出来说**：时间从 630 s 降到 317 s，是「**时间减少 49.7%**」，**不是「加速 49.7%」**。

```
时间减少比例 = (630 - 317) / 630 = 49.7%
加速倍数     = 630 / 317 = 1.99 倍
验算         = 1 / (1 - 0.497) = 1.99   <-- 公式：加速倍数 = 1 / (1 - 减少比例)
```

**「减少一半时间」等于「快两倍」，不等于「快 50%」。** 本仓库在这一条上出过错，看到百分数先问是哪个口径。

✅ GLM-5 报告把长尾这件事说得很直接：

> *"the optimization target is not aggregate throughput but **end-to-end latency, dominated by the slowest (long-tail) sample in each step**"*
> （优化目标不是总吞吐，而是端到端延迟——它由每一步里最慢的那个样本决定。）
> —— GLM-5 §3.6.2 Scaling Up: Tail-Latency Optimization

⚠️ 把上面那笔账和这句话对上：**2,601 GPU·秒是「aggregate throughput」的口径，630 秒是「end-to-end latency」的口径。两者差 1.94 倍，而这 1.94 倍全部来自 512 条里的 5 条。**

## 2.2 唯一的解法方向：让训练不等生成

所有架构分歧，都是这一句话的不同实现。先把「不这么做会怎样」结成一笔完整的账。

### ★ 同步架构一个迭代的完整时间账

设定（沿用 §2.1 那批 512 条样本、32B 模型）：**16 张 H100，8 张做 rollout、8 张做训练，分离部署，同步架构**。

| 阶段 | 做什么 | 墙钟 | 8 张推理卡在干什么 | 8 张训练卡在干什么 |
|---|---|---|---|---|
| ① rollout | 生成 512 条答案 | **630 s** | 在算，但只有 51.6% 有效（§2.1） | **全空** |
| ② 奖励 | 跑测试用例 / 判对错 / 算优势 | 40 s | 空（这活在 CPU 和沙箱上） | 空 |
| ③ 训练 | 前向 + 反向 + 优化器 | 80 s | **全空** | 满负荷 |
| ④ 权重同步 | 64 GB 权重重切分 + 搬回推理侧 | 10 s | 等着收 | 发完就等 |
| **合计** | | **760 s** | — | — |

> ⚠️ ③ 的 80 秒和 ④ 的 10 秒是**量级设定**，不是实测。④ 为什么是 10 秒而不是 1 秒，见 [03 章 §3.2](03-权重同步.md)——纯传输只要 1.3 秒，剩下的全是 resharding（重切分）和引擎唤醒。

把墙钟换算成 **GPU·秒**（卡数 × 秒数）来结账，这才是真正该看的口径：

| | 有效计算 GPU·秒 | 占用 GPU·秒 | 利用率 |
|---|---|---|---|
| 8 张推理卡 | 2,601（§2.1 算的打包工作量） | 8 × 760 = 6,080 | **42.8%** |
| 8 张训练卡 | 8 × 80 = 640 | 8 × 760 = 6,080 | **10.5%** |
| **全机 16 张** | **3,241** | **12,160** | **26.7%** |

⚠️ **把这三个数字记住：推理卡 42.8%、训练卡 10.5%、全机 26.7%。** 这就是「同步 RL」的真实成本。③ 的 80 秒里训练卡确实在满负荷跑，但它为了这 80 秒，要陪着等 680 秒（630 + 40 + 10）。

把浪费掉的 73.3% 拆开，看清楚每一块该用什么手段打：

| 气泡来源 | GPU·秒 | 占总机时 | 消灭它的手段 |
|---|---|---|---|
| **训练卡等生成**（①②④ 三段，8 × 680） | 5,440 | **44.7%** | **异步**：让训练卡去训上一批（本节「深度 1 及以上」） |
| **推理卡等训练**（②③④ 三段，8 × 130） | 1,040 | 8.6% | **异步**：让推理卡接着生成下一批 |
| **推理卡内部的长尾空转**（① 之内，5,040 − 2,601） | 2,439 | 20.1% | **partial rollout**（§2.4 Kimi）或**窗口化调度**（§2.4 MiniMax） |
| 真正在算 | 3,241 | 26.7% | — |
| 合计 | 12,160 | 100% | — |

⚠️ **这张表是全章最该记住的一张。** 它说明两件事：

1. **最大的一块气泡（44.7%）靠「异步」打，第三大的一块（20.1%）靠「partial rollout」打。这两个手段打的不是同一块，所以它们可以同时用**——这一点在 [03 章 §3.5.1](03-权重同步.md) 还会从另一个角度再说一遍。
2. **第二块（8.6%）是最小的一块，但它恰恰是「一步离策略」唯一能打到的那块。** 下面会看到这导致了一个很反直觉的结论。

### 🌐 Buffer 深度四档

所有异步方案的分类，都落在**五模块里的第 ③ 块：data buffer 有多深**。

```
深度 0（同步）
  生成一批 --> 训完 --> 生成下一批 --> ...
  训练卡在生成时空转，生成卡在训练时空转；样本 100% on-policy

深度 1（一步离策略 / one-step-off-policy）
  生成第 N+1 批  --+
                   +-- 同时进行
  训练第 N 批    --+
  样本恰好落后 1 个版本。这是「最便宜的异步」——只多一个缓冲区

深度 2~K（有界队列）
  生成 --> [ 队列，最多攒 K 批 ] --> 训练
  队列满了才阻塞生成。K 越大越不容易卡，但样本越陈旧

深度无穷（无界流 / fully async）
  生成永不停 --> [ 流 ] --> 训练按自己的节奏取
  吞吐最高，陈旧度完全靠算法侧修正兜底
```

### ★★ 三档放进同一笔账：加速倍数算出来

现在把 §2.1 和上面那笔账里的数字，逐档重算一遍。**算式全部列出来，可以自己验。**

**深度 1（单步异步）**：第 N+1 批的 rollout 和第 N 批的训练并行跑。

```
每迭代墙钟   = max(rollout + 奖励, 训练) + 权重同步
             = max(630 + 40, 80) + 10
             = 670 + 10 = 680 s
时间减少     = (760 - 680) / 760 = 10.5%
加速倍数     = 760 / 680 = 1.12 倍       <-- 验算 1/(1-0.105) = 1.12 OK
训练卡利用率 = 640 / (8 x 680) = 11.8%
```

⚠️ **收益只有 1.12 倍。为什么这么小？** 因为瓶颈在 rollout 那 670 秒里，而单步异步**没动这 670 秒的任何一个字节**。它只消灭了上表里「推理卡等训练」那 8.6% 的气泡。

> ★ **这是本章最反直觉的一条结论：如果你的长尾很严重，先做 partial rollout，不要先做异步。** 异步打的是 44.7% 那块（让训练卡别闲着），但它**不缩短墙钟**，因为墙钟由 rollout 决定。要缩短墙钟只有两条路：切长尾，或者让 rollout 跨迭代流起来。

**深度无穷（全异步）**：rollout 永不停，一批的长尾和下一批的头部重叠。墙钟退化成「这批样本的打包工作量」。

```
每迭代墙钟   = 2,601 GPU-秒 / 8 张卡 = 325 s
时间减少     = (760 - 325) / 760 = 57.2%
加速倍数     = 760 / 325 = 2.34 倍       <-- 验算 1/(1-0.572) = 2.34 OK
训练卡利用率 = 640 / (8 x 325) = 24.6%
全机利用率   = 3,241 / (16 x 325) = 62.3%
```

⚠️ 注意全异步之后**训练卡的利用率只有 24.6%，它仍然在等**。这暴露了一个被普遍忽略的问题：

> ★ **8 训 + 8 推这个配比本身就是错的。** 从上面的账可以直接读出来：训练只需要 640 GPU·秒，推理需要 2,601 GPU·秒，**需求比是 1 : 4**。16 张卡应该切成 **3 训 + 13 推**：
>
> ```
> rollout 墙钟   = 2,601 / 13 = 200 s
> 训练墙钟       =   640 /  3 = 213 s
> 每迭代墙钟     = max(200, 213) = 213 s
> 全机利用率     = 3,241 / (16 x 213) = 95.1%
> 相对同步的加速 = 760 / 213 = 3.57 倍
> ```
>
> ⚠️ **这是本文从上表推出的，不是任何一份技术报告的结论**，而且它忽略了显存约束（训练态每参数 16 字节，3 张卡装不下 32B，见下方提示）。但方向是对的：**异步真正的收益，一大半来自「它允许你把训推卡数解耦地调」**，而不是来自并行本身。

> ⚠️ **显存口径别记错**：训练一个 32B 模型，按 BF16 权重 2 + 梯度 2 + FP32 主副本 4 + Adam 一阶动量 m 4 + 二阶动量 v 4 = **16 字节/参数**（m 和 v **各** 4 字节，不是合计 4），光静态显存就是 32 × 16 = **512 GB**，一张 80 GB 的 H100 装不下，必须靠 ZeRO / FSDP 切开。详见 [../训练框架/分布式训练入门/02-显存去哪了.md](../训练框架/分布式训练入门/02-显存去哪了.md)。

### 四档对照总表

| | 深度 0 · 同步 | 深度 1 · 单步异步 | 深度 K · 有界队列 | 深度无穷 · 全异步 |
|---|---|---|---|---|
| **样本陈旧度** | **0 步**，完全 on-policy | **恰好 1 步** | **≤ K 步**，硬上界 | 无上界，只能实测分布 |
| **每迭代墙钟**（上面那笔账） | 760 s | 680 s | 680 s 与 325 s 之间 | 325 s |
| **相对同步的加速倍数** | 1.00× | **1.12×** | 1.1× ~ 2.3× | **2.34×** |
| **训练卡利用率** | 10.5% | 11.8% | 介于两者 | 24.6%（重配卡数后可到 ~95%） |
| **训练卡气泡** | **严重** | **仍然严重**（瓶颈没动） | 小 | 几乎没有 |
| **长尾还在不在** | 在 | **还在** | 看窗口开多大 | 在，但被跨迭代吸收了 |
| **需不需要 IS 修正** | 理论上不需要 | 建议要 | 要 | **必须要** |
| **实现复杂度**（✅ veRL 行数） | 1（基准） | ~1.1（553 行） | 中 | **~8**（4,335 行） |
| **谁在用** | TRL、OpenRLHF 默认、veRL 默认 | SkyRL、open-instruct、veRL `one_step_off_policy/` | ROLL、NeMo-RL、MiniMax Forge | AReaL、PipelineRL、TorchForge、**GLM-5 / slime** |

⚠️ 关于「需不需要 IS 修正」那一行，有一个**必须分清的混淆**：

> 同步档位下 `π_推理 = π_训练` 在**理论上**成立，所以 IS 比值应当恒等于 1。**但实测它不等于 1。** 那部分偏离**不是陈旧度造成的，是数值失配**——两个引擎的 kernel 算出了不同的 logprob。这是 [04 章](04-训推一致性.md) 的话题，和本章的异步档位**毫无关系**。
> ★ 把两者分开的办法很简单：**把配置改成「一批数据只做一次梯度更新 + `logp_old` 由训练引擎自己算」，此时 ratio 必须精确等于 1。** 如果不是，剩下的 100% 是数值失配。这条判据的完整版在 [../大模型算子开发/11-训推一致性算子层.md](../大模型算子开发/11-训推一致性算子层.md)。

⚠️ 这张表最重要的是**第 1 行和第 5 行此消彼长**。你没法两头都要：训练卡不空转，就意味着它在用旧样本训练。这是 RL 系统设计的**根本权衡**，后面所有东西都是在这条曲线上找位置。

✅ `fully_async_policy/` 里的文件名把架构直接写在脸上：

```
fully_async_main.py        主入口
fully_async_rollouter.py   生成侧，独立进程
fully_async_trainer.py     训练侧，独立进程
message_queue.py           <-- 两者之间的队列，就是「深度无穷」的那个流

```

而 `one_step_off_policy/` 只有 3 个文件、553 行：`main_ppo.py` + `ray_trainer.py` + `__init__.py`。

⚠️ 我的解读：**4,335 ÷ 553 = 7.8 倍，这个比例本身就是结论。**

从同步走到「一步离策略」，你只需要多开一个缓冲区、把两个阶段并行起来——改动很小。而从「一步离策略」走到「全异步」，你要额外处理：独立的生成进程生命周期、消息队列、动态调度、陈旧度追踪、失败恢复……复杂度陡增。

⚠️ 但要和 §2.2 的账对着读：**改动小不等于收益大。** 一步离策略只值 1.12 倍，全异步值 2.34 倍（重配卡数后 3.57 倍）。所以准确的说法是：

> **一步离策略是「最便宜的一档」，不是「性价比最高的一档」。** 它的真正价值在于：代码改动小到可以在现有同步管线上渐进验证，适合当第一步。但如果你的长尾严重（agentic、长 CoT、1M 上下文），**跳过它、直接上 partial rollout** 收益更大。选型见 [07-选型与实践.md](07-选型与实践.md)。

## 2.4 ★★ 三家前沿模型，三个不同的位置

这一节是全篇的核心。三份技术报告，在同一条轴上选了三个不同的点。

### ① GLM-5：走到最右边，彻底分离

✅ 原文（§4.1.1 Asynchronous RL Design）：

> *"we **decouple the training engine and the inference engine onto different GPU devices**. The inference engine **continuously generates** trajectories. Once the number of generated trajectories reaches a predefined threshold, the batch is sent to the training engine to update the model... The training engine updates the model parameters and **pushes the new weights back to the inference engine every K gradient updates**."*

拆开看这段话，四个设计决策：

| 原文短语 | 意思 | 对应的架构选择 |
|---|---|---|
| decouple ... onto different GPU devices | 训练和推理用不同的卡 | **disaggregated（分离部署）** |
| continuously generates | 生成永不停 | **buffer 深度 = 无穷** |
| reaches a predefined threshold | 攒够阈值才发一批 | 用「攒批」而不是「等对齐」来切分训练步 |
| every K gradient updates | 每 K 步才推一次权重 | 权重同步频率是**可调参数**，不是每步必做 |

⚠️ 对照 §2.2 的账看第三条：「攒够阈值才发一批」这个设计，正是把那 20.1% 的长尾空转吸收掉的机制——**不等最慢那条，攒够数就走，慢的那条算进下一批**。

✅ 还有一句容易被漏掉但很关键的：

> *"we also **reset the optimizer** after each weight update of the inference engine."*

⚠️ 我的理解：优化器状态（Adam 的一阶、二阶动量）是「对过去梯度的记忆」。异步 RL 里数据分布一直在漂，旧动量可能反而是噪声。每次推权重就重置一次优化器，等于**主动放弃跨版本的动量累积**，换取每一段训练内部的稳定性。这是个反直觉但很实在的工程选择——正常预训练里没人会这么干。

✅ 配套的还有一个 **Multi-Task Rollout Orchestrator**（多任务 rollout 编排器）：每个任务是一个独立的微服务，向中央编排器注册；编排器控制每个任务的 rollout 配比和生成速度；所有任务用统一的 message list 表示；**支持超过 1000 路并发 rollout**。

### ② Kimi-K3：留在最左边，同置

✅ 原文（§5.3 Infra for 1M Agentic RL）：

> *"We adopt **co-located RL training** to keep each 1M-context Kimi K3 RL experiment **within a few hundred GPUs**, and use **partial rollouts** to reduce tail latency from ultra-long trajectories."*

⚠️ 注意这句话的因果方向：**同置是结论，不是前提。** 前提是「每次实验要控制在几百张卡内」。

把这个约束和 §2.2 的账对上，就知道为什么：**分离部署要求训练侧和推理侧各自独占一批卡，而且这两批卡在对方工作时是闲着的。** §2.2 那张表里，同步 + 分离的全机利用率只有 26.7%——你买了 16 张卡，真正在算的只相当于 4.3 张。卡多的时候这笔浪费可以靠异步补回来；卡只有几百张、而上下文是 1M token 的时候，**与其买两套卡再想办法让它们重叠，不如一套卡轮流用**。同置的全机利用率天然更高，代价是训练和推理必须互相等。

那长尾怎么办？Kimi 不靠分离，靠另外三招：

| 手段 | ✅ 原文 | 解决什么 |
|---|---|---|
| **partial rollout**（部分 rollout） | *"use partial rollouts to **reduce tail latency** from ultra-long trajectories"* | 超长样本不必一次生成完，下一轮接着生成 |
| **外部 KV cache 池** | *"external KV-cache retention"*，write-back 设计：正在解码的块留在 GPU 显存，可复用但闲置的前缀在被驱逐时才写回 CPU 内存，下次复用前预取 | partial rollout 的前缀不用重算 |
| **可恢复 microVM 沙箱** | *"resumable microVM sandboxes to preserve long-lived model and environment state"* | agent 任务中断后环境状态还在（见 [06](06-AgenticRL-环境与沙箱.md)） |

⚠️ 这三招合起来，本质是**把「异步」从系统层挪到了样本层**：系统仍然是同步的，但单个样本可以跨步继续。这是一条被低估的路径。

★ **这条路线值多少，§2.1 第五步已经算过了**：512 条样本、长尾 5 条，partial rollout 把墙钟从 630 秒压到 317 秒，**加速 1.99 倍，推理侧利用率从 51.6% 到接近 100%**。注意这个 1.99 倍比「一步离策略」的 1.12 倍大得多，而且**它和异步是两件事，可以叠加**。两者为什么正交，[03 章 §3.5.1](03-权重同步.md) 从中断模型的角度再讲一遍。

> ⚠️ 一个容易被跳过的代价：partial rollout 要求把**没写完的序列连同它的 KV cache 一起存下来**。1M 上下文的 KV cache 有多大，是 Kimi 必须自建外部 KV 池的直接原因——这也是为什么这条路线「听起来简单、做起来贵」。KV cache 的显存账见 [../推理框架/推理优化入门/02-KV-Cache与显存账.md](../推理框架/推理优化入门/02-KV-Cache与显存账.md)。

### ③ MiniMax Forge：在中间插值

✅ Forge（§6.2）的架构是三层解耦。**每一层只认下一层的接口，不认实现**：

```
Agent Side  agent 侧
    纯粹的轨迹生产者，对「训练还是推理」完全无感知
  |
  |  发出补全请求
  v
Middleware Abstraction Layer  中间件抽象层
    |- Gateway Server : 路由所有补全请求
    |- Data Pool      : 分布式轨迹存储，异步收集
  |
  |  攒够一批就下发
  v
Training / Inference Side  训推侧
    |- Rollout Engine : 扮演策略 pi_theta，负责生成
    |- Train Engine   : 算 CISPO 梯度，同步权重回去
```

⚠️ 这个分层的价值在于：**agent 代码不需要知道自己是在被训练还是在被推理服务。** 10 万个 agent 脚手架只要会发 HTTP 补全请求就行，这是 agentic RL 能规模化的前提（见 [06](06-AgenticRL-环境与沙箱.md)）。

真正有意思的是它的调度策略——**Windowed FIFO（窗口化先进先出）**：

✅ 队列 `Q = [T_0, T_1, ..., T_{N-1}]`，维护一个头指针 `i`，窗口是 `[T_i, T_{i+W-1}]`。**窗口内**谁先完成用谁（贪心，不等顺序），**跨窗口边界**必须严格按序。实践取 **`W = 0.3N`**。

⚠️ 这条规则太抽象，用一个具体例子走一遍。设 N = 10 道题，窗口 `W = 3`，各题生成耗时差别极大：

```
T_0: 60s    T_1: 5s    T_2: 8s    T_3: 5s    T_4: 50s    T_5: 6s  ...
 ^ 长尾                                       ^ 长尾
```

头指针 `i = 0`，窗口 = `[T_0, T_1, T_2]`，这三道题同时在跑：

| 时刻 | 发生什么 | 窗口里还剩谁 |
|---|---|---|
| `t = 0` | 窗口 `[T_0 T_1 T_2]` 三个一起启动。T_3 想进来？门关着 | T_0 T_1 T_2 |
| `t = 5s` | T_1 完成 → **立刻交付**训练侧（窗口内不等顺序，这就是「贪心」） | T_0 T_2 |
| `t = 8s` | T_2 完成 → 立刻交付。窗口里只剩 T_0 在磨 | T_0 |
| `t = 8s ~ 60s` | **空转 52 秒**。T_3 明明只要 5 秒，但门关着 | T_0 |
| `t = 60s` | T_0 完成 → 交付，头指针前进到 3，窗口滑到 `[T_3 T_4 T_5]` | T_3 T_4 T_5 |

关键在 `t = 8s → t = 60s` 这一段：**T_3 明明只要 5 秒，却必须干等 T_0**。这是故意的，就是「跨窗口边界严格按序」的代价。

这个「等」买到的是**陈旧度的硬上界**：任何一条进入训练的轨迹，它出发时的权重与当前权重最多差一个窗口。全异步里这个差距**没有上界**——这正是 §2.2 那张四档表里「深度无穷」那一列写「无上界，只能实测分布」的意思。

顺带还堵住了另一个坑——完全贪心下长难题会被系统性地挤出 batch，**数据分布会偏**。这一点在 §2.5 还会再出现一次。

⚠️ 把 W 从 1 调到 N，就是在两个极端之间**显式插值**：

| 窗口 `W` | 行为 | 陈旧度上界 | 长尾暴露程度 | 等价于 |
|---|---|---|---|---|
| `W = 1` | 严格 FIFO，完全按顺序交付 | 0 | **全部暴露** | 同步（深度 0） |
| `W = 0.3N` | **Forge 实际取值** | ≤ 一个窗口 | 窗口内的长尾被吸收 | 有界队列（深度 K） |
| `W = N` | 完全贪心，谁先完成用谁 | **无上界** | 完全不暴露 | 全异步（深度无穷） |

W 越大，吞吐越高、陈旧度越不可控；W 越小，越接近同步。**把一个架构选择变成了一个可调旋钮**，这是三家里最工程化的做法。

✅ 另外两个 Forge 的加速手段值得单独记：

- **Prefix Tree Merging（前缀树合并）**：同一道题的 G 个答案共享同一段前缀，前缀只算一次然后分叉。报告称「**数学上等价于独立样本训练**」「**零近似误差**」，带来 **最高 40× 的训练加速**。⚠️ 「最高 40×」是报告给的上界，不是常态值；它的收益完全取决于前缀占总长度的比例——prompt 长、答案短的任务收益大，agentic 那种 prompt 短、轨迹极长的任务收益小。
- **全局 L3 KV Cache 池**：由分布式文件系统托底，配一个成本感知的请求路由器。

### 三家放在一起

| | GLM-5 | Kimi-K3 | MiniMax Forge |
|---|---|---|---|
| 训推放置 | **分离** | **同置** | 分离（三层解耦） |
| buffer 深度 | 无穷（连续生成） | 0（但样本可跨步） | 有界，窗口 `W = 0.3N` |
| 陈旧度上界 | 无 | 0（样本层面跨步除外） | **一个窗口，硬上界** |
| 长尾怎么解 | 靠异步吸收 + PD 分离 + FP8 | **partial rollout + 外部 KV 池** | **窗口内贪心 + 前缀树合并** |
| 打的是 §2.2 哪一块气泡 | 44.7% + 8.6% | **20.1%** | 20.1% 的一部分 + 8.6% |
| 明说的约束 | 744B / 28.5T token 规模 | *"within a few hundred GPUs"* | 10 万+ agent 脚手架 |

⚠️ **我的综合判断：这三个点在同一条「吞吐 ↔ 分布一致性」的权衡曲线上，谁也没有推翻谁。**

```
  分布一致性（样本越新越好）
      ^
      |  [Kimi-K3 同置]
      |     样本永远由最新权重生成；代价是训练卡要等生成
      |
      |              [MiniMax W=0.3N]
      |                 显式旋钮，陈旧度有硬上界
      |
      |                            [GLM-5 全异步]
      |                               吞吐拉满，一致性交给算法侧兜底
      +----------------------------------------------------------> 吞吐
```

选哪个点，取决于三个约束：**卡够不够**（Kimi 明说不够）、**上下文多长**（越长长尾越致命，§2.1 的 16 倍比值就是长度比）、**有没有算法侧的一致性兜底手段**（见 [04](04-训推一致性.md)）。

## 2.5 陈旧度怎么管：三种正交的手段

一旦离开深度 0，样本就带上了「版本落后」这个属性。🌐 业界的处理手段有三种，而且它们是**正交的**——可以同时用：

| 手段 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **① 逐样本版本拒绝** | 每个样本带一个版本号，太旧的直接丢 | 精确，粒度到单个样本 | 丢掉的是已经花掉的算力 |
| **② 深度限制** | 队列最多 K 层，满了就阻塞生成 | 简单，硬保证上界 | 阻塞生成 = 部分退回同步 |
| **③ IS 加权修正** | 不丢样本，在 loss 里乘一个重要性采样比值来纠偏 | 不浪费算力 | 比值方差大时反而更不稳（见 [04 §4.6](04-训推一致性.md)） |

🌐 HF 横评的结论是：**生产环境的趋势是三种混用**，而不是只靠一种。

⚠️ 用 §2.2 的账给手段 ① 估个价：全异步下每迭代 325 秒，如果版本门限设成「最多落后 2 步」，那么任何生成时间超过 650 秒的样本都会被丢掉——对照 §2.1 的分布表，**那 5 条 32K 的样本（630 秒）正好擦着线**。门限再紧一点，它们就全被丢了。而它们恰恰是最难的题。这直接引出下面这个坑。

### ⚠️ 非对称过滤会让「存活的正样本」系统性地更陈旧

> **这是本节最该记住的一条，因为它不会报错，只会让模型学偏。**

很多 RL 训练会做动态过滤——把全对或全错的组丢掉（因为组内没有区分度，优势全为零、梯度也为零，这是 DAPO 这类算法的标准做法，见 [../后训练/05-RLVR-可验证奖励.md](../后训练/05-RLVR-可验证奖励.md)）。

但难题的 rollout 通常**更长**，所以完成得更晚。把 §2.1 的分布表和这条规则叠起来：

| | p0–p50（2K） | p99–p100（32K） |
|---|---|---|
| 完成时刻 | 39.4 s | 630 s |
| 生成它的权重落后几步（按 325 s/步算） | 0 步 | **约 2 步** |
| 题目难度 | 偏简单 | 偏难 |
| 被「全对/全错」过滤掉的概率 | 高（简单题容易全对） | 低（难题答案分散，组内有区分度） |

⟹ **活下来、真正贡献梯度的那些样本，恰恰是最旧的那一批。**

**batch 级的陈旧度门控看不见这个偏差**——整批的平均陈旧度可能很正常（512 条里 500 条都是 0 步），但真正进 loss 的那几十条全是落后 2 步的。🌐 HF 横评据此认为**逐样本打版本号是必需的**，不能只在 batch 级别管。

⚠️ 这条和 §2.4 MiniMax 那条「完全贪心下长难题会被系统性挤出 batch」是**同一个病的两种症状**：长 = 难 = 晚 = 旧，而训练最需要的恰好是难的那些。
