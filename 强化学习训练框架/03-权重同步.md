# 03 · 权重同步：新权重怎么搬回生成引擎

> **这一篇干什么**：讲清楚五模块里的第 ⑤ 块。这是 RL 框架里最容易被低估、但工程量最大的一块。
> **难度** ★★ · **前置**：[02-架构主轴](02-架构主轴-同步到全异步.md)
> **读法**：本章 §3.2 会把「一个模型的权重要传多久」算成可验算的数字，结论可能和直觉相反——**传输几乎从来不是瓶颈，中断才是**。后面每一节都在这个结论上展开。
> **分工**：RL 的算法与数据在 [../后训练/](../后训练/README.md)，推理引擎本身在 [../推理框架/](../推理框架/README.md)。本章只讲「权重怎么从训练侧搬到推理侧」这一件事。

---

**本章关键词**

**resharding**（重切分）—— 训练态的并行切法和推理态不同，权重传过去要重新切一遍。
**TP / PP / DP / EP**（Tensor / Pipeline / Data / Expert Parallelism，张量 / 流水线 / 数据 / 专家并行）—— 四种把模型摊到多卡上的切法。
**ZeRO / FSDP**（Zero Redundancy Optimizer / Fully Sharded Data Parallel，零冗余优化器 / 完全分片数据并行）—— DeepSpeed 和 PyTorch 各自的显存分片方案。
**NCCL / HCCL**（NVIDIA / Huawei Collective Communications Library，集合通信库）—— 一群 GPU 之间高速传数据的标准库。
**RDMA**（Remote Direct Memory Access，远程直接内存访问）—— 网卡绕过 CPU 和内核，直接读写对端机器的内存。
**CUDA IPC**（CUDA Inter-Process Communication，CUDA 进程间通信）—— 同一台机器上不同进程直接共享显存指针，零拷贝。
**NIXL**（NVIDIA Inference Xfer Library，英伟达推理传输库）—— 面向推理场景的点对点传输抽象层。
**IB**（InfiniBand，无限带宽）—— 一套自带 RDMA 的专用高速网络。
**NVLink**—— 同一台机器内 GPU 之间的直连总线，不经过网卡。
**中断模型**—— 搬权重的时候，正在生成的那些序列怎么办。本章 §3.5 的主题。
**partial rollout**（部分 rollout）—— 长样本不必一次写完，到预算就存盘，下一轮接着写。

---

## 3.1 为什么这件事不简单

训练完一步，参数更新了。现在要让推理引擎用上新参数。听起来就是「拷贝一下」，但有三个麻烦：

**① 两边的切法不一样（resharding，重切分）。**
训练侧为了省显存，权重按 ZeRO / FSDP 切得七零八落（每张卡只有一小片）；推理侧为了跑得快，按 TP（张量并行）切成另一种形状。**中间必须做一次全局的重组**。这个在 [14 章 §14.4](../训练框架/分布式训练入门/14-RL训练框架.md) 讲过原理，这里只关心工程实现。

**② 权重很大。** 一个 700B 模型的 BF16 权重是 1.4 TB。就算只在机器内部搬，也不是瞬间的事。§3.2 会把这笔账完整算出来。

> ⚠️ **只搬权重，不搬梯度和优化器状态。** 训练态每个参数要占 **16 字节**（BF16 权重 2 + 梯度 2 + FP32 主副本 4 + Adam 一阶动量 m 4 + 二阶动量 v 4 —— **m 和 v 各 4 字节，不是合计 4**），但推理引擎只需要那 2 字节的权重。**搬回去的量是训练态显存的 1/8。** 很多人在估这笔账时会把 16 字节整个算进去，差 8 倍。显存口径详见 [../训练框架/分布式训练入门/02-显存去哪了.md](../训练框架/分布式训练入门/02-显存去哪了.md)。

**③ 搬的时候，生成要不要停？**
如果停，那这段时间推理卡在空转——异步架构辛辛苦苦省下来的时间又还回去了。如果不停，那正在生成的那些样本，前半段用旧权重、后半段用新权重，**一条轨迹里混了两个策略**。

这三个麻烦对应三个设计维度：**resharding 策略 × 传输层 × 中断模型**。⚠️ 本章会论证：**第三个维度的代价，比第二个大两个数量级。**

## 3.2 🌐 传输层七档

从最慢到最快，业界用过的传输方式大致是这七档：

| 档 | 方式 | 典型耗时 | 说明 |
|---|---|---|---|
| 7 | **文件系统 + 重启推理引擎** | 分钟级 | 最原始。存 checkpoint，杀掉推理进程，重新加载。只在小规模实验里能忍 |
| 6 | **HTTP PUT** | 秒~分钟 | 通过 HTTP 接口把权重推给推理服务 |
| 5 | **文件系统 + HTTP 通知** | 秒级 | 训练侧写共享盘，HTTP 只发一个「去读吧」的信号。跨机房可用 |
| 4 | **共享内存** | 亚秒 | 同一台机器上，训练进程和推理进程共享一块内存 |
| 3 | **CUDA IPC** | 亚秒 | 同机不同进程直接共享显存指针，**零拷贝**。同置架构的标准做法 |
| 2 | **NCCL 广播** | **~100–500 ms** | 标准的集合通信广播 |
| 1 | **NCCL + 分桶（bucketing）** | **~20 ms** | 把很多小张量打包成大桶再传，减少通信次数。🌐 veRL 通过 checkpoint engine 实现，是横评里最快的 |

> ⚠️ 易混：**NCCL 不等于 RDMA**。NCCL 是定义「一群 GPU 怎么一起传」的软件库，RDMA 是底下「数据实际怎么跑」的传输能力——跨机时 NCCL 会用 RDMA，机内 8 卡走的是 NVLink，一点 RDMA 都不沾。完整分层关系（含 NIXL / Mooncake 各在哪一层）见 [附-速查表 3.1](附-速查表.md)。
> 来源：[Keep the Tokens Flowing](https://huggingface.co/blog/async-rl-training-landscape)，访问于 2026-08。

⚠️ 注意档 1 和档 2 差了 **5~25 倍**，而两者用的是**同一个底层库**。差别只在「有没有把小张量打包」。这是典型的「工程细节决定量级」——一个 700B MoE 模型有几万个张量，一次一个地广播，光是启动开销就吃掉大部分时间。

### ★ 把它算成数字：一个模型的权重要传多久

上面那张表给的是量级，下面把它变成能自己验算的算术。

**第一步：权重有多少字节。** 算式只有一条：`字节数 = 参数量 × 每参数字节数`。

| 模型 | 参数量 | BF16（2 字节/参数） | FP8（1 字节/参数） |
|---|---|---|---|
| 7B | 7 × 10⁹ | **14 GB** | 7 GB |
| 32B | 32 × 10⁹ | **64 GB** | 32 GB |
| 70B | 70 × 10⁹ | **140 GB** | 70 GB |
| 700B（MoE 总参数） | 700 × 10⁹ | **1.4 TB** | 700 GB |

**第二步：三条链路各有多宽。** ⚠️ **这一步是本章最容易出错的地方**，两个单位坑本仓库都踩过：

| 链路 | 厂商标称 | ⚠️ 算「发出去要多久」该用的数 | 为什么 |
|---|---|---|---|
| **NVLink 4.0**（H100 机内） | 900 GB/s | **450 GB/s** | 900 是**双向聚合**（同时发 450 + 收 450）。单向发送只能用 450 |
| **InfiniBand NDR**（跨机） | 400 Gb/s | **50 GB/s** | 400 的单位是 **Gb（比特）不是 GB（字节）**，÷ 8 |
| **PCIe 5.0 ×16** | 128 GB/s | **63 GB/s** | 同样是双向聚合值，单向约 63 |

> ⚠️ **坑 1**：NVLink 900 是双向聚合，**单向 450**。
> ⚠️ **坑 2**：IB 的 400 是 **Gb** 不是 GB，`400 ÷ 8 = 50 GB/s`。
> ⟹ 同口径下 **NVLink : IB = 450 : 50 = 9 倍，不是 18 倍**。18 倍是「分子用双向值、分母用单向值」算出来的错误结果，是这一行最常见的错。

**第三步：相除。** `时间 = 字节数 ÷ 带宽`：

| 模型 / 精度 | 字节数 | NVLink 450 GB/s | IB 50 GB/s | PCIe 5.0 63 GB/s |
|---|---|---|---|---|
| 7B BF16 | 14 GB | **31 ms** | 280 ms | 222 ms |
| 7B FP8 | 7 GB | 16 ms | 140 ms | 111 ms |
| **32B BF16** | 64 GB | **142 ms** | **1.28 s** | 1.02 s |
| 70B BF16 | 140 GB | 311 ms | **2.80 s** | 2.22 s |
| 70B FP8 | 70 GB | 156 ms | 1.40 s | 1.11 s |
| 700B BF16 | 1.4 TB | 3.11 s | **28.0 s** | 22.2 s |
| 700B FP8 | 700 GB | 1.56 s | 14.0 s | 11.1 s |

⚠️ 这是**单条链路、点对点、理想线速**的时间。实际还要加上三样东西：

| 额外开销 | 是什么 | 量级 |
|---|---|---|
| **resharding** | 训练态 ZeRO/FSDP 切法 → 推理态 TP 切法的全局重组，是**计算 + 多轮通信** | ⚠️ 常常比传输本身还贵 |
| **broadcast 到 N 个推理实例** | NCCL ring 算法是流水化的，⚠️ 理想模型下时间近似与 N 无关，仍是 `字节 ÷ 带宽` 量级 | 约 1~2 倍 |
| **几万个小张量的启动开销** | 这正是上面七档表里档 1 和档 2 差 5~25 倍的原因 | 可以吃掉大部分时间 |

### ★ 一处可验算的交叉核对：Mooncake 的 16~17 秒

🌐 HF 横评提到：**Mooncake 的 checkpoint-engine 能在 256 张 H20 上把 Kimi-K2 的权重更新做到约 16~17 秒**。拿上面的表核一下：

```
Kimi-K2 总参数约 1T，原生 FP8  ==>  权重约 1,000 GB

单条 400G IB 的线速时间 = 1,000 GB / 50 GB/s = 20.0 s
实测的权重更新时间                           = 16~17 s
```

⚠️ **实测比单条链路的线速还快，说明它不止用了一条链路**——多网卡并行，或者把权重分片后多路并发。**这是本文的推断，不是博客的结论。** 但这个核对本身有价值：它说明 16~17 秒**不是实现不好，而是已经贴着物理上限了**。想再快，只剩两条路——**减少要传的字节**（FP8 已经用了，下一步是只传增量，见 §3.4），或者**加链路**。

### ⚠️ 所以权重同步到底是不是瓶颈？

把上面的传输时间和 [02 章 §2.2](02-架构主轴-同步到全异步.md) 那笔迭代时间账放在一起看：

| | 耗时 | 占一个 325 秒迭代的比例 |
|---|---|---|
| 32B BF16 跨机 IB 传输 | 1.28 s | **0.39%** |
| 32B BF16 机内 NVLink 传输 | 0.14 s | **0.04%** |
| 一次 rollout（打包后） | 325 s | 100% |

⟹ **传输本身不是瓶颈，百分之零点几而已。** 这和 [14 章 §14.3.4](../训练框架/分布式训练入门/14-RL训练框架.md) 的结论一致，也解释了 [01 章 §1.3](01-格局全景.md) 观察到的现象——五份技术报告全都对「权重同步怎么实现」语焉不详，因为它在端到端里占比太小。

> ★ **但别就此得出「权重同步不重要」。** 真正贵的不是把字节搬过去，而是**搬的时候要不要让生成停下来**。§3.5 会把这笔账也算出来：**排空一次生成的代价，可以是传输代价的两百倍。**

## 3.3 ✅ veRL 的六个 checkpoint engine

veRL 把权重同步单独抽成了一个组件层。✅ 本地实测（commit `b256ebf`，`verl/checkpoint_engine/`，共 3,540 行）：

| 文件 | 行数 | 后端 |
|---|---|---|
| `base.py` | 629 | 抽象基类 |
| `nccl_checkpoint_engine.py` | 515 | NVIDIA GPU 集合通信 |
| `hccl_checkpoint_engine.py` | 396 | **昇腾 NPU** 的对应实现 |
| `mooncake_checkpoint_engine.py` | 321 | Mooncake（月之暗面开源的传输层） |
| `nixl_checkpoint_engine.py` | 532 | NVIDIA Inference Xfer Library |
| `kimi_checkpoint_engine.py` | 391 | Kimi 的实现 |
| `delta_checkpoint_engine.py` | **672** | **只传增量** |
| `delta_sync/` | — | 增量同步的子模块 |

⚠️ 这张表本身就说明了两件事：

1. **权重同步值得一个独立的抽象层。** 3,540 行只干这一件事——不是「顺手写个 broadcast」的量级。
2. **`delta_checkpoint_engine.py` 是里面最大的一个（672 行），比 NCCL 那个还大。** 「只传变化的部分」这个想法很直观，但要处理增量编码、完整性校验、基准版本追踪，实现复杂度反而最高。

### ⚠️ 为什么要做六个后端，而不是一个

既然 §3.2 已经算出传输只占百分之零点几，为什么还要为它写 3,540 行、六个后端？答案不在「快多少」，在**参与方约束**：

| | NCCL 集合通信 | RDMA 点对点（NIXL / Mooncake） |
|---|---|---|
| 参与方约束 | 所有 rank 必须**同时在线、同步进场**凑齐一个 communicator | 谁准备好谁拉，**推理实例可以随时扩缩容** |
| 适合 | 同步架构、固定拓扑 | 异步架构、弹性推理池 |
| 一个实例挂了 | 整个 communicator 要重建 | 只影响它自己 |

⟹ **异步 RL 不想被「所有人必须同时到齐」卡住。** 这是六个后端存在的根本原因，而不是带宽。完整的分层关系见 [附-速查表 3.1](附-速查表.md)。

### 🌐↔✅ 一处交叉验证

🌐 HF 横评提到：**Mooncake 的 checkpoint-engine 能在 256 张 H20 上把 Kimi-K2 的权重更新做到约 16~17 秒**，该组件已进入 PyTorch 生态，并且有 NIXL 后端。

✅ 本地核对：veRL 的 `mooncake_checkpoint_engine.py` 和 `nixl_checkpoint_engine.py` **确实都存在**，与博客描述的组件与后端一一对应。

⚠️ 这是一条「联网材料 ↔ 本地源码」互相印证的链路。单看博客是二手信息，单看源码不知道性能量级，两边对上才是可用的结论。§3.2 又用带宽账给它加了第三个独立的验证角度。

## 3.4 ★ slime 的四条通路：把 3.2 那张表落成了源码

slime 的实现方式和 veRL 不同——它不做「后端抽象」，而是**直接把四种传输方式各写一个文件**。✅ 本地实测（commit `3778dbf`，`slime/backends/megatron_utils/update_weight/`，共 2,093 行）：

| 文件 | 行数 | 对应 §3.2 的哪一档 | 什么场景用 |
|---|---|---|---|
| `update_weight_from_tensor.py` | **432** | 档 3~4：同置时直接传张量（CUDA IPC / 共享内存） | **同置**，最快 |
| `update_weight_from_distributed.py` | **373** | 档 1~2：分布式集合通信 | 同机房分离部署 |
| `update_weight_from_disk_delta.py` | **304** | 档 5 + 增量：写共享盘，只写变化的字节 | **跨机房**，最省带宽 |
| `update_weight_from_disk.py` | 95 | 档 5：写共享盘，全量 | 兜底 / 调试 |
| `expert_routing.py` | 380 | — | **MoE 专家在重切分时怎么映射** |
| `common.py` | 206 | — | 公共逻辑 |

⚠️ 这个目录结构比任何文字都清楚：**权重同步不是一个方法，是一族方法，选哪个取决于训推放在哪。**

把它和 §3.2 的带宽表对上，选择标准一目了然：

| 训推放置 | 可用链路 | 32B BF16 传输时间 | slime 走哪个文件 |
|---|---|---|---|
| 同置（同一批 GPU） | 显存内，零拷贝 | **~0**（不复制，只换指针） | `from_tensor` |
| 分离，同机房 | IB 50 GB/s | 1.28 s | `from_distributed` |
| 分离，跨机房 | 广域网，⚠️ 带宽低一到两个数量级 | **分钟级** | `from_disk_delta`（只传变化的字节） |

★ **最后一行解释了增量同步为什么存在**：跨机房时 §3.2 的 50 GB/s 不再成立，全量传一个 70B 模型可能要几分钟——这时候「只传变化的 1%」就从优化变成了必需。

### ✅ Delta Weight Sync 的完整机制

slime 的 `examples/delta_weight_sync/README.md` 把设计写得很直白（✅ 原文）：

> *"Non-colocated weight sync that ships only the **changed bytes** between two syncs instead of a full checkpoint, for training/inference disaggregation **across clusters or datacenters**."*

流程是五步（⚠️ 下图只表示数据流向，不表示时间比例）：

```
  Trainer  --(1)(2)-->  Shared FS  --(3)-->  Inference Engine
                                                     |
                                                    (4)
                                                     |
                                                    (5)
                                                     v
                                          update_weights_from_disk
```

| 步 | 在哪一侧 | 做什么 |
|---|---|---|
| (1) | 训练侧 | 算出本次权重与上次同步时的差异 |
| (2) | 训练侧 | 按 HuggingFace checkpoint 的目录格式，把 per-tensor delta 写进共享文件系统 |
| (3) | 推理引擎 | 调 `/pull_weights` 拉取 delta |
| (4) | 推理引擎 | 把 delta 打到本机已有的完整 checkpoint 上 |
| (5) | 推理引擎 | **走普通的 `update_weights_from_disk` 路径**加载，不新开一条逻辑 |

✅ 几个具体到能直接抄的设计点：

| 设计点 | 内容 |
|---|---|
| 增量编码 | `xor`（最小最快）或 `overwrite`（幂等） |
| 完整性校验 | `xxh3-128`（默认）/ `blake3` / `adler32` |
| 端点收敛 | *"slime only ever talks to **one endpoint per engine**"*——每个引擎只暴露一个接口，内部自己分发到它跨的所有主机 |
| 复用既有路径 | 打完补丁后**走普通的 `update_weights_from_disk` 路径**，不新开一条加载逻辑 |
| 厂商无关 | 对象存储需要显式 commit/refresh 的，用 `--custom-update-weight-post-write-path` 钩子。✅ 原文：*"no vendor-specific code lives in slime"* |

⚠️ 最后两条是很有品味的工程决策。「打完补丁走普通加载路径」意味着 delta 只是一个**前置优化**，不改变下游任何逻辑，出问题时可以直接关掉降级到全量。「厂商特定代码不进主干」意味着接了新的存储不需要改 slime。

### 🌐↔✅ 又一处独立收敛

- ✅ slime 有 `update_weight_from_disk_delta.py`（304 行）+ `examples/delta_weight_sync/`
- ✅ veRL 有 `delta_checkpoint_engine.py`（672 行）+ `delta_sync/`

⚠️ 两家独立收敛到「只传增量」。这说明当训推跨机房部署成为常态时，**全量传输的带宽成本已经成为主要瓶颈**——不然没人会花几百行去实现一个增量协议。注意这和 §3.2 的「传输不是瓶颈」**不矛盾**：那个结论的前提是**同机房 IB**，一旦跨机房，前提就不成立了。

## 3.5 🌐 中断模型四档

传输层解决「多快」，中断模型解决「传的时候生成怎么办」。

| 档 | 模型 | 做法 | 代价 |
|---|---|---|---|
| 1 | **永不停（never-stop）** | 推理引擎**原地换成新权重**，在飞的序列接着往下生成；前缀 KV cache 是旧权重算出来的，**不重算**，继续复用 | 一条轨迹混两个版本，且前缀是**陈旧 KV** |
| 2 | **单请求中止（per-request abort）** | 通过 HTTP 接口逐个中止请求，换权重后重发 | 中止的部分算力浪费掉 |
| 3 | **软暂停 / 排空（soft pause / drain）** | 停止接新请求，等在飞的请求跑完，再换权重 | 排空期间吞吐逐渐降到零 |
| 4 | **逐步阻塞（per-step blocking）** | 每个训练步都完整停一次生成 | 最简单，也最慢 |

> 来源：HF 横评（同 3.2）+ 🌐 [PipelineRL 论文 arXiv:2509.19128](https://arxiv.org/abs/2509.19128)（TMLR 2026）、[ServiceNow 官方博客](https://huggingface.co/blog/ServiceNow/pipelinerl)，访问于 2026-09。

⚠️ **档 1 的机制容易写反**：不是「接着用**旧**权重跑完」（那样轨迹就是单版本的，和「跨两个版本」自相矛盾），而是**换成新权重、继续往下生成**，只有前缀的 KV cache 停留在旧版本。🌐 HF 横评进一步指出 PipelineRL 用的是**逐参数流式广播**（每个参数一次 RPC + NCCL broadcast），前向传播穿插在参数更新之间——所以在飞的序列**同一次前向里不同层可能用的是不同版本的权重**。严格说，这已经不只是「跨两个版本」，而是**层间混合**：它的 behavior policy 不对应任何一个真实存在过的模型。

⚠️ 档 1 看着最激进，但它其实和 [02 章](02-架构主轴-同步到全异步.md) 的全异步是一套逻辑：**既然已经接受了样本陈旧，那再多接受「一条轨迹里混两个版本」也不算什么**，反正下游有 IS 修正兜底（见 [04](04-训推一致性.md)）。🌐 PipelineRL 就是把这一条当作核心卖点；其论文做了 KL 实验——混合策略 + 复用陈旧 KV 相比完全重算，KL 只略高一点，所以保留了这个设计。

### ★ 中断的代价有多大：和 §3.2 对照着算一遍

§3.2 算出 32B 模型跨机传一次权重只要 **1.28 秒**。现在算另一半——**为了传这 1.28 秒，生成要停多久**。

一次权重同步的总停机时间由四块组成：

| 组成 | 是什么 | 32B / 8 卡 / IB 的量级 |
|---|---|---|
| **① 排空** | 等在飞的序列跑完 | **取决于当时最长那条还剩多少** |
| ② 传输 | §3.2 算过 | 1.28 s |
| ③ resharding + 引擎唤醒 | 重切分、重建 CUDA graph、预热 | ⚠️ 量级设定 5~10 s |
| ④ KV cache 处理 | 旧权重算出的 KV 作废时要重算前缀 | 看档位，档 1 不重算 |

**① 是唯一一个量级不确定、也是唯一一个大到离谱的。** 用 [02 章 §2.1](02-架构主轴-同步到全异步.md) 那个长度分布算：

```
最长的那 5 条样本，每条要写满 630 s
在随机时刻叫停，期望还剩  630 / 2 = 315 s
最坏情况（刚开始写）              = 630 s
```

| 中断模型 | 排空 | 传输 | resharding + 唤醒 | **合计停机** | 是传输时间的几倍 |
|---|---|---|---|---|---|
| 档 4 逐步阻塞 | ~315 s（期望） | 1.3 s | ~8 s | **~324 s** | **253×** |
| 档 3 软暂停 / 排空 | ~315 s（期望） | 1.3 s | ~8 s | **~324 s** | **253×** |
| 档 2 单请求中止 | 0（直接砍断） | 1.3 s | ~8 s | **~9 s** | 7× |
| 档 1 永不停 | 0 | 与生成重叠 | 与生成重叠 | **~0** | 0× |

⚠️ 三件事：

1. **排空的代价是传输的两百多倍。** 这就是为什么「选哪个传输层」远没有「选哪个中断模型」重要。⚠️ 315 秒是用 [02 章 §2.1](02-架构主轴-同步到全异步.md) 那个**示意分布**算出的期望值，真实数字取决于你自己的长度分布；但**量级上的结论（差两个数量级）对任何长尾明显的任务都成立**。
2. **档 2 看起来只要 9 秒，但有隐性成本**：被砍断的序列已经写出去的 token 全部作废，重发要从头再 prefill 一遍。按「期望砍在一半处」算，**浪费的算力约等于那些序列已完成工作量的一半**。
3. **档 1 把停机压到 0，代价是一条轨迹混了多个版本的权重。** 这是一笔明码标价的交易，不是 bug。

> ★ **一句话串起本章前半段**：§3.2 说传输只占 0.39%，这一节说排空能占到一个迭代的 100%——**权重同步这一块的全部工程量，其实都花在「怎么不排空」上。** veRL 的六个后端、slime 的四条通路、PipelineRL 的逐参数流式广播，目标都是同一个。

### 3.5.1 ⚠️ 档 1 与 partial rollout 差在哪

⚠️ 这两条路**光看「一条轨迹由多个版本产生」这个结果分不出来**——在这一点上它们确实一样。区别在目的、切点和时间尺度三个层面。

**① 最本质的：它们解决的根本不是同一个问题**

| | 要消灭的浪费 | 不用它会怎样 |
|---|---|---|
| **档 1 永不停** | 换权重时的 **GPU 气泡**——排空期间生成吞吐掉到零 | 每个训练步都有一段时间推理卡在空转 |
| **partial rollout** | **长尾**——一批里 99% 生成完了，剩 1% 超长样本让整批干等 | 见 [02 章 §2.1](02-架构主轴-同步到全异步.md)：512 个 32K rollout，必须等最慢那个 |

✅ Kimi 原文自己讲得很清楚（[02 章 §2.4](02-架构主轴-同步到全异步.md) 引的那句）：*"use partial rollouts to **reduce tail latency** from ultra-long trajectories"* —— 是 reduce **tail latency**，不是 reduce weight-sync overhead。

⚠️ 推论：**这两个是正交的，可以同时用。** 就算权重同步瞬间完成、完全不需要中断，K3 那种百万 token 上下文照样需要 partial rollout 切长尾；反过来，就算所有样本等长、没有长尾，PipelineRL 的永不停照样省下气泡。

> ★ 这一条在 [02 章 §2.2](02-架构主轴-同步到全异步.md) 的气泡分解表里有对应的数字：**「训练卡等生成」占 44.7%、「长尾空转」占 20.1%，是两块不同的气泡。** 档 1 打的是前者的一部分（换权重那段），partial rollout 打的是后者。两块加起来才是全部。

**② 切点谁说了算**

| | 档 1 | partial rollout |
|---|---|---|
| 切点位置 | **被动撞上**——权重什么时候到，就切在哪个 token | **主动选定**——到达 token 预算、或一个工具调用回合结束 |
| 可预测性 | 每条轨迹切点都不同，长轨迹可能被切好几次，事先不知道 | 调度器决定，可对齐语义边界 |
| 切点处生成 | **不停**，无缝往下走 | **真的停了**，这一段结束，存盘走人 |

**③ 时间尺度差一整个数量级**

- 档 1：切点前后只隔 **1 个 optimizer step**，同一个 rollout 批次内立刻续上。
- partial rollout：切点后**存进 buffer 等下一轮**，中间隔了**一整个训练迭代**。超长样本可能在 buffer 里躺好几轮。

⚠️ 反直觉的结论：**partial rollout 的版本跨度未必比档 1 小**，甚至可能更大。它「干净」不在跨度，而在于**边界清晰、每段能精确记上自己的版本号**，下游 IS 修正的分母是确定的。

⚠️ **待核实**：Kimi 原文只描述了 `external KV-cache retention` 的 write-back 机制，**没有说明跨权重更新时陈旧 KV 是丢弃重算还是继续复用**。若是后者，partial rollout 同样有陈旧 KV 污染，和档 1 在这一点上没有差别，上一段「比档 1 干净」的说法就要再降一档。需回一手技术报告 §5.3 核实。旁证：🌐 ServiceNow 另一篇 vLLM V0→V1 文章恰好踩过这个坑——prefix cache 命中了权重更新之前算出的状态，导致 V1 上出现不该有的退化，最后靠关掉 prefix caching 才定位清楚。

> ⚠️ 一句话：**档 1 是「换权重时不停下来」，partial rollout 是「长样本主动切段」。前者的多版本是为省气泡付的代价，后者的多版本是为砍长尾付的代价。**

⚠️ 注意 openPangu 那一行搬的**不是权重，是路由记录**（MoE 每个 token 选了哪几个专家）。这是 [04 章 §4.4](04-训推一致性.md) 的话题，但它出现在这里说明一件事：**推理侧要回传给训练侧的东西正在变多，这条通路的带宽预算要重新算。**

### ★ 两个旋钮，不是一个

⚠️ GLM-5 的「每 K 步推一次」是这里最实用的一条：**权重同步频率是一个独立的旋钮**。它和 [02 章 §2.2](02-架构主轴-同步到全异步.md) 的 buffer 深度是**两个不同的旋钮**，很多人会把它们混为一谈：

```
buffer 深度   K_buf  -- 控制「样本在队列里等多久」
权重同步频率 K_sync  -- 控制「推理引擎多久才拿到新权重」

真实陈旧度 ~= K_buf + K_sync
```

**两个旋钮都要调，而且它们的成本结构完全不同：**

| 旋钮 | 调大了省什么 | 调大了付什么 | 对应的账 |
|---|---|---|---|
| `K_buf` | **训练卡的空转时间** | 样本在队列里变旧 | [02 章 §2.2](02-架构主轴-同步到全异步.md)：墙钟 760 s → 325 s |
| `K_sync` | **通信带宽 + 中断次数** | 推理引擎用的权重更旧 | §3.2：每次省 1.3 s 传输；§3.5：每次省 ~324 s 排空 |

⚠️ **这里有一条交叉出来的结论，单看任一维度都看不出来**：

> `K_sync` 调大省下来的**不是 1.3 秒的传输，是 324 秒的排空**（§3.5 那张表）。所以——**如果你用的是档 1「永不停」，`K_sync` 这个旋钮几乎不值钱**，因为每次同步本来就不花钱，调大它只换来更陈旧的权重，没有任何收益。**`K_sync` 只在中断模型是档 2/3/4 时才有调的价值。**

**一个具体的数字**，把两个旋钮都拧上：设 `K_buf = 2`、`K_sync = 4`、每个训练步 325 秒（[02 章 §2.2](02-架构主轴-同步到全异步.md) 全异步那一档）：

```
推理引擎手上的权重最多落后   K_sync - 1 = 3 步
样本生成完又在队列里躺了     K_buf      = 2 步
最旧的那个样本，总共落后     3 + 2      = 5 步
换算成时间                   5 x 325 s  = 1,625 s = 27 分钟前的权重
```

⚠️ **「用 27 分钟前的策略生成的样本，去更新现在的策略」——这就是 IS 修正要兜住的距离。** 偏到多少就该警惕，[04 章 §4.6](04-训推一致性.md) 会算出来。
