# 04 · 训推一致性：同一个模型算出两种概率

> **这一篇干什么**：解释 RL 里最隐蔽、也最容易让训练悄悄掉点的一类 bug，以及五家的解法。
> **难度** ★★ · **前置**：[02-架构主轴](02-架构主轴-同步到全异步.md)
> **读法**：本章 §4.2 会用一个**三个数相加**的例子，把「为什么两个引擎算出的概率不一样」落到看得见的位上；§4.3 给一张「哪些差异是数值噪声、哪些是真 bug」的判据表。⚠️ 这一章的全部价值在那张判据表上。
> **本篇 🌐 材料统一出处**：[Keep the Tokens Flowing: Lessons from 16 Open-Source RL Libraries](https://huggingface.co/blog/async-rl-training-landscape)（下称「HF 横评」），访问于 2026-08，以官方仓库现状为准。
> **分工**：**kernel 与数值层的完整展开在 [../大模型算子开发/11-训推一致性算子层.md](../大模型算子开发/11-训推一致性算子层.md)**（一次前向有多少次归约、几个 ULP 怎么被放大成训练崩掉）。本章只讲**系统架构层**：五家自研系统各自怎么解、接口契约要怎么改。算法本身在 [../后训练/](../后训练/README.md)。

**本章关键词**

**logprob**（对数概率）—— 模型吐出某个 token 的概率取自然对数。RL 的 loss 直接吃这个数。
**ratio**（比值）—— `π_new / π_old`，新旧策略在同一个 token 上的概率之比。理想情况下在 1 附近。
**IS**（Importance Sampling，重要性采样）—— 承认样本来自旧策略，在 loss 里乘一个比值把偏差纠回来。
**PCC**（Pearson Correlation Coefficient，皮尔逊相关系数）—— 衡量两组数线性相关的程度，1 是完全一致。这里用来体检「推理算的 logprob」和「训练算的 logprob」对不对得上。
**ULP**（Unit in the Last Place，末位单位）—— 浮点数能表示的最小间隔。「差 1 个 ULP」是浮点误差的最小单位。
**归约**（reduction）—— 把一堆数加成一个数。浮点加法不满足结合律，**加的顺序一变结果就变**，这是本章一切问题的物理根源。
**MLA / MQA / MHA**（Multi-head Latent / Multi-Query / Multi-Head Attention，多头潜在 / 多查询 / 多头注意力）—— 三种注意力形式，见 [../推理框架/推理优化入门/07-注意力变体MQA-GQA-MLA.md](../推理框架/推理优化入门/07-注意力变体MQA-GQA-MLA.md)。
**MoE**（Mixture of Experts，混合专家）—— 每个 token 只激活一小部分参数。
**TITO**（Token-in-Token-out，token 进 token 出）—— 训练直接吃推理吐出的 token id，不经过「解码成文字再重新分词」。
**QAT**（Quantization-Aware Training，量化感知训练）—— 训练时就模拟量化误差。

## 4.1 问题是什么

RL 训练需要知道「模型生成某个 token 的概率是多少」。这个概率被用了两次：

```
推理引擎（vLLM / SGLang）生成答案  -->  顺手记下每个 token 的 logprob   <-- 第一次
                                                 |
                                                 v
训练引擎（Megatron / FSDP）重新前向一遍  -->  又算出一份 logprob        <-- 第二次
                                                 |
                                                 v
                        policy loss 里要用它们的比值 ratio = pi_new / pi_old
```

**理论上这两份应该完全一样**——同一份权重、同一段输入。

**实际上它们不一样。** 而且不一样的地方会被直接塞进 loss 的分母里。

### ⚠️ 先把两件事分开：陈旧度 vs 数值失配

> **这是本章第一个也是最重要的区分。** 「ratio 不等于 1」有两个完全不同的原因，混在一起就永远查不出来：

| | **陈旧度**（off-policy） | **数值失配**（numerical mismatch） |
|---|---|---|
| 原因 | 样本是**旧版权重**生成的 | 两个引擎用**同一份权重**也算不出同一个数 |
| 这是 bug 吗 | 不是，是异步架构的设计代价 | **一半是，一半不是**（§4.2 末尾的判据表） |
| 哪一章管 | [02 章](02-架构主轴-同步到全异步.md)、[03 章](03-权重同步.md) | **本章** |
| 怎么消除 | 回到同步（代价见 [02 §2.2](02-架构主轴-同步到全异步.md)） | 对齐 kernel / 精度 / 接口 |

★ **分离这两者的判据，只有一条，而且很硬**：

> **把配置改成「一批数据只做一次梯度更新 + `logp_old` 由训练引擎自己算」。此时 ratio 必须精确等于 1.0。**
>
> 如果不是，剩下的偏离 **100% 是数值失配**，和 off-policy 没有半点关系。这是把两半分开的唯一可靠手段。完整推导见 [../大模型算子开发/11-训推一致性算子层.md](../大模型算子开发/11-训推一致性算子层.md)。

⚠️ 这件事的恶劣之处在于**它不会报错**。训练照跑，loss 曲线看着也正常，只是模型效果慢慢变差，或者某一步突然梯度爆炸。

### ★ 为什么偏差会被放大：一个能算的例子

PPO / GRPO 这类算法会对 ratio 做**裁剪（clip）**，超出 `[1−ε, 1+ε]` 的 token 梯度被砍掉。取常用的 `ε = 0.2`：

```
clip 上界 ratio = 1.2
ratio = exp(logprob_new - logprob_old)
==> 能容忍的 logprob 偏差 = ln(1.2) = 0.1823
```

★ **记住 0.1823 这个数。它是 clip 机制的全部预算。**

| logprob 偏差 Δ | ratio = exp(Δ) | 落在 clip 区间里吗 | 后果 |
|---|---|---|---|
| 0.001 | 1.0010 | ✅ 远在区间内 | 无害 |
| 0.01 | 1.0101 | ✅ 区间内 | 可忽略 |
| 0.05 | 1.0513 | ✅ 区间内 | 梯度被放大 5.1% |
| 0.10 | 1.1052 | ✅ 勉强在内 | 梯度被放大 10.5% |
| **0.1823** | **1.2000** | ⚠️ **正好在边界** | 再多一点就被砍 |
| 0.20 | 1.2214 | ❌ **越界** | **梯度精确归零** |

⚠️ 读这张表要抓住两点：

1. **权重没变、策略没变、什么都没变**，纯粹因为两个引擎的 kernel 写法不同，就有 token 被判定成「策略变化过大」而丢掉梯度。
2. **0.1823 这个预算是和陈旧度共享的。** 数值失配吃掉 0.1 之后，留给真实策略变化的只剩 0.08 了。[02 章](02-架构主轴-同步到全异步.md) 算出全异步下样本可能落后 5 步（27 分钟前的权重），那 5 步带来的真实策略变化，本来就要占掉相当一部分预算。

> ★ **一句话：训推一致性不是「锦上添花的精度问题」，它在和异步架构抢同一份 clip 预算。** 这就是为什么 [01 章 §1.3](01-格局全景.md) 那张披露地图上，五家报告里有四家专门写了这个问题——异步越激进，这个预算越紧张。

## 4.2 ✅ openPangu 的三分类：五家里唯一给出诊断框架的

五份技术报告里，四家是在陈述「我们做到了训推一致」，**只有 openPangu 把「为什么会不一致」拆成了分类学**。这是本章的骨架。

> ✅ 来源：openPangu-2.0-Pro 报告 §10.3，详见 [业界模型技术报告/openPangu-2.0-Pro.md](../业界模型技术报告/openPangu-2.0-Pro.md)

### ★ 先用三个数相加看懂 B 类，再看分类

B 类是三类里最常见、也最容易被误判成 bug 的一类。它的全部原理就是一句话：**浮点加法不满足结合律。** 用一个能手算的例子走一遍。

**先用十进制的玩具版本，这样可以纯手算。** 假设有一台只能存 **3 位有效数字**的计算器（每做完一次加法就四舍五入到 3 位有效数字），要算 `1.00 + 0.004 + 0.004`：

| 加法顺序 | 第一步 | 存进 3 位有效数字 | 第二步 | 存进 3 位有效数字 | 最终结果 |
|---|---|---|---|---|---|
| **(a+b)+c** | 1.00 + 0.004 = 1.004 | ⚠️ **1.00**（0.004 被舍掉了） | 1.00 + 0.004 = 1.004 | ⚠️ **1.00** | **1.00** |
| **a+(b+c)** | 0.004 + 0.004 = 0.008 | 0.008（精确） | 1.00 + 0.008 = 1.008 | **1.01** | **1.01** |

⟹ **同样三个数、同样的加法，只换了顺序，结果差了 1%。** 第一种顺序里，两个小数各自都「太小，不足以改变 1.00 的第 3 位」，于是被逐个吞掉；第二种顺序里它们先攒在一起，攒成了一个「够大」的数。

**这就是浮点加法不满足结合律的全部原理：`(a+b)+c ≠ a+(b+c)`。** 没有任何一行是 bug——两行都在正确地做 3 位有效数字的加法。

★ **BF16 的处境是一样的，只是位数不同。** BF16 = Brain Float 16，有 **8 位二进制有效位**（7 位存储的尾数 + 1 位隐含位），`log₁₀(2⁸) = 2.4`，**相当于约 2~3 位十进制有效数字**——和上面那台玩具计算器是同一个量级。具体地：

```
BF16 在 1.0 附近，相邻两个可表示的数之间的间隔 = 2^-7 = 1/128 = 0.0078125
==> 任何小于间隔一半（2^-8 = 0.0039）的增量，加到 1.0 上都会被舍掉
```

⚠️ 真用 BF16 验算一遍（取 `a = 1.0`、`b = c = 3 × 2⁻¹⁰ = 0.0029296875`，两个 b 都小于 0.0039 这条线）：

| 加法顺序 | 过程 | 结果 |
|---|---|---|
| **(a+b)+c** | `1.0 + 0.00293` → 舍回 **1.0**；`1.0 + 0.00293` → 再舍回 **1.0** | **1.0** |
| **a+(b+c)** | `b+c = 0.0058594`（精确）；`1.0 + 0.0058594` → 舍到 **1.0078125** | **1.0078125** |

⟹ 差了整整一个 `2⁻⁷`。**✅ 这两行是本文用 IEEE 舍入规则（round-to-nearest-even）实际算过的，不是估的。**

★ **现在把这个例子放大。** 一次前向传播里，每个输出元素都是上千个乘积的和（矩阵乘的 K 维），而**训练引擎和推理引擎会选中不同的加法顺序**：

| | 训练引擎 | 推理引擎（decode 阶段） |
|---|---|---|
| batch 里有多少条 | 很大（几十到几百） | **1**（一次只解一个 token） |
| GEMM kernel 的选择 | M 大，**不需要切 K 轴**就能打满 GPU | M=1，**必须切 K 轴**才填得满 |
| ⟹ 加法顺序 | 一条长链，顺序加 | **切成多段并行加，再把段和相加** |
| ⟹ 结果 | 上表第 1 行 | 上表第 3 行 |

⚠️ **这不是谁实现错了，是两边各自选了对自己最快的 kernel。** 这就是 B 类的全貌。为什么 M=1 必须切 K，见 [../大模型算子开发/03-GEMM深度剖析.md](../大模型算子开发/03-GEMM深度剖析.md)；decode 阶段为什么 M=1，见 [../推理框架/推理优化入门/03-Prefill与Decode两阶段.md](../推理框架/推理优化入门/03-Prefill与Decode两阶段.md)。

### A 类 · 显式定义失配（数学上就不等价）

训练引擎和推理引擎是两套独立实现的代码库，公式本身就有差别。这类最好查，但也最难改——要改就得改一边的实现。

### B 类 · 计算图重排失配（数学等价，数值发散）

公式一样，但**算的顺序不一样**——就是上面那个三数相加的例子。三个来源：

| 来源 | 具体表现 |
|---|---|
| **① 部署策略** | ✅ MLA 在 decode 走 **Absorptive 模式（等价于 MQA）**、在训练/prefill 走 **Non-Absorptive 模式（MHA）**——同一份权重在两条路径上跑的是**不同的算子形状**<br>✅ MoE 的专家累加：训练侧按 **Expert-ID 升序**，推理侧按 **Top-k 分数降序** |
| **② 并行策略** | 训练和推理偏好不同的并行切法（TP 度不同），切法一变，浮点累加的分段方式就变——就是上表第 3 行那种情况 |
| **③ 融合算子** | kernel 融合会隐式重写计算图（不同 FlashAttention 家族、MoE 的 dispatch/combine kernel、采样算子） |

⚠️ **①那条最值得单独记：MLA 在训练和推理走的根本不是同一条算子路径。** 这不是实现疏忽，是性能优化的必然结果——decode 阶段吸收成 MQA 才快。所以只要用了 MLA，这个失配源就天然存在，**而且基本修不掉**：要两边走同一条路，等于让 decode 每一步都物化整条 KV（直接慢几倍）。正确的应对是承认它，在 §4.6 的 IS 修正层兜底。

⚠️ **②那条里的「MoE 专家累加顺序」很值得记**：训练按专家编号升序加，推理按分数降序加——**同样 8 个专家的输出，加的顺序完全不同**，就是上面那张表第 1 行 vs 第 3 行。这一条倒是**能修**：把两边的累加顺序统一就行，代价接近零。

### C 类 · 硬件调度非确定性（同一次运行到下一次都会变）

最底层、也最没法从框架层面解决的一类。✅ openPangu 举的是昇腾 NPU 的例子——按输入 shape 自动选 tiling 策略：

- **SplitK**：把矩阵乘的 K 轴累加拆到多个计算核上，累加顺序不固定
- **K 轴 swizzling**：交错访存提升带宽，同样改变顺序
- **AtomicAdd**：多核异步收集结果，**核到达的顺序是随机的**
- AllReduce 的 Ring / Tree 拓扑算法选择进一步放大发散

⚠️ C 类的特点是：**你连「复现问题」都做不到**，因为跑两次结果就不同。

⚠️ **B 类和 C 类的区别必须分清**：B 类是「形状变了 → kernel 选择变了」，是**确定的函数关系**（同样的 batch 每次结果一样）；C 类是「同一个 kernel 内部的到达顺序随机」，**同样的输入每次都可能不同**。⟹ **先消灭 C 类，否则后面所有测量都在噪声里**，连「有没有 B 类问题」都测不出来。

### ★★ 判据表：哪些差异是数值噪声，哪些是真 bug

> **这是全章最该直接拿去用的一段。** 上面讲了「为什么会不一样」，这里讲「不一样到什么程度该报警」。

**四个指标，按「从原因到结果」排**

| # | 指标 | 怎么测 | **正常** | **可疑** | **一定有 bug** |
|---|---|---|---|---|---|
| ① | **逐 token logprob 差的均值** `mean(Δ)` | 同一批样本，推理侧记一份、训练侧重算一份，逐 token 相减 | \|mean(Δ)\| < 1e-3 | 1e-3 ~ 1e-2 | **> 1e-2，或方向系统性偏一侧** |
| ② | **逐 token logprob 差的标准差** `σ(Δ)` | 同上 | σ < 0.01 | 0.01 ~ 0.05 | **> 0.05**（对照 §4.1 那张表：0.05 ÷ 0.1823 = 已经吃掉 clip 预算的 27%） |
| ③ | **train-rollout PCC** | 两份 logprob 向量求皮尔逊相关系数 | **> 0.999** | 0.99 ~ 0.999 | **< 0.99** |
| ④ | **top-k 专家重合度**（仅 MoE） | 同一个 token，训练侧选的专家集合 ∩ 推理侧选的 | > 99% | 95% ~ 99% | **< 95%** |

> ⚠️ 上表的阈值里，**只有 ③ 的 0.99 这条线有一手出处**（✅ openPangu 的 KPop 把 PCC 0.99 当作在线切换掩码策略的判据，见 §4.6）。**①②④ 三行的具体数字是 ⚠️ 本文按 §4.1 的 clip 预算 0.1823 反推的量级，不是任何论文给的阈值。** 用它们判量级可以，别当标准。
>
> ★ **④ 那条 95% 有一处独立佐证**：[大模型算子开发 · 11 训推一致性算子层 §11.9.2](../大模型算子开发/11-训推一致性算子层.md) 从算子侧另走一条路得出同一个指标（top-k 重合度），并在它的排查阶梯里同样把 **< 95%** 当作「该上确定性 kernel」的分界。两边口径独立、落点一致 —— ⚠️ 但那一章的 95% 也没有论文出处，所以这只是**两处互相印证的经验值**，不构成一手依据。
>
> ⚠️ 另外注意两边的 **σ 不是同一个量**：本表的 `σ(Δ)` 是 **logprob 差**的标准差，算子开发那章讲的 `σ > 0.1` 是 **IS 比值**的标准差。小偏差时 `ratio = exp(Δ) ≈ 1 + Δ`，两者数值接近，但量纲不同，**别混着引用**。

**三条「长什么样就是什么病」的判据**

⚠️ 比看绝对数值更有用的是**看形状**：

| 现象 | 是哪一类 | 为什么 | 怎么办 |
|---|---|---|---|
| 同一个引擎、同样输入，**跑两次结果就不同** | **C 类** | 硬件调度非确定性（AtomicAdd、SplitK 顺序随机） | **必须第一个修**，否则后面什么都测不准 |
| 逐层 PCC **平滑下降** | **B 类** | 每层贡献一点归约顺序差异，线性累积 | 对齐 TP 度 / 统一融合 kernel；兜不住就上 IS 修正 |
| 逐层 PCC **在某一层断崖下跌** | **A 类**或 **MoE 路由跳变** | 要么公式真的不同，要么那一层是 MoE 层、专家选择跳了 | 查那一层是不是 MoE；是就上 R3（§4.4） |
| **batch 从 1 改到 32，同一条序列结果变了** | **B 类** | kernel 按形状选，形状变了顺序就变 | batch-invariant kernel（§4.3 DeepSeek 那条） |

> ★ **「平滑下降 vs 断崖」是判读的全部技巧。** 先看曲线形状，再决定用哪个工具。逐层 PCC 曲线怎么测、每一级误差怎么放大，在 [../大模型算子开发/11-训推一致性算子层.md](../大模型算子开发/11-训推一致性算子层.md)。

**⚠️ 一条反直觉的判据：差异「小而系统性」比「大而随机」更危险**

| | 大而随机 | **小而系统性** |
|---|---|---|
| 例子 | C 类的 AtomicAdd 抖动 | B 类：推理侧的 kernel 系统性地把某类值算偏一个方向 |
| `mean(Δ)` | ≈ 0（正负抵消） | **≠ 0，稳定偏一侧** |
| 多步之后 | 像噪声，被平均掉 | **偏差累积，变成一个假的梯度方向** |
| 症状 | reward 曲线抖 | **reward 曲线平滑地不涨** |

⚠️ 所以**指标 ① 的「方向性」比它的绝对值重要**：`mean(Δ) = 0.005` 但稳定为正，比 `mean(Δ) = 0` 而 `σ = 0.02` 更需要查。前者是在往一个固定的错方向推模型。

## 4.3 五家怎么解的

| 模型 | 主要手段 | 层次 | ✅ 出处 |
|---|---|---|---|
| **DeepSeek-V4** | **batch-invariant 与确定性 kernel 库**，目标是训推之间的**逐位可复现（bitwise reproducibility）** | kernel 工程 | 专章 *High-Performance Batch-Invariant and Deterministic Kernel Libraries* |
| **Kimi-K3** | 全程 **MXFP4 QAT**（量化感知训练）——训练时就用推理的精度 | 数值格式 | §5 |
| **GLM-5** | FP8 rollout + **bitwise 量化 kernel**；**TITO** 保证 token 级一致 | 数值格式 + 接口 | §3.6.2、§4.1.2 |
| **openPangu** | **FP16 替代 BF16** + **KPop** 校正 + **R3 路由重放** + 两阶段白盒对齐 | 全栈 | §10.3 |
| **MiniMax** | **CISPO**（算法侧的 IS 修正） | 算法 | §6.2 |

⚠️ 这张表读出来的分层很清楚——同一个问题可以在**四个不同层次**上解。按「从上往下越根治、也越贵」排：

| 层 | 做法 | 谁在用 | 改哪里 | 代价 | 治到什么程度 |
|---|---|---|---|---|---|
| **算法层** | 承认不一致，在 loss 里修正它 | MiniMax(CISPO)、openPangu(KPop) | **只改 loss 函数** | **近乎为零** | 掩盖症状，不治因 |
| **接口层** | 不让 tokenize / detokenize 引入新误差 | GLM(TITO)、OpenRLHF(token-in-token-out) | 改数据通路 | **零**（见 §4.5） | **彻底消灭 A 类里的分词那一支** |
| **数值层** | 让两边用同一种精度 | Kimi(MXFP4 QAT)、GLM(FP8)、Pangu(FP16) | 改训练精度，要重训 | **大**（整个训练流程） | 大幅压缩 B 类 |
| **kernel 层** | 让两边逐位相同 | DeepSeek(batch-invariant kernel) | 重写算子库 | **最大** | **根治 B + C 类** |

⚠️ **大多数团队应该从上往下走**：先把接口层（零代价）做掉，再用算法侧修正兜住，只有当兜不住时才往下沉到数值层和 kernel 层。

> ★ **注意接口层的位置**：它代价为零、而且根治一整类问题，**所以它不是「第二选择」，它是唯一一个无条件该先做的**。§4.5 单独讲它。

### ★ openPangu 的 FP16 是个逆潮流选择

✅ openPangu 用 **FP16 替代 BF16**（配动态 loss scaling 处理梯度下溢）。**这是五家里唯一一个这么做的。**

⚠️ 为什么反潮流？两种格式都是 16 位，差别在于这 16 位怎么分：

| | 指数位 | 尾数位（含隐含位） | 动态范围 | 1.0 附近的间隔 |
|---|---|---|---|---|
| **BF16** | 8 | **8** | 和 FP32 一样大，约 ±3×10³⁸ | 2⁻⁷ = 0.0078 |
| **FP16** | 5 | **11** | 只到约 ±6.5×10⁴ | **2⁻¹⁰ = 0.00098** |

⟹ **FP16 在 1.0 附近的间隔只有 BF16 的 1/8**（`2⁻¹⁰ ÷ 2⁻⁷ = 1/8`），也就是精度高 3 个二进制位。

把这个和 §4.2 的三数相加例子对上：**间隔越小，「太小以至于被吞掉」的增量就越少，两种加法顺序的结果就越接近。** BF16 之所以成为训练默认，是因为它的动态范围大、不容易溢出；而训推一致性关心的恰恰是**精度**不是范围。openPangu 是把「不溢出」的问题交给 loss scaling，换取「更精确」。

⚠️ 这个取舍只有在训推一致性成为首要矛盾时才成立。混合精度训练的完整权衡见 [../训练框架/分布式训练入门/10-混合精度与FP8.md](../训练框架/分布式训练入门/10-混合精度与FP8.md)。

## 4.4 ★★ 一处独立收敛：R3 ↔ Keep Routing

这是本目录里我认为最有价值的一处交叉印证。

### ⚠️ MoE 把连续的数值噪声整流成了离散的跳变

**MoE 模型有一个 dense 模型没有的失配源**：每个 token 走哪几个专家，是由一个路由器（router）决定的。路由器的做法是——给每个专家打一个分，取分数最高的 k 个。

**而「取最高的 k 个」是一个阶跃函数。** 用一个具体例子看它有多脆：

| 专家编号 | 推理侧算出的分数 | 训练侧算出的分数（B 类误差 ~0.001） | 变了吗 |
|---|---|---|---|
| 3 | 0.812 | 0.8124 | — |
| 17 | **0.4031** | 0.4028 | ⚠️ 掉到第 3 名 |
| 21 | **0.4029** | 0.4033 | ⚠️ 升到第 2 名 |
| 8 | 0.251 | 0.2508 | — |

取 top-2：**推理侧选 {3, 17}，训练侧选 {3, 21}。**

⟹ 两个专家的分数只差 **0.0002**，而 B 类的数值误差就有 0.001 量级——**误差比差距还大 5 倍，排名就翻了。** 一旦翻了，这个 token 的输出就不是「差一点」，而是**经过了一个完全不同的全连接层**。

⚠️ **这就是 MoE 的特殊之处**：

| | dense 模型 | **MoE 模型** |
|---|---|---|
| 输入扰动 1e-3 | 输出扰动也在 1e-3 量级 | **要么 1e-3，要么跳变（量级无上界）** |
| 误差怎么传 | 连续、可估、线性累积 | **离散跳变 + 正反馈**（跳变让隐状态偏更多，偏更多又更容易跳） |
| 逐层 PCC 曲线 | 平滑下降 | **在某一层之后断崖下跌** |

★ **这就是 §4.2 末尾那张判据表里「断崖 → 查是不是 MoE 层」的物理原因。** 数值层的完整分析见 [../大模型算子开发/11-训推一致性算子层.md](../大模型算子开发/11-训推一致性算子层.md)。

### 两家独立给出了同一个解法

**把推理时的路由选择录下来，训练时重放。**

| | ✅ openPangu | 🌐 DeepSeek |
|---|---|---|
| 名字 | **Rollout Routing Replay（R3）** | **Keep Routing** / **Keep Sampling Mask** |
| 核心 | 推理时记录每个 token 的专家选择，训练时强制用同一套 | 同 |
| 平台 | 昇腾 NPU | 英伟达 GPU |

✅ openPangu 在基础 R3 之上做了**四点增强**，每一点都对应一个真实踩过的坑：

| 增强 | 解决的问题 |
|---|---|
| **流式传输路由** | 通过 OpenAI 兼容的流式 API 增量推送路由记录，把带宽需求摊到整个生成时间线上，而不是最后一次性传 |
| **元数据/数据分离** | 只把元数据放进 DataProto，**路由记录走 HCCL**，避开 Ray 的瓶颈和序列长度 padding |
| **Masked R3** ⚠️ | 观察到隐状态随 MoE 层加深、序列逐 token 推进而**累积发散**，此时强制全量重放会**严重扭曲 logits、PCC 骤降、可能梯度爆炸**。解法：自适应阈值——只有训练侧提出的专家选择与推理侧记录的**重合度超过阈值**时，才对该 token 重放 |
| **Cached R3** | agentic RL 多轮推理时，已解码的 token 在后续轮次会被**重新 prefill**，而 prefill 可能给出与当初生成时**不同的路由**。解法：持久化每个 token 首次生成时的路由，训练时重放缓存值 |

⚠️ **Masked R3 这一条最反直觉，也最有信息量**：全量重放不是「越多越好」。强行让训练侧走推理侧的路由，在隐状态已经发散的深层，反而是在**用错误的专家算错误的输入**，比不重放更糟。所以要设阈值——只在两边本来就接近的地方对齐。

★ **这是「一致性」和「正确性」的一次直接冲突，而且它和 §4.6 的 KPop 规则是同一个道理**：修正的强度要跟着实测的一致性程度走，不能设一个固定值。

### ⚠️ 这件事的真正含义：接口契约要变了

推理引擎交给训练引擎的东西，长期以来就是三元组：

```
(token_ids, logprobs, finish_reason)
```

R3 / Keep Routing 意味着这个契约必须扩展：

```
(token_ids, logprobs, finish_reason, routing_records, sampling_mask, ...)
```

⚠️ **这不只是「多传一个字段」，是回传带宽翻倍。** 粗略估一下量级：

```
原契约：每个 token 1 个 token_id (4 B) + 1 个 logprob (4 B) = 8 B
加路由：每个 token 每个 MoE 层要记 top-k 个专家编号
        设 58 个 MoE 层 x top-8 x 1 B = 464 B/token
==> ⚠️ 回传量增加约 58 倍（本文量级估算，不是实测）
```

⚠️ 这就是为什么 openPangu 必须做「流式传输」和「路由记录走 HCCL 而非 Ray」——⚠️ 本文推断：**原契约那 8 字节/token 塞在 Ray 的对象传递里完全无感，几百字节/token 就不行了。** 这也呼应 [03 章 §3.6](03-权重同步.md) 那条观察：推理侧要回传的东西正在变多，这条通路的带宽预算要重新算。

🌐 HF 那篇横评把这件事称为「**a breaking change everywhere**」（一处到处都要改的破坏性变更）——所有推理引擎要吐出路由，所有传输层要传路由，所有训练引擎要吃路由。

⚠️ 我的判断：**这是未来一到两年 RL 框架最确定的演进方向之一。** 两家不同架构（昇腾 NPU / 英伟达 GPU）、不同团队、不同模型的实验室独立收敛到同一个方案，说明这不是某家的特殊需求，而是 MoE + 异步 RL 组合下的结构性问题。

## 4.5 接口层：TITO

✅ GLM-5 §4.1.2 给了一个定义清楚的对比：

> *"**token-in-token-out (TITO)** means the training pipeline consumes the exact tokenization and decoded-token stream produced by the inference engine"*
> （TITO 指训练管线直接消费推理引擎产出的那份 token 流，不做任何重新分词。）

对立面是 **Text-in-Text-out**：推理引擎把 token 解码成文字 → 传给训练侧 → 训练侧重新分词。

### ⚠️ 用一个具体例子看它怎么坏事

问题在于 **`tokenize(detokenize(x)) ≠ x` 不总是成立**。走一遍：

| 步骤 | 内容 |
|---|---|
| ① 推理引擎生成 | token id 序列 `[..., 15339, 11, 1917, ...]`，共 **100** 个 token，每个都有自己的 logprob |
| ② 解码成文字 | `"hello, world"`（中间某处有两个连续空格，或一个被切成两半的中文字符） |
| ③ 传给训练侧 | 字符串 |
| ④ 训练侧重新分词 | ⚠️ 两个连续空格被合并成一个 token、或多字节字符的两半被重新拼成一个 token ⟹ 得到 **98** 个 token |
| ⑤ 算 loss | ❌ **100 个 logprob 对不上 98 个 token。全错位。** |

⚠️ 注意第 ⑤ 步的后果**不是「有几个 token 的概率不准」，是「从错位那一刻起，后面每一个 token 的 logprob 都配到了错的 token 上」**。这在 §4.2 的三分类里属于 **A 类**（显式定义失配），而且是 A 类里最恶劣的一种——因为它不产生「一点小误差」，它产生**完全无意义的 loss**。

常见的触发点：多字节字符（中文、emoji）被切在中间、特殊 token 的边界、连续空格的合并、行尾空白被 strip。

✅ GLM-5 的判断很硬：

> *"We find token-in-token-out is **critical** for asynchronous RL training."*

✅ 这不是 GLM 一家的观点。OpenRLHF 把 TITO 直接做成了架构基石——它的 README 把 `AgentExecutorBase` 标注为 *"(Token-in-Token-out Core)"*，并在设计原则表里写明：

| 原则 | 描述 | 收益 |
|---|---|---|
| **Token-in-Token-out** | 所有采样都产出 token 级轨迹 | **零文本级失配** |

⚠️ 这是本章里**最便宜的一条建议**：TITO 不需要改 kernel、不需要改精度、不需要改算法，只需要在接口上别做多余的解码-再编码。**如果你的 RL 管线还在传文本，先把这个改了。** 对照 §4.3 那张分层表——它是唯一一个「代价为零、却能根治一整类问题」的位置。

## 4.6 算法层：IS 修正家族

如果前面几层都兜不住，最后一道防线是在 loss 里做**重要性采样（Importance Sampling, IS）修正**——承认 `π_推理 ≠ π_训练`，然后乘一个比值把偏差纠回来。

### ★ IS 修正到底在干什么：一个能算的例子

IS 的数学形式只有一行：

```
用旧策略采的样本，估计新策略的梯度：
  E_{x ~ pi_new}[ f(x) ]  =  E_{x ~ pi_old}[ (pi_new(x) / pi_old(x)) * f(x) ]
                                              \____________________/
                                                   IS 比值 w
```

**直觉**：某个 token 在新策略下出现概率是旧策略的 2 倍，那用旧策略采到它时，就把它的贡献乘 2。

⚠️ **问题在于 `w` 的方差。** 用一个序列级的例子看它怎么爆炸——设一条 100 个 token 的轨迹，每个 token 的 logprob 偏差都是 Δ（同向）：

| 每 token 偏差 Δ | 单 token 的 w = exp(Δ) | **整条序列的 w = exp(100Δ)** | 后果 |
|---|---|---|---|
| 0.001 | 1.0010 | exp(0.1) = **1.11** | 可用 |
| 0.005 | 1.0050 | exp(0.5) = **1.65** | 开始偏 |
| 0.01 | 1.0101 | exp(1.0) = **2.72** | ⚠️ 这条样本的权重是别人的 2.7 倍 |
| **0.05** | 1.0513 | exp(5.0) = **148** | ❌ **一条样本吃掉整个 batch 的梯度** |
| 0.1 | 1.1052 | exp(10) = **22,026** | ❌ 彻底爆炸 |

⟹ **序列级 IS 比值是逐 token 比值的连乘，偏差在指数上累积。** 这就是 §4.2 末尾判据表里 `σ(Δ) > 0.05` 被判为「一定有 bug」的理由——到这个量级，IS 修正自己先崩了。

★ **这解释了整个 IS 家族为什么全都叫「截断」「裁剪」「掩码」**：它们本质上都是在给这个指数爆炸设一个闸。

🌐 常见的几个变体：

| 名称 | 全称 | 一句话 | 闸设在哪 |
|---|---|---|---|
| **TIS** | Truncated Importance Sampling（截断重要性采样） | 给 IS 比值设上限 | `w = min(w, C)` |
| **OPSM** | Off-Policy Sampling Mask（离策略采样掩码） | 用 mask 屏蔽掉偏差过大的 token | 超阈值的 token 直接不参与 |
| **TOPR** | Truncated/Tapered Off-Policy REINFORCE | 截断式的离策略 REINFORCE | 比值两端都收 |
| **CISPO** | Clipped Importance Sampling Policy Optimization | 裁剪**重要性权重本身**而不是裁剪比值，MiniMax 用的就是这个 | 裁 `w`，但梯度不归零 |
| **KPop** | （openPangu 自研） | 替代 IcePop 和常规拒绝采样的主校正机制 | 自适应 |

⚠️ **CISPO 和 TIS 的区别值得单独记**：PPO 的 clip 把越界 token 的**梯度精确归零**（§4.1 那张表的最后一行），而被 clip 掉的恰恰是偏差最大、也往往最有信息量的 token。CISPO 裁的是权重本身，**token 还在、梯度还在，只是权重被压住了**。算法细节见 [../后训练/](../后训练/README.md)，不在本目录重写。

### ✅ KPop 的 shadow 超参机制：修正强度该跟着实测走

✅ **KPop 有个值得单独记的设计——shadow 超参机制**：训练初期并行评估多个候选 `φ`，先估计它们的 mask 行为再定值。经验规则是：

| 实测 train-rollout PCC | 该怎么做 |
|---|---|
| **< 0.99** | 用**更严**的 mask（多屏蔽一些 token） |
| **> 0.99** | 用**更松**的 `φ`，以保留探索能力 |

⚠️ 这条经验规则本身就是本章的一个总结：**当训推已经足够一致（PCC > 0.99）时，过度修正反而有害**，因为它会压掉本该保留的探索。修正的强度应该跟着实测的一致性程度走，而不是设一个固定值。

★ **注意这和 §4.4 的 Masked R3 是同一条原则的两次出现**：

| | Masked R3 | KPop shadow 超参 |
|---|---|---|
| 在哪一层 | MoE 路由 | loss 函数 |
| 固定做法会怎样 | 全量重放 → 在发散的深层用错专家算错输入 | 固定强修正 → 压掉探索 |
| 自适应判据 | 专家重合度超阈值才重放 | **PCC 跨过 0.99 才换档** |

⟹ **「修正要自适应、不要一刀切」在两个完全不同的层次上各被独立发现了一次。** ⚠️ 这是本文的归纳，不是任一报告的结论；但两条证据来自同一份 openPangu 报告的不同小节，方向一致。

### ⚠️ 什么时候 IS 修正会失效

| 情形 | 为什么失效 | 征兆 |
|---|---|---|
| **数值失配太大**（`σ(Δ) > 0.05`） | 序列级 w 爆炸到 10² 量级，一条样本主导整个 batch | 梯度范数突然尖峰 |
| **陈旧度太大**（样本落后很多步） | `π_new` 和 `π_old` 的支撑集都快不重叠了，比值要么趋 0 要么趋无穷 | 有效样本数骤降 |
| **MoE 路由跳变** | `π_old` 这个「分母」本身就不对应任何一个真实模型 | PCC 断崖，IS 修正修的是个假的分母 |
| **档 1「永不停」的层间混合** | 见 [03 章 §3.5](03-权重同步.md)：behavior policy 不对应任何真实存在过的模型 | 同上 |

> ★ **最后两行是同一个病**：IS 修正的前提是「分母 `π_old` 是一个真实存在过的策略」。MoE 路由跳变和逐参数流式广播都破坏了这个前提。⚠️ 这是本文的推断，但它解释了为什么 PipelineRL 必须自己做 KL 实验来证明「混合策略 + 陈旧 KV」在实践中可接受——**理论上它是没有保证的。**

## 4.7 本章小结

### 两张能直接拿去用的表

**① 判据（完整版在 §4.2 末尾）**

| 指标 | 正常 | 一定有 bug |
|---|---|---|
| `mean(Δ)` | < 1e-3 | > 1e-2，或方向系统性偏一侧 |
| `σ(Δ)` | < 0.01 | **> 0.05**（序列级 IS 比值会爆到 148） |
| train-rollout PCC | > 0.999 | **< 0.99**（✅ 唯一有一手出处的阈值） |
| MoE top-k 专家重合度 | > 99% | < 95% |

**② 该按什么顺序修**

| 顺序 | 做什么 | 代价 | 治哪一类 |
|---|---|---|---|
| **第 1 步** | 先消灭 **C 类**（关掉硬件非确定性） | 性能略降 | C |
| **第 2 步** | **TITO**——别再传文本 | **零** | A 类里的分词那一支 |
| **第 3 步** | 对齐 MoE 专家累加顺序、对齐 TP 度 | 低 | B 类的一部分 |
| **第 4 步** | **IS 修正**兜底（CISPO / TIS / KPop） | 低（只改 loss） | 掩盖症状，不治因 |
| **第 5 步** | MoE 且重合度仍 < 95% → **R3 路由重放** | 中（要改接口契约） | MoE 路由跳变 |
| **第 6 步** | 还不行 → 下沉到数值层（FP16 / FP8 QAT）或 kernel 层（batch-invariant） | **大** | B + C 类根治 |

### 结论清单

| 结论 | 分级 |
|---|---|
| ⚠️ 「ratio ≠ 1」有两个来源：**陈旧度**和**数值失配**，必须先分开 | ⚠️ 关键区分 |
| ★ 分开的判据：一批数据只更新一次 + `logp_old` 自己算 ⟹ ratio 必须精确等于 1 | ⚠️ 判据 |
| `ε = 0.2` 时 clip 的全部预算是 `ln(1.2) = 0.1823`，数值失配和真实策略变化**共享**这份预算 | ⚠️ 本文推算 |
| 浮点加法不满足结合律：✅ 本文实算 BF16 下 `(a+b)+c = 1.0` 而 `a+(b+c) = 1.0078125`，差 2⁻⁷ | ✅ 实算 |
| 训练 batch 大不切 K、推理 decode M=1 必须切 K ⟹ 两边落在不同的加法顺序上 | ⚠️ 归纳 |
| 训推不一致不会报错，只会让模型悄悄变差或突然爆炸 | ⚠️ |
| openPangu 的三分类（A 定义失配 / B 计算图重排 / C 硬件非确定性）是唯一的诊断框架 | ✅ §10.3 |
| ⚠️ B 类 vs C 类：B 是确定的函数关系，C 是跑两次都不同 ⟹ **先消灭 C** | ⚠️ 归纳 |
| MLA 在 decode 走 MQA、训练走 MHA，是结构性失配源，用了 MLA 就有，**且基本修不掉** | ✅ + ⚠️ |
| MoE 专家累加顺序（训练按 ID 升序 / 推理按分数降序）**能修，代价接近零** | ✅ + ⚠️ |
| ⚠️ 「小而系统性」的差异比「大而随机」更危险——前者会累积成一个假梯度方向 | ⚠️ 归纳 |
| 解法分四层：算法 / 接口 / 数值 / kernel，越往下越根治越贵 | ⚠️ 归纳 |
| openPangu 用 FP16 替代 BF16：FP16 尾数 11 位 vs BF16 的 8 位，**1.0 附近间隔小 8 倍** | ✅ + ⚠️ 推算 |
| MoE 把连续噪声**整流成离散跳变**：两个专家分数差 0.0002 而误差有 0.001 ⟹ 排名翻转 | ⚠️ 本文构造的例子 |
| openPangu R3 与 DeepSeek Keep Routing 独立收敛到同一方案（跨 NPU / GPU 两个平台） | ✅ + 🌐 |
| Masked R3：全量路由重放反而有害，要设重合度阈值 | ✅ |
| 接口契约要从三元组扩到含 routing 与 mask；⚠️ 回传量粗估增加约 58 倍 | 🌐 + ⚠️ 量级估算 |
| TITO 是最便宜的一条改进：代价为零且根治一整类 A 类问题 | ✅ 双方 + ⚠️ |
| 序列级 IS 比值是逐 token 的连乘：`σ(Δ) = 0.05` 时 100 token 的 w 爆到 **148** | ⚠️ 本文推算 |
| KPop 的 shadow 超参：PCC > 0.99 就该放松修正 | ✅ |
| ⚠️ Masked R3 与 KPop 是同一条原则（修正要自适应）在两个层次上的独立出现 | ⚠️ 归纳 |
| ⚠️ IS 修正的前提是分母 `π_old` 对应一个真实存在过的策略；MoE 跳变和层间混合破坏了这个前提 | ⚠️ 推断 |
| veRL 注册了 12 个 policy loss，含 `gspo`(1545) 与 `cispo`(2046) | ✅ 实测 |
