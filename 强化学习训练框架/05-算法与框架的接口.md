## 5.1 去掉 critic 这笔账，两边都要记

RL 后训练最大的一次算法变迁，是从 PPO 走到 GRPO 这一类**去 critic** 的算法。

> **术语**：PPO = Proximal Policy Optimization（近端策略优化），RL 的基线算法。critic（价值网络）是一个和主模型同规模的辅助模型，负责预测「当前状态未来能拿多少分」。GRPO = Group Relative Policy Optimization（分组相对策略优化），同一道题生成 G 个答案，用组内的平均分当基线，从而**不需要 critic**。

### ✅ 收益侧：省掉 16Ψ 显存

[14 章](../训练框架/分布式训练入门/14-RL训练框架.md) 已经把这笔账算过了（Ψ = 参数量）：

```
PPO 的四个模型：
  actor     16 Ψ 字节（权重 + 梯度 + 优化器状态，全套）
  critic    16 Ψ 字节（全套）
  reference  2 Ψ 字节（只要 BF16 权重）
  reward     2 Ψ 字节
  ──────────────────────────────
  合计     ~36 Ψ 字节 ← 是预训练（16Ψ）的 2.25 倍

去掉 critic：36Ψ → 20Ψ，省掉整整 16Ψ，将近一半
```

### ⚠️ 代价侧：这笔账记在 rollout 上

省下来的显存不是白来的。**GRPO 需要同一道题生成 G 个答案才能算组内基线**，G 通常取 8~32。

```
PPO   ：64 道题 × 1 个答案  =    64 个 rollout
GRPO  ：64 道题 × G=16     = 1,024 个 rollout    ← 生成量 ×16
```

而 [02 章](02-架构主轴-同步到全异步.md) 已经说过，生成占了 RL 的 ~80% 时间。**把生成量乘以 16，等于把整个系统的瓶颈往生成侧又推了一大步。**

⚠️ 于是形成一条完整的因果链，这是本章最重要的一条：

```
去 critic（省显存）
   ↓
生成量 ×G（G=8~32）
   ↓
生成成为压倒性瓶颈
   ↓
必须上异步架构（否则训练卡全程空转）
   ↓
样本变陈旧
   ↓
需要 IS 修正 + 陈旧度管理
   ↓
需要更频繁/更快的权重同步
```

**一个「省显存」的算法改动，最终倒逼出了整套异步基建。** 这就是「算法倒逼框架」的最典型例子——你不能只看论文里那个「省掉一个模型」的结论。

## 5.2 ✅ veRL 的注册表：算法多样性有多少

框架侧要支撑多少种算法？veRL 给了一个可以直接数的答案。

### 优势估计器（advantage estimator）：14 种

✅ 本地实测，`verl/trainer/ppo/core_algos.py:88` 起的 `class AdvantageEstimator(str, Enum)`，L97–110 共 **14 个**：

```python
GAE = "gae"                                    # PPO 默认，需要 critic
GRPO = "grpo"
REINFORCE_PLUS_PLUS = "reinforce_plus_plus"
REINFORCE_PLUS_PLUS_BASELINE = "reinforce_plus_plus_baseline"
REMAX = "remax"                                # 用贪心解码分数当基线
RLOO = "rloo"                                  # 留一法
OPO = "opo"
GRPO_PASSK = "grpo_passk"
GPG = "gpg"
RLOO_VECTORIZED = "rloo_vectorized"            # 向量化实现
GRPO_VECTORIZED = "grpo_vectorized"
OPTIMAL_TOKEN_BASELINE = "optimal_token_baseline"
TIR_OPTIMAL_TOKEN_BASELINE = "tir_optimal_token_baseline"
GDPO = "gdpo"
```

紧跟着是 `ADV_ESTIMATOR_REGISTRY: dict[str, Any] = {}`（L113）和 `def register_adv_est(...)`（L116）——**注册表模式**。

### 策略损失（policy loss）：12 种

✅ 同一文件里的 12 个 `@register_policy_loss`（行号见 [04 章 §4.6](04-训推一致性.md) 的表）：
`vanilla` · `dppo_tv` · `dppo_kl` · `gspo` · `sapo` · `gpg` · `clip_cov` · `kl_cov` · `geo_mean` · `dro` · `cispo` · `bypass_mode`

⚠️ **14 × 12 的注册表说明了一件事：算法层已经被框架彻底「插件化」了。**
加一个新算法，只需要写一个函数、挂一个装饰器——不需要碰 rollout、不需要碰权重同步、不需要碰分布式。

### ✅ OpenRLHF 把这条原则写成了设计声明

OpenRLHF 的 README 里有一条明确的设计原则（✅ 原文）：

| 原则 | 描述 | 收益 |
|---|---|---|
| **Algorithm-Agnostic** | *"RL algorithms (PPO, REINFORCE++, etc.) are **decoupled from agent executors**"* | 任何算法配任何执行模式 |

并且它把「执行模式」和「RL 算法」明确标为**正交**（✅ 原文小标题：*"Two Execution Modes (**Orthogonal to RL Algorithms**)"*）：

```
        执行模式 →     Single-Turn        Multi-Turn
  算法 ↓
  PPO                    ✓                  ✓
  REINFORCE++            ✓                  ✓
  GRPO                   ✓                  ✓
  RLOO                   ✓                  ✓
  Dr. GRPO               ✓                  ✓
```

⚠️ 这个二维表是 RL 框架设计的一个成熟标志。**早期框架把「多轮」和「某个算法」耦在一起**（比如「我们的多轮实现只支持 GRPO」），成熟的框架会把它们拆成两个正交维度。选型时可以直接拿这条当检查项。

## 5.4 IS 修正为什么属于「算法与框架的接口」

[04 章 §4.6](04-训推一致性.md) 讲了 IS（Importance Sampling，重要性采样）修正家族。但这里要补一个视角：**IS 修正不是纯算法，它对框架有硬性要求。**

要在 loss 里算 `π_new(t) / π_old(t)`，框架必须提供：

| 需求 | 框架侧要做什么 |
|---|---|
| `π_old` 的值 | 推理引擎必须**吐出 logprob**，而且是训练侧信得过的那一份 |
| 逐 token 对齐 | 两份 logprob 要能一一对上 → 必须 **TITO**（见 [04 章 §4.5](04-训推一致性.md)） |
| 样本的版本号 | 要知道这个样本落后几步 → 需要**逐样本打版本标签** |
| MoE 的路由 | 路由不同则 logprob 不可比 → 需要 **R3 / Keep Routing**（见 [04 章 §4.4](04-训推一致性.md)） |

⚠️ 所以「换个 loss 函数」这件事，在 dense 小模型上确实只是改一行；**在 MoE + 异步的场景下，它牵动整条数据通路的契约**。这也是 [04 章](04-训推一致性.md) 那句「接口契约要扩展」的另一个角度的印证。

## 5.5 ⚠️ 一个容易踩空的坑：非对称过滤让存活样本更陈旧

这条值得单列，因为它同时属于算法和框架，两边都容易漏。

GRPO 这类算法通常配一个**动态过滤**：把组内**全对**或**全错**的题丢掉——因为组内没有区分度，优势全是 0，梯度也是 0，算了白算。

问题是：

```
简单题  → 模型基本全对 → 被过滤掉
        → 而且答案短，生成得快

难题    → 组内有对有错 → 保留下来 ★
        → 但答案长（要推理），生成得慢，完成得最晚
```

**结果：真正贡献梯度的那些样本，系统性地比批次平均更陈旧。**

⚠️ 而 batch 级的陈旧度门控**看不见这个偏差**——整批的平均陈旧度可能很健康，但存活下来的那部分全是最旧的。

🌐 HF 横评据此认为：**逐样本打版本号是必需的**，只在 batch 级别管陈旧度是不够的。

⚠️ 我的补充：这条还有一个推论——**过滤越激进，陈旧度偏差越大**。如果你同时开了「激进的动态过滤」和「宽松的 batch 级陈旧度上限」，实际训练用的样本可能比你以为的旧得多。这两个旋钮要一起调。

## 5.6 下一波会倒逼框架改什么

🌐 HF 横评列了几个正在到来的压力，这里按「对框架的要求」重新组织：

| 算法趋势 | 对框架的新要求 |
|---|---|
| **去 critic 成为默认** | 省下的 ~50% 训练显存被 rollout 吃掉 → 权重同步压力更大 |
| **非对称过滤普及** | 逐样本版本标签从「优化」变成「必需」 |
| **过程奖励模型（PRM）** | 奖励不再便宜——PRM 是一个要跑前向的模型 → 奖励计算本身要异步化（✅ 对照 veRL `experimental/reward_loop/` 1,961 行） |
| **多智能体协同进化** | 两个 agent 各自 p90 = 中位数的 5 倍 → **联合 p90 ≈ 中位数的 25 倍**，长尾指数级恶化 |
| **MoE + EP 支持** | 🌐 目前只有 Megatron 系后端和 PRIME-RL 的 FSDP2+EP 能处理 → 这是**新的分水岭** |

> **术语**：PRM = Process Reward Model（过程奖励模型），不只给最终答案打分，还给中间每一步打分。EP = Expert Parallelism（专家并行），MoE 里把不同专家放到不同卡上。p90 = 第 90 百分位耗时。

⚠️ 「联合 p90 ≈ 25 倍」那条最值得警惕：**长尾在多智能体场景下是相乘的，不是相加的。** 两个 agent 要同时都不慢才行，而它们各自慢的概率是独立的。这意味着 [02 章](02-架构主轴-同步到全异步.md) 讲的那些长尾手段，在多智能体场景下会从「优化项」变成「不做就跑不动」。

### ★ 在策略蒸馏用的是同一套管线

✅ 三家报告（GLM-5、Kimi-K3、openPangu）都提到了 **OPD = On-Policy Distillation（在策略蒸馏）**：学生模型自己生成，老师模型给概率，按 KL 散度拉齐。共享的形式是：

```
Â = sg[ log(π_teacher / π_θ) ]
```

（`sg` = stop-gradient，不回传梯度。）

⚠️ 从框架的角度看，**这就是把 RL 里的「奖励模型」换成了「教师模型」，其他一切照旧**——同样的 rollout、同样的 buffer、同样的权重同步。✅ veRL 的 `experimental/teacher_loop/`（373 行）就是这个：把 `reward_loop` 那套换成教师前向。

**所以做过异步 RL 基建的团队，做 OPD 几乎是零边际成本。** 反过来，只做过 SFT 的团队想上 OPD，要补的是整套 RL 基建。
