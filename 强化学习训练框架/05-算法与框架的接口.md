# 05 · 算法与框架的接口：换个算法，框架要改哪里

> **这一篇干什么**：算法论文只写公式，不写「实现它需要框架配合什么」。这一篇补上这层。
> **难度** ★★ · **前置**：[14 章 §14.2](../训练框架/分布式训练入门/14-RL训练框架.md)（四个模型与显存账）
> **本篇 🌐 材料统一出处**：[Keep the Tokens Flowing: Lessons from 16 Open-Source RL Libraries](https://huggingface.co/blog/async-rl-training-landscape)（下称「HF 横评」），访问于 2026-08，以官方仓库现状为准。
> **⚠️ 边界声明**：PPO / GRPO / DAPO 这些算法**本身**（目标函数长什么样、裁剪为什么那么设计、奖励从哪来）不在这里讲，它们在 [后训练/05-RLVR-可验证奖励.md](../后训练/05-RLVR-可验证奖励.md) 和 [后训练/06-奖励从哪来.md](../后训练/06-奖励从哪来.md)。本章只问一个问题：**这个算法要能跑起来，框架必须额外提供什么？**

**本章关键词**（第一次出现的缩写在这里一次性给全称）

**Ψ**（Psi）—— 本仓库统一用它表示**模型参数量**。7B 模型的 Ψ = 7×10⁹。
**IS**（Importance Sampling，重要性采样）—— 用「旧策略采的样」去估计「新策略的期望」时，必须乘上的那个修正比值。
**logprob**（log-probability，对数概率）—— 模型给某个 token 打的概率取对数。RL 的 loss 几乎全部建立在它之上。
**π_old / old_logprob** —— 生成这批样本时那一版权重给出的 logprob。注意是**那一版**，不是当前这一版。
**GAE**（Generalized Advantage Estimation，广义优势估计）—— PPO 默认的优势估计方法，需要 critic。
**critic**（价值网络）—— 和主模型同规模的辅助模型，预测「当前状态未来能拿多少分」。
**TITO**（Token-In-Token-Out，令牌进令牌出）—— 推理引擎直接收发 token id，中间不经过「文本」这一层，避免二次分词。见 [04 章 §4.5](04-训推一致性.md)。
**MoE**（Mixture of Experts，混合专家）—— 每个 token 只激活一部分「专家」子网络的模型结构。
**EP**（Expert Parallelism，专家并行）—— MoE 里把不同专家放到不同 GPU 上的并行方式。
**PRM**（Process Reward Model，过程奖励模型）—— 不只给最终答案打分，还给中间每一步打分的奖励模型。
**OPD**（On-Policy Distillation，在策略蒸馏）—— 学生模型自己生成，老师模型给概率，两边按 KL 散度拉齐。
**sg**（stop-gradient，停止梯度）—— 让某个量只参与数值计算、不参与反向传播。
**p90** —— 第 90 百分位耗时：100 条轨迹里排第 90 慢的那一条用了多久。

## 本章总表：算法要什么，框架就得给什么

先给一个比喻，这一章的全部内容都在这个比喻里。

**算法是菜谱，框架是厨房。** 换一道菜，有四种可能：**A** 只是换个调料配比，厨房一点不用动；**B** 要求「所有配菜必须同时下锅」，于是备菜流程得重排；**C** 要求「必须用上一锅的汤底」，于是厨房得多一个冰柜专门存汤底，还得给每份汤底贴上日期标签；**D** 要求多一道配菜，于是得多请一个厨师、多买一口锅。算法论文只写菜谱，B 和 C 这两类要求藏在字缝里 —— 这一章就是把它们挖出来。

| # | 算法侧的要求 | 算法为什么需要它 | ⚠️ 框架必须提供什么（硬要求） | 不提供会怎样 | 类别 |
|---|---|---|---|---|---|
| 1 | **优势基线来自 critic**（PPO / GAE） | 要知道「这个状态本来能拿多少分」才能算优势 | 多养一个和主模型同规模的网络：权重 + 梯度 + 优化器状态 + 它自己的并行切分 + 它自己的 checkpoint | 跑不了 PPO | **D** |
| 2 | **组内归一化**（GRPO / RLOO / Dr. GRPO / GRPO-PassK） | 用同一道题的 G 个答案互相当基线，省掉 critic | ⚠️ **调度器必须保证同一个 prompt 的 k 条轨迹落在同一个优化批次里**，并且每条样本带 `group_id`；过滤要**整组丢**，不能丢半组 | 组被打散 → 基线算错 → 优势全错，而且**不报错** | **B** |
| 3 | **token 级 IS 比值** `π_new(t)/π_old(t)`（PPO / CISPO / clip 系） | 样本是旧权重采的，必须修正分布偏移 | ① 拿得到 `old_logprob`（见下方推演）；② 训练与推理的 tokenizer、chat 模板、特殊 token、截断位置**逐字节一致**（TITO） | 比值逐 token 错位 → loss 看着正常、模型就是不涨 | **C** |
| 4 | **序列级 IS 比值**（GSPO） | 把比值做在整条序列上，方差更小 | 需要整条序列的 logprob 之和**与长度**；两侧的 mask（padding、工具返回段、思考段）必须完全一致 | 一个 mask 不一致，整条序列的比值就偏 | **C** |
| 5 | **KL 约束到 reference** | 防止模型跑太远、崩掉风格 | 常驻一份 reference 权重（2Ψ 字节，只要 BF16），或在 rollout 时就把 reference logprob 算好随样本带走 | 要么多占显存，要么多占一次前向 | **A / C** |
| 6 | **动态过滤 / 动态采样**（DAPO 一类：丢掉全对或全错的组） | 没有区分度的组梯度恒为 0，算了白算 | ⚠️ 批大小变成**动态的** —— 框架要么支持变长 batch，要么支持「过采样再截断」，要么支持**边过滤边补采样** | 批大小忽大忽小 → 学习率的有效步长跟着抖 | **B** |
| 7 | **陈旧度门控** | 异步架构下样本有新有旧，太旧的要丢 | **逐样本**（agentic 场景下是逐样本的**版本序列**）打权重版本标签，一路带到训练侧 | 只在 batch 级看平均陈旧度，会看不见 §5.5 那个偏差 | **C** |
| 8 | **过程奖励 PRM** | 稀疏的最终奖励不够，要给中间步骤打分 | 奖励计算本身要变成一个**要跑前向、要排队、要异步**的服务，不再是一个纯 CPU 函数 | 奖励计算卡在关键路径上，GPU 等打分 | **B** |
| 9 | **MoE 模型上做 IS 修正** | 同上第 3、4 条 | 路由必须可复现：R3 / Keep Routing（见 [04 章 §4.4](04-训推一致性.md)）；后端要支持 EP | 同一个 token 走了不同专家 → 两份 logprob 根本不可比 | **C** |
| 10 | **OPD 在策略蒸馏** | 用教师概率代替奖励 | 把「奖励模型」这一槽位换成「教师模型前向」，其余 rollout / buffer / 权重同步**一行不改** | —（这一条恰好是最便宜的） | **A** |

**四个类别的含义**（这是读懂这张表的钥匙）：

**A. 只改一个函数。** loss 换个写法、加个系数 —— 写一个新函数挂个装饰器就完事，框架完全不用动。§5.2 会看到 veRL 把这一类做成了注册表。

**B. 要改调度。** 算法对「哪些样本必须在一起」「一批要多大」提出了要求 —— 得动 rollout 调度器和批次组装逻辑。

**C. 要改数据通路契约。** 算法要求某个**额外的字段**从推理侧一路活着传到训练侧（logprob、版本号、路由、失败原因）—— 这是最贵的一类，因为它贯穿推理引擎、传输层、buffer、训练引擎四段，任何一段把字段丢了，整条链就断了。

**D. 要多养一个模型。** 整张表里只有第 1 行（critic）属于这一类。它不改契约、不改调度，但要多一套权重 + 梯度 + 优化器状态 + 并行切分 + checkpoint 保存恢复。⚠️ 它是四类里**唯一能用钱解决**的 —— 加卡就行。

⚠️ **「为什么换个算法要动框架」的答案就是这一句：论文只写 A，真正的工程量在 B 和 C。** 一个团队看着 GRPO 的公式说「不就是改个 advantage 嘛」，然后花三周在调度器上 —— 卡住他们的是总表第 2 行和第 6 行，而这两行在论文里只占半句话。

### 一个逐步推演：拿到 `old_logprob` 到底有几条路，各要付多少钱

总表第 3 行里那个 `old_logprob` 看起来人畜无害，但它是本章最典型的 C 类要求。设定一个具体场景：

| 设定项 | 取值 |
|---|---|
| 模型 | 7B（Ψ = 7×10⁹） |
| 一个迭代的批次 | 256 道题 × G=8 = **2,048 条轨迹** |
| 单条长度 | prompt 512 token + 回答 1,536 token = **2,048 token** |
| 批次总 token | 2,048 × 2,048 = **4.19×10⁶ token** |
| 训练卡 | 8 × H100，BF16 稠密算力 989 TFLOPS/卡，⚠️ 按 MFU 40% 折算 = **396 TFLOPS/卡** |

三条路：

| 路线 | 怎么做 | 额外显存 | 额外算力 | ⚠️ 风险 |
|---|---|---|---|---|
| **A. 推理引擎顺手吐** | rollout 时推理引擎本来就算了 logits，把采样位置的 logprob 一并返回 | 0 | 0（前向本来就在做） | 这份 logprob 来自**推理内核**，和训练内核算出来的不一样 —— 整个 [04 章](04-训推一致性.md) 都在处理这个口子 |
| **B. 训练侧用旧权重重算** | 多存一份生成时的 BF16 权重，训练前拿它跑一遍前向 | **+2Ψ = 14 GB**（分到 8 卡 = 1.75 GB/卡） | 一次完整前向 | 要管理「旧权重」的生命周期：存哪一版、存几版、异步架构下一批样本可能跨了好几版 |
| **C. 干脆用当前权重算** | 不存旧权重，直接拿当前权重算 `old_logprob` | 0 | 一次完整前向 | ⚠️ **比值恒等于 1，IS 修正直接失效** —— 等于偷偷把 off-policy 算法降级成了 on-policy，而指标上看不出来 |

路线 B 的算力这一项可以算到秒：

| 步 | 算什么 | 算式 | 结果 |
|---|---|---|---|
| ① | 一次前向的 FLOPs（经验公式：每参数每 token 约 2 次乘加） | 2 × 7×10⁹ × 4.19×10⁶ | **5.87×10¹⁶ FLOP = 58.7 PFLOP** |
| ② | 8 卡的有效算力 | 8 × 396×10¹² | 3.17×10¹⁵ FLOP/s |
| ③ | 耗时 | 5.87×10¹⁶ ÷ 3.17×10¹⁵ | **≈ 18.6 秒 / 迭代** |

⚠️ 18.6 秒是「为了拿到一个字段」付出的代价，外加 14 GB 显存。拿它对比路线 A 的 0 秒 0 字节，就明白为什么几乎所有框架的默认选择是 A —— 也就明白了为什么 [04 章](04-训推一致性.md) 那一整章的问题是躲不掉的：**大家都选了便宜的那条路，然后不得不去修它带来的不一致。**

## 5.1 去掉 critic 这笔账，两边都要记

RL 后训练最大的一次算法变迁，是从 PPO 走到 GRPO 这一类**去 critic** 的算法。

> **术语回顾**：PPO = Proximal Policy Optimization（近端策略优化），RL 的基线算法。GRPO = Group Relative Policy Optimization（分组相对策略优化），同一道题生成 G 个答案，用组内的平均分当基线，从而**不需要 critic**。两者的目标函数长什么样见 [后训练/05-RLVR-可验证奖励.md](../后训练/05-RLVR-可验证奖励.md)；这里只看它们对框架的要求差在哪。

### ✅ 收益侧：省掉 16Ψ 显存

[14 章](../训练框架/分布式训练入门/14-RL训练框架.md) 已经把这笔账算过了（Ψ = 参数量，单位是字节）：

| 模型 | 要存什么 | 占用 |
|---|---|---|
| **actor**（被训练的主模型） | BF16 权重 2Ψ + 梯度 2Ψ + FP32 主权重 4Ψ + Adam 一阶动量 4Ψ + 二阶动量 4Ψ | **16 Ψ** |
| **critic**（价值网络） | 同上，全套 | **16 Ψ** |
| **reference**（参考模型） | 只要 BF16 权重，不训练 | **2 Ψ** |
| **reward**（奖励模型） | 只要 BF16 权重，不训练 | **2 Ψ** |
| | **PPO 合计** | **36 Ψ** |
| | 去掉 critic 后（GRPO） | **20 Ψ** |

对照一下预训练：预训练只有 actor 一个模型，16Ψ。所以 **PPO 的显存是预训练的 36÷16 = 2.25 倍**；去掉 critic 之后降到 20÷16 = 1.25 倍。

省下的是 16Ψ，占原来的 16÷36 = **44.4%**（⚠️ 不是「一半」，也不要写成「省了 50%」—— 这一章后面还会再用到这个数）。7B 模型上就是 16 × 7×10⁹ = **112 GB**，正好是一台 8 卡 H100（8×80 = 640 GB）里相当可观的一块。

### ⚠️ 代价侧：这笔账记在 rollout 上，但很容易算错

省下来的显存不是白来的。**GRPO 需要同一道题生成 G 个答案才能算组内基线**，G 通常取 8~32。于是常见的对比是这样写的：

| | 题目数 | 每题答案数 G | rollout 总数 | 相对 PPO |
|---|---|---|---|---|
| PPO | 64 | 1 | 64 | 1× |
| GRPO（G=16） | 64 | 16 | 1,024 | 16× |

⚠️ **这个对比有一个没说出口的前提：它固定了「题目数」。** 如果固定的是「轨迹数」（一个优化批次里有多少条样本参与反向传播），账完全不一样 —— 而实践中更常见的恰恰是后者：

| | 题目数 | G | rollout 总数 | 进入训练的轨迹数 |
|---|---|---|---|---|
| PPO | 1,024 | 1 | 1,024 | 1,024 条 |
| GRPO（G=8） | 128 | 8 | 1,024 | 1,024 条 |

**同样 1,024 条轨迹，生成量一模一样。** 所以「GRPO 把生成量乘以 G」这句话**不是无条件成立的** —— 它只在「题目数不变」这个口径下成立。⚠️ 这是本章要拆掉的第一个含糊说法：**比较两个算法的开销之前，先问「固定的是哪个量」。**

那么同口径（固定轨迹数）下，GRPO 真正比 PPO 多花的生成在哪？有两处，都能算到小数点。

#### (a) 去掉 critic 之后训练侧变便宜了，生成占比被动上升

| 步 | 算什么 | 算式 | 结果 |
|---|---|---|---|
| ① | 约定计算单位：一次前向 = 1，一次反向 ≈ 2（反向大约是前向的两倍） | — | — |
| ② | PPO 训练侧的工作量 | actor(1+2) + critic(1+2) + reference(1) + reward(1) | **8 单位** |
| ③ | GRPO 训练侧的工作量 | actor(1+2) + reference(1) + reward(1) | **5 单位** |
| ④ | 训练侧减少了 | (8−5) ÷ 8 | **37.5%** |
| ⑤ | 设 PPO 的生成 : 训练 = 80 : 20，换算 1 个训练单位 | 20 ÷ 8 | 2.5 时间单位 |
| ⑥ | GRPO 的训练时间 | 5 × 2.5 | 12.5 |
| ⑦ | GRPO 的生成占比 | 80 ÷ (80 + 12.5) | **86.5%** |

⚠️ 从 80% 到 86.5%，是涨了 **6.5 个百分点**，不是「涨了 6.5%」—— 后者会被读成 80% × 1.065 = 85.2%，差着一截。本仓库这类地方一律写「百分点」。（这组数字是 ⚠️ 本文按上述假设推算的，不是任何一家的实测。）

#### (b) 动态过滤要过采样，这一项才是大头

GRPO 这类算法通常配一个动态过滤（§5.5 会细讲）：组内**全对**或**全错**的题丢掉，因为组内没有区分度、优势全是 0、梯度也是 0。被丢掉那些题的生成算力是白花的，必须靠过采样补回来。

| 步 | 算什么 | 算式 | 结果 |
|---|---|---|---|
| ① | ⚠️ 设全对/全错的组占 40%（这个比例随数据难度与模型能力大幅变动，这里只做量级示意） | — | 40% |
| ② | 要填满批次，必须过采样 | 1 ÷ (1 − 0.40) | **1.67 倍** |
| ③ | 生成时间 | 80 × 1.67 | 133.3 |
| ④ | 一个迭代的总时间（训练侧用 (a) 的 12.5） | 133.3 + 12.5 | **145.8** |
| ⑤ | 相对 PPO 的 100 | 145.8 ÷ 100 | **时间变成 1.46 倍** |
| ⑥ | 换成吞吐口径 | 1 ÷ 1.46 | **吞吐降到 68.6%，即减少 31.4%** |
| ⑦ | 生成占比 | 133.3 ÷ 145.8 | **91.4%**（比 PPO 高 **11.4 个百分点**） |

> ⚠️ **口径提醒 —— 本仓库最高频的一类错**：⑤ 的「时间变成 1.46 倍」和 ⑥ 的「吞吐减少 31.4%」说的是同一件事；但「时间增加 46%」和「吞吐减少 46%」**不是**同一件事。换算公式只有一条：`加速倍数 = 1 ÷ (1 − 时间减少比例)`。所以「时间减少 50%」= 加速 **2 倍**；「时间减少 90%」= 加速 **10 倍**；反过来「加速 50%」只对应时间减少 **33.3%**。看到「提速 X%」和「省了 X% 时间」，必须当成两个不同的数。

⚠️ 于是形成一条完整的因果链，这是本章最重要的一条：

```
去 critic（省 44% 显存，36 Psi -> 20 Psi）
   |
   v
训练侧工作量 -37.5%，同时动态过滤逼着过采样 x1.67
   |
   v
生成从占迭代时间 80% 涨到 91%
（分离部署下，训练卡的空闲时间占比同步上升）
   |
   v
同步架构里这 91% 的时间训练卡在白等 -> 必须上异步
   |
   v
样本不再来自最新那一版权重 -- 变陈旧
   |
   v
需要 IS 修正（要 old_logprob，本章总表第 3 行）
需要陈旧度管理（要逐样本版本标签，第 7 行）
   |
   v
需要更频繁、更快的权重同步（见 03 章）
```

**一个「省显存」的算法改动，最终倒逼出了整套异步基建。** 对照本章总表看得更清楚：去 critic 砍掉了第 1 行的要求，却同时点亮了第 2、3、6、7 行 —— **省掉一个 D 类要求，换来四个 B/C 类要求：省掉的那个能用钱解决（加卡），换来的四个只能用人解决（改调度、改契约）。**

## 5.2 ✅ veRL 的注册表：算法多样性有多少

框架侧要支撑多少种算法？veRL 给了一个可以直接数的答案。

### 优势估计器（advantage estimator）：14 种

✅ 本地实测，`verl/trainer/ppo/core_algos.py:88` 起的 `class AdvantageEstimator(str, Enum)`，L97–110 共 **14 个**：

```python
GAE = "gae"                                    # PPO 默认，需要 critic
GRPO = "grpo"
REINFORCE_PLUS_PLUS = "reinforce_plus_plus"
REINFORCE_PLUS_PLUS_BASELINE = "reinforce_plus_plus_baseline"
REMAX = "remax"                                # 用贪心解码分数当基线
RLOO = "rloo"                                  # 留一法
OPO = "opo"
GRPO_PASSK = "grpo_passk"
GPG = "gpg"
RLOO_VECTORIZED = "rloo_vectorized"            # 向量化实现
GRPO_VECTORIZED = "grpo_vectorized"
OPTIMAL_TOKEN_BASELINE = "optimal_token_baseline"
TIR_OPTIMAL_TOKEN_BASELINE = "tir_optimal_token_baseline"
GDPO = "gdpo"
```

紧跟着是 `ADV_ESTIMATOR_REGISTRY: dict[str, Any] = {}`（L113）和 `def register_adv_est(...)`（L116）—— **注册表模式**：新算法写一个函数，挂一个 `@register_adv_est("我的名字")`，框架启动时自动认领。

⚠️ 但请对照本章总表看这 14 个：`GAE` 需要 critic（第 1 行），`GRPO` / `RLOO` / `GRPO_PASSK` / `GRPO_VECTORIZED` / `RLOO_VECTORIZED` 这 5 个都需要**组内采样**（第 2 行）。**注册表只解决了 A 类要求 —— 组怎么采、怎么保证同组不被打散，这件事注册表管不了，它在调度器里。**

### 策略损失（policy loss）：12 种

✅ 同一文件里的 12 个 `@register_policy_loss`（行号见 [04 章 §4.6](04-训推一致性.md) 的表）：

`vanilla` · `dppo_tv` · `dppo_kl` · `gspo` · `sapo` · `gpg` · `clip_cov` · `kl_cov` · `geo_mean` · `dro` · `cispo` · `bypass_mode`

名义上 14 × 12 = 168 种组合（⚠️ 并非每一对都有意义，比如 `bypass_mode` 是个旁路开关而不是真正的损失），而**加一个新的只需要写一个函数、挂一个装饰器** —— 不用碰 rollout、不用碰权重同步、不用碰分布式。这就是「算法层已经被插件化」的含义。
### ✅ OpenRLHF 把「正交」写成了设计声明

OpenRLHF 的 README 里有一条明确的设计原则（✅ 原文）：

| 原则 | 原文 | 收益 |
|---|---|---|
| **Algorithm-Agnostic**（算法无关） | *"RL algorithms (PPO, REINFORCE++, etc.) are **decoupled from agent executors**"* | 任何算法配任何执行模式 |

并且它把「执行模式」和「RL 算法」明确标为**正交**（✅ 原文小标题：*"Two Execution Modes (**Orthogonal to RL Algorithms**)"*）。原文那张打勾表的信息，用 markdown 表格表达是这样：

| RL 算法 | Single-Turn（单轮） | Multi-Turn（多轮） |
|---|---|---|
| PPO | 支持 | 支持 |
| REINFORCE++ | 支持 | 支持 |
| GRPO | 支持 | 支持 |
| RLOO | 支持 | 支持 |
| Dr. GRPO | 支持 | 支持 |

⚠️ 这张「全是支持」的表看着像废话，其实是个**成熟度标志**。早期框架常常把「多轮」和「某个算法」耦在一起 —— 典型症状是文档里写「我们的多轮实现目前只支持 GRPO」。这种耦合意味着两件事被同一段代码管着：算多轮轨迹的优势（算法的事）和驱动工具调用循环（执行器的事）。一旦拆开，这张表就必然全是勾。**选型时可以直接把这张表当检查项：对着候选框架的文档，看它能不能填满。**

## 5.3 ★ 三方交叉验证：CISPO 从技术报告走到注册表

一个算法从「某家报告里提了一嘴」走到「我今天就能用」，这条路径是可以逐条回查的。以 CISPO（Clipped Importance Sampling Policy Optimization，裁剪重要性采样策略优化）为例：

| 环节 | 证据 | 分级 |
|---|---|---|
| **① 某家报告里用了** | MiniMax-M2 论文 §6.2.2：Train Engine 计算 **CISPO** 策略梯度 | ✅ |
| **② 开源框架实现了** | veRL `verl/trainer/ppo/core_algos.py:2046` → `@register_policy_loss("cispo")` | ✅ 本地实测 |
| **③ 生态里有更全的菜单** | ROLL 被 HF 横评点名为 IS 修正手段最全的一家 | 🌐 |

同样可查的还有 GSPO（Group Sequence Policy Optimization，分组序列策略优化）：✅ `core_algos.py:1545` → `@register_policy_loss("gspo")`。

⚠️ 这类核对的价值在于它能区分三种状态，而这三种状态在读论文时长得一模一样：

| 状态 | 你能做什么 | 怎么确认 |
|---|---|---|
| 只在论文里提过 | 自己从头实现 | 搜不到任何开源实现 |

## 5.4 IS 修正为什么属于「算法与框架的接口」

[04 章 §4.6](04-训推一致性.md) 讲了 IS 修正家族本身。这里要补的视角是：**IS 修正不是纯算法，它对框架有硬性要求。** 这正是本章总表第 3、4 行。

要在 loss 里算出 `π_new(t) / π_old(t)` 这个比值，框架必须同时满足四件事 —— 缺任何一件，比值都会悄悄算错：

| 需求 | 框架侧要做什么 | 缺了会怎样 |
|---|---|---|
| `π_old` 的值 | 推理引擎必须**吐出 logprob**，而且是训练侧信得过的那一份 | 退化成 §5.1 的路线 C：比值恒为 1 |
| 逐 token 对齐 | 两份 logprob 要能一一对上 → 必须 **TITO**（见 [04 章 §4.5](04-训推一致性.md)） | 错位一个 token，后面全错 |
| 样本的版本号 | 要知道这个样本落后几步 → **逐样本打版本标签** | 用一个过旧的样本做大幅更新，训练发散 |
| MoE 的路由 | 路由不同则 logprob 不可比 → **R3 / Keep Routing**（见 [04 章 §4.4](04-训推一致性.md)） | 比值里混进了「换了个专家」造成的差异 |

举个最小的例子说明「错位一个 token」有多隐蔽：

```
推理侧吐出的 token 序列：  [你] [好] [，] [世] [界]
训练侧重新分词得到的：     [你好] [，] [世界]

推理侧 5 个 logprob，训练侧 3 个 logprob。
两边长度都对不上，更别说逐位相除。

而代码不会报错 —— 它会用某种对齐规则（截断/补齐）硬凑，
然后给你一个「看起来挺正常」的 loss 曲线。
```

⚠️ 所以「换个 loss 函数」这件事：在 dense 小模型 + 同步训练上确实只是改一行；**在 MoE + 异步的场景下，它牵动从推理引擎到训练引擎的整条数据通路契约。** 这也是 [04 章](04-训推一致性.md) 那句「接口契约要扩展」的另一个角度的印证。

## 5.5 ⚠️ 一个容易踩空的坑：非对称过滤让存活样本更陈旧

这条值得单列，因为它同时属于算法和框架，两边都容易漏。

§5.1(b) 已经提过动态过滤：把组内**全对**或**全错**的题丢掉，因为组内没有区分度、优势全是 0。这个优化本身没问题，问题出在它和「谁跑得快」是相关的：

```
简单题  ->  模型基本全对  ->  被过滤掉
         而且答案短，生成得快，最早完成

难题    ->  组内有对有错  ->  保留下来  <-- 就是这批
         但答案长（要推理），生成得慢，最晚才完成
```

**于是：真正贡献梯度的那些样本，系统性地比批次平均更陈旧。** 这就是「非对称」的含义 —— 过滤不是随机地丢一半，它偏向于丢掉新鲜的那一半。

用一个具体的批次把这件事算出来：

| 步 | 情况 | 数字 |
|---|---|---|
| ① | 一批 512 条轨迹：简单题 256 条、难题 256 条 | 512 |
| ② | 简单题生成完的时刻（早）：对应权重版本 w₅₀ | 陈旧度 = 2 步 |
| ③ | 难题生成完的时刻（晚）：对应权重版本 w₄₄ | 陈旧度 = 8 步 |
| ④ | 全批次的平均陈旧度 | (2×256 + 8×256) ÷ 512 = **5 步** |
| ⑤ | 过滤后：简单题留下 10%（25.6 条），难题留下 90%（230.4 条） | 256 条 |
| ⑥ | **存活样本**的平均陈旧度 | (2×25.6 + 8×230.4) ÷ 256 = **7.4 步** |
| ⑦ | 如果门控设在「平均陈旧度 ≤ 6 步」 | ④ 是 5 步，**门控判定通过** |
| ⑧ | 而真正算梯度的那批 | ⑥ 是 7.4 步，**已经超了** |

⚠️ ⑦⑧ 两行就是这个坑的全貌：**batch 级的陈旧度门控看不见这个偏差。** 整批的平均陈旧度一切健康，但存活下来的那部分全是最旧的。（⚠️ 上表的具体数字是本文为了说明机制构造的，不是实测；成立的只是「⑥ > ④」这个方向性结论。）

🌐 HF 横评据此认为：**逐样本打版本号是必需的**，只在 batch 级别管陈旧度是不够的。✅ 而 GLM-5 的做法更严格一层，见 [06 章 §6.6](06-AgenticRL-环境与沙箱.md)。

⚠️ 本文的一个推论：**过滤越激进，陈旧度偏差越大。** 如果你同时开了「激进的动态过滤」和「宽松的 batch 级陈旧度上限」，实际训练用的样本会比你以为的旧得多。**这两个旋钮必须一起调** —— 把过滤率从 40% 提到 70% 的那次改动，等于偷偷把陈旧度上限也放宽了。

## 5.6 下一波会倒逼框架改什么

🌐 HF 横评列了几个正在到来的压力，这里按「对框架的要求」重新组织，并标回本章总表的行号：

| 算法趋势 | 对框架的新要求 | 总表第几行 |
|---|---|---|
| **去 critic 成为默认** | 省下的 44% 训练显存会被 rollout 吃掉；生成占比升到 90%+ → 权重同步压力更大 | 去掉 D，换来 B/C |
| **非对称过滤普及** | 逐样本版本标签从「优化」变成「必需」 | 7 |
| **过程奖励模型 PRM** | 奖励不再便宜 —— PRM 是一个要跑前向的模型 → 奖励计算本身要异步化（✅ 对照 veRL `experimental/reward_loop/`，1,961 行） | 8 |
| **多智能体协同进化** | 多个 agent 都跑完才算一条轨迹，长尾按智能体数量**成倍**恶化（下面算） | 2 |
| **MoE + EP 支持** | 🌐 截至材料访问时，只有 Megatron 系后端和 PRIME-RL 的 FSDP2+EP 能处理 → 这是**新的分水岭** | 9 |

### ⚠️ 多智能体的长尾到底恶化多少：一个要纠正的说法

本章上一版（以及这类讨论里常见的说法）写的是：「两个 agent 各自 p90 = 中位数的 5 倍 ⟹ 联合 p90 ≈ 中位数的 **25 倍**」。

⚠️ **这个算法不成立：p90 不能相乘。** 百分位数不是期望、不是方差，没有任何运算律允许把两个 p90 乘起来得到联合 p90。方向（多智能体会让长尾恶化）是对的，倍数是错的。正确的做法是先把「重尾」这件事标定成一个分布，再算。

| 步 | 做什么 | 算式 | 结果 |
|---|---|---|---|
| ① | 用帕累托分布刻画重尾：`P(T > t) = (t_min / t)^α` | — | — |
| ② | 中位数 m 满足 `(t_min/m)^α = 0.5`；p90 满足 `(t_min/t₉₀)^α = 0.1` | 两式相除 | `t₉₀/m = 5^(1/α)` |
| ③ | 题设 `t₉₀/m = 5`，反解形状参数 | `5^(1/α) = 5` | **α = 1**（极重的尾） |
| ④ | 此时 `m = 2·t_min` | 代入 ② | — |
| ⑤ | 两个 agent 并行、**都**跑完才算完：`P(max ≤ t) = F(t)²` | 要 `F(t)² = 0.9` | `F(t) = √0.9 = 0.9487` |
| ⑥ | 于是 `P(T > t) = 0.0513`，反解 t | `t = t_min / 0.0513` | `t = 19.49 · t_min` |
| ⑦ | 换算成中位数的倍数 | `19.49 ÷ 2` | **联合 p90 ≈ 9.7 × 中位数** |

**正确答案是 ≈ 9.7 倍，不是 25 倍。** 换个角度：联合 p90 ≈ 单 agent p90 的 **1.95 倍**，差不多就是「翻一番」。

那 25 倍对应什么？也能算出来：`t/m = 25` ⟹ `t = 50·t_min` ⟹ `P(T>t) = 0.02` ⟹ `F = 0.98` ⟹ `F² = 0.9604`。⚠️ **所以「中位数的 25 倍」其实是联合的 p96，不是 p90。** 这两个数差 6 个百分点的分位，在重尾分布下就差出 2.5 倍的时间 —— 这正是重尾最反直觉的地方。

把 agent 数量推广开（同样 α = 1 的标定）：

| 同时要跑完的 agent 数 N | 每个要达到的分位 `0.9^(1/N)` | 联合 p90 ÷ 中位数 |
|---|---|---|
| 1 | 0.9000 | **5.0×** |
| 2 | 0.9487 | **9.7×** |
| 4 | 0.9740 | **19.2×** |
| 8 | 0.9869 | **38.2×** |

⚠️ 规律是**大致线性**（agent 数翻倍，联合 p90 翻倍），不是「指数级」。⚠️ 但请注意这个线性结论依赖 α = 1 这个很极端的标定（α = 1 的帕累托分布连期望都不存在）；如果你的实际分布没那么重尾，p90/中位数就不会是 5，整张表都要重算。**这里真正该记住的不是数字，是方法：先用一个你能观测到的比值（p90 ÷ 中位数）标定分布，再算联合分位数。**

无论 9.7 还是 38，结论方向都一样：[02 章](02-架构主轴-同步到全异步.md) 讲的那些长尾手段（partial rollout、提前截断、落后者替换），在多智能体场景下会从「优化项」变成「不做就跑不动」。

### ★ 在策略蒸馏用的是同一套管线

✅ 三家报告（GLM-5、Kimi-K3、openPangu）都提到了 **OPD = On-Policy Distillation（在策略蒸馏）**：学生模型自己生成，老师模型给概率，按 KL 散度拉齐。共享的形式是：

```
A_hat = sg[ log( pi_teacher / pi_theta ) ]
```

（`sg` = stop-gradient，不回传梯度；`pi_theta` 是学生当前策略。）

⚠️ 从框架的角度看，**这就是把 RL 里的「奖励模型」这一个槽位换成「教师模型」，其他一切照旧** —— 同样的 rollout、同样的 buffer、同样的权重同步、同样的 IS 修正。✅ veRL 的 `experimental/teacher_loop/`（373 行）就是这个：把 `reward_loop` 那套换成教师前向。

对照本章总表，OPD 是第 10 行 —— 也是整张表里**唯一一个 A 类要求**：没有新的调度约束，没有新的数据通路字段。

**所以做过异步 RL 基建的团队，做 OPD 几乎是零边际成本。** 反过来，只做过 SFT（Supervised Fine-Tuning，监督微调）的团队想上 OPD，要补的是整套 RL 基建 —— 因为 OPD 的「学生自己生成」这四个字，已经把 rollout、buffer、权重同步全要上了。OPD 的算法细节见 [后训练/08-蒸馏与合并-OPD.md](../后训练/08-蒸馏与合并-OPD.md)。
