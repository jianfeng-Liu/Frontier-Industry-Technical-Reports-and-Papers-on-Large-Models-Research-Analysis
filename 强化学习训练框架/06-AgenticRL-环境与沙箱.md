**本章关键词**（第一次出现的缩写在这里一次性给全称）

**沙箱**（sandbox）—— 一个受限的执行环境，agent 在里面跑命令、改文件、发网络请求，跑坏了也只坏在里面。
**容器**（container）—— 靠 Linux 内核的 namespace（命名空间）+ cgroup（控制组）做隔离。**和宿主机共用同一个内核**，这是它最大的优点也是最大的弱点。
**microVM**（micro Virtual Machine，微型虚拟机）—— 一台被削到极简的虚拟机：有自己独立的内核，但去掉了传统虚拟机绝大部分设备模拟，所以启动极快。
**Firecracker** —— AWS 开源的 microVM 管理器，Lambda 和 Fargate 的底座，是本章出镜率最高的一个名字。
**KVM**（Kernel-based Virtual Machine，基于内核的虚拟机）—— Linux 内核自带的硬件虚拟化支持，Firecracker 和 QEMU 都架在它上面。
**OOM**（Out Of Memory，内存耗尽）—— 进程申请不到内存时被内核的 OOM killer 直接杀掉。
**快照 / checkpoint**（snapshot）—— 把一个沙箱此刻的完整状态（内存页 + 磁盘 + 寄存器）存下来，之后能原样恢复。
**冷启动**（cold start）—— 从零创建一个沙箱到它能执行第一条命令所需的时间。
**沙箱池化**（pooling）—— 预先开好一批空闲沙箱等着被领走，把冷启动从关键路径上挪开。
**harness / 脚手架** —— 包住模型、把它变成能操作计算机的 agent 的那一层代码（工具定义、循环、上下文管理）。
**ACI**（Agent-Computer Interface，智能体-计算机接口）—— 工具怎么定义、返回怎么裁剪的那套设计，见 [03-工具集与ACI.md](../harness评测框架/agent脚手架/03-工具集与ACI.md)。
**EROFS**（Enhanced Read-Only File System，增强只读文件系统）—— 一种只读镜像格式，支持按需加载，不用等整个镜像下载完。
**CRIU**（Checkpoint/Restore In Userspace，用户态检查点与恢复）—— Linux 上给进程做快照的工具，容器场景下的 checkpoint 多半靠它。
**沙箱·秒**（sandbox-second）—— 本章自造的计量单位：1 个沙箱活 1 秒 = 1 沙箱·秒。和「人·天」是同一种东西，用来把「开多少个」和「开多久」折成一个数。

## 6.1 Agentic RL 和普通 RL 差在哪

普通 RL 的一次 rollout，只有一来一回：

```
题目 --> 模型生成答案 --> 打分
```

Agentic RL 的一次 rollout，中间多了一个会转几十上百圈的环：

```
     题目
      |
      v
 .-->(1) 模型想   : 生成一段推理，末尾吐出一个工具调用
 |    |
 |    v
 |   (2) 环境执行 : 在沙箱里跑这条命令，拿到 stdout / 退出码 / 文件改动
 |    |
 |    v
 |   (3) 结果回填 : 把工具返回拼回上下文，成为下一轮的输入
 |    |
 |    v
 '---(4) 还没做完？回到 (1)   <-- 这个圈要转 30~100 次
      |
      v
     (5) 打分（跑测试 / 比对答案 / 让裁判模型评）
```

举个具体到能想象的例子 —— 一条「修一个 bug」的轨迹长这样：

| 轮次 | 模型做了什么 | 环境返回了什么 | 这一轮的耗时大头 |
|---|---|---|---|
| 1 | `ls -R src/` | 400 行文件列表 | 工具执行 0.3 秒 |
| 2 | 想了 800 token，决定读 `parser.py` | 1,200 行源码 | **模型生成 16 秒** |
| 3 | `grep -n "def tokenize" .` | 3 个匹配 | 工具执行 0.2 秒 |
| 4 | 想了 1,500 token，写了一个补丁 | 文件已改 | **模型生成 30 秒** |
| 5 | `pytest tests/test_parser.py` | 2 failed | **工具执行 45 秒**（跑测试慢） |
| 6~30 | 继续改、继续跑测试 | … | … |
| 收尾 | — | 全部通过 | 判定奖励：再跑一次完整测试 |

⚠️ 从这张表里能直接读出两件事，它们是本章后面所有工程设计的来源：

1. **沙箱绝大部分时间在发呆。** 第 2、4 轮加起来 46 秒，沙箱一条命令都没执行，但它必须活着 —— 因为它装着当前的文件改动、当前的工作目录、当前的进程状态。
2. **工具执行的耗时方差极大。** `grep` 0.2 秒，`pytest` 45 秒，两者差 200 倍。而这种慢是 CPU/IO 负载，**不占 GPU**。

差别不是「多轮」这么简单，而是三件事同时变了：

| | 普通 RL | Agentic RL |
|---|---|---|
| 一条轨迹多长 | 几千 token | ✅ MiniMax：**最长 192K token**；✅ Kimi-K3：**1M 上下文** |
| 谁在生成 | 只有模型 | 模型 + **环境**（环境返回的内容也在轨迹里，但**不该算模型的梯度** —— 这一条是 loss 里的 mask 要处理的） |
| 时间花在哪 | 几乎全在 GPU 解码 | ✅ Kimi-K3：**等模型推理结果的时间可占沙箱生命周期的 98%**；剩下的那一小部分才是工具真正在执行 |

> ⚠️ **这里要澄清一个很容易说反的地方。** 「沙箱 98% 的时间在等模型」和「Agentic RL 的长尾来自工具执行」**不矛盾，但说的是两件事**：
> **从沙箱这一侧看**：它的生命周期里 98% 在空等（等 GPU 把下一步生成出来），只有 ~2% 在真正执行命令。结论是「沙箱资源的浪费在等待」，于是要做 Pause/Resume。
> **从训练这一侧看**：那 2% 的工具执行是**插在 GPU 解码中间**的，GPU 在这段时间里拿不到这条轨迹的下一个 token。工具执行的方差又极大（0.2 秒 vs 45 秒），于是形成长尾。结论是「调度器必须能看见非 GPU 的延迟」。
> ⚠️ 两个「98%」和「2%」是同一组数字的两种读法。**说成「agent 大量时间在等工具执行」就把因果说反了** —— 它大量时间在等**模型**。

⚠️ 第三条是整章的关键：**Agentic RL 里，长尾不再只是「有的答案长」，而是「有的工具跑得慢」。** 而工具执行是 CPU/IO 负载、不占 GPU —— 这意味着一个纯 GPU 视角的调度器根本看不见这部分延迟，它只会看到「这张卡怎么又在 idle」。

## 6.2 ✅ 环境该放在架构的哪一层：GLM 给了明确答案

✅ GLM-5 论文 §4.1.1 的 Multi-Task Rollout Orchestrator（多任务 rollout 编排器）设计：

> *"we standardize trajectories from all agentic tasks into a **unified message-list representation**. This enables joint training of complex agentic frameworks (e.g., Software Engineering task) while also supporting centralized post-processing and logging for heterogeneous workloads. This design **cleanly isolates task-specific logic from the core training loop**, enabling seamless integration with multi-task RL training."*

拆开看：

| 设计 | 意思 | 对小白的翻译 |
|---|---|---|
| 每个任务 = 独立微服务，向中央编排器注册 | 加一个新任务不用改训练代码 | 像往插线板上插一个新电器，不用重新布线 |
| 统一的 message-list 表示 | 不管是搜索、编程还是数学，交给训练侧的格式是同一种 | 所有电器都用同一种插头 |
| 编排器控制每任务的 rollout 配比和生成速度 | 多任务混训时不会某个任务把资源吃光 | 插线板有总闸，一个电器不能把全家跳闸 |
| **task-specific logic 与 core training loop 彻底隔离** | ★ 这是全篇最重要的一条架构原则 | 修电器的人不用懂电网 |

⚠️ 一句话概括这条原则：**环境应该以「数据生成者」的身份接入，而不是以「训练循环的一处修改」的身份接入。** 实际含义是：写一个新环境的人不需要懂分布式训练；改训练循环的人不需要懂任何一个具体环境。两边通过一个固定的 message-list 契约解耦。

✅ 规模上，这个编排器**支撑超过 1,000 路并发 rollout**；✅ 而 GLM-5 为编程任务建了**超过 10,000 个可验证训练场景**（*"over 10,000 verifiable training scenarios"*）。

### ✅ MiniMax 的白盒 / 黑盒二分

MiniMax Forge（论文 §6.2.3）给了另一个角度 —— agent 有两种接法：

| 类型 | 定义 | 框架能看到什么 | 代价 |
|---|---|---|---|
| **白盒 agent** | 暴露自己的上下文管理逻辑：`s_{t+1} = f_CM(concat(s_t, a_t, o_t))` | 框架知道上下文是怎么拼的，可以做前缀复用、精确裁剪 | 你得按框架的格式把 agent 拆开 |
| **黑盒 agent** | 不透明的轨迹生产者，只把补全请求路由给 Gateway | 框架只看到「有个东西在请求补全」 | 前缀复用做不了，缓存命中率低 |

Forge 用同一个 **Gateway Server**（网关服务器）同时接住两种。✅ 报告原文：

> *"This design has been validated across **hundreds of distinct agent scaffolds** and **thousands of tool invocation formats**."*

⚠️ 这句话是 Agentic RL 基建设计的现实依据：**你不可能为每个 agent 脚手架写一套适配。** 唯一可扩展的做法是定义一个足够窄的接口（「给我补全」），让所有脚手架都能塞进来。这和 GLM 的 message-list 是同一个思路的两种实现 —— **窄接口换扩展性**。

## 6.3 ★★ 沙箱：先把账算出来，再看三家怎么做

环境要跑真实代码，就必须隔离。但在比较隔离技术之前，**先把规模和延迟这两笔账算出来** —— 因为答案完全是被这两笔账逼出来的。

### 账一：一个迭代要多少沙箱·秒，要同时开多少个

设一组具体的数字（和 §6.1 那条轨迹对得上）：

| 设定项 | 取值 |
|---|---|
| 一批轨迹数 | **512** |
| 每条轨迹的工具调用步数 | 平均 **30 步** |
| 每步工具执行时间 | 平均 **2 秒** |
| 每个沙箱的内存配额 | **2 GB** |

| 步 | 算什么 | 算式 | 结果 |
|---|---|---|---|
| ① | 一条轨迹的工具执行时间 | 30 × 2 秒 | **60 秒** |
| ② | 一批的工具执行总量 | 512 × 60 秒 | **30,720 沙箱·秒** ≈ 8.5 沙箱·小时 |
| ③ | 如果只开 1 个沙箱串行跑完这一批 | 30,720 秒 | **8.5 小时 / 迭代** —— 完全不可行 |
| ④ | 要把这一批的工具执行压进 10 分钟 | 30,720 ÷ 600 | **至少 52 个沙箱同时在执行命令** |

④ 看起来不大。但 ④ 只数了「正在执行命令」的沙箱 —— 而沙箱在**等模型生成下一步**的时候也必须活着，因为它装着当前的文件改动、工作目录、运行中的进程。于是真正的峰值是这样：

| 步 | 算什么 | 等待占 80%（保守） | 等待占 98%（✅ Kimi 口径） |
|---|---|---|---|
| ⑤ | 一条轨迹的**墙钟**时长 = 工具执行 ÷ (1 − 等待占比) | 60 ÷ 0.20 = **300 秒** | 60 ÷ 0.02 = **3,000 秒** |
| ⑥ | 512 条全并发时，同时活着的沙箱数 | **512** | **512** |
| ⑦ | 其中任一时刻真正在执行命令的 | 512 × 20% ≈ **102** | 512 × 2% ≈ **10** |
| ⑧ | 不做 Pause 的内存占用（2 GB/个） | 512 × 2 GB = **1,024 GB** | 512 × 2 GB = **1,024 GB** |
| ⑨ | 做了 Pause/Resume 之后 | 102 × 2 GB = **204 GB** | 10 × 2 GB = **20 GB** |
| ⑩ | 省了多少 | **80%** | **98%** |

⚠️ **⑧ 和 ⑨ 这两行就是整章的钱账：同样一批 512 条轨迹，不做 Pause 要 1 TB 内存，做了只要 20 GB。** 这就是为什么 §6.3 后面 Kimi 的「Pause 能省 98%」不是一个 nice-to-have，而是**能不能跑起来**的分界线。

再往上推一层，看看前沿规模下这个数字有多可怕：

| 并发沙箱规模 | 不做 Pause 的内存（按 2 GB/个） | 谁在这个量级 |
|---|---|---|
| 512 | 1 TB | 一个中等实验 |
| 1,000+ | 2 TB | ✅ GLM-5 的编排器 |
| 数万 | **数十 TB** | ✅ Kimi AgentENV |
| 数十万 | **数百 TB** | ✅ DeepSeek DSec 单集群 |

⚠️ 到数十万这个量级，内存就是唯一的硬约束 —— 这解释了为什么 DSec 要专门做「缓解重复的 page cache 占用」和「内存回收以支持安全超售」这两件听起来很枯燥的事。**在那个规模上，省内存就是省机器。**

### 账二：启动延迟乘以次数，就是纯浪费

第二笔账决定了「沙箱该活多久」。还是上面那批 512 条轨迹、每条 30 步：

| 启动方式 | 单次耗时 | **每条轨迹开一次**（512 次） | **每一步都重开一次**（15,360 次） |
|---|---|---|---|
| Docker 冷启动（⚠️ 量级估计 2~10 秒，这里取 5 秒） | 5 s | 2,560 沙箱·秒 = 工具执行量的 **8.3%** | 76,800 沙箱·秒 = **250%** |
| Firecracker microVM 冷启动（🌐 官方口径 ~125 ms 级） | 0.125 s | 64 沙箱·秒 = **0.21%** | 1,920 沙箱·秒 = **6.2%** |
| 从快照恢复（✅ Kimi 实测 49 ms） | 0.049 s | 25 沙箱·秒 = **0.08%** | 753 沙箱·秒 = **2.5%** |
| 从预热池里领一个（池化） | ≈ 0 | ≈ 0 | ≈ 0 |

（分母是账一 ② 的 30,720 沙箱·秒。）

⚠️ 这张表里有**三个结论**，每一个都对应一项真实的工程设计：

**结论 1：绝不能每步重开沙箱。** Docker 下「每步重开」的启动开销是工具执行时间的 **2.5 倍** —— 启动比干活还贵。所以一条轨迹必须配一个**长命的、有状态的**沙箱，跨步保留文件改动和工作目录。这也顺带解释了为什么沙箱不能做成无状态函数。

**结论 2：即使一条轨迹只开一次，Docker 的 8.3% 也不便宜。** 而且 5 秒只是均值，冷镜像、拉网络、装依赖都可能把它拖到几十秒，这个长尾会直接变成 rollout 的长尾。**这就是沙箱池化的全部理由**：把启动从关键路径上挪到后台，用「领一个」代替「开一个」。

**结论 3：microVM 的 125 ms 比 Docker 的 5 秒快约 40 倍。** 这是选 microVM 而不是 Docker 的**第二个**理由（第一个是隔离强度，见后面 Kimi 的 kernel panic）。而快照恢复的 49 ms 又比 microVM 冷启动快 2.6 倍 —— 于是「先做一个装好依赖的快照，之后所有沙箱都从快照起」成了标准做法。

### ★ 沙箱方案对照表：四条路，各自的代价

把账一账二的结论放进一张表，再加上隔离强度，候选方案就只剩四条（第五行是「不给 agent 执行环境」的退化方案）：

| 方案 | 隔离边界是什么 | 冷启动延迟 | 隔离强度 | 单机并发密度 | 状态能否快照 | 成本与复杂度 |
|---|---|---|---|---|---|---|
| **进程隔离**<br>（chroot + seccomp + rlimit） | 同一个内核、同一个容器里 fork 出来的进程 | ⚠️ 毫秒级 | **最弱**：共享内核与文件系统，一个 `rm -rf` 或一次内核 panic 就把邻居全带走 | **最高**，单机几百到上千 | 基本做不到（要自己实现进程状态序列化） | **最低**，几十行代码起步 |
| **容器**<br>（Docker / containerd） | 内核 namespace + cgroup | ⚠️ 冷 2~10 秒；镜像已在本地页缓存时可到几百毫秒 | **中**：共享宿主内核。内核级的崩溃（panic、死锁）会穿透隔离 | **高**，单机几十到几百 | 文件系统层可以（镜像分层）；内存状态要靠 CRIU，**很脆** | **低**，生态最成熟，什么都是现成的 |
| **microVM**<br>（Firecracker） | 独立内核 + KVM 硬件虚拟化 | 🌐 ~125 ms 级 | **强**：VM 边界。客户机内核崩了只崩自己 | **中高**，单机上百；内存是瓶颈 | ✅ **能，而且快** —— 内存页增量 checkpoint，Kimi 做到 133 ms 存 / 49 ms 恢 | **中**：要自建镜像格式、块设备驱动、快照管理 |
| **fullVM**<br>（QEMU） | 完整虚拟机，含设备模拟 | ⚠️ 秒到十秒级 | **最强**，可任意定制：换内核、装驱动、跑非 Linux | **低** | 能，但慢 | **高** |
| **远程服务**<br>（工具做成 HTTP 服务，agent 拿不到 shell） | 网络边界 | ≈ 0（服务常驻） | 取决于服务自己；agent 只能调你开放的那几个接口 | 取决于服务 | 无状态就不需要快照；有状态就很难 | **低**，但**表达力最弱** —— 做不了「让 agent 自由写代码」这类任务 |

⚠️ **怎么读这张表**：前四行是一条「隔离强度 ↑ / 启动速度 ↓ / 密度 ↓ / 复杂度 ↑」的单调链条，**唯独 microVM 在这条链条上是个例外** —— 它的隔离接近 fullVM，启动却接近容器。这个「例外」就是 Firecracker 被整个行业选中的原因，也是本章三家自研沙箱里有两家押注它的原因。

⚠️ 但请注意第五行：**如果你的任务不需要 agent 自由执行代码（比如只是调几个检索 API），远程服务是成本最低的正确答案。** 不要因为「大厂都上 microVM」就跟着上 —— 大厂上 microVM 是因为他们要训软件工程 agent。

**回到标题那个问题：为什么大家要上 microVM 而不是 Docker？** 三个理由，账一账二已经算完了两个：

| # | 理由 | 证据 |
|---|---|---|
| 1 | **隔离强度**：容器真的被 agent 搞崩过 | ✅ Kimi 原文的 kernel panic 和死锁（见下） |
| 2 | **启动延迟**：125 ms vs 5 秒，约 40 倍 | 账二结论 3 |
| 3 | **快照能力**：内存页增量 checkpoint 让 Pause/Resume 成为可能，进而省掉 98% 的内存 | 账一 ⑧⑨ |

### ✅ DeepSeek DSec：规模最大的一个

✅ 原文：*"we build a production-grade sandbox platform, **DeepSeek Elastic Compute (DSec)**"*

DSec 由三个 Rust 写的组件组成，彼此用自定义 RPC（Remote Procedure Call，远程过程调用）协议连接，各自可以横向扩展：

| 组件 | 角色 | 干什么 |
|---|---|---|
| **Apiserver** | API 网关 | 接住「给我开一个沙箱」「在这个沙箱里跑这条命令」这类请求 |
| **Edge** | 每台主机上的常驻 agent | 在本机真正创建、销毁、监控沙箱 |
| **Watcher** | 集群监控 | 盯着全集群的健康与容量，做调度与故障处理 |

三者全部架在 **3FS**（DeepSeek 自研的分布式文件系统）之上 —— 镜像、沙箱的持久化状态、轨迹日志都落在那里。

✅ **单个 DSec 集群管理数十万（hundreds of thousands）并发沙箱实例。** 按账一的 2 GB/个 折算，这是**数百 TB** 量级的内存账。

✅ 设计动机是四点观察，每一点直接对应一个工程难题：

| # | 观察 | 对应的工程难题 | 对应账目 |
|---|---|---|---|
| 1 | agentic 负载**高度异构** —— 从轻量函数调用到完整的软件工程任务 | 一套调度要同时服务 0.2 秒和 45 秒两种命令 | §6.1 那张轨迹表 |
| 2 | 环境镜像**又多又大**，但必须快速加载且支持迭代定制 | 冷启动 | 账二 |
| 3 | **高密度部署**要求高效的 CPU 与内存利用 | 单机能塞多少个 | 账一 ⑧ |
| 4 | **沙箱生命周期必须与 GPU 训练调度协同**，包括抢占和基于 checkpoint 的恢复 | 训练被抢占时沙箱怎么办 | 下面的「客户端快进」 |

✅ 三种运行时，按隔离强度分档（正好对应上面对照表的第 2/3/4 行）：

| 运行时 | 基座 | 特点 |
|---|---|---|
| **Container** | 完全 Docker 兼容 | **EROFS 按需加载**镜像 —— 不等整个镜像下载完就能起；预热容器池消除冷启动（**这正是账二结论 2 说的池化**） |
| **microVM** | **Firecracker** | VM 级隔离，面向安全敏感的高密度部署 |
| **fullVM** | **QEMU** | 支持任意定制 |

✅ 两处密度优化（都很具体，都是在抠账一 ⑧ 那个数）：

- 缓解虚拟化环境下**重复的 page cache 占用**。⚠️ 直白讲：1,000 个沙箱跑同一个镜像，默认情况下同一份只读文件会被缓存 1,000 次；去重之后缓存 1 次。
- 做内存回收以支持**安全超售**（oversubscription）—— 因为账一 ⑦ 告诉我们，任一时刻只有 2%~20% 的沙箱在真干活，剩下的内存可以借给别人。

✅ 另外还缓解了**容器运行时的自旋锁争用**，降低单沙箱 CPU 开销，提升单机装箱密度。

✅ **轨迹日志与抢占安全恢复**：DSec 为每个沙箱维护一份**全局有序的轨迹日志**，持久记录每一次命令调用及其结果。用途之一是「客户端快进」（client fast-forward）—— 训练任务被抢占时沙箱资源仍然保留，恢复时 DSec **重放已完成命令的缓存结果**，而不是真的重新执行一遍。

⚠️ 「重放缓存结果」这一招值得停一下。它等价于说：**agent 的轨迹是可以被「快进」的，只要环境的响应是确定性的。** 对照账一 ①，一条轨迹已经执行了 20 步、花了 40 沙箱·秒，抢占恢复时这 40 秒不用重来 —— 直接把 20 个结果按顺序喂回去，瞬间回到第 21 步。⚠️ 前提是环境确定性：如果某条命令的返回依赖当前时间或外部网络，重放就会和原来不一样。

### ✅ Kimi AgentENV：细节最锋利的一个

✅ Kimi-K3 论文 §5.3.2 用三种沙箱运行时（传统容器 / GPU 沙箱 / microVM），其中重点是与合作伙伴共建的 **AgentENV**，基于 **Firecracker**。三个设计目标：

**① 高保真隔离。** ✅ 原文给了一个很实在的理由：

> *"in our early experiments with traditional container-based sandbox runtimes, we observed several **kernel panics and deadlocks** caused by unintended agent operations."*

⚠️ 注意这句话的因果方向：**不是「为了安全合规」才上 microVM，是容器真的被 agent 搞崩过。** 而且 Kimi 明确说他们**想尽可能允许探索**（agent 会尝试 reward hacking、会做激进操作），所以不能靠「限制 agent 能干什么」来解决 —— 一限制就把探索空间也砍了。只能靠更强的隔离边界。⚠️ 这是对照表里「容器与宿主共享内核」那一栏的真实后果：**共享内核意味着客户机的内核 bug 会变成宿主机的 bug，一崩崩一片。**

**② 灵活的沙箱生命周期。** ✅ 增量 checkpoint：只保存自上次 checkpoint 以来**脏掉的内存页**（dirty pages），达到 —

> ✅ **checkpoint 延迟低至 133 ms，resume 延迟低至 49 ms**

在此之上提供三个高层操作：

| 操作 | 作用 | ✅ 关键数字 / 用途 | 对应账目 |
|---|---|---|---|
| **Pause / Resume** | 暂停的沙箱**不占内存也不占 CPU** | agent 等模型推理结果的时间**可占沙箱生命周期的 98%** —— 这段时间沙箱可以完全释放 | 账一 ⑧⑨：1 TB → 20 GB |
| **Fork** | 从当前状态精确复制一个新沙箱，原来的继续跑 | **用于奖励判定而不产生副作用** | 见下 |
| **Snapshot** | 定期存快照 | 错误恢复；也是「从快照起」的来源 | 账二结论 3 |

**③ 高效率高密度。** ✅ 数万个沙箱、每个镜像都不同，可能需要在数秒内创建完。用 **OverlayBD**（Overlay Block Device，叠加块设备）作为镜像格式，配自研的 **ublk**（userspace block，用户态块设备）驱动实现。

⚠️ 「Pause 能省 98%」是整章最值得记的一个数字，账一 ⑧⑨ 已经把它折算成了 1 TB → 20 GB。它说明一件反直觉的事：**Agentic RL 里沙箱资源的主要浪费不是执行，是等待。** 而这个等待恰好是**可以被精确识别的**（agent 在等模型返回，框架自己知道），所以能被彻底优化掉 —— 不像长尾那种只能缓解不能消除的东西。

⚠️ 「Fork 用于奖励判定」是一个很聪明的设计，值得单独说清楚它解决了什么：

```
不用 Fork 的做法：
  跑完 -> 在同一个沙箱里跑测试判分 -> 测试改了文件、装了包、起了服务
        -> 环境已经被污染，没法再续跑，也没法复现

用 Fork 的做法：
  跑完 -> Fork 一份 -> 在副本里跑测试判分 -> 判完把副本扔掉
        -> 原沙箱一点没动，可以继续跑，也可以再 Fork 一次判别的指标
```

⚠️ 它省掉的是「判完再把环境恢复原样」那整套逻辑 —— 而那套逻辑在实践中几乎不可能写对（装过的包怎么卸干净？改过的全局配置怎么还原？）。

### ✅ GLM-5：把环境故障当成数据质量问题

GLM 的角度不同 —— 它关心的是**沙箱失败会污染训练信号**。✅ 原文：

> *"coding-agent sandboxes can be inherently unstable and may fail for reasons unrelated to the model (e.g., environment crashes). Such failures introduce **noisy training signals** because they reflect **environment instability rather than the model's capability**. To mitigate this, we **record the failure reason for each sample and exclude samples that fail due to environment collapse**."*

⚠️ 这是一条被普遍低估的工程实践：**环境崩了不等于模型做错了。** 如果不区分，模型会学到「这类任务做不成，别试了」—— 而实际上只是基建不稳。要区分就必须**给每个样本记录失败原因**，这又是一条对数据通路契约的新要求（呼应 [05 章](05-算法与框架的接口.md) 本章总表的第 7 行和 [04 章 §4.4](04-训推一致性.md)）。

### 三家对照

| | DeepSeek DSec | Kimi AgentENV | GLM-5 |
|---|---|---|---|
| 隔离技术 | Container / **Firecracker** / QEMU 三档 | **Firecracker** microVM 为主 | ✅ 未细述 |
| 规模 | ✅ 单集群**数十万**并发 | ✅ **数万**个，秒级创建 | ✅ **1,000+** 并发 rollout |
| 恢复机制 | ✅ 全局有序轨迹日志 + 命令结果重放 | ✅ 增量内存页 checkpoint（133 ms 存 / 49 ms 恢） | ✅ 心跳驱动的容错 |
| 独特的一招 | 抢占安全的「客户端快进」 | **Pause 省 98% 内存** + **Fork 做无副作用奖励判定** | **按失败原因过滤样本** |
| 解决的是哪一维 | **规模** | **单沙箱效率** | **数据质量** |

⚠️ 三家的侧重完全不同，合起来才是一套完整方案。⚠️ 如果你只能抄一家：规模没上千就别抄 DeepSeek，**先抄 GLM 那一条**（记录失败原因）—— 它几乎零成本，而收益是让你的训练信号不再混进基建噪声。

## ★ 插一节：失败怎么办 —— 三类故障，和一个真问题

（⚠️ 这一节不编号，是为了不打乱原有的 6.1~6.7 编号，外部引用 §6.4~§6.7 仍然指向原来的内容。）

前面讲的都是「顺利的时候怎么跑得快」。但 agentic 环境最大的特点是**它经常不顺利**。这一节把失败处理拆成两步：先分类处置，再回答那个真问题 —— 失败的轨迹到底算不算样本。

### 第一步：三类故障，三种处置

| 故障 | 典型表现 | 怎么检测 | 工程处置 |
|---|---|---|---|
| **工具超时** | 一条命令跑不完：死循环、等交互输入、`pytest` 卡在某个用例上 | 单命令墙钟超时（比如 120 秒）+ 整条轨迹的总时间预算 | ★ **把超时变成一条正常的观测返回给模型**（`"command timed out after 120s"`），而不是直接判轨迹失败 —— 让模型学会「这条命令不该这么写」 |
| **沙箱 OOM** | 进程被内核 OOM killer 杀掉；microVM 内存耗尽 | cgroup / VM 的内存上限触发 | 同上，变成可见的错误观测，附带「你刚才那条命令吃掉了 8 GB」；⚠️ 同时要区分是**模型写了吃内存的代码**还是**你给的配额本来就不够** |
| **网络抖动** | 工具要调外部 API，超时或 5xx | HTTP 状态码 / 连接超时 | 幂等重试 + 指数退避；长期方案是**把外部依赖换成本地镜像或录制回放**，让环境变确定（这也顺带让 DSec 的「命令重放」能用） |
| **沙箱崩溃 / 被抢占** | 容器整个消失、宿主机被更高优先级任务抢走 | 心跳丢失 | 从快照恢复 + 命令日志重放（DSec 的客户端快进）；恢复不了才上报失败 |
| **奖励判定本身失败** | 跑测试的框架自己挂了、判分服务超时 | 判定返回了异常而不是分数 | **Fork 一份专门判定**，判定环境与工作环境分离；判定失败就重判，不要把它算成模型的 0 分 |

⚠️ 前两类（超时、OOM）和后三类有一个**本质区别**，这是整节的关键：

| | 超时 / OOM | 网络抖动 / 沙箱崩溃 / 判定失败 |
|---|---|---|
| 是谁造成的 | **模型的动作**造成的 | **基建**造成的 |
| 模型能不能避免 | 能（写更好的命令） | 不能 |
| 是不是有效训练信号 | ★ **是** —— 应该让模型学会避开 | **不是** —— 学了反而有害 |
| 处置 | 变成观测，继续跑，轨迹**保留** | 重试；重试不成则**排除** |

**判断标准只有一句话：这次失败，换一个更强的模型会不会不发生？** 会 → 是有效信号，保留；不会 → 是基建噪声，排除。

### 第二步：⚠️ 失败的轨迹算不算样本 —— 一个真问题

上面说「基建造成的失败要排除」。但**排除本身会引入选择偏差**，因为**环境崩溃率和任务难度是相关的**：难任务跑得久、装的依赖多、触发的边界情况多，所以更容易崩。把崩掉的都丢了，等于系统性地多丢难题。

把这件事算出来：

| 步 | 情况 | 数字 |
|---|---|---|
| ① | 一批 512 条：简单题 256 条、难题 256 条，难题占比 **50%** | 512 |
| ② | ⚠️ 设简单题的环境崩溃率 **2%**、难题 **15%**（量级示意，不是实测） | — |
| ③ | 简单题存活 | 256 × 0.98 = **250.9 条** |
| ④ | 难题存活 | 256 × 0.85 = **217.6 条** |
| ⑤ | 存活总数 | 250.9 + 217.6 = **468.5 条** |
| ⑥ | 存活样本里的难题占比 | 217.6 ÷ 468.5 = **46.4%** |
| ⑦ | 相对原始配比 | 50% − 46.4% = **少了 3.6 个百分点** |
| ⑧ | 换成相对口径 | 3.6 ÷ 50 = **难题的相对占比少了 7.1%** |

> ⚠️ ⑦ 和 ⑧ 是两个不同的数，不能互换：**「少了 3.6 个百分点」和「少了 7.1%」描述的是同一件事的两个口径。** 写成「难题少了 3.6%」是错的 —— 那会被读成 50% × (1−3.6%) = 48.2%。本仓库规则：**比例之间作差用「百分点」，作商用「%」。**

⚠️ 更要命的是 ⑧ 这个偏差**每个迭代都同向发生**。跑 1,000 个迭代，模型见到的难题总量就比你以为的少 7% —— 而难题恰恰是 §5.5 说的「真正贡献梯度」的那一批。**两个偏差还会叠加**：难题既更容易被陈旧度过滤掉（[05 章 §5.5](05-算法与框架的接口.md)），又更容易被环境崩溃过滤掉。

四条处置路线，各有各的代价：

| 路线 | 做法 | 代价 |
|---|---|---|
| **A. 全部丢弃** | 崩了的直接扔 | ⚠️ 上表的选择偏差 + 批大小变动导致有效学习率抖动 |
| **B. 当成模型失败，给 0 分** | 不区分原因 | ⚠️ **最糟**：模型学到「难题做不成」，而且这个错误信号和难度正相关 |
| **C. 保留在批次里，loss 权重置 0** | 样本还在，但不贡献梯度 | 批大小恒定（解决了 A 的后半个问题），但**选择偏差一点没解决** |
| **D. ✅ GLM 的做法 + 按原配比补采样** | 记录失败原因 → 只排除环境崩溃 → **按原难度配比补采样**把批次填回 512 | 要多一轮采样（成本见账一），但**这是唯一真正消掉偏差的做法** |

⚠️ **本文的判断**：✅ GLM 原文只写到「记录失败原因并排除」，**「按原配比补采样」这一步是本文的补充推论，不是 GLM 的结论。** 但没有这一步，排除本身就是一个新的偏差源 —— 你只是把「基建噪声」换成了「难度漂移」。

为什么「解析」会比「实现」贵这么多？因为解析要吃下所有不确定性：

| 解析要处理的情况 | 举例 |
|---|---|
| 不同模型的不同格式 | 有的吐 JSON，有的吐 XML 标签 `<tool_call>…</tool_call>`，有的用特殊 token |
| 流式解析 | token 一个一个来，要能在只看到半个 JSON 时就判断「这是一个工具调用的开头」 |
| 格式错误 | 模型吐了个缺右括号的 JSON，是重试、是截断、还是把错误返回给模型让它自己修 |
| 一次吐多个调用 | 并行工具调用要全部解出来 |
| 工具名/参数幻觉 | 模型叫了一个不存在的工具，或者给了多余的参数 |

这正是 [harness评测框架/agent脚手架/03-工具集与ACI.md](../harness评测框架/agent脚手架/03-工具集与ACI.md) 讲的那个问题，在训练侧的同一副面孔。

```
    └── codex.py          71 行   <- 真的是 Codex
```

✅ `claude_code.py` 里的 `ClaudeCodeHarness` 类，真的是在沙箱里装一个 Node 运行时、装 Claude Code 的 npm 包，然后用这些参数启动它：

```python
launch_flags = (
    "--permission-mode bypassPermissions "
    "--output-format stream-json --include-partial-messages "
    "--include-hook-events --verbose"
)
```

⚠️ 顺带注意 `--permission-mode bypassPermissions` 这一项：训练环境里把权限确认全关掉是合理的（没有人在旁边点「同意」），但这也意味着**沙箱是唯一的安全边界** —— 直接回到了本章开头那张对照表。

✅ `codex.py` 的注释更实在，把踩过的两个坑写在了文件头：

> *"Two non-obvious bits: the provider base_url must be inline in the TOML (Codex only honours env vars for the default OpenAI provider), and the config is written via a base64 round-trip to dodge shell-quoting traps."*

⚠️ **这件事的意义远超一个适配文件。** 它说明训练环境已经走到了这一步：不再是「我们自己写一个简化的 agent 循环来训练」，而是**直接把生产环境里真实用的那个 CLI 拉进沙箱训练**。模型是在它将来真正会被部署进去的那个 harness 里学习的。

✅ Kimi-K3 独立给出了同一个方向的判断 —— 它的可验证任务：

> *"Every task runs in a containerized sandbox and is rolled out under **diverse agent scaffolds rather than a single fixed harness, to promote cross-scaffold generalization**."*

⚠️ 两家的选择合起来读很有意思：

| | slime 的做法 | Kimi 的做法 |
|---|---|---|
| 怎么选 harness | **用真实的那一个**（Claude Code / Codex） | **用多个不同的** |
| 防的是什么问题 | **sim-to-real 差距** —— 训练时的简化 harness 和上线时的真 harness 不是一个东西 | **过拟合到单一脚手架** —— 模型学到的是「怎么讨好这个 harness」而不是「怎么解决问题」 |
| 失败的样子 | 训练分很高，换到真 CLI 上就崩 | 在训练用的 harness 上很强，换一个就掉点 |

⚠️ 两个问题都真实存在，而且**它们不是同一个问题**。理想做法大概是两者都做：用一组真实 CLI，而不是一个。

✅ slime 的沙箱抽象刻意做得很窄，文件头注释：

> *"The public sandbox contract is **intentionally small**: async context management, command execution, and file read/write. Agent examples can build task-specific setup, runner, and evaluator logic on top of this **without depending directly on one sandbox provider**."*

⚠️ 「async context management + command execution + file read/write」这三件事，正好就是 §6.1 那张循环图里环境要做的全部。**契约窄到这个程度，意味着你换沙箱后端（Docker 换 Firecracker 换远程服务）时，上层的任务代码一行都不用改** —— 这和 GLM 报告里那句「task-specific logic 与 core training loop 隔离」是同一条原则的源码实现。**报告说的和代码写的对上了。**

## 6.5 ★ 挂回 `harness评测框架/`

本仓库另有一个目录 [harness评测框架/agent脚手架/](../harness评测框架/agent脚手架/) 在讲 agent 脚手架。⚠️ 那边讲的东西和这一章是**同一件事的两面**：

| 同一个概念 | 在评测里叫 | 在训练里叫 | 两边各关心什么 |
|---|---|---|---|
| 让模型能操作计算机的那套东西 | **harness / 脚手架** | **environment / 环境** | 评测关心公平可复现；训练关心吞吐与可恢复 |
| 工具定义与返回裁剪 | **ACI** | 工具 schema + tool parser | 两边**完全一样**，见 [03-工具集与ACI.md](../harness评测框架/agent脚手架/03-工具集与ACI.md) |
| 隔离执行 | 沙箱 | 沙箱 | 评测要防作弊；训练要防崩 + 要能 pause/fork |
| 上下文怎么拼 | 上下文管理 | 白盒 agent 的 `f_CM` | 见 [04-上下文管理.md](../harness评测框架/agent脚手架/04-上下文管理.md) |

⚠️ 三条推论：

1. **评测 harness 的差异会直接变成训练环境的差异。** 那边 [08-脚手架怎么影响榜单分数.md](../harness评测框架/agent脚手架/08-脚手架怎么影响榜单分数.md) 讲的「同一个模型换个脚手架分数就变」，在训练侧对应的是「同一个模型换个环境学到的东西就不一样」。

2. **slime 的 `harness/claude_code.py` 是这条连接的实证。** 那边 [06-ClaudeCode与Codex逐项对照.md](../harness评测框架/agent脚手架/06-ClaudeCode与Codex逐项对照.md) 逐项对比了两个 CLI 的设计，而 slime 把这两个 CLI **原封不动搬进了训练环路** —— 那份对照读下来的每一条差异，都会成为训练信号的差异。

3. **训练侧比评测侧多两个硬需求**：可 pause/resume（评测跑完就完了，训练要跨步续跑、要扛抢占）和高并发（评测几百条，训练动辄几十万条 —— 账一已经把这个差距折成了 1 TB 内存）。这就是为什么 Kimi 要自己做 AgentENV、DeepSeek 要自己做 DSec，而不是直接用现成的评测沙箱。

## 6.6 ✅ 一处闭环：逐样本版本号

[02 章 §2.5](02-架构主轴-同步到全异步.md) 引了 HF 横评的结论：**逐样本打版本号是必需的**，batch 级门控不够。当时那是 🌐 材料。

✅ GLM-5 论文 §4.1.2 给了这条的一手实证 —— 而且比博客说的更细：

> *"we log the policy weight version used by the rollout engine at generation time. Specifically, for each response we record **the sequence of model versions involved, (w₀, ..., wₖ) with w₀ < ... < wₖ**. Let w′ denote the current policy version. We discard a sample if its **oldest** rollout version is too stale, i.e., if **w′ − w₀ > τ**."*

⚠️ 注意两个细节：

1. **一条轨迹记的不是一个版本号，是一个版本序列。** 因为 agentic 轨迹跨越多次权重更新 —— §6.1 那条「修 bug」轨迹跑了 30 轮、几分钟，这期间权重可能已经更新了好几版：第 1 轮工具调用用的是 w₀，第 10 轮可能已经是 w₃ 了。这正是 [03 章 §3.5](03-权重同步.md) 「永不停」中断模型的直接后果 —— 生成不停，权重照换。

2. **判据用的是最老的那个 w₀，不是平均、也不是最新。** 这是保守选择：只要轨迹里有任何一段太旧，整条丢掉。

用一条具体轨迹把它摊开：

```
一条跨了 4 个权重版本的轨迹：

  轮次  1  2  3  4  5  6  ...  28  29  30
  版本  w0 w0 w0 w1 w1 w2  ...  w3  w3  w3
        ^^                             ^^
        最老 = w0                      最新 = w3

当前策略版本 w' = w5
  按最老判： w' - w0 = 5 - 0 = 5
  按最新判： w' - w3 = 5 - 3 = 2
  按平均判： 大约 5 - 1.6 = 3.4

门限 tau = 4 时：按最老判 -> 丢弃；按最新或平均判 -> 保留
```

⚠️ 三种判法会给出**相反的结论**，而 GLM 选了最严的那一种。

**🌐 博客说「要逐样本打版本号」，✅ GLM 的实现是「要逐样本打版本**序列**，并按最旧的那个判」—— 一手材料比二手材料更严格。** ⚠️ 这也是本仓库反复强调的那条纪律的一个实例：**二手材料给方向，一手材料给判据。**

## 6.7 本章小结

| 结论 | 分级 |
|---|---|
| ⚠️ **澄清一处常见的说反**：沙箱 98% 的时间在**等模型**（不是等工具）；而长尾来自工具执行方差大。两者是同一组数字的两种读法 | ⚠️ 本文更正 |
| **账一**：512 轨迹 × 30 步 × 2 秒 = **30,720 沙箱·秒**；串行要 8.5 小时；压进 10 分钟需 ≥52 个沙箱**在执行**，但峰值要 **512 个活着** | ⚠️ 本文推算 |
| **账一的钱**：按 2 GB/沙箱，不做 Pause 要 **1 TB 内存**，做了只要 **20 GB**（98% 口径）—— 这是 Pause 的真正价值 | ⚠️ 本文推算 |
| **账二**：每步重开沙箱，Docker 的启动开销是工具执行量的 **250%**；每轨迹开一次也要 8.3%。这解释了沙箱必须有状态 + 必须池化 | ⚠️ 本文推算 |
| **上 microVM 而不是 Docker 的三个理由**：隔离强度（容器真被搞崩过）、启动快约 40 倍、能做内存页快照 | ✅ + ⚠️ |
| 四条沙箱路线（进程 / 容器 / microVM / fullVM）是一条单调链，**microVM 是链条上的例外**：隔离近 fullVM，启动近容器 | ⚠️ |
| ⚠️ 任务不需要 agent 自由执行代码时，**远程服务**是成本最低的正确答案，别盲目抄大厂 | ⚠️ |
| 环境应以「数据生成者」身份接入，与训练循环彻底隔离（GLM：统一 message-list） | ✅ + ⚠️ |
| MiniMax 白盒/黑盒二分 + Gateway 统一，已验证于数百种脚手架、数千种工具格式 | ✅ |
| DSec：三个 Rust 组件（Apiserver / Edge / Watcher）+ 3FS，单集群数十万并发，三档运行时 | ✅ |
| AgentENV：Firecracker microVM，checkpoint 133 ms / resume 49 ms | ✅ |
| **Pause 能省掉沙箱 98% 的生命周期** —— 浪费在等待而非执行 | ✅ |
| **Fork 用于无副作用的奖励判定**，省掉「判完再恢复环境」那套写不对的逻辑 | ✅ |
