# 07 · 选型与实践：我该用哪个，什么时候不该自研

## 7.1 · 先问三个问题，不是先看框架

⚠️ 我见过最常见的错误是「先挑框架，再想需求」。RL 框架的选型，**80% 由下面三个问题决定**，剩下 20% 才是框架本身的优劣：

```
Q1  你有多少卡？
    ├─ ≤ 8 卡          → 同置（colocated）。异步的收益还没有它的复杂度贵。
    ├─ 数十 ~ 数百卡    → ★ 分水岭。见 Q2。
    └─ 上千卡          → 分离 + 异步几乎是唯一答案。

Q2  你的轨迹有多长、多参差？
    ├─ 数学/短推理（输出 < 4K token，长度接近） → 长尾不严重，同步够用
    ├─ 长推理（16K~32K）                        → ★ 长尾开始吃掉一半以上时间
    └─ Agentic（多轮 + 工具 + 环境等待）        → 必须异步，且必须有沙箱

Q3  你要改的是算法，还是要跑通一个模型？
    ├─ 改算法（试新 loss / 新 advantage）  → veRL（注册表最全）或 OpenRLHF（最好改）
    └─ 跑模型（把一个已知配方跑到生产）    → slime（Megatron 后端最成熟）
```

⚠️ **Q1 和 Q2 会互相抵消。** 卡少但轨迹长（比如 8 卡跑 32K agentic），你既不能靠加卡缩短长尾，也不能靠同步硬扛——这是最难受的位置。这时候 ✅ Kimi-K3 的答案（同置 + partial rollout，见 [02 章 §2.4](02-架构主轴-同步到全异步.md)）比 GLM-5 的答案（全异步分离）更值得抄。

## 7.3 · ★ 三个最容易踩的坑

### 坑 1：以为「异步」是一个开关

⚠️ [02 章 §2.2](02-架构主轴-同步到全异步.md) 和 [03 章 §3.6](03-权重同步.md) 已经论证过：**异步至少是两个独立的旋钮**。

```
K_buf   = rollout 缓冲深度      （OpenRLHF: --train.async_queue_size，默认 1）
K_sync  = 权重同步间隔          （slime:    --update-weights-interval）

真实陈旧度 ≈ K_buf + K_sync
```

⚠️ 常见的翻车方式是：只调了 `K_buf`，以为陈旧度是 1，实际 `K_sync=8`，真实陈旧度接近 9。**训练崩了却查不出原因。**

**实践建议**：先把 `K_sync = 1` 固定住（每步都同步权重），只调 `K_buf`，等收敛稳定了再放松 `K_sync`。

### 坑 2：训推不一致，但你查不出来

⚠️ [04 章](04-训推一致性.md) 整章都在讲这个。对新手最重要的一条是：

> **训推不一致的表现不是报错，是「训练看起来在跑，但就是不涨」。**

✅ 最低成本的自查（openPangu 用的就是这个思路）：

```
① 拿同一批 prompt，分别用推理引擎和训练引擎算一遍 logprob
② 算两者的皮尔逊相关系数（PCC, Pearson Correlation Coefficient）
③ PCC < 0.99  →  ★ 有问题，先别调超参，先查一致性
```

⚠️ 这个 0.99 阈值来自 ✅ openPangu 的 KPop 方法（[04 章 §4.6](04-训推一致性.md)）——它把 PCC 当作在线判据来切换掩码策略。**你至少可以把它当离线体检用。**

### 坑 3：过滤了样本，却引入了偏差

⚠️ [05 章 §5.5](05-算法与框架的接口.md) 讲的非对称过滤陷阱，是最隐蔽的一个：

```
你以为的：      过滤掉全对/全错的组 → 保留有梯度信号的组 → 效率提升
实际发生的：    难题耗时长 → 难题的样本更陈旧 → 但难题恰好是「有信号」的那批
                → 存活下来的样本系统性偏陈旧 → batch 级的 staleness 门控看不见
```

**实践建议**：把 staleness 记录到**样本级**而不是 batch 级，并且分组统计。✅ GLM-5 更进一步——它记的是一条轨迹跨过的**权重版本序列** `(w₀, ..., wₖ)`，用最老的那个判断（[06 章 §6.6](06-AgenticRL-环境与沙箱.md)）。

## 7.4 · ⚠️ 什么时候不该自研

五家前沿模型全都自研了 RL 基建（[01 章 §1.3](01-格局全景.md)）。⚠️ 但这**不构成你也该自研的理由**——它们自研是因为踩到了下面这些线：

| 触发自研的真实原因 | 你踩到了吗 |
|---|---|
| 训练规模超过开源框架验证过的范围（数千卡） | 大概率没有 |
| 用了非 NVIDIA 硬件（昇腾等），通信/kernel 层要重写 | ✅ openPangu 是这个原因 |
| 算力预算是硬约束，必须把利用率榨到极致 | ✅ Kimi-K3 的 *"within a few hundred GPUs"* |
| 有和框架强耦合的自研模型结构（MoE 路由、MLA 变体） | 可能 |
| 环境/沙箱规模到了数十万并发（DeepSeek DSec） | 大概率没有 |

⚠️ 我的判断：**除了「非 NVIDIA 硬件」这一条，其余四条在绝大多数团队都不成立。**

而且注意 ✅ 一个关键事实：**slime 本身就是 GLM 的自研框架，但它是开源的**（[slime拆解](slime拆解.md)）。也就是说，「自研」和「用开源」在 2026 年已经不是二选一——**你可以直接用一个被前沿模型生产验证过的开源框架**。

⚠️ 更现实的做法是**分层自研**：

```
应该考虑自己写的：    环境 / 沙箱 / reward 函数 / agent harness
                     （✅ 三家报告都强调这一层要与训练循环解耦——
                       GLM「isolates task-specific logic from the core training loop」
                       slime「They do not fork the training kernel」
                       OpenRLHF 把用户代码挂在推理引擎侧）

基本不该自己写的：    训练后端 / 推理后端 / 权重同步传输层 / 并行策略
                     （这些是 10,000+ 行起步且和硬件强耦合的部分）
```

★ **这条分界线不是我编的，它是三家独立表述后收敛出来的同一条原则。** 它也解释了为什么 [06 章](06-AgenticRL-环境与沙箱.md) 说「评测的 harness 和训练的 environment 是同一件东西的两面」——**这一层本来就该是你自己的资产**。

## 7.5 · ⚠️ 一份务实的上手顺序

如果你从零开始，我会这样走：

```
第 1 周   跑通同步 PPO/GRPO，小模型（1.5B~7B）、短输出（< 2K）
          用 OpenRLHF。目标不是效果，是把五个模块（[01 章 §1.1]）都摸一遍。
          ★ 必须做：读 openrlhf/cli/train_ppo_ray.py:660-700 的参数断言

第 2 周   加长输出到 16K，观察生成时间占比
          ★ 你会亲眼看到「生成占 80% 时间」（✅ OpenRLHF README 原文）
          此时才有资格讨论异步

第 3 周   开 --train.async_enable，K_buf=1，K_sync=1
          对比 reward 曲线，确认没崩。这一步验证的是你的过滤/掩码没写错。

第 4 周   做训推一致性体检（§7.3 坑 2 的 PCC 三步）
          ⚠️ 我的建议是这一步越早越好，很多人是第 8 周才发现问题

第 2 月   按 Q1/Q2 决定是否换 slime / veRL
          换的成本主要在数据和 reward，不在框架 API
```

⚠️ **注意第 4 周那一条**。训推一致性检查在教程里从来没人讲，但它是 [04 章](04-训推一致性.md) 整章存在的理由——✅ 五家前沿报告里有四家专门写了这个问题。**它不是边角料，是主线。**

## 7.6 · 本篇小结

| 结论 | 分级 |
|---|---|
| 选型的 80% 由「卡数 / 轨迹长度参差 / 改算法还是跑模型」三问决定 | ⚠️ 我的归纳 |
| 卡少 + 轨迹长是最难受的位置，抄 Kimi 而不是抄 GLM | ⚠️ 推断 |
| veRL 覆盖最广 / slime 生产验证最硬 / OpenRLHF 最好读 / TRL 最快上手 | ✅ 实测 + ⚠️ |
| **异步不是一个开关，是 K_buf 和 K_sync 两个旋钮**；先固定 K_sync=1 | ✅ 源码 + ⚠️ 建议 |
| 训推不一致的表现是「不涨」而不是「报错」；用 PCC<0.99 做体检 | ✅ openPangu + ⚠️ |
| 非对称过滤会让存活样本系统性偏陈旧；staleness 记到样本级 | ⚠️ 推断 + ✅ GLM 版本序列 |
| 除「非 NVIDIA 硬件」外，四条自研触发条件在多数团队不成立 | ⚠️ 我的判断 |
| **分层自研**：环境/沙箱/reward/harness 自己写，后端/传输/并行不要碰 | ✅ 三家收敛 |
| 上手顺序：同步跑通 → 加长看长尾 → 开异步 → **第 4 周做一致性体检** | ⚠️ 建议 |
