## 7.1 · 先问三个问题，不是先看框架

⚠️ 我见过最常见的错误是「先挑框架，再想需求」。RL 框架的选型，**80% 由下面三个问题决定**，剩下 20% 才是框架本身的优劣：

```
Q1  你有多少卡？
    +- 8 卡以内         -> 同置（colocated）。异步的收益还没有它的复杂度贵。
    +- 数十 ~ 数百卡    -> (*) 分水岭。见 Q2。
    +- 上千卡           -> 分离 + 异步几乎是唯一答案。

Q2  你的轨迹有多长、多参差？
    +- 数学/短推理（输出 4K token 以内，长度接近） -> 长尾不严重，同步够用
    +- 长推理（16K ~ 32K）                         -> (*) 长尾开始吃掉一半以上时间
    +- Agentic（多轮 + 工具 + 环境等待）           -> 必须异步，且必须有沙箱

Q3  你要改的是算法，还是要跑通一个模型？
    +- 改算法（试新 loss / 新 advantage）  -> veRL（注册表最全）或 OpenRLHF（最好改）
    +- 跑模型（把一个已知配方跑到生产）    -> slime（Megatron 后端最成熟）
```

> **术语**：**同置**（colocated）= 训练和生成共用同一批 GPU，轮流用。**分离**（disaggregated）= 训练卡和生成卡是两批不同的卡，同时各干各的。详见 [02 章](02-架构主轴-同步到全异步.md)。

⚠️ **Q1 和 Q2 会互相抵消。** 卡少但轨迹长（比如 8 卡跑 32K agentic），你既不能靠加卡缩短长尾，也不能靠同步硬扛 —— 这是最难受的位置。这时候 ✅ Kimi-K3 的答案（同置 + partial rollout，见 [02 章 §2.4](02-架构主轴-同步到全异步.md)）比 GLM-5 的答案（全异步分离）更值得抄，因为 partial rollout 不要求你有两批卡。

### 三个具体场景，走一遍这三个问题

| 场景 | Q1 卡数 | Q2 轨迹 | Q3 目标 | 走到哪 | 决定性的是哪一问 |
|---|---|---|---|---|---|
| **A** 高校实验室，做数学推理的 GRPO 变体，要发论文 | 8×A100 | 输出 < 4K，长度接近 | 改算法 | **先 OpenRLHF 跑通 → 再换 veRL 做消融** | Q3。Q1/Q2 都说「同步就够」，所以框架选型只剩「哪个好改」 |
| **B** 公司产线，训一个代码 agent | 256×H100 | 32K + 工具调用 + 沙箱 | 跑模型 | **slime** | Q2。agentic 把「必须异步 + 必须有沙箱」变成硬门槛，而 slime 自带 harness |
| **C** 创业团队，主力 H800，同时要备一套国产卡方案 | 16×H800 | 16K 长推理 | 跑模型 | **veRL** | 都不是 —— 是 §7.2 那条**横切判断**：国产卡支持压倒其他所有考虑 |

⚠️ 场景 C 要注意：**横切判断（国产卡、Agentic、特殊模型结构）会直接否决三问的结论。** 先过横切判断，再走三问。

## 7.2 · 决策图与同口径对照表

```
我要做 RL 后训练
│
├─ 只想快速验证一个想法
│  └─> TRL
│
├─ 要做算法研究 / 发论文
│  └─> veRL
│
└─ 要长期迭代一条产线
   │
   ├─ 已有 Megatron 经验
   │  └─> slime
   │
   └─ HF 生态更熟
      └─> OpenRLHF
```

**两条横切判断**（和上面的树正交，先过这两条）：

| 横切条件 | 结论 |
|---|---|
| 要跑**国产卡**（昇腾等） | 看 veRL 的 hccl checkpoint engine；⚠️ 其余三家都要自己补通信层 |
| 要做 **Agentic + 沙箱** | slime 自带 `claude_code` / `codex` harness（见 [06 章 §6.4](06-AgenticRL-环境与沙箱.md)）；veRL 有 `agent_loop/` 但沙箱要自己接；OpenRLHF 把用户代码挂在推理引擎侧；TRL 没有 |

> ⚠️ **为什么「社区活跃度」这一行空着。** 这一项的时效性比其他所有行都强：star 数、commit 频率、issue 响应速度三个月就能翻盘，而本仓库的材料访问于 2026-08。**给一个过期的数字比不给更有害** —— 它会让你以为自己做了调研。请自己花十分钟查这三项：① 近 90 天的 commit 数；② 最近 20 个 issue 的中位首次响应时间；③ 有没有稳定的 release 节奏（而不是只有 main 分支在滚）。

> ⚠️ **「上手难度」和「可读性」这两行是我的主观判断**，依据是读源码时「从入口追到一次权重更新要跳几个文件」。你的背景不同，结论可能相反 —— 比如一个 Megatron 老手会觉得 slime 比 OpenRLHF 好懂得多。

## 7.3 · ★ 四个最容易踩的坑

### 坑 1：以为「异步」是一个开关

⚠️ [02 章 §2.2](02-架构主轴-同步到全异步.md) 和 [03 章 §3.6](03-权重同步.md) 已经论证过：**异步至少是两个独立的旋钮。**

```
K_buf   = rollout 缓冲深度     （OpenRLHF: --train.async_queue_size，默认 1）
K_sync  = 权重同步间隔         （slime:    --update-weights-interval）

真实陈旧度 ≈ K_buf + K_sync
```

⚠️ 常见的翻车方式是：只调了 `K_buf`，以为陈旧度是 1，实际 `K_sync = 8`，真实陈旧度接近 1 + 8 = **9**。**训练崩了却查不出原因** —— 因为监控面板上显示的 `async_queue_size = 1` 看起来一切正常。

**实践建议**：先把 `K_sync = 1` 固定住（每步都同步权重），只调 `K_buf`，等收敛稳定了再放松 `K_sync`。⚠️ 并且**把真实陈旧度打成一个独立的监控指标**，而不是靠两个配置项各自看。

### 坑 2：训推不一致，但你查不出来

⚠️ [04 章](04-训推一致性.md) 整章都在讲这个。对新手最重要的一条是：

> **训推不一致的表现不是报错，是「训练看起来在跑，但就是不涨」。**

✅ 最低成本的自查（openPangu 用的就是这个思路）：

```
(1) 拿同一批 prompt，分别用推理引擎和训练引擎算一遍 logprob
(2) 算两者的皮尔逊相关系数（PCC = Pearson Correlation Coefficient）
(3) PCC < 0.99  ->  (*) 有问题，先别调超参，先查一致性
```

⚠️ 这个 0.99 阈值来自 ✅ openPangu 的 KPop 方法（[04 章 §4.6](04-训推一致性.md)）—— 它把 PCC 当作**在线判据**来切换掩码策略。**你至少可以把它当离线体检用。**

### 坑 3：过滤了样本，却引入了偏差

⚠️ [05 章 §5.5](05-算法与框架的接口.md) 讲的非对称过滤陷阱，是最隐蔽的一个：

```
你以为的：    过滤掉全对/全错的组 -> 保留有梯度信号的组 -> 效率提升
实际发生的：  难题耗时长 -> 难题的样本更陈旧 -> 但难题恰好是「有信号」的那批
              -> 存活下来的样本系统性偏陈旧 -> batch 级的陈旧度门控看不见
```

⚠️ 而 [06 章](06-AgenticRL-环境与沙箱.md) 的失败处理一节给出了**第二个同向的偏差**：环境崩溃率和难度正相关，排除崩溃样本又会多丢难题。**两个偏差叠加，方向一致，都在把训练分布往简单题推。**

**实践建议**：把陈旧度记录到**样本级**而不是 batch 级，并且**按难度分组统计**。✅ GLM-5 更进一步 —— 它记的是一条轨迹跨过的**权重版本序列** `(w₀, ..., wₖ)`，用最老的那个判断（[06 章 §6.6](06-AgenticRL-环境与沙箱.md)）。

### 坑 4：⚠️ 读性能数字时的三个口径陷阱

选型阶段要读大量「我们比它快 X」的宣传。下面三个口径错误在这类材料里高频出现，**而且全都会让数字看起来更漂亮**：

| 陷阱 | 错在哪 | 正确算法 |
|---|---|---|
| **把「时间减少 X%」说成「加速 X%」** | 这是两个不同的数 | `加速倍数 = 1 ÷ (1 − 时间减少比例)`。时间减少 **50%** = 加速 **2 倍**（也就是「快了 100%」）；时间减少 **90%** = 加速 **10 倍**。反过来，「加速 50%」只对应时间减少 **33.3%** |
| **把「百分点」写成「百分比」** | 两个比例相减得到的是**百分点** | GPU 利用率从 40% 提到 55%，是提高了 **15 个百分点**，相对提升是 15÷40 = **37.5%**。写成「提升 15%」会被读成 40%×1.15 = 46% |
| **带宽单位混用** | **GB/s 和 Gb/s 差 8 倍**；聚合带宽和单向带宽又差 2 倍 | 见下面这笔账 |

带宽这一项值得单独算一遍，因为它直接影响 [03 章](03-权重同步.md) 的权重同步选型：

| 步 | 算什么 | 算式 | 结果 |
|---|---|---|---|
| ① | NVLink（第四代，H100）标称 | — | **900 GB/s** |
| ② | ⚠️ 但这个 900 是**双向聚合**（发 + 收加起来） | 900 ÷ 2 | **单向 450 GB/s** |
| ③ | InfiniBand NDR 标称 | — | **400 Gb/s**（小写 b = bit） |
| ④ | 换成字节 | 400 ÷ 8 | **50 GB/s** |
| ⑤ | **同单位、同方向**比 | 450 ÷ 50 | **9 倍** |
| ⑥ | ⚠️ 如果直接拿 900 ÷ 50 | 900 ÷ 50 | **18 倍 —— 错，多算了一倍** |

⚠️ **⑥ 这个「18 倍」是本仓库见过最多的一个数值错误。** 它的来源是拿「双向聚合的 NVLink」去比「单向的 IB」。做权重同步选型时，这一倍的差别会直接决定「跨节点同步到底可不可接受」的判断。

## 7.4 · ⚠️ 什么时候不该自研

五家前沿模型全都自研了 RL 基建（[01 章 §1.3](01-格局全景.md)）。⚠️ 但这**不构成你也该自研的理由** —— 它们自研是因为踩到了下面这些线：

| 触发自研的真实原因 | 你踩到了吗 | 谁因为这条自研的 |
|---|---|---|
| 训练规模超过开源框架验证过的范围（数千卡） | ⚠️ 大概率没有 | — |
| 用了非 NVIDIA 硬件（昇腾等），通信层 / kernel 层要重写 | **这一条最可能成立** | ✅ openPangu |
| 算力预算是硬约束，必须把利用率榨到极致 | ⚠️ 大概率没有 | ✅ Kimi-K3 的 *"within a few hundred GPUs"* |
| 有和框架强耦合的自研模型结构（MoE 路由、MLA 变体） | 可能 | — |
| 环境 / 沙箱规模到了数十万并发 | ⚠️ 大概率没有 | ✅ DeepSeek DSec（见 [06 章 §6.3](06-AgenticRL-环境与沙箱.md)） |

⚠️ 我的判断：**除了「非 NVIDIA 硬件」这一条，其余四条在绝大多数团队都不成立。**

而且注意 ✅ 一个关键事实：**slime 本身就是 GLM 的自研框架，但它是开源的**（见 [slime拆解.md](slime拆解.md)）。也就是说，「自研」和「用开源」在 2026 年已经不是二选一 —— **你可以直接用一个被前沿模型生产验证过的开源框架。**

⚠️ 更现实的做法是**分层自研**：

```
应该考虑自己写的：  环境 / 沙箱 / reward 函数 / agent harness
                    （三家报告都强调这一层要与训练循环解耦：
                      GLM     : "isolates task-specific logic from the core training loop"
                      slime   : "They do not fork the training kernel"
                      OpenRLHF: 把用户代码挂在推理引擎侧）

基本不该自己写的：  训练后端 / 推理后端 / 权重同步传输层 / 并行策略
                    （这些是 10,000+ 行起步、且和硬件强耦合的部分）
```

★ **这条分界线不是我编的，它是三家独立表述后收敛出来的同一条原则。** 它也解释了为什么 [06 章 §6.5](06-AgenticRL-环境与沙箱.md) 说「评测的 harness 和训练的 environment 是同一件东西的两面」—— **这一层本来就该是你自己的资产**：它编码的是你的业务、你的数据、你的评判标准，换框架时它应该能整体搬走。

## 7.5 · ⚠️ 一份务实的上手顺序

如果你从零开始，我会这样走：

| 时间 | 做什么 | 目标 | ★ 必须做的那一件事 |
|---|---|---|---|
| **第 1 周** | 跑通同步 PPO/GRPO，小模型（1.5B~7B）、短输出（< 2K），用 OpenRLHF | 不是效果，是把五个模块（[01 章 §1.1](01-格局全景.md)）都摸一遍 | 读 `openrlhf/cli/train_ppo_ray.py:660-700` 的参数断言 —— 那里写着哪些组合是非法的 |
| **第 2 周** | 把输出加长到 16K，观察生成时间占比 | 亲眼看到「生成占 80% 时间」（✅ OpenRLHF README 原文） | 此时才有资格讨论异步 |
| **第 3 周** | 开 `--train.async_enable`，`K_buf=1`、`K_sync=1` | 对比 reward 曲线，确认没崩 | 这一步验证的是你的过滤和掩码没写错，不是验证异步有多快 |
| **第 4 周** | 做训推一致性体检（§7.3 坑 2 的 PCC 三步） | 拿到一个 PCC 数字 | ⚠️ 这一步越早越好，很多人是第 8 周才发现问题 |
| **第 2 月** | 按 Q1/Q2 决定是否换 slime / veRL | — | 换的成本主要在数据和 reward，**不在框架 API** |

⚠️ **注意第 4 周那一条。** 训推一致性检查在教程里从来没人讲，但它是 [04 章](04-训推一致性.md) 整章存在的理由 —— ✅ 五家前沿报告里有四家专门写了这个问题。**它不是边角料，是主线。**

⚠️ 如果你要做 Agentic RL，在第 2 月之前再插一步：按 [06 章](06-AgenticRL-环境与沙箱.md) 的「账一」算一遍你的沙箱规模（轨迹数 × 步数 × 每步秒数），**在写第一行环境代码之前就知道自己要开多少个沙箱、要多少内存**。这笔账会直接决定你选容器还是 microVM。

| 结论 | 分级 |
|---|---|
| 选型的 80% 由「卡数 / 轨迹长度参差 / 改算法还是跑模型」三问决定 | ⚠️ 我的归纳 |
| ⚠️ **横切判断（国产卡 / Agentic / 特殊模型结构）会否决三问的结论**，要先过 | ⚠️ 我的归纳 |

| 训推不一致的表现是「不涨」而不是「报错」；用 PCC < 0.99 做体检 | ✅ openPangu + ⚠️ |

| ⚠️ **口径陷阱**：「时间减少 X%」≠「加速 X%」（`加速 = 1÷(1−减少比例)`）；比例作差用百分点；GB/s 与 Gb/s 差 8 倍 | ⚠️ 纪律 |
| ⚠️ **NVLink 900 GB/s 是双向聚合（单向 450）**，IB 400 Gb/s = 50 GB/s，同口径下 NVLink : IB = **9 倍不是 18 倍** | ⚠️ 本文更正 |
| 除「非 NVIDIA 硬件」外，四条自研触发条件在多数团队不成立 | ⚠️ 我的判断 |
