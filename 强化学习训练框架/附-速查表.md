### 3.1 传输层分层：NCCL / RDMA / NIXL / Mooncake 各在哪一层

这四个词在权重同步和 PD 分离的语境里经常混着出现，但它们**不在同一层**。一句话先定性：

> **NCCL 和 NIXL 是上层 API（定义「怎么传」的语义），RDMA 是下层传输能力（定义「数据实际怎么跑」），Mooncake 是一整套架构（自带传输引擎）。**

**语义层：上层调用的 API**

| | NCCL / HCCL | NIXL | Mooncake |
|---|---|---|---|
| **是什么** | 集合通信库 | 点对点传输抽象 | KVCache 架构 |
| **提供什么** | Broadcast / AllReduce | 多后端插件 | 传输引擎 + 存储 + 调度 |
| **一句话** | 「一群 GPU 一起传」 | 「把 A 搬到 B」 | 「池化整个集群」 |
| **往下接谁** | 直接落到传输层 | 经 **UCX** 落到传输层 | 自带传输引擎，落到传输层 |

```
       NCCL/HCCL            NIXL             Mooncake
           |                  |                  |
           |              +---------+            |
           |              |   UCX   |            |
           |              +---------+            |
           |                  |                  |
           v                  v                  v
    ----------------- 传输层：数据实际怎么跑 -----------------
```

**传输层：数据实际怎么跑**

| 范围 | 用什么 | 备注 |
|---|---|---|
| **跨机** | RDMA（InfiniBand 或 RoCE） | ⚠️ 没有 RDMA 网卡则退化成 TCP |
| | └ **GPUDirect RDMA** | 网卡**直接读写 GPU 显存**，不过主机内存 |
| **机内** | NVLink / NVSwitch、PCIe P2P、共享内存、CUDA IPC | 一点 RDMA 都不沾 |

⚠️ 三个最容易混的点：

| # | 常见误解 | 实际情况 |
|---|---|---|
| 1 | 「NCCL 属于 RDMA」 | **不属于。** NCCL 是软件库（定义「一群 GPU 怎么一起传」），RDMA 是传输能力。NCCL 跨机时确实走 RDMA，但机内 8 卡走的是 NVLink，一点 RDMA 都不沾；没有 RDMA 网卡时它退化成 TCP 照样能跑。反过来 RDMA 也不需要 NCCL，MPI / UCX / Mooncake 都直接调它 |
| 2 | 「GPU 的 RDMA 和 CPU 的 RDMA 是两种 RDMA」 | **只有一种。** 搬数据的永远是网卡，区别只在缓冲区在显存(HBM)还是主机内存(DRAM)。**线速上限完全一样**；GPUDirect 快在省掉 2 趟 PCIe 拷贝、不占主机内存带宽、CPU 全程不参与。⚠️ 但网卡和 GPU 若分属不同 CPU socket，点对点要穿 UPI，性能会断崖下跌——`nvidia-smi topo -m` 看到 `SYS` 就该警觉，看到 `PIX`/`PXB` 才是好的 |
| 3 | 「NIXL 和 Mooncake 二选一」 | **不是竞争关系。** NIXL 的后端插件列表里就有 `MOONCAKE`，可以把 Mooncake 当成自己的一条腿 |

**为什么权重同步要绕开 NCCL 另做后端？**

| | NCCL 集合通信 | RDMA 点对点（NIXL / Mooncake） |
|---|---|---|
| 参与方约束 | 所有 rank 必须**同时在线、同步进场**凑齐一个 communicator | 谁准备好谁拉，**推理实例可随时扩缩容** |
| 适合 | 同步架构、固定拓扑 | 异步架构、弹性推理池 |

⚠️ 归纳：这正是 [03-权重同步.md](03-权重同步.md) 里 veRL 要做六个 checkpoint engine 后端的根本原因——异步 RL 不想被「所有人必须同时到齐」卡住。

**三者的出身**

| | 出品方 | 定位 |
|---|---|---|
| **NCCL** | NVIDIA | GPU 集合通信标准库 |
| **NIXL** | NVIDIA，2025 年 GTC 开源，仓库 `ai-dynamo/nixl`（Dynamo 推理框架的数据平面） | 多后端点对点传输抽象层 |
| **Mooncake** | **月之暗面 Moonshot AI + 清华大学 MADSys 实验室**，论文获 USENIX FAST '25 最佳论文 | Kimi 线上推理平台；开源了 Transfer Engine（RDMA 传输层）+ Mooncake Store（分布式 KV Cache） |

> ✅ 本地实测：[源码/slime/](源码/slime/) 的 `tests/test_qwen3.6_35B_A3B_pd_mooncake.py:105` 里有 `--sglang-disaggregation-transfer-backend mooncake`——说明 slime 用 Mooncake 不只是同步权重，rollout 阶段 SGLang 的 PD 分离也走它。
> 🌐 来源：[ai-dynamo/nixl](https://github.com/ai-dynamo/nixl)、[Mooncake 论文 arXiv:2407.00079](https://arxiv.org/abs/2407.00079)、[USENIX FAST '25](https://www.usenix.org/conference/fast25/presentation/qin)，访问于 2026-09。

## 七、四笔可以自己验算的账

> 这一节不是查表，是**动笔算**。每笔账都给出「单位 → 代数字 → 交叉验算」三步，照着走一遍就不会记错。全目录凡是出现这几类数字的地方，口径都和这里一致。

### 7.1 权重同步的传输账：7B / 70B 要传多久

**第 0 步 · 两个单位陷阱必须先过**：

| 陷阱 | 错的写法 | 对的写法 | 差多少 |
|---|---|---|---|
| **NVLink 的 900** | 「NVLink 900 GB/s」直接拿来除 | **900 是双向聚合值**，单向是 **450 GB/s** | 2 倍 |
| **InfiniBand 的 400** | 「IB 400 GB/s」 | **400 是 Gb（比特）不是 GB（字节）**，÷ 8 = **50 GB/s** | 8 倍 |

⚠️ **这两个陷阱叠在一起，会把真实的 9 倍差距算成 18 倍。** 同单位下的正确比值：

```
NVLink : IB = 450 GB/s : 50 GB/s = 9 倍      <-- 对
                900    :  400    = 2.25 倍   <-- 错（混了单位，又混了双向/单向）
                900    :   50    = 18 倍     <-- 错（只改对了一半）
```

**第 1 步 · 算权重字节数**（BF16 = Brain Float 16，每个参数 2 字节）：

| 模型 | 参数量 | × 2 字节 | 权重大小 |
|---|---|---|---|
| 7B | 7 × 10⁹ | 14 × 10⁹ B | **14 GB** |
| 70B | 70 × 10⁹ | 140 × 10⁹ B | **140 GB** |

> ⚠️ 本节统一用十进制 GB（10⁹ 字节），和带宽的 GB/s 对齐。若用二进制 GiB（2³⁰ 字节），14 GB = 13.04 GiB——**换算差 7%，不影响量级，但别在同一个式子里混用。**

**第 2 步 · 除以带宽**：

```
7B，走 NVLink：   14 GB ÷ 450 GB/s = 0.0311 s = 31.1 ms
7B，走 IB：       14 GB ÷  50 GB/s = 0.280  s =  280 ms
70B，走 NVLink： 140 GB ÷ 450 GB/s = 0.311  s =  311 ms
70B，走 IB：     140 GB ÷  50 GB/s = 2.80   s =  2.80 s
```

**第 3 步 · 交叉验算**（两种算法应得同一个答案）：

```
按比值算： 280 ms ÷ 31.1 ms = 9.00     ✓ 等于 450 ÷ 50
按规模算： 311 ms ÷ 31.1 ms = 10.0     ✓ 等于 70B ÷ 7B
最贵那格： 2.80 s ÷ 31.1 ms = 90.0     ✓ 等于 9 × 10
```

**结果表**：

| | 7B（14 GB） | 70B（140 GB） |
|---|---|---|
| **NVLink 单向 450 GB/s**（机内） | 31.1 ms | 311 ms |
| **IB 400 Gb/s = 50 GB/s**（跨机） | 280 ms | **2.80 s** |
| 倍数 | 9× | 9× |

⚠️ **这四个数字全是理论下界**，只数「字节 ÷ 带宽」。真实耗时还要加上：① resharding（重切分，训练态的 TP/PP 切法转成推理态的切法）；② 推理引擎重建 KV cache 池；③ 排空在飞的生成。⚠️ 社区报告的落点从亚秒到数秒都有，**差异来自实现而非带宽，必须在自己的框架上测**，本表不给具体数字。

⚠️ **什么时候这笔账才要紧**：把它和「这一轮 rollout 用了多久」放在同一个分母上比。按 [大模型算子开发/10-RL算子.md](../大模型算子开发/10-RL算子.md) §10.9.2，8B 规模下同机同步只占一次迭代的 0.07%、跨机 0.6%——**通常不是瓶颈**。它变成问题只有两种场合：**（a）每轮 rollout 很短**（小 batch、短 response，分母小了），**（b）模型很大且必须跨机**（70B 跨机 2.80 s，若迭代本身只有 30 s 就接近 10%）。

### 7.2 显存账：16 字节 / 参数

**第 1 步 · 混合精度 AdamW 训练，一个参数要留五份东西**：

| # | 内容 | 精度 | 字节/参数 |
|---|---|---|---|
| ① | 权重 | BF16 | 2 |
| ② | 梯度 | BF16 | 2 |
| ③ | FP32 主副本（master weights） | FP32 | 4 |
| ④ | Adam 的 **m**（一阶动量） | FP32 | **4** |
| ⑤ | Adam 的 **v**（二阶动量） | FP32 | **4** |
| | **训练态合计** | | **16** |

⚠️ **最高频的错是漏掉 m 和 v 里的一个。** Adam 要存**两个**动量，各 4 字节：

```
正确：2 + 2 + 4 + 4 + 4 = 16 字节/参数  -->  7B × 16 =  112 GB
漏一个：2 + 2 + 4 + 4   = 12 字节/参数  -->  7B × 12 =   84 GB   <-- 错，少了 28 GB
```

**第 2 步 · 乘参数量**：

| 角色 | 字节/参数 | 7B | 70B |
|---|---|---|---|
| Actor（训练态） | 16 | **112 GB** | **1120 GB** |
| Reference（冻结，只前向） | 2 | 14 GB | 140 GB |
| Reward Model（同尺寸，冻结） | 2 | 14 GB | 140 GB |
| **rollout 引擎的那一份权重副本** | 2 | **14 GB** | **140 GB** |
| Critic / Value Model（**只 PPO 需要**，训练态） | 16 | **112 GB** | **1120 GB** |

**第 3 步 · 按算法合账**（⚠️ 别忘了 rollout 引擎那一份——这是 RL 比纯预训练多出来的一块）：

```
GRPO（无 Critic）：
  7B ：112（Actor）+ 14（Ref）+ 14（rollout 副本）             = 140 GB
  70B：1120        + 140      + 140                            = 1400 GB

PPO（有 Critic）：
  7B ：112 + 112（Critic）+ 14 + 14                            = 252 GB
  70B：1120 + 1120        + 140 + 140                          = 2520 GB
```

**第 4 步 · 换算成卡数**（H100 SXM5 单卡 HBM3 **80 GB**，8 卡一机 = 640 GB）：

```
7B  + GRPO：140 GB  / 640 GB = 21.9%  -->  一机绰绰有余，剩 500 GB 给激活和 KV cache
7B  + PPO ：252 GB  / 640 GB = 39.4%  -->  一机够用
70B + GRPO：1400 GB -->  光放状态就要 ceil(1400/80) = 18 张卡，实际 32 张起
70B + PPO ：2520 GB -->  光放状态就要 ceil(2520/80) = 32 张卡，实际 48 张起
```

⚠️ 「实际 N 张起」里的余量是给**激活**和 **KV cache** 的，这两块都随 batch 和序列长度变，不在「每参数多少字节」这个口径里。

> ★ **Critic 是 PPO 最贵的一件行李**：7B 规模下它一个人就占 112 GB，和 Actor 一样重，等于把显存需求翻倍。这才是 GRPO（以及 RLOO、REINFORCE++ 等去 critic 算法）在大模型上迅速普及的第一位原因，优势公式简单只是副产品。对照 [slime拆解.md](slime拆解.md) §10.1 和 [OpenRLHF拆解.md](OpenRLHF拆解.md) §8.1：**两家框架的六个优势估计器里，都只有 PPO 那一个需要 critic。**

> ★ **记住「16 字节 / 参数」这个口径，比记任何具体 GB 数都有用**——换模型直接乘。冻结模型是 2，训练态是 16，**比值正好 8 倍**。

### 7.3 「时间减少 X%」≠「加速 X%」

**两个方向的公式**：

```
加速倍数   = 1 / (1 − 时间减少比例)
时间减少比例 = 1 − 1 / 加速倍数
```

**对照表**（⚠️ 左右两列不是一回事，差距在高档位会非常大）：

| 时间减少 | 加速倍数 | 口语上常被误说成 |
|---|---|---|
| 10% | 1.11× | 「加速 10%」（勉强接近） |
| 20% | 1.25× | 「加速 20%」（已经差 5 个百分点） |
| 25% | 1.33× | 「加速 25%」 |
| 33.3% | **1.50×** | 「加速 33%」（实际是 50%） |
| 36.0% | 1.56× | — |
| 50% | **2.00×** | 「加速 50%」（实际是**翻倍**） |
| 75% | **4.00×** | 「加速 75%」（实际是 **4 倍**） |
| 90% | **10.0×** | 「加速 90%」（实际是 **10 倍**） |

**反过来**：

| 加速倍数 | 时间减少 |
|---|---|
| 1.25× | 20.0% |
| 1.50× | 33.3% |
| 2.00× | 50.0% |
| 3.00× | 66.7% |
| 10.0× | 90.0% |

⚠️ **判断一句话该套哪个公式，只看它的分母是什么**：

| 说法 | 分母是 | 该用哪个口径 |
|---|---|---|
| 「耗时从 50 s 降到 32 s」 | **原耗时 50 s** | 时间减少 36% |
| 「吞吐从 100 样本/s 涨到 156」 | **原吞吐 100** | 加速 1.56 倍 |

**一个本目录里的实例**（取自 [slime拆解.md](slime拆解.md) §4.2 的推演）：

```
同步档一次迭代 50.6 s，单步异步档 32.4 s

时间减少 = 1 − 32.4/50.6 = 36.0%
加速倍数 = 50.6/32.4      = 1.56 倍
验算     = 1/(1 − 0.360)  = 1.5625  ✓
```

⚠️ **说「异步让 RL 加速了 36%」是错的**，正确说法是「**迭代时间减少 36%**」或「**加速 1.56 倍**」。

### 7.4 百分比 vs 百分点

| 术语 | 什么时候用 | 例子 |
|---|---|---|
| **百分点**（percentage point，pp） | 两个**百分数相减** | 训练卡利用率从 34.8% 升到 64.0%，**升了 29.2 个百分点** |
| **百分比**（percent, %） | 一个量**相对自己**的变化 | 同一件事：64.0 ÷ 34.8 − 1 = **相对提升 83.9%** |

```
34.8%  -->  64.0%

说「提升了 29.2 个百分点」    ✓ 对
说「提升了 83.9%」            ✓ 对（相对口径）
说「提升了 29.2%」            ✗ 错——把百分点说成了百分比
说「提升了 83.9 个百分点」    ✗ 错——反过来也不行
```

⚠️ **一个判别诀窍**：两个数都带 % 号，相减得到的**一定是百分点**；只有「变化量 ÷ 原值」才是百分比。

⚠️ 这条在 MFU（Model FLOPs Utilization，模型算力利用率）和 Occupancy（占用率）这类本身就是百分数的指标上最容易出错，对照 [大模型算子开发/01-GPU硬件基础.md](../大模型算子开发/01-GPU硬件基础.md) §1.6.2 里「Occupancy 从 75% 掉到 62.5%，**掉了 12.5 个百分点**」的写法。

### 8.1 H100 SXM5（稠密口径）

| 项目 | 数值 | 备注 |
|---|---|---|
| **BF16 / FP16 算力** | **989 TFLOPS** | ⚠️ **稠密值**。见 8.2 |
| FP8 算力 | 1979 TFLOPS | 稠密值 |
| FP32（CUDA Core） | 67 TFLOPS | 不走 Tensor Core |
| **显存容量** | **80 GB** | HBM3 |
| **显存带宽** | **3.35 TB/s** | HBM3 |
| NVLink 4.0 单向 | **450 GB/s** | ⚠️ 900 GB/s 是双向聚合值 |
| PCIe 5.0 ×16 单向 | 63 GB/s 理论 / ⚠️ 约 50 GB/s 实测 | — |
| 8 卡一机 | 8 × 989 = **7.912 PFLOPS** · 640 GB | — |

> ⚠️ **HBM = High Bandwidth Memory（高带宽显存）**；**HBM3** 是 H100 SXM5 用的那一代。**SXM** 是 NVIDIA 的服务器 GPU 模组规格（对比 PCIe 插卡版，SXM 版功耗上限更高、带 NVLink）。

### 8.2 ⚠️ 1979 这个数字的两个身份，别搞混

```
NVIDIA 官方规格表里每个精度都有【稠密 / 稀疏】两列，稀疏值 = 稠密值 × 2：

  BF16 稠密  989 TFLOPS   <-- 常规算子用这个，本目录统一口径
  BF16 稀疏 1979 TFLOPS   <-- 要求权重满足 2:4 结构化稀疏才能达到
  FP8  稠密 1979 TFLOPS   <-- 和上面一行数值相同，但精度不同！
  FP8  稀疏 3958 TFLOPS
```

⚠️ **1979 同时是「BF16 的稀疏值」和「FP8 的稠密值」**，所以光看数字判断不了口径——**必须同时说精度和稠密/稀疏**。⚠️ 把 BF16 的稀疏值 1979 当稠密用，会把所有基于算力的推演都算错一半。

> ⚠️ **2:4 结构化稀疏** = 每连续 4 个权重里必须有 2 个是零，且零的位置要符合硬件规定的模式。常规训练出来的稠密权重**不满足**这个条件，RL 训练里基本用不上。

### 8.3 带宽换算速查

| 写法 | 换成 GB/s | 场合 |
|---|---|---|
| InfiniBand / RoCE **400 Gb/s** | ÷ 8 = **50 GB/s** | 跨机 |
| InfiniBand **200 Gb/s** | ÷ 8 = **25 GB/s** | 老一代跨机 |
| 以太网 **100 Gb/s** | ÷ 8 = **12.5 GB/s** | 没有 RDMA 网卡时 |
| NVLink 4.0「900 GB/s」 | ÷ 2 = **450 GB/s** 单向 | 机内 |
| HBM3「3.35 TB/s」 | = **3350 GB/s** | 卡内 |

⚠️ **两条规矩**：① **小写 b 是 bit（比特），大写 B 是 Byte（字节）**，网络厂商标 Gb、存储厂商标 GB，差 8 倍；② **互联总线的大数通常是双向聚合值**，算单向传输要除以 2。这两条踩错任意一条，结论就差 2 倍以上。

| **Split-K** | — | K 维切分 | GEMM 优化手段：把归约维切成几段并行算再相加。⚠️ **切几段会改变累加顺序** | [大模型算子开发/11-训推一致性算子层.md](../大模型算子开发/11-训推一致性算子层.md) |
| **PagedAttention** | — | 分页注意力 | KV cache 按页按需分配，不为最坏长度预留 | [大模型算子开发/09-推理侧算子.md](../大模型算子开发/09-推理侧算子.md) |

### 9.4 ⚠️ 三个最容易混的缩写对

| 容易混的一对 | 区别 |
|---|---|
| **TIS** vs **icepop** | 都是 IS 修正，都看重要性比值是否超界。**TIS 把超界的比值压回阈值（样本保留）**；**icepop 把超界的 token 置零（样本部分丢弃）**。✅ 两者在 slime `loss.py` 里是 `vanilla_tis_function`（883 行）和 `icepop_function`（907 行）两个独立函数 |
| **CP** vs **PP** | **CP（上下文并行）切的是序列长度维**，每张卡拿同一层的不同 token；**PP（流水线并行）切的是层**，每张卡拿不同层的全部 token |
| **MTP 层** vs **外部 draft model** | 两种投机解码的草稿来源。**MTP 层**和主模型在同一个 checkpoint 里（多出来几层）；**外部 draft model** 是独立的小模型。✅ slime 对前者支持在线训练（`--enable-mtp-training`），对后者文档自陈 WIP——区别见 [MILES拆解.md](MILES拆解.md) §2.4 |
