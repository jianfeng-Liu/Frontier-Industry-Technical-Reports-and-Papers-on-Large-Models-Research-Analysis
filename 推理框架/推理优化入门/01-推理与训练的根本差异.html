01 推理和训练到底差在哪

一句话：训练是算力不够用，推理是内存带宽不够用。这一条差异，决定了后面十二章的全部内容。

1.1 先看一个反直觉的现象

你用一张 H100 跑一个 7B/8B（70~80 亿参数）模型，同一张卡、同一个模型、同样的 BF16 精度：

场景 一次前向处理多少 token 算力利用率 显存带宽利用率
训练 8 × 4096 = 32768 40%~50%（⚠️ 公开报告的顶级水位） 远低于 100%
推理 · Decode（一次只服务一个用户） 1 0.34% ≈ 100%

算力利用率差了 100 多倍。卡没坏，是这件事本身的性质变了。

⚠️ 先把最容易误读的一点说清楚：上面右边那一列不是排版错误。Decode 的算力利用率只有千分之三，但它的显存带宽已经跑满了。这张卡没有在偷懒——它已经跑到硬件的物理上限，只是上限换到了另一条边上。「算力利用率低」在这里不是浪费，而是访存受限（Memory Bound）这件事的定义本身。整章后面所有的账，都建立在「哪一条边先到顶」这个判断上。

本章要做的就是把 0.34% 这个数字算出来，不是记住它。（左边那个 40%~50% 是训练侧的 MFU 水位，⚠️ 属于公开报告披露的经验值，不是能从硬件参数推出来的——推导和口径见 大模型算子开发/02 章 §2.6。）

1.2 差异的根源：一次前向要搬多少、要算多少

先定义两个词（第一次出现，给全称）：

📖 FLOPs（FLoating point OPerations，浮点运算次数）——「要算多少」。
📖 访存量 / MOPs（Memory OPerations，内存访问字节数）——「要从显存搬多少字节到计算单元」。
📖 算术强度（arithmetic intensity）——「每搬 1 个字节，配了多少次运算」，单位 FLOP/Byte。这是全书最重要的一个比值。

一个参数量为 Ψ（希腊字母 psi，代表参数个数）的稠密模型，跑一次前向传播，这一批里有 B 个 token：

要算：  ≈ 2 × Ψ × B  FLOPs
         ★ 每个参数参与一次乘、一次加 = 2 次运算，每个 token 都要走一遍全部权重

要搬：  ≈ 2 × Ψ  字节            （BF16，每参数 2 字节）
         ★★ 关键：不管这一批有 1 个 token 还是 1000 个 token，
            权重都只需要【搬一遍】—— 搬进来之后，B 个 token 共用它

于是有一个决定性的结论：

算术强度 = FLOPs ÷ 访存字节
         = (2 × Ψ × B) ÷ (2 × Ψ)
         = B

★★ 算术强度 ≈ 这一批的 token 数。一句话记住它。
   注意 Ψ 被约掉了 —— 模型多大都不影响这个比值，只有 B 影响。

⚠️ 这个式子只算了权重的搬运量。 推理还要搬 KV Cache，它和 B 成正比、不会被摊薄，所以上面这条「算术强度 = B」在 B 很大时会偏乐观。补全的账在 02 章 §2.6，那里会看到 B 大到一定程度后收益是怎么塌下来的。本章先用这个简化版建立直觉。

1.3 把这个数字和硬件对上

每张 GPU 都有一个「算力 / 带宽平衡点」，超过它才可能吃满算力。这个点叫屋脊点（ridge point）：

NVIDIA H100 SXM5（本系列统一基准）：
    BF16 稠密算力  = 989 TFLOP/s    （⚠️ 不是 1979 —— 那是带 2:4 稀疏的数字）
    HBM3 显存带宽  = 3.35 TB/s      （80 GB HBM3）

    屋脊点 = 989 × 10¹² ÷ (3.35 × 10¹²) ≈ 295 FLOP/Byte
                                            ↑ 常被四舍五入说成「约 300」

★ 含义：只有当算术强度 > 295 时，GPU 才【可能】吃满算力。
  低于这个数，GPU 一定在等数据，性能上限 = 带宽 × 算术强度。

现在把不同的 B 代进去，逐行算出来（屋顶线上限 = min(989, 3.35 × B) TFLOPS）：

场景 B（这一批的 token 数） 算术强度 = B 性能上限 = 3.35 × B 封顶后 占 989 TFLOPS 瓶颈
Decode，batch=1 1 1 3.35 TFLOPS 3.35 0.34% ❌ 访存受限
Decode，batch=8 8 8 26.8 26.8 2.7% ❌ 访存受限
Decode，batch=64 64 64 214 214 21.7% ❌ 访存受限
Decode，batch=295 295 295 989 989 100% ⚖️ 正好在屋脊点
Prefill，2000 token 的 prompt 2000 2000 6,700 989（封顶） 100% ✅ 算力受限
训练，batch 8 × 序列 4096 32768 32768 ≈ 110,000 989（封顶） 100% ✅ 算力受限

三件事从这张表里直接读出来：

① §1.1 那个 0.34% 是算出来的，不是测出来的。 3.35 ÷ 989 = 0.34%。它是 batch=1 解码在 H100 上的理论上限——写得再好的 kernel 也不可能超过它。

② 「算力利用率」和「带宽利用率」必须分开说。 同一行的两个数字完全相反：

算力利用率 = 实际 FLOP/s ÷ 989 TFLOPS      → batch=1 解码时  0.34%
带宽利用率 = 实际 Byte/s ÷ 3.35 TB/s       → batch=1 解码时  ≈ 100%

★★ 看到「推理时 GPU 利用率只有 3%」这种说法，第一件事是问【哪个利用率】。
   如果是算力利用率，那 Decode 阶段本来就该这么低，这是物理规律；
   如果连带宽利用率也上不去，那才是真有问题（kernel 写得差、下发跟不上）。

③ 屋脊点 295 这个数，第 4 行看起来很诱人，但它是个陷阱。 「把 batch 做到 295 就能吃满算力」在纸上成立，实际做不到——batch 做大要显存装 KV Cache，02 章 §2.3 会逐行算出：一张 H100 跑 8B 模型、4K 长度的对话，最多只装得下 100~116 条。够不到 295，差 3 倍。 这个矛盾是全书的主线。

🔑 ★★ 一句话总结这一节：解码阶段每生成一个字，都要把整个模型的权重从显存里搬一遍，却只做 1 个 token 的计算。屋脊点要求每搬 1 字节配 295 次运算，而 batch=1 只配了 1 次。买来的算力，用上了 1/295。

⚠️ 训练那一行是个粗估：训练除了前向还有反向和激活值的读写，算术强度不完全等于 B。但量级上 32768 ≫ 295 的结论稳固，结论不变。严格的算术强度推导见 大模型算子开发/02 章 §2.2，屋顶线模型见同章 §2.4。

1.4 那怎么办？——这就是整本教程

既然瓶颈是「搬一次权重只干了一点活」，那所有优化都在做同一件事：

★★ 让「每搬一次权重」干更多的活 ★★

四条路，后面十二章全部挂在这四条路上：

路线 具体做法 在做什么 讲在哪
① 一次多塞几个用户 连续批处理（continuous batching） 把 B 从 1 做到几十上百 04 章
↳ 前提：显存要装得下 KV PagedAttention、前缀缓存 不浪费已分配的显存 05 章
↳ 前提：显存要装得下 KV MQA / GQA / MLA 让每个 token 的 KV 更小 07 章
↳ 前提：显存要装得下 KV KV Cache 量化 让每个 token 的 KV 更小 09 章
② 一次多吐几个字 投机解码（一次前向验证多个候选 token） 把 B 从 1 做到 4~8，不需要更多用户 08 章
③ 让权重本身变小 权重量化 FP8 / INT4 分母（搬运字节）直接减半、减到 1/4 09 章
④ 别让 CPU 拖后腿 CUDA Graph、图编译 B=1 时 kernel 太小，CPU 下发都来不及 12 章

★ 05、07、09 三章表面在讲「省显存」，实际全都是为了「把 B 做大」这一件事。 这是本教程的骨架，读到后面如果觉得散，回来看这张表。

⚠️ 第 ④ 条容易被算错账，先打个预防针：kernel 的启动开销不是每个 kernel 串行相加的——CPU 下发第 2 个 kernel 和 GPU 执行第 1 个是同时进行的，下发是流水化的。正确的判据是 耗时 ≈ max(kernel 数 × 单个下发成本 ⚠️约 2 µs, GPU 执行时间)。只有前者更大时（这叫 Host Bound，下发受限），CUDA Graph 才有收益；否则收益是零。展开见 12 章 和 大模型算子开发/01 章 §1.8.2。

1.5 第二个根本差异：没有反向传播

这一条看起来平淡，但它悄悄改掉了并行策略的全部成本模型。

训练一次迭代：  前向 → 反向 → 优化器更新
推理一次迭代：  前向                     ← ★ 就这么多

带来三个后果。

① 显存账完全不同

训练框架/02 章 那张著名的表说训练每个参数要 16 字节。把两边逐项列出来对比：

每个参数要存什么 训练（BF16 混合精度 + AdamW） 推理（BF16）
BF16 权重 2 字节 2 字节
BF16 梯度 2 字节 —
FP32 主权重 4 字节 —
Adam 一阶动量 m 4 字节 —
Adam 二阶动量 v 4 字节 —
合计 16 字节 / 参数 2 字节 / 参数
代入 8B 模型 128 GB（一张 H100 装不下） 16 GB（一张 H100 轻松装下） 
⟹ ★ 同一个模型，推理的【权重】显存是训练的 1/8
⟹ ⚠️ 但推理多了一个训练几乎没有的大头：KV Cache
   8B 模型在一张 H100 上，KV Cache 能占到 50~58 GB —— 比权重本身大 3 倍多。
   这笔账整个 02 章都在算。

② 张量并行的通信次数【减半】

📖 TP（Tensor Parallelism，张量并行）——把每一层的权重矩阵横着或竖着切开，分给多张卡，每张卡算一部分，再通信合并。
📖 all-reduce（全归约）——所有卡把各自的一份数据求和，结果人人都拿到一份完整的。

训练：每层 4 次 all-reduce
       前向 2 次（Attention 之后、MLP 之后）
       反向 2 次（对应位置回传输入梯度）

推理：每层 2 次 all-reduce
       只有前向那 2 次                    ← ★ 少一半

✅ 源码可查：vLLM 的 RowParallelLinear.forward 在 linear.py:1660 只有一句 tensor_model_parallel_all_reduce，整个类里没有任何反向的通信代码——因为推理不需要。训练侧每层 4 次的来源见 训练框架/06 章。

③ 数据并行的含义彻底变了

📖 DP（Data Parallelism，数据并行）——同一个模型复制 N 份，每份处理不同的数据。

训练的 DP 推理的 DP
N 份副本在干什么 算同一个模型的不同数据分片 服务互不相关的用户
每步之后要做什么 ★ 必须 all-reduce 梯度，否则 N 份权重会分叉 ★ 什么都不做，各算各的
每卡通信量 梯度 2Ψ 字节（BF16），ring all-reduce 每卡收发 ≈ 4Ψ 字节 ≈ 0
代价 【重】操作，必须放在带宽好的位置 【轻】操作，几乎免费

⚠️ 上面一行的单位要小心：本仓库在 训练框架/03 章 §3.3 里把 ring all-reduce 的每卡通信量写成「2Ψ」，那里的 Ψ 指梯度总字节数；本章的 Ψ 指参数个数。BF16 下梯度是 2Ψ 字节，所以换算过来每卡收发约 4Ψ 字节。两处都没错，是 Ψ 的口径不同——看到 2Ψ / 4Ψ 先确认它数的是元素还是字节。

★★ 记住这一条，06 章 会用它解释一个让人困惑的现象：训练里 PP（流水线并行）排在最外层、DP 排在中间；推理里反过来，DP 排最外层、PP 排里面。不是谁写错了，是 DP 的成本从「最贵」变成了「几乎免费」，于是它该被挪到通信最差的那一层去。

1.6 第三个差异：训练是离线的，推理是在线的

先给三个词：

📖 TTFT（Time To First Token，首字延迟）——用户按下回车，到看到第一个字，隔了多久。
📖 TPOT（Time Per Output Token，每字延迟）——第一个字之后，后面每个字之间隔多久。
📖 SLO（Service Level Objective，服务等级目标）——你对用户承诺的延迟上限，比如「TTFT 的 P99 不超过 2 秒」。
这三个词 13 章 会详细讲，先混个眼熟。

训练 推理
一个作业活多久 几周到几个月 几百毫秒到几十秒
同时有多少「客户」在等 0（没人盯着） 几万个真人
只关心什么 总吞吐（MFU、tokens/s） ★ TTFT + TPOT + 吞吐，三个一起
慢一点的后果 多跑两天，能接受 用户走了，违反 SLO
优化的目标函数 最大化吞吐 ★ 在 SLO 约束下最大化吞吐

这带来一个训练里完全不存在的矛盾：

★ 提吞吐的手段（把 batch 做大）会【伤害】延迟
   ——batch 大了，每一步搬的 KV 更多，一步走得更慢 ⟹ TPOT 变差（02 章 §2.6 会把这个算出来）

★ 降延迟的手段（batch 做小、多卡切细）会【伤害】吞吐
   ——batch 小了，权重摊不薄，回到 0.34% 那个状态

⟹ 推理系统的每一个设计，本质都是在这条线上选一个点。
⟹ [10 章](10-PD分离.md) 的 PD 分离，就是发现
   「Prefill 和 Decode 这两件事根本不该在同一台机器上做」。

1.7 本章小结

# 结论 关键数字（H100 SXM5，BF16）
① 算术强度 ≈ 这一批的 token 数 B，要 > 295 FLOP/Byte 才吃得满算力 989 TFLOPS ÷ 3.35 TB/s = 295
② 训练算力受限（B ≈ 32768），Prefill 算力受限（B ≈ 几千），Decode 访存受限（B = 1） Decode batch=1 算力利用率 = 3.35 ÷ 989 = 0.34%
③ ★★ 但 Decode 的带宽利用率 ≈ 100%。算力低不是浪费，是 Memory Bound 的定义 两个利用率必须分开说
④ 所有推理优化都在做同一件事：让「搬一次权重」干更多的活 四条路见 §1.4 的表
⑤ 没有反向传播 ⟹ 权重显存 1/8、TP 通信 减半、DP 通信量 ≈ 0 16 字节/参数 → 2 字节/参数
⑥ ⟹ 并行策略的成本模型和训练不一样，不能照搬 06 章
⑦ 在线服务 ⟹ 多了「延迟 vs 吞吐」这条永恒的取舍线 TTFT / TPOT / SLO，13 章

自测三题（答案在对应小节）

  1. 一张 H100 跑 70B 模型（BF16），batch=1 解码。算术强度是多少？算力利用率上限是多少？换成 7B 模型，这两个数会变吗？
  2. 有人说「我们的推理服务 GPU 利用率只有 4%，浪费太严重了」。你要追问他哪一个数字，才能判断这是不是真的浪费？
  3. 训练 8B 模型（BF16 + AdamW）和推理 8B 模型，权重相关的显存分别是多少？为什么推理反而可能更吃紧？

参考答案

  1. 算术强度 = B = 1 FLOP/Byte，和模型大小无关（§1.2 里 Ψ 被约掉了）。算力利用率上限 = 3.35 TB/s × 1 FLOP/Byte ÷ 989 TFLOPS = 0.34%。换成 7B 完全不变——这正是「算术强度 ≈ B」这个式子最反直觉也最有用的地方：模型大小只影响绝对耗时（70B 每步搬 140 GB、7B 搬 14 GB），不影响利用率。参见 §1.2、§1.3。
  2. 追问是算力利用率还是带宽利用率。如果是算力利用率，Decode 阶段 4% 对应 batch ≈ 12，属于正常偏小，问题是 batch 上不去（去查 KV Cache 够不够、调度器有没有攒够请求），不是 kernel 慢；如果连带宽利用率都只有 4%，那才是真问题——大概率是 Host Bound（CPU 下发跟不上）或 kernel 实现差。参见 §1.1、§1.3 第 ② 点。
  3. 训练 = 8B × 16 字节 = 128 GB（一张 80 GB H100 装不下，必须切多卡）；推理 = 8B × 2 字节 = 16 GB。推理更吃紧是因为它多了 KV Cache 这一项，而且 KV Cache 随并发数和序列长度线性增长，很快超过权重本身。参见 §1.5 ①，详细账见 02 章。
