# 01 推理和训练到底差在哪

> **一句话**：训练是**算力**不够用，推理是**内存带宽**不够用。这一条差异，决定了后面十二章的全部内容。

---

## 1.1 先看一个反直觉的现象

你用一张 H100 跑一个 7B（70 亿参数）模型：

```
    ★ 训练时：GPU 的算力利用率能到 40%~50%
    ★ 推理时（一次只服务一个用户）：算力利用率常常【不到 1%】
```

同一张卡，同一个模型，差了 50 倍。**卡没坏，是这件事本身的性质变了。**

---

## 1.2 差异的根源：一次前向要搬多少、要算多少

先定义两个词（第一次出现，给全称）：

> 📖 **FLOPs**（**FL**oating point **OP**eration**s**，浮点运算次数）——「要算多少」。
> 📖 **访存量 / MOPs**（**M**emory **OP**eration**s**，内存访问字节数）——「要从显存搬多少数据到计算单元」。

一个参数量为 **Ψ**（希腊字母 psi，代表参数个数）的稠密模型，跑**一次**前向传播：

```
    要算：  ≈ 2Ψ FLOPs  × （这一批有多少个 token）
             ★ 每个参数参与一次乘、一次加 = 2 次运算

    要搬：  ≈ 2Ψ 字节（BF16 每参数 2 字节）
             ★★ 关键：不管这一批有 1 个 token 还是 1000 个 token，
                权重都只需要【搬一遍】
```

于是有一个决定性的比值：

```
    算术强度（arithmetic intensity）
        = FLOPs ÷ 访存字节
        = (2Ψ × B) ÷ (2Ψ)
        = B                              ← B 就是这一批的 token 数

    ★★ 算术强度 ≈ 批大小。一句话记住它。
```

---

## 1.3 把这个数字和硬件对上

每张 GPU 都有一个「性价比平衡点」——算力除以带宽：

```
    ⚠️ 演示用的量级（各家公开规格，具体数字随型号/精度而变）

    NVIDIA H100 (SXM)：  BF16 算力 ≈ 990 TFLOP/s
                         显存带宽 ≈ 3.35 TB/s
                         ⟹ 平衡点 ≈ 990e12 / 3.35e12 ≈ 300

    ★ 含义：只有当算术强度 > ~300 时，GPU 才可能吃满算力。
      低于这个数，GPU 一定在【等数据】，算力空转。
```

现在把训练和推理代进去：

| | 一批处理多少 token | 算术强度 | 瓶颈在哪 |
|---|---|---|---|
| **训练** | batch 8 × 序列 4096 = **32768** | ~32768 ≫ 300 | ✅ **算力受限**（compute-bound） |
| **推理 · Prefill**（读 prompt） | 一个 2000 字的 prompt = **2000** | ~2000 > 300 | ✅ **算力受限** |
| **推理 · Decode**（吐字） | **1**（一次只生成一个 token） | **~1** ≪ 300 | ❌ **访存受限**（memory-bound） |

> 🔑 **★★ 这就是那 50 倍的来源。**
> 解码阶段每生成一个字，都要把**整个模型的权重**从显存里搬一遍，却只做 **1 个 token** 的计算。
> 300 倍的算力买了，只用上 1/300。

---

## 1.4 那怎么办？——这就是整本教程

既然瓶颈是「搬一次权重只干了一点活」，那所有优化都在做同一件事：

```
    ★★ 让「每搬一次权重」干更多的活 ★★

    办法一：一次多塞几个用户进来（把 B 从 1 变成 256）
            → 连续批处理                          （04 章）
            → 但 B 变大的前提是显存装得下 KV Cache
              → PagedAttention、前缀缓存           （05 章）
              → MQA / GQA / MLA                    （07 章）
              → KV Cache 量化                      （09 章）
            ★ 你会发现 05、07、09 三章表面在讲省显存，
              实际全都是为了「把 B 做大」这一件事。

    办法二：一次多吐几个字（一次前向验证 4 个候选 token）
            → 投机解码                             （08 章）

    办法三：让权重本身变小，搬得更快
            → 权重量化 FP8 / INT4                  （09 章）

    办法四：别让 CPU 拖后腿（B=1 时 GPU kernel 太小，CPU 派发都来不及）
            → CUDA Graph、图编译                   （12 章）
```

---

## 1.5 第二个根本差异：没有反向传播

这一条看起来平淡，但它悄悄改掉了并行策略的全部成本模型。

```
    训练一次迭代：  前向 → 反向 → 优化器更新
    推理一次迭代：  前向                     ← ★ 就这么多
```

带来三个后果：

**① 显存账完全不同。**
[训练框架/02 章](../../训练框架/分布式训练入门/02-显存去哪了.md) 那张表说训练每个参数要 **16 字节**（参数 + 梯度 + Adam 的两个动量 + FP32 主权重）。推理呢：

```
    推理每个参数：   2 字节（BF16 权重）        ★ 就这些
    没有梯度、没有优化器状态、没有 FP32 主权重

    ⟹ ★ 同一个模型，推理的权重显存是训练的【1/8】
    ⟹ ⚠️ 但推理多了一个训练几乎没有的大头：KV Cache（02 章）
```

**② 张量并行的通信次数【减半】。**

```
    训练：每层 4 次 all-reduce（前向 2 次 + 反向 2 次）
    推理：每层 2 次 all-reduce（只有前向）      ← ★ 少一半

    ✅ 源码可查：vLLM 的 RowParallelLinear 在
       [linear.py:1660](../源码/vLLM/vllm/model_executor/layers/linear.py#L1660)
       只有一句 tensor_model_parallel_all_reduce，没有任何反向的通信。
```

**③ 数据并行的含义彻底变了。**

```
    训练的 DP：  N 份副本算不同数据 → ★ 每步必须 all-reduce 梯度同步
                 ⟹ 通信量 2Ψ，是个【重】操作

    推理的 DP：  N 份副本服务不同用户 → ★ 各算各的，【不需要同步】
                 ⟹ 通信量 ≈ 0，是个【轻】操作
```

> ★★ **记住这一条，06 章会用它解释一个让人困惑的现象**：
> 训练里 PP（流水线并行）排在最外层、DP 排中间；
> 推理里反过来，DP 排最外层、PP 排里面。
> **不是谁写错了，是 DP 的成本从「最贵」变成了「几乎免费」。**

---

## 1.6 第三个差异：训练是离线的，推理是在线的

```
    训练：  一个作业跑两个月，只关心【总吞吐】（MFU、tokens/s）
            ★ 慢一点没关系，只要不崩

    推理：  几万个用户同时在等，关心两件事：
            ① 我等了多久才看到第一个字？   → TTFT
            ② 后面的字吐得够不够快？       → TPOT
            ★ 而且要在【承诺的延迟上限（SLO）】内，还要吞吐尽量高
```

> 📖 **TTFT**（**T**ime **T**o **F**irst **T**oken，首字延迟）
> 📖 **TPOT**（**T**ime **P**er **O**utput **T**oken，每字延迟）
> 📖 **SLO**（**S**ervice **L**evel **O**bjective，服务等级目标——你对用户承诺的延迟上限）
> 这三个词 13 章会详细讲，先混个眼熟。

**这带来一个训练里完全不存在的矛盾**：

```
    ★ 提吞吐的手段（把 batch 做大）会【伤害】延迟
    ★ 降延迟的手段（batch 做小、多卡切细）会【伤害】吞吐

    ⟹ 推理系统的每一个设计，本质都是在这条线上选一个点。
    ⟹ 10 章的 PD 分离，就是发现「这两件事根本不该在同一台机器上做」。
```
