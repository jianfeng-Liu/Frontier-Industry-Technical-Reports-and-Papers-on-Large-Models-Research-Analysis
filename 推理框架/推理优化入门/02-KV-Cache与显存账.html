02 KV Cache 与显存账本

一句话：推理时显存被三样东西吃掉——权重（固定）、KV Cache（随用户数暴涨）、激活值（很小）。能同时服务多少用户，几乎完全由 KV Cache 决定。

2.1 为什么需要 KV Cache

先回忆注意力（Attention）在算什么。对第 t 个 token：

Q_t（Query，查询）要和【前面所有 token】的 K（Key，键）做点积，
再用得到的权重去加权【前面所有 token】的 V（Value，值）。

Attention(Q_t) = softmax( Q_t · [K_1 ... K_t]ᵀ / √d ) · [V_1 ... V_t]
                                 ↑ 需要历史          ↑ 需要历史

关键观察：第 t 步用到的 K_1..K_{t-1}，和第 t-1 步用到的完全是同一批数字。它们只取决于历史 token，不取决于现在在生成什么。所以要么每步重算，要么存下来。

把两种做法逐步算一遍。 设 prompt 有 10 个 token，要生成 1000 个字：

已生成到第几个字 无 KV Cache：本步要前向的 token 数 无 KV Cache：累计 有 KV Cache：本步 有 KV Cache：累计
第 1 个 10 10 1 1
第 2 个 11 21 1 2
第 10 个 19 145 1 10
第 100 个 109 5,950 1 100
第 1000 个 1009 509,500 1 1,000 
无 KV Cache 的累计公式：10·N + N(N−1)/2  ⟹ O(N²)
有 KV Cache 的累计公式：N                 ⟹ O(N)

★ 代入 N = 1000：509,500 ÷ 1,000 = 【509 倍】的计算量差距。
  而且这个差距随着回答变长【越来越大】——N = 4000 时是 2000 倍。

KV Cache 的做法就一句话：K_1..K_{t-1} 上一步已经算过了，存下来别扔。每步只算新 token 的 K_t、V_t，追加到缓存末尾。

🔑 KV Cache 不是「优化」，是推理的默认前提。 没有它，长文本生成慢到不可用（所以你不会在任何生产框架里看到「关掉 KV Cache」这个选项）。
代价是：它要占显存，而且占得非常多。 本章剩下的部分全是在算这笔账。

2.2 KV Cache 到底占多少——把公式推一遍

先给三个符号（第一次出现，给全称）：

📖 n_heads（注意力头数）——一层里有多少个独立的注意力「视角」。
📖 n_kv_heads / H_kv（KV 头数）——其中有多少个独立的 K、V。MHA（Multi-Head Attention，多头注意力）里 H_kv = n_heads；GQA（Grouped-Query Attention，分组查询注意力）里 H_kv < n_heads，多个 Q 头共用一份 K、V。这是省 KV Cache 的主战场（07 章）。
📖 head_dim / D_head（每个头的维度）——通常 n_heads × head_dim = d_model（隐藏维度）。

完整公式：

KV Cache 总字节 = 2 × L × H_kv × D_head × dtype × seq_len × batch
                  ↑   ↑    ↑        ↑        ↑        ↑        ↑
                 K,V  层数 KV头数  头维度   每元素   序列长度  并发
                                            字节数

代真实数字：Llama-3-8B（⚠️ 参数取自公开的模型配置文件 config.json，非论文披露表格）

L = 32 层，H_kv = 8（用了 GQA，32 个 Q 头共享 8 组 KV），D_head = 128，BF16 = 2 字节

逐项乘上去，每一步都看得到中间值：

第几步 乘什么 值 累积结果 这是什么
① K 和 V 两份 × 2 2 —
② KV 头数 H_kv × 8 16 —
③ 每头维度 D_head × 128 2048 个元素 一个 token、一层的 K+V 有 2048 个数
④ 每元素字节数（BF16） × 2 4096 字节 = 4 KiB ★ 单 token、单层
⑤ 层数 L × 32 131072 字节 = 128 KiB ★★ 单 token、全模型
⑥ 序列长度 8192 × 8192 1 GiB 一条 8K 长度的对话
⑦ 并发 64 条 × 64 64 GiB ⚠️ 已经超过一张 H100 的全部显存

🔑 ★ 记住第 ⑤ 行这个数：Llama-3-8B 每个 token 要 128 KiB 的 KV Cache。 本章后面所有的账都从它出发，它也是附-速查表 里那个 128 KB。

再看更长的上下文：

对话长度 KV Cache 占整张卡（79.6 GiB）
1K token 128 MiB 0.2%
4K token 512 MiB 0.6%
8K token 1 GiB 1.3%
32K token 4 GiB 5.0%
128K token 16 GiB 20% ← ★ 一个用户就吃掉这张卡的 1/5

⚠️ 单位说明，全章统一，请先读这一段。 本章算容量一律用 GiB（1 GiB = 2³⁰ 字节），因为显存的一切数字（nvidia-smi、PyTorch、KV 块大小）都是 2 的幂；算带宽（§2.6）才换成十进制 GB，因为 3.35 TB/s 是十进制单位。两套单位差 7%，混着用是本主题最常见的错账来源。另外，H100「80GB」的实际可用量是 79.6 GiB（nvidia-smi 报 81559 MiB），本章按这个数算。

⚠️ 128K 那一行要说清楚：Llama-3-8B 原版的上下文窗口只有 8K，128K 是 Llama-3.1-8B。但两者的 L / H_kv / D_head 完全一样，所以 128 KiB/token 这个单价通用。16 GiB 只占整张卡的 20%，但和 §2.3 的 KV 预算（约 50 GiB）比，一个长上下文用户就吃掉了近 1/3 的并发能力。

没用 GQA 的老模型有多可怕

如果 H_kv = 32（每个注意力头都有自己独立的 K、V，即 MHA）：

H_kv 单 token 全模型 KV 一条 8K 对话 58 GiB 的 KV 预算能装几条 8K 对话
GQA（Llama-3-8B 实际） 8 128 KiB 1 GiB 58
MHA（假想的同规模老模型） 32 512 KiB 4 GiB ★★ 14

（58 GiB 这个预算是怎么来的，下一节 §2.3 逐行扣给你看。）

★★ 同一个模型规模，只因为 KV 头数从 8 变成 32，并发能力就掉到 1/4。
   这就是 GQA 存在的全部理由（07 章）。

⚠️⚠️ 这里有一个极高频的计算错误，务必躲开。 MHA 下 H_kv × D_head = n_heads × D_head = d_model，所以公式可以简写成「每 token 每层 = 4 × d_model 字节」（FP16/BF16 下）。很多文章和速查卡片直接给这个简写式——但它只对 MHA 成立。

用 d_model 硬套 GQA 模型会怎样： Llama-3-8B 的 d_model = 4096 错算：4 × 4096 = 16384 字节/层 × 32 层 = 512 KiB/token ✗ 高估 4 倍 正确：2 × H_kv(8) × D_head(128) × 2 = 4096 字节/层 × 32 层 = 128 KiB/token ✓

★ 判断法则：公式里那个头数必须是 n_kv_heads，不是 n_heads。 遇到 MQA（H_kv = 1）或 MLA，高估的倍数更夸张——DeepSeek-V2 的 MLA 能把这个单价压到几十分之一。看到任何 KV Cache 估算，第一件事是去 config.json 里确认 num_key_value_heads。

★ 注意第 ① 行就是 01 章 §1.5 那个「16 GB 权重」——那里按十进制 GB 说，这里按 GiB 记账，同一个数。这也是为什么上一节要先把单位约定讲掉。
⚠️ ②③④ 三行标了 ⚠️，因为它们随框架版本、max_num_seqs、有没有开 CUDA Graph 而变，不是固定值。真实数字看 vLLM 启动日志里那几行 memory profiling results，别照抄这张表。

⚠️ 第 ⑤ 行是很多估算漏掉的一步，也是「我算出 58 GiB，日志却显示 50 GiB」的原因。 vLLM 的口径是：可用 KV 显存 = 总显存 × gpu_memory_utilization − 非 KV 的一切开销，不是「剩下多少给多少」。那 10% 是留给显存碎片和峰值抖动的安全垫，而且是从总显存里扣的，不是从剩余里扣的。
✅ 源码可查：requested_memory = 总显存 × gpu_memory_utilization 在 utils.py:444，相减那一步在 gpu_worker.py:559。
⟹ 想把 50 GiB 拿回到 58 GiB，就是把 --gpu-memory-utilization 往 0.95 甚至 0.98 调。代价是 OOM 风险，这是个真实存在的旋钮，不是玄学。

把 KV 预算换算成 token 数和并发数（单价 128 KiB/token）：

（验算一行：58 GiB ÷ 128 KiB = 58 × 1024 × 1024 ÷ 128 = 475,136；475,136 ÷ 4096 = 116。）

★★ 这就是全书的中心矛盾，现在两边的数字都有了：
01 章 §1.3 说「算术强度要 > 295 才吃得满算力，也就是 batch 要 295」。
这一章说「4K 对话的 batch 最多 100~116」。
够不到。差了 3 倍。
⟹ 05 / 07 / 09 三章，全部是在同一件事上想办法——让同样的显存装下更多 token，好让 batch 再往上顶一点。

2.4 vLLM 是怎么算这笔账的

vLLM 启动时不是「猜」剩多少显存，而是真跑一遍：

① 记一次基线快照：这张卡现在还空多少
② 加载权重，记下权重占了多少
③ 用最大 batch 跑一次【假的】前向（profile run），记下激活值峰值
   ★ 这一步同时也把 kernel 编译好了，顺带估一下 CUDA Graph 要占多少
④ 可用 KV 显存 = 总显存 × gpu_memory_utilization
                − 权重 − 激活峰值 − 上下文等一切非 KV 开销
⑤ 把这块显存一次性切成固定大小的【块】（block），交给 BlockPool 管

✅ 源码可查：主流程是 GpuWorker.determine_available_memory，在 gpu_worker.py:475；profile run 在 gpu_model_runner.py:6553；切块和分配在 gpu_model_runner.py:7756，块池 class BlockPool 在 block_pool.py:143。

关键设计：KV Cache 的总量在启动时就定死了，运行期一个字节都不再变。这个设计换来两件事：

好处 坏处
调度器随时知道「还剩几块」，能精确判断一条新请求装不装得下 想改 KV 预算必须重启服务
不会因为 KV 突然涨上来而 OOM（装不下就排队或抢占，见 04 章） profile 估偏了（比如激活峰值估低），运行期才暴露
显存不用反复向驱动申请释放，没有分配器抖动 多个模型共卡时互相挤，0.9 要手动分

2.5 三个能改变这笔账的旋钮

回头看 §2.2 那个公式 2 × L × H_kv × D_head × dtype × seq_len × batch——能拧的就是里面的因子：

旋钮 动哪个因子 做法 效果 讲在哪
减少 KV 头数 H_kv ↓ GQA / MQA / MLA GQA 缩 4~8 倍；MQA（H_kv=1）缩 数十倍；MLA 换压缩思路，缩得更多 07 章
降低精度 dtype ↓ KV Cache 用 FP8 存 再缩 2 倍，质量损失很小 09 章
别浪费已分配的 三个因子都不动 PagedAttention + 前缀复用 有效利用率从 20%~38% 提到 >96% 05 章

✅ 第三行那两个数字是 vLLM 论文（arXiv 2309.06180）的一手披露：分页之前，真正装 token 的显存只占已分配显存的 20.4%~38.2%，其余全是保留浪费、内部碎片、外部碎片三类损耗。拆解见 05 章 §5.1。
★ 注意这三个旋钮是可以叠乘的：GQA（÷4）× FP8（÷2）× 分页（×2.5 的有效利用率）≈ 同样显存装 20 倍的 token。这不是夸张，是三章内容合起来的实际效果。

还有一个「作弊」旋钮——根本不存全部：

★ StreamingLLM：只保留【最开头几个 token】+【最近的一个滑动窗口】，中间全扔
  ✅ 论文 arXiv 2309.17453（papers/StreamingLLM-Attention-Sinks-arXiv-2309.17453.pdf）
  它发现最开头的几个 token 是「注意力池（attention sink）」——模型会把
  用不掉的注意力权重倾倒在那里，扔了就崩；中间的反而可以扔。
  ⟹ 于是 seq_len 这个因子被【钉死】在窗口大小上，不再随对话变长而增长。
  ⚠️ 代价是真的丢信息，属于「近似方法」，和前三个旋钮【不是同一性质】：
     前三个无损或近乎无损，这个会改变模型的输出。

2.6 一个容易被忽略的点：KV Cache 也要被「搬」

01 章 说解码是访存受限，当时只算了权重。实际上每生成一个 token，要搬两样东西：

① 全部权重：              16.1 GB     ← 和 batch 无关，被 batch 内所有序列【摊薄】
② batch 内所有序列的 KV：  ？           ← ★ 和 batch 成【正比】，摊【不薄】

⚠️ 这一节换单位了：因为要除以带宽 3.35 TB/s，而带宽是十进制单位，所以这一节的字节数全部换成十进制 GB（1 GB = 10⁹ 字节）。于是 §2.3 里那个 15.0 GiB 的权重，在这里写成 16.1 GB；一条 4K 序列的 KV，§2.2 里是 512 MiB，这里是 0.537 GB。同一个字节数，两种写法，差 7%。 换算一次、说清楚，比混着用安全。

这一节把 01 章 §1.2 那个「算术强度 ≈ B」的简化版补全。 设序列长度 4096（每条占 0.537 GB 的 KV），显存带宽 3.35 TB/s，逐行算：

batch KV 搬运量 + 权重 16.1 GB 每步总搬运 每步耗时 吞吐 相对 batch=1 理想线性 权重占搬运量 算力利用率
1 0.5 GB 16.1 16.6 GB 4.96 ms 202 tok/s 1.0× 1× 97% 0.33%
8 4.3 16.1 20.4 6.08 ms 1,316 6.5× 8× 79% 2.1%
32 17.2 16.1 33.2 9.92 ms 3,225 16.0× 32× 48% 5.2%
64 34.4 16.1 50.4 15.1 ms 4,252 21.1× 64× 32% 6.9%
112 60.1 16.1 76.2 22.7 ms 4,925 24.4× 112× 21% 8.0%

每一列怎么来的，一行算术就能自己验：

每条序列的 KV = 4096 token × 131072 字节 = 0.537 GB
KV 搬运量 = batch × 0.537 GB                （batch=32：32 × 0.537 = 17.2 GB）
每步耗时  = 总搬运量 ÷ 3.35 TB/s            （33.2e9 ÷ 3.35e12 = 9.92 ms）
吞吐      = batch ÷ 每步耗时                 （32 ÷ 0.00992 = 3225 tok/s）
算力利用率 = 2 × 8.03e9 × batch ÷ 每步耗时 ÷ 989e12
                                            （5.14e11 ÷ 0.00992 ÷ 989e12 = 5.2%）
★ 112 这一行是 4K 序列下的显存上限：112 × 0.537 = 60.1 GB = 56.0 GiB，
  正好顶到 §2.3 那个 58 GiB 的理论预算。
  ⚠️ 如果按默认 gpu_memory_utilization=0.9 的 50 GiB 算，上限是 100 条，
     这张表的最后一行就要退到 batch=100（吞吐约 4800 tok/s）。

这张表一次说明了四件事：

① batch 的收益是有拐点的，而且拐点算得出来。 从 1 到 8，吞吐涨 6.5 倍（接近理想的 8 倍）；从 8 到 32，再涨 2.4 倍（理想是 4 倍）；从 32 到 112，只再涨 1.5 倍（理想是 3.5 倍）。原因就在「权重占搬运量」那一列：batch=1 时搬的 97% 是权重，加 batch 等于白赚；batch=112 时权重只占 21%，剩下 79% 是 KV——KV 随 batch 线性增长，摊不薄，加 batch 就不再白赚了。

② 所以 batch 不是越大越好，存在一个甜点区。 这张卡上大致是 32~64：吞吐已经拿到 16~21 倍，而每步耗时还在 10~15 ms。

③ 吞吐涨了 24 倍，TPOT 也变差了 4.6 倍。 每步耗时从 4.96 ms 涨到 22.7 ms——每个字之间的间隔变成了 4.6 倍。这是 01 章 §1.6 那条「延迟 vs 吞吐」取舍线的具体数字版，也是 13 章 §13.2 说「只报吞吐不报延迟没有意义」的依据。

④ 即便 batch 顶到显存上限，算力利用率也只有 8%。 而这整张表的前提是带宽 100% 用满。（顺带说明一处 0.01 的差异：batch=1 这一行算出 0.33%，而 01 章 §1.3 说 0.34%——因为那里只算了权重的搬运量，这里把 KV 也算进去了，分母变大一点，利用率就更低一点。这正是本节要补的那一项。）再次印证 01 章 的那句话：算力利用率低不是浪费，是 Memory Bound 的定义——想让算力利用率上去，只能改变算术强度（07 / 08 / 09 章），加不了 batch 就是加不了。

⚠️ 这张表是屋顶线的理论上限，不是实测。 它做了三个简化：(a) 假设带宽 100% 用满，真机的 attention kernel 达不到；(b) 忽略了 attention 自身的 FLOPs（4K 序列下约多 13% 的计算量）；(c) 忽略了 kernel 之间的空隙和 CPU 下发开销（小 batch 下这一项尤其明显，见 12 章）。真机的绝对数字会更差，但「收益递减 + TPOT 恶化」这两条趋势是稳的——它们直接来自「权重摊薄、KV 摊不薄」这个结构，和实现质量无关。

2.7 本章小结

# 结论 关键数字
① KV Cache 公式：2 × L × H_kv × D_head × dtype × seq_len × batch ★ Llama-3-8B：128 KiB / token（全模型）
② ⚠️ 头数必须用 n_kv_heads，不是 n_heads。4 × d_model 那个简写式只对 MHA 成立 硬套 GQA 会高估 4 倍，硬套 MQA 会高估几十倍
③ 一张 H100 装 8B 模型，理论剩 58 GiB 给 KV；但 vLLM 默认 gpu_memory_utilization=0.9 会压到 ≈ 50 GiB 50 GiB ÷ 128 KiB = 409,600 个 token
③′ ⚠️ 容量算 GiB、带宽算十进制 GB，两者差 7%，不要混用 15.0 GiB 权重 = 16.1 GB 权重，同一个数
④ 并发数 = KV 预算 ÷ 平均对话长度 4K 对话约 100 条，32K 对话只有 12 条
⑤ ★★ 中心矛盾：01 章要 batch = 295 才吃满算力，显存只给得起 100 05 / 07 / 09 三章都在解这一个矛盾
⑥ batch 大到一定程度后，搬 KV 的开销超过搬权重，收益递减 batch=1 时权重占搬运量 97%，batch=112 时只占 21%
⑦ 而且 batch 换来的吞吐是用 TPOT 买的 吞吐 ×24 的同时，每步耗时从 4.96 ms 变 22.7 ms（×4.6）

自测三题（答案在对应小节）

  1. 一个模型 num_hidden_layers=80、num_attention_heads=64、num_key_value_heads=8、head_dim=128，FP16。它每个 token 的 KV Cache 是多少？如果有人用 4 × d_model × 层数 算，会得出什么数？错在哪？
  2. 你把 --gpu-memory-utilization 从 0.9 调到 0.95，8B 模型在 H100 上能多装多少个 token？相当于多几条 8K 的并发？
  3. §2.6 的表里，batch 从 32 加到 64，吞吐只涨了 1.32 倍而不是 2 倍。用一行算术说明这 1.32 是从哪来的。

参考答案

  1. 正确算法：2 × 8 × 128 × 2 = 4096 字节/层，× 80 层 = 327,680 字节 = 320 KiB / token。用 4 × d_model 硬套：d_model = 64 × 128 = 8192，4 × 8192 = 32768 字节/层 × 80 = 2560 KiB = 2.5 MiB，高估了 8 倍——正好是 n_heads ÷ n_kv_heads = 64 ÷ 8 = 8。错在那个简写式的推导前提是 MHA（n_kv_heads = n_heads），而这个模型是 GQA。参见 §2.2 的 ⚠️⚠️ 提醒。
  2. 多出来的预算 = (0.95 − 0.9) × 79.6 GiB ≈ 4.0 GiB（其余各项开销不变，涨出来的全部落到 KV 上）。换算 token 数 = 4 GiB ÷ 128 KiB = 32,768 个 token，即多 4 条 8K 对话（8K 对话每条正好占 1 GiB）。⚠️ 代价是安全垫从 8.0 GiB 缩到 4.0 GiB，激活峰值抖动、长 prompt 或多模态输入变大时更容易 OOM。参见 §2.3 第 ⑤ 行。
  3. 搬运量从 33.2 GB 涨到 50.4 GB（涨 1.52 倍），token 数从 32 涨到 64（涨 2 倍）。吞吐 = token ÷ 搬运量 ∝ 2 ÷ 1.52 = 1.32。一行话：batch 翻倍，但要搬的字节涨了 1.52 倍，净收益只有 2 ÷ 1.52。 权重那 16.1 GB 是唯一被摊薄的部分，它占比越小，这个比值就越接近 1。参见 §2.6 第 ① 点。
