# 02 KV Cache 与显存账本

> **一句话**：推理时显存被三样东西吃掉——权重（固定）、KV Cache（随用户数暴涨）、激活值（很小）。**能同时服务多少用户，几乎完全由 KV Cache 决定。**

---

## 2.1 为什么需要 KV Cache

先回忆注意力（Attention）在算什么。对第 t 个 token：

```
    Q_t（Query，查询）要和【前面所有 token】的 K（Key，键）做点积，
    再用得到的权重去加权【前面所有 token】的 V（Value，值）。

    Attention(Q_t) = softmax( Q_t · [K_1 ... K_t]ᵀ / √d ) · [V_1 ... V_t]
                                     ↑ 需要历史          ↑ 需要历史
```

现在看解码过程。生成第 100 个字时，需要 K_1..K_99；生成第 101 个字时，需要 K_1..K_100。

```
    ★ 天真做法：每生成一个字，把前面 100 个 token 重新跑一遍前向
       ⟹ 生成 N 个字的总代价 ≈ O(N²)，1000 字要跑 50 万个 token 的量

    ★ KV Cache：K_1..K_99 上一步已经算过了，【存下来别扔】
       ⟹ 每步只算新 token 的 K_t、V_t，追加到缓存末尾
       ⟹ 生成 N 个字的总代价 ≈ O(N)
```

> 🔑 **KV Cache 不是「优化」，是推理的默认前提。** 没有它，长文本生成慢到不可用。
> 代价是：**它要占显存，而且占得非常多。**

---

## 2.2 KV Cache 到底占多少——把公式推一遍

一个 token、一层，要存 K 和 V 两个向量：

```
    单个 token、单层的 KV 字节数
        = 2（K 和 V 两份）
        × num_kv_heads（KV 头数）
        × head_dim（每个头的维度）
        × dtype_bytes（BF16 = 2 字节）

    整个模型：再乘以 num_layers（层数）

    一整条序列：再乘以 seq_len（这条序列有多少 token）

    整个服务：再乘以 batch_size（同时有多少条序列）
```

合成一条：

```
┌────────────────────────────────────────────────────────────────┐
│  KV Cache 总字节                                                │
│    = 2 × L × H_kv × D_head × dtype × seq_len × batch           │
│      ↑    ↑    ↑        ↑        ↑        ↑         ↑          │
│      K,V  层数 KV头数  头维度   精度   序列长度   并发数         │
└────────────────────────────────────────────────────────────────┘
```

**代真实数字：Llama-3-8B**（⚠️ 参数取自公开的模型配置，非论文披露表格）

```
    L = 32 层，H_kv = 8（用了 GQA，见 07 章），D_head = 128，BF16 = 2 字节

    单 token 单层：2 × 8 × 128 × 2 = 4096 字节 = 4 KB
    单 token 全模型：4 KB × 32 = 128 KB

    ★ 记住这个数：Llama-3-8B 每个 token 要 128 KB 的 KV Cache

    一条 8K 长度的对话：128 KB × 8192 = 1 GB
    一条 128K 长度的对话：128 KB × 131072 = 16 GB   ← ★ 一个用户吃掉一半 H100
```

**再看没用 GQA 的老模型有多可怕**——如果 H_kv = 32（每个注意力头都有自己的 KV）：

```
    单 token 全模型：128 KB × 4 = 512 KB
    一条 8K 对话：4 GB
    ★★ 一张 80GB 的 H100，去掉 16GB 权重，剩 64GB
       ⟹ 只能装 16 个用户。这就是 GQA 存在的理由（07 章）。
```

## 2.3 一张 H100 的完整显存账

拿 **Llama-3-8B，单张 H100 80GB，BF16** 算一遍：

```
┌─────────────────────────────────────────────────────────┐
│  项目                    大小        说明                │
├─────────────────────────────────────────────────────────┤
│  ① 模型权重             16 GB       8B × 2 字节，固定    │
│  ② CUDA / NCCL 上下文  ~1-2 GB      驱动和通信库开销     │
│  ③ 激活值（临时）       ~1-2 GB      前向中间结果，用完就放│
│  ④ 框架预留             ~2 GB       调度器、采样器等      │
├─────────────────────────────────────────────────────────┤
│  ⟹ 剩给 KV Cache：    ≈ 58-60 GB                        │
│                                                         │
│  ★ 58 GB ÷ 128 KB/token ≈ 475,000 个 token             │
│                                                         │
│     如果平均每条对话 4K token → 能装 ~116 条并发         │
│     如果平均每条对话 32K token → 只能装 ~14 条并发       │
└─────────────────────────────────────────────────────────┘
```

> ★★ **这就是全书的中心矛盾**：
> 01 章说「要把 batch 做大才吃得满算力（需要 >300）」。
> 这一章说「batch 做大就爆显存」。
> **05 / 07 / 09 三章，全部是在同一件事上想办法——让同样的显存装下更多 token。**

---

## 2.4 vLLM 是怎么算这笔账的

vLLM 启动时不是「猜」剩多少显存，而是**真跑一遍**：

```
    ① 加载权重，记下占了多少
    ② 用最大 batch 跑一次假的前向（profile run），记下激活值峰值
    ③ 剩下的显存 × gpu_memory_utilization（默认 0.9）
       ⟹ 全部划给 KV Cache，切成固定大小的【块】
```

> ✅ 这个流程在 vLLM 源码里叫 `determine_available_memory` / `initialize_kv_cache`，
> 块的管理在 [block_pool.py](../源码/vLLM/vllm/v1/core/block_pool.py)，
> `class BlockPool` 在 **L143**。

**关键设计**：KV Cache 的总量在启动时就**定死**了，运行期不再变。所以调度器随时知道「还剩几块」，装不下就排队或抢占（04 章）。

## 2.5 三个能改变这笔账的旋钮

| 旋钮 | 做法 | 效果 | 讲在哪 |
|---|---|---|---|
| **减少 H_kv** | MQA / GQA / MLA | KV 直接缩 4~8 倍，**最有效** | [07 章](07-注意力变体MQA-GQA-MLA.md) |
| **降低 dtype** | KV Cache 用 FP8 存 | 再缩 **2 倍**，几乎无损 | [09 章](09-量化.md) |
| **别浪费已分配的** | PagedAttention + 前缀复用 | 把利用率从 ~30% 提到 >90% | [05 章](05-PagedAttention与前缀缓存.md) |

还有一个「作弊」旋钮——**根本不存全部**：

```
    ★ StreamingLLM：只保留【最开头几个 token】+【最近的窗口】
      ✅ 论文 arXiv 2309.17453（papers/StreamingLLM-Attention-Sinks-arXiv-2309.17453.pdf）
      发现最开头的 token 是「注意力池（attention sink）」，扔了就崩，
      中间的反而可以扔。
      ⟹ 代价是真的丢信息，属于「近似方法」，和前三个不同性质。
```

## 2.6 一个容易被忽略的点：KV Cache 也要被「搬」

01 章说解码是**访存受限**，当时只算了权重。实际上每生成一个 token，要搬两样东西：

```
    ① 全部权重：              16 GB      ← 和 batch 无关
    ② batch 内所有序列的 KV：  ？          ← ★ 和 batch 成【正比】

    batch = 1，序列 4K：   KV 只有 0.5 GB，权重是大头
    batch = 128，序列 4K： KV 有 64 GB，★★ KV 反而成了大头
```

> ⚠️（我的推断，非论文披露）**这解释了一个实践现象**：
> batch 从 1 加到 32，吞吐几乎线性涨（权重摊薄了）；
> 从 32 加到 256，涨幅明显放缓（KV 的搬运量在线性增长，摊不薄）。
> **所以 batch 不是越大越好，存在一个甜点区。**

```

│  ① KV Cache = 2 × 层数 × KV头数 × 头维度 × 精度 × 长度 × 并发  │
│     ★ Llama-3-8B：每个 token 128 KB                           │
│                                                              │
│  ② 一张 H100 装 8B 模型 → ~58 GB 归 KV Cache → ~47 万 token   │

│                                                              │
│  ③ ★★ 中心矛盾：batch 要大才吃满算力，但 batch 大就爆显存       │

│                                                              │
│  ④ batch 大到一定程度后，搬 KV 的开销会超过搬权重              │
│     ⟹ 存在吞吐甜点，不是越大越好                              │
└──────────────────────────────────────────────────────────────┘
```
