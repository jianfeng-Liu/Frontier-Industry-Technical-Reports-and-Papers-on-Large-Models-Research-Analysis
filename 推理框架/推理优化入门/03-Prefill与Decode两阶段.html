03 Prefill 与 Decode：两个性格相反的阶段

一句话：一次推理被切成两段——Prefill（读题）一口气吃下整段 prompt，Decode（答题）一次只吐一个字、并行度恒等于 1。它们抢同一张卡，是推理系统一切复杂度的来源。
⚠️ 顺便先纠正一句到处流传的话：「Prefill 算力受限、Decode 访存受限」只有在 prompt 够长的时候才成立，短 prompt 的 Prefill 和 Decode 一样是访存受限的。§3.3 会把这个临界点算出来。

3.1 一次请求的完整生命

用户输入 "请介绍一下杭州"（假设 6 个 token），模型回答 200 个字：

    Prefill（预填充）── ★ 一次前向，处理 6 个 token
    ├── 把 6 个 token 【一次性】喂进模型
    ├── ① 算出全部 6 个位置的 K、V → 写进 KV Cache
    └── ② 只取最后一个位置的输出 → 采样出第 1 个字「杭」
                        ↓
    Decode（解码）── ★★ 199 次前向，每次只处理 【1 个】 token
    ├── 第   1 步：喂「杭」    → 注意力看 7 个 token   → 吐「州」
    ├── 第   2 步：喂「州」    → 注意力看 8 个 token   → 吐「是」
    ├── 第   3 步：喂「是」    → 注意力看 9 个 token   → 吐「浙」
    ├── ...
    └── 第 199 步：喂倒数第2字 → 注意力看 205 个 token → 吐「。」

    ★★ Decode 必须【严格串行】——不算出第 n 个字，就没法作为第 n+1 步的输入。
       Prefill 的 6 个 token 之间没有这个依赖，所以能一次算完。

🔑 第一个要刻进脑子的数字：这一条请求做了 200 次前向 = 1 次 Prefill + 199 次 Decode，Decode 占了 99.5% 的前向次数。
下一节会算出第二个数字：它同时也占了 99.5% 的墙上时间。

3.2 把这一条请求的时间账算出来

要算账，先把模型和卡钉死。全章用同一套数字，任何一行都能自己验算。

量 值 说明
模型 Llama-3-8B L = 32 层，KV 头数 8（GQA），head_dim = 128，BF16
参数量 8.03 B 主体 6.98 B + embedding 0.53 B + lm_head 0.53 B
权重显存 16.1 GB = 8.03 B × 2 字节
Decode 每步要读的权重 15.0 GB embedding 表那 1.05 GB 每步只查一行，不用整张读
每 token 的 KV Cache 128 KiB 02 章 已经推过
⚠️ 激活值读写（估算） 约 8.8 MB / token 把每层中间张量的读写逐项加起来的量级，算子融合做得好会明显更少
硬件 H100 SXM5 HBM3 80 GB / 3.35 TB/s，BF16 稠密峰值 989 TFLOPS
屋脊点 295 FLOP/Byte = 989 ÷ 3.35，01 章 里那个「约 300」的精确值

⚠️ 989 是稠密峰值。规格表上那个 1979 TFLOPS 是「带 2:4 稀疏」的，常规推理算子用不上，别拿它当基准。
📖 屋脊点（ridge point）——算力峰值 ÷ 带宽峰值。算术强度低于它，GPU 一定在等数据；高于它，才可能吃满算力。

现在把 Prefill 的一次前向和 Decode 的一步并排算（算力侧 = FLOP ÷ 989 TFLOPS，带宽侧 = 搬运字节 ÷ 3.35 TB/s，谁大谁是瓶颈）：

逐步算 Prefill（6 个 token，一次前向） Decode（第 1 步，上下文 7 token）
① 这一步处理几个 token 6 1
② 矩阵乘 FLOP 2 × 6.98e9 × 6 = 0.084 TFLOP 2 × 7.51e9 × 1 = 0.015 TFLOP
③ 注意力 FLOP 6 个 token 之间，< 0.001 TFLOP 可忽略
④ 读权重 15.0 GB 15.0 GB ← 一模一样
⑤ 读 KV Cache 0（这一步才刚写进去） 7 × 128 KiB = 0.9 MB
⑥ 写 KV Cache 6 × 128 KiB = 0.75 MiB 1 × 128 KiB
⑦ ⚠️ 激活读写（8.8 MB/token 估） 53 MB 9 MB
⑧ 搬运合计 15.05 GB 15.01 GB
⑨ 算术强度 I = ② ÷ ⑧ 8.4e10 ÷ 1.505e10 = 5.6 1.5e10 ÷ 1.501e10 = 1.0
⑩ 和屋脊点 295 比 5.6 ≪ 295 → ❌ 访存受限 1.0 ≪ 295 → ❌ 访存受限
⑪ 算力侧耗时 0.085 ms 0.015 ms
⑫ 带宽侧耗时 4.49 ms 4.48 ms
⑬ 耗时 = max(⑪, ⑫) 4.49 ms 4.48 ms
⑭ 每 token 成本 = ⑬ ÷ ① 4.49 ÷ 6 = 0.75 ms 4.48 ÷ 1 = 4.48 ms

先盯住第 ④ 行：两边读的权重字节数一模一样，都是 15.0 GB。 Prefill 读一次权重服务 6 个 token，Decode 读一次权重只服务 1 个 token。这就是全部的差别，而且它解释了第 ⑭ 行那个 6 倍——恰好等于 prompt 的长度。

接下来是整条请求的账：

次数 单次耗时 合计 占墙上时间
Prefill 1 4.49 ms 4.5 ms 0.5%
Decode 199 4.49 ms（上下文从 7 长到 205，KV 读取量只占 15 GB 的 0.2%，几乎不变） 893 ms 99.5%
合计 200 — 898 ms 100% 
    输出速度 = 200 token ÷ 0.898 s = ★ 223 token/s

    这 0.898 秒里，GPU 一共：
      算了   0.084 + 199 × 0.015 = 3.07 TFLOP
      搬了   15.05 + 199 × 15.01 = 3003 GB

    ⟹ 实现算力 = 3.07e12 ÷ 0.898 = 3.4 TFLOPS = 峰值 989 的 ★ 0.35%
    ⟹ 实现带宽 = 3003 ÷ 0.898  = 3344 GB/s = 峰值 3350 的 ★★ 99.8%

🔑 第二个要刻进脑子的数字，以及一个必须分清的区别：整块 H100 花 0.9 秒答这一句话，算力只用到 0.35%，但带宽几乎打满。
★★ 算力利用率低不是浪费，是 Memory Bound（访存受限）的定义——它是物理规律的读数，不是工程失误的读数。
⚠️ 上面那个 99.8% 是理论下界的必然结果（我们就是按「带宽打满」算出来的）。真机上 Decode 的 HBM 带宽利用率通常在 80%~90% 这个量级（⚠️ 典型经验值，无一手来源），所以实测 TPOT 会比 4.5 ms 大一些。
★ 想判断「这台机器有没有被浪费」，推理侧该看的是带宽利用率，不是算力利用率（13 章会再说一遍：MFU 在推理里不是好指标）。

📖 TTFT（Time To First Token，首字延迟）—— 基本等于 Prefill 的耗时，上面这个例子是 4.5 ms。
📖 TPOT（Time Per Output Token，每字延迟）—— 基本等于一步 Decode 的耗时，上面这个例子是 4.5 ms。
📖 MFU（Model FLOPs Utilization，模型算力利用率）—— 实现算力 ÷ 峰值算力，也就是上面那个 0.35%。

3.3 ⚠️ 「Prefill 算力受限」有个前提：prompt 得够长

上一节那个 6 token 的 Prefill，算术强度只有 5.6，离屋脊点 295 差 50 倍——它和 Decode 一样是访存受限的。所以「Prefill 算力受限」这句话不是无条件的。到多长才成立？把 prompt 长度 M 扫一遍就知道了：

prompt 长度 M 矩阵乘 FLOP 注意力 FLOP 搬运字节（15.0 GB + 8.8 MB × M） 算术强度 I 算力侧 带宽侧 TTFT 下界 瓶颈
6 0.08 TFLOP ~0 15.05 GB 5.6 0.09 ms 4.49 ms 4.5 ms ❌ 访存
128 1.79 TFLOP 0.004 16.13 GB 111 1.81 ms 4.81 ms 4.8 ms ❌ 访存
390 5.44 TFLOP 0.04 18.43 GB 297 ≈ 295 5.55 ms 5.50 ms 5.5 ms ★ 临界点
512 7.15 TFLOP 0.07 19.51 GB 370 7.30 ms 5.82 ms 7.3 ms ✅ 算力
2048 28.6 TFLOP 1.10 33.0 GB 899 30.0 ms 9.86 ms 30 ms ✅ 算力
8192 114 TFLOP 17.6 87.1 GB 1516 133 ms 26.0 ms 133 ms ✅ 算力
32768 457 TFLOP 282 303 GB 2436 747 ms 90.6 ms 747 ms ✅ 算力

⚠️ 那个临界点 390 是按「激活 8.8 MB/token」估出来的。如果算子融合做得好、激活流量减半，临界点降到约 350；完全忽略激活值则是 317。能确定的只有量级：几百个 token。
🔑 所以：prompt 短于几百个 token 时，Prefill 和 Decode 一样访存受限，一样只用得上百分之几的算力。 聊天场景里一句十几个字的问题，它的 Prefill 成本 ≈ 一步 Decode。

顺着这张表，再看「Decode 每 token 比 Prefill 贵多少倍」（Decode 那一列按同长度的上下文算）：

prompt 长度 M Prefill 每 token 成本 Decode 每 token 成本 倍数 为什么
6 0.75 ms 4.48 ms 6× 两边都访存受限，倍数 = M
128 37.6 µs 4.48 ms 119× 同上，倍数 = M
390 14.2 µs 4.50 ms 316× ★ Prefill 刚转算力受限，倍数顶到头
2048 14.7 µs 4.56 ms 311× 封顶，不再随 M 涨
32768 22.8 µs 5.77 ms 253× ⚠️ 回落——注意力的平方项开始吃 Prefill 
    ★★ 这条曲线的形状，一句话能说完：

       M < 临界点（几百）：两边都在读同一份 15 GB 权重
                           ⟹ 倍数 = M，线性上涨
       M ≈ 临界点：        Prefill 转为算力受限
                           ⟹ 倍数顶到【屋脊点的量级，约 300】，封顶
       M 很大（几万）：     注意力的 O(M²) 项让 Prefill 每 token 又变贵
                           ⟹ 倍数反而回落

    ⟹ ★ 「Decode 比 Prefill 贵两三百倍」是【峰值】，不是常数。

📖 这个「约 300」的上限，本质就是屋脊点 295 换了个说法——从单个矩阵乘出发能推出它精确等于 989 ÷ 3.35，整模型口径下因为 lm_head 之类的零碎项会偏到 310 左右。完整推导见 大模型算子开发 · 09 推理侧算子 §9.1.3（那一章是算子实现向的，本章只用结论）。

3.4 两个阶段的性格对照

项目 Prefill（预填充） Decode（解码）
一次前向处理多少 token 整段 prompt（6 ~ 几万） ★ 固定 1 个（再乘并发数）
矩阵形状 矩阵 × 矩阵（GEMM） ★ 向量 × 矩阵（GEMV，天生低效）
算术强度 ★ 不固定，≈ prompt 长度：6 → 5.6，2048 → 899 ★ ≈ 1，不管上下文多长、batch 多大都在这个量级
瓶颈 prompt > 约 400 token 才 ✅ 算力受限；更短的话 ❌ 和 Decode 一样访存受限 ❌ 恒定访存受限
算力利用率（MFU） 长 prompt：理论 100%，⚠️ 实测常 50%~70%；短 prompt：和 Decode 一样低 ★ batch=1 时 0.34%；靠攒 batch 能提到几十个百分点（04 章）
带宽利用率 长 prompt 时反而不高（算力才是瓶颈） ★★ 接近打满——这才是 Decode 的真实状态
KV Cache ★ 大量写入（6 token → 0.75 MiB） ★ 每步少量写（128 KiB）、大量读（整段历史）
一次耗时 6 token → 4.5 ms；2048 → 30 ms；32768 → 747 ms 每步 4.5 ms（上下文 512、batch 1）
在一条请求里的耗时占比 短 prompt 场景 0.5%；32K 长文场景 39%（§3.7） 反过来
决定哪个指标 TTFT（首字延迟） TPOT（每字延迟）
加卡（TP）的收益 ✅ 算力被切分，耗时接近线性下降 ⚠️ 权重字节也被切分，TPOT 确实能降；但每层多 2 次 all-reduce、kernel 数一个都没少 → 收益递减（06 章、12 章）

📖 GEMM（GEneral Matrix Multiply，通用矩阵乘）——矩阵乘矩阵，GPU 最擅长的形状。
📖 GEMV（GEneral Matrix-Vector multiply，矩阵向量乘）——矩阵乘一个向量。
📖 TP（Tensor Parallelism，张量并行）——把同一层的权重切到多张卡上，每层用 all-reduce 把结果拼回来。
★ GEMM 和 GEMV 的差别在哪：GEMM 把权重搬进来能复用很多次；GEMV 搬进来只用一次。Decode 天然是 GEMV，这就是 01 章那个「算术强度 ≈ 1」的具体形态。

3.5 ★★ 核心冲突：它们抢同一张卡

真实服务里，同一时刻既有新用户在 Prefill，又有老用户在 Decode。GPU 只有一个，怎么排？

做法一：Prefill 优先（vLLM v0 早期的默认）

    时间轴 ──────────────────────────────────────────►
    [ A的Prefill 8K prompt (133ms) ][ 所有人Decode ][ B的Prefill (133ms) ][ Decode ]
                                          ↑
                    ★★ 所有正在打字的用户，在这 133 ms 里【一个字都不吐】
                       用户感受：说到一半突然卡住

拿 §3.3 那张表算一下这个卡顿有多严重（假设正在 Decode 的用户 TPOT 是 5.9 ms）：

插进来的 prompt 长度 这一段 Prefill 耗时 老用户感受到的字间隔 是平时的几倍
512 7.3 ms 13.2 ms 2.2×
2048 30 ms 35.9 ms 6.1×
8192 133 ms 139 ms 23.4×
32768 747 ms 753 ms 127×

★ 这个现象有个名字：generation stall（生成停顿）。注意最后两行——长上下文时代，这个尖峰是不可接受的。
✅ Sarathi-Serve 论文（arXiv 2403.02310，papers/Sarathi-Serve-Chunked-Prefill-arXiv-2403.02310.pdf）就是冲着它去的。

做法二：Decode 优先

    ⟹ 新用户的 prompt 永远排不上队 → TTFT 无限长 → ★ 饿死（starvation）

做法三：★ 混合批（chunked prefill）——现在的主流答案

把长 Prefill 切成小块，每一步都塞进 Decode 批次里一起跑。假设 token 预算是 512、当前有 64 路 Decode，那么每一步的批次长这样：

这一步批次里的成员 贡献的 token 数
用户A 的 Prefill 第 3 块 448
用户C Decode 1
用户D Decode 1
……一直到用户 Z，共 64 个 Decode 请求 64
合计 512 ← ★ 这就是「token 预算」

妙在哪？把「纯 Decode 步」和「混合步」逐项算出来对比（64 路 Decode，平均上下文 512；那个长 prompt 是 7168 token = 448 × 16 块）：

逐步算 纯 Decode 步（不插 Prefill） 混合步（448 Prefill + 64 Decode）
① 这一步的 M（总 token 数） 64 512
② 矩阵乘 FLOP 64 × 0.015 = 0.96 TFLOP 6.25 + 0.96 = 7.21 TFLOP
③ 读权重 15.0 GB 15.0 GB ← 还是读一遍
④ 读 KV（64 路 × 512 token） 4.29 GB 4.29 GB + 0.12（这一块要重读前两块的 KV）
⑤ ⚠️ 激活读写 0.56 GB 4.51 GB
⑥ 搬运合计 19.85 GB 23.92 GB
⑦ 算术强度 I 0.96e12 ÷ 1.985e10 = 48 7.21e12 ÷ 2.392e10 = 302
⑧ 和屋脊点 295 比 48 ≪ 295 → ❌ 访存受限 302 > 295 → ✅ 算力受限，越过屋脊点了
⑨ 算力侧 / 带宽侧 0.97 ms / 5.93 ms 7.30 ms / 7.14 ms
⑩ 一步耗时 5.93 ms 7.30 ms
⑪ 算力利用率 16.4% ★ ~100%（理论上限；⚠️ 实测按 MFU 打折，约 50%~70%）

前后对照：

不切（做法一） 切成 16 块混进 Decode
老用户的字间隔（TPOT） 5.93 ms → 121 ms（20.4× 尖峰） 5.93 ms → 7.30 ms（1.23×）
那个长请求的 TTFT 115 ms 16 × 7.30 = 117 ms（+1.7%）
Prefill 那段时间的算力利用率 Prefill 步 ~100%，但 Decode 全停 ★ ~100%，而且 Decode 一步没停 
    ★★ 混合批的精髓，一句话：
       不是「把 Prefill 变快」（总 FLOP 一点没变），
       而是 ★「把 Prefill 富余的算力借给 Decode 用」。

       纯 Decode 步：算力只用 16.4%，带宽打满   ← 算力在空转
       纯 Prefill 步：算力打满，带宽闲着        ← 带宽在空转
       混在一起：   ★ 一次权重读取同时服务了 448 个 Prefill token
                    和 64 个 Decode token —— 这是一笔纯赚的买卖

    ⟹ ① Decode 用户【每一步都能吐字】，TPOT 从 20 倍尖峰压到 1.23 倍
    ⟹ ② 这一步的算术强度从 48 顶到 302，越过屋脊点，GPU 吃得满 → 吞吐也高
    ⟹ ③ 代价只有那个长请求的 TTFT +1.7%

✅ 源码可查：vLLM 调度器的 token 预算就是这个机制。
scheduler.py:497 开出预算：
python token_budget = self.max_num_scheduled_tokens
scheduler.py:564-568 给单条长 prompt 封顶、再被总预算夹一次：
python if 0 < self.scheduler_config.long_prefill_token_threshold < num_new_tokens: num_new_tokens = self.scheduler_config.long_prefill_token_threshold num_new_tokens = min( num_new_tokens, token_budget, input_budget - draft_slots )
★ long_prefill_token_threshold 就是「一条超长 prompt 单步最多切多少」，min(..., token_budget, ...) 就是「不许超总预算」。教科书式的实现。

📖 同一个思路在不同框架里叫法不同，看到了知道是一回事：
vLLM 叫 chunked prefill（分块预填充），DeepSpeed 叫 Dynamic SplitFuse（论文 arXiv 2401.08671），Sarathi-Serve 叫 stall-free batching（无停顿批处理）。

3.6 混合批也有代价

    ⚠️ 代价一：Prefill 被切块后，每一块都要【重读】前面已经写好的 KV
       上面第 ④ 行那个 0.12 GB 就是它。切 16 块，这笔重读是：
          第 1 块读 0、第 2 块读 448、第 3 块读 896 ... 第 16 块读 6720 个 token 的 KV
          累计 = (0+448+...+6720) × 128 KiB = 53760 × 128 KiB = 7.05 GB
       ★ 摊到 16 步上，每步平均多读 0.44 GB —— 相对每步的 19.9 GB，约 +2.2%
       ✅ Sarathi-Serve 论文明确讨论了这个开销，并给出了 chunk 大小的取舍

    ⚠️ 代价二：预算怎么定是个取舍，没有普适最优值
       预算太小 → 混合步的 M 掉回屋脊点以下，Prefill 反而变慢（TTFT 差）
       预算太大 → 尖峰压不下去，回到做法一的问题（TPOT 差）
       ★ 判据不是拍脑袋：M（chunk + 并发 Decode 数）要 ≥ 屋脊点对应的那个几百
         —— 这正是 §3.3 那张表的用处

    ⚠️ 代价三：两个阶段最优的【并行策略不一样】，混在一起只能用一套
       Prefill 想要大 TP（算力受限，切算力有效）
       Decode 想要小 TP + 大 DP（通信和 kernel 下发开销占比会随 TP 上升）
       ★★ 混合批被迫用同一套配置 ⟹ 两边都不是最优

第三条代价，直接催生了下一个想法：

    ★★ 既然两个阶段性格相反、最优配置也不同，
       为什么要把它们放在同一台机器上？

       ⟹ 拆开！Prefill 一个集群、Decode 一个集群，中间传 KV Cache
       ⟹ 这就是 【PD 分离】，见 [10 章](10-PD分离.md)
       ✅ 代表工作：DistServe (2401.09670)、Splitwise (2311.18677)、
          Mooncake (2407.00079)，三篇 PDF 都在 papers/ 里

★ PD 分离和 chunked prefill 是同一个矛盾的两种解法：前者在空间上把两段隔开，后者在时间上把长 Prefill 切碎。小集群用后者，大集群用前者。

3.7 谁是瓶颈，取决于你的输入输出长度比

❓ "Prefill 那么快，是不是可以忽略？"

不能。把 §3.3 的 TTFT 和 §3.2 的 TPOT 组合起来，扫一遍典型场景就清楚了：

场景 prompt 输出 TTFT（Prefill） 生成耗时 Prefill 占墙上时间 谁是瓶颈
聊天（"请介绍一下杭州"） 6 200 4.5 ms 199 × 4.49 = 893 ms 0.5% Decode
普通问答 512 300 7.3 ms 300 × 4.51 = 1353 ms 0.5% Decode
代码补全 2048 64 30 ms 64 × 4.56 = 292 ms 9.3% Decode
★ RAG / 长文档总结 32768 200 747 ms 200 × 5.77 = 1154 ms 39% ★ Prefill
★★ 长文抽取（只要一个 JSON） 32768 20 747 ms 20 × 5.77 = 115 ms 87% ★★ Prefill

📖 RAG（Retrieval-Augmented Generation，检索增强生成）——先去知识库检索一堆资料，塞进 prompt 再让模型回答。它的 prompt 天生很长。
⟹ ★★ 两个阶段谁是瓶颈，取决于你的【输入输出长度比】。 这个比值叫 P:D ratio（Prefill:Decode），是选型时第一个要问的数字（13 章）。
★ 最后两行说明了一件容易被忽略的事：同样的 32K prompt，输出长度一变，优化的方向就完全反过来——输出 200 字时该调 Decode，输出 20 字时该调 Prefill。

而前缀缓存正是最后两行的解药——如果 32768 个 token 里有 30000 个是每次都一样的系统提示词，那 Prefill 可以直接跳过它们（05 章）。

3.8 本章小结

① 一次请求 = 1 次 Prefill + N 次 Decode。 ★ 本章例子里 Decode 占 99.5% 的前向次数，也占 99.5% 的墙上时间。

② 一条请求的核心账本（Llama-3-8B，H100，prompt 6 token / 输出 200 token）：

Prefill Decode（每步）
处理 token 数 6 1
读权重 15.0 GB 15.0 GB ← 一模一样
算术强度 I 5.6 1.0
瓶颈 ❌ 访存（因为 prompt 太短！） ❌ 访存
耗时 4.49 ms 4.48 ms
每 token 成本 0.75 ms 4.48 ms
全程算力利用率 ★ 0.35% —
全程带宽利用率 ★★ 接近打满 —

③ ⚠️ 三条最容易记错的结论：

    ✗ 「Prefill 算力受限」
    ✓  只有 prompt 长于几百个 token（本章算出约 390）才成立。
       6 个 token 的 Prefill 算术强度只有 5.6，和 Decode 一样访存受限。

    ✗ 「Decode 的 GPU 利用率 <5%，太浪费了」
    ✓  要说清是哪种利用率。【算力】利用率 batch=1 时 0.34%，攒 batch 能提到几十个百分点；
       【带宽】利用率接近打满。算力低是 Memory Bound 的定义，是物理规律，不是浪费。
       ★ 推理侧该看的是带宽利用率。

    ✗ 「Decode 每 token 比 Prefill 贵两三百倍」
    ✓  那是【峰值】。倍数 = min(prompt 长度, 屋脊点量级约 300)，
       prompt 再长下去还会因为注意力的 O(M²) 项回落。

④ ★★ 两者抢同一张卡，三种排法：

    Prefill 优先 → 老用户卡住（generation stall），8K prompt 插队一次 = 23.4 倍字间隔
    Decode 优先 → 新用户饿死（starvation）
    ⟹ chunked prefill 混合批：切块塞进 Decode 批，两全
       ★ 算术强度 48 → 302（越过屋脊点 295），算力利用率 16.4% → ~100%（理论）
       ★ Decode 尖峰 20.4× → 1.23×，代价是长请求 TTFT +1.7%
    ✅ vLLM 用 token_budget 实现（scheduler.py:497 与 564-568）

⑤ 混合批的残余问题：两阶段最优的并行配置不同，混在一起只能用一套 ⟹ 催生 PD 分离（10 章）。
