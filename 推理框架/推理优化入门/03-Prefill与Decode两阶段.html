03 Prefill 与 Decode：两个性格相反的阶段

一句话：一次推理被切成两段——Prefill（读题）算力受限、并行度高，Decode（答题）访存受限、并行度=1。它们抢同一张卡，是推理系统一切复杂度的来源。

3.1 一次请求的完整生命

用户输入 "请介绍一下杭州"（假设 6 个 token），模型回答 200 个字：

    ┌─────────────── Prefill（预填充）───────────────┐
    │  把 6 个 token 【一次性】喂进模型              │
    │  ① 算出全部 6 个位置的 K、V → 写进 KV Cache    │
    │  ② 只取最后一个位置的输出 → 采样出第 1 个字「杭」│
    │  ★ 一次前向，处理 6 个 token                   │
    └───────────────────────────────────────────────┘
                          ↓
    ┌─────────────── Decode（解码）─────────────────┐
    │  第 1 步：喂「杭」→ 读 KV[0:6] → 吐「州」       │
    │  第 2 步：喂「州」→ 读 KV[0:7] → 吐「是」       │
    │  第 3 步：喂「是」→ 读 KV[0:8] → 吐「浙」       │
    │   ...                                          │
    │  第 199 步：................. → 吐「。」        │
    │  ★★ 199 次前向，每次只处理 【1 个】 token       │
    │  ★★ 而且必须【严格串行】——不算出第 n 个字，     │
    │      就没法作为第 n+1 步的输入                  │
    └───────────────────────────────────────────────┘

🔑 两个必须刻进脑子的数字：这一条请求做了 200 次前向，其中 1 次是 Prefill，199 次是 Decode。
Decode 占了 99.5% 的前向次数，却只贡献 200/206 的 token。

3.2 两个阶段的性格对照

┌──────────────┬────────────────────┬────────────────────┐
│              │  Prefill           │  Decode            │
├──────────────┼────────────────────┼────────────────────┤
│ 一次处理      │  整个 prompt        │  ★ 1 个 token      │
│ 的 token 数   │  （几百 ~ 几万）    │                    │
├──────────────┼────────────────────┼────────────────────┤
│ 算术强度      │  高（>300）         │  ★ ≈1，极低         │
│ 瓶颈          │  ✅ 算力受限        │  ❌ 访存受限        │
│ GPU 利用率    │  40%~70%           │  ★ 常常 <5%        │
├──────────────┼────────────────────┼────────────────────┤
│ 矩阵形状      │  矩阵 × 矩阵        │  ★ 向量 × 矩阵      │
│              │  (GEMM)            │  (GEMV，天生低效)   │
├──────────────┼────────────────────┼────────────────────┤
│ KV Cache      │  ★ 大量【写入】     │  ★ 少量写、大量【读】│
├──────────────┼────────────────────┼────────────────────┤
│ 耗时          │  一次几十~几百 ms   │  一次几~几十 ms     │
│ 总耗时占比    │  小                │  ★★ 大头            │
├──────────────┼────────────────────┼────────────────────┤
│ 决定哪个指标  │  TTFT（首字延迟）   │  TPOT（每字延迟）   │
├──────────────┼────────────────────┼────────────────────┤
│ 加卡（TP）    │  ✅ 有效，算力翻倍   │  ⚠️ 收益递减，       │
│ 的收益        │                    │  通信开销可能占主导 │
└──────────────┴────────────────────┴────────────────────┘

📖 GEMM（GEneral Matrix Multiply，通用矩阵乘）——矩阵乘矩阵，GPU 最擅长的形状。
📖 GEMV（GEneral Matrix-Vector multiply，矩阵向量乘）——矩阵乘一个向量。
★ 差别在哪：GEMM 把权重搬进来能复用很多次；GEMV 搬进来只用一次。Decode 天然是 GEMV，这就是 01 章那个「算术强度≈1」的具体形态。

3.3 ★★ 核心冲突：它们抢同一张卡

真实服务里，同一时刻既有新用户在 Prefill，又有老用户在 Decode。GPU 只有一个，怎么排？

做法一：Prefill 优先（vLLM v0 早期的默认）

    时间轴 ──────────────────────────────────────────►
    [ 用户A的Prefill (300ms) ][ 所有人Decode ][ 用户B的Prefill (300ms) ][ Decode ]
                                    ↑
                    ★★ 所有正在打字的用户，在这 300ms 里【一个字都不吐】
                       用户感受：说到一半突然卡住

这个现象有个名字：generation stall（生成停顿）。
✅ Sarathi-Serve 论文（arXiv 2403.02310，papers/Sarathi-Serve-Chunked-Prefill-arXiv-2403.02310.pdf）就是冲着它去的。

做法二：Decode 优先

    ⟹ 新用户的 prompt 永远排不上队 → TTFT 无限长 → ★ 饿死（starvation）

做法三：★ 混合批（chunked prefill）——现在的主流答案

把长 Prefill 切成小块，每一步都塞进 Decode 批次里一起跑：

    每一步的批次都长这样：
    ┌────────────────────────────────────────────────┐
    │  用户A Prefill 的第 3 块  (448 个 token)        │
    │  用户C Decode            (1 个 token)          │
    │  用户D Decode            (1 个 token)          │
    │  ...                                           │
    │  用户Z Decode            (1 个 token)          │
    ├────────────────────────────────────────────────┤
    │  合计 512 个 token  ← ★ 这就是「token 预算」     │
    └────────────────────────────────────────────────┘

    ★★ 妙在哪：
       ① Decode 用户【每一步都能吐字】，不再卡住 → TPOT 平稳
       ② 那 448 个 Prefill token 把算术强度顶上去了
          → 这一步不再是访存受限，GPU 吃得满 → 吞吐也高
       ③ 一次同时治好了 TPOT 和吞吐    ★ 这是这个设计的精髓

✅ 源码可查：vLLM 调度器的 token 预算就是这个机制。
scheduler.py:497 开出预算：
python token_budget = self.max_num_scheduled_tokens
scheduler.py:564-566 给单条长 prompt 封顶、再被总预算夹一次：
python if 0 < self.scheduler_config.long_prefill_token_threshold < num_new_tokens: num_new_tokens = self.scheduler_config.long_prefill_token_threshold num_new_tokens = min(num_new_tokens, token_budget, input_budget - draft_slots)
★ long_prefill_token_threshold 就是「一条超长 prompt 单步最多切多少」，min(..., token_budget, ...) 就是「不许超总预算」。教科书式的实现。

📖 同一个思路在不同框架里叫法不同，看到了知道是一回事：
vLLM 叫 chunked prefill，DeepSpeed 叫 Dynamic SplitFuse（论文 arXiv 2401.08671），Sarathi-Serve 叫 stall-free batching（无停顿批处理）。

3.4 混合批也有代价

    ⚠️ 代价一：Prefill 被切块后，每一块都要【重读】前面已经写好的 KV
       原本一次读完，现在读 N 次 → 额外的访存
       ✅ Sarathi-Serve 论文明确讨论了这个开销，并给出了 chunk 大小的取舍

    ⚠️ 代价二：预算怎么定是个玄学
       预算小 → Decode 用户吐字快（TPOT 好），但 Prefill 拖很久（TTFT 差）
       预算大 → 反过来
       ★ 没有普适最优值，取决于你的 SLO 更看重哪一个

    ⚠️ 代价三：两个阶段最优的【并行策略不一样】，混在一起只能用一套
       Prefill 想要大 TP（算力受限，加卡有效）
       Decode 想要小 TP + 大 DP（访存受限，加卡收益递减）
       ★★ 混合批被迫用同一套配置 ⟹ 两边都不是最优

第三条代价，直接催生了下一个想法：

    ★★ 既然两个阶段性格相反、最优配置也不同，
       为什么要把它们放在同一台机器上？

       ⟹ 拆开！Prefill 一个集群、Decode 一个集群，中间传 KV Cache
       ⟹ 这就是 【PD 分离】，见 [10 章](10-PD分离.md)
       ✅ 代表工作：DistServe (2401.09670)、Splitwise (2311.18677)、
          Mooncake (2407.00079)，三篇 PDF 都在 papers/ 里

3.5 顺带解决一个常见误解

❓ "Prefill 那么快，是不是可以忽略？"

不能。看两个场景：

    场景一：对话机器人，prompt 20 字、回答 500 字
            ⟹ Decode 是绝对大头，Prefill 可忽略

    场景二：★ RAG（检索增强生成）/ 长文档总结
            prompt 32000 字、回答 200 字
            ⟹ Prefill 要跑 32000 个 token，可能要【好几秒】
            ⟹ TTFT 全部由 Prefill 决定，Decode 反而不是瓶颈

    ⟹ ★★ 两个阶段谁是瓶颈，取决于你的【输入输出长度比】。
       这个比值叫 P:D ratio，是选型时第一个要问的数字（13 章）。

而前缀缓存正是场景二的解药——如果 32000 字里有 30000 字是每次都一样的系统提示词，那 Prefill 可以直接跳过它们（05 章）。
