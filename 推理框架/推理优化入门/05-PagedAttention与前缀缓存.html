05 PagedAttention 与前缀缓存

一句话：把操作系统的虚拟内存分页搬进 KV Cache 管理。这是 vLLM 之所以叫 vLLM 的原因（v = virtual，虚拟）。

5.1 先看没有分页时，显存被浪费成什么样

在 PagedAttention 之前，框架给每个请求分配 KV Cache 的做法是：按最大可能长度，一次性预留一整块连续显存。

    请求进来，max_tokens = 2048（用户设的上限）
    ⟹ 立刻预留 2048 个 token 的连续空间

    实际上它只生成了 100 个字就结束了
    ⟹ ★★ 1948 个 token 的空间，从头到尾【一次都没用过】

vLLM 论文（arXiv 2309.06180）把浪费拆成三类，这个分类非常清晰：

┌──────────────────────────────────────────────────────────────┐
│  一个预留了 2048 槽位、实际用了 100 个的请求：                  │
│                                                              │
│  [已用 100][ 保留 (reserved) ][  内部碎片 (internal frag.)  ] │
│   ↑         ↑                   ↑                            │
│   ①真在用   ②以后【可能】会用     ③★ 永远不会用到（因为提前结束）│
│                                                              │
│  ④ 外部碎片 (external fragmentation)：                        │
│     块与块之间剩下的零头，谁都装不下                            │
└──────────────────────────────────────────────────────────────┘

✅ 论文披露的数字（vLLM 论文 §1 / Figure 2）：在此前的系统里，
实际存储 token 的显存只占已分配显存的 20.4%~38.2%，
其余全是上面三类浪费。vLLM 把这个数字提到了 96% 以上。

5.2 PagedAttention：像操作系统那样管显存

这个类比是理解全章的钥匙：

┌──────────────────┬────────────────────────────────────┐
│  操作系统         │  vLLM                              │
├──────────────────┼────────────────────────────────────┤
│  进程            │  一个请求（一条序列）                │
│  虚拟地址空间     │  逻辑上连续的 KV 序列                │
│  物理内存页 (4KB) │  ★ KV 块（block），默认 16 个 token  │
│  页表            │  ★ block table（块表）               │
│  按需分页        │  写满一块才申请下一块                 │
│  写时复制 (COW)  │  ★ 并行采样多个候选时共享前缀          │
└──────────────────┴────────────────────────────────────┘

关键洞察：

    ★★ KV Cache 在【逻辑上】必须连续（注意力要按顺序读 K_1..K_t），
       但在【物理显存里】完全【不需要】连续。

    ⟹ 只要有一张表记住「逻辑第 i 块 → 物理第 j 块」，
       注意力 kernel 按表去取就行。

    逻辑视图（请求 A 看到的）:
    [tok 0..15][tok 16..31][tok 32..47][tok 48..63]
        块0        块1         块2         块3
         │          │           │           │
    块表: 7          2          19          5
         ▼          ▼           ▼           ▼
    物理显存（乱序摆放，中间还夹着别的请求的块）:
    ...[ #2 ]...[ #5 ]...[ #7 ]...[ #19 ]...

    ★ 收益一：不再需要连续大块 ⟹ 外部碎片【消失】
    ★ 收益二：写满一块才申请下一块 ⟹ 保留浪费【消失】
    ★ 收益三：最多浪费【最后一块】的零头 ⟹ 内部碎片 ≤ 15 个 token

★ 为什么块大小是 16？ 太小 → 块表变长、kernel 里查表开销大；
太大 → 最后一块的零头浪费变多。16 是一个经验平衡点。

代价：注意力 kernel 必须重写。标准的 FlashAttention 假设 KV 在显存里连续，PagedAttention 要求它先查块表再按块取数。这就是为什么这是个系统工作而不只是个内存分配器。

5.3 顺手解决的第二个问题：共享

分页带来一个几乎免费的红利——不同请求可以指向同一个物理块。

    并行采样（一个 prompt 生成 4 个候选答案）：
      候选1 块表: [7, 2, 19, 41]
      候选2 块表: [7, 2, 19, 55]
      候选3 块表: [7, 2, 19, 63]
      候选4 块表: [7, 2, 19, 88]
                   ↑─共享─↑
      ★ prompt 部分的 KV【只存一份】，省了 3 份的显存

    ★ 写时复制（copy-on-write）：某个候选要往共享块里写新 token 时，
      才复制一份自己的 —— 和操作系统 fork() 完全一样的机制

5.4 前缀缓存：把共享从「一个请求内」扩展到「所有请求之间」

上面的共享只发生在同一个 prompt 的多个候选之间。前缀缓存（prefix caching）把它推广到跨请求、跨时间。

    真实场景：所有用户都带着同一段 2000 字的系统提示词

    用户1 10:00 到达 → Prefill 2000 字 → ★ 把这些块【留在显存里别删】
    用户2 10:01 到达 → 发现前 2000 字一模一样
                     → ★★ 直接指向用户1 的块，Prefill 【跳过】
                     → TTFT 从 800ms 降到 20ms

怎么判断"一模一样"？——靠哈希。

    ★ 每个【写满的】块，算一个哈希：
       block_hash = hash( 上一块的 hash , 这一块的 16 个 token id , 额外键 )
                            ↑ ★ 链式的，保证【前缀路径】相同才算命中
                                                    ↑ 额外键 = 多模态图片、
                                                      LoRA 适配器 id 等

    ⟹ 查表：hash 在不在 BlockHashToBlockMap 里？在 → 直接复用

✅ 源码可查（vLLM）：
- 哈希函数 kv_cache_utils.py:618 hash_block_tokens
- 额外键 kv_cache_utils.py:580 generate_block_hash_extra_keys
- 哈希表 block_pool.py:33 class BlockHashToBlockMap
- 写满即入表 block_pool.py:225 cache_full_blocks
- 链的起点 kv_cache_utils.py:102 NONE_HASH，
种子字符串是 "vllm-none-hash"（L106）

★ 注意 cache_full_blocks 这个名字——只有写满的块才进缓存。
半满的块（cache_partial_block，L445）走另一条路，因为它的内容还会变。

5.5 SGLang 的另一条路：RadixAttention（基数树）

vLLM 用哈希表，SGLang 用树。这不是实现细节，是能力差异。

📖 基数树（radix tree，也叫压缩前缀树 / Patricia trie）——一种把公共前缀合并成一条边的树。

    三个请求：
      "你是一个助手。请介绍杭州"
      "你是一个助手。请介绍北京"
      "你是一个助手。今天天气"

    基数树自动长成：
                 ┌─「你是一个助手。」─┐        ← ★ 只存一份
                 │                    │
            ┌────┴────┐          ┌────┴────┐
         「请介绍」                「今天天气」
        ┌────┴────┐
     「杭州」   「北京」

    ★ 树结构给了哈希表给不了的三件事：
      ① 查询「最长公共前缀」是【一次树遍历】，不用逐块试哈希
      ② ★★ 调度器可以【提前问】：这个请求能命中多少？（04 章的缓存感知调度）
      ③ 淘汰时可以从【叶子】往上剪，天然保住被共享最多的根部

✅ 源码可查（SGLang，radix_cache.py）：
class TreeNode L238、class RadixCache L303、
match_prefix L377（最长前缀匹配）、insert L437、
evict L593（LRU 淘汰）、_split_node L705（插入时把一条边劈成两段——这是基数树的标志性操作）、
inc_lock_ref L623（在用的块不许淘汰）。

对比一句话：

vLLM 哈希表 SGLang 基数树
查询命中 逐块查哈希，O(块数) 一次遍历，O(前缀长度)
能否预估命中率 难 ★ 容易 ⟹ 支撑缓存感知调度
淘汰粒度 块级 LRU ★ 叶子优先，保根
实现复杂度 简单 复杂（要处理节点分裂/合并）

⚠️（我的判断）两者的最终命中效果在常见负载下接近，真正的差距在 ②——
SGLang 能把「命中率」当成调度输入，vLLM 更多是「命中了算赚到」。

5.6 缓存不是白拿的

    ⚠️ 一：缓存块占的显存，就是不能给新请求用的显存
       ⟹ 命中率低的负载（每个用户 prompt 都不一样）反而是负收益

    ⚠️ 二：★ 前缀缓存有【安全边界】问题
       用户A 的对话内容留在缓存里，用户B 如果能通过响应时间差异
       探测出「我的前缀命中了」，就能推断出 A 说过什么
       ⟹ 多租户场景要按租户隔离缓存空间

    ⚠️ 三：哈希碰撞（理论上）
       vLLM 用的是 Python 内置 hash + 可配置的哈希函数，
       ★ 生产环境有安全要求时应显式配置为加密哈希
