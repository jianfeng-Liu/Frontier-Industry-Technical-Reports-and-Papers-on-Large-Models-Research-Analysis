# 05 PagedAttention 与前缀缓存

> **一句话**：把操作系统的**虚拟内存分页**搬进 KV Cache 管理。这是 vLLM 之所以叫 vLLM 的原因（**v** = virtual，虚拟）。

---

## 5.0 本章的固定配置

后面每一笔账都用这一套数字，不换来换去。它和 [02 章](02-KV-Cache与显存账.md) 是同一套。

| 项目 | 取值 | 怎么来的 |
|---|---|---|
| 模型 | Llama-3-8B | 32 层，8 个 KV 头，head_dim = 128，BF16 |
| **每 token 的 KV Cache** | **128 KiB** | 2 × 32 层 × 8 头 × 128 × 2 字节 |
| 卡 | 单张 H100 SXM5 80 GB | HBM3 带宽 3.35 TB/s |
| **留给 KV Cache 的空间** | **56 GiB** | 80 GB 减权重 16 GB、再减框架与临时激活约 4 GB |
| 块大小 `block_size` | **16 个 token** | 一块 = 16 × 128 KiB = **2 MiB** |
| 用户设的生成上限 `max_tokens` | 2048 | §5.1 用它做朴素预分配 |

> 📖 **KiB / GiB**——1 KiB = 1024 字节，1 GiB = 1024³ 字节。厂商标的显存「80 GB」是十进制的 80 × 10⁹ 字节，换算成 GiB 只有 74.5 GiB。⚠️ 本章凡是算「装得下多少 token」一律用 KiB / GiB；02 章里写的「128 KB」指的就是这里的 128 KiB，同一个数。

## 5.1 先把浪费算出来：没有分页时显存去哪了

在 PagedAttention 之前，框架给每个请求分配 KV Cache 的做法是：**按最大可能长度，一次性预留一整块连续显存**。

```
    请求进来，用户设的上限让这条序列最长可能到 2048 个 token
    ⟹ 立刻预留 2048 × 128 KiB = 256 MiB 的【连续】显存

    实际上这条序列总共只用到 300 个 token（prompt 128 + 生成 172）就结束了
    ⟹ ★★ 1748 个 token 的空间，从头到尾【一次都没写过】
```

**跟着这个请求走一遍，看这块显存的使用曲线**：

```
    一个请求的 256 MiB 预留块（每格 64 个 token，共 32 格）

    刚分配时      ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░   32 格全空
    Prefill 完    ██░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░   prompt 128 tok
    生成 100 个后 ████░░░░░░░░░░░░░░░░░░░░░░░░░░░░   228 tok
    生成 172 个后 █████░░░░░░░░░░░░░░░░░░░░░░░░░░░   300 tok，然后吐 <EOS>
    请求结束      ────────────────────────────────   整块 256 MiB 一次性还回去

    █ = 真的写了 KV        ░ = 分给它了、但一个字节都没写过
```

vLLM 论文（arXiv 2309.06180）把 ░ 的部分拆成三类，这个分类要记住，后面一直用：

| 名字 | 什么意思 | 在上图里是哪一块 | 分页治得了吗 |
|---|---|---|---|
| **保留**（reserved） | 分给它了，将来**可能**会用到 | 请求还在生成时，前面那一片 ░ | ✅ 治：写满一块才申请下一块，根本不提前留 |
| **内部碎片**（internal fragmentation） | 分给它了，但**注定**用不到 | 请求结束那一刻还是 ░ 的 1748 个槽 | ✅ 治到只剩「最后一块的零头」 |
| **外部碎片**（external fragmentation） | 总空闲量够，但**凑不出一整块连续的** | 图里看不到，它在显存全局 | ✅ **定义上消失**（所有块一样大） |

**外部碎片长什么样**——它是「连续」这个要求逼出来的：

```
    朴素做法要的是【一整段连续的 256 MiB】。
    服务器跑了一阵，请求来来去去，显存被打成这个样子：

    显存布局   ████ .... ██████ ... ███ ..... ████
    每段大小   240   120   360    90  180  140  200      （单位 MiB）
               占用  空闲  占用   空闲 占用  空闲 占用

    ├── 空闲总量 = 120 + 90 + 140 = 350 MiB  >  256 MiB
    ├── ★ 但最大的一段连续空闲只有 140 MiB
    └── ⟹ 新请求被拒之门外，而显存明明还空着 350 MiB
```

> ✅ **论文披露的数字**（vLLM 论文 §1 / Figure 2）：在此前的系统里，**真正存着 token 的显存只占已分配显存的 20.4%~38.2%**，其余全是上面三类浪费。**vLLM 把这个数字提到了 96% 以上。**

## 5.2 把这笔账算成具体的并发数

光说「浪费 60%」没有痛感，换算成「少服务多少用户」才有。假设一个典型的聊天负载，`max_tokens` 统一设成 2048：

| 请求类型 | 占比 | 实际用到的 token | 预留的 token | 白占的 token |
|---|---|---|---|---|
| 短问答（「今天几号」） | 50% | 300 | 2048 | 1748 |
| 中等回答 | 30% | 800 | 2048 | 1248 |
| 长回答 | 15% | 2000 | 2048 | 48 |
| 顶到上限被截断 | 5% | 2048 | 2048 | 0 |
| **加权平均** | — | **792** | **2048** | **1256** |

加权平均怎么算的：`0.50×300 + 0.30×800 + 0.15×2000 + 0.05×2048 = 792` 个 token。

```
    ★ 有效利用率 = 792 ÷ 2048 = 38.7%

    ⟹ 这个数字正好落在 vLLM 论文报告的 20.4%~38.2% 的上沿。
       论文不是在举极端例子，这就是【日常负载】的样子。
```

**分页之后同一笔账**：请求不再预留 2048，而是写满一块（16 token）才申请下一块。最后一块平均空一半，也就是 **平均每个请求多占 8 个 token**。

```
    分页后每请求平均占用 = 792 + 8 = 800 个 token = 100 MiB
                                 ↑
                    ★ 内部碎片的通式：平均 = block_size ÷ 2 个 token
```

两种做法并排：

| | 朴素预分配 | PagedAttention（block = 16） |
|---|---|---|
| 每个请求占用 | 2048 tok = **256 MiB** | 平均 800 tok = **100 MiB** |
| 56 GiB 能同时装 | 57344 ÷ 256 = **224 个请求** | 57344 ÷ 100 = **573 个请求** |
| 白占的显存比例 | **61.3%** | 8 ÷ 800 = **1.0%** |
| 外部碎片 | 有，而且越跑越碎 | **结构上不存在** |
| **并发提升** | — | **2.56 倍** |

> ★ **这个 2.56 倍不是常数，它等于「预留上限 ÷ 平均真实长度」**（2048 ÷ 800）。很多服务的 `max_tokens` 默认是 8192 甚至更大——那时朴素做法每请求要 1 GiB，56 GiB 只装得下 56 个，倍数就变成 **7.9 倍**。⟹ **服务端把上限设得越宽松，分页救回来的越多。** 那笔 8192 上限的账在 [大模型算子开发 09 章 §9.3.3](../../大模型算子开发/09-推理侧算子.md)。

## 5.3 PagedAttention：像操作系统那样管显存

**这个类比是理解全章的钥匙**，一行一行对着看：

| 操作系统 | vLLM | 本章的具体值 |
|---|---|---|
| 进程 | 一个请求（一条序列） | — |
| 虚拟地址空间 | 逻辑上连续的 KV 序列 | 该请求的第 0…t 个 token |
| 物理内存页（4 KB） | ★ **KV 块**（block） | 16 个 token = 2 MiB |
| 页表 | ★ **块表**（block table） | 逻辑块号 → 物理块号 |
| 物理页帧 | 显存里的物理块 | 56 GiB ÷ 2 MiB = **28,672 块** |
| 按需分页 | 写满一块才申请下一块 | §5.2 的 1.0% 碎片率 |
| 写时复制（COW） | ★ 共享前缀 + 引用计数 | §5.4 |
| 换出到磁盘（swap） | 抢占：换到 CPU 内存，或直接丢弃重算 | §5.7 |

**关键洞察只有一句**：

```
    ★★ KV Cache 在【逻辑上】必须连续（注意力要按顺序读 K_1..K_t），
       但在【物理显存里】完全【不需要】连续。

    ⟹ 只要有一张表记住「逻辑第 i 块 → 物理第 j 块」，
       注意力 kernel 按表去取就行。
```

```
    逻辑视图（请求 A 自己看到的，连续的一条）:
    [tok 0..15][tok 16..31][tok 32..47][tok 48..63]
        块0        块1         块2         块3
         │          │           │           │
    块表: 7          2          19          5
         ▼          ▼           ▼           ▼
    物理显存（乱序摆放，中间还夹着别的请求的块）:
    ...[ #2 ]...[ #5 ]...[ #7 ]...[ #19 ]...

    ★ 收益一：不再需要连续大块  ⟹ 外部碎片【消失】
    ★ 收益二：写满一块才申请下一块 ⟹ 保留浪费【消失】
    ★ 收益三：最多浪费【最后一块】的零头 ⟹ 内部碎片 ≤ 15 个 token
```

> ★ **为什么块大小是 16？** 太小 → 块表变长、查表更频繁，而且**一次能连续搬的字节数变少，合并访存效率下降**；太大 → 最后一块的零头浪费变多。16 是一个经验平衡点。⚠️ vLLM 常用 16，SGLang 的默认值随版本变化，以自己那一版的配置为准。

**代价**：注意力 kernel 必须重写。标准的 FlashAttention 假设 KV 在显存里是一整条，PagedAttention 要求它**先查块表，再按块取数**。kernel 侧究竟改了哪几行、这次查表贵不贵，见 [大模型算子开发 09 章 §9.3.4](../../大模型算子开发/09-推理侧算子.md)（结论：查表的表很小，常驻 L2，在访存受限的算子里几乎免费）。**这就是为什么 PagedAttention 是个系统工作，而不只是个内存分配器。**

## 5.4 顺手解决的第二个问题：共享与引用计数

分页带来一个几乎免费的红利——**不同请求的块表可以指向同一个物理块**。

**场景一：并行采样**（一个 prompt 生成 4 个候选答案）。

```
      候选1 块表: [7, 2, 19, 41]
      候选2 块表: [7, 2, 19, 55]
      候选3 块表: [7, 2, 19, 63]
      候选4 块表: [7, 2, 19, 88]
                   ↑─共享─↑
      ★ prompt 部分的 KV【只存一份】，省了 3 份的显存
```

**场景二：所有用户共用同一段系统提示词**——这才是生产环境的大头。算一笔账：

```
    系统提示词 2000 个 token  ⟹  2000 ÷ 16 = 125 块（正好整除）
    125 块 × 2 MiB = 250 MiB
    假设同时有 100 个用户在线，每个人的请求都带着这 2000 字
```

| | 不共享 | 共享同一份 |
|---|---|---|
| 系统提示词占的显存 | 100 × 250 MiB = **24.4 GiB** | **250 MiB** |
| 占 56 GiB 池子的比例 | **43.6%** | 0.4% |
| 需要做的 Prefill 次数 | 100 次 × 2000 token | **1 次** |

> ★★ **43.6% 的 KV 显存在存 100 份一模一样的东西。** 这是分页之后最容易摘的果子。

**引用计数（reference count）怎么记账**——这是共享能安全工作的全部机制：

| 物理块 | 里面装的是 | 谁在用 | 引用计数 | 能回收吗 |
|---|---|---|---|---|
| #71 … #12（共 125 块） | 系统提示词的 2000 token | 用户 A / B / C | **3** | ❌ 不能 |
| #55 | 用户 A 自己的问题 | 用户 A | 1 | A 结束后可以 |
| #83 | 用户 B 自己的问题 | 用户 B | 1 | B 结束后可以 |

```
    引用计数的三条规则：

    ① 新请求命中了某段前缀  ⟹ 那些块的计数 +1，【不复制任何数据】
    ② 请求结束             ⟹ 它块表里的所有块计数 −1
    ③ 计数归 0             ⟹ 块回到空闲池
       ★ 但【内容不清空】——下次还可能被别人命中。这是 §5.5 的伏笔。
```

**写时复制（copy-on-write）**：某个候选要往一个**共享的、还没写满的**块里追加 token 时，先把这一块复制一份、改引用计数，再往副本里写。**和操作系统 `fork()` 之后的行为一模一样。**

## 5.5 前缀缓存：把共享从「一个请求内」扩展到「所有请求之间」

§5.4 的共享，发生在**同时在线**的请求之间。**前缀缓存（prefix caching）把它推广到跨请求、跨时间**——靠的就是上面第 ③ 条规则：**计数归 0 的块，内容还在。**

```
    用户1 10:00 到达 → Prefill 2000 字 → 生成完毕 → 块计数归 0
                     ★ 但这 125 块【留在池子里，内容不动】
    用户2 10:01 到达 → 发现前 2000 字一模一样
                     → ★★ 计数 +1 直接接管，Prefill 【跳过】
```

**TTFT 省了多少**（沿用 8B / H100 的口径）：

| | 没有前缀缓存 | 命中前缀缓存 |
|---|---|---|
| 要 Prefill 的 token | 2000（系统提示词）+ 30（用户问题） | 只有 30 |
| 理论耗时 | 约 30 ms | 约 0.5 ms |
| ⚠️ 按 50~60% 实际利用率 | **约 50~60 ms** | **约 1 ms**，加上调度/采样开销，几毫秒量级 |

> ⚠️ **别照搬「800 ms 降到 20 ms」这类数字**（本章旧版就是这么写的，**偏大得离谱**）。8B 模型在 H100 上做 2000 token 的 Prefill，算力侧就是 30 ms 量级——推导见 [大模型算子开发 09 章 §9.1.4](../../大模型算子开发/09-推理侧算子.md)。几百毫秒的 TTFT 只会出现在**更大的模型**（70B 以上）或者**队列已经堵住**的时候，那时省下来的主要是排队时间，不是 Prefill 时间。**引用 TTFT 数字必须带上模型大小和是否排队。**

**怎么判断「一模一样」？——靠链式哈希。**

```
    ★ 每个【写满的】块，算一个哈希：

       block_hash = hash( 上一块的 hash ,
                          这一块的 16 个 token id ,
                          额外键 )
                      ↑                        ↑
          ★ 链式的，保证【整条前缀路径】     额外键 = 多模态图片、
            都相同才算命中                    LoRA 适配器 id 等

    ⟹ 查表：这个 hash 在不在 BlockHashToBlockMap 里？在 → 直接复用
```

> ★ **为什么必须链式？** 因为「第 5 块内容相同」不代表「前 4 块也相同」。把上一块的 hash 拌进来，等于把整条前缀压进了一个值里——两个块 hash 相同，就意味着从头到这里完全一致。

> ✅ **源码可查**（vLLM）：
> - 哈希函数 [kv_cache_utils.py:618](../源码/vLLM/vllm/v1/core/kv_cache_utils.py#L618) `hash_block_tokens`
> - 额外键 [kv_cache_utils.py:580](../源码/vLLM/vllm/v1/core/kv_cache_utils.py#L580) `generate_block_hash_extra_keys`
> - 哈希表 [block_pool.py:33](../源码/vLLM/vllm/v1/core/block_pool.py#L33) `class BlockHashToBlockMap`
> - 写满即入表 [block_pool.py:225](../源码/vLLM/vllm/v1/core/block_pool.py#L225) `cache_full_blocks`
> - 链的起点 [kv_cache_utils.py:102](../源码/vLLM/vllm/v1/core/kv_cache_utils.py#L102) `NONE_HASH`，种子字符串是 `"vllm-none-hash"`（L106）

> ★ 注意 `cache_full_blocks` 这个名字——**只有写满的块才进缓存**。半满的块（`cache_partial_block`，L445）走另一条路，因为它的内容还会变，现在算的哈希下一步就作废了。

## 5.6 SGLang 的另一条路：RadixAttention（基数树）

vLLM 用**哈希表**，SGLang 用**树**。这不是实现细节，是能力差异。

> 📖 **基数树**（radix tree，也叫压缩前缀树 / Patricia trie）——一种把公共前缀合并成**一条边**的树。普通前缀树一条边只放一个字符，基数树一条边可以放一整段。

```
    三个请求：
      A  "你是一个助手。请介绍杭州"
      B  "你是一个助手。请介绍北京"
      C  "你是一个助手。今天天气"

    基数树自动长成这样（★ 每条边上挂的是【一段 token 的 KV】）：

    (root)
      └── 「你是一个助手。」          ← ★ KV 只存一份，A / B / C 共用
            ├── 「请介绍」            ← ★ 只存一份，A / B 共用
            │     ├── 「杭州」        ← A 独占
            │     └── 「北京」        ← B 独占
            └── 「今天天气」          ← C 独占
```

**B 到达时省了多少**：

| 请求 | 总 prompt 长度 | 沿树走能复用的 | 真正要新算的 |
|---|---|---|---|
| A（第一个到） | 「你是一个助手。请介绍杭州」 | 0 | 全部 |
| B | 同长度 | 「你是一个助手。请介绍」 | 只剩「北京」 |
| C | — | 「你是一个助手。」 | 「今天天气」 |

```
    ★ 树结构给了哈希表给不了的三件事：

    ① 查「最长公共前缀」是【一次树遍历】，不用从第 1 块开始逐块试哈希
    ② ★★ 调度器可以【提前问】：这个请求能命中多少？
       ⟹ 这就是 04 章的「缓存感知调度」——把高命中的请求排在一起跑
    ③ 淘汰时从【叶子】往上剪，天然保住被共享最多的根部
       （哈希表的块级 LRU 做不到这一点，它不知道谁是根）
```

> ✅ **源码可查**（SGLang，[radix_cache.py](../源码/SGLang/python/sglang/srt/mem_cache/radix_cache.py)）：`class TreeNode` **L238**、`class RadixCache` **L303**、`match_prefix` **L377**（最长前缀匹配）、`insert` **L437**、`evict` **L593**（LRU 淘汰）、`_split_node` **L705**（插入时把一条边劈成两段——这是基数树的标志性操作）、`inc_lock_ref` **L623**（在用的块不许淘汰，就是 §5.4 的引用计数）。

**对比一句话**：

| | vLLM 哈希表 | SGLang 基数树 |
|---|---|---|
| 查询命中 | 逐块查哈希，O(块数) | 一次遍历，O(前缀长度) |
| 能否预估命中率 | 难 | ★ 容易 ⟹ 支撑缓存感知调度 |
| 淘汰粒度 | 块级 LRU | ★ 叶子优先，保根 |
| 实现复杂度 | 简单 | 复杂（要处理节点分裂 / 合并） |

> ⚠️（我的判断，非实测）两者的**最终命中效果在常见负载下接近**，真正的差距在第 ② 条——SGLang 能把「命中率」当成调度的输入，vLLM 更多是「命中了算赚到」。

## 5.7 装不下的时候：抢占

分页把并发从 224 提到 573，但显存总有用完的一天——一批请求同时进入长生成，块池见底。这时调度器必须**抢占**某些请求，把它们的块吐出来：

| 策略 | 做法 | 代价 | 什么时候划算 |
|---|---|---|---|
| **换出**（swap） | 把它的块拷到 CPU 内存，之后再拷回来 | 过 PCIe，⚠️ 约 64 GB/s，比 HBM 慢 50 倍 | 块很多、重算很贵时 |
| **重算**（recompute） | 直接丢弃这些块，之后重新 Prefill 一遍 | 一次 Prefill 的算力 | 序列短时更简单也更省心 |

```
    一个 2048 token 的请求，KV = 256 MiB

    换出再换回：256 MiB × 2 ÷ 64 GB/s ≈  8.4 ms
    丢弃再重算：Prefill 2048 token     ≈ 30 ms（算力侧理论下界）

    ⟹ 这个长度下换出更快；但重算不占 CPU 内存、不抢 PCIe，实现也简单得多。
    ⚠️ 实际选哪个还要看 PCIe 是不是已经被别的流量占满，生产系统两种都要有。
```

## 5.8 缓存不是白拿的（但也没那么贵）

```
    ⚠️ 一：★ 前缀缓存有【安全边界】问题
       用户A 的对话内容留在缓存里。用户B 如果能通过【响应时间差异】
       探测出「我这段前缀命中了」，就能反推出 A 说过什么
       ⟹ ★★ 多租户场景必须按租户隔离缓存空间，或把租户 id 拌进哈希的「额外键」

    ⚠️ 二：记账本身要钱
       每一步都要算哈希 / 走树、维护引用计数、维护 LRU 顺序
       ⟹ 命中率极低的负载（每个用户的 prompt 都完全不同），
          这些开销就是纯亏——只是亏得不多

    ⚠️ 三：哈希碰撞（理论上）
       vLLM 默认用 Python 内置 hash，可配置换成别的
       ⟹ ★ 生产环境有安全要求时应显式配置为加密哈希
```

> ⚠️ **一处要纠正本章旧版的说法**：旧版写「缓存块占的显存就是不能给新请求用的显存，所以命中率低时是负收益」。**这不准确。** vLLM 和 SGLang 的实现里，引用计数归 0 的块**仍然躺在空闲池里**，新请求一伸手就被 LRU 立刻淘汰掉（`evict` / `BlockPool` 的空闲队列）。⟹ **前缀缓存不会挤占并发**，它不是「划一块地出来当缓存」，而是「反正要空着，顺便留着内容」。真正的代价是上面那三条，不是显存。

## 5.9 本章小结

```
    ① 分页前：显存有效利用率只有 20%~38%（✅ vLLM 论文披露）
       浪费分三类：保留 / 内部碎片 / 外部碎片
       ⟹ 本章的负载算出来是 38.7%，正好在论文区间的上沿

    ② ★★ PagedAttention = 操作系统的虚拟内存
       逻辑连续 + 物理离散 + 块表，块大小 16 个 token
       ⟹ 外部碎片【结构上消失】，内部碎片降到 1.0%
       ⟹ 本章配置下并发 224 → 573（2.56 倍）；
          max_tokens 设得越宽松，倍数越大（8192 时是 7.9 倍）
       代价：注意力 kernel 要重写成「先查表再取数」

    ③ 分页顺手带来【共享】：引用计数 + 写时复制
       ⟹ 100 个用户共用一段 2000 字系统提示词：
          24.4 GiB（43.6% 的池子）→ 250 MiB

    ④ 前缀缓存把共享推广到跨请求、跨时间
       靠的是「计数归 0 的块内容不清空」
       vLLM：★ 链式哈希 + 哈希表（✅ hash_block_tokens）
       SGLang：★ 基数树（✅ RadixCache）⟹ 能预估命中率 ⟹ 缓存感知调度

    ⑤ ★ 前缀缓存【不挤占并发】（空闲块随时可被 LRU 淘汰）
       它真正的代价是：记账开销 + 跨租户信息泄露面
```
