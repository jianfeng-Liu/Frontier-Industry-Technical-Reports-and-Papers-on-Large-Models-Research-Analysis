## 6.0 先把结论摆出来

```
┌───────────────────────────────────────────────────────────────────┐
│  训练（Megatron-LM）的 rank 排布顺序：                             │
│      tp - cp - ep - dp - pp        ← ★ PP 在最外，DP 在中间        │

└───────────────────────────────────────────────────────────────────┘
```

## 6.1 先复习：rank 排布顺序到底在说什么

> 📖 **rank**——每张 GPU 的全局编号，0, 1, 2, ... N-1。
> 📖 **排布顺序**——把这 N 个编号 reshape 成一个多维数组，**哪个维度变化最快**。

vLLM 就是字面意义上地 reshape 了一下：

```python
# ✅ parallel_state.py:1826
all_ranks = torch.arange(world_size).reshape(
    -1,                                    # ExternalDP
    data_parallel_size,                    # DP
    pipeline_model_parallel_size,          # PP
    prefill_context_model_parallel_size,   # PCP
    tensor_model_parallel_size,            # TP   ← ★ 最后一维 = 变化最快
)
```

**「变化最快」= 组内 rank 编号连续 = 物理距离最近。** 这就是全部的含义。

```
    ★ 步长（stride）= 同组内相邻两个 rank 的编号差

      TP  组：步长 1                     ← ★ 最近，同一台机器内，走 NVLink
      PCP 组：步长 = TP
      PP  组：步长 = PCP × TP
      DP  组：步长 = PP × PCP × TP       ← ★ 最远，跨机器，走网络

    ⟹ ★★ 排在【越后面】的维度，通信越【近】越【快】。
       所以排布顺序的设计原则永远是同一条：
       ★★★ 通信量最大的维度，放到最后（离得最近）。
```

拿一个具体例子：**8 卡，TP=2，PP=2，DP=2**（PCP=1）：

```
    reshape 成 [1, 2, 2, 1, 2]，即 [ExtDP=1][DP=2][PP=2][PCP=1][TP=2]

    rank 0 1 2 3 4 5 6 7 摆进去：

              DP=0                    DP=1
        ┌───────────────┐      ┌───────────────┐
    PP=0│  rank 0, 1    │      │  rank 4, 5    │
        │   └─TP 组─┘   │      │   └─TP 组─┘   │
    PP=1│  rank 2, 3    │      │  rank 6, 7    │
        │   └─TP 组─┘   │      │   └─TP 组─┘   │
        └───────────────┘      └───────────────┘

    ⟹ TP 组：[0,1] [2,3] [4,5] [6,7]           步长 1  ★最近
    ⟹ PP 组：[0,2] [1,3] [4,6] [5,7]           步长 2
    ⟹ DP 组：[0,4] [1,5] [2,6] [3,7]           步长 4  ★最远

    ★★ 请对比训练：训练里 DP 步长小于 PP，DP 比 PP 【近】。
       这里反过来了。
```

> ✅ 各组的构造代码：
> TP [parallel_state.py:1843](../源码/vLLM/vllm/distributed/parallel_state.py#L1843)（直接 `view(-1, tp)`，不需要转置，因为它已经在最后一维）；
> PP [L1891](../源码/vLLM/vllm/distributed/parallel_state.py#L1891)（`all_ranks.transpose(2, 4)`——把第 2 维换到最后）；
> DP [L1908](../源码/vLLM/vllm/distributed/parallel_state.py#L1908)（`all_ranks.transpose(1, 4)`）。
> ★ 代码注释把这套手法说得很清楚：*"to get group_ranks for each dimension, transpose that dimension to the last dimension, then reshape to 2D, then unbind"*。

## 6.2 ★★ 为什么反过来：一张表说清

回到那条唯一的原则——**通信量大的放近处**。所以只要比较四个维度在训练/推理下各自的通信量：

```
┌────────┬──────────────────────────┬──────────────────────────┐
│  维度   │  训练的通信量             │  推理的通信量             │
├────────┼──────────────────────────┼──────────────────────────┤
│  TP    │ 每层 4 次 all-reduce      │ 每层 2 次 all-reduce      │
│        │ （前向2 + 反向2）          │ ★ 没有反向，直接减半      │
│        │ ⟹ 最大，必须放最近         │ ⟹ 仍然最大，仍放最近      │
├────────┼──────────────────────────┼──────────────────────────┤
│  PP    │ 每个 micro-batch 传一次   │ 每步传一次激活            │
│        │ 激活（前向）+ 梯度（反向） │ ★ 只有前向，量减半        │
│        │ 量中等，可以跨机           │ 量中等，可以跨机           │
├────────┼──────────────────────────┼──────────────────────────┤
│  DP    │ ★★ 每步 all-reduce 全部    │ ★★ 几乎【为零】           │
│        │ 梯度 = 2Ψ                 │ 各副本服务不同用户，       │
│        │ ⟹ 【非常贵】，必须离得近   │ 不需要同步任何东西         │
│        │                          │ ⟹ 【可以扔到天涯海角】     │
├────────┼──────────────────────────┼──────────────────────────┤
│  EP    │ 每层 2 次 all-to-all      │ 每层 2 次 all-to-all      │
│  (MoE) │ + 反向 2 次               │ ★ 没有反向                │
└────────┴──────────────────────────┴──────────────────────────┘
```

> 🔑 **★★★ 全章最重要的一句话**：
> 训练的 DP 每步要 all-reduce 整个模型的梯度（[训练框架/05 章](../../训练框架/分布式训练入门/05-ZeRO与FSDP.md) 算过是 2Ψ），
> 所以 DP 必须排在 PP 前面（更近）。
> **推理的 DP 只是「N 份完全独立的副本，各服务各的用户」，一个字节都不用传。**
> 既然它不花通信，就理应被踢到最外圈，把宝贵的近距离带宽让给 TP 和 PP。

**再补一个二阶原因**（⚠️ 我的推断，代码注释支持但未明说）：

```
    ★ DP 在最外层，还有一个工程上的好处：
      「一个 DP 副本」= 一段连续的 rank = 一个完整的、自洽的推理引擎实例。
      ⟹ 可以整块地启动、整块地挂掉重启、整块地做弹性伸缩
      ⟹ 这正是 ExternalDP 这一维存在的意义：
         代码注释说它用于 "verl integration"（强化学习框架），
         ★ every dp rank can generate independently
```

## 6.3 逐个维度：推理里它们各自怎么用

### ① TP（张量并行）——切权重，仍然是主力

> 📖 **TP**（**T**ensor **P**arallelism，张量并行）——把每一层的权重矩阵切开，每张卡存一片。

推理里的 TP 和训练完全同构，还是那套「列切 + 行切」：

```
    一个 MLP（多层感知机）块：
      第一个线性层：★ 按【列】切（ColumnParallelLinear）→ 不需要通信
      激活函数：                                        → 逐元素，不需要通信
      第二个线性层：★ 按【行】切（RowParallelLinear）   → ⚠️ 需要 all-reduce

    注意力块同理，QKV 按列切，输出投影按行切 → ⚠️ 一次 all-reduce

    ⟹ ★ 每层 2 次 all-reduce（注意力 1 次 + MLP 1 次）
```

> ✅ **源码可查**（vLLM [linear.py](../源码/vLLM/vllm/model_executor/layers/linear.py)）：
> `ColumnParallelLinear` **L407**（注意 `gather_output` 默认 **False**——★ 故意不 all-gather，把结果直接喂给下一个行切层，省掉一次通信）；
> `QKVParallelLinear` **L971**（QKV 三个矩阵合并成一个列切层）；
> `RowParallelLinear` **L1510**，唯一那次通信在 **L1660**：
> ```python
> output = tensor_model_parallel_all_reduce(output_parallel)
> ```

**推理里 TP 的两个新特点**：

```
    ★ 特点一：TP 是【降低单卡显存 + 降低延迟】的主要手段
      TP=8 ⟹ 权重和 KV Cache 都切成 1/8
           ⟹ 单个 token 的计算和访存都变成 1/8 ⟹ ★ TPOT 直接变快
      ⟹ 这是训练里没有的动机（训练不在乎单步延迟）

    ⚠️ 特点二：TP 在 Decode 阶段【收益递减】
      Decode 本来就访存受限、kernel 很小。TP=8 之后，
      每张卡的计算小到「通信时间 > 计算时间」
      ⟹ ★ 再加卡就是纯亏。经验上 TP 一般不超过单机卡数（8）。
      ⟹ 想再扩，用 DP 加副本，不要继续加 TP。
```

**一个 TP 的硬约束**：

```
    ⚠️ TP 数必须能整除【KV 头数】。
       Llama-3-8B 用了 GQA，只有 8 个 KV 头 ⟹ ★ TP 最大只能到 8。
       TP=16 的话，有的卡分不到 KV 头。
       （框架的绕法是复制 KV 头，但那就白费显存了）
```

### ② PP（流水线并行）——推理里地位下降

> 📖 **PP**（**P**ipeline **P**arallelism，流水线并行）——把模型按层切成几段，每张卡放一段。

```
    ★ 训练里 PP 很重要：它是唯一能把超大模型放下、且通信量小的手段。
    ⚠️ 推理里 PP 的地位明显下降，原因是【气泡】。
```

```
    训练的流水线：一个 batch 切成 N 个 micro-batch 灌进去
                 ⟹ 气泡率 ≈ (PP-1) / (PP-1+N)，N 可以很大 ⟹ 气泡小

    ★★ 推理的 Decode：每一步只有【1 个 token】
       ⟹ 没有 micro-batch 可切！
       ⟹ 气泡率 ≈ (PP-1)/PP，PP=4 时高达 75%

    ⚠️ 挽救办法：靠【连续批处理】天然的多请求来填流水线——
       不同请求处在不同的流水段上，互相填对方的气泡。
       ⟹ 所以推理的 PP 必须配合【大并发】才有意义。
```

> ⚠️（我的判断）实践中的选择顺序通常是：
> **能单机 TP 装下 → 只用 TP；单机装不下 → 先考虑量化（09 章）；还是装不下 → 才上 PP 跨机。**
> PP 主要用在「模型大到单机 8 卡也放不下」的场景（比如 DeepSeek-V3 这种 671B）。

### ③ DP（数据并行）——推理里含义完全不同

```
    ★ 训练的 DP：同一个 batch 切开，算完【必须 all-reduce 梯度】
    ★ 推理的 DP：★★ 就是「多开几个一模一样的服务实例」

    ⟹ 没有任何梯度、没有任何同步、通信量 = 0
    ⟹ 扩容方式：想翻倍吞吐？DP 翻倍即可，线性扩展
```

**但有一个坑**，代码注释专门警告了：

```python
# ✅ parallel_state.py:1819-1823
# DP is the data parallel group that is part of the model,
# all the ranks in the same DP group should generate simultaneously,
# i.e. the `generate` call in the same DP group should be called together,
# otherwise it will cause deadlock.
```

```
    ★★ 为什么会死锁？
       DP 组内虽然不传梯度，但如果模型里有 MoE 层，
       MoE 的 all-to-all 是【跨 DP 组】的集合通信（见 §6.4）。
       集合通信要求所有参与者【同时到场】。
       ⟹ 某个 DP rank 因为没请求而不发起 generate，其他人就永远在等它。
    ⟹ 这就是为什么 vLLM 里 DP 组必须「同步地一起 generate」，
       没请求的 rank 也要发一个【假的空 batch】进去凑数（dummy run）。
```

### ④ EP（专家并行）——MoE 专用

> 📖 **EP**（**E**xpert **P**arallelism，专家并行）——MoE 模型里，把不同的专家放到不同卡上。
> 📖 **MoE**（**M**ixture **o**f **E**xperts，混合专家）——每个 token 只激活一小部分参数。

EP 的 rank 组构造很有意思，它是 **DP × PCP × TP 三个维度合并**出来的：

```python
# ✅ parallel_state.py:1923 附近
group_ranks = all_ranks.transpose(1, 2).reshape(
    -1, data_parallel_size * prefill_context_model_parallel_size *
        tensor_model_parallel_size).unbind(0)
```

```
    ⟹ ★ EP 组 = 「同一个 PP 段内的所有卡」
       含义：专家在一层内横着切，但不跨流水线段——这符合直觉，
             因为不同 PP 段本来就是不同的层。
```

11 章会详细讲 MoE 推理和负载均衡（EPLB）。

### ⑤ 推理独有的新维度：PCP 和 DCP

这是训练侧没有的东西，vLLM 的比较新的加法：

```
    📖 CP（Context Parallelism，上下文并行）——把【序列】切开，
       不同卡负责序列的不同片段。训练侧也有（Ring Attention 等）。

    ★ vLLM 把它拆成了两个独立的旋钮：
      📖 PCP = Prefill Context Parallel（预填充上下文并行）
              → 处理超长 prompt 时，把 prompt 切段并行做 Prefill
              ★ 它在 rank 布局里占了独立一维（PP 和 TP 之间）
      📖 DCP = Decode Context Parallel（解码上下文并行）
              → 把【KV Cache】按序列维切到多张卡上
              ★ 主要解决的是「tp 超过 KV 头数后，KV 被白白复制」
                （单卡装不下超长序列只是顺带的好处，见 6.4.1）

    ⟹ ★★ 为什么要拆成两个？因为 03 章那条：两个阶段性格不同，
       Prefill 想切序列换算力，Decode 想切序列换显存。目标不一样。
```

> ✅ 布局里 PCP 的位置见 L1826 的 reshape；DCP 的组在 TP 组之后构造
> （[parallel_state.py:1851-1866](../源码/vLLM/vllm/distributed/parallel_state.py#L1851-L1866)）。
> ★ DCP **不占全局维度**——它是从已有的那五维里再切出来的，这和 PCP 不同。
>
> ⚠️ **一处要说准**：常说的「DCP 从 TP 组内部再切」只在 **PCP=1** 时成立。
> PCP>1 时源码会先转置再 reshape，注释写得很明白：
> ```python
> if dcp_size > 1:
>     # DCP spans PCP first, then TP for full TP x PCP groups.
>     dcp_ranks = dcp_ranks.transpose(-1, -2)
> group_ranks = dcp_ranks.reshape(-1, dcp_size).unbind(0)
> ```
> ⟹ DCP 组**先沿 PCP 铺，铺满了才溢出到 TP**。这也是为什么配置校验里
> PCP>1 时合法的 dcp 只有 `1 / pcp / tp*pcp` 三个值
> （[parallel.py:533](../源码/vLLM/vllm/config/parallel.py#L533)）。

> **DCP 具体怎么实现的？** ⟹ 下一节 6.4 整节都在讲这件事。

## 6.4 ★★ DCP 深挖：KV 到底怎么切、怎么拼回来

⑤ 里只说了 DCP「把 KV 按序列维切开」，这一节把它拆到能对着源码逐行读的程度。
之所以值得单开一节：DCP 是这一轮长上下文推理里**最实用的一个旋钮**，而它的设计里有两处相当反直觉。

> ✅ vLLM 官方文档：[docs/serving/context_parallel_deployment.md](../源码/vLLM/docs/serving/context_parallel_deployment.md)
> 命令行开关：`-dcp <size>` / `--decode-context-parallel-size`

---

### 6.4.1 真正的动机：不是「放不下」，是「白白重复」

先纠正一个很容易想岔的地方。DCP 的第一动机**不是**「单条 128K 序列的 KV 一张卡装不下」——那只是顺带的好处。真正的痛点是：

```
    ★ TP 切 KV Cache，是沿【KV 头数 H】这一维切的。
      但 H 是模型结构定死的，切不动了怎么办？

      tp_size ≤ H  ⟹ 正常切，每卡拿 H/tp 个头 ✅
      tp_size > H  ⟹ ★★ 没得切了，只能【每卡存一份一模一样的】
                    重复倍数 = tp_size / H
```

这就是 07 章「MLA 让 KV 变小」的副作用：**KV 越小，TP 越容易越过 H 这道坎**。

| 模型 | 注意力类型 | KV 头数 H | 典型部署 | ★ KV 重复倍数 |
|---|---|---|---|---|
| DeepSeek-R1 | MLA | **1** | `-tp 8` | **8×** |
| Kimi-K2 | MLA | **1** | `-tp 16` | **16×** |
| Qwen3-235B-A22B | GQA | 4 | `-tp 8` | 2× |

> ✅ 这三个例子和倍数都是官方文档里的原话（context_parallel_deployment.md 的 Case study 段）。

`-tp 16` 跑 Kimi-K2，等于 16 张卡的 KV Cache 显存**存了 16 份同样的东西**。加上 `-dcp 16` 就能完全消掉；加 `-dcp 8` 则降到 2×，但通信只发生在**单机内**（NVLink），代价更小。

```
    ⟹ ★★ 记住这句：DCP【不增加 GPU 数量】。
       它不是「再加几张卡来装 KV」，而是把 TP 组里那些
       本来存重复副本的卡，改成【各存一段】。
```

---

### 6.4.2 存：交错分片（interleave）——第一处反直觉

KV 要沿序列长度 `T` 切，怎么切？

```
    ✗ 朴素想法：切成连续的 N 段，rank0 拿前 1/N，rank1 拿next 1/N……
      ★★ 死在哪：Decode 阶段序列【是在长长的】。
         每生成一个 token，各段的边界就要挪一次，还得跨卡搬数据。
         成本完全无法接受。

    ✅ vLLM 的做法：交错分片（interleave）
      ★ token 归谁，【只取决于它的绝对位置】，和序列当前多长无关。
```

> ✅ 实现在 Triton 内核里：
> [block_table.py:410-475](../源码/vLLM/vllm/v1/worker/block_table.py#L410-L475)
> ```python
> virtual_block_size   = KV_CACHE_BLOCK_SIZE * TOTAL_CP_WORLD_SIZE
> virtual_block_indices = pos // virtual_block_size
> virtual_block_offsets = pos - virtual_block_indices * virtual_block_size
> # 这个 token 归不归我？
> is_local = (virtual_block_offsets // CP_KV_CACHE_INTERLEAVE_SIZE
>            ) % TOTAL_CP_WORLD_SIZE == TOTAL_CP_RANK
> ```

📖 **Triton**——OpenAI 的 GPU 内核编程语言，写起来像 Python，编译出来接近手写 CUDA。
📖 **slot mapping**——「第 i 个 token 的 KV 该写进显存池的哪个槽位」这张映射表。

`cp_kv_cache_interleave_size` 默认 **1**（[parallel.py:362](../源码/vLLM/vllm/config/parallel.py#L362)），也就是**逐 token 轮流坐庄**：

```
    dcp_size = 4 时（interleave=1）：

    位置:   0    1    2    3    4    5    6    7    8   ...
    归属: rank0 rank1 rank2 rank3 rank0 rank1 rank2 rank3 rank0 ...
            └─────────一轮─────────┘└─────────一轮─────────┘

    ⟹ ★★ 新生成的 token 位置是 T, T+1, T+2……
       套同一个公式就自然落到不同 rank 上。
       【天然均衡，永远不需要重新分配、不需要搬数据】。
```

不归自己的 token，槽位号直接写成占位值：

```python
slot_ids = tl.where(is_local, slot_ids, PAD_ID)
```

> ⚠️ 约束：`block_size` 必须 ≥ `cp_kv_cache_interleave_size` 且能被它整除
> （[parallel.py:371](../源码/vLLM/vllm/config/parallel.py#L371)）。

> 📌 **出处**：这个交错方案由月之暗面（Moonshot）的 Chao Hong 提出，
> 论文 [arXiv:2507.07120](http://arxiv.org/abs/2507.07120)。vLLM 文档里明确致谢了。

### 6.4.3 算：用 LSE 把半成品精确拼回来——第二处反直觉

切完之后每张卡只有 1/N 的 KV，各自算出来的注意力结果都是**残缺**的。怎么合并？

```
    ✗ 不能直接相加或求平均——softmax 的分母是全局的，
      各卡分母不同，加起来毫无意义。

    ✅ 靠 LSE。
```

📖 **LSE**（**L**og-**S**um-**E**xp，对数-求和-取指数）——FlashAttention 分块算 softmax 时会顺手吐出的一个标量，记录了这一块内所有注意力分数的「归一化底数」。
★★ 有了它，几块局部结果可以**精确**（不是近似）拼成全局结果——和 Ring Attention、Flash-Decoding 是同一个数学技巧。

Decode 完整走一遍（[mla_attention.py:957-996](../源码/vLLM/vllm/model_executor/layers/attention/mla_attention.py#L957-L996)）：

```
   ① Query all-gather ─────────────── dcp_manager.query_gather(mqa_q)
      每卡本来只有 num_heads/tp 个查询头，
      在 DCP 组内全收集，凑齐【整组的头】
                    ↓
   ② 本地注意力 ──────────────────── impl.forward_mqa(...)
      全部的头  ×  本地那 1/N 的 KV
      → 局部 output + 局部 lse
                    ↓
   ③ LSE 校正 ────────────────────── dcp_manager.combine(...)
      组内 all-gather 所有 lse → 算出全局 lse
      本地 output 乘以 exp(本地lse − 全局lse) 做缩放
                    ↓
   ④ Reduce-scatter ──────────────── 沿【头】维归约并切回
      每卡拿回自己那份头，且已是完整正确的结果

   ⟹ ★ ①+④ 合起来就是默认通信后端的名字：ag_rs = AllGather + ReduceScatter
```

第 ③ 步的缩放因子，就是那个 Triton 内核 `_correct_attn_cp_out_kernel` 干的事：

> ✅ [dcp.py:140-150](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L140-L150)
> ```python
> lse_finally = lse_tmp - lse          # 本地 lse − 全局 lse
> factor = tl.exp(lse_finally)
> output = output * factor
> ```

```
    ⟹ ★★ 注意方向：Decode 是【广播 query、各算各的 KV】。
       为什么不反过来收集 KV？因为 Decode 每步只有 1 个 query token，
       query 是【极小】的，KV 是【极大】的——当然搬小的那个。
```

### 6.4.4 Prefill 阶段反过来：收集 KV

分块预填充（chunked prefill）要对**已有上下文**做注意力，但那些 KV 按 6.4.2 散在各卡上。这时候 query 不再是 1 个 token 而是一大片，成本关系反转：

```
    ⟹ ★ Prefill：all-gather【KV】。和 Decode 正好相反。
```

> ✅ [mla_attention.py:2829-2851](../源码/vLLM/vllm/model_executor/layers/attention/mla_attention.py#L2829-L2851)
> 源码里连 workspace 的内存布局都画了图：
> ```
> # |------- N tokens --------|--------- N*dcp_size tokens ----------|
> # |<- use for local_gather ->|<--------- use for allgather -------->|
> ```

收集完还要 `reorg_kvcache()` 重排——因为交错分片打乱了顺序，得还原成连续序列才能喂给注意力内核。

```
    ⟹ ★★ 这正是 ⑤ 里那句「两个阶段性格不同」的具体体现：
       同一份切开的 KV，Decode 搬 query，Prefill 搬 KV。
       一个旋钮，两条完全相反的数据流。
```

### 6.4.5 两个可以再压一压的优化

> ⚠️ 这两个**都是可选项，默认都不开**。看不懂可以先跳过，不影响理解 DCP 主线。

#### 先补课：三个「集合通信」动作

📖 **集合通信**（collective communication）——多张卡之间搬数据的几个标准动作。
不先说清这三个，下面 ① 讲不通。

```
    假设 4 张卡，每张卡手里有一块数据

    ① AllGather（全收集）
       卡0[A] 卡1[B] 卡2[C] 卡3[D]
       ⟹ 卡0[ABCD] 卡1[ABCD] 卡2[ABCD] 卡3[ABCD]
       ★ 数据变多，「人手一份完整的」

    ② ReduceScatter（归约-散射）
       每张卡都有【完整尺寸】的一份，要把 4 份加起来
       ⟹ 加完之后，每张卡只拿走结果的 1/4
       ★ 数据变少，「加完各拿各的那段」

    ③ All-to-All（全交换）
       每张卡把自己的数据切成 4 份，第 i 份【定向发给】第 i 张卡
       ⟹ 卡0 收到 [卡0的第0份, 卡1的第0份, 卡2的第0份, 卡3的第0份]
       ★ 总量不变，是个「转置」，各拿各需要的
```

#### ① 换通信模式：`--dcp-comm-backend a2a`

回看 6.4.3 的 decode 四步，第 ③④ 步用了**两次**集合通信：

```
    ③ AllGather(lse)      ← 小。目的：每张卡都得知道全局 lse 才能算缩放因子
    ④ ReduceScatter(out)  ← 大。目的：各卡局部结果加起来，再各拿各的头

    ★★ 问题：这两趟是【串行】的。
       必须先等 lse 收齐、算完缩放，才能开始归约 output。
```

**★★ 为什么非得两趟？因为 ReduceScatter 只会做加法，不会做加权。**

权重 `exp(local_lse − global_lse)` 必须在**发出去之前**就乘好，
而 `global_lse` 要等所有卡的 lse 都齐了才算得出 ⟹ 被迫先来一趟 AllGather。

```
    ⟹ ★ 根子在于：计算（加权）被夹在通信中间，受制于通信原语的能力。
       a2a 的解法是把顺序颠倒过来 ——【先搬运，后计算】。
       All-to-All 不做任何算术，纯搬数据，
       于是加权可以推迟到收完之后【在本地】做。
```

**第 0 步：搬运前，每张卡手里是什么**

例子沿用：**DeepSeek-R1，`-tp 8 -dcp 8`，batch=16，128 个注意力头，输出维度 512，bf16**。

做完 query all-gather 之后，每张卡都对**全部 128 个头**算了一遍注意力，
只不过用的是自己那 1/8 份 KV：

```
    rank0:  out[16, 128, 512] + lse[16, 128]   ← 128 个头，基于 KV 分片 0
    rank1:  out[16, 128, 512] + lse[16, 128]   ← 同样 128 个头，基于 KV 分片 1
    ...                                          （八份都是半成品）

    但最终每张卡只需保留 128 ÷ 8 = 16 个头（下游 o_proj 按头切）

    ★★ 我【有】：全部 128 个头  ×  我的 1 份 KV
       我【要】：我的 16 个头    ×  全部 8 份 KV
       ⟹ 行列对调 —— 这正是 All-to-All 的定义
```

**第 1 步：打包 —— 一个精心设计的缓冲区形状**

> ✅ [dcp.py:747-751](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L747-L751)
> ```python
> send_buffer, recv_buffer = _dcp_a2a_send_recv_buffers(
>     (world_size, B, H_per_rank, D + lse_pack_dim), ...)
> ```

代入数字就是 `[8, 16, 16, 514]`：

```
    [    8    ,   16   ,     16      ,        514        ]
      发给谁    batch    我给他的      512 个数 + lse
     (收件人)   (16 条)   16 个头          ↑        ↑
                                        向量   缝在尾巴上的 lse

    ★ 第 0 维是【收件人地址】：send_buffer[j] = 我要发给 rank j 的包裹。
      包裹里装的，正是 rank j 最终要负责的那 16 个头。
```

> ✅ 打包内核里这一行就是全部逻辑（[dcp.py:464](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L464)）：
> ```python
> src_head_idx = rank_idx * H_PER_RANK + local_head_idx
> ```
> 即 `send_buffer[j]` ← 我的 `out[:, j*16 : (j+1)*16, :]`。
> ★ **打包纯粹是一次「按头重新排序」，没有任何算术。**

📖 **那个多出来的 `+2`（`lse_pack_dim`）是什么**

缓冲区是 bf16 的（跟 out 同类型），而 lse 必须保持 fp32——它要进指数函数，
精度掉了结果就错。源码的办法是**把一个 fp32 按位劈成两个 16 位塞进去**：

> ✅ [dcp.py:539-543](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L539-L543)（收端拼回来）
> ```python
> lo = lo_raw.to(tl.uint16, bitcast=True).to(tl.uint32)
> hi = hi_raw.to(tl.uint16, bitcast=True).to(tl.uint32)
> lse_val = (lo | (hi << 16)).to(tl.float32, bitcast=True)
> ```
> 📖 `bitcast` = 不转换数值、只重新解释这 16 个比特。**精度一位不丢。**
> fp32 缓冲区场景下 `lse_pack_dim = 1`，不用劈（[dcp.py:410](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L410)）。

```
    ⟹ ★★ 这个小技巧就是「两趟变一趟」的实现关键：
       lse 不再需要单独一趟通信，
       它搭上了 output 的顺风车，
       跟自己要加权的那份数据装在【同一个包裹】里。
```

**第 2 步：一次 All-to-All，完成转置**

> ✅ [dcp.py:765](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L765)
> ```python
> work = dist.all_to_all_single(recv_buffer.view(-1), send_buffer.view(-1),
>                               group=cp_group.device_group, async_op=True)
> ```

搬完之后，站在 **rank 3** 的角度看自己的 `recv_buffer[8, 16, 16, 514]`：

```
    recv_buffer[0] ← rank0 发来：头 48~63 的半成品（基于 KV 分片 0）+ 各自 lse
    recv_buffer[1] ← rank1 发来：头 48~63 的半成品（基于 KV 分片 1）+ 各自 lse
    ...
    recv_buffer[7] ← rank7 发来：头 48~63 的半成品（基于 KV 分片 7）+ 各自 lse

    ★★ 第 0 维的含义变了：
       发之前是「收件人」，收到后是「寄件人」——这就是转置。

    ⟹ rank3 对于自己负责的头 48~63，八块 KV 分片的答案【全齐了】，
       每份还自带 lse。不需要再跟任何人通信。
```

**第 3 步：本地合并 —— 三遍循环**

> ✅ [dcp.py:504-627 `_dcp_a2a_unpack_combine_kernel`](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L504-L627)，
> 一个 Triton 内核，对每个 (token, 头) 独立跑，沿 `rank_idx` 循环 8 次、走三遍：

```
    第一遍（L528）找最大值（防指数溢出）
            lse_max = max(lse_0 … lse_7)                       L549

    第二遍（L554）算全局 lse
            lse_sum    = Σ exp(lse_i − lse_max)                L576
            global_lse = log(lse_sum) + lse_max                L581

    第三遍（L586）加权求和
            weight_i = exp(lse_i − global_lse)                 L608
            acc     += partial_i × weight_i                    L616

    ⟹ 输出 [16, 16, 512]
       ★ 跟 ReduceScatter 吐出来的形状【一模一样】，下游 o_proj 完全不用改。
       ✅ 驱动函数注释原话：Combined output [B, H/N, D] (head-scattered)
```

**为什么这样加权是精确的，不是近似**

实算一组（假设 4 张卡，lse 分别是 10、12、9、11）：

| | rank0 | rank1 | rank2 | rank3 | 合计 |
|---|---|---|---|---|---|
| lse | 10.0 | 12.0 | 9.0 | 11.0 | |
| weight | 0.08714 | **0.64391** | 0.03206 | 0.23688 | **1.0000000000** |

```
    exp(lse_i) 就是第 i 块 softmax 的【分母】，
    所以 weight_i = exp(lse_i) / Σ exp(lse_j) = 第 i 块分母占总分母的比例。

    ⟹ ★★ softmax 的分子分块可加，分母也分块可加，
       按分母占比加权求和 = 完整 softmax 的【精确】结果。
       这不是近似，是恒等式（浮点误差以内）。
```

★★ 关键差别一句话：**校正的地点变了**

| | 校正在哪做 | 集合通信次数 |
|---|---|---|
| `ag_rs`（默认） | 发之前 ⟹ 必须先把 lse 收齐（多一趟） | 2 |
| `a2a` | **收之后** ⟹ 这张卡已集齐自己那些头的全部 N 份局部答案 | **1** |

**这一趟到底省了什么：把字节数算出来**

⚠️ 以下按上面同一组参数（B=16, H=128, D=512, bf16, dcp=8）实算：

| | 通信量 | 集合通信次数 |
|---|---|---|
| `ag_rs` AllGather(lse) | 7.2 KB | |
| `ag_rs` ReduceScatter(out) | 1.835 MB | |
| **`ag_rs` 合计** | **1.842 MB** | **2 次** |
| **`a2a` All-to-All** | **1.842 MB** | **1 次** |

```
    ★★ 字节数完全打平，一个 KB 都没省！

    两边的 lse 开销恰好抵消：
      ag_rs：lse 广播给所有人（每卡拿到全部 128 个头的 lse）  7.2 KB
      a2a  ：lse 只定向送给这个头的主人（那 +2 个槽）         7.2 KB
```

> ⚠️ **所以「两趟变一趟」省的不是带宽**，是这三样：
> 1. **一次内核启动 + 一次同步点**。61 层 × 每 token 一遍，固定开销累积起来不小。
> 2. **不用物化那个加权后的全尺寸张量**。`ag_rs` 要先写出完整的
>    `[16,128,512]` = 2 MB 中间结果再喂给 ReduceScatter；
>    `a2a` 的 combine 内核直接写 `[16,16,512]` = 0.26 MB。★ 省的是 HBM 读写。
> 3. **A2A 天生点对点**，不像 AllGather 那样人人都收一份用不上的数据。
>
> ⟹ 因此它在**小 batch、通信延迟占主导**的场景收益才明显。

> ⚠️ **两处容易误读的地方**
>
> **① `a2a` 只替换「合并」这半程，不碰 query all-gather。**
> `MLADCPManager` 里 `_init_combine` 和 `_init_query_gather` 是**两条独立的路**
> （[dcp.py:1220 起](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L1220)）。
> `--dcp-comm-backend a2a` 只改前者。decode 开头那趟 query all-gather 照走不误——
> ★ 省掉它是下面 ② 讲的 `qrep` 的活，**两码事**，可叠加也可各用各的。
> ```
>     query all-gather   2.06 MB   ← a2a 不管这个，qrep 才管
>     合并               1.84 MB   ← a2a 管的是这个
>     ────────────────────────────
>     合计               3.91 MB
> ```
>
> **② `a2a` 不是默认值，也不是无脑更优。**
> ✅ [parallel.py:354](../源码/vLLM/vllm/config/parallel.py#L354) 默认 `"ag_rs"`。
> 因为 `ReduceScatter` 跑在 NCCL 里，是 NVIDIA 调优多年的「通信+归约」融合实现；
> `a2a` 把归约挪进了自家 Triton 内核，还要额外开 send/recv 两块 2.1 MB 缓冲区
> （⚠️ [dcp.py:419](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L419) 用的是 `torch.empty`
> 而非共享 workspace，注释说明是为了避开 CUDA Graph 把地址烤死的坑）。
> ★ **赢不赢要实测。**

> ✅ 选项定义 [parallel.py:40](../源码/vLLM/vllm/config/parallel.py#L40)
> `DCPCommBackend = Literal["ag_rs", "a2a"]`，
> 实现 [dcp.py:704 `dcp_a2a_lse_reduce`](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L704)。
> ⚠️ 硬约束两条：`H % dcp_size != 0` 直接抛异常（128 % 8 = 0，本例过关）；
> `a2a` 要求 `dcp > 1`（[parallel.py:541](../源码/vLLM/vllm/config/parallel.py#L541)）。
> ★ 若硬件支持 symmetric memory（对称内存，NVLink 上的直接远端读写），
> 会自动再切到 `DirectDCPA2AWorkspace` 绕开 NCCL，日志里会打
> `Using direct symmetric-memory DCP A2A for MLA.`

```
    ⟹ ★★ 一句话记住两条路的区别：
       ag_rs = 先问清楚权重，乘好了再交给【只会做加法】的搬运工  → 问一趟 + 搬一趟
       a2a   = 数据和权重装一个包裹直接寄给收件人，收到了自己算   → 只搬一趟
```

#### ② 干脆省掉第 ① 步的 query all-gather（qrep）

📖 **qrep** = query replicate（查询复制）。用具体数字走一遍最清楚。
例子：**DeepSeek-R1（128 个注意力头），`-tp 8 -dcp 2`**。

**默认行为（`ColumnParallelLinear`）**：

```
    q_proj 权重按 tp=8 切成 8 份：
       rank0→头0-15   rank1→头16-31   rank2→头32-47  ...

    DCP 组 = {rank0, rank1}
       （两张卡各存一半 KV：偶数位置 token / 奇数位置 token）

    ★ decode 时 rank0 要干什么？
      它手上只有【一半的 KV】，但必须对【组内全部 32 个头】各算一遍，
      算完再和 rank1 的结果做 LSE 合并（6.4.3）。
      ⟹ 可它只有 16 个头的 q！
      ⟹ ★★ 所以必须 all-gather：rank0的16头 + rank1的16头 = 32头
```

**开了 qrep（`DCPGroupColumnParallelLinear`）**：

> ✅ [linear.py:626-631](../源码/vLLM/vllm/model_executor/layers/linear.py#L626-L631)
> ```python
> super().__init__(..., tp_rank=rank // self.group_size,       # 1 // 2 = 0
>                       tp_size=world_size // self.group_size)  # 8 // 2 = 4
> ```

```
    ★ 权重不再按 8 切，改成按 4 切（= tp/dcp），每份 32 个头：
       rank0 (tp_rank = 0//2 = 0) → 头0-31
       rank1 (tp_rank = 1//2 = 0) → 头0-31   ← ★★ 和 rank0【一模一样】
       rank2 (tp_rank = 2//2 = 1) → 头32-63
       rank3 (tp_rank = 3//2 = 1) → 头32-63

    ⟹ ★★ rank0 一出手就持有 32 个头，正好是组内全头。
       all-gather 直接跳过。
```

★ 代价说白了就是：**组内两张卡把同一个矩阵乘法各算了一遍**。
q_proj 的算力和权重显存都变成 `×dcp_size`。

那 Prefill 怎么办？Prefill 不需要组内全头，于是切回正常的 TP 分片：

> ✅ [linear.py:633-641](../源码/vLLM/vllm/model_executor/layers/linear.py#L633-L641)
> ```python
> n = out.shape[-2] // self.group_size      # 32 // 2 = 16
> start = self.rank_in_group * n            # rank0→0, rank1→16
> return out[..., start : start + n, :]     # 切回自己那 16 头
> ```

```
    ⟹ ★ 又一次「拿算力换通信」——q_proj 算了冗余的一遍，但省一趟 all-gather。
       和 6.2 那张成本表是同一个思路：推理阶段【带宽比算力金贵】。
```

> ⚠️ **两个前提**（不满足就不会启用）：
> - 默认**关闭**，需显式开环境变量 `VLLM_DCP_Q_REPLICATE=1`
>   （[envs.py:200](../源码/vLLM/vllm/envs.py#L200)、[envs.py:1562](../源码/vLLM/vllm/envs.py#L1562)）
> - 要求 `dcp > 1` **且** `pcp ≤ 1`
>   （[deepseek_v2.py:1044-1048](../源码/vLLM/vllm/model_executor/models/deepseek_v2.py#L1044-L1048)）

### 6.4.6 限制条件（配错了直接起不来）

| 约束 | 适用 | ✅ 校验位置 |
|---|---|---|
| `tp % dcp == 0` | MLA | [parallel.py:531](../源码/vLLM/vllm/config/parallel.py#L531) |
| PCP>1 时 `dcp ∈ {1, pcp, tp*pcp}` | 通用 | [parallel.py:533](../源码/vLLM/vllm/config/parallel.py#L533) |
| `tp` 必须**严格大于** KV 头总数 | GQA/MQA | [model.py:1435](../源码/vLLM/vllm/config/model.py#L1435) |
| `dcp ≤ tp // kv_heads` | GQA/MQA | [model.py:1444](../源码/vLLM/vllm/config/model.py#L1444) |
| 每 KV 头的 Q 头数能被 `dcp` 整除 | GQA/MQA | [model.py:1455](../源码/vLLM/vllm/config/model.py#L1455) |
| `block_size ≥ interleave_size` 且整除 | 通用 | [parallel.py:371](../源码/vLLM/vllm/config/parallel.py#L371) |

**★★ 第二条那个白名单为什么长这样：`dcp ∈ {1, pcp, tp*pcp}`**

先注意两个分支**宽严不一样**——这个反差就是解题入口：

> ✅ [parallel.py:529-539](../源码/vLLM/vllm/config/parallel.py#L529-L539)
> ```python
> if pcp == 1:
>     # DCP reuses the TP ranks when PCP is disabled.
>     if tp % dcp != 0:  raise ...          # ← 只要整除就行，tp=8 可配 dcp=2/4/8
> elif dcp not in (1, pcp, tp * pcp):       # ← 变成一张【白名单】，只剩三个值
>     raise ValueError("When PCP is enabled, DCP must be disabled, span the "
>                      "PCP axis, or span the full TP x PCP axis. ...")
> ```

**① rank 是按什么顺序摆的**

> ✅ [parallel_state.py:1817](../源码/vLLM/vllm/distributed/parallel_state.py#L1817)
> `# the layout order is: ExternalDP x DP x PP x PCP x TP`

TP 在最里层、变得最快，PCP 在它外面一层，所以 `rank = pcp × TP + tp`。
拿 `TP=4, PCP=2`（8 张卡）排成二维（**行 = PCP，列 = TP**）：

```
              tp0   tp1   tp2   tp3
      pcp0  [  0     1     2     3  ]
      pcp1  [  4     5     6     7  ]
```

**② DCP 组是怎么切的：先转置，再切块**

> ✅ [parallel_state.py:1856-1859](../源码/vLLM/vllm/distributed/parallel_state.py#L1856-L1859)
> ```python
> if dcp_size > 1:
>     # DCP spans PCP first, then TP for full TP x PCP groups.
>     dcp_ranks = dcp_ranks.transpose(-1, -2)      # (PCP,TP) → (TP,PCP)
> group_ranks = dcp_ranks.reshape(-1, dcp_size).unbind(0)
> ```

转置把矩阵转 90°，**PCP 变成变得最快的那一维**，拉平成一条队列：

```
    转置后：      pcp0  pcp1        拉平：  0, 4,  1, 5,  2, 6,  3, 7
            tp0  [  0     4  ]              └──┘  └──┘  └──┘  └──┘
            tp1  [  1     5  ]              每两个恰好是一个 PCP 组
            tp2  [  2     6  ]
            tp3  [  3     7  ]      然后 reshape(-1, dcp) = 每 dcp 个切一刀
```

★ 关键对照：✅ [parallel_state.py:1871-1874](../源码/vLLM/vllm/distributed/parallel_state.py#L1871-L1874)
里 **PCP 组用的是同一个转置**，只是每 `pcp` 个切一刀。
⟹ **两条队列是同一条队列，区别只在刀距。**

**③ 于是白名单可以这么读**

⚠️ 实测 `TP=4, PCP=2`（PCP 组 = `[0,4] [1,5] [2,6] [3,7]`）：

| dcp | DCP 分组 | 一个 DCP 组 = 几个 PCP 组 | |
|---|---|---|---|
| 1 | `[0] [1] [2] … [7]` | **半个** | ✅ |
| 2 = pcp | `[0,4] [1,5] [2,6] [3,7]` | **正好 1 个**（与 PCP 组逐位相同）| ✅ |
| **4** | `[0,4,1,5]  [2,6,3,7]` | **2 个** | ❌ |
| 8 = tp×pcp | `[0,4,1,5,2,6,3,7]` | **全部 4 个** | ✅ |

```
    ⟹ ★★ 规则的白话版：
       DCP 组要么不碰 PCP 组（dcp=1，一卡一组），
       要么【正好等于一个】PCP 组（dcp=pcp），
       要么把所有 PCP 组【一口气全吞下】（dcp=tp×pcp）。
       ★ 不许「挑几个 PCP 组拼一起」。
```

`dcp=4` 被拒**不是因为切不出来**——上表显示它切得齐齐整整、一张卡不多不少。
被拒是因为它拼出来的组**在系统里对应不上任何已有的东西**：
它横跨了 PCP 全部 2 行 × TP 的**一半**（2 列），比一个 PCP 组大、比全世界小，是个「四不像」。

**④ 承重的那个事实：KV 分片只认 DCP 一个维度**

> ✅ [backend.py:945-946](../源码/vLLM/vllm/v1/attention/backend.py#L945-L946)
> ```python
> self.total_cp_world_size = self.dcp_world_size      # ← 不是 dcp × pcp
> self.total_cp_rank = self.dcp_rank
> ```

6.4.2 那个交错分片公式里的 `TOTAL_CP_WORLD_SIZE` / `TOTAL_CP_RANK`，
喂进去的就是它俩（✅ [block_table.py:150-151](../源码/vLLM/vllm/v1/worker/block_table.py#L150-L151)）。
**PCP 完全不参与 KV 分片。** 于是 prefill 和 decode 之间必须对上账：

```
    prefill：PCP 把 token 分给 pcp 张卡各算一段，
             算完在 PCP 组内做一次 KV all-gather，
             再配一个 write_mask 决定「我收到这么多，但只写属于我的那些」
             ✅ pcp_manager.py:579 _convert_to_gathered_slot_mappings

    decode ：谁存哪些 token，由 DCP 的交错分片说了算

    ★★ write_mask 要能算对，DCP 的切法和 PCP 的切法就得能【互相翻译】。
       dcp = pcp     → 同一批卡、同一种切法，mask 是恒等的        ⟹ 最省事
       dcp = tp×pcp  → DCP 组 = 整个 TP×PCP 矩形，是个天然范围    ⟹ 能对齐
       dcp = 4       → 「半个 TP 轴」在 vLLM 里【没有对应的通信组】
                       （TP 组是完整 4 卡，PCP 组是 2 卡，没有等于「tp0+tp1 两列」的）
```

**⑤ 那为什么 `pcp = 1` 时反而允许「半个 TP 轴」**

因为那时候**根本没转置**（PCP 维长度为 1，转了等于没转），
DCP 组就是在 TP 组**内部**连续切块：`tp=4, dcp=2` → `[0,1] [2,3]`。
✅ 源码注释直说了：*"DCP reuses the TP ranks when PCP is disabled."*

```
    ⟹ ★ 一维里切段，怎么切都是段；
       二维里切，就可能切出个歪的矩形。
       这就是两个分支宽严不一的全部原因。
```

**⑥ 实操上要当心的一个坑**

单节点经典配方是 `-tp 8 -dcp 8`（DeepSeek-R1，MLA 的 KV 头数 H=1，8 倍重复全消掉）。

```
    ★★ 一旦加上 -pcp 2，-dcp 8 立刻【非法】！

       tp=8, pcp=2  →  合法 dcp ∈ {1, 2, 16}
                                    ↑        ↑
                              只消 2 倍   要 16 卡（两个节点）
```

想在 16 卡上既开 PCP 又完全消除 KV 重复，只能 `-tp 8 -pcp 2 -dcp 16`，
⚠️ 代价是 DCP 通信跨节点走 InfiniBand/RoCE 而不是 NVLink——
对照 6.4.7 算的那笔账（每层每 step 约 3.91 MB），带宽掉一个数量级，很可能得不偿失。

> ⚠️ **诚实标注**：④⑤ 两段「为什么中间值要禁」是我从代码结构推的，
> **源码里没有任何注释解释原因**，报错信息本身也只是列了张白名单、没给证明。
> 工程上看这些中间值应该是**能做但没做**，跟官方文档对 `dcp ≤ tp/H` 上限的措辞
> 一个调性。另外 ✅ [pcp_manager.py:125-160](../源码/vLLM/vllm/v1/worker/gpu/pcp_manager.py#L125-L160)
> `validate_config` 显示 **PCP 目前限制还很多**：只支持 MLA，不支持 PP、DP、
> 多模态、LoRA、投机解码，且只能用 PIECEWISE CUDA Graph。
> ★ 这块整体还在早期，白名单窄一点很合理。

---

`dcp ≤ tp/H` 这个上界值得单独说一句——它是**有意设的，不是做不到**：

> ✅ 文档原话（意译）：理论上可以把 dcp 开得更大来进一步切 KV、加速解码。
> 但 Decode 阶段 query token 本来就少，多出来的 `dcp − tp/H` 张卡
> 在**非注意力层无事可做**，收益不明。为简单起见就卡在 `tp/H`。

```
    ⟹ ★★ 所以官方给的调参顺序是：
       ① 先把 tp 加到性能满意
       ② 再用 dcp 消掉 KV 重复
       【不要一上来就调 dcp】。
```

### 6.4.7 算一笔账：计算和通信到底是什么关系

前面讲的都是「怎么做」，这一节回答「值不值」。
⚠️ 下面全部是**模型估算**，不是实测数字——用来建立数量级直觉，不能当 benchmark 引。

**参数**：DeepSeek-R1（61 层、128 个 query 头、MLA 压缩维 512 + rope 64 = 576），
`-tp 8`，batch=16，上下文 32K，bf16，H100 SXM（HBM 带宽 3.35 TB/s、NVLink 450 GB/s、
峰值算力 989 TFLOP/s）。口径：**单层、单张卡、一次 decode step**。

| | `dcp=1` | `dcp=8` |
|---|---|---|
| 参与计算的 query 头数 | 16 | **128**（query 被 all-gather 过来了）|
| 本卡持有的 KV token 数 | 32768 | **4096**（只存 1/8）|
| 注意力 FLOP | 18.25 G | **18.25 G ← 一模一样** |
| 本层要读的 KV | 604.0 MB | **75.5 MB** |
| HBM 读取耗时 | 180.3 µs | **22.5 µs** |
| 算术强度（FLOP/Byte）| 30.2 | **241.8** |
| NVLink 通信量 | 0 | 3.91 MB |
| 通信耗时 | 0 | 8.7 µs |
| **★ 合计** | **180.3 µs** | **31.2 µs（5.8×）** |
| KV Cache 占用/卡（61 层）| 34.31 GiB | **4.29 GiB** |

```
    ★★ 这张表里最反直觉的一行是【注意力 FLOP 完全相同】。

       dcp=1：16 个头  × 32768 个 KV
       dcp=8：128 个头 × 4096 个 KV     ← 头数 ×8，KV 数 ÷8，乘积不变

    ⟹ DCP【一个浮点运算都没省】。
       它省的全部是【访存】：每张卡只需要读 1/8 的 KV。
```

**为什么省访存就等于省时间：算术强度**

📖 **算术强度**（arithmetic intensity）= 每从显存读 1 字节能做多少次浮点运算。
📖 **Roofline 拐点** = 峰值算力 ÷ 显存带宽。H100 上是 `989 TFLOP/s ÷ 3.35 TB/s ≈ 295`。
低于这个数就是**访存受限**（memory-bound），GPU 大部分时间在等数据、算力闲着。

```
    dcp=1： 30.2  ←── 远低于 295，严重访存受限，算力几乎全闲
    dcp=8：241.8  ←── 逼近 295，快把 GPU 喂饱了

    ⟹ ★★ Decode 阶段的本质困境：query 只有几个 token，
       却要把整个 KV Cache 从 HBM 里搬一遍。
       DCP 把「搬一遍」变成「搬 1/8」，
       同时让每张卡多算 8 倍的头把算力填上 —— 【拿闲置算力换访存】。
```

**通信在这笔账里占多大**

```
    3.91 MB 拆开看（每层每 step）：
      query all-gather      2.06 MB   ← 大头。qrep 能省掉它（见 6.4.5 ②）
      lse all-gather        0.01 MB
      output reduce-scatter 1.84 MB   ← a2a 能把它和 lse 合成一趟（见 6.4.5 ①）

    8.7 µs 通信  vs  节省的 157.8 µs 访存  ⟹ 通信只吃掉收益的 5%
```

⚠️ 但这个比例**强烈依赖上下文长度**：访存收益随 T 线性增长，通信量却基本不随 T 变
（它只跟 batch 和头数有关）。按同样的模型倒推**盈亏平衡点**：

```
    ⚠️ B=16 时约 1800 token 上下文
       ⟹ 短上下文（几百 token）开 DCP 反而【亏】——通信费白花。
          长上下文（几万 token）才是它的主场。
```

**顺带记住这几个数**

```
    DeepSeek-R1 的 KV Cache 密度（MLA 压缩后）：
      每 token 每层  = (512 + 64) × 2 B = 1152 B
      每 token 全模型 = 1152 × 61      = 68.6 KiB
      一条 32K 请求   = 2.14 GiB       ← 一条！所以显存永远不够用
```

**自己换硬件跑一遍**（把 `HBM_BW / NVL / PEAK` 换成 H200、B200 的即可）

```python
# DeepSeek-R1 / MLA，单层、单 rank、一次 decode step
L, HID       = 61, 7168      # 层数 / hidden
H_TOTAL      = 128           # query 头数
KV_LORA, ROPE = 512, 64      # MLA 压缩维 / rope 维
D_Q          = KV_LORA + ROPE  # 576，query 与 KV 的 latent 维
BYTES        = 2             # bf16
B, T         = 16, 32768     # batch / 上下文长度
TP           = 8
HBM_BW, NVL, PEAK = 3.35e12, 450e9, 989e12   # ← H100 SXM，换卡改这行

def run(dcp):
    heads = H_TOTAL // (TP // dcp)      # 本卡参与计算的 query 头数
    T_loc = T // dcp                    # 本卡持有的 KV token 数
    flops = 2*(D_Q + KV_LORA)*T_loc * heads * B     # q·k + attn·v
    kv_B  = B * T_loc * D_Q * BYTES                 # 本卡本层要读的 KV
    comm  = 0 if dcp == 1 else (
        B*H_TOTAL*D_Q*BYTES*(dcp-1)/dcp             # query all-gather
      + B*H_TOTAL*4*(dcp-1)/dcp                     # lse all-gather
      + B*H_TOTAL*KV_LORA*BYTES*(dcp-1)/dcp)        # output reduce-scatter
    return dict(heads=heads, T_loc=T_loc, ai=flops/kv_B,
                t_hbm=kv_B/HBM_BW, t_net=comm/NVL,
                total=kv_B/HBM_BW + comm/NVL,
                kv_gpu=B*T_loc*D_Q*BYTES*L/2**30)

a, b = run(1), run(8)
print(f"算术强度  {a['ai']:.1f} → {b['ai']:.1f}   (拐点 {PEAK/HBM_BW:.0f})")
print(f"单层耗时  {a['total']*1e6:.1f} µs → {b['total']*1e6:.1f} µs"
      f"  ({a['total']/b['total']:.1f}×)")
print(f"KV/卡     {a['kv_gpu']:.2f} GiB → {b['kv_gpu']:.2f} GiB")
```

```
    ⟹ ★★ 这一节的结论一句话：
       DCP 不省算力，只省访存；而 decode 恰恰是【访存受限】的，
       所以省访存 = 省时间。通信是要付的学费，
       上下文越长学费占比越低。
```

## 6.5 SGLang 的路子：干脆不要全局 DP 维度

vLLM 是「五维张量 reshape」。SGLang 走了一条**完全不同**的路。

```python
# ✅ SGLang parallel_state.py:2408
if world_size != tensor_model_parallel_size * pipeline_model_parallel_size:
    raise RuntimeError(...)
```

```
    ★★ 读懂这一行：SGLang 的全局网格里【只有 TP 和 PP 两个维度】。
       world_size 严格等于 tp × pp。没有 DP 这一维的位置。
```

那 SGLang 怎么做数据并行？答案很反直觉：

```
    ★★★ 它把【同一个 TP 组】，针对模型的不同部分，
        用【不同的方式】重新切分。

    ┌─────────────────────────────────────────────────────┐
    │  注意力部分：  tp_size = attn_dp × attn_cp × attn_tp │
    │  MoE 部分：    tp_size = moe_dp × moe_ep × moe_tp    │
    │                                                     │
    │  ★ 同样的 8 张卡，在注意力层眼里是一种分组，          │
    │    在 MoE 层眼里是另一种分组。                        │
    └─────────────────────────────────────────────────────┘
```

> ✅ **源码可查**（SGLang [parallel_state.py](../源码/SGLang/python/sglang/srt/distributed/parallel_state.py)）：
> `_TP` **L2446**、`_ATTN_CP` **L2526**、`_ATTN_TP` **L2571**、
> `_MOE_DP`/`_MOE_EP` **L2636**、`_MOE_TP` **L2666**、`_PP` **L2689**。
> 其中 MoE 那一侧的除法尤其直白（**L2587**）：
> ```python
> moe_tp_size = tensor_model_parallel_size // moe_ep_size // moe_dp_size
> ```
> 而 **L2554** 有个漂亮的短路：
> ```python
> if attn_tp_size == tensor_model_parallel_size:
>     _ATTN_TP = _TP        # ★ 不切的话直接复用 TP 组，不新建通信组
> ```

**★ 为什么 SGLang 要这么设计？——因为 MoE 模型的注意力和 MoE 层，最优切法根本不同。**

```
    以 DeepSeek-V3 这类模型为例（⚠️ 以下是机理说明，非论文数字）：

    ★ 注意力层：用了 MLA（07 章），KV Cache 已经压得很小。
      如果还按 TP=8 切注意力头 ⟹ 每张卡都要存【同一份】KV 的一部分，
      而且 all-reduce 开销大。
      ⟹ 更好的做法：★ 注意力层用 DP！每张卡处理【不同的请求】，
         各自持有完整的小 KV，一次 all-reduce 都不用。
         这就是 attn_dp，SGLang 叫 【DP Attention】。

    ★ MoE 层：256 个专家，每个 token 只激活 8 个。
      ⟹ 最优做法是 EP：专家分散到各卡，token 通过 all-to-all 路由过去。

    ⟹ ★★ 同一个模型，注意力想要 DP，MoE 想要 EP。
       vLLM 的固定五维网格表达不了这个；
       SGLang 干脆放弃全局网格，让每一部分自己决定怎么切。
```

> ✅ DP Attention 的实现在 [dp_attention.py](../源码/SGLang/python/sglang/srt/layers/dp_attention.py)：
> `compute_dp_attention_world_info` **L326**、`initialize_dp_attention` **L343**。
> 注意力算完要把结果聚回来，SGLang 提供了两条路径（**L489** `_dp_gather_via_all_reduce`
> 和 **L531** `_dp_gather_via_all_gather`），★ 因为哪条快取决于 batch 形状。
> `DpPaddingMode` **L81** 处理各 DP rank 序列长度不一样时的补齐问题。

## 6.6 ★ 两种设计哲学的对比

```
┌──────────────┬─────────────────────┬──────────────────────────┐
│              │  vLLM               │  SGLang                  │
├──────────────┼─────────────────────┼──────────────────────────┤
│  全局网格     │ 5 维固定：           │ ★ 2 维：world = tp × pp   │
│              │ ExtDP×DP×PP×PCP×TP  │                          │
├──────────────┼─────────────────────┼──────────────────────────┤
│  DP 怎么来    │ ★ 网格里的一个维度   │ ★ 从 TP 组内部【再切】    │
│              │ （整块副本）         │ （按模型部位分别切）      │
├──────────────┼─────────────────────┼──────────────────────────┤
│  灵活性      │ 低：所有层用同一套切法│ ★ 高：注意力和 MoE 可以   │
│              │                     │ 用完全不同的切法          │
├──────────────┼─────────────────────┼──────────────────────────┤
│  理解成本     │ ★ 低：一次 reshape   │ 高：要跟踪 6+ 个通信组    │
│              │ 就看懂全部           │ 之间的关系                │
├──────────────┼─────────────────────┼──────────────────────────┤
│  最擅长      │ 稠密模型、通用场景    │ ★ 超大 MoE（DeepSeek 类） │
└──────────────┴─────────────────────┴──────────────────────────┘
```

> ⚠️（我的判断，非官方表述）可以这样记：
> **vLLM 把并行策略当成「部署配置」——先定好网格，模型往里填。**
> **SGLang 把并行策略当成「模型属性」——模型的每一部分自己声明想怎么切。**
> 两条路都在收敛：vLLM 后来加了 DCP/PCP 和 EP 的独立处理，SGLang 也在补 PP。

## 6.7 实践：怎么选

给一个可操作的决策树（⚠️ 经验法则，非论文结论）：

```
    ① 模型（含 KV Cache）单卡放得下？
       → ★ TP=1，DP=卡数。最简单、吞吐最高、没有任何通信。

    ② 单卡放不下，单机 8 卡放得下？
       → ★ TP = 刚好够装下的最小值（2/4/8），DP = 机器数
       → ⚠️ 不要为了「更快」盲目加 TP，Decode 阶段收益递减
       → ⚠️ TP 必须整除 KV 头数

    ③ 单机放不下（>200B 稠密 / 超大 MoE）？
       → 先试量化（09 章）能不能塞回单机
       → 塞不回：机内 TP=8，★ 机间 PP（或 MoE 的 EP）
       → ⟹ 这就是「机内 TP、机间 PP、最外 DP」，
            ★ 和训练的口诀字面一样，但 DP 的「最外」这次是【真的最外】

    ④ tp 已经超过模型的 KV 头数 H 了？（MLA 模型 H=1，tp≥2 就中）
       → ★ 此时 KV Cache 正在被复制 tp/H 份，纯浪费
       → 上 DCP：-dcp <size>，size ≤ tp/H，不用加卡
       → ⚠️ 顺序别搞反：先把 tp 加到性能满意，再加 dcp（见 6.4.6）
       → 单条序列超长装不下，也是靠这个旋钮，但那是顺带的

    ⑤ 首字延迟被超长 prompt 拖垮？
       → 上 PCP（预填充上下文并行），或者直接上 PD 分离（10 章）
```
