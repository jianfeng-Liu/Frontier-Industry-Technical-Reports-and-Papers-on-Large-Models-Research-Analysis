## 6.0 先把结论摆出来

同一批维度名，训练和推理把它们摆成了两种顺序。为了让「调了个个儿」一眼看得见，下面这张表**统一按「离得最近 → 离得最远」的方向**写（两个框架的原生写法方向相反，不统一就没法比）：

| | 最近（组内 rank 编号连续，走 NVLink） | → | → | → | 最远（跨机，走网络） |
|---|---|---|---|---|---|
| **训练**（Megatron-LM） | TP | CP | EP | ★ **DP** | ★ **PP** |
| **推理**（vLLM） | TP | PCP | ★ **PP** | ★ **DP** | ExternalDP |

```
    ★★ 盯住 PP 和 DP 这两格：

       训练：… EP → 【DP】 → 【PP】        DP 比 PP 【近】
       推理：… PCP → 【PP】 → 【DP】 …     PP 比 DP 【近】   ← 对调了

    ⟹ 不是谁写错了。
       是 DP 的通信成本从「最贵之一」变成了【几乎为零】。
```

> ✅ **原文可查**：vLLM [parallel_state.py:1817](../源码/vLLM/vllm/distributed/parallel_state.py#L1817)
> ```python
> # the layout order is: ExternalDP x DP x PP x PCP x TP
> ```
> ⚠️ **注意这行注释的方向和上表是反的**：vLLM 这里写的是 reshape 的维度顺序，**最后一维变化最快 = 最近**，所以 TP 在字符串末尾。Megatron 的 `order="tp-cp-ep-dp-pp"` 则是**从最快到最慢**，TP 在开头。两边都是「TP 最近」，只是书写习惯相反——上表已经统一过来了。

这一章就是要把这个「调个个儿」讲透。

## 6.1 先复习：rank 排布顺序到底在说什么

> 📖 **rank**——每张 GPU 的全局编号，0, 1, 2, ... N−1。
> 📖 **排布顺序**（layout order）——把这 N 个编号 reshape 成一个多维数组，**哪个维度变化最快**。

vLLM 就是字面意义上地 reshape 了一下：

```python
# ✅ parallel_state.py:1826
all_ranks = torch.arange(world_size).reshape(
    -1,                                    # ExternalDP
    data_parallel_size,                    # DP
    pipeline_model_parallel_size,          # PP
    prefill_context_model_parallel_size,   # PCP
    tensor_model_parallel_size,            # TP   ← ★ 最后一维 = 变化最快
)
```

**「变化最快」= 组内 rank 编号连续 = 物理距离最近。** 这就是全部的含义。

📖 **步长**（stride）——同一个组里，相邻两个 rank 的编号差。步长越小，这两张卡越可能插在同一台机器上、走 NVLink 而不是走网络。

| 维度（从内到外） | 步长公式 | 代入 TP=2, PCP=1, PP=2, DP=2 | 物理含义 |
|---|---|---|---|
| **TP** | 1 | **1** | ★ 最近，同机内，走 NVLink |
| PCP | TP | 2 | 同机内 |
| PP | PCP × TP | 2 | 同机内或跨机 |
| **DP** | PP × PCP × TP | **4** | ★ 最远，跨机，走 IB |
| ExternalDP | DP × PP × PCP × TP | 8 | 完全独立的进程组 |

```
    ⟹ ★★ 排在【越后面】（越内层）的维度，通信越【近】越【快】。
       所以排布顺序的设计原则永远是同一条，训练推理都一样：

       ★★★ 通信量最大的维度，放到最内层（离得最近）。
```

拿一个具体例子走一遍：**8 卡，TP=2，PP=2，DP=2**（PCP=1）。reshape 成 `[ExtDP=1][DP=2][PP=2][PCP=1][TP=2]`，把 rank 0~7 按「最后一维变化最快」的顺序填进去，得到的是一棵树（★ 注意 TP 组永远在树的最底层，因为它最内层）：

```
    DP=0 ─┬─ PP=0 ──── TP 组 = [0, 1]      ← rank 编号连续
          └─ PP=1 ──── TP 组 = [2, 3]

    DP=1 ─┬─ PP=0 ──── TP 组 = [4, 5]
          └─ PP=1 ──── TP 组 = [6, 7]
```

把三种组横着摘出来对比：

| 组类型 | 有哪些组 | 步长 | 跨度 |
|---|---|---|---|
| **TP 组** | `[0,1] [2,3] [4,5] [6,7]` | **1** | ★ 最紧，一定同机 |
| PP 组 | `[0,2] [1,3] [4,6] [5,7]` | 2 | 中等 |
| **DP 组** | `[0,4] [1,5] [2,6] [3,7]` | **4** | ★ 最松，可能跨机 |

```
    ★★ 请对比训练：训练里 DP 的步长【小于】PP，DP 比 PP 更近。
       这里反过来了——DP 的步长 4 > PP 的步长 2。
```

> ✅ 各组的构造代码：
> TP [parallel_state.py:1843](../源码/vLLM/vllm/distributed/parallel_state.py#L1843)（直接 `view(-1, tp)`，不需要转置，因为它已经在最后一维）；
> PP [L1891](../源码/vLLM/vllm/distributed/parallel_state.py#L1891)（`all_ranks.transpose(2, 4)`——把第 2 维换到最后）；
> DP [L1908](../源码/vLLM/vllm/distributed/parallel_state.py#L1908)（`all_ranks.transpose(1, 4)`）。
> ★ 代码注释把这套手法说得很清楚：*"to get group_ranks for each dimension, transpose that dimension to the last dimension, then reshape to 2D, then unbind the last dimension"*。

## 6.2 ★★ 为什么反过来：把四个维度的通信量摆在一起

回到那条唯一的原则——**通信量大的放近处**。所以只要比较四个维度在训练 / 推理下各自的通信量，答案就自己浮出来了。

| 维度 | 训练每步通信 | 推理每步通信 | 变了什么 | 该排哪 |
|---|---|---|---|---|
| **TP** | 每层 **4** 次 all-reduce（前向 2 + 反向 2） | 每层 **2** 次 all-reduce | ★ 没有反向，次数直接减半 | 训练最近，推理**仍然最近** |
| **PP** | 每 micro-batch 传一次激活（前向）+ 一次梯度（反向） | 每步传一次激活 | ★ 只剩前向 | 量中等，两边都可以跨机 |
| **DP** | ★★ 每步 all-reduce **整个模型的梯度** | ★★ **0 字节** | ★★★ 从「最贵之一」变成「免费」 | 训练必须近，推理**可以扔到天涯海角** |
| **EP** | 每层 2 次 all-to-all + 反向 2 次 | 每层 **2** 次 all-to-all | ★ 没有反向 | 两边都很贵，越近越好 |

> 🔑 **★★★ 全章最重要的一句话**：
> 训练的 DP 每步要 all-reduce 整个模型的梯度（[训练框架/05 章 §5.3](../../训练框架/分布式训练入门/05-ZeRO与FSDP.md) 算过是 **2Ψ** 字节，Ψ = 参数个数），所以 DP 必须排在 PP 前面（更近）。
> **推理的 DP 只是「N 份完全独立的副本，各服务各的用户」，一个字节都不用传。**
> 既然它不花通信，就理应被踢到最外圈，把宝贵的近距离带宽让给 TP 和 PP。

**那个 2Ψ 有多大？** 拿 70B 模型代一下就知道为什么训练里 DP 非近不可：

| | 训练 DP | 推理 DP |
|---|---|---|
| 每步要 all-reduce 的字节 | 2Ψ = 2 × 70×10⁹ = **140 GB** | **0** |
| 走 NVLink 450 GB/s 要多久 | **311 ms** | 0 |
| 走 IB 50 GB/s 要多久 | **2.8 s** ⚠️ | 0 |

```
    ⟹ ★★ 训练的 DP 一旦跨机就是灾难（2.8 秒！），所以必须往近处排、
       还得靠梯度分桶 + 反向计算重叠硬藏起来。
       推理的 DP 分母是 0，怎么排都不花钱 ⟹ 直接扔最外层。
```

**再补一个二阶原因**（⚠️ 我的推断，代码注释支持但未明说）：

```
    ★ DP 在最外层，还有一个工程上的好处：
      「一个 DP 副本」= 一段连续的 rank = 一个完整的、自洽的推理引擎实例。
      ⟹ 可以整块地启动、整块地挂掉重启、整块地做弹性伸缩
      ⟹ 这正是 ExternalDP 这一维存在的意义：
         ✅ 代码注释说它用于 "verl integration"（强化学习框架），
            "every dp rank can generate independently"
```

### 6.2.1 顺手把四个维度的「切什么 / 省什么 / 代价」列成一张表

这张表是全章的骨架，后面每一节都在给其中一格填细节。⚠️ 通信量一列都是**单向、每卡、每层、每步**口径；B = 这一步 batch 里的 token 数，H = hidden 维度，b = 每元素字节数。

| 维度 | 切的是什么 | 每卡权重 | 每卡 KV Cache | 每层每步通信量（单向） | ★ 主要代价 |
|---|---|---|---|---|---|
| **TP** | 层**内**的权重矩阵（按行 / 列） | **÷ TP** | **÷ TP**（⚠️ 但有上限，见 §6.3 ①） | 2 次 all-reduce ≈ `2 × 2 × B×H×b × (TP−1)/TP` | ★ 每层两个**同步点**，Decode 阶段收益递减 |
| **PP** | 层**间**（模型切成几段） | **÷ PP** | **÷ PP** | 1 次 P2P send ≈ `B×H×b` ← ★ 最省 | ★★ **气泡**：Decode 每步只有 1 token，没有 micro-batch 可填 |
| **DP** | 什么都不切，**整份复制** | **× 1**（不省！） | × 1（不省） | **0** | ★ 显存占用翻 DP 倍；MoE 场景必须同步 generate（见 §6.3 ③） |
| **EP** | MoE 的**专家**（按专家编号） | 专家部分 **÷ EP** | × 1（KV 不受 EP 影响） | 2 次 all-to-all ≈ `2 × B×K×H×b × (1−1/EP)` | ★★ 专家**负载不均**，耗时由最慢的卡决定 |
| **DCP** | **KV Cache** 沿序列位置 | × 1 | **÷ DCP** | all-gather(Q) + reduce-scatter(out)，见 §6.4.7 | ★ 不加卡但要额外通信；短上下文时亏（§6.4.7） |
| **PCP** | Prefill 时的**序列** | × 1 | × 1（⚠️ PCP 不参与 KV 分片，见 §6.4.6 ④） | Prefill 时 KV all-gather | ★ 限制多，目前只支持 MLA |

```
    ⚠️ 这张表里最容易看漏的一格：【DP 的权重是「× 1」，不是「÷ DP」】。

       推理的 DP 是「多开几个一模一样的实例」，每个实例都要完整一份权重。
       ⟹ 它买的是【吞吐】，不是【显存】。
       ⟹ 想省显存只能靠 TP / PP / EP / DCP，DP 一分钱都不省。
```

⚠️ 关于 EP 那一行的公式，有一项**最常被漏掉**：

```
    每卡单向 Dispatch 字节 = B × K × H × b × (1 − 1/EP)
                             ▲   ▲   ▲   ▲       ▲
                        本卡这步  ★复制  隐藏  每元素  减掉本来就
                        的 token  K 份  维度  字节数  落在自己卡上的

    📖 K = Top-K，每个 token 要路由到几个专家（DeepSeek-V3 是 8）

    ⚠️⚠️ 漏掉【× Top-K】，这笔账会小 8 倍，
         然后你会得出「MoE 通信不算什么」的错误结论。
    ⟹ 逐步推演见 [11 章 §11.3.1](11-MoE推理与专家并行.md)。
```

## 6.3 逐个维度：推理里它们各自怎么用

### ① TP（张量并行）——切权重，仍然是主力

> 📖 **TP**（**T**ensor **P**arallelism，张量并行）——把每一层的权重矩阵切开，每张卡存一片，算完用 all-reduce 把结果拼回来。

推理里的 TP 和训练完全同构，还是那套「列切 + 行切」：

```
    一个 MLP（多层感知机，Multi-Layer Perceptron）块：

      第一个线性层：★ 按【列】切（ColumnParallelLinear）→ 不需要通信
      激活函数：                                        → 逐元素，不需要通信
      第二个线性层：★ 按【行】切（RowParallelLinear）   → ⚠️ 需要 1 次 all-reduce

    注意力块同理：QKV 按列切，输出投影按行切          → ⚠️ 1 次 all-reduce

    ⟹ ★ 每层 2 次 all-reduce（注意力 1 次 + MLP 1 次）
```

> ✅ **源码可查**（vLLM [linear.py](../源码/vLLM/vllm/model_executor/layers/linear.py)）：
> `ColumnParallelLinear` **L407**（★ 注意 `gather_output` 默认 **False**——故意不 all-gather，把结果直接喂给下一个行切层，省掉一次通信）；
> `QKVParallelLinear` **L971**（QKV 三个矩阵合并成一个列切层）；
> `RowParallelLinear` **L1510**，唯一那次通信在 **L1660**：
> ```python
> if self.reduce_results and self.tp_size > 1:
>     output = tensor_model_parallel_all_reduce(output_parallel)
> ```

#### ★★ 把 TP 的账逐项算出来：同一个模型，TP=1 到 TP=16

这是本节的核心。空口说「收益递减」没用，**得把拐点算出来**。

**配置**（⚠️ 下面全是**模型估算**，用来建立数量级直觉，不是 benchmark 数字）：

| 项 | 值 |
|---|---|
| 模型 | Llama-3-70B（80 层，hidden H = 8192，**64 个 query 头，8 个 KV 头**，head_dim = 128） |
| 精度 | BF16（2 字节），权重共 **140 GB = 130.4 GiB** |
| 负载 | decode，batch **B = 32** 条并发，每条上下文 **T = 2048** |
| 硬件 | H100 SXM5：HBM 3.35 TB/s / 80 GB（= 74.5 GiB）；机内 NVLink **450 GB/s 单向**；跨机 IB **50 GB/s** |
| 口径 | **一次 decode step、单张卡** |

**第一步：先把「每卡要装什么、要读什么」一行行摆出来。**

| 逐项 | TP=1 | TP=2 | TP=4 | **TP=8** | TP=16（跨 2 机） |
|---|---|---|---|---|---|
| 每卡权重 | 130.4 GiB | 65.2 GiB | 32.6 GiB | **16.3 GiB** | 8.15 GiB |
| 每卡分到几个 **KV 头**（共 8 个） | 8 | 4 | 2 | **1** | ⚠️ **1（复制了 2 份）** |
| 每 token 每层每卡 KV 字节 = `2 × n_kv_heads × head_dim × b` | 4096 B | 2048 B | 1024 B | **512 B** | ⚠️ **512 B，没再降** |
| 每卡 KV Cache 总量（80 层 × 32 × 2048） | 20.0 GiB | 10.0 GiB | 5.0 GiB | **2.5 GiB** | ⚠️ **2.5 GiB，没再降** |
| **每卡显存合计**（权重 + KV） | 150.4 GiB ❌ | 75.2 GiB ❌ | 37.6 GiB ✅ | **18.8 GiB ✅** | 10.7 GiB ✅ |

```
    ⚠️⚠️ 全表最该记住的一格，就是 TP=16 那两个「没再降」。

    ★ TP 切 KV Cache，是沿【KV 头数】这一维切的。
      Llama-3-70B 只有 8 个 KV 头（它用了 GQA）。

      TP ≤ 8  ⟹ 正常切，每卡拿 8/TP 个头 ✅
      TP = 16 ⟹ ★★ 没得切了！框架的做法是【每卡存一份一模一样的】
                 复制倍数 = TP / n_kv_heads = 16 / 8 = 2

    ⟹ ★★★ 从 TP=8 迈到 TP=16：权重确实又省了一半（16.3 → 8.15 GiB），
             但 KV Cache 【一个字节都没省】（2.5 GiB → 2.5 GiB）。
             通信量却涨了，还跨了机。这就是拐点的来源。
```

> ⚠️ **一个常见的误解要纠正**：很多资料写「TP 必须整除 KV 头数，否则起不来」。**这不对**——框架不会报错，它会**默默复制 KV 头**把你的配置跑起来。所以这不是一个「硬约束」，而是一个**沉默的显存陷阱**：你以为加卡省了 KV，其实没省。（真正会报错的是 DCP 的配置校验，见 §6.4.6。）
>
> ⚠️ 也别把这条套到 MLA 模型上——MLA 的 KV 潜向量**没有头这一维**（等效 `n_kv_heads = 1`），所以 `TP ≥ 2` 就已经在复制了。这正是 §6.4 整节要解决的问题。

**第二步：把时间算出来。** 三项相加：读权重 + 读 KV + 通信。

| 逐项 | TP=1 | TP=2 | TP=4 | **TP=8** | TP=16（跨 2 机） |
|---|---|---|---|---|---|
| ① 读权重耗时 = 每卡权重 ÷ 3.35 TB/s | 41.79 ms | 20.90 ms | 10.45 ms | **5.22 ms** | 2.61 ms |
| ② 读 KV 耗时 | 6.41 ms | 3.21 ms | 1.60 ms | **0.80 ms** | ⚠️ **0.80 ms，没再降** |
| ③ 每层每次 all-reduce 的载荷 = `B × H × b` | — | 512 KiB | 512 KiB | 512 KiB | 512 KiB |
| ④ 每步通信总字节 = `160 × 2 × 载荷 × (TP−1)/TP` | 0 | 83.9 MB | 125.8 MB | **146.8 MB** | 157.3 MB |
| ⑤ 通信耗时 = ④ ÷ 带宽 | 0 | 0.19 ms | 0.28 ms | **0.33 ms** | ⚠️ **3.15 ms**（IB，慢 9 倍） |
| ⑥ ⚠️ 160 次集合通信的固定开销（≈10 µs/次机内，≈30 µs 跨机） | 0 | 1.6 ms | 1.6 ms | **1.6 ms** | ⚠️ **4.8 ms** |
| **⑦ 单步耗时 ≈ ①+②+⑤+⑥** | **48.2 ms** | **25.9 ms** | **13.9 ms** | **★ 7.95 ms** | **11.4 ms** ❌ |
| 相对 TP=1 的加速比 | 1.00× | 1.86× | 3.46× | **★ 6.06×** | **4.24× ← 倒退** |
| ★ 并行效率 = 加速比 ÷ TP | 100% | **93%** | **87%** | **76%** | **27%** |
| 这一档比上一档省了多少 | — | −22.3 ms | −12.0 ms | **−6.0 ms** | **＋3.4 ms ❌** |

```
    ⟹ ★★★ 拐点就在这张表的最后一行：

       TP: 1 → 2   省 22.3 ms   ← 值
       TP: 2 → 4   省 12.0 ms   ← 值
       TP: 4 → 8   省  6.0 ms   ← 还值，但每翻倍省的量在减半
       TP: 8 → 16  ★ 【倒退】3.4 ms   ← 不值！

    ★★ 三个原因叠在一起，缺一个都不会翻车：
       ① KV 显存和 KV 访存都【不再减少】（KV 头复制）
       ② 通信跨机，带宽从 450 GB/s 掉到 50 GB/s，慢 9 倍
       ③ 160 次集合通信的固定开销也跟着跨机翻 3 倍

    ⟹ 🔑 经验法则：★ TP 不要超过单机卡数（通常 8），也不要超过 KV 头数。
       想再扩吞吐，加 DP 副本，不要继续加 TP。
```

> ⚠️ **第 ⑥ 行那个固定开销要说清口径，这里最容易算错。** 那 10 µs/次**不是「kernel 启动开销」的简单累加**——kernel 启动本身是**流水化**的（CPU 提前下发，GPU 排队执行），几百个 kernel 的启动开销**不能串行相加**，那样会严重高估（这也是 CUDA Graph 能救场的前提，见 [12 章](12-CUDA-Graph与图编译.md)）。
> ★ 真正不能流水化的是 all-reduce 自带的**同步点**：这一层的 all-reduce 没收齐，下一层的计算就不能开始，GPU 只能干等。**这部分是真的串行、真的要相加。** 所以第 ⑥ 行算的是「同步等待」，不是「启动开销」。⚠️ 10 µs / 30 µs 是量级估计，无实测来源。

> ⚠️ **再补一个必须说清口径的地方：「算力利用率」。** 上表每一档的**算力**都闲着：这一步的矩阵乘 FLOP ≈ `2 × Ψ × B ÷ TP`，TP=8 时是 0.56 TFLOP，跑完只要 **0.57 ms**，而搬数据要 6.02 ms。
> ```
>     TP=8 这一档的两个利用率，方向完全相反：
>       算力利用率 = 0.56 TFLOP ÷ 7.95 ms ÷ 989 TFLOP/s ≈ ★ 7%
>       带宽利用率 = 6.02 ms ÷ 7.95 ms              ≈ ★★ 76%
> ```
> ★★ **算力利用率只有 7%，不是浪费，是 Memory Bound 的定义**（这一步的算术强度 ≈ B = 32，远低于屋脊点 295）。带宽才是被榨干的那一项。想让算力利用率上去，唯一的办法是提高算术强度——加大 batch、量化、投机解码，**加 TP 不但不能提高它，反而会降低**（FLOP 被切了，字节也被切了，比值不变；但多出来的通信时间进了分母）。详见 [01 章 §1.3](01-推理与训练的根本差异.md)。

**推理里 TP 的两个新特点**（对比训练）：

```
    ★ 特点一：TP 在推理里【同时】降显存和降延迟，训练里只降显存。
      TP=8 ⟹ 权重和 KV 都切成 1/8 ⟹ 单卡搬的字节变成 1/8
           ⟹ ★ TPOT（每字延迟）直接变快 6 倍（上表第 ⑦ 行）
      ⟹ 训练不在乎单步延迟，只在乎吞吐，所以没有这个动机。

    ⚠️ 特点二：也正因为它降延迟，很容易【加过头】。
      训练里 TP 加过头，代价是 MFU 掉几个点；
      推理里 TP 加过头（越过 KV 头数、越过单机），代价是【延迟反而变高】。
```

### ② PP（流水线并行）——推理里地位明显下降

> 📖 **PP**（**P**ipeline **P**arallelism，流水线并行）——把模型按**层**切成几段，每张卡放一段，激活值像流水线一样在段之间往下传。

```
    ★ 训练里 PP 很重要：它是唯一能「把超大模型放下」且【通信量极小】的手段
      （每 micro-batch 只传一份激活，对比 TP 每层 2 次 all-reduce）。

    ⚠️ 推理里 PP 的地位明显下降，罪魁祸首只有一个：【气泡】。
```

📖 **气泡**（bubble）——流水线的头尾阶段，有些卡还没拿到数据 / 已经做完了，只能空转。气泡率 = 空转时间 ÷ 总时间。

| | 一次能灌多少个 micro-batch N | 气泡率公式 | PP=4 时 | PP=8 时 |
|---|---|---|---|---|
| **训练** | 一个 global batch 能切出几十上百个 | `(PP−1) / (PP−1+N)` | N=32 → **8.6%** | N=32 → **18%** |
| **推理 · Prefill** | 长 prompt 可以切 chunk，勉强能切几个 | 同上 | N=4 → 43% | N=4 → 64% |
| **推理 · Decode** | ★★ 每步只有 **1 个 token**，**切不出 micro-batch** | `(PP−1) / PP` | ★★ **75%** | ★★ **87.5%** |

```
    ⟹ ★★ PP=4 做 decode，75% 的时间在空转。
       等价于：你买了 4 张卡，只用上了 1 张的算力。

    ⚠️ 唯一的挽救办法：靠【连续批处理】天然的多请求来填流水线——
       不同请求处在不同的流水段上，互相填对方的气泡。
       （这相当于把「并发请求数」当成了 micro-batch 数 N。）

    ⟹ ★★★ 所以推理的 PP 必须配合【大并发】才有意义。
       并发数 < PP 的时候，PP 是纯亏。
```

> ⚠️（我的判断，非官方结论）实践中的选择顺序通常是：**能单机 TP 装下 → 只用 TP；单机装不下 → 先考虑量化（[09 章](09-量化.md)）；还是装不下 → 才上 PP 跨机。**
> PP 主要用在「模型大到单机 8 卡也放不下」的场景（比如 DeepSeek-V3 这种 671B）。

### ③ DP（数据并行）——同一个名字，推理里含义完全不同

> 📖 **DP**（**D**ata **P**arallelism，数据并行）。⚠️ **这是全章最容易被名字骗到的一个维度**：训练和推理的 DP 除了名字，几乎没有共同点。

| | 训练的 DP | 推理的 DP |
|---|---|---|
| 每个副本拿到什么 | 同一个 batch 的**不同切片** | ★ **完全不同的用户请求** |
| 算完要做什么 | ⚠️ **必须 all-reduce 梯度**（2Ψ 字节） | ★★ **什么都不用做** |
| 每步通信量 | 140 GB（70B 模型） | **0** |
| 它买到的是 | 更大的有效 batch → 更快收敛 | ★ **吞吐**，线性扩展 |
| 它省的显存 | ZeRO/FSDP 切了才省（[训练框架/05 章](../../训练框架/分布式训练入门/05-ZeRO与FSDP.md)） | ⚠️ **一分钱都不省**，每副本一份完整权重 |
| 该排在哪 | 近（通信贵） | ★ 最外圈（通信免费） |

```
    ⟹ ★★ 一句话：推理的 DP 就是「多开几个一模一样的服务实例」。
       想把吞吐翻倍？DP 翻倍即可，线性扩展，零通信。
       ⚠️ 但显存也跟着翻倍——DP 是拿显存换吞吐，不是省显存的手段。
```

**但有一个坑**，vLLM 的代码注释专门警告了：

```python
# ✅ parallel_state.py:1819-1823
# DP is the data parallel group that is part of the model,
# all the ranks in the same DP group should generate simultaneously,
# i.e. the `generate` call in the same DP group should be called together,
# otherwise it will cause deadlock.
```

```
    ★★ 「通信量为 0」，为什么还会死锁？

    因为「为 0」只在【稠密模型】上成立。一旦模型里有 MoE 层：
      MoE 的 all-to-all 是【跨 DP 组】的集合通信（见 ④ 和 §6.5）。
      而集合通信的铁律是：所有参与者【必须同时到场】。

    ⟹ 某个 DP rank 因为手上没请求而不发起 generate，
       其他 rank 就在 all-to-all 里永远等它 ⟹ 整个服务卡死。

    ⟹ ★ 这就是为什么 vLLM 要求 DP 组「同步地一起 generate」：
       没请求的 rank 也得发一个【假的空 batch】进去凑数（dummy run）。
```

```
    ⚠️ 所以 §6.2 那句「推理 DP 通信量为 0」要加个限定：
       稠密模型 ⟹ 真的是 0。
       MoE 模型 ⟹ DP 本身不传数据，但它被 EP 的 all-to-all 绑住了节奏，
                  必须同步推进 ⟹ ★ 一个 rank 慢，全组一起慢。
```

### ④ EP（专家并行）——MoE 专用

> 📖 **EP**（**E**xpert **P**arallelism，专家并行）——MoE 模型里，把不同的**专家**放到不同卡上。
> 📖 **MoE**（**M**ixture **o**f **E**xperts，混合专家）——把一个大 FFN 拆成很多个小 FFN（「专家」），每个 token 只激活其中一小部分（Top-K 个）。

**EP 为什么非用不可**：MoE 的参数几乎全在专家里，不切根本放不下。

| | DeepSeek-V3（671B 总参数，37B 激活） |
|---|---|
| 专家部分参数占比 | ★ 约 **95%** |
| 每层 256 个路由专家，每 token 只激活 | **Top-K = 8** 个 |
| 不切（TP 复制专家）每卡要装 | 671B × 1 B（FP8）= **671 GB** ❌ |
| EP=32 每卡装专家 | ≈ **20 GB** ✅ |

EP 的 rank 组构造很有意思，它是把 **DP × PCP × TP 三个维度合并**出来的：

```python
# ✅ parallel_state.py:1923 附近
group_ranks = all_ranks.transpose(1, 2).reshape(
    -1, data_parallel_size * prefill_context_model_parallel_size *
        tensor_model_parallel_size).unbind(0)
```

```
    ⟹ ★ EP 组 = 「同一个 PP 段内的所有卡」

       含义：专家在一层内横着切，但【不跨流水线段】。
       这符合直觉——不同 PP 段本来就是不同的层，
       第 1 段的专家和第 2 段的专家属于不同层，没有交换的必要。
```

**EP 的代价，一定要把 Top-K 算进去**：

| 步 | 在算什么 | 式子（EP=32，t=64 token/卡，H=7168，BF16） | 结果 |
|---|---|---|---|
| ① | 本卡这步的 token 数 t | — | 64 |
| ② | ⚠️ **每个 token 复制成 Top-K 份** | 64 × **8** | **512 份** |
| ③ | 一份多大 | H × b = 7168 × 2 | 14 KiB |
| ④ | 全部发出去 | 512 × 14 KiB | 7 MiB |
| ⑤ | 扣掉本来就落在本卡的 | × (1 − 1/32) | **6.78 MiB** ← Dispatch |
| ⑥ | Combine 原路返回 | × 2 | **13.6 MiB / 层** |
| ⑦ | 58 个 MoE 层（前 3 层是稠密 FFN） | × 58 | **787 MiB / 卡 / step** |

```
    ⚠️⚠️ 第 ② 步（× Top-K）是【最常被漏掉】的一项，漏了这笔账会小 8 倍。

    ★★ 787 MiB 走哪条线，差一个数量级：
       全关在机内（NVLink 450 GB/s 单向）   ⟹ 1.8 ms
       EP=32 要跨 4 台机，3/4 的流量走 IB   ⟹ ★ 13~16 ms

    ⟹ MoE 并行策略第一原则：【尽可能把 all-to-all 关在 NVLink 域里】。
```

> ⚠️ **注意上面两个带宽的口径**：NVLink 用的是 **450 GB/s**（900 GB/s 的一半，因为 900 是双向聚合）；IB 用的是 **50 GB/s**（400 **Gb**/s ÷ 8）。这两处是通信估算里最高发的错误。
> ⟹ 完整推演、负载均衡和 EPLB 见 [11 章 §11.3 / §11.5](11-MoE推理与专家并行.md)。

### ⑤ 推理独有的新维度：PCP 和 DCP

这是训练侧没有的东西，vLLM 比较新的加法。

```
    📖 CP（Context Parallelism，上下文并行）——把【序列】切开，
       不同卡负责序列的不同片段。训练侧也有（Ring Attention 等，
       见 [训练框架/08 章](../../训练框架/分布式训练入门/08-序列并行与上下文并行.md)）。

    ★ vLLM 把它拆成了两个独立的旋钮：

      📖 PCP = Prefill Context Parallel（预填充上下文并行）
              → 处理超长 prompt 时，把 prompt 切段并行做 Prefill
              ★ 它在 rank 布局里占了【独立一维】（PP 和 TP 之间）

      📖 DCP = Decode Context Parallel（解码上下文并行）
              → 把【KV Cache】按序列位置切到多张卡上
              ★ 主要解决的是「TP 越过 KV 头数后，KV 被白白复制」
                （单卡装不下超长序列只是顺带的好处，见 §6.4.1）
```

| | PCP | DCP |
|---|---|---|
| 服务哪个阶段 | Prefill | Decode |
| 切什么 | 这一次 Prefill 的 **query token** | ★ 常驻的 **KV Cache** |
| 想换到什么 | ★ **算力**（多卡一起算长 prompt，降 TTFT） | ★ **显存 + 访存**（每卡只存 / 只读 1/N 的 KV） |
| 占不占全局维度 | ★ 占（reshape 的第 4 维） | ⚠️ **不占**——从已有五维里再切出来 |
| 主要数据流方向 | all-gather **KV** | all-gather **query** |

```
    ⟹ ★★ 为什么要拆成两个旋钮？因为 [03 章 §3.4](03-Prefill与Decode两阶段.md) 那条：
       两个阶段性格相反 —— Prefill 想切序列换【算力】，
                          Decode 想切序列换【显存】。
       目标不一样，最优的切法和数据流方向也就不一样。
```

> ✅ 布局里 PCP 的位置见 L1826 的 reshape；DCP 的组在 TP 组之后构造
> （[parallel_state.py:1851-1866](../源码/vLLM/vllm/distributed/parallel_state.py#L1851-L1866)）。
> ★ DCP **不占全局维度**——它是从已有的那五维里再切出来的，这和 PCP 不同。
>
> ⚠️ **一处要说准**：常说的「DCP 从 TP 组内部再切」只在 **PCP=1** 时成立。PCP>1 时源码会先转置再 reshape，注释写得很明白：
> ```python
> if dcp_size > 1:
>     # DCP spans PCP first, then TP for full TP x PCP groups.
>     dcp_ranks = dcp_ranks.transpose(-1, -2)
> group_ranks = dcp_ranks.reshape(-1, dcp_size).unbind(0)
> ```
> ⟹ DCP 组**先沿 PCP 铺，铺满了才溢出到 TP**。这也是为什么配置校验里 PCP>1 时合法的 dcp 只有 `1 / pcp / tp*pcp` 三个值（✅ [parallel.py:533](../源码/vLLM/vllm/config/parallel.py#L533)，详见 §6.4.6）。

> **DCP 具体怎么实现的？** ⟹ 下一节 §6.4 整节都在讲这件事。

## 6.4 ★★ DCP 深挖：KV 到底怎么切、怎么拼回来

§6.3 ⑤ 里只说了 DCP「把 KV 按序列位置切开」，这一节把它拆到能对着源码逐行读的程度。之所以值得单开一节：DCP 是这一轮长上下文推理里**最实用的一个旋钮**，而它的设计里有两处相当反直觉。

> ✅ vLLM 官方文档：[docs/serving/context_parallel_deployment.md](../源码/vLLM/docs/serving/context_parallel_deployment.md)
> 命令行开关：`-dcp <size>` / `--decode-context-parallel-size`

---

### 6.4.1 真正的动机：不是「放不下」，是「白白重复」

先纠正一个很容易想岔的地方。DCP 的第一动机**不是**「单条 128K 序列的 KV 一张卡装不下」——那只是顺带的好处。真正的痛点，就是 §6.3 ① 那张表最后一列暴露的那个：

```
    ★ TP 切 KV Cache，是沿【KV 头数 H】这一维切的。
      但 H 是模型结构定死的，切不动了怎么办？

      tp_size ≤ H  ⟹ 正常切，每卡拿 H/tp 个头 ✅
      tp_size > H  ⟹ ★★ 没得切了，框架只能【每卡存一份一模一样的】
                    ★ 重复倍数 = tp_size / H
```

⚠️ 这里必须把 KV Cache 的通式摆正，因为**套错公式会让这笔账错好几倍**：

```
    ✅ 通式（唯一正确的一条）：
       每 token 每层 KV 字节 = 2 × n_kv_heads × head_dim × 字节数
                               ▲        ▲            ▲        ▲
                            K 和 V   ★KV 头数    每头维度   精度

    ⚠️⚠️ 最常见的错法：拿 d_model（hidden 维度）去套
       「每 token 每层 = 2 × d_model × 字节数」。
       这条只对【MHA】成立（因为 MHA 的 n_kv_heads × head_dim 恰好 = d_model）。

       代入 Llama-3-70B（d_model=8192，8 个 KV 头 × 128 = 1024）：
         错的算法：2 × 8192 × 2 = 32768 B
         ✅ 正确：  2 × 8 × 128 × 2 = 4096 B
       ⟹ ★ 高估 【8 倍】。MQA 模型（1 个 KV 头）会高估 64 倍。

    ⟹ 逐个变体的字节数见 [07 章 §7.5](07-注意力变体MQA-GQA-MLA.md)。
```

这就是 [07 章](07-注意力变体MQA-GQA-MLA.md)「MLA 让 KV 变小」的副作用：**KV 越小，TP 越容易越过 H 这道坎**。

| 模型 | 注意力类型 | KV 头数 H | 典型部署 | ★ KV 重复倍数 | 白费的显存占比 |
|---|---|---|---|---|---|
| Llama-3-70B | GQA | 8 | `-tp 8` | 1×（刚好不重复） | 0 |
| Llama-3-70B | GQA | 8 | `-tp 16` | **2×** | 50% |
| Qwen3-235B-A22B | GQA | 4 | `-tp 8` | **2×** | 50% |
| DeepSeek-R1 | MLA | **1** | `-tp 8` | **8×** | ★ **87.5%** |
| Kimi-K2 | MLA | **1** | `-tp 16` | **16×** | ★★ **93.75%** |

> ✅ 后三行的例子和倍数都是 vLLM 官方文档里的原话（`context_parallel_deployment.md` 的 Case study 段）。前两行是我按同一条公式代出来的。

`-tp 16` 跑 Kimi-K2，等于 16 张卡的 KV Cache 显存**存了 16 份同样的东西**——**93.75% 的 KV 显存是纯浪费**。加上 `-dcp 16` 就能完全消掉；加 `-dcp 8` 则降到 2×，但通信只发生在**单机内**（NVLink），代价更小。

```
    ⟹ ★★ 记住这句：DCP【不增加 GPU 数量】。
       它不是「再加几张卡来装 KV」，而是把 TP 组里那些
       本来存重复副本的卡，改成【各存一段】。

       -tp 8         →  8 张卡，每张存【同一份】KV 的全部     （8× 重复）
       -tp 8 -dcp 8  →  8 张卡，每张存【1/8 段】KV            （无重复）
                        ★ 卡数一张没加，KV 显存降到 1/8
```

---

### 6.4.2 存：交错分片（interleave）——第一处反直觉

KV 要沿序列长度 `T` 切，怎么切？

```
    ✗ 朴素想法：切成连续的 N 段，rank0 拿前 1/N，rank1 拿下一个 1/N……
      ★★ 死在哪：Decode 阶段序列【是在一直变长的】。
         每生成一个 token，各段的边界就要挪一次，还得跨卡搬数据。
         成本完全无法接受。

    ✅ vLLM 的做法：交错分片（interleave）
      ★ token 归谁，【只取决于它的绝对位置】，和序列当前多长无关。
```

> ✅ 实现在 Triton 内核里：[block_table.py:410-475](../源码/vLLM/vllm/v1/worker/block_table.py#L410-L475)
> ```python
> virtual_block_size    = KV_CACHE_BLOCK_SIZE * TOTAL_CP_WORLD_SIZE
> virtual_block_indices = pos // virtual_block_size
> virtual_block_offsets = pos - virtual_block_indices * virtual_block_size
> # 这个 token 归不归我？
> is_local = (virtual_block_offsets // CP_KV_CACHE_INTERLEAVE_SIZE
>            ) % TOTAL_CP_WORLD_SIZE == TOTAL_CP_RANK
> ```

📖 **Triton**——OpenAI 的 GPU 内核编程语言，写起来像 Python，编译出来接近手写 CUDA（见 [大模型算子开发/07 章](../../大模型算子开发/07-Triton编程.md)）。
📖 **slot mapping**——「第 i 个 token 的 KV 该写进显存池的哪个槽位」这张映射表。

`cp_kv_cache_interleave_size` 默认 **1**（✅ [parallel.py:362](../源码/vLLM/vllm/config/parallel.py#L362)），也就是**逐 token 轮流坐庄**：

```
    dcp_size = 4 时（interleave = 1）：

    位置:    0     1     2     3     4     5     6     7     8   ...
    归属:  rank0 rank1 rank2 rank3 rank0 rank1 rank2 rank3 rank0 ...
           |<------- 1 -------->|<------- 2 -------->|
           ↑ 每 dcp_size(=4) 个 token 循环一轮，位置 0~3 是第 1 轮，4~7 是第 2 轮

    ⟹ ★★ 新生成的 token 位置是 T, T+1, T+2……
       套同一个公式（pos % 4）就自然落到不同 rank 上。
       【天然均衡，永远不需要重新分配、不需要搬数据】。
```

⚠️ 换个 `interleave_size` 就不是逐 token 了，这是源码 docstring 明确写的两种模式：

| `interleave_size` | 语义 | 位置 0~7 在 dcp=4 下归谁 |
|---|---|---|
| **1**（默认） | ★ token 级：`token i → rank (i % dcp)` | `0,1,2,3,0,1,2,3` |
| `= block_size`（如 8） | block 级：填满 rank i 的一个 block 才轮到 rank i+1 | `0,0,0,0,0,0,0,0`（这 8 个全归 rank0） |

不归自己的 token，槽位号直接写成占位值：

```python
slot_ids = tl.where(is_local, slot_ids, PAD_ID)
```

> ⚠️ 约束：`block_size` 必须 ≥ `cp_kv_cache_interleave_size` 且**能被它整除**（✅ [parallel.py:371](../源码/vLLM/vllm/config/parallel.py#L371) 附近的 docstring 原文：*"Block_size should be greater than or equal to cp_kv_cache_interleave_size. Block_size should be divisible by cp_kv_cache_interleave_size."*）。
> ⚠️ 另外这个参数**刚改过名**：旧名 `dcp_kv_cache_interleave_size`，源码注释说它「will be deprecated when PCP is fully supported」。老文章和老命令行里可能还是旧名。

> 📌 **出处**：这个交错方案由月之暗面（Moonshot AI）的 Chao Hong 提出，论文 [arXiv:2507.07120](http://arxiv.org/abs/2507.07120)。vLLM 文档里明确致谢了。

### 6.4.3 算：用 LSE 把半成品精确拼回来——第二处反直觉

切完之后每张卡只有 1/N 的 KV，各自算出来的注意力结果都是**残缺**的。怎么合并？

```
    ✗ 不能直接相加或求平均——softmax 的分母是【全局】的，
      各卡算出来的分母都不一样，加起来毫无意义。

    ✅ 靠 LSE。
```

📖 **LSE**（**L**og-**S**um-**E**xp，对数-求和-取指数）——FlashAttention 分块算 softmax 时会顺手吐出的一个标量，记录了这一块内所有注意力分数的「归一化底数」，即 `log Σ exp(score)`。
★★ 有了它，几块局部结果可以**精确**（不是近似）拼成全局结果——和 Ring Attention、Flash-Decoding 是同一个数学技巧（见 [大模型算子开发/04 章](../../大模型算子开发/04-FlashAttention全系.md)）。

Decode 完整走一遍（✅ [mla_attention.py:957-996](../源码/vLLM/vllm/model_executor/layers/attention/mla_attention.py#L957-L996)）：

```
   ① Query all-gather ─────────────── dcp_manager.query_gather(mqa_q)
      每卡本来只有 num_heads/tp 个查询头，
      在 DCP 组内全收集，凑齐【整组的头】
                    ↓
   ② 本地注意力 ──────────────────── impl.forward_mqa(...)
      全部的头  ×  本地那 1/N 的 KV
      → 局部 output + 局部 lse
                    ↓
   ③ LSE 校正 ────────────────────── dcp_manager.combine(...)
      组内 all-gather 所有 lse → 算出全局 lse
      本地 output 乘以 exp(本地 lse − 全局 lse) 做缩放
                    ↓
   ④ Reduce-scatter ──────────────── 沿【头】维归约并切回
      每卡拿回自己那份头，且已是完整正确的结果

   ⟹ ★ ①+④ 合起来就是默认通信后端的名字：ag_rs = AllGather + ReduceScatter
```

第 ③ 步的缩放因子，就是那个 Triton 内核 `_correct_attn_cp_out_kernel` 干的事：

> ✅ [dcp.py:140-150](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L140-L150)
> ```python
> lse_finally = lse_tmp - lse          # 本地 lse − 全局 lse
> factor = tl.exp(lse_finally)
> output = output * factor
> ```

```
    ⟹ ★★ 注意数据流的方向：Decode 是【广播 query、各算各的 KV】。

       为什么不反过来收集 KV？因为 Decode 每步只有 1 个 query token，
       query 是【极小】的（几 MB），KV 是【极大】的（几 GB）
       —— 当然搬小的那个。
```

### 6.4.4 Prefill 阶段反过来：收集 KV

分块预填充（chunked prefill）要对**已有上下文**做注意力，但那些 KV 按 §6.4.2 散在各卡上。这时候 query 不再是 1 个 token 而是一大片，成本关系反转：

| | query 有多大 | KV 有多大 | ⟹ 搬哪个 |
|---|---|---|---|
| **Decode** | 1 token × 头数 → 几 MB | 整段历史 → 几 GB | ★ 搬 **query**（all-gather Q） |
| **Prefill** | 一个 chunk（几千 token） | 已有上下文的 1/N | ★ 搬 **KV**（all-gather KV） |

```
    ⟹ ★ Prefill：all-gather【KV】。和 Decode 正好相反。
```

> ✅ [mla_attention.py:2829-2851](../源码/vLLM/vllm/model_executor/layers/attention/mla_attention.py#L2829-L2851)
> 源码里连 workspace 的内存布局都画了图：
> ```
> # |------- N tokens --------|--------- N*dcp_size tokens ----------|
> # |<- use for local_gather ->|<--------- use for allgather -------->|
> ```

收集完还要 `reorg_kvcache()` 重排——因为交错分片打乱了顺序，得还原成连续序列才能喂给注意力内核。

```
    ⟹ ★★ 这正是 §6.3 ⑤ 里那句「两个阶段性格不同」的具体体现：
       同一份切开的 KV，Decode 搬 query，Prefill 搬 KV。
       一个旋钮，两条完全相反的数据流。
```

### 6.4.5 两个可以再压一压的优化

> ⚠️ 这两个**都是可选项，默认都不开**。看不懂可以先跳过，不影响理解 DCP 主线。

#### 先补课：三个「集合通信」动作

📖 **集合通信**（collective communication）——多张卡之间搬数据的几个标准动作。不先说清这三个，下面 ① 讲不通。（更完整的介绍见 [训练框架/03 章](../../训练框架/分布式训练入门/03-通信原语.md)。）

```
    假设 4 张卡，每张卡手里有一块数据

    ① AllGather（全收集）
       卡0[A] 卡1[B] 卡2[C] 卡3[D]
       ⟹ 卡0[ABCD] 卡1[ABCD] 卡2[ABCD] 卡3[ABCD]
       ★ 数据变多，「人手一份完整的」

    ② ReduceScatter（归约-散射）
       每张卡都有【完整尺寸】的一份，要把 4 份加起来
       ⟹ 加完之后，每张卡只拿走结果的 1/4
       ★ 数据变少，「加完各拿各的那段」
       ⚠️ 关键限制：它只会做【加法】，不会做加权。

    ③ All-to-All（全交换）
       每张卡把自己的数据切成 4 份，第 i 份【定向发给】第 i 张卡
       ⟹ 卡0 收到 [卡0的第0份, 卡1的第0份, 卡2的第0份, 卡3的第0份]
       ★ 总量不变，是个「转置」，各拿各需要的
       ★ 它【不做任何算术】，纯搬运。
```

#### ① 换通信模式：`--dcp-comm-backend a2a`

回看 §6.4.3 的 decode 四步，第 ③④ 步用了**两次**集合通信：

```
    ③ AllGather(lse)      ← 小。目的：每张卡都得知道全局 lse 才能算缩放因子
    ④ ReduceScatter(out)  ← 大。目的：各卡局部结果加起来，再各拿各的头

    ★★ 问题：这两趟是【串行】的。
       必须先等 lse 收齐、算完缩放，才能开始归约 output。
```

**★★ 为什么非得两趟？因为 ReduceScatter 只会做加法，不会做加权。**

权重 `exp(local_lse − global_lse)` 必须在**发出去之前**就乘好，而 `global_lse` 要等所有卡的 lse 都齐了才算得出 ⟹ 被迫先来一趟 AllGather。

```
    ⟹ ★ 根子在于：计算（加权）被夹在通信中间，受制于通信原语的能力。

       a2a 的解法是把顺序颠倒过来 ——【先搬运，后计算】。
       All-to-All 不做任何算术，纯搬数据，
       于是加权可以推迟到收完之后【在本地】做。
```

> ✅ 官方 docstring 把收益说得很具体（[parallel.py:354-360](../源码/vLLM/vllm/config/parallel.py#L354)）：
> ```python
> dcp_comm_backend: DCPCommBackend = "ag_rs"
> """Communication backend for Decode Context Parallel (DCP).
> - "ag_rs": AllGather + ReduceScatter (default, existing behavior)
> - "a2a": All-to-All exchange of partial outputs + LSE, then
>   combine with Triton kernel. Reduces NCCL calls from 3 to 2
>   per layer for MLA models.
> """
> ```
> ★ **注意是「3 → 2」，不是「2 → 1」**：整层其实有 3 次 NCCL 调用——query all-gather、lse all-gather、output reduce-scatter。`a2a` 把**后两次合成一次**，query all-gather 它不碰（见下面 ⚠️ ①）。

**第 0 步：搬运前，每张卡手里是什么**

例子沿用：**DeepSeek-R1，`-tp 8 -dcp 8`，batch=16，128 个注意力头，输出维度 512，bf16**。

做完 query all-gather 之后，每张卡都对**全部 128 个头**算了一遍注意力，只不过用的是自己那 1/8 份 KV：

```
    rank0:  out[16, 128, 512] + lse[16, 128]   ← 128 个头，基于 KV 分片 0
    rank1:  out[16, 128, 512] + lse[16, 128]   ← 同样 128 个头，基于 KV 分片 1
    ...                                          （八份都是半成品）

    但最终每张卡只需保留 128 ÷ 8 = 16 个头（下游 o_proj 按头切）

    ★★ 我【有】：全部 128 个头  ×  我的 1 份 KV
       我【要】：我的 16 个头    ×  全部 8 份 KV
       ⟹ 行列对调 —— 这正是 All-to-All 的定义
```

**第 1 步：打包 —— 一个精心设计的缓冲区形状**

> ✅ [dcp.py:747-751](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L747-L751)
> ```python
> send_buffer, recv_buffer = _dcp_a2a_send_recv_buffers(
>     (world_size, B, H_per_rank, D + lse_pack_dim), ...)
> ```

代入数字就是 `[8, 16, 16, 514]`：

```
    [    8    ,   16   ,     16      ,        514        ]
      发给谁    batch    我给他的      512 个数 + lse
     (收件人)   (16 条)   16 个头          ↑        ↑
                                        向量   缝在尾巴上的 lse

    ★ 第 0 维是【收件人地址】：send_buffer[j] = 我要发给 rank j 的包裹。
      包裹里装的，正是 rank j 最终要负责的那 16 个头。
```

> ✅ 打包内核里这一行就是全部逻辑（[dcp.py:464](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L464)）：
> ```python
> src_head_idx = rank_idx * H_PER_RANK + local_head_idx
> ```
> 即 `send_buffer[j]` ← 我的 `out[:, j*16 : (j+1)*16, :]`。
> ★ **打包纯粹是一次「按头重新排序」，没有任何算术。**

📖 **那个多出来的 `+2`（`lse_pack_dim`）是什么**

缓冲区是 bf16 的（跟 out 同类型），而 lse 必须保持 fp32——它要进指数函数，精度掉了结果就错。源码的办法是**把一个 fp32 按位劈成两个 16 位塞进去**：

> ✅ [dcp.py:539-543](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L539-L543)（收端拼回来）
> ```python
> lo = lo_raw.to(tl.uint16, bitcast=True).to(tl.uint32)
> hi = hi_raw.to(tl.uint16, bitcast=True).to(tl.uint32)
> lse_val = (lo | (hi << 16)).to(tl.float32, bitcast=True)
> ```
> 📖 `bitcast` = 不转换数值、只重新解释这 16 个比特。**精度一位不丢。**
> fp32 缓冲区场景下 `lse_pack_dim = 1`，不用劈（[dcp.py:410](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L410)）。

```
    ⟹ ★★ 这个小技巧就是「两趟变一趟」的实现关键：
       lse 不再需要单独一趟通信，
       它搭上了 output 的顺风车，
       跟自己要加权的那份数据装在【同一个包裹】里。
```

**第 2 步：一次 All-to-All，完成转置**

> ✅ [dcp.py:765](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L765)
> ```python
> work = dist.all_to_all_single(recv_buffer.view(-1), send_buffer.view(-1),
>                               group=cp_group.device_group, async_op=True)
> ```

搬完之后，站在 **rank 3** 的角度看自己的 `recv_buffer[8, 16, 16, 514]`：

```
    recv_buffer[0] ← rank0 发来：头 48~63 的半成品（基于 KV 分片 0）+ 各自 lse
    recv_buffer[1] ← rank1 发来：头 48~63 的半成品（基于 KV 分片 1）+ 各自 lse
    ...
    recv_buffer[7] ← rank7 发来：头 48~63 的半成品（基于 KV 分片 7）+ 各自 lse

    ★★ 第 0 维的含义变了：
       发之前是「收件人」，收到后是「寄件人」——这就是转置。

    ⟹ rank3 对于自己负责的头 48~63，八块 KV 分片的答案【全齐了】，
       每份还自带 lse。不需要再跟任何人通信。
```

**第 3 步：本地合并 —— 三遍循环**

> ✅ [dcp.py:504-627 `_dcp_a2a_unpack_combine_kernel`](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L504-L627)，一个 Triton 内核，对每个 (token, 头) 独立跑，沿 `rank_idx` 循环 8 次、走三遍：

```
    第一遍（L528）找最大值（防指数溢出）
            lse_max = max(lse_0 … lse_7)                       L549

    第二遍（L554）算全局 lse
            lse_sum    = Σ exp(lse_i − lse_max)                L576
            global_lse = log(lse_sum) + lse_max                L581

    第三遍（L586）加权求和
            weight_i = exp(lse_i − global_lse)                 L608
            acc     += partial_i × weight_i                    L616

    ⟹ 输出 [16, 16, 512]
       ★ 跟 ReduceScatter 吐出来的形状【一模一样】，下游 o_proj 完全不用改。
       ✅ 驱动函数注释原话：Combined output [B, H/N, D] (head-scattered)
```

**为什么这样加权是精确的，不是近似**

实算一组（假设 4 张卡，lse 分别是 10、12、9、11）：

| | rank0 | rank1 | rank2 | rank3 | 合计 |
|---|---|---|---|---|---|
| lse | 10.0 | 12.0 | 9.0 | 11.0 | |
| exp(lse − lse_max)，lse_max = 12 | 0.13534 | 1.00000 | 0.04979 | 0.36788 | 1.55301 |
| weight = exp(lse_i) / Σ exp(lse_j) | 0.08714 | **0.64391** | 0.03206 | 0.23688 | **1.0000000000** |

```
    exp(lse_i) 就是第 i 块 softmax 的【分母】，
    所以 weight_i = exp(lse_i) / Σ exp(lse_j) = 第 i 块分母占总分母的比例。

    ⟹ ★★ softmax 的分子分块可加，分母也分块可加，
       按分母占比加权求和 = 完整 softmax 的【精确】结果。
       ★ 权重和恰好等于 1（上表最后一格），这不是近似，
         是恒等式（浮点误差以内）。
```

★★ 关键差别一句话：**校正的地点变了**

| | 校正在哪做 | 这一层的 NCCL 调用次数 |
|---|---|---|
| `ag_rs`（默认） | 发之前 ⟹ 必须先把 lse 收齐（多一趟） | **3**（Q-AG + lse-AG + out-RS） |
| `a2a` | **收之后** ⟹ 这张卡已集齐自己那些头的全部 N 份局部答案 | **2**（Q-AG + a2a） |

**这一趟到底省了什么：把字节数算出来**

⚠️ 以下按上面同一组参数（B=16, H=128, D=512, bf16, dcp=8）实算，口径是**单层、单卡、一次 decode step 的单向发送量**：

| | 通信量 | 怎么算的 |
|---|---|---|
| `ag_rs` AllGather(lse) | **7.2 KB** | 16 × 128 × 4 B × 7/8 |
| `ag_rs` ReduceScatter(out) | **1.835 MB** | 16 × 128 × 512 × 2 B × 7/8 |
| **`ag_rs` 合计** | **1.842 MB**，**2 次调用** | |
| **`a2a` All-to-All** | **1.842 MB**，**1 次调用** | 8 × 16 × 16 × 514 × 2 B × 7/8 |

```
    ★★ 字节数完全打平，一个 KB 都没省！

    两边的 lse 开销恰好抵消：
      ag_rs：lse 广播给所有人（每卡拿到全部 128 个头的 lse）  7.2 KB
      a2a  ：lse 只定向送给这个头的主人（那 +2 个槽）         7.2 KB
```

> ⚠️ **所以「两趟变一趟」省的不是带宽**，是这三样：
> 1. **一个同步点。** ⚠️ 注意口径：这里省的**不是** kernel 启动开销——kernel 启动是流水化的，不能串行累加（见 §6.3 ① 那条注解）。省的是 `ag_rs` 里「必须等 lse 收齐才能继续」这个**真串行的等待**。61 层 × 每 token 一遍，累积起来不小。
> 2. **不用物化那个加权后的全尺寸张量。** `ag_rs` 要先写出完整的 `[16,128,512]` = 2 MB 中间结果再喂给 ReduceScatter；`a2a` 的 combine 内核直接写 `[16,16,512]` = 0.26 MB。★ 省的是 HBM 读写。
> 3. **A2A 天生点对点**，不像 AllGather 那样人人都收一份用不上的数据。
>
> ⟹ 因此它在**小 batch、通信延迟占主导**的场景收益才明显。

> ⚠️ **两处容易误读的地方**
>
> **① `a2a` 只替换「合并」这半程，不碰 query all-gather。**
> `MLADCPManager` 里 `_init_combine` 和 `_init_query_gather` 是**两条独立的路**（[dcp.py:1220 起](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L1220)）。`--dcp-comm-backend a2a` 只改前者。decode 开头那趟 query all-gather 照走不误——★ 省掉它是下面 ② 讲的 `qrep` 的活，**两码事**，可叠加也可各用各的。
> ```
>     query all-gather   2.06 MB   ← a2a 不管这个，qrep 才管
>     合并               1.84 MB   ← a2a 管的是这个
>     ────────────────────────────
>     合计               3.91 MB   ← 这就是 §6.4.7 那笔账里的通信项
> ```
>
> **② `a2a` 不是默认值，也不是无脑更优。**
> ✅ [parallel.py:354](../源码/vLLM/vllm/config/parallel.py#L354) 默认 `"ag_rs"`。因为 `ReduceScatter` 跑在 NCCL 里，是 NVIDIA 调优多年的「通信 + 归约」融合实现；`a2a` 把归约挪进了自家 Triton 内核，还要额外开 send/recv 两块 2.1 MB 缓冲区（⚠️ [dcp.py:419](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L419) 用的是 `torch.empty` 而非共享 workspace，注释说明是为了避开 CUDA Graph 把地址烤死的坑，见 [12 章](12-CUDA-Graph与图编译.md)）。
> ★ **赢不赢要实测。**

> ✅ 选项定义 [parallel.py:40](../源码/vLLM/vllm/config/parallel.py#L40) `DCPCommBackend = Literal["ag_rs", "a2a"]`，实现 [dcp.py:704 `dcp_a2a_lse_reduce`](../源码/vLLM/vllm/v1/attention/ops/dcp.py#L704)。
> ⚠️ 硬约束两条：`H % dcp_size != 0` 直接抛异常（128 % 8 = 0，本例过关）；`a2a` 要求 `dcp > 1`（✅ [parallel.py:541](../源码/vLLM/vllm/config/parallel.py#L541)，报错原文 *"dcp_comm_backend='a2a' requires decode_context_parallel_size > 1."*）。
> ★ 若硬件支持 symmetric memory（对称内存，NVLink 上的直接远端读写），会自动再切到 `DirectDCPA2AWorkspace` 绕开 NCCL，日志里会打 `Using direct symmetric-memory DCP A2A for MLA.`

```
    ⟹ ★★ 一句话记住两条路的区别：
       ag_rs = 先问清楚权重，乘好了再交给【只会做加法】的搬运工  → 问一趟 + 搬一趟
       a2a   = 数据和权重装一个包裹直接寄给收件人，收到了自己算   → 只搬一趟
```

#### ② 干脆省掉第 ① 步的 query all-gather（qrep）

📖 **qrep** = query replicate（查询复制）。用具体数字走一遍最清楚。
例子：**DeepSeek-R1（128 个注意力头），`-tp 8 -dcp 2`**。

**默认行为（`ColumnParallelLinear`）**：

```
    q_proj 权重按 tp=8 切成 8 份：
       rank0→头0-15   rank1→头16-31   rank2→头32-47  ...

    DCP 组 = {rank0, rank1}
       （两张卡各存一半 KV：偶数位置 token / 奇数位置 token）

    ★ decode 时 rank0 要干什么？
      它手上只有【一半的 KV】，但必须对【组内全部 32 个头】各算一遍，
      算完再和 rank1 的结果做 LSE 合并（§6.4.3）。
      ⟹ 可它只有 16 个头的 q！
      ⟹ ★★ 所以必须 all-gather：rank0 的 16 头 + rank1 的 16 头 = 32 头
```

**开了 qrep（`DCPGroupColumnParallelLinear`）**：

> ✅ [linear.py:626-631](../源码/vLLM/vllm/model_executor/layers/linear.py#L626-L631)
> ```python
> super().__init__(..., tp_rank=rank // self.group_size,       # 1 // 2 = 0
>                       tp_size=world_size // self.group_size)  # 8 // 2 = 4
> ```

```
    ★ 权重不再按 8 切，改成按 4 切（= tp/dcp），每份 32 个头：
       rank0 (tp_rank = 0//2 = 0) → 头0-31
       rank1 (tp_rank = 1//2 = 0) → 头0-31   ← ★★ 和 rank0【一模一样】
       rank2 (tp_rank = 2//2 = 1) → 头32-63
       rank3 (tp_rank = 3//2 = 1) → 头32-63

    ⟹ ★★ rank0 一出手就持有 32 个头，正好是组内全头。
       all-gather 直接跳过。
```

把两条路的账并排列出来（DeepSeek-R1，`-tp 8 -dcp 2`，B=16，bf16，单层单卡）：

| 逐项 | 默认（ColumnParallel） | ★ 开 qrep |
|---|---|---|
| q_proj 权重按几切 | 8 | **4** |
| 每卡 q_proj 权重 | 1× | ⚠️ **2×**（`× dcp`） |
| 每卡 q_proj 的 GEMM 算力 | 1× | ⚠️ **2×**（同一个矩阵乘算了两遍） |
| decode 时手上有几个头 | 16 | **32 = 组内全头** |
| 还要不要 query all-gather | ⚠️ 要 | ★ **不要** |
| 省掉的通信 = `B × H × D_q × b × (1−1/dcp)` | — | `16×128×576×2×1/2` = **1.18 MB / 层** |
| Prefill 怎么办 | 正常 | ★ 切回正常 TP 分片（见下） |

那 Prefill 怎么办？Prefill 不需要组内全头，于是**在算完之后切回**正常的 TP 分片：

> ✅ [linear.py:633-641](../源码/vLLM/vllm/model_executor/layers/linear.py#L633-L641)
> ```python
> n = out.shape[-2] // self.group_size      # 32 // 2 = 16
> start = self.rank_in_group * n            # rank0→0, rank1→16
> return out[..., start : start + n, :]     # 切回自己那 16 头
> ```

```
    ⟹ ★ 又一次「拿算力换通信」——q_proj 多算了冗余的一遍，但省一趟 all-gather。

    ★★ 为什么这笔交易在推理里划得来？回看 §6.3 ① 那条：
       decode 阶段算力利用率只有 7%，算力【大量闲置】；
       而带宽和同步点是真瓶颈。
       ⟹ 用闲着的算力去换稀缺的带宽，当然划算。
       ⟹ 这和 §6.2 那张成本表是同一个思路：【推理阶段带宽比算力金贵】。
```

> ⚠️ **两个前提**（不满足就不会启用）：
> - 默认**关闭**，需显式开环境变量 `VLLM_DCP_Q_REPLICATE=1`（✅ [envs.py:200](../源码/vLLM/vllm/envs.py#L200)、[envs.py:1562](../源码/vLLM/vllm/envs.py#L1562)）
> - 要求 `dcp > 1` **且** `pcp ≤ 1`（✅ [deepseek_v2.py:1044-1048](../源码/vLLM/vllm/model_executor/models/deepseek_v2.py#L1044-L1048)）

```
    ★★ 倒数三条（GQA/MQA 专用）连起来读，正好复述了 §6.4.1 的动机：

       「tp 必须【严格大于】KV 头数」
          ⟹ 因为 tp ≤ H 的时候 KV 本来就切得开、根本没有重复，
             DCP 无事可做，开它纯属添乱 ⟹ 直接拒绝。

       「dcp ≤ tp // H」
          ⟹ 重复倍数就是 tp/H，DCP 最多也只能消掉这么多。
             再大就是无米之炊。
```

**★★ 那个白名单为什么长这样：`dcp ∈ {1, pcp, tp*pcp}`**

先注意两个分支**宽严不一样**——这个反差就是解题入口：

> ✅ [parallel.py:529-539](../源码/vLLM/vllm/config/parallel.py#L529-L539)
> ```python
> if pcp == 1:
>     # DCP reuses the TP ranks when PCP is disabled.
>     if tp % dcp != 0:  raise ...          # ← 只要整除就行，tp=8 可配 dcp=2/4/8
> elif dcp not in (1, pcp, tp * pcp):       # ← 变成一张【白名单】，只剩三个值
>     raise ValueError(
>         "When PCP is enabled, DCP must be disabled, span the PCP "
>         "axis, or span the full TP x PCP axis. ...")
> ```

**① rank 是按什么顺序摆的**

TP 在最内层、变化最快，PCP 在它外面一层，所以 `rank = pcp_idx × TP + tp_idx`。拿 `TP=4, PCP=2`（8 张卡）排成二维（**行 = PCP，列 = TP**）：

```
              tp0   tp1   tp2   tp3
      pcp0  [  0     1     2     3  ]
      pcp1  [  4     5     6     7  ]
```

**② DCP 组是怎么切的：先转置，再切块**

> ✅ [parallel_state.py:1856-1859](../源码/vLLM/vllm/distributed/parallel_state.py#L1856-L1859)
> ```python
> if dcp_size > 1:
>     # DCP spans PCP first, then TP for full TP x PCP groups.
>     dcp_ranks = dcp_ranks.transpose(-1, -2)      # (PCP,TP) → (TP,PCP)
> group_ranks = dcp_ranks.reshape(-1, dcp_size).unbind(0)
> ```

转置把矩阵转 90°，**PCP 变成变化最快的那一维**，拉平成一条队列：

```
    转置后：      pcp0  pcp1        拉平：  0, 4,  1, 5,  2, 6,  3, 7
            tp0  [  0     4  ]              └──┘  └──┘  └──┘  └──┘
            tp1  [  1     5  ]              每两个恰好是一个 PCP 组
            tp2  [  2     6  ]
            tp3  [  3     7  ]      然后 reshape(-1, dcp) = 每 dcp 个切一刀
```

★ 关键对照：✅ [parallel_state.py:1871-1874](../源码/vLLM/vllm/distributed/parallel_state.py#L1871-L1874) 里 **PCP 组用的是同一个转置**，只是每 `pcp` 个切一刀。⟹ **两条队列是同一条队列，区别只在刀距。**

**③ 于是白名单可以这么读**

按上面那条队列 `0,4,1,5,2,6,3,7` 逐个 dcp 值切一遍（`TP=4, PCP=2`，PCP 组 = `[0,4] [1,5] [2,6] [3,7]`）：

| dcp | 刀距 | 切出来的 DCP 分组 | 一个 DCP 组 = 几个 PCP 组 | 判定 |
|---|---|---|---|---|
| 1 | 1 | `[0] [4] [1] [5] …` | **半个** | ✅ |
| **2 = pcp** | 2 | `[0,4] [1,5] [2,6] [3,7]` | **正好 1 个**（与 PCP 组逐位相同） | ✅ |
| **4** | 4 | `[0,4,1,5]  [2,6,3,7]` | **2 个** | ❌ **被拒** |
| **8 = tp×pcp** | 8 | `[0,4,1,5,2,6,3,7]` | **全部 4 个** | ✅ |

```
    ⟹ ★★ 规则的白话版：
       DCP 组要么不碰 PCP 组（dcp=1，一卡一组），
       要么【正好等于一个】PCP 组（dcp=pcp），
       要么把所有 PCP 组【一口气全吞下】（dcp=tp×pcp）。
       ★ 不许「挑几个 PCP 组拼一起」。
```

`dcp=4` 被拒**不是因为切不出来**——上表显示它切得齐齐整整、一张卡不多不少。被拒是因为它拼出来的组**在系统里对应不上任何已有的东西**：它横跨了 PCP 全部 2 行 × TP 的**一半**（2 列），比一个 PCP 组大、比全世界小，是个「四不像」。

**④ 承重的那个事实：KV 分片只认 DCP 一个维度**

> ✅ [backend.py:945-946](../源码/vLLM/vllm/v1/attention/backend.py#L945-L946)
> ```python
> self.total_cp_world_size = self.dcp_world_size      # ← 不是 dcp × pcp
> self.total_cp_rank = self.dcp_rank
> ```

§6.4.2 那个交错分片公式里的 `TOTAL_CP_WORLD_SIZE` / `TOTAL_CP_RANK`，喂进去的就是它俩（✅ [block_table.py:150-151](../源码/vLLM/vllm/v1/worker/block_table.py#L150-L151)）。**PCP 完全不参与 KV 分片。** 于是 prefill 和 decode 之间必须对上账：

```
    prefill：PCP 把 token 分给 pcp 张卡各算一段，
             算完在 PCP 组内做一次 KV all-gather，
             再配一个 write_mask 决定「我收到这么多，但只写属于我的那些」
             ✅ pcp_manager.py:579 _convert_to_gathered_slot_mappings

    decode ：谁存哪些 token，由 DCP 的交错分片说了算

    ★★ write_mask 要能算对，DCP 的切法和 PCP 的切法就得能【互相翻译】。
       dcp = pcp     → 同一批卡、同一种切法，mask 是恒等的        ⟹ 最省事
       dcp = tp×pcp  → DCP 组 = 整个 TP×PCP 矩形，是个天然范围    ⟹ 能对齐
       dcp = 4       → 「半个 TP 轴」在 vLLM 里【没有对应的通信组】
                       （TP 组是完整 4 卡，PCP 组是 2 卡，
                         没有任何一个组等于「tp0+tp1 两列」）
```

**⑤ 那为什么 `pcp = 1` 时反而允许「半个 TP 轴」**

因为那时候**根本没转置**（PCP 维长度为 1，转了等于没转），DCP 组就是在 TP 组**内部**连续切块：`tp=4, dcp=2` → `[0,1] [2,3]`。✅ 源码注释直说了：*"DCP reuses the TP ranks when PCP is disabled."*

```
    ⟹ ★ 一维里切段，怎么切都是段；
       二维里切，就可能切出个歪的矩形。
       这就是两个分支宽严不一的全部原因。
```

**⑥ 实操上要当心的一个坑**

单节点经典配方是 `-tp 8 -dcp 8`（DeepSeek-R1，MLA 的 KV 头数 H=1，8 倍重复全消掉）。

| 配置 | 合法 dcp | 能消掉几倍重复 | 需要几张卡 |
|---|---|---|---|
| `-tp 8`（pcp=1） | 1 / 2 / 4 / **8** | ★ **8 倍全消** | 8（单机） |
| `-tp 8 -pcp 2` | ⚠️ **只有 1 / 2 / 16** | dcp=2 只消 2 倍 | 8 |
| `-tp 8 -pcp 2 -dcp 16` | — | ★ 8 倍全消 | ⚠️ **16（两机）** |

```
    ★★ 一旦加上 -pcp 2，原来好用的 -dcp 8 立刻【非法】！

       tp=8, pcp=2  →  合法 dcp ∈ {1, 2, 16}
                                    ↑        ↑
                              只消 2 倍   要 16 卡（两个节点）
```

想在 16 卡上既开 PCP 又完全消除 KV 重复，只能 `-tp 8 -pcp 2 -dcp 16`，⚠️ 代价是 DCP 通信跨节点走 InfiniBand/RoCE 而不是 NVLink——对照 §6.4.7 算的那笔账（每层每 step 约 3.91 MB），带宽从 450 GB/s 掉到 50 GB/s，**通信耗时从 8.7 µs 涨到 78 µs**，很可能得不偿失。

> ⚠️ **诚实标注**：④⑤ 两段「为什么中间值要禁」是我从代码结构推的，**源码里没有任何注释解释原因**，报错信息本身也只是列了张白名单、没给证明。工程上看这些中间值应该是**能做但没做**，跟官方文档对 `dcp ≤ tp/H` 上限的措辞一个调性。
> 另外 ✅ [pcp_manager.py:125-160](../源码/vLLM/vllm/v1/worker/gpu/pcp_manager.py#L125-L160) `validate_config` 显示 **PCP 目前限制还很多**：只支持 MLA，不支持 PP、DP（这条已经进了上面那张表）、多模态、LoRA、投机解码，且只能用 PIECEWISE CUDA Graph。
> ★ 这块整体还在早期，白名单窄一点很合理。

`dcp ≤ tp/H` 这个上界值得单独说一句——它是**有意设的，不是做不到**：

> ✅ 文档原话（意译）：理论上可以把 dcp 开得更大来进一步切 KV、加速解码。但 Decode 阶段 query token 本来就少，多出来的 `dcp − tp/H` 张卡在**非注意力层无事可做**，收益不明。为简单起见就卡在 `tp/H`。

```
    ⟹ ★★ 所以官方给的调参顺序是：
       ① 先把 tp 加到性能满意
       ② 再用 dcp 消掉 KV 重复
       【不要一上来就调 dcp】。
```

### 6.4.7 算一笔账：计算和通信到底是什么关系

前面讲的都是「怎么做」，这一节回答「值不值」。
⚠️ 下面全部是**模型估算**，不是实测数字——用来建立数量级直觉，不能当 benchmark 引。

**参数**：DeepSeek-R1（61 层、128 个 query 头、MLA 压缩维 512 + rope 64 = 576），`-tp 8`，batch=16，上下文 32K，bf16，H100 SXM5（HBM 3.35 TB/s、NVLink **450 GB/s 单向**、BF16 稠密峰值 **989 TFLOP/s**、屋脊点 **295**）。口径：**单层、单张卡、一次 decode step**。

| 逐项 | `dcp=1` | `dcp=8` | 怎么变的 |
|---|---|---|---|
| 参与计算的 query 头数 | 16 | **128** | ★ query 被 all-gather 过来了，**×8** |
| 本卡持有的 KV token 数 | 32768 | **4096** | ★ 只存 1/8，**÷8** |
| 注意力 FLOP | 18.25 G | **18.25 G** | ★★ **一模一样**（×8 和 ÷8 抵消） |
| 本层要读的 KV 字节 | 604.0 MB | **75.5 MB** | ÷8 |
| ① HBM 读取耗时 = 字节 ÷ 3.35 TB/s | **180.3 µs** | **22.5 µs** | ÷8 |
| ② 算力耗时 = FLOP ÷ 989 TFLOP/s | 18.5 µs | 18.5 µs | 不变 |
| 算术强度（FLOP/Byte） | **30.2** | **241.8** | ×8 |
| 和屋脊点 295 比 | ❌ 30 ≪ 295，**严重访存受限** | ⚠️ 242 < 295，**仍是访存受限，但已逼近** | |
| 一次注意力 kernel ≈ max(①, ②) | 180.3 µs（①主导） | **22.5 µs**（① 仍略大于 ②） | |
| ③ NVLink 通信量 | 0 | 3.91 MB | |
| ④ 通信耗时 = ③ ÷ 450 GB/s | 0 | **8.7 µs** | |
| **★ 合计 ≈ max(①,②) + ④** | **180.3 µs** | **★ 31.2 µs（5.8×）** | |
| ★ 算力利用率 = ② ÷ 合计 | **10.3%** | **59%** | ★ 从闲置到大半用上 |
| ★ 带宽利用率 | **≈ 100%** | 72% | ⚠️ 方向和上一行相反 |
| KV Cache 占用 / 卡（61 层） | 34.31 GiB | **4.29 GiB** | ÷8 |

```
    ★★ 这张表里最反直觉的一行是【注意力 FLOP 完全相同】。

       dcp=1：16 个头  × 32768 个 KV
       dcp=8：128 个头 × 4096 个 KV     ← 头数 ×8，KV 数 ÷8，乘积不变

    ⟹ DCP【一个浮点运算都没省】。
       它省的全部是【访存】：每张卡只需要读 1/8 的 KV。
```

> ⚠️ **两处口径必须说准，否则这张表会被读反**：
>
> **① `dcp=8` 之后是不是变成「算力受限」了？——★ 还不是。** 算术强度 241.8 **仍然低于**屋脊点 295，所以严格说它**依旧是访存受限**，只是从「远远受限」变成了「刚好卡在边界内侧」。表里那行 `max(①,②)` 也印证了这点：22.5 µs > 18.5 µs，搬数据**仍然比算得慢**，只是差距从 10 倍缩到 1.2 倍。
> ⟹ 正确的说法是「**从严重访存受限拉到接近屋脊点**」，不是「拉成算力受限」。
>
> **② 算力利用率 10.3% → 59%，是「从浪费变成不浪费」吗？——不完全是。** `dcp=1` 那 10.3% 不是谁写错了 kernel，**它就是 Memory Bound 的定义**（物理规律：算术强度 30 的负载在屋脊点 295 的机器上，天花板就是 30/295 = 10.2%）。同一行的带宽利用率是 **≈100%**——硬件里被榨干的那一项其实已经满了。
> ⟹ ★★ 所以看到「GPU 利用率低」第一件事是问**哪个利用率**：算力低 + 带宽满 = 正常的访存受限；算力低 + 带宽也低 = 那才是真有问题（kernel 写得差、CPU 下发跟不上）。详见 [01 章 §1.3 第 ② 点](01-推理与训练的根本差异.md)。

**为什么省访存就等于省时间：算术强度**

📖 **算术强度**（arithmetic intensity）= 每从显存读 1 字节能做多少次浮点运算。
📖 **屋脊点**（ridge point）= 峰值算力 ÷ 显存带宽。H100 上是 `989 TFLOP/s ÷ 3.35 TB/s ≈ **295** FLOP/Byte`。低于这个数就是**访存受限**（memory-bound），GPU 大部分时间在等数据、算力闲着。

```
    屋顶线（roofline）上看这两个点：纵轴是算力利用率，横轴是算术强度

     100% |                            +------------------- 算力屋顶 989 TFLOP/s
          |                          /
          |                        /
          |                      /
      59% |- - - - - - - - - - -*  dcp=8  (AI = 241.8)
          |                   /  :
          |                 /    :
          |               /      :
     10.3%|- - - - -*   /        :        <- 斜线段 = 带宽屋顶(访存受限区)
          |       /              :
          |     /                :
          +----+----------------+---+---------------------> 算术强度 (FLOP/Byte)
              30              241.8 295
            dcp=1                    ^ 屋脊点

    ⟹ ★ 两个点【都落在斜线上】，也就是都还在访存受限区。
       dcp=8 只是从 30 挪到了 242，离屋脊点 295 已经很近，但还没过去。

    ⟹ ★★ Decode 阶段的本质困境：query 只有几个 token，
       却要把整个 KV Cache 从 HBM 里搬一遍。
       DCP 把「搬一遍」变成「搬 1/8」，
       同时让每张卡多算 8 倍的头把算力填上 —— 【拿闲置算力换访存】。
```

**通信在这笔账里占多大**

| 通信项 | 字节 | 式子 | 谁能省掉它 |
|---|---|---|---|
| query all-gather | **2.06 MB** | `16 × 128 × 576 × 2 × 7/8` | ★ `qrep`（§6.4.5 ②） |
| lse all-gather | 0.01 MB | `16 × 128 × 4 × 7/8` | ★ `a2a` 把它并进下一项 |
| output reduce-scatter | **1.84 MB** | `16 × 128 × 512 × 2 × 7/8` | ★ `a2a`（§6.4.5 ①） |
| **合计** | **3.91 MB** | ÷ 450 GB/s = **8.7 µs** | |

```
    8.7 µs 通信  vs  节省的 157.8 µs 访存  ⟹ ★ 通信只吃掉收益的 5%
```

⚠️ 但这个比例**强烈依赖上下文长度**：访存收益随 T **线性增长**，通信量却**基本不随 T 变**（它只跟 batch 和头数有关）。所以一定存在一个盈亏平衡点。把它解出来：

| 步 | 在算什么 | 式子 | 结果 |
|---|---|---|---|
| ① | 每层省下的 KV 字节 | `B × T × D_Q × b × (1 − 1/8)` | `16 × T × 576 × 2 × 7/8` = **16128 × T** |
| ② | 省下的访存时间 | ① ÷ 3.35 TB/s | `16128 × T ÷ 3.35e12` |
| ③ | 要付的通信时间（与 T 无关） | 3.91 MB ÷ 450 GB/s | **8.7 µs** |
| ④ | 令 ② = ③，解出 T | `T = 8.7e−6 × 3.35e12 ÷ 16128` | ★ **T ≈ 1800 token** |

```
    ⟹ ★★ B=16 时，盈亏平衡点约 1800 token 上下文。

       T <  1800  ⟹ 开 DCP 反而【亏】——通信费白花
       T ≈ 1800  ⟹ 打平
       T ≫ 1800  ⟹ ★ 这才是它的主场（32K 时净赚 5.8 倍）

    ⚠️ B 变大平衡点会左移（通信量随 B 线性涨，访存收益也随 B 线性涨，
       两边同比例 ⟹ ★ 平衡点其实【与 B 无关】，只由「每 token 每层的
       KV 字节 vs 每 token 的通信字节」这个比值决定）。
```

**顺带记住这几个数**

```
    DeepSeek-R1 的 KV Cache 密度（MLA 压缩后，✅ 用的是通式，不是 d_model）：
      每 token 每层  = (512 + 64) × 2 B     = 1152 B
      每 token 全模型 = 1152 × 61           = 68.6 KiB
      一条 32K 请求   = 68.6 KiB × 32768    = 2.14 GiB   ← 一条！

    ⟹ 所以显存永远不够用，这也是 DCP 存在的理由。
```

**自己换硬件跑一遍**（把 `HBM_BW / NVL / PEAK` 换成 H200、B200 的即可）

```python
# DeepSeek-R1 / MLA，单层、单 rank、一次 decode step
L, HID        = 61, 7168     # 层数 / hidden
H_TOTAL       = 128          # query 头数
KV_LORA, ROPE = 512, 64      # MLA 压缩维 / rope 维
D_Q           = KV_LORA + ROPE   # 576，query 与 KV 的 latent 维
BYTES         = 2            # bf16
B, T          = 16, 32768    # batch / 上下文长度
TP            = 8
# ⚠️ NVL 用的是【单向】450 GB/s，不是标称的 900（900 是双向聚合）
# ⚠️ PEAK 用的是 BF16【稠密】989 TFLOP/s，不是稀疏的 1979
HBM_BW, NVL, PEAK = 3.35e12, 450e9, 989e12   # ← H100 SXM5，换卡改这行

def run(dcp):
    heads = H_TOTAL // (TP // dcp)      # 本卡参与计算的 query 头数
    T_loc = T // dcp                    # 本卡持有的 KV token 数
    flops = 2*(D_Q + KV_LORA)*T_loc * heads * B     # q·k + attn·v
    kv_B  = B * T_loc * D_Q * BYTES                 # 本卡本层要读的 KV
    comm  = 0 if dcp == 1 else (
        B*H_TOTAL*D_Q*BYTES*(dcp-1)/dcp             # query all-gather
      + B*H_TOTAL*4*(dcp-1)/dcp                     # lse all-gather (fp32)
      + B*H_TOTAL*KV_LORA*BYTES*(dcp-1)/dcp)        # output reduce-scatter
    t_hbm, t_flop, t_net = kv_B/HBM_BW, flops/PEAK, comm/NVL
    return dict(heads=heads, T_loc=T_loc, ai=flops/kv_B,
                t_hbm=t_hbm, t_flop=t_flop, t_net=t_net,
                total=max(t_hbm, t_flop) + t_net,   # ★ 计算和访存在同一个 kernel 里，取 max
                kv_gpu=B*T_loc*D_Q*BYTES*L/2**30)   # GiB

a, b = run(1), run(8)
print(f"算术强度  {a['ai']:.1f} → {b['ai']:.1f}   (屋脊点 {PEAK/HBM_BW:.0f})")
print(f"单层耗时  {a['total']*1e6:.1f} µs → {b['total']*1e6:.1f} µs"
      f"  ({a['total']/b['total']:.1f}×)")
print(f"算力利用率 {a['t_flop']/a['total']:.1%} → {b['t_flop']/b['total']:.1%}")
print(f"KV/卡     {a['kv_gpu']:.2f} GiB → {b['kv_gpu']:.2f} GiB")
```

```
    ⟹ ★★ 这一节的结论一句话：
       DCP 不省算力，只省访存；而 decode 恰恰是【访存受限】的，
       所以省访存 = 省时间。通信是要付的学费，
       上下文越长学费占比越低（约 1800 token 是分界线）。
```

### 6.4.8 这一节小结

| # | 要点 | 关键数字 / 出处 |
|---|---|---|
| ① | ★★ **动机**：`tp > KV 头数 H` 时，KV Cache 被白白复制 `tp/H` 份。MLA 模型 H=1，最惨 | DeepSeek-R1 `-tp 8` → **8×**（浪费 87.5%）；Kimi-K2 `-tp 16` → **16×**（浪费 93.75%）。★ DCP **不加卡**，只把重复副本改成「各存一段」 |
| ② | ★★ **存**：交错分片，token 归属**只看绝对位置** | ✅ `block_table.py` 的 Triton 内核，`interleave` 默认 1（逐 token）。⟹ 序列变长时新 token 自然落位，**零重分配**。📌 方案来自 Moonshot，[arXiv:2507.07120](http://arxiv.org/abs/2507.07120) |
| ③ | ★★ **算**：LSE **精确**合并，不是近似 | Decode：广播 query → 各算局部 → LSE 校正 → ReduceScatter。Prefill：**反过来**，all-gather KV 再 reorg。⟹ ★ 一个旋钮，两条相反的数据流 |
| ④ | **两个可选优化** | `a2a` 把 NCCL 调用从 **3 次降到 2 次**（字节数一分没省，省的是同步点和中间张量）；`qrep` 用 `×dcp` 的冗余算力换掉 query all-gather |
| ⑤ | **调参顺序** | ① 先加 `tp` 到性能满意 → ② 再用 `dcp` 消重复。上界 `dcp ≤ tp/H` 是**故意**设的 |
| ⑥ | ★★ **账**：DCP **不省一个 FLOP**，省的全是访存 | 16 头 × 32768 KV → 128 头 × 4096 KV，乘积不变，读的字节 ÷8。算术强度 **30 → 242**（⚠️ 屋脊点 295，**242 仍在访存受限侧**，只是逼近了边界）。⚠️ 约 **1800 token** 以下开 DCP 反而亏 |

## 6.5 SGLang 的路子：干脆不要全局 DP 维度

vLLM 是「五维张量 reshape」。SGLang 走了一条**完全不同**的路。

```python
# ✅ SGLang parallel_state.py:2407
if world_size != tensor_model_parallel_size * pipeline_model_parallel_size:
    raise RuntimeError(
        f"world_size ({world_size}) is not equal to "
        f"tensor_model_parallel_size ({tensor_model_parallel_size}) x "
        f"pipeline_model_parallel_size ({pipeline_model_parallel_size})")
```

```
    ★★ 读懂这一行：SGLang 的全局网格里【只有 TP 和 PP 两个维度】。
       world_size 严格等于 tp × pp。没有 DP 这一维的位置。
```

那 SGLang 怎么做数据并行？答案很反直觉：**它把同一个 TP 组，针对模型的不同部分，用不同的方式重新切分。**

| 模型的哪一部分 | 这部分眼里，`tp_size` 被分解成 | 于是这部分实际用的并行 |
|---|---|---|
| **注意力层** | `tp_size = attn_dp × attn_cp × attn_tp` | ★ 可以是纯 DP（`attn_dp = tp_size`） |
| **MoE 层** | `tp_size = moe_dp × moe_ep × moe_tp` | ★ 可以是纯 EP（`moe_ep = tp_size`） |

```
    ★ 同样的 8 张卡：
      在注意力层眼里  → 是 8 个独立的 DP 副本（各服务不同请求）
      在 MoE 层眼里    → 是 8 个 EP 分片（各持有 1/8 的专家）

    ⟹ ★★ 同一批 rank，一层之内换一次身份。
```

> ✅ **源码可查**（SGLang [parallel_state.py](../源码/SGLang/python/sglang/srt/distributed/parallel_state.py)）：
> `_TP` **L2446**、`_ATTN_CP` **L2526**、`_ATTN_TP` **L2571**、`_MOE_DP`/`_MOE_EP` **L2636**、`_MOE_TP` **L2666**、`_PP` **L2689**。
> 其中 MoE 那一侧的除法尤其直白（**L2587**）：
> ```python
> moe_tp_size = tensor_model_parallel_size // moe_ep_size // moe_dp_size
> ```
> 而 **L2554** 有个漂亮的短路：
> ```python
> if attn_tp_size == tensor_model_parallel_size:
>     _ATTN_TP = _TP        # ★ 不切的话直接复用 TP 组，不新建通信组
> ```

**★ 为什么 SGLang 要这么设计？——因为 MoE 模型的注意力层和 MoE 层，最优切法根本不同。**

| | 注意力层（MLA） | MoE 层 |
|---|---|---|
| 这部分的参数量 | 小（DeepSeek-V3 里约 5%） | ★ 大（约 95%） |
| 这部分的 KV Cache | ★ 全部在这（但 MLA 压得很小） | 无 |
| 用 TP 切会怎样 | ⚠️ **MLA 的 KV 没有头可切 ⟹ 只能复制**（§6.4.1） | 专家复制到每卡 ⟹ **671 GB，装不下** |
| 用 DP 会怎样 | ★ 每卡存自己那批请求的完整小 KV，**0 次 all-reduce** | ⚠️ 装不下 |
| 用 EP 会怎样 | 无意义（没有专家） | ★ 每卡 1/EP 的专家，**装得下** |
| ⟹ **最优** | ★★ **DP**（SGLang 叫 **DP Attention**） | ★★ **EP** |

```
    ⟹ ★★ 同一个模型，注意力想要 DP，MoE 想要 EP，需求【直接冲突】。

       vLLM 的固定五维网格表达不了这个：
         DP 是全局一维，一旦定了 DP=8，所有层都得按 DP=8 走。
       SGLang 干脆放弃全局网格，让每一部分自己决定怎么切。
```

> ★ 关于「MLA 逼出了 Attention DP」这条因果链的完整推演（含显存对比：同样的显存，TP=8 只服务 1 个用户，DP=8 服务 8 个），见 [07 章 §7.7](07-注意力变体MQA-GQA-MLA.md)。
> ⚠️ 实际部署不是非黑即白：✅ DeepSeek-V3 官方的 Prefill 最小部署单元是 4 机 32 卡，注意力部分用的是 **TP4 + DP8** 的混合，不是纯 DP（见 [11 章 §11.2](11-MoE推理与专家并行.md)）。**「注意力 DP」说的是方向，不是一个非此即彼的开关。**

> ✅ DP Attention 的实现在 [dp_attention.py](../源码/SGLang/python/sglang/srt/layers/dp_attention.py)：`compute_dp_attention_world_info` **L326**、`initialize_dp_attention` **L343**。
> 注意力算完要把结果聚回来，SGLang 提供了**两条**路径（**L489** `_dp_gather_via_all_reduce` 和 **L531** `_dp_gather_via_all_gather`），★ 因为哪条快取决于 batch 形状。
> `DpPaddingMode` **L81** 处理各 DP rank 序列长度不一样时的补齐问题。

## 6.6 ★ 两种设计哲学的对比

| | **vLLM** | **SGLang** |
|---|---|---|
| **全局网格** | 5 维固定：`ExtDP × DP × PP × PCP × TP` | ★ 2 维：`world_size = tp × pp` |
| **DP 怎么来** | ★ 网格里的**一个维度**（整块副本） | ★ 从 TP 组内部**再切**（按模型部位分别切） |
| **同一层内能不能换切法** | ❌ 不能，所有层用同一套 | ★ **能**：注意力 `attn_dp×attn_cp×attn_tp`，MoE `moe_dp×moe_ep×moe_tp` |
| **灵活性** | 低 | ★ 高 |
| **理解成本** | ★ 低：一次 `reshape` 就看懂全部 | 高：要跟踪 6+ 个通信组之间的关系 |
| **上下文并行** | ★ 拆成两个独立旋钮（PCP + DCP） | `attn_cp` + `dcp`，挂在 TP 分解里 |
| **最擅长** | 稠密模型、通用场景 | ★ 超大 MoE（DeepSeek / Kimi 类） |
| ✅ 关键代码 | [parallel_state.py:1817](../源码/vLLM/vllm/distributed/parallel_state.py#L1817) 一行注释 + L1826 的 reshape | [parallel_state.py:2407](../源码/SGLang/python/sglang/srt/distributed/parallel_state.py#L2407) 那个 `raise` + L2587 的除法 |

> ⚠️（我的判断，非官方表述）可以这样记：
> **vLLM 把并行策略当成「部署配置」——先定好网格，模型往里填。**
> **SGLang 把并行策略当成「模型属性」——模型的每一部分自己声明想怎么切。**
> 两条路都在收敛：vLLM 后来加了 DCP/PCP 和 EP 的独立处理，SGLang 也在补 PP。

## 6.7 实践：怎么选

给一个可操作的决策树（⚠️ 经验法则，非论文结论）：

```
    ① 模型（含 KV Cache）单卡放得下？
       → ★ TP=1，DP=卡数。最简单、吞吐最高、没有任何通信。

    ② 单卡放不下，单机 8 卡放得下？
       → ★ TP = 刚好够装下的【最小值】（2/4/8），DP = 机器数
       → ⚠️ 不要为了「更快」盲目加 TP：§6.3 ① 那张表算过，
            并行效率 TP=2 是 93%、TP=8 只剩 76%
       → ⚠️ TP 越过 KV 头数，KV 显存就不再减少了（但框架不报错！）

    ③ 单机放不下（>200B 稠密 / 超大 MoE）？
       → 先试量化（[09 章](09-量化.md)）能不能塞回单机
       → 塞不回：机内 TP=8，★ 机间 PP（或 MoE 的 EP）
       → ⚠️ PP 必须配大并发，否则 decode 气泡率 (PP-1)/PP 吃掉一切
       → ⟹ 这就是「机内 TP、机间 PP、最外 DP」，
            ★ 和训练的口诀字面一样，但 DP 的「最外」这次是【真的最外】

    ④ tp 已经超过模型的 KV 头数 H 了？（MLA 模型 H=1，tp≥2 就中）
       → ★ 此时 KV Cache 正在被复制 tp/H 份，纯浪费
       → 上 DCP：-dcp <size>，size ≤ tp/H，★ 不用加卡
       → ⚠️ 顺序别搞反：先把 tp 加到性能满意，再加 dcp（见 §6.4.6）
       → ⚠️ 上下文短于约 1800 token 时，DCP 的通信费收不回来（§6.4.7）
       → 单条序列超长装不下，也是靠这个旋钮，但那是顺带的

    ⑤ 首字延迟被超长 prompt 拖垮？
       → 上 PCP（预填充上下文并行），⚠️ 但它现在不支持 DP / PP / 投机解码
       → 或者直接上 PD 分离（[10 章](10-PD分离.md)）
```

把「想解决什么问题」和「该拧哪个旋钮」对起来：

| 你的痛点 | ★ 该拧的旋钮 | ⚠️ 别拧的 | 为什么 |
|---|---|---|---|
| 权重装不下 | TP → PP → 量化 | DP | ★ DP 不省一点显存（§6.2.1） |
| 吞吐不够，延迟可接受 | ★ **DP** 加副本 | TP | TP 收益递减，DP 线性扩展且零通信 |
| TPOT（每字延迟）太高 | TP（到单机卡数为止） | PP | PP 在 decode 里气泡率 (PP−1)/PP |
| TTFT（首字延迟）太高 | PCP、PD 分离、chunked prefill | — | Prefill 是算力问题（⚠️ 仅当 prompt 够长，见下） |
| KV Cache 装不下 / 并发上不去 | ★ **DCP**（若 tp>H）、GQA/MLA、KV 量化 | TP（越过 H 就没用了） | §6.4.1 |
| MoE 专家装不下 | ★ **EP** | TP | 专家 TP 要复制，671 GB 装不下 |
| 长 prompt 并发下 TTFT 抖动 | chunked prefill + 调度 | — | [03 章 §3.5](03-Prefill与Decode两阶段.md) / [04 章](04-连续批处理与调度.md) |

> ⚠️ **上表「TTFT 太高」那一行有个前提必须说清**：常说的「Prefill 是算力受限、所以加卡（TP/PCP）线性提速」**不是无条件成立的**。
> ★ **算术强度不是 Prefill 的固有属性，它大致等于 prompt 长度 M。** 一个 6 token 的 Prefill，算术强度只有 **5.6**，离屋脊点 295 差 50 倍——**它和 Decode 一样是访存受限的**，加卡只能按带宽比例提速，PCP 更是纯亏（通信费白花）。
> 🔑 临界点在 **几百个 token** 这个量级：[03 章 §3.3](03-Prefill与Decode两阶段.md) 按整模型口径算出 **M ≈ 390**，[大模型算子开发/09 章 §9.1.3](../../大模型算子开发/09-推理侧算子.md) 按单个 GEMM 口径算出 **M ≥ 325**（口径不同，量级一致）。
> ⟹ ★★ 所以「Prefill 算力受限」要加限定：**prompt 长于几百 token 时成立**。聊天场景里一句十几个字的问题，它的 Prefill 成本 ≈ 一步 Decode，谈不上「算力受限」。

## 6.8 本章小结

| # | 要点 | 关键数字 / 出处 |
|---|---|---|
| ① | ★★ **vLLM 布局**：`ExternalDP × DP × PP × PCP × TP`（最后一维变化最快 = 最近） | ✅ [parallel_state.py:1817](../源码/vLLM/vllm/distributed/parallel_state.py#L1817) 原文注释。⟹ 和训练的 `tp-cp-ep-dp-pp` 相比，★ **PP 和 DP 换了位置** |
| ② | ★★★ **换位的唯一原因** | 训练 DP 每步 all-reduce **2Ψ** 梯度（70B → 140 GB，跨机 2.8 s）⟹ 贵 ⟹ 必须近。推理 DP 是独立副本，**0 字节** ⟹ 免费 ⟹ 可以最远。★ 原则从来没变：**通信量大的维度放最近** |
| ③ | **TP**：仍是主力，每层 **2** 次 all-reduce（训练 4 次） | ★ 收益递减是**算得出来的**：并行效率 TP=2 → 93%、TP=4 → 87%、TP=8 → 76%、**TP=16 → 27%（倒退）**。⚠️⚠️ 拐点的根因是 **TP 越过 KV 头数后 KV 被复制、显存和访存都不再减少**，框架**不报错** |
| ④ | **PP**：★ 地位下降 | Decode 每步只有 1 token，**切不出 micro-batch** ⟹ 气泡率 `(PP−1)/PP`，PP=4 就是 **75%**。必须靠大并发填 |
| ⑤ | **DP**：★ 变成「多开实例」 | 通信 0、线性扩吞吐，但 ⚠️ **一点显存都不省**。MoE 场景下必须同步 generate 防死锁（dummy run） |
| ⑥ | **EP**：MoE 专用 | ⚠️ 单向 dispatch = `t × **K** × H × b × (1−1/EP)`，**别漏 × Top-K**（漏了小 8 倍）。⚠️ NVLink 分母用 **450**（不是 900），IB 用 **50 GB/s**（400 Gb ÷ 8） |
| ⑦ | **PCP / DCP**：★ 推理独有 | Prefill 和 Decode 各要一个上下文并行，**数据流方向相反**。★★ DCP 详见 §6.4：交错分片**存** + LSE 精确合并**算**；动机是消 KV 重复（`tp/H` 份），**不加卡** |
| ⑧ | ★★ **SGLang 的另一条路** | `world_size == tp × pp`，**没有全局 DP 维**（✅ [parallel_state.py:2407](../源码/SGLang/python/sglang/srt/distributed/parallel_state.py#L2407)）。改为把 TP 组**按模型部位重新切**：注意力 `attn_dp × attn_cp × attn_tp`，MoE `moe_dp × moe_ep × moe_tp`。★ 动机：MoE 模型的注意力层想要 DP、MoE 层想要 EP，**需求冲突** |
| ⑨ | ⚠️ **两个必须带口径的说法** | **(a)** 「Decode GPU 利用率低」= **算力**利用率低（0.34%~59%），但**带宽**利用率接近 100%——算力低是 Memory Bound 的**定义**（物理规律），不是浪费。**(b)** 「Prefill 算力受限」只在 prompt **长于几百 token** 时成立；算术强度 ≈ M，M=6 时只有 5.6，和 Decode 一样访存受限 |
