# 06 推理中的并行策略 ⭐ 核心章

> **一句话**：推理用的还是 TP / PP / DP / EP 那几个名字，但**成本模型全变了**——所以最优的排布顺序和训练**正好相反**。

## 6.0 先把结论摆出来

```
┌───────────────────────────────────────────────────────────────────┐
│  训练（Megatron-LM）的 rank 排布顺序：                             │
│      tp - cp - ep - dp - pp        ← ★ PP 在最外，DP 在中间        │
│                                                                   │
│  推理（vLLM）的 rank 排布顺序：                                    │
│      ExternalDP - DP - PP - PCP - TP   ← ★★ PP 在 DP 【里面】     │
│                                                                   │
│  ★★ 一模一样的两个维度，相对位置【调了个个儿】。                    │
│     不是谁写错了——是 DP 的通信成本从「最贵之一」变成了「几乎为零」。│
└───────────────────────────────────────────────────────────────────┘
```

> ✅ **原文可查**：vLLM [parallel_state.py:1817](../源码/vLLM/vllm/distributed/parallel_state.py#L1817)
> ```python
> # the layout order is: ExternalDP x DP x PP x PCP x TP
> ```

这一章就是要把这个「调个个儿」讲透。

## 6.1 先复习：rank 排布顺序到底在说什么

> 📖 **rank**——每张 GPU 的全局编号，0, 1, 2, ... N-1。
> 📖 **排布顺序**——把这 N 个编号 reshape 成一个多维数组，**哪个维度变化最快**。

vLLM 就是字面意义上地 reshape 了一下：

```python
# ✅ parallel_state.py:1826
all_ranks = torch.arange(world_size).reshape(
    -1,                                    # ExternalDP
    data_parallel_size,                    # DP
    pipeline_model_parallel_size,          # PP
    prefill_context_model_parallel_size,   # PCP
    tensor_model_parallel_size,            # TP   ← ★ 最后一维 = 变化最快
)
```

**「变化最快」= 组内 rank 编号连续 = 物理距离最近。** 这就是全部的含义。

```
    ★ 步长（stride）= 同组内相邻两个 rank 的编号差

      TP  组：步长 1                     ← ★ 最近，同一台机器内，走 NVLink
      PCP 组：步长 = TP
      PP  组：步长 = PCP × TP
      DP  组：步长 = PP × PCP × TP       ← ★ 最远，跨机器，走网络

    ⟹ ★★ 排在【越后面】的维度，通信越【近】越【快】。
       所以排布顺序的设计原则永远是同一条：
       ★★★ 通信量最大的维度，放到最后（离得最近）。
```

拿一个具体例子：**8 卡，TP=2，PP=2，DP=2**（PCP=1）：

```
    reshape 成 [1, 2, 2, 1, 2]，即 [ExtDP=1][DP=2][PP=2][PCP=1][TP=2]

    rank 0 1 2 3 4 5 6 7 摆进去：

              DP=0                    DP=1
        ┌───────────────┐      ┌───────────────┐
    PP=0│  rank 0, 1    │      │  rank 4, 5    │
        │   └─TP 组─┘   │      │   └─TP 组─┘   │
    PP=1│  rank 2, 3    │      │  rank 6, 7    │
        │   └─TP 组─┘   │      │   └─TP 组─┘   │
        └───────────────┘      └───────────────┘

    ⟹ TP 组：[0,1] [2,3] [4,5] [6,7]           步长 1  ★最近
    ⟹ PP 组：[0,2] [1,3] [4,6] [5,7]           步长 2
    ⟹ DP 组：[0,4] [1,5] [2,6] [3,7]           步长 4  ★最远

    ★★ 请对比训练：训练里 DP 步长小于 PP，DP 比 PP 【近】。
       这里反过来了。
```

> ✅ 各组的构造代码：
> TP [parallel_state.py:1843](../源码/vLLM/vllm/distributed/parallel_state.py#L1843)（直接 `view(-1, tp)`，不需要转置，因为它已经在最后一维）；
> PP [L1891](../源码/vLLM/vllm/distributed/parallel_state.py#L1891)（`all_ranks.transpose(2, 4)`——把第 2 维换到最后）；
> DP [L1908](../源码/vLLM/vllm/distributed/parallel_state.py#L1908)（`all_ranks.transpose(1, 4)`）。
> ★ 代码注释把这套手法说得很清楚：*"to get group_ranks for each dimension, transpose that dimension to the last dimension, then reshape to 2D, then unbind"*。

## 6.2 ★★ 为什么反过来：一张表说清

回到那条唯一的原则——**通信量大的放近处**。所以只要比较四个维度在训练/推理下各自的通信量：

```
┌────────┬──────────────────────────┬──────────────────────────┐
│  维度   │  训练的通信量             │  推理的通信量             │
├────────┼──────────────────────────┼──────────────────────────┤
│  TP    │ 每层 4 次 all-reduce      │ 每层 2 次 all-reduce      │
│        │ （前向2 + 反向2）          │ ★ 没有反向，直接减半      │
│        │ ⟹ 最大，必须放最近         │ ⟹ 仍然最大，仍放最近      │
├────────┼──────────────────────────┼──────────────────────────┤
│  PP    │ 每个 micro-batch 传一次   │ 每步传一次激活            │
│        │ 激活（前向）+ 梯度（反向） │ ★ 只有前向，量减半        │
│        │ 量中等，可以跨机           │ 量中等，可以跨机           │
├────────┼──────────────────────────┼──────────────────────────┤
│  DP    │ ★★ 每步 all-reduce 全部    │ ★★ 几乎【为零】           │
│        │ 梯度 = 2Ψ                 │ 各副本服务不同用户，       │
│        │ ⟹ 【非常贵】，必须离得近   │ 不需要同步任何东西         │
│        │                          │ ⟹ 【可以扔到天涯海角】     │
├────────┼──────────────────────────┼──────────────────────────┤
│  EP    │ 每层 2 次 all-to-all      │ 每层 2 次 all-to-all      │
│  (MoE) │ + 反向 2 次               │ ★ 没有反向                │
└────────┴──────────────────────────┴──────────────────────────┘
```

> 🔑 **★★★ 全章最重要的一句话**：
> 训练的 DP 每步要 all-reduce 整个模型的梯度（[训练框架/05 章](../../训练框架/分布式训练入门/05-ZeRO与FSDP.md) 算过是 2Ψ），
> 所以 DP 必须排在 PP 前面（更近）。
> **推理的 DP 只是「N 份完全独立的副本，各服务各的用户」，一个字节都不用传。**
> 既然它不花通信，就理应被踢到最外圈，把宝贵的近距离带宽让给 TP 和 PP。

**再补一个二阶原因**（⚠️ 我的推断，代码注释支持但未明说）：

```
    ★ DP 在最外层，还有一个工程上的好处：
      「一个 DP 副本」= 一段连续的 rank = 一个完整的、自洽的推理引擎实例。
      ⟹ 可以整块地启动、整块地挂掉重启、整块地做弹性伸缩
      ⟹ 这正是 ExternalDP 这一维存在的意义：
         代码注释说它用于 "verl integration"（强化学习框架），
         ★ every dp rank can generate independently
```

## 6.3 逐个维度：推理里它们各自怎么用

### ① TP（张量并行）——切权重，仍然是主力

> 📖 **TP**（**T**ensor **P**arallelism，张量并行）——把每一层的权重矩阵切开，每张卡存一片。

推理里的 TP 和训练完全同构，还是那套「列切 + 行切」：

```
    一个 MLP（多层感知机）块：
      第一个线性层：★ 按【列】切（ColumnParallelLinear）→ 不需要通信
      激活函数：                                        → 逐元素，不需要通信
      第二个线性层：★ 按【行】切（RowParallelLinear）   → ⚠️ 需要 all-reduce

    注意力块同理，QKV 按列切，输出投影按行切 → ⚠️ 一次 all-reduce

    ⟹ ★ 每层 2 次 all-reduce（注意力 1 次 + MLP 1 次）
```

> ✅ **源码可查**（vLLM [linear.py](../源码/vLLM/vllm/model_executor/layers/linear.py)）：
> `ColumnParallelLinear` **L407**（注意 `gather_output` 默认 **False**——★ 故意不 all-gather，把结果直接喂给下一个行切层，省掉一次通信）；
> `QKVParallelLinear` **L971**（QKV 三个矩阵合并成一个列切层）；
> `RowParallelLinear` **L1510**，唯一那次通信在 **L1660**：
> ```python
> output = tensor_model_parallel_all_reduce(output_parallel)
> ```

**推理里 TP 的两个新特点**：

```
    ★ 特点一：TP 是【降低单卡显存 + 降低延迟】的主要手段
      TP=8 ⟹ 权重和 KV Cache 都切成 1/8
           ⟹ 单个 token 的计算和访存都变成 1/8 ⟹ ★ TPOT 直接变快
      ⟹ 这是训练里没有的动机（训练不在乎单步延迟）

    ⚠️ 特点二：TP 在 Decode 阶段【收益递减】
      Decode 本来就访存受限、kernel 很小。TP=8 之后，
      每张卡的计算小到「通信时间 > 计算时间」
      ⟹ ★ 再加卡就是纯亏。经验上 TP 一般不超过单机卡数（8）。
      ⟹ 想再扩，用 DP 加副本，不要继续加 TP。
```

**一个 TP 的硬约束**：

```
    ⚠️ TP 数必须能整除【KV 头数】。
       Llama-3-8B 用了 GQA，只有 8 个 KV 头 ⟹ ★ TP 最大只能到 8。
       TP=16 的话，有的卡分不到 KV 头。
       （框架的绕法是复制 KV 头，但那就白费显存了）
```

### ② PP（流水线并行）——推理里地位下降

> 📖 **PP**（**P**ipeline **P**arallelism，流水线并行）——把模型按层切成几段，每张卡放一段。

```
    ★ 训练里 PP 很重要：它是唯一能把超大模型放下、且通信量小的手段。
    ⚠️ 推理里 PP 的地位明显下降，原因是【气泡】。
```

```
    训练的流水线：一个 batch 切成 N 个 micro-batch 灌进去
                 ⟹ 气泡率 ≈ (PP-1) / (PP-1+N)，N 可以很大 ⟹ 气泡小

    ★★ 推理的 Decode：每一步只有【1 个 token】
       ⟹ 没有 micro-batch 可切！
       ⟹ 气泡率 ≈ (PP-1)/PP，PP=4 时高达 75%

    ⚠️ 挽救办法：靠【连续批处理】天然的多请求来填流水线——
       不同请求处在不同的流水段上，互相填对方的气泡。
       ⟹ 所以推理的 PP 必须配合【大并发】才有意义。
```

> ⚠️（我的判断）实践中的选择顺序通常是：
> **能单机 TP 装下 → 只用 TP；单机装不下 → 先考虑量化（09 章）；还是装不下 → 才上 PP 跨机。**
> PP 主要用在「模型大到单机 8 卡也放不下」的场景（比如 DeepSeek-V3 这种 671B）。

### ③ DP（数据并行）——推理里含义完全不同

```
    ★ 训练的 DP：同一个 batch 切开，算完【必须 all-reduce 梯度】
    ★ 推理的 DP：★★ 就是「多开几个一模一样的服务实例」

    ⟹ 没有任何梯度、没有任何同步、通信量 = 0
    ⟹ 扩容方式：想翻倍吞吐？DP 翻倍即可，线性扩展
```

**但有一个坑**，代码注释专门警告了：

```python
# ✅ parallel_state.py:1819-1823
# DP is the data parallel group that is part of the model,
# all the ranks in the same DP group should generate simultaneously,
# i.e. the `generate` call in the same DP group should be called together,
# otherwise it will cause deadlock.
```

```
    ★★ 为什么会死锁？
       DP 组内虽然不传梯度，但如果模型里有 MoE 层，
       MoE 的 all-to-all 是【跨 DP 组】的集合通信（见 §6.4）。
       集合通信要求所有参与者【同时到场】。
       ⟹ 某个 DP rank 因为没请求而不发起 generate，其他人就永远在等它。
    ⟹ 这就是为什么 vLLM 里 DP 组必须「同步地一起 generate」，
       没请求的 rank 也要发一个【假的空 batch】进去凑数（dummy run）。
```

### ④ EP（专家并行）——MoE 专用

> 📖 **EP**（**E**xpert **P**arallelism，专家并行）——MoE 模型里，把不同的专家放到不同卡上。
> 📖 **MoE**（**M**ixture **o**f **E**xperts，混合专家）——每个 token 只激活一小部分参数。

EP 的 rank 组构造很有意思，它是 **DP × PCP × TP 三个维度合并**出来的：

```python
# ✅ parallel_state.py:1923 附近
group_ranks = all_ranks.transpose(1, 2).reshape(
    -1, data_parallel_size * prefill_context_model_parallel_size *
        tensor_model_parallel_size).unbind(0)
```

```
    ⟹ ★ EP 组 = 「同一个 PP 段内的所有卡」
       含义：专家在一层内横着切，但不跨流水线段——这符合直觉，
             因为不同 PP 段本来就是不同的层。
```

11 章会详细讲 MoE 推理和负载均衡（EPLB）。

### ⑤ 推理独有的新维度：PCP 和 DCP

这是训练侧没有的东西，vLLM 的比较新的加法：

```
    📖 CP（Context Parallelism，上下文并行）——把【序列】切开，
       不同卡负责序列的不同片段。训练侧也有（Ring Attention 等）。

    ★ vLLM 把它拆成了两个独立的旋钮：
      📖 PCP = Prefill Context Parallel（预填充上下文并行）
              → 处理超长 prompt 时，把 prompt 切段并行做 Prefill
              ★ 它在 rank 布局里占了独立一维（PP 和 TP 之间）
      📖 DCP = Decode Context Parallel（解码上下文并行）
              → 把【KV Cache】按序列维切到多张卡上
              ★ 解决的是「单条 128K 序列的 KV 太大，一张卡放不下」

    ⟹ ★★ 为什么要拆成两个？因为 03 章那条：两个阶段性格不同，
       Prefill 想切序列换算力，Decode 想切序列换显存。目标不一样。
```

> ✅ 布局里 PCP 的位置见 L1826 的 reshape；DCP 的组在 TP 组之后构造（约 L1860+），
> ★ 注意 DCP 是从 **TP 组内部**再切的，不占全局维度——这和 PCP 不同。

## 6.4 SGLang 的路子：干脆不要全局 DP 维度

vLLM 是「五维张量 reshape」。SGLang 走了一条**完全不同**的路。

```python
# ✅ SGLang parallel_state.py:2408
if world_size != tensor_model_parallel_size * pipeline_model_parallel_size:
    raise RuntimeError(...)
```

```
    ★★ 读懂这一行：SGLang 的全局网格里【只有 TP 和 PP 两个维度】。
       world_size 严格等于 tp × pp。没有 DP 这一维的位置。
```

那 SGLang 怎么做数据并行？答案很反直觉：

```
    ★★★ 它把【同一个 TP 组】，针对模型的不同部分，
        用【不同的方式】重新切分。

    ┌─────────────────────────────────────────────────────┐
    │  注意力部分：  tp_size = attn_dp × attn_cp × attn_tp │
    │  MoE 部分：    tp_size = moe_dp × moe_ep × moe_tp    │
    │                                                     │
    │  ★ 同样的 8 张卡，在注意力层眼里是一种分组，          │
    │    在 MoE 层眼里是另一种分组。                        │
    └─────────────────────────────────────────────────────┘
```

> ✅ **源码可查**（SGLang [parallel_state.py](../源码/SGLang/python/sglang/srt/distributed/parallel_state.py)）：
> `_TP` **L2446**、`_ATTN_CP` **L2526**、`_ATTN_TP` **L2571**、
> `_MOE_DP`/`_MOE_EP` **L2636**、`_MOE_TP` **L2666**、`_PP` **L2689**。
> 其中 MoE 那一侧的除法尤其直白（**L2587**）：
> ```python
> moe_tp_size = tensor_model_parallel_size // moe_ep_size // moe_dp_size
> ```
> 而 **L2554** 有个漂亮的短路：
> ```python
> if attn_tp_size == tensor_model_parallel_size:
>     _ATTN_TP = _TP        # ★ 不切的话直接复用 TP 组，不新建通信组
> ```

**★ 为什么 SGLang 要这么设计？——因为 MoE 模型的注意力和 MoE 层，最优切法根本不同。**

```
    以 DeepSeek-V3 这类模型为例（⚠️ 以下是机理说明，非论文数字）：

    ★ 注意力层：用了 MLA（07 章），KV Cache 已经压得很小。
      如果还按 TP=8 切注意力头 ⟹ 每张卡都要存【同一份】KV 的一部分，
      而且 all-reduce 开销大。
      ⟹ 更好的做法：★ 注意力层用 DP！每张卡处理【不同的请求】，
         各自持有完整的小 KV，一次 all-reduce 都不用。
         这就是 attn_dp，SGLang 叫 【DP Attention】。

    ★ MoE 层：256 个专家，每个 token 只激活 8 个。
      ⟹ 最优做法是 EP：专家分散到各卡，token 通过 all-to-all 路由过去。

    ⟹ ★★ 同一个模型，注意力想要 DP，MoE 想要 EP。
       vLLM 的固定五维网格表达不了这个；
       SGLang 干脆放弃全局网格，让每一部分自己决定怎么切。
```

> ✅ DP Attention 的实现在 [dp_attention.py](../源码/SGLang/python/sglang/srt/layers/dp_attention.py)：
> `compute_dp_attention_world_info` **L326**、`initialize_dp_attention` **L343**。
> 注意力算完要把结果聚回来，SGLang 提供了两条路径（**L489** `_dp_gather_via_all_reduce`
> 和 **L531** `_dp_gather_via_all_gather`），★ 因为哪条快取决于 batch 形状。
> `DpPaddingMode` **L81** 处理各 DP rank 序列长度不一样时的补齐问题。

## 6.5 ★ 两种设计哲学的对比

```
┌──────────────┬─────────────────────┬──────────────────────────┐
│              │  vLLM               │  SGLang                  │
├──────────────┼─────────────────────┼──────────────────────────┤
│  全局网格     │ 5 维固定：           │ ★ 2 维：world = tp × pp   │
│              │ ExtDP×DP×PP×PCP×TP  │                          │
├──────────────┼─────────────────────┼──────────────────────────┤
│  DP 怎么来    │ ★ 网格里的一个维度   │ ★ 从 TP 组内部【再切】    │
│              │ （整块副本）         │ （按模型部位分别切）      │
├──────────────┼─────────────────────┼──────────────────────────┤
│  灵活性      │ 低：所有层用同一套切法│ ★ 高：注意力和 MoE 可以   │
│              │                     │ 用完全不同的切法          │
├──────────────┼─────────────────────┼──────────────────────────┤
│  理解成本     │ ★ 低：一次 reshape   │ 高：要跟踪 6+ 个通信组    │
│              │ 就看懂全部           │ 之间的关系                │
├──────────────┼─────────────────────┼──────────────────────────┤
│  最擅长      │ 稠密模型、通用场景    │ ★ 超大 MoE（DeepSeek 类） │
└──────────────┴─────────────────────┴──────────────────────────┘
```

> ⚠️（我的判断，非官方表述）可以这样记：
> **vLLM 把并行策略当成「部署配置」——先定好网格，模型往里填。**
> **SGLang 把并行策略当成「模型属性」——模型的每一部分自己声明想怎么切。**
> 两条路都在收敛：vLLM 后来加了 DCP/PCP 和 EP 的独立处理，SGLang 也在补 PP。

---

## 6.6 实践：怎么选

给一个可操作的决策树（⚠️ 经验法则，非论文结论）：

```
    ① 模型（含 KV Cache）单卡放得下？
       → ★ TP=1，DP=卡数。最简单、吞吐最高、没有任何通信。

    ② 单卡放不下，单机 8 卡放得下？
       → ★ TP = 刚好够装下的最小值（2/4/8），DP = 机器数
       → ⚠️ 不要为了「更快」盲目加 TP，Decode 阶段收益递减
       → ⚠️ TP 必须整除 KV 头数

    ③ 单机放不下（>200B 稠密 / 超大 MoE）？
       → 先试量化（09 章）能不能塞回单机
       → 塞不回：机内 TP=8，★ 机间 PP（或 MoE 的 EP）
       → ⟹ 这就是「机内 TP、机间 PP、最外 DP」，
            ★ 和训练的口诀字面一样，但 DP 的「最外」这次是【真的最外】

    ④ 单条序列就超长（128K+），KV 单卡放不下？
       → 上 DCP（解码上下文并行）

    ⑤ 首字延迟被超长 prompt 拖垮？
       → 上 PCP（预填充上下文并行），或者直接上 PD 分离（10 章）
```
