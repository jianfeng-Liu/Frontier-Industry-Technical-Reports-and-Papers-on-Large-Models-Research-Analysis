# 08 投机解码

> **一句话**：Decode 时 GPU 的**算力**在空转（带宽却已经打满），那就**用这些空着的算力去猜后面几个字**——猜对了白赚，猜错了也几乎没亏。
> ⚠️ 本章要纠两个到处流传的说法：① 「接受率 95%、猜 4 个 = 平均接受 3.8 个」——**错**，串行依赖下正确值是 **4.52**（§8.2.2）；② 「验证 5 个 token 和验证 1 个一样贵」——**只在小 batch 下成立**，batch 越过约 60 之后验证成本线性上涨，加速比会塌（§8.6.1）。

## 8.0 本章的固定配置

全章用同一套数字，任何一行都能自己验算。和 [03 章 §3.2](03-Prefill与Decode两阶段.md) 完全一致，这样两章的表能直接对照。

| 量 | 值 | 说明 |
|---|---|---|
| 模型 | Llama-3-8B | L = 32 层，KV 头数 8（GQA），head_dim = 128，BF16 |
| **Decode 每步读的权重** | **15.0 GB** | 权重共 16.1 GB，embedding 表每步只查一行，不用整张读 |
| 每 token 每层 KV | 2 × 8 × 128 × 2 字节 = 4 KiB | ★ 公式是 `2 × n_kv_heads × head_dim × 字节数`，⚠️ **不是** `4 × d_model`（[02 章](02-KV-Cache与显存账.md)） |
| 每 token KV（全 32 层） | **128 KiB** | = 4 KiB × 32 |
| 每 token 矩阵乘 FLOP | **0.015 TFLOP** | = 2 × 7.51 e9 |
| ⚠️ 激活值读写（估算） | 约 8.8 MB / token | ⚠️ 量级估算，算子融合做得好会明显更少 |
| 上下文长度 | 512 token | 全章固定 |
| 硬件 | H100 SXM5 | HBM3 **80 GB** / **3.35 TB/s**，BF16 **稠密**峰值 **989 TFLOPS** |
| **屋脊点** | **295 FLOP/Byte** | = 989 ÷ 3.35 |

> ⚠️ 989 是**稠密**峰值。规格表上那个 **1979 TFLOPS 是「带 2:4 稀疏」的**，常规推理算子用不上。拿 1979 去算，屋脊点会变成 591，本章后面每一个「越过屋脊点」的判断都会反过来。
> ⚠️ **GB 和 GiB 差 7%**：权重这类按 10⁹ 报的量写 GB，KV Cache 这类按 2 的幂算出来的量写 KiB / GiB，本章严格区分。

**本章一直在用的五个符号**，先摆在这里，后面每一节都会引用：

| 符号 | 读作 | 含义 | 典型值 |
|---|---|---|---|
| **α** | alpha | **单个** token 的接受率 | 0.6 ~ 0.9 |
| **γ** | gamma | 草稿长度（一轮猜几个） | 3 ~ 5 |
| **E** | — | ★ 一轮**期望产出**的 token 数（**含**末尾那个白送的 bonus token） | 见 §8.2.2 |
| **c** | — | 草稿**单步**耗时 ÷ 目标**单步**耗时 | 0.05 ~ 0.4 |
| **r** | — | ★★ 验证 **γ+1** 个 token 的耗时 ÷ 验证 **1** 个的耗时 | 小 batch ≈ 1，大 batch 会涨到 3 以上 |

```
    ★★★ 本章只有一个总公式，其余全是它的特例：

                          E
        加速比  =  ───────────────
                    γ · c  +  r
                    ↑        ↑
                 草稿的钱   验证的钱

        分子 E  由【接受率】决定  ⟹ §8.2.2
        γ·c    由【草稿多快】决定 ⟹ §8.2.3
        r      由【batch 多大】决定 ⟹ §8.6.1   ★★ 最容易被忽略的一项
```

> 🔑 市面上（包括 [本目录速查表](附-速查表.md)、[大模型算子开发 §9.6.3](../../大模型算子开发/09-推理侧算子.md)）常见的那个式子 `(1 − α^(γ+1)) / ((1 − α)(1 + γ·c))`，就是**把 r 默认当成 1** 的版本。**在 batch=1 下它是对的；在生产负载下它是乐观的。** 本章第 8.6 节专门算 r。

## 8.1 这个想法为什么成立——把「几乎免费」算出来

### 8.1.1 先把 Decode 那一步的利用率说清口径

回到 01/03 章那个数字，但这次**必须说清是哪种利用率**：

```
    batch=1、上下文 512 的一步 Decode：

      搬运 = 权重 15.0 GB + KV 512×128 KiB (67 MB) + 激活 8.8 MB
           = 15.076 GB          ⟹ 带宽侧耗时 15.076e9 ÷ 3.35e12 = 4.500 ms
      计算 = 1 × 0.015 TFLOP    ⟹ 算力侧耗时 1.502e10 ÷ 9.89e14 = 0.015 ms

      一步耗时 = max(4.500, 0.015) = ★ 4.50 ms

    ⟹ 【算力】利用率 = 0.015 ÷ 4.500 = 0.34%
    ⟹ 【带宽】利用率 = 按定义就是 100%（我们就是按打满算出来的）
```

> ⚠️ **「Decode 时 GPU 利用率只有 0.3%，太浪费了」这句话必须补口径。** 低的是**算力**利用率，而**带宽**几乎打满。★★ **算力利用率低不是浪费，它就是 Memory Bound（访存受限）的定义**——是物理规律的读数，不是工程失误的读数。
> ⟹ 所以投机解码**不是「把浪费的东西捡回来」**，而是**「在带宽这条已经排满的流水线上，顺便多塞几件活给闲着的算力单元」**。这个区别决定了它什么时候有用、什么时候没用。
> 📖 **Memory Bound / Compute Bound**（访存受限 / 算力受限）——算术强度低于屋脊点叫访存受限（GPU 在等数据），高于屋脊点叫算力受限（GPU 在等自己算完）。

### 8.1.2 ★ 验证 5 个 token 到底贵多少——逐项算

现在问核心问题：**同一步前向，如果喂进去 5 个 token 而不是 1 个，会慢多少？**

| 逐步算（batch = 1，上下文 512） | 普通 Decode（1 个 token） | ★ 投机验证（γ=4，5 个 token） |
|---|---|---|
| ① 这一步的 query token 数 | 1 | **5** |
| ② 读权重 | 15.0 GB | 15.0 GB ← ★★ **一模一样** |
| ③ 读 KV Cache | 512 × 128 KiB = 67.1 MB | 67.1 MB ← ★ **也一模一样**（5 个 query 位置共享同一段 KV） |
| ④ 写 KV Cache | 1 × 128 KiB | 5 × 128 KiB = 0.64 MiB |
| ⑤ ⚠️ 激活读写（8.8 MB/token 估） | 8.8 MB | 44.0 MB ← **只有这一项真的涨了** |
| ⑥ 搬运合计 | **15.076 GB** | **15.111 GB**（+0.23%） |
| ⑦ 矩阵乘 FLOP | 0.015 TFLOP | 0.075 TFLOP（×5） |
| ⑧ 算术强度 I = ⑦ ÷ ⑥ | 1.0 | **5.0** |
| ⑨ 和屋脊点 295 比 | 1.0 ≪ 295 → ❌ 访存受限 | 5.0 ≪ 295 → ❌ **还是访存受限** |
| ⑩ 算力侧耗时 | 0.015 ms | 0.076 ms |
| ⑪ 带宽侧耗时 | **4.500 ms** | **4.511 ms** |
| ⑫ 一步耗时 = max(⑩,⑪) | **4.500 ms** | **4.511 ms** |
| ⑬ **r = ⑫之比** | 1.000 | ★★ **1.002 —— 只贵 0.2%** |

```
    ★★★ 第 ②③ 两行是全章的地基：

       权重那 15.0 GB 是【固定成本】，和这一步算几个 token 完全无关。
       KV 那 67 MB 也是固定的 —— 5 个 query 位置读的是【同一段历史】。

       多喂 4 个 token，只多带了 4 × 8.8 MB = 35 MB 的激活流量，
       占 15.1 GB 的  0.23%。

    ⟹ 于是有了这笔交易：
       用一个【小而快】的东西先猜 γ 个字，
       再用【大模型一次前向】同时验证这 γ 个字对不对。
       ★ 对的部分直接采纳，第一个错的地方就地纠正。
```

> ✅ [大模型算子开发 §9.6.1](../../大模型算子开发/09-推理侧算子.md) 用单个 FFN GEMM 算同一件事，得到 **+0.1%**；本章按整模型算得 **+0.23%**，差在那一项激活读写的估算上。**能确定的是量级：千分之几。**
> ⚠️ 原稿这里写的是「≈ 1.05 T」，也就是 +5%。那个数**偏大了 20 倍**——它把「验证变贵」的量级说错了，会让人以为草稿开销和验证开销是同一个量级的东西（在小 batch 下完全不是）。

### 8.1.3 ⚠️ 「几乎免费」是有有效期的

第 ⑨ 行那个「还是访存受限」，是上面整笔交易成立的**唯一前提**。它什么时候失效？

```
    ★ 验证步的算术强度，随 batch 增长会怎么走：

        I_验证(B) = B × 5 × 0.015e12
                    ─────────────────────────────
                    15.0e9 + B×67.1e6 + B×5×8.8e6

        B →   1  ⟹    5.0      ❌ 访存
        B →  64  ⟹  217        ❌ 访存
        B → 105  ⟹  295        ★★ 撞上屋脊点
        B → 512  ⟹  535        ✅ 算力受限 —— 验证不再免费
        B →  ∞   ⟹  676（渐近上限）

    ⚠️ 对照：【普通】Decode 的算术强度渐近到 198，【永远】越不过 295。
       ⟹ ★★ 换句话说，投机解码正是那个把 Decode 推过屋脊点的东西，
          而一旦推过去，它自己赖以成立的前提就没了。
```

> 🔑 **这是本章最重要的一句话，先放在这里，§8.6 再把账算完**：投机解码的物理基础是「Decode 访存受限、算力空闲」。**它做的事情恰恰是消耗算力**——所以它天生会走到自己的反面。batch 越大，走得越快。

## 8.2 一次投机解码长什么样，以及它到底能快多少

### 8.2.1 先走一遍流程

```
    当前已生成："杭州是浙江省的"          草稿长度 γ = 4

    ① 草稿阶段（draft）：小模型【自回归】跑 4 步
       猜出："省" "会" "，" "位"
       ★ 每一步都要一次小模型前向 —— 注意这 4 步是【串行】的，
         因为第 2 个字要在「第 1 个字是省」的前提下才猜得出来。
         ★★ 记住这句，§8.2.2 整节都是它的后果。

    ② 验证阶段（verify）：★ 大模型【一次】前向，
       把 "杭州是浙江省的" + ["省","会","，","位"] 一起喂进去
       ⟹ 拿到大模型在【5 个位置】本来会输出什么
         （4 个草稿位置 + 1 个「草稿全对的话，下一个该是什么」的位置）
       ★ causal mask 保证第 i 个位置只看得见它前面的，所以 5 个分布一次算完

       位置1：大模型也想输出「省」     ✅ 接受
       位置2：大模型也想输出「会」     ✅ 接受
       位置3：大模型想输出「城」，草稿是「，」   ❌ 拒绝
       位置4：★ 不用看了，前面已经错了，后面全作废

    ③ 收尾：把被拒的位置 3、4 的 KV Cache【回滚】掉

    ④ 结果：这一次大模型前向，产出了 【"省" "会" "城"】 3 个 token
       （2 个接受 + 1 个用大模型自己的输出【就地纠正】）
       ★★ 第 3 个是白送的 —— 拒绝的那一刻顺手就拿到了正确答案
```

```
    ⟹ 原本要 3 次大模型前向，现在 1 次搞定。

    ⚠️ 但【别急着说「加速 3 倍」】。3 是这一轮的【毛产出】，不是加速比：
       ① 小模型那 4 步也花了钱          ⟹ 分母里的 γ·c
       ② 验证那一次比普通一步略贵        ⟹ 分母里的 r
       ③ 这只是【运气好的一轮】，要算的是【期望】 ⟹ 分子 E

    ⟹ 三件事分别在 §8.2.2（E）、§8.2.3（c）、§8.6.1（r）里算。
```

> 📌 ✅ 论文 arXiv 2211.17192（`papers/Speculative-Decoding-arXiv-2211.17192.pdf`），Google，2022。
> 论文最重要的贡献**不是**这个想法，而是**证明了第 ② ④ 步在数学上是无损的**——见 §8.3。

### 8.2.2 ⚠️ 期望产出不是 α × γ——这是全篇最高频的错

> ❓ 「接受率 95%，一次猜 4 个，那平均接受 0.95 × 4 = 3.8 个。」
> **错。正确值是 4.52。** 而且**接受率越低，这个错法错得越离谱**。

**错在哪**：

```
    ★★ 草稿 token 是【串行依赖】的。

       t₂ 是在「t₁ 已经被接受」这个前提下生成的。
       一旦 t₁ 被拒，t₂ t₃ t₄ 【就算内容碰巧是对的，也全部作废】
       —— 因为它们建立在一个已经被推翻的前缀上。

    ⟹ 所以不是「4 个各自独立地以 0.95 通过」，
       而是「一条链，从头走，第一次失败就停」。
    ⟹ 这是【几何分布】，不是【二项分布】。
```

**正确的公式**（设每个位置独立地以概率 α 被接受，草稿长度 γ）：

```
                 1 − α^(γ+1)
        E   =   ─────────────          ★ 含末尾那个白送的 bonus token
                    1 − α

    ★ 它就是等比数列求和：E = 1 + α + α² + … + α^γ
      第 k 项 α^k 的含义 = 「前 k 个全被接受」的概率
      （第 0 项那个 1 = 无论如何都会有的那个 bonus token）
```

**用 γ = 1 手算验证一遍**（最容易验的一档）：

```
    公式给出：(1 − α²) / (1 − α) = 1 + α

    直接数一遍所有情况：
      草稿被拒（概率 1−α） ⟹ 大模型就地出 1 个     ⟹ 产出 1
      草稿被收（概率 α）   ⟹ 草稿 1 个 + bonus 1 个 ⟹ 产出 2

      期望 = (1−α)×1 + α×2 = 1 − α + 2α = 1 + α     ✅ 对上了
```

**γ = 4 时，两种算法差多少**：

| 接受率 α | ✗ 线性 `α×γ` | ✗ 线性 `α×γ+1` | ✅ 正确 `(1−α⁵)/(1−α)` | 线性版高估 | 🔑 天花板 `1/(1−α)` |
|---|---|---|---|---|---|
| 0.95 | 3.80 | 4.80 | **4.52** | +6% | 20.0 |
| 0.90 | 3.60 | 4.60 | **4.10** | +12% | 10.0 |
| 0.80 | 3.20 | 4.20 | **3.36** | +25% | 5.0 |
| 0.70 | 2.80 | 3.80 | **2.77** | +37% | 3.3 |
| 0.60 | 2.40 | 3.40 | **2.31** | +47% | 2.5 |
| 0.50 | 2.00 | 3.00 | **1.94** | **+55%** | 2.0 |
| 0.30 | 1.20 | 2.20 | **1.43** | +54% | 1.4 |

> ★ **注意两种线性错法方向相反**：忘了 bonus token 的 `α×γ`（3.80）**偏小**，记得 bonus 的 `α×γ+1`（4.80）**偏大**，真值 4.52 夹在中间。**两个都别用。**
> ⚠️ **真实场景的 α 大多落在 0.6~0.9 这一带**，正是线性算法开始明显失真的区间（高估 12%~47%）。

**🔑 最有用的一个推论：天花板 `1 / (1 − α)`**

```
    γ → ∞ 时，E → 1 / (1 − α)      ★ 这是【任凭你猜多长】都突破不了的上限

       α = 0.50 ⟹ 最多 2.0 个/轮      ⟹ 加速比天花板 2×
       α = 0.80 ⟹ 最多 5.0 个/轮
       α = 0.90 ⟹ 最多 10.0 个/轮
       α = 0.95 ⟹ 最多 20.0 个/轮

    ★★ 所以 γ 加得再大也没用 —— 逐 γ 看 α=0.8 这一行就明白：
       γ  =  1     2     3     4     5     6     8    12    ∞
       E  = 1.80  2.44  2.95  3.36  3.69  3.95  4.33  4.73  5.00
                                      ↑ 到这里已经吃掉天花板的 74%
                                      再往后每加一个 γ，收益都在缩水
```

> ⚠️ **别把 E 当成「实测接受长度」直接套**。✅ arXiv 2601.11580（*Speculative Decoding: Performance or Illusion?*）的实测结论是：**接受长度在 token 位置之间、请求之间、数据集之间剧烈波动**，用一个全局平均 α 代入公式只能得到一个**乐观的量级估计**。论文自己的例子：InstructCoder / BS=1 / n-gram，**理论上限 2.75×，实测只有 2.1×**。

### 8.2.3 加速比：把草稿的钱和验证的钱都算进去

产出多了，但每一轮也多花了草稿模型的钱。把 §8.0 那个总公式展开：

```
    每轮成本（以「一次普通 Decode 步」为单位）
        = γ · c        ← 草稿模型跑 γ 步
        + r            ← 目标模型验证一次（§8.1.2 算过，小 batch 下 r ≈ 1.00）

                     E            (1 − α^(γ+1)) ÷ (1 − α)
    加速比  =  ───────────  =  ──────────────────────────
                γ·c + r                 γ·c + r
```

**📖 c 怎么估**：两个模型都是访存受限，所以 `c ≈ 两个模型的权重字节数之比`——**理论上**是这样。⚠️ **实测比这个悲观得多**：

| 配置 | 权重比（理论 c） | ✅ 实测 c（arXiv 2601.11580） | 差多少 |
|---|---|---|---|
| Llama3-70B 配 Llama3.2-1B | ⚠️ 约 1.8%（推断） | **12.5%** | ★ 差约 7 倍 |
| Qwen3-8B 配 Qwen3-0.6B | ⚠️ 约 7.5%（推断） | **37.5%** | ★ 差约 5 倍 |

> ★ **为什么实测的 c 这么差**：小模型的一步前向，权重是少了，但 **kernel 的个数一个都没少**。当每个 kernel 都小到「GPU 还没热身就跑完了」，瓶颈就从带宽转成了 CPU 下发和 kernel 启动延迟——**它不再按权重比缩放了**。这也是为什么框架要给草稿模型单独上 CUDA Graph（[12 章](12-CUDA-Graph与图编译.md)），SGLang 甚至专门写了 `eagle_draft_cuda_graph_runner.py`。
> ⚠️ 顺带纠一个常见算法：**kernel 启动开销不能「3 µs × 200 个 = 0.6 ms」这样串行相加**——下发是流水化的（CPU 派发第 n+1 个时 GPU 正在跑第 n 个）。真正的症状是 nsys 时间线上 **kernel 之间出现大片空白**。
> ⚠️ 上表「权重比」一列是我按常见模型尺寸推算的，**不是论文给的**；论文给的是 c 那一列。

**代入 γ = 4、c = 0.1、r = 1.0（batch=1）**，每轮成本 = 0.4 + 1.0 = **1.4**：

| 接受率 α | 每轮产出 E | **加速比** | 评价 |
|---|---|---|---|
| 0.95 | 4.52 | **3.23×** | 同源蒸馏草稿 + 简单任务 |
| 0.90 | 4.10 | **2.93×** | 很好 |
| 0.80 | 3.36 | **2.40×** | ★ 典型好情况 |
| 0.70 | 2.77 | **1.98×** | ★ 典型一般情况 |
| 0.60 | 2.31 | **1.65×** | 还行 |
| 0.50 | 1.94 | **1.38×** | 勉强 |
| **0.29** | **1.40** | **1.00×** | ★★ **盈亏平衡点** |
| 0.30 | 1.43 | 1.02× | 白忙一场 |
| 0.20 | 1.25 | **0.89×** | ❌ **比不开还慢** |

```
    ★ 盈亏平衡点怎么来的：要求  E > γ·c + r

       γ=4、c=0.1、r=1  ⟹  要求 E > 1.4
       解 (1 − α⁵)/(1 − α) = 1.4  ⟹  ★ α* ≈ 0.29

    ⟹ 接受率低于 29%，投机解码是【净亏损】：
       花了草稿的钱，产出还不如不猜。
```

> 🔑 **盈亏平衡点是可以自己算的，而且它会随负载移动。** 上面这个 0.29 是**小 batch**（r=1）下的值。§8.6.1 会看到：r 一涨，这条红线就往上抬——**同一个草稿模型、同一个接受率，在低并发下赚钱，在高并发下亏钱。**

### 8.2.4 最优 γ 不是固定的，它随接受率走

γ 有两股方向相反的力：**γ 越大，一轮可能吐更多字（E 涨，但边际递减）；γ 越大，草稿本身越贵（γ·c 线性涨）**。所以存在最优 γ：

**加速比随 γ 的变化（c = 0.1、r = 1）**：

| γ | α = 0.5 | α = 0.8 | α = 0.9 |
|---|---|---|---|
| 1 | 1.36× | 1.64× | 1.73× |
| 2 | ★ **1.46×** 最优 | 2.03× | 2.26× |
| 3 | 1.44× | 2.27× | 2.65× |
| 4 | 1.38× | 2.40× | 2.93× |
| 6 | 1.24× | ★ **2.47×** 最优 | 3.26× |
| 8 | 1.11× | 2.40× | 3.40× |
| 10 | 1.00× | 2.29× | ★ **3.43×** 最优 |

```
    ★★ 一句话读这张表：【接受率越高，越值得多猜几个】。

       α = 0.5 ⟹ 猜 2 个就到头，猜 4 个反而不如猜 2 个
       α = 0.8 ⟹ 最优在 6 附近，而且 3~8 这一段很平（2.27 ~ 2.47），
                  ⟹ 🔑 γ 选在平台区就行，不必精调
       α = 0.9 ⟹ 一口气猜 10 个都还在涨

    ⚠️ 而 α 是【随任务、随请求、随 token 位置变的】（§8.2.2 末尾那条实测）。
    ⟹ ★ 固定一个 γ 到处用，是把好场景和坏场景【一起做砸】的办法。
    ⟹ 这就是框架里「自适应投机」存在的理由（§8.6.2）。
```

## 8.3 ★ 为什么是「无损」的——这一点最容易被误解

> ❓ 常见误解："用小模型猜，输出质量肯定会降。"
> **不会。投机解码的输出分布和不用它【完全一致】。**

### 先说清「无损」到底指什么

```
    ❌ 无损 ≠ 每次生成的文本【逐字一样】
    ✅ 无损 = 输出的【概率分布】一样
```

举个例子：大模型在某个位置本来会给出 `"好" 60%  "热" 30%  "冷" 10%`。**无损保证的是：开了投机解码之后，这个位置吐出各个字的概率还是精确的 60/30/10。** 你跑一万次，统计频率对得上；但具体某一次吐哪个字，可能和不开时不同。

### ★★ 秘密在两步：一步「删」，一步「补」

关键在**拒绝时怎么处理**，论文给出的是一个精确的采样算法：

```
    设：大模型（目标）的概率是 p(x)，小模型（草稿）的是 q(x)，草稿猜的是 x̂

    【第一步 · 删】接受判据
       ★ 若 p(x̂) ≥ q(x̂)：  直接接受
       ★ 若 p(x̂) < q(x̂)：  以概率 p(x̂)/q(x̂) 接受
                            （小模型比大模型更爱这个词，就按比例打折）

    【第二步 · 补】拒绝后的重采样        ★★★ 全部魔法都在这里
       一旦拒绝，【不是】丢掉重来，而是由【大模型自己】
       从修正后的分布 norm(max(0, p − q)) 里重新采一个

    ⟹ ★★ 数学上可以证明：最终采出来的 token，
       服从的分布【严格等于】p —— 也就是大模型本来的分布。
```

> 🔑 **一句话抓住它**：**第一步负责【删】**——压掉小模型过度偏爱的词；**第二步负责【补】**——把被压掉的概率质量精确地还回去。
> **删完必须补，否则分布不守恒。** 记住这句，下面的「有损验证」就是一句话能说清的事了。

```
    ⟹ 这意味着：
       ✅ 小模型再烂，也【不会降低质量】，只会降低加速比
       ✅ 所以草稿模型可以大胆用最快的，甚至用 n-gram 查表
       ⚠️ 但注意：这是【分布相同】，不是【逐 token 相同】。
          开了投机解码后，同样的随机种子可能生成不同的具体文本。
          ★ 做回归测试时这一点会咬人。
```

> 🔑 **顺手记一个数**，§8.7 会直接用到它：**在这套规则下，单个草稿 token 的接受率恰好等于 `α = 1 − TVD(q, p)`**。
> 📖 **TVD**（**T**otal **V**ariation **D**istance，总变差距离）——衡量两个概率分布「有多不一样」的一把尺子，**0 = 完全相同，1 = 完全不搭界**。
> ⟹ 也就是说，§8.2 那些表里的 α **不是玄学，是有闭式公式可算的**：草稿分布和目标分布越像，α 越高。

### ⚠️ 2026 更新：市面上开始出现【有损验证】了

> ✅ 论文：*Revisiting Lossy Verification in Speculative Decoding: Mechanisms, Trade-offs, and Failure Modes*（arXiv 2607.26627，2026-07-29）

上面那套无损保证**是可以被放弃的**——已经有一批方法为了速度放松严格的分布匹配。

> 🔑 **用上面的框架一句话概括：有损验证 = 把【第二步】拆掉或改掉。**

论文的措辞很重：这会**悄悄改写解码分布**（silently rewrites）。⚠️ **「悄悄」是重点**——不报错、不告警，你只会发现分数莫名其妙低了一点。

> ✅ 论文把它们归成两类，并指出**彼此差异「大多是表面的」**（本质是同一个病）。

#### ① 截断式验证：过滤 ≠ 纠正比例

**做法**：不再算 `p/q` 的比值，改成先划一条线圈出「**允许集合**」（目标模型认为合理的那批词），草稿猜的词**只要落进集合里就放行**。

```
    ✅ Medusa 的 typical acceptance ── 允许集合来自 η-sampling（按熵动态定门槛线）
    ✅ SpecCascade                  ── 允许集合来自 min-p sampling（门槛 = 最高概率 × 某比例）
```

> 📌 这两个本来都是正经的**截断采样**，用途是「把长尾烂词砍掉」，是个好东西。
> **问题不在截断本身，在于拿它当【验证判据】。**

**★★ 陷阱在这**：拒绝的直接丢弃、**不做第二步重采样**——正好丢掉了上面那个「补」的步骤。

```
    它【想要】的是「截断后的【目标】分布」   p(x) / Z(p)
    它【实际产出】的是「截断后的【草稿】分布」q(x) / Z(q)
                                              ↑↑ 换成 q 了
```

> 📖 `Z` 是**归一化常数**：砍掉一部分词之后，剩下的概率加起来不到 1，要除以剩余总和把它拉回 1。

**为什么会变成 q？——因为过滤只能删掉不合格的选项，删不掉合格选项之间的错误比例。** 一个具体例子：

```
    假设词表只有 A / B / C 三个词

    大模型 p ：  A 0.6    B 0.3    C 0.1
    小模型 q ：  A 0.2    B 0.7    C 0.1
    允许集合 ： {A, B}                       （C 被截断掉了）

    ✅ 你【想要】的  = p 在 {A,B} 上归一化   → A 66.7%   B 33.3%
    ❌ 你【实际得到】= 草稿抽 A 的概率 0.2、抽 B 的 0.7，
                       C 被拒了就丢掉不算    → A 22.2%   B 77.8%
                                                ↑↑ A 和 B 的主次【完全颠倒了】
```

> 门卫只查「你有没有资格进门」，不管「进门的人里各类人占多少比例」——**而比例恰恰就是分布的全部内容。**
>
> ⟹ ✅ 论文原话：输出「**像草稿模型，而不像目标分布**」。
> ⚠️ 说白了：**你花大钱部署 72B，实际拿到的是接近小模型的输出质量。**

#### ② 协作式验证：干脆承认掺水

**做法**：不装了，直接把两个分布按比例混起来。

```
    实际产出 = λ·p(x) + (1−λ)·q(x)     ← 凸组合（加权平均，两个权重加起来 = 1）

       λ = 1   → 纯目标模型（等价无损）
       λ 越小  → 掺的草稿越多，越快，也越偏

    ✅ CoS（固定混合系数 λ）、lenience 宽容度（λ 自适应调整）
```

> 📌 这一类至少是**诚实的**——λ 明摆着是个旋钮，你知道自己在拿质量换速度。
> ⚠️ **截断式的真正问题在于它【看起来像无损】。**

#### ✅ 质量掉多少（Qwen2.5-72B / LLaMA-3.1-8B 实测）

```
    ★ 在标准投机解码下（单草稿、一条链）：
      还好，和配对基线差距 ≤ 1.4 分

    ★★ 但一上 EAGLE-3（树形/多草稿），差距炸开：
       typical acceptance 的平均分差   −0.32  ⟶  【−6.32】
                          INCLUDE 上          【−8.8】
       ⚠️ 甚至【低于 EAGLE-3 自己的基线】：MATH 69.84 vs 73.20
          ⟹ 本来是为了加速，结果【速度和质量一起亏】
```

> 📖 **配对基线**（paired baseline）= 用**同样的截断设置**、但走**无损**验证的对照组。
> 必须这样比，才能把「截断本身的好处」和「有损验证的代价」分开——见下面的建议 ①。

**★ 为什么树形上更糟（✅ 论文 Lemma 2）**

> 📖 **KL 散度**（Kullback-Leibler divergence，相对熵）：和上面的 TVD 一样，是衡量「两个概率分布差多远」的一把尺子，**0 = 完全相同**，越大差得越远。这里用它量「实际输出分布」和「本该的目标分布」之间的失真。

```
    标准 SD  ：草稿越训越好（q → p）时，KL → 0
               ⟹ ✅ 失真是【可以消掉的】，把草稿练好就有回报

    EAGLE-3 ：KL 收敛到一个【正的常数】
               ⟹ ⚠️ 存在一条【地板】，草稿再完美，失真也消不掉
```

> ⚠️ **我的直觉理解**（论文给的是定理，这层解释是我的推断）：树形一次摆出多个候选、「谁先通过就用谁」，这本身是一种 **best-of-n 式的挑选**，会系统性地放大草稿的偏好——而这个放大效应跟「草稿准不准」无关，所以 `q = p` 了它也还在。

**★★★ 最阴险的一点：任务越难，坑越深**

```
    无损 vs 截断式的差距
       GSM8K（小学数学应用题）   +0.38pp
       AIME （竞赛数学）        【+6.67pp】     ← 17 倍
```

> 📖 **pp = percentage point，百分点**（绝对差值，不是相对比例）。
>
> ⚠️ **这才是真正要命的地方**：你在 GSM8K 上测，看到 0.38 个百分点，结论是「几乎无损，上线吧」——**但你的用户在做难题时，实际掉的是 6.67 个百分点。**
> ★ **为什么**：难题的正确答案往往依赖那些概率不高但关键的 token，而分布被拉向草稿模型时，恰恰就是这些 token 最先被牺牲掉。
> ⟹ **拿 GSM8K 测是【测不出来】的。**

#### 🔑 ✅ 论文给选型的三条

| | 建议 | 为什么 |
|---|---|---|
| ① | **别拿默认解码当基线**，要和**分布匹配的配对基线**比 | 否则「截断本身的好处」和「验证方案的代价」混在一起互相抵消，你会得到一个假的「没掉分」结论 |
| ② | **树形 / EAGLE-3 上不要用截断式验证** | 失真不随草稿变好而消失（有地板），换来的块效率提升**根本不抵** |
| ③ | ★ **真想要截断的好处，就直接对目标模型做截断，再用无损验证** | 顺序换一下即可：先让**大模型自己**截断出想要的分布，再对它走标准的两步无损验证。✅ 实测这样做**全程不低于 EAGLE-3 基线** |

> ★★ **第 ③ 条是最实用的结论**：你想要的「砍掉长尾烂词」这个好处，**根本不需要牺牲无损性**——把截断放在目标模型这一侧就行了。
> ⟹ **有损验证是一笔不必要的交易。**

> 🔑 **本节一句话**：无损投机解码 = **删 + 补**两步；有损验证省掉了「补」，于是输出**悄悄从「大模型的分布」滑向「小模型的分布」**——链式投机上滑一点点，树形投机上滑很多，而且**简单任务上你完全看不出来**。

## 8.4 草稿从哪来——六种流派

六种流派各自在 §8.0 那个公式里动不同的项：有的提 **α**（猜得准），有的压 **c**（猜得快），有的两个一起动。**先看完六种，§8.4 末尾有一张横向对照表。**

### ① 独立小模型（draft model）

```
    用同系列的小模型，比如 Llama-3-70B 配 Llama-3.2-1B
    ✅ 优点：接受率高（同源，分布接近），✅ 实测 α ≈ 0.75
    ✅ 优点：零训练成本 —— 现成的模型，拿来就用
    ⚠️ 缺点一：★ 要额外占一份显存（1B BF16 ≈ 2.0 GB），还要额外维护一个模型
    ⚠️ 缺点二：★★ c 最大的一类（实测 12.5% ~ 37.5%，见 §8.2.3）
              ⟹ 目标模型越小，这条路越不划算
```

### ② Medusa：给大模型加几个「多头」

> ✅ 论文 arXiv 2401.10774（`papers/Medusa-Multiple-Decoding-Heads-arXiv-2401.10774.pdf`）

```
    ★ 不要独立小模型。直接在大模型最后一层上，
      并排接【几个额外的输出头】：
        头1 预测下一个 token（原本就有）
        头2 预测下下个 token      ← 新增
        头3 预测下下下个 token    ← 新增
        ...
    ⟹ ★ 一次前向就同时得到了草稿，草稿开销【几乎为零】⟹ c ≈ 0
    ⚠️ 缺点：各个头【互相独立】地预测，不知道彼此猜了什么
            ⟹ 越靠后的头越不准 ⟹ α 沿位置衰减
```

> ⚠️ **「几乎零成本」只是指时间，显存不是零。** 每个 Medusa 头本质上是一份 `lm_head`，而 lm_head 是全模型最大的单张矩阵之一：
> ```
>     Llama-3-8B：d_model 4096 × 词表 128256 × 2 字节 = 1.05 GB / 头
>     接 4 个头 ⟹ 约 4.2 GB
>              ⟹ 占 16.1 GB 模型权重的 【26%】
> ```
> ⚠️ 这个数是我按公式算的（不是论文披露值）。**它意味着 KV Cache 的可用空间要少掉 4 GB，也就是少几万个 token 的并发容量**（[02 章](02-KV-Cache与显存账.md)）——这笔账在选型时经常被漏掉。

### ③ ★ EAGLE：在特征层面做自回归（工业界事实标准）

> ✅ 论文 arXiv 2401.15077（`papers/EAGLE-Speculative-Sampling-arXiv-2401.15077.pdf`）

```
    ★ EAGLE 的洞察：
      Medusa 的问题是各头独立。要让草稿连贯，草稿过程本身就该是自回归的。
      但用完整的小模型又太贵。

    ★★ 折中：只跑【一层】轻量的 Transformer，
       而且它的输入不是 token，是大模型倒数第二层的【隐藏特征】。
       ⟹ 特征比 token 信息量大得多 ⟹ 一层就够
       ⟹ 草稿又快又准，接受率显著高于 Medusa
```

```
    ★ 显存账（Llama-3-8B 口径，⚠️ 我按结构算的估值）：
       一层 decoder（attn 41.9 M + MLP 176.2 M）  = 218 M 参数
       加一个把 2×4096 特征压回 4096 的 fc 层      =  34 M 参数
       合计 252 M × 2 字节                        ≈ ★ 0.50 GB
       ★★ lm_head 是【和目标模型共用】的，不另算  ⟹ 比 Medusa 4 个头省 8 倍
```

```
    ⟹ EAGLE 是现在两个框架都重点支持的方案。
    ✅ vLLM：[eagle.py](../源码/vLLM/vllm/v1/spec_decode/eagle.py)
    ✅ SGLang：speculative/ 目录下有 eagle_info.py、eagle_utils.py、
       eagle_worker_v2.py、multi_layer_eagle_utils.py、
       ★ eagle_draft_cuda_graph_runner.py（专门给草稿模型也上 CUDA Graph，
         就是为了压 §8.2.3 那个「小模型被 kernel 启动拖住」的 c）
       ★ eagle_disaggregation.py（★ 投机解码 + PD 分离的组合，见 [10 章](10-PD分离.md)）
       —— 光 EAGLE 相关就有 8 个文件，可见它的分量
```

### ④ n-gram / 后缀解码：★ 不用模型，直接查表

```
    ★ 观察：很多场景下，要生成的内容【在上文里出现过】
       - 代码补全：变量名反复出现
       - 文档问答/RAG：答案大段照抄原文
       - 多轮对话：复述用户的话

    ⟹ 草稿 = 从已有文本里【查一个匹配的后缀，把它后面的字抄过来】
    ⟹ ★★ 零模型、零显存、零训练，✅ 实测 c 全程 < 2%
    ⚠️ 在自由创作类任务上接受率接近 0，等于白跑

    ✅ vLLM: ngram_proposer.py / ngram_proposer_gpu.py / suffix_decoding.py
    ✅ SGLang: ngram_worker.py / ★ cpp_ngram/（用 C++ 实现以降低查表开销）
```

> 🔑 **n-gram 是 §8.0 公式的一个极端点**：`c ≈ 0`，于是加速比退化成 `E / r`——**只要接受率不是 0，它就几乎稳赚**。所以「代码补全 / RAG 先无脑上 n-gram」是一条没有风险的建议。

### ⑤ MTP：模型自带的多 token 预测

> 📖 **MTP**（**M**ulti-**T**oken **P**rediction，多 token 预测）
> ✅ DeepSeek-V3 技术报告（arXiv 2412.19437 §5.4.3）在**预训练阶段**就加了 MTP 目标

```
    ★ 和 Medusa 像，但 MTP 的头是【预训练时一起训】的，不是事后接的
    ⟹ 质量和一致性都更好
    ⚠️ 代价：★★ 这是【预训练期】的决定，事后加不上
       ⟹ 用别人的开源权重，没有 MTP 头就是没有
    ✅ SGLang: frozen_kv_mtp_worker_v2.py、frozen_kv_mtp_info.py 等
```

**✅ 一手披露的数字，以及一次漂亮的交叉验算**：

```
    ✅ DeepSeek-V3 官方口径（arXiv 2412.19437 §5.4.3）：
         第二个 token 的接受率  α = 85% ~ 90%
         端到端 TPS 提升        ★ 1.8 倍

    ⚠️ 网上流传的「DeepSeek-V3 的 MTP 加速 3 倍」是【错的】。

    ★★ 用 §8.2 的公式反推，看官方那个 1.8 合不合理：
       V3 的 MTP 只多预测【一个】token ⟹ γ = 1
       取 α = 0.875（85~90 的中点）

         E = (1 − α²)/(1 − α) = 1 + α = ★ 1.875
         MTP 头只有一层、和主干共享绝大部分计算 ⟹ c ≈ 0.03
         batch 不大时 r ≈ 1

         加速比 ≈ 1.875 ÷ (1×0.03 + 1) = ★ 1.82×

    ⟹ 🔑 和官方披露的 1.8× 【严丝合缝】。
       ⟹ ① 公式对了；② 1.8 这个数也对了；
       ⟹ ③ ★★ 而且 1.875 是 γ=1 的【绝对上界】—— 3× 在数学上根本不可能。
```

> 📖 **TPS**（**T**okens **P**er **S**econd，每秒 token 数）。
> ★ 这个例子值得记住：**看到任何投机解码的加速比，先用 `E = (1−α^(γ+1))/(1−α)` 算一遍上界。** 超过上界的数字，要么是 γ 比你以为的大，要么就是错的。

### ⑥ ★★ 半自回归：DSpark（2026 年的新流派）

> ✅ 论文：*DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation*
> （arXiv 2607.05147，2026-07-06，DeepSeek-AI × 北京大学，33 位作者，MIT 开源，已部署在 DeepSeek-V4 的服务系统里）
> ✅ 一手源码就在本仓库：`推理框架/源码/vLLM/vllm/v1/worker/gpu/spec_decode/dspark/`

**先看它要解决的两难：**

```
    ★ 全自回归草稿（③ EAGLE 一类）：后面能看到前面 ⟹ α 高
      ⚠️ 但草稿【自己就串行了】⟹ 慢 ⟹ c 大

    ★ 全并行草稿（DFlash 一类）：一次前向出所有位置 ⟹ c 小
      ⚠️ 但位置之间互相不知道对方猜了什么 ⟹ ★★【后缀衰减】⟹ α 沿位置掉

    ⟹ 🔑 两条路各自压住了 §8.0 公式的一项，却把另一项做坏了。
```

✅ **「后缀衰减」实测**（条件接受率：只统计前面都被接受的情况，不受前缀错误连累）：

```
    DFlash  Chat：位置1 0.72  ⟶  位置7 【0.63】   ← 越往后越不准
    DFlash  Code：位置1 0.87  ⟶  位置7 【0.78】

    ★★ 而 EAGLE-3 在 Chat 上【反而上升】：0.53 ⟶ 0.74
       ⟹ 自回归能吃到「前面已经定下来了」这个信息，越往后越确定
       ⟹ ★ 这正是并行草稿丢掉的东西
```

> 📌 ✅ 论文给衰减起的名字叫 **multi-modal collision（多模态碰撞）**：并行位置只能对「所有可能的前驱」求平均，而不是实际采到的那一个。举的例子很传神——把 "of course" 和 "no problem" 平均起来，得到 **"of problem"**。

**DSpark 的折中：主干并行，采样时把依赖补回去**

```
    ① 并行阶段：DFlash 主干【一次前向】⟹ 隐状态 h₁…h_γ + 基础 logits U₁…U_γ
    ② 顺序阶段：★ 逐个采样，每步给基础 logits 加一个偏置 B_k，
                B_k 依赖【前一个实际采到的 token】

    ★★ 关键设计：B_k 按自回归方式分解，保证每个 token 的 softmax 概率【精确】
       ⟹ 于是 8.3 那套拒绝采样照常能用 ⟹ ✅ 仍然【无损】
```

> 📖 **Markov head（马尔可夫头，默认方案）**：只依赖「上一个 token」的一阶偏置 B(x_{k−1}, x_k)，用低秩分解 B = W₁W₂ 实现，✅ 秩 r = 256。叫马尔可夫，就是因为只看前一步。
> ⚠️ 论文也试过 RNN 头（带门控的循环状态），✅ 结论是「只有边际收益」，主要出现在长 γ 上，因复杂度和部署性质被放弃。
> ⚠️ 这里的 `r = 256` 是**矩阵的秩**，和本章那个「验证成本比 r」是两回事，只是论文和本章撞了字母。

✅ **接受长度 τ（每轮平均，含 bonus token）—— 取 Qwen3-8B 一行：**

```
    草稿方案      GSM8K   HumanEval   MT-Bench   Alpaca
    ─────────────────────────────────────────────────────
    Eagle3         5.30      4.33       2.66      2.54
    DFlash         5.33      4.64       3.11      2.98
    ★ DSpark      6.17      5.52       3.72      3.58

    ✅ 宏平均提升（Qwen3-8B）：相对 Eagle3 +26.7%，相对 DFlash +18.4%
    ✅ 深度消融：★★ 2 层的 DSpark 在所有领域【打过 5 层的 DFlash】
```

> ★ **把这些 τ 反推回 α，能感受到量级**：τ = 5.30 意味着（按 §8.2.2 的天花板 `1/(1−α)`）等效 α 至少要 0.8 以上；τ = 6.17 则要 0.84 以上。⚠️ 这是我的反推，论文没直接给 α。

```
    ⚠️⚠️ 一个重要反例，别被「并行胜过自回归」带偏：

    ⟹ ★ 并行草稿的优势【不跨模型家族普适】

## 8.5 树形投机：一次猜多条路

线性草稿只猜一条序列。**树形草稿**同时猜多个分支：

> ✅ SpecInfer 论文 arXiv 2305.09781（`papers/SpecInfer-Tree-Speculative-arXiv-2305.09781.pdf`）

```
                     "杭州是浙江省的"
                      ┌────┴────┐
                    "省"       "首"        ← 两个候选
                   ┌──┴──┐      │
                 "会"   "城"   "府"
                  │
                 "，"

    ★ 一次前向验证【整棵树】，接受最长的那条合法路径
    ⟹ 接受长度显著提高（多条路总有一条对）

    ★ 实现关键：树形注意力掩码（tree attention mask）
      让树上每个节点，只能看见【自己到根的那条路径】，看不见兄弟分支。
      ⟹ 靠一个精心构造的 attention mask 在一次前向里完成
```

> 🔑 **用 §8.0 的公式看树形，它做的事一句话就能说清**：**把分子 E 往上抬，代价是把分母的 r 往上抬。** 线性投机送 γ+1 个 token 去验，树形送 k+1 个（k 是树的节点数，常见 21、63），**r 的涨幅直接和 k 成正比**。

### ⚠️⚠️ 2026 实测泼冷水：树形不是免费的，它在高并发下塌得比线性还快

> ✅ 来源：*Speculative Decoding: Performance or Illusion?*（arXiv 2601.11580，Berkeley，含 Ion Stoica）
> ✅ 环境：SGLang v0.5.9 + FlashInfer，H100 80GB

```
    ★ k=21 的树，Qwen3-8B / GSM8K：
        batch = 1   ⟹ 1.85×（线性只有 1.65×）  ✅ 树确实更好
        ★★ batch = 64 ⟹ 【所有负载、两个模型，全部跌破 1×】
                        而同条件下【线性投机始终 > 1×】

    ★ 看这两个数就明白为什么（k: 1 → 6 → 21）：
        接受长度   2.25  →  2.51  →  2.92    ⟹ E 确实涨了（+30%）
        接受率     0.415 →  0.300 →  0.095   ⟹ ★★ 崩了（−77%）

    ⟹ 树越大，送去验证的 token 数暴涨，而其中【绝大多数是废的】
       低并发时算力空闲、废了也不心疼；★★ 高并发时这就是纯粹的浪费
```

**✅ 用本章的公式把这个「跌破 1×」复算一遍**（Llama-3-8B 口径，⚠️ 按实测效率打折：算力按峰值 60%、带宽按 85% 计）：

| 情形 | 这一步送去验的 token 数 M | 验证步耗时 | 普通 Decode 步耗时 | **r** | E ÷ r 的上界 |
|---|---|---|---|---|---|
| 树 k=21，**batch = 1** | 1 × 22 = 22 | 5.35 ms | 5.29 ms | **1.01** | 2.92 ÷ 1.01 = **2.89×** |
| 树 k=21，**batch = 64** | 64 × 22 = **1408** | **35.7 ms** | 6.97 ms | ★★ **5.12** | 2.92 ÷ 5.12 = ❌ **0.57×** |

```
    ★★ 读这张表的两行：

       batch=1  ：验 22 个和验 1 个几乎一样贵（r=1.01）
                  ⟹ 树是白赚的 —— 上界 2.89×，✅ 实测 1.85×
                  （差的那一截是草稿本身的 γ·c 和树掩码构造开销）

       batch=64 ：M 冲到 1408，早就过了屋脊点，t ∝ M
                  ⟹ r 从 1.01 蹿到 5.12
                  ⟹ ★★★ 就算草稿【完全免费】，0.57 也不可能 > 1
                  ⟹ 和论文实测的「全部跌破 1×」对上了
```

> 🔑 **所以树形投机和 §8.6 的规律是叠加的，不是抵消的**：树形把 `r` 放大了约 k/γ 倍，于是它比线性投机**更早**触到那条不划算的红线。
> ★ 一条可操作的判据：**树的大小 k 应该跟着 batch 反向调。** 低并发用大树，高并发退回线性甚至关掉。这正是下一节「自适应投机」在做的事。

## 8.6 ⚠️ 投机解码什么时候【不该开】

这是最容易踩的坑，务必记住：

```
    ★★★ 投机解码花的是【空闲的算力】。
        batch 大的时候，算力【不空闲】，这笔交易就不成立了。
```

原稿这里只有一张定性的「batch=1 加速 2~3 倍 / batch=256 负收益」的表。**下面把它换成能验算的数。**

### 8.6.1 ★★ 把 r 算出来：验证从「免费」到「主要成本」

用 §8.0 那套配置（Llama-3-8B、H100、上下文 512、γ=4），扫一遍 batch：

| batch B | 普通 Decode 一步 | 投机验证一步（M = 5B） | **r** | 验证步算术强度 | 瓶颈 | **加速比**（α=0.8, c=0.1） |
|---|---|---|---|---|---|---|
| 1 | 4.500 ms | 4.511 ms | **1.002** | 5.0 | ❌ 访存 | **2.40×** |
| 8 | 4.659 ms | 4.743 ms | **1.018** | 37.8 | ❌ 访存 | **2.37×** |
| 32 | 5.203 ms | 5.539 ms | **1.065** | 130 | ❌ 访存 | **2.29×** |
| 64 | 5.928 ms | 6.600 ms | **1.113** | 217 | ❌ 访存 | **2.22×** |
| **≈105** | — | — | — | **295** | ★★ **临界点** | — |
| 128 | 7.378 ms | **9.720 ms** | **1.317** | 329 | ✅ **算力** | **1.96×** |
| 256 | 10.28 ms | **19.44 ms** | **1.891** | 443 | ✅ 算力 | **1.47×** |
| 512 | 16.08 ms | **38.88 ms** | **2.418** | 535 | ✅ 算力 | **1.19×** |

```
    ★★ 这张表的形状，一句话：

       B < 105：验证步还在【访存受限】区，多喂的 token 藏在权重搬运后面
                ⟹ r 几乎不动（1.00 → 1.11），★ 验证【确实是免费的】

       B ≈ 105：验证步的算术强度撞上屋脊点 295
                ⟹ ★★★ 从这里开始，t ∝ M，多喂一个 token 就真的多花一份钱

       B > 105：r 线性上涨 ⟹ 加速比线性下滑

    ⚠️ 注意【普通】Decode 在这张表里【始终没过屋脊点】
       （它的算术强度渐近到 198 < 295，见 §8.1.3）
    ⟹ 🔑 是投机解码自己把这一步推过了屋脊点，然后被自己推过去的那条线反噬。
```

**⚠️ 上表用的是 H100 的理论峰值。按真机效率打折，这条线来得更早：**

```
    取 MFU 60%（算力 593 TFLOPS）、MBU 85%（带宽 2.85 TB/s）
       ⟹ 有效屋脊点 = 593 ÷ 2.85 = 208（不是 295）
       ⟹ ★★ 临界 batch 从 105 掉到 【约 60】

    重算几档（同样 α=0.8, γ=4, c=0.1）：
       B =  64  ⟹ r = 1.16  ⟹ 加速比 2.15×
       B = 128  ⟹ r = 1.87  ⟹ 加速比 1.48×
       B = 256  ⟹ r = 2.68  ⟹ 加速比 1.09×
       B = 384  ⟹ r = 3.14  ⟹ ❌ 0.95×   ← 跌破 1
       B = 512  ⟹ r = 3.43  ⟹ ❌ 0.88×

    ✅ 这个「约 60」和 arXiv 2601.11580 实测「batch=64 上树形全线跌破 1×」
       是同一条线 —— ★ 两个来源互相印证。
```

> ⚠️ MFU 60% / MBU 85% 是**经验量级**（[13 章](13-性能指标与压测.md)），不是实测值；上面两组数的**形状**可信，**具体 batch 数要在你自己的卡和框架上压一遍**。

### 8.6.2 ★★★ 一条可以证明的硬边界：完全算力受限时，投机解码必亏

上面是数值。其实还有一个**一行就能证完**的结论：

```
    ★ 前提：batch 大到验证步【完全算力受限】，此时耗时严格正比于 M

       ⟹ r = M_验证 ÷ M_普通 = (γ+1) × B ÷ B = 【γ + 1】

    ★ 每轮成本 = γ·c + r = γ·c + (γ+1)
    ★ 每轮产出 E ≤ γ + 1        ← ★★ 一轮最多也就 γ 个草稿 + 1 个 bonus

                        E              γ + 1
       加速比 = ───────────────  <  ───────── = 1
                 γ·c + (γ+1)          γ + 1

    ⟹ ★★★ 恒小于 1。和 α 多高、γ 多大、用哪种草稿【统统无关】。
```

> 🔑 **这就是「投机解码是延迟优化，不是吞吐优化」的严格版本。** 它不是经验规律，是算术：**在算力吃满的机器上，任何多算的 token 都要有人付钱，而投机解码产出的 token 数永远不可能超过它送去验的 token 数。**
> ★ 反过来也说明了它为什么在低并发下几乎白赚：那时 `r ≈ 1 ≪ γ+1`，不等式整个反过来。

**顺带把「延迟」和「吞吐」两笔账分开**，它们亏的方式不一样：

```
    ★ 延迟侧（TPOT）：上面那张表就是，加速比随 B 下滑，B 很大时跌破 1

    ★ 吞吐侧：还要额外亏一笔【白烧的 FLOP】
       α = 0.8、γ = 4 ⟹ 每轮喂 5 个位置，平均只产出 3.36 个
       ⟹ ★★ 32.8% 的算力【算了但被丢掉了】

       低并发：这些算力本来就闲着 ⟹ ✅ 白烧不心疼
       高并发：这些算力本来能服务别的请求 ⟹ ❌ 直接从吞吐里扣
```

```
    ⟹ ★ 结论：
       适用：单用户 / 低并发、对 TPOT 敏感的场景（代码补全、交互式对话）
       不适用：高并发批处理服务
```

> ⚠️ 顺带纠一处仓库内的说法：[推理框架总目录](../README.md) 把 08 章描述成「唯一能同时降延迟又提吞吐的技巧」。**按本节的推导，这句话在高并发下是反的**——投机解码在算力受限区**只降吞吐**。（⚠️ 那个文件不在本次改动范围内，此处仅作标注。）

### 8.6.3 所以框架要做「自适应投机」，还要为草稿留位置

```
    ⟹ 框架的应对：按当前 batch 动态调 γ，甚至在高负载时【自动关掉】
       ✅ SGLang: adaptive_spec_params.py、adaptive_runtime_state.py
       ✅ vLLM: spec_decode/dynamic/
```

**另外，调度器要为草稿 token 预留槽位**——这是 [04 章](04-连续批处理与调度.md)那行代码的解释：

```python
# ✅ vLLM scheduler.py:566
num_new_tokens = min(num_new_tokens, token_budget, input_budget - draft_slots)
#                                                  ★ 减掉给草稿 token 预留的槽位
```

```
    ★ 为什么必须预留：验证那一步要把 γ 个草稿 token 也写进 KV Cache，
      被拒的部分再回滚。这笔显存是【真的要先占住】的。

    算一下 γ=4、batch=256 时这笔瞬时开销：
      256 × 5 × 128 KiB = ★ 160 MiB
    ⟹ 绝对值不大，但它是【从 token 预算里扣】的：
       预算 512 的一步，留给草稿 5×B 之后，能塞进来的新 Prefill 块就少了
    ⟹ 🔑 所以开投机解码会【间接抬高 TTFT】—— 这笔账在 §8.6.1 的表里没有体现。
```

### 8.6.4 ★★ 2026 更新：这个决策已经从【batch 粒度】下沉到【token 粒度】

§8.6.1 那张表是**二元**的：看 batch 大小，决定开还是不开、γ 调大还是调小——**整个 batch 共用一个策略**。

✅ DSpark（§8.4 ⑥）证明了更细的做法：**同一个 batch 里，靠谱的草稿送去验，不靠谱的当场砍掉。**

一个很有说服力的旁证是：DeepSeek 生产环境为什么长期卡在 MTP-1（只猜 1 个 token）？

```
    ✅ 论文原话：静态的多 token 草稿（MTP-3 / MTP-5）在高并发下
       会【严格降低】aggregate throughput —— 验证开销过大

    ⟹ ★★ 所以不是「猜多了没用」，而是【静态地猜多】没用
       ⟹ 能动态收缩，才敢把 γ 放大
```

```
    ★ 用 §8.6.2 的不等式看这件事，就很清楚了：
      静态 γ=5 意味着【每个请求都按 γ=5 交 r 的钱】，
      但其中很多请求的草稿早在位置 2 就该被砍掉了 —— 它们交了钱，没买到东西。
    ⟹ 🔑 动态调度做的事，本质是【把 r 只花在 E 还在涨的那些 token 上】。
```

✅ **生产实测的调度行为**（DeepSeek-V4-Flash）：

```
    并发 < ~200  ⟹ 预算从 MTP-1 的【静态 2 个】扩张到【4~6 个】/请求
    并发 ↑       ⟹ 预算【平滑收缩】，而不是啪一下关掉

    ★★ 对比 §8.6.1 那张 batch 表：那是【阶跃】的开关，
       置信度调度是【连续】的旋钮 —— 机制见 §8.7
```

## 8.7 ★★ 2026 新战场：瓶颈搬到了【验证侧】

前面六种流派全都在优化**草稿**（也就是 §8.0 公式的分子 E 和 `γ·c` 那一项）。2026 年一批工作指出：**这个方向的边际收益已经很小了，因为大头根本不在那儿——大头在 r。**

### ✅ 先看时间都花在哪

> ✅ 来源：*Speculative Decoding: Performance or Illusion?*（arXiv 2601.11580）
> ✅ 环境：vLLM v0.10.1.1，H100 80GB，batch 1~512

```
    ★★★ 验证（目标模型前向）占执行时间的 【42% ~ 95%】
         —— 且随模型规模和 batch 增大而上升

    ★ 而草稿侧的开销：
        n-gram                   ⟹ 全程 < 2%
        EAGLE / EAGLE-3          ⟹ BS=1 时 12~20%，BS=512 时【3~7%】
        独立草稿模型（70B 目标）  ⟹ BS=1 时 21%，  BS=512 时【3%】
        拒绝采样本身             ⟹ < 1.7%

    ⟹ 🔑 batch 一大，草稿开销就摊薄到个位数百分比了。
       ★★ 你把草稿再优化一倍，动的是那 3%；验证那 42~95% 一动不动。
```

> ★ 这和 §8.6.1 算出来的 r 是同一件事的两种说法：**batch 越大，`γ·c` 越不重要，`r` 越支配一切。**

### ✅ 理论上限：加速比被一个你想不到的量卡住

```
    ✅ 论文给的式子（就是 §8.0 总公式在 r = 1 时的版本）：

        E(加速比) = (1 − α^(k+1)) / ((1 − α) · (k·c + 1))

       α = 接受率        k = 一次猜的长度（本章别处写作 γ）
       ★★ c = 【草稿一次前向 ÷ 目标一次前向】的时间比

    ⟹ ✅ 论文的关键论断：草稿方法的【绝对速度无关紧要】，
       只有它【相对于目标模型】的耗时才进这个公式。
```

**这解释了一个反直觉的实测现象：**

```
    Llama3-70B 配 Llama3.2-1B  ⟹ c ≈ 12.5%，接受率 75%
    Qwen3-8B   配 Qwen3-0.6B   ⟹ c ≈ 37.5%，接受率 81%  ← 接受率【更高】

    ⚠️ 但小目标模型上，投机解码反而【更不划算】

    ★ 代入 γ=4 算一遍就看得见：
       70B：E(0.75) = 3.05，成本 1 + 4×0.125 = 1.50  ⟹ 2.03×
       8B ：E(0.81) = 3.43，成本 1 + 4×0.375 = 2.50  ⟹ ★ 1.37×
                     ↑ 分子更大            ↑ 分母大得多，被吃掉了

    ⟹ ★★ 目标模型越小，草稿相对越贵，c 越大，分母被 γ·c 拖垮
       ⟹ 🔑 投机解码是【大模型】的游戏 —— 模型越大越赚
```

✅ 而且实测离理论上限还差得远：InstructCoder / BS=1 / n-gram，**实测 2.1× vs 理论上限 2.75×**。

> ⚠️ 论文同时指出**接受长度随 token 位置、随请求、随数据集剧烈变化**——这意味着 §8.2 那些用「一个全局 α」算出来的表，给的是**上界和形状**，不是预测值。**拿它来判断「值不值得试」，不要拿它来承诺 SLA。**

### ★★ DSpark 的置信度调度：验证侧的第一个生产级答案

回到 §8.4 ⑥ 结尾留的那个问题——**哪些猜测值得去验**。

#### 先看它要解决的场景

前面刚说了，验证占执行时间的 42%~95%。**验证的成本取决于「这一步一共送了多少个 token 给目标模型」**——也就是 §8.6.1 那个 M。而在真实服务里，同时有很多个请求：

```
    这一步引擎里有 4 个请求，每个都猜了 5 个 token：

      请求 A：  猜1  猜2  猜3  猜4  猜5
      请求 B：  猜1  猜2  猜3  猜4  猜5
      请求 C：  猜1  猜2  猜3  猜4  猜5
      请求 D：  猜1  猜2  猜3  猜4  猜5
                                        ⟹ 一共 20 个 token 要验

    ⚠️ 但里面很多是【明显没戏】的猜测：
       验它们要花钱，几乎肯定被拒，白花。
```

> 🔑 **DSpark 的问题**：既然验证这么贵，**能不能只挑最有希望的那些去验？**
> ★ 注意这跟前六种流派完全不是一回事——它**不改进草稿模型**（不动 α，不动 c），它只决定「这一步验哪些」（动 M，也就是动 r）。

#### 三步走

**① 训一个「置信度头」，预测每个猜测能不能活下来**

```
    在草稿模型上挂一个小头，给每个位置输出一个数 c_k ∈ (0,1)

    ✅ 它的语义：假设前面几个都被接受了，【这一个】能被接受的概率
       （所以叫「条件」概率——不算前面已经死掉的情况）

    ⚠️ 这个 c_k 和 §8.0 那个「草稿÷目标耗时比 c」是两回事，只是论文撞了字母。
```

这个头**怎么训**？妙就妙在，「一个草稿 token 被接受的概率」有**现成的闭式公式**，不用去实测——就是 §8.3 末尾记下的那条：

```
    ✅ c_k* = 1 − ½‖p_k^draft − p_k^target‖₁
                    ↑ 这一坨就是【总变差距离】TVD
```

> **所以这条公式读起来非常直白**：
> ```
>     草稿分布和目标分布【越像】 ⟹ 距离越小 ⟹ 接受概率越高
>     两者完全一样             ⟹ 距离 0    ⟹ 接受概率 100%
> ```
> ★ 这正是 §8.3 那套拒绝采样规则的一个**数学副产品**——接受率恰好等于 `1 − TVD`。所以 ✅ 论文管它叫**「解析的」逐步接受率**：有公式可算，不需要跑一遍看看。

```
    ✅ 训练方式：拿 c_k* 当【软标签】做二元交叉熵
    ✅ 位置加权 w_k = exp(−(k−1)/γ)     ← 越靠前的位置权重越大
```

> ★ **为什么靠前的位置更重要**：位置 1 要是猜错了，后面 2~5 全部作废。**前面的错误代价大得多，所以要优先预测准。** γ 控制衰减快慢。
> ⟹ 这正是 §8.2.2 那个「串行依赖」在调度层的回响：**同一个几何链条，既决定了 E 的公式，也决定了这里的权重形状。**

**② 累乘出「前缀存活概率」**

单个位置的 `c_k` 是「**假设前面都活着**」的条件概率。可实际上我们关心的是「**这个位置到底能不能被用上**」——那得前面每一个都活着才行。条件概率连乘就得到它：

```
    a_{r,j} = c_{r,1} × c_{r,2} × … × c_{r,j}      ← 请求 r 的第 j 个位置

    举例（c = 0.9, 0.8, 0.7, 0.6, 0.5）：
      位置1  0.9
      位置2  0.9×0.8            = 0.72
      位置3  0.9×0.8×0.7        = 0.504
      位置4  0.9×0.8×0.7×0.6    = 0.302
      位置5  0.9×…×0.5          = 0.151
                                  ↑ 只有 15% 的概率能用上，却要花和位置1一样的验证成本
```

> ★ **这就是 §8.2.2 那个几何求和的逐请求版本**：把上面这一列加起来（0.9+0.72+0.504+0.302+0.151 = 2.58），再加上必得的 bonus token，就是这个请求这一轮的期望产出。**α 恒定时它退化成 `(1−α^(γ+1))/(1−α)`；α 逐位置变化时，只能这样一项项乘。**

**③ 把所有请求的所有位置混在一起排序，取 top-k**

```
    A位1 0.90 │ B位1 0.85 │ A位2 0.72 │ C位1 0.70 │ B位2 0.61 │ A位3 0.50 │ …
    └────────── 预算 B 个，就从左往右取 B 个 ──────────┘

    ⟹ 结果自然就是「A 验 3 个、B 验 2 个、C 验 1 个、D 一个都不验」这种
       ★ 预算被【按希望大小】分给了不同请求，而不是每个请求平均分
```

#### ★ 这里有个很漂亮的性质，让上面第 ③ 步几乎不要钱

先说**为什么这事本来该很难**：

```
    ⚠️ 每个请求选出来的位置【必须是从头连续的一段】

       ✅ 合法：验 位置1、2、3
       ❌ 非法：验 位置1、5     ← 位置 5 的内容是建立在 2、3、4 之上的，
                                  跳过它们，位置 5 根本无从验起

    ⟹ 于是这看起来是个【带约束的分配问题】，通常要专门解一下。
```

**但实际上根本不用**——因为存活概率是**累乘**出来的，而乘的每个数都 ≤ 1：

```
    a_{r,1} ≥ a_{r,2} ≥ a_{r,3} ≥ …          ★ 沿位置【只会单调递减】

    ⟹ 你只要选中了「A 的位置 3」，那 A 的位置 1、2 的分数【必然更高】，
       ⟹ 它们【一定】也已经在 top-k 里了
    ⟹ ★★ 全局 top-k 的结果，天然就是每个请求取一段前缀，不可能非法
```

> ✅ 你本地那份 vLLM 源码的文档串直接点破了这一点：
> `vllm/v1/worker/gpu/spec_decode/adaptive_verification.py`
> *"Survival only decreases along a request, so a global top-k always admits continuously along steps with a request."*

```
    ⟹ ★★ 于是「全局最优分配」用【一次排序 + 取前 B 个】就做完了，
       不需要任何额外约束、不需要解规划 —— 工程上极便宜。
```

#### ★★ 它优化的目标不是接受率，是吞吐

**这是最容易被忽略、但最有价值的一处设计。** 一个自然的想法是「让接受率最高」，但那是错的目标——**验得越多，接受的绝对数量越多，但每一步也越慢。** 真正该最大化的是两者的乘积：

```
    ✅ Θ = τ · SPS(B)

       τ      = 这一步【期望能接受】的 token 数        ⟹ 「每步产出多少 token」
       SPS(B) = 送 B 个 token 去验时，引擎每秒能跑几步  ⟹ 「每秒能跑多少步」
                ★ 这是【离线压测】出来的引擎吞吐曲线，不是算出来的

       ⟹ 两者相乘 = 每秒产出多少 token = 吞吐
```

```
    B 调大  ⟹ τ 上升（验得多，接受得多）
            ⚠️ 但 SPS(B) 下降（每步更重，跑得更慢）
    ⟹ ★ 存在一个最优的 B，Θ 就是用来找它的
```

> ★★ **注意 Θ 就是 §8.0 那个加速比公式的「实测版」**：`τ` 对应分子 E，`1/SPS(B)` 对应分母里的 r。**区别在于——本章的 r 是我按屋顶线算出来的，DSpark 的 `SPS(B)` 是压测出来的。** 后者把 kernel 分块、CUDA Graph、调度抖动这些算不出来的东西全都包进去了。
> ⟹ ★ 这是「算法」和「服务系统」真正耦合在一起的地方：**换一张卡、换一个框架版本，这条曲线就得重新压测**（怎么压见 [13 章 §13.4](13-性能指标与压测.md)）。

#### ⚠️ 落地踩的两个坑（这段最值得工程同学看）

```
    ⚠️ 坑一：真实的 SPS(B) 是【阶梯状】的，不是一条光滑曲线
             ⟹ GPU kernel 按固定块大小切分，B 从 128 变 129 可能直接掉一个台阶
             ⟹ ★ 这也正是 §8.6.1 那张理论表和真机对不齐的原因之一

    ⚠️ 坑二：每步选出来的 token 数都在变，和【CUDA Graph 重放】直接冲突（见 [12 章](12-CUDA-Graph与图编译.md)）
             📖 CUDA Graph 把 kernel 调用序列【录制】成一张固定的图来省派发开销，
                但它要求【张量形状固定】。每步 B 都变 ⟹ 图没法重放 ⟹ 优化全废
```

**✅ 解法：让调度器【异步】跑，和主流程错开两步**

```
    容量上限 K      ← 用【两步之前】的置信度估出来（滞后，但形状可以提前定死）
    当前这批 token  ← 仍按【最新】的累乘置信度排序（动态 top-K，实时）

    ⟹ 「验几个」提前定好 ⟹ 形状稳定 ⟹ CUDA Graph 能用
    ⟹ 「验哪几个」实时决定 ⟹ 不损失调度质量
```

> ★★ **精妙之处**：这个「两步滞后」顺手还解决了一个**正确性**问题。
>
> ```
>     ⚠️ 隐患：如果调度器能根据【当前步实际采到的 token】来决定验几个，
>              那「验多少」就和「采到了什么」相关了 —— 这会把分布带偏。
>
>     ✅ 而滞后两步意味着：调度决策所依据的信息，
>        在当前步的 token 被采出来【之前】就已经固定了
>        ⟹ 调度器【不可能偷看】当前步的结果 —— 这就是所谓的【因果屏障】
> ```
>
> ⟹ ✅ 于是 §8.3 的无损性依然成立：**调度只影响「验几个」（快慢），不影响「验出什么」（分布）。**

> 🔑 **这一节一句话**：草稿侧问的是「**怎么猜得更准**」（分子 E），已经卷到头了；验证侧问的是「**在给定吞吐目标下，这一步到底该验几个 token**」（分母 r）——那是个**调度问题**，不是模型问题。

## 8.8 本章小结

**① 立论，以及它的有效期。** Decode 时**算力**利用率 0.34%、**带宽**几乎打满（⚠️ 说「GPU 利用率低」必须带口径，算力低是 Memory Bound 的**定义**，不是浪费）。batch=1 时验证 5 个 token 比验证 1 个只贵 **0.23%**，所以猜字几乎白赚。★★ 但这个前提在 batch 越过约 **105**（按 H100 峰值）/ 约 **60**（按 MFU 60%、MBU 85% 打折）之后就失效了。

**② ★★★ 全章只有一个公式**，其余都是它的特例：

```
                      E                 1 − α^(γ+1)
    加速比  =  ───────────────   ，  E = ─────────────
                 γ · c  +  r              1 − α

      α 单 token 接受率 ｜ γ 草稿长度 ｜ E 一轮期望产出（含 bonus）
      c 草稿单步 ÷ 目标单步 ｜ r 验证 γ+1 个 ÷ 验证 1 个
```

**③ ⚠️ 三条最容易记错的结论**：

```
    ✗ 「α=0.95、γ=4 ⟹ 平均接受 3.8 个」（或 4.8 个）
    ✓  草稿是【串行依赖】的，一错全废 ⟹ 几何求和 ⟹ 【4.52】
       α 越低错得越离谱：α=0.5 时线性算法高估 55%
       🔑 且有天花板 1/(1−α)：α=0.8 时【猜多长都不会超过 5 个/轮】

    ✗ 「验证多个 token 几乎免费」
    ✓  只在【访存受限区】免费。batch 越过屋脊点后 t ∝ M，r 线性上涨
       ★★★ 完全算力受限时可以证明：E ≤ γ+1 而成本 = γ·c+(γ+1)
            ⟹ 加速比【恒小于 1】，与 α、γ、草稿方案全都无关

    ✗ 「DeepSeek-V3 的 MTP 加速 3×」
    ✓  官方口径是【第二 token 接受率 85~90%、TPS 提升 1.8×】（2412.19437 §5.4.3）
       ★ 反推交叉验证：γ=1、α=0.875 ⟹ E = 1.875 是【绝对上界】
         ⟹ 3× 在数学上不可能；算上 c≈0.03 得 1.82×，和官方 1.8× 严丝合缝
```

**④ 无损性 = 删 + 补两步**（§8.3）。第一步按 `p/q` 打折接受（删），第二步从 `norm(max(0, p−q))` 重采（补）。⚠️ 是**分布相同**，不是**逐 token 相同**——回归测试会被咬。⚠️ 2026 起出现的**有损验证**省掉了「补」，实际产出**滑向草稿分布**；而且**任务越难坑越深**（GSM8K +0.38pp ⟶ AIME +6.67pp），**拿 GSM8K 验收是测不出来的**。✅ 论文的解法很实用：想要截断的好处，就**对目标模型做截断，再走无损验证**——不必牺牲无损性。

**⑤ 草稿六流派**（§8.4 末尾有完整对照表）：

| | α | 额外显存（8B 口径） | 额外训练 | c |
|---|---|---|---|---|
| 独立小模型 | ✅ ~0.75 | ⚠️ ~2.0 GB | 零 | ⚠️ 12.5%~37.5% |
| Medusa 多头 | ⚠️ 沿位置衰减 | ⚠️ ~1.05 GB / 头 | 小 | 极小 |
| ★ EAGLE | ✅ 好 | ~0.50 GB | 中 | 中小 |
| ★ n-gram / 后缀 | ⚠️ 两极分化 | ★★ ≈ 0 | 零 | ✅ < 2% |
| MTP | ✅ 0.85~0.90 | 已含 | ⚠️⚠️ 只能预训练期加 | 极小 |
| ★★ DSpark 半自回归 | ✅ 比 EAGLE-3 +26.7% | 主干 + 马尔可夫头 | 中 | 低 |

⟹ **树形**（§8.5）一次验多条分支，E 涨 30% 但 r 涨到 5 倍，所以比线性**更早**塌：k=21 在 batch=1 时 1.85×，batch=64 时**全线跌破 1×**。

**⑥ ★★★ 最重要的一条：投机解码是【延迟】优化，不是吞吐优化。** 高并发时算力不空闲 ⟹ 收益消失甚至负收益（§8.6.2 有一行证明）。★★ 且**目标模型越小越不划算**：70B 配 1B 是 2.03×，8B 配 0.6B 只有 1.37×——即便后者接受率更高，c 太大就全被吃掉了。

**⑦ ★★ 2026 新战场在【验证侧】**（§8.7）。✅ 验证占执行时间 **42%~95%**，草稿开销在大 batch 下只剩 **3%~7%**——**你把草稿再优化一倍，动的是那 3%**。✅ DSpark 的答案：按**前缀存活概率**做全局 top-k 分配验证预算，决策粒度从 **batch** 下沉到 **token**；目标函数 `Θ = τ · SPS(B)` 里直接嵌了**引擎的实测吞吐曲线**；靠「两步滞后」同时拿到 CUDA Graph 兼容性和**因果屏障**（调度不偷看当前步结果 ⟹ 无损性保住）。

**⑧ 🔑 一张上手的决策表**：

| 你的情况 | 怎么做 |
|---|---|
| 代码补全 / RAG / 文本改写 | ✅ ★ 直接上 **n-gram**，零显存零训练，`c < 2%` |
| 低并发 + 交互式对话 | ✅ 上 **EAGLE**，2~3× |
| 目标模型 ≤ 8B | ⚠️ 先估 c，很可能不划算（1.37× 那一档） |
| 高并发批处理（batch ≥ 几十） | ❌ **关掉**，或用自适应 γ 让它自己收缩 |
| 想用树形草稿 | ⚠️ 只在 batch 很小时；k 要跟着 batch 反向调 |
| 看到一个加速比数字 | ★ 先用 `E = (1−α^(γ+1))/(1−α)` 算上界，超过上界的一律存疑 |
| 想用截断式验证（typical acceptance 等） | ⚠️ 别在 EAGLE-3 上用；⚠️ 别拿 GSM8K 验收 |
