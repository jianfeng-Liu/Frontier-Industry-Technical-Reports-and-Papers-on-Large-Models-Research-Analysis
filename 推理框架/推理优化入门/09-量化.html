09 量化

一句话：把数字存得更短。这是唯一一个同时打中「权重搬运量」和「KV Cache 大小」两个瓶颈的手段——所以它是投入产出比最高的优化。

📖 量化（quantization）——用更少的比特表示同一个数值。BF16（16 位）→ FP8（8 位）→ INT4（4 位）。每降一档，显存和搬运量大致减半。

本章分工：这里讲的是推理服务侧的账——量化怎么变成更低的延迟、更多的并发、更少的卡。至于量化 kernel 内部怎么写、误差怎么用 RMSE / SQNR 量、scale 乘在 GEMM 的哪一步，那是算子实现向的题目，见 大模型算子开发 · 06 量化算子。本章需要深入的地方会直接链过去，不重复。

9.1 量化在推理里为什么比在训练里重要得多

    训练：主要用 BF16，因为★ 反向传播对数值精度敏感，
          梯度是小量，精度不够会累积误差、训练发散。

    推理：★★ 只有前向，误差【不累积到梯度里】。
          而且 01 章说了，Decode 阶段是【访存受限】——
          ⟹ 权重从 16 位变 8 位，搬运量直接【减半】

    ⟹ ★ 训练量化是「省显存」，推理量化是「省显存【并且】提速」。
       性质完全不同。

★ 「速度翻倍」这句话要加一个前提：只在这个算子确实卡在搬运上时才成立。batch=1 的 Decode 是最理想的情况，字节减半就是时间减半；batch 大到几百之后，瓶颈换成算力，权重量化的提速就兑现不出来了。§9.3 会把这笔账算出来。

9.2 先把算术走一遍：8 个数，一张表

后面所有的名词——scale、zero-point、对称/非对称、per-channel、离群值——都是同一段算术的不同切法。先用 8 个具体的数把它走完，之后再出现就不用猜了。

这就是那 8 个数（当成某一层权重里连续的 8 个元素）：

x = [ 0.617, -1.284,  0.036,  2.540, -0.905,  0.331, -1.872,  1.109 ]
      索引0   索引1   索引2   索引3   索引4   索引5   索引6   索引7

（挑 2.540 是为了让算术干净：2.540 ÷ 127 = 0.020 整。真实张量不会这么配合，但流程一模一样。）

📖 scale（缩放因子）——一个整数刻度代表多大的实数。scale = 0.02 意思是「整数 +1」对应「实数 +0.02」。
📖 zero-point（零点）——实数 0 落在哪个整数上。对称量化里它恒为 0，所以看不见；非对称量化里它是第二个要存的参数。

9.2.1 对称量化：完整走一遍

三步，就这三步（b = 位宽，这里 b = 8，即 INT8）：

① 定 scale：  scale = max(|x|) / (2^(b-1) − 1)      分母对 INT8 是 127
② 量化：      q     = clamp( round(x / scale), −127, +127 )
③ 反量化：    x̂     = q × scale

代进去：max(|x|) = 2.540，所以 scale = 2.540 ÷ 127 = 0.020。

9.2.2 非对称量化：同样 8 个数再走一遍

对称量化默认「正负两边一样宽」。如果数据偏向一侧，正半轴或负半轴的档位就白白空着。非对称量化多存一个 zero-point，把区间平移到无符号整数 [0, 255] 上，省下那半边。

① scale      = ( max(x) − min(x) ) / (2^b − 1)        分母对 INT8 是 255
② zero_point = round( −min(x) / scale )
③ q          = clamp( round(x / scale) + zero_point, 0, 255 )
④ x̂          = (q − zero_point) × scale

代进去：max = 2.540，min = −1.872，区间宽度 = 4.412。

scale      = 4.412 ÷ 255 = 0.017302        ← 比对称的 0.020 小了 13%
zero_point = round( 1.872 ÷ 0.017302 ) = round(108.20) = 108

       分子分母差不多，比值就接近 1。

★ 为什么工程上宁可损失那 15% 也要用对称？ 看上表第 4 行：非对称的 x̂ = (q − zp) × scale 展开进矩阵乘会变成 Σ(q_w − zp_w)(q_x − zp_x)，交叉项 zp_w × Σq_x 和 zp_x × Σq_w 都得单独算。对称量化里 zp 恒为 0，这些项全部消失，整数矩阵乘可以原样用 Tensor Core，scale 留到最后一步再乘。省下的这点 kernel 复杂度，比 15% 的精度值钱。展开推导见 大模型算子开发 §6.8.1。

9.2.3 粒度：同一组数，三种切法

📖 量化粒度（granularity）——多少个数共用一个 scale。这是整个量化里最有杠杆的一个旋钮，因为 §9.2.1 那条规律说了：scale 由组里最大的那个数独家决定，组越小，被大数拖累的人越少。

把那 8 个数摆成一个 2 × 4 的权重矩阵（2 个输出通道 × 4 个输入维度）：

  输出通道 0        0.617     -1.284      0.036      2.540           2.540
  输出通道 1       -0.905      0.331     -1.872      1.109           1.872

       第 2 组 = { 0.036 , 2.540 }，它的 scale 还是 0.020，

    ⟹ 为什么？因为全局最大值 2.540 就在这一组里。
       ★ 细粒度的全部作用是【把大数关进小房间】，

         ⟹ 和大数【同房间】的那位（0.036），该多惨还是多惨。

9.2.5 scale 不是免费的：INT4 的有效位宽是 4.15，不是 4

粒度越细，scale 越多，而 scale 自己也要占字节。INT8 下这笔开销可以忽略，INT4 下不能——因为权重本体缩了一半，scale 没缩。

    INT4，group size = 128，非对称（scale 用 FP16，zero-point 用 INT4）：

      每 128 个权重要存：
          权重    128 × 4 bit  = 64 字节
          scale   1 个 FP16    =  2 字节
          zp      1 个 INT4    =  0.5 字节
                              ─────────
          合计                 = 66.5 字节

      ⟹ 平均每个权重 = 66.5 × 8 ÷ 128 = 【4.15625 bit】   ← ★ 不是 4 bit
      ⟹ 相对 BF16 的压缩比 = 16 ÷ 4.15625 = 【3.85 倍】   ← ★ 不是 4 倍

把这个 3.85 代到 Llama-3-8B（80.3 亿参数）上：

权重格式 每权重位数 权重总大小 一张 H100（79.6 GiB）剩给 KV Cache
BF16 16 16.06 GB = 15.0 GiB 58 GiB（02 章 §2.3 那笔账）
FP8 / INT8 8 8.03 GB = 7.5 GiB 65.5 GiB（+13%）
INT4，g=128 4.15625 4.17 GB = 3.9 GiB 69.1 GiB（+19%）

⚠️ 单位约定，和 02 章 保持一致：算容量用 GiB（1 GiB = 2³⁰ 字节），算带宽用十进制 GB（3.35 TB/s 是十进制）。两套差 7%，混着用是这个主题最常见的错账来源。上表两列都给了，就是为了让你看清它们不是一个数。
★ 顺带纠正一个直觉：权重从 15 GiB 压到 3.9 GiB，省下的 11 GiB 只让 KV 预算涨了 19%——因为分母里 KV 本来就占了大头（58 GiB）。量化权重主要买的是「速度」，不是「并发」；想买并发得量化 KV Cache（§9.7）。
group size = 128 是社区收敛下来的默认值；g = 32 精度更好但有效位宽涨到 4.625 bit，体积优势被吃掉一截。这笔账在 大模型算子开发 §6.2.6。

9.3 ★★ 在屋顶线上看：量化省的是绝对时间，不是相对位置

这一节是本章最容易讲错、也最值得讲对的一段。量化没有减少任何一次乘法——FLOP（浮点运算次数）一次都没少，它减少的只有字节。那它到底怎么变快的？

⚠️ INT4 那一列是个例外，要说清楚：它的相对位置确实动了（0.34% → 1.31%），因为分子翻了 3.85 倍而分母（屋脊点 295）没变——INT4 在 Hopper 上没有对应的 Tensor Core，算之前必须解压回 BF16（§9.8）。但 1.31% 仍然是深度访存受限，所以时间还是等于搬运时间，3.85 倍的加速依然成立。

⚠️⚠️ 「GPU 利用率低」这句话必须带口径。 上表里 batch=1 的 BF16 Decode，算力利用率 0.34%，但同一时刻 HBM 带宽利用率接近 100%。说「GPU 只用了 0.34%」会让人以为在浪费卡，其实卡已经榨干了——榨的是带宽那一侧。⟹ 报任何利用率数字，先说清是算力（Tensor Core / SM）还是带宽（HBM），否则这个数字没有意义。（01 章 §1.3、02 章 §2.6 是同一件事的两个视角。）

收益会随 batch 消失——临界点能算出来。 Decode 阶段权重只读一遍、被整个 batch 共享，所以算术强度 ≈ batch 大小 B（乘上位宽带来的倍数）：

权重格式 算术强度 计算单元的屋脊点 转为算力受限的 batch 之后还剩什么收益
BF16 B 295（BF16） B ≈ 295 —
FP8 / W8A8 2B 591（FP8） B ≈ 295 ← 和 BF16 一样 ✅ 算力也翻倍，超过临界点后还能继续快
INT4 / W4A16 3.85B 295（仍走 BF16） ★ B ≈ 77 ⚠️ 只剩显存收益，不再提速 
    ★★ 这张表解释了两个现象：

    ① W4A16 在 batch 很小时是加速之王（3.85×），
       ⟹ 但 batch 一过 77 就【触顶】，再大就完全没用了。
       ⟹ 所以它是【端侧 / 单用户 / 低并发】的方案。

    ② FP8 的临界点和 BF16 一样是 295，
       ⟹ 意思是：不管 batch 多大，FP8 都【不会失效】——
          小 batch 靠带宽赢，大 batch 靠算力赢。
       ⟹ 所以它是【高吞吐服务集群】的方案。

⚠️ 上面是理论模型，忽略了 KV Cache 的搬运、Attention、通信和 kernel 启动开销；长上下文时 KV 的流量会顶上来（02 章 §2.6），临界点会往下挪。能确定的是量级，不是小数点。 另外 大模型算子开发 §6.1.3 给的是 90 和 345——那是「单个 4096×4096 GEMM、把激活进出的流量也算上」的口径，本章是「整模型、只算权重」的口径，两套数字不冲突，是同一个量级的两种算法。

⚠️ 那 Prefill 呢？ 常见说法是「Prefill 算力受限，所以权重量化对它没用」。这句话有前提，不是无条件成立的：

    Prefill 的算术强度 ≈ prompt 长度 M（每个 token 复用同一份权重）
    ⟹ M 小于屋脊点时，Prefill 和 Decode 一样【访存受限】。

    ✅ 03 章 §3.3 把这个临界点扫出来了：M ≈ 390（量级是【几百个 token】）

      M = 6（一句「今天天气怎么样」）  ⟹ I = 5.6    ⚠️ 访存受限，量化【照样提速】
      M = 128                        ⟹ I = 111    ⚠️ 仍然访存受限
      M ≈ 390                        ⟹ I ≈ 295    ★ 临界点
      M = 2048（一篇长文档）          ⟹ I = 899    ✅ 算力受限，W4A16 不提速

    ⟹ ★★ 所以正确的说法是：
       「prompt 长到几百个 token 以上时，Prefill 才是算力受限的，
         那时只有 W8A8 / FP8 这种【也量化激活】的方案才对 TTFT 有用。」
    ⚠️ 聊天场景里一句十几个字的问题，它的 Prefill 其实是访存受限的，
       W4A16 对它【也有效】。

🔑 这解释了一个实践现象：同一个 INT4 模型，长文档摘要的 TTFT（Time To First Token，首字延迟）几乎没变化，但聊天的 TPOT（Time Per Output Token，每字延迟）快了一倍。不是量化没生效，是两个场景的瓶颈不在同一侧。（指标定义见 13 章。）

9.4 三个可以独立量化的对象

初学者最容易混淆的一点：「量化」这个词在不同语境下指的是不同的东西。它有三个互相独立的对象，收益、难度、影响的指标都不一样。

量化对象 省的是什么 ★ 直接改善的指标 难度 为什么
① 权重（Weight） 显存 + 每步搬运量 ★ TPOT（Decode 变快） ✅ 容易 权重是静态的，可以离线慢慢算最优量化点，算错了大不了重来
② 激活值（Activation） 能用上 FP8/INT8 的计算单元 ★ TTFT（长 prompt 的 Prefill 变快） ⚠️ 难 激活值随输入变，离线看不全；而且有离群值（§9.2.4、§9.6）
③ KV Cache 每个 token 的 KV 字节数 ★★ 并发数 / 吞吐 ✅ 中等 FP8 几乎无损；但它在线产生，没有离线校准的机会 
    ★★ 命名规则：常见的 W4A16、W8A8 就是在说前两项
       W4A16 = Weight 4 位、Activation 16 位   （只量化权重）
       W8A8  = Weight 8 位、Activation 8 位    （权重和激活都量化）
       ⚠️ 这个记号【不包含 KV Cache】。KV 是单独一个开关
          （vLLM 里是 --kv-cache-dtype，和权重量化互不干涉）。

    ★ 为什么 W4A16 在开源模型里最常见？
      因为 Decode 是【访存受限】——瓶颈在搬权重，不在算（§9.3）。
      量化激活值只能提升算力，而算力本来就空着 99.66%。
      ⟹ ★ 只量化权重，就已经吃到了绝大部分收益，
           而且【不需要校准激活、不会踩离群值的坑】，风险低得多。

★ 一个务实的排序：想要什么，就量化什么。
想让吐字变快（TPOT）→ 量化权重。
想让装下更多并发（吞吐）→ 量化 KV Cache，这比量化权重直接得多（§9.2.5 算过：权重从 15 GiB 压到 3.9 GiB，KV 预算只涨 19%）。
想让长 prompt 的首字变快（TTFT）→ 只有量化激活才有用，也只有这条路要处理离群值。

9.5 权重量化的两大流派

先说清楚基线是什么，不然看不出这两个流派到底在解决什么问题。

    📖 RTN（Round-To-Nearest，最近邻取整）——最朴素的量化，
       就是 §9.2.1 那三步：每个权重【各自】四舍五入到最近的格子点，
       一次搞完，不需要任何数据。

    ⚠️ RTN 的毛病：它在优化【错的东西】。
       它让「每个权重」尽量接近原值，
       ★★ 但我们真正想要的是「这一层的【输出】」尽量接近原值。

    ⟹ 这两件事不是一回事。权重是要【乘上输入】再相加的：
       一个权重错 0.01，如果它对应的输入是 100，输出就错 1；
       另一个权重错 0.05，如果它对应的输入是 0.1，输出才错 0.005。
       ★ 后者错得更多，但对输出的伤害小 20 倍。

    ⟹ ★★ 两条路线就从这个缺口分叉：
       GPTQ：错了【当场补】       —— 事后补偿
       AWQ ：让重要的权重【少错】 —— 事前保护

📖 PTQ（Post-Training Quantization，训练后量化）——模型训练完之后再量化，不改训练流程。本节两个方案都属于这一类。（对照是 QAT，Quantization-Aware Training，量化感知训练，要改训练流程，推理服务侧一般碰不到。）

📖 先解释一个容易卡住的地方：为什么这一节满屏 FP16，而 §9.1 说训练用 BF16？

两者都是 16 位，区别只在于这 16 位怎么切：
FP16（half precision，半精度）= 1 符号 + 5 指数 + 10 尾数
BF16（bfloat16，brain float）= 1 符号 + 8 指数 + 7 尾数
⟹ BF16 的指数位和 FP32 一样宽 ⟹ 动态范围大、不易溢出 ⟹ 训练偏爱它（§9.1 那段的原因）。
⟹ FP16 尾数多 3 位 ⟹ 同样范围内更精确，但范围窄，训练时得配 loss scaling 兜着。

✅ 这两篇论文（2022 / 2023）通篇只用 FP16，BF16 一次都没出现——这不是笔误：
AWQ 论文第 3 页明写它的推理 kernel 就是 FP16×INT4 GEMM；
⚠️（背景补充，非论文原文）它们评测的 OPT / LLaMA 系列，发布的权重也确实是 FP16 的。

⟹ ★★ 但这对理解本节毫无影响：这里的「FP16」只是在说 【没被量化的 16 位原始精度】。真正的对比是 16 位 vs 3/4 位，不是 FP16 vs BF16。你在心里把它读成「原始精度」就行。
⚠️ 反过来说，照抄论文口径写 FP16 是对的，换成 BF16 反而会把人家的 kernel 实现说错。

① GPTQ：逐层重建，用二阶信息补偿

✅ 论文 arXiv 2210.17323（papers/GPTQ-Post-Training-Quantization-arXiv-2210.17323.pdf）
📖 名字来源：论文脚注 1 说明，GPTQ = OPT（模型家族名）+ PTQ（post-training quantization，训练后量化）。

它优化的目标，论文公式 (1) 写得很直白：

    ✅ argmin ‖ W·X − Ŵ·X ‖²      （X = 校准数据在这一层的【输入激活】）
       └── 注意：不是 ‖W − Ŵ‖。
       ★★ 目标里根本没要求「量化后的权重接近原权重」，
          只要求【这一层的输出接近】。

    ⟹ 这就给了 GPTQ 一张许可证：
       ★ 只要输出对得上，它可以【故意把某个权重改远一点】。

★ 一个具体例子（数字是我编的，为了让格子粗到肉眼可见）

    设某一行有 2 个权重：w = [0.7, 0.2]，输出 y = 0.7·x₁ + 0.2·x₂
    量化网格粗到只有 3 个格子：{ 0.0 , 0.5 , 1.0 }
    再设：校准数据上观察到 x₁ 和 x₂ 【几乎总是同时出现、大小相近】（记作 x）
          ⟹ 真实输出 y ≈ 0.7x + 0.2x = 0.9x

  ── RTN 的做法：各自四舍五入 ──────────────────────
    0.7 → 0.5     （0.7 离 0.5 更近）
    0.2 → 0.0     （0.2 离 0.0 更近）
    ŷ = 0.5x + 0.0x = 0.5x
    ⚠️ 误差 = 0.5x − 0.9x = −0.4x        ← 差了将近一半

  ── GPTQ 的做法：量化一个，补一个 ────────────────
    第 1 步  量化 w₁：0.7 → 0.5
            ★ 记账：输出【欠了】 0.2·x₁
    第 2 步  ★★ 在量化 w₂ 之前，先把这笔亏空【转嫁】给它。
            因为 x₂ ≈ x₁，用 w₂ 去补是等效的：
            w₂ ← 0.2 + 0.2 = 0.4      ← 注意：0.4 已经【离原值 0.2 很远了】
    第 3 步  量化 w₂：0.4 → 0.5        （0.4 离 0.5 更近）
            ŷ = 0.5x + 0.5x = 1.0x
    ✅ 误差 = 1.0x − 0.9x = +0.1x       ← 误差缩小到 1/4

    ★ 看懂这一点就看懂 GPTQ 了：
      它把 w₂ 从 0.2 改成 0.4（单看权重是「改错了」），
      ⟹ 却让【整层的输出】更准了。

那 Hessian（海森矩阵）在里面扮演什么角色？

    上面那步「转嫁」我偷懒用了一个假设：x₁ ≈ x₂。
    ★ 真实情况下，通道之间的相关性各不相同，
      「w₁ 欠的账该往 w₂ 上加多少」需要算出来。这就是 Hessian 的活。

    ✅ 论文（第 3 页公式 (2)）：H = 2·X·Xᵀ
       ⟹ ★★ 它不是对训练 loss 求二阶导，
            而是对上面那个【逐层输出误差】对权重求的二阶导。
       ⟹ 展开看，X·Xᵀ 就是【输入通道两两之间的相关矩阵】：
            第 (i,j) 项 = 通道 i 和通道 j 在校准数据上有多「同进同退」。

    ✅ 补偿公式（论文公式 (2)）：
       δ = −(w_q − quant(w_q)) / [H⁻¹]_qq  ·  (H⁻¹)_{:,q}
            └────────┬───────┘              └─────┬────┘
            刚犯下的这笔误差                按相关性分摊给剩下的权重

    ⟹ ★ 一个很有用的直觉：
       通道之间【越相关】，补偿越有效；
       如果所有通道【完全不相关】（H 是对角阵），一个权重的账没人能接，
       ⟹ GPTQ 就【退化成 RTN】。
       这解释了为什么它在大模型上收益更明显——大模型的通道冗余更多。

    ✅ 关键性质（论文第 4 页）：H 只依赖【输入 X】，不依赖权重值。
       ⟹ 所以同一层里【所有行可以共用一份 H⁻¹】。这是全部提速的根基。

★ 论文的三个工程改进（Section 4，原文就叫 Step 1/2/3）

    ✅ Step 1  Arbitrary Order Insight（任意顺序）
       前身 OBQ（Optimal Brain Quantization）每次挑「当前误差最小」的权重先量化，
       ⚠️ 导致每一行的顺序都不同 ⟹ 每行都要单独维护 H⁻¹。
       ★ 论文发现：贪心选序【收益很小】，索性所有行【按列统一顺序】。
       ⟹ H⁻¹ 更新次数从「每个权重一次」降到「每列一次」，
          复杂度降低 min{行数, 列数} 倍。

    ✅ Step 2  Lazy Batch-Updates（惰性批量更新）
       ⚠️ 瓶颈居然不是算力，是【访存】——每次更新要刷一遍巨大的矩阵，
          却只做几次浮点运算，GPU 算力全空转。
       ★ 观察：第 i 列的取整决策，只受【这一列自己】的更新影响。
       ⟹ 一次攒 B = 128 列，更新先只在这 128 列的小块里做，
          整块做完再统一刷全局矩阵一次。
       ✅ 理论计算量【一点没降】，但实测「快一个数量级」。

    ✅ Step 3  Cholesky Reformulation（Cholesky 重构）
       ⚠️ 数值不稳：H⁻¹ 反复更新会退化成【不定矩阵】，
          导致算法朝错误方向猛改权重，整层量化直接报废。
       ✅ 论文原话：模型超过几十亿参数时，这「几乎必然发生在至少几层上」。
       ★ 小模型加阻尼就够（λ 取对角线均值的 1%），大模型不够。
       ⟹ 洞察：整个过程真正需要的只是 H⁻¹ 的【第 q 行、从对角线往右那一段】，
          可以用一次 Cholesky 分解【全部预先算好】，不再反复更新。

✅ 关键数字（全部来自论文，单张 NVIDIA A100-80GB）

    校准数据：128 条 × 2048 token，取自 C4（随机网页文本）
              ★ 不含任何任务数据，所以结果仍算 zero-shot

    量化耗时：OPT-175B  4.2 小时     BLOOM-176B  3.8 小时
              （摘要里概括为「约 4 GPU 小时」）
              对比：OPT-13B 20.9 分钟、OPT-30B 44.9 分钟

质量（WikiText2 困惑度，越低越好。📖 PPL / perplexity（困惑度）——语言模型的标准评测指标，粗略可以理解成「模型在每个位置平均要在多少个候选词之间犹豫」，越低越好）：

    ⟹ ★ 反常识，但论文明确这么说：【模型越大越好量化】。
       1750 亿参数的 OPT-175B 只掉 0.03，
       1.25 亿参数的 OPT-125M 掉了 3.47。
    ⟹ ★ 直觉：大模型的通道冗余多，H 的非对角元素强，
       「把账转嫁给别人」这件事更容易成立（见上文 Hessian 那段）。

    ① 加速只在 batch=1 这种【访存受限】场景成立。
       大 batch / 长 prompt 的 Prefill 是算力受限，论文说 kernel「不直接适用」，
       ⟹ ★ 那种场景下 GPTQ 的价值退化成【省卡，而不是提速】。
       （就是 §9.3 那张「临界 batch ≈ 77」的表）

② AWQ：★ 全部 INT4 + 等价逐通道缩放

✅ 论文 arXiv 2306.00978（papers/AWQ-Activation-Aware-Quantization-arXiv-2306.00978.pdf）
📖 AWQ = Activation-aware Weight Quantization，激活感知的权重量化。

⚠️⚠️ 先纠正一个流传极广的误解。 网上（包括不少博客和课件）把 AWQ 描述成「保留 1% 的重要权重为 FP16，其余量化成 INT4」。这不是 AWQ 的做法。 那是论文用来论证动机的一个对照实验（Table 1），论文紧接着在 Limitations 里明确否定了这条路——理由是混合精度对硬件不友好。AWQ 的实际做法是：所有权重统统 INT4，一个 FP16 都不留，靠一组等价的逐通道缩放因子来保护重要通道。 下面按论文的叙述顺序走一遍：先看那个对照实验说明了什么，再看它为什么被否决，最后看真正的方案。

★★ 第一步：那个一锤定音的对照实验（论文 Table 1）

论文问了一个很干脆的问题：如果允许把 1% 的权重通道留在 FP16 不量化，那这 1% 该怎么挑？

✅ OPT-6.7B，INT3 + group size 128，WikiText 困惑度（越低越好）：

方案 困惑度 说明
FP16 原始模型（天花板） 10.86 —
RTN 全量化（地板） 23.54 ⚠️ 崩了
★ 按【激活值】大小挑 1% 留 FP16 11.39 ✅ 几乎救回来了
按【权重】大小挑 1% 留 FP16 22.37 ⚠️ 几乎没用
★ 随机挑 1% 留 FP16 24.23 ⚠️ 没用 
    ★★ 看最后两行：按权重自己的大小去挑（22.37），
       和【随机乱挑】（24.23）几乎一个水平！
    ⟹ 这就是论文标题里 Activation-aware 的全部含义：
       ★ 权重重不重要，看的是【和它相乘的那个激活值有多大】，
         不是权重自己有多大。
    ⟹ 回到 §9.5 开头那个例子：权重错 0.01 但输入是 100，输出就错 1；
       ★ 决定伤害大小的是【权重误差 × 输入幅度】这个乘积。

⚠️ 第二步：但这个方案被论文自己否决了

    ✅ 论文 Limitations 段的原话大意：
       留 1% 的 FP16 会造成【混合精度数据类型】，
       ⟹ 同一个矩阵里既有 INT3 又有 FP16，
          排布不规整，kernel 没法高效跑 ——【硬件不友好】。
       ⚠️ 更具体地说：Tensor Core 要求一整块数据同类型同布局，
          中间插着 1% 的 FP16 会把整块打散，
          ⟹ 省下的带宽全被不规则访存和分支吃回去。

    ⟹ ★★ 于是 AWQ 换了个思路，这才是它真正的方案：
       「不真的保留 FP16，但要达到同样的保护效果。」

★ 第三步：真正的解法——把重要通道【放大】再量化

先看论文用的量化公式（公式 (1)），和 §9.2.1 那三步是同一件事：

    ✅ Q(w) = Δ · Round(w / Δ)  ，  Δ = max(|w|) / 2^(N−1)
       ★ 划重点：Δ（格子间距，就是 §9.2 的 scale）
                 由【整个 group 的最大值】决定，和某个单独的权重无关。
       ⟹ 这正是 §9.2.1 那条规律③，AWQ 的全部魔法都建立在它上面。

★ 一个具体例子

    设：INT4（N=4 ⟹ 2^(N−1) = 8），某个 group 里最大权重是 0.80
        ⟹ Δ = 0.80 / 8 = 0.1
        ⟹ 可以表示的值是 { 0 , 0.1 , 0.2 , 0.3 , … }

    设：这个 group 里有一个【重要通道】的权重 w = 0.24
        （之所以重要，是因为和它相乘的激活值很大）

  ── 直接量化 ────────────────────────────────
    0.24 / 0.1 = 2.4  →  Round = 2  →  Q(w) = 0.2
    ⚠️ 误差 = 0.04

  ── AWQ：先把它放大 s = 2 倍 ──────────────────
    ★ 关键：0.24 × 2 = 0.48 < 0.80，
      ⟹ group 的最大值【没变】 ⟹ Δ 也【没变】，还是 0.1
      ⟹ ★★ 也就是说：这次放大【没让任何别人吃亏】

    0.48 / 0.1 = 4.8  →  Round = 5  →  0.5
    推理时再除回 s = 2  →  0.5 / 2 = 0.25
    ✅ 误差 = 0.01                      ← 小了
    ⚠️ 别被这个 4 倍唬住：单个权重的误差是【碰运气】的
       （§9.2.1 那条 🔑 说过），论文保证的是【平均】按 1/s 缩小，
       这里刚好赶上个好位置。

    ★★ 换个角度看，会更清楚为什么必然变好：
       量化结果除以 s 之后，这个权重能落到的值变成了
         { 0 , 0.05 , 0.10 , 0.15 , … }      ← ★ 格子密了一倍
       ⟹ 放大 s 倍，等价于给这个通道【多了 log₂(s) 位有效精度】，
          而【一个比特都没多存】。这就是 AWQ 的全部戏法。

    ⟹ ★★ 对比一下就明白它为什么比「留 1% FP16」好：
       两者都是给重要通道更多精度，
       但 AWQ 是靠【改数值】做到的，数据类型自始至终只有 INT4 一种，
       ⟹ 矩阵排布完全规整，kernel 跑得动。

    ✅ 论文的形式化说法（公式 (3)）：
       误差之比 = (Δ′ / Δ) · (1 / s)
       其中 Δ′ 是放大后的新格距。
       ★ 因为 Round(·) 的平均误差恒定在【0.25 个格子】不随 s 变
         （§9.2.1 那条 🔑 推过：均匀分布在 [0, 0.5] 上，均值 0.25），
         真实误差是 Δ × 0.25，缩放后是 Δ′ × 0.25，
       ⟹ 做比值时 0.25 【直接约掉了】，才剩下干净的 (Δ′/Δ) · (1/s)。
       ⟹ ★ 如果取整误差本身会随 s 变，这整套推导就塌了。

⚠️ 那个「0.25」依赖「权重在一个格子内均匀分布」这个假设。权重整体是钟形分布，但在单个格子那么窄的区间里近似是平的，所以站得住。✅ 论文自己的措辞也是 roughly 和 We empirically find——经验结论，不是定理。

★ 所以 s 到底怎么定？

    ✅ 论文的目标函数（公式 (4)）——注意它优化的是【整层输出】，
       和 GPTQ 的目标其实是同一个：
       s* = argmin ‖ Q(W·diag(s)) · (diag(s)⁻¹·X) − W·X ‖
       ★ 中间那两个 diag(s) 和 diag(s)⁻¹ 互相抵消，
         所以这个变换在【数学上完全等价】，不改变模型行为。

    ⚠️ 但 Round(·) 不可导，没法反向传播。
    ⟹ ★ 论文的处理简单得有点朴素：把搜索空间【压缩到一维】
       ✅ s = sₓ^α          （sₓ = 该通道激活值的【平均幅度】）
          α = 0  ⟹ 完全不缩放
          α = 1  ⟹ 最激进的缩放
       ⟹ 在 [0, 1] 上【网格搜索】一个 α 就完事了。
    ⟹ ★★ 所以 AWQ 全程【不需要反向传播、不需要回归求解】，
         它只需要统计每个通道激活值的平均大小。
    ⟹ ★ 而且 diag(s)⁻¹ 可以【离线融合进前一层】（LayerNorm 的权重、
         或上一个线性层的输出通道），运行时【零额外开销】。

9.6 ★ 激活值量化：离群值与 SmoothQuant

✅ SmoothQuant 论文 arXiv 2211.10438（papers/SmoothQuant-arXiv-2211.10438.pdf）

§9.2.4 已经用 8 个数演示过离群值的破坏力了。这里只补一句它在真实模型里的形态，然后直接讲解法。

    ★★ 现象：大模型的激活值里，有极少数几个【通道】的数值
       比其他通道大【上百倍】。这就是【离群值（outlier）】。

    ⚠️ 注意「通道」这个词：它不是随机分布的几个元素，
       ★ 而是【固定的那几个通道，从头到尾、对所有 token 都大】。
       ⟹ 这正是 §9.2.4 最后那段说的：
          沿 token 方向切 group，每一组都会切到这根刺，
          ⟹ 细粒度【一个也救不了】。

    ⟹ 量化要把整个范围映射到 256 个格子（INT8）。
       范围被一个 100 倍的离群值撑开之后，
       ★ 剩下 99% 的正常数值全被挤进前几个格子（§9.2.4 算过：只用到 3 个）
       ⟹ 精度彻底崩掉。

★★ SmoothQuant 的解法（一个非常优雅的技巧）

    观察：激活值难量化，而【权重好量化】——
          权重的分布集中、没有离群值（它是训练出来的参数，不是数据）。
    ⟹ ★ 那就把难度【从激活转移一部分给权重】。

       Y = (X · diag(s)⁻¹) · (diag(s) · W)
            └─────┬──────┘   └──────┬─────┘
            激活除以 s，变平滑     权重乘以 s，变陡一点

    ★ 数学上【完全等价】——diag(s)⁻¹ 和 diag(s) 相邻相消，
      模型的输出一个比特都没变。
    ★ 而且 diag(s)⁻¹ 可以【离线融合进前一层】
      （LayerNorm 的 weight，或上一个线性层的输出通道），
      ⟹ 运行时【零额外开销】，推理时根本看不到这一步。

★ 用 §9.2.4 那组数把它算出来

设这一层有 4 个输入通道，通道 3 是离群通道。列出每个通道在激活和权重两侧的最大绝对值：

    缩放因子的算法（论文公式 (4)）：
        s_j = max|X_j|^α  /  max|W_j|^(1−α)         ✅ 论文默认 α = 0.5
输入通道 j 激活侧最大绝对值 权重侧最大绝对值 s_j（α=0.5） 变换后 激活侧 变换后 权重侧
0 0.905 0.5 1.345 0.673 0.673
1 1.284 0.4 1.792 0.717 0.717

3 ⚠️ 254.0 0.6 20.58 12.35 12.35 
    ★★ α = 0.5 有一个漂亮的性质，上表最后两列已经露出来了：
       变换后【两边的 max 完全相等】，都等于 √(max|X| · max|W|)。
       验算通道 3：√(254.0 × 0.6) = √152.4 = 12.35  ✓
       ⟹ 也就是说，α = 0.5 把难度【对半分】。

    ── 激活这一侧（大赚）──────────────────────
       离群倍数  254.0 / 0.905 = 280×   →   12.35 / 0.673 = 18.3×
       per-tensor scale  254.0/127 = 2.000  →  12.35/127 = 0.0972
       ✅ 格子细了【20.6 倍】，那 7 个正常数终于有地方放了

    ⟹ ★★ 为什么这笔买卖划算？因为两边的【起点】天差地别：
       激活从 280× 下来，是从「完全没法量化」变成「能量化」；
       权重从 2× 上去，是从「非常好量化」变成「还行」。
    ⟹ ★ α 就是这个分配比例的旋钮：
       α → 0  ⟹ 全不转移（退化成原样），激活照样崩
       α → 1  ⟹ 全转移给权重，轮到权重崩
       ✅ 论文默认 α = 0.5；⚠️ 对离群更严重的模型建议调大（量级 0.75）。

⚠️ 上表的激活/权重数值是我为了演示编的（沿用 §9.2.4 那组数），机理是论文的，数字不是。论文在真实模型上的实测效果、以及 α 的完整扫描，见原论文；带 RMSE 的完整两通道推导见 大模型算子开发 §6.4。
★ 一个容易忽略的前提：SmoothQuant 只在「你打算量化激活」时才需要。做 W4A16 / W8A16（激活留 16 位）时，离群值根本不是问题——因为没人去量化它。这也是 §9.4 说「只量化权重风险低得多」的具体含义。

★★ 那 scale 到底什么时候定？——动态量化 vs 静态量化

    ★ 先厘清一件事：这个区分【只对激活值有意义，对权重没有】。
      权重在推理时不会变 ⟹ scale 离线算好就行，永远是「静态」的。
      ✅ vLLM 源码里权重的量化描述符直接写死 static=True（kFp8StaticTensorSym）

    ⟹ ★★ 所以「动态 / 静态」问的其实是同一个问题：
       【激活值的缩放系数 scale，是什么时候定下来的？】

       📖 静态量化（static）：★ 离线定。
          拿校准数据跑一遍，记下激活值的范围，
          把 scale 【固化进 checkpoint】，推理时直接读。

       📖 动态量化（dynamic）：★ 当场定。
          推理时拿到真实激活值，【现场求 max、现场算 scale】。

★ 一个具体例子（量化到 INT8，scale = max|x| / 127）

    校准时看到的 max|x| = 6.0  ⟹  scale = 6.0 / 127 = 0.047（固化进权重文件）

    线上来了个请求，实际 max|x| = 18.0（比校准时见过的大得多）

  ── 静态 ──────────────────────────────────
    18.0 / 0.047 = 381  >  127
    ⚠️ 超出 INT8 上限 ⟹ 被【截断（clip）】到 127
    ⟹ ★ 本来是 18 的值被当成了 6，信息【直接丢掉】，而且无法挽回

  ── 动态 ──────────────────────────────────
    当场看到 max|x| = 18.0 ⟹ scale = 18.0 / 127 = 0.142
    ✅ 18 被正确表示，不截断

    ⚠️ 代价：必须【先把整个 tensor 扫一遍求 max】才能开始量化
       ⟹ 多一次读，而且难和上一个 kernel 融合
静态 static 动态 dynamic
scale 何时定 离线，校准时 运行时，每次现算
需要校准集 ⚠️ 需要 ✅ 不需要
运行时开销 ✅ 零（直接读常数） ⚠️ 多扫一遍激活值求 max
kernel 融合 ✅ 可以融进上一层的 epilogue ⚠️ 要先做一次全张量归约
遇到分布漂移 ⚠️ 截断，掉精度，不可挽回 ✅ 自动适应
适合 追求极致延迟、且校准集确实覆盖线上分布 ★ 默认选它

⚠️⚠️ 一个必须澄清的误解：动态量化【不解决】离群值问题

这两件事经常被混为一谈，但它们根本不在一个层面：

问题 它是什么 谁来解决
静态 → 动态 ★【跨请求】的范围漂移——校准集没覆盖到线上分布 动态 scale
离群值 ★【同一个 tensor 内部】，某个通道比别人大上百倍 SmoothQuant（§9.6 上半节） 
    ⟹ ★★ 动态量化只是把 scale 【调大到能装下那个离群值】，
       剩下 99% 的正常值【照样被挤进前几个格子】——
       就是 §9.2.4 那张表，一点没变。
    ⟹ ★ 所以就算用了动态量化，SmoothQuant 依然必要。
       这两者是【正交的】，要一起上。

★ 为什么推理框架默认用动态？

    ✅ vLLM 的默认值就是 "dynamic"
       （fp8.py 的 Fp8Config：activation_scheme: str = "dynamic"）

    ⟹ ★ 理由是账算得过来：AWQ 论文 Figure 3(c) 测过，
       【权重的访存量比激活值大 1~3 个数量级】（图上标注 79× 和 1700×）
       ⟹ 多扫一遍激活值，相对于搬权重的开销【几乎不要钱】
       ⟹ 而且省掉了整个校准环节，部署简单，还没有分布漂移的风险

    ✅ vLLM 里 block-wise（分块）量化更是【强制】dynamic——
       配成 static 会直接抛错。

    ⟹ ★ 那什么时候才用静态？
       追求极致延迟、且能把 scale 融进上一个 kernel 的 epilogue 时。
       ⚠️ 但前提是你的校准集真的覆盖了线上分布——这个前提很脆。

    ★ 最后提醒一个【正交维度】，很容易和上面搞混：【粒度】（§9.2.3）
      per-tensor（整个张量一个 scale）
      per-token （每个 token 一个）
      per-channel（每个通道一个）

    ⟹ ★★「静态/动态」管的是【何时定】，「粒度」管的是【定几个】，
       两个维度可以任意组合。
    ✅ vLLM 把它们拆得很干净：ScaleDesc(dtype, static, group_shape) 三元组，
       所以源码里 kStaticTokenScale 和 kDynamicTokenScale 是并存的。

✅ fp8.py（ACTIVATION_SCHEMES = ["static", "dynamic"]，静态时才注册 input_scale 参数）
✅ quant_utils.py（ScaleDesc / GroupShape 的定义）

9.7 ★★ KV Cache 量化——对并发数最直接的那一项

§9.2.5 算过：把权重从 15 GiB 压到 3.9 GiB，KV 预算只涨 19%。想要并发，得直接动 KV。

先把单价公式摆出来（02 章 §2.2 推过）：

    每 token 每层的 KV 字节数 = 2 × n_kv_heads × head_dim × 每元素字节数
                                ↑        ↑           ↑            ↑
                              K 和 V   KV 头数     头维度      ★ 量化动的是这一项

    ⚠️ 那个头数必须是 n_kv_heads（GQA 的 KV 头数），不是 n_heads。
       用 n_heads 会把 Llama-3-8B 高估 4 倍。

    代 Llama-3-8B（L = 32 层，n_kv_heads = 8，head_dim = 128）：
      BF16（2 字节）：2 × 8 × 128 × 2 = 4096 B = 4 KiB/层 × 32 = 【128 KiB/token】
      FP8 （1 字节）：2 × 8 × 128 × 1 = 2048 B = 2 KiB/层 × 32 = 【 64 KiB/token】
      ★ 公式里只有最后一项变了，其余全是模型结构定死的。

把它换算成并发数（KV 预算取 02 章 §2.3 那笔账）：

配置 权重 KV 预算 KV 单价 能装的 token 数 8K 对话并发数
全 BF16（基线） 15.0 GiB 58 GiB 128 KiB 475,136 58 条
只量化权重到 FP8 7.5 GiB 65.5 GiB 128 KiB 536,576 65 条（+12%）
★ 只量化 KV 到 FP8 15.0 GiB 58 GiB 64 KiB 950,272 ★ 116 条（+100%）
★★ 两个一起量化 7.5 GiB 65.5 GiB 64 KiB 1,073,152 ★★ 131 条（+126%） 
    ★★ 对比第 2 行和第 3 行，这是本章最该记住的一组对比：

       只量化权重  ⟹ 并发 +12%   （但 TPOT 减半，吐字快一倍）
       只量化 KV   ⟹ 并发 +100%  （但 TPOT 基本不变）

    ⟹ ★ 它们买的是【完全不同的东西】，不能互相替代。
       想要吞吐 ⟹ 量化 KV。想要延迟 ⟹ 量化权重。两个都要 ⟹ 都开。
    ⚠️ 上表的「+12%」不等于「吞吐 +12%」——
       吞吐还受调度、Prefill 抢占等因素影响（04 / 10 章）。
       这里只算显存这一项。

    ★ 为什么 KV 量化几乎无损？（⚠️ 我的理解，非论文原文）
      ① KV 只被 softmax 加权求和消费，softmax 本身有归一化的平滑作用
      ② 误差不会像权重那样在层间【反复相乘放大】——
         每一层的 KV 是独立产生、独立消费的
    ⟹ 实践上 FP8 KV Cache 是「几乎白拿」的，很多部署默认就开
    ⚠️ 但 INT4 KV 就有明显损失了，尤其在长上下文任务上——
       上下文越长，attention 的权重分布越尖，
       ★ 一个被量化坏的 key 就足以把 softmax 的峰值挪到错的位置。

★ KV 量化和权重量化的关键差别：它是【在线产生】的，没有离线校准的机会。

    ✅ vLLM 的实现（kv_cache.py）正好印证这一点，它有两条路：

    ① per-tensor 静态（现在 --kv-cache-dtype fp8 走的路）
       ✅ 源码注释：「Only support per-tensor scaling factor for fp8 KV cache」
       ⟹ k_scale / v_scale 是【两个标量】，从 checkpoint 里读。
       ⚠️ checkpoint 里没有的话就用 1.0，并打一条 warning：
          「Using KV cache scaling factor 1.0 for fp8_e4m3」
       ⟹ ★ 看到这条 warning 说明你的 KV 其实【没做任何缩放】，
            直接把原值塞进 E4M3 的 ±448 里了。不一定错（KV 幅度本来就不大），
            但这不是「校准过」的状态。

    ② per-token-head 动态（int8_per_token_head / fp8_per_token_head /
                          int4_per_token_head 等）
       ✅ 源码注释：scales are computed dynamically per (token, head)
          in the kernel at cache-write time —— 【写进 cache 的那一刻当场算】
       ⟹ 这时 k_scale / v_scale 被直接设成 1.0 并删掉，因为用不上了。
       ⟹ ★ 这就是 §9.2.3「粒度」那一节在 KV 上的落地：
            每个 (token, head) 一个 scale，粒度细到不能再细，
            而且【天然是动态的】——KV 是现算出来的，压根没法静态。

✅ 源码可查：quantization/kv_cache.py（BaseKVCacheMethod、KVCacheScaleParameter），模式枚举在 v1/kv_cache_interface.py（KVQuantMode）。
★ 启动参数 --kv-cache-dtype，取值远不止 fp8 一个：fp8(= fp8_e4m3) / fp8_e5m2 / fp8_ds_mla（MLA 专用）/ int8_per_token_head / int4_per_token_head / nvfp4 / turboquant_* 等。⚠️ 除了 fp8 之外，其余大多需要特定的 attention 后端或硬件，开之前先查你这版 vLLM 的支持矩阵。
⚠️ INT4 KV 的有效位宽同样不是 4（§9.2.5 那笔账）——per-token-head 的 scale 和 zero-point 都要占地方，所以实际压缩比明显小于 4 倍。

9.8 硬件才是真正的裁判

一个初学者最容易忽略的事实：量化能不能提速，取决于这张卡有没有对应的计算单元。没有，就只能「存 4 位、算之前解压回 16 位」——省搬运，不省算力（§9.3 那张表的 INT4 列）。

H100 SXM5 的稠密峰值（本书全章统一用这组数）：

精度 稠密峰值 屋脊点（÷ 3.35 TB/s）
FP32 67 TFLOPS 20
BF16 / FP16 989 TFLOPS 295 FLOP/Byte
FP8（E4M3 / E5M2） 1979 TFLOPS 591 FLOP/Byte
INT8 1979 TOPS 591 OP/Byte
HBM3 80 GB（79.6 GiB 可用）/ 3.35 TB/s —

⚠️⚠️ 这里有一个本仓库已经踩过的坑，务必躲开。 规格表里 BF16 除了 989 还有一个 1979，那是 2:4 结构化稀疏的值（要求权重按「每 4 个里恰好 2 个是 0」的模式剪枝），常规推理用不上。拿 1979 当 BF16 稠密值用，屋脊点会算成 591 而不是 295，后面所有「是算力受限还是访存受限」的判断【全部反过来】。
★ 记法：BF16 的稠密值是 989；1979 是 FP8/INT8 的稠密值，也是 BF16 的稀疏值——两个 1979 不是同一回事。

各精度的硬件支持版图：

精度 原生 Tensor Core 从哪一代起 推理里的实际含义
BF16 / FP16 ✅ A100（Ampere） 基准线
INT8 ✅ T4（Turing） A100 上也有，是没有 FP8 的卡的主力方案
★ FP8（E4M3/E5M2） ✅ H100 / H200（Hopper） ★ 显存减半 + 算力翻倍 + 几乎无损，H100 上的默认答案
★ MXFP4 / NVFP4 ✅ B200（Blackwell） 带块缩放（block scale）的 4 位浮点，不是回到 INT4
⚠️ INT4 ⚠️ Hopper 起没有 Turing / Ampere 有，Hopper 移除 ⚠️ 只省搬运（Decode 提速），不省算力

⚠️ INT4 在 Hopper 上那个坑，值得单独说清楚——它会【静默掉速】

    Turing / Ampere（sm_75 / sm_80）：
        ✅ 有真正的 INT4 矩阵指令，PTX 的 mma.s4 会编译成 IMMA.*.S4.S4

    Hopper（sm_90）：
        ✅ wmma 的 experimental::precision::s4 / u4 / b1
           已在 CUDA 文档中【弃用并移除】
        ⚠️ 但 PTX 的 mma.s4 为了前向兼容【仍然能编译通过】，
           只是被翻译成 INT8 模拟（或一串跑在 CUDA Core 上的整数指令）
        ⚠️ wgmma（Hopper 的主力矩阵指令）【压根不支持 INT4】

    Blackwell（sm_100）：
        重新引入的是低精度【浮点】FP4/FP6（NVFP4、MXFP4），走块缩放路线，
        ⚠️ 不是把 INT4 加回来。

⚠️⚠️ 「静默」二字是重点：在 H100 上跑一个依赖 mma.s4 的 kernel，不报错、不拒绝编译，只是悄悄失去 Tensor Core 加速。你看到的是「INT4 怎么比 INT8 还慢」，却找不到任何错误信息。
⟹ ★ 所以在 Hopper 上，INT4 的价值 100% 在「权重存储和带宽」，0% 在「算力」——W4A16 这个名字本身就说明了：A 那一侧是 16 位，因为计算一定要回到 BF16/FP16。（kernel 层面的细节见 大模型算子开发 §6.8.4。）

⚠️ 再纠正一个关于 FP8 精度的常见说法

📖 E4M3 = 1 符号位 + 4 指数位 + 3 尾数位；E5M2 = 1 + 5 + 2。（FP8 只有这两种格式。）

    ⚠️ 常见错误：「E4M3 有 3 位尾数，所以是 3 位有效数字」。
       ★ 把【二进制尾数位数】当成了【十进制有效位数】，这是两回事。

    ✅ 正确算法：E4M3 的有效数是 3 个显式尾数位 + 1 个隐含位 = 4 bit
                 ⟹ log₁₀(2⁴) = 1.204  ⟹ 约【1.2 位十进制】
                 E5M2：2 + 1 = 3 bit  ⟹ log₁₀(2³) ≈ 【0.9 位十进制】

    ✅ 横向对比：
       BF16  8 bit 有效数（7 显式 + 1 隐含）  ⟹ ≈ 2.4 位十进制
       INT8  8 bit                           ⟹ ≈ 2.4 位十进制
       E4M3  4 bit 有效数                     ⟹ ≈ 1.2 位十进制
       INT4  4 bit                           ⟹ ≈ 1.2 位十进制

    ⟹ ★★ 两条反直觉但重要的结论：
       ① E4M3 和 INT4 的【十进制精度是同一个量级】（都约 1.2 位）。
          FP8 赢在【动态范围】（E4M3 能表示 ±448 到 0.002，跨 2¹⁵），
          ★ 不是赢在精度。
       ② ⚠️【没有离群值、分布均匀时，INT8（2.4 位）反而比 E4M3（1.2 位）更准】。
          ⟹ 这也是为什么 INT8 + SmoothQuant 在 A100 上依然是很强的方案，
             不是「只因为 A100 没有 FP8 才凑合用」。

★ 一句话总结这两种 8 位格式的分工：INT8 的绝对误差处处相同（§9.2.1 那条规律①），所以数值小的地方相对误差爆炸；E4M3 的相对误差处处相同（约 6%），所以不管数值多小都保得住——代价是大数那一头反而不如 INT8 准。完整的逐值对照表在 大模型算子开发 §6.5.2。

✅ vLLM 的量化目录直接反映了这个硬件版图：fp8.py、input_quant_fp8.py、fbgemm_fp8.py（FP8 一族）、mxfp4.py（Blackwell）、moe_wna16.py（MoE 专用的权重量化）、experts_int8.py、torchao.py、modelopt.py（对接 NVIDIA 的量化工具链）。★ 从文件数量就能看出：FP8 是当前的主战场。

⚠️ 以下是经验法则，不是论文结论。 任何量化上线前都要跑一遍你自己场景的评测。

方案 权重 激活 KV 省带宽 省算力 要校准 精度风险 最适合

★ FP8 全家桶 FP8 FP8 FP8 2× ✅ 2× 在线算即可 ✅ 极小 ★ H100/H200 的默认答案
W8A8 + SmoothQuant INT8 INT8 — 权重 2× ✅ 2× ⚠️ 需要 中（卡在离群值） A100、大 batch、高吞吐

★ 决策流程——按「你的瓶颈是什么」来走，不要按「哪个位宽低」来走：

① 先确定瓶颈在哪（13 章的指标）
     TPOT 太高、吐字慢      ⟹ Decode 访存受限 ⟹ ★ 量化【权重】
     并发上不去、KV 使用率 >95% ⟹ 显存受限   ⟹ ★ 量化【KV Cache】
     TTFT 太高、且 prompt 很长（>几百 token）⟹ Prefill 算力受限
                                              ⟹ ★ 量化【激活】（W8A8/FP8）
     TTFT 太高、但 prompt 很短  ⟹ ⚠️ 不是算力问题，是【排队】，
                                  去看调度（04 章）和 PD 分离（10 章），不是量化能救的

② 看你的卡有没有 FP8 单元
     H100 / H200 / B200      ⟹ ★ FP8 权重 + FP8 KV，一步到位
     A100 / A6000 / 4090     ⟹ 没有 FP8，走 INT 路线：
                                batch 小 ⟹ W4A16（AWQ）
                                batch 大 ⟹ W8A8 + SmoothQuant

③ batch 有多大（§9.3 算过临界点）
     batch ≲ 77   ⟹ W4A16 收益最大（3.85×）
     77 ~ 295     ⟹ W4A16 开始触顶，FP8/W8A8 更稳
     ≳ 295        ⟹ ★ 只有【也量化激活】的方案还在提速，
                     W4A16 只剩「省显存 / 省卡」的价值

④ 单卡放不下，在「先量化」和「上多卡 TP」之间选
     ⟹ ★ 先量化。TP 要付 AllReduce 的通信代价（06 章 §6.6），
        量化不付。能用量化省下一次跨卡，通常更划算。

⑤ 精度掉了怎么办（按投入从低到高）
     a. ★ 把敏感层排除在量化之外（lm_head、首尾各几层）—— 最便宜最有效
     b. 细化粒度：per-tensor → per-channel → per-group(128) → per-group(32)
     c. 换算法：RTN → AWQ → GPTQ（或叠加）
     d. 量化激活时加 SmoothQuant / 调大 α
     e. 降低野心：INT4 退回 INT8，或只量化权重不量化 KV

★ 步骤 ⑤ 的 a 永远先试。 lm_head 和头尾几层贡献了绝大部分的量化敏感度，把它们留在 BF16 只多占几百 MB，却常常能把掉下去的精度救回来大半。所有量化工具都提供这个开关（HuggingFace 系叫 modules_to_not_convert）。

⚠️⚠️ 最后一条，也是最重要的一条：论文里的困惑度持平，不代表你的业务指标持平。 困惑度是在维基百科文本上算的平均值，它对「偶尔一个 token 选错」非常不敏感；而你的业务可能恰恰卡在那个 token 上——JSON 里少个引号、工具调用的函数名拼错、长链推理在第 7 步走偏。⟹ 上线前必须用你自己的评测集跑一遍，看的是业务指标，不是 PPL。

9.10 本章小结

  ① ★ 推理量化 ≠ 训练量化：推理是访存受限，
     权重位宽减半 ⟹ 搬运减半 ⟹ ★ Decode 直接提速。
     训练量化只是「省显存」。

  ② ★★ 量化省的是【绝对时间】，不是【相对位置】（§9.3）
     算术强度翻倍，屋脊点也翻倍 ⟹ 在屋顶线上纹丝不动，
     ⟹ 但搬的字节少了一半，时间就少了一半。
     ⟹ ⚠️ 说「利用率低」必须讲口径：算力 0.34%，带宽接近 100%。

  ③ 三个【互相独立】的量化对象，买的东西完全不同：
     权重     ⟹ TPOT（吐字快）      W4A16 最常见
     激活值   ⟹ TTFT（长 prompt）   要处理离群值，最难
     KV Cache ⟹ ★★ 并发数（+100%）  最直接的吞吐收益

  ④ 所有量化的算术都是同一套（§9.2）：
     scale 由【组里最大的那个数】独家决定
     ⟹ 绝对误差处处相同 ⟹ 小数值的相对误差最大
     ⟹ 离群值把 scale 撑粗 100 倍 ⟹ 其余元素只剩 1.6 比特
     ⟹ 细粒度能【隔离】伤害，但救不了和大数【同组】的那位

  ⑤ 权重量化两大流派，目标函数是同一个（最小化【整层输出】误差）：
     GPTQ：错了当场补，用 Hessian（输入相关矩阵）分摊
     AWQ ：★ 全部 INT4 + 等价逐通道缩放，
           ⚠️ 不是「保留 1% FP16」——那是被论文否决的对照实验
     ⟹ 实践默认 AWQ，理由是对校准集分布不挑食

  ⑥ 激活量化的拦路虎是【离群值】（整个通道都大）
     ⟹ SmoothQuant：X/s 配 W·s，数学等价，把难度对半分给权重
     ⟹ ★ 动态/静态 = scale【何时定】，和离群值【正交】，别混为一谈

  ⑦ ★ 硬件是裁判：
     FP8 从 H100 起原生；MXFP4 从 Blackwell 起原生
     ⚠️ INT4 在 Hopper 上【没有】Tensor Core，还会【静默掉速】
     ⚠️ BF16 稠密是 989 不是 1979（1979 是稀疏值 / FP8 值）
     ⚠️ E4M3 约 1.2 位十进制，和 INT4 同量级；
        FP8 赢在【动态范围】，没有离群值时 INT8 反而更准
