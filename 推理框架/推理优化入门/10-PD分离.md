## 10.1 03 章遗留的问题

回顾一下混合批（chunked prefill）解决了什么、没解决什么：

```
    ✅ 解决了：Decode 用户不再被 Prefill 卡住（无停顿）
    ✅ 解决了：单步算术强度被顶上去，GPU 吃得满

    ⚠️ 没解决的三件事：
      ① 两个阶段的【最优并行策略】不同，混在一起只能用一套
      ② 两个阶段仍在【互相干扰】——Prefill 的大块计算
         会让同批 Decode 的延迟出现抖动
      ③ ★ 两个阶段对【硬件】的需求都不同：
         Prefill 要算力 ⟹ 想要 H100
         Decode 要带宽和显存 ⟹ ★ 便宜的老卡（A100）可能性价比更高
```

> ★★ **PD 分离的立论**：既然是两种性质不同的工作负载，就应该像微服务一样**拆成两个独立集群**，各自按自己的最优方式配置和扩缩容。

## 10.2 ★★ 先看一个具体例子：一次 RAG 问答

抽象的"两个集群"很难有感觉。我们把一个真实请求从头到尾走一遍。

### 场景设定

```
    模型：Llama-3-8B（fp16，权重 16 GB）
    卡  ：H100（BF16 稠密算力 ~989 TFLOPS，显存带宽 3.35 TB/s）

    ★ 当前状态：8 个老用户正在打字（都处在 Decode 阶段）
    ★ 新来的第 9 个用户：RAG 问答
       ├─ 输入：一份文档 + 问题 = 【4096 个 token】  ⟸ Prefill 要干的活
       └─ 输出：200 个字                            ⟸ Decode 要干的活
```

> ⚠️ 下面所有毫秒数都是**按 roofline 粗算的量级估计**（算力/带宽 × 一个经验利用率），
> 不是实测值。★ 看**相对关系**，不要记绝对数字。

**两个基准耗时**（⚠️ 估算，单张 H100）：

```
    ① Prefill 4096 token 要多少算力？
       FLOPs ≈ 2 × 参数量 × token 数 = 2 × 8e9 × 4096 ≈ 65 TFLOPs
       按 40% 利用率（≈400 TFLOPS 有效）⟹ 65 / 400 ≈ ★ 165 ms

    ② Decode 一个 token 要多少时间？
       每步必须把【全部 16 GB 权重】搬一遍（01 章：访存受限）
       按 70% 带宽利用率（≈2.3 TB/s）⟹ 16 / 2300 ≈ ★ 7 ms
       ⟹ 200 个字 ≈ 1.4 秒
```

### 剧情 A：不分离（chunked prefill 混部，03/04 章的方案）

只有 1 张卡，它既要伺候 8 个老用户吐字，又要给新用户读那 4096 个 token。
chunked prefill 的做法是：**把 4096 切成 8 块，每块 512 token，掺进 decode 批次里一起算**。

```
    时间轴 ──────────────────────────────────────────────────►

    正常时（没有新请求）：
    [7ms][7ms][7ms][7ms]  ⟸ 8 个老用户，每 7ms 每人吐一个字

    第 9 个用户来了之后的 8 步：
    [ 27ms ][ 27ms ][ 27ms ][ 27ms ][ 27ms ][ 27ms ][ 27ms ][ 27ms ]
      ↑每步 = 8 个 decode token + ★ 512 个 prefill token 一起算
       512 个 token 的算力 ≈ 2×8e9×512/400e12 ≈ 20ms，加原来的 7ms

    ⟹ ★★ 老用户的感受：打字速度从 7ms/字 【掉到 27ms/字】，慢了近 4 倍，
       而且这个"卡顿"持续 8×27 ≈ 216 ms
    ⟹ 新用户的 TTFT（首字延迟）= 216 ms
```

> 🔑 **看懂这里就看懂了 PD 分离的动机**：
> chunked prefill 把"一次 300ms 的大停顿"摊成了"8 次 20ms 的小停顿"——
> ★ 停顿变平滑了，**但总量一点没少**。老用户该慢还是慢。
> ⟹ 因为**算力就那么多，两个人分，谁都快不了**。

### 剧情 B：分离（2 张卡：1 张 P + 1 张 D）

```
   ① 路由器收到第 9 个用户的请求
      ⟹ 看到它是新请求（要 Prefill），派给 【P 卡】
      ★ D 卡完全不知道这件事，8 个老用户【一个字都没慢】

   ② P 卡独占算力跑 4096 token 的 Prefill
      ⟹ 165 ms，产出【4096 个位置的完整 KV Cache】
      ⟹ 同时采样出第 1 个字（比如"根"）

   ③ ★★★ 把 KV Cache 搬到 D 卡（本方案唯一的额外成本）
      4096 token × 128 KB/token = 【512 MB】
      走 400 Gbps InfiniBand（50 GB/s）⟹ 约 10 ms
      ★ 而且这 10ms 还能和第 ② 步【重叠】掉大半（见 §10.6 的分层传输）

   ④ D 卡接过 KV，把第 9 个用户【加进正在跑的批次】
      ⟹ 从此他和另外 8 个人一样，每 7ms 吐一个字

   ⟹ 新用户 TTFT = 165 + 10 ≈ 175 ms
   ⟹ ★★ 老用户 TPOT 全程 7ms，【零抖动】
```

### ⚠️ 但这个对比不公平——补上诚实的那一栏

剧情 B 用了 2 张卡，剧情 A 只用了 1 张。**必须按同样的卡数再比一次**：

```
┌─────────────┬──────────────────┬──────────────────┬──────────────────┐
│  2 张卡怎么用 │ ⓐ 混部×2         │ ⓑ 分离 1P+1D     │ ⓒ 分离 2P+0D ✗  │
├─────────────┼──────────────────┼──────────────────┼──────────────────┤
│  拓扑        │ 两张卡各跑一个完 │ 一张只 Prefill    │ 配比错了的反例    │
│             │ 整实例，各管一半 │ 一张只 Decode     │                  │
│             │ 用户            │                  │                  │
├─────────────┼──────────────────┼──────────────────┼──────────────────┤
│  老用户 TPOT │ ⚠️ 27ms（抖动）  │ ✅ 7ms（平稳）    │ ✗ D 卡不够，      │
│             │ ——但只影响落在   │                  │   老用户全体排队  │
│             │   那张卡的一半人 │                  │                  │
├─────────────┼──────────────────┼──────────────────┼──────────────────┤
│  新用户 TTFT │ 216 ms           │ ✅ 175 ms         │ ✅ 165 ms        │
├─────────────┼──────────────────┼──────────────────┼──────────────────┤
│  额外要求    │ ✅ 无             │ ⚠️ RDMA 网络      │ ⚠️ RDMA 网络     │
│             │                  │ ⚠️ 一个路由器     │                  │
└─────────────┴──────────────────┴──────────────────┴──────────────────┘
```

```
    ★★ 真正的结论（三句话）：
      ① 同样的卡数下，分离能把【干扰】消掉 ⟹ TPOT 平稳、TTFT 也更好
      ② 代价是 512 MB 的 KV 必须搬过去 ⟹ ★ 没有 RDMA 就别做（§10.6）
      ③ ★★ P:D 配比一旦错了（列 ⓒ），比混部还差 ⟹ 这是运维的持续难题（§10.7）
```

> ⚠️ **为什么 ⓐ 拆成两张卡，那 27ms 却没变好？**
> 因为 Decode 那 7ms 是【搬 16 GB 权重】的时间（01 章：访存受限），
> ★ 用户从 8 个减到 4 个，权重还是要搬同样一遍 ⟹ 7ms 一点不变。
> 而掺进来的 512 个 prefill token 是实打实的算力 ⟹ 那 20ms 也一点不减。
> ⟹ ★★ **单纯"多买一张卡分流"救不了干扰，只有"把两种活分开"才行。**

### ★ 一个必须想通的问题：D 卡凭什么能接着往下生成？

小白最容易卡在这：**这份 prompt 是 P 卡算的，D 卡从头到尾没见过它，怎么就能续写？**

```
    ⟹ 因为 Transformer 生成第 n+1 个字时，需要的【全部历史信息】
       就只有两样东西：

       ① ★★ KV Cache —— 前面 4096 个位置、每一层算出来的 K 和 V
          形状：[32 层] × [K 和 V 两份] × [4096 个位置] × [8 个 KV 头 × 128 维]
          ⟹ 这就是那 512 MB 的全部内容

       ② 上一步吐出来的那个 token（"根"）

    ★ 把这两样搬过去，D 卡就"什么都知道了"——
      它不需要重算 prompt，也不需要看到原始文本。
      ⟹ ★★ 【KV Cache 就是这次对话的全部记忆，它是可以搬家的】
      ⟹ 这一句是 PD 分离能成立的全部理由，也是 Mooncake
        "以 KVCache 为中心"那句主张的根。
```

> ⚠️ 512 MB 这个数字怎么来的（**推算，非论文披露**）：
> Llama-3-8B 有 32 层、8 个 KV 头（GQA）、每头 128 维、fp16 每个数 2 字节。
> 每 token = 2(K和V) × 32 × 8 × 128 × 2 字节 = **128 KB**；× 4096 token = **512 MB**。
> ★ 这个算法在 02 章（KV Cache 与显存账）有完整推导。

## 10.3 架构长什么样

```
    用户请求
       │
       ▼
   ┌───────────┐
   │  路由器    │  ★ 决定这个请求去哪个 P 实例、哪个 D 实例
   └─────┬─────┘
         ▼
   ┌─────────────────────┐
   │  Prefill 集群 (P)    │  ★ 算力受限 ⟹ 大 TP、追求算力
   │  ┌────┐ ┌────┐      │     跑完 prompt，产出【完整的 KV Cache】
   │  │ P0 │ │ P1 │ ...  │
   │  └────┘ └────┘      │
   └──────────┬──────────┘
              │  ★★★ 传输 KV Cache ← 这是整个方案的成败关键
              ▼
   ┌─────────────────────┐
   │  Decode 集群 (D)     │  ★ 访存受限 ⟹ 小 TP、大 DP、追求显存和并发
   │  ┌────┐ ┌────┐      │     接过 KV，开始逐字生成
   │  │ D0 │ │ D1 │ ...  │
   │  └────┘ └────┘      │
   └──────────┬──────────┘
              ▼
          流式返回给用户
```

**分离后各自能做的最优选择**（★ 这是全部收益的来源）：

```
┌──────────────┬────────────────────┬────────────────────────┐
│              │  Prefill 集群       │  Decode 集群            │
├──────────────┼────────────────────┼────────────────────────┤
│  并行策略     │ ★ 大 TP（算力受限， │ ★ 小 TP + 大 DP        │
│              │   加卡有效）        │  （加 TP 收益递减）     │
├──────────────┼────────────────────┼────────────────────────┤
│  批策略      │ 小 batch 即可打满   │ ★ 尽可能大的 batch      │
│              │ （单个长 prompt 就  │  （要把算术强度顶上去） │
│              │   够撑满算力）      │                        │
├──────────────┼────────────────────┼────────────────────────┤
│  硬件        │ 算力强的卡          │ ★ 显存大、带宽高、       │
│              │                    │   可以是更便宜的卡       │
├──────────────┼────────────────────┼────────────────────────┤
│  扩缩容      │ ★ 按【输入 token 量】│ ★ 按【输出 token 量】    │
│              │   独立扩缩          │   独立扩缩              │
├──────────────┼────────────────────┼────────────────────────┤
│  优化目标     │  TTFT              │  TPOT                  │
└──────────────┴────────────────────┴────────────────────────┘
```

> 🔑 **第 4 行是被低估的一条**。真实业务的 P:D 比例（输入长度 : 输出长度）随时间波动很大——
> 白天大家问长文档（P 重），晚上大家闲聊（D 重）。
> **合在一起，你只能整体扩容；分开了，才能各扩各的。**

> ⚠️ **但第 1 行「大 TP vs 小 TP + 大 DP」这句话很容易被误解**——它说的只是注意力那一段，
> 不是「D 侧每张卡放一份完整模型」。**下一节（§10.4）用一个 505B 的 MoE 把它整个拆开。**

## 10.4 ★★ 「P 用大 TP、D 用大 DP」到底是怎么切的

> 上一节那张表里，「大 TP」和「小 TP + 大 DP」只是两行字。这一节把它拆开——
> **因为这是本章最容易被误解的一句话，而且误解的方向很危险。**
>
> 全程用一个真实模型当例子：**openPangu-2.0-Pro，505B 总参 / 18B 激活的 MoE**
> （架构见 [业界模型技术报告/openPangu-2.0-Pro.md](../../业界模型技术报告/openPangu-2.0-Pro.md)）。
> 设定：**P 实例 32 卡、D 实例 32 卡**。

### ★ 先破一个误解

```
    ★ 常听到的说法：「P 侧全用 TP=32，D 侧全用 DP」

    ⚠️ 这句话【省略了主语】——它说的只是【注意力那一段】。

      ① MoE 那一段，P 和 D 【都是 EP】，切法一模一样
      ② D 侧的 DP【不是】「每张卡放一份完整模型」
         ⟹ 505B 就算 W8A8 也要 ~505 GB，没有任何一张卡装得下一个副本
      ③ 32 张卡从头到尾都是切开的，只是【切的维度换了】
```

回收 [06 章 §6.3 ④](06-推理中的并行策略.md) 的一条源码事实：**vLLM 里 EP 组不是你手配的一维，它是 `DP × PCP × TP` 三个维度合并出来的**（`parallel_state.py:1923`）：

```
    TP=32, DP=1   + 开专家并行  ⟹  EP 自动 = 32
    TP=1,  DP=32  + 开专家并行  ⟹  EP 还是 = 32

    ★★ 同一批 32 张卡，【MoE 层的视角完全没变】。
       变的只是「注意力层怎么用这 32 张卡」。
```

### 10.4.1 先把模型拆成三块，因为三块的切法根本不同

📖 **MLA**（**M**ulti-head **L**atent **A**ttention，多头潜在注意力）——把 KV 压成一个低秩"潜向量"再存，KV cache 因此小很多（[07 章](07-注意力变体MQA-GQA-MLA.md)）。★ 它是下面整节的关键角色。

⚠️ 参数量按 openPangu Table 8 的配置推算（50 层 = 3 dense + 47 MoE，hidden 5120，64 头，MLA 的 KV 秩 512 + RoPE 维 64，路由专家 384 + 共享 1，专家中间维 1792）：

```
┌─────────────────┬──────────┬───────────────────────────────────────┐
│ 权重块          │ 参数量   │ 能怎么切                              │
├─────────────────┼──────────┼───────────────────────────────────────┤
│ 路由专家 ×384   │ 497 B    │ ★★ 只能 EP：单个专家才 27.5M，      │
│ （占 98.4%）    │          │   TP 再切 32 份 ⟹ 1792/32 = 56 维    │
│                 │          │   矩阵小到算子跑不满（11 章 §11.2）   │
├─────────────────┼──────────┼───────────────────────────────────────┤
│ MLA 注意力      │ 4.0 B    │ TP 行（按头切）、DP 也行（复制）      │
│                 │          │ ★★ 全部的分歧就在这一块             │
├─────────────────┼──────────┼───────────────────────────────────────┤
│ Dense FFN +     │ 3.6 B    │ 都行。量太小，怎么切都不影响大局      │
│ 共享专家 + 词表 │          │                                       │
└─────────────────┴──────────┴───────────────────────────────────────┘

    ⟹ ★ 498 B（98%）的专家参数，P 和 D 都是 EP=32，各卡 384/32 = 12 个完整专家。
       所谓「P 用 TP、D 用 DP」的全部争议，是在那 4 B 的注意力权重上。
```

### 10.4.2 P 侧（TP=32）每张卡拿到什么

```
  注意力（每层）
    ├─ W^DQ  (5120×1536) ┐  这两个矩阵【不带「头」这一维】
    ├─ W^DKV (5120×576)  ┘  ⟹ ★ 切不了，32 张卡各存一份（复制）≈ 10.8M/层
    └─ W^UQ / W^UK / W^UV / W^O   ≈ 69.2M/层，带头维
                                  ⟹ 64 头 ÷ 32 = ★ 每卡 2 个头
    ⟹ 每卡 ≈ 12.96M/层 × 50 层 ≈ 0.65 B
       （理想切法只要 0.125 B，多出来的 0.54 B 就是那份「切不动只能复制」的低秩投影）

  Dense FFN（3 层）
    16128 ÷ 32 = 每卡 504 维      ← 列切 gate/up、行切 down，每层一次 all-reduce

  MoE（47 层）
    384 专家 ÷ 32 = 每卡 12 个【完整】专家 ≈ 15.5 B     ← ★ 这是 EP，不是 TP

  ──────────────────────────────────────────
  每卡合计 ≈ 16.3 B ≈ 16.3 GB @ W8A8
```

> ⚠️ **一个真实系统里的细节**：openPangu 报告写的 prefill 注意力**并不是「全 TP」**，
> 而是 **DSA 层走 CP、SWA 层走 TP**（CP 方案代号 **Felix**）。
> 📖 **DSA**（Deep / DeepSeek **S**parse **A**ttention，稀疏注意力）——每个 token 只挑固定数量（openPangu 是 2048 个）的历史 KV 参与计算，但**要在全序列范围里挑**。
> 📖 **SWA**（**S**liding **W**indow **A**ttention，滑动窗口注意力）——只看最近固定窗口（openPangu 是 512）内的 token。
>
> 理由很直白——DSA 层要看全序列，128K 的 prompt 切序列（CP）比切头划算；
> SWA 层窗口只有 512，切序列没有意义，切头就够了。
> **⟹ 「P 侧大 TP」是个粗略说法，真实配置往往是 CP 和 TP 混着上。**

### 10.4.3 D 侧（Attention DP=32）每张卡拿到什么

```
  注意力
    ⟹ ★ 不切了。4.0 B 权重，32 张卡各存一份完整的
    ⟹ 每张卡处理【不同的请求】，注意力算完【一次通信都不用】

  Dense FFN / 共享专家 / 词表
    ⟹ 跟着注意力一起复制（它们和注意力在同一条「非 MoE」路径上）

  MoE
    ⟹ 还是 EP=32，每卡 12 个专家        ← ★★ 和 P 侧一模一样

  ──────────────────────────────────────────
  每卡 ≈ 15.5(专家) + 4.0(注意力) + 3.6(其余) ≈ 23 GB @ W8A8
  ★ 比 P 侧多花约 7 GB/卡。买的就是下面这条。
```

### 10.4.4 ★★ 为什么 decode 必须反着来——三条理由，第 ② 条是决定性的

#### ① decode 的矩阵已经小到切不动了

```
    prefill：一次进 128K token，每卡 2 个头
             ⟹ GEMM 形状 131072 × 2 × 128    ← ★ 算子吃得饱，切了确实快

    decode ：一次只进 batch=40 个 token，每卡 2 个头
             ⟹ GEMM 形状 40 × 2 × 128        ← ★ 算子空转，
                                               时间全花在 all-reduce 和 kernel 启动上
```

这就是 §10.3 那句「Prefill 算力受限 ⟹ 大 TP 加卡有效；Decode 访存受限 ⟹ 加 TP 收益递减」的**具体形状**。

#### ② ★★★ MLA 在 decode 端吸收成 MQA 之后，KV cache 按头切不动了，只能整份复制

```
    ★ MLA 有两种等价的算法形态（07 章）：
        Non-Absorptive（训练 / prefill）⟹ 展开成 MHA，有 64 个头
        Absorptive    （decode）      ⟹ ★ 等价于 MQA，KV 只剩【1 个头】

    ★ TP 的前提是「按头切」。KV 只剩 1 个头 ⟹ 32 张卡怎么切？
    ⟹ 切不了，只能【32 张卡各存一份完全相同的 KV cache】
```

⚠️ 按上面的配置推一笔账（KV 秩 512 + RoPE 维 64 = 576，bf16，DSA:SWA = 1:2）：

```
    单条 128K 序列的 KV cache：
      17 个 DSA 层：17 × 576 × 2B × 131072  ≈ 2.5 GB   ← 随上下文线性增长
      33 个 SWA 层：33 × 576 × 2B × 512     ≈  19 MB   ← 窗口 512，★ 恒定
      ─────────────────────────────────────  ≈ 2.5 GB / 条

    TP=32 ：32 张卡各存【同一条】的 2.5 GB ⟹ 花掉 80 GB 只服务【1 个】用户
    DP=32 ：32 张卡各存【不同的】2.5 GB   ⟹ 同样 80 GB 服务【32 个】用户

    ⟹ ★★★ 同样的显存，并发差 32 倍。这才是 Attention DP 的真正动机。
```

> ★ [06 章 §6.3 ⑤](06-推理中的并行策略.md) 那个 **DCP**（Decode Context Parallel）就是来补同一个洞的——
> 在 TP 组内部按序列维再切 KV，让「TP 超过 KV 头数后 KV 被白白复制」这件事不发生。
> **Attention DP 和 DCP 是同一种病的两种药**：前者换请求维、后者换序列维。

#### ③ DP 把有效 batch 放大了 32 倍，MoE 的 all-to-all 才划算

```
    TP=32：32 张卡在算【同一批】40 个 token
           ⟹ 全系统只有 40 个 token 要路由给 384 个专家
           ⟹ 每个专家平均分到 40×8/384 < 1 个 token ⟹ all-to-all 纯亏

    DP=32：32 张卡在算【32 批不同的】40 个 token = 1280 个 token
           ⟹ 每个专家平均 1280×8/384 ≈ 27 个 token ⟹ 专家 GEMM 才有形状

    ⟹ ★★ 注意力想要 DP、MoE 想要 EP，而【DP 恰好在喂饱 EP】。
       这是 [11 章 §11.7](11-MoE推理与专家并行.md) 那张图的另一半。
```

### 10.4.5 ⚠️ DP 不是白拿的，三条代价

```
    ⚠️ ① 多花 ~7 GB/卡 复制注意力 + dense + 词表（§10.4.3 算过）

    ⚠️ ② ★ 32 个 DP rank 必须【步调一致地一起 generate】
          因为 MoE 的 all-to-all 是跨 DP 组的集合通信，
          某张卡这一步没请求，也得塞一个【假 batch（dummy run）】进去凑数，
          否则另外 31 张卡永远在等它。
          ⟹ vLLM 源码注释写死了这条（06 章 §6.3 ③）

    ⚠️ ③ P 和 D 的专家热度分布不同 ⟹ EPLB 要【分两套配】（11 章 §11.5）
```

### ★ 本节一句话

```
┌────────────────────────────────────────────────────────────────────┐
│  「P 用 TP、D 用 DP」说的只是【注意力】那 4 B。                    │
│   占 98% 的专家参数，两边都是 EP，切法完全相同。                   │
│                                                                    │
│   P 侧选 TP：prompt 长 ⟹ GEMM 大 ⟹ 切开真能压 TTFT               │
│   D 侧选 DP：① GEMM 已经小到切不动                                 │
│              ② ★★ MLA 吸收成 MQA 后 KV 按头切不动，              │
│                 TP 会把 KV cache 复制 32 份 ⟹ 并发掉 32 倍        │
│              ③ DP 放大有效 batch，正好喂饱 MoE 的 all-to-all       │
└────────────────────────────────────────────────────────────────────┘
```

## 10.5 三篇代表论文，三个不同的出发点

### ① DistServe——从「goodput」这个指标出发

> ✅ arXiv 2401.09670（`papers/DistServe-Prefill-Decode-Disaggregation-arXiv-2401.09670.pdf`）

论文先定义了一个关键指标（✅ 原文）：

> *"maximize per-GPU **goodput**, defined as the maximum request rate that can be served adhering to the SLO attainment goal"*

> 📖 **goodput（有效吞吐）**——**在满足延迟承诺（SLO）的前提下**，每张 GPU 每秒能服务的请求数。
> ★ 和普通 throughput 的区别：**跑得再快，超了 SLO 就不算数。**
> ⟹ 这个指标是整个 PD 分离领域的立论基础。

**结果**（✅ 论文摘要原文）：

> *"DistServe can serve **7.4× more requests** or **12.6× tighter SLO**, compared to state-of-the-art systems, while staying within latency constraints"*

### ② Splitwise——从「成本和功耗」出发

> ✅ arXiv 2311.18677（`papers/Splitwise-Phase-Splitting-arXiv-2311.18677.pdf`），Microsoft

```
    ★ 视角不同：微软关心的是【数据中心怎么配机器最省钱省电】
    ⟹ 提出【异构集群】：Prefill 用新卡，Decode 用老卡
```

**结果**（✅ 论文摘要原文）：

> *"Splitwise clusters achieve up to **1.4× higher throughput at 20% lower cost**. Alternatively, they can deliver **2.35× more throughput under the same power and cost budgets**."*

### ③ Mooncake——从「真实线上系统」出发

> ✅ arXiv 2407.00079（`papers/Mooncake-KVCache-Centric-arXiv-2407.00079.pdf`），月之暗面（Kimi）

```
    ★ 这是唯一一篇【从生产系统里长出来】的论文，
      所以它关心的问题最"脏"，也最实用：

      ★★ 核心主张：以 KVCache 为中心（KVCache-centric）
         把整个集群的 CPU 内存、SSD 都organize 成一个
         【分布式 KV Cache 池】，而不只是点对点传一次。
      ⟹ 于是前缀缓存（05 章）也变成了【全局共享】的：
         P 实例算过的 KV，其他实例也能命中
      ★ 还包含一个很现实的东西：【基于预测的早期拒绝】
         ——过载时提前拒掉注定超 SLO 的请求，而不是让所有人一起慢
```

**结果**（✅ 论文摘要原文）：

> *"Mooncake can achieve up to a **525% increase in throughput** in certain simulated scenarios while adhering to SLOs. Under real workloads, Mooncake's innovative architecture enables Kimi to handle **75% more requests**."*

> ⚠️ **注意这两个数字的差别**：525% 是**模拟场景**，75% 是**真实负载**。
> ★ 论文自己把它们区分得很清楚，我们引用时也要区分。**真实世界的收益永远小于最优场景。**

## 10.6 ★★ 成败关键：KV Cache 怎么传过去

这是 PD 分离唯一的、也是致命的成本。先算一笔账：

```
    Llama-3-8B，一个 4K 长度的 prompt（⚠️ 推算，来源见 §10.2 末尾）：
      KV = 128 KB/token × 4096 = ★ 512 MB

    走 100 Gbps 以太网（12.5 GB/s）：512 MB ÷ 12.5 GB/s ≈ 41 ms
    走 400 Gbps InfiniBand (50 GB/s)：              ≈ 10 ms
    ★ 走 NVLink（900 GB/s）：                       ≈ 0.6 ms

    ⟹ ★★ 如果 Prefill 本身只花 100 ms，
       那 41 ms 的传输就是【41% 的额外延迟】，收益被吃掉一大半。
    ⟹ ★★★ 所以 PD 分离几乎必然要求【高速互联】(RDMA/InfiniBand)。
       在普通以太网集群上做 PD 分离，大概率是负收益。
```

> 📖 **RDMA**（**R**emote **D**irect **M**emory **A**ccess，远程直接内存访问）——
> 网卡直接读写对端显存/内存，**不经过 CPU、不经过内核协议栈**。这是 PD 分离能落地的硬件前提。

**三个降低传输成本的关键技巧**：

```
    ★ ① 分层传输（layer-wise / 边算边传）
       不要等整个 prompt 算完再传。
       ⟹ 第 1 层算完就传第 1 层的 KV，同时算第 2 层
       ⟹ ★★ 传输和计算【重叠】，隐藏掉大部分传输时间
       ⟹ 这是最重要的一条

    ★ ② 只传需要的部分
       如果 D 实例本地已经有部分前缀缓存，就只传差集

    ★ ③ 直接写进对端的 KV 块
       用 RDMA 把数据直接落到 D 实例的 PagedAttention 块里，
       ⟹ 省掉一次拷贝
```

**框架里这一层叫「KV 连接器」，做成了可插拔的**：

> ✅ **vLLM**（[kv_transfer/kv_connector/v1/](../源码/vLLM/vllm/distributed/kv_transfer/kv_connector/v1/)）：
> `base.py` 定义接口，实现有 `nixl/`（NVIDIA 的 RDMA 传输库）、`mooncake/`、
> `lmcache_connector.py`、`moriio/`、`hf3fs/`、`offloading/`、
> ★ `multi_connector.py`（可以把多个后端串起来，比如先查本地再查远端）。
>
> ✅ **SGLang**（[disaggregation/](../源码/SGLang/python/sglang/srt/disaggregation/)）：
> `prefill.py` / `decode.py` 是两端的主逻辑，
> 后端有 `nixl/`、`mooncake/`、`mori/`、`ascend/`（昇腾），
> ★ 还有 `fake/`（用来在没有 RDMA 的环境下做功能测试——很实用的工程设计），
> 以及 `decode_kvcache_offload_manager.py`（★ D 端的 KV 换出到 CPU/SSD）。

> 📖 **NIXL**（NVIDIA Inference Xfer Library）——NVIDIA 的推理数据传输库，
> 是目前两个框架都在用的主流 RDMA 后端。

## 10.7 ⚠️ PD 分离的代价，以及什么时候【不该用】

```
    ⚠️ ① 运维复杂度【显著上升】
       两个集群、一个路由器、一套 KV 传输通道，都要监控和调优
       ⟹ ★ 对小规模部署，这个复杂度不值得

    ⚠️ ② 需要 RDMA 网络（见 §10.6 的账）

    ⚠️ ③ ★ 短 prompt 场景是【负收益】
       prompt 只有 50 字，Prefill 本身 5 ms，
       传 KV 却要 1 ms + 一次网络往返 ⟹ 净亏

    ⚠️ ④ 资源配比是个持续调优问题
       P:D 机器数配错了，某一边就会成为瓶颈，
       另一边的卡在空转 ⟹ 反而不如混部
```

```
    ★★ 什么时候该上 PD 分离（⚠️ 经验判断）：
       ✅ 规模足够大（几十张卡以上），有 RDMA
       ✅ 长 prompt 场景（RAG、长文档、代码库问答）
       ✅ 有明确的、分别针对 TTFT 和 TPOT 的 SLO
       ✅ P:D 比例波动大，需要独立扩缩容

       ❌ 单机 8 卡以内 ⟹ 老老实实用 chunked prefill
       ❌ 短 prompt 为主的聊天场景
       ❌ 没有 RDMA
```
