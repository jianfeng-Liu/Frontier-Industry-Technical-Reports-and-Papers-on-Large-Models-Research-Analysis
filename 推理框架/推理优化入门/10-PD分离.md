# 10 PD 分离（Prefill / Decode Disaggregation）

> **一句话**：03 章发现两个阶段性格相反、最优配置冲突。这一章的答案很暴力——**把它们放到不同的机器上去**。
>
> ★ 没感觉的话，直接跳到 **§10.2** —— 那里有一个 4K 文档 RAG 问答的完整例子，把「混部」和「分离」两种剧情按毫秒逐帧放了一遍，**并且诚实地算出了「2 张卡的小规模下分离其实不划算」**。
>
> ⚠️ **本章立论有一个前提，读之前必须先知道**：「Prefill 算力受限、Decode 访存受限」这句话**不是无条件的**。Prefill 的算术强度大致等于 prompt 长度，**prompt 短于几百个 token 时它和 Decode 一样访存受限**。PD 分离的全部收益都建在「prompt 足够长」这个前提上（§10.1 末尾、§10.2.7）。

## 10.0 本章的固定配置

全章只用一个模型、一张卡，所有数字都能互相对上。⚠️ 和 [03 章](03-Prefill与Decode两阶段.md)、[大模型算子开发 09 章](../../大模型算子开发/09-推理侧算子.md) 用的是同一套配置。

| 量 | 值 | 说明 |
|---|---|---|
| 模型 | Llama-3-8B | 官方 `config.json` |
| 参数量 | 8.03 B | 主体 6.98 B + embedding 0.53 B + lm_head 0.53 B |
| 层数 L / 隐藏维 H | 32 / 4096 | — |
| Query 头数 / **KV 头数** | 32 / **8** | ★ GQA，KV 头只有 Q 头的 1/4 |
| head_dim | 128 | — |
| 数据类型 | BF16 | 2 字节/元素 |
| **权重显存** | **16.1 GB** | = 8.03 B × 2 |
| **KV Cache 单价** | **128 KiB / token** | ★ 全章反复用，推导见 [02 章 §2.2](02-KV-Cache与显存账.md) |
| 硬件 | **H100 SXM5** | 132 SM，**HBM3 80 GB / 3.35 TB/s**，BF16 **稠密** 峰值 **989 TFLOPS** |
| **屋脊点** | **295 FLOP/Byte** | = 989 ÷ 3.35 |

> ⚠️ **989 是稠密峰值。** 官方规格表里那个 **1979 TFLOPS 是「带 2:4 结构化稀疏」的**，常规推理算子用不上。全系列统一用 989 / 屋脊点 295。
>
> ⚠️ **本章用两套折扣，请先记住**：Prefill 按 **40% 算力利用率**（≈ **396 TFLOPS** 有效），Decode 按 **70% 带宽利用率**（≈ **2.345 TB/s** 有效）。这两个折扣是经验值，**不是实测**，换个框架换个版本就会变。★ 看**相对关系**，不要记绝对毫秒数。
>
> ⚠️ **容量用 GiB，带宽用 GB。** 显存侧的一切（`nvidia-smi`、KV 块大小）都是 2 的幂，用 **GiB**（1 GiB = 2³⁰ 字节）；带宽标称值（3.35 TB/s、50 GB/s）是十进制，用 **GB**。两者差 7%，**混着用是本主题最常见的错账来源**。换算：**512 MiB = 537 MB**。

**本章会反复出现的缩写，先一次性给全称**：

> 📖 **TTFT**（**T**ime **T**o **F**irst **T**oken，首字延迟）——从请求发出到吐出第 1 个字。**Prefill 决定它。**
> 📖 **TPOT**（**T**ime **P**er **O**utput **T**oken，每字延迟）——生成阶段平均每个字的间隔。**Decode 决定它。**
> 📖 **TBT**（**T**ime **B**etween **T**okens，相邻两字间隔）——⚠️ 和 TPOT 的区别：TPOT 是**平均值**，TBT 是**每一次**的实测值。★ 用户抱怨「卡了一下」，卡的是 **TBT 的尖峰**，平均值可能一点没变（[13 章 §13.1.2](13-性能指标与压测.md)）。
> 📖 **SLO**（**S**ervice **L**evel **O**bjective，服务等级目标）——对外承诺的延迟上限，例如「P99 的 TTFT 不超过 500 ms」。
> 📖 **KV Cache**（键值缓存）——把历史每个 token、每一层算出的 K 和 V 存下来，生成下一个字时直接读，不用重算（[02 章](02-KV-Cache与显存账.md)）。
> 📖 **GQA**（**G**rouped-**Q**uery **A**ttention，分组查询注意力）——多个 Q 头共用一组 K、V，KV Cache 因此小很多（[07 章](07-注意力变体MQA-GQA-MLA.md)）。
> 📖 **TP / DP / EP / CP**（**T**ensor / **D**ata / **E**xpert / **C**ontext **P**arallelism，张量 / 数据 / 专家 / 序列并行）——四种把模型或数据切到多卡上的方式（[06 章](06-推理中的并行策略.md)）。
> 📖 **MoE**（**M**ixture **o**f **E**xperts，混合专家）——每个 token 只激活一小部分「专家」子网络（[11 章](11-MoE推理与专家并行.md)）。
> 📖 **chunked prefill**（分块预填充）——把一个长 prompt 切成若干块，每块掺进 Decode 批次里一起算（[03 章 §3.5](03-Prefill与Decode两阶段.md)）。★ 它是 PD 分离**在单机上的竞争方案**，本章全程拿它当对照组。

## 10.1 03 章遗留的问题

先回顾混合批（chunked prefill）解决了什么、没解决什么。

```
    ✅ 解决了：Decode 用户不再被一整段 Prefill 卡住（尖峰从 21× 压到 2.6×，§10.2.2）
    ✅ 解决了：单步算术强度被顶上去，一次权重读取同时服务
               512 个 prefill token 和几十个 decode token ⟹ 纯赚

    ⚠️ 没解决的三件事：
      ① 两个阶段的【最优并行策略】不同，混在一起只能用一套
      ② 两个阶段仍在【互相干扰】——Prefill 的大块计算
         会让同批 Decode 的 TBT 出现抖动（不是尖峰了，但还在）
      ③ ★ 两个阶段对【硬件】的需求不同：
         Prefill 吃算力  ⟹ 想要算力强的新卡
         Decode 吃带宽和显存 ⟹ ★ 便宜的老卡可能性价比更高
```

> ★★ **PD 分离的立论**：既然是两种性质不同的工作负载，就应该像微服务一样**拆成两个独立集群**，各自按自己的最优方式配置和扩缩容。

### ⚠️ 但这个立论有个前提，而且它经常不成立

「Prefill 算力受限、Decode 访存受限」是本章一切推理的地基。**这句话只有在 prompt 足够长时才成立。**

> 🔑 **算术强度不是 Prefill 的固有属性，它大致等于 prompt 长度 M。**
> 一段 6 个 token 的 prompt，它的算术强度只有 **5.6**，离屋脊点 295 差 50 倍——**它和 Decode 一样是访存受限的**，一样只用得上百分之几的算力。
> ★ 临界点在**几百个 token 的量级**：[03 章 §3.3](03-Prefill与Decode两阶段.md) 按整模型口径（含激活流量）算出 **M ≈ 390**；[大模型算子开发 09 章 §9.8.3](../../大模型算子开发/09-推理侧算子.md) 按单个 FFN GEMM 口径算出 **M ≥ 325**。⚠️ 两个数口径不同，**能确定的只有量级：几百**。

```
    ⟹ ★★★ 于是 PD 分离的收益是【有条件的】：

       prompt 远长于临界点（RAG、长文档、代码库）
         ⟹ Prefill 真的算力受限，两阶段画像真的相反 ⟹ ✅ 分离有收益

       prompt 短于临界点（闲聊、短指令）
         ⟹ ★ Prefill 也是访存受限，和 Decode 是【同一种病】
         ⟹ 没有「两种相反的最优配置」可供分别优化
         ⟹ 而且 Prefill 本身只要几毫秒，压根卡不住 Decode
         ⟹ ❌ 分离只剩成本（一次 KV 搬运 + 一次网络往返），没有收益

    ⟹ §10.2.7 会把这条曲线逐行算出来。
```

> ⚠️ **顺带把「GPU 利用率低」这句话的口径说清楚**，它在 PD 分离的讨论里被滥用得最厉害。Decode 阶段「GPU 利用率只有百分之几」指的是**算力（FLOPS）利用率**；同一时刻它的**显存带宽利用率是接近 100% 的**。★★ 算力利用率低**是 Memory Bound 的定义，是物理规律，不是浪费**——权重必须整份读一遍，这件事本身就把时间用掉了，多出来的算力没有活可干。所以「PD 分离能把利用率从 5% 提到 80%」这类说法，要么在偷换指标，要么在讲 Prefill 那一侧。**分离真正买到的不是「填满算力」，是「不互相打断」和「各自配硬件」。**

## 10.2 ★★ 先看一个具体例子：一次 RAG 问答

抽象的「两个集群」很难有感觉。我们把一个真实请求从头到尾走一遍，**每一毫秒都算出来**。

> 📖 **RAG**（**R**etrieval-**A**ugmented **G**eneration，检索增强生成）——先去知识库检索一堆资料，塞进 prompt 再让模型回答。★ 它的 prompt 天生很长，是 PD 分离最典型的适用场景。

### 10.2.1 场景设定与两个基准耗时

```
    模型 / 卡：Llama-3-8B（BF16，权重 16.1 GB）/ H100 SXM5（§10.0）

    ★ 当前状态：8 个老用户正在打字（都处在 Decode 阶段）
       每人身后挂着约 4096 token 的上下文

    ★ 新来的第 9 个用户：RAG 问答
       输入：一份文档 + 问题 = 【4096 个 token】   ⟸ Prefill 要干的活
       输出：200 个字                             ⟸ Decode 要干的活
```

**基准一：Prefill 这 4096 个 token 要多久？**

| 项 | 算式 | 值 |
|---|---|---|
| 线性层 FLOP | 2 × 8.03e9 × 4096 | 65.8 TFLOP |
| 注意力 FLOP | 2 × 32头 × 4096² × 128 × 2 ÷ 2（causal）× 32层 | 4.4 TFLOP |
| **FLOP 合计** | — | **70.2 TFLOP** |
| 搬运字节 | 权重 16.1 GB + 激活约 8.8 MB/token × 4096（36.0 GB） | 52.1 GB |
| **算术强度 I** | 70.2e12 ÷ 52.1e9 | **1348** ≫ 屋脊点 295 ⟹ ✅ **算力受限** |
| 算力侧耗时 | 70.2e12 ÷ 396e12（40% MFU） | **177 ms** ← 瓶颈 |
| 带宽侧耗时 | 52.1e9 ÷ 2.345e12 | 22.2 ms |
| **⟹ Prefill 耗时** | max(177, 22.2) | ★ **177 ms** |

**基准二：这 8 个人 Decode 一步要多久？**

| 项 | 算式 | 值 |
|---|---|---|
| 权重字节 | 8.03 B × 2 | 16.1 GB |
| KV 字节 | 8 人 × 4096 token × 128 KiB = 4 GiB | 4.3 GB |
| **搬运合计** | — | **20.4 GB** |
| FLOP | 2 × 8.03e9 × 8 token | 0.13 TFLOP |
| **算术强度 I** | 0.13e12 ÷ 20.4e9 | **6.3** ≪ 295 ⟹ ❌ **访存受限** |
| 带宽侧耗时 | 20.4e9 ÷ 2.345e12 | ★ **8.7 ms** ← 瓶颈 |
| 算力侧耗时 | 0.13e12 ÷ 396e12 | 0.33 ms（算力利用率 **3.8%**） |
| **⟹ 稳态 TBT** | max(8.7, 0.33) | ★ **8.7 ms** ⟹ 200 字 ≈ **1.74 秒** |

> 🔑 **把这两行并排看，就是整章的地基**：同一张卡，同一个模型——
> **Prefill 那一步**：算力用到 **40%**（这就是那个 MFU 折扣，理论上限是 100%），带宽只跑到 52.1 GB ÷ 177 ms = 294 GB/s，**约 9% 的峰值带宽**。
> **Decode 那一步**：带宽用到 **70%**（这就是那个带宽折扣，理论上限也是 100%），算力只用了 **3.8%**。
> ★★ 两者**各自把一种资源用到自己的上限、把另一种资源闲在那里**——而且闲的还不是同一种。这才是「性格相反」的准确含义，也是「一张卡装两种活必然两头不讨好」的全部理由。
>
> ⚠️ 再强调一次 §10.1 的条件：**上面那个「算力受限」是 4096 这个长度买来的**。同一个模型，prompt 换成 64 个 token，算术强度掉到 **62**，Prefill 立刻变回访存受限，耗时被权重读取钉死在 **7.1 ms**（比算力侧的 2.6 ms 还慢）（§10.2.7 有完整的扫描表）。

### 10.2.2 剧情 A：不分离（chunked prefill 混部，03 章的方案）

只有 1 张卡，它既要伺候 8 个老用户吐字，又要给新用户读那 4096 个 token。

**先看不切会怎样（Prefill 优先，vLLM v0 早期的默认）**：

```
    时间轴 ──────────────────────────────────────────────────►

    [D][D][D][ P P P P P P P P P P P P P P P P P P P P ][D][D][D]
              ↑ 这一整段 177 ms，8 个正在生成的请求【全部停摆】

    ⟹ 老用户感受到的 TBT = 177 + 8.7 = ★ 185.7 ms
       是平时 8.7 ms 的 ★★ 21 倍 ⟹ 吐字吐得好好的，突然卡住 0.19 秒
```

**chunked prefill 的做法**：把 4096 切成 8 块，每块 512 token，**掺进 decode 批次里一起算**。

⚠️ 这里有一个特别容易算错的地方，先说清楚。

```
    ❌ 错误算法：「512 个 token 的 prefill 要 20 ms，加上原来 decode 的 8.7 ms
                  ⟹ 这一步 28.7 ms」

    ★★ 为什么错：混合批【不是把两件事先后做一遍】，而是【合并成同一个 GEMM】。
       512 个 prefill token 和 8 个 decode token 排进同一个矩阵的 M 维，
       权重【只读一遍】就同时服务了两边。

    ✅ 正确算法：这一步的耗时 = max(算力侧, 带宽侧)，不是相加。
```

| 混合步（chunk 512 + 8 路 decode）的账 | 算式 | 值 |
|---|---|---|
| chunk 线性层 FLOP | 2 × 8.03e9 × 512 | 8.22 TFLOP |
| chunk 注意力 FLOP（8 块平摊） | 4.4 ÷ 8 | 0.55 TFLOP |
| 8 路 decode FLOP | 2 × 8.03e9 × 8 | 0.13 TFLOP |
| **FLOP 合计** | — | **8.90 TFLOP** |
| 搬运 | 权重 16.1 + decode KV 4.3 + chunk 激活约 4.5 | 24.9 GB |
| 算力侧 | 8.90e12 ÷ 396e12 | **22.5 ms** ← 瓶颈 |
| 带宽侧 | 24.9e9 ÷ 2.345e12 | 10.6 ms |
| **⟹ 一步耗时** | **max(22.5, 10.6)** | ★ **22.5 ms** |

> ⚠️ 「8 块平摊」是简化。**靠后的 chunk 要看更长的历史，注意力那一项实际是递增的**：第 1 块几乎为 0，第 8 块约 1.0 TFLOP。平摊后总量对得上，单步误差在 ±1 ms 量级。

```
    时间轴 ──────────────────────────────────────────────────►

    稳态（没有新请求）：
    [8.7][8.7][8.7][8.7]   ⟸ 8 个老用户，每 8.7 ms 每人吐一个字

    第 9 个用户来了之后的 8 步：
    [22.5][22.5][22.5][22.5][22.5][22.5][22.5][22.5]

    ⟹ ★★ 老用户：TBT 从 8.7 ms 变成 22.5 ms，是原来的【2.6 倍】，
       这个抖动持续 8 × 22.5 = 【180 ms】
    ⟹ 新用户 TTFT = 180 ms
```

> 🔑 **看懂这里就看懂了 PD 分离的动机**：chunked prefill 把「一次 177 ms 的大停顿」摊成了「8 次 13.8 ms 的小拖慢」——★ 尖峰从 **21×** 压到了 **2.6×**，这是巨大的改善。**但总的算力消耗一点没少**：8 × 22.5 = 180 ms，和独占跑 177 ms 几乎一样。
> ⟹ 因为**算力就那么多，两个人分，谁都快不了**。★★ chunked prefill 治的是**分布**（尖峰变平），治不了**总量**。

> ⚠️ **注意这里的表述纪律**（[13 章 §13.5](13-性能指标与压测.md)）：上面说「TBT 是原来的 2.6 倍」「尖峰从 21× 压到 2.6×」，**没有说「延迟降低了 8 倍」**。8 只是 4096 ÷ 512，是 chunk 的个数，不是任何一个延迟指标的改善倍数。★ 同理，「时间减少 60%」等于「加速 **2.5** 倍」，不是「加速 60%」——本仓库在这上面栽过跟头。

### 10.2.3 剧情 B：分离（2 张卡，1 张 P + 1 张 D）

```
   ① 路由器收到第 9 个用户的请求
      ⟹ 看到它是新请求（要 Prefill），派给【P 卡】
      ★ D 卡完全不知道这件事，8 个老用户【一个字都没慢】

   ② P 卡独占算力跑 4096 token 的 Prefill
      ⟹ 177 ms，产出【4096 个位置的完整 KV Cache】
      ⟹ 同时采样出第 1 个字（比如「根」）

   ③ ★★★ 把 KV Cache 搬到 D 卡（本方案唯一的额外成本）
      4096 token × 128 KiB/token = 512 MiB = 537 MB
      走 400 Gb/s InfiniBand 单卡对单卡（50 GB/s 线速）⟹ 10.7 ms
      ★ 这 10.7 ms 能和第 ② 步【重叠】掉大半（§10.6 的分层传输）

   ④ D 卡接过 KV，把第 9 个用户【加进正在跑的批次】
      ⟹ 从此他和另外 8 个人一样逐字生成
      ⟹ D 卡上变成 9 个人，搬运 16.1 + 4.83 = 20.9 GB ⟹ TBT 8.9 ms

   ⟹ 新用户 TTFT = 177 + 10.7 ≈ 188 ms（不重叠）
                  ≈ 178 ms（分层重叠后）
   ⟹ ★★ 老用户 TBT 全程 8.7 ms ⟹ 8.9 ms，【零尖峰】
```

### 10.2.4 ⚠️ 把两个剧情按【同样的卡数】摆在一起——结论和你想的不一样

剧情 B 用了 2 张卡，剧情 A 只用了 1 张。**必须按同样的 2 张卡再比一次**，否则整个对比是假的。

**⚠️ 补一个新对照组「混部 ×2」**：两张卡各跑一个完整实例，8 个老用户一边 4 个，新请求落到其中一张。这一组的账要重算，因为**每张卡的 KV 少了一半**：

| 混部 ×2，单卡的账 | 算式 | 值 |
|---|---|---|
| 稳态搬运 | 权重 16.1 + 4 人 × 4096 × 128 KiB（2.15 GB） | 18.3 GB |
| **稳态 TBT** | 18.3e9 ÷ 2.345e12 | ★ **7.8 ms**（⚠️ 比单卡 8 人时还**快**） |
| 混合步 FLOP | chunk 8.77 + 4 路 decode 0.064 | 8.83 TFLOP |
| **混合步耗时** | 8.83e12 ÷ 396e12 | **22.3 ms** |
| TTFT | 8 × 22.3 | **178 ms** |

**三组并排**（同样 2 张 H100，同样 8+1 个用户，4096 token 输入）：

| 指标 | ⓐ 混部 ×2（各跑完整实例） | ⓑ 分离 1P + 1D | ⓒ 分离 2P + 0D ✗ |
|---|---|---|---|
| 拓扑 | 两张卡各跑一份完整模型，用户各管一半 | 一张只 Prefill，一张只 Decode | 配比错了的反例 |
| 老用户稳态 TBT | ✅ **7.8 ms**（KV 分摊到两卡） | ⚠️ 8.7 ms（KV 全压在 D 卡） | ✗ 没有 D 卡，全体排队 |
| 老用户 Prefill 期间 TBT | ⚠️ **22.3 ms**（2.9× 抖动，但只影响落在那张卡的 4 个人） | ✅ **8.7 → 8.9 ms，零抖动** | ✗ 不可用 |
| 新用户 TTFT | ✅ **178 ms** | ⚠️ **188 ms**（不重叠）/ 178 ms（重叠后） | 177 ms |
| 最大并发（KV 预算约 60 GiB/卡，4K 上下文） | ✅ **约 240 条**（两卡都能存 KV） | ⚠️ **约 120 条**（只有 D 卡存 KV，P 卡的显存基本闲置） | 0 |
| 额外要求 | ✅ 无 | ⚠️ RDMA 网络 + 一个路由器 + KV 连接器 | ⚠️ 同左 |
| 运维复杂度 | ✅ 低 | ⚠️ 高（两套配置、两套监控、一个配比要调） | — |

> ⚠️⚠️ **诚实的结论：在 2 张卡这个规模上，PD 分离并不划算。**
> ★ 混部 ×2 的 **TTFT 更好**（178 vs 188，因为省掉了那 10.7 ms 搬运）、**稳态 TBT 更好**（7.8 vs 8.7，因为 KV 分摊在两张卡上）、**最大并发是两倍**（P 卡的 80 GB 显存在分离方案里几乎全闲着）。分离唯一赢的是**抖动**：22.3 ms 的 2.9× 抖动 vs 完全没有抖动。
> ⟹ **花一倍的显存、加一套 RDMA、换一个没有抖动**——小规模下这笔买卖不成立。这和 §10.7「小规模别做」是同一件事，只不过现在它有数字了。

> ⚠️ **为什么 ⓐ 拆成两张卡，那个 22 ms 的抖动却没变好？**
> 因为 Decode 那 7.8 ms 的主体是【搬 16.1 GB 权重】（访存受限）。★ 用户从 8 个减到 4 个，**权重还是要整份搬一遍** ⟹ 只省掉了 KV 那 2.15 GB，8.7 → 7.8 ms，仅此而已。而掺进来的 512 个 prefill token 是实打实的算力 ⟹ 那 13.8 ms 一点不减。
> ⟹ ★★ **单纯「多买一张卡分流」救不了干扰，只有「把两种活分开」才行**——但把两种活分开，你得为此付出别的东西。

```
    ★★★ 那 PD 分离的收益到底什么时候才冒出来？三条，一条都不能少：

      ① 规模大到 P 侧和 D 侧各自都有【好几个节点】
         ⟹ 这时 P 卡的显存不再是「白买的」，因为 P 节点数 ≪ D 节点数（§10.3.3）

      ② 并发高到 Prefill 【不是偶发事件而是持续流】
         ⟹ 2.9× 的抖动不再是「偶尔卡一下」，而是【一直卡着】

      ③ ★★ 两侧真的用了【不同的配置或不同的硬件】
         ⟹ 上面那张表里两侧都是 H100 + TP=1，
            所以「各自最优配置」这个最大的收益项，一分钱都没体现出来。
            §10.4 会用一个 505B 的 MoE 把这一项算出来。
```

### 10.2.5 ★★ 那 512 MiB 到底怎么搬过去——把带宽口径钉死

这是 PD 分离唯一的、也是致命的额外成本。**算它之前，必须先把带宽的口径弄对，这是本主题最容易出错的地方。**

> 📖 **NVLink**（英伟达机内卡间高速互联）——⚠️ H100 SXM5 标称的 **900 GB/s 是【双向聚合】**，意思是「同时发出 450 + 收进 450」。★★ **算「我要发出 X 字节要多久」时，分母只能用 450 GB/s**，用 900 会把时间算少一半。
> 📖 **InfiniBand**（**IB**，机间高速网络）——每卡配一张 **400 Gb/s** 网卡。⚠️ **Gb 是比特（bit），不是字节**：400 ÷ 8 = **50 GB/s** 单向线速。✅ DeepSeek 报告的实测可达约 40 GB/s。
> 📖 **PCIe 5.0 ×16**（CPU 与 GPU 之间的总线）——⚠️ 常说的 128 GB/s **也是双向值**，**单向理论约 63 GB/s**。只有「KV 要绕一趟主机内存」时才走它。
> 📖 **RDMA**（**R**emote **D**irect **M**emory **A**ccess，远程直接内存访问）——网卡直接读写对端显存/内存，**不经过 CPU、不经过内核协议栈**。★ 这是 PD 分离能落地的硬件前提。
> ⚠️ **凡是看到「字节数 ÷ 带宽」的式子，第一件事是确认两边是不是同一个方向口径。**

**4096 token 的 KV = 512 MiB = 537 MB，走不同的线要多久**：

| 走哪条线 | 单向可用带宽 | 搬 537 MB 耗时 | 占 Prefill（177 ms）的比例 | 什么时候会走这条 |
|---|---|---|---|---|
| ★ NVLink（同机 8 卡内） | **450 GB/s**（900 ÷ 2） | **1.2 ms** | **0.7%** | P 和 D 在同一台机器上（很少见，那就不叫分离了） |
| ★ InfiniBand 400 Gb/s，**单卡↔单卡** | **50 GB/s**（400 ÷ 8） | **10.7 ms** | **6.1%** | ✅ 最常见的部署形态 |
| 同上，按实测打折 | 40 GB/s | 13.4 ms | 7.6% | 真实集群 |
| ★★ IB，**8 卡↔8 卡并行**（两侧都 TP=8） | 8 × 50 = **400 GB/s 聚合** | **1.3 ms** | 0.8% | ★ KV 本来就按卡切开了，8 张网卡同时发 |
| PCIe 5.0 ×16（绕一趟主机内存） | **63 GB/s** 单向 | 8.5 ms | 4.8% | ⚠️ 老架构或没有 GPUDirect 时，**而且要走两趟** |
| ❌ 100 Gb/s 普通以太网 | 12.5 GB/s | **42.9 ms** | **24%** | ⚠️ 不要在这种集群上做 PD 分离 |

> 🔑 **注意倒数第二列有个惊人的规律：比例几乎是个常数。**
> 因为 KV 大小和 Prefill 耗时**都正比于 prompt 长度 M**，M 一约掉就只剩「每 token 的搬运成本 ÷ 每 token 的计算成本」：

```
    每 token 搬运（IB 50 GB/s）= 131072 字节 ÷ 50e9  = ★ 2.62 µs
    每 token 计算（4096 长度，40% MFU）= 17.1 GFLOP ÷ 396e12 = ★ 43.3 µs

    ⟹ 搬运开销占比 = 2.62 / 43.3 = ★★ 6.1%     ← 和 prompt 长短【几乎无关】

    换条线，这个常数就变：
      NVLink 450 GB/s  ⟹ 0.29 / 43.3 = ★  0.7%   ✅ 可以忽略
      IB     50  GB/s  ⟹ 2.62 / 43.3 = ★  6.1%   ✅ 可以接受
      PCIe   63  GB/s  ⟹ 2.08 / 43.3 =     4.8%   ⚠️ 但通常要走两趟 ⟹ ~10%
      以太   12.5 GB/s ⟹ 10.5 / 43.3 = ★★ 24%    ❌ 收益被吃掉一大半
```

> ★★★ **这就是「没有 RDMA 就别做 PD 分离」的定量版本。** 不是「慢一点」，是**把 TTFT 直接抬高四分之一**——而分离本来就不改善 TTFT（§10.2.4），再加 24%，纯亏。
>
> ⚠️ 上面这个常数还有两个前提：① Prefill 真的算力受限（M 大于几百，否则分母被权重读取钉死，比例会失真）；② 模型用了 GQA。**换成没有 GQA 的老模型（MHA），每 token 的 KV 是 512 KiB 而不是 128 KiB，这个比例直接 ×4**（§10.2.6 末尾）。

### 10.2.6 ★ 一个必须想通的问题：D 卡凭什么能接着往下生成？

小白最容易卡在这：**这份 prompt 是 P 卡算的，D 卡从头到尾没见过它，怎么就能续写？**

```
    ⟹ 因为 Transformer 生成第 n+1 个字时，需要的【全部历史信息】
       就只有两样东西：

       ① ★★ KV Cache —— 前面 4096 个位置、每一层算出来的 K 和 V
          形状：[32 层] × [K 和 V 两份] × [4096 个位置] × [8 个 KV 头 × 128 维]
          ⟹ 这就是那 512 MiB 的全部内容

       ② 上一步吐出来的那个 token（「根」）

    ★ 把这两样搬过去，D 卡就「什么都知道了」——
      它不需要重算 prompt，也不需要看到原始文本。
      ⟹ ★★ 【KV Cache 就是这次对话的全部记忆，它是可以搬家的】
      ⟹ 这一句是 PD 分离能成立的全部理由，也是 Mooncake
        「以 KVCache 为中心」那句主张的根（§10.5 ③）。
```

**512 MiB 这个数字怎么来的**（⚠️ 按公开的 `config.json` 推算，非论文披露）：

```
    ★★ KV Cache 每 token 每层 = 2 × n_kv_heads × head_dim × 每元素字节数
                                 ↑        ↑            ↑          ↑
                               K 和 V   ★ KV 头数    每头维度    BF16 = 2

    Llama-3-8B：2 × 8 × 128 × 2 = 4096 字节 = 4 KiB / token / 层
                × 32 层           = ★ 128 KiB / token
                × 4096 token      = ★★ 512 MiB
```

> ⚠️⚠️ **最容易犯的错：用 `d_model` 硬套 MHA 的公式去算一个 GQA 模型。**
> 常见的错误写法是 `2 × L × d_model × 字节数` = 2 × 32 × 4096 × 2 = **512 KiB/token**——**比真值高了整整 4 倍**。
> ★ 因为 Llama-3-8B 是 **GQA**：32 个 Q 头只配了 **8 个 KV 头**，`n_kv_heads × head_dim = 8 × 128 = 1024`，**不是** `d_model = 4096`。
> ⟹ ★★ **公式里那一项必须是 `n_kv_heads × head_dim`，不是 `d_model`。** MHA 模型下两者恰好相等，所以这个错误在老模型上看不出来，一换到 GQA/MQA/MLA 就会高估好几倍到十几倍（[02 章 §2.2](02-KV-Cache与显存账.md)、[07 章 §7.5](07-注意力变体MQA-GQA-MLA.md)）。

### 10.2.7 ⚠️⚠️ 回到那个前提：prompt 多长，分离才值？

§10.1 说了「Prefill 算力受限」是有条件的。现在把 prompt 长度 M 扫一遍，**看收益是怎么随 M 出现的**。

⚠️ 全部按 §10.0 的口径（40% MFU / 70% 带宽，权重 16.1 GB，激活约 8.8 MB/token）。「混部尖峰」一列指 chunked prefill（chunk = 512）下老用户 TBT 相对 8.7 ms 稳态的倍数。

| prompt M | 算术强度 I | Prefill 瓶颈 | Prefill 耗时 | 混部下 TBT 尖峰 | KV 大小 | 搬运 @IB 50 GB/s | 搬运占比 | **PD 分离值不值** |
|---|---|---|---|---|---|---|---|---|
| **64** | **62** | ❌ **访存**（被权重钉死） | **7.1 ms** | **1.02×** | 8 MiB | 0.17 ms | 2.4% | ❌ **不值**：没有尖峰可消，两阶段是同一种病 |
| **390** | **323** ≈ 屋脊点 | ★ **临界** | 15.9 ms | **1.9×** | 49 MiB | 1.0 ms | 6.4% | ⚠️ **临界**：收益刚够抵消复杂度 |
| **1024** | 665 | ✅ 算力 | 42 ms | **2.5×** | 128 MiB | 2.7 ms | 6.4% | ⚠️ **开始有** |
| **4096** | 1348 | ✅ 算力 | **177 ms** | **2.6×** | 512 MiB | 10.7 ms | 6.1% | ✅ **值**（§10.2.4 的例子） |
| **32768** | 2653 | ✅ 算力 | **2040 ms** | **2.6×**（不切则 **235×**） | 4 GiB | 86 ms | 4.2% | ✅✅ **非常值** |

```
    ★★★ 这张表要读出三件事：

      ① M = 64 那一行：Prefill 耗时【不随 M 下降了】，卡在 7.1 ms。
         因为这时瓶颈是「把 16.1 GB 权重整份读一遍」——
         ⟹ ★ 和 Decode 一模一样的病。两阶段【没有性格差异可以利用】。

      ② 混部尖峰那一列在 M ≥ 1024 之后【基本不涨了】（2.5× → 2.6×）。
         因为 chunk 固定 512，每一步的形状就固定了，M 变的只是步数。
         ⟹ ★ 所以「长 prompt 更需要分离」，真正的原因不是尖峰更高，
            而是【尖峰持续得更久】：M=1024 抖 85 ms，M=32768 抖 5.3 秒。

      ③ 搬运占比一列几乎是常数 ~6%（§10.2.5 推过）。
         ⟹ ★★ 所以「prompt 越长、搬 KV 越亏」这个直觉是【错的】。
            长 prompt 的 KV 确实更大，但 Prefill 也更久，两者同比例长。
```

> ⚠️ 上表的 I 值和 [03 章 §3.3](03-Prefill与Decode两阶段.md) 的同类表略有出入（那里 M=390 时 I = 297，这里是 323）。原因是**分母口径不同**：03 章按 15.0 GB 记权重（GiB 口径），本章按 16.1 GB（十进制 GB 口径）。★ 差 7%，**结论完全一样：临界点在几百 token 的量级**。这正是 §10.0 那条「容量用 GiB、带宽用 GB」纪律要防的坑。

> 🔑 **一句话收口**：**PD 分离不是一个「总是更好」的架构，它是一个【用复杂度和显存，换长 prompt 场景下的延迟稳定性】的交易。** prompt 短、规模小、没有 RDMA——这三条里中任何一条，交易就不划算。

## 10.3 架构长什么样

### 10.3.1 拓扑

```
    用户请求
       │
       ▼
   ── 路由器 ────────────────────────────────
      ★ 决定这个请求去哪个 P 实例、哪个 D 实例
   ─────────────────────────────────────────
         │
         ▼
   ── Prefill 集群 (P) ─────────────────────
      ├── P0    ★ 算力受限（★ 前提：prompt 够长，§10.1）
      ├── P1        ⟹ 大 TP / CP，追求单请求的算力
      └── ...       跑完 prompt，产出【完整的 KV Cache】
   ─────────────────────────────────────────
         │
         │  ★★★ 传输 KV Cache ← 这是整个方案的成败关键（§10.6）
         ▼
   ── Decode 集群 (D) ──────────────────────
      ├── D0    ★ 访存受限（★ 这一条是无条件的）
      ├── D1        ⟹ 小 TP + 大 DP，追求显存和并发
      └── ...       接过 KV，开始逐字生成
   ─────────────────────────────────────────
         │
         ▼
    流式返回给用户
```

> ⚠️ 上图两个集群的框特意**只画了左边界**。★ 带右边框的 ASCII 框里一旦有中文，渲染成 HTML 时**必然错位**——中文是双宽字符，等宽字体对不齐。本章所有对照表因此都改成了 markdown 表格。

### 10.3.2 ★ 两个阶段的资源画像，逐项对照

这张表是**全部收益的来源**：两列几乎没有一行是一样的，把它们塞进同一组 GPU、用同一套配置跑，必然两头不讨好。

| 维度 | Prefill 集群（P） | Decode 集群（D） |
|---|---|---|
| **一步处理多少 token** | 整段 prompt（几百 ~ 几万） | ★ 固定 1 个 × 并发数 |
| **矩阵形状** | 矩阵 × 矩阵（GEMM），M 很大 | 向量 × 矩阵（GEMV），M = batch |
| **算术强度** | ⚠️ **≈ prompt 长度**，不是固定值：64 → 62，4096 → 1348 | ★ **恒定 ≈ 1~10**，怎么调都在这个量级 |
| **瓶颈** | prompt > 约 400 token 才 ✅ 算力受限；更短 ❌ 和 Decode 一样访存受限 | ❌ **无条件访存受限** |
| **算力（FLOPS）利用率** | 长 prompt 可达 40~70% | ★ **3~8%** ——⚠️ 这是 Memory Bound 的**定义**，不是浪费 |
| **带宽利用率** | ⚠️ 长 prompt 时反而**很低**（约 9%，§10.2.1） | ★★ **接近 100%** ——这才是 Decode 的真实状态 |
| **显存吃在哪** | 权重 + 瞬时激活（**KV 只是产出，用完即走**） | ★★ 权重 + **大量长期驻留的 KV**（并发的上限就在这） |
| **并行策略** | ★ 大 TP / CP（切算力，加卡接近线性） | ★ 小 TP + 大 DP（加 TP 收益递减，§10.4.4） |
| **批策略** | 小 batch 即可打满（单个长 prompt 就够撑满算力） | ★ 尽可能大的 batch（唯一能把算术强度顶上去的旋钮） |
| **量化的收益** | 中等（算力受限，减字节换不来时间） | ★★ **大**（访存受限，权重字节减半直接快近一倍，[09 章](09-量化.md)） |
| **想要的硬件** | 高 TFLOPS 的新卡 | ★ 高 HBM 带宽 + **大显存**；算力过剩 ⟹ **便宜的老卡可能更划算** |
| **扩缩容依据** | ★ 按【输入 token 量】 | ★ 按【输出 token 量】 |
| **优化目标 / SLO** | **TTFT** | **TPOT / TBT** |
| **投机解码有没有用** | ❌ 没有（算力本来就满了） | ✅ 有（算力过剩，拿来换带宽，[08 章](08-投机解码.md)） |

> 🔑 **「扩缩容依据」这一行是被低估的一条**。真实业务的输入输出长度比随时间波动很大——白天大家问长文档（P 重），晚上大家闲聊（D 重）。**合在一起，你只能整体扩容；分开了，才能各扩各的。** ⟹ §10.3.3 把这条算成具体的机器台数。

> ⚠️ **但「大 TP vs 小 TP + 大 DP」这一行很容易被误解**——它说的**只是注意力那一段**，不是「D 侧每张卡放一份完整模型」。**§10.4 用一个 505B 的 MoE 把它整个拆开。**

> ★ 这张表的算子实现视角（同一套结论、按 GEMM 和屋顶线讲）在 [大模型算子开发 09 章 §9.4.3](../../大模型算子开发/09-推理侧算子.md)，**那一章还有 chunked prefill 的 chunk_size 下界推导（§9.8.3，M ≥ 325）**，本章不重复。

### 10.3.3 ★★ P 节点和 D 节点各配几台——把配比算出来

这是 PD 分离上线后**最持续的运维难题**。配错了，某一边排队、另一边空转，**比混部还差**。

**推导只有三行**：

```
    ★ 配平的条件 = 两侧的【请求处理速率】相等。

      P 节点吞吐  λ_P = 1 ÷ T_prefill(L_in)                    （请求/秒/节点）
      D 节点吞吐  λ_D = (B ÷ TPOT) ÷ L_out                     （请求/秒/节点）
                         ★ (B ÷ TPOT) = 这台 D 节点每秒能吐多少 token
                           再除以每条请求要吐多少个 ⟹ 每秒能做完几条请求

      ⟹ N_P × λ_P = N_D × λ_D
      ⟹ ★★ N_P : N_D = λ_D : λ_P
```

**代进四种真实负载**（单卡 H100 当一个节点，Llama-3-8B，口径同 §10.0；B 受 KV 预算约 60 GiB/卡 限制）：

| 场景 | 输入 L_in | 输出 L_out | T_prefill | **λ_P**（req/s） | D 侧 batch B | TPOT | **λ_D**（req/s） | **⟹ N_P : N_D** |
|---|---|---|---|---|---|---|---|---|
| 闲聊 | 128 | 400 | 7.3 ms ❌访存 | **137** | 64 | 8.0 ms | **19.9** | ★ **1 : 6.9**（D 重） |
| 普通问答 | 512 | 300 | 20.9 ms | **47.8** | 64 | 9.2 ms | **23.1** | **1 : 2.1** |
| ★ Agent / 推理模型（长输出） | 2048 | 4096 | 86 ms | **11.6** | 32 | 14.2 ms | **0.55** | ★★ **1 : 21**（极度 D 重） |
| ★ RAG 长文档 | 4096 | 200 | 177 ms | **5.65** | 32 | 14.4 ms | **11.1** | **2 : 1**（P 重） |
| ★★ 长文抽取（只要一个 JSON） | 32768 | 20 | 2040 ms | **0.49** | 8 | 21.5 ms | **18.6** | ★★★ **38 : 1**（极度 P 重） |

```
    ★★★ 这张表最该记住的不是任何一个数字，是它的【跨度】：

       同一个模型、同一张卡，最优配比从【1 : 21】一路走到【38 : 1】——
       ★ 相差【800 倍】，而变的只有「输入输出长度分布」这一件事。

    ⟹ ① 「PD 分离的配比一般是 1:4」这种说法【毫无意义】，
         不给输入输出长度分布就谈配比，等于没说。
    ⟹ ② ★★ 同一个服务里混着长文抽取和 Agent 长输出两种流量，
         【不存在一个能同时配平两者的静态配比】
         ⟹ 这就是为什么工业界要做【动态转换】：
            让节点能在 P 角色和 D 角色之间切换（Splitwise 的 mixed pool，§10.5 ②）。
    ⟹ ③ 注意「闲聊」那一行：T_prefill 是【访存受限】算出来的 7.3 ms，
         这时候根本不该分离（§10.2.7）。配比表在这一行只是形式上有解。
```

> ⚠️ **上表的四个简化，落地前必须补上**：① 忽略了 KV 搬运占用的时间和网络排队；② 假设 D 侧 batch 恒定为 B，真实系统里它随到达率波动，且**受 KV 预算封顶**（这才是 D 侧的硬约束）；③ 用平均长度代替了分布，**真实负载的长尾会让 P 侧排队远比均值预测的严重**；④ 没留余量——线上至少要按峰值的 70% 负载配，不能配到 100%。
> ★ 真实系统里这个配比是**在线测出来并持续调整的**，不是一次算准的。压测方法见 [13 章 §13.4](13-性能指标与压测.md)，**先画延迟-吞吐曲线、再画 SLO 横线读 goodput**，两侧各读一次。

## 10.4 ★★ 「P 用大 TP、D 用大 DP」到底是怎么切的

> §10.3.2 那张表里，「大 TP」和「小 TP + 大 DP」只是两行字。这一节把它拆开——**因为这是本章最容易被误解的一句话，而且误解的方向很危险。**
>
> 全程用一个真实模型当例子：**openPangu-2.0-Pro，505B 总参 / 18B 激活的 MoE**（架构见 [业界模型技术报告/openPangu-2.0-Pro.md](../../业界模型技术报告/openPangu-2.0-Pro.md)）。设定：**P 实例 32 卡、D 实例 32 卡**。
>
> ★ 这一节也是 §10.2.4 留下的那个缺口——那里的 2 卡例子**两侧配置一模一样**，所以「各自最优配置」这个最大的收益项一分钱都没体现。这里体现出来了。

### ★ 先破一个误解

```
    ★ 常听到的说法：「P 侧全用 TP=32，D 侧全用 DP」

    ⚠️ 这句话【省略了主语】——它说的只是【注意力那一段】。

      ① MoE 那一段，P 和 D 【都是 EP】，切法一模一样
      ② D 侧的 DP【不是】「每张卡放一份完整模型」
         ⟹ 505B 就算 W8A8 也要约 505 GB，没有任何一张卡装得下一个副本
      ③ 32 张卡从头到尾都是切开的，只是【切的维度换了】
```

回收 [06 章 §6.3 ④](06-推理中的并行策略.md) 的一条源码事实：**vLLM 里 EP 组不是你手配的一维，它是 `DP × PCP × TP` 三个维度合并出来的**（`parallel_state.py:1923`）：

```
    TP=32, DP=1   + 开专家并行  ⟹  EP 自动 = 32
    TP=1,  DP=32  + 开专家并行  ⟹  EP 还是 = 32

    ★★ 同一批 32 张卡，【MoE 层的视角完全没变】。
       变的只是「注意力层怎么用这 32 张卡」。
```

### 10.4.1 先把模型拆成三块，因为三块的切法根本不同

> 📖 **MLA**（**M**ulti-head **L**atent **A**ttention，多头潜在注意力）——把 K、V 压成一个低秩「潜向量」再存，KV Cache 因此小很多（[07 章 §7.4](07-注意力变体MQA-GQA-MLA.md)）。★ 它是下面整节的关键角色。
> 📖 **W8A8**（Weight 8-bit / Activation 8-bit）——权重和激活都量化到 8 位整数或 FP8，权重字节数是 BF16 的一半（[09 章](09-量化.md)）。

⚠️ 下表参数量按 openPangu Table 8 的配置**推算**（50 层 = 3 dense + 47 MoE，hidden 5120，64 头，MLA 的 KV 秩 512 + RoPE 维 64，路由专家 384 + 共享 1，专家中间维 1792）。**报告没有直接给这个拆分。**

| 权重块 | 参数量 | 占比 | 能怎么切 |
|---|---|---|---|
| **路由专家 ×384** | **497 B** | **98.4%** | ★★ **只能 EP**：单个专家才 27.5 M，TP 再切 32 份 ⟹ 中间维 1792/32 = 56，矩阵小到算子跑不满（[11 章 §11.2](11-MoE推理与专家并行.md)） |
| **MLA 注意力** | **4.0 B** | 0.8% | TP 行（按头切）、DP 也行（整份复制）⟹ ★★ **全部的分歧就在这一块** |
| Dense FFN + 共享专家 + 词表 | 3.6 B | 0.7% | 都行。量太小，怎么切都不影响大局 |

```
    ⟹ ★ 498 B（99%）的参数，P 和 D 都是 EP=32，各卡 384/32 = 12 个完整专家。
       所谓「P 用 TP、D 用 DP」的全部争议，是在那 4 B 的注意力权重上——
       ★★ 不到总参数的 1%。
```

### 10.4.2 P 侧（TP=32）每张卡拿到什么

```
  注意力（每层）
    ├─ W^DQ  (5120×1536)     这两个矩阵【不带「头」这一维】
    ├─ W^DKV (5120×576)      ⟹ ★ 切不了，32 张卡各存一份（复制）≈ 10.8 M/层
    └─ W^UQ / W^UK / W^UV / W^O   ≈ 69.2 M/层，带头维
                                  ⟹ 64 头 ÷ 32 = ★ 每卡 2 个头

    ⟹ 每卡 ≈ 12.96 M/层 × 50 层 ≈ 0.65 B
       （理想切法只要 0.125 B，多出来的 0.54 B
         就是那份「切不动只能复制」的低秩投影）

  Dense FFN（3 层）
    └─ 16128 ÷ 32 = 每卡 504 维
       ← 列切 gate/up、行切 down，每层一次 all-reduce

  MoE（47 层）
    └─ 384 专家 ÷ 32 = 每卡 12 个【完整】专家 ≈ 15.5 B
       ← ★ 这是 EP，不是 TP

  ⟹ 每卡合计 ≈ 16.3 B ≈ 16.3 GB @ W8A8
```

> ⚠️ **一个真实系统里的细节**：openPangu 报告写的 prefill 注意力**并不是「全 TP」**，而是 **DSA 层走 CP、SWA 层走 TP**（CP 方案代号 **Felix**）。
> 📖 **DSA**（**D**eep**S**eek **S**parse **A**ttention，稀疏注意力）——每个 token 只挑固定数量（openPangu 是 2048 个）的历史 KV 参与计算，但**要在全序列范围里挑**。
> 📖 **SWA**（**S**liding **W**indow **A**ttention，滑动窗口注意力）——只看最近固定窗口（openPangu 是 512）内的 token。
> 📖 **CP**（**C**ontext **P**arallelism，序列并行）——把一条序列按 token 位置切到多张卡上（[06 章 §6.3 ⑤](06-推理中的并行策略.md)）。
>
> 理由很直白——DSA 层要看全序列，128K 的 prompt 切序列（CP）比切头划算；SWA 层窗口只有 512，切序列没有意义，切头就够了。
> ⟹ ★★ **「P 侧大 TP」是个粗略说法，真实配置往往是 CP 和 TP 混着上。**

### 10.4.3 D 侧（Attention DP=32）每张卡拿到什么

```
  注意力
    ⟹ ★ 不切了。4.0 B 权重，32 张卡各存一份完整的
    ⟹ 每张卡处理【不同的请求】，注意力算完【一次通信都不用】

  Dense FFN / 共享专家 / 词表
    ⟹ 跟着注意力一起复制（它们和注意力在同一条「非 MoE」路径上）

  MoE
    ⟹ 还是 EP=32，每卡 12 个专家     ← ★★ 和 P 侧一模一样

  ⟹ 每卡 ≈ 15.5（专家）+ 4.0（注意力）+ 3.6（其余）≈ 23 GB @ W8A8
     ★ 比 P 侧多花约 7 GB/卡。买的就是下面 §10.4.4 ② 那条。
```

### 10.4.4 ★★ 为什么 decode 必须反着来——三条理由，第 ② 条是决定性的

#### ① decode 的矩阵已经小到切不动了

```
    prefill：一次进 128K token，每卡 2 个头
             ⟹ GEMM 形状 131072 × 2 × 128    ← ★ 算子吃得饱，切了确实快

    decode ：一次只进 batch=40 个 token，每卡 2 个头
             ⟹ GEMM 形状 40 × 2 × 128        ← ★ 算子空转
```

这就是 §10.3.2 那句「Prefill 大 TP 加卡有效；Decode 加 TP 收益递减」的**具体形状**。加 TP 之后 decode 每一步多出来的时间去哪了：

| 多出来的开销 | 说明 |
|---|---|
| ✅ **每层两次 all-reduce** | 真实且随 TP 增大而变慢，**这是主要项** |
| ✅ **GEMM 掉出算力区** | M=40、每卡 2 头，算子根本跑不满，切得越碎越浪费 |
| ⚠️ **kernel 数量一个都没少** | TP 切走了每个 kernel 的工作量，**但 kernel 的个数不变** ⟹ 单卡上「每个 kernel 的计算时间」变短，而下发一个 kernel 的 CPU 开销没变 ⟹ 更容易滑进 **Host Bound**（CPU 下发跟不上 GPU 执行） |

> ⚠️⚠️ **这里有个流传很广的错误说法要纠正**：「一层有 200 个 kernel，每个启动 5 µs，所以光启动就 1 ms」——**这个加法是错的**。★ **kernel 的下发是流水化的**：CPU 在下发第 n+1 个 kernel 的同时，GPU 正在执行第 n 个，两者重叠。只要**下发速率**跟得上**执行速率**，启动开销就被完全隐藏，一秒钟也不多花。
> ⟹ ★★ 正确的判据不是「把每个 kernel 的启动时间加起来」，而是比较两条流水线的**速率**：`CPU 每秒能下发多少个 kernel` vs `GPU 每秒能执行完多少个`。前者小于后者时才叫 Host Bound，这时 GPU 时间线上会出现**肉眼可见的空隙**。
> ⟹ 这也正是 **CUDA Graph** 要解决的问题：把整张图一次性下发，把 CPU 侧的下发速率从「每个 kernel 一次」变成「每步一次」（[12 章](12-CUDA-Graph与图编译.md)、[大模型算子开发 09 章 §9.9](../../大模型算子开发/09-推理侧算子.md)）。

#### ② ★★★ MLA 在 decode 端吸收成 MQA 之后，KV cache 按头切不动了，只能整份复制

> 📖 **MQA**（**M**ulti-**Q**uery **A**ttention，多查询注意力）——所有 Q 头共用**同一组** K、V，即 KV 头数 = 1（[07 章 §7.2](07-注意力变体MQA-GQA-MLA.md)）。

```
    ★ MLA 有两种等价的算法形态（07 章 §7.4）：
        Non-Absorptive（训练 / prefill）⟹ 展开成 MHA，有 64 个头
        Absorptive    （decode）        ⟹ ★ 等价于 MQA，KV 只剩【1 个头】

    ★ TP 切注意力的前提是「按头切」。KV 只剩 1 个头 ⟹ 32 张卡怎么切？
    ⟹ 切不了，只能【32 张卡各存一份完全相同的 KV cache】
```

⚠️ 按上面的配置推一笔账（KV 秩 512 + RoPE 维 64 = 576 维，BF16 = 2 字节，DSA:SWA = 1:2）：

| 项 | 算式 | 值 |
|---|---|---|
| 17 个 DSA 层 | 17 × 576 × 2 B × 131072 token | **2.5 GiB** ← 随上下文线性增长 |
| 33 个 SWA 层 | 33 × 576 × 2 B × 512（窗口封顶） | 19 MiB ← ★ **恒定**，不随上下文长 |
| **单条 128K 序列合计** | — | ★ **约 2.5 GiB / 条** |
| **TP=32 的下场** | 32 张卡各存【同一条】的 2.5 GiB | 花掉 **80 GiB** 只服务【**1 个**】用户 |
| **DP=32 的下场** | 32 张卡各存【不同的】2.5 GiB | 同样 **80 GiB** 服务【**32 个**】用户 |

```
    ⟹ ★★★ 同样的显存，并发差【32 倍】。这才是 Attention DP 的真正动机。
       ★ 对照 §10.4.3：为此多花的是 7 GB/卡 的权重复制。
         用 7 GB 换 32 倍并发——这是本章里性价比最高的一笔交易。
```

> ★ [06 章 §6.3 ⑤](06-推理中的并行策略.md) 那个 **DCP**（**D**ecode **C**ontext **P**arallel，解码序列并行）就是来补同一个洞的——在 TP 组内部按序列维再切 KV，让「TP 超过 KV 头数后 KV 被白白复制」这件事不发生。**Attention DP 和 DCP 是同一种病的两种药**：前者换请求维、后者换序列维。完整推导在 [06 章 §6.4](06-推理中的并行策略.md)。

#### ③ DP 把有效 batch 放大了 32 倍，MoE 的 all-to-all 才划算

```
    TP=32：32 张卡在算【同一批】40 个 token
           ⟹ 全系统只有 40 个 token 要路由给 384 个专家
           ⟹ 每个专家平均分到 40×8/384 < 1 个 token ⟹ all-to-all 纯亏

    DP=32：32 张卡在算【32 批不同的】40 个 token = 1280 个 token
           ⟹ 每个专家平均 1280×8/384 ≈ 27 个 token ⟹ 专家 GEMM 才有形状

    ⟹ ★★ 注意力想要 DP、MoE 想要 EP，而【DP 恰好在喂饱 EP】。
       这是 [11 章 §11.7](11-MoE推理与专家并行.md) 那张图的另一半。
```

### 10.4.5 ⚠️ DP 不是白拿的，三条代价

```
    ⚠️ ① 多花约 7 GB/卡 复制注意力 + dense + 词表（§10.4.3 算过）
          ★ 但换来 32 倍并发，这笔账是赚的

    ⚠️ ② ★ 32 个 DP rank 必须【步调一致地一起 generate】
          因为 MoE 的 all-to-all 是跨 DP 组的集合通信，
          某张卡这一步没请求，也得塞一个【假 batch（dummy run）】进去凑数，
          否则另外 31 张卡永远在等它。
          ⟹ vLLM 源码注释写死了这条（06 章 §6.3 ③）
          ⟹ ★ 后果：低负载时这 32 张卡里可能有一半在算空气

    ⚠️ ③ P 和 D 的专家热度分布不同 ⟹ EPLB 要【分两套配】（11 章 §11.5）
```

> 📖 **EPLB**（**E**xpert **P**arallelism **L**oad **B**alancer，专家并行负载均衡器）——把热门专家复制到多张卡上、冷门专家合并，让 all-to-all 不被最慢的那张卡拖死（[11 章 §11.5](11-MoE推理与专家并行.md)）。

### ★ 10.4 一句话收口

| 那 99% 的专家参数 | 那 1% 的注意力参数 |
|---|---|
| P 和 D **切法完全相同**，都是 EP=32，各卡 12 个完整专家 | ★★ **全部的分歧都在这里** |

**P 侧选 TP 的理由**：prompt 长 ⟹ GEMM 的 M 很大 ⟹ 切开真能压 TTFT。⚠️ 真实系统里往往是 CP（长序列层）+ TP（短窗口层）混着上，不是纯 TP。

**D 侧选 DP 的理由，按重要性排**：

| # | 理由 | 量级 |
|---|---|---|
| ★★★ ② | MLA 吸收成 MQA 后 KV **按头切不动**，TP 会把 KV cache 复制 32 份 | **并发差 32 倍** |
| ★★ ③ | DP 放大有效 batch 32 倍，正好喂饱 MoE 的 all-to-all | 专家从「<1 个 token」到「27 个 token」 |
| ★ ① | decode 的 GEMM 已经小到切不动（M=40），再切只剩 all-reduce 和下发开销 | 收益递减，可能为负 |

## 10.5 三篇代表论文，三个不同的出发点

### ① DistServe——从「goodput」这个指标出发

> ✅ arXiv 2401.09670（`papers/DistServe-Prefill-Decode-Disaggregation-arXiv-2401.09670.pdf`）

论文先定义了一个关键指标：

> 📖 **goodput（有效吞吐）**——**在满足延迟承诺（SLO）的前提下**，每张 GPU 每秒能服务的请求数。★ 和普通 throughput 的区别：**跑得再快，超了 SLO 就不算数。** ⟹ 这个指标是整个 PD 分离领域的立论基础，也是 [13 章 §13.4](13-性能指标与压测.md) 压测流程里「画一条 SLO 横线」那一步在做的事。

**结果**（✅ 论文摘要原文）：

> *"DistServe can serve **7.4× more requests** or **12.6× tighter SLO**, compared to state-of-the-art systems, while staying within latency constraints **for > 90% of requests**."*

> ⚠️ **三条引用纪律，缺一条就会把这个数字用错**：
> ① 「7.4× more requests」和「12.6× tighter SLO」是**二选一**，不是同时拿到——放松 SLO 换吞吐，或收紧 SLO 换延迟，是同一条 goodput 曲线上的两个点。
> ② 原文带一个常被漏掉的限定：**「> 90% of requests」**，也就是 **P90** 口径，不是全部请求。
> ③ ★ 这是 **goodput**（每 GPU、满足 SLO）的倍数，**不是裸吞吐的倍数**，更不是「延迟降低 7.4 倍」。

### ② Splitwise——从「成本和功耗」出发

> ✅ arXiv 2311.18677（`papers/Splitwise-Phase-Splitting-arXiv-2311.18677.pdf`），Microsoft

```
    ★ 视角不同：微软关心的是【数据中心怎么配机器最省钱省电】
    ⟹ 提出【异构集群】：Prefill 用新卡（H100），Decode 用老卡（A100）
       ——因为 Decode 的算力本来就用不掉（§10.3.2）
```

**结果**（✅ 论文摘要原文）：

> *"Splitwise clusters achieve up to **1.4× higher throughput at 20% lower cost**. Alternatively, they can deliver **2.35× more throughput under the same power and cost budgets**."*

> ★★ **Splitwise 还给了 §10.3.3 那个「配比没有静态解」问题一个工程答案**（✅ 论文 §IV-A 原文描述）：它维护**三个**机器池——prompt 池、token 池，外加一个**mixed 池**。队列太长时，调度器把机器**临时挪进 mixed 池**，让它像非分离系统那样跑混合批；队列排空后再挪回原池。论文明确写道 *"Switching pools does not incur any noticeable latency."*
> ⚠️ **而且论文自己坦承了一个和 §10.2.4 完全一致的结论**（✅ 原文）：*"At high load, Splitwise devolves into the iso-count Baseline, since it starts mixed batching with all the machines in the mixed pool."* ——**高负载下 Splitwise 会退化成混部基线。** ★ 也就是说，PD 分离的收益主要在**中低负载**区间（那里延迟稳定性值钱），高负载下大家殊途同归。

### ③ Mooncake——从「真实线上系统」出发

> ✅ arXiv 2407.00079（`papers/Mooncake-KVCache-Centric-arXiv-2407.00079.pdf`），月之暗面（Kimi）

```
    ★ 这是唯一一篇【从生产系统里长出来】的论文，
      所以它关心的问题最「脏」，也最实用：

      ★★ 核心主张：以 KVCache 为中心（KVCache-centric）
         把整个集群的 CPU 内存、SSD 都组织成一个
         【分布式 KV Cache 池】，而不只是点对点传一次。
      ⟹ 于是前缀缓存（05 章 §5.5）也变成了【全局共享】的：
         P 实例算过的 KV，其他实例也能命中
      ★ 还包含一个很现实的东西：【基于预测的早期拒绝】
         ——过载时提前拒掉注定超 SLO 的请求，而不是让所有人一起慢
         ⟹ ★★ 这其实是 goodput 指标的直接推论：
            一个注定超 SLO 的请求，跑完了也不计分，不如不跑
```

**结果**（✅ 论文摘要原文）：

> *"Mooncake can achieve up to a **525% increase in throughput** in certain simulated scenarios while adhering to SLOs. Under real workloads, Mooncake's innovative architecture enables Kimi to handle **75% more requests**."*

> ⚠️⚠️ **这两个数字有三个坑，逐条拆开**：
> ① **模拟 vs 真实**：525% 是 **certain simulated scenarios**（特定模拟场景），75% 是 **real workloads**（真实负载）。★ 论文自己把它们区分得很清楚，我们引用时也必须区分。**真实世界的收益永远小于最优场景，这里差了 7 倍。**
> ② ★ **"525% increase" 是「增加 525%」，也就是变成原来的 6.25 倍，不是 5.25 倍。** 同理 "75% more requests" 是变成 **1.75 倍**。英文的 "increase by X%" 一律是在原值之上再加 X%。
> ③ 这是**吞吐**的倍数，吞吐侧说百分比没有歧义；但**延迟侧永远不要用百分比**——「时间减少 60%」等于「加速 2.5 倍」，写成「加速 60%」就差了 4 倍（[13 章 §13.5](13-性能指标与压测.md) 有完整的换算表）。

**三篇放在一起看**：

| | DistServe | Splitwise | Mooncake |
|---|---|---|---|
| 出发点 | 指标定义（goodput） | 数据中心成本与功耗 | 生产系统的脏问题 |
| 最大贡献 | ★ 把「满足 SLO 的吞吐」立成标准指标 | ★ 异构集群 + **mixed 池动态转换** | ★★ **全局 KV Cache 池** + 早期拒绝 |
| 关键数字（✅ 摘要原文） | **7.4×** 请求 **或** 12.6× 更紧 SLO（P90 口径，二选一） | **1.4×** 吞吐 @ **20%** 更低成本 | 模拟 **+525%**（= 6.25×）/ ⚠️ 真实 **+75%**（= 1.75×） |
| 对本章的回响 | §10.3.3 的配比要按 goodput 配平 | §10.2.4「小规模不划算」「高负载退化成混部」 | §10.2.6「KV 就是全部记忆」的极致推论 |

## 10.6 ★★ 成败关键：KV Cache 怎么传过去

§10.2.5 已经把账算清楚了，结论重申一遍：

```
    ★★ 搬运开销占 Prefill 的比例 ≈ 一个常数，只取决于【走哪条线】：

       NVLink 450 GB/s（单向）  ⟹  0.7%   ✅ 可以忽略
       IB     50  GB/s（单向）  ⟹  6.1%   ✅ 可以接受，这是主流形态
       PCIe   63  GB/s（单向）  ⟹  4.8% × 两趟 ≈ 10%   ⚠️ 勉强
       以太   12.5 GB/s         ⟹ ★ 24%   ❌ 收益被吃光

    ⟹ ★★★ 所以 PD 分离几乎必然要求【RDMA / InfiniBand】。
       在普通以太网集群上做 PD 分离，大概率是负收益。
```

### 10.6.1 三个降低传输成本的关键技巧

```
    ★★ ① 分层传输（layer-wise / 边算边传）—— 最重要的一条
       不要等整个 prompt 算完再传。
       ⟹ 第 1 层算完就传第 1 层的 KV，同时算第 2 层
       ⟹ 传输和计算【重叠】，理论上只剩最后一层的传输暴露在外
       ⟹ 4096 token 的例子：10.7 ms ⟹ 暴露部分约 10.7/32 ≈ 0.3 ms
       ✅ Splitwise 论文 Fig.13 画的就是这件事
          （serialized transfer vs per-layer transfer）

    ★ ② 只传需要的部分
       如果 D 实例本地已经命中了部分前缀缓存（05 章 §5.5），
       就只传【差集】。★ 长系统提示词场景下这一条能省掉绝大部分。

    ★ ③ 直接写进对端的 KV 块
       用 RDMA 把数据直接落到 D 实例的 PagedAttention 块里（05 章 §5.3），
       ⟹ 省掉一次「先收到缓冲区、再拷进 KV 池」的拷贝

    ⚠️ ④ 别忘了还有一条【不传】的路：
       让 P 和 D 落在同一台机器的不同卡上，走 NVLink（0.7%）。
       ★ 但这样就失去了「两侧用不同硬件」的收益，
         而且 P:D 配比被机内卡数锁死（§10.3.3）——通常不这么做。
```

> ⚠️ **分层传输不是免费的。** 它把一次大传输拆成 32 次小传输，**每次都要付一遍固定开销**（RDMA 的 work request 提交、完成队列轮询、可能的同步）。★ 当 prompt 很短时，32 次小传输的固定开销之和可能**超过**一次大传输——这又是一条「短 prompt 不该分离」的理由。所以框架通常会按 KV 块大小攒批，而不是严格逐层发（块的概念见 [05 章 §5.3 PagedAttention](05-PagedAttention与前缀缓存.md)，「只传差集」依赖的前缀缓存见 [§5.5](05-PagedAttention与前缀缓存.md)）。

### 10.6.2 框架里这一层叫「KV 连接器」，做成了可插拔的

> ✅ **vLLM**（[kv_transfer/kv_connector/v1/](../源码/vLLM/vllm/distributed/kv_transfer/kv_connector/v1/)）：`base.py` 定义接口，实现有 `nixl/`（NVIDIA 的 RDMA 传输库）、`mooncake/`、`lmcache_connector.py`、`moriio/`、`hf3fs/`、`offloading/`，★ 以及 `multi_connector.py`（可以把多个后端串起来，比如先查本地再查远端）。
>
> ✅ **SGLang**（[disaggregation/](../源码/SGLang/python/sglang/srt/disaggregation/)）：`prefill.py` / `decode.py` 是两端的主逻辑，后端有 `nixl/`、`mooncake/`、`mori/`、`ascend/`（昇腾），★ 还有 `fake/`（用来在没有 RDMA 的环境下做功能测试——很实用的工程设计），以及 `decode_kvcache_offload_manager.py`（★ D 端的 KV 换出到 CPU/SSD）。

> 📖 **NIXL**（**N**VIDIA **I**nference **X**fer **L**ibrary，英伟达推理数据传输库）——目前两个框架都在用的主流 RDMA 后端，屏蔽了底层是 IB、RoCE 还是 NVLink 的差别。

## 10.7 ⚠️ PD 分离的代价，以及什么时候【不该用】

### 10.7.1 五条代价，都有数字

| # | 代价 | 量级（本章的例子） | 出处 |
|---|---|---|---|
| ⚠️ ① | **运维复杂度显著上升** | 两个集群 + 一个路由器 + 一套 KV 传输通道，各自要监控、调优、扩缩容 | §10.3.1 |
| ⚠️ ② | **必须有 RDMA 网络** | 换成 100 Gb/s 以太网，搬运开销从 6% 涨到 **24%** | §10.2.5 |
| ⚠️ ③ | ★ **短 prompt 场景零收益** | M=64 时混部尖峰只有 **1.02×**——**根本没有干扰可消** | §10.2.7 |
| ⚠️ ④ | ★★ **P 侧显存基本闲置** | 小规模下最大并发**直接减半**（240 → 120 条） | §10.2.4 |
| ⚠️ ⑤ | ★★ **配比是持续调优问题，而且没有静态解** | 同一模型同一张卡，最优配比横跨 **1:21 到 38:1** | §10.3.3 |

> ⚠️ **把 ③ 说透一点，因为它最反直觉。** prompt 只有 50 个 token 时：Prefill 本身是**访存受限**的，耗时被权重读取钉死在 **7.0 ms**（算力侧只要 2.0 ms，用不上）；它的 KV 只有 6.25 MiB，搬过去只要 **0.13 ms**——★ **搬运其实很便宜，问题不在这儿。**
> ★★ 真正的问题是：**收益是零。** 这 7.0 ms 的 Prefill 掺进 decode 批次里，只会把 TBT 从 8.7 ms 抬到 8.9 ms（1.02×），**压根没有尖峰需要消除**；而且两阶段都是访存受限，**不存在两套相反的最优配置可以分别优化**。⟹ 于是一次路由决策、一次 RDMA 握手、一次跨机往返（合计零点几到几毫秒）**全都是纯亏**。**收益为零时，任何成本都是净亏。**

### 10.7.2 一张决策表

| 你的情况 | 该用什么 | 为什么 |
|---|---|---|
| 单机 8 卡以内 | ❌ **别分离，用 chunked prefill** | §10.2.4：小规模下混部的 TTFT、稳态 TBT、最大并发**三项全赢** |
| 没有 RDMA（普通以太网） | ❌ **别分离** | §10.2.5：搬运吃掉 24% 的 TTFT |
| 主要是短 prompt 聊天（几十~一两百 token） | ❌ **别分离** | §10.2.7：Prefill 也是访存受限，没有性格差异可利用 |
| 输入输出比极度不稳定，且不打算做动态转换 | ⚠️ **谨慎** | §10.3.3：静态配比无解，会有一侧长期空转 |
| ✅ 规模几十张卡以上 + 有 RDMA + 长 prompt（RAG / 长文档 / 代码库） | ✅ **上** | 三个前提同时满足，收益才真正兑现 |
| ✅ 有明确的、**分别**针对 TTFT 和 TPOT 的 SLO | ✅ **上** | 这正是 goodput 指标存在的意义（§10.5 ①） |
| ✅ 用 MLA 的大 MoE（DeepSeek / openPangu 类） | ✅✅ **强烈建议** | §10.4.4 ②：D 侧走 Attention DP 能换来 **32 倍并发** |

> 🔑 **一句话判据**：**PD 分离不解决「算力不够」，它解决「两种活互相打断」和「两种活想要不同的机器」。** ★ 先确认你的场景里这两个问题真的存在、而且真的严重，再谈分离。

## 10.9 本章小结

**① 立论，以及它的前提。** 两个阶段性格相反 ⟹ 拆成两个集群，各自最优配置。★★ 但「Prefill 算力受限」**不是无条件的**——算术强度大致等于 prompt 长度，临界点在**几百个 token** 的量级（03 章算 M≈390，算子 09 章算 M≥325）。**prompt 短于它，两阶段是同一种病，分离没有收益可赚。**

**② 那个 4K RAG 例子，同样 2 张卡的诚实对账**（§10.2.4）：

| | 混部 ×2 | 分离 1P+1D |
|---|---|---|
| 新用户 TTFT | ✅ 178 ms | ⚠️ 188 ms（不重叠） |
| 老用户稳态 TBT | ✅ 7.8 ms | 8.7 ms |
| 老用户 Prefill 期间 TBT | ⚠️ 22.3 ms（2.9× 抖动） | ✅ **8.9 ms，零抖动** |
| 最大并发 | ✅ 约 240 条 | ⚠️ 约 120 条 |

⟹ ★★★ **小规模下 PD 分离并不划算**：它只赢了「抖动」一项，却付出了一倍显存和一套 RDMA。**收益要等到「规模大 + 并发高 + 两侧真的用不同配置」三条同时成立才兑现。**

**③ 之所以搬得动**：★★【**KV Cache 就是这次对话的全部记忆**】。4096 token × 128 KiB = 512 MiB，搬过去 D 卡就什么都知道了。⚠️ 那个 128 KiB 是 `2 × n_kv_heads(8) × head_dim(128) × 2字节 × 32层`——**用 `d_model` 硬套会算成 512 KiB，高 4 倍**。

**④ 搬运成本是个常数，只取决于走哪条线**（§10.2.5）：

| 线路 | 单向可用带宽 | 占 Prefill 的比例 |
|---|---|---|
| NVLink | **450** GB/s（900 是双向聚合） | 0.7% ✅ |
| InfiniBand 400 Gb/s | **50** GB/s（Gb ÷ 8） | 6.1% ✅ |
| PCIe 5.0 ×16 | **63** GB/s 单向 | 4.8% × 两趟 ⚠️ |
| 100 Gb/s 以太网 | 12.5 GB/s | **24%** ❌ |

⟹ **没有 RDMA 就别做。** 再加一条 ★ 分层边算边传（和计算重叠，能把暴露的传输时间压到约 1/32）。框架把这一层做成了可插拔的「KV 连接器」（NIXL / Mooncake / LMCache）。

**⑤ ★★ §10.4「P 用 TP、D 用 DP」的真相**（例：openPangu 505B MoE，各 32 卡）：占 **99%** 的专家参数两边都是 **EP=32，切法完全相同**；分歧只在那 **4 B（不到 1%）** 的注意力上。★★★ D 侧选 DP 的决定性理由是 **MLA 吸收成 MQA 后 KV 按头切不动**——TP 会把同一份 KV cache 复制 32 份，**并发直接掉 32 倍**；代价只是多复制 7 GB/卡 的权重。

**⑥ 配比没有静态解**（§10.3.3）。同一个模型、同一张卡，最优 P:D 从 **1:21**（Agent 长输出）一路到 **38:1**（长文抽取），跨度 **800 倍**。⟹ 不给输入输出长度分布就谈「配比一般是 1:4」，等于没说。Splitwise 的工程答案是 **mixed 池动态转换**。

**⑦ 三篇论文，三个视角**（数字均为 ✅ 摘要原文，⚠️ 口径已标注）：

| 论文 | 数字 | ⚠️ 引用时必须带上的口径 |
|---|---|---|
| DistServe | **7.4×** 请求 **或** 12.6× 更紧 SLO | 二选一；P90 口径；是 **goodput** 不是裸吞吐 |
| Splitwise | **1.4×** 吞吐 @ **20%** 更低成本 | 论文自承**高负载下退化成混部基线** |
| Mooncake | 模拟 **+525%** / 真实 **+75%** | ★「+525%」= **6.25 倍**不是 5.25 倍；模拟与真实差 7 倍 |

**⑧ ⚠️ 不该用的场景**：小规模（8 卡以内）、短 prompt 为主、没有 RDMA。⟹ 那些场景下 **chunked prefill 才是对的答案**。

**⑨ ⚠️ 口径纪律，三条**：① 「Decode GPU 利用率低」说的是**算力**利用率，它的**带宽**利用率接近 100%——低算力利用率是 Memory Bound 的**定义**，不是浪费。② H100 SXM5 稠密峰值是 **989 TFLOPS**，1979 是带 2:4 稀疏的，推理用不上。③ 「时间减少 60%」= **加速 2.5 倍**，不是「加速 60%」。
