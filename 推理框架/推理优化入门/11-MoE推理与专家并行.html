11 MoE 推理与专家并行

一句话：MoE 把「参数量」和「计算量」解耦了——参数多到必须切开放，计算量却很小。这个组合让 MoE 推理的瓶颈从「算」变成了「传」和「等」。

11.1 MoE 是什么，以及它给推理带来的新账本

📖 MoE（Mixture of Experts，混合专家）——把 Transformer 里的 MLP（前馈层）
换成 N 个并列的「专家」，每个 token 由一个路由器（router / gate）决定只送进其中 K 个。

    稠密模型：每个 token → 走过【全部】参数
    MoE 模型：每个 token → ★ 只走过 K/N 的参数

✅ 以 DeepSeek-V3 为例（论文摘要原文，arXiv 2412.19437）：

"a strong Mixture-of-Experts (MoE) language model with 671B total parameters with 37B activated for each token."

    ★★ 把这两个数字放进推理的账本里，矛盾就出来了：

    671B 总参数 × FP8(1字节) = ★ 671 GB 显存      ⟹ 需要【至少 9 张 H100】才装得下
    37B 激活参数              = ★ 计算量只相当于一个 37B 的模型

    ⟹ ★★★ 你被迫用 9+ 张卡，却只做 37B 的计算量。
       ⟹ 单卡算力利用率天然很低
       ⟹ MoE 推理的核心难题不是「算得慢」，而是
          【怎么让这么多张卡不空转】

11.2 三种切法，只有一种对

模型太大必须切。有三个选择：

    ★ 选项一：TP（把每个专家的权重矩阵切开，每卡一片）
      ⚠️ 问题：每个专家本来就不大，再切成 1/8 ⟹ 矩阵小到 GPU 跑不动
      ⚠️ 而且每层还是要 all-reduce
      ⟹ ❌ 对 MoE 层不合适

    ★ 选项二：DP（每张卡放一份完整模型）
      ⚠️ 问题：671 GB 一张卡放不下
      ⟹ ❌ 不可行

    ★★ 选项三：EP（Expert Parallelism，专家并行）
      ★ 把 256 个专家【分给】8 张卡，每卡 32 个【完整的】专家
      ✅ 每个专家的矩阵保持完整 ⟹ GPU 跑得动
      ✅ 显存平摊
      ⚠️ 代价：token 必须【跑到专家所在的卡上去】⟹ all-to-all 通信
      ⟹ ★★ 这是唯一正确的选择

11.3 EP 的通信：all-to-all

📖 all-to-all（全交换）——每张卡都要给其他每张卡发一份不同的数据。
和 all-reduce（每张卡收到同样的结果）不同，all-to-all 每张卡收到的东西都不一样。

    一个 MoE 层的完整流程：

    ① 路由：每个 token 算出「我该去哪 8 个专家」
    ② ★ dispatch（分发）：all-to-all #1
       把每个 token 的隐藏向量，发到它选中的专家所在的卡
    ③ 计算：每张卡用【本地】的专家处理收到的 token
    ④ ★ combine（聚合）：all-to-all #2
       把结果发回 token 原来所在的卡，按路由权重加权求和

    ⟹ ★★ 每个 MoE 层 = 2 次 all-to-all
       一个 60 层的模型 ⟹ ★ 120 次 all-to-all

    ⚠️ all-to-all 为什么是噩梦：
      ① ★ 它是【同步屏障】——所有卡必须一起到场、一起完成
      ② ★★ 它的耗时由【最慢的那张卡】决定
      ③ 通信量和 batch 里的 token 数成正比
      ④ 跨机的 all-to-all 走网络，比 NVLink 慢一个数量级

    ⟹ 于是 §11.4 那个问题变成了 MoE 推理的头号敌人。

11.4 ★★ 头号敌人：专家负载不均衡

    理想情况：256 个专家，每个都收到差不多数量的 token
    ★★ 真实情况：路由器是【学出来的】，它有强烈的偏好。
       某些「热门专家」收到的 token 是冷门专家的【几十倍】。

    后果（这是一条因果链，要连起来看）：

    某张卡上恰好聚集了几个热门专家
      ⟹ ★ 这张卡要处理的 token 数是别人的 5 倍
      ⟹ 它算得慢
      ⟹ ★★ all-to-all 是同步的，【所有其他卡都在等它】
      ⟹ ★★★ 整层的耗时 = 最慢那张卡的耗时
      ⟹ 其余 7 张卡的算力全部浪费

    ⟹ ★ 这就是为什么 MoE 推理的实际 MFU 常常低得可怜。

而且推理比训练更麻烦：

    训练：可以在损失函数里加【负载均衡辅助损失】，
          ★ 强迫模型自己学会均匀路由

    ⚠️ 推理：模型已经训完了，路由行为【改不了】。
          而且不同的业务负载（中文/代码/数学）会激活【不同的热门专家】
    ⟹ ★★ 只能在【部署层面】想办法：
       既然专家的热度改不了，那就【改专家放在哪张卡上】。

11.5 EPLB：把热门专家摊开

📖 EPLB（Expert Parallelism Load Balancer，专家并行负载均衡器）

    ★★ 核心思路两条：

    ① 重排（rearrange）：
       统计每个专家的实际负载，把【热门专家分散】到不同卡上，
       让每张卡的总负载尽量相等。
       ⟹ 这是一个装箱问题（bin packing）

    ② ★ 冗余专家（redundant experts）：
       特别热的专家，干脆在【多张卡上各放一份副本】，
       ⟹ 它的 token 就能被分摊到多张卡
       ⟹ 代价是多占一点显存——但 MoE 本来就是拿显存换算力的

    ⟹ ★ 关键：负载分布随业务变化 ⟹ 这个重排必须是【在线动态】的，
       而且要能在【不中断服务】的前提下把专家权重搬到别的卡上。

✅ 源码可查：

vLLM（distributed/eplb/）：
eplb_state.py（当前专家分布状态）、policy/（重排算法）、
rebalance_execute.py（★ 执行搬运）、eplb_communicator.py、
★ async_worker.py（异步做重排，不阻塞推理——这是能上线的关键）。

SGLang（srt/eplb/）分得更细：
expert_distribution.py（★ 统计谁热谁冷）、
expert_location.py（★ 专家现在在哪）、
expert_location_dispatch.py（按位置分发 token）、
expert_location_updater.py（★ 在线更新位置）、
eplb_algorithms/（多种均衡算法）、
lplb_solver.py（求解器）、
★ eplb_simulator/（离线模拟器——可以拿历史负载先算出最优布局再上线，
不用在生产环境试错，这是很务实的工程设计）。

★ 从这两个目录的文件数就能读出一个信号：
EPLB 不是一个小优化，它是大规模 MoE 部署的必备组件。

11.6 MoE 推理的其他麻烦

    ⚠️ ① Decode 阶段的 batch 太小 ⟹ 专家更加吃不饱
       batch=8 的一步，只有 8 个 token，选出 64 个 (expert, token) 对，
       ★ 分散到 256 个专家上 ⟹ 大部分专家【一个 token 都没有】
       ⟹ MoE 在小 batch 下效率极差
       ⟹ ★★ 这是 MoE 模型比稠密模型【更需要大并发】的原因

    ⚠️ ② 专家权重的显存无法用 KV 换
       稠密模型显存不够可以少放几个用户；
       ★ MoE 的 671 GB 专家权重是【硬性占用】，一点都省不了

    ⚠️ ③ ★ Prefill 和 Decode 的专家热度分布【不一样】
       ⟹ 回收 10 章：PD 分离后，两个集群要各配一套 EPLB

    ⚠️ ④ all-to-all 和计算难以重叠
       不像 TP 的 all-reduce 有成熟的重叠技巧，
       all-to-all 的依赖关系更强
       ⟹ ★ 这是当前学术和工程上最活跃的优化点之一
         （DeepEP 这类专用通信库就是冲这个去的）

11.7 ★ 回收 06 章：为什么 SGLang 要为 MoE 重新设计并行

现在可以完整地解释 06 章那个「注意力用 DP、MoE 用 EP」的设计了：

    ★ 同一个 DeepSeek-V3，两部分的诉求【正好相反】：

    ┌──────────────┬──────────────────────────────────────┐
    │  注意力层     │  用了 MLA（07 章）⟹ KV 极小           │
    │              │  ⟹ ★ 每卡存完整 KV 完全可行            │
    │              │  ⟹ ★★ 用 DP：各卡处理不同请求，        │
    │              │       【零通信】                       │
    ├──────────────┼──────────────────────────────────────┤
    │  MoE 层       │  671B 参数，一张卡放不下               │
    │              │  ⟹ ★★ 必须用 EP：专家分散 + all-to-all │
    └──────────────┴──────────────────────────────────────┘

    ⟹ ★★★ 一个模型内部，两部分要用【完全不同的并行策略】。
       vLLM 的固定五维网格（ExtDP×DP×PP×PCP×TP）表达不了这个；
       SGLang 干脆放弃全局 DP 维，让每部分自己声明切法：
         attn: attn_dp × attn_cp × attn_tp
         moe:  moe_dp × moe_ep × moe_tp
       ✅ [parallel_state.py:2587](../源码/SGLang/python/sglang/srt/distributed/parallel_state.py#L2587)

    ⟹ ★ 一句话总结这个设计：
       【MLA 让注意力层不需要切，MoE 让专家层不得不切。
        既然需求分裂了，切法就也该分裂。】
