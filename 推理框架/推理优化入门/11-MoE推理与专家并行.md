# 11 MoE 推理与专家并行

> **一句话**：MoE 把「参数量」和「计算量」解耦了——**参数多到必须切开放，计算量却很小**。这个组合让 MoE 推理的瓶颈从「算」变成了「传」和「等」。

---

## 11.1 MoE 是什么，以及它给推理带来的新账本

> 📖 **MoE**（**M**ixture **o**f **E**xperts，混合专家）——把 Transformer 里的 MLP（**M**ulti-**L**ayer **P**erceptron，多层感知机，也叫前馈层 / FFN）换成 N 个并列的「专家」，每个 token 由一个**路由器**（router，也叫 gate / 门控）决定只送进其中 K 个。

```
    稠密模型：每个 token → 走过【全部】参数
    MoE 模型：每个 token → ★ 只走过 K/N 的参数
```

**本章全程用 DeepSeek-V3 做例子，先把配置摆齐**（后面每一笔账都从这张表取数）：

| 参数 | 值 | 来源 |
|---|---|---|
| 总参数 | **671 B** | ✅ V3 技术报告摘要（arXiv 2412.19437） |
| 每 token 激活参数 | **37 B** | ✅ 同上 |
| 层数 | 61（★ 前 3 层是稠密 FFN，后 **58 层**才是 MoE） | ✅ V3 技术报告 |
| 每个 MoE 层的**路由专家** | 256 个 | ✅ V3 技术报告 |
| 每个 MoE 层的**共享专家** | 1 个（📖 共享专家 = 每个 token 都必过，不参与路由） | ✅ V3 技术报告 |
| **Top-K** | **8**（从 256 个路由专家里选 8 个） | ✅ V3 技术报告 |
| 隐藏维度 H | 7168 | ✅ V3 技术报告 |
| 专家中间维度 | 2048 | ✅ V3 技术报告 |

> *"a strong Mixture-of-Experts (MoE) language model with **671B total parameters** with **37B activated for each token**."*（✅ V3 摘要原文）

**把 671 和 37 这两个数字放进推理的账本里，矛盾立刻出来**：

```
    激活率 = 37 ÷ 671 = ★ 5.5%

    671 B 权重 × 1 字节（✅ V3 原生就是 FP8 训练的，权重就是 FP8）
      = 671 GB     ⟹ ★ 光是把权重放下，就要 671 ÷ 80 = 9 张 H100
      （换成 BF16 是 1342 GB，要 17 张）

    37 B 激活参数
      = ★ 计算量只相当于一个 37B 的稠密模型

    ⟹ ★★★ 你买了 9 张以上卡的显存，却只买到了 37B 的计算量。
       ⟹ 单卡算力利用率天然很低
       ⟹ ★★ MoE 推理的核心难题不是「算得慢」，而是【怎么让这么多卡不空转】
```

> ⚠️ **「9 张」只是权重的理论下界**，真实部署要给 KV Cache、激活、通信缓冲留地方，还要把通信关在高带宽域里（§11.3）。✅ V3 官方给的最小部署单元是：**Prefill 4 机 32 卡、Decode 18 机 144 卡**（开源周 Day 6 博客）。

## 11.2 三种切法，只有一种对

模型太大必须切。有三个选择。先算一层 MoE 的路由专家权重有多大：

```
    一个专家 = W_gate + W_up + W_down，每个都是 7168 × 2048
             = 3 × 7168 × 2048 = 44,040,192 ≈ 44.0 M 参数

    256 个路由专家 = 256 × 44.0 M = 11.27 B 参数
    BF16 存储      = 11.27e9 × 2 = ★ 22.55 GB     ← 这才【一层】
    58 个 MoE 层   = 22.55 × 58  = ★★ 1308 GB
```

| 切法 | 怎么切 | 每卡的路由专家权重（一层 / 58 层，BF16） | 能不能用 | 为什么 |
|---|---|---|---|---|
| **DP**（Data Parallelism，数据并行） | 每张卡放一份**完整**模型，各算各的请求 | 22.55 GB / **1308 GB** | ❌ **不可行** | 一张 80 GB 的卡差 16 倍 |
| **TP**（Tensor Parallelism，张量并行） | 把**每个专家的矩阵**切成 8 片 | 2.82 GB / 163 GB | ⚠️ 能跑，但亏 | 专家中间维 2048 ÷ 8 = 256，矩阵太瘦，GPU 跑不满；而且每层还要 all-reduce |
| **EP**（Expert Parallelism，专家并行） | 256 个专家**整个整个地**分给 32 张卡，每卡 8 个 | **705 MB** / **40.9 GB** | ✅ **唯一正解** | 每个专家的矩阵保持完整，GPU 跑得动；显存平摊 |

```
    ★ 显存这件事上，EP 和 TP 是【等效】的——都是「除以并行度」。
      真正的区别在通信：

      EP 通信量 ÷ TP 通信量 = Top-K ÷ 并行度 = K / p

      p = 8  ：比值 1.0    ⟹ 一样
      p = 32 ：比值 0.25   ⟹ ★ EP 便宜 4 倍
      p = 64 ：比值 0.125  ⟹ ★★ EP 便宜 8 倍

    ⟹ ★ 并行度一旦超过 Top-K，EP 就开始碾压 TP，差距随 p 线性拉开。
       直觉：TP 让【每一个 token】都参与【每一次】通信；
             EP 只搬【被路由到的那 K 份】。
             MoE 的稀疏性（K=8 ≪ N=256）在 TP 下完全用不上。
```

> ★ 这个 `K / p` 的推导在 [大模型算子开发 08 章 §8.4.3](../../大模型算子开发/08-MoE算子与通信.md)。**EP 的代价是**：token 必须跑到专家所在的卡上去 ⟹ **all-to-all 通信**，这就是 §11.3。

**✅ DeepSeek-V3 官方实际用的配置**：

| 阶段 | EP | 规模 | 每卡的路由专家 | 来源 |
|---|---|---|---|---|
| **训练** | **64** | 2048 张 H800，PP=16，**TP=1** | 4 个 | ✅ V3 技术报告 §3.1 |
| **推理 Prefill** | **32** | 4 机 32 卡；注意力部分 TP4 + DP8 | 9 个（含 32 个冗余专家，见 §11.5）+ 1 共享 | ✅ V3 技术报告 §3.4 / 开源周 Day 6 |
| **推理 Decode** | **144** | 18 机 144 卡 | 2 个 + 1 共享 | ✅ 开源周 Day 6 博客 |

> ⚠️ **同一件事有两个官方数字，要说清出处**：V3 技术报告写的 Decode 配置是 40 机 320 卡 / EP320（每卡 1 个专家）；两个月后的开源周博客写的是 18 机 144 卡 / EP144。**两个都是官方的，对应不同时期的部署。**

> ★ 顺带注意 Prefill 那一行：**注意力部分和 MoE 部分用的是完全不同的并行策略**（注意力 TP4 + DP8，MoE EP32）。这是 §11.7 整节要讲的事。

## 11.3 EP 的通信：all-to-all，以及把它的量算出来

> 📖 **all-to-all（全交换）**——每张卡都要给**其他每一张卡**发一份**不同**的数据。和 all-reduce（每张卡最后拿到**同样**的结果）不同，**all-to-all 每张卡收到的东西都不一样**。

```
    一个 MoE 层的完整流程：

    ① 路由：每个 token 算出「我该去哪 8 个专家」
    ② ★ dispatch（分发）：all-to-all #1
       把每个 token 的隐藏向量，发到它选中的专家所在的卡
    ③ 计算：每张卡用【本地】的专家处理收到的 token
    ④ ★ combine（聚合）：all-to-all #2
       把结果发回 token 原来所在的卡，按路由权重加权求和

    ⟹ ★★ 每个 MoE 层 = 2 次 all-to-all
       DeepSeek-V3 有 58 个 MoE 层 ⟹ ★ 每次前向 116 次 all-to-all
       （⚠️ 不是 61 × 2 = 122——前 3 层是稠密 FFN，不参与）
```

### 11.3.1 通信量：一步一步算出来

**设定**：EP = 32，decode 阶段，每张卡这一步手上有 **t = 64** 个 token。为了让公式好读，先按 BF16（2 字节）算。

| 步 | 在算什么 | 式子 | 结果 |
|---|---|---|---|
| ① | 本卡这一步的 token 数 t | — | **64** |
| ② | ★★ 每个 token 要复制成 **Top-K** 份 | 64 × **8** | **512 份** |
| ③ | 一份多大 | H × 字节数 = 7168 × 2 | **14 KiB** |
| ④ | 全部发出去 | 512 × 14 KiB | 7 MiB |
| ⑤ | 扣掉本来就落在自己卡上的那部分 | × (1 − 1/32) | **6.78 MiB** ← 这是 Dispatch |
| ⑥ | Combine 原路返回，量一样 | × 2 | **13.6 MiB / 层** |
| ⑦ | 58 个 MoE 层 | × 58 | **787 MiB / 每卡 / 每个 decode 步** |

```
    写成公式（★ 这是本章最该记住的一条）：

    每卡单向 Dispatch 字节 = t × K × H × b × (1 − 1/EP)
                             ▲   ▲   ▲   ▲       ▲
                          本地  ★复制  隐藏  每元素  减掉落在
                          token  K 份  维度  字节数  自己身上的

    ⚠️ 第 ② 步（× Top-K）是【最常被漏掉】的一项。
       漏了它，这笔账会小 8 倍，然后你会得出「MoE 通信不算什么」的错误结论。
```

### 11.3.2 同样的字节数，走哪条线差 7 倍

> 📖 **先把带宽的口径弄对，这是最容易出错的地方**：
> - **NVLink**（机内卡间互联）：H100 SXM5 标称 **900 GB/s 是【双向聚合】**——意思是「同时发出 450 + 收进 450」。⚠️ 算「我要发出 X 字节要多久」时，**分母只能用 450 GB/s**，用 900 会乐观整整一倍。
> - **InfiniBand**（机间网络）：每卡一张 400 **Gb**/s 网卡。⚠️ Gb 是**比特**，÷ 8 = **50 GB/s** 单向线速。✅ DeepSeek 报告实测可达 >40 GB/s。
> - ⚠️ **凡是看到「通信量 ÷ 带宽」的式子，第一件事是确认两边是不是同一个方向口径。**

EP = 32 意味着 **4 台机器 × 8 卡**。一个 token 副本的去向（按均匀路由）：

```
    落在本卡        1/32   → 不用发
    落在本机其他卡  7/32   → 走 NVLink
    ★ 落在其他机器  24/32  → 走 IB        ← 3/4 的流量在这里
```

| 走哪条线 | 一步要搬的量（58 层，收发合计） | 单向带宽 | 耗时 |
|---|---|---|---|
| 假想：32 卡全在一台机器里 | 787 MiB | NVLink **450 GB/s** | **1.8 ms** |
| 机内那 7/32 的部分 | 178 MiB | NVLink **450 GB/s** | 0.4 ms |
| ★ 跨机那 24/32 的部分 | **609 MiB** | IB **50 GB/s**（线速） | **12.8 ms** |
| ★ 同上，按实测 40 GB/s | 609 MiB | IB 40 GB/s | 16.0 ms |
| **实际合计** | — | — | **约 13~16 ms** |

```
    ⟹ ★★ 同样 787 MiB，关在机内是 1.8 ms，跨 4 台机就变成 13 ms 以上。
       ★★★ MoE 并行策略设计的第一原则：
            【尽可能把 all-to-all 关在 NVLink 域里。】
```

**有个参照物才知道 13 ms 是多是少**——同一个 decode 步，这张卡还要**读一遍自己的专家权重**：

```
    每卡专家权重 = 58 层 × 705 MB = 40.9 GB（BF16）
    读一遍       = 40.9e9 ÷ 3.35e12 = ★ 12.2 ms

    ⟹ ★★ 通信 13 ms ≈ 访存 12 ms，两者【同一个量级】。
       谁都藏不住谁 ⟹ 通信和计算必须重叠，这不是锦上添花，是必须做。
```

> ★ V3 实际上把**权重和 dispatch 都做成了 FP8**（1 字节），上面两项各减半；再加上「节点受限路由」（限制一个 token 最多只去 4 台机器），跨机流量还能再降 43%。完整的三笔账（EP=8 机内 / EP=64 跨机 / 加上两个优化）在 [大模型算子开发 08 章 §8.3.4](../../大模型算子开发/08-MoE算子与通信.md)。

```
    ⚠️ all-to-all 为什么是噩梦——四条，第 ② 条是致命的：
      ① ★ 它是【同步屏障】：所有卡必须一起到场、一起完成
      ② ★★ 它的耗时由【最慢的那张卡】决定
      ③ 通信量和 batch 里的 token 数成正比，压不下去
      ④ 跨机走网络，比 NVLink 慢一个数量级（上表：11 倍）

    ⟹ 于是 §11.4 那个问题变成了 MoE 推理的头号敌人。
```

## 11.4 ★★ 头号敌人：专家负载不均衡

```
    理想情况：256 个专家，每个都收到差不多数量的 token
    ★★ 真实情况：路由器是【学出来的】，它有强烈的偏好。
       某些「热门专家」收到的 token 是冷门专家的【几十倍】。
```

**把代价算出来**。为了表能放下，缩小到 **EP = 8**（每卡 32 个专家），每卡 t = 64 个 token，Top-8：

```
    全系统 token 副本总数 = 8 卡 × 64 token × 8 = 4096
    完全均匀时，每张卡应该处理 4096 ÷ 8 = ★ 512 个副本
```

| 卡号 | 实际收到的副本数（⚠️ 构造的示意分布） | 相对平均 | 这张卡在干什么 |
|---|---|---|---|
| 卡 0 | **1280** | **2.50×** | ★ 上面有几个热门专家，全场最忙 |
| 卡 1 | 900 | 1.76× | 忙 |
| 卡 2 | 620 | 1.21× | 略忙 |
| 卡 3 | 450 | 0.88× | 算完了，**在等卡 0** |
| 卡 4 | 350 | 0.68× | 在等卡 0 |
| 卡 5 | 280 | 0.55× | 在等卡 0 |
| 卡 6 | 130 | 0.25× | 在等卡 0 |
| 卡 7 | 86 | 0.17× | 在等卡 0 |
| **合计 / 平均** | **4096 / 512** | 1.00× | — |

```
    ⟹ 整层的耗时 = 最慢那张卡 = 1280 个副本的耗时
    ⟹ ★★★ 有效算力利用率 = 平均 ÷ 最大 = 512 ÷ 1280 = 40%
       ★ 60% 的算力在【空等】，而且是【每一层都等一次】。

    这就是为什么 MoE 推理的实际 MFU（模型算力利用率）常常低得可怜。
```

**因果链要连起来看**：

```
    某张卡上恰好聚集了几个热门专家
      ⟹ ★ 这张卡要处理的 token 数是别人的 2.5 倍
      ⟹ 它算得慢
      ⟹ ★★ all-to-all 是【同步】的，所有其他卡都卡在 combine 这一步等它
      ⟹ ★★★ 整层耗时 = 最慢那张卡的耗时
      ⟹ 其余 7 张卡的算力全部浪费
```

**而且推理比训练更麻烦**：

```
    训练：可以在损失函数里加【负载均衡辅助损失】，
          ★ 强迫模型自己学会均匀路由
          （✅ DeepSeek-V3 走得更远：它【不加辅助损失】，
             而是给每个专家一个可动态调整的【偏置项】，
             专家太热就把偏置调低——因为辅助损失本身会伤模型质量）

    ⚠️ 推理：模型已经训完了，路由行为【改不了】。
          而且不同的业务负载（中文 / 代码 / 数学）会激活【不同的热门专家】

    ⟹ ★★ 只能在【部署层面】想办法：
       既然专家的热度改不了，那就【改专家放在哪张卡上】。  ⟹ §11.5
```

> ⚠️ **一个常见误解要澄清**：很多讲 MoE 的材料会说「热门专家超过容量上限后，多余的 token 就被丢掉（token dropping）」。**DeepSeek-V3 不是这样**——✅ V3 技术报告明确写了，得益于它的负载均衡策略，**训练和推理全程都不丢弃任何 token**。
>
> ★ 这件事要这样理解：**丢 token 和等慢卡，是同一个问题的两种付账方式。** 丢 token 换来齐整的形状和可预测的耗时，代价是精度；不丢 token 保住精度，代价就是上表那 60% 的空等。容量因子和 token dropping 的完整账在 [大模型算子开发 08 章 §8.6](../../大模型算子开发/08-MoE算子与通信.md)。

## 11.5 EPLB：把热门专家摊开

> 📖 **EPLB**（**E**xpert **P**arallelism **L**oad **B**alancer，专家并行负载均衡器）——DeepSeek 在 2025 年开源周放出的工具，vLLM 和 SGLang 都有对应实现。

```
    ★★ 核心思路两条：

    ① 重排（rearrange）：
       统计每个专家的实际负载，把【热门专家分散】到不同卡上，
       让每张卡的总负载尽量相等。
       ⟹ 本质是一个装箱问题（bin packing）
       ⟹ 注意它【不增加显存】，只是换个摆法

    ② ★ 冗余专家（redundant experts）：
       特别热的专家，干脆在【多张卡上各放一份副本】，
       ⟹ 路由到它的 token 就能被分摊到多张卡
       ⟹ 代价是多占一点显存——但 MoE 本来就是拿显存换算力的
```

**✅ DeepSeek-V3 Prefill 部署的真实数字**（开源周 Day 6 博客）：

| 项 | 值 | 怎么来的 |
|---|---|---|
| 路由专家 | 256 | 模型结构 |
| **冗余专家** | **+32** | 给最热的 32 个专家各加一份副本 |
| 合计要摆的专家 | 288 | 256 + 32 |
| 卡数（EP） | 32 | 4 机 32 卡 |
| **每卡摆几个** | **9 个路由专家 + 1 个共享专家** | 288 ÷ 32 = 9 |
| **显存代价** | **+12.5%** | 32 ÷ 256 |

**效果**（回到 §11.4 那张 8 卡的表，⚠️ 右列是示意，不是实测）：

| | 重排 + 冗余之前 | 之后 |
|---|---|---|
| 最忙的卡 | 1280 副本 | 约 600 |
| 平均 | 512 | 512 |
| 最大 ÷ 平均 | **2.50** | 约 1.17 |
| **有效算力利用率** | **40%** | **约 85%** |
| 额外显存 | 0 | +12.5% |

```
    ⟹ ★ 关键：负载分布随业务变化（今天代码多、明天中文多）
       ⟹ 这个重排必须是【在线动态】的，
          而且要能在【不中断服务】的前提下把专家权重搬到别的卡上。
```

> ✅ **源码可查**：
>
> **vLLM**（[distributed/eplb/](../源码/vLLM/vllm/distributed/eplb/)）：`eplb_state.py`（当前专家分布状态）、`policy/`（重排算法）、`rebalance_execute.py`（★ 执行搬运）、`eplb_communicator.py`、★ `async_worker.py`（**异步**做重排，不阻塞推理——这是能上线的关键）。
>
> **SGLang**（[srt/eplb/](../源码/SGLang/python/sglang/srt/eplb/)）分得更细：`expert_distribution.py`（★ 统计谁热谁冷）、`expert_location.py`（★ 专家现在在哪）、`expert_location_dispatch.py`（按位置分发 token）、`expert_location_updater.py`（★ 在线更新位置）、`eplb_algorithms/`（多种均衡算法）、`lplb_solver.py`（求解器）、★ `eplb_simulator/`（**离线模拟器**——可以拿历史负载先算出最优布局再上线，不用在生产环境试错，这是很务实的工程设计）。

> ★ 从这两个目录的文件数就能读出一个信号：**EPLB 不是一个小优化，它是大规模 MoE 部署的必备组件。**

> ★ 对算子层的连带要求：**专家权重的布局不能写死。** Grouped GEMM 拿到的权重指针数组、专家到卡的映射表，都必须是运行时可变的。如果实现里把「专家 i 在卡 i mod EP 上」硬编码进 kernel，EPLB 就用不了（[大模型算子开发 08 章 §8.5.5](../../大模型算子开发/08-MoE算子与通信.md)）。

## 11.6 MoE 推理的其他麻烦

**① Decode 阶段的 batch 太小 ⟹ 专家吃不饱**，这是 MoE 特有的：

| 每步的 batch | (专家, token) 对数 = batch × 8 | 每个专家平均分到 | ⚠️ 一个 token 都没收到的专家占比 |
|---|---|---|---|
| 8 | 64 | 0.25 | **约 78%** |
| 64 | 512 | 2 | 约 14% |
| 256 | 2048 | 8 | 约 0.03% |
| 1024 | 8192 | 32 | ≈ 0% |

```
    ⚠️ 最后一列是【按均匀路由做泊松近似估算】的：空置率 ≈ e^(−对数÷256)。
       真实路由有强烈偏好，冷门专家只会更空。

    ⟹ batch=8 时，256 个专家里有 200 个一个 token 都没有，
       却还要为它们走一遍 all-to-all 的同步流程。
    ⟹ ★★ 这就是 MoE 模型比稠密模型【更需要大并发】的原因，
       也是 DeepSeek 要把 Decode 的 EP 开到 144 的原因之一——
       EP 越大，全系统能同时凑到的 token 越多，专家才有形状可算。
```

**② 专家权重的显存无法拿 KV 来换**：

```
    稠密模型显存不够，可以少放几个用户（KV 少占点）；
    ★ MoE 的专家权重是【硬性占用】，一个字节都省不了。
      EP=32 时每卡 40.9 GB（BF16）/ 20.4 GB（FP8），先扣掉再谈 KV。
```

**③ ★ Prefill 和 Decode 的专家热度分布【不一样】**：

```
    ⟹ 回收 10 章：PD 分离之后，两个集群要各配一套 EPLB（10 章 §10.4.5）
```

**④ all-to-all 和计算难以重叠**：

```
    不像 TP 的 all-reduce 有成熟的重叠技巧，all-to-all 的依赖关系更强：
    dispatch 不完，本地专家就没数据可算。
    ⟹ ★ 这是当前学术和工程上最活跃的优化点之一
       （DeepEP 这类专用通信库、双 micro-batch 交错，都是冲这个去的）
```

## 11.7 ★ 回收 06 章：为什么 SGLang 要为 MoE 重新设计并行

现在可以完整地解释 06 章那个「注意力用 DP、MoE 用 EP」的设计了。

**★ 同一个 DeepSeek-V3，两部分的诉求正好相反**：

| | 注意力层 | MoE 层 |
|---|---|---|
| 权重有多大 | 小（MLA 的投影矩阵，全模型约 11 B） | **巨大**（58 层 × 22.55 GB = 1308 GB） |
| KV Cache | 用了 MLA（[07 章](07-注意力变体MQA-GQA-MLA.md)）⟹ 每 token 只要 68.6 KiB | 不产生 KV |
| 能不能 TP 切 | ⚠️ **MLA 的 KV 没有头维度，TP 只能整份复制**（07 章 §7.7） | 能，但并行度 > K 之后就输给 EP（§11.2） |
| ⟹ 最优切法 | ★★ **DP**：各卡处理不同请求，注意力层**零通信** | ★★ **EP**：专家分散 + all-to-all |
| 显存后果 | DP=8 时，同样显存服务 8 个用户而不是 1 个 | EP=32 时，每卡 40.9 GB 而不是 1308 GB |

```
    ⟹ ★★★ 一个模型内部，两部分要用【完全不同的并行策略】。

       vLLM 的固定五维网格（ExternalDP × DP × PP × PCP × TP）表达不了这个；
       SGLang 干脆放弃全局 DP 维，让每一部分自己声明切法：
         注意力：attn_dp × attn_cp × attn_tp
         MoE   ：moe_dp × moe_ep × moe_tp
       ✅ [parallel_state.py:2587](../源码/SGLang/python/sglang/srt/distributed/parallel_state.py#L2587)
```

**★ 还有一层因果，比「需求不同」更漂亮**：

```
    注意力用 DP ⟹ 32 张卡在算【32 批不同的】请求
                ⟹ 全系统这一步的 token 数【×32】
                ⟹ ★★ MoE 那边每个专家分到的 token 也【×32】
                ⟹ 回到 §11.6 那张表：从「78% 的专家空转」跳到「专家吃得饱」

    ⟹ ★★★ 不是「注意力想 DP、MoE 想 EP，只好各让一步」，
       而是【注意力的 DP 恰好在喂饱 MoE 的 EP】。两者互相成全。
       （这张图的另一半在 [10 章 §10.4.4](10-PD分离.md)）
```

```
    ⟹ ★ 一句话总结这个设计：
       【MLA 让注意力层不需要（也没法）切，MoE 让专家层不得不切。
        既然需求分裂了，切法就也该分裂。】
```

## 11.8 本章小结

```
    ① ★★ MoE 解耦了参数量和计算量
       ✅ DeepSeek-V3：671B 总参数，37B 激活（激活率 5.5%）
       ⟹ 光放权重就要 9 张 H100（FP8），却只做 37B 的计算
       ⟹ ★ 核心难题不是「算得慢」，是「这么多卡怎么不空转」

    ② 三种切法只有 EP 对
       DP：一层 22.55 GB × 58 层 = 1308 GB，放不下
       TP：专家中间维 2048÷8 = 256，矩阵太瘦跑不满
       EP：★ EP=32 时每卡 40.9 GB（BF16）
       ★ EP 通信 ÷ TP 通信 = K / p，并行度超过 Top-K 后 EP 碾压 TP
       ✅ V3 实配：训练 EP=64 / Prefill EP=32 / Decode EP=144

    ③ 代价是每层 2 次 all-to-all，★ 58 个 MoE 层 = 116 次
       ★★ 通信量公式：t × Top-K × H × 字节数 × (1 − 1/EP)
          ⚠️ 别漏 × Top-K，漏了小 8 倍
       ⚠️ NVLink 900 GB/s 是【双向聚合】，算单向要用 450
          IB 400 Gb/s ÷ 8 = 50 GB/s
       ★ 算出来：787 MiB/卡/步。全在机内 1.8 ms，跨 4 机 13~16 ms
         ⟹ 第一原则：把 all-to-all 关在 NVLink 域里

    ④ ★★★ 头号敌人是【专家负载不均衡】
       热门专家 → 某张卡变慢 → all-to-all 同步 → 全员等它
       ⟹ 整层耗时 = 最慢那张卡；最忙 2.5× 平均 ⟹ 有效利用率只有 40%
       ⚠️ 训练能靠辅助损失（V3 用的是无辅助损失的偏置法），
          推理【改不了路由】
       ⚠️ ✅ V3 官方明确：训练和推理【都不丢弃 token】
          ⟹ 丢 token 和等慢卡，是同一个问题的两种付账方式

    ⑤ ★ EPLB：改不了专家热度，就改【专家放哪】
       重排（不占显存）+ 冗余副本（✅ V3 Prefill 加 32 个，+12.5% 显存）
       + ★ 在线动态调整
       ✅ vLLM eplb/（async_worker 异步重排）
       ✅ SGLang eplb/（★ 还带离线模拟器）

    ⑥ ★ MoE 比稠密模型更需要大并发
       batch=8 时 78% 的专家一个 token 都收不到

    ⑦ ★★ 回收 06 章：MLA 让注意力可以（也只能）DP，MoE 让专家必须 EP
       ⟹ 而且 DP 把有效 token 数放大了 32 倍，★ 恰好在喂饱 EP
       ⟹ 需求分裂 ⟹ SGLang 的分部位切分设计
```
