# 12 CUDA Graph 与图编译

> **一句话**：小 batch 解码时，GPU 每个 kernel 只跑几十微秒，而 CPU 派发一个 kernel 也要几微秒——**CPU 追不上 GPU 了**。这一章讲怎么把 CPU 从关键路径上拿掉。

---

## 12.1 一个反直觉的瓶颈

先看 GPU 是怎么被驱动的：

```
    Python 代码 → PyTorch 算子 → CUDA Runtime → 驱动 → ★ 一个 kernel 排进 GPU 队列

    ★ 每个 kernel 的【CPU 端派发开销】：大约 5~20 微秒（μs）
```

现在数一数一次解码前向要派发多少 kernel：

```
    一层里有：QKV 投影、RoPE、注意力、输出投影、all-reduce、
             两个 LayerNorm、MLP 的三个矩阵乘、激活函数、残差相加 ...
             ★ 保守估计 15~30 个 kernel

    32 层 × 25 ≈ ★★ 800 个 kernel

    CPU 派发总耗时：800 × 10 μs = ★ 8 毫秒
```

```
    ★★ 关键对比（Llama-3-8B，单张 H100，batch=1 解码）：

       GPU 实际计算时间：  ≈ 5 ms
       ★ CPU 派发时间：    ≈ 8 ms

    ⟹ ★★★ GPU 有 3 ms 在【干等 CPU 喂饭】。
       这个现象叫【CPU 瓶颈 / launch overhead bound】。
```

> 🔑 **为什么这个问题只在推理里严重？**
> 训练的 batch 大，每个 kernel 要跑几毫秒，派发那 10 μs 完全可以忽略。
> **Decode 的 batch=1，kernel 小到只跑几十微秒——派发开销占比一下子变成主角。**
> ⟹ ★ 这是 01 章「解码阶段一切都不一样」的第三个后果（前两个是访存受限和 GEMV）。

## 12.2 CUDA Graph：把 800 次派发变成 1 次

> 📖 **CUDA Graph**——把一连串 kernel 调用**录制**成一张固定的图，之后**一次调用就把整张图交给 GPU**。

```
    ★ 录制（capture）阶段（只做一次，在启动时）：
      跑一遍前向，但不真执行，而是把
      「先跑 kernel A，再跑 B，B 依赖 A……」这个结构记下来

    ★ 重放（replay）阶段（每一步）：
      ★★ CPU 只发【一条】指令：「重放这张图」
      ⟹ 800 次派发 → 1 次
      ⟹ CPU 开销从 8 ms 降到 ★ 几十微秒
      ⟹ GPU 不再等 CPU
```

**⚠️ 但 CUDA Graph 有三个硬性限制**，理解它们才能理解框架为什么要做得那么复杂：

```
    ⚠️ ① 形状必须固定
       录制时 batch=8，重放时也必须是 batch=8。
       ⟹ ★ 框架的做法：为一批【预设的 batch 大小】各录一张图
          （比如 1,2,4,8,16,...,256），
          实际 batch=5 时，★ 用 batch=8 的图，多出来的位置填【垃圾数据】
       ⟹ 📖 这叫 padding（补齐）。代价是算了一点无用功，
          但比 CPU 瓶颈划算得多。

    ⚠️ ② 显存地址必须固定
       图里记的是【绝对地址】。所以输入输出必须放在
       ★ 预先分配好的固定缓冲区里，每次把新数据【拷进去】。

    ⚠️ ③ 不能有依赖数据的控制流
       图是死的。★ 「if 某个条件成立就走另一条路」录不进去。
```

**⟹ 于是有一条重要推论**：

```
    ★★ Prefill 阶段【几乎用不了】CUDA Graph。
       因为 prompt 长度千变万化，形状不固定，为每种长度录图不现实。
    ★★ 而 Prefill 本来就是算力受限、kernel 很大，
       派发开销占比小 ⟹ ★ 它也【不需要】CUDA Graph。

    ⟹ ★★★ 完美互补：需要它的（Decode）形状固定，
             形状不固定的（Prefill）不需要它。
```

## 12.3 图编译（torch.compile）：另一件事

**初学者最容易把这两个混起来，它们解决的是不同的问题**：

```
┌──────────────┬────────────────────────┬──────────────────────┐
│              │  CUDA Graph            │  图编译 torch.compile │
├──────────────┼────────────────────────┼──────────────────────┤
│  解决什么     │ ★ CPU 派发开销          │ ★ kernel 本身不够好   │
│  怎么做      │ 把派发【打包成一次】     │ ★【融合】多个算子     │
│              │                        │  成一个更大的 kernel  │
│  kernel 数量 │ ★ 不变（还是 800 个）   │ ★ 变少（融合了）      │
│  典型收益     │ 小 batch 下 20%~50%    │ 10%~30%              │
└──────────────┴────────────────────────┴──────────────────────┘
```

> 📖 **算子融合（kernel fusion）**——把「LayerNorm → 乘法 → 加法」三个 kernel 合成一个。
> ★ 好处不只是少启动两次，更重要的是**中间结果不用写回显存再读出来**——
> 回收 01 章：**推理是访存受限的，省一次显存往返比省一次计算值钱得多。**

```
    ★★ 两者是【叠加】关系，不是二选一：
       torch.compile 先把 800 个 kernel 融合成 400 个（每个更高效）
       CUDA Graph 再把这 400 次派发打包成 1 次
```

## 12.4 ★ vLLM 的分段方案：读懂那个枚举

vLLM 把两件事的组合做成了一个五值枚举。**读懂它，就读懂了这一章的全部工程权衡**：

```python
# ✅ 源码原文：config/compilation.py:53
class CUDAGraphMode(enum.Enum):
    NONE = 0
    PIECEWISE = 1
    FULL = 2
    FULL_DECODE_ONLY = (FULL, NONE)          # ★ 注意：值是【元组】
    FULL_AND_PIECEWISE = (FULL, PIECEWISE)
```

**元组是关键**。源码里有两个方法解释了它（同文件 L65-69）：

```python
def decode_mode(self):   return CUDAGraphMode(self.value[0]) ...  # ★ 纯解码步用第 0 个
def mixed_mode(self):    return CUDAGraphMode(self.value[1]) ...  # ★ 混合步用第 1 个
```

```
    ★★★ 也就是说：这个配置允许【同一次部署，两种批次用两种模式】。
       为什么需要这样？回收 03 章——连续批处理下有两种批次：
         ① 纯 Decode 批（全是 1-token）    ⟹ 形状规整，★ 可以用 FULL 图
         ② 混合批（含 chunked prefill）    ⟹ 形状不规整，用不了 FULL 图
```

逐个解释这五个值：

```
    ★ NONE
      完全不用 CUDA Graph。★ 调试时用，或者形状实在太乱。

    ★ PIECEWISE（分段）
      ★★ 这是 vLLM 的招牌做法：
      把模型切成若干段，★ 把「注意力」这个形状会变的算子【挖掉】，
      剩下的部分（全是形状固定的矩阵乘和逐元素操作）分段录成小图。
      ⟹ 注意力用手写 kernel（FlashAttention 等）单独跑，
         其余部分享受 CUDA Graph
      ⟹ ★ 兼容性最好：不管 prompt 多长都能用

    ★ FULL（整图）
      整个前向录成一张图，★ 包括注意力。
      ⟹ 收益最大（连注意力的派发也省了）
      ⚠️ 但要求注意力后端支持固定形状 ⟹ 兼容性差

    ★★ FULL_DECODE_ONLY = (FULL, NONE)
      纯 Decode 批 → FULL（形状规整，用最快的）
      混合批       → NONE（形状乱，干脆不用）
      ⟹ ★ 适合【不开 chunked prefill】的部署：
         反正混合批很少，不值得为它做优化

    ★★★ FULL_AND_PIECEWISE = (FULL, PIECEWISE)
      纯 Decode 批 → FULL（榨干性能）
      混合批       → PIECEWISE（退一步，但仍有收益）
      ⟹ ★ 这是【两全其美】的配置，也是 03 章 chunked prefill
         场景下的推荐值
```

```
    ⟹ ★★ 一句话读懂这个枚举的设计意图：
       【解码步形状规整，就上最激进的 FULL；
        混合步形状不规整，就退回 PIECEWISE 保底。
        一次部署，两套策略。】
```

## 12.5 ⚠️ 代价

```
    ⚠️ ① 启动变慢
       要为几十个 batch 大小分别录图，★ 启动可能多花 1~5 分钟
       ⟹ 频繁重启的场景（自动扩缩容）要权衡

    ⚠️ ② 显存额外开销
       每张图要占一份固定缓冲区，几十张图加起来 ★ 可能吃掉几个 GB
       ⟹ 回收 02 章：这部分显存是从 KV Cache 里扣的 ⟹ 并发数下降
       ⟹ ★ 所以 batch 大小列表不能设太密

    ⚠️ ③ 大 batch 时收益消失
       batch=256 时 kernel 本来就跑得久，★ 派发开销占比可忽略
       ⟹ CUDA Graph 只在【小 batch 低延迟】场景有明显价值
       ⟹ ★ 和 08 章的投机解码是同一个规律：
          ★★ 【填补空闲的优化，在忙碌时都会失效】

    ⚠️ ④ padding 的浪费
       batch=5 用 batch=8 的图 ⟹ 3 个位置在算垃圾
       ⟹ ★ 所以 batch 大小列表在小值处要密（1,2,4,8），
          大值处可以疏（128,256）
```

## 12.6 SGLang 的做法

思路一致，但做得更细——因为它要覆盖更多场景：

```
    ✅ 除了主模型的图，SGLang 还为【草稿模型】单独做图（回收 08 章）：
       eagle_draft_cuda_graph_runner.py
       eagle_draft_extend_cuda_graph_runner.py
       multi_layer_eagle_draft_extend_cuda_graph_runner.py
       frozen_kv_mtp_cuda_graph_runner.py

    ★ 为什么草稿模型也要单独做图？
      因为草稿模型【更小】⟹ 它的 kernel 更小
      ⟹ ★★ CPU 派发开销占比【更严重】
      ⟹ 不给草稿模型上 CUDA Graph，投机解码的加速会被派发开销吃掉一大半
```

> ★ 这是一个很好的例子，说明这些优化不是彼此独立的：
> **投机解码（08）的实际收益，取决于 CUDA Graph（12）做得好不好。**
