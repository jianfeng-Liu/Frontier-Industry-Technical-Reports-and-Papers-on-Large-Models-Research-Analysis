13 性能指标与压测

一句话：「吞吐提升 3 倍」在没说清输入输出长度、并发数、延迟约束之前，是一句没有信息量的话。这一章教你怎么问对问题。

13.1 四个核心指标

┌──────────┬────────────────────────┬──────────────────────────┐
│  指标     │  定义                   │  由什么决定               │
├──────────┼────────────────────────┼──────────────────────────┤
│ ★ TTFT   │ 从请求到达到收到第 1 个 │ ★ Prefill 速度            │
│ 首字延迟  │ token 的时间            │  + 排队时间               │
├──────────┼────────────────────────┼──────────────────────────┤
│ ★ TPOT   │ 相邻两个输出 token 之间 │ ★ Decode 速度             │
│ 每字延迟  │ 的平均间隔              │  （访存受限）             │
├──────────┼────────────────────────┼──────────────────────────┤
│  E2E     │ 端到端总时间            │ ★ = TTFT + TPOT × 输出长度│
├──────────┼────────────────────────┼──────────────────────────┤
│ ★ 吞吐    │ 每秒处理的 token 数     │  batch 大小 × 单步速度    │
│ Throughput│ 或每秒完成的请求数      │                          │
└──────────┴────────────────────────┴──────────────────────────┘

📖 TTFT = Time To First Token（首字延迟）
📖 TPOT = Time Per Output Token（每字延迟），也叫 ITL（Inter-Token Latency）
📖 E2E = End-to-End latency（端到端延迟）

一个必须建立的直觉——把指标和体验对上：

    TTFT = 500 ms  ⟹ 用户感觉「按下回车后愣了半秒」  ★ 可以接受
    TTFT = 3 s     ⟹ 用户以为卡了                    ❌ 不可接受

    TPOT = 20 ms   ⟹ 每秒 50 个字，★ 比人阅读速度快，体验流畅
    TPOT = 100 ms  ⟹ 每秒 10 个字，★ 明显能看出在一个个蹦字

13.2 ★★ 最重要的一条：吞吐和延迟是对立的

    batch 从 1 加到 256：
      ★ 吞吐：上升（权重搬运被摊薄，01 章）
      ★ TPOT：变差（KV 搬运量线性增长 + 排队，02 章 §2.6）

    ⟹ ★★★ 「吞吐提升 3 倍」这句话，如果没说
       【延迟变成了多少】，那它可能只是把 batch 调大了而已。
       ★ 任何人都能靠调大 batch「提升吞吐」。

⟹ 所以 10 章 DistServe 提出的那个指标才是对的：

📖 goodput（有效吞吐）——在满足 SLO 的前提下的最大吞吐。
✅ DistServe 论文原文："the maximum request rate that can be served adhering to the SLO attainment goal"

    ★★ 正确的表述方式长这样：
       「在 P99 TTFT < 1s、P99 TPOT < 50ms 的约束下，
         单卡吞吐从 800 tokens/s 提升到 2400 tokens/s」
       ↑ 这才是一句有信息量的话。

📖 P99——把所有请求的延迟排序，第 99 百分位的值。
★ 务必看 P99，不要只看平均值。 平均 200 ms、P99 5 s 的系统，
意味着每 100 个用户里就有 1 个等了 5 秒——而他很可能就此流失。
⚠️ 抢占（04 章）和专家负载不均（11 章）都会造成长尾，平均值完全看不出来。

13.3 ★ 压测必须说清的四件事

看到任何性能数字，先问这四个问题：

    ① ★★ 输入/输出长度分布是多少？（P:D ratio）
       ISL=128, OSL=2048   ⟹ Decode 主导，几乎在测 Decode 性能
       ISL=8192, OSL=128   ⟹ ★ Prefill 主导，测的是完全另一回事
       ⟹ 这两组数字之间【没有可比性】
       📖 ISL = Input Sequence Length，OSL = Output Sequence Length

    ② ★★ 是固定并发还是固定到达率？
       固定并发（N 个客户端循环发）⟹ 测【最大能力】，★ 没有排队概念
       固定到达率（每秒 X 个请求）⟹ ★ 测【真实服务】，能看出排队和过载
       ⟹ ★ 只有后者能测出有意义的 P99

    ③ ★ 前缀重合度多少？
       如果压测脚本用同一个 prompt 打 1000 次，
       ⟹ ★★ 前缀缓存 100% 命中，Prefill 成本接近 0
       ⟹ 这个数字漂亮但【毫无意义】

    ④ ★ 精度、并行配置、硬件
       FP8 vs BF16、TP=1 vs TP=8、H100 vs A100
       ⟹ 换任何一个，数字都不可比

⚠️ 这四条里，第 ③ 条最常被无意中违反。
很多"性能对比"的差异，实际来自压测数据的前缀重合度不同。

13.4 一个可执行的压测流程

    ★ 第一步：画出【延迟-吞吐曲线】，而不是测一个点

      并发 1  → 记录 (吞吐, TTFT_P99, TPOT_P99)
      并发 2  → ...
      并发 4, 8, 16, 32, 64, 128, 256 → ...

      画成图：横轴吞吐，纵轴 P99 延迟
      ⟹ ★★ 你会看到一条"曲棍球杆"形状的曲线：
         前半段延迟平缓上升（系统还有余力）
         ★ 某一点后延迟【陡然上升】（开始排队，过载了）
      ⟹ ★★★ 那个拐点，就是这套配置的【真实容量】

    ★ 第二步：画一条你的 SLO 横线
      比如 P99 TPOT = 50 ms
      ⟹ ★ 横线和曲线的交点 = goodput = 你真正能承诺的吞吐

    ★ 第三步：改一个变量，重画
      开 FP8 KV Cache → 重画 → ★ 看拐点右移了多少
      开投机解码       → 重画 → ★ 注意看高并发段是不是【变差】了（08 章）

★★ 只有画出曲线，才能回答「这个优化到底有没有用」。
单点测试极容易得出「优化 A 提升 3 倍」这种在别的并发下完全不成立的结论。

13.5 ★ 常用工具

    ★ vllm bench serve（vLLM 自带）
      ⟹ 支持多种数据集（ShareGPT、随机、自定义），
         直接输出 TTFT/TPOT/E2E 的均值和各分位数
      ⟹ ★ 支持固定到达率（--request-rate），能测排队

    ★ python -m sglang.bench_serving（SGLang 自带）
      ⟹ 接口和上面几乎一样，★ 可以用同一套参数对比两个框架

    ★ GenAI-Perf（NVIDIA）
      ⟹ 跨框架、跨后端的统一压测工具

    ⚠️ 注意：两个框架自带的压测脚本，默认数据集和默认参数【不一样】。
       ★ 直接拿各自 README 里的数字对比，是无效的。
       要对比就必须用【同一个数据集、同一组参数】自己重跑。

13.6 ★ 排查清单：性能不达标时按顺序查

    ① 看 GPU 利用率
       持续 <30%？ ⟹ ★ 可能是 CPU 瓶颈（12 章）或 batch 太小
       ⟹ 先确认 CUDA Graph 开了没

    ② 看 KV Cache 使用率（框架日志里都有）
       长期 >95%？ ⟹ ★ 显存是瓶颈，频繁抢占
       ⟹ 上 FP8 KV（09 章）/ 换 GQA/MLA 模型（07 章）/ 加卡

    ③ 看抢占次数（vLLM 日志有 preemption 计数）
       ★ 非零就说明在颠簸 ⟹ 降低 max_num_seqs 反而可能变快

    ④ 看前缀缓存命中率
       ⟹ 命中率低但业务上本该有共享前缀？检查 prompt 拼接方式
          （★ 变动的内容如时间戳放在开头，会毁掉整个前缀缓存）

    ⑤ TTFT 高但 TPOT 正常
       ⟹ Prefill 是瓶颈：调小 chunked prefill 粒度、
          开前缀缓存、考虑 PD 分离（10 章）

    ⑥ TPOT 高但 TTFT 正常
       ⟹ Decode 是瓶颈：★ 增大 TP、量化权重、上投机解码（低并发时）

    ⑦ ★ MoE 模型且各卡利用率不均
       ⟹ 专家负载不均衡 ⟹ 上 EPLB（11 章）

🔑 第 ④ 条里那个「时间戳放开头」的坑，实践中极其常见。
系统提示词里写 当前时间：2026-08-21 10:23:45，
⟹ 每个请求的第一个块的哈希都不同 ⟹ ★★ 整条前缀缓存链全部失效（05 章的链式哈希）。
⟹ 正确做法：把易变内容放到 prompt 末尾。

13.7 ⚠️ 关于 MFU：推理里它没那么重要

训练侧最看重的指标 MFU，在推理里要小心使用：

📖 MFU（Model FLOPs U**tilization，模型算力利用率）——
实际算力 ÷ 硬件峰值算力。见 训练框架/12 章。

    ⚠️ ★★ 推理的 Decode 阶段【本质上就是访存受限】，
       它的 MFU 天生只有百分之几——★ 这【不是缺陷】，是物理性质。
       ⟹ 追求高 MFU 会把你引向错误的方向（比如盲目加大 batch 伤延迟）

    ★ 推理该看的是【MBU】：
      📖 MBU = Model Bandwidth Utilization（模型带宽利用率）
              = 实际达到的访存带宽 ÷ 硬件峰值带宽
      ⟹ ★★ 这才是 Decode 阶段的正确标尺。MBU 到 70%+ 就已经很好了。

    ⟹ ★ 一句话：Prefill 看 MFU，Decode 看 MBU。
