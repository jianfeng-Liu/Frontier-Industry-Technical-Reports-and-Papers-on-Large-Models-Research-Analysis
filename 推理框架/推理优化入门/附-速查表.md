## 一、核心公式

```
★ 算术强度（决定瓶颈在算力还是带宽）                          【01】
    算术强度 ≈ 这一批的 token 数
    > ~300（H100 BF16 平衡点）⟹ 算力受限
    < ~300                    ⟹ ★ 访存受限
    ⟹ Decode 时 batch=1 ⟹ 算术强度≈1 ⟹ 算力利用率 <1%

★★ KV Cache 大小                                            【02】
    字节 = 2 × 层数 × KV头数 × 头维度 × 精度 × 序列长度 × 并发
           ↑K,V

    Llama-3-8B（32层, 8个KV头, 128头维, BF16）
      ⟹ ★ 每 token 128 KB
      ⟹ 8K 对话 = 1 GB，128K 对话 = 16 GB

★ 可用 KV 空间                                               【02】
    ≈ 显存总量 − 权重 − 激活 − CUDA上下文 − 框架预留
    H100 80GB 跑 8B BF16 ⟹ ★ 约 58 GB ⟹ 约 47 万 token

★ 最大并发 ≈ 可用 KV token 数 ÷ 平均对话长度                 【02】

★ 端到端延迟                                                 【13】
    E2E = TTFT + TPOT × 输出长度

★ 投机解码加速比                                             【08】
    ≈ (平均接受 token 数 + 1) ÷ (1 + 草稿开销)

    ★★ 严格版（含上限）：(1 − α^(k+1)) ÷ ((1 − α)(k·c + 1))
       α = 接受率   k = 猜的长度
       ★ c = 【草稿一次前向 ÷ 目标一次前向】的耗时比
       ⟹ 🔑 c 才是隐藏的杀手：目标模型越小 c 越大，越不划算
          70B 配 1B    ⟹ c≈12.5%，接受率 75% ⟹ 划算
          8B  配 0.6B  ⟹ c≈37.5%，接受率 81% ⟹ ⚠️ 反而不划算
```

## 三、并行策略速查

```
★★ vLLM 的 rank 排布（✅ parallel_state.py:1817 原文注释）      【06】
    ExternalDP × DP × PP × PCP × TP
                                  ↑ 变化最快 = 物理最近

    步长：TP=1, PCP=TP, PP=PCP×TP, DP=PP×PCP×TP
    ⟹ ★ TP 最近，DP 最远

★★ 对比训练（Megatron-LM）                                    【06】
    tp - cp - ep - dp - pp
    ⟹ ★ PP 最外、DP 在中间   ← 和推理【正好相反】

★★★ 反过来的唯一原因                                          【06】
    原则没变：通信量大的维度放最近
    变的是 DP 的通信量：
      训练 DP：每步 all-reduce 2Ψ 梯度 ⟹ 贵 ⟹ 必须近
      推理 DP：独立副本，通信量 = 0     ⟹ 免费 ⟹ 可以最远

★★ SGLang 的做法（✅ parallel_state.py:2408）                  【06】
    world_size == tp_size × pp_size   ← ★ 没有全局 DP 维
    TP 组按模型部位【重新切】：
      注意力：attn_dp × attn_cp × attn_tp
      MoE：  moe_dp × moe_ep × moe_tp
    ★ 动机：MoE 模型的注意力想要 DP，MoE 层想要 EP
```

### 各并行维度在推理中的成本

| 维度 | 通信量 | 特点 | 上限建议 |
|---|---|---|---|
| **TP** | 每层 **2** 次 all-reduce（训练 4 次） | ★ 降显存**和**降延迟 | ★ 不超过单机卡数；**必须整除 KV 头数** |
| **PP** | 每步一次点对点 | ⚠️ Decode 只有 1 token，气泡大 | 单机放不下才用 |
| **DP** | ★ **≈0** | ★ 就是多开实例 | 随便加；⚠️ MoE 下必须同步 generate 防死锁 |
| **EP** | 每层 **2** 次 all-to-all | ⚠️ 同步屏障，怕负载不均 | 配 EPLB |
| **PCP** | 序列切分 | Prefill 用，降 TTFT | 超长 prompt |
| **DCP** | 从 TP 组内再切 | ★ 单条序列 KV 放不下时用 | 128K+ |

## 四、决策树

```
★ 选并行配置                                                  【06】
    单卡装得下？          → TP=1，DP=卡数（最优）
    单机 8 卡装得下？     → TP=最小够用值，DP=机器数
    单机装不下？          → 先量化；不行则机内 TP=8 + 机间 PP/EP
    单条序列 KV 放不下？   → DCP
    超长 prompt 拖垮 TTFT？→ PCP 或 PD 分离

★ 选量化方案                                                  【09】
    H100/H200         → ★ FP8 权重 + FP8 KV（默认答案）
    A100              → AWQ / GPTQ 的 W4A16
    并发是瓶颈         → ★ 优先量化 KV Cache（并发直接翻倍）
    Prefill 慢        → 只有 W8A8 有用（Decode 量化对它没帮助）

★ 要不要开投机解码                                            【08】
    低并发 / 交互式     → ✅ 开，2~3 倍加速
    高并发批处理        → ❌ 别开，★ 会降吞吐
    代码补全 / RAG      → ✅ ★ 直接上 n-gram，零成本
    目标模型 ≤ 8B      → ⚠️ 先算 c，很可能不划算
    树形草稿(k=21)      → ⚠️ BS=1 更好(1.85×)，★★ BS=64 全线跌破 1×
    有损验证(截断式)     → ⚠️ 别在 EAGLE-3 上用；别拿 GSM8K 验收

★ 要不要上 PD 分离                                            【10】
    < 8 卡             → ❌ 用 chunked prefill
    没有 RDMA          → ❌ 传 KV 的代价吃掉全部收益
    长 prompt + 大规模  → ✅ 上
    短 prompt 聊天      → ❌ 负收益

★ 选 CUDA Graph 模式（vLLM）                                  【12】
    开了 chunked prefill → ★ FULL_AND_PIECEWISE（推荐）
    没开 chunked prefill → FULL_DECODE_ONLY
    注意力后端不兼容      → PIECEWISE
    调试                → NONE
```

## 五、排查清单

```
GPU 利用率长期 <30%   → ★ CPU 瓶颈？检查 CUDA Graph【12】/ batch 太小
KV 使用率长期 >95%    → 显存瓶颈 → FP8 KV【09】/ 换 GQA-MLA 模型【07】
抢占次数非零          → 在颠簸 → ★ 调小 max_num_seqs 反而更快【04】
前缀缓存命中率低       → 🔑 ★ 检查易变内容（时间戳）是否放在 prompt 开头【05】
TTFT 高、TPOT 正常    → Prefill 瓶颈 → 前缀缓存 / PD 分离【10】
TPOT 高、TTFT 正常    → Decode 瓶颈 → 加 TP / 量化 / 投机解码【08】
MoE 各卡利用率不均     → ★ 专家负载不均 → EPLB【11】
P99 远高于均值        → 长尾 → 查抢占【04】和专家不均【11】
```
