# 推理框架横向对比与选型

> 标记：✅ = 论文/源码原文可查证 ｜ ⚠️ = 我的推断，不是官方结论

---

## 一、先说结论：四个框架的定位

```
    ★ vLLM         —— 事实标准。生态最大，模型支持最快，出问题最容易搜到答案
    ★ SGLang       —— 超大 MoE + 高前缀复用场景的性能上限
    ★ TensorRT-LLM —— NVIDIA 官方，单卡/小规模延迟的天花板，代价是灵活性
    ★ DeepSpeed-FastGen —— 微软，Dynamic SplitFuse 的提出者；★ 今天更多是【历史坐标】
```

⚠️ **一句话选型**（我的判断）：
**不知道选什么就选 vLLM**；跑 DeepSeek 这类超大 MoE 或多轮对话密集就试 SGLang；
只服务一两个固定模型、追求极致 TTFT 且能忍受编译流程，才考虑 TensorRT-LLM。

## 二、各自的论文主张（✅ 原文）

| 框架 | 论文原文关键数字 |
|---|---|
| **vLLM** (PagedAttention, 2309.06180) | 现有系统的 KV 显存有效利用率仅 **20.4%–38.2%** ✅ |
| **SGLang** (RadixAttention, 2312.07104) | *"achieves up to **6.4× higher throughput** compared to state-of-the-art inference systems"* ✅ |
| **DeepSpeed-FastGen** (2401.08671) | *"up to **2.3x higher effective throughput**, **2x lower latency** on average, and up to **3.7x lower (token-level) tail latency**, compared to state-of-the-art systems like vLLM"* ✅ |
| **TensorRT-LLM** | ⚠️ 无同行评审论文，性能数据来自 NVIDIA 官方博客与 MLPerf 提交 |

> ⚠️ **这些数字不能横向相加减！**
> 每篇论文的对照基线、模型、硬件、负载都不同，而且都是**发表当时**的快照。
> 2026 年的 vLLM 早已吸收了 chunked prefill（DeepSpeed-FastGen 的核心贡献）和前缀缓存。
> 🔑 **看论文数字要问 13 章 §13.4 的那四个问题。**

## 三、★★ 逐维度对比

### 3.1 核心技术

| | vLLM | SGLang | TensorRT-LLM | DS-FastGen |
|---|---|---|---|---|
| 显存管理 | ★ PagedAttention（原创） | 分页 + ★★ 基数树 | 分页 | 分页 |
| 前缀缓存 | 链式哈希表 | ★★ RadixAttention（8 变体） | ★ 有，较基础 | ⚠️ 弱 |
| 连续批处理 | ✅ | ✅ | ✅ (in-flight batching) | ✅ |
| 分块 Prefill | ✅ | ✅ | ✅ | ★ **原创**(Dynamic SplitFuse) |
| 缓存感知调度 | ❌ | ★★ LPM / ROUTING_KEY | ❌ | ❌ |
| 执行方式 | ★ Python + 编译 | ★ Python + 编译 | ★★ **提前编译成引擎** | Python |

### 3.2 并行策略（06 章）

| | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 全局网格 | `ExtDP×DP×PP×PCP×TP` ✅(L1817) | ★ `tp×pp` ✅(L2408) | `TP×PP` |
| DP 位置 | ★ 网格里的一维 | ★★ TP 组内再切 | ⚠️ 需外部编排 |
| 专家并行 | ✅ EP + EPLB | ✅ EP + ★ 离线模拟器 | ✅ |
| 上下文并行 | ✅ PCP / DCP | ✅ ATTN_CP | ⚠️ 有限 |
| **配置心智** | ★ 先定网格 | ★ 按模型部位声明 | ★ 编译期就固定 |

### 3.3 工程属性

| | vLLM | SGLang | TensorRT-LLM | DS-FastGen |
|---|---|---|---|---|
| 新模型上线速度 | ★★★ 最快 | ★★ 快 | ★ 慢（要写/等插件） | ⚠️ 已基本停滞 |
| 硬件支持 | ★★ N卡/A卡/昇腾/TPU… | ★★ N卡/A卡/昇腾 | ★ **仅 NVIDIA** | 主要 NVIDIA |
| 部署复杂度 | ★ 低（pip 装完就跑） | ★ 低 | ★★ 高（编译引擎） | 中 |
| 社区活跃度 | ★★★ | ★★★ | ★★ | ⚠️ 低 |
| 换模型/换配置 | ★ 改参数重启 | ★ 改参数重启 | ⚠️ **要重新编译** | 改参数重启 |

> ★★ **TensorRT-LLM 的核心取舍就在最后一行**：
> 它把「运行时的灵活」换成了「编译期的极致优化」。
> ⟹ 算子融合、kernel 自动选型、图固化都能做到最彻底
> ⟹ ⚠️ 但你改一个 TP 度、换一个量化格式、加一个 LoRA，都可能要重编
> 🔑 **模型固定、SLO 严苛的线上服务** ⟹ 值。**要频繁试模型的团队** ⟹ 不值。

## 四、★★ 选型决策图

```
    开始
     │
     ├─ 只能用 NVIDIA 卡，且模型固定 ≥3 个月不变？
     │     └─ 是 ─→ ⚠️ 先用 vLLM 上线，同时评估 TensorRT-LLM
     │                  ★（先有服务再谈极致，别一上来就啃编译）
     │
     ├─ 模型是 DeepSeek-V3/R1 这类【超大 MoE】？
     │     └─ 是 ─→ ★★ SGLang（EP + DP-Attention + EPLB 最成熟）
     │
     ├─ 负载是【多轮对话 / 长系统提示词 / Agent 反复调用】？
     │     └─ 是 ─→ ★★ SGLang（RadixAttention + LPM 调度是为此而生）
     │              ⚠️ 前提：前缀命中率确实高，先测再定
     │
     ├─ 要跑非 NVIDIA 硬件？
     │     └─ 是 ─→ ★ vLLM（后端最全）
     │
     └─ 其他所有情况 ─→ ★★★ vLLM
                          ★ 理由不是它最快，是【出问题时你搜得到答案】
```

## 五、★ 什么时候该换框架

⚠️（以下是我的经验判断，不是官方建议）

```
    ★ 不该换的情况：
      ✗ 「听说 X 比 vLLM 快 2 倍」  ⟹ 先问 13 章那四个问题
      ✗ 「压测数字好看」            ⟹ 压测负载和线上负载一样吗？
      ✗ 「新框架功能更多」          ⟹ 你用得上几个？

    ★★ 该换的信号（要同时满足）：
      ✓ 已经把【当前框架的参数调优】做完了
        （chunked prefill 开了吗？前缀缓存开了吗？量化上了吗？
          gpu_memory_utilization 顶到 0.92 了吗？）
      ✓ 用【线上真实流量回放】测过，新框架确实赢
      ✓ 赢的幅度 > 30%（★ 低于这个数，运维成本吃掉收益）
      ✓ 团队有人能读新框架的源码

    ⟹ ★★★ 90% 的性能问题，答案在【参数】和【负载形状】里，不在【框架选择】里。
```

## 六、★ 一个常被忽略的维度：可观测性

⚠️ 选型时容易只看吞吐，但线上真正折磨人的是「出问题时看不见」：

```
    要确认框架能不能给你这些（13 章）：
      □ 每个请求的 TTFT / TPOT 分位数
      □ ★ 当前【前缀缓存命中率】       ← 决定要不要上 SGLang 的唯一依据
      □ ★ 当前【抢占次数】             ← 抢占频繁 = 显存不够，不是框架慢
      □ ★ 当前【批次里 Prefill/Decode 的比例】
      □ 排队等待时长 vs 实际计算时长   ← ★ 区分「机器不够」和「框架慢」
      □ MoE：★ 各专家的负载分布        ← 11 章的倾斜问题

    ⟹ ★★ 如果你连「命中率是多少」都答不上来，
       那么「要不要换 SGLang」这个问题，现在无法回答。
```
