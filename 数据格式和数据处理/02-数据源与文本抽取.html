02 · 数据源与文本抽取

这一章回答两个问题：训练数据到底是从哪弄来的？抓下来的东西长什么样、怎么变成能用的文本？
容量口径沿用 01 章：1 TB = 10¹² 字节，1 TiB = 2⁴⁰ 字节，差 9.95%；凡给容量都注明压缩 / 未压缩。

2.1 五个数据源，各自的角色

大模型的训练语料不是一个东西，是五类来源按配比拌起来的（配比怎么定见 10 章）：

来源 ⚠️ 典型占比 从哪来 特点 ★ 它负责模型的什么能力
① 网页（web） 60 ~ 90% Common Crawl（免费）或自建爬虫（大厂几乎都自建） 量最大、最脏、多样性最好 ★ 语言能力和世界常识的主体
② 代码（code） 5 ~ 20% GitHub 公开仓库（The Stack、StarCoder 数据集） 结构严格、噪声低、许可证问题复杂 ★ 不只是"会写代码"——公认能显著提升推理能力
③ 学术与书籍 2 ~ 10% arXiv、PubMed、开放获取图书 长文档、逻辑连贯、信息密度高 ★ 长上下文能力和专业知识
④ 精选高质量 1 ~ 5% 维基百科、StackExchange、教科书 量小但质量极高 常被重复采样多次（up-sampling）
⑤ 合成（synthetic） 0 ~ 30% 用别的模型生成或改写 可控、但有"模型自产自销"的风险 ★ 2024 年后增长最快的一类，见 12 章

⚠️ "典型占比"那一列是我从各家公开语料配比里归纳的量级区间，不是任何一家的官方数字。 真实配比往往是各家最不愿意公开的东西之一。注意区间加起来远超 100%——因为它们是不同家的取值范围，不是同一家的一组配比。

2.2 Common Crawl：这个领域的地基

Common Crawl（CC） 是一个非营利组织，每一两个月对全网做一次爬取，并把结果免费公开。几乎所有开源语料（C4、RefinedWeb、Dolma、FineWeb、DCLM、Nemotron-CC）都是从它出发的。

一次快照（一个 dump，如 CC-MAIN-2024-10）的量级：

量 数值 口径说明
网页数 约 25 ~ 30 亿 ✅ CC 的 dump 公告逐次给出
未压缩内容 约 400 TiB = 440 TB ✅ CC 公告里报的就是这个量（"uncompressed content"）
压缩后的 WARC 文件 约 90 TiB = 99 TB ⚠️ 量级；就是大家口口相传的"90 TB"
隐含的压缩比 440 ÷ 99 = 4.44 倍 ⚠️ 我的除法。HTML 重复标签多，压得特别狠
累计快照数 约 100 个（2008 年至今） ★ 但快照之间重复度极高

★★ "90 TB" 和 "400 TiB" 是同一批网页。 这是本章第一个必须钉死的口径：⚠️ 看到任何 CC 相关的容量数字，先问"压没压"。差 4.44 倍，足以让留存率算错好几倍（01 章 §1.4 演示了这个坑）。

★ 快照之间重复度极高——同一个网页会在几十个快照里出现，所以"用 100 个快照 = 100 倍数据"是错的，见 06 章。FineWeb 用了 96 个快照才得到 15 T token，平均每快照只贡献约 1560 亿 token。

CC 提供三种文件格式

这是初学者第一个容易踩的坑：同一批网页，CC 提供三种加工程度不同的文件。

格式 全称 里面装的是什么 ⚠️ 单快照体积（压缩后） 占 WARC 的 什么时候用
WARC Web ARChive（网页归档） ★ 完整的原始 HTTP 响应：HTTP 头 + 完整 HTML 约 90 TiB = 99 TB 100% 想自己抽正文。★ 前沿做法
WAT Web Archive Transformation（元数据提取） 元数据：链接、标题、HTTP 头。不含正文 约 22 TiB = 24 TB 24% 分析链接图、做站点级统计
WET WARC Encapsulated Text（纯文本提取） CC 帮你抽好的纯文本 约 9 TiB = 9.9 TB 10% 图省事。★ 但质量差

⚠️ 三行体积都是压缩后的量级数字，逐快照浮动，以你要用的那个 dump 的 CC 公告为准。但 WET ≈ WARC 的 10% 这个比值相当稳定，§2.3 会用它反推一件事。

★★ WET 还是 WARC，是一个真实存在、影响很大的决策点。

WET 的抽取质量很差——它基本上就是"把所有 HTML 标签删掉"，所以导航栏、"登录 / 注册"、Cookie 提示、页脚版权全都留在正文里。

✅ RefinedWeb 论文（arXiv:2306.01116）明确报告：他们从 WARC 出发用 trafilatura 自己抽正文，而不是用 WET，并把这作为 RefinedWeb 质量领先的原因之一。FineWeb 也走 WARC 路线。 而更早的 C4 用的是 WET。

⚠️ 我的归纳："从 WET 换成 WARC + 好抽取器"，大概是 2020→2023 这几年数据质量提升里性价比最高的单点改动——因为它不需要任何模型，只是换一个开源库。

2.3 ★★★ 文本抽取：为什么这一步决定了上限

直觉类比

想象你要从一份报纸上"只把新闻内容剪下来"。

  • WET 的做法：把整版纸拿去，把所有图片撕掉，剩下的字全留着——包括报头、日期、广告、"第 3 版转下页"、订阅电话。
  • 好抽取器的做法：认出"这一块是正文，那一块是广告栏"，只剪正文那一块。

★★ 所以"正文只占网页的百分之几"这句话，有两个很不一样的版本：

WET 式抽取（删标签留全部文字）→ 约 6.75%；主正文抽取（trafilatura 这类）→ 约 3.1%。

三条抽取路线：同一个页面各抽一遍

还是上面那个玩具页面。三种做法抽出来的东西完全不同：

抽取路线 怎么做的 抽出字符 是正文的几倍 带不带导航 / 页脚 丢了什么 代表实现
① 裸正则删标签 re.sub(r'<[^>]+>', '', html)，三行代码 161 2.82 倍 ★ 全带，连 CSS 和 JS 源码都当成正文 什么都没丢，但混进了 104 个字符的垃圾 自己手写的脚本
② WET 式 先删 script / style，再取全部文本节点 123 2.16 倍 ★ 带 title、导航、侧栏、页脚 只丢了 CSS + JS（38 字符） CC 的 .wet 文件
③ 主正文抽取 按 DOM 密度 + 链接密度打分选块 57 1.00 倍 ✓ ★ 全不带 丢了 <title>（13 字符，⚠️ 有时是有用的信息） trafilatura、resiliparse、jusText

逐项验算（这三行数字可以互相对上）：

验算 算式 结果
① 比 ② 多的部分 CSS 16 + JS 22 38 → 161 − 123 = 38 ✓
② 比 ③ 多的部分 title 13 + 导航 14 + 侧栏 7 + 页脚 32 66 → 123 − 57 = 66 ✓
③ 占 ① 的比例 57 ÷ 161 35%

⚠️ 上表是按三种路线的"设计目标"手工推演的，不是真的跑了 trafilatura 和 resiliparse。 同一个页面，这两个库的实际输出会有几个字符的差别（比如 h1 算不算正文、<title> 要不要单独放一个字段），而且会随页面结构浮动。结论的量级可靠，具体字符数不要当实测引用。

trafilatura 和 resiliparse 怎么选

trafilatura resiliparse
实现语言 Python（底层 lxml） Rust / C++（Chatnoir 工具链）
卖点 ★ 准确率，它自己的基准里 F1 领先 ★ 吞吐，⚠️ 通常快一个数量级
谁在用 ✅ RefinedWeb、FineWeb ✅ DCLM
什么时候选它 快照数不多、想要最好的正文 要扫几十个快照、CPU 小时是主要成本

⚠️ "快一个数量级"是我按两者的实现语言和公开说法给的量级判断，不是跑分。真要选，拿你自己的几千个页面各跑一遍，比任何基准都准。

实践里不要自己写抽取器，直接用上面这两个。✅ FineWeb 用的是 trafilatura。

②的核心指标写成公式

文本密度(node) = 该节点子树里的【纯文本字符数】
                ────────────────────────────────
                 该节点子树里的【标签数量】

链接密度(node) = 该节点里【<a> 标签内的文字数】 / 【总文字数】

判定：文本密度高 且 链接密度低  →  正文
      文本密度低 或 链接密度高  →  导航 / 页脚 / 广告
                              ↑ 导航栏的特征就是"全是链接、每条几个字"

用上面那个页面算一遍，看这两个信号有多好分：

节点 纯文本字符 标签数 文本密度 <a> 内字符 链接密度 判定
div.content 57 4（div+h1+2×p） 14.3 0 0.00 ✅ 正文
div.nav 14 1 14.0 0 0.00 ⚠️ 密度骗过了，要靠别的信号（文本太短、无句读）
div.sidebar 7 3（div+2×a） 2.3 7 1.00 ❌ 导航：链接密度顶格
div.footer 32 1 32.0 0 0.00 ⚠️ 密度也骗过了，靠"版权所有 ©"这类关键词兜

★★ 这张表顺手揭掉了一层滤镜：两个密度指标并不万能。 div.nav 和 div.footer 的链接密度都是 0、文本密度还不低，光看公式判不出来。真实的抽取器还要叠一堆信号：文本长度下限（14 个字符太短）、句读比例（正文有句号逗号，导航没有）、常见 class 名黑名单（nav/footer/sidebar/comment）、标签位置。⚠️ 这就是为什么"自己写一个"几乎一定写不好——真正的工作量全在这些补丁里。

伪代码

def extract_main_text(html):
    dom = parse_html(html)
    for node in dom.walk():
        if node.tag in ("script", "style", "noscript", "svg"):
            node.remove()                       # ① 先删非内容标签

    candidates = []
    for node in dom.walk():
        text  = node.text_content()
        n_tag = count_tags(node)
        n_link_char = sum(len(a.text) for a in node.find_all("a"))

        text_density = len(text) / max(n_tag, 1)
        link_density = n_link_char / max(len(text), 1)

        if len(text) > 100 and text_density > 20 and link_density < 0.3:
            candidates.append(node)             # ② 打分选块

    main = pick_largest_contiguous(candidates)  # ③ 选最大的连续正文区
    return normalize_whitespace(main.text_content())

⚠️ 拿上面那个玩具页面跑这段伪代码，一个候选块都选不出来——因为 len(text) > 100 这个门槛，整个页面的正文才 57 个字符。真实网页的正文通常几百到几千字符，这个门槛是按真实网页定的。这正好说明：抽取器的每个阈值都是统计意义上的，对单个短页面经常失效。

2.4 网页以外的四类源，各有各的坑

代码

来源：GitHub 公开仓库（The Stack v1/v2、StarCoder Data）
坑：
  ① 许可证 —— 不是所有公开仓库都允许训练。要按 SPDX 许可证白名单过滤
     SPDX = Software Package Data Exchange，一套许可证标识符的标准写法
     （如 MIT、Apache-2.0、GPL-3.0-only）
  ② 自动生成的文件 —— .min.js、protobuf 生成的代码、lock 文件
     ★ 这些体积巨大且完全没有学习价值，必须按文件名和特征剔除
  ③ 一个仓库被 fork 一万次 —— 去重的重灾区
  ④ 二进制和大文件 —— 通常按"行平均长度""字母比例"过滤

⚠️ 代码的字节/token 比值和自然语言完全不同，估容量时别套用网页的数字。原因是变量名千奇百怪、缩进和符号极多：

语料类型 ⚠️ 字符/token ⚠️ 每 token 的源文本字节 这个数可靠吗
代码 2.6 ~ 2.8 约 2.7 字节 ✅ 较可靠。★ 代码几乎全是 ASCII，所以"字符"和"字节"这两种口径在这里是同一个数，不受 09 章 §9.5 那条口径矛盾影响（数字取自 openPangu-2.0 报告 Table 4 的代码一列）
英文 约 4 约 4.2 字节 ⚠️ 经验区间（约 0.75 单词/token）
中文 ⚠️ 1.5 ~ 2 个汉字 约 5.25 字节（一个汉字 3 字节） ⚠️ 只能用经验区间。不要用 Table 4 的"中文 3.82"做绝对换算，见 09 章 §9.5

★ 同样 1 GB 的源文件，代码能切出的 token 数大约是英文的 1.5 倍（4.2 ÷ 2.7）、是中文的 1.9 倍（5.25 ÷ 2.7）。所以"代码占 20%"这句话，按字节算和按token算差出一截——04 章 §4.5 讲 BlendedDataset 权重时会专门算这笔账。

学术论文（arXiv / PubMed）

来源：arXiv 提供 LaTeX 源码和 PDF 两种
★ 关键选择：用 LaTeX 源码，不要用 PDF
   PDF 抽文本会把两栏排版搅乱、公式变成乱码、表格塌成一行
   LaTeX 源码则可以精确地把公式保留成 $...$ 形式
坑：LaTeX 宏、\input 引用、参考文献列表（通常整段删掉）

书籍

坑：★ 版权是最大的问题。Books3 这个曾被广泛使用的语料因版权争议被下架
现在的合规做法：只用公有领域（Project Gutenberg）+ 明确开放许可的
参考：Common Pile 就是"只用明确开放许可的语料"这条路线的代表

维基百科与问答站

特点：量小（中英文全部加起来也就百亿 token 级别）但质量极高
常见做法：★ 重复采样 2~5 次（up-sampling），见 10 章
坑：Wiki 的模板、信息框（infobox）、引用标记 [1][2] 要清掉

⚠️ "量小"小到什么程度，值得算一下：

量 值 怎么来的
英文维基百科正文体积 ⚠️ 约 6 ~ 20 GB 未压缩 区间这么宽，是因为"算不算讨论页/模板/重定向"口径差别极大
折成 token（⚠️ 英文 4.2 字节/token） ⚠️ 约 14 ~ 48 亿 除法是我做的
所有语言版本加起来 ⚠️ 百亿（10 B）token 量级 —
占 15 T 总预算 1×10¹⁰ ÷ 1.5×10¹³ = 0.067% —

★ 这就解释了为什么高质量源一定要重复采样：按原始体积，维基百科在 15 T 的预算里根本就看不见。要让它占到 1%，得重复采样 15 遍（0.01 ÷ 0.00067）。⚠️ 实践中一般只重复 2 ~ 5 遍，因为再多就开始明显地"背下来"了（11 章）。

2.5 ⚠️ 一件很少被讲、但很重要的事：自建爬虫

上面全在讲 Common Crawl，但几乎所有前沿闭源模型都不只用 CC。原因很实在：

Common Crawl 的局限：
  ① 它的爬取策略是通用的，不为"训练大模型"优化
     → 大量 PDF、图片页被抓了但没用，很多好站点抓得很浅
  ② 它遵守 robots.txt，而现在越来越多站点在 robots.txt 里禁止 AI 爬虫
     → ★ CC 的可用内容在【逐年缩水】
  ③ 所有人用的都是同一份 CC → 你的数据没有任何独特性

⚠️ 这是我的判断，不是某篇论文的结论：数据侧的竞争差距，很大一部分已经不在"算法多聪明"，而在"你有没有自己的抓取管线和独家数据"。开源语料能追平的是前者，追不平后者。

五家国产模型的数据源披露程度（详见 16 章）：⚠️ 总体而言，这一代技术报告对数据源的披露远比对架构的披露吝啬——架构会给出每一层的维度，数据往往只有一句"经过严格清洗的高质量多语言语料"。

2.7 小结

① 五类数据源：网页（主体）/ 代码（提推理）/ 学术书籍（长文档）
              / 精选高质量（重复采样）/ 合成（增长最快）
   ⚠️ 占比区间是各家取值的范围，不是同一家的一组配比（所以加起来超 100%）

② Common Crawl 是地基。单快照的两个口径要分清：
   未压缩内容 ~400 TiB = 440 TB   ← ✅ CC 公告报的是这个
   压缩 WARC  ~90 TiB  = 99 TB    ← 大家口口相传的"90 TB"
   隐含压缩比 4.44 倍 ⟹ ★ 看到 CC 的容量数字，先问"压没压"

③ 三种文件格式必须分清（体积都是压缩后）：
   WARC ~90 TiB = 完整原始 HTML        ← ★ 前沿做法从这里出发
   WAT  ~22 TiB = 元数据，不含正文
   WET  ~9 TiB  = CC 帮你抽的纯文本    ← 图省事，但质量差（C4 用的这个）
   ★ WET / WARC ≈ 10%，这个比值能用来反推正文占比

④ ★ 正文到底占网页多少（§2.3 两条推演）：
   WET 式抽取（删标签留全部文字）→ 约 6.75% 的未压缩 HTML 字节
   主正文抽取（trafilatura 这类）→ 约 3.1%
   ⚠️ 旧版写的"10~15%"偏高，已改

⑤ ★ 同一个玩具页面，三种路线抽出来的字符数：
   裸正则 161（连 CSS/JS 源码都当正文） > WET 式 123 > 主正文 57
   差值能逐项对上：161−123 = CSS16+JS22；123−57 = title13+导航14+侧栏7+页脚32

⑥ 好抽取器的核心信号：文本密度高 + 链接密度低 = 正文
   ⚠️ 但这两个信号判不出 nav 和 footer（§2.3 那张表算过）
      真实抽取器还要叠：长度下限 + 句读比例 + class 名黑名单
   ⟹ 别自己写，用 trafilatura（准）或 resiliparse（快）

⑦ 非网页源各有各的坑：
   代码 → 许可证 + 自动生成文件
          ⚠️ 字节/token：代码 2.7 / 英文 4.2 / 中文 5.25，相差到 1.9 倍
          ⚠️ 中文那个数只能用经验区间（1.5~2 汉字/token），见 09 章 §9.5
   论文 → 用 LaTeX 别用 PDF
   书籍 → 版权；Wiki → ⚠️ 只有约 10 亿 token = 总预算的 0.007%，必须重复采样

⑧ ⚠️ CC 的可用内容在逐年缩水（robots.txt 拒绝 AI 爬虫），
   且人人都用同一份 → 前沿团队几乎都自建爬虫
