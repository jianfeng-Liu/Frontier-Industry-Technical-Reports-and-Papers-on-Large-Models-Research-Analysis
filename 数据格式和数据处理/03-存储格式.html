03 · 存储格式：JSONL / Parquet / Arrow / WebDataset

这一章讲"清洗阶段"的文件格式。 训练时真正读的那个格式（.bin / .idx）是下一章。
核心只有一个概念：行存 vs 列存。 搞懂它，这一章其余部分都是推论。
本章会把同一份数据在五种格式下的字节数和 IO 次数全部算出来（§3.6），这样"选哪个格式"就不再是感觉问题。

先把本章要用的三套口径钉死

容量：沿用 01 章，1 TB = 10¹² 字节、1 TiB = 2⁴⁰ 字节（差 9.95%），1 GB = 10⁹、1 GiB = 2³⁰（差 7.37%）。

压缩：同一件事有三种说法，数值完全不同，混用是本领域最常见的口误。以 6203 字节压到 2068 字节为例：

说法 算式 数值 什么时候该用
压缩到 X% 2068 ÷ 6203 33% 谈"剩多少"、算存储账单
压缩 X 倍（压缩比） 6203 ÷ 2068 3.0 倍 谈"省了几倍"、比较算法
省了 X% 1 − 2068/6203 67% 谈"节约多少"

⚠️⚠️ "压缩到 33%"、"压缩 3 倍"、"省了 67%" 是同一件事的三种说法（上表三行算的是同一对数字）。 而"压缩 33%"这个说法是歧义的——它既可能指"压到 33%"（省 67%），也可能指"省了 33%"（压到 67%）。本教程不使用"压缩 X%"这种写法。 看到别人这么写，一定要回头确认。

速度：同理，"时间减少 X%"和"加速 X 倍"是两回事，换算关系是：

加速倍数 = 1 / (1 − 时间减少比例)
时间减少比例 = 1 − 1 / 加速倍数
时间减少 对应加速
50% 2.0 倍
60% 2.5 倍
75% 4.0 倍
80% 5.0 倍

⚠️ 所以"解压时间减少 60%"不等于"解压快 60%"，它等于"解压快 2.5 倍"。⚠️ 而"加速 60%"通常指 1.6 倍（时间减少 37.5%）。本教程统一用"快 N 倍"的写法。

3.1 先说清楚：为什么会有好几种格式

一份数据在生命周期里会换好几次格式，因为不同阶段的访问模式完全不同：

阶段 典型操作 ★ 想要的性质 用什么格式
① 抓取 / 抽取 一条条追加写 ★ 追加便宜、能流式处理 JSONL / WARC
② 清洗 / 过滤 "把 quality_score < 2 的删掉"、"统计各语言的 token 总数" ★ 只读某几列要快；★ 压缩率高（省存储费） Parquet
③ 训练 "给我第 8,231,904 号样本"，每秒几千到几万次随机读 ★★ 随机访问 O(1)；★ 零解析开销 .bin + .idx（04 章）

★★ 一句话概括：JSONL 便于写和流式过，Parquet 便于筛和存，.bin/.idx 便于随机取。 现实中的流水线就是 JSONL → Parquet → .bin/.idx 一路转下去。

3.2 JSONL：最简单、最通用的那个

JSONL = JSON Lines（每行一个 JSON 对象），有时也写作 .jsonl / .ndjson（Newline-Delimited JSON，换行分隔的 JSON）。

{"id":"a1","text":"番茄炒蛋是一道家常菜……","url":"http://...","lang":"zh"}
{"id":"a2","text":"def quicksort(arr):\n    if len(arr)…","url":"http://...","lang":"code"}
{"id":"a3","text":"The mitochondrion is the powerhouse…","url":"http://...","lang":"en"}
     ↑ 每一行是一个【完整的、独立的】JSON 对象，行末是 \n

为什么它统治了这个领域的第一阶段

✅ 追加写只要 open(f,"a") 然后 write(json.dumps(d)+"\n")
✅ 流式处理不需要把整个文件读进内存 —— 一行一条，读一行处理一行
✅ 可以直接 split / cat / grep / wc -l，所有 Unix 工具都能用
✅ 一个文件坏了半截，前半截仍然可用（每行独立）
✅ 人能直接看懂
✅ 天然可并行：切成 N 个文件块，N 台机器各处理一块

❌ 体积大 —— 全是文本，字段名每行都要重复存一遍
❌ 解析慢 —— 每读一条都要跑一次 JSON parser
❌ ★ 不支持随机访问 —— 想要第 800 万条，只能从头数 800 万个 \n
❌ 不支持"只读某一列" —— 要拿 lang 字段也得把整行 text 解析出来

"字段名每行重复存一遍"到底多花钱？ §3.6 会给精确数字，先给结论：一条带 2000 个汉字正文的记录里，字段名 + 标点 + 引号共占 203 字节，正文占 6000 字节——结构开销只有 3.3%；但如果是一条只有元数据、没有正文的记录（去重 / 打标签阶段的常见形态），253 字节里有 153 字节是字段名和标点，占 60%。★ JSONL 的体积问题只在"记录短"的时候才严重。

★ preprocess_data.py（Megatron 的预处理脚本）的输入就是 JSONL，这是这个领域最标准的交接格式。它默认读的字段名是 "text"。

一定要配的：分片 + 压缩

单个 JSONL 文件绝不能做成 2 TB，实践中一定是切成很多分片（shard）：

data/
  ├── part-00000.jsonl.zst     ← 每片 ~500 MB（压缩后）
  ├── part-00001.jsonl.zst
  ├── ...
  └── part-04095.jsonl.zst

压缩格式的选择：

格式 ⚠️ 压缩比（中文 UTF-8 文本，量级） ⚠️ 单核解压速度 能并行解压 什么时候用
gzip 约 2.5 倍（压缩到 40%） 约 200 ~ 400 MB/s ❌ 不能 最通用，和谁都能对接
zstd 约 3.0 倍（压缩到 33%） 约 800 ~ 1500 MB/s ✅ 能 ★ 现在的默认选择
lz4 约 1.8 倍（压缩到 55%） 几 GB/s ✅ 能 临时中间文件，CPU 比磁盘贵时

⚠️ 上表三列数字都是量级，不是跑分：压缩比强烈依赖内容（代码比中文好压，base64 几乎不可压），解压速度依赖 CPU 和压缩等级。自己的数据自己测，三行命令的事。

★ zstd 对 gzip 的优势，用上面钉好的口径说一遍：压缩比 3.0 倍 vs 2.5 倍（体积再小 17%），解压 快 3 ~ 4 倍（= 解压时间减少 67% ~ 75%）。⚠️ 注意不要说成"解压快 300%"或"压缩 17%"，那都是歧义写法。

3.3 ★ 核心概念：行存 vs 列存

这是整章唯一需要真正理解的东西。

直觉类比

想象一个 Excel 表格要存到磁盘上，只有两种存法：

原始表格（text 列故意画宽，因为它在真实语料里就是最宽的那一列）：

   row  id  text                    lang  score
   r1   a1  "tomato-egg recipe..."  zh    2.7
   r2   a2  "def quicksort(arr).."  code  4.1
   r3   a3  "The mitochondrion.."   en    1.2

【行存 row-based】—— 一行的所有字段挨着放（JSONL 就是这样）

  磁盘布局: [a1|"tomato-egg..."|zh|2.7][a2|"def quick..."|code|4.1][a3|"The mito..."|en|1.2]
            |<--------- r1 ---------->||<---------- r2 ---------->||<-------- r3 --------->|

  要拿"所有的 score"? -> 必须把三段全部读进来，跳着取
     ★ 而 text 字段极长 —— 你为了拿 3 个浮点数，读了几十 KB 文本

【列存 columnar】—— 同一列的所有值挨着放（Parquet 就是这样）

  磁盘布局: [a1|a2|a3]["tomato..."|"def qu..."|"The mi..."][zh|code|en][2.7|4.1|1.2]
            |<- id ->||<------------- text -------------->||<- lang ->||<- score ->|

  要拿"所有的 score"? -> ★ 只读最右边那一小段
                          text 那一大坨【碰都不用碰】

列存的两个额外好处（比"少读"更重要）

① ★ 压缩率暴涨
   同一列的数据【类型相同、取值相似】，压缩算法能吃得很饱：
       lang 列： zh,zh,zh,en,en,en,en,zh,code,...
                 → 字典编码：{zh:0, en:1, code:2} + [0,0,0,1,1,1,1,0,2,...]
                 → 再游程编码：(0,×3)(1,×4)(0,×1)(2,×1)
                 → 原本几百 MB 的字符串列 → 几 KB
   而行存里 "zh" 夹在两段长文本中间，压缩器根本发现不了这个规律

② ★ 谓词下推（predicate pushdown）
   Parquet 在每个数据块（row group）的页脚记了【每列的 min / max】
   查 "score > 3.5" 时，某个块的 score.max = 2.9 → ★ 整块直接跳过，不解压

⚠️⚠️ 本章旧版在这里写过一句"Parquet 通常比 gzip 后的 JSONL 再小 30~60%"，这句话要加条件才成立。 §3.6 把两种记录形态都算了一遍：

记录形态 JSONL+gzip Parquet+zstd Parquet 小多少
A：2000 汉字正文 + 7 个元数据字段 2481 B 2030 B 只小 18%
B：只有元数据、无正文（12 个字段） 84 B 28 B 小 67%

★ 结论：长文本列一旦占主导，Parquet 的压缩优势就被摊薄了——因为那一大坨正文谁压都是压一样的三倍，列存帮不上忙。"30~60%" 只在短字段占主导时成立。 长文本场景下，列存的价值几乎全部来自"只读需要的列"，不是压缩。

什么时候不该用列存

❌ 要一条条追加写（列存必须凑够一批才能写一个块）
❌ 每次都要读整行的全部字段（那列存反而多了拼装开销）
❌ 只有一列（那就没有"列"的概念了）

★★ 这正好解释了流水线的换格式点：抽取阶段是一条条追加写 → JSONL；清洗阶段是反复按列筛选统计 → Parquet。

3.4 Parquet 与 Arrow：一对经常被搞混的兄弟

它们是同一个社区做的两个东西，分工完全不同：

Apache Parquet Apache Arrow
活在哪 ★ 磁盘上（on-disk） ★ 内存里（in-memory）
为什么优化 为存储：压缩、编码、谓词下推 为计算：字段定长对齐，CPU 可直接向量化处理
压不压缩 ✅ 压（zstd / snappy / gzip） ❌ 不压（压了就不能直接算了）
用的时候要做什么 必须先解压 + 解码 ★ 什么都不用做，直接按下标访问
杀手特性 谓词下推 + 列投影 ★★ 零拷贝（zero-copy）：不同进程 / 不同语言可以共享同一块内存。Python 读进来的 Arrow 表，C++ 那边不用序列化就能直接用
文件后缀 .parquet .arrow / .feather（其实是把内存布局原样落盘）

两者的关系是一条单向的管道：

  Parquet（磁盘，压缩，省空间）
      │
      │  读取时：解压 + 解码 + 展开
      ▼
  Arrow（内存，不压缩，可直接算）

★ HuggingFace datasets 库的底层就是 Arrow。 你 load_dataset(...) 之后它在磁盘上缓存的 .arrow 文件，就是把 Arrow 内存布局直接 mmap 到磁盘——所以它加载 100 GB 数据集"秒开"，因为根本没有真的读进内存，只是建立了内存映射。

mmap（memory-mapped file，内存映射文件）：让操作系统把一个磁盘文件"假装"成一段内存地址。你按数组下标访问，操作系统在背后按需从磁盘换页（paging）进来。这是整个数据领域最重要的一个系统技巧——下一章的 .bin 文件也靠它。

★ mmap 为什么"秒开"，说白了：open + mmap 这两个系统调用一个字节都不读，只是在进程的地址空间里登记"这段地址对应那个文件的那一段"。真正的磁盘读发生在你第一次访问某个下标的时候，而且只读那一个 4 KB 页。⚠️ 代价是：第一次访问每一页都要等一次磁盘（冷页，约 100 µs 量级），所以 mmap 快的是"打开"，不是"随机访问的第一次"。

3.5 WebDataset 与 MDS：为"顺序流式读"设计的

前面几种格式都假设数据在本地磁盘上。但真实训练时数据往往在对象存储（S3、OSS）上，几百 TB，本地根本放不下。这时的访问模式变了：顺序流式拉取，边拉边训。

WebDataset MDS（Mosaic Data Shard，MosaicML StreamingDataset）
底层是什么 ★ 就是普通的 .tar 文件，没有任何自定义格式 tar 风格的分片 + 一个索引文件
怎么组样本 ★ 同一个 basename 的文件自动被打包成一条样本 索引里直接记录每条样本的位置
远程读 ✅ 一个 HTTP GET 流式拉，边拉边解；S3 / HTTP 直接读，不需要任何特殊服务 ✅ 同样支持，另有自动本地缓存与预取
随机访问 ❌ 不能（tar 是纯顺序格式） ✅ 支持确定性的随机访问
shuffle 怎么办 ★ 靠两级近似（见下） 可以真随机，因为有索引
断点续训 要自己实现 ✅ 内置：记录"已经消费到第几个样本"
多模态 ✅ 友好（图片、音频直接当文件塞进去） ✅ 友好
谁在用 OpenCLIP、图文训练栈 MosaicML / Databricks 训练栈

一个 WebDataset 分片内部长这样：

shard-000123.tar 里面：
    000000.txt   000000.json
    000001.txt   000001.json     ← 同一个 basename 的两个文件
    000002.txt   000002.json        被自动配成一条样本

★ shuffle 的两级近似是流式格式的关键妥协，值得记住（14 章会再讲）：

① shard 级：把 4096 个 shard 的顺序随机打乱；② 样本级：维护一个 10000 条样本的缓冲区，随机从里面抽一条，抽走就补一条。

合起来的效果 ≈ 全局随机，但从头到尾只做顺序读。⚠️ 注意它只是"≈"：缓冲区只有 10000 条，所以相距超过 10000 条的两个样本永远不可能换位置。对需要严格全局 shuffle 的场景（比如课程学习的对照实验），这个近似是不够的。

3.6 ★★★ 把账算出来：同一份数据，五种格式各占多少字节、随机读一条要几次 IO

前面全是定性描述。这一节用一份具体的数据把所有格式的字节数和 IO 次数算到底。

规范数据：100 万篇中文网页

参数 值 说明
文档数 100 万篇 —
每篇正文 2000 个汉字 = 2000 字符
每篇正文 UTF-8 字节 6000 字节 2000 × 3（一个汉字 3 字节）
每篇 token 数 ⚠️ 1143 2000 ÷ 1.75 = 1142，加 1 个 <eod>。⚠️ 这里用的是经验区间 1.5 ~ 2 汉字/token 的中值，不是 openPangu 报告 Table 4 的"中文 3.82"——理由见 09 章 §9.5 那条口径矛盾。★ 取区间两端（2 汉字/token 和 1.5 汉字/token）会得到 1001 ~ 1334 token，下面每个"每条字节"都跟着浮动 −12% ~ +17%
每篇源文本字节/token ⚠️ 5.25 6000 ÷ 1143
元数据字段 7 个 id / url / language / language_score / quality_score / token_count / dump

一条 JSONL 记录长这样（正文用省略号代替）：

{"id":"cc-2024-10-0000123456","text":"番番番……（2000 个汉字）","url":"http://example.com/recipe/tomato-egg","language":"zh","language_score":0.98,"quality_score":2.7,"token_count":1143,"dump":"CC-MAIN-2024-10"}

先把这一条的字节数拆开（json.dumps(..., ensure_ascii=False) + "\n"，可以自己跑一遍验证）：

成分 字节 占比
正文（text 的值） 6000 96.7%
字段名 + 引号 + 冒号 + 逗号 + 花括号 + 换行 203 3.3%
合计一条 6203 100%

五种格式的体积

格式 一条占多少字节 100 万条合计 相对 JSONL 怎么算的
WARC.gz（原始网页） ⚠️ 约 36.7 KB ⚠️ 36.7 GB 5.9 倍 99 TB 压缩 ÷ 27 亿页（02 章 §2.2）。正文只占其中 6000/163000 = 3.7%，其余是 HTML / JS / CSS
JSONL（未压缩） 6203 6.20 GB 1.00 ✅ 精确
JSONL + gzip ⚠️ 约 2481 ⚠️ 2.48 GB 0.40 6203 ÷ 2.5
JSONL + zstd ⚠️ 约 2068 ⚠️ 2.07 GB 0.33 6203 ÷ 3.0
Parquet + zstd ⚠️ 约 2030 ⚠️ 2.03 GB 0.33 正文列 6000÷3.0 = 2000，加 7 个小列压完约 30
.bin + .idx（uint16） 2286 + 20 2.29 GB + 20 MB 0.37 1143 × 2 字节；.idx 每条 4+8+8 = 20 字节（04 章 §4.3）
.bin + .idx（int32） 4572 + 20 4.57 GB + 20 MB 0.74 1143 × 4 字节

★★★ 这张表里最该记住的一行：.bin（int32，4.57 GB）比 Parquet+zstd（2.03 GB）大 2.25 倍。

很多人以为"tokenize 之后数据会变小"。算一遍就知道不是：中文源文本 ⚠️ 5.25 字节/token，.bin 里 4 字节/token——tokenize 只"压"了 1.31 倍，而 zstd 轻松压 3 倍。★ 所以 .bin 不是省空间的格式，它是用 2 倍多的磁盘换 O(1) 随机访问（下面马上算这笔交易值不值）。

⚠️ 而且这个比值随语言变：

语料 ⚠️ 源文本字节/token .bin int32 .bin ÷ 源文本 结论
中文 约 5.25 4 0.76 略小一点
英文 约 4.2 4 0.95 基本一样大
代码 ⚠️ 约 2.7 4 1.48 ★ .bin 比源文本还大一半

★ 所以".bin 要多少 TB"这个问题，不用管语料里中文英文代码各占几成——.bin 那一边永远是确定的：15 T token × 4 字节 = 60 TB，不管什么语言。 变的是"同样一份源文本能切出多少 token"。

随机读第 823,190 条要付多少代价

这是训练阶段唯一重要的指标。假设 NVMe 固态盘顺序读 2 GB/s、zstd 解压 1 GB/s、随机读一个冷页约 100 µs（⚠️ 都是量级）：

格式 要做什么 实际读入的字节 ⚠️ 大致耗时
JSONL（未压缩） ❌ 没有索引，只能从头数 \n：平均扫过半个文件 5.11 GB（823190 × 6203） 2.6 s
JSONL + zstd（500 MB/片） ❌ 先定位到哪一片，然后把整片解压，再数 \n 500 MB 0.5 s
Parquet + zstd 读文件页脚 1 次 → 定位 row group → 整组读入并解压（row_group_size=10000） 20.3 MB 约 20 ms
Parquet + zstd（只要 id 和 score） 同上，但只读这两列的 chunk ⚠️ 约 0.1 MB 约 1 ms
WARC.gz 需要额外的 CDX 索引：查索引 1 次 + HTTP range GET 1 次 约 36.7 KB 网络往返，几十 ms
.bin + .idx ✅ 查 .idx 的 2 个数组元素 → 在 .bin 的 mmap 上切一刀 2286 字节（跨 1 ~ 2 个 4 KB 页） 约 100 ~ 200 µs（冷页）／约 1 µs（页缓存命中）

最后一行对第一行的倍数：2.6 s ÷ 100 µs = 约 2.6 万倍。

★★★ 这 2.6 万倍就是 04 章 存在的全部理由。 注意它不是靠压缩或更快的磁盘换来的——.bin（int32）比压缩后的 Parquet 还大 2.25 倍。它靠的是把"第 n 条在哪"这个信息单独存成一个定长数组，于是"找"这个动作从 O(n) 变成 O(1)。用 2 倍多的磁盘换 2.6 万倍的查找速度，这笔交易毫无悬念。

顺便回答：为什么 .bin 不压缩

压缩是【变长】的：同样 1143 个 token，压完可能 1600 字节，也可能 2600 字节
     → 第 n 条的字节偏移就不能用乘法算出来，必须查表
     → 而且取出来还要解压，每条几十微秒
★ 而 .bin 的全部价值就在于"定长 + 零解析"
     → 压缩会同时毁掉这两条
⟹ 结论：.bin 宁可多占一倍磁盘，也不能压
   （反过来说，这也是 tokenize 必须放在落盘之前的原因之一：
     它是唯一一种【不破坏定长性】的压缩）

谓词下推能省多少：把旧版那个"200 GB"算清楚

本章旧版写过"扫 10 TB 语料做一次筛选，可能只真正读了 200 GB"。用上面的数字验算：

步骤 算式 结果
只读 id + score 两列占整表的比例 10 B ÷ 2030 B 0.49%
扫 10 TB 语料实际读入 10 TB × 0.49% 约 49 GB
加上 row group 粒度的浪费 + min/max 跳不掉的块 ⚠️ 乘 1 ~ 4 倍 约 50 ~ 200 GB

★ 所以"200 GB"是这个区间的上端，不是典型值。⚠️ 真实比例取决于你读几列、列有多宽、row_group_size 多大。但量级是对的：列投影 + 谓词下推能把扫表成本压到百分之几。

3.8 一段能跑的代码：三种格式互转

import json, pyarrow as pa, pyarrow.parquet as pq

# ---------- 写 JSONL ----------
with open("docs.jsonl", "w", encoding="utf-8") as f:
    for d in docs:                       # docs = [{"id":..,"text":..,"lang":..,"score":..}]
        f.write(json.dumps(d, ensure_ascii=False) + "\n")

# ---------- JSONL → Parquet ----------
rows = [json.loads(l) for l in open("docs.jsonl", encoding="utf-8")]
table = pa.Table.from_pylist(rows)
pq.write_table(table, "docs.parquet", compression="zstd",
               row_group_size=10000)     # ★ 一个 row group = 谓词下推的最小跳过单位

# ---------- 在 Parquet 上做"只读两列 + 过滤" ----------
# ★ 注意 columns=[...]：text 那一大坨【完全不会被读进来】
t = pq.read_table("docs.parquet", columns=["id", "score"],
                  filters=[("score", ">", 3.5)])   # ← 谓词下推到文件层
print(t.num_rows)

# ---------- 流式读 JSONL（内存恒定，无论文件多大）----------
def stream(path):
    with open(path, encoding="utf-8") as f:
        for line in f:                   # ★ 一次只有一行在内存里
            yield json.loads(line)

# ---------- 把 §3.6 那张体积表自己跑一遍 ----------
rec = {"id": "cc-2024-10-0000123456", "text": "番" * 2000,
       "url": "http://example.com/recipe/tomato-egg", "language": "zh",
       "language_score": 0.98, "quality_score": 2.7,
       "token_count": 1143, "dump": "CC-MAIN-2024-10"}
line = json.dumps(rec, ensure_ascii=False) + "\n"
print(len(line.encode("utf-8")))            # → 6203
print(len(rec["text"].encode("utf-8")))     # → 6000  （正文）
print(6203 - 6000)                          # → 203   （结构开销）

⚠️ row_group_size 是 Parquet 唯一一个必须自己调的参数。 太大（比如 100 万）→ 随机读一条要解压一大坨；太小（比如 100）→ 页脚元数据膨胀、压缩率变差。★ 长文本语料常用 1000 ~ 10000。

3.9 挂回真实系统

系统 用什么格式 说明
Common Crawl WARC / WAT / WET 见 02 章
各家开源语料的发布形式 ✅ Parquet FineWeb、DCLM、Dolma、Essential-Web 在 HuggingFace 上都是 Parquet
HuggingFace datasets ✅ Arrow（mmap 缓存） 所以 load_dataset 秒开
Megatron preprocess_data.py 输入 ✅ JSONL → 输出 .bin/.idx 04 章
多模态训练（图文） ✅ WebDataset（tar） 图片当文件直接塞

⚠️ 一个常见的困惑先在这里澄清：你从 HuggingFace 下载的 FineWeb 是 Parquet，但不能直接拿它训练——它里面是文本，还没 tokenize。中间必须跑一次 preprocess_data.py 转成 .bin/.idx。很多人第一次做训练卡在这一步。

★ 顺手估一下这一步要多久和多大：FineWeb 全量 15 T token，按 §3.6 的比例，Parquet 约 44 TB（✅ HuggingFace 数据集卡给的体积），转出来的 .bin 是 60 TB（int32）。⚠️ tokenize 是纯 CPU 活，单核大约每秒几 MB 文本，全量跑完是几千核 × 几天的量级——所以这一步的产物必须放共享存储并复用，不要每次训练重跑。

3.10 小结

① 三套口径先钉死（本章开头）：
   容量   1 TB = 10^12，1 TiB = 2^40，差 9.95%
   压缩   "压缩到 33%" = "压缩 3 倍" = "省了 67%" 是同一件事
          ⚠️ "压缩 33%" 是歧义写法，本教程不用
   速度   加速倍数 = 1/(1−时间减少比例)
          ⚠️ "时间减少 60%" = "快 2.5 倍"，不是"快 60%"

② 一份数据一生要换三次格式，因为访问模式完全不同：
   JSONL（追加写、流式过） → Parquet（按列筛、省存储） → .bin/.idx（随机取）

③ ★ 行存 vs 列存 是本章唯一的核心概念
   行存：一行的字段挨着放。要一列就得读全部
   列存：一列的值挨着放。→ ① 只读需要的列 ② 同类值压缩率暴涨
                            ③ 每块记 min/max → 谓词下推整块跳过
   ⚠️ 但"Parquet 比 gzip 的 JSONL 小 30~60%"只在【短字段占主导】时成立：
      长文本记录只小 18%，纯元数据记录才小 67%（§3.3 那张表）
      ⟹ 长文本场景下，列存的价值几乎全在"只读需要的列"，不在压缩

④ ★★ §3.6 的账（100 万篇 × 2000 汉字 ≈ 1143 token，可自己验算）：
   体积   .bin int32 4.57 GB > JSONL 6.20... 排序要分开看：
          未压缩： JSONL 6.20 GB > .bin int32 4.57 > .bin uint16 2.29
          压缩后： gzip 2.48 > zstd 2.07 ≈ Parquet 2.03
   ★★ .bin（int32）比压缩后的 Parquet 大 2.25 倍 ——
      因为 tokenize 只"压"了 1.31 倍（中文 5.25 字节/token → 4 字节/token），
      而 zstd 压 3 倍。⟹ .bin 不是省空间的格式
      ⚠️ .bin ÷ 源文本：中文 0.76、英文 0.95、代码 1.48
   随机读一条  JSONL 2.6 s ≫ zstd 0.5 s ≫ Parquet 20 ms ≫ .bin 100 µs
          ★ 差 2.6 万倍，靠的不是压缩，是把"第 n 条在哪"单独存成定长数组
          ⟹ 用 2 倍多的磁盘换 2.6 万倍的查找速度

⑤ 为什么 .bin 不压缩：压缩是变长的，会同时毁掉"定长"和"零解析"
   ⟹ 宁可多占一倍磁盘。tokenize 是唯一不破坏定长性的压缩

⑥ Parquet = 磁盘格式（压缩）；Arrow = 内存格式（不压缩，零拷贝可直接算）
   HuggingFace datasets 底层是 Arrow + mmap → 所以"秒开"

⑦ mmap（内存映射文件）：把磁盘文件当内存数组用，操作系统按需换页
   ★ 这是数据领域最重要的系统技巧，下一章还要靠它
   ⚠️ 它快的是"打开"，不是"随机访问的第一次"（冷页仍要等一次磁盘）

⑧ 数据在远程对象存储时换用流式格式：
   WebDataset = 就是 tar，纯顺序读，shuffle 靠 shard 级 + 缓冲区两级近似
     ⚠️ 缓冲区只有万条量级 → 相距超过一万条的样本永远换不了位置
   MDS = 多了索引，支持确定性随机访问 + 断点续训

⑨ ⚠️ 从 HuggingFace 下的 Parquet 语料【不能直接训练】，
   里面是文本，必须先 tokenize 成 .bin/.idx
   ★ FineWeb 全量：44 TB Parquet → 60 TB .bin，几千核 × 几天
