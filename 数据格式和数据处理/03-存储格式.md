# 03 · 存储格式：JSONL / Parquet / Arrow / WebDataset

> **这一章讲"清洗阶段"的文件格式。** 训练时真正读的那个格式（`.bin` / `.idx`）是下一章。
> **核心只有一个概念：行存 vs 列存。** 搞懂它，这一章其余部分都是推论。

---

## 3.1 先说清楚：为什么会有好几种格式

一份数据在生命周期里会**换好几次格式**，因为不同阶段的访问模式完全不同：

```
阶段              典型操作                        想要的性质
──────────────────────────────────────────────────────────────
① 抓取/抽取      一条条追加写                     ★ 追加便宜、能流式处理
                 → JSONL / WARC

② 清洗/过滤      "把 quality_score < 2 的删掉"    ★ 只读某几列要快
                 "统计各语言的 token 总数"        ★ 压缩率高（省存储费）
                 → Parquet

③ 训练           "给我第 8,231,904 号样本"        ★ ★ 随机访问 O(1)
                 每秒几万次随机读                  ★ 零解析开销
                 → .bin + .idx（下一章）
```

> ★★ **一句话概括**：**JSONL 便于写和流式过，Parquet 便于筛和存，`.bin/.idx` 便于随机取。**
> 现实中的流水线就是 `JSONL → Parquet → .bin/.idx` 一路转下去。

---

## 3.2 JSONL：最简单、最通用的那个

**JSONL** = **JSON Lines**（每行一个 JSON 对象），有时也写作 `.jsonl` / `.ndjson`（Newline-Delimited JSON）。

```
{"id":"a1","text":"番茄炒蛋是一道家常菜……","url":"http://...","lang":"zh"}
{"id":"a2","text":"def quicksort(arr):\n    if len(arr)…","url":"http://...","lang":"code"}
{"id":"a3","text":"The mitochondrion is the powerhouse…","url":"http://...","lang":"en"}
     ↑ 每一行是一个【完整的、独立的】JSON 对象，行末是 \n
```

### 为什么它统治了这个领域的第一阶段

```
✅ 追加写只要 open(f,"a") 然后 write(json.dumps(d)+"\n")
✅ 流式处理不需要把整个文件读进内存 —— 一行一条，读一行处理一行
✅ 可以直接 split / cat / grep / wc -l，所有 Unix 工具都能用
✅ 一个文件坏了半截，前半截仍然可用（每行独立）
✅ 人能直接看懂
✅ 天然可并行：切成 N 个文件块，N 台机器各处理一块

❌ 体积大 —— 全是文本，字段名每行都要重复存一遍
❌ 解析慢 —— 每读一条都要跑一次 JSON parser
❌ ★ 不支持随机访问 —— 想要第 800 万条，只能从头数 800 万个 \n
❌ 不支持"只读某一列" —— 要拿 lang 字段也得把整行 text 解析出来
```

> ★ **`preprocess_data.py`（Megatron 的预处理脚本）的输入就是 JSONL**，这是这个领域最标准的交接格式。它默认读的字段名是 `"text"`。

### 一定要配的：分片 + 压缩

单个 JSONL 文件绝不能做成 2 TB，实践中一定是**切成很多分片（shard）**：

```
data/
  ├── part-00000.jsonl.zst     ← 每片 ~500 MB（压缩后）
  ├── part-00001.jsonl.zst
  ├── ...
  └── part-04095.jsonl.zst

压缩格式的选择：
  gzip  ——  最通用，压缩率一般，★ 不能并行解压
  zstd  ——  ★ 现在的默认选择。解压快 3~5 倍，压缩率还更好
  lz4   ——  最快但压缩率低，适合临时中间文件
```

## 3.3 ★ 核心概念：行存 vs 列存

这是整章唯一需要真正理解的东西。

### 直觉类比

想象一个 Excel 表格要存到磁盘上，只有两种存法：

```
原始表格：
        id    text（很长）        lang    score
  行1:  a1    "番茄炒蛋……"        zh      2.7
  行2:  a2    "def quicksort……"   code    4.1
  行3:  a3    "The mitochond……"   en      1.2


【行存 row-based】—— 一行的所有字段挨着放（JSONL 就是这样）
  磁盘布局： [a1|番茄炒蛋……|zh|2.7] [a2|def quick……|code|4.1] [a3|The mit…|en|1.2]
                                    ↑                        ↑
  要拿"所有的 score"？ → 必须把三段【全部】读进来，跳着取
     ★ 而 text 字段极长 —— 你为了拿 3 个浮点数，读了几十 KB 文本


【列存 columnar】—— 同一列的所有值挨着放（Parquet 就是这样）
  磁盘布局： [a1|a2|a3] [番茄炒蛋…|def quick…|The mit…] [zh|code|en] [2.7|4.1|1.2]
             └─ id ─┘  └────────── text ───────────┘  └─ lang ─┘  └─ score ─┘
                                    ↑                              ↑
  要拿"所有的 score"？ → ★ 只读最后那一小段，text 那一大坨【碰都不用碰】
```

### 列存的两个额外好处（比"少读"更重要）

```
① ★ 压缩率暴涨
   同一列的数据【类型相同、取值相似】，压缩算法能吃得很饱：
       lang 列： zh,zh,zh,en,en,en,en,zh,code,...
                 → 字典编码：{zh:0, en:1, code:2} + [0,0,0,1,1,1,1,0,2,...]
                 → 再游程编码：(0,×3)(1,×4)(0,×1)(2,×1)
                 → 原本几百 MB 的字符串列 → 几 KB
   而行存里 "zh" 夹在两段长文本中间，压缩器根本发现不了这个规律
   ⚠️ 我的经验量级：同一份语料，Parquet 通常比 gzip 后的 JSONL 再小 30~60%

② ★ 谓词下推（predicate pushdown）
   Parquet 在每个数据块的页脚记了【每列的 min / max】
   查 "score > 3.5" 时，某个块的 score.max = 2.9 → ★ 整块直接跳过，不解压
   → 扫 10 TB 语料做一次筛选，可能只真正读了 200 GB
```

### 什么时候**不该**用列存

```
❌ 要一条条追加写（列存必须凑够一批才能写一个块）
❌ 每次都要读整行的全部字段（那列存反而多了拼装开销）
❌ 只有一列（那就没有"列"的概念了）
```

> ★★ **这正好解释了流水线的换格式点**：
> **抽取阶段是一条条追加写 → JSONL；清洗阶段是反复按列筛选统计 → Parquet。**

## 3.4 Parquet 与 Arrow：一对经常被搞混的兄弟

```
┌─ Apache Parquet ────────────────────────────────────────────┐
│  ★ 磁盘上的格式（on-disk）                                   │
│  为【存储】优化：压缩、编码、谓词下推                          │
│  读的时候必须解压 + 解码                                      │
│  文件后缀 .parquet                                           │
└─────────────────────────────────────────────────────────────┘
┌─ Apache Arrow ──────────────────────────────────────────────┐
│  ★ 内存里的格式（in-memory）                                 │
│  为【计算】优化：不压缩，字段定长对齐，CPU 可以直接向量化处理  │
│  ★★ 零拷贝（zero-copy）：不同进程/语言可以【共享同一块内存】  │
│     Python 读进来的 Arrow 表，C++ 那边不用序列化就能直接用     │
└─────────────────────────────────────────────────────────────┘

关系：      Parquet（磁盘，压缩）
              │  读取时解压展开
              ▼
            Arrow（内存，不压缩，可直接算）
```

> ★ **HuggingFace `datasets` 库的底层就是 Arrow。** 你 `load_dataset(...)` 之后它在磁盘上缓存的 `.arrow` 文件，就是把 Arrow 内存布局直接 mmap 到磁盘——所以它加载 100 GB 数据集"秒开"，因为**根本没有真的读进内存，只是建立了内存映射**。

**mmap（memory-mapped file，内存映射文件）**：让操作系统把一个磁盘文件"假装"成一段内存地址。你按数组下标访问，操作系统在背后按需从磁盘换页进来。**这是整个数据领域最重要的一个系统技巧**——下一章的 `.bin` 文件也靠它。

## 3.5 WebDataset 与 MDS：为"顺序流式读"设计的

前面几种格式都假设**数据在本地磁盘上**。但真实训练时数据往往在**对象存储**（S3、OSS）上，几百 TB，本地根本放不下。

这时的访问模式变了：**顺序流式拉取，边拉边训**。

```
┌─ WebDataset ────────────────────────────────────────────────┐
│  做法：★ 就是普通的 .tar 文件！                              │
│                                                             │
│  shard-000123.tar 里面：                                    │
│      000000.txt   000000.json                               │
│      000001.txt   000001.json     ← 同一个 basename 的文件  │
│      000002.txt   000002.json        自动被打包成一条样本   │
│                                                             │
│  ✅ tar 是纯顺序格式 → 一个 HTTP GET 流式拉，边拉边解        │
│  ✅ 不需要任何特殊服务，S3/HTTP 直接读                       │
│  ✅ 多模态友好（图片、音频直接当文件塞进去）                  │
│  ❌ ★ 不能随机访问                                          │
│     → shuffle 靠【两级近似】：shard 级打乱 + 缓冲区内打乱     │
└─────────────────────────────────────────────────────────────┘

┌─ MDS（Mosaic Data Shard，MosaicML StreamingDataset）────────┐
│  ✅ 比 WebDataset 多了一个索引 → ★ 支持确定性的随机访问      │
│  ✅ 内置断点续训：记录"已经消费到第几个样本"                  │
│  ✅ 自动做本地缓存与预取                                     │
└─────────────────────────────────────────────────────────────┘
```

> ★ **shuffle 的两级近似**是流式格式的关键妥协，值得记住（[14 章](14-采样-shuffle-与断点续训.md)会再讲）：
> ```
> ① shard 级：把 4096 个 shard 的【顺序】随机打乱
> ② 样本级：维护一个 10000 条样本的缓冲区，随机从里面抽一条，抽走就补一条
> → 合起来的效果 ≈ 全局随机，但从头到尾只做【顺序读】
> ```

## 3.6 四种格式的一张对照表

| | **JSONL** | **Parquet** | **WebDataset** | **`.bin`+`.idx`** |
|---|---|---|---|---|
| 布局 | 行存 | **列存** | 行存（tar） | ★ 纯二进制数组 |
| 内容 | 文本 | 文本 | 任意文件 | ★ **整数 token** |
| 追加写 | ✅ 极易 | ⚠️ 按块 | ✅ | ✅ |
| 随机访问 | ❌ | ⚠️ 块级 | ❌ | ✅ **O(1)** |
| 只读某列 | ❌ | ✅ **强项** | ❌ | 不适用 |
| 压缩率 | 差 | ✅ **最好** | 看内容 | ⚠️ 通常不压 |
| 人可读 | ✅ | ❌ | ⚠️ | ❌ |
| 用在哪一步 | ①抽取 ②交接 | ③清洗筛选 | ④远程流式 | ⑤ **训练** |

## 3.7 一段能跑的代码：三种格式互转

```python
import json, pyarrow as pa, pyarrow.parquet as pq

# ---------- 写 JSONL ----------
with open("docs.jsonl", "w", encoding="utf-8") as f:
    for d in docs:                       # docs = [{"id":..,"text":..,"lang":..,"score":..}]
        f.write(json.dumps(d, ensure_ascii=False) + "\n")

# ---------- JSONL → Parquet ----------
rows = [json.loads(l) for l in open("docs.jsonl", encoding="utf-8")]
table = pa.Table.from_pylist(rows)
pq.write_table(table, "docs.parquet", compression="zstd",
               row_group_size=10000)     # ★ 一个 row group = 谓词下推的最小跳过单位

# ---------- 在 Parquet 上做"只读两列 + 过滤" ----------
# ★ 注意 columns=[...]：text 那一大坨【完全不会被读进来】
t = pq.read_table("docs.parquet", columns=["id", "score"],
                  filters=[("score", ">", 3.5)])   # ← 谓词下推到文件层
print(t.num_rows)

# ---------- 流式读 JSONL（内存恒定，无论文件多大）----------
def stream(path):
    with open(path, encoding="utf-8") as f:
        for line in f:                   # ★ 一次只有一行在内存里
            yield json.loads(line)
```

## 3.8 挂回真实系统

| 系统 | 用什么格式 | 说明 |
|---|---|---|
| **Common Crawl** | WARC / WET | 见 [02 章](02-数据源与文本抽取.md) |
| **各家开源语料的发布形式** | ✅ **Parquet** | FineWeb、DCLM、Dolma、Essential-Web 在 HuggingFace 上都是 Parquet |
| **HuggingFace `datasets`** | ✅ **Arrow**（mmap 缓存） | 所以 `load_dataset` 秒开 |
| **Megatron `preprocess_data.py`** | 输入 ✅ **JSONL** → 输出 `.bin/.idx` | [04 章](04-训练格式-Megatron索引.md) |
| **多模态训练（图文）** | ✅ **WebDataset**（tar） | 图片当文件直接塞 |
| **MosaicML / Databricks 训练栈** | **MDS** | 内置断点续训 |

> ⚠️ **一个常见的困惑先在这里澄清**：你从 HuggingFace 下载的 FineWeb 是 **Parquet**，但**不能直接拿它训练**——它里面是**文本**，还没 tokenize。中间必须跑一次 `preprocess_data.py` 转成 `.bin/.idx`。**很多人第一次做训练卡在这一步。**

## 3.9 小结

```
① 一份数据一生要换三次格式，因为访问模式完全不同：
   JSONL（追加写、流式过） → Parquet（按列筛、省存储） → .bin/.idx（随机取）

② ★ 行存 vs 列存 是本章唯一的核心概念
   行存：一行的字段挨着放。要一列就得读全部
   列存：一列的值挨着放。→ ① 只读需要的列 ② 同类值压缩率暴涨
                            ③ 每块记 min/max → 谓词下推整块跳过

③ Parquet = 磁盘格式（压缩）；Arrow = 内存格式（不压缩，零拷贝可直接算）
   HuggingFace datasets 底层是 Arrow + mmap → 所以"秒开"

④ mmap（内存映射文件）：把磁盘文件当内存数组用，操作系统按需换页
   ★ 这是数据领域最重要的系统技巧，下一章还要靠它

⑤ 数据在远程对象存储时换用流式格式：
   WebDataset = 就是 tar，纯顺序读，shuffle 靠 shard 级 + 缓冲区两级近似
   MDS = 多了索引，支持确定性随机访问 + 断点续训

⑥ ⚠️ 从 HuggingFace 下的 Parquet 语料【不能直接训练】，
   里面是文本，必须先 tokenize 成 .bin/.idx
```
