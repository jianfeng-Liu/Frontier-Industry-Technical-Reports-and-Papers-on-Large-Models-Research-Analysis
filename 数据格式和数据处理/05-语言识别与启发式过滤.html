05 · 语言识别与启发式过滤

流水线上最便宜的一刀，也是砍掉份额最大的一刀。
这一章全是"规则"，没有模型，没有数学——但它决定了后面所有昂贵步骤要处理多少数据。

5.1 为什么第一刀必须用规则，而不是模型

输入规模：一次 Common Crawl 快照 ≈ 25 亿个网页

假设用一个小模型给每篇打分：
    一篇 1 毫秒（已经很快了）
    → 25 亿毫秒 = 29 天 × 单机
    → 就算 1000 台机器并行，也要 40 分钟，且要 1000 台 GPU

而一条正则/一次计数：
    一篇 10 微秒
    → 100 倍便宜，纯 CPU

★★ 所以流水线的顺序是【固定的、由成本决定的】：
      便宜的规则先跑，把量砍下来 → 昂贵的模型后跑
   这个原则叫【级联过滤 cascade】，在整个领域里到处都是。

成本梯度（⚠️ 我的量级估算，用于建立直觉）：

  正则 / 计数        ~ 10 μs/篇     ← 本章
  语言识别 fastText  ~ 50 μs/篇     ← 本章
  MinHash 签名       ~ 1 ms/篇      ← 06 章
  困惑度（小 n-gram/小模型）~ 5 ms/篇  ← 07 章
  分类器（BERT 级）  ~ 20 ms/篇     ← 07 章
  大模型打标签       ~ 1 s/篇       ← 07 章（所以要蒸馏成小模型）

  ★ 跨度 5 个数量级 —— 顺序错了，成本差几百倍

5.2 语言识别（LID）

LID = Language IDentification（语言识别），判断一段文字是哪种语言。

为什么必须先做

① 后面几乎所有规则都是【语言相关】的
   "平均词长 > 10 就丢掉" —— 对英文合理，对德文误杀，对中文毫无意义
   "标点占比" —— 中文用「，。」英文用「,.」，判断逻辑不同
   ★ 所以必须先分流，再按语言各走各的规则

② 配比是按语言定的（"中文 30% 英文 60%"），不识别就没法配

③ 大量网页是【机器翻译】或【乱码混杂】的，LID 的置信度分能顺手筛掉

怎么做：fastText

fastText 是 Facebook（Meta）开源的一个轻量文本分类库。它的语言识别模型 lid.176.bin 认 176 种语言，~ 130 MB，单条判断几十微秒，是这个领域事实上的标准。

原理很简单，不需要神经网络的直觉也能懂：

① 把文本切成【字符 n-gram】（连续的 n 个字符）
      "hello world" → "hel","ell","llo","lo ","o w",...

② 每个 n-gram 查一个 embedding 向量，全部【求平均】
      ★ 注意：只是平均，没有顺序、没有注意力 —— 所以极快

③ 平均向量过一个线性分类器 + softmax → 176 个语言的概率

为什么有效：不同语言的字符组合分布差别巨大
      "th","he","in" → 强烈的英文信号
      "de","la","es" → 西班牙/法语信号
      汉字本身 → 中文信号

用法与阈值

import fasttext
model = fasttext.load_model("lid.176.bin")

def detect(text):
    # ★ 必须先把换行去掉，fastText 用 \n 分隔样本
    labels, probs = model.predict(text.replace("\n", " "), k=1)
    return labels[0].replace("__label__", ""), probs[0]

lang, score = detect(doc["text"])
if lang == "en" and score >= 0.65:      # ✅ FineWeb 用的就是 0.65
    keep(doc)

✅ FineWeb 的阈值是 0.65（论文明确写了这个数）。
⚠️ 阈值的取舍：调高 → 更纯但丢掉大量多语言混排的技术文档（比如中文博客里贴英文代码）；调低 → 混进乱码。0.6~0.7 是常见区间。

三个坑

① ★ 代码文件会被判成各种奇怪的语言
   Python 代码常被判成英文（因为关键字是英文），也可能被判成别的
   → 代码源【不要过 LID】，单独走一条线

② 短文本极不准
   < 50 字符的文本，LID 基本靠猜 → 通常先按长度过滤再做 LID

③ 简繁体 / 方言 / 罗马化
   lid.176 把中文当一类，不区分简繁；粤语、闽南语支持很差

5.3 ★ 启发式规则：三代规则集

"启发式（heuristic）"就是人拍脑袋想出来、但确实管用的经验规则。这个领域有三套被反复引用的规则集。

第一代：C4 规则（2019，arXiv:1910.10683 附录）

C4 是 Google T5 论文里构建的语料，它的规则是这个领域的起点。✅ 论文里明确列出的包括：

① 只保留【以句末标点结尾】的行（. ! ? "）
   ★ 直觉：导航栏、按钮文字、标签云都不以句号结尾
   ★ 这一条极其有效，也极其粗暴 —— 代码、列表、诗歌全被误杀

② 丢掉少于 5 句话的页面；只保留至少 3 个词的行

③ 丢掉含有"脏词表"里任何词的页面
   ⚠️ 这条后来被广泛批评：会系统性地删掉 LGBTQ、医学、法律相关的正当内容

④ 丢掉含 "javascript" 字样的行（说明是"请开启 JS"提示）
   丢掉含 "lorem ipsum"（排版占位文）的页面
   丢掉含 "{" 的页面   ← ★ 这一条把【所有代码】都删了

⑤ 丢掉含 "terms of use / privacy policy / cookie" 的行

★ ④ 里那条 "丢掉含 { 的页面"，是 C4 一个著名的副作用：C4 里几乎没有代码。后来大家发现代码对推理能力很重要，这条规则就成了反面教材。

⚠️ 我的归纳：C4 规则的时代特征是"宁可错杀"——因为 2019 年数据管够，纯度比数量重要。到了 2024 年数据不够用了，风向就反过来了（见 12 章 Nemotron-CC 主动放松过滤）。

第二代：Gopher 规则（2021，DeepMind）

Gopher 的规则更"统计化"，不看具体词，看分布特征。⚠️ 下面这组阈值在业界被广泛复用（FineWeb、Dolma、RefinedWeb 都实现了 Gopher 系规则），具体数值以各自实现为准：

文档级：
  □ 词数不在 [50, 100000] 之间             → 丢
  □ 平均词长不在 [3, 10] 之间               → 丢  ★ 抓乱码和拼接文本
  □ 含 "#" 的行 > 10%                       → 丢  ★ 抓 markdown 目录/标签墙
  □ 以省略号结尾的行 > 30%                  → 丢  ★ ★ 抓"阅读全文…"列表页
  □ 以项目符号开头的行 > 90%                → 丢  ★ 抓纯列表页
  □ 含字母的词 < 80%                        → 丢  ★ 抓纯数字表格
  □ 不含至少 2 个停用词(the/be/to/of/and...)→ 丢  ★ 抓非自然语言

重复度（★ Gopher 最有价值的部分，见下）：
  □ 重复行占比 > 30%                        → 丢
  □ 重复段落占比 > 30%                      → 丢
  □ top-2gram 占比 > 20%                    → 丢
  □ 重复 5-gram 占总字符 > 15%              → 丢

★★ 重复度那一组特别重要，它抓的是"文档内部重复"，和 06 章的"文档之间重复"是两回事，很容易混。
例子：一个商品页把"包邮 正品保证 七天退换"重复了 200 遍。它和别的文档都不重复（去重抓不到它），但它本身没有任何信息量。

第三代：FineWeb 自己加的三条（2024）

✅ FineWeb 论文报告，他们在 C4 + Gopher 之上又加了几条自研过滤器，其中效果最好的三条（论文里给了各自的收益）大意是：

① 行末不带标点的行占比过高 → 丢
② 极短行（< 30 字符）占比过高 → 丢
③ 重复行的【字符数】占比过高 → 丢

⚠️ 具体阈值请以 papers/FineWeb-Decanting-the-Web-arXiv-2406.17557.pdf 为准；我这里只保留方向性描述，避免转述出错。

5.4 一段能跑的实现

import re
from collections import Counter

STOPWORDS_EN = {"the", "be", "to", "of", "and", "that", "have", "with"}
END_PUNCT = (".", "!", "?", '"', "。", "！", "？", "”")

def heuristic_filter(text, lang="en"):
    """返回 (是否保留, 被哪条规则拒掉)"""
    lines = [l for l in text.split("\n") if l.strip()]
    words = text.split()
    n_w, n_l = len(words), len(lines)
    if n_w == 0 or n_l == 0:
        return False, "empty"

    # ---- 长度 ----
    if not (50 <= n_w <= 100_000):
        return False, "word_count"

    # ---- 平均词长（★ 只对空格分词的语言有意义）----
    if lang in ("en", "de", "fr"):
        avg_len = sum(len(w) for w in words) / n_w
        if not (3 <= avg_len <= 10):
            return False, "avg_word_len"
        if len(STOPWORDS_EN & {w.lower() for w in words}) < 2:
            return False, "no_stopwords"

    # ---- 行级形态 ----
    if sum(l.rstrip().endswith("…") or l.rstrip().endswith("...")
           for l in lines) / n_l > 0.30:
        return False, "ellipsis_lines"          # ★ 抓"阅读全文…"列表页
    if sum(l.lstrip().startswith(("•", "-", "*", "·"))
           for l in lines) / n_l > 0.90:
        return False, "bullet_lines"
    if sum(not l.rstrip().endswith(END_PUNCT) for l in lines) / n_l > 0.70:
        return False, "no_terminal_punct"

    # ---- ★ 文档【内部】重复度（Gopher 系）----
    dup_line_chars = sum(len(l) for l, c in Counter(lines).items()
                         if c > 1 for _ in range(c - 1))
    if dup_line_chars / max(len(text), 1) > 0.30:
        return False, "dup_lines"

    grams = [" ".join(words[i:i+5]) for i in range(n_w - 4)]
    if grams:
        top_n, top_g = Counter(grams).most_common(1)[0][::-1][0], None
        most = Counter(grams).most_common(1)[0]
        if most[1] * 5 / n_w > 0.15:
            return False, "dup_5gram"

    return True, None

★ 实践建议：一定要把"被哪条规则拒掉"记下来并统计。
每条规则各砍掉多少，是调流水线唯一可靠的抓手。
⚠️ 一个真实的失败模式：某条规则因为一个 bug 砍掉了 80% 的数据，而你只看总量的话完全发现不了。

5.5 中文特有的问题

上面的规则几乎全是为英文设计的。中文要单独处理：

① ★ 没有空格分词 → "词数""平均词长"这两类规则【直接失效】
   替代：用【字符数】，或者先用 jieba 之类分词（但那又慢了 100 倍）
   实践：中文一般改用【字符数】+【标点密度】

② 标点必须用中文标点表（，。！？；：""）
   ★ 一个常见 bug：只判 ASCII 标点 → 所有中文文档都被判成"不以标点结尾"→ 全灭

③ 简繁混排、全角半角混排 → 需要 Unicode 归一化（NFKC）

④ ★ 中文互联网的垃圾形态和英文不同：
   - 采集站/伪原创（同义词替换过的洗稿）→ 06 章的近似去重能抓一部分
   - 小说站的分章页（每页只有几百字 + 大段导航）
   - 全角空格和不可见字符插入（用来绕过查重）
     → ★ 必须做 Unicode 归一化 + 零宽字符清除，否则去重会失效

import unicodedata, re
ZERO_WIDTH = re.compile(r"[​-‏‪-‮﻿]")

def normalize_zh(text):
    text = ZERO_WIDTH.sub("", text)            # ★ 先清零宽字符
    text = unicodedata.normalize("NFKC", text)  # 全角→半角，兼容字符归一
    text = re.sub(r"[ \t]+", " ", text)
    text = re.sub(r"\n{3,}", "\n\n", text)
    return text.strip()

⚠️ 零宽字符这一条是我特别想强调的：内容农场会插入零宽空格来绕过平台查重。如果不清掉，你的 MinHash 去重（06 章）会认为两篇一模一样的洗稿文是不同文档，全部留下来。这是一个静默失效的坑。

5.6 挂回真实系统

语料 LID 启发式规则
C4 langdetect ✅ 自己那套（句末标点、脏词表、{）
CCNet fastText 轻量规则 + ✅ 困惑度（见 07 章）
RefinedWeb fastText ✅ 明确采用 Gopher 系规则 + 行级修正
Dolma fastText Gopher 系 + C4 系（✅ 全流程开源可复现）
FineWeb ✅ fastText，阈值 0.65 ✅ C4 + Gopher + 自研三条
Nemotron-CC — ✅ 主动放松启发式规则以保留更多 token

★ 注意最后一行的方向反转：Nemotron-CC 明确主张放松过滤，理由是长周期训练（15 T token 以上）时，唯一 token 的数量比纯度更值钱——因为数据不够就得重复，而重复的边际收益递减（11 章）。这是 2024 年之后的新共识方向之一。

5.7 小结

① ★★ 流水线顺序由【成本】决定：便宜的规则先跑砍量，昂贵的模型后跑
   成本跨度 5 个数量级（正则 10μs → 大模型打标 1s）

② 语言识别（LID）必须最先做，因为后面的规则全是语言相关的
   工具：fastText lid.176.bin，几十微秒一条
   ✅ FineWeb 阈值 0.65
   坑：代码别过 LID；短文本不准；不区分简繁

③ 三代启发式规则集：
   C4（2019）    —— 词表和标点规则，宁可错杀
                    ★ "丢掉含 { 的页面" 把代码全删了，著名反面教材
   Gopher（2021）—— 统计分布规则 + ★【文档内部重复度】
   FineWeb（2024）—— 在前两者之上再加自研三条

④ ★ 区分两种"重复"，极易混淆：
   文档【内部】重复 —— 一句话在同一篇里重复 200 遍  → 本章的 Gopher 规则
   文档【之间】重复 —— 两篇文档一模一样            → 06 章的去重

⑤ 中文要单独一套：字符数代替词数、中文标点表、
   ★ Unicode 归一化 + 零宽字符清除（否则洗稿文的去重会静默失效）

⑥ 实践铁律：★ 记录每条规则各砍掉多少，否则出了 bug 你完全看不见
