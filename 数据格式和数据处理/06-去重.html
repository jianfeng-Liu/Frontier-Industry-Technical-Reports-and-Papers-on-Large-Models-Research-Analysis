06 · ⭐ 去重：四个粒度

全教程最重要的一章。 去重是整个数据流水线里收益最确凿、争议最小的一步——
别的环节（质量过滤怎么定义"好"、配比怎么配）都还在吵，去重是公认必做的。

⚠️ 本章数字口径：容量沿用 05 章的十进制约定（1 GB = 10⁹ 字节）。★ 更要紧的是"去重率"的分母：同一次去重，按文档数算、按字节数算、按token 数算，能得出三个差好几倍的数字——6.1 节会用论文里的两张表把这件事钉死。

6.1 先看一个真实的数字

✅ Lee et al., arXiv:2107.06499（Katherine Lee 等，Google，2021-07，ACL 2022）——这是这个领域的奠基论文。✅ 下面所有数字我都从 papers/Dedup-Deduplicating-Training-Data-Makes-LM-Better-arXiv-2107.06499.pdf 里逐句核对过。

✅ 一个 61 个单词的英文句子，在 C4 里逐字重复了 61036 次（论文原文："a 61-word sequence in C4 that is repeated 61,036 times verbatim"）。

而 C4 已经是当时过滤得最认真的开源语料之一。

这是本章最该先讲的一件事。论文报了两组留存数字，它们的分母不同，不可以直接比：

★★ 把 C4 那两行并排看：

    NearDup      3.04%   ← 分母是【文档数】
    ExactSubstr  7.18%   ← 分母是【token 数】

⟹ 这两个数字【不是】"7.18% 比 3.04% 删得多一倍"。
   它们量的根本不是同一件东西：
     一个说"有 3.04% 的文档整篇被删掉"，
     一个说"有 7.18% 的 token 被从各篇文档里抠掉（★ 没有任何文档被整篇删除）"。

⟹ ✅ 论文自己点出了这一点，原文大意是：
   "平均而言 ExactSubstr 删掉的总内容【比 NearDup 更多】，
    尽管 ExactSubstr 不整篇删除任何样本 —— 例如它删掉了 C4 里 7.18% 的 token。"

⚠️ 所以每次看到"去重删掉了 X%"，第一个要问的问题永远是：
   【X% 的分母是文档数、字节数，还是 token 数？】

⚠️ 一个真实的失败模式：同一个团队里 A 用文档数报留存率、B 用 token 数报留存率，两人对同一次去重给出 3% 和 7% 两个数，然后花一周争论"哪一步出了 bug"。先统一分母，再讨论数值。

★ 还有一个 LM1B 那一行值得单独看：它只删掉 0.76% 的 token，✅ 论文给的解释是 LM1B 有 90% 的文档不到 50 个 token，而 ExactSubstr 的最小匹配长度就是 50 token——短文档连"参与匹配"的资格都没有。 这就是"同一个方法在不同语料上留存率差 25 倍"的原因，不是方法好坏。

✅ 逐字复述（memorization）的比例，论文 Table 4——无提示生成 10 万条序列，统计其中逐字照抄训练数据的 token 占比：

模型（1.5 B 参数的 "XL"，训练语料不同） 训练 1 epoch 训练 2 epochs

★ 自己验一遍"少了 10 倍"这个说法：
    1.926% ÷ 0.189% = 10.2 倍    ✅ 和论文说的 "∼10× more memorization" 一致

其余三条（✅ 论文明确报告）：

① 标准数据集的验证集里，【超过 4%】的内容能在训练集里找到
   ★ 具体地：C4 验证集 4.60%、RealNews 验证集 14.35%（上面 Table 2）
   ⟹ 也就是说，"验证 loss"里有一部分是在考背诵 —— 08 章专门讲这件事

② 去重后训练步数更少就能达到同样或更好的准确率

③ ✅ 在 Wiki-40B 上，ExactSubstr 去重让 1.5 B 的 XL 模型困惑度
   【降低了将近 3 个点】（论文原文 "almost 3 points perplexity on Wiki-40B"）
   ★ 尽管训练数据【变少了】
   ⚠️ 口径：这是"困惑度绝对值降了约 3"，不是"降低了 3%"

★★ ③ 这一条是全领域最有说服力的实验之一：数据变少了，效果反而变好了。
这直接印证了 01 章的因果链①——训练预算固定时，垃圾 token 挤占的是好 token 的位置。

6.2 为什么会有这么多重复？

① 转载与聚合     一篇新闻被 500 个站点转载、被 RSS 聚合器收录
② 模板           同一个 CMS 生成的 10 万个页面，只有正文那一小块不同
③ 分页与镜像     同一篇文章的 /page/1 /page/2 /print 版本
④ ★ 跨快照重复   Common Crawl 每月抓一次，同一个页面被抓了 80 次
   —— 这是量最大的一类，也最容易被忽略
⑤ 法律样板文     隐私政策、许可证、免责声明
⑥ 洗稿/伪原创    同义词替换、语序调整（★ 精确匹配抓不到）

★ ④ 值得特别强调：很多人以为"用 100 个 CC 快照就有 100 倍数据"。实际上快照之间的重叠率极高——所以真实增量远小于线性。这是新手最常见的误判。

✅ 一个可以量化的旁证（我从 papers/Dolma-Open-Corpus-of-Three-Trillion-Tokens-arXiv-2402.00159.pdf 核对过）：Dolma 做段落级去重时，"这一步删掉了大约 70% 的段落，主要是页眉和导航元素"。⚠️ 注意它的分母是段落数，不是文档数也不是 token 数——按上一节的规矩，这个 70% 不能和别处的留存率直接比。

6.3 ★★ 四个粒度：本章的骨架

去重不是一件事，是四件不同的事，抓的是四种不同的重复。它们互补而非替代，现代流水线通常叠着用。

# 粒度 判据（一句话） 手段 成本 ★ 抓得到 ⚠️ 抓不到 / 代价
① 精确文档
Exact		 两篇文档一字不差 整篇算一个哈希，哈希相同即重复 ★ 最便宜 转载、跨快照重复 改一个标点就漏
② 近似文档
NearDup / Fuzzy		 两篇文档 80% 的内容一样 MinHash + LSH 中 模板页、加了广告的转载、改几个词的洗稿 只有一大段相同、其余完全不同的情况
③ 子串
ExactSubstr		 两篇里有一模一样的 ≥ 50 token 片段 后缀数组（suffix array） 高 长引用、嵌入的法律条文、代码片段 ★ 它删的是【片段】不是整篇，所以"删了多少文档"恒为 0
④ 语义
SemDeDup		 说的是同一件事，但用词完全不同 embedding + 聚类 ★ 最贵（要给每篇跑一次模型） 翻译、改写、同题材水文 ⚠️ 也最容易删错（"语义相似" ≠ "信息冗余"）

★ 这张表的最后一列就是后面各节要展开的东西。② 是主力，工作量最大，也是唯一需要认真理解算法的一个。

6.4 ① 精确去重：最简单的那个

import hashlib
seen = set()
for doc in docs:
    # ★ 先归一化！否则大小写/空格/零宽字符的差异会让它整体失效（见 05 章 normalize_zh）
    key = normalize(doc["text"])
    h = hashlib.sha256(key.encode()).digest()     # ★ 用 digest()（32 字节）不是 hexdigest()（64 字节）
    if h in seen:
        continue
    seen.add(h)
    keep(doc)

★ 先算清楚 seen 到底要多少内存

这是精确去重唯一的难点。设有 100 亿（10¹⁰）篇文档：

存法 每元素理论字节 100 亿篇合计 同一个数的二进制口径
SHA-256 原始摘要 digest() 32 B 320 GB 298 GiB
SHA-256 十六进制串 hexdigest() 64 B 640 GB 596 GiB
⚠️ 放进 Python set 里的真实开销（digest()） ★ 约 78 B ★ 约 780 GB 727 GiB
⚠️ 放进 Python set 里（hexdigest()） 约 118 B 约 1.18 TB 1.07 TiB
截断成 8 字节、存进扁平数组 8 B 80 GB 75 GiB 
★★ 第三行是最容易被忽略的一行。验算过程：
    sys.getsizeof(bytes(32))     = 65 字节   ← 32 字节数据 + 33 字节 Python 对象头
    set 的槽位                    ≈ 8 / 0.6 ≈ 13 字节   ← 哈希表装载因子要留余量
    合计 ≈ 78 字节/元素 ⟹ 1e10 × 78 B ≈ 780 GB

⟹ ★ "320 GB" 这个教科书数字，在 Python 里实际要 780 GB，是 2.4 倍。
   ⚠️ 用 hexdigest() 的话是 1.18 TB，又多 50% —— 所以上面代码特意用了 digest()。

截断成 8 字节会不会撞车？ 这是个可以算的问题：

10¹⁰ 个随机 64 位值，期望的碰撞【对数】≈ n² / (2 · 2⁶⁴)
    = 1e20 / 3.689e19 ≈ 2.7 对

⟹ ★ 期望约 3 篇不重复的文档被误判成重复而删掉 —— 在 100 亿篇里可以忽略。
⟹ ⚠️ 但"至少发生一次碰撞"的概率是 93%，所以【别声称它是零误差的】。
   ★ 这就是"精确去重"的第一个让步：工程上的"精确"通常是 10⁻⁹ 量级的近似。

三种解法

① 分桶排序（最稳妥）
   按 hash 的前 2 字节分成 65536 个桶 → 每桶单独去重 → 完全精确
   ★ 因为相同的 hash 必然落在同一个桶，分桶不会漏
   ★ 代价：要落盘一遍（外排序），但内存需求降到 1/65536

② Bloom filter（省内存，有假阳性）
   用 m 位的位数组 + k 个哈希函数
   ★ 会误判"见过"（假阳性）→ 误删少量不重复的文档
   ★ 绝不会误判"没见过"（无假阴性）→ 不会漏掉重复的
   ✅ Dolma 用的就是 Bloom filter，做【文档级 + 段落级】精确去重

③ 段落级去重
   ★ 一个很实用的中间做法：按段落算哈希，只删重复的【段落】
   能抓到"正文不同但页脚相同"的模板页，而整篇哈希抓不到
   ✅ Dolma 报告这一步删掉了约 70% 的【段落】

Bloom filter 的取舍：一张可以直接查的表

位数组 m 位，插入 n 个元素，用 k 个哈希函数
    假阳性率 ≈ (1 − e^(−kn/m))^k
    最优 k   = (m/n) · ln2

✅ 下面每一行我都代进公式算过（k 取最优值的四舍五入）：

每元素位数 m/n 最优 k（取整） 假阳性率 100 亿文档需要的内存
8 6 2.16% 10.0 GB（9.3 GiB）
10 7 0.82%（"约 1%"） 12.5 GB（11.6 GiB）
12 8 0.31% 15.0 GB（14.0 GiB）
14 10 0.12%（"约 0.1%"） 17.5 GB（16.3 GiB）
16 11 0.05% 20.0 GB（18.6 GiB） 
★★ Bloom filter 的全部价值就在最后一列：
   100 亿文档、12.5 GB —— 单机内存装得下，而 Python set 要 780 GB。

⚠️ 但请把"假阳性率"换算成绝对值再做决定：
   1e10 篇 × 0.82% = 8200 万篇不重复的文档被误删。
   ★ "不到 1%"听起来很小，8200 万篇听起来就不小了。
   ⟹ 要不要接受，取决于你是在做【预训练主语料】（可以接受）
      还是在做【精选高质量语料】（绝对不能接受，该用分桶排序）。

6.5 ★★ ② 近似去重：MinHash + LSH

这是去重的主力，也是本章唯一需要认真理解的算法。

第一步：把"相似"定义成一个数

先把文档变成集合——切成 n-gram（连续 n 个词，这里的"词"按空格切，中文要先分词或改按字符，见 05 章 5.5 节）：

doc A = "the cat sat on the mat"
doc B = "the cat sat on a mat"

3-gram 集合：
  A = { "the cat sat", "cat sat on", "sat on the", "on the mat" }
  B = { "the cat sat", "cat sat on", "sat on a",   "on a mat"   }

Jaccard 相似度（两个集合的重叠程度）：

              |A ∩ B|          交集大小
  J(A,B) =  ───────────  =  ─────────────
              |A ∪ B|          并集大小

  取值 0（毫无重叠）到 1（完全相同）

上面这对：交集 = 2，并集 = 6  ⟹  J = 2/6 = 1/3 ≈ 0.333

问题： 10 亿篇文档，两两比较是 5 × 10¹⁷ 次（= n²/2）。宇宙热寂了也算不完。

第二步：MinHash —— 把一个大集合压成 k 个数

这是全章最漂亮的一个想法。

★★ 核心定理：
   取一个随机哈希函数 h，把集合里每个元素都哈希一遍，只保留【最小的那个值】。
   那么对任意两个集合 A、B：

           P[ min h(A) == min h(B) ]  =  J(A, B)

   ★ 也就是说：「两个集合的最小哈希值撞在一起」这件事发生的概率，
     【恰好等于】它们的 Jaccard 相似度。

为什么？ 一个不用公式的证明：

把 A∪B 里的所有元素，按 h 值从小到大排队。
问：排在【第一位】的那个元素，来自哪里？

  情况甲：它在 A∩B 里（两边都有）→ 那么 min h(A) 和 min h(B) 都是它 → 相等 ✅
  情况乙：它只在 A 里          → min h(A) 是它，min h(B) 不是 → 不等 ❌
  情况丙：它只在 B 里          → 同上 → 不等 ❌

因为 h 是随机的，"排第一的是谁"是在 A∪B 里【均匀随机】挑一个。
挑中交集里元素的概率 = |A∩B| / |A∪B| = J(A,B)。   ∎

★★ 第二步半：手算一遍，把这个定理摸实

上面那个证明看懂了不等于相信了。用刚才那对句子把签名完整算出来。

① 给 6 个 shingle 编号（并集一共 6 个）：

编号 shingle 属于
s1 the cat sat ★ A 和 B（交集）
s2 cat sat on ★ A 和 B（交集）
s3 sat on the 只在 A
s4 on the mat 只在 A
s5 sat on a 只在 B
s6 on a mat 只在 B 
A = {s1, s2, s3, s4}      B = {s1, s2, s5, s6}
交集 = {s1, s2} → 2 个      并集 = 6 个       J = 2/6 = 1/3

② 用 6 个哈希函数 h_a(x) = (a · x) mod 7，a = 1…6。★ 7 是质数且大于 6，所以这 6 个函数各自把 {1…6} 打乱成一个完整的排列——正好是定理里要的"随机排队"。

✅ 下表每个格子我都算过（例如 h3(s2) = 3 × 2 mod 7 = 6）：

哈希函数 s1 s2 s3 s4 s5 s6 min h(A) min h(B) 相等？
h₁ = 1x mod 7 1 2 3 4 5 6 1（来自 s1） 1（来自 s1） ★ 是
h₂ = 2x mod 7 2 4 6 1 3 5 1（来自 s4） 2（来自 s1） 否
h₃ = 3x mod 7 3 6 2 5 1 4 2（来自 s3） 1（来自 s5） 否
h₄ = 4x mod 7 4 1 5 2 6 3 1（来自 s2） 1（来自 s2） ★ 是
h₅ = 5x mod 7 5 3 1 6 4 2 1（来自 s3） 2（来自 s6） 否
h₆ = 6x mod 7 6 5 4 3 2 1 3（来自 s4） 1（来自 s6） 否 
签名（k = 6）：
    signature(A) = [ 1, 1, 2, 1, 1, 3 ]
    signature(B) = [ 1, 2, 1, 1, 2, 1 ]
                     ↑        ↑
                   相等     相等          ⟹ 相等 2 个 / 共 6 个

    Ĵ(A,B) = 2 / 6 = 0.3333   ★ 和真实的 J = 1/3 一模一样

③ ★★ 现在看一眼每一行加粗的 1 在哪里——定理的全部内容就在这一列上：

哈希函数 整个并集里 h 值最小的那个元素 它在交集里吗 签名是否相等
h₁ s1 ★ 在 是
h₂ s4 不在（只属 A） 否
h₃ s5 不在（只属 B） 否
h₄ s2 ★ 在 是
h₅ s3 不在（只属 A） 否
h₆ s6 不在（只属 B） 否 
★★★ 两列完全同步：【签名相等】 ⟺ 【并集里 h 值最小的元素落在交集里】

⟹ 于是概率就是"随机挑一个元素、挑中交集"的概率 = |A∩B| / |A∪B| = J。
⟹ 这不是近似，是【恒等】。近似只来自"k 有限"这一件事。

★ 还可以用更硬的方式验证一次：
  把 6 个 shingle 的所有 6! = 720 种排队顺序全枚举一遍，
  数一数有多少种顺序满足"排第一的落在交集里"：
     按对称性，每个 shingle 排第一的顺序各有 720 / 6 = 120 种，
     交集里有 2 个 shingle ⟹ 120 × 2 = 240 种
     240 / 720 = 1/3 = J     ✅ 精确相等（我也用程序枚举验证过）

第二步四分之三：k 取多大，误差有多少

于是：用 k 个不同的哈希函数，数一下有几位相等，除以 k，就是 J 的估计。

signature(A) = [ min h₁(A), min h₂(A), ..., min h_k(A) ]     ← k 个整数

  Ĵ(A,B) = (signature 中对应位置相等的位数) / k

★★ 这就把一篇几万字的文档，压成了 k 个整数（k 通常 64~256）

★ 误差怎么算：k 位里每一位"相等"都是一次独立的、成功概率为 J 的伯努利试验，所以 Ĵ 是一个二项比例，标准差 = √( J(1−J) / k )，在 J = 0.5 处取最大值 1 / (2√k)。

k J = 0.5 时的标准差 J = 0.8 时的标准差 最坏情况上界 1/(2√k)
16 0.125 0.100 0.125
64 0.063 0.050 0.063
128（最常用） 0.044 0.035 0.044
256 0.031 0.025 0.031
512 0.022 0.018 0.022

⚠️ 这里要纠正一个流传很广的说法：常见的口诀是"误差 ≈ 1/√k，k=128 → ±0.09"。1/√k 不是标准差——标准差是 1/(2√k)，k=128 时是 ±0.044。1/√k = 0.088 恰好约等于 2 个标准差，也就是 95% 置信区间的半宽。
★ 两种说法都能用，但必须说清是 1σ 还是 2σ，否则你会在"阈值该留多少余量"上差一倍。

第三步：LSH —— 避免两两比较

签名短了，但 10 亿 × 10 亿 次比较还是不行。

LSH = Locality-Sensitive Hashing（局部敏感哈希），思路是分带（banding）：

把 k=128 个签名，切成 b=16 个"带"，每带 r=8 个数：

  signature = [ s1 .. s8 | s9 .. s16 | ... | s121 .. s128 ]
               |--band 1-| |--band 2-|       |--band 16--|

★ 规则：只要【有任何一个 band 完全相同】，两篇文档就成为"候选对"

实现：给每个 band 的 8 个数算一个哈希，扔进哈希表。
      同一个桶里的文档 → 候选对。★ 不需要任何两两比较！

这个规则的效果，是一条 S 形曲线：

两篇文档 Jaccard = s 时，成为候选对的概率：

    P(s) = 1 - (1 - s^r)^b

拆成三步读（★ 从里往外）：
    s^r            = 某一个 band 的 r 个数【全部相同】的概率
    (1 - s^r)      = 这个 band 【不】全同的概率
    (1 - s^r)^b    = b 个 band 【全都不】全同的概率
    1 - (…)^b      = 至少有一个 band 全同 ⟹ 成为候选对

★★★ 第三步半：参数怎么定 —— 把 S 曲线算出来

b 和 r 是整条流水线上最该自己算一遍、而不是抄别人的两个数。✅ 下表每一格我都代进 P(s) = 1 − (1 − s^r)^b 算过，四组都固定 k = b × r = 128：

★★ 那么为什么大家选 16 × 8？ 把目标写成两句话，再回去查表：

目标① 召回：真重复（J ≥ 0.8）要基本都抓到
目标② 代价：低相似度的那一大坨（J ≤ 0.5）别涌进候选集
        ⟹ 因为候选对进来之后还要【逐对算真实 Jaccard 验证】，

8 × 16 0.204 ⚠️ 漏掉 80% 的真重复 0.000 ✅ ✗ 召回太低，去重形同没做

★ 换个角度看"涌入"这件事有多要命：
    P(s=0.3) 从 16×8 的 0.001 变成 32×4 的 0.229 —— ★ 放大了 229 倍。
    而语料里 J ≈ 0.3 的文档对数量，比 J ≥ 0.8 的【多好几个数量级】
    （绝大多数文档对彼此毫不相干）。
  ⟹ ⚠️ 候选集被这一大坨主导，验证阶段的成本会从"可做"变成"做不完"。
  ⟹ ★★ 这就是调参口诀背后真正的机制，不是"陡一点好看"。

★★ 调参口诀（现在它有数字支撑了）：
b 调大 → 阈值降低、更激进（召回高但候选集暴涨）；r 调大 → 阈值升高、更保守（候选集小但漏得多）。
b × r = k 固定，所以这俩此消彼长。
想让曲线更陡（阈值上下判得更干脆）→ 加大 k。 代价是签名更长、内存更多、算得更慢。
⚠️ 实践中 k=128, b=16, r=8（真实半数点 ≈ 0.67）和 k=128, b=14, r=9 这一带是常见起点；上线前务必自己代一遍公式查表，别抄口诀。

完整实现

import numpy as np, hashlib
from collections import defaultdict

K, B, R = 128, 16, 8                 # ★ 必须满足 K = B * R
MOD = np.uint64((1 << 32) - 5)       # ★ 一个小于 2^32 的质数，原因见下

rng = np.random.default_rng(42)
A  = rng.integers(1, int(MOD), K, dtype=np.uint64)   # h_i(x) = (A_i·x + Bp_i) mod MOD
Bp = rng.integers(0, int(MOD), K, dtype=np.uint64)

def shingles(text, n=5):
    w = text.split()
    return {" ".join(w[i:i+n]) for i in range(max(len(w) - n + 1, 1))}

def minhash(text):
    sh = shingles(text)
    if not sh:
        return None
    # ★ 把每个 shingle 压成一个 32 位整数（digest_size=4），保证它 < 2^32
    x = np.array([int.from_bytes(hashlib.blake2b(s.encode(), digest_size=4).digest(), "big")
                  for s in sh], dtype=np.uint64)
    # ★ A_i < 2^32 且 x < 2^32 ⟹ 乘积 < 2^64，uint64 刚好【不溢出】
    H = (A[:, None] * x[None, :] + Bp[:, None]) % MOD      # 形状 [K, |sh|]
    return H.min(axis=1).astype(np.uint32)                 # 形状 [K]

⚠️ 这里有两个真实的坑，都会"不报错但算错"：

```
① 混用 int64 和 uint64
numpy 里 int64 数组 × uint64 数组 会被提升成 float64，
★ 而 float64 只有 53 位有效位 —— 61 位的大整数会被【静默截断】，
签名全错，但程序一声不响跑完。
⟹ 解法：两边都显式写 dtype=np.uint64，模数也写成 np.uint64(...)。

② 用 (1<<61)-1 这个梅森质数 + 向量化
它是数学上的常见选择，但 2^61 级的数相乘会【溢出 uint64】。
⟹ 解法：要么像上面一样把 shingle 哈希压到 32 位、模数取 < 2^32 的质数
（乘积 < 2^64，刚好安全）；
要么用 Python 大整数逐个算（正确但慢几十倍）。
```

✅ 我把上面这段代码跑过一遍自检：两段 200 词、真实 Jaccard = 0.661 的文本，k=128 估出 0.656，落在 1 个标准差（0.042）之内。

# ---- 建 LSH 索引 ----
buckets = [defaultdict(list) for _ in range(B)]
sigs = {}
for i, doc in enumerate(docs):
    sig = minhash(doc["text"])
    if sig is None:
        continue
    sigs[i] = sig
    for b in range(B):
        band = sig[b*R:(b+1)*R].tobytes()      # ★ 8 个数拼成 key
        buckets[b][hashlib.blake2b(band, digest_size=16).digest()].append(i)

# ---- 收候选对 → 并查集聚类 → 每簇留一篇 ----
parent = list(range(len(docs)))
def find(x):
    while parent[x] != x:
        parent[x] = parent[parent[x]]; x = parent[x]
    return x
def union(a, b):
    ra, rb = find(a), find(b)
    if ra != rb: parent[max(ra, rb)] = min(ra, rb)

for b in range(B):
    for bucket in buckets[b].values():
        for j in bucket[1:]:
            union(bucket[0], j)               # ★ 同桶即认为重复（没做真实 Jaccard 验证）

keep_ids = {find(i) for i in sigs}            # 每个连通分量留一个代表

⚠️ 一个真实的工程陷阱：连通分量会"串联"。
A 和 B 相似、B 和 C 相似，但 A 和 C 可能完全不像。用并查集会把 A、B、C 并成一簇只留一篇。
在超大规模上这会形成巨型连通分量（几百万篇被并成一簇），删得过狠。
缓解手段：① 在簇内做一次真实 Jaccard 验证再合并（★ 也就是上面代码省掉的那一步） ② 限制簇的最大规模 ③ 改用"只删和代表元相似的"而非传递闭包。

★ 精确去重 vs 模糊去重：代价对照

① 精确去重（哈希 / Bloom） ② 模糊去重（MinHash + LSH）
判据 整篇字节级一致 Jaccard ≥ 阈值（典型 0.7~0.8）
每篇的计算量 1 次哈希 切 shingle + k 次哈希取 min（★ 本章开头估的 ~1 ms，比精确去重贵约 100 倍）
每篇的存储 8~32 字节 k 个整数，k=128 时 512 字节（★ 贵 16~64 倍）
额外的索引结构 无 b 张哈希表（b=16）
候选验证阶段 无 ★ 有，而且常常是真正的瓶颈（见上面"涌入"那段）
能并行吗 ✅ 完美并行（按哈希前缀分桶） 签名阶段完美并行；★ 分桶和聚类阶段要全局 shuffle，是大规模下最难的工程部分
抓到什么 转载、跨快照重复 ＋ 模板页、加广告的转载、改几个词的洗稿
误删风险 极低（Bloom 的假阳性可算，见 6.4） ⚠️ 中等：阈值偏低 + 并查集传递闭包 → 巨型簇，可能删掉大量不相似文档
调的旋钮 几乎没有（只有 Bloom 的 m/n） ⚠️ 四个：n-gram 的 n、k、b、r —— 每个都会显著改变结果
什么时候做 ★ 最先做，先把量砍下来 紧随其后
省不省得掉 不能省（最便宜、收益确凿） ★ 不能省（这是去重收益的主要来源）

★ 一句话总结这张表：精确去重几乎是免费的、无旋钮的、必做的；模糊去重贵 100 倍、有四个旋钮、而且工程难点全在"候选对验证"和"全局 shuffle"这两处——不在算法本身。初学者容易把时间花在理解 MinHash 上，而真实项目里 90% 的调试时间花在后面那两处。

6.6 ③ 子串去重：后缀数组

MinHash 是整篇判断。但有一种重复它抓不到：

文档 A：8000 词的技术博客  +  末尾 500 词的开源许可证
文档 B：3000 词的项目说明  +  末尾 500 词的【同一份许可证】

Jaccard 很低（内容主体完全不同）→ MinHash 判为"不重复" → 两篇都留
★ 但那 500 词的许可证，在整个语料里出现了上百万次

✅ Lee et al. 的 ExactSubstr 就是解决这个的：找出所有出现超过一次、长度 ≥ 50 token 的子串，把它们删掉（删的是片段，不是文档）。

⚠️ 口径提醒（和 6.1 节呼应）：因为它不整篇删除任何文档，所以"它删了百分之多少的文档"恒等于 0。它的留存率只能按 token 数报——这就是论文 Table 2 和 Table 3 分母不同的根本原因，不是作者随意选的。

后缀数组：怎么在近似线性的时间里找出所有重复子串

把整个语料拼成一个巨大的字符串 S（长度 n = 几万亿）

后缀数组 SA = 把 S 的所有 n 个后缀【按字典序排好】后的起始位置列表

例：S = "banana"
    所有后缀：          排序后：              SA
      0: banana           5: a                [5,
      1: anana            3: ana               3,
      2: nana             1: anana             1,
      3: ana              0: banana            0,
      4: na               4: na                4,
      5: a                2: nana              2]

★★ 关键性质：如果两个后缀有很长的公共前缀，它们在排序后【必然相邻】
   → 所以只要扫一遍相邻对，算它们的最长公共前缀（LCP = Longest Common Prefix），
     LCP ≥ 50 的地方就是一个重复子串！
   → ★ 从"两两比较 O(n²)" 变成"排一次序 + 扫一遍"

# 概念演示（真实实现要用并行后缀数组构造，见论文开源代码）
def find_dup_substrings(S, min_len=50):
    n = len(S)
    SA = sorted(range(n), key=lambda i: S[i:])     # ⚠️ 这样排是 O(n² log n)，仅用于演示
    dups = []
    for i in range(n - 1):
        a, b = SA[i], SA[i+1]
        l = 0
        while a+l < n and b+l < n and S[a+l] == S[b+l]:
            l += 1
        if l >= min_len:
            dups.append((a, l))                     # 位置 a 起 l 个字符是重复的
    return dups

✅ 论文的工程做法：并行构造 —— 切成 K 块各自建部分后缀数组，再并行归并。开源在 google-research/deduplicate-text-datasets。

⚠️ 代价提示（我的量级估算，不是论文数字）：后缀数组每个位置要存一个整数指针，用 int64 就是 8 字节 / 输入字节；加上 LCP 数组和中间结果，实践中常说 8~12 倍于原文的内存或磁盘。这是它比 MinHash 贵得多的根本原因——MinHash 每篇只要 512 字节，后缀数组要 8 倍全文。

★ 还有一个由 6.1 节 LM1B 那一行推出的实用结论：它对短文档完全无效。 最小匹配长度是 50 token，而 ✅ 论文报告 LM1B 有 90% 的文档不到 50 token——这些文档连参与匹配的资格都没有，所以 LM1B 上只删掉了 0.76% 的 token。如果你的语料以短文本为主（问答、评论、标题），别把算力花在这一步。

6.7 ④ 语义去重：SemDeDup

前三种全是字面匹配。但这两篇怎么办？

A: "线粒体是细胞的能量工厂，负责通过氧化磷酸化产生 ATP。"
B: "细胞里制造能量的细胞器叫线粒体，它靠氧化磷酸化合成 ATP。"

Jaccard ≈ 0.1（几乎没有共同 5-gram）→ 前三种方法全部判"不重复"
★ 但它们承载的信息完全一样

✅ SemDeDup（arXiv:2303.09540，Abbas / Tirumala / Simig / Ganguli / Morcos，Meta AI，2023-03）：

① 用一个预训练模型把每篇文档编码成一个向量
   ✅ 论文：图文对用 CLIP，纯文本用 OPT 的 embedding
② k-means 把所有向量聚成很多簇
   ★ 为什么要聚类？因为不能两两算余弦相似度（还是 O(n²)）
     聚类把比较限制在【簇内】，这是和 LSH 一样的"先分桶"思路
③ 簇内两两算余弦相似度，超过阈值的只留一个
   ✅ 留哪个？论文的策略是留【离簇中心最远】的那个（保多样性）

✅ 论文报告的效果（我从 papers/SemDeDup-Semantic-Deduplication-arXiv-2303.09540.pdf 核对过原文）：

数据集 ✅ 论文原话的内容 ★ 换算成不含歧义的说法
LAION-440M（图文对） 删掉 50% 的数据而性能损失极小；"training speed is twice as fast and completes in half the time" 训练时间变成原来的 1/2 = 加速 2 倍 = 时间减少 50%
分布外（out-of-distribution） 性能反而提升 —
C4（纯文本） 优于此前的 SOTA 去重方法，并带来 15% 的效率收益，有时性能还更好 时间减少约 15%，即加速约 1.18 倍

6.8 ★ 一个反直觉的发现：去重不是越彻底越好

✅ FineWeb 论文报告了一个重要的负面结果。✅ 下面的数字我从 papers/FineWeb-Decanting-the-Web-arXiv-2406.17557.pdf 逐句核对过：

做法 去重后剩下的 token 效果
全局 MinHash（96 个快照放在一起，按时间从新到旧迭代去重） 4 T ⚠️ 抽 350 B 训消融模型，相比完全不去重几乎没有提升，远低于 RefinedWeb
★ 按单个快照各自独立去重 20 T ★ 明显更好，这成了 FineWeb 的最终方案 
★ 先把这组数字的说法摆正（接上一节的 ②）：
    20 T → 4 T 是【压缩到 20%】，也就是【压缩 5 倍】。
    ⚠️ 不要写成"压缩了 20%"（那意思是只删掉 20%，完全相反）。

✅ 论文还做了一个关键的追加实验，直接解释了为什么：

拿最老的那个快照（2013-48）切成两份，各训一个模型：
   (a) 全局去重后【留下来】的那部分         ≈ 31 B token（约占原始的 10%）
   (b) 全局去重时【被删掉】的那部分，
       再单独做一次独立去重后             ≈ 171 B token（来自被删的约 460 B）

✅ 结果：(a) 留下来的那 10%，质量【比被删掉的那 90% 更差】。
✅ 论文还做了人工抽样确认，原文大意：
   "留下来的数据里，广告、不连贯的关键词堆砌、排版糟糕的文本都更多。"

★★ 为什么会这样？ ✅ 论文给的机制是：全局去重把"在多个快照里反复出现的页面"砍到只剩一份，而一个页面能被反复抓到，本身就是它比较重要 / 质量较高的信号。砍完之后剩下的，反而富集了只出现过一次的低质量页面。论文把这个现象叫 "global deduplication upsamples lower-quality data"（全局去重相当于给低质数据做了上采样）。

⚠️ 注意这里的"越老的快照损失越大"：✅ 论文明确写了，应用到最老的快照时，这一步删掉了高达 90% 的数据——因为它要和后面 95 个快照全部比一遍。所以这个坑的严重程度和快照数量正相关，小规模实验上根本看不出来。

✅ 论文顺带报告，几种行级去重变体（删重复行、删重复的 3 行跨段等，分别删掉 77.8% / 85% / 80.9% 的 token）全都比"只做按快照独立 MinHash"更差，所以 FineWeb 最终没有加任何额外去重。

★★ 这个结论值得记住，因为它违反了"去重越干净越好"的朴素直觉。
⚠️ 我的推论：这也说明"重复次数"本身是一个可用的质量信号——但它和"重复浪费预算"是一对张力，怎么权衡目前没有定论。

相关的另一条：精选高质量语料（Wiki、教科书）常常被【故意重复采样】2~5 次（见 10 章）。所以"重复"在流水线里同时是要消除的东西和要制造的东西——取决于重复的是什么。

6.10 小结

① ★★ 去重率的分母必须先说清：文档数 / 字节数 / token 数，三者差好几倍
   ✅ Lee et al. 同一篇论文里：
      NearDup 删掉 C4 的 3.04%    ← 分母是【文档数】
      ExactSubstr 删掉 C4 的 7.18% ← 分母是【token 数】
   ⟹ 这两个数【不能比】。ExactSubstr 根本不整篇删文档，
      所以它"删掉多少文档"恒为 0，只能按 token 报。

② ★ 去重是全流水线【收益最确凿】的一步
   ✅ Lee et al. 2107.06499（全部核对过原文）：
      · C4 里一个 61 词的句子逐字重复了 61036 次
      · 无提示生成的逐字复制率 1.926% → 0.189%（★ 降到 1/10，不是"降低 10%"）
      · 验证集有 >4% 能在训练集找到（C4 4.60%、RealNews 14.35%）
      · ★ Wiki-40B 上 ExactSubstr 让 1.5B 模型困惑度降了近 3 个点
        （绝对值降 3，不是降 3%），尽管数据【变少了】

③ ★★ 四个粒度，互补不替代：
   ① 精确    整篇哈希          → 转载、跨快照        最便宜
   ② 近似    MinHash + LSH     → 模板页、洗稿  ★主力
   ③ 子串    后缀数组          → 长引用、许可证片段  贵，★ 对短文本无效
   ④ 语义    embedding + 聚类  → 翻译、改写          最贵、最易删错

④ 精确去重真正的难点是内存，★ 教科书数字会骗你：
   100 亿篇 × 32 字节 = 320 GB（十进制；= 298 GiB）
   ⚠️ 但放进 Python set 实际要约 780 GB（对象头 + 哈希表槽位，2.4 倍）
   Bloom filter：每元素 10 位 → 假阳性 0.82%，只要 12.5 GB
   ⚠️ 但 0.82% × 100 亿 = 8200 万篇被误删 —— 把比例换算成绝对值再决定

⑤ MinHash 的核心定理：P[min h(A) = min h(B)] = J(A,B)
   ★ 6.5 节用 6 个 shingle 手算过一遍：【签名相等 ⟺ 并集里 h 最小的元素在交集里】
     枚举 6! = 720 种排队顺序，恰好 240 种满足 ⟹ 240/720 = 1/3 = J（精确相等）
   ⟹ 用 k 个哈希数相等的位数，就估出了 Jaccard
   ⚠️ 误差是二项比例的标准差 √(J(1−J)/k) ≤ 1/(2√k)：k=128 → ±0.044（1σ）
      ★ 流传的"1/√k = ±0.09"其实是 2σ（95% 区间半宽），别当标准差用

⑥ LSH 分带：k 个签名切成 b 带 × r 行，任一带全同即候选对
   P(s) = 1 − (1−s^r)^b
   ✅ k=128, b=16, r=8 实算：s=0.5 → 0.061；s=0.7 → 0.613；
      s=0.8 → 0.947；s=0.9 → 1.000
   ⚠️ "阈值 ≈ (1/b)^(1/r)" 这个口诀指的是【拐点】，该点 P ≈ 0.63（趋向 1−1/e），
      ★【不是 0.5】。真正的半数点 s = (1 − 0.5^(1/b))^(1/r)，b=16,r=8 时是 0.674
   ★ 选 16×8 的真实理由：J=0.8 召回 0.947，而 J=0.5 只涌入 0.061 ——
     候选对要逐对验证，低相似度那一大坨涌进来就算不完了
   ★ b 大 → 激进；r 大 → 保守；k 大 → 曲线更陡（代价是签名更长）

⑦ 后缀数组：拼成一个长串排序所有后缀，
   ★ 公共前缀长的后缀排完必相邻 → 扫一遍相邻对就找出所有重复子串
   ⚠️ 代价约 8~12 倍原文的内存；对 < 50 token 的短文档完全无效

⑧ ★★ 两个反直觉的点：
   ✅ FineWeb：全局跨快照去重（剩 4 T）【比】按快照单独去重（剩 20 T）更差
      —— 20 T → 4 T 是"压缩到 20%"/"压缩 5 倍"，★ 不是"压缩了 20%"
      ✅ 追加实验直接证明：留下来的那 10%，质量比被删掉的 90% 更差
      ✅ 机制：被反复抓到本身是质量信号，全局去重等于给低质数据上采样
   而精选语料反而要【故意重复采样】2~5 次
   → "重复"在流水线里同时是要消除的和要制造的东西

⑨ 三组极易混的说法（6.7 节）：
   "时间减半" = "加速 2 倍" = "时间减少 50%"
   ⚠️ 但 "加速 50%" 只意味着时间减少 33.3% —— 差了近一倍
   "压缩到 20%" = "压缩 5 倍" ≠ "压缩了 20%"

⑩ 工程陷阱：
   · 并查集会把 A~B~C 串成巨型连通分量，删得过狠
     → 簇内做真实 Jaccard 验证 / 限制簇规模 / 不做传递闭包
   · ⚠️ numpy 里 int64 × uint64 会被静默提升成 float64 → 签名全错且不报错
   · ⚠️ 梅森质数 (1<<61)−1 配向量化会溢出 uint64 → 改用 < 2^32 的质数
