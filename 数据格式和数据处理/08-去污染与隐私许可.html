08 · ⭐ 去污染、隐私与许可

前面三章删数据，理由都是"这数据不好"。这一章删数据，理由是"这数据好，但不能要"。

★ 这是唯一一章里，删错了不会让模型变差，但会让你的评测分数变成废纸（去污染），或者让你上不了线（隐私与许可）。

⚠️ 本章数字口径（与 05 章、06 章 一致）：容量一律十进制（1 GB = 10⁹ 字节、1 TB = 10¹² 字节；⚠️ GB 与 GiB 差 7.4%、TB 与 TiB 差 10%）。凡出现百分比，★ 一定写清分母是文档篇数、字节数还是 token 数——06 章 §6.1 已经用 Lee et al. 的两张表钉死过这件事：同一篇论文里 NearDup 删掉 C4 的 3.04%（分母 = 文档数）、ExactSubstr 删掉 7.18%（分母 = token 数），这两个数不可比。本章的污染率和 PII 命中率同样如此。

8.1 这一章站在哪个位置：建库侧 vs 评测侧

先把分工说清楚，否则你会以为本章和隔壁的评测教程重复了。

你现在站在【建库侧】：
   手上有训练语料（几百 TB 的文本），★ 但模型【还没有训】。
   ⟹ 你能做的事：把评测题从语料里删掉，让分数一开始就是干净的。

隔壁 [harness 评测框架 / 评测入门 06 数据污染] 站在【评测侧】：
   模型已经训好了，★ 甚至是别人家的闭源模型，你只能调 API。
   ⟹ 它能做的事：判断"这个分数里有多少是背出来的"。

⟹ ★★ 同一个问题、两个位置，能用的工具【完全不同】。
   本节末尾那张表就是这条分界线。

📘 评测侧那一章在这里：../harness评测框架/评测入门/06-数据污染.md。本章不重复它的内容——它的 §6.3.2 已经逐步推演过"改一个词就能绕过 n-gram"，§6.3.2b 讲过中文和短题面的结构性盲区，§6.3.3 给了五种检测法的假阳假阴全表。本章只写建库侧：你手上有什么、能做什么、代价是多少。

一句话说清污染是什么

你训练时用了 100 T token 的网页数据。
而 MMLU、GSM8K、HumanEval 这些评测题，★ 全都公开挂在网上。
   （MMLU = Massive Multitask Language Understanding，57 学科选择题
     GSM8K = Grade School Math 8K，小学应用题 8000 道
     HumanEval = OpenAI 的 164 道 Python 编程题）
   ⟹ 它们大概率【已经在你的训练数据里了】

于是评测的时候：
   模型不是在"推理"，而是在【回忆】它见过的答案
   ⟹ 分数虚高，而且【你完全不知道虚高了多少】

✅ 这不是理论担忧。 06 章 §6.1 引的 Lee et al.（arXiv:2107.06499）在论文 Table 2 里报了精确值：

语料 验证集中能在训练集里找到的占比 分母
C4 ✅ 4.60% 文档（样本）数
RealNews ✅ 14.35% 文档（样本）数

⚠️ 口径必须说清：这两个数来自论文 Table 2，判据是 NearDup（近似文档去重），分母是样本数。论文正文里常被引用的那句话是 "more than 4% of examples"，✅ 精确到小数就是上表这两个值。⚠️ 同一篇论文 Table 3 的 ExactSubstr 口径下，C4 验证集能在训练集找到的只有 1.38%，分母是 token 数——同一件事两个口径差 3.3 倍。所以"验证集有 4% 被污染"这句话，必须跟上"按什么算的"。

★★ 为什么说它比"数据脏"更危险？

数据脏     ⟹ 模型变差 ⟹ ★ 你的评测分【会告诉你】
数据污染   ⟹ 模型没变好，但评测分【涨了】
           ⟹ ★★ 你的仪表盘在骗你，而你无从察觉

更糟的是：你会据此做出错误决策——
  "这个数据配方 MMLU 涨了 3 分，采纳！"
  ⚠️ 实际上只是这个配方多混进了一些 MMLU 的题。

★ 这正是 07 章 §7.6 列的风险之一：一个只会让分数涨、不会让分数跌的 bug，在数据流水线里可以存活好几个月。

三种污染，一种比一种难查

① 逐字污染（verbatim）
   训练数据里出现了一模一样的题目和答案
   ⟹ ★ 可以查，本章 8.2 讲怎么查

② 改写污染（paraphrased）
   题目被翻译成中文、被改写成另一种问法后出现在训练集里
   ⟹ ⚠️ n-gram 匹配【完全查不到】，需要语义匹配

③ ★ 间接污染（indirect / 分布污染）
   训练数据里没有原题，但有大量【专门针对这个评测写的题解和练习题】
   （比如各种 "MMLU 备考题库"、"GSM8K 风格数学题集"）
   ⟹ ⚠️ 这个几乎【无法定义边界】：
      "刷了很多同类型的题"和"学会了这个能力"到底怎么区分？
   ⟹ ★★ 而 [07 章] §7.4 讲的质量分类器，会【主动把这类内容筛进来】
      —— 因为它们"长得像好数据"：有题有解、结构工整、知识密度高。

⚠️ 我的判断（不是论文结论）：现在公开报告的评测分数，基本都受 ② 和 ③ 不同程度的影响，只是没人能量化。这也是为什么业界越来越依赖私有测试集、发布日期晚于模型训练截止日的新题（LiveBench / LiveCodeBench 这类做法）和人工对战评测。✅ 这三条缓解手段的代价对照，harness 06 章 §6.4 有一张完整的表。

⑤ 黑盒行为测试（扰动 + 时间切分） ❌ 不能 ★ 要能调用模型 不删语料 能看出污染的整体规模，⚠️ 定位不到是哪一条 
★★★ 把这张表压成一句话：

   ② ④ ⑤ 全都要【先有一个训好的模型】。
   ⟹ 它们在你这个阶段【物理上做不了】——那是评测侧的事。

   ⟹ 🔑 所以建库侧的去污染工作，实际上只有两件：
        ① 把评测集切成 n-gram，扫一遍语料；
        ③ 见到 canary 串就整文件删掉。

   ⚠️ 而这两件事【都不能保证干净】：
        ① 对改写和翻译无效（三种污染里的 ② ③ 它都抓不到）；
        ③ 完全依赖评测集作者事先埋了串。
   ⟹ ★ 所以"我们做了去污染"这句话的真实含义是：
        "我们删掉了逐字照抄、且评测集我们当时知道的那部分。"

8.2 ★★ 怎么做去污染：n-gram 匹配

最标准的做法，✅ GPT-3 论文用的是 13-gram（n-gram = 连续 n 个词组成的片段）。整个流程只有四步：

① 把所有评测集（MMLU / GSM8K / HumanEval / MATH / C-Eval / ...）
   的【题目和答案】收集起来
   │
② 归一化（转小写、去标点、压空白），切成 n-gram
   │
③ 建一个哈希集合   ← ★ 只存 8 字节哈希，不存原文（成本见 8.2 末）
   │
④ 扫训练语料：任何文档只要撞上【一个】n-gram
   ⟹ 丢掉（丢整篇还是只丢那一段，是一个要专门决定的事，见下）

一段能跑的实现（★ 以及一个必须修掉的 bug）

import hashlib, re

N = 13

def normalize(t: str) -> str:
    t = t.lower()
    t = re.sub(r"[^\w\s]", " ", t)           # 去标点
    return re.sub(r"\s+", " ", t).strip()    # 压空白

def _h(s: str) -> bytes:
    # ★★ 必须用【稳定】哈希。绝不能用内置 hash()，理由见下面那一段。
    return hashlib.blake2b(s.encode("utf-8"), digest_size=8).digest()

def ngrams(text: str, n: int = N):
    w = normalize(text).split()
    for i in range(len(w) - n + 1):
        yield _h(" ".join(w[i:i+n]))

def build_eval_ngrams(eval_texts, n: int = N) -> set:
    s = set()
    for t in eval_texts:
        s.update(ngrams(t, n))               # 只存哈希，省内存
    return s

def is_contaminated(text: str, eval_ngrams: set, n: int = N) -> bool:
    return any(g in eval_ngrams for g in ngrams(text, n))

⚠️⚠️⚠️ 这一段的重点不是算法，是那个 _h。本教程此前的版本在这里写的是内置 hash()，那是一个会静默出错的 bug。 ✅ 我在本机跑了一遍：

$ for i in 1 2 3; do python3 -c "print(hash('at sixty kilometres per hour'))"; done
-8851492295212081839
490494123140038673
1662192923934921210

$ for i in 1 2; do python3 -c \
    "import hashlib;print(hashlib.blake2b(b'at sixty kilometres per hour',digest_size=8).hexdigest())"; done
077f3b6ad02cf055
077f3b6ad02cf055

★ 同一个字符串，三个进程，内置 hash() 给出【三个不同的值】。

原因：Python 3.3 起（PEP 456），str 和 bytes 的 hash()
      带一个【进程级随机盐】，由环境变量 PYTHONHASHSEED 控制。
      这是为了防哈希碰撞拒绝服务攻击，是有意设计。

⚠️⚠️ 它为什么是"静默"出错的：
   建集合跑在进程 A（比如一个 build 脚本），
   扫语料跑在进程 B（比如 Spark / Ray / multiprocessing 的 worker），
   ⟹ 进程 B 算出的哈希【永远不可能】出现在进程 A 建的集合里，
   ⟹ is_contaminated() 恒返回 False，
   ⟹ 报表上写着【污染率 0.00%】，而且不报任何错。

★★★ 而 0.00% 看起来像好消息 —— 这就是它能活几个月的原因。
   （⟹ 完全对应 8.1 那条：只会让指标变好看的 bug 最难发现。）

★ 一条可以直接抄的自检：把评测集的 n-gram 集合落盘，然后另起一个进程把其中随机 100 条读出来查一遍，必须 100 条全中。⚠️ 这个检查只要 5 行代码，却能挡住上面这整类 bug。同样的要求也适用于 17 章 Step 6 那段流水线代码——它直接调用的就是本节这两个函数。

★★★ n 怎么选：一个能自己验算的推演

教科书只会说"n 小了误杀、n 大了漏检"。下面把它算出来。✅ 下面每一个数字我都在本机跑过（脚本就是上面那段代码）。

测试题（24 个词）：

A train leaves the station at nine in the morning and travels at
sixty kilometres per hour for three hours before stopping for lunch

三篇训练文档，代表三种真实情况：

文档 内容 它到底是不是污染
D1 论坛帖子原文转载了整道题，还附了答案 ✅ 是真污染，必须删
D2 一篇热身题，只抄了前 10 个词（"A train leaves the station at nine in the morning."） ❌ 不是污染，删掉就是误杀
D3 一篇讲城际列车的文章，含常见短语 "at sixty kilometres per hour for three hours" ❌ 不是污染，这是英语里的大路话

✅ 实测命中数（命中 = 该文档的 n-gram 里有多少个落在评测集的哈希集合里）：

n 评测题能切出的窗口数 D1（真污染） D2（只抄 10 词） D3（含常见短语） 判定结果
5 20 20 6 4 ⚠️ 三篇全判污染 —— D2、D3 都是误杀
8 17 17 3 1 ⚠️ 仍然三篇全判污染
13 12 12 0 0 ✅ 只有 D1 被判 —— 这就是 13 的理由
20 5 5 0 0 ✅ 也只判 D1，⚠️ 但窗口数掉到 5 
★ 这张表的每一个数都能用一个减法验算出来：
   一段 L 个词的文本，能切出的 n-gram 窗口数 = max(0, L − n + 1)

   D2 只抄了 10 个词 ⟹ n=13 时 10 − 13 + 1 = −2 ⟹ 0 个窗口
   D3 的常见短语 8 个词 ⟹ n=13 时 8 − 13 + 1 = −4 ⟹ 0 个窗口
   ⟹ 🔑 n=13 能挡住它们，不是因为算法聪明，
        ★★ 而是因为【它们根本凑不出 13 个连续词的重合】。

⚠️ 而这也立刻说明了 n 大的代价：
   n=20 时评测题自己只剩 5 个窗口（24 − 20 + 1）。
   ⟹ 改掉题目里任意一个词，就会打断它所在的全部 20 个窗口，
      5 个窗口里能被打断好几个 ⟹ ★ 抗改写能力急剧下降。
   ⟹ n=21 时这道 24 词的题只剩 4 个窗口；n=25 时【一个都没有】。

🔑 所以 8~13 这个区间不是魔法数字，是一个夹出来的结果：
     下界由【常见短语有多长】定（英语大路话常在 5~8 个词）
     上界由【题目有多长】定（题目越短，n 必须越小才有窗口）
⚠️ 而这意味着：各家取不同的 n，报出来的"已去污染"根本不是一回事，
   ★ 而且【短题目的评测集，天生比长题目的更难去污染】。

⚠️⚠️ 中文的结构性盲区：同一道题，两种切分口径，一个能检一个彻底失效

上面整套推演有一个隐含前提：normalize(t).split() 能把文本切成词。 对英文成立，★ 对中文完全不成立——中文不打空格。

✅ 拿一道中文小学应用题实测（小明有十二盒饼干，每盒六块，一共多少块？，去掉标点后 17 个汉字）：

切分口径 切出多少个单元 13-gram 窗口数 = max(0, L − 13 + 1) 结果
按空白切（split()，即上面代码的默认行为） 1 0 ⚠️⚠️ 整道题检不出任何东西
按字切（每个汉字一个单元） 17 5 ✅ 能检
按词切（分词后：小明 / 有 / 十二 / 盒 / 饼干 / 每 / 盒 / 六 / 块 / 一共 / 多少 / 块） 12 0 ⚠️ 完全检不出 
★★★ 请把这张表读两遍：【同一道题，三种口径，两种结论。】

  按空白切 ⟹ 0 个窗口 ⟹ 返回"干净"
  按词切   ⟹ 0 个窗口 ⟹ 返回"干净"
  按字切   ⟹ 5 个窗口 ⟹ 能查出来

⟹ 🔑 对建库侧来说，这【不是一个 bug 报告，是一个你必须自己做的决定】：
     你要先选定中文的切分口径，★ 然后把 n 跟着改掉。
  ⚠️ 直接把英文那套（空白切 + n=13）套到中文语料上，
     ⟹ 它不是"效果差"，是【一个窗口都产生不了】，
     ⟹ 于是对每一道中文题都返回"干净"，污染率报 0.00%。
     ★★ 又是一个"只会让指标变好看"的静默失败。

★ 一个能用的中文起点（⚠️ 我的建议，不是论文结论）：
     按【字】切，n 取 20~30 个汉字。
  理由：13 个汉字约等于 6~9 个中文词，相当于英文的 n=6~9，偏误杀；
        而 20~30 个汉字约 10~15 个词，量级上才和英文 n=13 可比。
  ⚠️ 代价：短题面（像"中国的首都是哪里"7 个字）照样一个窗口都没有。

⚠️ 评测侧看这件事是另一个角度——"看到'我们做了 n-gram 去污染'这句话，对 C-Eval / CMMLU 这类中文集它等于什么都没做"。✅ 那一段的完整论证在 harness 06 章 §6.3.2b。本章关心的是你这一侧的动作：换切分、改 n、并且把中文和英文的污染率分开报。★ 如果两者混在一个数字里，中文那部分的 0% 会被英文的几个百分点稀释掉，你永远看不出中文根本没被检查过。

★★ 丢整篇还是只丢命中的那一段：一个 615 比 1 的账

原始流程的第 ④ 步写的是"整篇丢掉"。先算一下这件事有多贵：

一篇 8000 词的优质长文（比如一篇完整的技术教程），
   里面有【一段 13 个词】恰好和某道评测题重合。

整篇丢：损失 8000 词
只丢命中段落（假设那段 13 词所在的段落约 13 词）：损失 13 词

⟹ 损失比 = 8000 ÷ 13 ≈ 615 : 1

★★ 也就是说，为了删掉 13 个有问题的词，你扔掉了 615 倍的好内容。
⚠️ 而且这不是罕见情况：n=13 的命中【本来就应该是稀疏的】
   —— 一篇长文越长，它凑出某个 13-gram 的机会就越多（见 8.2 末的窗口数：
      8000 词的文档有 7988 个窗口，而一篇 500 词的只有 488 个）。
   ⟹ 🔑 整篇丢这个策略，【系统性地偏向于删掉长文档】，
        而长文档恰好是 [13 章] 的打包和 [19 章] §19.9 的长上下文最缺的那种数据。
策略 删掉多少 实现难度 ⚠️ 风险
整篇丢 命中文档的全部内容 最简单，一个布尔判断 ⚠️ 损失比可达 615 : 1；系统性偏向删长文
只丢命中的段落 命中段落 中等：要按段落切、按段落建索引 ⚠️ 文档被切开后语义断裂，上下文不连贯
只丢命中的句子 / 把那一段改写 最少 ★ 最高 ⚠️ 改写本身要调模型，成本量级完全不同

★ 业界的实际做法是"两级都做"。 ✅ 06 章 §6.9 那张表里 Dolma 的 Bloom filter 就同时跑文档级和段落级（✅ 段落级删掉约 70% 的段落）。既然去重已经建好了段落级的索引，去污染就应该复用它——这正好是下一段要讲的事。

★★★ 去重和去污染在工程上是同一套机制

这是 ✅ Dolma（arXiv:2402.00159）披露的一个很漂亮的工程事实。✅ 我从 papers/Dolma-Open-Corpus-of-Three-Trillion-Tokens-arXiv-2402.00159.pdf 核对过原文：

✅ "We also implement a Bloom filter (Bloom, 1970) compatible with our mixer which enables linear-time probabilistic detection of duplicates. We can repurpose this for test set decontamination by first seeding the Bloom filter with test examples, then flagging any detected duplicates when mixing the pre-training data."

★ 把这句话翻成大白话：

  去重在问：  "这段文字，我【以前见过】吗？"
  去污染在问："这段文字，在【评测集】里出现过吗？"

  ⟹ 🔑 这是【同一个问题】，只是"见过的东西"那个集合不一样：
       去重  ⟹ 集合 = 已经处理过的语料
       去污染 ⟹ 集合 = 评测集（★ 一开始就预先塞进去，叫 "seeding"）

⟹ ★★ 工程含义：你【不需要】为去污染单独写一套系统。
     把评测集先 seed 进去重用的那个 Bloom filter，
     再在混合（mix）训练数据时把命中的标出来，就做完了。
  ★ 成本几乎为零：同一个数据结构、同一遍扫描、同一套段落级切分。

⚠️ 但要注意 Bloom filter 带来的一个口径问题：Bloom filter 有假阳性（06 章 §6.4 算过：每元素 10 位时约 0.82%），⟹ 它会把一些干净文档误报成污染。在去重场景里，0.82% 的误删是可以接受的代价；⚠️ 在去污染场景里，这 0.82% 会直接变成你报出来的"污染率"的底噪。★ 如果你测出来的污染率本身只有 0.1%，那你测到的东西基本全是 Bloom filter 的假阳性。🔑 报污染率之前，先算一遍你的假阳性率，确认信号比底噪大。

★★ 一个绕不过去的时序问题

★★ 评测集是【不断增加】的。

  你 2024 年训模型时做了去污染，2025 年出了一个新评测集 ——
  它的题目可能早就在你 2024 年抓的那批网页里了，
  而你 2024 年做去污染时，★ 根本不知道这个评测集的存在。

⟹ ★★★ "已去污染"这句话只对【当时已知的评测集】成立，
     对未来的评测集【完全不成立】，而且永远补不回来
     —— 模型已经训完了。

建库侧只有两个动作能对冲这件事（⚠️ 我的整理）：

动作 做法 ★ 它能换到什么 ⚠️ 它换不到什么
① 存住 n-gram 索引，而不是只存结论 把语料的 n-gram 索引落盘并长期保留，而不是扫完就扔 ★★ 以后出了新评测集，可以事后回答"这批题在不在我的训练数据里" ⚠️ 不能把模型里已经学到的东西取出来；只能告诉你污染了多少
② canary string（金丝雀字符串） 评测集作者在文件里埋一个独一无二的 GUID 串；★ 你这一侧的责任是见到这个串就把整个文件删掉 ★ 一条字符串匹配，近乎免费，且跨语言、抗改写（串本身不会被翻译） ⚠️ 完全依赖评测集作者事先埋了；⚠️ 清洗流程（05 章的规则）常把这种"怪行"删掉，串没了、题留下了

★ ① 那一行值得单独说，因为它常被省掉。✅ Dolma 的 PDF 里提到它的去污染是在 mixer 阶段做的——也就是说索引是流水线的一个持久产物，不是临时变量。★ 这条和 8.5 的数据溯源是同一个思路：可观测性要在事故发生之前就留下来。 ⚠️ 代价是存储：按 8.2 末的算法，1e10 篇语料的全量 13-gram 索引是 4.88e12 个窗口 × 8 字节 ≈ 39 TB，⟹ 实践中一般只对抽样或只对最终入库的那部分建长期索引。

⚠️ ② 的 canary 串还有一个容易被忽略的坑：如果你不删文件、只删那一行串，你就把"这个文件被污染过"的唯一证据毁掉了，而题目还留在语料里。🔑 见到 canary 串，删文件，不要删串。

★★★ 成本账：去污染该排在流水线的哪一步

05 章 §5.1 定下了级联过滤（cascade）的原则：便宜的先跑，把量砍下来，贵的后跑。 那么去污染有多贵？分两头算，★ 结论会让人意外。

第一头：评测集侧的哈希集合有多大？（⚠️ 下面的规模假设是我的取值，不是某家的披露）

假设：30 万条评测样本（★ 把目前常用的几十个评测集全加起来，大致是这个量级）
      每条平均 120 个词 ⟹ 每条 120 − 13 + 1 = 108 个 13-gram 窗口

哈希集合元素数 = 300,000 × 108 = 3240 万个 13-gram
存法 每元素 总量 说明
扁平存 8 字节哈希（排序数组 / numpy / Bloom filter） 8 字节 ✅ 259 MB（= 247 MiB） ★ 一台笔记本随便装得下
Python set of int ⚠️ 实测约 66 字节 ⚠️ 2.14 GB（= 1.99 GiB） ★ 贵 8.2 倍 
⚠️ 那 66 字节是我在本机实测出来的，拆开看：
     sys.getsizeof(set) ÷ 元素数 ≈ 34 字节   ← 哈希表的槽位（含为控制装载率留的空槽）
   + 每个 64 位整数对象本身        32 字节   ← ★ Python 的 int 是堆上对象，不是 8 字节裸整数
   ───────────────────────────────────────
   ≈ 66 字节 / 元素

⚠️ 如果按进程 RSS 量，还会更高（实测约 114 字节/元素），
   因为 set 扩容时会反复重建哈希表、留下内存碎片。
⟹ ★ 口径说明：上表取的是"getsizeof + int 对象"这个可解释的口径。
     ⚠️ 三个口径（34 / 66 / 114 字节）差 3.4 倍，★ 报内存数字时必须说清量的是哪一个。
     （⟹ 和 [06 章](06-去重.md) §6.4 讲 Python set 开销时是同一个坑。）

🔑 第一头的结论：评测集侧【小到可以忽略】。 259 MB 意味着这个集合可以整个塞进每一个 worker 的内存，不需要任何分布式查询、不需要 Redis、不需要分片。★ 初学者容易把工程复杂度想象在这一头，而它根本不在这一头。

第二头：扫一遍训练语料要多久？

假设：1e10 篇文档（100 亿篇，和 [06 章] 的规模假设一致）
      每篇平均 500 个词

每篇的窗口数 = 500 − 13 + 1 = 488
总窗口数     = 1e10 × 488 = 4.88e12 个

每个窗口的成本 = 拼字符串 + 算一次 blake2b + 查一次哈希表
⚠️ 取 1 μs / 窗口（★ 我的量级估算，不是实测；Python 实现会更慢，
   Rust / C++ 实现可以做到几百纳秒）

单核耗时 = 4.88e12 × 1 μs = 4.88e6 秒 = 56.5 天
1000 核   = 4880 秒        = 1.36 小时
折算每篇  = 488 μs ≈ 0.5 毫秒

   ⟹ 按级联原则，它应该排在分类器【前面】。"

  ⟹ ★ 去污染是整条流水线里【最需要反复重跑】的那一步：

⚠️⚠️ 而一旦你改成"只丢命中的段落"（也就是 8.2 建议的那个 615 : 1 的优化），这个前提就没了。 挖掉一段会改变文档的长度、重复率、质量分——而这些正是 05 章 的规则和 07 章 的分类器赖以打分的输入。

  【整篇丢】 ⟹ 纯过滤器，顺序随便 ⟹ 放最后，重跑最便宜。

  【丢段落】 ⟹ 它改变文档内容，顺序【不可交换】：
      · 放在质量过滤【之后】：⚠️ 你打的质量分是基于"还没被挖段落"的
        那一版文档算的，挖完以后那个分数已经不成立了。
      · 放在质量过滤【之前】：★ 分数是基于最终文本算的，逻辑上更正确，
        ⚠️ 代价是要扫 4.3e8 篇而不是 2.58e8 篇（贵 1.7 倍）。
  ⟹ 🔑 我的建议：丢段落就放在质量过滤【之前】，多花那 1.7 倍。
     ★ 理由是它顺带修掉了一个很难发现的不一致——
       "入库文档的质量分，和它实际的文本不匹配"。

★ 还有第三个考虑，它建议把去污染和去重放在一起：8.2 末讲的 Dolma 做法——✅ 去污染复用去重的那个 Bloom filter，同一遍扫描、同一套段落切分，边际成本几乎为零。⟹ ⚠️ 这和"放最后"是一组真实的张力，没有唯一答案：

🔑 我的读法：第一遍建库跟去重合着做（省一遍扫描），同时把去污染保留成一个能独立重跑的步骤，因为你一定会重跑它。

8.3 ★★ 隐私：PII 的识别与处理

PII = Personally Identifiable Information（个人可识别信息），指能定位到具体某个人的信息。

典型的 PII：
   姓名、邮箱、手机号、身份证号、住址、
   银行卡号、社保号、车牌号、IP 地址、生物特征

★ 为什么在大模型场景下特别危险：
   模型会【逐字背下】训练数据
   （✅ [06 章] §6.1：不去重的 1.5B 模型，无提示生成的逐字复制率 1.926%）
   ⟹ 有人在论坛贴过自己的手机号 ⟹ 模型可能在对话里把它吐出来
   ⟹ ★★ 这已经不是"数据质量问题"，是【合规事故】
      —— 它不会让你的分数掉，它会让你的产品下线。

★★★ 一张对照表：哪类数据、什么风险、业界怎么处理、代价是什么

⚠️ "姓名"那一行是这张表里唯一没有好答案的，原因是：★ 正则和 NER 都无法区分公众人物和普通人。

"马云宣布……"        ⟹ 该留（公开的、与公共事务相关的）
"张三的电话是……"     ⟹ 该删

⟹ ⚠️ 两者在文本形式上【完全一样】：都是"中文姓名 + 谓语"。
⟹ ★ 所以实践中的妥协是：【不单独删姓名】，
     只删"姓名 + 联系方式【同时出现】"的那一段。
  🔑 也就是把判据从"出现了 PII"换成"出现了【可关联】的 PII 组合"
     —— 一个名字本身不能定位到人，名字加电话就能。

✅ Dolma 的真实做法：三类正则，两档阈值

这是目前披露最完整的一套开源语料 PII 处理方案。✅ 下面每一条我都从 papers/Dolma-Open-Corpus-of-Three-Trillion-Tokens-arXiv-2402.00159.pdf 核对过原文（正文"Filtering Personally Identifiable Information"一段，细节在论文附录 §I）：

★ 第一个决定：【不用模型，只用正则】

  ✅ 论文原文："Dolma's size makes it impractical to use model-based
     PII detectors like Presidio (Microsoft, 2018); instead, we rely on
     carefully-crafted regular expressions that sacrifice some accuracy
     for significant speed-up."
     （Presidio 是微软开源的 PII 检测工具，基于 NER 模型）

  ⟹ 🔑 翻译：★★ 在 3 T token 的规模上，"准确"输给了"跑得完"。
     这是本教程反复出现的那个权衡（[05 章] §5.1 的级联原则）在 PII 上的又一次出现。

★ 第二个决定：【只抓三类】
  ✅ 论文原文："we focus on three kinds of PII that are detectable with
     high precision: email addresses, IP addresses and phone numbers."
  ⟹ ★ 注意它挑的标准是【高精确率（high precision）】，不是高召回率
     —— 宁可漏掉一些，也不要误伤。

✅ 两档阈值和各自影响的文档比例（✅ 全部来自论文；⚠️ 分母务必看清）：

一篇文档里检出的 PII span 数 ✅ 怎么处理 ✅ 影响的文档占比 ⚠️ 分母是什么
≤ 5 个 替换成占位符（三竖线包起来的 EMAIL_ADDRESS / PHONE_NUMBER / IP_ADDRESS） ✅ 0.02% 文档篇数，范围是那 25 个 Common Crawl 快照
≥ 6 个 ★ 整篇删除 ✅ 0.001% 同上 
★★ 为什么 ≥6 个就整篇删，而不是继续替换？
  ✅ 论文给的理由："pages containing abundant phone numbers and email
     addresses are likely to pose a greater risk of disclosing other
     PII classes."
  ⟹ 🔑 翻译：一个页面上有六个以上的电话和邮箱，
       ★ 它大概率是【通讯录、名单、泄露的数据库导出】这类东西。
       这时候你抓到的那三类只是冰山一角 ——
       页面上还会有姓名、住址、职位，⚠️ 而那些你的正则抓不到。
  ⟹ ★★ 所以这一档的判据不是"PII 多"，而是【"PII 密度高"是一个信号】：
       它在提示你"这一整篇的性质不对"。
       ★ 这是一个很值得学的设计：用能测的东西，去代理测不了的东西。

⚠️ 把两个数字摆在一起看，先别被"0.02%"的小数点骗了：
     0.02%  + 0.001%  = 0.021% 的文档被动过
   ⟹ 按篇数算确实微不足道。
   ⚠️ 但 Dolma 跨 40 亿+ 篇文档（[07 章] §7.7 那张表），
      0.021% × 4e9 ≈ 【84 万篇】文档被改写或删除。
   🔑 ★★★ 又是那条纪律：把比例换成绝对值再做判断。
      （⟹ [06 章] §6.4 对 Bloom filter 的假阳性做过同一件事。）

✅ 一个可以自己验算的成本锚点

✅ 论文正文给了一个速率数字，⚠️ 但它的口径必须说准：那 122 这个数不是 PII 过滤单独的速率，而是整套工具链复现 C4 配方时的整体过滤速率。

✅ 论文原文："In internal tests to replicate C4 recipe, our toolkit
   performed filtering at a rate of 122 CPU hours per TB; for reference,
   processing the full 'raw' Dolma files totaling 200 TB on a
   c6a.48xlarge instance with 192 vCPUs would take 5 days."

★ 自己把这句话验算一遍（这是检验自己有没有读懂口径的最好办法）：

    200 TB × 122 CPU 小时/TB = 24400 CPU 小时
    24400 CPU 小时 ÷ 192 vCPU = 127.1 小时 = 5.30 天

  ✅ 和论文说的 "would take 5 days" 对得上。

⟹ ★★ 这组数给你的量级直觉：
     【把 200 TB 原始文本做完规则 + PII 过滤，一台 192 核的机器，一周之内。】
   ★ 注意它是纯 CPU 的，不占 GPU —— 这正是 [05 章] §5.1 说的
     "便宜的那一档"，PII 处理属于这一档。
⚠️ 口径提醒：这里的 TB 是十进制（10¹² 字节）；若论文原意是 TiB，
   折算差 10%，但不影响"一周之内"这个结论。

★★★ 一个很反直觉的实验结果：怎么处理 PII，对模型效果没有影响

✅ 论文原文："In data ablation experiments, we find that execution
   details around PII (e.g., removal versus special token replacement)
   had no effect on model performance, which is expected given the tiny
   percentage of affected data."

⟹ 🔑 ★★★ 这句话值一整节：
     【"删整篇"还是"替换成占位符"，模型效果上测不出差别。】

★ 为什么：因为被动到的只有 0.021% 的文档（上表），
  ⚠️ 而 0.021% 的数据变化，在模型效果上本来就低于噪声。

⟹ ★★ 那么选哪一种？既然【效果维度上这个选择是自由的】，
     就应该完全按【其他维度】来选：

       合规维度    ⟹ 删整篇更"干净"，但你删掉的 99% 是无辜内容
       数据量维度  ⟹ 替换保留了句子结构，一个字都不浪费
       审计维度    ⟹ ★★ 替换会在文本里【留下痕迹】
                     （占位符本身就是"这里曾有 PII"的记录）
                     而删整篇是【无痕的】：事后你无法知道
                     某一篇到底是因为 PII 被删的，还是因为别的规则

⟹ 🔑 所以本教程的建议是【替换 + 把命中计数落盘】，
     ★ 理由不是效果（效果上没差别），★★ 而是【可审计】。
     ⟹ 和 8.5 的数据溯源是同一条逻辑。

⚠️ 但替换也有一个必须处理的副作用：占位符会变成一个高频 token，于是模型可能在生成时莫名其妙冒出 |||EMAIL_ADDRESS|||。

★ 两个缓解办法（⚠️ 我的整理，不是论文结论）：
  ① 用【不容易被 tokenizer 切成单个常用 token】的形式
     —— ✅ Dolma 的 ||| 三竖线包裹就有这个效果（[09 章] 讲 tokenizer 时会更清楚）
  ② 随机化：一部分替换成占位符，一部分直接删掉那几个字符
     ⟹ 让模型学不到"这个位置必定出现某个固定串"
⚠️ 代价：② 会让审计变难（因为不是每一处都留痕了）。★ 这是一个真实的取舍。

一段能跑的实现（★ 含一个无法用正则解决的坑）

import re

PATTERNS = {
    "<EMAIL>":     re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+"),
    "<PHONE_CN>":  re.compile(r"(?<!\d)1[3-9]\d{9}(?!\d)"),
    # ★ IP：加 0~255 范围校验，并把前后边界从 (?<!\d) 放宽到 (?<![\d.])
    "<IP>":        re.compile(
        r"(?<![\d.])(?:(?:25[0-5]|2[0-4]\d|1\d\d|[1-9]?\d)\.){3}"
        r"(?:25[0-5]|2[0-4]\d|1\d\d|[1-9]?\d)(?![\d.])"),
    "<IDCARD_CN>": re.compile(r"(?<!\d)\d{17}[\dXx](?!\d)"),
}

def mask_pii(text):
    hits = {}
    for tag, pat in PATTERNS.items():
        text, n = pat.subn(tag, text)
        if n:
            hits[tag] = n
    return text, hits        # ★ 一定要把命中统计留下来，用于审计（见 8.5）

   999.1.1.1   ⟹ 999 超过 255，不再匹配

               ⚠️ 原写法会输出 "<IP>.5" —— 这是上面那个"破坏原文"的同一类错误

⚠️⚠️ 但最后一行【修不掉】，而且【永远修不掉】：
   "1.2.3.4" 作为 IP 地址【完全合法】，作为版本号也【完全合法】。
   ⟹ ★★★ 两者在【字符串层面是同一个东西】，
        正则看不到上下文，所以它【原理上】无法区分。

★ 三个能做的（⚠️ 我的整理）：
  ① 接受它。把一个版本号替换成 <IP>，损失几乎为零

        在这一类上宁可误伤，因为误伤的代价确实小）
  ② 看上下文：前面紧挨着 "v" / "version" / "版本" / 在代码块里 ⟹ 跳过
     ⚠️ 这是启发式，会有新的漏检
  ③ 排除私有网段和保留网段以外的"不像真实 IP"的值
     ⚠️ 但 1.2.3.4 是一个真实可路由的地址，这一招对它也无效

⟹ 🔑 结论：★★ 正则能做到"格式正确"，做不到"语义正确"。
     ★ 凡是 PII 的格式和正常内容的格式撞车的（IP vs 版本号、
       身份证号 vs 18 位订单号、手机号 vs 11 位编号），
       ⟹ 你只能在【误伤】和【漏检】之间选一个，选不出两全。
     ⚠️ 而对 PII 来说，★★ 应该一律选【宁可误伤】——
        因为误伤的代价是损失一点数据，漏检的代价是合规事故。

⚠️ 中文身份证号还有一个比正则更好的办法：校验位。 18 位身份证号的最后一位是前 17 位的加权模 11 校验码，⟹ ★ 一个随机的 18 位数字串通过校验的概率只有约 1/11 ≈ 9%。🔑 先用正则抓候选，再用校验位过一遍，误报率能降一个数量级，而且这一步几乎不花时间。★ 银行卡号的 Luhn 校验位同理。

8.5 ★★ 数据溯源：一个被低估的工程要求

前面四节每一节都落到同一个要求上：你必须知道每一条数据是怎么来的、被谁动过。 这件事叫数据溯源（provenance）。

在你的每条记录里，除了 text，至少还要有：

  {
    "id": "...",
    "text": "...",
    "source": "commoncrawl/CC-MAIN-2024-10",   <- 哪来的
    "url": "https://...",                       <- 原始地址
    "crawl_date": "2024-03-01",                 <- 什么时候抓的
    "license": "CC-BY-4.0" | "unknown",         <- 许可依据（8.4）
    "pipeline_version": "v3.2",                 <- 哪一版流水线处理的
    "filters_passed": ["lid", "gopher", "dedup", "quality>=3.5"],
    "pii_hits": {"<EMAIL>": 2, "<PHONE_CN>": 1}, <- ★ 8.3 的命中计数
    "decontam": {"n": 13, "eval_set_version": "2024-03", "hit": false}
  }

★★ 后面那四个字段，每一个都是前面某一节逼出来的：
   pipeline_version   <- 规则有 bug 时，定位受影响的数据
   filters_passed     <- 想调某个阈值时，知道哪些数据会变
   pii_hits           <- 8.3：替换比删除更可审计，前提是你把计数留下来
   decontam           <- 8.2 的时序问题：
                         ★ 记下【你是用哪一版评测集清单扫的】，
                         ⟹ 半年后出了新评测集，你能回答"这批题扫过没有"

★★★ 为什么 pipeline_version 和 filters_passed 极其重要，用一个具体场景说：

半年后你发现"某条规则写错了"（★ 比如 8.3 那个手机号正则没加数字边界，
把电商语料打得满篇是 <PHONE>）。

⟹ 有这两个字段：
     查出哪些记录的 filters_passed 里带那条规则、
     且 pipeline_version 落在出 bug 的那几版，
     ★ 只重跑那一部分。

⟹ 没有这两个字段：
     ⚠️ 你无法区分"哪篇是被那条规则动过的"，
     ★★ 只能【整条流水线从头重跑】。
     按 8.2 那张成本表，重跑全量是 1e10 篇的量级
     —— 几周时间 + 几十万的算力账单。

★ 而 decontam.eval_set_version 这一格是本章新加的、也最容易被省掉的一格：它让 8.2 那个"永远补不回来"的时序问题，至少变成一个能回答的问题。⚠️ 它不能让你把模型里学到的东西取出来，★ 但它能让你在新评测集出来时，在几小时内给出"这批题当年扫没扫过"的答案，而不是"不知道"。

★★ 这一条是我最想强调的工程建议之一，因为它在事故发生前看起来完全没必要，而在事故发生后是唯一的救命稻草。同样的逻辑在 05 章（记录每条规则砍掉多少）和 07 章（人工抽样看被删的）都出现过——可观测性是数据流水线里最容易被省掉、也最不该省的东西。

⚠️ 而在中文场景下它已经不是"建议"了：8.4 那张表里《生成式人工智能服务管理暂行办法》对训练数据来源合法性有明确要求，⟹ 你得能说明来源。★ 没有 source / url / crawl_date / license 这四个字段，这件事无法说明。

8.6 小结

① ★★★ 先记住你站在【建库侧】：有语料，没模型。
   ⟹ 五种污染检测法里，只有两种在这个阶段做得了（8.1 那张表）：
        ① n-gram 重叠   ⟹ ✅ 能做，唯一能定位"哪一篇语料脏"的
        ③ canary 串     ⟹ ✅ 能做，但只能"见到就删"
        ② 困惑度 / ④ 成员推断 / ⑤ 黑盒行为测试 ⟹ ❌ 都要先有模型
   🔑 所以"我们做了去污染"的真实含义是：
      "我们删掉了逐字照抄、且评测集我们当时知道的那部分。"

② ★★ 污染比"数据脏"危险，因为它【让指标骗你】：
   数据脏 ⟹ 分数掉 ⟹ 你看得见
   污染   ⟹ 分数涨 ⟹ ★ 你看不见，还会据此做出错误决策
   ✅ Lee et al. 论文 Table 2：C4 验证集 4.60%、RealNews 14.35%
      能在训练集里找到 —— ⚠️ 分母是【文档数】。
   ⚠️ 同一篇论文 Table 3 的 ExactSubstr 口径下 C4 只有 1.38%，
      分母是【token 数】 —— ★ 同一件事两个口径差 3.3 倍。

③ 三种污染，一种比一种难查：
   逐字      ⟹ n-gram 能查
   改写/翻译 ⟹ ⚠️ n-gram 查不到
   ★ 间接（针对性题库）⟹ 几乎无法定义边界，
     ⚠️ 而 [07 章] §7.4 的质量分类器还会【主动把它们筛进来】

④ ★★★ n 为什么取 13：✅ 8.2 用三篇文档实测过（可自己验算）
   窗口数 = max(0, 词数 − n + 1)
     n=5  ⟹ D1 命中 20 / D2 命中 6 / D3 命中 4  ⟹ 两篇误杀
     n=8  ⟹ 17 / 3 / 1                          ⟹ 仍然两篇误杀
     n=13 ⟹ 12 / 0 / 0                          ⟹ ✅ 只判真污染那一篇
     n=20 ⟹ 5 / 0 / 0                           ⟹ 也只判一篇，但窗口少一半多
   🔑 8~13 不是魔法数字，是夹出来的：
      下界由【常见短语有多长】定，上界由【题目有多长】定。

⑤ ⚠️⚠️ 中文有一个结构性盲区，★ 这是建库侧必须自己做的决定：
   同一道 17 字的中文题（`小明有十二盒饼干，每盒六块，一共多少块？`）
     按空白切 split() ⟹ 1 个单元  ⟹ 0 个 13-gram ⟹ ⚠️ 报"干净"
     按词切（12 词）   ⟹ 0 个 13-gram            ⟹ ⚠️ 报"干净"
     按字切（17 字）   ⟹ 5 个 13-gram            ⟹ ✅ 能查
   🔑 把英文那套（空白切 + n=13）直接套到中文上，
      ★★ 它不是"效果差"，是【一个窗口都产生不了】，污染率恒报 0.00%。
   ★ 起点建议（⚠️ 我的建议）：按【字】切，n 取 20~30 个汉字；
     ★★ 并且【中英文污染率分开报】，否则中文的 0% 会被英文稀释掉。

⑥ ⚠️⚠️⚠️ 一个会静默出错的 bug：不要用 Python 内置 hash() 建 n-gram 集合。
   ✅ 实测：同一个字符串，三个进程，三个不同的哈希值
      （Python 3.3 起 str/bytes 的 hash 按进程加盐，PEP 456 / PYTHONHASHSEED）
   ⟹ 建集合和扫语料跑在不同进程 ⟹ 永远查不中 ⟹ 污染率报 0.00% ⟹ 不报错
   ★ 改用 hashlib.blake2b(s, digest_size=8)。
   🔑 自检只要 5 行：把集合落盘，另起进程抽 100 条查回来，必须 100 条全中。

⑦ ★★ 丢整篇还是只丢命中段落：一个 615 : 1 的账
   8000 词的长文，因为 13 个词命中而被整篇丢 ⟹ 损失比 8000 ÷ 13 ≈ 615 : 1
   ⚠️ 而且整篇丢【系统性偏向删长文档】（长文窗口多，命中机会多）
   ★ 业界做法是文档级 + 段落级两级都做（✅ Dolma 的 Bloom filter 就是这样）

⑧ ★★★ 去重和去污染在工程上是【同一套机制】
   ✅ Dolma 原文："repurpose this for test set decontamination by
      first seeding the Bloom filter with test examples"
   去重问"我以前见过吗"，去污染问"评测集里有吗" ⟹ 同一个问题，换个集合
   ⚠️ 但 Bloom filter 有假阳性（[06 章] §6.4：每元素 10 位约 0.82%）
      ⟹ 🔑 报污染率前先算假阳性率，★ 确认信号比底噪大。
         如果你测出 0.1% 的污染率，那基本全是假阳性。

⑨ ★★ 它该排在流水线哪一步：由【重跑成本】决定，不是单次成本
   评测集侧极小：3240 万个 13-gram，扁平 8 字节存 ✅ 259 MB（= 247 MiB）
      ⚠️ 而 Python set of int 实测约 66 字节/元素 ⟹ 2.14 GB，贵 8.2 倍
   扫语料侧是全部成本：1e10 篇 × 488 窗口 = 4.88e12 个窗口
      ⟹ 单核 56.5 天、1000 核 1.36 小时、折算 488 μs/篇（≈ 规则的 49 倍）
   ★ 放最前要扫 1e10 篇（56.5 核日），放末尾只扫 2.58e8 篇（35 核时）
      ⟹ 【重跑一次便宜 38.8 倍】，而评测集不断增加 ⟹ 你一定会重跑它
   ⚠️ 但有一个前提：只有【整篇丢】是纯过滤器，顺序才可交换。
      ★★ 改成【丢段落】就会改变文档内容 ⟹ 顺序不可交换
      ⟹ 🔑 丢段落就放在质量过滤【之前】（贵 1.7 倍），
           否则入库文档的质量分和它实际的文本不匹配。

⑩ PII = Personally Identifiable Information（个人可识别信息）
   危险不在于模型变差，★ 在于模型会【逐字背诵】 ⟹ 合规事故
   ✅ Dolma 的真实做法（全部核对过原文）：
      · 不用 Presidio 这类 NER 模型 —— ★ 3 T token 的规模上"准确"输给"跑得完"
      · 只抓三类：邮箱 / IP / 电话，★ 挑选标准是【高精确率】而非高召回率
      · ≤5 个 PII span ⟹ 替换成占位符，影响 ✅ 0.02% 的文档
      · ≥6 个          ⟹ 整篇删除，      影响 ✅ 0.001% 的文档
        ★★ ≥6 这一档的判据不是"PII 多"，是【"PII 密度高"是个信号】：
           那大概率是通讯录、名单、泄露的数据库导出
           ⟹ 你抓到的三类只是冰山一角。★ 用能测的代理测不了的。
      · ⚠️ 分母是【文档篇数】，范围是那 25 个 Common Crawl 快照
        ⟹ 0.021% × 40 亿篇 ≈ 【84 万篇】被改写或删除
           🔑 把比例换成绝对值再做判断。
      · ✅ 速率 122 CPU 小时/TB —— ⚠️ 口径是【整套工具链复现 C4 配方】，
        不是 PII 单项。验算：200 TB × 122 ÷ 192 vCPU = 127 小时 = 5.3 天
        ✅ 和论文说的 "would take 5 days" 对上。

⑪ ★★★ 一个反直觉的结果：✅ Dolma 的消融实验发现
   【"删整篇"还是"替换成占位符"，模型效果上测不出差别】
   （因为只影响 0.021% 的数据，低于噪声）
   ⟹ 🔑 既然效果维度上这个选择是自由的，就该按【可审计性】选：
        ★ 替换会在文本里留下痕迹（占位符本身就是"这里曾有 PII"的记录），
          而删整篇是【无痕的】—— 事后你无法知道一篇是因为什么被删的。
   ⚠️ 代价：占位符会变高频 token，要做随机化；而随机化又会让审计变难。

⑫ ⚠️ 正则的边界：能做到"格式正确"，做不到"语义正确"。✅ 两个坑都实测过
   · 手机号不加 (?<!\d) / (?!\d) ⟹ 把订单号【从中间劈开】成
     "20241<PHONE>123456" —— ★ 这不只是误报，是【破坏了原文】
   · IP 的 0~255 范围校验能修掉 999.1.1.1 和 1.2.3.4.5，
     ⚠️ 但【修不掉 1.2.3.4】—— 它作为 IP 和作为版本号都完全合法，
     ★★ 正则看不到上下文，【原理上】无法区分。
   🔑 凡是 PII 格式和正常内容格式撞车的，只能在误伤和漏检之间选一个。
      ★ 对 PII 一律选【宁可误伤】：误伤损失一点数据，漏检是合规事故。
   ★ 中文身份证号和银行卡号有校验位（随机串通过率约 1/11），
     ⟹ 正则抓候选 + 校验位过一遍，误报率降一个数量级，几乎不花时间。

⑬ 许可：Books3 下架 / robots.txt 收紧 / 代码许可证不明
   ✅ Books3 = The Pile 里权重 12.07%、原始体积 100.96 GiB 的书籍子集
      ⚠️ 当成 100.96 GB 算就少 7.4%（十进制是 108.4 GB）
      ★ 用论文 Table 1 两列相除可推出约 19.66 万份文档（= 19.66 万本书）
   三条路线：照用不误 / 只用开放许可（Common Pile）/ 买授权
      ★★ 路线 ③ 的存在意味着：【数据差距是买出来的，流水线优化补不回来】
   ⚠️ 中文还要考虑 PIPL 与《生成式人工智能服务管理暂行办法》
      ⟹ ★★ 后者把 8.5 的数据溯源从"最佳实践"变成了【硬要求】

⑭ ⚠️ 全行业的披露状况（✅ 出自 Dolma 论文附录 §C，2024-02 快照）：
   【去污染那一列几乎是空的】—— PaLM 2 / LLaMA / OPT 都是 N/A，
   GPT-4 只报事后统计（判据是去空白后的精确子串，★ 和 13-gram 不可比），
   Llama 2 那一格填的其实是【去重】方法（★★ 又一次印证 ⑧）。
   ⟹ 🔑 你无法判断任何两家的分数在污染程度上可不可比。
   ★ 唯一把许可做进流水线的是 LLaMA：GitHub 代码只取 Apache / BSD / MIT。

⑮ ★★ 数据溯源（provenance）：每条记录都要带
   source / url / crawl_date / license / pipeline_version / filters_passed
   ★ 再加本章逼出来的两个：pii_hits（⑪ 的可审计性）
                         decontam.eval_set_version（④⑨ 的时序问题）
   ⟹ 出了问题能定点重跑，而不是整条流水线从头再来（几周 + 几十万）
   🔑 它在事故发生前看起来完全没必要，★★ 事故发生后是唯一的救命稻草。
