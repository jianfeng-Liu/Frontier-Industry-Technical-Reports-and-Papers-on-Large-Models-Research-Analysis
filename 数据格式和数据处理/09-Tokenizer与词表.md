## 9.1 为什么不能按字/按词切

```
方案①：按【字符】切
   "hello" → h, e, l, l, o
   ✅ 词表极小（几百个）
   ❌ ★ 序列变得极长 —— 而注意力的开销是 O(L²)
      一篇 2000 词的文章 → 12000 个 token，成本翻好几倍

方案②：按【词】切
   "hello world" → hello, world
   ✅ 序列短
   ❌ 词表爆炸：英文常用词就几十万，加上时态变化、专有名词，无穷无尽
   ❌ ★ 遇到没见过的词只能给一个 <UNK>（unknown，未知词）
      → 模型永远学不会新词、拼写错误、代码里的变量名
   ❌ ★★ 中文根本没有"词"的天然边界

★★ 所以答案是【中间路线】：切成"子词"（subword）
   常见词整个保留，罕见词拆成有意义的碎片
       "unbelievable" → "un" + "believ" + "able"
       "深度学习"      → "深度" + "学习"
   ⟹ 词表可控（10 万量级）+ 序列不长 + ★ 永远不会有 <UNK>
```

## 9.2 ★ BPE：这个领域用得最多的算法

**BPE** = **Byte Pair Encoding**（字节对编码）。

✅ 出处：[arXiv:1508.07909](https://arxiv.org/abs/1508.07909)，Rico Sennrich 等，2015-08，*Neural Machine Translation of Rare Words with Subword Units*。
★ 有意思的是，BPE 原本是 1994 年的一个**数据压缩**算法，Sennrich 把它借来做分词——**这也是为什么后面"压缩率"会成为衡量 tokenizer 的核心指标**。

### 算法：只有一条规则

> **反复找出当前语料里【出现次数最多的相邻符号对】，把它合并成一个新符号。重复 N 次。**

### 手算一遍

```
语料（简化成词频表）：
    "low"    出现 5 次
    "lower"  出现 2 次
    "newest" 出现 6 次
    "widest" 出现 3 次

初始：全部拆成字符（末尾加 </w> 表示词尾）
    l o w </w>          ×5
    l o w e r </w>      ×2
    n e w e s t </w>    ×6
    w i d e s t </w>    ×3

── 第 1 轮：数所有相邻对 ──
    (e,s): 6+3 = 9   ← ★ 最多
    (s,t): 6+3 = 9
    (l,o): 5+2 = 7
    (o,w): 5+2 = 7
    ...
  合并 (e,s) → "es"
    n e w es t </w>   ×6
    w i d es t </w>   ×3

── 第 2 轮 ──
    (es,t): 9  ← 最多  → 合并成 "est"
    n e w est </w>    ×6
    w i d est </w>    ×3

── 第 3 轮 ──
    (est,</w>): 9  → 合并成 "est</w>"     ★ 学会了英语的最高级后缀！

── 第 4 轮 ──
    (l,o): 7  → "lo"
── 第 5 轮 ──
    (lo,w): 7 → "low"                     ★ 学会了词根 "low"

最终词表 = 初始字符 + 这些合并出来的新符号
最终【合并规则表】= [(e,s), (es,t), (est,</w>), (l,o), (lo,w), ...]  ★ 有顺序！
```

> ★★ **关键理解：BPE 的产物是两个东西**
> ```
> ① vocab   —— 所有 token 的列表（token → id）
> ② merges  —— ★【有序的】合并规则表
> ```
> **编码新文本时，就是按 merges 的顺序，从头到尾把能合的都合掉。**
> 顺序不能变——变了切出来就是另一套 token。这也是为什么 tokenizer 文件必须和模型权重**严格配套**。

```python
# 编码：按 merges 顺序反复合并（概念版）
def encode(word, merges):
    symbols = list(word) + ["</w>"]
    for a, b in merges:                       # ★ 必须按训练时的顺序
        i = 0
        while i < len(symbols) - 1:
            if symbols[i] == a and symbols[i+1] == b:
                symbols[i:i+2] = [a + b]
            else:
                i += 1
    return [vocab[s] for s in symbols]
```

## 9.3 字节级 BPE 与 byte fallback：怎么保证"什么都能切"

上面的 BPE 是在**字符**上做的。但字符有 15 万种（Unicode），而且总有你没见过的（生僻字、emoji、古文字）。

```
★ 解决办法：不在【字符】上做 BPE，在【字节】上做。
   任何文本先转成 UTF-8 字节序列 → 只有 256 种可能的基础符号
   ⟹ ★★ 任何输入都一定能被表示出来，永远不会有 <UNK>

  这叫【字节级 BPE / byte-level BPE】，GPT-2 之后成为主流。

  变体：byte fallback —— 平时按字符 BPE，遇到词表里没有的字符
       才退回到字节表示。SentencePiece 的常见配置。
```

> ⚠️ **对中文极其重要的一个后果：**
> ```
> UTF-8 里一个汉字占 【3 个字节】
> → 如果 tokenizer 训练语料里【中文很少】，"锟"这种字没被合并成一个 token
> → 它就会被切成 3 个字节 token
> ⟹ ★ 同一句中文，在中文友好的 tokenizer 上是 20 个 token，
>      在中文不友好的 tokenizer 上可能是 50 个
>   → 存储贵 2.5 倍、训练贵 2.5 倍、推理贵 2.5 倍、上下文窗口缩水 2.5 倍
>
> ★★ 这就是为什么国产模型都要【自己重训 tokenizer】，而不是直接用开源的。
> ```

**其他几种算法**（知道名字就够）：

```
WordPiece   —— BERT 用的。和 BPE 几乎一样，只是合并时选的不是"最高频"
               而是"最能提升语言模型似然"的那一对
Unigram LM  —— SentencePiece 的另一种模式。★ 思路【反过来】：
               先弄一个巨大的候选词表，再迭代地【删掉】贡献最小的
SentencePiece —— ⚠️ 注意：它是一个【库】，不是一种算法。
               它同时实现了 BPE 和 Unigram 两种模式。很多人会搞混。
               ★ 它的真正卖点是【把空格也当普通字符处理】（用 ▁ 表示），
                 于是不需要预先分词 —— 对中文、日文这类无空格语言是必需的
```

## 9.4 ★★ 词表大小怎么定：一个四方拉扯的权衡

```
词表 V 变大 →
  ✅ 压缩率变好（同样的文本用更少的 token）
     → 序列变短 → 训练和推理都变便宜
     → 上下文窗口能装更多真实内容
     
  ❌ Embedding 矩阵变大：V × d
     V=15万, d=5120 → 7.68 亿参数，★ 光输入 embedding 就快 8 亿
     再加输出层（LM head）又是一份 → ★ 15 亿参数花在"查表"上
     
  ❌ 输出 softmax 变慢：每一步都要在 V 个词上算概率
  
  ❌ ★ 罕见 token 训练不足
     词表里排在最后的那些 token，可能在整个语料里只出现几百次
     → 它们的 embedding 基本是随机初始化的状态
     → ★★ 这就是"glitch token"（故障 token）现象的来源：
        某些 token 一旦出现，模型行为会变得完全不可预测
        
  ❌ ★★★ 【04 章的存储成本断崖】：
     V ≤ 65535 → .bin 用 uint16，每 token 2 字节
     V > 65535 → .bin 用 int32，每 token 4 字节
     → 15 T token 的数据集：30 TB vs 60 TB，★ 直接翻倍
```

> ★ **现实的落点**：现在的大模型词表普遍在 **12 万 ~ 20 万**之间。已经远超 65535，所以**存储翻倍这笔账大家都认了**——因为多语言能力比存储费重要得多。

### ⚠️ 一个 Megatron 特有的坑：词表要能被整除

```
✅ Megatron 有一个参数 --make-vocab-size-divisible-by（默认 128）

原因：★ 输出层（LM head）是按【张量并行 TP】切开的，
      V 必须能被 (TP 大小 × 128) 整除，才能均匀切分且对齐 GPU 的计算单元

现象：你的 tokenizer 是 151,552 个 token，
      但模型里的 Embedding 矩阵是 151,552 → 被补齐到某个更大的数
      → ★ 多出来的那些行是【永远不会被用到的填充】
      
⚠️ 新手困惑："为什么 config 里的 vocab_size 和 tokenizer 的长度对不上？"
   答案就是这个填充。★ 计算 loss 时要把填充位置屏蔽掉，否则概率质量会漏。
```

## 9.5 ★ 压缩率：怎么衡量一个 tokenizer 好不好

```
压缩率 = 平均每个 token 覆盖多少个【字符】
         ★ 越高越好（同样的文本用更少 token）

别名：fertility（生育率）= 每个词平均切成几个 token，★ 越低越好
      —— 是同一件事的倒过来说法，看到别人用哪个都不要慌
```

✅ **openPangu-2.0 技术报告 Table 4 的实测数据**（这是本章最有价值的一手数字）：

| 词表 | 词表大小 | 中文 | 英文 | 多语言 | 代码 | 行业 | **平均** |
|---|---|---|---|---|---|---|---|
| openPangu-1.0 | 153,376 | 3.82 | 4.30 | 2.80 | 2.80 | 4.18 | 2.56 |
| openPangu-2.0-**3digit** | 150,400 | **4.04** | 4.27 | **3.37** | 2.77 | **4.51** | **2.71** |
| openPangu-2.0-**single-digit** | 149,600 | 3.82 | 4.15 | 3.32 | 2.56 | 4.27 | 2.59 |

```
读法：
  ① 中文 3.82~4.04 —— ★ 平均一个 token 覆盖将近 4 个汉字
     这是【中文友好】tokenizer 的正常水平
  ② 代码只有 2.56~2.80 —— ★ 代码是最难压缩的，
     因为变量名千奇百怪、缩进和符号极多
  ③ "平均"那一列比各分项都低 —— ⚠️ 说明它不是简单算术平均，
     ✅ 报告没说加权方式，我不做推测
```

## 9.6 ★★★ 一个绝佳的教学案例：openPangu 为什么故意选了压缩率更差的那个

看上表：**3digit 变体在几乎所有语料上压缩率都更好**（平均 2.71 vs 2.59）。

✅ **但报告明确说：openPangu-2.0 最终采用的是 single-digit 变体。**

先解释这两个变体的区别：

```
数字 "12345" 怎么切？

  3-digit 变体      → "123" + "45"      （按最多 3 位一组合并）
  single-digit 变体 → "1"+"2"+"3"+"4"+"5"  ★ 每个数字单独一个 token
```

✅ 报告给出的理由（我按原文转述）：

```
① 常规 BPE 是按【共现频率】合并数字的
   → "2024" 因为常见被合成一个 token，
     "2025" 可能被切成 "202"+"5"
   ⟹ ★★ 同一个位置上的数字，切法【不一致】
      模型很难学到"个位、十位、百位"这种稳定的结构

② single-digit 让数字表示【完全规整】
   ✅ 报告点名的三个受益场景：
      · 数值推理（做算术）
      · 多模态定位（坐标、bounding box 都是数字）
      · 工具调用（tool 参数里全是数字）

③ 代价：压缩率损失一点点（平均 2.71 → 2.59，约 4%）
```

> ★★★ **这个案例值得反复琢磨，因为它推翻了一个很自然的直觉：**
>
> ```
> 错误直觉：tokenizer 的目标是【压缩率最高】
> 实际情况：tokenizer 的目标是【让模型好学】
>           压缩率只是其中一个因素，而且不是最重要的那个
> ```
>
> ★ 同样的逻辑也解释了另外两个业界常见做法：
> ```
> · 代码模型会给【连续空格】和【制表符】专门开 token
>   （早期 GPT-2 没做，导致它写 Python 缩进特别吃力）
> · 多数模型会禁止 token【跨越换行符】合并
>   —— 否则 "。\n第" 会被合成一个 token，破坏结构
> ```
>
> ⚠️ 我的补充：**openPangu 这个选择在 2025 年之后已经接近共识**——多家模型都采用了逐位数字切分。但它把"为什么"写进了报告并给了对照表，这在技术报告里是很少见的坦诚。

## 9.7 训练 tokenizer 的实操

```python
from tokenizers import Tokenizer, models, trainers, pre_tokenizers, decoders

tok = Tokenizer(models.BPE(unk_token=None))       # ★ 字节级 BPE 不需要 unk

tok.pre_tokenizer = pre_tokenizers.Sequence([
    # ★ 数字逐位切开 —— 就是 9.6 说的 single-digit
    pre_tokenizers.Digits(individual_digits=True),
    # ★ 禁止 token 跨越空白与标点合并
    pre_tokenizers.ByteLevel(add_prefix_space=False, use_regex=True),
])
tok.decoder = decoders.ByteLevel()

trainer = trainers.BpeTrainer(
    vocab_size=151552,
    min_frequency=2,
    special_tokens=["<|endoftext|>", "<|im_start|>", "<|im_end|>",
                    "<|pad|>"] + [f"<|reserved_{i}|>" for i in range(64)],
    #                              ★★ 预留一批空 token！见下方说明
    initial_alphabet=pre_tokenizers.ByteLevel.alphabet(),   # 256 个字节全放进去
)
tok.train_from_iterator(sample_corpus_iter(), trainer=trainer)
tok.save("tokenizer.json")
```

### ★ 训练语料怎么选（比算法本身更重要）

```
① ★★ 必须【按最终训练配比采样】
   如果你的训练数据是 中文30% 英文50% 代码20%，
   那 tokenizer 的训练样本也要按这个比例
   ⚠️ 一个真实的失败：拿英文语料训 tokenizer，然后训中文模型
      → 中文全部退化成字节，成本翻 3 倍

② 采样量不需要很大
   ★ 几 GB ~ 几十 GB 就够了，因为 BPE 只看频率统计，收敛很快
   （对比：模型训练要几十 TB）

③ ⚠️ 要先做基础清洗
   如果采样里混进大量乱码或 base64 字符串，
   → 词表里会浪费几千个 token 在垃圾模式上
```

### ★ 为什么要预留 reserved token

```
模型训完之后，你想加一个新的特殊 token（比如新的工具调用标记）：
   → 改词表大小 = 改 Embedding 矩阵形状 = ★ 得重训

⟹ 所以【一开始就预留几十上百个空 token】，以后想加什么直接占用一个
★ 这是所有正经模型的标准做法。你在开源模型的 tokenizer 里
  经常能看到 <|reserved_special_token_37|> 这类东西，就是干这个的。
```

## 9.8 ⚠️ 四个真实会踩的坑

```
① ★★★ 换了 tokenizer 必须重跑 preprocess_data
   .bin 里存的是【整数 id】。换词表后同一个 id 指向完全不同的词。
   ★ 现象：loss 从第一步就停在随机水平且不下降。
   ⚠️ 这是 04 章列的五个坑里【最隐蔽】的一个，因为程序不会报任何错。

② 训练和推理用了不同版本的 tokenizer
   哪怕只差一条 merge 规则，切出来的 token 边界就会不同
   ★ 现象：模型在自己的评测里正常，一上线就变傻
   ★ 这也是 GLM-5.2 报告里提到的 RL 训练"重新 tokenize 会破坏对齐"的同一类问题

③ 特殊 token 被用户输入注入
   用户在输入里打了 "<|im_start|>" 这几个字符 —— 
   ⚠️ 如果 tokenizer 把它编码成【真正的特殊 token】而不是普通文本，
      用户就能伪造对话角色。
   ★ 正确做法：用户输入编码时必须关掉特殊 token 解析
      （HuggingFace 里就是 tokenizer(text) 时不要开 special token 解析）

④ glitch token（训练不足的 token）
   词表尾部的罕见 token 在语料里出现次数极少 → embedding 近乎随机
   ★ 现象：某些奇怪字符串会让模型输出完全失控
   ★ 缓解：训完 tokenizer 后统计每个 token 在全语料的出现频次，
          把出现次数低于阈值的 token 剔掉重训
```

## 9.10 小结

```
① 按字切 → 序列太长（注意力 O(L²)）；按词切 → 词表爆炸 + <UNK>
   ⟹ 子词（subword）是中间路线

② ✅ BPE（[1508.07909](https://arxiv.org/abs/1508.07909)，Sennrich 2015）只有一条规则：
   反复合并【出现次数最多的相邻符号对】
   产物 = vocab（token→id）+ ★【有序的】merges 规则表
   ★ 它原本是 1994 年的数据压缩算法 —— 所以"压缩率"成了核心指标

③ 字节级 BPE：在 UTF-8 字节上做 → 只有 256 个基础符号 → 永不 <UNK>
   ⚠️ 一个汉字 3 字节：tokenizer 不含中文 → 中文成本翻 2~3 倍
      ★ 这就是国产模型必须自己重训 tokenizer 的原因

④ ★ 词表大小的四方权衡：
   大 → 压缩率好、序列短
      ❌ Embedding + LM head 参数暴涨（15万×5120 ≈ 15 亿参数）
      ❌ 罕见 token 训练不足 → glitch token
      ❌★ 04 章的断崖：V>65535 → .bin 从 2 字节变 4 字节，存储【翻倍】
   现实落点：12 万 ~ 20 万
   ⚠️ Megatron 会把 V 补齐到能被 TP×128 整除 → config 和 tokenizer 长度对不上

⑤ 压缩率 = 每 token 覆盖多少字符（越高越好）；fertility 是它的倒过来说法
   ✅ openPangu-2.0 实测：中文 ~3.8-4.0，代码只有 ~2.6-2.8（代码最难压）

⑥ ★★★ openPangu 的教学案例：
   3digit 变体压缩率更好（2.71 vs 2.59），但最终选了 single-digit。
   理由：★ 频率驱动的数字合并【切法不一致】，模型学不到位值结构；
        逐位切分让数值推理、多模态坐标、工具参数都规整
   ⟹ ★★ tokenizer 的目标不是"压缩率最高"，是"让模型好学"

⑦ 训 tokenizer：★ 采样必须按最终训练配比；几十 GB 就够；
   ★ 一定要预留几十个 reserved token（否则以后加特殊 token 要重训）

⑧ ⚠️ 四个坑：换词表没重跑 preprocess（loss 卡在随机且不报错）/
   训推 tokenizer 版本不一致 / 用户输入里的特殊 token 注入 / glitch token
```
