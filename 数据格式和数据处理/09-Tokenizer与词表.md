## 9.1 为什么不能按字/按词切

```
方案①：按【字符】切
   "hello" → h, e, l, l, o
   ✅ 词表极小（几百个）
   ❌ ★ 序列变得极长 —— 而注意力的开销是 O(L²)
      一篇 2000 词的文章 → 12000 个 token，成本翻好几倍

方案②：按【词】切
   "hello world" → hello, world
   ✅ 序列短
   ❌ 词表爆炸：英文常用词就几十万，加上时态变化、专有名词，无穷无尽
   ❌ ★ 遇到没见过的词只能给一个 <UNK>
      （UNK = unknown，未知词；也叫 OOV = Out-Of-Vocabulary，词表外）
      → 模型永远学不会新词、拼写错误、代码里的变量名
   ❌ ★★ 中文根本没有"词"的天然边界

★★ 所以答案是【中间路线】：切成"子词"
   （subword，子词 —— 比词小、比字符大的单位）
   常见词整个保留，罕见词拆成有意义的碎片
       "unbelievable" → "un" + "believ" + "able"
       "深度学习"      → "深度" + "学习"
   ⟹ 词表可控（10 万量级）+ 序列不长 + ★ 永远不会有 <UNK>
```

## 9.2 ★ BPE：这个领域用得最多的算法

**BPE** = **Byte Pair Encoding**（字节对编码）。

✅ 出处：[arXiv:1508.07909](https://arxiv.org/abs/1508.07909)，Rico Sennrich 等，2015-08，*Neural Machine Translation of Rare Words with Subword Units*。
★ 有意思的是，BPE 原本是 1994 年的一个**数据压缩**算法，Sennrich 把它借来做分词——**这也是为什么后面"压缩率"会成为衡量 tokenizer 的核心指标**。

### 算法：只有一条规则

> **反复找出当前语料里【出现次数最多的相邻符号对】，把它合并成一个新符号。重复 N 次。**

### ★★ 手算五轮：看着词表自己长出来

下面这个例子请**拿笔跟着数一遍**。整章最该花时间的就是这一小节——看完你就知道 tokenizer 文件里那几万行 merges 是怎么来的。

**语料**（简化成"词 → 出现次数"的频率表，只有 4 个词）：

```
    "low"    出现 5 次
    "lower"  出现 2 次
    "newest" 出现 6 次
    "widest" 出现 3 次

初始：全部拆成字符，每个词末尾加 </w> 表示词尾
    l o w </w>          ×5
    l o w e r </w>      ×2
    n e w e s t </w>    ×6
    w i d e s t </w>    ×3

初始词表（11 个基础符号）：l o w e r n s t i d </w>
初始 token 总数：4×5 + 6×2 + 7×6 + 7×3 = 20 + 12 + 42 + 21 = 95
```

> ⚠️ **先说清一条规则，否则你自己数会卡住**：经常出现**多个对并列最高频**的情况。本例统一用「**并列时取扫描顺序里先遇到的那个**」（按词表顺序、每个词从左到右）。✅ 真实实现（`tokenizers`、`sentencepiece`）也必须定下某个确定的打破平局规则，否则同一份语料会训出不同的词表。

**第 1 轮** —— 数出全部相邻对（出现次数 = 所在词的词频之和）：

| 相邻对 | 来自哪些词 | 次数 |
|---|---|---|
| `(l,o)` | low ×5、lower ×2 | 7 |
| `(o,w)` | low ×5、lower ×2 | 7 |
| `(w,e)` | lower ×2、newest ×6 | 8 |
| **`(e,s)`** | newest ×6、widest ×3 | **9** ← 并列第一，扫描序最靠前 |
| `(s,t)` | newest ×6、widest ×3 | **9** ← 并列 |
| `(t,</w>)` | newest ×6、widest ×3 | **9** ← 并列 |
| `(n,e)` / `(e,w)` | newest ×6 | 6 |
| `(w,</w>)` | low ×5 | 5 |
| `(w,i)` / `(i,d)` / `(d,e)` | widest ×3 | 3 |
| `(e,r)` / `(r,</w>)` | lower ×2 | 2 |

合并 `(e,s)` → 新 token **`es`**，语料变成：

```
    l o w </w>          ×5
    l o w e r </w>      ×2
    n e w es t </w>     ×6
    w i d es t </w>     ×3
```

**第 2 ~ 5 轮** —— 每一轮重新数一遍（这一步不能偷懒，合并会改变所有计数）：

| 轮 | 最高频对 | 次数 | 新 token | 合并后的语料（只列变化的词） | 词表大小 | 语料 token 总数 |
|---|---|---|---|---|---|---|
| 1 | `(e,s)` | 9 | **`es`** | `n e w es t </w>` ×6<br>`w i d es t </w>` ×3 | 11 → 12 | 95 → 86 |
| 2 | `(es,t)` | 9 | **`est`** | `n e w est </w>` ×6<br>`w i d est </w>` ×3 | 12 → 13 | 86 → 77 |
| 3 | `(est,</w>)` | 9 | **`est</w>`** ★ | `n e w est</w>` ×6<br>`w i d est</w>` ×3 | 13 → 14 | 77 → 68 |
| 4 | `(l,o)` | 7 | **`lo`** | `lo w </w>` ×5<br>`lo w e r </w>` ×2 | 14 → 15 | 68 → 61 |
| 5 | `(lo,w)` | 7 | **`low`** ★ | `low </w>` ×5<br>`low e r </w>` ×2 | 15 → 16 | 61 → 57 |

```
★ 第 3 轮的 "est</w>" 是英语的【最高级后缀】—— 算法没有任何语法知识，
  纯靠频率就把它挖出来了。
★ 第 5 轮的 "low" 是一个【词根】。
⟹ 这就是子词切分"有意义"的由来：高频共现的片段，往往正好是语言里的语素。
```

**五轮之后的账**：

```
词表：11 个基础符号 → 16 个（新增 es / est / est</w> / lo / low）
语料 token 总数：95 → 57

⚠️ 这里有一个非常容易说错的地方（本章后面还会再碰到一次）：
    57 ÷ 95 = 60%     ⟹ 正确说法是「压缩到了 60%」
    95 ÷ 57 = 1.67    ⟹ 正确说法是「压缩了 1.67 倍」
    ❌ 错误说法：「压缩了 60%」—— 那意思是只剩 40%，和事实差了一半
★ 「压缩到 X%」和「压缩 X 倍」是两件事，互为倒数，写报告时务必说清是哪个。
```

> ★★ **关键理解：BPE 的产物是两个东西**
> ```
> ① vocab   —— 所有 token 的列表（token → id）
> ② merges  —— ★【有序的】合并规则表
>    本例：[(e,s), (es,t), (est,</w>), (l,o), (lo,w)]
> ```
> **编码新文本时，就是按 merges 的顺序，从头到尾把能合的都合掉。** 顺序不能变——变了切出来就是另一套 token。这也是为什么 tokenizer 文件必须和模型权重**严格配套**。

### ★ 用这 5 条规则去切两个没见过的词

```
① "lowest"（语料里从来没出现过）
   初始：  l o w e s t </w>
   规则①(e,s)   → l o w es t </w>
   规则②(es,t)  → l o w est </w>
   规则③(est,</w>) → l o w est</w>
   规则④(l,o)   → lo w est</w>
   规则⑤(lo,w)  → low est</w>
   ⟹ 结果：["low", "est</w>"]  ★ 只用 2 个 token，而且恰好切成【词根 + 后缀】
      模型没见过 "lowest"，但它见过 "low" 和 "est</w>"，所以能泛化

② "newer"
   初始：  n e w e r </w>
   五条规则一条都匹配不上
   ⟹ 结果：["n","e","w","e","r","</w>"]  6 个 token
   ★ 这说明【词表太小】。真实训练会跑 15 万轮而不是 5 轮，
     "new" / "er</w>" 这类片段早就被合出来了。
```

> ⚠️ **"有序"这两个字实测会出事**：如果把规则④⑤换个顺序（先 `(lo,w)` 再 `(l,o)`），切 `"lowest"` 时 `(lo,w)` 根本匹配不上（那一刻还没有 `lo` 这个符号），结果会变成 `["l","o","w","est</w>"]` —— **4 个 token 而不是 2 个**。同一份 vocab、同一份规则集合，只是顺序不同，切出来就是另一套 id。

```python
# 编码：按 merges 顺序反复合并（概念版，对应上面手算的过程）
def encode(word, merges, vocab):
    symbols = list(word) + ["</w>"]
    for a, b in merges:                       # ★ 必须按训练时的顺序
        i = 0
        while i < len(symbols) - 1:
            if symbols[i] == a and symbols[i+1] == b:
                symbols[i:i+2] = [a + b]      # 合并，不前进（可能要连合多次）
            else:
                i += 1
    return [vocab[s] for s in symbols]
```

## 9.3 字节级 BPE 与 byte fallback：怎么保证"什么都能切"

上面的 BPE 是在**字符**上做的。但字符有十几万种（Unicode 码点），而且总有你没见过的（生僻字、emoji、古文字）。

```
★ 解决办法：不在【字符】上做 BPE，在【字节】上做。
   任何文本先转成 UTF-8 字节序列 → 只有 256 种可能的基础符号
   ⟹ ★★ 任何输入都一定能被表示出来，永远不会有 <UNK>

  这叫【字节级 BPE / byte-level BPE】，GPT-2 之后成为主流。

  变体：byte fallback（字节兜底）—— 平时按字符 BPE，遇到词表里没有的字符
       才退回到字节表示。SentencePiece 的常见配置。
```

### ⚠️ 先把三个单位钉死：字符 / 字节 / token

这三个词在 tokenizer 这一块**天天被混用**，而且混了之后数字会差 2~3 倍。本章后面 9.5 的那条跨目录矛盾，根子就在这里。

| 单位 | 准确定义 | "今天天气不错，我们出去散步吧。" | "The weather is nice today, let's go out for a walk." |
|---|---|---|---|
| **字符**（character，Unicode 码点） | 人眼看到的一个字/一个标点 | **15** | **51** |
| **字节**（byte，UTF-8 编码后） | 存到磁盘上实际占几个字节 | **45**（每个汉字和全角标点都是 3 字节） | **51**（全是 ASCII，1 字节/字符） |
| **单词**（word） | 空格分出来的词 | ⚠️ 不适用，中文没有空格边界 | **11** |
| **token** | tokenizer 切出来的单位，模型真正看到的东西 | ⚠️ 经验值 **8 ~ 10** | ⚠️ 经验值 **13 ~ 15** |

```
★★ 把上面这张表换算成"每个 token 覆盖多少"，会得到一个反直觉的结论：

  按【字符】算：  中文 15 ÷ 9  ≈ 1.7 字符/token
                 英文 51 ÷ 14 ≈ 3.6 字符/token     → 中文看着只有英文的一半

  按【字节】算：  中文 45 ÷ 9  ≈ 5.0 字节/token
                 英文 51 ÷ 14 ≈ 3.6 字节/token     → ★ 中文反而【更高】

⟹ 同一份数据，换个口径结论直接反过来。
   所以看到任何"每 token 覆盖 N 个 character"的数字，
   ★ 第一件事是问：这个 character 是【码点】还是【字节】？
```

> ⚠️ **对中文极其重要的一个后果：**
> ```
> UTF-8 里一个汉字占 【3 个字节】
> → 如果 tokenizer 训练语料里【中文很少】，"锟"这种字没被合并成一个 token
> → 它就会被切成 3 个字节 token
> ⟹ ★ 同一句中文，在中文友好的 tokenizer 上是 20 个 token，
>      在中文不友好的 tokenizer 上可能是 50 个
>   → 存储、训练、推理的成本同比例上升，上下文窗口同比例缩水（本例 2.5 倍）
>
> ★★ 这就是为什么国产模型都要【自己重训 tokenizer】，而不是直接用开源的。
> ```

**其他几种算法**（知道名字就够）：

```
WordPiece   —— BERT 用的。和 BPE 几乎一样，只是合并时选的不是"最高频"
               而是"最能提升语言模型似然"的那一对
Unigram LM  —— （Unigram Language Model，一元语言模型）SentencePiece 的另一种模式。
               ★ 思路【反过来】：先弄一个巨大的候选词表，
                 再迭代地【删掉】贡献最小的
SentencePiece —— ⚠️ 注意：它是一个【库】，不是一种算法。
               它同时实现了 BPE 和 Unigram 两种模式。很多人会搞混。
               ★ 它的真正卖点是【把空格也当普通字符处理】（用 ▁ 表示），
                 于是不需要预先分词 —— 对中文、日文这类无空格语言是必需的
```

## 9.4 ★★ 词表大小怎么定：一个四方拉扯的权衡

```
词表 V 变大 →
  ✅ 压缩率变好（同样的文本用更少的 token）
     → 序列变短 → 训练和推理都变便宜
     → 上下文窗口能装更多真实内容

  ❌ Embedding 矩阵变大：V × d
  ❌ 输出 softmax 变慢：每一步都要在 V 个词上算概率
  ❌ ★ 罕见 token 训练不足
  ❌ ★★★ 存储成本断崖（04 章的坑）
```

下面把这四笔账**一项一项算出来**，因为"大概会变大"这种说法没法支撑决策。

### 账① Embedding 与 LM head 的参数量

设 V = 150,000（当代主流量级），d = hidden size（隐层宽度）。

| 模型规模 | d | 输入 Embedding = V×d | 加上 LM head（不共享权重）| 占总参数量（共享 / 不共享） |
|---|---|---|---|---|
| 1.5 B | 1,536 | 2.30 亿 | 4.61 亿 | **15.4% / 30.7%** |
| 7 B | 4,096 | 6.14 亿 | 12.29 亿 | **8.8% / 17.6%** |
| 70 B | 8,192 | 12.29 亿 | 24.58 亿 | **1.8% / 3.5%** |
| 400 B | 16,384 | 24.58 亿 | 49.15 亿 | **0.6% / 1.2%** |

```
★★ 这张表解释了一个常被问起的现象：
   为什么【小模型倾向于用小词表】，大模型反而敢把词表做到 20 万？

   因为同一个 15 万词表：
     在 1.5 B 模型上吃掉 15%~31% 的参数预算 —— 这些参数是"查表"，不参与推理计算
     在 400 B 模型上只占 0.6%~1.2% —— 完全可以忽略

   ⚠️ 注意"占比"的口径：上表的分母是【总参数量】。
      对 MoE（Mixture of Experts，混合专家）模型，总参数量和每 token 激活参数量
      是两个不同的数，Embedding 在后者里的占比会高得多（Embedding 对每个 token 都全量参与）。
```

### 账② 输出 logits 张量有多大（★ 最容易被忽略的一笔）

LM head 的输出是一个 `[token 数, V]` 的张量，叫 **logits**（未归一化的打分）。

```
设：micro-batch = 1 条序列，序列长度 s = 8192，V = 150,000

  logits 元素个数 = 8192 × 150,000 = 1,228,800,000 ≈ 12.3 亿
  BF16（2 字节）  = 2,457,600,000 字节 = 2.46 GB = 2.29 GiB
  FP32（4 字节）  = 4,915,200,000 字节 = 4.92 GB = 4.58 GiB
                   └─ ★ 交叉熵一般要升到 FP32 算，否则数值不稳

★★ 对照账①：7 B 模型的整个 Embedding 矩阵（BF16）只有
   6.14 亿 × 2 字节 = 1.23 GB。
   ⟹ 【一个 micro-batch 的 logits 张量，比整个 Embedding 矩阵还大 2~4 倍。】
   而且前向的 logits、softmax 的输出、反向的梯度往往要同时在显存里。

⚠️ 这就是为什么训练框架一定要做【词表并行的交叉熵】或者【分块 softmax】：
   不是为了省算力，是因为这个张量按朴素写法直接放不下。
   ✅ 实现细节见隔壁 大模型架构入门/02-Embedding与词表.md 的"词表并行"一节。

⚠️ 单位提醒：2.46 GB 和 2.29 GiB 是同一个数的两种写法，差 7.4%
   （1 GiB = 1024³ 字节 = 1.0737 GB）。看到"显存占用 2.3 G"要问清是哪个。
```

### 账③ 罕见 token 训练不足 → glitch token

```
词表里排在最后的那些 token，可能在整个语料里只出现几百次
→ 它们的 embedding 基本停留在随机初始化的状态
→ ★★ 这就是 "glitch token"（故障 token）现象的来源：
   某些 token 一旦出现，模型行为会变得完全不可预测
```

### 账④ ★★★ 04 章的存储成本断崖

```
V ≤ 65,535 → .bin 可以用 uint16，每 token 2 字节
V > 65,535 → .bin 必须用 int32，每 token 4 字节
             （65,535 = 2¹⁶ − 1，uint16 能表示的最大值）

代进 15 T token 的数据集：
   uint16：15e12 × 2 字节 = 3.0e13 字节 = 30.0 TB = 27.3 TiB
   int32 ：15e12 × 4 字节 = 6.0e13 字节 = 60.0 TB = 54.6 TiB
   ★ 直接翻倍，多出 30 TB（= 27.3 TiB）

⚠️ 又是单位：30 TB ≠ 30 TiB，差 10%（1 TiB = 1024⁴ 字节 = 1.0995 TB）。
   买盘按 TB 标，`df -h` 按 TiB 显示 —— 这 10% 足够让一次扩容做错。
```

> ★ **现实的落点**：现在的大模型词表普遍在 **12 万 ~ 20 万**之间。已经远超 65,535，所以**存储翻倍这笔账大家都认了**——因为多语言能力比存储费重要得多。

### ⚠️ 一个 Megatron 特有的坑：词表要能被整除

```
✅ Megatron 有一个参数 --make-vocab-size-divisible-by（默认 128）

原因：★ 输出层（LM head）是按【张量并行 TP = Tensor Parallelism】切开的，
      V 必须能被 (TP 大小 × 128) 整除，才能均匀切分且对齐 GPU 的计算单元

现象：你的 tokenizer 训出来是 149,600 个 token，
      但模型 config 里的 vocab_size 是 151,552
      → ★ 多出来的 1,952 行是【永远不会被用到的填充】
        （151,552 = 128 × 1184，而 149,600 ÷ 128 = 1168.75 不整）

⚠️ 新手困惑："为什么 config 里的 vocab_size 和 tokenizer 的长度对不上？"
   答案就是这个填充。★ 计算 loss 时要把填充位置屏蔽掉，否则概率质量会漏。
```

## 9.5 ★ 压缩率：怎么衡量一个 tokenizer 好不好

```
压缩率 = 平均每个 token 覆盖多少个【字符】
         ★ 越高越好（同样的文本用更少 token）

别名：fertility（生育率）= 每个词平均切成几个 token，★ 越低越好
      —— 是同一件事的倒过来说法，看到别人用哪个都不要慌
```

### ✅ openPangu-2.0 技术报告 Table 4 的一手数据

### ★ 自己量一遍：别让脚本把字节当字符

```python
# ★ 量 tokenizer 压缩率的正确姿势：三个分母全都打印出来
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("你的模型目录")

def report(text, name):
    n_tok  = len(tok.encode(text, add_special_tokens=False))
    n_char = len(text)                          # Unicode 码点数
    n_byte = len(text.encode("utf-8"))          # ★ 和 n_char 完全不是一个数
    n_cjk  = sum(1 for c in text if "一" <= c <= "鿿")   # 只数汉字
    print(f"{name}: {n_tok} token | "
          f"{n_char/n_tok:.2f} 字符/token | "
          f"{n_byte/n_tok:.2f} 字节/token | "
          f"{n_cjk/n_tok:.2f} 汉字/token | "
          f"汉字占全部字符 {n_cjk/max(n_char,1):.0%}")

report("今天天气不错，我们出去散步吧。", "纯中文")
report("The weather is nice today, let's go out for a walk.", "纯英文")
# ★ 最后那一列是关键：如果"汉字占比"只有 60%，
#   那"字符/token"这个数就被 ASCII 拉高了，不能当"汉字/token"读。
```

## 9.6 ★★★ 一个绝佳的教学案例：openPangu 为什么故意选了压缩率更差的那个

看上表：**3digit 变体在五个分项上全部优于 single-digit**（平均 2.71 vs 2.59）。

✅ **但报告明确说：openPangu-2.0 最终采用的是 single-digit 变体。**

先解释这两个变体的区别：

```
数字 "12345" 怎么切？

  3-digit 变体      → "123" + "45"        （按最多 3 位一组合并）
  single-digit 变体 → "1"+"2"+"3"+"4"+"5"  ★ 每个数字单独一个 token
```

✅ 报告给出的理由（我按原文转述）：

```
① 常规 BPE 是按【共现频率】合并数字的
   → "2024" 因为常见被合成一个 token，
     "2025" 可能被切成 "202"+"5"
   ⟹ ★★ 同一个位置上的数字，切法【不一致】
      模型很难学到"个位、十位、百位"这种稳定的结构

② single-digit 让数字表示【完全规整】
   ✅ 报告点名的三个受益场景：
      · 数值推理（做算术）
      · 多模态定位（坐标、bounding box 都是数字）
      · 工具调用（tool 参数里全是数字）

③ 代价：压缩率损失一点点
   平均 2.71 → 2.59，★ 下降 (2.71−2.59)/2.71 = 4.4%
   ⚠️ 注意这里又是"压缩到"与"压缩"的区别：
      2.59 ÷ 2.71 = 95.6%，所以是【压缩率退到原来的 95.6%】，
      也就是序列会变长约 1/0.956 − 1 = 4.6%。
   ★ 而且即便退了这 4.4%，single-digit（2.59）仍然【优于 openPangu-1.0 的 2.56】。
     ⟹ 这笔代价其实是"少赚了"，不是"亏了"。
```

> ★★★ **这个案例值得反复琢磨，因为它推翻了一个很自然的直觉：**
>
> ```
> 错误直觉：tokenizer 的目标是【压缩率最高】
> 实际情况：tokenizer 的目标是【让模型好学】
>           压缩率只是其中一个因素，而且不是最重要的那个
> ```
>
> ★ 同样的逻辑也解释了另外两个业界常见做法：
> ```
> · 代码模型会给【连续空格】和【制表符】专门开 token
>   （早期 GPT-2 没做，导致它写 Python 缩进特别吃力）
> · 多数模型会禁止 token【跨越换行符】合并
>   —— 否则 "。\n第" 会被合成一个 token，破坏结构
> ```
>
> ⚠️ 我的补充：**openPangu 这个选择在 2025 年之后已经接近共识**——多家模型都采用了逐位数字切分。但它把"为什么"写进了报告并给了对照表，这在技术报告里是很少见的坦诚。

## 9.7 训练 tokenizer 的实操

```python
from tokenizers import Tokenizer, models, trainers, pre_tokenizers, decoders

tok = Tokenizer(models.BPE(unk_token=None))       # ★ 字节级 BPE 不需要 unk

tok.pre_tokenizer = pre_tokenizers.Sequence([
    # ★ 数字逐位切开 —— 就是 9.6 说的 single-digit
    pre_tokenizers.Digits(individual_digits=True),
    # ★ 禁止 token 跨越空白与标点合并
    pre_tokenizers.ByteLevel(add_prefix_space=False, use_regex=True),
])
tok.decoder = decoders.ByteLevel()

trainer = trainers.BpeTrainer(
    vocab_size=151552,
    min_frequency=2,
    special_tokens=["<|endoftext|>", "<|im_start|>", "<|im_end|>",
                    "<|pad|>"] + [f"<|reserved_{i}|>" for i in range(64)],
    #                              ★★ 预留一批空 token！见下方说明
    initial_alphabet=pre_tokenizers.ByteLevel.alphabet(),   # 256 个字节全放进去
)
tok.train_from_iterator(sample_corpus_iter(), trainer=trainer)
tok.save("tokenizer.json")
```

### ★ 训练语料怎么选（比算法本身更重要）

```
① ★★ 必须【按最终训练配比采样】
   如果你的训练数据是 中文30% 英文50% 代码20%，
   那 tokenizer 的训练样本也要按这个比例
   ⚠️ 一个典型的失败：拿英文语料训 tokenizer，然后训中文模型
      → 中文大面积退化成字节表示，成本按 9.3 那条账上升 2~3 倍
      （⚠️ "2~3 倍"是按"一个汉字 3 字节 vs 一个 token 覆盖 1.5~2 字"
        推出来的量级，不是某次实测）

② 采样量不需要很大
   ★ 几 GB ~ 几十 GB 就够了，因为 BPE 只看频率统计，收敛很快
   （对比：模型训练要几十 TB）

③ ⚠️ 要先做基础清洗
   如果采样里混进大量乱码或 base64 字符串，
   → 词表里会浪费几千个 token 在垃圾模式上
```

### ★ 为什么要预留 reserved token

```
模型训完之后，你想加一个新的特殊 token（比如新的工具调用标记）：
   → 改词表大小 = 改 Embedding 矩阵形状 = ★ 得重训

⟹ 所以【一开始就预留几十上百个空 token】，以后想加什么直接占用一个
★ 这是所有正经模型的标准做法。你在开源模型的 tokenizer 里
  经常能看到 <|reserved_special_token_37|> 这类东西，就是干这个的。
```

## 9.8 ⚠️ 四个真实会踩的坑

```
① ★★★ 换了 tokenizer 必须重跑 preprocess_data
   .bin 里存的是【整数 id】。换词表后同一个 id 指向完全不同的词。
   ★ 现象：loss 从第一步就停在随机水平且不下降。
   ⚠️ 这是 04 章列的五个坑里【最隐蔽】的一个，因为程序不会报任何错。
   ★ 怎么自查：随机抽几条 .bin 里的 id 序列，用新 tokenizer 解码回文本看看是不是人话。

② 训练和推理用了不同版本的 tokenizer
   哪怕只差一条 merge 规则，切出来的 token 边界就会不同
   （★ 回想 9.2 那个 "lowest" 的例子：规则顺序一换，2 个 token 变 4 个）
   ★ 现象：模型在自己的评测里正常，一上线就变傻
   ★ 这也是 GLM-5.2 报告里提到的 RL 训练"重新 tokenize 会破坏对齐"的同一类问题

③ 特殊 token 被用户输入注入
   用户在输入里打了 "<|im_start|>" 这几个字符 ——
   ⚠️ 如果 tokenizer 把它编码成【真正的特殊 token】而不是普通文本，
      用户就能伪造对话角色。
   ★ 正确做法：用户输入编码时必须关掉特殊 token 解析
      （HuggingFace 里就是 tokenizer(text) 时不要开 special token 解析）

④ glitch token（训练不足的 token）
   词表尾部的罕见 token 在语料里出现次数极少 → embedding 近乎随机
   ★ 现象：某些奇怪字符串会让模型输出完全失控
   ★ 缓解：训完 tokenizer 后统计每个 token 在全语料的出现频次，
          把出现次数低于阈值的 token 剔掉重训
```

## 9.10 小结

```
① 按字切 → 序列太长（注意力 O(L²)）；按词切 → 词表爆炸 + <UNK>/OOV
   ⟹ 子词（subword）是中间路线

② ✅ BPE（Byte Pair Encoding，[1508.07909](https://arxiv.org/abs/1508.07909)，Sennrich 2015）只有一条规则：
   反复合并【出现次数最多的相邻符号对】；并列时必须有确定的打破平局规则
   ★ 9.2 的五轮手算：11 个基础符号 → 16 个，语料 95 token → 57 token
     ⟹ 压缩【到】60%，也就是压缩了 1.67 倍（⚠️ 这两句话不一样！）
   产物 = vocab（token→id）+ ★【有序的】merges 规则表
   ★ 顺序一换，"lowest" 从 2 个 token 变 4 个 —— 所以 tokenizer 必须和权重严格配套
   ★ 它原本是 1994 年的数据压缩算法 —— 所以"压缩率"成了核心指标

③ 字节级 BPE：在 UTF-8 字节上做 → 只有 256 个基础符号 → 永不 <UNK>
   ⚠️⚠️ 三个单位千万别混：字符（码点）/ 字节（UTF-8）/ token
      同一句中文：15 字符 = 45 字节 ≈ 9 token
      按字符算中文 1.7/token、英文 3.6/token（中文看着差一半）
      按字节算中文 5.0/token、英文 3.6/token（★ 中文反而更高）
      ⟹ 换个口径结论反过来
   ⚠️ 一个汉字 3 字节：tokenizer 不含中文 → 中文成本上升 2~3 倍
      ★ 这就是国产模型必须自己重训 tokenizer 的原因

④ ★ 词表大小的四笔账（9.4 全部算出来了）：
   账① V=15万、d=4096 时 Embedding+LM head = 12.3 亿参数
       → 占 1.5B 模型的 31%，但只占 400B 模型的 1.2%
       ★ 所以小模型倾向小词表，大模型才敢做到 20 万
   账② logits 张量 [8192, 150000] FP32 = 4.92 GB = 4.58 GiB
       ★ 比整个 Embedding 矩阵还大 —— 这是词表并行交叉熵存在的真正原因
   账③ 罕见 token 训练不足 → glitch token
   账④★ 04 章的断崖：V>65,535 → .bin 从 2 字节变 4 字节
       15 T token：30.0 TB（27.3 TiB） vs 60.0 TB（54.6 TiB），★ 翻倍
   现实落点：12 万 ~ 20 万
   ⚠️ Megatron 会把 V 补齐到能被 TP×128 整除 → config 和 tokenizer 长度对不上
      （149,600 → 151,552 = 128×1184，多出 1,952 行填充）

⑤ 压缩率 = 每 token 覆盖多少字符（越高越好）；fertility 是它的倒过来说法
   ✅ openPangu-2.0 论文 §2.6 / Table 4：中文 3.82~4.04、代码 2.56~2.80（代码最难压）
   ⚠️⚠️ 但"中文 3.82"不能按"将近 4 个汉字"读：
      报告没披露 Chinese 测试集构成，两种解释都成立
      （① 混了大量 ASCII；② 脚本里的 character 其实按字节算，3.82÷3 ≈ 1.27 汉字）
      ★ 处理口径：Table 4 原样保留，只做【跨变体相对比较】；
        要绝对换算就用 ⚠️ 经验值 1.5~2 汉字/token
   ⚠️ "平均"列比所有分项都低 → 数学上不可能是这五列的加权平均
      ⟹ ⚠️ 推断：它覆盖的语料多于这五列（很可能含 188 种低资源语言）

⑥ ★★★ openPangu 的教学案例：
   3digit 变体五个分项全胜（平均 2.71 vs 2.59），但最终选了 single-digit。
   理由：★ 频率驱动的数字合并【切法不一致】，模型学不到位值结构；
        逐位切分让数值推理、多模态坐标、工具参数都规整
   代价：压缩率 −4.4%（序列长 +4.6%），而且 2.59 仍优于 1.0 的 2.56
   ⟹ ★★ tokenizer 的目标不是"压缩率最高"，是"让模型好学"

⑦ 训 tokenizer：★ 采样必须按最终训练配比；几十 GB 就够；
   ★ 一定要预留几十个 reserved token（否则以后加特殊 token 要重训）

⑧ ⚠️ 四个坑：换词表没重跑 preprocess（loss 卡在随机且不报错）/
   训推 tokenizer 版本不一致 / 用户输入里的特殊 token 注入 / glitch token
