# 11 · ⭐ 喂多少：Scaling Law 与"数据不够用了"

> **这一章回答两个问题：**
> **① 给定算力，应该训多大的模型、喂多少数据？**
> **② 数据不够怎么办——重复用行不行、能重复几遍？**
>
> ★ 第二个问题的答案（**约 4 遍**）是本章最实用的一个数字。
> ★★ 本章所有结论都会**代到 7 B / 70 B / 400 B 三个规模上算一遍卡时**，不只给公式。

---

## 11.1 先把"算力"这个单位钉死

```
N_p = 模型参数量        （很多论文里写作 N）
N_d = 训练总 token 数   （很多论文里写作 D）
C   = 训练总计算量，单位 FLOPs（FLoating-point OPerations，浮点运算次数）

★★ 一个必须记住的近似公式：
        C ≈ 6 · N_p · N_d
```

### ★ 那个 6 是怎么来的：一项一项数

```
考虑【一个参数】在【一个 token】上要被用到几次浮点运算。

① 前向传播（forward）
   这个参数参与一次乘累加（multiply-accumulate）：
       1 次乘法 + 1 次加法 = 2 FLOPs
   ⟹ 前向 = 2 · N_p   （每个 token）

② 反向传播（backward）—— ★ 这里要算【两笔】，不是一笔
   做反向传播时，每一层都要算两个不同的梯度：
     · 对【输入】的梯度（要往下一层传）   → 又一次乘累加 = 2 FLOPs
     · 对【权重】的梯度（要拿去更新参数） → 又一次乘累加 = 2 FLOPs
   ⟹ 反向 = 4 · N_p   （所以"反向约是前向的 2 倍"是这么来的）

③ 合计 = 2 + 4 = ★ 6 FLOPs / 参数 / token
   ⟹ C ≈ 6 · N_p · N_d
```

### ⚠️ `6N` 没有包含什么（这四条每一条都会让人算错）

```
⚠️ ① 不含【优化器更新】
   AdamW 每一步对每个参数做十几次标量运算，但那是【每个优化步一次】，
   不是每个 token 一次。摊到 token 上是 N_p × 10 / (每步的 token 数)，
   ★ 全局 batch 几百万 token 时这一项是千分之几，可以忽略。
   ⟹ 所以"6N 不含优化器"这句话的正确含义是"忽略它没问题"，
      不是"你漏了一大块"。

⚠️ ② 不含【注意力里与序列长度相关的那部分】
   —— 这一项【不能忽略】，长上下文时它会超过 6N。下面单独算。

⚠️ ③ 不含【激活重算（activation recomputation / gradient checkpointing）】
   开了全量重算，前向要多做一遍 → C 变成约 8·N_p·N_d（+33%）。
   ★ 这是工程选择，不是物理量。算卡时的时候要问清楚开没开。

⚠️ ④ Embedding 查表本身不算 FLOP（它是一次索引，不是乘法），
   但【输出层 LM head】是真实的矩阵乘，而且它通常已经被算进 N_p 里了。
```

### ★★ 补全式：`C ≈ (6·N_p + 12·L·s·h) · N_d`

```
L = 层数（layers）
s = 序列长度（sequence length）
h = 隐层宽度（hidden size）

★ 这一项是哪来的？注意力里有两个矩阵乘【不涉及任何参数】：
    ① Q·Kᵀ：每个 token 的 query（长度 h）要和 s 个 key 做点积
             = s·h 次乘累加 = 2·s·h FLOPs
    ② A·V ：注意力权重（长度 s）去加权 s 个 value（宽度 h）
             = s·h 次乘累加 = 2·s·h FLOPs
  前向合计 4·s·h，反向 ×2 = 8·s·h，★ 每层每 token 共 12·s·h
  × L 层 ⟹ 12·L·s·h

⚠️⚠️ 极其重要的一条：这个 12·L·s·h 【没有扣掉因果掩码】。
   自回归模型里第 i 个 token 只能看前 i 个，平均只需要一半的注意力计算。
   ⟹ ★【12·L·s·h 是一个上界】，真实值约为它的一半（≈ 6·L·s·h）。
      ⚠️ 很多博客直接拿 12·L·s·h 当真实值，会把长上下文的成本高估一倍。
```

**代进真实配置看这一项有多大**（⚠️ 下表的 L / h 是按常见开源配置取的典型值，不是某个具体模型的官方参数）：

| 模型量级 | L | h | 序列长度 s | `12·L·s·h` | `6·N_p` | 注意力项占比（上界） | ★ 扣掉因果掩码后 |
|---|---|---|---|---|---|---|---|
| 7 B | 32 | 4,096 | **4 K** | 6.44e9 | 4.2e10 | 15.3% | **约 7.7%** |
| 7 B | 32 | 4,096 | **32 K** | 5.15e10 | 4.2e10 | ★ **122.7%** | **约 61.4%** |
| 7 B | 32 | 4,096 | **128 K** | 2.06e11 | 4.2e10 | ★★ **490.9%** | **约 245.4%** |
| 70 B | 80 | 8,192 | **4 K** | 3.22e10 | 4.2e11 | 7.7% | **约 3.8%** |
| 70 B | 80 | 8,192 | **32 K** | 2.58e11 | 4.2e11 | 61.4% | **约 30.7%** |
| 70 B | 80 | 8,192 | **128 K** | 1.03e12 | 4.2e11 | ★ **245.4%** | **约 122.7%** |

```
★★★ 这张表给出一条很清晰的使用边界：

  序列长度 ≤ 8 K           → ★ 用 6N 就行，误差在 10% 量级以内
  序列长度 32 K            → ⚠️ 注意力项已经和 6N 同量级，必须加上
  序列长度 ≥ 128 K         → ★★ 注意力项【超过】参数项，6N 严重低估

★ 还有一个有意思的对比：同样 32 K 序列，
  7 B 模型的注意力项占 61%，70 B 只占 31%。
  ⟹ 模型越大，"参数项"摊得越开，注意力项反而相对变小。
    这也是为什么长上下文训练在小模型上尤其贵。

⚠️ 本章后面 11.2 / 11.3 的卡时估算都用【6N】（假设序列 4 K ~ 8 K）。
   你自己要算 128 K 上下文的训练，记得把上面那一列加回去。
```

**这个公式的用处**：把"算力"翻译成"模型大小 × 数据量"的一条**等高线**。

```
你有 1e24 FLOPs 的算力预算，那么下面每一组都刚好花光它：

    N_p = 10 B,  N_d = 16.7 T   都满足 6·N_p·N_d = 1e24
    N_p = 70 B,  N_d = 2.4 T
    N_p = 500 B, N_d = 0.33 T

★ 全都"花光了预算"，但效果完全不同 —— 那到底该选哪个？
  ⟹ 这就是 Chinchilla 要回答的问题。
```

## 11.2 ★★ Chinchilla：算力应该怎么分配

✅ **Training Compute-Optimal Large Language Models**
（[arXiv:2203.15556](https://arxiv.org/abs/2203.15556)，Jordan Hoffmann 等，DeepMind，2022-03）

### 它推翻了什么

```
在它之前（2020 年 Kaplan 等的工作影响下），业界的共识是：
   ★ "算力主要应该花在【把模型做大】上，数据量增长可以慢一点"
   ✅ Chinchilla 论文原文转述 Kaplan 的结论：算力涨 10 倍，
      ★ 模型应该涨 5.5 倍，而 token 数只涨 1.8 倍
   → 于是有了 GPT-3（175 B，训了约 300 B token）
     和 Gopher（280 B，训了约 300 B token）

Chinchilla 说：★★ 这些模型全都【严重欠训练】（significantly under-trained）。
```

### 它的结论

```
★★★ 参数量和数据量应该【等比例增长】。
   ✅ 论文原文："for every doubling of model size the number of
      training tokens should also be doubled"

   最优比例（论文的核心经验法则）：
       ★ N_d / N_p ≈ 20     "每 1 个参数配约 20 个训练 token"
```

### 它的证据

```
✅ 论文训了【400 多个】模型（70 M ~ 16 B 以上参数，5 B ~ 500 B token），
   用三种独立方法拟合：
     方法一：固定模型大小，变数据量（Minimum over training curves）
     方法二：固定算力，让参数和 token 同时变（IsoFLOP profiles）
     方法三：拟合一个损失函数（Parametric fit）
   ✅ 三种方法给出的指数一致（见下）。

✅ 最有力的验证：
   训了一个叫 Chinchilla 的模型 —— 70 B 参数、1.4 T token
   用的算力和 Gopher（280 B 参数、300 B token）★ 完全相同
   → Chinchilla 在几乎所有评测上【全面超过】4 倍大的 Gopher
   ★ 参数少 4 倍，数据多 4.7 倍，效果更好
   ✅ 并且 MMLU 平均准确率 67.5%，比 Gopher 高出 7 个百分点以上
```

### ★★ 20 这个数是怎么推出来的：把推导方向写清楚

✅ 论文拟合的损失函数形式（**论文 Eq. 2**）：

```
    L(N_p, N_d)  =  E  +  A / N_p^α  +  B / N_d^β
                    |         |             |
                   (1)       (2)           (3)

✅ 论文拟合值（论文附录 D.2 / Eq. 10）：
      E = 1.69，A = 406.4，B = 410.7，α = 0.34，β = 0.28
```

三项的含义（★ 这是整章唯一需要看懂的公式）：**(1) E = 不可约损失**，也就是语言本身的熵，再多算力也降不下去；**(2) A / N_p^α = 模型不够大带来的损失**，参数越多这一项越小；**(3) B / N_d^β = 数据不够多带来的损失**，token 越多这一项越小。✅ 论文对第 (1) 项的原话是"the loss for an ideal generative process on the data distribution, and should correspond to the entropy of natural text"。

**★ 推导（四步，可以自己验算）**：

```
目标：在算力约束 6·N·D = C 下最小化 L。

第 1 步：用约束把 D 消掉
   D = C / (6N)
   L(N) = E + A·N^(−α) + B·(C/6)^(−β)·N^(β)
                                      └─ ★ 注意这里变成了 N 的【正】次幂：
                                         N 越大 → D 越小 → 这一项越大

第 2 步：对 N 求导并令它等于 0
   dL/dN = −α·A·N^(−α−1) + β·B·(C/6)^(−β)·N^(β−1) = 0

第 3 步：整理
   α·A·N^(−α−1) = β·B·(C/6)^(−β)·N^(β−1)
   N^(α+β) = (α·A)/(β·B) · (C/6)^β

第 4 步：开方，得到论文 Eq. 4 的闭式解
   N_opt = G · (C/6)^a ,   D_opt = (1/G) · (C/6)^b
   其中  G = [ (α·A)/(β·B) ]^(1/(α+β))
         a = β/(α+β) ,  b = α/(α+β) ,  ★ a + b = 1

★★★ 关键一步在这里：
   D_opt / N_opt = (1/G²) · (C/6)^(b−a)

   ⟹ 如果 α = β，那么 a = b = 1/2，于是 (b−a) = 0，
      ★ D/N 就是一个【不随算力 C 变化的常数】—— 这才是
        "等比例增长"和"20 tokens/参数"这条经验法则的真正来源。

   ⚠️ 注意不要把因果说反：
      ❌ 错误说法："α ≈ β，所以加参数和加数据的边际收益差不多，所以 D/N ≈ 20"
      ✅ 正确说法："α = β 使两个指数都等于 1/2，于是 D/N 不随 C 漂移；
                   而 20 这个具体数值来自方法一/二的实测拟合（见下表）。"
```

### ⚠️⚠️ 一个必须知道的矛盾：论文公布的那五个系数，算不出 20

```
把 E=1.69, A=406.4, B=410.7, α=0.34, β=0.28 代进第 4 步的闭式解：

   α+β = 0.62
   a = 0.28/0.62 = 0.4516 ，  b = 0.34/0.62 = 0.5484
   G = [(0.34×406.4)/(0.28×410.7)]^(1/0.62) = (138.18/114.996)^1.6129 = 1.3447

   在 Gopher 的算力 C = 5.76e23 上：
     N_opt = 1.3447 × (9.6e22)^0.4516 = 3.22e10 ≈ 32 B
     D_opt = 9.6e22 / 3.22e10         = 2.98e12 ≈ 3.0 T
     ★ D/N = 92.6     ← ⚠️ 不是 20，是 93

   而且因为 b − a = 0.0968 > 0，★ D/N 会【随算力一路上涨】：
     C = 1.92e19 → D/N ≈ 34
     C = 5.76e23 → D/N ≈ 93
     C = 1.30e28 → D/N ≈ 244

⚠️ 所以"方法三的参数"和"方法一/二的 20:1"以及论文自己的 Table 3
   【内部不一致】。这不是我算错 —— ✅ 已有专门的复现工作指出这件事：
   ✅ "Chinchilla Scaling: A replication attempt"
      （[arXiv:2404.10102](https://arxiv.org/abs/2404.10102)，Besiroglu 等，Epoch AI，2024-04）
      它报告了三条：
        ① 论文公布的参数对重建数据拟合得不好；
        ② 论文给的置信区间窄到需要几十万次实验才能支撑，而实际只有约 400 次；
        ③ ★ 这组参数蕴含的分配策略与论文自己的方法一/二、
           以及训练 Chinchilla 时用的 20:1 经验法则【互相矛盾】。
      ✅ 它重新拟合后得到的点估计约为【25.6 tokens/参数】，与 20:1 相容。
      ⚠️ 这篇论文不在本目录 papers/ 内，以上是转述其公开摘要与结论。

★★★ 所以本章的使用口径（请照这个来）：
   ✅ 要一个【能用的数】：用 Table 3 / 20:1（本章后面全部用这个）
   ✅ 要理解【为什么是等比例】：用 11.2 那四步推导
   ⚠️ 不要拿 (E, A, B, α, β) 这五个数去算最优点 —— 算出来的不是 20
```

```python
# ★ 你可以自己跑一遍，亲眼看看那五个系数给出的 D/N 不是 20
import numpy as np

def chinchilla_closed_form(C, A=406.4, B=410.7, al=0.34, be=0.28):
    """返回 (最优参数量, 最优 token 数)；用的是 11.2 第 4 步的闭式解"""
    G = ((al * A) / (be * B)) ** (1.0 / (al + be))
    a = be / (al + be)
    N = G * (C / 6.0) ** a
    return N, (C / 6.0) / N

for C in [1.92e19, 5.76e23, 1.30e28]:
    N, D = chinchilla_closed_form(C)
    print(f"C={C:.2e}  N_p={N/1e9:9.2f} B  N_d={D/1e12:8.2f} T  D/N={D/N:6.1f}")
# 输出的 D/N 是 34 / 93 / 244 —— ⚠️ 和 Table 3 的 20~21 差很远，见上面那段说明
```

## 11.3 ★★★ 但现在没有人按 Chinchilla 训了

这是本章**最重要的一段**，也是新手最容易被误导的地方。

| 模型 | 参数 N_p | 训练 token N_d | **D/N** | 是 Chinchilla 最优（20）的几倍 |
|---|---|---|---|---|
| Gopher（2021） | 280 B | 300 B | **1.07** | ⚠️ 0.05 倍 —— ★ 严重**欠**训练 |
| Chinchilla（2022） | 70 B | 1.4 T | **20** | 1 倍（基准点） |
| LLaMA-2 系列的 7 B 档 | 7 B | 2 T | **286** | ★ **14.3 倍** |
| Llama-3-8B | 8 B | 15 T | **1,875** | ★★ **93.8 倍** |

⚠️ **上表的来源说明**：Chinchilla 与 Gopher 两行 ✅ 来自 Chinchilla 论文（本目录 `papers/` 内）；**LLaMA-2 / Llama-3 两行的 token 数取自 Meta 的公开说法（分别是"2 万亿 token"和"超过 15 万亿 token"），⚠️ 这两篇报告不在本目录 `papers/` 内，我没有回溯一手 PDF**；D/N 与倍数两列是我按前两列算的。

```
按 Chinchilla 的标准，后两行是【极度过训练（over-trained）】。
那 Meta 是算错了吗？—— ★ 没有。是【优化目标不同】。
```

### ★★ 为什么：把推理成本也放进目标函数

```
★★ Chinchilla 优化的是【训练算力】。
   但一个模型训完之后，要被【推理几万亿次】。

   总成本 = 训练成本（一次性） + 推理成本（× 调用次数）
                                  └─ ★ 商业上这一项通常大得多 ─┘

★ 推理的 FLOP 账（自回归生成，忽略注意力项和 prefill）：
     每生成 1 个 token ≈ 2 · N_p FLOPs（★ 只有前向，所以是 2N 而不是 6N）
   ⟹ 一生推理成本 ≈ 2 · N_p · N_inf     （N_inf = 一生要生成的 token 总数）
```

**★★ 盈亏平衡算一遍**（下面的数字可以自己验算）：

```
设：一个 70 B 模型，按 Chinchilla 最优训（1.4 T token）
    训练成本 C_train = 6 × 7e10 × 1.4e12 = 5.88e23 FLOPs

它一生要生成多少 token？分三档看推理成本 2 · N_p · N_inf：

   N_inf = 10 T（1e13）output token  → 1.4e24 FLOPs = 训练的 ★ 2.4 倍
   N_inf = 100 T（1e14）output token → 1.4e25 FLOPs = 训练的 ★★ 23.8 倍
   N_inf = 1 P（1e15）output token   → 1.4e26 FLOPs = 训练的 ★★★ 238 倍

⚠️ 量级参照：1e14 output token ÷ 365 天 ≈ 每天 2740 亿 output token。
   对一个被广泛调用的商业模型，这个量级是现实的。
   ⟹ ★ 推理成本比训练成本大一两个数量级，这不是夸张。
```

```
★★★ 于是"该不该过训"就变成一道可以算的题：

设想把模型【砍一半】：70 B → 35 B，仍然服务 1e14 个 output token。

  推理侧省下：2 × (7e10 − 3.5e10) × 1e14 = ★ 7.0e24 FLOPs

  把省下的这 7.0e24 全部投进训练（加在 35 B 的 Chinchilla 最优之上）：
      35 B 的 Chinchilla 最优训练 = 6 × 3.5e10 × 7e11 = 1.47e23
      新的训练预算 = 7.0e24 + 1.47e23 = 7.15e24 FLOPs
      对应的 token 数 = 7.15e24 ÷ (6 × 3.5e10) = ★ 3.40e13 = 34 T token
      ⟹ D/N = 34e12 / 3.5e10 = ★★ 约 972 : 1

★★★ 结论：只要这个模型的一生推理量到了 100 T output token 这个量级，
     你可以把一个 35 B 模型【喂到 34 T token（972:1）】，
     总成本（训练 + 推理）仍然不高于"70 B 喂 1.4 T"，
     而且每一次推理【永久便宜一半】。

⟹ ★★ 这就是 LLaMA 系列把 7 B 档喂到 2 T token（286:1）、
     Llama-3-8B 喂到 15 T（1875:1）的全部理由。
     ★ 不是算错，是把目标函数从"训练算力"换成了"训练 + 一生推理"。

⚠️ 上面这笔账做了三处简化，不要当精确结论用：
   ① 假设"35 B 喂到 34 T"真能追上"70 B 喂 1.4 T"的能力 ——
      ★ 这一步需要标度律来回答，而过训区间的标度律本身就不可靠（见 11.5）；
   ② 只算了 FLOPs，没算显存、带宽、KV cache ——
      ⚠️ 实际推理成本里访存经常是瓶颈，而 KV cache 也随模型变小而变小，
      ★ 所以真实的推理侧收益通常比这笔 FLOP 账【更大】；
   ③ 没算"模型变小 ⟹ 能力上限变低"这个硬约束。
```

> ✅ **这件事有专门的论文把它形式化了**：*Beyond Chinchilla-Optimal: Accounting for Inference in Language Model Scaling Laws*（[arXiv:2401.00448](https://arxiv.org/abs/2401.00448)，Sardana 等，2024-01）把目标函数从"训练 FLOPs"改成"**训练 + 一生推理的总 FLOPs（或总美元）**"，再去求最优的 (N, D)。⚠️ 该论文不在本目录 `papers/` 内，上面那笔账是我按同一个思路自己算的，不是它的原文数字。

一张对照表帮你记住（⚠️ 我的整理，用于建立直觉）：

| 你真正在优化什么 | 最优策略 | D/N 典型值 |
|---|---|---|
| ★ 只关心训练算力 | Chinchilla 最优点 | **约 20** |
| ★ 关心部署后的推理成本 | 过训练小模型 | **100 ~ 2,000** |
| ★ 追求绝对能力上限 | 两者都拉满 | 视预算而定 |
| ★ 要在手机 / 边缘设备上跑 | ★★ 极度过训小模型 | **> 1,000** |

> ★★ **给小白的一句话总结**：
> **Chinchilla 告诉你"在给定训练算力下损失最低的点在哪"，但那个点【不是商业上最优的点】。**
> 现在的模型几乎全都**故意站在 Chinchilla 曲线的右边**（数据更多、模型更小）。
>
> ⚠️ 所以看到有人说"这个模型不符合 Chinchilla 最优、训练是浪费的"，这是**对 Chinchilla 的误用**。

### ★ 这直接引出了本教程的核心矛盾

```
模型故意变小 + 数据量拉到极致
   ⟹ ★★ 对【数据量】的需求爆炸式增长
   ⟹ 而高质量网页是【有限的】
   ⟹ 于是有了 11.4 的问题：不够了怎么办？

★ 把 11.2 那张卡时表和这里的过训倍数乘起来，感受一下这个需求有多猛：
    7 B 按 Chinchilla 训：140 B token，4,100 卡时
    7 B 喂到 2 T：        2 T token，约 5.9 万卡时   ← ★ 算力 14.3 倍
    8 B 喂到 15 T：       15 T token，约 50.6 万卡时 ← ★ 算力 94 倍
  ⟹ 同一个尺寸的模型，"过训"让训练账单涨了两个数量级。
    ★ 大家还是愿意付 —— 因为推理账单更大。
```

## 11.4 ⚠️ 数据墙：到底还剩多少数据

### ✅ 一个可以引用的一手数字

✅ Scaling Data-Constrained Language Models（[arXiv:2305.16264](https://arxiv.org/abs/2305.16264)）在**论文 §1** 开头给了一个很具体的推算：把 Chinchilla 的分配律外推到一个 **530 B 参数**的模型，需要训 **11 T token**，✅ 论文原话是这"对应**超过 30 TB 的文本数据**"。

```
★ 先自己验算一下这两个数：
   530e9 × 20 = 1.06e13 ≈ 11 T token  ✓ 就是 20:1
   30e12 字节 ÷ 11e12 token ≈ ⚠️ 2.7 字节/token
     —— 这是【英文纯文本】的典型口径（约 4 个 ASCII 字符一个 token，
        再扣掉空白的共享）。中文完全不是这个数，见 09.3。
```

### ⚠️ 换算成存储时，三件事千万别混

| | 它是什么 | 15 T token 对应多少 |
|---|---|---|
| **原始文本**（.jsonl / .txt，UTF-8） | 清洗后的人类可读文本 | ⚠️ 按 2.7 字节/token ≈ **40.5 TB = 36.8 TiB** |
| **训练用 .bin**（token id，int32） | 04 章那个整数数组 | **60.0 TB = 54.6 TiB**（见 09.4 账④） |
| **训练用 .bin**（token id，uint16） | 词表 ≤ 65,535 才能用 | **30.0 TB = 27.3 TiB** |

```
★★ 注意一件反直觉的事：
   【tokenize 之后文件反而变大了】（40.5 TB → 60.0 TB）。
   因为一个 token id 占 4 个字节，而它平均只代表 2.7 个字节的原文。
   ⟹ ★ 做容量规划时，原始文本和 .bin 要【分别算，然后相加】，
      因为两份通常都要留着（.bin 要能重建，原文要能复查）。

⚠️ 而且上面六个数里 TB 和 TiB 差 10%：
   1 TiB = 1024⁴ 字节 = 1.0995 TB。
   ★ 买盘按 TB 标，`df -h` 按 TiB 显示 —— 一次 300 TB 的采购，
     这 10% 就是 30 TB 的缺口。
```

### ⚠️ 还剩多少：量级估算

```
⚠️ 以下是我整理的量级估算，不是任何一篇论文的精确结论：

   Common Crawl 全部快照去重后的英文文本    ~ 几十 T token 量级
   加上所有语言、代码、论文、书籍            ~ 100 ~ 数百 T token 量级

   而单个前沿模型的训练量已经到了 15 ~ 30 T token

★★ 结论：数量级上已经【在同一个量级】了。

✅ 一个可引用的外部佐证：Scaling Data-Constrained LMs 论文 §1 引用了
   Villalobos 等的估计 —— ★ 在 Chinchilla 分配律 + 模型越做越大的趋势下，

   ⚠️ Villalobos 等的原论文不在本目录 papers/ 内，这里是转引。
   ⚠️ 而且注意：11.3 说明了现在大家【不按 Chinchilla 训】，

## 11.5 ★★★ 重复几遍还有用？答案是"约 4 遍"

✅ **Scaling Data-Constrained Language Models**
（[arXiv:2305.16264](https://arxiv.org/abs/2305.16264)，Niklas Muennighoff 等，HuggingFace / Harvard / 图尔库大学，2023-05，NeurIPS 2023 最佳论文亚军）

**这是本教程最实用的一篇论文。** 它系统地回答了"数据不够时重复用会怎样"。

### 实验设置（★ 这个设置必须看懂，否则结论会读反）

```
✅ 训了 400 多个模型，1000 万 ~ 90 亿参数，最多重复到 1500 个 epoch
✅ 拟合用了其中 182 个样本

★★★ 关键：它的对照是【固定总训练 token 数，变唯一数据量】，
     不是"训更久"。
   ✅ 论文 Table（Figure 4 下方）给的三组设定：

     算力 C      参数 N    总训练 token D    唯一数据量 D_C 的八个档
     9.3e20      2.8 B     55 B              55 / 28 / 18 / 14 / 11 / 9 / 4 / 1.25 B
     2.1e21      4.2 B     84 B              84 / 42 / 28 / 21 / 17 / 12 / 6 / 1.9 B
     9.3e21      8.7 B     178 B             178 / 88 / 58 / 44 / 35 / 25 / 13 / 4 B

   ★ 读法：同一行里所有八个模型都训了【一样多的 token】，
     唯一数据量越小 → epoch 数越多（178/44 = 4 epoch，178/4 ≈ 44 epoch）。
   ⟹ 所以结论是"同样的算力，手头唯一数据少到什么程度才开始吃亏"，
     ★ 而不是"重复训能不能当成更多算力用"。
```

### ✅ 核心结论一：4 遍以内几乎没有代价

```
★★★ ✅ 论文原文："training with up to 4 epochs of repeated data
   yields negligible changes to loss compared to having unique data."

✅ 论文给的具体实例（★ 这就是"几乎没有差别"的量化）：
     8.7 B 参数模型，总共训 178 B token。
       方案 A：178 B 唯一 token，训 1 遍
       方案 B：★ 44 B 唯一 token，训 4 遍
     ⟹ 方案 B 的最终验证 loss 只比方案 A ✅【高 0.5%】。

★★ 换成人话：你手上只有四分之一的数据，
   但把它重复 4 遍去填满同样的训练预算，
   最终效果和"真有 4 倍数据"几乎一样。
   ★ 这是数据受限时最划算的一招。
```

### ✅ 核心结论二：★★ 它给出了"有效 token 数"的公式——可以代进去算

✅ 论文把"重复数据的价值衰减"显式建模进了一个修正版的 Chinchilla 公式。**它的核心就是一个替换**：公式里原本的 `D`（实际过了多少 token）被换成 `D'`（**有效 token 数**）：

```
     D' = U + R*_D · U · ( 1 − e^(−R_D / R*_D) )
          │   └──────────────┬──────────────┘
          │                  └─ 重复部分贡献的"等效新数据"
          └─ 第一遍（唯一数据本身），价值 100%

  U     = 唯一 token 数（unique tokens）
  R_D   = ★ 重复【次数】= epoch 数 − 1（训 1 遍时 R_D = 0）
  R*_D  = ✅ 论文拟合出的常数 = 15.387756（论文附录 B，通常写作 ≈ 15.4）
          ★ 它的含义：重复的"半衰期"——超过这么多次之后收益急剧衰减
  （另有 R*_N = 5.309743 管"多余参数"的衰减；R*_N < R*_D 说明
    ★ 多余的参数比重复的数据衰减得更快 ⟹ 数据受限时应该优先加 epoch 而不是加参数）
```

**★★ 代进去算一张表**（下表每一行我都用上面那个公式算过，可以自己复核）：

| epoch 数 | 重复次数 R_D | **有效 token D'/U** | 实际过的量 /U | ★ 有效率 | ★ 这一遍相当于几遍新数据 |
|---|---|---|---|---|---|
| 1 | 0 | **1.000** | 1 | **100.0%** | 1.000（基准） |
| 2 | 1 | **1.968** | 2 | **98.4%** | 0.968 |
| 3 | 2 | **2.875** | 3 | **95.8%** | 0.907 |
| **4** | **3** | ★ **3.726** | 4 | ★ **93.1%** | ★ **0.850** |
| 5 | 4 | 4.522 | 5 | 90.4% | 0.797 |
| 8 | 7 | 6.624 | 8 | 82.8% | 0.656 |
| **16** | **15** | ★ **10.582** | 16 | ★ **66.1%** | ★ **0.390** |
| 32 | 31 | 14.335 | 32 | 44.8% | 0.138 |
| **41** | **40** | ★ **15.244** | 41 | ★ **37.2%** | ★★ **0.077** |
| 101 | 100 | 16.365 | 101 | 16.2% | 0.002 |
| **→ ∞** | ∞ | ★★★ **16.388**（= 1 + R*_D） | ∞ | → 0 | 0 |

```
★★★ 这张表一次性解释了 4 / 16 / 40 这三个刻度，而且它们不是三条独立的经验：

  · epoch = 4   → 有效率 93.1%，这一遍还值 0.850 遍新数据
                  ⟹ ★【零代价线】。只亏 7%，loss 上看不出来（实测 +0.5%）。
  · epoch = 16  → 有效率 66.1%，这一遍只值 0.390 遍新数据
                  ⟹ ★【还值得做线】。✅ 论文原话是"repeating can be made
                     up to around 16 epochs"。
  · epoch = 41  → 这一遍只值 0.077 遍新数据，有效 token 已经爬到 15.24，
                  ★ 距离天花板 16.39 只剩 7%
                  ⟹ ★★【死线】。✅ 论文 Figure 1 的标注就是
                     "At 40 epochs, repeating is worthless"。

★★★ 而最该记住的是最后一行那个【天花板】：
     不管你重复多少遍，有效 token 数永远不会超过 ★ 16.4 × U。
     ⟹ 这就是"重复用"这条出路的硬上限。
       你有 1 T 唯一数据，无论怎么重复，最多也只相当于 16.4 T 新数据。
       ★ 想突破这个上限，只能靠 12 章的合成数据或者 05/07 章的放松过滤。

⚠️ 一句必须补的：上面"有效率 93.1%"说的是【有效 token 数】打了 7% 折，
   不是【loss 变差 7%】。loss 里这一项还要再开 0.35 次方，
   而且 loss 里还有不可约项 1.87 压着 ——
   ★ 用论文自己的公式（附录 Eq. 17）算方案 A / B 的 loss：
       A（178 B 唯一，1 遍）= 2.2122
       B（ 44 B 唯一，4 遍）= 2.2314   → ⚠️ 高 0.87%
   ✅ 论文实测是 0.5%，我按它自己的拟合公式算是 0.87%，
     ★ 同一个量级，说明"0.5%"这个实测值和公式是自洽的。
```

### ✅ 核心结论三：下游任务的拐点和 loss 的拐点**在同一个位置**

```
✅ 论文 §7 / Figure 6（4.2 B 模型、总 84 B token、19 个任务的平均分）原话：
   "differences in downstream performance are insignificant for up to
    around 4 epochs (25% budget) and then start dropping,
    ★ which aligns with our results on test loss in §6."

⚠️⚠️ 这里要纠一个很容易传错的说法：
   ❌ 错误："下游任务比 loss 更早变差，所以按 4 把关更稳"
   ✅ 正确：✅ 论文明确说下游的拐点【与 loss 的拐点一致】，都在 4 epoch 附近。

★ "按 4 来把关"这个建议依然成立，但理由不是"下游更早崩"，而是：
   ① 4 epoch 以内【loss 和下游同时】几乎无损（zero-cost 区间）；
   ② 过了 4 之后两者【同时】开始掉，而下游分数的噪声更大、更难察觉。
```

### ✅ 核心结论四：数据受限时，"坏做法"反而划算

```
✅ 论文 §7 做了三条替代策略的对照（4.2 B 模型、总 84 B token）：

  ① 【混入代码】补足缺的自然语言 token
     ✅ 用 The Stack 的 Python 代码去填，和自然语言随机打散
     ✅ 结论：填到 50% 都还能保住下游表现
     ⟹ ★ 这不是"代码让模型更聪明"，而是"代码比重复第 10 遍更值"

  ② 【放宽困惑度过滤】
     ✅ 设定：从 178 B token 出发（是预算的两倍），
        取困惑度最低的 25% → 得到 44 B，再重复近 2 遍填满 84 B
  ③ 【放宽去重】
     ✅ 设定：删掉 100 字符重叠的样本 → 只剩 21 B，要重复 4 遍

  ✅ 论文的总体判断：数据受限时，与其把数据筛得很干净然后反复重复，
     ★ 不如留下更多（稍脏的）唯一数据。
  ⟹ ★★ 这直接为 Nemotron-CC 的"主动放松过滤"提供了理论依据
     （见 [07 章](07-质量过滤.md)）。
```

          不是论文的实测曲线；纯 ASCII，可以数格子）

★ 图上三个标记的含义：**A = epoch 4，零代价线**（这一遍还值 0.850 遍新数据）；**B = epoch 16，还值得做线**（0.390 遍）；**C = epoch 41，死线**（0.077 遍）。

> ★★★ **这个"4"是本章最该记住的数字。** 它直接给了你一条**可操作的检查规则**：
>
> ```
> 回到 [10 章](10-数据配比.md) 10.7 那段代码 —— 它会打印每个数据集重复几遍。
> ★ 任何一项超过 4，就要警惕：
>    这部分权重可能是【浪费】的，不如降下来给别的数据。
> ★ 回想 10.7 那个算例：wiki 那一行是 9.00 遍
>    → 查上表，epoch 9 的有效率只有 80.4%，第 9 遍只值 0.614 遍新数据
>    → ⚠️ 这 3% 的配比预算里，有五分之一是白花的。
> ```
>
> ⚠️ **注意边界条件**：这个"4"是在**该论文的实验设定下**（C4 / OSCAR、最大 8.7 B 参数、最多 178 B token）得出的。数据质量越高、越多样，可重复次数可能更多；反之更少。**把它当作一个数量级参考，而不是一条物理定律。**

## 11.6 把三章串起来：一个完整的决策流程

```
输入：算力预算 C，手头的唯一数据量 U，部署后预期的一生推理量 N_inf

  ① 先按 Chinchilla 算一个参考点（11.2）
        在 D = 20·N 和 C = 6·N·D 两个条件下解 N：
            120 · N² = C   ⟹   N* = sqrt(C / 120)，  D* = 20 · N*

  ② 根据推理量【往右修正】：推理量越大，模型越往小调（11.3）
        N = N* / k        （k 常见取 2 ~ 10；N_inf 越大，k 越大）
        D = C / (6 · N)   ← ★ 数据量自动放大 k 倍（因为 C 固定）

  ③ 检查数据够不够（11.5）
        epochs = D / U
        if epochs <= 4 :  ✅ 够，重复不超过 4 遍，有效率 ≥ 93%
        elif epochs <= 16: ⚠️ 还能做，但要接受有效率掉到 66~93%
        else:              ❌ 不行，三选一或组合：
              · 放松过滤，把 U 做大                    # 05 / 07 章
              · 合成数据                              # 12 章
              · ★ 承认上限，把 D 压回 4·U，把省下的算力给 N

  ④ 把 C 折成卡时，确认工期排得下（11.2）
        卡时 = C / (峰值 FLOPS × MFU × 3600)

  ⑤ 在 D 内部分配各领域配比                            # 10 章
  ⑥ 检查每个数据集各自的重复次数是否也 ≤ 4             # 10.7 的代码
  ⑦ 设计多阶段退火，把最好的数据留到最后 10~20%        # 10.6
```

### ★★ 走一遍完整算例

```
给定：C = 1e24 FLOPs，手头唯一数据 U = 3 T token，预期一生推理 1e14 output token

① Chinchilla 参考点
     120 · N² = 1e24  →  N² = 8.333e21  →  N* = 9.13e10 = ★ 91.3 B
     D* = 20 × 9.13e10 = 1.826e12 = ★ 1.83 T token
     验算：6 × 9.13e10 × 1.826e12 = 1.00e24 ✓

② 按推理量往小调。1e14 output token 这个量级（11.3 算过，推理是训练的 20 多倍），
   取 k = 4：
     N = 91.3 B / 4 = ★ 22.8 B
     D = 1e24 / (6 × 2.28e10) = ★ 7.30 T token
     D/N = 7.30e12 / 2.28e10 = ★ 320 : 1   （Chinchilla 最优的 16 倍）

③ 数据够不够？
     epochs = 7.30 T / 3 T = ★ 2.43 遍
     2.43 ≤ 4  ⟹ ✅ 够。
     查 11.5 那张表（R_D = 1.43）：有效 token = 2.374 × U，
     实际过了 2.434 × U  →  ★ 有效率 97.4%，只亏 2.6%。
     ⟹ ✅ 这个配置是健康的。

④ 卡时
     1e24 ÷ 1.424e18 = ★ 70.2 万卡时
     2,048 张 H100 → 343 小时 ≈ ★ 14.3 天墙上时间
     ⚠️ 别忘了乘一个"实际会重启/掉卡/调参"的系数，1.3 ~ 2 倍很常见。

⑤~⑦ 剩下三步回 10 章。

★★ 如果第③步算出来是 8 遍怎么办？三条路的账可以直接比：
   · 把 D 压回 4·U = 12 T？—— ⚠️ 不行，12 T > 7.30 T，本来就没超
     （这条路是给"D 远大于 4U"的情形用的）
   · 真遇到 D = 24 T、U = 3 T（8 遍）：
       方案甲：D 压回 4U = 12 T，省下的算力给 N
               → N = C/(6·12e12)，模型变大一倍，★ 但推理永久变贵
       方案乙：合成 / 放松过滤，把 U 从 3 T 做到 6 T
               → 8 遍降到 4 遍，有效率从 82.8% 回到 93.1%
       方案丙：硬着头皮训 8 遍
               → 有效率 82.8%，相当于白扔 17% 的算力
     ⟹ ★ 三条路都能算出数来，这就是本章的用处。
```

> ★ 这七步就是"数据侧顶层设计"的全部骨架。**记住这个流程，比记住任何一个具体数字都有用。**

## 11.7 小结

```
① ★★ C ≈ 6 · N_p · N_d  —— 把算力翻译成"模型大小 × 数据量"
   6 的来源：前向 2（一次乘累加）+ 反向 4（对输入的梯度 2 + 对权重的梯度 2）
   ⚠️ 不含：优化器更新（可忽略，千分之几）/ 激活重算（开了要 ×1.33）/
          ★ 注意力里与序列长度相关的那部分（不能忽略）
   ★★ 补全式 C ≈ (6·N_p + 12·L·s·h) · N_d
      ⚠️ 12·L·s·h 是【上界】，没扣因果掩码，真实值约为它的一半
      代入后的使用边界：s ≤ 8 K 用 6N 就行；s = 32 K 注意力项同量级；
      s ≥ 128 K 时注意力项【超过】参数项（7 B / 128 K：491% 上界，约 245% 实际）

② ✅ Chinchilla（2203.15556）：参数量和数据量应【等比例增长】
   ★ 最优 N_d / N_p ≈ 20（✅ 论文 Table 3 实测 20.0 ~ 21.6，九个数量级只漂 8%）
   证据：400+ 个模型 + 三种方法；
        ★ 70 B / 1.4 T 的 Chinchilla 在同等算力下全面超过 280 B / 300 B 的 Gopher
   公式：L = E + A/N_p^α + B/N_d^β，✅ E=1.69, A=406.4, B=410.7, α=0.34, β=0.28
   ★★ 20 的推导（11.2 四步）：代入约束 → 求导 → N_opt = G·(C/6)^(β/(α+β))
      ⟹ ★【α = β 时两个指数都是 1/2，D/N 才不随 C 漂移】
        ⚠️ 不要说成"α≈β 所以边际收益相等所以 20"，因果是反的
   ⚠️⚠️ 把公布的五个系数代进闭式解，在 Gopher 算力上得到 D/N = 93 而不是 20，
      且 D/N 随算力从 34 爬到 244 —— ★ 方法三与方法一/二【内部不一致】
      ✅ 已有复现工作指出此事（[2404.10102](https://arxiv.org/abs/2404.10102)，Epoch AI），
         重拟合后约 25.6 tokens/参数，与 20:1 相容
      ⟹ ★ 口径：要数就用 Table 3 / 20:1，别用那五个系数去算最优点

③ ★★ 卡时账（⚠️ H100 BF16 稠密 989 TFLOPS、MFU 40% ⟹ 1.424e18 FLOP/卡时；
   ⚠️⚠️ 规格表上 1,979 TFLOPS 是【开稀疏】的，拿它算会少一半）：
      7 B   / 140 B token / C=5.88e21 → 约 4,100 卡时（64 卡 2.7 天）
      70 B  / 1.4 T       / C=5.88e23 → 约 41.3 万卡时（1024 卡 16.8 天）
      400 B / 8 T         / C=1.92e25 → 约 1,348 万卡时（8192 卡 68.6 天）
   ★ 形状：参数 ×10 ⟹ token ×10 ⟹ ★ 算力 ×100（平方关系）

④ ★★★ 但现在没人按 Chinchilla 训（本章最重要的一段）：
   LLaMA-2 的 7 B 档 D/N = 286（14.3 倍），Llama-3-8B D/N = 1875（93.8 倍）
   ★ 原因：Chinchilla 只优化【训练】算力，而商业上【推理】成本大得多
      推理每 token ≈ 2·N_p（只有前向）
      70 B 模型服务 1e14 output token → 推理 1.4e25 FLOPs = 训练的 ★ 23.8 倍
   ★★ 盈亏平衡算例（11.3）：70 B → 35 B 推理省 7.0e24 FLOPs，
      全投进训练可以把 35 B 喂到 ★ 34 T token（972 : 1），总成本不增，
      而每次推理【永久便宜一半】⟹ 这就是过训的全部理由
   ✅ 形式化版本见 [2401.00448](https://arxiv.org/abs/2401.00448)（⚠️ 不在本目录 papers/）
   ⚠️ 所以"不符合 Chinchilla 就是浪费"是对它的误用

⑤ ⚠️ 这直接造成了【数据墙】：
   ✅ 论文一手数字：530 B 参数按 20:1 要 11 T token = "超过 30 TB 文本"
      ⟹ ⚠️ 约 2.7 字节/token（英文口径，中文完全不同）
   ⚠️⚠️ 三种存储别混（15 T token 为例）：
      原始文本 40.5 TB（36.8 TiB）/ .bin int32 60.0 TB（54.6 TiB）/
      .bin uint16 30.0 TB（27.3 TiB）
      ★ tokenize 之后文件反而变大（4 字节的 id 代表 2.7 字节的原文）
      ⚠️ TB 与 TiB 差 10%，300 TB 的采购里这就是 30 TB 的缺口
   ⚠️ 可用文本总量（~100 至数百 T token 量级）与单模型训练量（15~30 T）
      已经在同一个数量级上

⑥ ★★★ ✅ Scaling Data-Constrained LMs（2305.16264）——最实用的一篇：
   ★ 实验设置要看懂：固定总训练 token，变【唯一数据量】；
     不是"训更久"，而是"手头数据少到什么程度才开始吃亏"
   · ✅ 重复最多约 【4 个 epoch】，loss 几乎无差别
     ✅ 实例：8.7 B 模型 / 总 178 B token，用 44 B 唯一重复 4 遍，
        验证 loss 只比"178 B 唯一训 1 遍"高 0.5%
   · ★★ 有效 token 公式：D' = U + R*_D·U·(1 − e^(−R_D/R*_D))，
     ✅ R*_D = 15.387756（另 R*_N = 5.309743，★ R*_N < R*_D ⟹
        数据受限时优先加 epoch 而不是加参数）
     代入后 4 / 16 / 40 三个刻度全部对上（11.5 那张表）：
        epoch 4  → 有效率 93.1%，这一遍值 0.850 遍新数据  = 零代价线
        epoch 16 → 有效率 66.1%，这一遍值 0.390 遍新数据  = 还值得做线
        epoch 41 → 这一遍只值 0.077 遍，有效 token 15.24  = 死线
     ★★★ 天花板：D'/U 最多 = 1 + R*_D = 16.4
        ⟹ 1 T 唯一数据，无论怎么重复最多只相当于 16.4 T 新数据
   · ⚠️⚠️ 纠一个常见传错：✅ 论文说下游任务的拐点【与 loss 一致】
     （"up to around 4 epochs ... then start dropping, which aligns with
       our results on test loss"），★ 不是"下游比 loss 更早变差"
   · ★ 数据受限时，混入代码（填到 50% 仍可）、放宽过滤反而划算
     → 为 Nemotron-CC 的"主动放松过滤"提供了理论依据
   ⚠️ "4"是该实验设定下（C4/OSCAR、≤8.7 B、≤178 B token）的结论，
      当量级参考用，别当物理定律

⑦ ★ 决策流程七步：Chinchilla 算参考点（N*=sqrt(C/120)）→ 按推理量往小调 k 倍 →
   检查 epochs = D/U ≤ 4 → 折成卡时核工期 → 定配比 →
   检查各数据集重复次数 → 设计退火
   ★★ 11.6 的算例：C=1e24、U=3 T、k=4 ⟹ 22.8 B / 7.30 T / 320:1 /
      2.43 遍（有效率 97.4%）/ 70.2 万卡时 / 2048 卡 14.3 天
```
