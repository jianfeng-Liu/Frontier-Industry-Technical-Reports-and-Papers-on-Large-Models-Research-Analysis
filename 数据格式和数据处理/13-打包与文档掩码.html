13 · ⭐ 打包与文档掩码：最后一公里的效率与正确性

数据已经洗干净、配好比、转成 .bin 了。最后一个问题是：
长短不一的文档，怎么塞进一个整整齐齐的 [B, L] 张量？

★ 这一章讲的东西直接决定训练速度，而且藏着一个很多人不知道自己踩了的正确性坑。

13.1 问题的由来

GPU 要的是一个规整的张量：   tokens.shape = [B, L] = [512, 4096]

而你手上的文档长这样：
    doc0   312 token
    doc1  8734 token
    doc2    47 token
    doc3  1205 token
    ...
    ★ 长度分布通常是【重尾】的：大量很短的，少量极长的

三种做法：

① 补齐（padding）
   [doc0 ----312---][PAD PAD PAD ... PAD]  共 4096
   ❌ ★ 浪费巨大

② 截断（truncation）
   doc1 只取前 4096，后面 4638 个 token ★ 直接扔掉
   ❌ 丢数据，且长文档的后半永远学不到

③ ★ 拼接后切分（concatenate & chunk）
   把所有文档首尾相接成一条长流，每 4096 切一刀
   ✅ 零浪费、零丢弃
   ❌ ★★ 一条样本里会混进好几篇【毫不相干】的文档 → 13.4 的正确性问题

★★★ 关键认知（很多人没搞清楚）：
04 章讲的 Megatron GPTDataset 用的就是③——它本来就是拼接后切分的。
所以【预训练阶段根本没有 padding 浪费】。

⟹ ★ "打包（packing）"这个话题，主要是【后训练/SFT】的问题， 因为 SFT 的一条样本（一轮对话）★不能被从中间切断。 而预训练阶段真正的问题是③带来的【跨文档污染】。 ⟹ 这一章因此分成两半： 13.2-13.3 讲【打包】—— 主要面向 SFT 13.4-13.6 讲【文档掩码】—— 预训练和 SFT 都要

★★★ 先澄清：③ 的"切一刀"和 ② 的"截断"完全不是一回事

很多混乱都出在这两个词被混用了：

② 截断丢弃（truncate & discard）
   doc1 有 8734 token → 只留前 4096，★ 后面 4638 个【永久扔掉】
   ⟹ 语料真的少了一块，长文档的后半【永远学不到】

③ 拼接后切分（concat & chunk）
   doc1 有 8734 token → 前 4096 在样本 k，
                        中间 4096 在样本 k+1，
                        剩下 542 个接着排在 k+2 的开头
   ⟹ ★★ 一个 token 都没丢，只是【被切到了相邻几条样本里】

★★★ 全教程（以及所有讲预训练的文献）说"可以截断"，
     指的永远是 ③ 这种【切分】，绝不是 ② 那种【丢弃】。

★★★ 为什么 ③ 这种"从文档中间切开"是可以接受的

原因一（最本质）：预训练的监督单位是 token，不是"一篇文档"

预训练做的是 next-token prediction（下一个词预测）：
   给定前面所有 token，预测下一个 token。
★ loss（损失）是在【每一个位置上单独算】的，然后取平均。

  文本:  今天  天气  很   好   ，   我   出去  跑步
  标签:        天气  很   好   ，   我   出去  跑步  …
              ↑ 每个位置都是一条独立的监督信号
  ⟹ ★ 一条 4096 的样本 = 4096 条监督信号，而不是"1 条样本"

从中间切开之后：
   前半段          每个位置上文都完整        → 信号 ★ 100% 有效
   后半段（新样本开头） 开头几十个 token 上文缺失 → 信号 ★【变弱】，但【没有变错】

★★ 关键认知：上文不完整的续写，本身就是一个【合法的】语言建模任务。
   模型在推理时本来就经常要在没有完整前文的情况下往下写。
   ⟹ 这不是脏数据，只是【难度更高】的数据。

原因二：受影响的 token 占比很小，且会被 shuffle 稀释

⚠️ 下面是我为了给量级感构造的粗估，不是论文结论：

  设 s = 8192（序列长），平均文档长度 ≈ 1000 token
     ⟹ 一条样本里约拼了 8 篇
     ⟹ 边界数 = 7 个【文档之间的接缝】 + 1 个【样本开头的续写点】≈ 8 个
  设每个边界之后 ~50 个 token 处于"上文不足"的劣化区

     劣化占比 ≈ 8 × 50 / 8192 = 400 / 8192 ≈ 4.9% ≈ 5%

★ 而且切点位置会随 shuffle 种子变化（见 [14 章](14-采样-shuffle-与断点续训.md)）：
  同一篇文档在不同轮次里切在不同地方
  ⟹ 长期看，每个位置都被"完整上文"覆盖过。

原因三：不切的代价是 GPU 闲死

Transformer 训练要求一个 batch 里所有序列★等长，否则要 padding。
而注意力开销 ∝ 序列长度的【平方】 ⟹ padding 的浪费会被平方放大。

  按最长文档补齐      → ★ 利用率可能 < 20%（见 13.2 的 89% 极端例子）
  按文档分桶          → 中等，实现复杂（这条路见 13.7）
  ★ 拼接后切分         → 利用率 ≈ 100%，代价只是边界处那 ~5%

★★ 那 SFT 为什么就不能切

预训练 SFT / 后训练
监督单位 ★ 单个 token ★ 一条完整样本（prompt + 完整回答）
从中间切开的后果 少数 token 上文变短，信号变弱 回答被砍掉，信号变错
模型会学到什么 「在信息不全时也要合理续写」——有用 「话说到一半就停」——★方向错误
数据规模 万亿（T）级，5% 可稀释 十万~百万级，★ 每条都金贵
结论 ★ 可以切分 ★ 不能切分（所以才要 13.3 的装箱打包）

★★★ 这张表就是 13.1 开头那句"打包主要是 SFT 的问题"的完整理由：
预训练不需要装箱，是因为它本来就允许把文档切开；
SFT 必须装箱，是因为它的样本一旦切开，信号就废了。

✅ 但"可以接受"不等于"没有代价"

✅ Fewer Truncations Improve Language Modeling
（arXiv:2404.10830，Hantian Ding 等，AWS AI Labs，2024-04-16）

⚠️ 核对说明：这篇论文的 PDF 不在本教程的 papers/ 目录里。下面的数字来自
arXiv 官方摘要（编号 ↔ 标题 ↔ 第一作者 ↔ 首次提交日期已通过 arXiv API 核对），
✅ 属于一手来源，但未逐句核对正文——引用时请以原文为准。

✅ 论文摘要明确指出的问题：
   拼接切分虽然高效，★ 但会"破坏数据完整性"——
   它把大量文档切成不完整的碎片，导致模型★学不会生成
   【基于完整上下文的、逻辑连贯且事实一致】的内容。

★★ 说人话的例子：
   原文  「……XX 公司 2023 年的营收是 |切| 47 亿美元。」
   切开后：前提句在样本 k，数字在样本 k+1
   ⟹ 模型学到的是"营收是"后面可以接【任意数字】
   ⟹ ★★ 这正是【幻觉（hallucination）】的一种制造机制

✅ 论文提出 Best-fit Packing（最优装箱打包）：
   用"长度感知的组合优化"打包，★ 在保持和拼接切分【同等训练效率】的前提下，
   完全消除【不必要的】截断。

✅ 摘要报告的收益（相对提升）：
   阅读理解 +4.7% ／ 上下文遵循 +16.8% ／ 程序合成 +9.2%
   ★★ 闭域幻觉（closed-domain hallucination）最多减少 58.3%

★★★ 所以本节的完整结论是一个权衡，不是一句"随便切"：
预训练【能够】容忍切分 —— 因为监督单位是 token，切分只让信号变弱不变错 但切分【不是免费的】 —— ✅ 事实和它的前提被切散，是幻觉的成因之一 ⟹ ★ 正确的态度：能少切就少切（13.3 的装箱 / 13.7 的分桶）， 而不是"反正预训练能截断，无所谓"。

13.2 padding 到底浪费了多少

✅ Efficient Sequence Packing without Cross-contamination
（arXiv:2107.02027，Mario Michael Krell 等，Graphcore，2021-06。✅ PDF 已归档在 papers/，下面带 ✅ 的句子我逐句核对过原文）

✅ 论文摘要与正文报告的实测：

· ✅ 在常见的 NLP 数据集上，★ 高达 50% 的 token 是 padding
    （原文 "up to 50% of all tokens can be padding"）
· ✅ 极端例子：GLUE-CoLA 在序列长度 128 下，★★ padding 占比最高到 89%
    —— 也就是说 GPU 有 89% 的算力在算空气
· ✅ 连 BERT 自己的 Wikipedia 预训练集，在序列长度 512 下 padding 也占 50%
    ✅ 原因写得很直白：长度正好是 512 的样本【只占 23.5%】，
       其余 76.5% 的样本都在补空气（长度范围是 5 ~ 512）
· ✅ 论文摘要的提法是：打包给 BERT 的 phase-2 预训练带来【2× 加速】

★ 为什么这么夸张？因为 填充浪费率 = 1 − 平均长度 / 序列长度 s。
长度分布重尾时，你为了容纳那少数几条长的，把 s 设得很大，于是绝大多数样本都在补空气。

⚠️ 先把"加速"的口径钉死，后面全章都要用

⚠️ 这是本章最容易被混着用的一组词，三句话说的不是同一件事：

说法 含义 和"浪费率 w"的关系 例子（w = 50%）
「padding 占 50%」 一条样本里一半 token 是空气 浪费率 w = 0.50 —
「有效算力只有 50%」 利用率 = 1 − w 利用率 = 0.50 —
「时间减少 50%」 耗时从 1 降到 0.5 减少比例 = w 耗时 1 → 0.5
「加速 2×」 同样的活，用一半时间 加速倍数 = 1 / (1 − w) 1 / (1 − 0.5) = 2× 
★★★ 把这条公式记住，后面自己算任何打包/掩码收益都靠它：

     加速倍数 = 1 / (1 − 时间减少比例)

  ⚠️ 两个最常见的口误：
     · 「时间减少 50%」说成「加速 50%」 —— 后者只有 1.5×，差一倍
     · 「时间减少 90%」对应的是 10× 而不是 9× —— 1/(1−0.9) = 10

  ⟹ 本章凡是写「约 2× 加速」的地方，背后都是"浪费率 ≈ 50% 被消掉"。
  ⚠️ 而且这是【理想上界】：真实加速还要扣掉打包本身的开销，见 13.3 的实测表。

13.3 ★ 打包 = 一个装箱问题

✅ 论文的核心贡献之一，就是把它明确地表述成了经典的【装箱问题（bin packing）】：

给你一堆长度不同的物品（文档），
和无限个容量为 L 的箱子（样本），
★ 求：用最少的箱子装下所有物品。

⟹ 这是运筹学里研究了几十年的经典 NP-hard 问题，有大量成熟的近似算法。

三个够用的算法

① 首次适应递减 First-Fit-Decreasing (FFD，首次适应 + 降序)
   ★ 先把所有文档【从长到短】排序，
     每篇依次放进【第一个装得下】的箱子；都装不下就开新箱子
   ★ 实现十行代码，效果见下面 13.3.1 的手算表

② 最佳适应递减 Best-Fit-Decreasing (BFD，最佳适应 + 降序)
   放进【放完后剩余空间最小】的箱子。稍好一点，稍慢一点

③ ✅ 论文提出的两个方法（针对超大规模）：
   · SPFHP（shortest-pack-first histogram-packing，最短箱优先的直方图打包）
     ★ 关键洞察：几百万篇文档，长度取值却**最多只有 s 种**（1 ~ s），
       所以不必逐篇处理，按【长度桶】处理就行 → 复杂度大幅下降
     ⚠️ 注意这里的 s 是序列长（比如 512 或 4096），不是文档篇数
   · NNLSHP（non-negative least squares histogram-packing，
     非负最小二乘直方图打包）—— 把"每种长度组合模式用多少次"
     解成一个非负最小二乘问题
   ✅ 论文报告这两种方法能达到接近理论最优的打包效率（实测数字见 13.3.2）

④ ✅ Best-fit Packing（2404.10830，AWS，见 13.1）
   ★ 同样是装箱，但它的目标函数不是"省 padding"（预训练本来就没有 padding），
     而是 ★★【最小化文档被切断的次数】
   ⟹ 这说明装箱这套工具在预训练里【也有用】，只是优化目标换了一个：
        SFT 装箱  → 目标是【填满箱子】，省算力
        预训练装箱 → 目标是【别切碎文档】，保数据完整性
   ✅ 摘要报告：在保持与拼接切分同等训练效率的前提下消除不必要的截断，
      ★ 闭域幻觉最多减少 58.3%

def pack_first_fit_decreasing(lengths, s=4096):
    """返回 [[doc_idx, ...], ...]，每个子列表是一个样本（一个"箱子"）"""
    order = sorted(range(len(lengths)), key=lambda i: -lengths[i])   # ★ 长的先放
    bins, remain = [], []
    for i in order:
        li = lengths[i]
        if li > s:                       # 超长文档单独处理（切分或丢弃）
            bins.append([i]); remain.append(0); continue
        for b in range(len(bins)):
            if remain[b] >= li:
                bins[b].append(i); remain[b] -= li
                break
        else:
            bins.append([i]); remain.append(s - li)
    return bins

# ★ 一定要打印这两个数字：它们是打包好坏的唯一指标
#   利用率     = sum(lengths) / (len(bins) * s)
#   填充浪费率 = 1 - 利用率

⚠️ 一个实践细节：FFD 每次要扫所有箱子，箱子多了会慢。
★ 实用做法：分块处理（每 10 万篇文档独立打包一次），几乎不损失效率，速度快几个数量级。

13.3.1 ★★★ 把浪费率算出来：一个能手算验证的例子

★ 这一小节是本章最该亲手跟着算一遍的地方。规模刻意选到纸上就能验算。

设定（刻意取小，方便核对）：

序列长 s = 16
10 篇文档的长度： 13  11  9  8  7  5  4  3  2  2
总 token 数 = 13+11+9+8+7+5+4+3+2+2 = 64

★ 理论下界：至少要 ceil(64 / 16) = 4 个箱子
  ⟹ 如果真能装到 4 个箱子，就是【零浪费】

做法 ① 一篇一条，补齐到 s（也就是 13.1 的做法①）

每篇文档独占一条样本，不足 16 的补 PAD：
  [13+3PAD] [11+5PAD] [9+7PAD] [8+8PAD] [7+9PAD]
  [5+11PAD] [4+12PAD] [3+13PAD] [2+14PAD] [2+14PAD]
  ⟹ 10 个箱子，总容量 10 × 16 = 160，实装 64

做法 ② 贪心 next-fit（按文档原顺序来，装不下就开新箱，★ 不排序）

13 → 箱1（余 3）；11 装不下 → 封箱，开箱2
11 → 箱2（余 5）； 9 装不下 → 封箱，开箱3
 9 → 箱3（余 7）； 8 装不下 → 封箱，开箱4
 8 → 箱4（余 8）； 7 装得下 → 箱4（余 1）；5 装不下 → 封箱，开箱5
 5 → 箱5（余11）； 4 → 余 7；3 → 余 4；2 → 余 2；2 → 余 0
⟹ 箱1=13 / 箱2=11 / 箱3=9 / 箱4=8+7 / 箱5=5+4+3+2+2
⟹ 5 个箱子，总容量 5 × 16 = 80，实装 64

做法 ③ FFD（降序 + 放进第一个装得下的箱）

（记号：箱N(r) 表示箱 N 还剩 r 的空间；no = 放不下，YES = 放进去）

文档 13：所有箱都放不下（还没有箱子）→ 开新箱1，余 3
文档 11：箱1(3) no                   → 开新箱2，余 5
文档  9：箱1(3) no，箱2(5) no         → 开新箱3，余 7
文档  8：箱1(3) no，箱2(5) no，箱3(7) no → 开新箱4，余 8
文档  7：箱1(3) no，箱2(5) no，箱3(7) YES → 箱3 余 0
文档  5：箱1(3) no，箱2(5) YES            → 箱2 余 0
文档  4：箱1(3) no，箱2(0) no，箱3(0) no，箱4(8) YES → 箱4 余 4
文档  3：箱1(3) YES                       → 箱1 余 0
文档  2：箱1(0) no，箱2(0) no，箱3(0) no，箱4(4) YES → 箱4 余 2
文档  2：箱1~箱3 均 no，箱4(2) YES        → 箱4 余 0

⟹ 最终四个箱子（★ 每个都正好装满 16）：
     箱1 = 13 + 3         = 16
     箱2 = 11 + 5         = 16
     箱3 =  9 + 7         = 16
     箱4 =  8 + 4 + 2 + 2 = 16
⟹ 4 个箱子，总容量 64，实装 64 —— ★★ 正好打到理论下界

① 最大的一跳在【①→②】：只要肯把文档拼起来，浪费立刻从 60% 掉到 20%。
   ⟹ 这解释了为什么"随便拼一下"就能拿到绝大部分收益。

② 第二跳【②→③】是【先排序】带来的：
   ★ 贪心 next-fit 不排序，长文档会把箱子卡住，后面的小文档没机会填进去；

   真实语料上 FFD 做不到 0% 浪费，具体能到多少见下面 13.3.2 的实测表。

⚠️ 还有两个这个小例子覆盖不到的情况：
   · 有文档比 s 还长（比如 17 > 16）→ ★ 它装不进任何箱子，
     只能走 13.1 的做法③把它【切开】（预训练）或丢弃/截断（SFT）
   · 长度分布极度重尾（大量 1~2 token 的碎文档）→ 箱子里会塞进上百篇，

13.4 ★★★ 跨文档污染：本章最重要的正确性问题

现在假设你把三篇不相干的文档打包进了同一条样本：

  路线一：--reset-attention-mask （+ --reset-position-ids）

     ⟹ ★ 正确性有了，但掩码是"先算完整的注意力、再把该屏蔽的位置乘 0"

     ⟹ ★ 这才是 13.6 说的"又正确又快"的那条路

     max_seqlen = (cu_seqlens[1:] - cu_seqlens[:-1]).max()
   ⟹ ★ 和 13.6 讲的两个入参完全对得上，不是我编的。

① 历史原因：早期实现里块对角掩码要显式构造 [s, s] 的掩码矩阵， s=4096 时是 4096² ≈ 1678 万个 bool，★ 显存和带宽开销都很实在 ② 预训练时如果文档普遍很长（一条样本里就 1~2 篇文档），污染影响较小 ③ ★ 而 SFT 场景下文档普遍很短（一轮对话几百 token）， 一条样本里能塞十几条 —— 此时污染影响【大得多】 ⟹ 实践建议：★ 预训练可以斟酌，SFT【必须打开】。

13.6 ★★★ 一个反直觉的好消息：文档掩码其实更快

很多人以为"加掩码 = 多做一件事 = 更慢"。恰恰相反。

朴素注意力的开销 ∝ 序列长度的平方。

  不加掩码：一条 4096 的样本 → 4096² = 16,777,216 ≈ 1678 万次
  加掩码后：假设塞了 8 篇各 512 的文档
            → 8 × 512² = 8 × 262,144 = 2,097,152 ≈ 210 万次
            ★★ 恰好是 1/8 !

★ 一般地：一条样本里塞 k 篇文档、长度分别是 s₁..s_k（Σsᵢ = s）：
     注意力开销正比于 Σ sᵢ²，而不加掩码是 s²
  ⟹ 省下的比例 = 1 − (Σ sᵢ²) / s²
  ⟹ ★ 等长时 Σ sᵢ² = k·(s/k)² = s²/k，所以是【降到 1/k】
  ⚠️ 不等长时要差一些：长度越不均，Σ sᵢ² 越大。
     例：s=4096 拆成 [3000, 1000, 96] →
         (3000²+1000²+96²)/4096² = 10,009,216 / 16,777,216 ≈ 0.60
         ★ 只降到 60%，远不是 1/3 = 33%。
     ⟹ ★★ "降到 1/k"是【均匀分布下的最好情况】，不是普遍结论。

⚠️⚠️ 但别把"注意力降到 1/k"当成"训练快 k 倍"

⚠️ 这是本章最容易被夸大的一个结论。注意力只是训练算力的一部分。

★ 训练算力的标准拆分（每个 token 每次训练步的 FLOP，浮点运算次数）：

     总 FLOP/token  ~=  [A]  +  [B]

       [A] = 6 * N              <- 矩阵乘部分，★ 与序列长【无关】
       [B] = 12 * L * s * h     <- ★ 注意力分数部分，正比于 s
                                   ★★【只有 [B] 能被文档掩码省掉】

  N = 非嵌入参数量    L = 层数    s = 序列长    h = 隐藏维度

★ 那个 6N 的来历（必须说清，否则后面算不对）：
     2N = 前向   +   4N = 反向（反向约为前向的 2 倍）
   ⚠️⚠️ 6N【不含优化器更新】的开销（Adam 的 m/v 更新、梯度裁剪、通信等）
        —— 它算的是"矩阵乘的浮点运算"，优化器那部分通常另算。
   ⚠️ 也不含激活重算（recompute）：开了重算要再加一次前向，约 +2N。

代入一个具体模型算一遍（★ 7B 量级：N = 6.7e9，L = 32，h = 4096）：

2,048 4.02e10 3.22e9 7.4% 4.02e10 + 4.0e8 1.07× 6.5%
4,096 4.02e10 6.44e9 13.8% 4.02e10 + 8.1e8 1.14× 12.1%
8,192 4.02e10 1.29e10 24.3% 4.02e10 + 1.6e9 1.27× 21.2%

131,072 4.02e10 2.06e11 83.7% 4.02e10 + 2.6e10 3.73× 73.2% 
★★★ 这张表才是 13.6 的真实结论，和"快 8 倍"相差很远：

  s = 4096 时：注意力只占 13.8% 的算力，
    ★ 把它降到 1/8 也只换来【1.14× 整体加速】（耗时减少 12%）。
  s = 128K 时：注意力占 83.7%，
    ★★ 降到 1/8 换来【3.73×】—— 这时候才真叫"快得多"。

⟹ ★★★ 一句话总结：
     【文档掩码的加速收益，随序列长平方级地变重要。】
     短上下文下它主要是个【正确性】措施；
     ★ 长上下文下它才同时是个【性能】措施。

⚠️ 顺手避开那个口误（13.2 的公式）：
   s=4096 那一行是「耗时减少 12.1%」⟹ 加速 1/(1−0.121) = 1.14×，
   ★ 不是"加速 12%"，也绝不是"快 8 倍"。

⚠️ 这张表里只有两列是硬事实（6N 与 12·L·s·h 的公式），
   ★ 其余都是把 N/L/h 代进公式的算术 —— 换个模型形状，占比会变，
     但【"注意力占比随 s 上升"】这个趋势不变。
⚠️ 另外这是朴素 O(s²) 注意力的账。稀疏/线性注意力（DSA、SWA 之类）
   会把 12·L·s·h 这一项本身压下去，★ 那时掩码的性能收益也跟着缩水。

而且，所有这些收益都有一个前提：算子必须真的跳过那些被掩掉的块，而不是"算完再乘 0"。

★★ 这就是【变长注意力（varlen attention）】的用途。
   FlashAttention 提供了专门的变长接口，需要三样东西：

   cu_seqlens        —— cumulative sequence lengths，★ 累积长度前缀和
                        例：三篇文档长 300/1200/2596
                            → cu_seqlens = [0, 300, 1500, 4096]
                        ★ 这就是 04 章 .idx 里"边界表"思想的复现
   max_seqlen        —— 本 batch 里最长的一篇，用于分配工作空间
   cu_seqlens_padded —— 对齐补齐后的版本（某些实现需要）

★ THD 与 SBHD：两种张量摆法

SBHD 格式（传统）  = [Sequence, Batch, Heads, Dim]
   ★ 规整的四维张量，每条样本长度相同（不足补 padding）

THD 格式（变长）   = [Total_tokens, Heads, Dim]
   ★★ 把整个 batch 的所有 token 【拍平成一维】，
     不同序列的边界靠 cu_seqlens 描述 —— 完全没有 padding

  ⚠️ 换个口径看同一组数字：这次把 300/1200/2596 当成【batch 里的三条样本】
     （而不是上面那个"一条样本里的三篇文档"）
    SBHD: 必须补到最长的 2596 → [2596, 3, H, D]
          空气 = (2596−300) + (2596−1200) + (2596−2596)
               = 2296 + 1396 + 0 = ★ 3692 个位置
          有效率 = 4096 / (2596×3) = 4096 / 7788 = ★ 52.6%
    THD : 拍平成 [4096, H, D]  ★ 一个 padding 都没有，有效率 100%
    ⟹ ★★ 同一批数据，SBHD 有近一半的算力在算空气

⟹ ★★ THD + cu_seqlens 是现在长上下文和 SFT 训练的标准做法。
   Transformer Engine / FlashAttention / 各家训练框架都支持。

★★★ 把这一节的结论说透：
"打包 + 文档掩码 + 变长注意力"这三件事必须一起做，才能同时拿到【正确性】和【速度】。
只打包不掩码 → 快，但★有跨文档污染（很多人的现状） 打包 + 掩码但用 SBHD → 正确，但掩码是"算完乘 0"，★ 没有省下算力 ★ 打包 + 掩码 + THD/varlen → 又正确又快

13.7 另一条路：按长度分桶（Dataset Decomposition）

✅ Dataset Decomposition: Faster LLM Training with Variable Sequence Length Curriculum
（arXiv:2405.13226，Hadi Pouransari 等，Apple，2024-05）

它对 13.1 的做法③提出了一个根本性的替代：

★ 传统做法（concat-and-chunk）：
  把所有文档拼成一条流 → 每 L 切一刀
  ❌ 一条样本里混了多篇文档（要靠 13.5 的掩码补救）
  ❌ ★ 长文档被切碎，模型看不到完整的长依赖

★★ Dataset Decomposition 的做法：
  把语料按文档长度分解成【一组桶】，桶的容量是 2 的幂：
     bucket_8    放长度 ~256 的片段
     bucket_9    放长度 ~512 的
     bucket_10   放长度 ~1024
     ...
     bucket_13   放长度 ~8192

  训练时，★ 每个 batch 【只从一个桶里取】
  ⟹ 同一个 batch 内所有序列等长 → 零 padding、零跨文档污染

★ 额外的好处：既然桶是显式的，就可以【控制各桶的采样比例随时间变化】
  → 前期多用短序列（便宜、收敛快），后期加大长序列比例
  → ★★ 这就是标题里的"变长序列课程（curriculum）"
  ✅ 论文把这条课程叫 Grow-P2（逐级放大 2 的幂）

✅ 论文原文明确写到的三件事（✅ PDF 已归档在 papers/，我核对过摘要与第 2 节）：

✅ 论文的说法 为什么关键
「每个桶 Dᵢ 装的是长度为 2ⁱ 的序列，且每条都抽自单独一篇文档」 ★★ 这是"零跨文档污染"的结构性保证——不靠掩码，靠数据本身就不混
「训练每一步从桶 Dᵢ 取 b / 2ⁱ 条序列」 ★ 批内 token 总数恒定 ⟹ 显存平稳，不会因为换桶而 OOM
「用 8k 上下文训 1B 模型的成本，等于基线方法训 2k 上下文的成本」 ★★ 这是最直观的收益表述：上下文翻两番而不加钱 
✅ 论文报告的量化收益（摘要 + Fig.1）：
   · ★★ 达到目标精度最多快【6×】（原文 "up to 6× faster training"）
   · ★ 数据效率 >【4×】（同等精度所需 token 数）
   · 即使训到 1.1 T token，相对基线仍有 +2.4 的平均精度优势
⚠️ 这些是在 RefinedWeb 上、1B 量级模型、最长上下文 8192 的设定下测的，
   ★ 不要直接外推到"任何规模都快 6 倍"。

★ 怎么选：
预训练、想省事、框架已支持 Megatron 那套 → 用 concat-and-chunk + 文档掩码 想要长上下文能力、且能改数据管线 → ★ 按长度分桶更优 SFT → ★ 必须打包 + 掩码（样本不能切断）

13.9 ⚠️ 六个坑

① ★★ 以为加了 <eod> 就不用掩码了
   ✅ 论文明确否定：分隔符 token 【不能】消除跨文档污染

② 打开了 --reset-attention-mask 但用的是 SBHD 稠密注意力
   → 正确性有了，★ 但速度一点没省（掩码是"算完乘 0"）
   → 要拿到加速必须走 THD + cu_seqlens
   ★ 在 Megatron 上就是换用 --dataloader-inter-document-masking

③ ⚠️ cu_seqlens 算错 —— 最常见的是【差一错误】
   它的长度必须是【序列条数 + 1】，且首元素为 0、末元素为总 token 数
   ★ 现象：loss 略微偏高但不崩，★ 极难发现。
   ★ 自检：assert cu[0]==0 and cu[-1]==total and (np.diff(cu)>0).all()

④ SFT 时 loss 掩码没跟着打包一起走
   打包后一条样本里有 10 轮对话，
   ★ 每一轮的"只对 assistant 部分算 loss"的掩码都要跟着重新对齐
   ⚠️ 现象：模型学会了生成用户的提问。见 [15 章](15-后训练数据格式.md)

⑤ ⚠️⚠️ 把"注意力降到 1/k"当成"训练快 k 倍"（13.6）
   ★ 只有 12·L·s·h 那一项能省，6N 那一项一分不省
   ⟹ 7B 量级、s=4096、k=8 时整体只有【1.14×】
   ★ 自检：先算 12·L·s·h / (6N + 12·L·s·h)，★ 这个比例就是你的收益上限

⑥ ⚠️ 只看"打包效率"选算法（13.3.2）
   ✅ SORT 的效率 99.9%，但开销 OH ≫100% ⟹ 实测【比不打包还慢】
   ★ 必须同时看【效率】和【开销/对数据顺序的破坏】

13.10 小结

① 变长文档 → 定长 [B,L]，三种做法：补齐(浪费) / 截断丢弃(真丢数据) /
   ★ 拼接后切分(零浪费，但引入跨文档污染)
   ★★★ Megatron GPTDataset 用的就是第三种
      ⟹ 预训练【本来就没有 padding 浪费】，
        "打包"主要是 SFT 的问题（SFT 样本不能从中间切断）

①b ★★★ 为什么预训练【可以】从文档中间切开（13.1）：
   ★ 先分清两个词：②是【丢弃】后半，③是【切到下一条样本】——一个 token 都没丢
   本质原因：预训练的监督单位是 ★【token】不是文档。loss 逐位置计算，
     一条 4096 的样本 = 4096 条监督信号；切开只让边界后几十个 token
     ★【上文变短 → 信号变弱】，而不是【变错】——上文不全的续写本身就是合法任务
   ⚠️ 粗估：L=8192、平均文档 1000 token 时，劣化 token 占比 ≈ 5%，且被 shuffle 稀释
   ★★ 而 SFT 切开是把回答砍掉 → 模型学会【说到一半就停】，是【方向错误】
   ✅ 但切分不免费（2404.10830，AWS，⚠️ PDF 未归档、数字取自 arXiv 摘要）：
      事实与其前提被切散是幻觉成因之一；Best-fit Packing 在同等训练效率下
      ★ 使闭域幻觉最多减少 58.3%（阅读理解 +4.7% / 上下文遵循 +16.8% / 程序合成 +9.2%）
   ⟹ ★ 正确态度是"能少切就少切"，不是"反正能截断，无所谓"

② ✅ 打包的收益（2107.02027，PDF 已归档）：常见数据集里高达 50% 是 padding，
   GLUE-CoLA@128 极端到 89%，✅ 连 BERT 的 Wikipedia 集@512 也是 50%
   （✅ 因为长度正好 512 的样本只占 23.5%）
   ⚠️ 口径：**加速倍数 = 1/(1−时间减少比例)** —— 摘要的「2×」落到
      ✅ Table 1 的实测是【1.913×】（NNLSHP, depth 3），不是整数 2
   ★ 本质是经典的【装箱问题】。13.3.1 手算了一组 10 篇文档 @ s=16：
      ★ 一篇一条补齐 → 浪费 60% ／ 贪心 next-fit → 20% ／ FFD/BFD → 0%
      ⟹ ★★ 最大的一跳来自"肯拼起来"，第二跳来自"先降序排"
   ✅ Table 1 的实测（13.3.2）纠正三个误解：
      · ★ GREEDY（来一篇装一篇）打包效率只有【≈78%】，不是 99%
      · ★ NNLSHP 在 depth 3 就有 99.7%，SPFHP 要 depth 8 才 98.9%
      · ★★★ SORT 的效率 99.9% 但开销 OH ≫100% ⟹ 实测【比不打包还慢】
        —— 评价打包必须同时看【效率】和【开销】两列

③ ★★★ 跨文档污染：一条样本里塞了三篇不相干的文档，
   默认因果掩码让后面的能看到前面的 → 模型在学【虚假的统计关系】
   ★★ 13.4 把格子数出来了：s=12 塞 3 篇各 4 token ⟹ 因果允许 78 格，
      其中【48 格（61.5%）是跨文档的垃圾】
      ★ 一般式：等长塞 k 篇 ⟹ 跨文档格子占比 ≈ 1 − 1/k
        （k=8 → 87.5%，k=16 → 93.8%）
      ⟹ ★★★ SFT 下九成以上的注意力计算在学虚假关系
   ✅ 论文明确：★ 加 <eod> 分隔符【不能】解决（"not sufficient"）
      ⚠️ 但注意归因：那个「F1 平均降 0.35%」的量化证据，
         ✅ 论文是【转引 RoBERTa】的，★ 不是 Graphcore 自己的实测

④ ★★ 解法 = 块对角注意力掩码 + 位置 id 重置
   ✅ Megatron 有【三个】开关（我核对过本仓库里的 Megatron-LM 源码）：
     --reset-attention-mask   造 [s,s] 掩码矩阵（★ 正确但不省算力）
     --reset-position-ids     位置 id 每篇从 0 重数
     --dataloader-inter-document-masking
        ★★ 直接输出 cu_seqlens 给变长算子 —— 这才是"又对又快"的那条路
        ✅ 源码里就是一行前缀和：cumsum([0] + document_lengths)
   ⚠️⚠️ 三个全是 action='store_true' ⟹【默认关闭】
      → 不改配置的话你的训练是带污染的
   ★ 预训练可斟酌（文档长时影响小），SFT 必须开（文档短、一条塞十几个）

⑤ ★★ 文档掩码不但不慢，反而更快 —— ⚠️ 但【别把收益说大了】
   注意力开销 ∝ Σsᵢ²；等长塞 k 篇才是降到 1/k
   ⚠️ 不等长要差得多：[3000,1000,96] 只降到 60%，不是 1/3
   ⚠️⚠️ 更重要的是：注意力只是总算力的一部分。
     总 FLOP/token ≈ 6N + 12·L·s·h，★【只有后一项能被掩码省掉】
     （6N = 2N 前向 + 4N 反向，⚠️ 不含优化器、不含激活重算）
     ⟹ 7B 量级（N=6.7e9, L=32, h=4096）、k=8 时的整体加速：
          s=4K  → 注意力占 13.8% → 整体仅【1.14×】（耗时 −12%）
          s=32K → 占 56.2%       → 【1.97×】
          s=128K→ 占 83.7%       → 【3.73×】
     ⟹ ★★★ 短上下文下掩码主要是【正确性】措施；
          长上下文下它才同时是【性能】措施
   ★ 而且前提是算子真的跳过被掩的块 ⟹ 必须用变长注意力：
     cu_seqlens（累积长度前缀和，★ 就是 .idx 边界表思想的复现）
     + THD 格式（把整 batch 拍平成一维，零 padding）
     ★ 同一批 300/1200/2596：SBHD 有效率 52.6%，THD 100%
   ⟹ 打包 + 掩码 + THD 三件事要一起做

⑥ ✅ 另一条路 Dataset Decomposition（2405.13226，Apple，PDF 已归档）：
   桶 Dᵢ 装长度 2ⁱ 的序列，✅【每条都抽自单独一篇文档】
     ⟹ ★★ 零污染是【结构性】保证，不靠掩码
   ✅ 每步从 Dᵢ 取 b/2ⁱ 条 ⟹ 批内 token 数恒定、显存平稳
   ✅ 收益：到达目标精度最多快【6×】／数据效率 >【4×】／
      ★「8k 上下文的 1B 模型，训练成本等于基线的 2k 上下文」
   ⚠️ 设定是 RefinedWeb、1B 量级、最长 8192 —— 别外推成"永远快 6 倍"

⑦ ⚠️ 六个坑：以为 <eod> 够用 / 开了掩码但用 SBHD 没省算力 /

   SFT 打包后 loss 掩码没跟着对齐（★ 模型学会生成用户提问）/
   ⚠️ 把"注意力降 1/k"当成"快 k 倍" / ⚠️ 只看打包效率不看开销
