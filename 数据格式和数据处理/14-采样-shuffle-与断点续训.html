14 · ⭐ 采样、shuffle 与断点续训

数据准备好了、打包好了。最后一个问题：
训练时按什么顺序喂？中途挂了怎么接着喂？

★ 这一章的东西不影响数据质量，但直接影响训练能不能复现、能不能救回来。
⚠️ 而且它是整个数据链路里最容易写出"不报错的 bug"的一段。

14.1 顺序为什么要紧

假设你不 shuffle，按数据集顺序喂：

   前 20% 全是中文网页
   中间 50% 全是英文网页
   后 20% 全是代码
   最后 10% 全是数学

会发生什么？
   ★ 训到代码那一段时，模型正在"忘掉"中文
     —— 这叫【灾难性遗忘 catastrophic forgetting】
   ★ 每次切换数据源，loss 曲线会出现一个明显的台阶
   ★★ 最终模型的能力会严重偏向【最后看到的那种数据】

★★ 一句话原理：随机梯度下降的理论保证，建立在每个 batch 是从整体分布里独立同分布采样这个前提上。
顺序一有结构，这个前提就破了，训练动力学会跑偏。

⚠️ 但注意：这不代表"顺序永远该是完全随机的"。10 章的退火和 13 章的长度课程，都是故意制造顺序结构。
★ 区别在于：那是被设计出来的、可控的结构；而"忘了 shuffle"是不受控的意外结构。

14.2 回顾：Megatron 的三层索引

04 章讲过 GPTDataset 构建时会生成三个数组，这里把它们和"采样"这件事对上：

① document_index  —— ★ 定义【一个 epoch 内文档的访问顺序】
   长度 = 文档数 × epoch 数
   ⟹ 它决定了"文档级"的打乱

② sample_index    —— ★ 定义【第 i 条样本从哪篇文档的哪个偏移开始】
   把首尾相接的 token 流按 seq_len 切成样本（13 章的做法③）
   ⟹ 它是"从文档流到定长样本"的映射表

③ shuffle_index   —— ★ 定义【样本被访问的顺序】
   长度 = 样本总数，内容是 0..N-1 的一个随机排列
   ⟹ 它决定了"样本级"的打乱

训练第 step 步、第 j 条样本，实际取的是：

   真实样本编号 = shuffle_index[ step × GBS + j ]
   ★ GBS = Global Batch Size（全局批大小），一步优化里所有 GPU 合起来吃掉多少条样本
   起止位置    = sample_index[ 真实样本编号 ]
   文档        = document_index[ ... ]
   token       = .bin 里对应的字节

★★★ 关键性质：这三个数组是【预先算好并存成文件】的。
   ⟹ 取第 i 条样本是 O(1) 的数组查表，不需要"从头遍历"。
   ⟹ ★ 这一条直接决定了 14.5 的断点续训能做得多干净。

★ 为什么打乱要分成"文档级"和"样本级"两层？
只打乱文档级：样本的【访问顺序】没变，仍按文档流从前往后走 ⟹ 同一篇长文档切出的 10 条样本，还是挤在相邻的几个 step 里 只打乱样本级：访问顺序打散了，但每条样本的【内容】仍由原始文档流决定 ⟹ 原本挨着的两篇文档（同源、同批抓取、甚至互为重复） 照样被拼进同一条或相邻的样本里 ★ 两层管的不是同一件事： 文档级决定"哪些内容被拼进同一条样本"，样本级决定"这些样本按什么顺序喂进去" 都打乱，才能既打散文档之间的邻接关系，又打散同一文档内部片段的出现时机

14.3 大规模下真正的做法：两级 shuffle

⚠️ 一个残酷的现实：shuffle_index 是一个覆盖全体样本的随机排列。

15 T token / 4096 = 约 36.6 亿条样本
→ shuffle_index 用 int64 存 = ★ 约 29 GB 的一个数组

⟹ 单机内存能扛，但每一次取样本都是【完全随机的磁盘位置】
   ★★ 随机读 = 磁盘吞吐掉到几十分之一

03 章提过的两级 shuffle就是为解决这个而生的：

┌─ 第一级：★ 文件级/分片级 shuffle（粗粒度）───────────────┐
│    语料被切成几千个 shard 文件（每个几 GB）              │
│    每个 epoch 开始时，★ 把 shard 的【顺序】随机打乱      │
│    → 只打乱几千个元素，成本可以忽略                      │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─ 第二级：★★ 缓冲区 shuffle（细粒度）─────────────────────┐
│    维护一个容量 K（比如 10 万条）的内存缓冲区：          │
│      · 顺序读入样本填满缓冲区                            │
│      · 每次【从缓冲区里随机取一条】输出                  │
│      · 立刻顺序读一条新的补进来                          │
│    ⟹ ★ 磁盘上是【顺序读】，输出是【局部随机】           │
└─────────────────────────────────────────────────────────┘

★★ 两级合起来的效果 ≈ 全局随机，而磁盘访问模式 ≈ 顺序读。

import random
def two_level_shuffle(shard_paths, buf_size=100_000, seed=42):
    rng = random.Random(seed)
    rng.shuffle(shard_paths)                      # ★ 第一级
    buf = []
    for path in shard_paths:
        for sample in iter_shard(path):           # ★ 顺序读
            if len(buf) < buf_size:
                buf.append(sample); continue
            i = rng.randrange(buf_size)           # ★ 第二级
            yield buf[i]
            buf[i] = sample
    rng.shuffle(buf)
    yield from buf                                # 收尾把缓冲区倒空

⚠️ 缓冲区大小 K 的权衡：
K 太小 → 相邻输出的样本仍然来自磁盘上相邻的位置，★ 打乱不充分 K 太大 → 内存吃紧、启动时要等很久才填满 ★ 经验值：K 至少要比【一个 global batch】大一到两个数量级 ★ 自检：随手抽 1000 条连续输出，看它们的 shard 来源是不是足够分散

14.4 ★★ 确定性：为什么必须能一模一样地重跑

★ 你会遇到的场景：
  · 模型训到第 8 万步 loss 突然爆了 → 你想知道那一步喂的是什么数据
  · 换了个优化器超参想做 A/B → ★ 数据顺序必须完全一致，否则对比没意义
  · 机器挂了要续训 → 必须从中断处【原样】接上
  · 复现别人的结果

⟹ 结论：★★ 数据流水线必须是【给定 seed 就完全确定】的纯函数。

要做到这一点，有几条硬规矩：

① ★ 所有随机性都从一个显式 seed 派生，不许用系统时间、不许用进程 id
   ⚠️ random.shuffle(x) 不传 seed = 不可复现

② ★★ 数据的随机流要和【模型的随机流】分开
   模型侧的随机（dropout、参数初始化）用 seed_model
   数据侧的随机（shuffle）用 seed_data
   ⚠️ 如果共用一个全局随机流，改一下 dropout 就会连数据顺序一起变
      → ★ 你的 A/B 实验就白做了，而且你根本不会发现

③ ★ 不能依赖字典/集合的遍历顺序、不能依赖 os.listdir() 的返回顺序
   ⚠️ 这两个在不同机器、不同文件系统上顺序可能不同
   ★ 一律 sorted() 之后再用

④ ★ 多进程 DataLoader 的 worker 也要各自拿到确定的 seed
   通常是 seed = base_seed + rank * num_workers + worker_id

★★ Megatron 的做法值得学：它把索引数组存成文件，文件名里带一个由 (数据集路径、seed、样本数、split、seq_len) 算出来的哈希。
⟹ 参数完全一样 → 命中缓存 → ★ 顺序必然一致 ⟹ 任何一个参数变了 → 哈希变 → ★ 重新构建，且你能从文件名看出变了 ★ 这等于把"确定性"这件事变成了文件系统上可见的事实，而不是一个口头约定。

⚠️ 04 章提过的那个坑在这里要再说一遍：
索引只在一个 rank 上真正构建，但【所有 rank 都必须走进那段代码】（其他 rank 在屏障上等）。
★ 如果你写了个 if rank == 0: 把整段包起来，程序会静默挂死——不报错，就是不动。

14.5 ★★★ 断点续训：数据侧到底要存什么

千卡训练几个月，中途一定会挂（硬件故障、网络抖动、OOM（Out Of Memory，显存耗尽）、有人碰了电源）。
模型权重和优化器状态大家都知道要存。但数据的进度也是状态。

错误做法与正确做法

❌ 最常见的错误：挂了之后【从头开始遍历数据】
   → 前 8 万步看过的数据又看一遍
   → ★ 相当于对那部分数据多训了一个 epoch，配比和重复次数全乱了
   → ⚠️ 而且【不报任何错】，你只会看到 loss 曲线有点怪

❌ 第二种错误：随便挑个 seed 重新 shuffle
   → 顺序变了，之前没看过的数据可能永远看不到，看过的又看好几遍

✅ 正确做法：★★ 存下【已消费的样本数】consumed_samples
   续训时：
     · 用【完全相同的 seed 和参数】重建索引 → 得到一模一样的三个数组
     · ★ 直接从 shuffle_index[consumed_samples] 开始取
     ⟹ 因为索引是数组，这是 O(1) 的跳转，不需要"空转"前面的步数

# 保存
ckpt = {
    "model": ..., "optimizer": ...,
    "consumed_train_samples": consumed,   # ★★ 数据侧唯一必须存的东西
    "data_seed": args.seed,               # ★ 存下来是为了续训时能自检
    "data_config_hash": cfg_hash,         # ★ 配比/split/seq_len 的哈希
}

# 恢复
assert ckpt["data_seed"] == args.seed, "★ seed 变了，续训不等价！"
assert ckpt["data_config_hash"] == cfg_hash, "★ 数据配置变了，续训不等价！"
start = ckpt["consumed_train_samples"]
for i in range(start, total_samples):     # ★ 直接跳到断点处
    yield get_sample(shuffle_index[i])

★★★ 上面那两行 assert 是本章最值得抄走的两行代码。
没有它们，"改了配比之后从旧 checkpoint 续训"这种事会悄无声息地发生，
而事后你完全无法解释模型为什么怪。

⚠️ 几个会让"续训不等价"的隐形因素

① ★★ 改了 --train-iters 或 global batch size
   → 总样本数变了 → ★ 索引数组要重建 → shuffle 顺序整个变了
   ⚠️ 这是最反直觉的一个：你只是想"多训一会儿"，
      结果把【已经训过的部分的顺序】也一起改掉了

② 改了数据配比 / 加了一个新数据集
   → BlendedDataset 的组成变了 → 索引重建
   ★ 这在实践中很常见（中途想加数据），
     ⟹ 正确的处理方式是【把它当成一个新阶段】（10 章的多阶段），
        而不是假装续训是连续的

③ ⚠️ DataLoader 的 worker 数量变了
   如果你的采样逻辑依赖 worker_id 分片，改 num_workers 会改变分配
   ★ 稳妥做法：让采样只依赖 (global_step, dp_rank)，★ 不依赖 worker 数

④ ⚠️ 预取（prefetch）的样本在崩溃时已被读出但没进梯度
   → 严格来说会丢几个 batch。★ 通常可以接受，但要知道它存在

14.6 多机多卡：谁拿哪一份数据

一次训练里，GPU 被切成几个维度（隔壁 [大模型架构入门] 讲过并行方式）：

  DP  数据并行 Data Parallel      —— ★ 不同 DP rank 处理【不同的数据】
  TP  张量并行 Tensor Parallel    —— ★ 同一份数据被切开算
  PP  流水并行 Pipeline Parallel  —— ★ 同一份数据流过不同的层

★★★ 于是数据侧的铁律只有一条：
   【同一个 DP 组内的所有 GPU（也就是 TP 组和 PP 组里的所有卡）
     必须拿到【完全一样】的那一份数据；
     不同 DP rank 之间必须拿到【完全不重叠】的数据。】

一个 global batch = GBS 条样本，切给 DP_SIZE 个数据并行组：

   dp_rank 0 拿  shuffle_index[base + 0 : base + m]
   dp_rank 1 拿  shuffle_index[base + m : base + 2m]
   ...                              其中 m = GBS / DP_SIZE

  ★ 通常的实现：只有 TP-rank 0 且 PP 首尾级的卡真正读数据，
    然后【广播】给同 TP/PP 组的其他卡 —— 既保证一致，又不浪费 IO

⚠️ 两个典型故障：
  · 同 TP 组的卡读到了不同数据 → ★ 梯度 all-reduce 出来是垃圾
    现象：loss 剧烈震荡或直接 NaN
  · 不同 DP rank 拿到重复数据 → 有效 batch 变小、部分数据永远看不到
    现象：★ 不报错，只是收敛慢一点点 —— 极难发现
★ 自检：训练启动时让每张卡打印它第一个 batch 的 token 校验和（比如 md5 前 8 位），
       手动看一眼是不是"同 TP 组相同、不同 DP 组不同"。

14.7 ⚠️ 五个坑

① ★★ 挂了从头重新遍历数据（14.5）—— 不报错，配比悄悄变了

② ★★ 数据随机流和模型随机流共用一个全局 seed
   → 改 dropout 顺带改了数据顺序 → ★ A/B 实验全部作废

③ shuffle 缓冲区 K 太小
   ★ 现象：loss 曲线上有周期性的小波动，周期恰好对应 shard 大小
   —— ★ 这是一个很好的诊断信号，看到就该怀疑 shuffle 不充分

④ ⚠️ 只在 rank 0 里构建索引（把 if rank==0 包住了整段）
   → ★ 程序静默挂死在屏障上，不报错、不超时、日志停在那里

⑤ ⚠️ 中途加数据集 / 改 train-iters 后直接续训
   → 索引重建 → 顺序全变 → ★ "续训"实际上是一次新的训练
   ★ 正确姿势：当成 10 章的一个新阶段来对待，并在实验记录里写清楚

14.8 小结

① 不 shuffle 会导致灾难性遗忘、loss 台阶、能力偏向最后看到的数据
   ★ 原理：SGD 的保证建立在"每个 batch 独立同分布采样"上
   ⚠️ 但退火（10 章）和长度课程（13 章）是【故意设计的顺序】—— 
     区别在于"受控"还是"意外"

② Megatron 三层索引各管一件事：
   document_index → 文档访问顺序 / sample_index → 样本切分位置 /
   shuffle_index → ★ 样本访问顺序
   ★★★ 关键性质：它们是【预先算好的数组】⟹ 取第 i 条是 O(1) 查表
      ⟹ 这是 ⑤ 断点续训能做干净的前提

③ ★★ 大规模下用【两级 shuffle】：
   一级 = 打乱 shard 顺序（几千个元素，成本忽略）
   二级 = 容量 K 的缓冲区随机取（磁盘顺序读、输出局部随机）
   ⟹ 效果≈全局随机，访问模式≈顺序读
   ⚠️ K 至少要比一个 global batch 大一到两个数量级

④ ★★ 确定性四条规矩：
   显式 seed 派生 / ★ 数据 seed 与模型 seed 分开 /
   不依赖 listdir 与字典顺序（一律 sorted）/ worker seed 也要确定
   ★ Megatron 把索引存成【文件名带参数哈希】的缓存 —— 
     把确定性变成了文件系统上可见的事实
   ⚠️ 索引只在一个 rank 构建，但所有 rank 都要进那段代码，否则★静默挂死

⑤ ★★★ 断点续训数据侧只需存一个东西：consumed_train_samples
   续训时用相同 seed 重建索引 → 直接跳到 shuffle_index[consumed]
   ★ 一定要加两行 assert：seed 一致、数据配置哈希一致
   ⚠️ 会让"续训不等价"的隐形因素：改 train-iters / 改 GBS / 改配比 /
      改 num_workers ⟹ 都会重建索引、改变顺序
      ★ 中途加数据请当成一个【新阶段】，别假装是连续的

⑥ ★★★ 多机多卡铁律：同 DP 组内（TP/PP 各卡）数据必须【完全相同】，
   不同 DP rank 之间必须【完全不重叠】
   ★ 通常由 TP-rank 0 读数据再广播
   ⚠️ 前者错 → loss 震荡/NaN；★ 后者错 → 不报错，只是悄悄变慢变差
   ★ 自检：启动时打印每卡首个 batch 的 token 校验和，肉眼比对
