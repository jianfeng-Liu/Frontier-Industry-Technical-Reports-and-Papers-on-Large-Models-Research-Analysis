# 14 · ⭐ 采样、shuffle 与断点续训

> **数据准备好了、打包好了。最后一个问题：**
> **训练时按什么顺序喂？中途挂了怎么接着喂？**
>
> ★ 这一章的东西**不影响数据质量，但直接影响训练能不能复现、能不能救回来**。
> ⚠️ 而且它是整个数据链路里**最容易写出"不报错的 bug"**的一段。

---

## 14.1 顺序为什么要紧

```
假设你不 shuffle，按数据集顺序喂：

   前 20% 全是中文网页
   中间 50% 全是英文网页
   后 20% 全是代码
   最后 10% 全是数学

会发生什么？
   ★ 训到代码那一段时，模型正在"忘掉"中文
     —— 这叫【灾难性遗忘 catastrophic forgetting】
   ★ 每次切换数据源，loss 曲线会出现一个明显的台阶
   ★★ 最终模型的能力会严重偏向【最后看到的那种数据】
```

> ★★ **一句话原理**：随机梯度下降的理论保证，建立在**每个 batch 是从整体分布里独立同分布采样**这个前提上。
> 顺序一有结构，这个前提就破了，训练动力学会跑偏。
>
> ⚠️ **但注意**：这不代表"顺序永远该是完全随机的"。[10 章](10-数据配比.md)的**退火**和 [13 章](13-打包与文档掩码.md)的**长度课程**，都是**故意制造顺序结构**。
> ★ 区别在于：**那是被设计出来的、可控的结构；而"忘了 shuffle"是不受控的意外结构。**

## 14.2 回顾：Megatron 的三层索引

[04 章](04-训练格式-Megatron索引.md)讲过 `GPTDataset` 构建时会生成三个数组，这里把它们和"采样"这件事对上：

```
① document_index  —— ★ 定义【一个 epoch 内文档的访问顺序】
   长度 = 文档数 × epoch 数
   ⟹ 它决定了"文档级"的打乱

② sample_index    —— ★ 定义【第 i 条样本从哪篇文档的哪个偏移开始】
   把首尾相接的 token 流按 seq_len 切成样本（13 章的做法③）
   ⟹ 它是"从文档流到定长样本"的映射表

③ shuffle_index   —— ★ 定义【样本被访问的顺序】
   长度 = 样本总数，内容是 0..N-1 的一个随机排列
   ⟹ 它决定了"样本级"的打乱
```

```
训练第 step 步、第 j 条样本，实际取的是：

   真实样本编号 = shuffle_index[ step × GBS + j ]
   ★ GBS = Global Batch Size（全局批大小），一步优化里所有 GPU 合起来吃掉多少条样本
   起止位置    = sample_index[ 真实样本编号 ]
   文档        = document_index[ ... ]
   token       = .bin 里对应的字节

★★★ 关键性质：这三个数组是【预先算好并存成文件】的。
   ⟹ 取第 i 条样本是 O(1) 的数组查表，不需要"从头遍历"。
   ⟹ ★ 这一条直接决定了 14.5 的断点续训能做得多干净。
```

> ★ 为什么打乱要分成"文档级"和"样本级"两层？
> ```
> 只打乱文档级：样本的【访问顺序】没变，仍按文档流从前往后走
>              ⟹ 同一篇长文档切出的 10 条样本，还是挤在相邻的几个 step 里
> 只打乱样本级：访问顺序打散了，但每条样本的【内容】仍由原始文档流决定
>              ⟹ 原本挨着的两篇文档（同源、同批抓取、甚至互为重复）
>                 照样被拼进同一条或相邻的样本里
> ★ 两层管的不是同一件事：
>   文档级决定"哪些内容被拼进同一条样本"，样本级决定"这些样本按什么顺序喂进去"
>   都打乱，才能既打散文档之间的邻接关系，又打散同一文档内部片段的出现时机
> ```

## 14.3 大规模下真正的做法：两级 shuffle

⚠️ **一个残酷的现实**：`shuffle_index` 是一个覆盖**全体样本**的随机排列。

```
15 T token / 4096 = 3.662 × 10⁹ 条 ≈ 36.6 亿条样本
→ shuffle_index 用 int64（8 字节）存
  = 3.662e9 × 8 = 2.93 × 10¹⁰ 字节

★ 写成两种单位（⚠️ 这两个差 7.4%，别混着说）：
    十进制 GB（10⁹ 字节）  → ★ 29.3 GB
    二进制 GiB（2³⁰ 字节） →   27.3 GiB
  ⟹ 本章此后一律用【十进制 GB】，所以说"约 29 GB"。

⟹ 单机内存能扛，但每一次取样本都是【完全随机的磁盘位置】
   ★★ 随机读 = 磁盘吞吐掉到几十分之一
```

### 14.3.1 ★★★ 先把 shuffle 的几种做法摊在一张表上

> ★ 这张表是本节的核心。**纵向比的不是"哪个更随机"，而是"随机性、内存、能不能精确续训"三者怎么换"。**

| 做法 | 怎么做 | 内存开销 | 随机性 | ★★ 能否 O(1) 精确续训 | 磁盘访问 |
|---|---|---|---|---|---|
| **① 不 shuffle** | 按语料原顺序喂 | 0 | 无 | ✅ 能（记 offset 即可） | 顺序读（最快） |
| **② 全局 shuffle**<br>（Megatron `shuffle_index`） | 对**全体样本**生成一个随机排列，**存成数组** | ★★ 排列数组本身<br>（36.6 亿条 → **29 GB**） | ★★★ 真·全局 | ✅★★ **能**：`shuffle_index[consumed]` 一次查表 | ★★ **全随机读**（最慢） |
| **③ 分片内 shuffle**<br>（shard-local） | 只在**每个 shard 内部**打乱，shard 顺序不变 | 一个 shard 的索引（几 MB） | ★ **弱**：同 shard 的样本永远挨着出现 | ✅ 能（记 shard 号 + 片内 offset） | ★ 顺序读 |
| **④ 窗口 / 缓冲区 shuffle**<br>（buffer / reservoir） | 维护容量 K 的缓冲区，每次从里面随机取一条，再顺序补一条进来 | ★ **K 条样本**（K=10 万 × 4096 token × 2 B ≈ **0.8 GB**） | ★★ 局部随机，窗口越大越像全局 | ⚠️⚠️ **不能**：缓冲区内容 + RNG 状态都是隐藏状态，<br>要么存下来，要么**从头空转 N 条**重放 | ★★ 顺序读 |
| **⑤ 两级 = ① shard 顺序打乱 + ④ 缓冲区** | 见下 | ★ 同 ④ | ★★★ 接近全局 | ⚠️ 同 ④ | ★★ 顺序读 |

```
★★★ 这张表最该带走的一行是【④ 的续训那一格】：

   缓冲区 shuffle 便宜、随机性也够，★ 但它是【有状态的流】——
   "我现在吐到第 N 条了"这一个数字，★ 根本不足以还原它的内部状态。
   ⟹ 想精确续训只有两条路：
       a) 把缓冲区里那 K 条样本的 id + RNG 状态一起存进 checkpoint
       b) ★ 重放：从头再消费 N 条、扔掉，纯粹为了把状态走到位（O(N) 空转）

⚠️⚠️ 这里有一个【本章内部必须说清的张力】，很多教程会前后矛盾：
   · 14.3 推荐的是【④/⑤ 缓冲区方案】（为了磁盘顺序读）
   · 14.5 会说【只存 consumed_samples 就够了】
   ★★★ 这两句话只有在【② 全局 shuffle 数组】方案下【同时成立】！
   ⟹ 所以 Megatron 选了 ②：它宁可吃 29 GB 内存和随机读，
        ★ 换来"断点续训是 O(1) 查表"这个性质。
   ⟹ ★ 而你如果用 WebDataset / MDS 那类 ④ 式流水线，
        14.5 那套"只存 consumed_samples"就【不够用】，必须另外处理。
        （14.5 末尾会把这一条单列出来）
```

### 14.3.2 两级 shuffle 具体长什么样

[03 章](03-存储格式.md)提过的**两级 shuffle**就是为了在"顺序读"的前提下拿到"接近全局"的随机性：

```
第一级：★ 文件级 / 分片级 shuffle（粗粒度）
  ├── 语料被切成几千个 shard 文件（每个几 GB）
  ├── 每个 epoch 开始时，★ 把 shard 的【顺序】随机打乱
  └── 只打乱几千个元素，成本可以忽略
        │
        ▼
第二级：★★ 缓冲区 shuffle（细粒度）
  ├── 维护一个容量 K（比如 10 万条）的内存缓冲区
  ├── 顺序读入样本填满缓冲区
  ├── 每次【从缓冲区里随机取一条】输出
  ├── 立刻顺序读一条新的补进来
  └── ⟹ ★ 磁盘上是【顺序读】，输出是【局部随机】

★★ 两级合起来的效果 ≈ 全局随机，而磁盘访问模式 ≈ 顺序读。
```

```python
import random
def two_level_shuffle(shard_paths, buf_size=100_000, seed=42):
    rng = random.Random(seed)
    rng.shuffle(shard_paths)                      # ★ 第一级
    buf = []
    for path in shard_paths:
        for sample in iter_shard(path):           # ★ 顺序读
            if len(buf) < buf_size:
                buf.append(sample); continue
            i = rng.randrange(buf_size)           # ★ 第二级
            yield buf[i]
            buf[i] = sample
    rng.shuffle(buf)
    yield from buf                                # 收尾把缓冲区倒空
```

> ⚠️ **缓冲区大小 K 的权衡**：
> ```
> K 太小 → 相邻输出的样本仍然来自磁盘上相邻的位置，★ 打乱不充分
> K 太大 → 内存吃紧、启动时要等很久才填满
> ★ 经验值：K 至少要比【一个 global batch】大一到两个数量级
> ★ 自检：随手抽 1000 条连续输出，看它们的 shard 来源是不是足够分散
> ```

## 14.4 ★★ 确定性：为什么必须能一模一样地重跑

```
★ 你会遇到的场景：
  · 模型训到第 8 万步 loss 突然爆了 → 你想知道那一步喂的是什么数据
  · 换了个优化器超参想做 A/B → ★ 数据顺序必须完全一致，否则对比没意义
  · 机器挂了要续训 → 必须从中断处【原样】接上
  · 复现别人的结果

⟹ 结论：★★ 数据流水线必须是【给定 seed 就完全确定】的纯函数。
```

**要做到这一点，有几条硬规矩：**

```
① ★ 所有随机性都从一个显式 seed 派生，不许用系统时间、不许用进程 id
   ⚠️ random.shuffle(x) 不传 seed = 不可复现

② ★★ 数据的随机流要和【模型的随机流】分开
   模型侧的随机（dropout、参数初始化）用 seed_model
   数据侧的随机（shuffle）用 seed_data
   ⚠️ 如果共用一个全局随机流，改一下 dropout 就会连数据顺序一起变
      → ★ 你的 A/B 实验就白做了，而且你根本不会发现

③ ★ 不能依赖字典/集合的遍历顺序、不能依赖 os.listdir() 的返回顺序
   ⚠️ 这两个在不同机器、不同文件系统上顺序可能不同
   ★ 一律 sorted() 之后再用

④ ★ 多进程 DataLoader 的 worker 也要各自拿到确定的 seed
   通常是 seed = base_seed + rank * num_workers + worker_id
```

> ★★ **Megatron 的做法值得学**：它把索引数组**存成文件**，文件名里带一个**参数哈希**。

✅ 我把这一段核对到了本仓库里的 Megatron-LM 源码（`megatron/core/datasets/megatron_dataset.py`），**哈希的输入是这些**：

| ✅ 参与哈希的东西 | 来源 | 改了会怎样 |
|---|---|---|
| 数据集自身的标识（`.bin` 前缀等） | `unique_identifiers` | 换数据集 → 索引重建 |
| `num_samples`（总样本数） | `unique_identifiers["num_samples"]` | ★★ 改 `--train-iters` 或 GBS → 它变 → **整个 shuffle 顺序变** |
| `index_split`（train / valid / test） | `unique_identifiers["index_split"]` | 划分变 → 重建 |
| `random_seed` | `_key_config_attributes()` | 换 seed → 重建 |
| `sequence_length` | 同上 | 改 seq_len → 重建 |
| `split` / `split_matrix` | 同上 | 改 998,1,1 这类比例 → 重建 |
| `tokenizer` | 同上 | ★ 换 tokenizer → 重建 |

```
✅ 源码里是一行 MD5：
     unique_description_hash = hashlib.md5(json.dumps(unique_identifiers))

✅ 然后三个索引各存成一个文件，★ 文件名前缀就是这个哈希：
     {hash}-GPTDataset-train-document_index.npy
     {hash}-GPTDataset-train-sample_index.npy
     {hash}-GPTDataset-train-shuffle_index.npy
   ⟹ ★ 正好对应 14.2 讲的那三个数组。

⟹ 参数完全一样 → 命中缓存 → ★ 顺序必然一致
⟹ 任何一个参数变了 → 哈希变 → ★ 重新构建，且你能从文件名【看出】变了
★★ 这等于把"确定性"这件事变成了【文件系统上可见的事实】，而不是口头约定。

★★★ 顺手记住上表里最毒的那一行：num_samples 也在哈希里。
   ⟹ 这就是 14.5 ① 那个坑的根因 —— "我只是想多训一会儿"
      会改掉 num_samples → 哈希变 → ★ 连【已经训过那段】的顺序都变了。
```
>
> ⚠️ [04 章](04-训练格式-Megatron索引.md)提过的那个坑在这里要再说一遍：
> **索引只在一个 rank 上真正构建，但【所有 rank 都必须走进那段代码】**（其他 rank 在屏障上等）。
> ★ 如果你写了个 `if rank == 0:` 把整段包起来，**程序会静默挂死**——不报错，就是不动。

## 14.5 ★★★ 断点续训：数据侧到底要存什么

千卡训练几个月，**中途一定会挂**（硬件故障、网络抖动、OOM（Out Of Memory，显存耗尽）、有人碰了电源）。
模型权重和优化器状态大家都知道要存。**但数据的进度也是状态。**

### 14.5.1 ★★★ 先把"要恢复什么"列全

> ★ 这张表是本章最该贴在墙上的东西。**每一行漏掉，都会产生一种"不报错的 bug"。**

| # | 要恢复的状态 | 存在哪 | ⚠️ 漏掉它会怎样 | 症状 |
|---|---|---|---|---|
| ① | **数据顺序本身**<br>（三个索引数组） | 不用存：★ 用**相同参数**重建即可（14.4 的哈希保证一致） | 换了 seed / 改了 `num_samples` 或 GBS → 重建出的顺序完全不同 | ★ "续训"实际是一次新训练；loss 曲线有个说不清的小台阶 |
| ② | **已消费的样本数**<br>`consumed_train_samples` | ✅ checkpoint 里（Megatron 真的存了这个字段） | ★★ **从头重新遍历数据** → 前面看过的又看一遍 | ⚠️ **完全不报错**。那部分数据被多训一个 epoch，配比和重复次数全乱 |
| ③ | **数据侧 RNG 状态**<br>（缓冲区 shuffle 用） | ⚠️ 只有 ④/⑤ 式流水线需要（14.3.1 的表） | 缓冲区里那 K 条、以及下一次抽谁，全都丢了 | ★ 续训后局部顺序和原本不同；**数组式方案（Megatron）不受影响** |
| ④ | **模型侧 RNG 状态**<br>（dropout、数据增强） | checkpoint 的 `rng_state` | dropout 掩码序列变了 | ★ 不是错误，但**破坏逐 bit 可复现**，A/B 实验失去可比性 |
| ⑤ | **优化器状态**<br>（Adam 的 m / v） | checkpoint | 动量从零重启 | ★★ 续训后头几百步 loss **明显抬头**，然后慢慢爬回来 |
| ⑥ | **学习率调度器的位置**<br>（`num_steps`） | checkpoint；✅ Megatron 还会拿它和 `consumed_train_samples` **对账** | 学习率跳回高位或提前衰减到底 | ★★ loss 阶跃式变差或训练提前"冻住" |
| ⑦ | **micro-batch / GBS 的 ramp-up 进度** | 由 `consumed_train_samples` 推出 | batch size 曲线对不上 | ★ 有效 batch 与原计划不符，梯度噪声水平变了 |

```
★★★ 把最常见的两种错法对照一下，就知道为什么 ② 是重灾区：

❌ 错法 A：只恢复【step 数】，数据从头读
   → 第 8 万步继续记 step，但数据迭代器回到了第 0 条
   → ★★ 前 8 万步的数据【被完整看第二遍】
   → ⚠️ 不报任何错。你只会看到那段数据对应的 loss 异常低（它见过了），
        以及最终模型对"语料前段"过拟合。

❌ 错法 B：数据位置对了，但【优化器状态】没恢复（只 load 了权重）
   → ★★ Adam 的动量和二阶矩从零开始
   → 现象：续训头几百步 loss 先涨一截再回落 —— ★ 这是最经典的"续训毛刺"

✅ 正确做法 = 上表七行【全部】就位。
   ★ 其中只有 ② 是"数据侧必须显式写进 checkpoint"的那一个，
     ①③ 靠"参数一致 + 重建"，④⑤⑥⑦ 是训练框架本来就该存的。
```

### 14.5.2 错误做法与正确做法

```
❌ 最常见的错误：挂了之后【从头开始遍历数据】
   → 前 8 万步看过的数据又看一遍
   → ★ 相当于对那部分数据多训了一个 epoch，配比和重复次数全乱了
   → ⚠️ 而且【不报任何错】，你只会看到 loss 曲线有点怪

❌ 第二种错误：随便挑个 seed 重新 shuffle
   → 顺序变了，之前没看过的数据可能永远看不到，看过的又看好几遍

✅ 正确做法：★★ 存下【已消费的样本数】consumed_samples
   续训时：
     · 用【完全相同的 seed 和参数】重建索引 → 得到一模一样的三个数组
     · ★ 直接从 shuffle_index[consumed_samples] 开始取
     ⟹ 因为索引是数组，这是 O(1) 的跳转，不需要"空转"前面的步数
```

```python
# 保存
ckpt = {
    "model": ..., "optimizer": ...,
    "consumed_train_samples": consumed,   # ★★ 数据侧唯一【必须显式存】的东西
    #                                   （前提是走数组式索引，见 14.3.1 表的 ②）
    "data_seed": args.seed,               # ★ 存下来是为了续训时能自检
    "data_config_hash": cfg_hash,         # ★ 配比/split/seq_len 的哈希
}

# 恢复
assert ckpt["data_seed"] == args.seed, "★ seed 变了，续训不等价！"
assert ckpt["data_config_hash"] == cfg_hash, "★ 数据配置变了，续训不等价！"
start = ckpt["consumed_train_samples"]
for i in range(start, total_samples):     # ★ 直接跳到断点处
    yield get_sample(shuffle_index[i])
```

> ★★★ **上面那两行 `assert` 是本章最值得抄走的两行代码。**
> 没有它们，"改了配比之后从旧 checkpoint 续训"这种事会**悄无声息地发生**，
> 而事后你完全无法解释模型为什么怪。

✅ **这不是我编的字段名**：我在本仓库的 Megatron-LM 源码里核对过，`megatron/training/checkpointing.py` 里确实有 `args.consumed_train_samples`，而且 `--override-ckpt-iteration` 这条路径就是用 `consumed_train_samples = iteration × global_batch_size` 反算出来的——★ 这恰好从反面印证了下面 ① 那条：**GBS 变了，这个换算就全错了**。

### ⚠️ 几个会让"续训不等价"的隐形因素

```
① ★★ 改了 --train-iters 或 global batch size
   → 总样本数变了 → ★ 索引数组要重建 → shuffle 顺序整个变了
   ⚠️ 这是最反直觉的一个：你只是想"多训一会儿"，
      结果把【已经训过的部分的顺序】也一起改掉了

② 改了数据配比 / 加了一个新数据集
   → BlendedDataset 的组成变了 → 索引重建
   ★ 这在实践中很常见（中途想加数据），
     ⟹ 正确的处理方式是【把它当成一个新阶段】（10 章的多阶段），
        而不是假装续训是连续的

③ ⚠️ DataLoader 的 worker 数量变了
   如果你的采样逻辑依赖 worker_id 分片，改 num_workers 会改变分配
   ★ 稳妥做法：让采样只依赖 (global_step, dp_rank)，★ 不依赖 worker 数

④ ⚠️ 预取（prefetch）的样本在崩溃时已被读出但没进梯度
   → 严格来说会丢几个 batch。★ 通常可以接受，但要知道它存在

⑤ ⚠️⚠️ 你用的不是【数组式索引】，而是【缓冲区式流水线】
   （WebDataset / MDS / 自己写的 IterableDataset —— 14.3.1 表里的 ④⑤）
   → ★★ 此时 consumed_train_samples【不够】：缓冲区内容和 RNG 状态
     也是隐藏状态，它们没进 checkpoint，续训就不等价
   ★ 三条可选的出路（按工程代价从低到高）：
       a) 承认不精确，★ 只保证"不重看已消费的 shard"（代价：顺序对不上）
       b) ★ 把 (shard 游标 + 缓冲区里的 id 列表 + RNG state) 一起存进 ckpt
       c) ★★ 干脆换成数组式索引（Megatron 路线）——
          用 29 GB 内存和随机读，换 O(1) 的精确续训
   ⚠️ 实践里最常见的是 a)，★ 但一定要【在实验记录里写清楚】
      它不是严格续训，否则后人复现不出来还以为是自己错了。
```

## 14.6 多机多卡：谁拿哪一份数据

```
一次训练里，GPU 被切成几个维度（隔壁 [大模型架构入门] 讲过并行方式）：

  DP  数据并行 Data Parallel      —— ★ 不同 DP rank 处理【不同的数据】
  TP  张量并行 Tensor Parallel    —— ★ 同一份数据被切开算
  PP  流水并行 Pipeline Parallel  —— ★ 同一份数据流过不同的层

★★★ 于是数据侧的铁律只有一条：
   【同一个 DP 组内的所有 GPU（也就是 TP 组和 PP 组里的所有卡）
     必须拿到【完全一样】的那一份数据；
     不同 DP rank 之间必须拿到【完全不重叠】的数据。】
```

```
一个 global batch = GBS 条样本，切给 DP_SIZE 个数据并行组：

   dp_rank 0 拿  shuffle_index[base + 0 : base + m]
   dp_rank 1 拿  shuffle_index[base + m : base + 2m]
   ...                              其中 m = GBS / DP_SIZE

  ★ 通常的实现：只有 TP-rank 0 且 PP 首尾级的卡真正读数据，
    然后【广播】给同 TP/PP 组的其他卡 —— 既保证一致，又不浪费 IO
```

```
⚠️ 两个典型故障：
  · 同 TP 组的卡读到了不同数据 → ★ 梯度 all-reduce 出来是垃圾
    现象：loss 剧烈震荡或直接 NaN
  · 不同 DP rank 拿到重复数据 → 有效 batch 变小、部分数据永远看不到
    现象：★ 不报错，只是收敛慢一点点 —— 极难发现
★ 自检：训练启动时让每张卡打印它第一个 batch 的 token 校验和（比如 md5 前 8 位），
       手动看一眼是不是"同 TP 组相同、不同 DP 组不同"。
```

## 14.7 ⚠️ 七个坑

```
① ★★ 挂了从头重新遍历数据（14.5）—— 不报错，配比悄悄变了
   ★ 症状：那段数据对应的 loss 异常低（模型见过了）

② ★★ 数据随机流和模型随机流共用一个全局 seed
   → 改 dropout 顺带改了数据顺序 → ★ A/B 实验全部作废

③ shuffle 缓冲区 K 太小
   ★ 现象：loss 曲线上有周期性的小波动，周期恰好对应 shard 大小
   —— ★ 这是一个很好的诊断信号，看到就该怀疑 shuffle 不充分

④ ⚠️ 只在 rank 0 里构建索引（把 if rank==0 包住了整段）
   → ★ 程序静默挂死在屏障上，不报错、不超时、日志停在那里

⑤ ⚠️ 中途加数据集 / 改 train-iters 后直接续训
   → 索引重建 → 顺序全变 → ★ "续训"实际上是一次新的训练
   ✅ 根因已查实：num_samples 在 Megatron 的索引哈希输入里（14.4 的表）
   ★ 正确姿势：当成 10 章的一个新阶段来对待，并在实验记录里写清楚

⑥ ⚠️⚠️ 只 load 了模型权重、没恢复【优化器状态】
   → ★ Adam 的动量/二阶矩从零重启
   ★ 症状：续训头几百步 loss 先涨一截再回落 —— 经典的"续训毛刺"
   ⚠️ 这一条不属于数据侧，但它和 ① 的症状容易被混为一谈，所以列在这里

⑦ ⚠️⚠️ 用缓冲区式流水线（WebDataset/MDS/自写 IterableDataset）
   却照抄"只存 consumed_samples"这一招
   → ★★ 缓冲区内容和 RNG 状态没进 checkpoint ⟹ 续训不等价
   ★ 见 14.5 隐形因素 ⑤ 的三条出路
```

## 14.8 小结

```
① 不 shuffle 会导致灾难性遗忘、loss 台阶、能力偏向最后看到的数据
   ★ 原理：SGD 的保证建立在"每个 batch 独立同分布采样"上
   ⚠️ 但退火（10 章）和长度课程（13 章）是【故意设计的顺序】—— 
     区别在于"受控"还是"意外"

② Megatron 三层索引各管一件事：
   document_index → 文档访问顺序 / sample_index → 样本切分位置 /
   shuffle_index → ★ 样本访问顺序
   ★★★ 关键性质：它们是【预先算好的数组】⟹ 取第 i 条是 O(1) 查表
      ⟹ 这是 ⑤ 断点续训能做干净的前提

③ ★★ shuffle 有五种做法（14.3.1 一张表对齐三个维度）：
   ① 不 shuffle ② 全局 shuffle 数组 ③ 分片内 ④ 缓冲区 ⑤ 两级
   ★ 关键取舍：
     ② 全局数组 → 随机性最好 + ★★ 能 O(1) 精确续训，
        代价是 36.6 亿条样本要 **29.3 GB（= 27.3 GiB）** 的 int64 数组
        ⚠️ 外加【全随机磁盘读】
     ④/⑤ 缓冲区 → 顺序读、内存只要 K 条（K=10 万 ≈ 0.8 GB），
        ⚠️⚠️ 但它是【有状态的流】，★ 不能靠一个 consumed 数字精确续训
   ⟹ ★★★ Megatron 选 ②，就是拿内存和随机读换"续训是查表"
   ⚠️ 用 ④ 的话 K 至少要比一个 global batch 大一到两个数量级

④ ★★ 确定性四条规矩：
   显式 seed 派生 / ★ 数据 seed 与模型 seed 分开 /
   不依赖 listdir 与字典顺序（一律 sorted）/ worker seed 也要确定
   ★ Megatron 把索引存成【文件名带参数哈希】的缓存 —— 
     把确定性变成了文件系统上可见的事实
     ✅ 哈希输入已核对源码：数据集标识 / num_samples / index_split /
        random_seed / sequence_length / split / split_matrix / tokenizer
     ✅ 产物就是那三个 .npy（document_index / sample_index / shuffle_index）
   ⚠️ 索引只在一个 rank 构建，但所有 rank 都要进那段代码，否则★静默挂死

⑤ ★★★ 断点续训要恢复【七件事】（14.5.1 整张表）：
   ① 数据顺序（靠参数一致重建）② consumed_train_samples ③ 数据侧 RNG
   ④ 模型侧 RNG ⑤ 优化器状态 ⑥ LR 调度器位置 ⑦ batch ramp-up 进度
   ★ 其中只有 ② 是【数据侧必须显式写进 checkpoint】的
     ✅ Megatron 的 checkpointing.py 里确实有这个字段
   ⚠️ 两种最典型的错法，★ 症状完全不同但都不报错：
     · 只恢复 step 数、数据从头读 → ★ 前 8 万步数据被看两遍，
       那段的 loss 异常低
     · 只 load 权重、优化器状态归零 → ★ 续训头几百步 loss 先涨再落
   ★ 一定要加两行 assert：seed 一致、数据配置哈希一致
   ⚠️ 会让"续训不等价"的隐形因素：改 train-iters / 改 GBS / 改配比 /
      改 num_workers ⟹ 都会重建索引、改变顺序
      ✅ 根因查实：num_samples / seed / seq_len / split / tokenizer
         全都在 Megatron 的索引哈希输入里（14.4 的表）
      ★ 中途加数据请当成一个【新阶段】，别假装是连续的
   ⚠️⚠️ 而且"只存 consumed"这一招【只在数组式索引下成立】——
      用缓冲区式流水线时必须额外存缓冲区内容 + RNG 状态

⑥ ★★★ 多机多卡铁律：同 DP 组内（TP/PP 各卡）数据必须【完全相同】，
   不同 DP rank 之间必须【完全不重叠】
   ★ 通常由 TP-rank 0 读数据再广播
   ⚠️ 前者错 → loss 震荡/NaN；★ 后者错 → 不报错，只是悄悄变慢变差
   ★ 自检：启动时打印每卡首个 batch 的 token 校验和，肉眼比对
```
