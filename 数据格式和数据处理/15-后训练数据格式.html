15 · ⭐ 后训练数据格式：从"纯文本"到"结构化对话"

前面 14 章讲的都是【预训练】的数据。
这一章讲【后训练】——也就是把一个"只会续写"的模型变成"能对话、会用工具"的模型时，数据长什么样。

★ 这一章几乎不涉及大规模清洗，但格式细节出错的代价极高，
而且每一个坑都不会报错，只会让模型行为变得莫名其妙。

15.1 先说清楚：预训练数据和后训练数据的根本区别

预训练数据：
   { "text": "北京是中国的首都，位于华北平原北部……" }
   ★ 一整篇纯文本，【每一个 token 都要算 loss】
   ★ 训练目标：预测下一个词
   ★ 规模：万亿 token

后训练数据（SFT）：
   {
     "messages": [
       {"role": "system",    "content": "你是一个helpful的助手"},
       {"role": "user",      "content": "北京在哪？"},
       {"role": "assistant", "content": "北京位于华北平原北部……"}
     ]
   }
   ★ 有【角色结构】
   ★★★ 训练目标：只学【assistant 说的话】，不学 user 说的话
   ★ 规模：几万 ~ 几百万【条】

⚠️ 先把"小多少"这个数算对：别拿「条」和「token」比

⚠️ 「后训练数据比预训练小六个数量级」这句话流传很广，但它在偷换单位：

预训练的规模单位是【token】：   10¹² token（万亿级）
后训练的规模单位是【条】：      10⁵ ~ 10⁶ 条

❌ 直接相除：10¹² / 10⁶ = 10⁶ ⟹ "小六个数量级"
   ★ 错在哪：★★ 分子是 token 数，分母是【样本条数】—— 两个不同的量纲。

✅ 换成同一个单位（token）再比：
   一条 SFT 样本（多轮对话 + 回答）平均约 10³ token
     ⟹ 后训练总量 ≈ 10⁵~10⁶ 条 × 10³ token/条 = 10⁸ ~ 10⁹ token
   ⟹ 10¹² / 10⁹ = 10³     （数据多的那一端）
      10¹² / 10⁸ = 10⁴     （数据少的那一端）
   ⟹ ★★★ 按 token 算，后训练比预训练小【三到四个数量级】，不是六个。

★ 还要再扣一刀才是"真正学到的量"：
  后训练里【只有 assistant 的部分算 loss】（15.3），
  一条多轮样本里 assistant 占比常在 30%~50%
  ⟹ ★ 真正产生梯度的 token 又要再打个对折 ⟹ 约 10⁷·⁷ ~ 10⁸·⁷
  ⟹ ★★ 所以"小四到五个数量级"是更诚实的说法。

⚠️ 这不是抠字眼。整本教程里 token / 字符 / 字节 / 条 这四个单位反复出现，混一次结论就错一个数量级：
★ 条 要乘平均长度才是 token；★ token 要乘平均压缩率（9.5 节：中文约 3.8~4.0 字符/token）才是字符；★ 中文一个汉字在 UTF-8 里通常是 3 字节，所以"字符数"和"字节数"也差着三倍。

SFT = Supervised Fine-Tuning（有监督微调），指用"问题—标准回答"配对数据继续训练模型。
它是后训练的第一步，后面通常还有 RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）、DPO（Direct Preference Optimization，直接偏好优化）或 RLVR（Reinforcement Learning with Verifiable Rewards，基于可验证奖励的强化学习）等对齐阶段（15.7 / 15.8）。
★ 这四个缩写本章都会用到，后面不再重复展开。

★★ 核心认知：底层训练机制【完全没变】，还是"预测下一个 token"。
   变的只有两件事：
     ① 输入被套进了一个【固定的结构化模板】
     ② ★★★ loss 只在一部分位置上计算

15.2 ChatML：把对话拍平成一串 token

模型只认 token 序列。所以那个 JSON 必须先被拍平（flatten）成纯文本。

ChatML（Chat Markup Language，对话标记语言）是目前最通用的一种拍法：

<|im_start|>system
你是一个helpful的助手<|im_end|>
<|im_start|>user
北京在哪？<|im_end|>
<|im_start|>assistant
北京位于华北平原北部……<|im_end|>

★ 三个要点：
  ① <|im_start|> / <|im_end|> 是【特殊 token】—— 09 章说过要在训 tokenizer 时
     就【预留】好，它们在词表里是单独的 id，不是几个字符拼出来的
  ② 角色名（system/user/assistant）是【普通文本】，跟在 <|im_start|> 后面
  ③ ★★ 生成时，模型看到的最后是：
        <|im_start|>assistant\n
     ⟹ 这叫【生成提示 generation prompt】，是在"请你现在开始说话"

★ chat template：一个必须知道的实践细节

每家模型的模板都【不一样】：
   ChatML 用 <|im_start|>...<|im_end|>
   Llama 系用 [INST] ... [/INST] 或 <|start_header_id|>
   还有各种各样的变体

★★ 所以现在的开源模型会在 tokenizer 配置里带一个 chat_template
   （一段 Jinja2 模板），由框架统一渲染。

⚠️⚠️ 最常见的线上事故：
   训练时用模板 A 拼数据，推理时框架用模板 B 渲染
   → ★ 模型看到的格式和训练时不一样
   → 现象：模型开始自问自答、不停止、或者回答质量断崖式下跌
   ★ 自检：把一条训练样本用【推理时的那条代码路径】渲染一遍，
          和训练时拼出来的字符串做【逐字符 diff】

15.3 ★★★ loss 掩码：本章最重要的一件事

拍平之后是一串 token。但【不是每个 token 都该算 loss】。

  <|im_start|>user \n 北京在哪？ <|im_end|> \n   <|im_start|>assistant \n 北京位于…… <|im_end|>
  |<------------ loss_mask = 0 ----------->|   |<---------- loss_mask = 1 ---------->|
         ★ 不学（这是别人说的）                        ★ 学（这是你该说的）

★★★ 逐 token 把 mask 标出来：一条真的多轮样本

★ 上面那张示意图只分了两段。真实样本是多轮交替的，所以这里把一条完整样本一个 token 一个 token 列出来。

原始样本（两轮对话）：

{"messages": [
  {"role": "system",    "content": "你是一个严谨的助手。"},
  {"role": "user",      "content": "北京在哪？"},
  {"role": "assistant", "content": "北京位于华北平原北部。"},
  {"role": "user",      "content": "人口多少？"},
  {"role": "assistant", "content": "约 2100 万。"}
]}

拍平 + 逐段标 mask（⚠️ 为了看得清，把"一个角色头 / 一段正文"当成一组；真实实现是逐 token 的）：

# token 段（ChatML 拍平后） 属于谁 loss_mask 为什么
1 <\|im_start\|> system \n 框架 0 ★ 角色头是模板，不是模型要生成的内容
2 你是一个严谨的助手。 system 0 ★ 系统提示是我们写给它的，不是它说的
3 <\|im_end\|> \n 框架 0 这一轮不是 assistant 的，结束符也不学
4 <\|im_start\|> user \n 框架 0 同 1
5 北京在哪？ user 0 ★★ 最关键的一行：学了它，模型就会自己编问题
6 <\|im_end\|> \n 框架 0 同 3
7 <\|im_start\|> assistant \n 框架 0 ⚠️ 易错：这是推理时由框架喂进去的生成提示，模型不需要学会打出它
8 北京位于华北平原北部。 assistant ★ 1 ✅ 这才是我们要教的
9 <\|im_end\|> 框架 ★★ 1 ★★★ 必须学！ 它是停止信号（见下方说明）
10 \n 框架 0 或 1 ⚠️ 各家实现不一；★ 关键是训练和推理用同一套（见 15.2）
11 <\|im_start\|> user \n 框架 0 第二轮开始
12 人口多少？ user 0 同 5
13 <\|im_end\|> \n 框架 0 —
14 <\|im_start\|> assistant \n 框架 0 同 7
15 约 2100 万。 assistant ★ 1 ✅ 第二段要学的内容
16 <\|im_end\|> 框架 ★★ 1 同 9 
★★★ 这张表要读出来的四件事：

① ★ mask=1 的区域【不是一段，是多段】（第 8-9 组、第 15-16 组）
   ⟹ 这就是 15.4 说"多轮要写成【逐段】mask"的原因。

② ★★ 结束符 <|im_end|> 的 mask 是 1 —— ★ 和它前面的正文一起学。
   ⟹ 但只在【assistant 的那一轮】是 1（第 9、16 组）；
      user/system 那几轮的 <|im_end|>（第 3、6、13 组）仍是 0。
   ⚠️ 这是最容易写成"所有 <|im_end|> 都学"或"所有都不学"的地方，两种都错。

③ ★ 角色头（<|im_start|>assistant\n）的 mask 是 0。
   ⚠️ 新手直觉是"模型要学会说自己是 assistant"—— 不需要。
      ★ 推理时这几个 token 是【框架替它写进去】的（15.2 的"生成提示"）。

④ ★★ ⚠️ 粗估一下有效 token 占比（★ 下面两个数都是估的，不是实测）：
   整条样本假设 ≈ 60 个 token，mask=1 的两段（第 8-9、15-16 组）≈ 17 个
   ⟹ ★ 只有约 17/60 ≈ 28% 的 token 在产生梯度。
   ⟹ 这就是 15.1 那段"真正学到的 token 还要再打对折"的来历。
   ★ 自检时别猜：直接 print(sum(mask), len(mask)) —— 这两个数必须自己量。

自检脚本（强烈建议每次改完格式都跑）：

# ★★★ 把 mask==1 的位置解码回文本打印出来，肉眼比对
learned = tok.decode([t for t, m in zip(ids, mask) if m == 1])
print(repr(learned))
# ✅ 期望输出（顺序拼接，不多一个字不少一个字）：
#    '北京位于华北平原北部。<|im_end|>约 2100 万。<|im_end|>'
# ⚠️ 如果里面出现了"北京在哪？"→ ★ 你把 user 也学了（坑①）
# ⚠️ 如果末尾没有 <|im_end|>  → ★ 你漏了结束符（坑②）
# ⚠️ 如果整体错开一格（比如开头多了个"。"）→ ★ 移位差一（坑③）

为什么必须这样？

如果对 user 部分也算 loss：
   → ★★ 模型在学"怎么提问"
   → 现象：★ 你问它一个问题，它回答完之后【自己又编了一个新问题】，
          然后自问自答下去，停不下来
   —— 这是新手做 SFT 最常见的失败现象，而且往往找不到原因

def build_sft_sample(messages, tok, max_len=4096):
    ids, mask = [], []
    for m in messages:
        head = tok.encode(f"<|im_start|>{m['role']}\n", add_special_tokens=False)
        body = tok.encode(m["content"], add_special_tokens=False)
        tail = tok.encode("<|im_end|>\n", add_special_tokens=False)

        learn = (m["role"] == "assistant")          # ★★ 只有 assistant 要学
        ids  += head + body + tail
        mask += [0]*len(head) + [int(learn)]*len(body) + [int(learn)]*len(tail)
        #        ↑ 角色头永远不学    ↑ 正文按角色决定   ↑ ★ 结束符【要学】！
    return ids[:max_len], mask[:max_len]

★★★ 注意上面那个 tail 的掩码是 1，不是 0。
<|im_end|> 是【停止信号】。 如果不对它算 loss → 模型永远学不会"什么时候该停" → ⚠️ 现象：回答完了继续往下胡说，直到撞上最大长度 ★ 这是 loss 掩码里最容易写错的一个位置。

★ 移位（shift）：一个差一错误的重灾区

语言模型的训练目标是"用位置 i 预测位置 i+1"，所以：

   logits[i]  ←→  labels[i+1]

⟹ ★ 你的 loss_mask 也必须跟着移一位，否则整体错开一格：
   模型会用"assistant 的最后一个 token"去预测"下一轮 user 的第一个字"

★ 自检方法（强烈建议每次改完格式都跑一遍）：
   把 loss_mask == 1 的位置对应的 token 【解码回文本打印出来】，
   ⟹ 肉眼确认：★ 打出来的应该【正好就是 assistant 说的话 + 结束符】，
     不多一个字，不少一个字。

15.4 多轮对话怎么展开

一条 5 轮的对话，有两种做法：

① ★ 一条样本，多段 loss（推荐）
   把 5 轮全部拼成一条序列，
   ★ 其中 3 段 assistant 的位置 mask=1，其余为 0
   ✅ 优点：只算一遍前向，效率高；★ 且模型能看到完整的对话历史

② 拆成 3 条样本
   第 1 条：轮1 → 答1
   第 2 条：轮1+答1+轮2 → 答2
   第 3 条：轮1+答1+轮2+答2+轮3 → 答3
   ❌ 前缀被重复计算多次，★ 算力浪费严重
   ✅ 但在某些框架里实现更简单

★★ 现在几乎都用①。这也是为什么 15.3 的 mask 要写成【逐段】的，
   而不是简单的"最后一段是答案"。

⚠️ 和 13 章的联动：SFT 样本普遍很短（几百 token），
所以一条 4096 的序列里会塞进十几条不同的对话。
★ 此时 13 章的文档掩码是【必须】的，而且 loss_mask 要跟着打包一起重排 ——
这两件事任何一个漏了，都不会报错，只会让模型变怪。

15.5 工具调用的数据格式

要让模型会用工具（function calling），训练数据里就得有工具调用的样本。

一次完整的工具调用，在数据里是【四段】：

  ① user       "北京今天天气怎么样？"
  ② assistant  ★ 发起调用（这一段【要学】）
                 <tool_call>{"name":"get_weather","arguments":{"city":"北京"}}</tool_call>
  ③ tool       ★ 工具返回结果（这一段【不学】—— 是环境给的，不是模型说的）
                 {"temp": 28, "condition": "晴"}
  ④ assistant  "北京今天晴，28 度。"（这一段【要学】）

★★ 掩码规则的推广（比"只学 assistant"更准确的说法）：

   【只学【模型自己产生】的 token，不学【环境或对方产生】的 token】

   user 说的        → 不学
   tool 返回的      → ★ 不学（新手最容易在这里出错）
   system 提示      → 不学
   assistant 说的   → 学
   assistant 发起的工具调用 → ★ 学（这是模型的决策！）

⚠️ 三个实践细节：
  ① 工具定义（有哪些工具、参数是什么）通常放在 system 里，★ 不学
  ② ★ 参数必须是【严格合法的 JSON】—— 训练数据里如果有格式错的样本，
     模型会学会输出格式错的 JSON，而下游解析器会直接崩
     ★ 建议：入库前对每一条 tool_call 做 json.loads() 校验，不通过就丢
  ③ ★ 要有【负样本】：不需要调工具的问题，模型应该直接回答
     否则模型会学成"什么问题都先调一次工具"

15.6 推理数据：思维链要不要学、怎么学

现在的模型普遍有"先想后答"的能力，数据格式上体现为：

<|im_start|>assistant
<think>
用户问的是……我需要先算……所以答案是……
</think>
北京位于华北平原北部。<|im_end|>

★ 三个设计问题（各家做法不同）：

① <think> 里的内容要不要算 loss？
   ★ 要学 —— 否则模型学不会怎么思考。
   ⚠️ 但有些做法会给思维链一个【更低的 loss 权重】。

② 多轮对话里，上一轮的 <think> 要不要保留在上下文里？
   ★ 多数做法是【不保留】—— 下一轮只看到上一轮的最终答案。
     理由：思维链很长，保留会迅速吃光上下文
   ⟹ ★★ 于是训练数据的拼接方式必须和推理时【严格一致】，
        否则又是 15.2 那个模板不一致的坑

③ 思维链数据从哪来？
   ★ 主要靠 [12 章](12-合成数据.md)的合成 + 拒绝采样：
     让模型对同一道题采样 N 次 → ★ 只保留【最终答案正确】的那些轨迹
   ⟹ 这正是 12.7 说的【可验证领域】的做法

⚠️ 一个诚实的说明：思维链数据的具体构造方法是当前各家披露最少的部分之一。
★ 上面写的是公开可见的通行做法，不代表任何一家的具体实现。详见 16 章。

15.7 偏好数据：给"哪个回答更好"打标

SFT 之后的对齐阶段，需要的是另一种格式的数据：

{
  "prompt":   "写一首关于秋天的诗",
  "chosen":   "……（人类/模型评判为更好的回答）",
  "rejected": "……（更差的回答）"
}

★ 注意它是【成对】的，而且共享同一个 prompt。

两种用法：

① 训一个【奖励模型 RM】（Reward Model）
   目标：让 RM 给 chosen 打的分 > 给 rejected 打的分
   损失：L = −log σ( r(chosen) − r(rejected) )
   ★ 其中 σ 是 sigmoid，把"分差"压到 (0,1) 区间当概率看
     ⟹ 分差越大，损失越小；分差为 0 时损失 = −log 0.5 ≈ 0.693
   ★ 然后用这个 RM 去做强化学习（PPO 等）

② ★ 直接偏好优化 DPO
   跳过 RM，★ 直接用这对数据去优化模型本身
   ⟹ 少训一个模型、少一个环节，工程上简单得多
   ⟹ ★ 这是它这两年被广泛采用的主要原因

★★ 偏好数据的三个来源（成本递减、噪声递增）：
  ① 人工标注          —— 最贵、最准
  ② ★ 模型评判（LLM-as-a-judge）—— 用一个强模型来打分
  ③ ★ 规则/验证器自动构造 —— 数学题：对的当 chosen，错的当 rejected
     ⟹ 又回到 12.7 的【可验证领域】

⚠️ 偏好数据最大的陷阱：★【长度偏置】
   人类和模型评判都倾向于给【更长的回答】更高分
   → 模型学会了"把话说长"而不是"把话说好"
   ★ 缓解：构造数据时控制 chosen/rejected 的长度分布，
          或在训练目标里做长度归一化

15.8 ★★★ 三种后训练数据格式：字段逐项对照

★ 前面 15.1-15.7 是一节一种格式地讲。这一节把 SFT / 偏好对 / RLVR 三种格式并排摊在一张表上，因为实践中你会在同一个项目里同时用到三种，最容易搞混的就是"哪个字段是必需的、loss 怎么算"。

字段对照表

★★★ 一句话串起这三种：

  ① SFT    = 「照着这个答案说」          —— 教【格式和风格】
  ② 偏好对 = 「这两个里哪个更好」        —— 教【人类偏好】（没有标准答案的领域）
  ③ RLVR   = 「你自己试，我只告诉你对不对」—— 教【把事情做对】（有标准答案的领域）

★★ 为什么 ③ 这两年火起来：★ 它是唯一一种【数据量不受人工标注产能限制】的格式
   —— 只要题目和判题器到位，模型可以自己采样出任意多的训练信号。
   ⟹ 这正是 [12.7 节](12-合成数据.md)"可验证领域是合成数据的甜区"的另一面。

同一道题，三种格式各写一遍

★ 刻意用同一个问题，这样区别一眼就能看出来。

① SFT：

{"messages": [
  {"role": "system",    "content": "你是一个数学助手，先给步骤再给答案。"},
  {"role": "user",      "content": "一个班有 36 人，其中 5/9 是女生，男生有多少人？"},
  {"role": "assistant", "content": "女生 = 36 × 5/9 = 20 人。\n男生 = 36 − 20 = 16 人。\n答：男生有 16 人。"}
]}

★ loss 在哪：只有最后那段 assistant 的内容 + 它的 <|im_end|>（mask=1）
⚠️ 这条样本的质量【完全取决于那段答案写得对不对】——
   ★ 如果答案算错了，模型就学会了错的算法，而且学得很扎实。

② 偏好对：

{"prompt": "一个班有 36 人，其中 5/9 是女生，男生有多少人？",
 "chosen":   "女生 = 36 × 5/9 = 20 人，所以男生 = 36 − 20 = 16 人。答：16 人。",
 "rejected": "36 的 5/9 大约是 20 人左右，剩下的就是男生，应该有十几个人。"}

★ 注意这一对的差别【不在对错，而在"好不好"】：
  rejected 其实没说错，只是【含糊、不给确数】。
⟹ ★★ 这正是偏好数据擅长的事：教【表达方式和严谨程度】，
   而这种东西没法写成"标准答案"。
⚠️ 而这也是【长度偏置】的来源：chosen 通常更长更完整
   ⟹ ★ 模型可能学成"把话说长"而不是"把话说准"（15.7）。

③ RLVR：

{"prompt": "一个班有 36 人，其中 5/9 是女生，男生有多少人？",
 "answer": "16",
 "verifier": "exact_match_after_normalize"}

★★★ 注意这条样本里【没有任何一段"回答"】！
   它只有：题目 + 标准答案 + 怎么判。

★ 训练时发生的事：
   ① 模型对这道题采样 8 条回答（温度 > 0，所以每条不一样）
   ② 判题器各判一次 → 比如 3 条答出 16（奖励 1），5 条答错（奖励 0）
   ③ ★ 按奖励给这 8 条轨迹加权，做策略梯度更新
   ⟹ ★★ 答对的那 3 条被"鼓励"，答错的 5 条被"抑制"

★★ 和 ① 的本质区别：
   ① 的监督信号是【别人写的那一条答案】——★ 模型只能模仿
   ③ 的监督信号是【自己生成、被判对的那几条】——★ 模型在自己的分布上改进
   ⟹ 这就是为什么 ③ 对"把题做对"这类能力提升更直接。

⚠️⚠️ ③ 最大的坑是【奖励被钻空子（reward hacking）】：
   · 判题器写成"答案里出现 16 就算对" → ★ 模型学会把 0~100 全列一遍
   · 判题器只看最终数字 → ★ 模型学会跳过推理直接猜一个常见答案
   ★ 所以 verifier 这一行代码的严格程度，直接决定这份数据有没有用。

⚠️ 一个诚实的边界：本节只讲【数据长什么样】。
   ★ PPO（Proximal Policy Optimization，近端策略优化）、
     GRPO 这些算法怎么用这些数据做更新，属于强化学习的范围，
     不在本教程（数据侧）的范围内。

15.9 ★ 后训练数据：少而精 vs 多而杂

预训练的逻辑是【越多越好】（11 章的 scaling law）。
★★ 后训练的逻辑【完全不同】：

  · SFT 数据的作用更像是"教格式和风格"，而不是"教知识"
    ——知识在预训练阶段就已经在模型里了
  · ⟹ 少量高质量数据就能激活出很好的对话能力

⚠️ LIMA（Less Is More for Alignment，"对齐上少即是多"，arXiv:2305.11206）
   这篇工作是这个观点的代表：它用【约一千条】精心挑选的样本
   就做出了很强的对话能力。
   ⚠️⚠️ 核对说明：该论文的 PDF【不在本目录 papers/ 内】，
      ★ 上面这句是通行说法，我没有逐句核对原文 ——
      具体数字、模型规模与评测口径请以原文为准。

★ 所以后训练数据的工作重心和预训练【正好相反】：

   预训练：★ 规模优先 —— 工作量在【大规模自动化清洗】
   后训练：★ 质量优先 —— 工作量在【逐条人工审核和构造】

⚠️ 但要注意：这个"少而精"的结论主要针对【通用对话能力】。
   ★ 要教会模型【具体的新技能】（工具调用、特定格式、长思维链），
     数据量还是要上去的 —— 因为那确实是在教新东西。

15.10 ⚠️ 八个坑

① ★★★ loss 掩码写错，把 user 的部分也学了
   → 模型自问自答、停不下来。★ 这是最经典的 SFT 失败现象

② ★★ 忘了对 <|im_end|> 算 loss
   → 模型不知道什么时候停，回答完继续胡说到最大长度

③ ★★ 移位差一：loss_mask 没跟着 labels 一起移一位
   ★ 自检：把 mask==1 的位置解码打印出来，肉眼比对是不是正好是 assistant 的话

④ ★★ 训练模板和推理模板不一致（15.2）
   ★ 自检：用推理那条代码路径渲染一条训练样本，做逐字符 diff

⑤ ★ tool 返回的内容被当成 assistant 学了
   → 模型学会【自己编造工具返回结果】，而不是等工具真的返回
   ⚠️ 这个现象特别隐蔽，因为编出来的结果往往看着挺合理

⑥ ★ SFT 打包后 loss_mask 没跟着重排（13 章坑④）
   一条 4096 的序列里塞了十几条对话，每条的 mask 边界都要重新对齐

⑦ ⚠️⚠️ 截断把 <|im_end|> 砍掉了（★ 15.3 那段代码就藏着这个坑）
   ids[:max_len] 这一刀如果落在最后一轮 assistant 的中间，
   → ★ 这条样本就变成"话说到一半、没有结束符"的样本
   → ⚠️ 症状和坑② 一模一样（模型不知道何时停），但原因完全不同
   ★ 正确做法：★★ 以【轮】为单位截断 ——
     装不下一整轮就【整轮丢掉】，绝不半轮入库
   ★ 自检：assert ids[-1] == eos_id（或"最后一个 mask=1 的 token 是结束符"）

⑧ ⚠️ 把 RLVR 的样本当 SFT 喂进去（15.8）
   RLVR 的样本里【根本没有回答】，只有题目 + 标准答案 + 判题器
   → ★ 如果你把 answer 字段直接当成 assistant 的回答去做 SFT，
     模型学到的是"看到题目就蹦一个裸答案"，★ 推理过程全丢

15.11 小结

① 预训练数据 = 纯文本、每个 token 都算 loss、万亿 token
   后训练数据 = 结构化对话、★★★ 只对一部分位置算 loss、几万~几百万【条】
   ★★ 底层机制没变（还是预测下一个 token），变的只有【模板】和【loss 掩码】
   ⚠️⚠️ 别信"小六个数量级"：★ 那是拿【token 数】除【条数】得出的，量纲不对
      ✅ 换成同一单位：10⁵~10⁶ 条 × ~10³ token/条 = 10⁸~10⁹ token
         ⟹ 10¹²/10⁹ ~ 10¹²/10⁸ = ★【小三到四个数量级】
      ★ 再扣掉 mask=0 的部分（assistant 常只占 30%~50%）
         ⟹ 按"真正产生梯度的 token"算，★ 约小四到五个数量级

② ChatML 把对话拍平成 token 串：<|im_start|>role\n内容<|im_end|>
   ★ 特殊 token 要在 09 章训 tokenizer 时就预留好
   ★ 结尾的 <|im_start|>assistant\n 叫【生成提示】
   ⚠️⚠️ 最常见线上事故：训练模板 ≠ 推理模板
      → 自问自答 / 不停止 / 质量断崖
      ★ 自检：用推理代码路径渲染训练样本，逐字符 diff

③ ★★★ loss 掩码是本章最重要的一件事：
   ★ 准确的规则不是"只学 assistant"，而是
     【只学模型自己产生的 token，不学环境/对方产生的】
     user 不学 / system 不学 / ★ tool 返回不学 / assistant 学 /
     ★ assistant 发起的工具调用【要学】（那是模型的决策）
   ★★ 15.3 把一条两轮样本【逐 token】标了一遍，三个易错点：
     · ★ mask=1 是【多段】而不是一段（每轮 assistant 各一段）
     · ★★ <|im_end|> 要学，★ 但只有 assistant 那几轮的要学；
       user/system 那几轮的结束符仍是 0 —— 两种一刀切都错
     · ★ 角色头 <|im_start|>assistant\n 的 mask 是【0】
       （推理时它由框架写进去，模型不需要学会打出它）
   ★ 移位差一是重灾区：自检办法是把 mask==1 的 token 解码打印出来看，
     ★ 打出来必须【正好是各段 assistant 的话 + 结束符】，不多不少一个字

④ 多轮对话：★ 一条样本多段 loss（推荐，前向只算一遍）
   而不是拆成 N 条（前缀被重复计算）

⑤ 工具调用数据是四段：user / ★assistant 发起调用（学）/
   ★tool 返回（不学）/ assistant 总结（学）
   ⚠️ 参数必须是严格合法 JSON（入库前 json.loads 校验）
   ⚠️ 要有【不需要调工具】的负样本，否则模型逢问必调工具

⑥ 推理数据：<think> 内容★要学；多轮里上一轮的 think ★通常不保留
   （于是训练拼接必须和推理严格一致）；
   来源主要是★合成 + 拒绝采样（只留最终答案正确的轨迹）—— 即 12.7 的可验证领域

⑦a ★★★ 三种格式的字段对照（15.8 整张表）：
   ① SFT    必需【标准答案】，loss = 对 assistant 段的交叉熵
   ② 偏好对 必需【chosen/rejected 成对、共享 prompt】，
            loss = −log σ(r_chosen − r_rejected)，★ 没有唯一正确答案
   ③ RLVR   ★★★【样本里根本没有回答】，只有 prompt + answer/test_cases
            + verifier；★ 回答是训练时模型自己采样出来的
   ★ 一句话：① 照着答案说（教格式）／② 哪个更好（教偏好）／
     ③ 自己试、我只判对错（教把事做对）
   ★★ ③ 的独特价值：★ 唯一一种【不受人工标注产能限制】的格式
      ⚠️ 代价是最大的坑变成【奖励被钻空子 reward hacking】——
         verifier 写松一点，模型就去钻它

⑦b 偏好数据是【成对】的 (prompt, chosen, rejected)
   → 训 RM（L = −log σ(r_chosen − r_rejected)）或 ★ 直接用 DPO
   三个来源：人工 / 模型评判 / ★ 验证器自动构造
   ⚠️ 最大陷阱是【长度偏置】：评判者偏爱长回答 → 模型学会把话说长

⑧ ★ 后训练的逻辑和预训练【相反】：不是越多越好，而是少而精
   （SFT 主要教格式与风格，知识来自预训练）
   ⚠️ 但教【新技能】（工具、长思维链）时数据量还是要上去

⑨ ⚠️ 八个坑全部【不报错】：学了 user / 没学结束符 / 移位差一 /
   模板不一致 / 学了 tool 返回（★ 模型编造工具结果）/ 打包后 mask 没重排 /
   ★ 截断把结束符砍掉（★ 要以【轮】为单位截断，装不下就整轮丢）/
   ★ 把 RLVR 的 answer 当 assistant 回答去做 SFT（推理过程全丢）
