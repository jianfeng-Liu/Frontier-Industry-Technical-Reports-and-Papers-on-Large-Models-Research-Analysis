A. 记号与单位

文档 document   一篇独立文本（一个网页 / 一本书的一章 / 一个代码文件）
                ★ 数据领域最基本的单位
token           文本切分后的最小单位，一个整数 id
语料 corpus     一堆文档的集合（The Pile、FineWeb 都是语料）
分片 shard      语料被切成的文件块，典型 100 MB ~ 2 GB 一片

L   = 序列长度（一条训练样本多少 token），如 4096 / 8192
B   = batch size
V   = 词表大小（vocabulary size）
N_d = 训练集总 token 数            ← Chinchilla 里的 D
N_p = 模型参数量                   ← Chinchilla 里的 N

1 T token = 10¹² 个 token
⚠️ 粗估：15 T token 的原始文本 ≈ 60 TB 左右的 UTF-8 纯文本
中文 1 个汉字 ≈ 0.5~1 token ／ 英文 1 个单词 ≈ 1.3 token   ⚠️ 经验区间

★ A.1 容量单位：十进制 vs 二进制（这个坑会让你的数字差 10%）

★ 两套单位，名字像、值不一样：
   十进制（硬盘标称、论文、云账单常用）    二进制（操作系统、内存常用）
   1 KB = 10³  = 1,000                     1 KiB = 2¹⁰ = 1,024
   1 MB = 10⁶  = 1,000,000                 1 MiB = 2²⁰ = 1,048,576
   1 GB = 10⁹                              1 GiB = 2³⁰ = 1,073,741,824
   1 TB = 10¹²                             1 TiB = 2⁴⁰ = 1,099,511,627,776
   1 PB = 10¹⁵                             1 PiB = 2⁵⁰

★★ 差多少（这才是要记的）：
   GB → GiB   1 GiB = 1.0737 GB   ⟹ 差 7.4%
   TB → TiB   1 TiB = 1.0995 TB   ⟹ 差 10.0%
   PB → PiB   1 PiB = 1.1259 PB   ⟹ 差 12.6%
   ★ 规律：每上一个台阶，差距再多 2.4%。到 PB 级已经差一个零头了。

⚠️ 实践后果：同一份语料，论文说"1 TB"、`du -h` 显示"931G"
   —— 两个都对，931 GiB = 1.0 TB。★ 不是谁算错了，是单位不同。
   ⚠️ 所以跨来源比语料大小之前，先确认对方说的是哪一套。
   ★ Linux 下 `ls -l` / `du -b` 给字节数（最可靠）；`du -h` 给 KiB/MiB/GiB；
     `du -h --si` 给 KB/MB/GB。

★★ A.2 token / 字符 / 字节：三个单位的换算（全教程最容易搞错的一处）

★★★ 先记死这条链的方向：
       字节 bytes  ──（看编码）──▶  字符 characters  ──（看 tokenizer）──▶  token
   ★ 两步都【不是】固定倍数，所以"token 数"永远不能从字节数精确反推。

① 字节 ⟷ 字符（由 UTF-8 编码决定，这一步是确定的）
   ASCII（英文字母、数字、半角标点）  1 字符 = 1 字节
   ★ 汉字 / 中文标点（全角）          1 字符 = 3 字节   ← 最常用的那条
   拉丁扩展（é ü ñ）、希腊、西里尔     1 字符 = 2 字节
   emoji、部分生僻汉字                1 字符 = 4 字节
   ⟹ ★ 所以"一个汉字 3 字节"是中文 token 成本的根源（见 H.3 的 UTF-8 一条）

② 字符 ⟷ token（由 tokenizer 决定，⚠️ 只有经验区间，没有定理）
   ⚠️ 下面是 15 万量级词表的经验值，不是任何论文的结论：
      中文  1 token ≈ 1~2 个汉字        （反过来：1 汉字 ≈ 0.5~1 token）
      英文  1 token ≈ 3~4 个字母        （反过来：1 单词 ≈ 1.3 token）
      代码  1 token ≈ 2~3 个字符        ★ 最难压，缩进和符号很碎
   ⚠️ 词表越大、训练语料越贴近目标语言，压得越狠。换个 tokenizer 这组数就变。

③ ★ 直接从字节估 token（工程上最常用的那个粗口径）
   纯英文文本   1 token ≈ 4 字节
   纯中文文本   1 token ≈ 3~6 字节     （1~2 个汉字 × 3 字节）
   ★ 中英混排   1 token ≈ 4 字节        ← 本教程和 §19.3 那篇数据墙论文都用这个
   ⟹ 所以 15 T token ≈ 15e12 × 4 = 6e13 字节 = 60 TB（十进制）= 54.6 TiB

★★ 一个具体例子，照着数一遍就记住了：
   文本：    「大模型 LLM」
   字符数：  7     ← '大' '模' '型' ' ' 'L' 'L' 'M'
   字节数：  13    ← 3+3+3（三个汉字）+ 1（空格）+ 1+1+1（三个字母）
   token 数：⚠️ 只能实测，不能算。大概 3~5 个
             （"大模型"可能被切成 1~2 个 token，" LLM" 可能 1~2 个）
   ⟹ ★ 同一段文本，三个数字分别是 7 / 13 / "大概 3~5"。
      前两个是【事实】，第三个是【要跑一遍 tokenizer 才知道的】。

⚠️⚠️ 四条最容易犯的错：
   ① 把"X 字符/token"当成"X 汉字/token" —— 差 3 倍，见 §C 那条 ⚠️⚠️
   ② 把论文的 TB 当成系统的 TiB     —— 差 10%
   ③ 用字节数除以 4 得出 token 数后，当成【精确值】汇报
      ★ 这只是量级估算，凡是这么来的数字都该带 ⚠️
   ④ ★★ 把英文的【字符】和【单词】搞混 —— 差 5 倍多。
      128 K token 对英文装得下约 9.8 万【单词】，★ 不是 50 万。
      50 万是【字符】的量级。⟹ 看到"能装多少万字"先问清是字还是单词。
      ★ 完整换算表见 [9.5 节](09-Tokenizer与词表.md)。

B. 核心公式

① Jaccard 相似度（去重的定义式，[06 章](06-去重.md)）
      J(A,B) = |A ∩ B| / |A ∪ B|
   ★ MinHash 的性质：P[minhash(A) == minhash(B)] = J(A,B)
      ⟹ 这就是为什么能用哈希来估相似度

② LSH 分带的命中概率 / 误判率（[06.5 节](06-去重.md)）
      P(成为候选对) = 1 − (1 − s^r)^b      s = 两篇文档的真实 Jaccard
      b 个带 × 每带 r 行 = k 个 minhash    ★ 必须满足 k = b × r
   ⚠️ 这里故意用小写 b, r, k，和 06 章一致 —— 因为 §A 里的大写 B 是 batch size
   ★★ 公式的两端就是两种错：
      s 低却进了同一个桶 = 假阳（误判成重复）→ ★ 多花钱做两两精算，不会删错
      s 高却没进同一个桶 = 假阴（漏掉真重复）→ ★★ 脏数据直接留在语料里
      ⟹ 调 (b, r) 就是在两者之间挪，★ 没有同时消掉两者的配置
      ★ 假阳只浪费算力（后面还会逐对算真 Jaccard），假阴是真的漏 —— 所以宁可偏假阳

③ 困惑度（[07 章](07-质量过滤.md)）
      PPL = exp( −(1/N) Σ log p(x_i | x_<i) )
   ★ 越低 = 模型越"熟悉"这段文本。⚠️ 但低 ≠ 好（见 07.3）

④ Chinchilla 最优（[11.2 节](11-喂多少-ScalingLaw.md)）
      给定算力 C ≈ 6 · N_p · N_d 时，N_p 与 N_d 应【同比例】增长
   ★ 经验落点：N_d / N_p ≈ 20，口头叫 "20 tokens per parameter"
      例：7 B 参数 → Chinchilla 最优约 140 B token
          70 B 参数 → 约 1.4 T token
   ⚠️⚠️ 【Chinchilla 最优 ≠ 实践最优】，这是全教程最容易被误用的一条：
      · Chinchilla 优化的是"给定【训练】算力，怎么分配参数和数据"
      · ★ 它【完全没考虑推理成本】。而真实世界里一个模型要被调用几十亿次
      · ⟹ 推理成本固定时，★【把小模型喂过量】反而更划算 ——
           同样的服务质量，参数更少 ⟹ 每次推理更便宜、显存更省
      ✅ 最有名的反例：LLaMA 把 7 B 模型喂到 1 T token（≈ 143 : 1），
         LLaMA 2 的 7 B 喂到 2 T token ⟹ ★ 约 286 : 1，是 20 : 1 的 14 倍
      ⟹ ★★ 所以"远超 20"不是偷懒，是【换了一个优化目标】。
         看到一份报告的 token/参数 远大于 20，不要读成"它违反了 scaling law"。
      ★ 本教程覆盖的五家都远超 20 ⟹ 见 §C 的语料规模表自己除一下

⑤ 数据受限下的重复（[11.5 节](11-喂多少-ScalingLaw.md)）
   ✅ 2305.16264 的三个数字（均为报告原文）：
      · ★ 重复到约 4 个 epoch，loss 与"同等数量的全新数据"差别可忽略
        （✅ 实例：8.7 B 模型重复 4 遍，验证 loss 只高 0.5%）
      · ★ 一直到约 16 个 epoch 仍有有意义的收益，★ 之后收益衰减极快
      · ★ 到 40 个 epoch，重复已经【毫无价值】

⑥ 偏好损失（[15 章](15-后训练数据格式.md)）
      L = −log σ( r(chosen) − r(rejected) )      σ = sigmoid

⑦ 打包利用率（[13 章](13-打包与文档掩码.md)）
      利用率 = 总 token 数 / (箱子数 × L)
   ★ 打印这个数字，它是打包好坏的唯一指标

⑧ ★★ 训练算力 6N：那个 6 是怎么来的（[11.1 节](11-喂多少-ScalingLaw.md)）
      C ≈ 6 · N_p · N_d      单位 FLOP，N_p = 参数量，N_d = 总 token 数
   ★ 拆开看，每个参数、每个 token 的 6 次浮点运算：
      前向 2N   ← 一次乘加 = 1 乘 + 1 加 = 2 FLOP，每个权重用一次
      反向 4N   ← 要算两组梯度（对输入的、对权重的），各 2N
      ─────────
      合计 6N
   ⚠️⚠️ 这个 6N 【不含】下面这些，别拿它当账单：
      · 优化器更新（Adam 的一阶/二阶动量）—— ★ 完全没算在内
      · 注意力里的 QK^T 与 AV 两个矩阵乘（它们不按参数量走，按序列长度走）
      · 激活函数、归一化、softmax、通信、重计算（activation recomputation）
   ★ 补上注意力那一项的【补全式】（⚠️ 仍是估算）：
      每个 token 的训练 FLOP ≈ 6·N_p + 12 · L · s · h
      整次训练            C ≈ N_d · ( 6·N_p + 12 · L · s · h )
        N_p = 参数量   N_d = 总 token 数
        L = 层数   s = 序列长度   h = 隐藏维度
      ★ 那个 12 的来历：QK^T 和 AV 两个矩阵乘，前向各 2·s·h（合 4·L·s·h），
        反向是前向的两倍（8·L·s·h）⟹ 4 + 8 = 12·L·s·h
   ⚠️⚠️ 关于 12·L·s·h 这一项，两件事必须知道：
      ① ★ 它【没有扣掉因果掩码】。自回归模型只算下三角，真实量约是一半。
         ⟹ 所以这一项是【上界】，实际约 6·L·s·h。
      ② ★ 它随 s 【线性】增长（对整条序列是平方）—— 所以长上下文训练中
         这一项会从"可忽略"变成"主导项"。短序列下 6N 够用，长序列下不够。
   ★ 一个数量级感：s=4096 时这一项通常只占几个百分点；
     s=128 K 时它可以超过 6·N_p 那一项。⚠️ 自己代一遍，别背结论。

⑨ ★ "压缩到 X%" ≠ "压缩 X 倍"（[03 章](03-存储格式.md) / 去重汇报口径）
      压缩到 20%   ⟹ 剩下原来的 1/5  ⟹ 压缩【5 倍】
      压缩 5 倍    ⟹ 剩下 20%
      压缩了 20%   ⟹ ⚠️ 剩下 80%！只少了 1/5
   ⟹ ★★「压缩到 X%」「压缩 X 倍」「压缩了 X%」是三句不同的话。
      换算：压缩倍数 = 1 / (剩余比例)   剩余比例 = 1 − 减少比例
   ⚠️ 中文技术文里"压缩了 80%"和"压缩到 80%"经常被混用 ——
      ★ 看到这种写法，去找它旁边有没有绝对数值（原来多大、现在多大）来锚定。

⑩ ★★ "时间减少 X%" ≠ "加速 X%"（最常见的读数错误之一）
      加速倍数 = 1 / (1 − 时间减少比例)
      时间减少比例 = 1 − 1 / 加速倍数
   ★ 对照着记几个点：
      时间减少 20%  ⟹ 加速 1.25×  （不是 1.2×）
      时间减少 50%  ⟹ 加速 2×
      时间减少 75%  ⟹ 加速 4×
      时间减少 90%  ⟹ 加速 10×
      ───────────────────────────
      加速 2×       ⟹ 时间减少 50%
      加速 3×       ⟹ 时间减少 66.7%
      加速 10×      ⟹ 时间减少 90%
   ⚠️⚠️ "加速 50%" 的字面意思是 1.5×（时间减少 33.3%），
      ⚠️ 但大量中文材料用它来说"时间减少一半"（= 2×）。
      ⟹ ★ 这两种读法差了 33%。看到"加速 X%"务必找绝对耗时来确认。
      ★ 本教程一律写成"加速 N×"或"耗时从 A 降到 B"，不写"加速 X%"。

⑪ ★★ 去重率 / 过滤率的【分母】：三种口径差别巨大
      同一步操作，可以汇报成三个完全不同的数字：
      · 按【文档数】   删掉的文档数 / 原文档数
      · 按【字节数】   删掉的字节数 / 原字节数
      · 按【token 数】 删掉的 token 数 / 原 token 数
   ★★ 为什么差得远：被删掉的重复文档【系统性地偏短】
      （样板页、导航页、商品参数页、自动生成的占位页都又短又重复）
      ⟹ 所以通常有：★ 按文档数的去重率 > 按字节/token 的去重率
      ⚠️ 反过来，如果一个管线主要删的是长文档（比如整本盗版书、
         大段镜像文档），不等式会【反过来】。★ 没有固定方向，只有固定陷阱。
   ⚠️⚠️ 实践后果：两份报告都说"去重率 30%"，可能一个在说文档数、
      一个在说 token 数，★ 两者对应的真实工作量差一倍以上。
   ★ 所以：① 看到留存率/去重率/过滤率，第一件事是找它的分母；
           ② 自己汇报时【必须写清分母】，本教程 §C 那张表用的是【字节数】。
   ★ 一个一手佐证：[16.4 节](16-五家报告的数据章节.md)里 GLM 的汇报口径是
     「模糊去重后唯一 token +28%」—— ✅ 它明确说了是 token，★ 这是好习惯。

✅ 下表每一格都是把 P = 1 − (1 − s^r)^b 直接代进去算出来的，可以自己验。行按"越往下越严"排。

   ② 从上往下看一列 = 调严的代价。看 s=0.8 那一列：

      ★ 前五行还算平缓，到 9×13 直接掉到 39.9% ——

   ③ k = b·r 变大 ⟹ 曲线更陡，但算哈希的成本线性上涨

⚠️⚠️ 关于"阈值"那一列，必须说清楚（[06.5 节](06-去重.md)有完整推导）：
   ⚠️ 常见口诀写"阈值（P=0.5 处）≈ (1/b)^(1/r)" —— ★ 这句话【不对】。
      把 (1/b)^(1/r) 代回公式得 P = 1 − (1 − 1/b)^b，
      而 (1 − 1/b)^b 在 b 变大时趋向 1/e ≈ 0.368
      ⟹ ★ 这个点上的 P 恒定在 0.63~0.68 附近，趋向 1 − 1/e ≈ 0.632
   ⟹ ★★ 所以 (1/b)^(1/r) 是 S 曲线【最陡处 / 拐点】的近似，【不是半数点】。
   ★ 真正的半数点要解方程：s = (1 − 0.5^(1/b))^(1/r)
      代 b=16, r=8：s = (1 − 0.957603)^(1/8) ≈ 0.674   ← 不是 0.707，更不是 0.75
   ⚠️ 本表早先的版本在这里写过「k=128, b=16, r=8 → s* ≈ 0.75」，★ 两处都错：
      算术上应是 0.707（不是 0.75），含义上是拐点（不是半数点）。★ 已改。

启发式过滤 ~60% 7.2 TB Gopher 那套规则
精确 + 模糊去重 ~45% 3.2 TB ★ 单步砍得最狠的一刀
质量过滤 ~30% 0.97 TB ★ 争议最大的一步（"什么叫好数据"没有共识） 
★ 连乘一遍：0.30 × 0.40 × 0.60 × 0.45 × 0.30 = 0.0097
  ⟹ 总留存率约 1%（粗口径常说"约 0.9%~1%"）
  ⟹ 100 TB → 约 0.97 TB 纯文本
  ⟹ 按 1 token ≈ 4 字节换算：0.97e12 / 4 ≈ 2.4e11 ≈ 2400 亿 token
     ⚠️ 这个"2400 亿"是【按字节数除以 4】推的，不是数出来的

✅ 报告原文对这个指标的定义（一字不改）：
   "We evaluate tokenizer efficiency using the average number of
    characters covered per token, where a higher value indicates
    better compression."

✅ Table 4 的 Chinese 一列（原始值，不做任何换算）：
   openPangu-1.0              词表 153,376   →  3.82
   openPangu-2.0-3digit       词表 150,400   →  4.04
   openPangu-2.0-single-digit 词表 149,600   →  3.82   ← 最终采用的那个
   ✅ Code 一列：2.80 / 2.77 / 2.56   ★ 代码是五类语料里最难压的

⚠️⚠️ 这个 3.82 只能用来做【跨变体的相对比较】，不要拿它换算成「一个 token 覆盖几个汉字」。 理由很具体：

为什么 说明
报告的原词是 characters 它没有说是 Chinese characters（汉字）。两者差三倍：一个汉字的 UTF-8 编码通常是 3 字节，所以"3.82 字节/token"和"3.82 汉字/token"是完全不同的两句话
3.82 汉字/token 高得不寻常 ⚠️ 这一行是我的经验判断，不是任何论文的结论：对一个 15 万量级的词表，中文 tokenizer 的压缩率一般落在 1.5~2 汉字/token 这个范围，3.82 会是它的两倍多。★ 要确认请自己拿一段中文跑一遍目标 tokenizer —— 这是一分钟的事
⚠️ 两种可能，报告都没说清 ① 中文测试集里混了大量 ASCII（英文、标点、数字、代码片段），把 character 计数抬高了；② 脚本里的 character 实际是按字节统计的——若按字节算，3.82 字节/token ÷ 3 字节/汉字 ≈ 1.27 汉字/token，正好落回上面那个经验区间
⟹ 本教程的口径 只记 3.82 这个原始值本身，用它比较"1.0 vs 2.0-3digit vs 2.0-single-digit 谁压得更好"（这是报告真正想说明的事，也是报告里唯一可靠的用法）。不往"多少汉字"这个方向换算。

⚠️ 同一张 Table 4 还有第二处口径问题，一并记在这里：它的 Average 一列（2.56 / 2.71 / 2.59）比表里【每一个】单项都低（以 openPangu-1.0 为例：Chinese 3.82、English 4.30、Multilingual 2.80、Code 2.80、Industry 4.18，最小值是 2.80，而 Average 写的是 2.56）。★ 一个权重非负的加权平均必须落在最小值和最大值之间，这是数学事实——所以这个 Average 一定不是表里这五列的加权平均，它必然覆盖了表中没列出的语料、或者用了别的算法。⚠️ 报告没有说明。 ⟹ 这意味着 9.6 节那句"平均 2.71 vs 2.59"引的是一个口径不明的数；★ 但那里的结论方向仍然可靠——因为 3digit 在五个分项上全部优于 single-digit，不需要靠 Average 来支撑。★ 所以：要论证"哪个变体压得好"，引分项，不要引 Average。

★ 要对照本教程别处的口径：README 记号约定和本表 §A 给的是 1 个汉字 ≈ 0.5~1 token（也就是 1~2 汉字/token）——这是经验区间，和上面那个 3.82 不是同一个指标，不要放在一起比。

D. ★ 三条因果链（全教程骨架）

【链一】数据墙 → 从"筛掉"转向"抢救"

    → 标签驱动【课程采样】⟹ ★ 标注是因，课程是果

【链二】文档长度分布重尾 → 打包 → 污染 → 掩码 → 变长算子
  文档长短不一（13.1）
    → 补齐浪费巨大（✅ 极端 89%）→ 必须【拼接/打包】

    → ✅ 一手佐证：DeepSeek-V4「与 V3 不同，采用样本级注意力掩码」

【链三】确定性 → 断点续训
  训练会崩（14 章）
    → 续训必须喂【完全相同】的数据顺序
    → ⟹ 数据顺序必须是【seed 的纯函数】，不能依赖 listdir/dict 顺序

★★ I. ⚠️ 口径陷阱总表（看到这些写法就要停一下）

这一节不讲算法，只讲【同一个事实被写成不同数字】的那些地方。 ★ 本教程遇到的每一次数字对不上，根源基本都在这张表里。读任何一份技术报告之前先过一遍。

# 看到这种写法 ⚠️ 要先确认什么 为什么会差
1 「X GB / TB / PB」 对方说的是十进制（10⁹/10¹²）还是二进制（GiB/TiB）？ TB vs TiB 差 10%，PB vs PiB 差 12.6%。详见 §A.1
2 「X 字/token」「X characters per token」 原文写的是 character 还是 Chinese character？是不是其实按字节算的？ 一个汉字 3 字节 ⟹ 差 3 倍。详见 §C 的 ⚠️⚠️
3 「X token」 用的哪个 tokenizer、什么词表大小？ 换个 tokenizer，同一份语料的 token 数能差 20~40%
4 「去重率 / 过滤率 / 留存率 X%」 分母是文档数、字节数、还是 token 数？ 被删的重复文档系统性偏短 ⟹ 三个口径能差一倍以上。详见 §B⑪
5 「压缩到 X%」vs「压缩 X 倍」vs「压缩了 X%」 是哪一句？ "压缩到 20%" = 压缩 5 倍 = 压缩了 80%。详见 §B⑨
6 「加速 X%」 是 1+X% 倍，还是"耗时减少 X%"？ "加速 50%" 字面是 1.5×，很多材料用它指 2×。详见 §B⑩
7 「训练用了 X FLOPs」 是 6N 口径（不含优化器、不含注意力项）还是实测？含不含重计算？ 6N 是下界口径；长序列下漏掉的注意力项能占大头。详见 §B⑧
8 「X tokens per parameter」 是 Chinchilla 最优（≈20）还是实际喂量（可达 200~300）？ 两者优化的是不同目标，不是谁违规。详见 §B④
9 「模型在 BENCH 上得 X 分」 BENCH 的版本号是什么？ ✅ 同一个 GLM-5.2：Terminal-Bench 2.1 上 81.0，3.0 上 4.6。★ 跨版本比分数比数据污染更容易骗到人（19.8 节）
10 「语料有 X T token」 是去重前还是去重后？是唯一 token 还是喂进去的 token（含重复 epoch）？ ✅ GLM 的汇报口径就专门写成"模糊去重后唯一 token"（16.4 节）—— ★ 这是因为两者能差一倍
11 「实测 / 我们观察到」 有没有给出实验设置（模型规模、语料、评测集）？ ⚠️ 本教程里凡是回溯不到一手来源的"实测"，一律标 ⚠️ 或不写
12 「论文说 §x.y」 这个 §x.y 是本教程的小节，还是那篇论文的小节？ ★ 本教程的约定：引外部文献一律写成「报告 §x.y」或「原文 §x.y」，裸 §x.y 一律指本教程自己的小节 
★★ 一条可以直接用的自检规则：

   凡是一个数字你【说不出它的分母和单位口径】，
   就【不要】把它抄进自己的文档里。
   ⟹ 宁可写"约 1 TB（按字节数，去重后）"这种啰嗦的写法，
      也不要写一个干净但口径不明的"1 TB"。

★ 本教程自己的口径（统一声明一次）：
   · 语料大小   默认【十进制 TB】，默认【去重后】
   · 留存率     默认按【字节数】（§C 那张表）
   · token 数   默认按【1 token ≈ 4 字节】粗估，★ 凡是这么来的都带 ⚠️
   · 加速       一律写「N×」或「耗时从 A 降到 B」，★ 不写「加速 X%」
   · 外部节号   一律写「报告 §x.y」，★ 裸 §x.y 只指本教程
