检索增强生成 RAG

一句话：让模型答题前，先去资料库里查几页相关材料，连同问题一起塞进去，再让它作答。

⚠️ 先说清楚三件事

① 这是一份单章笔记，不是完整专题。
RAG 在本仓库是个"到处被引用、但没有主场"的概念 —— 推理框架/、harness评测框架/、多模态大模型/ 三个目录都拿它当例子或参照物。这份笔记把散落的引用收拢到一处，并补上原理。第 4 节是交叉引用汇总，想看细节请点回原章节。

② 记号约定：

   ✅  = 能追到一手出处（论文表号 / 本仓库已核对过的章节）
   ⚠️  = 我的判断、推断或估算，引用前请自行核实
   无记号 = 教科书级通用机制，不涉及具体数字

③ 时效：写于 2026 年 9 月。 第 1–3 节讲原理，过期慢；第 5 节讲 agentic RAG 的走向，过期最快。

一句话地图

         你的问题
            │
   ┌────────▼─────────┐    ① 检索 Retrieval
   │  资料库（你的文档） │ ──▶ 捞出最相关的几段
   └──────────────────┘
            │
            ▼            ② 增强 Augmented
   [ 捞到的段落 + 原问题 ] ──▶ 拼成一个很长的 prompt
            │
            ▼            ③ 生成 Generation
        大模型作答

RAG = Retrieval-Augmented Generation（检索增强生成），名字就是这三步。

1. 为什么需要它

大模型有两个天生的毛病：

  1. 不知道你的私有数据 —— 你公司的内部文档、你的代码库，它训练时没见过。
  2. 知识有截止日期 —— 训练完之后发生的事，它一概不知。

类比：闭卷考试 vs 开卷考试。 模型原本闭卷答题，全靠脑子里记住的；RAG 就是允许它开卷 —— 但注意，是你替它翻好书、把那几页撕下来递过去，它自己不会翻书。（"自己会翻书"是第 5 节的 agentic RAG。）

想让模型用上你的数据，一共三条路：

路线 做法 代价 什么时候用
重新训练 / 微调 拿你的数据继续训模型 几十上百张卡、几天；每加一份文档就要再来一次 要改变模型的能力或风格
长上下文全塞 把整个文档库塞进 prompt 贵且慢，且有上限；见 推理框架/02-KV-Cache与显存账 资料本来就不多
★ RAG 只塞检索到的那几段 不动模型，加一份文档只要重新索引 要让模型知道新的/私有的事实

⚠️ 我的判断：这三条路不是竞争关系，实践中经常叠着用 —— 先微调出领域风格，再靠 RAG 供事实。

2. 三步怎么转

   你的问题：「我们公司的报销上限是多少？」
        │
        ├─① 检索（Retrieval）
        │    拿问题去资料库里搜  →  捞出最相关的 3 段文字
        │    （比如《员工手册》第 7 章的三个段落）
        │
        ├─② 增强（Augmented）
        │    把捞到的段落 + 原问题，拼成一个【很长的 prompt】
        │    ┌────────────────────────────────────┐
        │    │ 参考资料：                          │
        │    │  「差旅住宿每晚上限 800 元…」        │
        │    │  「餐饮每日上限 150 元…」            │
        │    │ 请根据以上资料回答：报销上限是多少？  │
        │    └────────────────────────────────────┘
        │
        └─③ 生成（Generation）
             模型读完这一大坨，吐出答案

★ 注意②的形状：输入变得很长（几千个 token），输出还是很短（几百个字）。这个不对称是第 4.1 节的全部由来。

3. 第①步展开：到底怎么"搜"

3.1 先切块（chunking）

资料库不能整本书当一个单位 —— 太长了塞不进去，也不精确。要先切成块（chunk），一般几百个 token 一块。

   《员工手册》80 页
        │  切块
        ▼
   [块1: 入职流程…] [块2: 考勤…] … [块N: 报销标准…]
        ⟹ 检索的单位是【块】，不是【文件】

⚠️ 切块的边界怎么定（按段落 / 按标题 / 定长 + 重叠）是工程上最容易翻车的地方之一：切碎了丢上下文，切大了不精确。

3.2 两种搜法

搜法 原理 强在哪 弱在哪
关键词检索（如 BM25） 对字面。问题里有"报销"，就找含"报销"的块 精确、快、可解释 换个说法就搜不到（"费用报账"）
向量检索（embedding） 把每块文字变成一串数字，意思相近的数字也相近，找离问题最近的块 能跨说法，抓语义 可能召回"看着像但没关系"的块
混合检索 两个都跑，合并结果 实践中的默认选择 要调融合权重

embedding（嵌入向量） = 把一段文字压成一串固定长度的数字（比如 1024 个），这串数字代表它的"意思坐标"。把文字变数字这套机制，和 数据格式和数据处理/09-Tokenizer与词表 是同源的。

3.3 再重排（rerank）

检索快但粗。常见做法是两段式：

   第一段：检索  →  快速捞出 50 个候选块（要的是【别漏】）
        │
   第二段：rerank →  用一个更贵、更准的小模型逐个打分，
                    只留最好的 3~5 块（要的是【别错】）
        │
        ▼
     塞进 prompt

✅ rerank 是长上下文评测里的标准子任务 —— MiniMax M3 论文 Table 3 的 HELMET-128K 就有 Rerank/RAG 这一项（详见 业界模型技术报告/MiniMax-M3.md）。

4. RAG 在本仓库的三个角色

别串了 —— 同一个词，在三个目录里扮演三种完全不同的东西。

4.1 在 推理框架/：它是"长输入短输出"的典型负载

推理优化入门/10-PD分离 整章拿 RAG 当例子：

   输入：一份文档 + 问题 = 4096 个 token   ⟸ Prefill 要干的活
   输出：200 个字                          ⟸ Decode 要干的活

⚠️ 该章按 roofline 粗算（Llama-3-8B、单张 H100，量级估计不是实测）：

  • Prefill 那 4096 个 token ≈ 165 ms —— 算力受限
  • Decode 那 200 个字 ≈ 1.4 秒（每个 token 约 7 ms）—— 访存受限

🔑 两件事的瓶颈完全不同，硬塞在一张卡上会互相拖累 —— 这就是 PD 分离（Prefill/Decode 分离）要解决的问题。

顺带，08-投机解码 里说 RAG 是 n-gram 投机解码的神器：因为 RAG 的答案经常大段照抄参考资料，而原文就摆在 prompt 里，直接查表就能猜中下一个词，零成本加速。

4.2 在 harness评测框架/：它是"弱脚手架"的反面教材

✅ SWE-agent 论文 Table 1，SWE-bench Lite，同一个 GPT-4 Turbo，一个字没换：

脚手架 % Resolved
RAG（一轮盲写） 2.67
Shell-only agent（能跑 shell，但界面是原生 Linux） 11.00
SWE-agent（专门设计的界面） 18.00 
   ⟹ 🔑 差出来的 15 个点，全是【脚手架】贡献的。

为什么 RAG 只有 2.67？ 因为它的流程是：关键词搜出几个文件 → 塞进 prompt → 模型一次性吐补丁 → 用正则抠出来 → 完。

★★ 一轮。没有工具。没有反馈。不跑测试。不知道自己改对没有。

详见 agent脚手架/01-两个harness不是一个东西。

4.3 在 多模态大模型/：它是一条被看好的路线的参照物

超长视频不可能整段塞进模型，得先检索出相关的几个片段 —— 这个思路和文本 RAG 是一个形状。05-位置编码与视频 和 14-演进主线与开放问题 都提到"检索路线和文本 RAG 同构"，并（⚠️ 作者判断）倾向认为检索路线会赢。

5. 天花板：RAG 不是 agent

   ★★ RAG      ：查资料 → 写答案。【一轮，不看结果】
   ★★ agent    ：想 → 动手 → 看报错 → 再想 → 再动手。【多轮，看结果】

这是 4.2 节那 6.7 倍差距的根源。RAG 把资料递过去就撒手了，模型写错了也没有第二次机会。

agentic RAG（⚠️ 这个方向变化很快）是把检索本身变成 agent 的一个工具：模型自己决定搜什么、要不要再搜一次、搜到的够不够。这时"翻书"的动作从你替它做变成它自己做，就跨到了 agent脚手架/ 那一层。

一句话记住它的适用边界：

RAG 擅长"答案就在某份文档里、找到就能抄"的活；不擅长"要试几次才知道对不对"的活。
前者是问答、客服、文档总结；后者是改代码、跑实验 —— 那些得上 agent。

缩写 英文全称 中文 一句话

chunk — 块 资料切分后的最小检索单位
embedding — 嵌入向量 把一段文字压成一串代表"意思"的数字
