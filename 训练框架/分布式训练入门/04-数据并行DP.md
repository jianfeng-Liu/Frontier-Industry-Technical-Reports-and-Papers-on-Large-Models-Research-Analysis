# 04 · 数据并行 DP：最简单的一种，也是一切的基础

> **这一章的目标**：讲清最容易理解的一种并行。
> 读完你应该能回答：为什么"每张卡算完梯度求平均"在数学上是对的？为什么它一点显存都不省？以及 global batch size 这个东西为什么会限制你能用多少张卡？

> 📌 **DP** = **D**ata **P**arallel，数据并行。

---

## 4.1 想法：一人分几条

**最朴素的思路**：模型每张卡都放一份，把这一批数据分开算。

```
    一个 batch 有 32 条样本，4 张卡：

    ┌──────────────────────────────────────────────────────────┐
    │  卡0：完整模型 ┃ 样本 0~7    →  前向 → 反向 → 梯度 g₀      │
    │  卡1：完整模型 ┃ 样本 8~15   →  前向 → 反向 → 梯度 g₁      │
    │  卡2：完整模型 ┃ 样本 16~23  →  前向 → 反向 → 梯度 g₂      │
    │  卡3：完整模型 ┃ 样本 24~31  →  前向 → 反向 → 梯度 g₃      │
    └──────────────────────────────────────────────────────────┘
                              ↓
              ★ All-Reduce：g = (g₀+g₁+g₂+g₃) / 4
                              ↓
              每张卡用【同一个 g】更新自己的那份模型
                              ↓
              ★ 4 份模型的权重始终【完全一致】
```

> 🔑 **最后一行是全章的关键**：因为起点一致（初始化时 broadcast 过）、每步的更新量一致（all-reduce 过），所以四份模型**永远是同一个模型**。这也是为什么最后只需要保存卡0 的那一份。

---

## 4.2 为什么"求平均"在数学上是对的

**很多人在这里将信将疑：分开算再平均，真的等于一起算吗？** —— **完全等于。**

```
    训练的损失函数是【所有样本损失的平均】：

        L = (1/32) · Σ_{i=0}^{31} loss(样本 i)

    梯度是线性算子，可以拆：

        ∇L = (1/32) · Σ_{i=0}^{31} ∇loss(样本 i)

            = (1/4) · [ (1/8)Σ_{i=0}^{7}  ∇loss  ←卡0 算的 g₀
                      + (1/8)Σ_{i=8}^{15} ∇loss  ←卡1 算的 g₁
                      + (1/8)Σ_{i=16}^{23}∇loss  ←卡2 算的 g₂
                      + (1/8)Σ_{i=24}^{31}∇loss ]←卡3 算的 g₃

            = (g₀ + g₁ + g₂ + g₃) / 4          ★ 就是 all-reduce 求平均

    ★★ 结论：4 张卡各算 8 条再平均，和 1 张卡算 32 条，得到的梯度【逐位相同】
       （忽略浮点加法顺序造成的极小差异，13 章会讲这个）
```

> 🔑 **所以数据并行是"数学上完全无损"的**——它不是近似，不是妥协。**这就是它成为一切并行基础的原因。**

---

## 4.3 ⚠️ 它一点显存都不省

**这是初学者最常见的误解，必须专门强调。**

```
    ┌───────────────────────────────────────────────────────┐
    │  4 张卡做数据并行，每张卡上有什么：                     │
    │                                                       │
    │  ① 参数     完整一份    ❌ 没省                        │
    │  ② 梯度     完整一份    ❌ 没省                        │
    │  ③ 优化器   完整一份    ❌ 没省                        │
    │  ④ 激活值   1/4        ✅ 省了（batch 变成 1/4）       │
    └───────────────────────────────────────────────────────┘

    ★ 70B 模型：每张卡还是要 1120 GB 的模型状态。加多少张卡都一样。
```

> ✅ ZeRO 论文原文（[papers/ZeRO-...-arXiv-1910.02054.pdf](../papers/ZeRO-Memory-Optimizations-Trillion-Parameter-arXiv-1910.02054.pdf)）：
> *"Basic data parallelism (DP) does not reduce memory per device, and runs out of memory for models with more than 1.4B parameters on current generation of GPUs with 32 GB memory."*
>
> ```
> ★ 注意这个具体数字：32 GB 的卡，纯数据并行的上限是【1.4B 参数】。
>   1.4B × 16 字节 = 22.4 GB，剩下的留给激活值 —— 账对得上。
> ```

> 🔑 **一句话记住**：
> **数据并行治的是「太慢」，不治「装不下」。** 02 章那张表里，DP 那一行只有第 ④ 列有 ✅。

## 4.4 工程实现：怎么把通信藏起来

**朴素实现是这样的（❌ 慢）**：

```python
# ❌ 朴素版：先全部算完，再一次性通信
loss.backward()                          # 所有层的梯度都算完
for p in model.parameters():
    all_reduce(p.grad)                   # ★ 这段时间 GPU 完全空转
optimizer.step()
```

**问题**：反向传播算完之后才开始通信，通信的几百毫秒里 GPU 什么也不干。

### ✅ 真实实现：梯度桶 + 重叠

**回忆 [03 章 §3.4](03-通信原语.md)：反向传播是从最后一层往前算的。**

```
    时间 ─────────────────────────────────────────────►

    计算：  [层100 反向][层99 反向][层98 反向]...[层1 反向]
                  │          │          │
                  ▼          ▼          ▼
    通信：    [传层100]  [传层99]   [传层98]   ...
              ↑ 在后台进行，不阻塞计算

    ★ 等层1 算完时，前面 99 层的梯度早传完了
      → 通信开销几乎为 0
```

**但如果每个参数单独发一次，会有另一个问题**：

```
    一个 70B 模型有几万个参数张量（每层的 W_q、W_k、W_v、W_o、W_gate...）
    → 几万次小通信，每次都有固定开销（延迟）
    → ★ 光是"启动通信"的开销就把时间吃光了

    ✅ 解法：【梯度桶 gradient bucketing】
       把相邻的若干个梯度张量攒进一个"桶"（典型 25 MB），
       桶满了才发一次 → 通信次数从几万降到几百
```

> ✅ 这正是 PyTorch **DDP**（**D**istributed **D**ata **P**arallel，分布式数据并行）论文的核心内容（[papers/PyTorch-Distributed-DDP-arXiv-2006.15704.pdf](../papers/PyTorch-Distributed-DDP-arXiv-2006.15704.pdf)）。

**代码上你什么都不用做**：

```python
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

dist.init_process_group("nccl")           # 初始化 NCCL 通信
model = MyModel().cuda()
model = DDP(model, device_ids=[local_rank])   # ★ 就这一行

for batch in loader:                      # 每张卡拿到【不同】的 batch
    loss = model(batch).loss
    loss.backward()                       # ★ 梯度桶和 all-reduce 在这里面自动发生
    optimizer.step()
    optimizer.zero_grad()
```

> 📌 **rank / local_rank**：
> - **rank**：这张卡在**整个集群**里的编号（0 ~ N−1）
> - **local_rank**：这张卡在**本机**的编号（0 ~ 7）
> - **world_size**：总卡数 N
> **这三个词在所有分布式框架里都是这个意思。**

## 4.5 ★ 一个硬约束：global batch size

**数据并行的扩展性有一个天花板，而且不是技术上的，是算法上的。**

```
    global batch size B  =  micro-batch size b  ×  数据并行度 N  ×  梯度累积步数 a

    ★ 想用更多卡（N ↑）：
        要么 B 跟着涨          → ⚠️ B 太大会伤收敛质量
        要么 b 变小            → ⚠️ b 太小 GPU 吃不饱，MFU 掉
        要么 a 变小（到 1 为止）→ 到头了
```

> ✅ Megatron 第一篇论文就点出了这个问题（[papers/Megatron-1-...-arXiv-1909.08053.pdf](../papers/Megatron-1-LM-Model-Parallelism-arXiv-1909.08053.pdf)）：
> *"large batch training introduces complications into the optimization process that can result in reduced accuracy or longer time to convergence, offsetting the benefit of increased training throughput"*

```
    ★★ 这就是为什么大规模训练【必须】用模型并行 ★★

    举例（⚠️ 我的算例）：
      global batch = 2048 条，micro-batch = 1，不做梯度累积
      → 数据并行度最多 2048
      → 而 Llama 3.1 405B 用了 16,000 张卡
      → ★ 剩下的 16000/2048 ≈ 8 倍，必须靠 TP × PP 这些"切模型"的方式来消化
```

> 📌 **梯度累积（gradient accumulation）**：算好几个 micro-batch 的梯度**先攒着不更新**，攒够 a 次再更新一次。效果等价于用了 a 倍大的 batch，但显存只需要一个 micro-batch 的量。**这是"显存不够但想要大 batch"的标准做法。**

## 4.6 一个历史注脚：Horovod

**2018 年之前，TensorFlow 自带的数据并行用的是"参数服务器"架构，扩展性很差。**

> ✅ Horovod 论文（[papers/Horovod-arXiv-1802.05799.pdf](../papers/Horovod-arXiv-1802.05799.pdf)，Uber，2018）：
> *"we lost about half of our resources due to communication overhead when training on 128 GPUs"*
> *"When we ran the standard TensorFlow benchmarking suite on 128 NVIDIA Pascal GPUs... both the Inception V3 and ResNet-101 models were unable to leverage nearly half of our GPU resources."*

**Horovod 的贡献就是把 Ring All-Reduce 引入了主流深度学习框架。** 现在 PyTorch DDP 内置了同样的东西，Horovod 本身用得少了，但**它是这条线的起点，值得知道**。

## 4.7 挂回真实框架

| 框架 | 数据并行怎么用 |
|---|---|
| **PyTorch** | `DistributedDataParallel`（DDP），一行包一下 |
| **Megatron-LM** | `--data-parallel-size` 由总卡数除以其他并行度**自动推出**，不用显式指定 |
| **DeepSpeed** | ZeRO stage 0 就是普通 DP |
| **TorchTitan** | 基于 `DTensor` 的新实现，把 DP 和 FSDP 统一了 |

**Megatron 里的位置**（[../源码/Megatron-LM/megatron/core/parallel_state.py](../源码/Megatron-LM/megatron/core/parallel_state.py)，Megatron-Core 0.20.0）：

```
全局变量 _DATA_PARALLEL_GROUP 就是数据并行的通信组。
✅ 该文件 docstring 里给出的官方例子（16 张 GPU，TP=2，PP=4）：

    8 data_parallel groups:
        [g0, g2], [g1, g3], [g4, g6], [g5, g7],
        [g8, g10], [g9, g11], [g12, g14], [g13, g15]

★ 注意 g0 和 g2 一组 —— 隔了一个。为什么？06 章讲完 TP 你就明白了：
  g0、g1 是一对 TP，g2、g3 是另一对 TP。
  所以数据并行是在"TP 组之间"配对的：g0↔g2 都是各自 TP 组里的 0 号。
```

```
    ⚠️ 这里有个特别容易记反的地方，先记住结论，理由留到 12 章：

      并行维度"由内到外"（rank 编号变化从快到慢）的顺序是
          ★★ TP → CP → EP → DP → PP ★★
      ✅ 源码里就是一个字符串常量：order = "tp-cp-ep-dp-pp"

      ★ 不是 TP → PP → DP。DP 在【中间】，PP 在【最外】。

    ⟹ 这直接决定了上面那些方括号里的数字：

        DP 组步长 = TP     = 2  → [g0, g2]        ★ 所以"隔了一个"
        PP 组步长 = TP×DP  = 4  → [g0, g4, g8, g12]

    为什么是这个顺序（而不是把 PP 放中间）？一句话预告：
      ★ TP 每层 4 次阻塞式通信，躲不掉，必须吃机内高速链路；
      ★ PP 只在 stage 边界发 2 次异步 P2P，而且它的主要成本是【气泡】不是带宽，
        所以最适合被推到跨机的慢网络上。
    完整论证见 [12 章 §12.8 · rank 排布顺序](12-并行策略组合与MFU.md)。
```

## 4.8 本章小结

```
① 数据并行 = 每张卡一份完整模型，各算各的 batch，梯度 all-reduce 求平均

② ★ 它在数学上【完全无损】：
   ∇L = (1/N)Σ∇L_i，因为梯度是线性算子。不是近似，是恒等。

③ ★★ 它一点【模型状态】显存都不省 —— 只省激活值 ★★
   ✅ ZeRO 论文：32 GB 的卡上，纯 DP 的上限是【1.4B 参数】
   → 治「太慢」，不治「装不下」

④ 工程实现两个要点（PyTorch DDP 论文的核心）：
   ★ 反向从后往前算 → 每层算完立刻开始传，通信藏进后续计算
   ★ 梯度桶：攒够 ~25 MB 才发一次，避免几万次小通信的延迟开销
   代码上就是 model = DDP(model) 一行

⑤ ★ 硬天花板：global batch = micro-batch × DP度 × 梯度累积
   卡数超过 global batch 能容纳的范围时，DP 就走到头了
   ✅ Megatron-1 论文明说了大 batch 伤收敛
   → 这就是【必须】上模型并行（TP/PP）的算法层面原因，不只是显存原因

⑥ Ring All-Reduce 每卡通信量 ≈ 2Ψ，与卡数无关（03 章）
   → 这是 DP 能扩到几千卡的技术原因
```
