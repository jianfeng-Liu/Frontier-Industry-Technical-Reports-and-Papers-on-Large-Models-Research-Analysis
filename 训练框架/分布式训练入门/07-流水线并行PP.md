# 07 · 流水线并行 PP 与气泡

> **这一章的目标**：讲清"把层切开"这件事，以及它带来的那个独有的代价——**气泡**。
> 读完你应该能回答：气泡率公式 `(p−1)/m` 是怎么推的？1F1B 比 GPipe 好在哪（提示：不是气泡率）？交错式公式里的 `v·m` 那个 v 是**从哪来的**？"零气泡"那个"零"，到底是拆 B/W 拆出来的，还是拿显存买的？

> 📌 **PP** = **P**ipeline **P**arallel，流水线并行。也叫 **inter-layer model parallelism**（层间模型并行）。

---

## 7.1 想法：像工厂流水线一样

```
    一个 80 层的模型，4 张卡：

    ┌──────────┬──────────┬──────────┬──────────┐
    │  卡0     │  卡1     │  卡2     │  卡3     │
    │ 层 1~20  │ 层 21~40 │ 层 41~60 │ 层 61~80 │
    └──────────┴──────────┴──────────┴──────────┘
         │          │          │          │
    数据 ──────────►──────────►──────────►── loss

    ★ 每张卡只存 1/4 的层 → 参数、梯度、优化器状态都 ÷4
    ★ 卡之间只传【一个激活张量】[b, s, d]，不是整个权重
      → 通信量比 TP 小得多 → ★★ 可以跨机器用 ★★
```

**每张卡负责的那一段叫一个 stage（阶段）。**

> 🔑 **PP 和 TP 的本质区别，用一句话概括**：
> ```
> TP：所有卡【同时】处理【同一批数据】的【同一层】的不同部分
>     → 通信频繁（每层 4 次），但没有空转
> PP：不同卡处理【不同层】
>     → 通信稀疏（每个 stage 边界 1 次），但★天然会空转★
> ```

---

## 7.2 ★ 那个天然的空转：气泡

**最朴素的流水线（一次只喂一个 batch）**：

```
    时间 ────────────────────────────────────────────────────►

    卡0  [F₁]                            [B₁]
    卡1       [F₁]                  [B₁]
    卡2            [F₁]        [B₁]
    卡3                 [F₁][B₁]

         F = forward（前向）   B = backward（反向）

    ★★ 任何时刻只有【一张卡】在干活，其余三张在等 ★★
       → 4 张卡的利用率 = 25%，还不如一张卡！
```

**解法：把 batch 切成很多小份（micro-batch），像流水线一样一个接一个送进去。**

```
    m = 4 个 micro-batch：

    时间 ────────────────────────────────────────────────────────────►
    卡0  [F₁][F₂][F₃][F₄]░░░░░░░░░░░░[B₄][B₃][B₂][B₁]
    卡1  ░░░░[F₁][F₂][F₃][F₄]░░░░░░[B₄][B₃][B₂][B₁]░░░░
    卡2  ░░░░░░░░[F₁][F₂][F₃][F₄][B₄][B₃][B₂][B₁]░░░░░░░░
    卡3  ░░░░░░░░░░░░[F₁][F₂][F₃][F₄][B₄][B₃][B₂][B₁]░░░░░░░░░░░░

         ░ = ★ 气泡（bubble），GPU 空转

    ★ 现在大部分时间四张卡都在干活了，但【头尾】还是有空转。
```

> 📌 **micro-batch（微批）**：把一个 global batch 切成 m 份，每份单独走一遍流水线，梯度攒起来最后一起更新。**这和 [04 章 §4.5](04-数据并行DP.md) 的梯度累积是同一件事**，只是在流水线场景下它是**必需的**，不是可选的。

### 气泡率的公式

```
    ★ 推导（用"格子数"数）：

    一个 micro-batch 走完全程需要 p 个 stage（p = 流水线深度）。
    第一个 micro-batch 到达最后一张卡，前面已经过了 (p−1) 个时间格。
    → ★ 每张卡在头部要等 (p−1) 格，尾部同理

    有效工作时间：  m 格（m 个 micro-batch）
    气泡时间：      (p−1) 格

                          (p − 1)
    ★★  气泡率  =  ───────────────  ★★
                       m + (p − 1)
```

```
    举例：
      p=4, m=4    →  3/7  = 43%    ❌ 太糟了
      p=4, m=16   →  3/19 = 16%    ⚠️ 还行
      p=8, m=64   →  7/71 = 10%    ✅ 可以接受
      p=8, m=128  →  7/135 = 5%    ✅ 很好

    ★★ 结论：m 要远大于 p。经验法则是 m ≥ 4p ★★
```

> 🔑 **但 m 不能无限大**，因为 `global batch = micro_batch_size × m × DP度`——回到了 [04 章 §4.5](04-数据并行DP.md) 那个 global batch 天花板。**★ 这是分布式训练里所有约束互相打架的第一个典型例子。**

## 7.3 GPipe → 1F1B：省的不是气泡，是显存

### GPipe（2019）：先全部前向，再全部反向

> ✅ [papers/GPipe-...-arXiv-1811.06965.pdf](../papers/GPipe-Pipeline-Parallelism-arXiv-1811.06965.pdf) 原文：
> *"GPipe utilizes a novel batch-splitting pipelining algorithm, resulting in almost linear speedup when a model is partitioned across multiple accelerators."*
> *"There has been a 36× increase in the model capacity."*

```
    卡0  [F₁][F₂][F₃][F₄]░░░░░░░░░░░░[B₄][B₃][B₂][B₁]
                        ↑
    ★★ 问题在这里：4 个 micro-batch 的【激活值】全部要留着，
       一直留到反向开始 —— 显存峰值 ∝ m ★★

    而 §7.2 又说 m 要大（m ≥ 4p 才能压住气泡）
    → ★ 气泡和显存直接打架
```

### 1F1B（One Forward One Backward）：一前一后交替

**核心改动：让反向【尽早】开始，一个前向配一个反向。**

```
    卡0  [F₁][F₂][F₃][F₄][B₁][F₅][B₂][F₆][B₃]...
                        ↑    ↑
                        │    └─ ★ B₁ 一做完，micro-batch 1 的激活立刻释放
                        └────── 稳态时最多只留 p 份激活

    ★★ 气泡率【和 GPipe 完全一样】：还是 (p−1)/(m+p−1)
       但峰值显存从 ∝ m 降到了 ∝ p ★★
```

> ✅ Zero Bubble 论文（[papers/Zero-Bubble-...-arXiv-2401.10241.pdf](../papers/Zero-Bubble-Pipeline-Parallelism-arXiv-2401.10241.pdf)）把这件事说得很准：
> *"1F1B offers faster memory clearance by early scheduling the backward passes. With the same number of microbatches, it yields similar bubble ratios but with a distinct advantage in peak memory."*
>
> ```
> ★ 注意 "similar bubble ratios but ... advantage in peak memory" 这半句。
>   ★★ 1F1B 省的是【显存】，不是气泡 —— 这是最容易记错的一点 ★★
>   但因为显存省了，你才【敢】把 m 调大，间接把气泡压下去了。
> ```

> ✅ PipeDream-2BW 论文（[papers/PipeDream-2BW-...-arXiv-2006.09503.pdf](../papers/PipeDream-2BW-Memory-Efficient-Pipeline-arXiv-2006.09503.pdf)）是 1F1B 这条线的代表作：
> *"PipeDream does not periodically flush the pipeline but stores multiple weight versions, which increases throughput but also increases the memory footprint"*
> *"we propose double-buffered weight updates (2BW), a technique that reduces the memory footprint of training while avoiding pipeline flushes"*
> *"PipeDream-2BW achieves end-to-end speedups of 1.3× to 20× for various GPT models compared to an optimized model-parallel baseline"*、*"up to 3.2× faster than GPipe"*
>
> ⚠️ **注意**：PipeDream 原版是**异步**的（用了旧版本的权重算梯度），**改变了优化器语义**。Megatron 用的是它的同步变体 **PipeDream-Flush**——论文原话：*"a variant of 2BW (called PipeDream-Flush) that trades off throughput for even lower memory footprint and vanilla semantics"*。**"vanilla semantics"（原味语义）就是"和单卡训练数学上等价"的意思。**

## 7.4 ★ 交错式（Interleaved）：把气泡再砍一半

**这是 Megatron 第二篇论文的主要贡献。**

### 想法

```
    朴素 PP（p=4，16 层）：每张卡拿【连续的一大段】

        卡0: 层1-4    卡1: 层5-8    卡2: 层9-12   卡3: 层13-16

    交错式（p=4，vpp=2）：每张卡拿【不连续的两小段】

        卡0: 层1-2  和  层9-10
        卡1: 层3-4  和  层11-12
        卡2: 层5-6  和  层13-14
        卡3: 层7-8  和  层15-16

    ★ 16 层现在是【8 个 stage】，但还是 4 张卡
    → 每个 stage 的计算变短 → 流水线"格子"变细 → 气泡也跟着变细
```

> ✅ **这个例子不是我编的**，是 Megatron 源码 [../源码/Megatron-LM/megatron/core/parallel_state.py](../源码/Megatron-LM/megatron/core/parallel_state.py) docstring 里的原文（tp=1, pp=4, vpp=2, 16 层）：
> ```
> GPU 0: [1, 2] [9, 10]
> GPU 1: [3, 4] [11, 12]
> GPU 2: [5, 6] [13, 14]
> GPU 3: [7, 8] [15, 16]
> ```

### 效果

```
              (p − 1)                              (p − 1)
    朴素： ─────────────        交错式(v段)： ───────────────────
            m + (p − 1)                        v·m + (p − 1)
```

**⚠️ "分母里的 m 变成了 v·m" 只是代数变形留下的表象。物理上真正发生的事，是【分子被除以了 v】。**

### ★ 这个公式是怎么来的（两步推导）

约定 `t_f + t_b = 1`：一个 micro-batch 在【一整段 stage】上跑完前向+反向，记作 1 个时间格。

**第一步：先把朴素式拆成两部分**

```
    ① 每张卡的【实际计算时间】
       = m 个 micro-batch × 1 格
       = m 格

    ② 【气泡时间】= 填充 + 排空
       填充：卡3 要等 micro-batch 1 依次穿过卡0、卡1、卡2 → 等 (p−1)·t_f
       排空：卡0 的最后一次反向，要等梯度从卡3 一路传回 → 等 (p−1)·t_b
       合计 = (p−1)(t_f + t_b) = (p−1) 格

    总墙钟时间 = m + (p − 1)

                      (p − 1)
    气泡率 = ─────────────────       ✅ 这就是 §7.2 那个公式
                   m + (p − 1)
```

> ⚠️ **你会在不同地方看到两个长得不一样的气泡公式，它们都对，只是【分母的定义】不同**：
> ```
>     (p − 1)          气泡 ÷ 【总墙钟时间】 → "空转占了整段时间的百分之几"
>   ───────────        ★ 本书统一用这个，因为它就是 1 − GPU 利用率
>    m + (p − 1)
>
>     (p − 1)          气泡 ÷ 【理想计算时间】 → "比理想情况多花了百分之几"
>   ───────────        ★ Megatron-2 论文用的是这个（bubble time fraction）
>        m
> ```
> ★ 两者在 m ≫ p 时数值很接近（比如 p=8, m=64：10% vs 11%），但**读论文时要看清楚它在除以谁**。

**第二步：交错式只动了其中【一部分】**

★ 关键认知：**交错式一点计算量都没省，它只是把"流水线一跳"的粒度切细了 v 倍。**

```
    模型现在被切成 p·v 个 chunk（小段），每个 chunk 只有原来一整段的 1/v 厚
    → 单个 chunk 跑一个 micro-batch 的耗时 = 1/v 格

    ① 计算时间：★★ 完全不变 ★★
       每张卡每个 micro-batch 要跑 v 个 chunk，每个 1/v 格
       → v × (1/v) = 1 格 → 总共还是 m 格
                             ↑ ★ 分母里的 m 从头到尾没被动过 ★

    ② 气泡时间：★★ 除以 v ★★
       填充时，卡3 只需等卡0/1/2 各跑完【一个 chunk】，而不是一整段
       每个 chunk 只要 1/v 格
       → 气泡 = (p−1)(t_f + t_b)/v = (p−1)/v 格
```

```
    ★ 代进去：
                     (p − 1)/v
       气泡率 = ─────────────────
                   m + (p − 1)/v

    ★★ 分子分母【同乘 v】，分数值不变，但形式变了 ★★

                      (p − 1)
              = ─────────────────      ✅ 交错式公式
                   v·m + (p − 1)
```

> 🔑 **一句话记住**：`v·m` 里那个 v 是**从分子挪到分母去的**。
> 真实的物理事件是「**气泡的绝对时长缩短了 v 倍**」，而计算时间 m 纹丝不动。
> ★ 交错式不会让你**算得更快**，只会让你**等得更少**。

### 数一数到底省多少

```
    p = 8, m = 32：

      v = 1（朴素）   7/(32+7)  = 17.9%   ──┐
      v = 2           7/(64+7)  =  9.9%     │ ★ v 每翻一倍
      v = 4           7/(128+7) =  5.2%     │   气泡约减半
      v = 8           7/(256+7) =  2.7%   ──┘

    ⚠️ 这是【只算计算、不算通信】的理想值。实测收益远没这么线性——见下面的代价。
```

> ✅ Megatron-2 论文（[papers/Megatron-2-...-arXiv-2104.04473.pdf](../papers/Megatron-2-PTD-P-Efficient-Large-Scale-Training-arXiv-2104.04473.pdf)）原文：
> *"We propose a novel interleaved pipelining schedule that can improve throughput by 10+% with memory footprint comparable to existing approaches."*
> *"We propose a novel interleaved schedule that can improve throughput by as much as 10% compared to previously-proposed schedules with comparable memory footprint."*

> ⚠️ **代价**：通信次数变多了（每张卡现在要收发 v 次而不是 1 次）。**论文明确说了这个取舍**：*"By assigning multiple stages to the same device, it further reduces the bubble size at the cost of more communication and higher peak memory."*（这句来自 Zero Bubble 论文对交错式的总结）

> 📌 **术语**：这个 v 在 Megatron 里叫 **VPP** = **V**irtual **P**ipeline **P**arallel，虚拟流水线并行度。参数是 `--num-layers-per-virtual-pipeline-stage`。

### ⚠️ 那为什么不把 v 开到 100

```
    ① ★ 通信次数 ×v
       一个 micro-batch 原本只跨 (p−1) 次卡边界，现在要跨 (p·v − 1) 次。
       气泡省下的时间，会被【多出来的 P2P 通信】吃回去一部分。
       （P2P = point-to-point，点对点收发，见 [03 章](03-通信原语.md)）
       → ★★ 实践中 v = 2 或 4 是甜点，再大收益递减甚至倒挂 ★★

    ② ★ 激活显存不降反升
       流水线里同时"在飞"的 micro-batch 变多 → 要缓存的中间激活更多
       ✅ Zero Bubble 论文原话已经点了：
          "at the cost of more communication and ★higher peak memory★"
       ⚠️ 这又和 §7.3「1F1B 省显存」的收益打架 —— 又一次约束互相打架

    ③ ★ 整除约束
       Megatron 要求 micro-batch 数 m 能被 p 整除，
       且总层数要能被 (p × v) 均分 —— 层数不凑巧时 v 根本开不起来
```

## 7.5 ✅ PTD-P：Megatron-2 的总成绩

**PTD-P** = **P**ipeline + **T**ensor + **D**ata **P**arallelism，这三者的组合。

> ✅ 论文摘要原文：
> *"Our approach allows us to perform training iterations on a model with 1 trillion parameters at 502 petaFLOP/s on 3072 GPUs (per-GPU throughput of 52% of theoretical peak)."*
> *"we demonstrate close to linear scaling to 3072 A100 GPUs, with an achieved end-to-end training throughput of 163 teraFLOP/s per GPU"*
> *"we estimate end-to-end training of this model to take ∼3 months"*

```
    ✅ 1T 参数 / 3072 张 A100 / 502 PFLOP/s / 每卡 163 TFLOP/s / 52% 峰值
    ⚠️ 验算：3072 × 163 TFLOP/s = 500.7 PFLOP/s  ✅ 和 502 对得上
```

> ⚠️★ **别把这个 52% 转述成"52% MFU"** —— 这是最常见的误引。
> 论文原话是 "of theoretical peak"（不表态），而它的 FLOPs 公式
> **把重计算的额外前向算进了分子**（系数 96 而非 72）。
> ⟹ 按现在通行的口径，这是 **HFU**；换算成 MFU ≈ **39%**。
> ⟹ 详见 [12 章 §12.2 的订正](12-并行策略组合与MFU.md)。

**论文还给了几条非常实用的经验，值得单独列出来**：

> ✅ *"sub-optimal combinations of tensor and pipeline model parallelism can lead to up to 2× lower throughput, even with high-bandwidth network links between servers"*
> → ★ **配比选错，性能差 2 倍。** 这就是 [12 章](12-并行策略组合与MFU.md)存在的理由。
>
> ✅ *"tensor model parallelism is effective within a multi-GPU server, but pipeline model parallelism must be used for larger models"*
> → ★ 和 [06 章](06-张量并行TP.md)的铁律完全一致。
>
> ✅ *"the optimal value of the microbatch size is problem-dependent and can increase throughput by 15%"*
> → ★ micro-batch size 也是一个要调的旋钮。
>
> ✅ *"When training a trillion-parameter model on 3072 GPUs, our implementation used an effective bisection bandwidth of 892 GB/s for pipeline-parallel communication, and 13 TB/s for data-parallel communication."*
> → ⚠️ 注意这两个数差 **14.6 倍**——PP 的通信量确实比 DP 小得多，这是它能跨机的原因。

## 7.6 零气泡：气泡真的能到 0 吗

**Zero Bubble 论文（2023）的答案是：能——但"零"是有前提的。**

> ✅ 原文：*"we introduce a scheduling strategy that, to our knowledge, is the first to successfully achieve zero pipeline bubbles under synchronous training semantics."*

⚠️ 这一节最后会**用论文自己的数据打这个"零"的假**。先把机制讲透。

---

### 7.6.1 核心洞察：反向传播其实是【两件事】

先把"反向传播"这个黑盒打开。一个线性层，前向就一句话：

```
    Y = X · W

    X: [4, 3]   ← 4 个样本，每个 3 维（输入激活）
    W: [3, 2]   ← 权重矩阵
    Y: [4, 2]   ← 输出
```

反向时，上游传下来 `G = dL/dY`（loss 对本层输出的梯度，形状同 Y）。拿到 G 之后要算**两个**东西：

```
    ★ ① B：对【输入】的梯度   dL/dX = G · Wᵀ
              [4,2] · [2,3] = [4,3]    ← 和 X 同形状 ✓

    ★ ② W：对【权重】的梯度   dL/dW = Xᵀ · G
              [3,4] · [4,2] = [3,2]    ← 和 W 同形状 ✓
```

> 🔑 **盯着这两行看**：它们是**两个各自独立的矩阵乘法**。
> ①式里没用到 dL/dW，②式里也没用到 dL/dX。
> ★★ 也就是说——**它俩谁先算、隔多久算，完全不影响结果。** ★★

**这就是全部的"洞察"。** 听起来平平无奇，但下一步就变魔术了。

📌 **术语约定**：后文用 **F** 指前向、**B** 指算 `dL/dX`、**W** 指算 `dL/dW`。注意这个 **W 是动词（算权重梯度这个动作）**，不是权重矩阵本身，别和 §7.4 的 VPP 段数 v 搞混。

---

### 7.6.2 ★ 这两件事，命运完全不同

```
                     ┌──────────────────────────┐
                     │  ① B: dL/dX = G · Wᵀ     │
    G = dL/dY ──┬───►│                          │──► 往回传给上一个 stage
                │    └──────────────────────────┘    ★★ 有人在等它！★★
                │
                │    ┌──────────────────────────┐
                └───►│  ② W: dL/dW = Xᵀ · G     │──► 存进梯度 buffer，躺着
                     │                          │    ★★ 整轮之内没有任何人等 ★★
                     └──────────────────────────┘    直到所有 micro-batch 算完，
                                                     optimizer.step() 才来取一次
```

**为什么 ① 有人等？** 反向传播是一条链：上一层要拿到 `dL/dX`（对它来说就是它的 `dL/dY`）才能开工。你不给，上一层就干等——**这正是 §7.2 那个气泡的来源**。

**为什么 ② 没人等？** `dL/dW` 是**死胡同**。算出来就存着，反向链条上谁也不消费它。

> 🏃 **接力赛类比（这个最好懂）**
> ```
>     你跑完你这一棒，有两件事要做：
>
>     ① 交棒给下一位  ──► ★ 下一位伸着手在等，必须【立刻】交   = B
>     ② 填一张"本棒用时/配速"的表交教练
>                     ──► ★ 教练赛后才汇总，【什么时候填都行】   = W
>
>     ❌ 传统调度：非要【填完表】才交棒 → 下一位干等你写字
>     ✅ 零气泡  ：先交棒，表等有空了再填
> ```

> ✅ 论文 Figure 1 图注就是这个：*"Computation Graph for MLP ... B F W  Forward Backward"* ——**它把反向明确画成了 B 和 W 两个独立节点。**

### 7.6.3 ✅ 论文 Table 2：三种调度的气泡公式

> ✅ 原文 Table 2（第 5 页），`M_B` = 一个 B 所需的激活显存：
> ```
>   Schedule   Bubble size                  Peak activations memory
>   ──────────────────────────────────────────────────────────────
>   1F1B       (p−1)(T_F + T_B + T_W)       p·M_B
>   ZB-H1      (p−1)(T_F + T_B − T_W)       p·M_B          ← ★显存不变★
>   ZB-H2      (p−1)(T_F + T_B − 2T_W)      (2p−1)·M_B     ← ★显存翻倍★
> ```

代入论文的理想假设 `T_F = T_B = T_W = T`：

```
    1F1B  → (p−1)(T+T+T)  = 3T(p−1)      基准
    ZB-H1 → (p−1)(T+T−T)  =  T(p−1)      ★ 剩 1/3（不是 1/2！）
    ZB-H2 → (p−1)(T+T−2T) =     0        ★★ 真的是 0 ★★
```

> ✅ 论文原话对得上：*"the bubble size is reduced to a **third** of 1F1B's size"*（§2.1）

    ③  平行四边形：4 张卡都是【24 格实心不断】，只是各自右移 1 格
       ★★ 没有任何缺口 = 零气泡 ★★
```

### 7.6.5 ★★ 那 9 格气泡，到底是谁付的账

| | 头部气泡 | 尾部气泡 | **合计** | 峰值在飞 micro-batch |
|---|---|---|---|---|
| **1F1B** | 6 | 3 | **9** | 4（= p） |
| **ZB-H1** | 3 | 0 | **3** | 4（= p，★显存没涨★） |
| **ZB-H2** | 0 | 0 | **0** | 7（= 2p−1，★显存翻倍★） |

```
    ★ 拆 B/W 这一招，独立拿下 9 → 3（占总量的 2/3）
        · 头部 6→3：梯度回传不再被 W 拖慢
        · 尾部 3→0：W 变成填料

    ★ 最后那 3 格，拆 B/W 【拿不下】—— 它是纯粹的"流水线还没填满"
      只能靠【暖机多灌前向】填，而多灌前向 = 多存激活
      ★★ 这 1/3 是拿【2 倍激活显存】买来的，不是拆出来的 ★★
```

> 🔑 **常见误解**：以为"拆开 B/W 就能把气泡砍一半"。
> 实际是——**拆 B/W 拿走 2/3（因为它同时改善头和尾两处）**，
> 而**剩下的 1/3 根本不是拆出来的，是用显存买的**。

### 7.6.6 ⚠️ 打假：这个"零"是有条件的

论文 §2.3 **自己就说了**真实的时间关系不是 1:1:1：

```
✅ 原文（第 4 页）："We can see that ★T_W < T_F < T_B★ and ★T_B + T_W = 2T_F★"

✅ Table 1 的 FLOPs（每层 transformer）：
     F: sbh(24h + 4s)
     W: sbh(24h)        ← ★ W 恒比 F 少 sbh·4s → T_W 严格小于 T_F ★
```

⚠️ **把真实关系代回 ZB-H2 公式（这一步是本书推的，论文没直接写）**：

```
    T_B = 2T_F − T_W  代入：

    ZB-H2 气泡 = (p−1)(T_F + T_B − 2T_W)
                = (p−1)(T_F + 2T_F − T_W − 2T_W)
                = ★ 3(p−1)(T_F − T_W) ★

    而论文自己说 T_W < T_F  ⇒  ★★ 这个值严格大于 0 ★★

    再代入 Table 1 的 FLOPs：
                ≈ 3(p−1)·T_F · ─── s ───
                                 6h + s
    → ★ 序列越长(s↑)、hidden 越窄(h↓)，残留气泡越大
```

**论文对此是诚实的**，§3 开头就承认了：

> ✅ *"scheduling under the assumption that T_F = T_B = T_W introduces **unwanted bubbles**, especially for models where these values differ significantly. Moreover, **communication time (T_comm) ... is often ignored** in handcrafted schedules"*

#### ✅ Table 5 实测：ZB-H2 根本不是 0

```

### 7.6.7 收束：三层，别混成一层

```
① 拆 B/W          → 只是【解锁条件】，把 W 变成可搬运的填充料
                     单靠它（ZB-H1）= 气泡剩 1/3，显存不变
                     ★ "砍一半"的直觉在这层，实际是砍 2/3 ★

② + 2 倍显存多灌前向 → 梯形掰成平行四边形（ZB-H2）
                     理想假设下 = 0，★实测 2.6%~10.8%★

③ + ILP 自动搜调度  → 用真实 profile 的 T_F/T_B/T_W/T_comm 求解（ZB-2p）
                     ★★ 这才是实测 <1% 的那个 ★★
```

> ⚠️ **论文标题里的 "Zero Bubble" 是 ② 在理想假设下的理论结果，工程上真正能用的是 ③。**

> ✅ 效果原文：*"our method outperforms the 1F1B schedule up to 23% in throughput under a similar memory limit. This number can be further pushed to 31% when the memory constraint is relaxed."*

> ⚠️ 论文还提到最后一步的难点：*"to truly achieve zero bubble, we introduce a novel technique to bypass synchronizations during the optimizer step"* —— **优化器那一步的同步（比如梯度裁剪要算全局范数）也会造成气泡，需要单独处理。**

## 7.7 一个必须提的坑：负载不均

```
    ★ 简单地"每张卡 20 层"往往是错的，因为：

    ① 第一个 stage 多了 embedding 层
    ② 最后一个 stage 多了 LM head（输出投影到词表，[d, 150000]，很大）
       ★ 还要算 loss，而 loss 那里的 [b, s, V] 张量是全模型最大的激活之一
    ③ 如果层不能被 p 整除，只能有的卡多一层

    → ★ 流水线的速度由【最慢的那个 stage】决定，其余卡陪着空转
    → 实践中要给首尾两个 stage 【少分几层】来配平
```

> 📌 Megatron 有专门的参数处理这个：`--decoder-first-pipeline-num-layers` 和 `--decoder-last-pipeline-num-layers`，可以单独指定首尾 stage 的层数。

## 7.8 ★ 显存压力落在哪张卡上

**§7.7 讲的是【计算】的不均衡，这一节补【显存】的不均衡——它比计算那个更要命，因为计算不均只是慢，显存不均是直接 OOM。**

> 📌 **OOM** = **O**ut **O**f **M**emory，显存溢出。训练进程被 CUDA 直接打死的那种。

问题要拆成两个维度问，别混：

```
    ★ 空间维度：哪一张卡（哪个 stage）水位最高
    ★ 时间维度：一个 iteration 里哪个时刻是峰值
```

### 7.8.1 空间：stage 0 缓存 p 份激活，往后逐级递减

**答案直接藏在 §7.6.4 那张 1F1B 甘特图里**，数一下每张卡在第一个 B 到来之前灌了几个前向：

```
卡0 │F1 F2 F3 F4  .  .  .  .  .  . B1 ...   → 手里攒着 4 份激活 = p
卡1 │ . F1 F2 F3  .  .  .  . B1 ...         → 3 份 = p−1
卡2 │ .  . F1 F2  .  . B1 ...               → 2 份 = p−2
卡3 │ .  .  . F1 B1 ...                     → 1 份 = 1

    ★★ 完美的阶梯：stage i 缓存 (p − i) 份激活 ★★
```

**为什么是阶梯**：一份激活从"算完前向"到"反向用完可以释放"要等多久，取决于它离流水线尾巴多远。

```
    stage 0 的激活   → 要等 micro-batch 一路走到 stage p−1、再一路爬回来 → 等最久 → 攒最多
    stage p−1 的激活 → 前向刚做完，下一格就反向 → 立刻释放 → 只攒 1 份
```

> ✅ Megatron-2 论文（[papers/Megatron-2-...-arXiv-2104.04473.pdf](../papers/Megatron-2-PTD-P-Efficient-Large-Scale-Training-arXiv-2104.04473.pdf)）原话：
> *"This schedule limits the number of **in-flight microbatches** (the number of microbatches for which the backward pass is outstanding and **activations need to be maintained**) to **the depth of the pipeline**, instead of the number of microbatches in a batch."*

> 📌 **in-flight microbatch（在飞微批）** = 前向已经算完、反向还没做、激活必须留着的那些 micro-batch。
> ★★ **它的数量就是激活显存的直接度量** —— 后面所有分析都盯着这一个数。

> ✅ Zero Bubble 论文 Table 2（§7.6.3 已引）说的是同一件事：1F1B 的 `Peak activations memory = p·M_B`，**那个 p 就是 stage 0 的那 p 份。**

**⚠️ 一个具体的数（推断值，按张量形状硬算，不是实测）**：

设定 80 层 / h=8192 / s=4096 / micro-batch=1 / TP=8 + 序列并行 + 选择性重计算（即每层 `34·s·b·h/t` 字节，公式出自 [11 章](11-重计算与激活优化.md)）/ p=8：

```
    每层每 micro-batch ≈ 136 MB

    stage0  在飞 8 份 × 10 层 = 10.62 GB   ★★ 最大 ★★
    stage1  在飞 7 份 × 10 层 =  9.30 GB
    stage2  在飞 6 份 × 10 层 =  7.97 GB
    stage3  在飞 5 份 × 10 层 =  6.64 GB
    stage4  在飞 4 份 × 10 层 =  5.31 GB
    stage5  在飞 3 份 × 10 层 =  3.98 GB
    stage6  在飞 2 份 × 10 层 =  2.66 GB
    stage7  在飞 1 份 × 10 层 =  1.33 GB   ← 只有 stage0 的 1/8

    ★ 首尾差 p 倍 —— 这就是 PP 最大的显存不均衡
```

### 7.8.2 ★★ 反直觉：把 p 开大，stage 0 的激活【一点都不降】

```
    stage 0 的激活总量 = p 份 × (L/p 层) = ★ L 层 × 1 份 ★
                          ↑          ↑
                       在飞份数    每卡层数
                        ∝ p       ∝ 1/p     → ★★ p 被约掉了 ★★

    ⚠️ 上面那个例子里 "stage0 = 10.62 GB" 和 "整个模型跑一份 micro-batch 的
       激活总量" 是同一个数 —— 不是巧合，是必然。
```

🔑 **一句话**：**PP 切的是参数、梯度、优化器状态（都 ÷p），激活它没切。**

对照 [02 章](02-显存去哪了.md)的"显存四大块"看得最清楚——**PP 只动了前三块，第四块（激活）纹丝不动。**

```
    ❌ 错误直觉："模型放不下 → 加 PP"
    ✅ 准确说法：
        参数放不下（模型太大）      → ★ 加 PP 有用 ★
        激活放不下（序列太长/batch 大）→ ★ 加 PP 没用 ★
                                       要靠 TP+序列并行（08 章）、
                                       上下文并行（08 章）、重计算（11 章）
```

⚠️ 这条推论是本书从论文公式推的，论文没直接这么写——**标【推断】**。

### 7.8.3 时间：峰值在 warmup 结束、第一个 backward 之前那一格

```
    卡0 │F1 F2 F3 F4 │ B1 F5 B2 F6 B3 F7 ... │ B6 B7 B8 │
         └─ warmup ─┘└──── 稳态 1F1B ───────┘└ cooldown┘
                    ↑
              ★★ 峰值就在这一格 ★★
              手里刚攒满 p 份，而第一个 B 还没开始释放

    稳态：做一个 B 释放一份、做一个 F 灌进一份 → ★ 水位横着走，不再涨 ★
    cooldown：只出不进 → 单调下降
```

> 📌 **warmup（暖机）/ steady state（稳态）/ cooldown（排空）** 是 1F1B 调度的三段。

🔑 **推论**：**OOM 几乎总发生在训练刚起步的头几个 iteration，而不是跑了几小时之后。**跑过 10 步没炸，基本就不会因为激活炸了（碎片化除外）。

#### 各调度的峰值对比

| 调度 | 峰值出现在 | stage 0 在飞份数 | 出处 |
|---|---|---|---|
| **GPipe** | 全部 m 个前向做完时 | **m** ⚠️ ∝ micro-batch 总数 | §7.3 |
| **1F1B** | warmup 末尾 | **p** | ✅ Table 2 `p·M_B` |
| **VPP（交错式）** | warmup 末尾（warmup 更长） | 略高于 p | ⚠️ 见下方分歧 |
| **ZB-H1** | warmup 末尾 | **p**（★和 1F1B 一样★） | ✅ Table 2 `p·M_B` |
| **ZB-H2** | warmup 末尾 | **2p−1**（★约翻倍★） | ✅ Table 2 `(2p−1)·M_B` |

> ⚠️ **VPP 这一行，两篇论文说法不一致，这里不和稀泥**：
> - Megatron-2 自称 *"with memory footprint **comparable** to existing approaches"*
> - Zero Bubble 论文回头总结交错式时说 *"at the cost of more communication and **higher peak memory**"*
>
> 机制上确实会涨（warmup 要灌更多前向才填得满 p·v 个 chunk），但涨幅在 Megatron 作者看来属于"可比"。
> ★ **实践态度：开 VPP 前给 stage 0 留出显存余量。**

> ⚠️★ **注意 ZB-H2 是反方向的**：它拿 2 倍激活显存去买最后那 1/3 气泡（§7.6.5）。
> **stage 0 本来就快爆的场景下，ZB-H2 是敌人不是朋友** —— 该选 ZB-H1（显存不涨）或 ZB-2p（带显存约束的 ILP 搜索版）。

---

### 7.8.4 ⚠️ 例外：最后一个 stage 的 logits 尖峰

上面说 stage 0 最大，说的是**稳态激活总量**。但末 stage 有个别人没有的东西：

```
    末 stage 要做：hidden [b, s, h]  ──LM head──►  logits [b, s, V]
                                                            ↑
                                              ★ V = 词表大小，15 万起步 ★

    ★★ 从 h=8192 一下膨胀到 V=150000，宽了 18 倍 ★★
    而且交叉熵通常要 upcast 到 fp32 算 softmax → 又 ×2
```

> 📌 **LM head**（**L**anguage **M**odel head，语言模型输出头）：把最后一层隐藏状态投影到词表维度的矩阵 `[h, V]`，用来预测下一个 token。
> 📌 **upcast（升精度）**：bf16 算 softmax 容易数值不稳，所以先转成 fp32 再算。

同样设定（s=4096, V=150000），⚠️ 推断值：

```
    不切词表：  bf16 logits 1.14 GB + fp32 副本 2.29 GB + 反向梯度 2.29 GB ≈ ★5.7 GB★
    TP 切词表： ÷8 → ≈ 0.72 GB
```

```
    ✅ 做了 vocab-parallel（词表按 TP 切）
       末 stage 合计 ≈ 1.33 + 0.72 = 2.1 GB   ← 仍远小于 stage0 的 10.6 GB
       ★ stage 0 稳赢

    ⚠️ 没切词表 / p 很小 / micro-batch 开大 / 序列很长
       那 5.7 GB 是【一次性尖峰】，可能瞬间顶穿
       ★ 末 stage 反超
```

> 📌 **vocab-parallel（词表并行）**：把 `[h, V]` 沿 V 方向按 TP 度切开，每张卡只算词表的一段，配合并行版交叉熵。Megatron 默认就是这么做的。

🔑 **两者性质不同，别混**：

```
    stage 0   → ★ 持续高水位 ★  整个 iteration 一直占着     = "住得满"
    末 stage  → ★ 瞬时尖峰 ★    只在算 loss 的几十毫秒占着  = "突然挤一下"

    ⚠️ 尖峰更容易触发 OOM，即使它的【平均】显存低得多。
    → 这就是 Megatron 后来做 fused cross-entropy、分块算 logits 的原因。
```

---

### 7.8.5 别忘了首尾还各多背一块权重

激活之外，首末 stage 各自还多扛一个大矩阵——这是 §7.7 那三条的显存版：

```
    首 stage：word embedding 表  [V, h]
    末 stage：LM head            [h, V]     ← 很多模型这两个是 tied（共享权重）的

    V=150000, h=8192 → 12.3 亿参数
    光权重 bf16 就 2.46 GB，再加梯度 + 优化器状态（Adam 两个动量 + fp32 主权重）→ ×6~8

    ⚠️ 这一坨相当于 15 层 transformer 的参数量，却被塞给了首尾两张卡
       （TP 会把它切开，但切完仍然是首尾两端独有的额外负担）
```

---

### 7.8.6 ✅ 对策一览（按性价比排）

| 手段 | 作用 | 代价 |
|---|---|---|
| **首尾 stage 少分层** | 直接削掉 stage 0 的层数 | 无，本来就该做 ✅ `--decoder-first-pipeline-num-layers` / `--decoder-last-pipeline-num-layers` |
| **vocab-parallel + fused 交叉熵** | 消掉末 stage 的 logits 尖峰 | 无 |
| **选择性重计算** | 每层激活 `34+5as/h` → `34`（GPT-3 省 70%） | ✅ 只花 2.7% 算力（[11 章](11-重计算与激活优化.md)） |
| **前段 stage 激活 offload 到 CPU** | 前面的激活要等很久才用，正是最佳卸载对象 | PCIe 带宽 ✅ Megatron *"Pipeline-aware fine-grained activation offloading"* |
| **改用 ZB-H1** | 气泡降到 1/3，★显存分文不涨★ | 实现复杂度 |
| **完全重计算** | 激活降到 `2sbh` | ⚠️ 30~40% 算力，最后的手段 |

## 7.9 本章小结

```
① PP = 把【层】切开，每张卡负责连续的一段（一个 stage）
   ★ 卡间只传一个激活张量 [b,s,d] → 通信量远小于 TP → 可以跨机器
   ✅ Megatron-2 实测：PP 通信占用 892 GB/s，DP 占 13 TB/s，差 14.6 倍

② ★★ 代价是【气泡】：气泡率 = (p−1)/(m+p−1) ★★
   → m 要远大于 p，经验法则 m ≥ 4p
   ⚠️ 但 m 受 global batch 天花板限制（04 章）—— 约束互相打架

③ ★ GPipe → 1F1B 省的是【显存】不是气泡（最容易记错的一点）
   ✅ Zero Bubble 论文原话："similar bubble ratios but ... advantage in peak memory"
   GPipe 峰值显存 ∝ m，1F1B ∝ p
   → 显存省了才【敢】把 m 调大，间接压住气泡
   ⚠️ PipeDream 原版是异步的（改了优化器语义），Megatron 用的是
      同步变体 PipeDream-Flush（论文称 "vanilla semantics"）

④ ★ 交错式（VPP）：每张卡拿【不连续的 v 小段】，气泡率约 ÷v
   ✅ Megatron 源码 docstring 的官方例子（pp=4, vpp=2, 16 层）：
      GPU0: [1,2][9,10]  GPU1: [3,4][11,12] ...
   ★★ 公式 (p−1)/(v·m+p−1) 的来历：v 是【从分子挪到分母】的 ★★
      计算时间 m 完全没变（v 个 chunk × 1/v 厚 = 1 格）
      变的是气泡 → (p−1) 缩成 (p−1)/v → 分子分母同乘 v 才成了 v·m
   ✅ Megatron-2 实测提升 10%+
   ⚠️ 代价：通信次数 ×v、峰值显存上升、层数要能被 p×v 均分
      → 实践中 v = 2~4 是甜点

⑤ ✅ PTD-P 总成绩：1T 参数 / 3072 张 A100 / 502 PFLOP/s / 52% 峰值
   ✅ ★ 关键警告："配比选错，吞吐差 2 倍" → 12 章存在的理由

⑥ ★ 零气泡：把反向拆成 B（算 dL/dX，下游在等，急）和 W（算 dL/dW，没人等，不急）
   ✅ Table 2 三行公式：1F1B (p−1)(T_F+T_B+T_W) / ZB-H1 (…−T_W) / ZB-H2 (…−2T_W)
   ★★ 三层要分清，别混成一层 ★★
      ① 拆 B/W        → 气泡剩 1/3（不是 1/2），显存不变      = ZB-H1
      ② +2倍显存多灌F → 梯形掰成平行四边形，理想下 = 0        = ZB-H2
      ③ +ILP 自动搜   → ★实测 <1% 的是这个★                  = ZB-2p
   ⚠️ ZB-H2 的"零"只在 T_F=T_B=T_W 下成立；论文自己说 T_W<T_F<T_B
      代回去气泡 = 3(p−1)(T_F−T_W) > 0，Table 5 实测 2.6%~10.8%
   ✅ 比 1F1B 快 23%（同显存）/ 31%（放宽显存）

⑦ ⚠️ 负载不均（计算侧）：首 stage 多 embedding，末 stage 多 LM head + loss
   → 流水线速度由最慢 stage 决定，要给首尾少分几层

⑧ ★★ 显存压力（§7.8）：空间上 stage 0 最大，时间上峰值在 warmup 末尾 ★★
   空间：stage i 缓存 (p−i) 份激活 → 呈 p, p−1, …, 1 的阶梯，首尾差 p 倍
   ✅ Megatron-2 原话："limits the number of in-flight microbatches …
      to the depth of the pipeline"
   时间：峰值 = warmup 最后一格（攒满 p 份、第一个 B 还没释放）
      → ★ OOM 几乎总在头几个 iteration，跑过 10 步就基本安全 ★
   ★★ 最反直觉的一点：p 开大，stage 0 的激活【一点都不降】★★
      p 份 × (L/p 层) = L —— p 被约掉了
      ⟹ PP 解决"参数放不下"，不解决"激活放不下"（那是 08 / 11 章的事）
   ⚠️ 例外：末 stage 的 logits [b,s,V] 是全模型最大单张量，
      没做 vocab-parallel 时形成【瞬时尖峰】，可能反超 stage 0
   ⚠️ ZB-H2 显存翻倍 (2p−1)·M_B —— stage 0 紧张时它是敌人，该选 ZB-H1
```
