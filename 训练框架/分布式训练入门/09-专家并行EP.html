09 · 专家并行 EP

这一章的目标：讲清最后一种切法。它和前四种不一样——前四种对任何模型都适用，EP 只对 MoE 模型适用。
读完你应该能回答：MoE 为什么必须要一种新的并行方式？all-to-all 为什么是 EP 的心脏也是它的痛处？"容量因子"和"丢 token"是怎么回事？为什么说 EP 是"从 DP 里借卡"？

📌 EP = Expert Parallel，专家并行。
📌 MoE = Mixture of Experts，专家混合。如果你完全不知道 MoE 是什么，先读隔壁的 ../../业界模型技术报告/大模型架构入门/10-MoE.md，那里从零讲起。本章只需要你知道下面这一句。

9.1 一句话回顾 MoE，以及它给系统出的难题

    普通 Transformer 层：         MoE 层：

        每个 token                    每个 token
            ↓                             ↓
      【唯一的一个 FFN】            ★【路由器】选 top-k 个专家
            ↓                        ↓        ↓
          输出                    专家3      专家17     （共 256 个专家）
                                     ↓        ↓
                                  加权求和 → 输出

    ★ 参数量：256 个专家 → 参数是普通 FFN 的 256 倍
    ★ 计算量：每个 token 只走 k=8 个 → 计算只有 8 倍
    → ★★ 参数量暴涨但计算量不涨，这就是 MoE 的全部卖点 ★★

✅ 这条路线的两篇奠基论文都用数字说明了它有多值：
- GShard（papers/GShard-arXiv-2006.16668.pdf）："scale up multilingual neural machine translation Transformer model with Sparsely-Gated Mixture-of-Experts beyond 600 billion parameters... trained on 2048 TPU v3 accelerators in 4 days"
- Switch Transformer（papers/Switch-Transformers-arXiv-2101.03961.pdf）："pre-training up to trillion parameter models... and achieve a 4x speedup over the T5-XXL model"，并且 "up to 7x increases in pre-training speed with the same computational resources"

★ 但这给系统出了一个前四章都解决不了的难题

    问题：256 个专家的参数放不下（这是 [02 章](02-显存去哪了.md) 的"病"①②③）

    ❌ 用 TP 切？ 每个专家的矩阵本来就不大，切成 8 份后每份太小
                  → GPU 算小矩阵效率极低（[06 章](06-张量并行TP.md) 讲过）
                  → 而且通信次数 × 256
    ❌ 用 PP 切？ 专家是【同一层内】的并列关系，不是前后关系，切不了
    ❌ 用 ZeRO？  可以，但每次前向都要 all-gather 全部 256 个专家的参数
                  —— 而这个 token 只用其中 8 个，★ 白搬 32 倍的数据

    ★★ 关键观察：专家之间是【天然独立】的 ★★
       专家 3 和专家 17 各算各的，中间没有任何交互
    → ✅ 那就一张卡放几个专家，让【token 去找专家】，而不是【专家来找 token】

9.2 EP 的机制：让 token 出差

    EP=4，8 个专家：

    ┌────────┬────────┬────────┬────────┐
    │  卡0   │  卡1   │  卡2   │  卡3   │
    │ 专家0,1│ 专家2,3│ 专家4,5│ 专家6,7│
    └────────┴────────┴────────┴────────┘

    但★每张卡手里的 token 是不一样的★（它们来自不同的 DP 分片/序列分片），
    而这些 token 被路由器分配给了【散落在各张卡上】的专家。

    → 于是每张卡都要"把自己的 token 寄给对应的卡，同时收别人寄来的 token"
    → ★★ 这正是 [03 章 §3.2](03-通信原语.md) 讲的 all-to-all ★★

完整的四步

    ① 路由（Router）
       每张卡本地算：我的每个 token 该去哪几个专家
       → 得到 expert_indices

    ② ★ Dispatch：all-to-all #1
       按目的地把 token 重新打包，全体交换
       "卡0 手里所有要去专家 4 的 token" → 发给卡2
       ↓
       ★ 交换完，每张卡手里都是【属于自己专家的】token

    ③ 专家计算
       每张卡本地跑自己那几个专家的 FFN
       ★ 完全没有通信，纯计算 —— EP 的价值就在这一步

    ④ ★ Combine：all-to-all #2
       把结果原路寄回去，每个 token 回到它原来的卡
       ↓
       按路由权重加权求和 → 输出

    形状变化（[08 章](08-序列并行与上下文并行.md) 那种"换切法"的思路又来了）：

    dispatch 前： 每张卡 = 【1/N 的 token】 × 【全部专家的候选】
    dispatch 后： 每张卡 = 【全部卡来的 token】 × 【1/EP 的专家】

    ★ 和 Ulysses 的"切序列 ⇄ 切头"是同一种把戏：
      换一个维度来切，好让本地能独立计算。

9.3 ⚠️ all-to-all：EP 的心脏，也是它的病灶

    ★ all-to-all 是所有通信原语里【最难受】的一个：

    ① 每张卡都要和【其它每一张卡】通信 → N² 条逻辑连接
    ② 消息小而碎（每对卡之间只有几百个 token）
       → 延迟（latency）占主导，带宽根本吃不满
    ③ ★★ 它卡在关键路径上 ★★
       专家计算必须等 dispatch 全部完成才能开始
       —— 不像 DP 的梯度 all-reduce 可以和反向计算重叠
    ④ 跨机器时尤其惨：走 [03 章](03-通信原语.md) 那条 50 GB/s 的网络

✅ 这个开销有多大？Megatron 官方文档自己给了数字——../源码/Megatron-LM/megatron/core/transformer/moe/README.md 原文：
"EP All-to-All can consume 30-40% of training time without optimization. These features hide or reduce EP communication overhead."

    ★★ 30~40% 的训练时间花在一个通信原语上 ★★
    → 这就是为什么 MoE 训练框架的一大半工作量都在优化 all-to-all

Megatron 给的两个对策（✅ 同一份文档的表格）：

优化 做法 开关
EP A2A Overlap ✅ "Overlaps All-to-All with computation by merging FWD-BWD passes of adjacent microbatches" --overlap-moe-expert-parallel-comm --delay-wgrad-compute
Shared Expert Overlap ✅ "Runs shared expert computation concurrently with EP token transfer" --moe-shared-expert-overlap

🔑 第二条特别巧妙，值得拆开讲：
```
现在的 MoE 大多有【共享专家】（每个 token 都必走的那个 FFN，不需要路由）。
★ 共享专家的计算【不依赖 all-to-all 的结果】
→ 那就在 token 满天飞的时候，顺手把共享专家算了
→ ★ 白赚一段重叠时间

这是个典型例子：★ 模型架构的一个设计（共享专家），
意外地给系统层送了一个可以填的空隙。
```

9.4 ★ 负载不均：MoE 独有的麻烦

    ★ 前四种并行，每张卡的工作量是【天然相等】的（切得一样大）
    ★ EP 不是：★★ 工作量由路由器【运行时】决定 ★★

    理想：      256 个专家各分到 1/256 的 token
    现实：      专家 7 分到 20%，专家 200 分到 0.01%
                → 卡2 忙死，其余卡空转等它
                → ★ 整个 step 的速度 = 最慢那张卡的速度

对策一：容量因子 + 丢 token（老办法）

✅ Switch Transformer 论文的定义（原文）：
$$\text{expert capacity} = \left(\frac{\text{tokens per batch}}{\text{number of experts}}\right)\times \text{capacity factor}$$
"A capacity factor greater than 1.0 creates additional buffer to accommodate for when tokens are not perfectly balanced across experts. If too many tokens are routed to an expert (referred to later as dropped tokens), computation is skipped and the token representation is passed directly to the next layer through the residual connection. Increasing the expert capacity is not without drawbacks, however, since high values will result in wasted computation and memory."

    ★ 翻译：给每个专家规定一个固定的坑位数。

      坑位不够 →  ❌ 多出来的 token 被【丢掉】，直接走残差跳过这一层
                    （模型质量受损）
      坑位太多 →  ❌ 大量坑位是空的，pad 成 0 参与计算
                    （算力和显存被浪费）

    ★★ 为什么非要固定坑位？因为 GPU 的矩阵乘要【定形状】的张量 ★★
       ——这是一个纯粹由硬件逼出来的妥协，不是算法上想要的。

✅ MegaBlocks 论文（papers/MegaBlocks-Efficient-MoE-arXiv-2211.15841.pdf）把这个困境说得最清楚：
"These formulations force a tradeoff between model quality and hardware efficiency, as users must choose between dropping tokens from the computation or wasting computation and memory on padding."
"This decision is often made through hyperparameter tuning, which increases the complexity of using MoEs."

对策二：dropless MoE（现在的做法）

✅ MegaBlocks 的解法：
"we reformulate MoE computation in terms of block-sparse operations and develop new block-sparse GPU kernels that efficiently handle the dynamism present in MoEs. Our approach never drops tokens and maps efficiently to modern hardware, enabling end-to-end training speedups of up to 40% over MoEs trained with the state-of-the-art Tutel library and 2.4× over DNNs trained with the highly-optimized Megatron-LM framework."
"We use this formulation to train dropless-MoEs (dMoEs)."

    ★ 核心想法：不要强行把不等长的东西 pad 成等长，
      而是把它表示成一个【块稀疏矩阵】，写专门的 kernel 直接算。

    → 一个 token 都不丢，也不 pad
    → ✅ Megatron 现在默认就是 dropless（源码 README：
        "Token dropless MoE (dMoE) - Advanced routing without token dropping"）

对策三：从算法侧治本 —— 负载均衡损失

    ★ 上面两条都是"系统侧忍受不均衡"，还有一条是"算法侧不让它不均衡"：

    在损失函数里加一项，惩罚"专家使用率不均匀"
      → Megatron: --moe-router-load-balancing-type aux_loss
                  --moe-aux-loss-coeff 1e-2

    ⚠️ 但这一项会和主损失【打架】（为了均衡而牺牲了路由质量）
    → 新一代做法是 aux-loss-free：不加损失项，只调一个偏置
      （DeepSeek-V3 起的主流做法，见隔壁
       [../../业界模型技术报告/大模型架构入门/10-MoE.md](../../业界模型技术报告/大模型架构入门/10-MoE.md)）

🔑 这一节是全教程里"系统和算法耦合最紧"的地方：负载均衡既是一个训练目标问题，也是一个调度问题，两边都得管。

9.5 ★ EP 在并行体系里的位置：它是从 DP 里"借"卡

这是初学者最容易困惑的一点。回忆 README 那条铁律：

$$TP \times PP \times CP \times DP = N$$

EP 在哪儿？答案是：EP 不在这条式子里，它是在 DP 的那部分卡上【再切一刀】。

    ★ 一个直观的理解：

    模型的注意力部分（稠密）  →  用 TP / PP / CP / DP，照旧
    模型的专家部分（稀疏）    →  这些卡换一个身份，重新编组成 EP

    ★★ 同一批 GPU，在【注意力层】和【专家层】用【两套不同的分组方式】★★

✅ 这在 Megatron 源码里写得非常清楚——../源码/Megatron-LM/megatron/core/parallel_state.py 第 51–54 行的注释原文：
```

_EXPERT prefix in group name means it's used for expert layer in MoE models.

_EXPERT_MODEL denotes expert parallelism which splits number of experts across the group.

_EXPERT_TENSOR denotes tensor parallelism of expert which splits tensor across the group.

_EXPERT_DATA denotes data parallelism of expert which replicates weight across the group.

```
✅ 同文件另一处注释："CP is only included in default RankGenerator, and EP only in expert RankGenerator."

★ 有【两套 RankGenerator】—— 一套给稠密层，一套给专家层。 这就是"同一批卡两套分组"在代码里的样子。

所以 MoE 训练里有一组独立的旋钮：

参数 含义 默认
--expert-model-parallel-size EP 度：专家分到几张卡上 1
--expert-tensor-parallel-size ETP：专家【内部】还要不要再 TP 切 ✅ 同 TP（源码文档："Recommended to set to 1 for fine-grained MoE models"）

📌 ✅ 为什么细粒度 MoE 推荐 ETP=1：现在的 MoE 专家越做越小（DeepSeek 那种 256 个小专家），本来就小的矩阵再 TP 切一刀会更碎，得不偿失。这和 06 章 说的"TP 切太细会让矩阵变小、效率下降"是同一个道理。

✅ 一个真实的配置（源码 README 里的 Mixtral 8×7B 例子）

--num-experts 8
--expert-model-parallel-size 8        # ★ 8 个专家分到 8 张卡，一卡一个
--moe-router-topk 2                   # 每个 token 走 2 个专家
--moe-router-load-balancing-type aux_loss
--moe-aux-loss-coeff 1e-2
--moe-grouped-gemm                    # ★ 见 §9.6
--moe-token-dispatcher-type alltoall  # ★ §9.2 那两次 all-to-all

9.6 一个绕不开的工程细节：GroupedGEMM

    ★ 问题：每张卡上有 8 个专家，就要跑 8 次小矩阵乘。

    8 次独立的 kernel 启动
      → 每次都有固定开销（kernel launch overhead）
      → 每个矩阵又都不大，GPU 根本没吃饱
      → ★ 大量时间浪费在"启动"而不是"计算"上

✅ 源码 README 的说明："Grouped GEMM | Batches multiple expert GEMM operations into a single kernel call, improving GPU utilization | --moe-grouped-gemm"
以及问题描述："Fine-grained MoE produces many small operations that can underutilize GPU resources. These optimizations reduce kernel launch overhead and improve GPU utilization."

    ★ GroupedGEMM = 把 N 个"形状不同的小矩阵乘"塞进【一次】kernel 调用
    → 这是 MoE 能高效跑起来的必需品，不是可选优化

📌 GEMM = GEneral Matrix Multiply，通用矩阵乘法。GPU 上所有线性层最终都归结成 GEMM 调用。

9.7 ⚠️ EP 的账：它省什么、不省什么

    ✅ 省：专家部分的【参数 + 梯度 + 优化器状态】÷ EP
       —— 而 MoE 模型 90%+ 的参数都在专家里，所以这个 ÷ 非常值钱

    ❌ 不省：注意力部分（那部分靠 TP/PP/ZeRO）
    ❌ 不省：激活（那部分靠 SP/CP/重计算，见 [08](08-序列并行与上下文并行.md)、[11](11-重计算与激活优化.md) 章）
    ⚠️ 反而增加：dispatch 之后每张卡手里的 token 变多了
       → ★ 专家部分的激活显存反而可能【涨】

    ⚠️ 代价：
       ① 两次 all-to-all，占 30~40% 训练时间（未优化时）
       ② 负载不均，速度由最慢的卡决定
       ③ ★ 强烈建议 EP 组【放在机内】走 NVLink
          —— 和 [06 章](06-张量并行TP.md) 的 TP 抢同一批高速链路，
             ★ 这就是 12 章那个"配比选择"问题最难的一块

9.9 本章小结

① ★ EP 是唯一一种【只对特定架构（MoE）有意义】的并行方式
   MoE：参数量 ×256，计算量 ×8 —— 参数涨而计算不涨
   ✅ GShard 600B / 2048 TPU / 4 天；✅ Switch 万亿参数 / 比 T5-XXL 快 4 倍

② ★ 为什么前四种不够：TP 把小专家切得更碎、PP 切不动并列关系、
   ZeRO 要 all-gather 全部 256 个专家但只用 8 个（白搬 32 倍）
   → 关键观察：★ 专家之间天然独立 → 一卡放几个专家，让 token 去找专家

③ EP 四步：路由 → ★all-to-all dispatch → 本地专家计算 → ★all-to-all combine
   ★ 和 Ulysses 是同一种把戏：换一个维度切，好让本地能独立算

④ ⚠️ all-to-all 是心脏也是病灶：碎、延迟主导、★在关键路径上
   ✅ Megatron 官方文档："EP All-to-All can consume 30-40% of training time"
   对策：微批 FWD-BWD 合并重叠；★ 用【共享专家】的计算去填 all-to-all 的空隙

⑤ ★ 负载不均是 MoE 独有的（前四种切得一样大，EP 由路由器运行时决定）
   老办法：容量因子 + 丢 token
     ✅ Switch 定义：capacity = (tokens/experts) × capacity_factor
     ✅ MegaBlocks 一针见血："force a tradeoff between model quality and
        hardware efficiency ... drop tokens or waste computation on padding"
   新办法：★ dropless（块稀疏 kernel），一个不丢也不 pad
     ✅ MegaBlocks：比 Tutel 快 40%，比 Megatron-LM 快 2.4×
   算法侧：负载均衡损失 → 现在流行 aux-loss-free

⑥ ★★ EP 不在 TP×PP×CP×DP=N 这条式子里，它是在 DP 那部分卡上再切一刀
   ✅ 源码有【两套 RankGenerator】：一套给稠密层，一套给专家层
   ✅ 细粒度 MoE 推荐 ETP=1（专家本来就小，再切更碎）

⑦ GroupedGEMM：把很多个小矩阵乘塞进一次 kernel 调用 —— MoE 的必需品

⑧ ⚠️ EP 只省专家部分的模型状态；激活反而可能涨；EP 组要放机内，
   ★ 会和 TP 抢同一批 NVLink

五种切法到此讲完。 接下来两章讲另一类完全不同的思路：不切，也能省——10 章把每个数字变小，11 章干脆不存、要用时再算。
