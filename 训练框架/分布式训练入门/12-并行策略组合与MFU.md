## 12.2 ★ MFU：先学会量体温

**在调任何参数之前，你需要一个能判断"我现在跑得好不好"的数字。**

### 定义

```
    ┌────────────────────────────────────────────────────┐
    │  MFU = 【模型本身必须做的浮点运算】                  │
    │        ────────────────────────────────            │
    │        【硬件理论上能做的浮点运算】                  │
    └────────────────────────────────────────────────────┘
```

> 📌 **MFU** = **M**odel **FLOPs **U**tilization，**模型算力利用率**。
> 📌 **FLOPs** = **FL**oating-point **OP**eration**s**，浮点运算次数。**⚠️ 注意结尾的 s 是复数不是"每秒"**；每秒的写法是 **FLOP/s**。这两个记号在论文里经常被混用，看到时按上下文判断。

### 怎么算

**分子**用 [01 章](01-为什么需要分布式训练.md)那个公式：

$$\text{每步的模型 FLOPs} \approx 6\,\Psi\,T$$

```
    Ψ = 参数量（MoE 用【激活参数量】），T = 这一步吃了多少 token
    ★ 6 = 前向 2 + 反向 4（反向要算两个梯度，所以是前向的两倍）
```

**分母**是硬件峰值 × 卡数 × 用时：

$$\text{MFU} = \frac{6\,\Psi\,T}{N \times P_{\text{peak}} \times t_{\text{step}}}$$

```
    ★★ 一个完整的算例（⚠️ 举例数字，不是任何真实系统的披露值）：

      模型 175B，2048 张 H100（BF16 峰值 989 TFLOP/s，不含稀疏加速）
      global batch = 1024 条 × 4096 token = 4.19 M token
      实测一步用了 26 秒

      分子 = 6 × 175e9 × 4.19e6      = 4.40e18 FLOPs
      分母 = 2048 × 989e12 × 26      = 5.27e19 FLOPs
      MFU  = 4.40 / 52.7            ≈ 8.4%   ← ⚠️ 太低了，有大问题
```

### ★★ 关键：分子里【不算】重计算

```
    ★ 这是 MFU 这个指标最重要的设计：

      分子只算【模型定义上必须的】6ΨT，
      ★ 重计算多做的那一遍前向【不计入分子】。

    → 所以开了完全重计算，MFU 会【下降】（做了更多实际运算，
      但模型需要的运算没变，时间却变长了）

    ⟹ ★★ 这正是 [11 章](11-重计算与激活优化.md)那个
       "54.2% vs 42.1%" 的含义：同一个模型、同一批卡，
       ✅ 选择性重计算比完全重计算的 MFU 高 12 个点。
```

> 📌 **另一个容易混淆的指标：HFU**（**H**ardware **FLOPs** **U**tilization，硬件算力利用率）。**它把重计算也算进分子**——衡量的是"硬件忙不忙"，而 MFU 衡量的是"忙得有没有意义"。**★ 开了重计算时 HFU > MFU，两者的差值就是重计算的开销。看论文时一定要看清报的是哪个。**

### 什么算好

| MFU | 评价 |
|---|---|
| < 25% | ⚠️ 配置有明显问题，去查 §12.5 |
| 30~40% | 能跑，但有明显提升空间 |
| **40~50%** | ★ 大多数生产训练的正常水位 |
| **> 55%** | ★★ 调得很好了 |
| > 70% | 一般只出现在小模型 / 短序列 / 特调场景 |

**✅ 有据可查的几个标杆**：

| 系统 | 规模 | 数字 | ★ 实际是哪个口径 | 出处 |
|---|---|---|---|---|
| PTD-P（Megatron-2） | 1T 参数，3072 A100 | **52%** | ⚠️ **HFU**（见下方订正） | ✅ 2104.04473 |
| Megatron-3 完全重计算 | 530B，2240 A100 | **42.1%** | MFU | ✅ 2205.05198 |
| Megatron-3 选择性重计算 | 530B，2240 A100 | **★ 54.2%**（快 29%） | MFU | ✅ 2205.05198 |
| MegaScale | 175B，**12,288** GPU | **★★ 55.2%**（比 Megatron-LM 高 1.34×） | ✅ 明确写了 MFU | ✅ 2402.15627 |

> ✅ MegaScale 摘要原文：*"MegaScale achieves **55.2% Model FLOPs Utilization (MFU)** when training a **175B** LLM model on **12,288 GPUs**, improving the MFU by **1.34×** compared to Megatron-LM."*

#### ⚠️★★ 订正：Megatron-2 那个 52%，不是 MFU

**这是一个流传很广的误引，本文之前也写错了，在此更正。**

```
    ✅ 论文摘要原文（只说了"理论峰值"，★ 没说是 MFU）：
       "per-GPU throughput of 52% of theoretical peak"

    ⟹ ★ 那到底是哪个口径？去看它的 FLOPs 公式（论文第 12 页）：
```

> ✅ **论文原文（附录，决定性证据）**：
> *"We also note that equation (3) assumes **activation recomputation** and
> **takes into account the floating-point operations associated with the extra forward pass**."*
>
> ✅ 它给出的公式是：**F = 96·B·s·l·h²·(1 + s/6h + V/16lh)**

```
    ★★ 盯住那个系数 96。

      标准的 MFU 分子用的是  72·B·s·l·h²
        （前向 24 + 反向 48 = 72，★ 反向是前向的 2 倍，见 §12.2）

      Megatron-2 用的是      96·B·s·l·h²
        （96 = 72 × 4/3，★ 多出来的 24 就是【重计算的那次额外前向】）

    ⟹ ★★★ 分子里【算了】重计算 ⟹ 按 §12.2 的定义，这是 HFU，不是 MFU。
```

**换算过去是多少？**

```
    MFU = HFU × 72/96 = 52% × 0.75 ≈ ⚠️ 39%

    ⚠️ 这是我按公式做的换算，论文本身【没有】报告 MFU 数字。
```

> 🔑 **★★ 为什么必须较这个真？** 因为不订正的话，这张表会给出错误的结论：
> ```
>     ✗ 错误读法：「Megatron-2 是 52%，MegaScale 是 55.2%，
>                   ⟹ 三年过去只进步了 3 个百分点，★ 分布式训练停滞了」
>
>     ✅ 正确读法：「Megatron-2 是 39% MFU，MegaScale 是 55.2% MFU，
>                   ⟹ ★★ 实际提升了 40% 以上」
>
>     ⟹ 🔑 一个口径错误，能把"重大进步"读成"原地踏步"。
> ```
>
> ⚠️ **也不要因此说 Megatron-2 的论文有问题**：
> **MFU / HFU 这组术语是 2022 年 PaLM 论文才明确区分的**，
> 而 Megatron-2 发表于 2021 年 4 月。
> ★ 它说的 "52% of theoretical peak" 在当时是准确表述——
> **是后人把它转述成"52% MFU"时丢了口径。**

> ★ **给你自己的启示**：以后看到任何"XX% 利用率"，先问三句：
> ```
>     ① 分子里【算没算】重计算？        ⟹ 决定是 MFU 还是 HFU
>     ② 峰值用的是【稠密还是稀疏】算力？ ⟹ 稀疏峰值是稠密的 2 倍，能把数字腰斩
>     ③ 论文自己【用了哪个词】？         ⟹ "of theoretical peak" 是【不表态】，
>                                          不能默认按 MFU 读
> ```

## 12.3 ★★★ PTD-P 的三条 Takeaway（本章最硬的部分）

**PTD-P 论文最有价值的不是它的性能数字，而是它明确写出来的三条经验法则。**⭐ **这三条直接告诉你旋钮该按什么顺序拧。**

### ✅ Takeaway #1：TP 不要跨机

> *"When considering different forms of model parallelism, **tensor model parallelism should generally be used up to degree g when using g-GPU servers**, and then **pipeline model parallelism can be used to scale up to larger models across servers**."*

```
    ★ 翻译成人话：
      一台机器有 8 张卡（NVLink 互联）→ ★ TP 最多开到 8
      还不够大？→ ★ 再往上用 PP 跨机器

    为什么？回忆 [03 章](03-通信原语.md)的带宽阶梯：
      机内 NVLink       ~900 GB/s
      机间 InfiniBand   ~50 GB/s      ★★ 差约 18 倍
```

```
    ★ 为什么偏偏是 TP 不能跨机（而不是 PP）：

      TP：每层【4 次 all-reduce】（[06](06-张量并行TP.md)/[08](08-序列并行与上下文并行.md)）
          → 80 层 = 320 次集合通信，★ 而且【卡在计算路径上】，必须等
      PP：相邻 stage 之间【1 次 P2P 发送】
          → 只在 stage 边界通信，★ 而且可以和计算重叠

    ⟹ ★★ 通信最密集的那个维度，要放在带宽最快的那条链路上 ★★
       这是全章唯一一条【几乎没有例外】的规则。
```

> ✅ 论文自己诊断的病因：*"the all-reduce communication required for tensor parallelism needs to go through **inter-server links, which are slower** than the high-bandwidth NVLink available within a multi-GPU server"*，以及 *"a high degree of model parallelism can create **small matrix multiplications (GEMMs), potentially decreasing GPU utilization**"*。

```
    ★ 注意第二个病因，它常被忽略：
      TP 开太大 → 每张卡分到的矩阵变得又小又窄
      → GPU 的 Tensor Core 吃不饱（矩阵太小，启动开销占比升高）
      → ★ 就算通信是免费的，算力利用率也会掉
```

### ✅ Takeaway #2：先把模型塞下，剩下的全给 DP

> *"When using data and model parallelism, a total model-parallel size of **M = t · p** should be used so that the model's parameters and intermediate metadata **fit in GPU memory**; **data parallelism can be used to scale up training to more GPUs**."*

```
    ★★ 这条给出了整个调参的【骨架顺序】：

      ① 先问：TP × PP 开到多少，模型才【装得下】？   ← 显存问题
      ② 装下之后，剩下的卡【全部给 DP】              ← 扩展问题

    ⟹ ★ TP 和 PP 是【被迫】开的（不开就 OOM），
       DP 才是【想开】的（它最便宜、最好扩展）
```

```
    ⚠️ 一个重要的现代补充（PTD-P 是 2021 年的论文）：
       今天 ZeRO/FSDP 让 DP 也能省显存（[05 章](05-ZeRO与FSDP.md)），
       所以 ①②之间多了一步：
       ★ 能用 ZeRO-1 解决的，就不要动 TP/PP。
```

### ✅ Takeaway #3：micro-batch 没有万能值

> *"The **optimal microbatch size b depends on** the throughput and memory footprint characteristics of the model, as well as **the pipeline depth p, data-parallel size d, and batch size B**."*

```
    ★ b 被两股力量拉扯：

      b 变大 → 单卡矩阵变大 → GPU 效率↑（✅ 论文实测最高 1.3×）
             → 但激活显存 ∝ b，↑；且 m = B/(b·DP) 变小
               → ★ 流水线气泡 (p−1)/(m+p−1) 变大（[07 章](07-流水线并行PP.md)）

      b 变小 → 气泡小，显存省
             → 但每次矩阵乘太小，GPU 吃不饱

    ⟹ ★ 没有公式能算出最优 b，只能【实测扫几个值】。
       ⚠️ 常见起点：b = 1、2、4，配 PP 时优先试 b=1（气泡最小）。
```

## 12.4 ★ 一套可以照做的调参顺序

**把上面三条 Takeaway 加上第三部分的工具，拼成一条流程。**⚠️ **这是我按论文结论 + 常见工程实践整理的顺序，不是某篇论文的原文。**

```
┌── 第 0 步：先把【免费的】全开 ──────────────────────────┐
│   ✅ FlashAttention        （更快，无代价）              │
│   ✅ BF16 混合精度         （[10 章](10-混合精度与FP8.md)）│
│   ✅ SP（若 TP>1）         （[08 章](08-序列并行与上下文并行.md)，通信量不变）│
│   ✅ 选择性重计算          （[11 章](11-重计算与激活优化.md)，2.7% 换 70%）│
│   ✅ 各种 overlap 开关     （见 §12.6）                   │
│   ★ 这一步没有任何取舍，不开是纯亏。                      │
└──────────────────────────────────────────────────────────┘
              ↓
┌── 第 1 步：TP —— 只在【一台机器内】 ───────────────────┐
│   从 TP=1 起步，OOM 了就翻倍：1 → 2 → 4 → 8            │
│   ★★ 硬上限 = 单机卡数（Takeaway #1）                   │
│   ⚠️ MoE 模型：优先用 EP 而不是 TP（[09 章](09-专家并行EP.md)）│
└──────────────────────────────────────────────────────────┘
              ↓
┌── 第 2 步：还装不下 → PP 跨机 ─────────────────────────┐
│   PP = 装得下的最小值（★ 不要多开，每一级都带气泡）      │
│   同时保证 m = B/(b·DP) ≥ 4p（[07 章](07-流水线并行PP.md)）│
│   ★ 开了 PP 就顺手开 VPP（--num-layers-per-virtual-...）│
│     气泡再除以 v，代价是通信次数 ×v                      │
└──────────────────────────────────────────────────────────┘
              ↓
┌── 第 3 步：序列很长（≥32K）→ CP ───────────────────────┐
│   ★ 只有长序列才开。短序列开 CP 是纯亏（[08 章](08-序列并行与上下文并行.md)）│
└──────────────────────────────────────────────────────────┘
              ↓
┌── 第 4 步：剩下的卡【全给 DP】 ────────────────────────┐
│   DP = N / (TP × PP × CP)          （Takeaway #2）      │
│   ★ 显存还紧张 → ZeRO-1（几乎无代价）→ ZeRO-2 → ZeRO-3  │
│   ⚠️ ZeRO-3 通信量大，和 PP 一起用要谨慎                 │
└──────────────────────────────────────────────────────────┘
              ↓
┌── 第 5 步：扫 micro-batch b ───────────────────────────┐
│   试 b = 1, 2, 4，看哪个 MFU 最高（Takeaway #3）        │
└──────────────────────────────────────────────────────────┘
              ↓
┌── 第 6 步：还是不够快 → 加重计算 / 上 FP8 ─────────────┐
│   ★ 这一步是【真的取舍】了，要一边测 MFU 一边看 loss。   │
└──────────────────────────────────────────────────────────┘
```

### 一个走完全程的例子（⚠️ 演示用，非真实披露配置）

```
    题目：400B 稠密模型，1024 张 H100（128 台 × 8 卡），序列 8K

    第 1 步  显存账（[02 章](02-显存去哪了.md)）：
             模型状态 = 400e9 × 16 字节 = 6400 GB
             单卡 80 GB → ★ 至少要切到 80 份以上才装得下
             TP = 8（打满单机）→ 每份 800 GB，★ 还是不够

    第 2 步  PP：6400 / (8 × 80) = 10 → ★ 取 PP = 16 留余量
             （层数要能整除，80 层 / 16 = 5 层每 stage）

    第 4 步  DP = 1024 / (8 × 16) = ★ 8
             ★ 开 ZeRO-1：优化器状态再切 8 份，
               每卡模型状态 ≈ 6400/(8×16) × (4/16 + 12/16/8) ≈ 15 GB

    第 5 步  m = B/(b·DP)，要 ≥ 4p = 64
             取 b=1、B=512 → m = 512/8 = 64  ✅ 刚好

    ⟹ 最终： TP=8, PP=16, DP=8, b=1, VPP=4, ZeRO-1, SP+选择性重计算
       验算： 8 × 16 × 1 × 8 = 1024  ✅
       气泡： (16−1)/(64+16−1)/4 ≈ 4.7%   ★ 可以接受
```

## 12.5 ⚠️ MFU 低的时候查什么

```
    ★ 按【收益 ÷ 排查成本】排序的清单：

    ① TP 跨机了吗？
       → 看 TP 组的 rank 是不是落在同一台机器上
       → ★ 这一条能解释绝大多数"莫名其妙的慢"

    ② 气泡多大？   (p−1)/((m+p−1)·v)
       → m < 4p 就是配错了。★ 要么 B 调大，要么 PP 调小

    ③ 重计算开太狠了吗？
       → 完全重计算 = ✅ 直接损失 30~40%
       → 换成 selective 试试

    ④ overlap 开关漏了吗？（§12.6）
       → 这些是白给的，忘开就是纯亏

    ⑤ 单卡矩阵是不是太小了？
       → TP 太大会把矩阵切碎（Takeaway #1 的第二个病因）
       → ★ hidden_size / TP 建议 ≥ 1024

    ⑥ 数据管道跟得上吗？
       → ★ 一个隐蔽的坑：GPU 在等数据。
         把 dataloader 摘掉喂假数据跑一次，MFU 若明显上升，
         问题就在数据侧（见 [../../数据格式和数据处理/](../../数据格式和数据处理/README.md)）

    ⑦ 有慢卡（straggler）吗？→ [13 章](13-断点续训与容错.md)
```

## 12.6 ✅ 一个真实的逐项拆解（MegaScale Table 3）

**MegaScale 论文给了一张极其有教育意义的表：从 47.7% 一路加到 65.3%，每一项各值多少。**（175B 模型，256 卡，batch 256）

| # | 加上什么 | MFU | 累计提升 |
|---|---|---|---|
| 1 | baseline | 47.7% | — |
| 2 | + PTB（并行 transformer block） | 52.3% | +4.6% |
| 3 | + SWA（滑动窗口注意力） | 53.3% | +5.6% |
| 4 | ★ **+ TP overlap** | 55.5% | +7.8% |
| 5 | ★ **+ PP overlap** | 58.0% | +10.3% |
| 6 | ★ **+ DP overlap** | 59.5% | +11.8% |
| 7 | + 高效算子 | 61.2% | +13.5% |
| 8 | + 杂项优化 | 62.3% | +14.6% |
| 9 | + LAMB（batch ×3） | 65.3% | +17.6% |

```
    ★★ 请注意第 4、5、6 行 ★★

    三个 overlap 加起来 = ★ 4.0 个百分点（55.5 → 59.5 的路上占了大头）
    而它们都是【纯粹的工程开关】——不改模型、不改超参、不影响收敛。

    ⟹ ★ 这就是为什么 §12.4 第 0 步要把 overlap 全打开。
```

> ⚠️ 注意第 2、3、9 行（PTB / SWA / LAMB）**改动了模型或优化器**，不是免费的——论文自己也强调它们*"do not affect the model convergence"*，但那是经过验证的结论，不能直接照搬到别的模型上。**★ 第 4~8 行才是可以无脑抄的部分。**

### 什么是 overlap

```
    ★ 核心思想一句话：★【通信的时候，让 GPU 别闲着】★

    ┌─ 不 overlap ────────────────────────┐
    │  计算 ████    通信 ▒▒▒▒  计算 ████   │  总时间 = 计算 + 通信
    └──────────────────────────────────────┘

    ┌─ overlap ──────────────────────────┐
    │  计算 ████████████                  │  总时间 = max(计算, 通信)
    │  通信   ▒▒▒▒▒▒                      │  ★ 通信被"藏"起来了
    └──────────────────────────────────────┘

    三个战场：
      DP overlap：反向算第 k 层时，第 k+1 层的梯度已经在 all-reduce 了
                  ★ 这是 [04 章](04-数据并行DP.md) 讲的 bucket 机制
      TP overlap：把 all-gather 拆块，算一块传一块
                  ⚠️ 需要 TP≥2 且开 SP
      PP overlap：P2P 发送和计算并行（--overlap-p2p-comm，开 VPP 时自动打开）
      EP overlap：all-to-all 和相邻 micro-batch 的计算并行（[09 章](09-专家并行EP.md)）
```

## 12.7 自动并行：能不能让机器自己搜？

**既然组合空间这么大，为什么不让程序自己搜？—— 有人做了。**

```
    ✅ Alpa（[papers/Alpa-Auto-Parallel-arXiv-2201.12023.pdf](../papers/Alpa-Auto-Parallel-arXiv-2201.12023.pdf)）
       ★ 关键洞察：把并行分成【两个层次】分别搜
          inter-operator（算子之间 → 类似 PP）
          intra-operator（算子内部 → 类似 TP/DP）
       → 用整数规划 + 动态规划分层求解

    ✅ GSPMD（[papers/GSPMD-Auto-Parallel-arXiv-2105.04663.pdf](../papers/GSPMD-Auto-Parallel-arXiv-2105.04663.pdf)）
       ★ 思路不同：用户只标注【几个关键张量】怎么切，
         编译器自动把切分方式【传播】到整张计算图
       → 这是 Google TPU 栈（JAX/XLA）的路线

    ⚠️ 为什么工业界主流仍然是手工配：
       ① 搜索本身要花钱（Alpa 的搜索时间在大模型上不可忽略）
       ② 手工的解已经足够好 —— Takeaway #1/#2 把空间砍掉了 99%
       ③ ★ 生产环境需要【可解释、可复现】：
          出问题时要能一眼看懂配置，自动搜出来的解不好排查
```

### 🔑 rank 排布顺序：为什么是 TP → CP → EP → DP → PP

**上面那些并行度设完，还有一件事没定：16 张卡里，谁和谁组成一个 TP 组？谁和谁组成一个 DP 组？** 这个"排座位"的规则，在源码里就是一个字符串常量。

```
✅ megatron/core/parallel_state.py：order = "tp-cp-ep-dp-pp"
   （由 megatron/training/initialize.py 传进 initialize_model_parallel()）

      tp  -  cp  -  ep  -  dp  -  pp
     最内 ←——— 通信敏感度递减 ———→ 最外
   变化最快                      变化最慢

★★ 最容易记反的一点：DP 在【中间】，PP 才在【最外】★★
   不是 TP → PP → DP。
```

#### 怎么用它算出每张卡的身份

```
    ★ 规则：rank = 各维度下标 × "比它更内层的所有维度的乘积" 之和

    以源码 docstring 的官方例子（16 卡，TP=2，PP=4 ⟹ DP=2，CP=EP=1）：

        rank = tp_id  +  2 × dp_id  +  4 × pp_id
               └─内─┘     └─中─┘        └─外─┘

    ✅ 于是三种组的 rank【步长】各不相同（和 docstring 列出的分组完全对得上）：

      TP 组：只变 tp_id，步长 = 1          → [g0,g1] [g2,g3] …        紧挨着
      DP 组：只变 dp_id，步长 = TP = 2     → [g0,g2] [g1,g3] …        ★ 隔一个
      PP 组：只变 pp_id，步长 = TP×DP = 4  → [g0,g4,g8,g12] …         隔三个

    ★★ [04 章](04-数据并行DP.md) 那个"g0 和 g2 一组，隔了一个"的疑问，
       答案就是这个步长 2 —— 它等于 TP，因为 DP 的外面一层正好是 TP。
```

#### 为什么偏偏是这个顺序

**因为 rank 编号的"内外"直接等于物理链路的"快慢"。**

```
    ★ 事实一：global_rank = 节点号 × 每节点卡数 + 本地卡号
      → rank 0~7 必然在第一台机器，8~15 在第二台
      ⚠️ 这是 torchrun / Slurm 的标准分配，不是 Megatron 定的，但 Megatron 依赖它

    ★ 事实二：[03 章](03-通信原语.md)的带宽阶梯
      机内 NVLink 900 GB/s   vs   机间 InfiniBand 50 GB/s   ★ 差 18 倍

    ⟹ ★★ 步长越小 → rank 越挨着 → 越可能同机 → 拿到的链路越快 ★★
       所以整个 order 就是一条按【通信敏感度】排的降序队列，
       敏感度最高的排最内层，去抢最快的线。
```

| 维度 | 通信原语 | 触发频率 | 在关键路径上？ | 座次 |
|---|---|---|---|---|
| **TP** | all-reduce | **每层 4 次** | ✅ 完全阻塞，下一层必须干等 | 最内 → 机内 |
| **CP** | all-gather / ring | 每层注意力 | ✅ 阻塞 | 紧随 TP |
| **EP** | all-to-all | 每个 MoE 层 | ✅ 阻塞 | 第三 |
| **DP** | all-reduce | **每 iteration 1 次** | ❌ 可与反向重叠 | 中间 |
| **PP** | P2P send/recv | 每 micro-batch，仅 stage 边界 | ❌ 可被 1F1B 掩盖 | 最外 → 跨机 |

```
    ⚠️ 一笔演示用的账（h=8192, s=4096, b=1, bf16, 80 层, TP=2/PP=4；非真实披露配置）

      单个激活张量 = 4096 × 8192 × 2 B = 64 MB

      TP：每卡 20 层 × 4 次 × 64 MB ≈ 5 GB     ★ 且是 80 次【阻塞式】集合通信
      PP：每卡 2 × 64 MB = 128 MB              ★ 且是 2 次【异步】P2P

      ⟹ 通信量差 ~40 倍，同步次数差 40 倍，★★ 相乘就是几百倍的敏感度差距
```

#### ★ PP 放最外层：§12.3 没说透的三个理由

§12.3 Takeaway #1 讲的是"TP 通信太密集，**不能**跨机"。**★ 反过来问：为什么 PP 特别【适合】被推到慢网络上？**

```
    ① 它的通信量与模型多深【无关】
       80 层切 4 段，边界永远只有 3 个 —— ★ 层数翻倍，PP 通信量不变。
       而 TP 每层都通信，层数翻倍它就翻倍。

    ② 它是 P2P，不是集合通信
       集合通信要求全组同步就位，一个慢的拖垮全组；
       ★ P2P 只需上下游【两方】就绪，对跨机网络的抖动宽容得多。

    ③ ★★ 最关键：PP 的主要成本压根不是带宽，是气泡 ★★
       气泡率 = (p−1)/m（[07 章](07-流水线并行PP.md)）
       ★ 这个数字和网速【一点关系都没有】。
       ⟹ 把 PP 挪到慢网络上，它最大的那块开销纹丝不动。
```

> ✅ Zero Bubble 论文（[03 章](03-通信原语.md)引过同一句）说的就是这件事：*"PP is particularly advantageous for utilizing **cross-server connections**, especially at the scale of thousands of GPUs"*

#### 那 DP 为什么在中间，不在最外？

```
    ★ 因为 DP 的通信量是三者里【最大】的（整份梯度，GB 量级）。
      "能和反向重叠"只藏得住【延迟】，藏不住【带宽】——
      ★ 带宽不够时，反向都算完了梯度还没传完，照样卡住。

    对比两种排布下 DP 组的落位（还是 16 卡 TP=2/PP=4）：

      tp-cp-ep-dp-pp（默认）    DP 组 = [g0,g2]  步长 2  → ★ 机内，走 NVLink ✅
      tp-cp-ep-pp-dp（反过来）  DP 组 = [g0,g8]  步长 8  →   跨机，走 IB     ❌

    ⟹ ★★ 一句话：TP 抢最快的线，DP 抢剩下最快的，PP 拿最慢的那条 ★★
```

```
    ⚠️ 当 TP × DP > 单节点卡数时，DP 无论如何都会跨机。Megatron 还有一层兜底：

      ✅ parallel_state.py 的 create_hierarchical_groups()
         把一个大 DP 组拆成【机内子组 + 机间子组】：
         先在机内用 NVLink 做 reduce-scatter，再跨机做一次小得多的 all-reduce。

      ★ DP 放中间正是这种分层拆分能成立的【前提】——
        如果 DP 组的 rank 是零散跳跃的，根本切不出干净的机内子组。
```

#### 想反过来？有开关，但基本用不上

```bash
--use-tp-pp-dp-mapping     # ✅ order 变成 "tp-cp-ep-pp-dp"（见 initialize.py）
                           #    DP 组 → [g0,g8]、[g1,g9]…（跨机）
                           #    PP 组 → [g0,g2,g4,g6]…（机内）
```

```
    ⚠️ 什么时候才该考虑（推断，论文和源码都没给建议）：
      · 序列极长 / micro-batch 很大 → 边界激活张量涨到几百 MB，PP 不再"轻"
      · 集群拓扑特殊：节点内卡很多，但节点间网络极弱

    ★ 标准 DGX / HGX 集群上不要动它 —— 默认的 tp-cp-ep-dp-pp 就是最优解。
```

## 12.9 本章小结

```
① ★ MFU = 6ΨT / (卡数 × 峰值算力 × 步时长)
   ★★ 分子【不含重计算】—— 所以开完全重计算 MFU 会掉
   📌 HFU 含重计算，衡量"硬件忙不忙"；MFU 衡量"忙得有没有意义"
   ✅ 标杆：Megatron-3 54.2%（530B/2240卡）、
      ⚠️ PTD-P 常被引作"52% MFU"——★ 那其实是 HFU，换算 MFU ≈39%（§12.2 订正）、
           MegaScale 55.2%（175B/12288卡）
   ★ 40~50% 是正常水位，>55% 算调得好

② ★★★ PTD-P 三条 Takeaway（本章的骨架）：
   #1 ✅ TP 开到单机卡数为止，再大用 PP 跨机
      → 因为 TP 每层 4 次 all-reduce 卡在计算路径上，
        而机内 NVLink 比机间 IB 快约 18 倍
      → ⚠️ 第二个病因常被忽略：TP 太大会把矩阵切碎，GPU 吃不饱
   #2 ✅ TP×PP 只开到"装得下"，剩下的卡全给 DP
      → TP/PP 是被迫开的，DP 才是想开的
      → ⚠️ 现代补充：能用 ZeRO-1 解决的就别动 TP/PP
   #3 ✅ 最优 micro-batch 没有公式，取决于 p、d、B 和模型本身
      → b↑ 则 GPU 效率↑（实测最高 1.3×）但气泡↑、显存↑

③ ★ 调参顺序：免费项全开 → TP(≤单机) → PP(最小) → CP(仅长序列)
   → DP(剩下全部) → 扫 b → 才轮到真取舍（重计算/FP8）

④ ✅ MegaScale Table 3 是最好的教材：47.7% → 65.3%
   ★ 其中 TP/PP/DP 三个 overlap 贡献约 4 个百分点，且【完全免费】
   ⚠️ 但 PTB/SWA/LAMB 那几行动了模型，不能无脑抄

⑤ overlap 的本质：总时间从【计算+通信】变成【max(计算,通信)】

⑥ MFU 低的排查顺序：TP 跨机 → 气泡 → 重计算过度 → overlap 漏开
   → 矩阵切太碎(hidden/TP ≥ 1024) → 数据管道 → 慢卡

⑦ 自动并行（Alpa 分两层搜 / GSPMD 传播标注）技术上可行，
   ⚠️ 但工业界仍手工配：搜索有成本、手工解够好、生产要可解释

⑧ ★★ rank 排布顺序 = TP → CP → EP → DP → PP（由内到外）★★
   ✅ 源码常量 order = "tp-cp-ep-dp-pp"
   ★ 易错：DP 在【中间】，PP 在【最外】，不是 TP→PP→DP
   → 组内步长：TP=1 ｜ DP=TP ｜ PP=TP×DP
     （04 章"g0 和 g2 一组"的步长 2，就是这么来的）
   → 排序依据是【通信敏感度】，rank 内外 = 链路快慢：
     TP 每层 4 次阻塞通信，躲不掉 → 抢机内 NVLink
     DP 量最大但可与反向重叠   → 中间，尽量留机内
     ★ PP 主要成本是气泡(p−1)/m 而非带宽 → 丢给跨机慢网络最划算
```
