# 14 · RL 训练框架：为什么需要另一套

> **前十三章讲的都是【预训练】：数据是现成的，喂进去、算 loss、更新。这一章讲一件形状完全不同的事。**
> 读完你应该能回答：RL 训练比预训练多了什么？**为什么"生成"这一步会把整套系统的假设推翻**？什么是 single-controller 和 multi-controller，为什么要混着用？以及**"训练和推理用不同并行度"这个矛盾怎么解**？

---

## 14.1 先看清楚形状的不同

```
    ┌─ 预训练（前十三章）───────────────────────────────┐
    │                                                    │
    │   固定的数据集  →  模型  →  loss  →  更新           │
    │                                                    │
    │   ★ 只有【一个】模型                                │
    │   ★ 数据是【死】的，训练前就全部准备好了            │
    │   ★ 每一步的形状完全相同 → 好切、好排、好预测        │
    └────────────────────────────────────────────────────┘

    ┌─ RL 训练 ─────────────────────────────────────────┐
    │                                                    │
    │   题目 → ★【模型自己生成答案】→ 打分 → 用分数更新    │
    │                ↑ 这一步是新的，也是全部麻烦的来源     │
    │                                                    │
    │   ★★ 有【好几个】模型同时在场                       │
    │   ★★ 数据是【模型自己造】的，每一步都不一样          │
    │   ★★ 生成的长度不定 → ★ 形状不固定                   │
    └────────────────────────────────────────────────────┘
```

> 📌 **RL** = **R**einforcement **L**earning，强化学习。**一句话：不给标准答案，只给一个"你做得好不好"的分数，让模型自己摸索。**
> 📌 **RLHF** = **R**einforcement **L**earning from **H**uman **F**eedback，基于人类反馈的强化学习。**分数来自人类偏好（或者一个学人类偏好训出来的模型）。**

---

## 14.2 ★ 场上有几个模型

**以最经典的 PPO 为例。**✅ HybridFlow 论文（[papers/HybridFlow-veRL-...-2409.19256.pdf](../papers/HybridFlow-veRL-RLHF-Framework-arXiv-2409.19256.pdf)）的描述：*"An RLHF system typically consists of **multiple models, e.g., an actor, a critic, a reference policy, and one or multiple reward models**."*

```
    ┌──────────────────────────────────────────────────────────┐
    │  ① actor      正在被训练的模型      ★ 要训练 → 要优化器状态 │
    │  ② critic     估计"这一步值多少分"  ★ 要训练 → 要优化器状态 │
    │  ③ reference  训练开始前的模型快照   只前向，★ 参数冻结     │
    │  ④ reward     打分模型              只前向，★ 参数冻结     │
    └──────────────────────────────────────────────────────────┘

    ★★ 显存账瞬间变了（回忆 [02 章](02-显存去哪了.md) 的 16 字节/参数）：
      actor    ：16 Ψ 字节（全套）
      critic   ：16 Ψ 字节（全套）
      reference： 2 Ψ 字节（只要 BF16 权重）
      reward   ： 2 Ψ 字节
      ─────────────────────────────
      ★ 合计约 36 Ψ 字节 —— 是预训练的 2.25 倍
```

> 📌 **为什么需要 reference（参考模型）**：防止模型为了拿高分而"跑偏"（比如学会输出讨好打分器的怪话）。**做法是在 loss 里加一项惩罚，罚"你离出发时的自己有多远"。★ 所以必须留一份出发时的快照。**

```
    ⚠️ 注意：现在的很多算法（GRPO 等）会去掉 critic，
       用一组采样的平均分当基线 → ★ 省掉整整 16Ψ
       这也是它们流行的一个重要工程原因。
```

## 14.3 ★★★ 真正的麻烦：生成和训练是两种完全不同的负载

**这一节是整章的核心。**

```
    ┌─ 阶段 ① 生成（rollout）────────────────────────────┐
    │  给 1024 道题，让 actor 每题写 512 个 token         │
    │                                                     │
    │  ★ 这是【推理】：一个 token 一个 token 地吐          │
    │  ★★ 访存受限（memory-bound）—— 每吐一个 token       │
    │     都要把整个模型的权重读一遍                       │
    │  ★ 需要 KV cache、需要 continuous batching          │
    │  ★ 长度不定：有的题答 50 token，有的答满 512         │
    └─────────────────────────────────────────────────────┘

    ┌─ 阶段 ② 训练 ──────────────────────────────────────┐
    │  把生成的结果打包，算 loss，反向，更新               │
    │                                                     │
    │  ★ 这是【训练】：一次处理整条序列                    │
    │  ★★ 算力受限（compute-bound）—— 大矩阵乘             │
    │  ★ 需要优化器状态、需要梯度、需要重计算              │
    └─────────────────────────────────────────────────────┘

    ★★★ 同一个 actor 模型，在两个阶段里的【最优并行策略完全不同】★★★
```

```
    ★ 为什么最优策略不同（这是关键）：

      生成阶段：访存受限 → ★ 希望 TP 大一点
                （TP 大 → 每张卡只需读 1/TP 的权重 → 吐字更快）
                但不需要优化器状态，显存压力小

      训练阶段：算力受限 → ★ 希望 TP 小一点
                （回忆 [12 章](12-并行策略组合与MFU.md) Takeaway #1：
                 TP 大会把矩阵切碎、通信变多）
                但需要 16Ψ 显存，压力大

    ⟹ ★★ 于是出现一个预训练里从不存在的需求：
       ★★★【同一个模型的参数，要在两种切分方式之间来回搬】★★★
       这就是 "resharding"（重新分片）。
```

## 14.4 ✅ HybridFlow / veRL 的两个核心设计

### 设计一：单控制器 + 多控制器混合

**先解释这两个词。**

```
    ┌─ multi-controller（多控制器）───────────────────────┐
    │  ★ 每张卡跑【同一份代码】，各自根据 rank 决定干什么   │
    │  → 这就是 Megatron / PyTorch DDP 的模式（SPMD）      │
    │                                                      │
    │  ✅ 快：没有中心节点发号施令，没有调度开销            │
    │  ❌ 死板：要表达"A 模型算完把结果给 B 模型"这种        │
    │     跨模型的复杂流程，代码会变得极其难写              │
    └──────────────────────────────────────────────────────┘

    ┌─ single-controller（单控制器）──────────────────────┐
    │  ★ 一个中心进程发号施令："你算这个，你把结果给他"     │
    │  → 传统 RL 框架（RLlib 等）的模式                    │
    │                                                      │
    │  ✅ 灵活：整个数据流写成一个 for 循环，一眼看懂        │
    │  ❌ 慢：★ 每一个算子都要中心节点下发指令              │
    │     —— LLM 有【几十亿个算子】，调度开销压垮一切        │
    └──────────────────────────────────────────────────────┘
```

> ✅ 论文对这个困境的诊断：*"In the RLHF dataflow, each node corresponds to an LLM with **up to billions of operators**, computed using some complex parallelism. **A single-controller paradigm is inefficient**"*；而多控制器 *"can be **inflexible** due to nesting distributed computation and data communication"*。

> ✅ **HybridFlow 的解法（这是全章最漂亮的一个设计）**：
> *"Our key observation is that utilizing the **single-controller paradigm on the inter-node level** enables **flexible expression of various data dependencies** and easy coordination of inter-node data resharding with minimal overhead, while integrating the **multi-controller paradigm within intra-node computation** enhances **computation efficiency** substantially."*

```
    ★★★ 一句话：★【大处用单控制器，小处用多控制器】★ ★★★

    ┌────────────────────────────────────────────────────┐
    │  模型【之间】的编排  →  单控制器                     │
    │    "actor 生成 → reward 打分 → actor 训练"          │
    │    ★ 只有几十个节点，调度开销可以忽略                │
    │    ★ 换个 RL 算法只要改这几行                        │
    │                                                     │
    │  模型【内部】的计算  →  多控制器（SPMD）             │
    │    每个模型内部照旧用 Megatron/FSDP 的方式跑         │
    │    ★ 几十亿算子，一个指令都不用中心节点管            │
    └────────────────────────────────────────────────────┘

    🔑 ★ 这个思路值得记住，它是一个通用的系统设计模式：
       ★★【在"变化多但数量少"的层面要灵活，
           在"变化少但数量多"的层面要高效】★★
```

### 设计二：3D-HybridEngine 解决 resharding

> ✅ *"We further design a **3D-HybridEngine** for efficient **actor model resharding between training and generation phases**, with **zero memory redundancy** and significantly reduced communication overhead."*

```
    ★ 朴素做法（"零冗余"要解决的问题）：
      在显存里同时放【训练版切分】和【生成版切分】两份参数
      → ⚠️ 参数占用直接翻倍

    ★★ 3D-HybridEngine 的目标：不留第二份，
       在两种切分之间原地转换，并把通信量压到最小。
```

✅ **总成绩**：*"Our experimental results demonstrate **1.53×∼20.57× throughput improvement**"*。

```
    ⚠️ 注意这个区间跨度非常大（1.5 倍到 20 倍）。
    ★ 我的解读：提升多少完全取决于基线在哪个环节被卡住 ——
      如果基线的瓶颈正好是 resharding 或者模型放置不合理，
      提升就极大；如果基线已经调好了，提升就是那 1.53×。
      ⚠️ 看到这类跨度极大的加速比时，要去正文找【是哪个配置下的】。
```

## 14.5 ★ 一个绕不开的问题：训练引擎和推理引擎不是同一套代码

```
    ★ 生成阶段，你会想用 vLLM / SGLang（推理引擎）：
      它们有 PagedAttention、continuous batching，比训练框架的
      朴素生成快【一个数量级】

    ★ 训练阶段，你要用 Megatron / FSDP：
      它们有优化器、有反向、有并行策略

    ⟹ ★★ 于是同一个模型的权重，要在【两个不同的框架】之间来回搬。
```

```
    ⚠️ 这带来一个非常隐蔽、但在实践中反复出现的问题：

    ★★★ 训练引擎和推理引擎算出来的概率【不完全一样】★★★

      为什么？—— 📌 回忆 [13 章 §13.7](13-断点续训与容错.md)：
        ① 浮点加法不满足结合律
        ② 两套框架用的 kernel 实现不同、切分方式不同、
           batch 组织方式不同 → 规约顺序不同

    ⚠️ 后果：RL 算法里要算"这个 token 在旧策略下的概率"。
       如果生成时算的概率和训练时算的概率对不上，
       ★ 重要性采样比值就带上了系统误差 → 训练可能不稳。

    ⟹ ★ 这就是为什么"训推一致性"在 RL 时代突然变成一个热门工程问题。
       在纯预训练时代，它只是个学术洁癖；在 RL 里，它影响收敛。
```

## 14.6 ⚠️ 还有一个纯工程的痛点：长尾

```
    一批 1024 道题同时生成：

      大多数题：答 100 个 token 就结束了  ████
      少数几题：一直答到 4096 上限        ████████████████████████

    ★★ 而这一批必须【全部结束】才能进入训练阶段
    → ★ 整批的耗时 = 最长的那一条
    → ⚠️ GPU 利用率在生成阶段的后半段断崖式下跌
```

```
    ★ 这和 [13 章](13-断点续训与容错.md) 的慢卡是【同一个病】：
      同步屏障 + 负载不均 = 全场等最慢的。

    ★ 常见缓解手段（⚠️ 我的归纳，非某一篇论文的结论）：
      ① 生成和训练【流水化】：先完成的样本先送去训练
      ② 把长度相近的样本编在一批
      ③ 设置更激进的截断长度
```

## 14.7 挂回真实框架

| 框架 | 定位 | 特点 |
|---|---|---|
| **veRL**（HybridFlow） | ★ 目前最主流的开源 RL 训练框架 | ✅ 单/多控制器混合 + 3D-HybridEngine |
| **OpenRLHF** | 基于 Ray + DeepSpeed | 上手快，架构更直白 |
| **NeMo-Aligner** | NVIDIA 栈 | 和 Megatron 深度绑定 |
| **VeOmni** | 多模态训练框架 | ⚠️ RL 能力仍在演进（README 列为"upcoming"，路线是**接入 veRL**） |

```
    ★ 从模块看它们的共同结构（读任何一个 RL 框架都可以按这个找）：
      ① 一个 rollout / generation 模块      → 接推理引擎
      ② 一个 trainer 模块                   → 接训练引擎
      ③ ★ 一个 resharding / weight-sync 模块 → §14.4 的核心
      ④ 一个 controller / trainer loop      → §14.4 的单控制器那一层
      ⑤ 一个 replay buffer / 数据流模块
```

## 14.8 本章小结

```
① ★ RL 与预训练的形状差异：多了【生成】这一步
   → 场上有 4 个模型（actor/critic/reference/reward）
   → ★ 显存约 36Ψ 字节，是预训练 16Ψ 的 2.25 倍
   ⚠️ 去掉 critic 的算法（GRPO 等）省掉整整 16Ψ，
      这是它们流行的一个重要工程原因

② ★★★ 核心矛盾：生成是【访存受限的推理】，训练是【算力受限的训练】
   → 同一个 actor，两个阶段的最优并行策略【相反】
     （生成想 TP 大以摊薄权重读取；训练想 TP 小以免切碎矩阵）
   ⟹ 产生预训练里不存在的需求：★ resharding（参数在两种切法间搬）

③ ✅ HybridFlow 的两个设计：
   ★★ 混合控制器：模型【之间】用单控制器（灵活，节点少）
                   模型【内部】用多控制器 SPMD（高效，算子多）
      ✅ 原文："single-controller on the inter-node level...
              multi-controller within intra-node computation"
      🔑 通用模式：变化多但数量少的层面要灵活，
                   变化少但数量多的层面要高效
   ★ 3D-HybridEngine：resharding 做到【零显存冗余】
   ✅ 总成绩 1.53×~20.57×
      ⚠️ 区间跨度极大 → 看这类数字务必回正文查是哪个配置

④ ★ 生成用推理引擎（vLLM/SGLang）、训练用训练引擎（Megatron/FSDP）
   ⚠️ 两套代码算出的概率对不上（浮点结合律 + kernel/切分不同）
   → ★★ "训推一致性"从学术洁癖变成影响收敛的工程问题

⑤ ⚠️ 长尾：一批里最长的那条决定整批耗时
   ★ 和 [13 章](13-断点续训与容错.md)的慢卡同病：同步屏障 + 负载不均

⑥ ★ 任何 RL 框架都能拆成 5 块：rollout / trainer /
   ★ resharding / controller loop / replay buffer
```
