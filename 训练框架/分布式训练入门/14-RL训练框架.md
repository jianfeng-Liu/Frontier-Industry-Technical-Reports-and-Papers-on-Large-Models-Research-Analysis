# 14 · RL 训练框架：为什么需要另一套

> **前十三章讲的都是【预训练】：数据是现成的，喂进去、算 loss、更新。这一章讲一件形状完全不同的事。**
> 读完你应该能回答：RL 训练比预训练多了什么？**为什么"生成"这一步会把整套系统的假设推翻**？**一次 RL 迭代的时间到底花在哪里——是花在反向传播上吗**？什么是 single-controller 和 multi-controller，为什么要混着用？以及**"训练和推理用不同并行度"这个矛盾怎么解**？

---

## 14.1 先看清楚形状的不同

**两种训练的骨架对比**：

| | 预训练（前十三章） | RL 训练（本章） |
|---|---|---|
| 数据从哪来 | ★ 固定数据集，训练前就全部准备好 | ★★ **模型自己生成**，每一步都不一样 |
| 场上有几个模型 | ★ 只有一个 | ★★ 好几个（§14.2） |
| 每一步的形状 | ★ 完全相同 → 好切、好排、好预测 | ★★ 生成长度不定 → **形状不固定** |
| 一步里有几种负载 | 一种（训练） | ★★★ 两种（生成 + 训练），而且**要求相反**（§14.3） |
| 瓶颈在哪 | 反向传播（算力受限） | ★★ **生成**（访存受限），不是反向传播（§14.3.4） |

**画成流程就是这样**：

```
    预训练 —— 一条直线，一种负载

      固定数据集  →  模型  →  loss  →  更新


    RL 训练 —— 一个闭环，两种负载

      ① 题目（从数据集取）
      ② ★ 模型自己生成答案（rollout）    ← ★★ 这一步是新的，也是全部麻烦的来源
      ③ 打分（reward）
      ④ 算优势（advantage）
      ⑤ 用优势更新模型
      ⑥ ★★ 把新权重搬回生成引擎  →  回到 ②
```

> 📖 **RL** = **R**einforcement **L**earning，强化学习。**一句话：不给标准答案，只给一个"你做得好不好"的分数，让模型自己摸索。**
> 📖 **RLHF** = **R**einforcement **L**earning from **H**uman **F**eedback，基于人类反馈的强化学习。**分数来自人类偏好（或者一个学人类偏好训出来的模型）。**
> 📖 **rollout**（中文常直接叫"rollout"或"采样/生成"）：让当前模型对一批题目生成答案的那个阶段。**★ 本章后面反复出现的就是这个词。**

## 14.2 ★ 场上有几个模型，数据怎么在它们之间流

### 14.2.1 四个模型

**以最经典的 PPO 为例。**✅ HybridFlow 论文（[papers/HybridFlow-veRL-...-2409.19256.pdf](../papers/HybridFlow-veRL-RLHF-Framework-arXiv-2409.19256.pdf)）的描述：*"An RLHF system typically consists of **multiple models, e.g., an actor, a critic, a reference policy, and one or multiple reward models**."*

| # | 模型 | 干什么 | 要不要训练 | 显存开销 |
|---|---|---|---|---|
| ① | **actor** | 正在被训练的模型，负责生成答案 | ✅ 要 | ★ 全套 16 字节/参数 |
| ② | **critic** | 估计"从这个状态出发大概能拿多少分" | ✅ 要 | ★ 全套 16 字节/参数 |
| ③ | **reference** | 训练开始前的模型快照 | ❌ 只前向，参数冻结 | 2 字节/参数 |
| ④ | **reward** | 打分模型 | ❌ 只前向，参数冻结 | 2 字节/参数 |

> 📖 **PPO** = **P**roximal **P**olicy **O**ptimization，近端策略优化，最经典的 RL 算法。
> 📖 **GRPO** = **G**roup **R**elative **P**olicy **O**ptimization，组相对策略优化。**★ 它的关键工程差别是【不要 critic】**——同一道题采 G 条答案，用这 G 条的平均分当基线，替代 critic 的作用。
> 📌 **为什么需要 reference（参考模型）**：防止模型为了拿高分而"跑偏"（比如学会输出讨好打分器的怪话）。**做法是在 loss 里加一项惩罚，罚"你离出发时的自己有多远"。★ 所以必须留一份出发时的快照。**

### 14.2.2 ★★ 显存账：从 16 字节/参数变成 36 字节/参数

**先把"16 字节/参数"这个口径拆开**（[02 章](02-显存去哪了.md) 的那张表）：

| 内容 | 精度 | 字节/参数 | 70B 模型 |
|---|---|---|---|
| 权重 | BF16 | 2 | 140 GB |
| 梯度 | BF16 | 2 | 140 GB |
| FP32 主权重 | FP32 | 4 | 280 GB |
| Adam **m**（一阶动量） | FP32 | 4 | **280 GB** |
| Adam **v**（二阶动量） | FP32 | 4 | **280 GB** |
| **训练态合计** | | **16** | **1120 GB** |

```
    ⚠️ 这里最容易错的一处：m 和 v 是【两个】各 4 字节/参数的 FP32 张量。
       70B 下【各】280 GB，两个加起来 560 GB，不是 280 GB。
       ★ 记"16 字节/参数"这个口径，比记任何具体 GB 数都有用 —— 换模型直接乘。
```

**四个模型各自套上这个口径**：

| 角色 | 字节/参数 | 8B 模型 | 70B 模型 |
|---|---|---|---|
| ① actor（训练态） | 16 | 128 GB | **1120 GB** |
| ② critic（训练态，**只有 PPO 需要**） | 16 | 128 GB | **1120 GB** |
| ③ reference（冻结） | 2 | 16 GB | 140 GB |
| ④ reward（冻结，假设同尺寸） | 2 | 16 GB | 140 GB |
| **四个模型合计** | **★ 36** | **288 GB** | **2520 GB** |
| （对照）预训练只有一个模型 | 16 | 128 GB | 1120 GB |
| **倍数** | **★ 2.25×** | | |

```
    ⚠️ 上表还漏了一项：Rollout 引擎（vLLM / SGLang）自己那份 BF16 权重副本。
       它和 actor 的训练态副本是【两份不同布局的东西】，不能共用。
       ＋2 字节/参数：8B → 16 GB，70B → 140 GB

    ★ 补全后的真实账：
      PPO  合计 38 字节/参数 → 8B: 304 GB   70B: 2660 GB
      GRPO 合计 22 字节/参数 → 8B: 176 GB   70B: 1540 GB   ← 去掉 critic 的 16

    ★★ 一张 H100 是 80 GB，单机 8 卡 = 640 GB：
      8B  + GRPO：176 GB（27.5%）→ 剩 464 GB 给激活和 KV Cache   ✓ 宽裕
      8B  + PPO ：304 GB（47.5%）→ 剩 336 GB                     ✓ 够用
      70B + GRPO：1540 GB → 光放状态就要 ⌈1540/80⌉ = 20 张卡，实际 32 张起
      70B + PPO ：2660 GB → 光放状态就要 34 张卡，实际 48 张起
```

> ★ **critic 是 PPO 最贵的一件行李**：它和 actor 一样重，等于把训练态显存需求翻倍。**⚠️ 现在流行的 GRPO 等算法去掉 critic，省掉整整 16 字节/参数（70B 下是 1120 GB）——★★ 这才是它们在大模型上迅速普及的第一位工程原因**，advantage 公式变简单只是副产品。这笔账在 [强化学习训练框架 §5.1](../../强化学习训练框架/05-算法与框架的接口.md) 里还有算法侧的另一半。

### 14.2.3 ★★★ 一次迭代的数据流：谁在哪张卡上跑，搬什么

**先定一套具体配置，后面每个数字都从它推出来。★ 这套配置和 [大模型算子开发 §10.1.1](../../大模型算子开发/10-RL算子.md) 完全一致，两边的数字可以逐格对上。**

```
模型     LLaMA-3-8B（Ψ = 8.0 × 10⁹ 参数），BF16
         32 层，隐藏维度 h = 4096，32 个 Q head / 8 个 KV head（GQA），head_dim = 128
         → 权重 = 8.0×10⁹ × 2 字节 = ★ 16 GB
         → KV Cache 每 token = 2(K和V) × 8 head × 128 × 2 字节 × 32 层 = 128 KB

硬件     8 × H100 SXM5
         BF16 稠密峰值 989 TFLOP/s（⚠️ 1979 是稀疏值，稠密训练用不上）
         HBM3 80 GB / 3.35 TB/s
         机内 NVLink 900 GB/s 是【双向聚合】→ 单向 450 GB/s
         机间 InfiniBand 400 Gb/s ÷ 8 = 50 GB/s

算法     GRPO，带 KL 惩罚（所以保留 reference）
         每次迭代 B = 64 道题，每题采 G = 8 条答案 → 512 条序列
         题目长 512 token，答案长度上限 4096 token
```

> 📖 **GQA** = **G**rouped-**Q**uery **A**ttention，分组查询注意力。**多个 Q head 共用一组 K/V head，KV Cache 因此小一大截**（本例 32 个 Q head 只配 8 个 KV head，KV Cache 缩到四分之一）。
> 📖 **Prefill / Decode**：把题目一次性读进去、并行算出所有 K/V 的阶段叫 **Prefill**（预填充）；之后一个 token 一个 token 往外吐的阶段叫 **Decode**（解码）。**★ 两者的性能特征完全不同**，见 [推理框架 · 推理优化入门 03](../../推理框架/推理优化入门/03-Prefill与Decode两阶段.md)。

**一次迭代的九个步骤**：

| 步骤 | 在哪里跑 | 搬进来什么 | 产出什么 |
|---|---|---|---|
| ① 取题目 | CPU / 数据集 | 64 道题 | 复制成 512 条 |
| ② Prefill（把题目读进去） | Rollout 卡组（8 卡） | 512 × 512 个 token | 512 份 KV Cache |
| ③ Decode × 最多 4096 步 | Rollout 卡组 | 上一步吐的 token | 答案 token + `logp_old` |
| ④ 打分 | CPU 验证器（或 reward 模型） | 512 条答案的文本 | 512 个 reward |
| ⑤ 优势估计（组内归一化） | CPU 或任一张卡 | 512 个 reward | 512 个 advantage |
| ⑥ reference 前向 | Train 卡组（8 卡） | 512 × 约 1792 个 token | `logp_ref` |
| ⑦ 重新前向 + 反向 | Train 卡组 | 同上 + advantage | 梯度 |
| ⑧ AdamW 更新 | Train 卡组 | 梯度 + 优化器状态 | 新权重 |
| ⑨ **权重同步** | **Train → Rollout** | **新权重 16 GB** | Rollout 引擎刷新 |

**把它按时间轴摊开，"谁在等谁"就一目了然了**：

```
    时间 ─────────────────────────────────────────────────────────────→

    Rollout 卡组  ██████████████████████████  ....................  ████
                  ②③ Decode（最多 4096 步）    空转（等新权重）     下一轮

    Train 卡组    ..........................  ██████████████████  ......
                  空  转（等  数  据）            ⑥⑦⑧ 前向反向更新    空转

    CPU           ..........................  ██  ....................
                                               ④⑤ 打分 + 优势估计

    权重通路      ..............................................  ══>  ⑨

      █ = 在干活      . = 空转      ══> = 搬权重

    ★★ 两条泳道从不重叠：Rollout 跑的时候训练卡闲着，
       训练跑的时候 Rollout 卡闲着。
```

> ★ **这张图就是整个 RL 工程的核心矛盾**。预训练只有一条泳道，从头到尾在干同一件事；RL 有两条互相等待的泳道，**而且两边要的东西完全相反**——Rollout 要低延迟、大 KV Cache、小显存占用；训练要高算力利用率、大激活存储、全套优化器状态。§14.3 讲这个"相反"到底反在哪，§14.6 讲那两块"空转"怎么治。

### 14.2.4 ⚠️ 一个反直觉的数字：上行 3 MB，下行 16 GB

**很多人第一次看 RL 架构图，会以为"rollout 产出的一大堆 token 和概率"是通信大头。算一下就知道完全不是**：

| 方向 | 内容 | 大小 |
|---|---|---|
| Rollout → Train（上行） | `token_ids`：512 × 1024 个 int32 | 2.10 MB |
| Rollout → Train（上行） | `logp_old`：512 × 512 个 float32 | 1.05 MB |
| Rollout → Train（上行） | `reward`：512 个 float32 | 2 KB |
| | **上行合计** | **≈ 3.2 MB** |
| **Train → Rollout（下行）** | **新权重（8B，BF16）** | **★★ 16 GB** |

```
    下行 ÷ 上行 = 16 GB ÷ 3.2 MB ≈ ★ 5000 倍
```

> ★ **RL 的通信量几乎全在"把新权重送回生成引擎"这一步上**，而不是在采样结果上。这解释了为什么 RL 框架的设计文档里"权重怎么同步"永远是头几章，而"采样结果怎么传"从来不是问题。**⚠️ 但注意："通信量最大"不等于"耗时占比最大"——§14.3.4 会看到权重同步的耗时占比只有百分之零点几。** 权重同步的完整横向对照（七档传输层、六个 checkpoint engine、四条通路）在 [强化学习训练框架 · 03 权重同步](../../强化学习训练框架/03-权重同步.md)。

## 14.3 ★★★ 真正的麻烦：生成和训练是两种完全不同的负载

**这一节是整章的核心。**

### 14.3.1 两个阶段，两套要求

| | 阶段 ① 生成（rollout） | 阶段 ② 训练 |
|---|---|---|
| 在做什么 | 64 道题 × 每题 8 条 = 512 条序列，每条最多写 4096 个 token | 把生成的结果打包，算 loss，反向，更新 |
| 本质是 | ★ **推理**：一个 token 一个 token 地吐 | ★ **训练**：一次处理整条序列 |
| 卡在哪 | ★★ **访存受限**（Memory Bound）——每吐一个 token 都要把整个模型的权重读一遍 | ★★ **算力受限**（Compute Bound）——大矩阵乘 |
| 需要什么 | KV Cache、continuous batching、PagedAttention | 优化器状态、梯度、重计算 |
| 形状 | ★ **长度不定**：有的题答 50 token，有的答满 4096 | ★ 打包后形状固定 |
| 希望 TP 大还是小 | ★ **大**（每卡少读点权重，吐字更快） | ★ **小**（TP 大会把矩阵切碎、通信变多） |

> 📖 **TP** = **T**ensor **P**arallelism，张量并行，见 [06 章](06-张量并行TP.md)。
> 📖 **KV Cache**：自回归生成时，前面每个 token 算出来的 Key/Value 存下来复用，避免每吐一个字都重算整条前缀。
> 📖 **continuous batching**（连续批处理）：一条序列生成完就立刻把新请求塞进这个批次，让批次大小保持满载。**⚠️ 这一招在 RL 的 rollout 里用不上，原因见 §14.6.1。**
> 📖 **PagedAttention**（分页注意力）：像操作系统管内存那样，按固定大小的"页"给 KV Cache 按需分配，不为"万一答满 4096"预留整块。**★ 这两项都出自推理引擎，完整讲解见 [推理框架 · 推理优化入门](../../推理框架/推理优化入门/README.md)。**

### 14.3.2 ⚠️ "生成阶段 GPU 利用率低"——先说清楚是哪个利用率

**这是 RL 讨论里最常被说错的一句话，必须先钉死口径。**

```
    ★ 生成阶段的算术强度（每读 1 字节权重能做几次浮点运算）：

      batch 里有 b 条序列同时在吐字，那么读一遍 16 GB 权重，
      能顺带为这 b 条序列各算一次前向：

        算术强度 = 2·Ψ·b FLOP ÷ 2·Ψ 字节 = ★ b FLOP/字节

      H100 SXM5 的分界点（ridge point）：
        989 × 10¹² FLOP/s ÷ 3.35 × 10¹² 字节/s = ★★ 295 FLOP/字节
```

| batch 里同时活着几条 | 算术强度 | 和 295 比 | 结论 |
|---|---|---|---|
| 1 | 1 | 远小于 | 极度访存受限 |
| 64 | 64 | 小于 | ★ 访存受限 |
| 256 | 256 | 接近 | 临界 |
| 512 | 512 | 大于 | 转为算力受限 |

```
    ⟹ ★★★ RL 的 rollout 通常跑在几十到几百条并发上，
       算术强度 < 295 → ★【算力利用率低是物理规律，不是浪费】★

    ⚠️ 三个必须分清的口径（和 13 章 §13.5.2 是同一张表）：

      ① nvidia-smi 的 utilization.gpu  → 生成阶段【接近 100%】，因为一直有 kernel 在跑
      ② 算力利用率（MFU）              → 生成阶段【只有个位数】，这是定义决定的
      ③ HBM 带宽利用率                 → 生成阶段【接近 100%】，kernel 已经写到头了

    ★★ 所以"rollout 的 GPU 利用率只有 5%，太浪费了"这句话是【口径不清】：
       它说的是 ②，而 ② 低恰恰说明 kernel 写对了（该卡在带宽上就卡在带宽上）。
       ⟹ ★ rollout 真正的浪费【不在这里】，在 §14.6 的长尾。
```

> 📖 **MFU** = **M**odel **FLOPs **U**tilization，模型算力利用率 = 模型必须做的浮点运算 ÷ 硬件理论上能做的浮点运算，见 [12 章 §12.2](12-并行策略组合与MFU.md)。
> 📖 **FLOP / PFLOP / TFLOP/s**：**FLOP** = 浮点运算次数；**P** = 10¹⁵（peta），**T** = 10¹²（tera）。**⚠️ 带 `/s` 的是"每秒"，不带的是"总次数"，论文里经常混用，按上下文判断。**
> 📖 **Memory Bound / Compute Bound**（访存受限 / 算力受限）：一个算子的算术强度低于硬件的 ridge point（分界点）时，它的速度由显存带宽决定，算力必然用不满。**★ 这是屋顶线模型（Roofline）的基本结论**，完整讲解见 [大模型算子开发 · 02 屋顶线与性能剖析](../../大模型算子开发/02-屋顶线与性能剖析.md)。

### 14.3.3 ★★ 于是出现一个预训练里从不存在的需求

```
    生成阶段：访存受限 → ★ 希望 TP 大一点
              （TP 大 → 每张卡只需读 1/TP 的权重 → 吐字更快）
              但不需要优化器状态，显存压力小

    训练阶段：算力受限 → ★ 希望 TP 小一点
              （回忆 12 章 Takeaway #1：TP 大会把矩阵切碎、通信变多）
              但需要 16 字节/参数，显存压力大

    ⟹ ★★★【同一个模型的参数，要在两种切分方式之间来回搬】★★★
       这就是 "resharding"（重新分片）。§14.4 讲它怎么解。
```

> 📖 **resharding**（重新分片）：把同一份参数从一种并行切分布局，转换成另一种并行切分布局。**★ 预训练里只有"改并行度续训"时才会碰到（[13 章 §13.4](13-断点续训与容错.md)），而 RL 里【每一次迭代都要做一遍】。**

---

### 14.3.4 ★★★ 把耗时占比算出来：瓶颈在 rollout，不在反向传播

**"生成和训练是两种负载"到目前为止还只是定性的。下面把 §14.2.3 那套配置的一次迭代，逐项算成秒。★ 完整推导（包括 KV 读取量那 18.14 TB 是怎么来的）在 [大模型算子开发 §10.8](../../大模型算子开发/10-RL算子.md)，这里只搬结论和口径。**

**第一张表：理论下界**（假设 kernel 完美、调度零开销）

| 阶段 | 算什么 / 搬什么 | 怎么算 | 理论耗时 | 占比 |
|---|---|---|---|---|

```
       在理论下界那张表里，rollout 占 77.3%，比例反而更高。
```

**★ 权重同步到底占多少：四种部署，四个数量级**

|---|---|---|---|---|

```
       ★ 把 900 填进分母，算出来的同步耗时会小一半。

         (a) 每次迭代的 rollout 很短（小 batch、短答案 → 分母小了）

```

## 14.4 ✅ HybridFlow / veRL 的两个核心设计

### 14.4.1 设计一：单控制器 + 多控制器混合

**先解释这两个词。**

| | **multi-controller**（多控制器） | **single-controller**（单控制器） |
|---|---|---|
| 怎么跑 | ★ 每张卡跑**同一份代码**，各自根据 rank 决定干什么 | ★ 一个中心进程发号施令："你算这个，你把结果给他" |
| 谁在用 | Megatron / PyTorch DDP / FSDP（即 SPMD） | 传统 RL 框架（RLlib 等） |
| ✅ 优点 | **快**：没有中心节点发号施令，没有调度开销 | **灵活**：整个数据流写成一个 for 循环，一眼看懂 |
| ❌ 缺点 | **死板**：要表达"A 模型算完把结果给 B 模型"这类跨模型流程，代码极难写 | **慢**：★ 每一个算子都要中心节点下发指令——LLM 有【几十亿个算子】，调度开销压垮一切 |

> 📖 **SPMD** = **S**ingle **P**rogram **M**ultiple **D**ata，单程序多数据。**一份代码、每张卡跑自己那一份数据**，就是前十三章一直在用的模式。

> ✅ 论文对这个困境的诊断：*"In the RLHF dataflow, each node corresponds to an LLM with **up to billions of operators**, computed using some complex parallelism. **A single-controller paradigm is inefficient**"*；而多控制器 *"can be **inflexible** due to nesting distributed computation and data communication"*。

> ✅ **HybridFlow 的解法（这是全章最漂亮的一个设计）**：
> *"Our key observation is that utilizing the **single-controller paradigm on the inter-node level** enables **flexible expression of various data dependencies** and easy coordination of inter-node data resharding with minimal overhead, while integrating the **multi-controller paradigm within intra-node computation** enhances **computation efficiency** substantially."*

```
    ★★★ 一句话：★【大处用单控制器，小处用多控制器】★ ★★★

    模型【之间】的编排  →  单控制器
      "actor 生成 → reward 打分 → actor 训练"
      ★ 只有几十个节点，调度开销可以忽略
      ★ 换个 RL 算法只要改这几行
          │
          │  每个方框内部，进去之后换成另一套
          ▼
    模型【内部】的计算  →  多控制器（SPMD）
      每个模型内部照旧用 Megatron / FSDP 的方式跑
      ★ 几十亿算子，一个指令都不用中心节点管

    🔑 ★ 这个思路值得记住，它是一个通用的系统设计模式：
       ★★【在"变化多但数量少"的层面要灵活，
           在"变化少但数量多"的层面要高效】★★
```

| | 层面 | 数量级 | 变化频率 | 选哪种 |
|---|---|---|---|---|
| 外层 | 模型之间的编排 | 几十个节点 | ★ 换算法就变 | 单控制器（要灵活） |
| 内层 | 模型内部的算子 | ★★ 几十亿个 | 基本不变 | 多控制器（要高效） |

### 14.4.2 设计二：3D-HybridEngine 解决 resharding

> ✅ *"We further design a **3D-HybridEngine** for efficient **actor model resharding between training and generation phases**, with **zero memory redundancy** and significantly reduced communication overhead."*

```
    ★ 朴素做法（"零冗余"要解决的问题）：
      在显存里同时放【训练版切分】和【生成版切分】两份 actor 参数
      → ⚠️ 参数那一项直接翻倍（8B 下多占 16 GB，70B 下多占 140 GB）

    ★★ 3D-HybridEngine 的目标：不留第二份，
       在两种切分之间【原地】转换，并把转换时的通信量压到最小。

    ★ 为什么叫 3D：训练侧的切分是 TP × PP × DP 三个维度，
      生成侧是另一组 TP × PP × DP，
      它要做的是这两组三维网格之间的重映射。
```

✅ **总成绩**：*"Our experimental results demonstrate **1.53×∼20.57× throughput improvement**"*（✅ 已核对 arXiv 2409.19256 摘要原文）。

```
    ⚠️ 注意这个区间跨度非常大（1.53 倍到 20.57 倍，差 13 倍）。
    ★ 我的解读：提升多少完全取决于基线在哪个环节被卡住 ——
      如果基线的瓶颈正好是 resharding 或者模型放置不合理，提升就极大；
      如果基线已经调好了，提升就是那 1.53×。
      ⚠️ 看到这类跨度极大的加速比时，一定要去正文找【是哪个配置下的】。

    ⚠️ 再提醒一次 13 章 §13.6 那个读数陷阱：
      "1.53× 加速" = 时间减少 34.6%；"20.57× 加速" = 时间减少 95.1%。
      ★ 加速倍数 = 1 ÷ (1 − 时间减少比例)。两种说法别混着比。
```

## 14.5 ★ 一个绕不开的问题：训练引擎和推理引擎不是同一套代码

```
    ★ 生成阶段，你会想用 vLLM / SGLang（推理引擎）：
      它们有 PagedAttention、continuous batching，
      比训练框架里那套朴素的 generate() 快【一个数量级】

    ★ 训练阶段，你要用 Megatron / FSDP（训练引擎）：
      它们有优化器、有反向、有并行策略

    ⟹ ★★ 于是同一个模型的权重，要在【两个不同的框架】之间来回搬。
       —— 这就是 §14.2.3 步骤 ⑨ 那条"权重通路"。
```

```
    ⚠️ 这带来一个非常隐蔽、但在实践中反复出现的问题：

    ★★★ 训练引擎和推理引擎算出来的概率【不完全一样】★★★

      为什么？—— 📌 回忆 13 章 §13.7：
        ① 浮点加法不满足结合律
        ② 两套框架用的 kernel 实现不同、切分方式不同、
           batch 组织方式不同 → 归约顺序不同

    ⚠️ 后果：RL 算法里要算"这个 token 在旧策略下的概率" logp_old。
       ratio = exp(logp_new − logp_old)

       如果 logp_old 由【推理引擎】给出，而 logp_new 由【训练引擎】算出，
       ★ 这个 ratio 的偏离里就混进了【纯粹的系统误差】——
         它不是"策略变了"，是两套 kernel 算得不一样。
       ⟹ ★★ 重要性采样比值带上系统误差 → clip 会误伤 → 训练可能不稳。

    ⟹ ★ 这就是为什么"训推一致性"在 RL 时代突然变成一个热门工程问题。
       在纯预训练时代，它只是个学术洁癖；在 RL 里，它影响收敛。
```

> 📖 **ratio（重要性采样比值）**：`exp(logp_new − logp_old)`，衡量"新策略比旧策略更倾向于生成这个 token 多少倍"。PPO / GRPO 用它给梯度加权，并在它偏离 1 太远时做截断（clip）。
> 📖 **TITO** = **T**oken-**I**n-**T**oken-**O**ut，token 进 token 出。★ 生成侧吐出的 token id 直接喂给训练侧，**中途不要解码成文本再重新分词**——分词边界一变，两边算的就不是同一条序列了。这是训推一致里最便宜、最该先做的一条。

> **深入 →** 本章只讲到"为什么会不一致"。**这个问题的完整拆解——一次前向有多少次归约、几个 ULP 的误差怎么经过四级台阶放大成训练崩掉、batch 不变性是什么、五条对策各自的代价——在 [大模型算子开发 · 11 训推一致性算子层](../../大模型算子开发/11-训推一致性算子层.md)（算子/数值视角）和 [强化学习训练框架 · 04 训推一致性](../../强化学习训练框架/04-训推一致性.md)（五家自研系统各自怎么解）。★ 那两篇引用本节，不重写本节。**

## 14.6 ⚠️ 真正的浪费来源：长尾

**§14.3.2 已经说过，rollout 的算力利用率低是物理规律、不是浪费。那 RL 真正浪费掉的时间在哪？在这一节。**

### 14.6.1 现象：批次只会衰减，不会回升

```
    一批 512 条序列（64 道题 × 8 条）同时生成：

      大多数：答 512 个 token 就结束了   ████
      少数几条：一直答到 4096 上限       ████████████████████████████████

    ★★ 而这一批必须【全部结束】才能进入训练阶段
    → ★ 整批的耗时 = 最长的那一条
```

> ★ **为什么不能像推理服务那样"补位"**：线上推理服务里，一条序列生成完了，调度器立刻塞一条新请求进来补位（这就是 continuous batching），批次大小基本恒定。**⚠️ RL 的 rollout 不能这么干**——这一批就是 512 条，是算法定死的（64 道题 × 8 条答案），有序列写完了**也没有新活可补**。**⟹ ★★ 批次只会衰减，不会回升。**

### 14.6.2 ★★★ 把浪费算出来

**看一张卡上的 64 条序列，假设长度分布是这样**（⚠️ 举例分布，和 [大模型算子开发 §10.2.1](../../大模型算子开发/10-RL算子.md) 一致）：

| 条数 | 答案长度 | 说明 |
|---|---|---|
| 32 | 512 | 简单题，早早答完 |
| 16 | 1024 | |
| 8 | 2048 | |
| 8 | 4096 | 写到上限被截断 |

**把 Decode 的 4096 步切成四段，列出每一步有多少条序列还活着**：

| 步区间 | 步数 | 还活着几条 | 这段产出的 token | 每步读权重耗时 | 这段的耗时 |
|---|---|---|---|---|---|
| 1 – 512 | 512 | **64** | 32768 | 4.78 ms | 2.45 s |
| 513 – 1024 | 512 | 32 | 16384 | 4.78 ms | 2.45 s |
| 1025 – 2048 | 1024 | 16 | 16384 | 4.78 ms | 4.89 s |
| 2049 – 4096 | 2048 | **8** | 16384 | 4.78 ms | **9.78 s** |
| **合计** | **4096** | — | **81920** | — | **19.6 s** |

```
    ★ 那个 4.78 ms 是怎么来的，以及它为什么是全节的关键：

      一步必须把 16 GB 权重完整读一遍（Decode 是 Memory Bound，§14.3.2）
        16 GB ÷ 3.35 TB/s = ★ 4.776 ms
      ★★ 这个成本和【这一步有几条序列活着】完全无关 ——
         给 64 条出 token 是 4.78 ms，只给 8 条出 token 还是 4.78 ms。
```

```
    ⟹ ★★★ 于是浪费可以直接算出来：

      实际产出                  = 81920 个 token
      若批次恒定 64 跑满 4096 步 = 64 × 4096 = 262144 个 token
                                ────────────────────────────
      ★★ 批次有效利用率          = 81920 ÷ 262144 = ★ 31.25%

      每 token 的读权重成本      = 19.6 s ÷ 81920   = 239 µs
      理想（批次恒为 64）        = 4.776 ms ÷ 64    =  74.6 µs
                                ────────────────────────────
      ★ 长尾让每 token 成本涨了   239 ÷ 74.6 = 3.20 倍  （= 1 ÷ 31.25% ✓）
```

**画出来是这个形状**：

```
    还活着的序列数
      64 ┤████████████████
         │                ▲ 一半序列在第 512 步就答完了
      32 ┤                ████████████████
         │
      16 ┤                                ████████████████████████████
       8 ┤                                                            ████████████████████████████████████████████████████
         └────────────────┴───────────────┴──────────────────────────┴──────────────────────────────────────────────────────→
         0              512            1024                        2048                                                  4096
                                                                                                                    Decode 步

    ← 前 512 步产出 32768 token，耗 2.45 s →     ← 后 2048 步只产出 16384 token，耗 9.78 s →
      每 token 成本 74.6 µs（理想值）              每 token 成本 597 µs（理想值的 8 倍）
```

### 14.6.3 ★★ 长尾吃掉了整体多少时间

```
    把 §14.3.4 和上面这一节的两个数字乘起来：

      rollout 读权重占整体时间          = 48.4%
      其中被长尾浪费掉的比例 (1 − 31.25%) = 68.75%
                                        ──────────────
      ★★★ 48.4% × 68.75% = ★ 33%

    ⟹ ★★ 一次 RL 迭代里有【三分之一】的时间，
       纯粹是在为已经写完的序列反复搬那 16 GB 权重。
```

| 浪费来源 | 占整体时间 | 是不是真浪费 | 能不能治 |
|---|---|---|---|
| ★★★ **长尾（批次衰减）** | **约 33%** | ✅ **是**，纯浪费 | ✅ 能治，见下 |
| rollout 的"算力利用率低" | — | ❌ 不是，是 Memory Bound 的定义 | ❌ kernel 已经到头了 |
| 权重同步 | 0.07% ~ 1.3% | 算不上 | 优化收益很小 |
| 反向传播 | 27.5% | ❌ 不是，是必要计算 | 还有 MFU 余量可榨 |

```
    ⚠️ 注意这张表推翻了两个流传很广的说法：
       ⚠️ "RL 慢是因为权重同步太频繁"  → 它只占 0.07%~1.3%
       ⚠️ "RL 慢是因为反向传播太重"    → 反向只占 27.5%，rollout 占 64%
    ★★ RL 慢的第一原因是长尾，第二原因是 rollout 本身的带宽硬下界。
```

> ⚠️ **而且长尾这块浪费在监控上【看不见】**：这段时间里 HBM 带宽利用率接近 100%（确实在拼命读权重），`nvidia-smi` 的 utilization 也接近 100%（确实一直有 kernel 在跑）。**★ 只有把"活着的序列数"这条曲线画出来，浪费才现形。** 这正是 [13 章 §13.5.2](13-断点续训与容错.md) 那三个口径要分清的原因。

### 14.6.4 ★ 治长尾的三条路

| 手段 | 怎么做 | 代价 |
|---|---|---|
| ① ★★ **异步 rollout** | 生成和训练流水化：先完成的样本先送去训练，不等整批 | ⚠️ 训练用的数据"陈旧"了（**off-policy**：生成它的那份权重已经不是当前权重了），算法要能容忍 |
| ② ★ **partial rollout** | 到时间就截断，没写完的下一轮接着写 | ⚠️ 同上，而且实现复杂 |
| ③ **加大 batch / 长度分桶** | 把长度相近的样本编在一批；或者干脆加大 batch 摊薄 | ★ 最便宜，但治标：分布本身还是散的 |
| ④ 更激进的截断长度 | 把 4096 上限压到 1024 | ⚠️ 直接影响能力上限，是算法决策不是工程决策 |

```
    ★ 这和 13 章 §13.5 的慢卡是【同一个病】：
      ★★ 同步屏障 + 负载不均 = 全场等最慢的。
      区别只在于：慢卡是【硬件】不均，长尾是【数据】不均。
```

> **深入 →** ①②这条"从同步走向全异步"的架构主轴，以及各家框架分别停在哪一档，见 [强化学习训练框架 · 02 架构主轴](../../强化学习训练框架/02-架构主轴-同步到全异步.md)；算子侧的优先级清单见 [大模型算子开发 §10.10](../../大模型算子开发/10-RL算子.md)。

## 14.8 本章小结

```
① ★ RL 与预训练的形状差异：多了【生成】这一步
   → 场上有 4 个模型（actor / critic / reference / reward）
   → ★ 显存 36 字节/参数，是预训练 16 字节/参数的 2.25 倍
     ⚠️ 再加 Rollout 引擎自己那份 BF16 副本 → PPO 38、GRPO 22
     70B：PPO 2660 GB（34 张卡起），GRPO 1540 GB（20 张卡起）
   ⚠️ 显存口径要背熟：16 = BF16 权重 2 + BF16 梯度 2 + FP32 主权重 4
      + Adam m 4 + Adam v 4。★ m 和 v 是【两个】，70B 下各 280 GB
   ⚠️ 去掉 critic 的算法（GRPO 等）省掉整整 16 字节/参数，
      这是它们在大模型上流行的第一位工程原因

② ★★ 一次迭代九步、两条泳道：Rollout 卡组和 Train 卡组从不重叠
   ★ 上行（token + logp + reward）≈ 3.2 MB，下行（新权重）16 GB，差 5000 倍
   ⚠️ 但"通信量大"≠"耗时占比大"：权重同步只占 0.07%~1.3%

③ ★★★ 核心矛盾：生成是【访存受限的推理】，训练是【算力受限的训练】
   → 同一个 actor，两个阶段的最优并行策略【相反】
     （生成想 TP 大以摊薄权重读取；训练想 TP 小以免切碎矩阵）
   ⟹ 产生预训练里不存在的需求：★ resharding（参数在两种切法间搬）
   ⚠️⚠️ 说"生成阶段 GPU 利用率低"必须说口径：
      nvidia-smi ≈100%，HBM 带宽 ≈100%，算力利用率个位数
      ★ 算术强度 = 并发条数 FLOP/字节，H100 的 ridge point 是 295
      ⟹ ★★ 算力利用率低是【物理规律】，不是浪费

④ ★★★ 耗时账（8B / 8×H100 / GRPO / 512 条序列，⚠️ 推算非实测）：
   rollout 三项 64.0%（理论下界口径 77.3%）
   重新前向+反向 27.5%   reference 前向 7.3%   权重同步 0.6%
   ⟹ ★★ 瓶颈在 rollout，不在反向传播

⑤ ✅ HybridFlow 的两个设计：
   ★★ 混合控制器：模型【之间】用单控制器（灵活，节点少）
                   模型【内部】用多控制器 SPMD（高效，算子几十亿）
      ✅ 原文："single-controller on the inter-node level...
              multi-controller within intra-node computation"
      🔑 通用模式：变化多但数量少的层面要灵活，
                   变化少但数量多的层面要高效
   ★ 3D-HybridEngine：resharding 做到【零显存冗余】
   ✅ 总成绩 1.53×~20.57×
      ⚠️ 跨度 13 倍 → 看这类数字务必回正文查是哪个配置

⑥ ★ 生成用推理引擎（vLLM/SGLang）、训练用训练引擎（Megatron/FSDP）
   ⚠️ 两套代码算出的概率对不上（浮点结合律 + kernel/切分/batch 不同）
   → ratio = exp(logp_new − logp_old) 里混进系统误差 → clip 误伤
   → ★★ "训推一致性"从学术洁癖变成影响收敛的工程问题
   ★ 最便宜的一条对策：TITO（token 进 token 出，中途不要解码再分词）

⑦ ★★★ 长尾才是真正的浪费来源：
   ★ 批次只会衰减不会回升（不像推理服务能补位）
   ★ 每步固定读 16 GB（4.78 ms），和这一步有几条序列活着【完全无关】
   ★★ 批次有效利用率 31.25% → 每 token 成本涨 3.20 倍
   ★★★ 48.4% × (1 − 31.25%) = ★ 吃掉整体约 33% 的时间
   ⚠️ 而且它在监控上看不见（带宽和 utilization 都接近 100%）
   ★ 和 13 章 慢卡同病：同步屏障 + 负载不均 = 全场等最慢的
   ★ 治法：异步 rollout / partial rollout / 长度分桶

⑧ ★ 任何 RL 框架都能拆成 5 块：rollout / trainer /
   ★ resharding / controller loop / replay buffer
```
