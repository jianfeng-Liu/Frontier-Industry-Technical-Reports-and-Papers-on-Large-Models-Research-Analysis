## A · 记号

```
Ψ  参数量（个）        N   总 GPU 数
s  序列长度            b   micro-batch size
h  hidden size         B   global batch size
a  注意力头数          m   micro-batch 个数 = B/(b×DP)
L  层数                v   词表大小

t/TP 张量并行   p/PP 流水线并行   d/DP 数据并行
cp/CP 上下文并行  ep/EP 专家并行   vpp 虚拟流水线（interleaving）

⚠️ 字母 v 有两个用处：本表和 README 的记号约定里 v = 词表大小；
   而 07 章讲交错式流水线时，论文和正文用 v 表示【虚拟流水线度】。
   ★ 本表一律写成 vpp，避免歧义。

⚠️★ Ψ 有【两套口径】，差整整一倍，看任何材料前先确认用的是哪套：
   01/02/13 章、本表的「16Ψ 字节 / 12Ψ 字节」 → Ψ = 参数的【个数】
   03/05 章的通信量「2Ψ / 3Ψ」、ZeRO 论文     → Ψ = 一份梯度的【字节数】
   BF16 换算：Ψ_字节 = 2 × Ψ_个数       70B → 70×10⁹ 个 = 140 GB
   ⚠️ 最常见的错法：拿「通信量 2Ψ」配上「Ψ = 70B 个」算出 140 GB，
      少了一半 —— 正确答案是 280 GB。专节见 03 章 §3.3.0

★ 铁律：TP × PP × CP × DP = N      （EP 从 DP 里借，见 09 章）
★ 默认 rank 排布顺序：TP → CP → EP → DP → PP     （12 章 §12.8）
   ↑ 由内到外 = 变化最快到最慢。★ 易错：DP 在【中间】，PP 在【最外】
   ✅ 源码常量 order = "tp-cp-ep-dp-pp"（parallel_state.py）
   组内 rank 步长：TP=1 ｜ DP=TP ｜ PP=TP×DP
     16 卡 TP=2/PP=4 → TP[g0,g1] ｜ DP[g0,g2] ｜ PP[g0,g4,g8,g12]
   为什么：TP 通信最密且阻塞 → 抢机内 NVLink；PP 主要成本是气泡不是带宽 → 丢给跨机
   反向排布开关：--use-tp-pp-dp-mapping（基本用不上）
```

## B · 核心公式（背这七个就够）

```
┌──────────────────────────────────────────────────────────
│ ① 训练显存的四大块          （02 章 §2.2）
│
│    参数 2Ψ  +  梯度 2Ψ  +  优化器 12Ψ  +  激活
│    ↑BF16     ↑BF16      ↑FP32 主权重 4 + Adam m 4 + Adam v 4
│
│    ⚠️★ m 和 v 是【两项】，【各】4 字节，合计 8Ψ，不能合成一份。
│       漏掉一项会把 70B 的 1120 GB 算成 600 GB —— 本仓库真踩过这个坑。
│
│    合计 ≈ 16Ψ + 激活    →  70B 模型光静态就要 1120 GB（14 张 H100）
│
│    ⚠️ 变体：梯度用 FP32 缓冲区累加的实现是 18Ψ，不是 16Ψ
│       （Megatron-LM 的常见配置就是这一档）
│    ⚠️ SGD+momentum 或 Muon（只有一个动量）是 12Ψ
│    ⚠️ 这里的 Ψ 是【参数个数】口径，见 §A
└──────────────────────────────────────────────────────────

┌──────────────────────────────────────────────────────────
│ ② ZeRO 三阶段            （05 章 §5.2）
│
│    ZeRO-1  切优化器 →  2Ψ + 2Ψ + 12Ψ/d
│    ZeRO-2  再切梯度 →  2Ψ + 2Ψ/d + 12Ψ/d
│    ZeRO-3  再切参数 →  (2Ψ + 2Ψ + 12Ψ)/d = 16Ψ/d
│
│    ★ ZeRO-1 / ZeRO-2 是【白赚】：省 4 倍 / 8 倍显存，通信量一分不多
│    ★ ZeRO-3 = FSDP，通信量 3Ψ 对 2Ψ，是 DP 的 1.5×
│      ⚠️ 这里的 Ψ 换成【字节】口径（见 §A）；且 all-gather 躺在前向
│         的关键路径上，实测减速常【超过】1.5 倍这个账面值
└──────────────────────────────────────────────────────────

┌──────────────────────────────────────────────────────────
│ ③ 单层激活显存           （11 章 §11.3，Megatron-3 式 2205.05198）
│
│    每层 ≈ sbh × (34 + 5as/h)     字节
│              ↑基础   ↑注意力矩阵那一坨
│
│    ★ 选择性重计算只砍掉 5as/h 那一项
│      GPT-3（a=96, s=2048, h=12288）：5as/h = 80
│      → 80/114 = 70.2% 的激活被省掉，代价只有 2.7% 算力  ✅ 对上论文
│    ★ 开 TP+SP 后变成 sbh × (34 + 5as/h) / t（08 章 §8.3）
└──────────────────────────────────────────────────────────

┌──────────────────────────────────────────────────────────
│ ④ 全量重计算的 O(√n)     （11 章 §11.2，1604.06174）
│
│    n 层切成 k 段：总显存 = k + n/k
│    对 k 求导置零 → k = √n → 总显存 = 2√n
│
│    ★ 代价：多一次前向 = 4/3 倍算力 = +33%
└──────────────────────────────────────────────────────────

┌──────────────────────────────────────────────────────────
│ ⑤ 流水线气泡率           （07 章 §7.2.3 / §7.4.3）
│
│    朴素 1F1B：  bubble = (p − 1) / (m + p − 1)
│    开 vpp 后：  bubble = (p − 1) / (vpp × m + p − 1)
│
│    ⚠️★ 交错式【不是】把整个气泡率除以 vpp —— vpp 乘的是分母里的 m。
│       p=8、m=32：17.9% → vpp=2 时 9.9%（不是 8.95%），vpp=4 时 5.2%
│
│    ★ 减气泡只有三条路：m 变大、p 变小、开 vpp
│    ✅ 经验法则 m ≥ 4p（07 章 §7.2.4）
│
│    ⚠️ 还有第二套口径：Megatron-2 论文用 (p−1)/m，分母是【理想计算时间】
│       同一配置数字更大（p=8,m=32 → 21.9% vs 本表的 17.9%），别混引
│    ⚠️ 推理 decode 阶段 m = 1，气泡率 = (p−1)/p，p=8 就是 87.5%
└──────────────────────────────────────────────────────────

┌──────────────────────────────────────────────────────────
│ ⑤' 流水线激活显存分布    （07 章 §7.8）
│
│    stage i 缓存的 micro-batch 数 = p − i
│      → stage 0 最大（p 份），末 stage 最小（1 份），差 p 倍
│
│    stage 0 激活 = p 份 × (L/p 层) = ★ L 层 × 1 份 ★
│      ★★ p 被约掉 → 加大 PP 度，stage 0 的激活一点都不降 ★★
│      ⟹ PP 治"参数放不下"，不治"激活放不下"
│
│    峰值时刻 = warmup 最后一格（第一个 backward 之前）
│      → OOM 几乎总在头几个 iteration
│
│    ✅ Zero Bubble 论文 Table 2 的峰值激活：
│       1F1B = p·M_B ｜ ZB-H1 = p·M_B（不涨）｜ ZB-H2 = (2p−1)·M_B（翻倍）
│       对应气泡：1F1B 的 1 ｜ ZB-H1 剩 1/3 ｜ ZB-H2 理论 0
└──────────────────────────────────────────────────────────

┌──────────────────────────────────────────────────────────
│ ⑥ MFU                    （12 章 §12.2）
│
│              6 × Ψ × T
│    MFU = ─────────────────────
│           N × P_peak × t_step
│
│    T = 这一步处理的 token 数
│    P_peak = 单卡【稠密】峰值算力（⚠️ 别填稀疏值，见 §C）
│
│    ★★ 6Ψ 的构成，三个 2 一个都不能多、一个都不能少（§12.2.2）：
│         2Ψ 前向
│       + 2Ψ 反向算【输入】梯度 dx = dy·Wᵀ
│       + 2Ψ 反向算【权重】梯度 dW = xᵀ·dy
│       ─────────────────────────────────
│       = 6Ψ 每 token
│
│    ⚠️★ 6Ψ 里【不含优化器】：优化器是 per-step、per-parameter 的，
│       不随 token 数增长，量级只有千万分之一。把它算进来是概念错误。
│    ⚠️★ 6Ψ 漏了注意力里的 QKᵀ 和 PV（它们不含参数、只看序列长）。
│       补全式 = 6Ψ + 12·L·s·h
│         12 的来历：QKᵀ 前向 2 + PV 前向 2 = 4，反向是前向 2 倍 → +8
│
│       ★ 漏掉的比例随 s 【线性】增长（70B 形状：L=80, h=8192, Ψ=70e9）
│            s      12·L·s·h     补项 ÷ 6Ψ
│           2K      1.61e10       +3.8%
│           4K      3.22e10       ★ +7.7%
│           8K      6.44e10       ★★ +15.3%
│          32K      2.58e11       ⚠️ +61.4%
│         ⟹ 序列每翻倍，被漏掉的比例就翻倍。s=32K 时报的 MFU 会低一大截。
│
│       ⚠️ 该补项【没有扣因果掩码】（decoder 实际只算一半），是【上界】
│       🔑 业界仍统一用保守的 6ΨT，因为它只依赖参数量、横向可比；
│          s ≥ 32K 报 MFU 时应额外注明是否含补项
│
│    ★★ 分子【不含】重计算 —— 这就是 MFU 和 HFU 的分家（11 章 §11.4.4）
│
│                      实际执行的 FLOP
│         HFU = MFU × ──────────────────
│                      模型必需的 FLOP
│
│       不重计算     ⟹ 比值 = 1，       HFU = MFU
│       全量重计算   ⟹ 多跑一遍完整前向，6Ψ → 8Ψ，
│                      HFU = MFU × 8/6 = ×1.333
│       选择性重计算 ⟹ 只重算 5as/h 那一小块，系数【严格小于】4/3
│                      （11 章本例 ×1.026，GPT-3 ×1.027）
│
│    ⚠️★ 高频错误（本表此前就写错过）：
│       Megatron-3 的 42.1% 和 54.2% 【两个都是 MFU】（530B, 2240×A100），
│       分别对应【全量重计算】和【选择性重计算】两种配置，
│       ★ 不是「MFU 对 HFU」的一组对照。PaLM 那一组 46.2% / 57.8%
│         才是同一次训练同时报的 MFU 和 HFU。
└──────────────────────────────────────────────────────────

┌──────────────────────────────────────────────────────────
│ ⑦ Checkpoint：大小与最优间隔    （13 章 §13.2 / §13.3）
│
│    大小 = FP32 主权重 4Ψ + 动量 m 4Ψ + 二阶动量 v 4Ψ = 12Ψ 字节
│           + 学习率调度器 + ★数据加载位置 + ★随机数（RNG）状态
│    ★ 盘上 12Ψ，显存里 16Ψ —— 差的是 BF16 权重（可从 FP32 转出）
│      和 BF16 梯度（存盘点在这一步开始前，此时是 0）
│
│    70B → 840 GB      400B → 4.8 TB
│    ⚠️ 840 GB 在 du -h 眼里是 782 GiB（差 7.4%），申请配额前问清口径
│    ⚠️ 4.8 TB ÷ 2 GB/s ≈ 40 分钟 —— 所以必须用两段式异步存
│    ★★ 但两段式只是把这 40 分钟【挪到后台】，没让它变快
│       ⟹ 存盘间隔 ≥ T_写 × 2~3，否则背压打回 GPU
│
│    ★★★ 该多久存一次：Young/Daly 最优间隔
│
│              T* = √( 2 · C · MTBF )        ← 一阶式，够用
│
│         C    = 每次存盘【阻塞 GPU】的时间（不是后台写完的时间）
│         MTBF = 平均无故障间隔（万卡规模按 10 小时算）
│
│       ★ 最优点上「存盘浪费 C/T」恒等于「重算浪费 T/(2·MTBF)」
│         ⟹ 现场判据：存盘开销 > 平均重算时间 = 存太勤，反之太稀
│       ★ T* 只随 √C 走：C 压低 100 倍，T* 才缩 10 倍
│       例：C = 5 s、MTBF = 10 h → T* ≈ 10 分钟，总浪费 ≈ 2.6%
│
│    ⟹ ★★ 真正能用的间隔 = max( T* , T_写 × 2~3 )
│       400B + 2 GB/s 那一档被背压顶到 100 分钟，总浪费升到 ⚠️ 9.3%
│
│    ✅ 出处（已回溯）：
│       Young (1974), CACM 17(9): 530–531        ← 一阶近似
│       Daly (2006), FGCS 22(3): 303–312         ← 高阶修正
│         高阶式 T_opt = √(2δ(M+R)) − δ
│         δ = 写 checkpoint 耗时，M = MTBF，R = 重启开销
│       ⚠️ C 远小于 MTBF 时两者几乎一样；存一次要十几分钟而 MTBF
│          只有几小时的，改用高阶式
└──────────────────────────────────────────────────────────
```

## C · 关键的量级感（记住数量级就行，不用记精确值）

```
【带宽差几个数量级】                                （03 章 §3.1、11 章）
   ⚠️ 下面【统一按单向】。厂商标称常是双向聚合值，混用会得出错的倍数。

   HBM3（卡内显存）       ~3.35 TB/s      ← 基准
   NVLink 4.0（同机卡间） 单向 450 GB/s   ≈ HBM 的 1/7.4
                          （标称 900 GB/s 是【双向聚合】= 18 link × 25）
   InfiniBand NDR（跨机） 单向  50 GB/s   ≈ NVLink 的 1/9    ★★
                          （400 Gb/s ÷ 8 = 50 GB/s，小 b 是比特）
   PCIe 5.0 ×16（到 CPU） 单向  63 GB/s   ≈ HBM 的 1/53
                          （⚠️ 实测约 50，无公开来源；128 GB/s 是双向）
   本地 SSD               ⚠️ ~2 GB/s（量级参考，无来源）

   ★★ NVLink : IB ≈ 9×（同为单向）  ←── 解释 PTD-P Takeaway #1
      （TP 通信量最大且阻塞 → 必须留在机内）

   ⚠️ 本表此前写「≈ 1/18」，那是拿 NVLink 的双向 900 去比 IB 的单向 50，
      口径不对。9 倍已经足够支撑「TP 必须留在机内」这个结论。
      另注：8 卡只配 4 张网卡时每卡摊到 25 GB/s，那种配置下确实接近 18 倍，
      但原因是网卡数量不足，不是链路本身的差距。

【单卡算力基准：H100 SXM5】                （07 章 §7.8.1、13 章 §13.3.1）
   BF16 稠密峰值     989 TFLOP/s    ← ★ MFU 的分母填这个
     ⚠️ 规格表上的 1979 TFLOP/s 是【2:4 结构化稀疏】值，稠密训练用不上
   FP32               67 TFLOP/s
   HBM3               80 GB / 3.35 TB/s
   屋脊点（ridge point） 989e12 ÷ 3.35e12 ≈ ★ 295 FLOP/字节
     → 算术强度低于 295 的算子是【访存瓶颈】，重算它最划算（11 章 §11.4）
       5as/h 那一项算术强度 ≈ 100 → 该重算，这正是选择性重计算挑中它的原因

   （对照）A100 BF16 稠密 312 TFLOP/s
     ★★ MFU 是【分母敏感】指标：同样吞吐，分母从 312 换成 989 掉到 1/3。
        ⟹ 引用 MFU 必须带硬件平台。

【通信原语的量级】                                （03 章 §3.3）
   all-reduce  = reduce-scatter + all-gather，通信量是后两者的 2×
   ring all-reduce 的通信量 ≈ 2(N−1)/N × 数据量 ≈ 2× 数据量
   ★ 和 N 基本无关 —— 这是 ring 算法最重要的性质
   ⚠️ 这里的「数据量」= 一份梯度的【字节数】（§A 的第二套口径）

【各并行方式的通信频次】                      （06、07、09 章）
   TP  每层 4 次 all-reduce（前向 2 + 反向 2）      ★最密、且阻塞
       80 层 = 320 次，全部串在关键路径上，藏不掉
   SP  把 all-reduce 拆成 reduce-scatter + all-gather，总量不变
   PP  每个 stage 边界 2 次点对点 send/recv         ★最省
   DP  每步 1 次 all-reduce（★ 量最大，但可与反向重叠）
   EP  每层 2 次 all-to-all      ✅ 未优化时可占 30-40% 训练时间
                                 （Megatron 官方文档原话）
   🔑 判断一个维度贵不贵看三件事：① 通信量 ② 同步次数 ③ 能否重叠
      ★ ②③ 比 ① 更决定成败：DP 的量是 TP 的 7 倍，却便宜得多。

【MFU 的档位】                                （12 章 §12.2.6）
   < 25%   ⚠️ 配置有明显问题 → 走一遍 §H
   25-35%  能跑，但大概率漏了免费项（§G 第 ① 步）
   35-45%  ★ 几千卡以上大集群的【正常水位】
   45-55%  ★★ 调得不错，收益开始递减
   > 55%   ★★★ 调得很好了
   > 70%   ⚠️ 先怀疑口径：是不是 HFU？分母是不是用了稀疏峰值？

   ✅ 有据可查的标杆 —— ★★ 每一行都必须带【硬件平台】，否则没有意义
     GPT-3 175B            V100                21%    MFU
     Megatron-Turing 530B  2240 × A100         30%    MFU
     PaLM 540B             ★ 6144 块 TPU v4    46.2%  MFU（同时报 HFU 57.8%）
        ⚠️ 是 TPU 不是 GPU，更不是 H100 —— 2022 年 4 月 H100 还没出货
     Megatron-3 530B       2240 × A100         42.1%  MFU（全量重计算）
     Megatron-3 530B       2240 × A100         54.2%  MFU（选择性重计算）
     MegaScale 175B        ★ 12288 × A100      55.2%  MFU
        ⚠️ 论文自述是 Ampere（A100，峰值 312），不是 H100
     Llama 3.1 405B        8K–16K × H100       38–43% MFU
     VeOmni 7B / 192K ctx  ⚠️ 论文未写硬件      61.5%  MFU（2508.02317）
        ⚠️ 小模型 + 超长上下文本就容易跑高，和 MegaScale 不是同一道题
   ⚠️ PTD-P（Megatron-2）那个流传很广的 52% 【不是 MFU】，原文说的是
      "52% of theoretical peak"，实为 HFU；换算成 MFU 约 39%（12 章 §12.2.7）

【故障是常态】                                （13 章 §13.1）
   ✅ MegaScale：一次生产任务（12288 卡、跑了几周）中恢复超过 100 次
   ⚠️ 若单卡【月】故障率 0.1%，1 万卡一个月全都不出事的概率
      = 0.999^10000 ≈ 0.0045%，期望故障 ≈ 10 次/月
      （1024 卡就已经是 35.9%，即 64% 的概率一个月内至少坏一次）
   ⚠️ 用 MegaScale 的数反推真实值：100 ÷ (12288 卡 × 1.4 月) ≈ 0.58%/月，
      是上面假设值的约 6 倍 —— 因为"故障"还含网卡、交换机、ECC、
      文件系统超时、宿主机重启、软件死锁，任何一环断了任务就挂
   ★ 万卡规模下 MTBF 是【小时】量级：本教程一律按 10 小时算

   ⚠️★ 口径统一：本表和 13 章一律用【月故障率】，不用「日可用性」。
      两者换算：日故障率 ≈ 月故障率 ÷ 30。
      所以「单卡日可用性 99.9%」= 日故障率 0.1%/天 ≈ 3%/月，
      比 13 章用的 0.1%/月 严苛 30 倍 —— 巧的是 0.999^10000 这个算式
      两边长得一样，★ 但含义完全不同，别互相转述。

【读数换算：三个最容易被读错的量】       （01 章 §1.3、06/11/12 章反复出现）
   ★ 加速倍数 = 1 / (1 − 时间减少比例)
       时间减少 60%   ⟹ 加速 2.5 倍  （不是 1.6 倍）
       时间减少 85.5% ⟹ 加速 6.90 倍
       反过来：加速 1.34 倍 ⟹ 时间减少 25.4%（不是 34%）
     ⚠️「时间减少 X%」≠「加速 X%」—— 这两个数在做容量规划时差出一倍多的机器
   ★ 双向 vs 单向：算「发出 X 字节要多久」时，分母一律用单向带宽
   ★ GB vs GiB：本教程 1 GB = 10⁹ 字节；du -h / ls -h 用 GiB = 2³⁰，差 7.4%
       840 GB 的 checkpoint 在 du -h 眼里显示 782 GiB
```

## D · ★★★ 三条因果链（真正需要理解的部分）

```
链条一：为什么 TP 不能跨机                （06 章 §6.4、12 章 §12.3）
──────────────────────────────────────────────────────
   TP 每层 4 次 all-reduce（前向 2 + 反向 2）→ 80 层 = 320 次
   ★ 而且这 320 次全串在关键路径上，藏不进计算里（和 DP 不同）
        ↓
   跨机带宽只有机内的 1/9（同按单向口径；见 §C）
        ↓
   ✅ 论文原话："inter-server links, which are slower than
      the high-bandwidth NVLink"
        ↓
   ★ 而且还有第二个常被忽略的原因：切太碎会产生
     "small GEMMs, potentially decreasing GPU utilization"
        ↓
   ⇒ Takeaway #1：TP 度数 ≤ 单机 GPU 数，跨机用 PP


链条二：为什么选择性重计算这么划算                    （11 章）
──────────────────────────────────────────────────────
   注意力矩阵是 [s,s]，随序列长【平方】增长
        ↓
   但它的计算量只是几个 softmax 和 dropout —— 很便宜
        ↓
   ✅ 判据原文："take up a considerable amount of memory
      but are not computationally expensive to recompute"
        ↓
   ⇒ 只重算这一部分：省 70% 激活，只花 2.7% 算力
        ↓
   ★ 而 FlashAttention 干脆让 [s,s] 从不落显存，
     使 5as/h 这一项在现代系统里基本消失


链条三：为什么 RL 训练要"重新分片"                    （14 章）
──────────────────────────────────────────────────────
   生成阶段 = 推理，是【访存瓶颈】→ 想要大 TP 摊薄权重读取
        ↓
   训练阶段 = 反向传播，是【算力瓶颈】→ 想要小 TP 避免通信
        ↓
   同一个 actor 模型，两个阶段的最优切法【不同】
        ↓
   ⇒ 必须在两种分片间来回转换 = resharding
        ↓
   ✅ HybridFlow 的 3D-HybridEngine 做到 "zero memory redundancy"
```

## G · ★ 调参顺序（12 章 §12.4.1 的浓缩版）

```
① 先开免费的：FlashAttention、BF16 混合精度、SP（TP>1 时）、
   选择性重计算、各种 --overlap-* 开关、融合算子
   ★ 这些不改模型、不损精度、几乎白给
   ✅ 光 overlap 一项，MegaScale 实测值 6.2 个 MFU 百分点

② TP：不超过单机 GPU 数（通常 8）—— 这是硬上限
   ★ 软上限：保证 h / TP ≥ 1024，否则矩阵切太碎、Tensor Core 吃不饱
   ⚠️ MoE 模型优先用 EP 而不是 TP（DeepSeek-V3 训练时 TP=1）

③ PP：能不开就不开；要开就开到刚好装得下
   ★ 层数要能被 p 整除；保证 m = B/(b·DP) ≥ 4p
   ★ 记得顺手开 vpp 减气泡（代价：通信次数 × v）

④ CP：只有序列长度 ≥ 32K 才考虑。短序列开 CP 是纯亏。

⑤ DP = N / (TP × PP × CP)   ← 剩下的全给它
   ★ 显存还紧 → ZeRO-1（几乎无代价）→ ZeRO-2 → ZeRO-3
   ⚠️ ZeRO-3 通信量 1.5×，和 PP 一起用要谨慎

⑥ 扫 micro-batch size b：试 b = 1, 2, 4，没有公式，只能实测
   ✅ 论文：更大的 b 能让单卡吞吐提升【最多 1.3×】
   ★ 配了 PP 时优先试 b=1（m 最大 → 气泡最小）

⑦ 到这里才开始做真正的取舍（加重计算粒度、上 FP8）
   ★ 这一步要一边测 MFU 一边看 loss 曲线

★★ 顺序不能打乱：① 无条件收益 → ②③④【消耗】卡数 →
   ⑤【吃掉剩下】的卡数 → ⑥⑦ 只微调，不改卡的分配。
   ⚠️ 反过来（先定 DP 再挤 TP/PP）会得到一个装不下的配置。
```

## H · ⚠️ MFU 偏低时的排查顺序（12 章 §12.5.4，按「收益 ÷ 排查成本」排序）

```
1. ★★ TP 跨机了吗 —— 打印每个 TP 组的 global rank，看是否同一个 node
      能解释绝大多数"莫名其妙的慢"（06 章：TP 跨机并行效率从 86% 掉到 25%）
2. 口径对吗 —— 报的是 MFU 还是 HFU？分母用的是【稠密】峰值吗？
      长序列（≥32K）有没有注明是否含 12·L·s·h 补项？
3. overlap 开关漏了吗 —— 检查那五个 --overlap-* 参数（✅ 值 6.2 个百分点）
4. 气泡多大 —— 算 (p−1)/(vpp·m + p−1)；★ m < 4p 就是配错了
5. 重计算开太狠了吗 —— full 改 selective（✅ 全量重算白扔 MFU × 6/8，即 25%）
6. 单卡矩阵太小了吗 —— h / TP ≥ 1024？
7. ★ 喂假数据跑一遍（dataloader 换成随机张量，跑 20 步）
      —— MFU 立刻上去了，瓶颈就在数据管道。⚠️ 只跑几十步，假数据会污染 loss
8. 有慢卡吗 —— 收集各 rank 的 iteration time 看方差；
      集合通信被最慢那张卡拖住整组（13 章 §13.5）
9. kernel 层：nsys 看全局 → ncu 深挖单个 kernel。★ 前八条排完再来这里
```
