0 · ★ 三十秒版本

   预训练，追极致吞吐，愿意忍受复杂度        →  Megatron-LM
   显存实在不够，想卸载到 CPU/NVMe          →  DeepSpeed
   中等规模，想看懂/改源码，或已在 PyTorch 生态 →  FSDP / TorchTitan
   做 RLHF / RLVR 后训练                    →  veRL (HybridFlow)
   多模态、超长上下文，或想让并行策略与模型解耦 →  VeOmni

★ 但更常见的真实情况是【混着用】：
  用 Megatron 或 VeOmni 训基座 → 用 veRL 做 RL 后训练 → 用 vLLM/SGLang 部署。
  这三段用的是三套不同的框架，靠 checkpoint 格式衔接。

1 · 先理解一件事：训练框架到底在解决什么

   给你 1024 张 GPU 和一个 400B 的模型，你要回答的问题是：

   ① 模型放不下 ───→ 怎么切？                    切法 = 并行策略
   ② 切开后要通信 ─→ 什么时候通信、走哪条链路？   通信 = 性能瓶颈
   ③ 显存还是不够 ─→ 哪些东西可以不存、可以重算？ 显存 = 硬约束
   ④ 卡会坏 ──────→ 怎么存、怎么恢复？           容错 = 能不能跑完
   ⑤ 数据要喂进来 ─→ 怎么不让 GPU 等数据？        数据 = 常被忽略的瓶颈

★★ 所有训练框架都在回答这五个问题。
   它们的差别不在于【答不答】，而在于：
     - 提供了哪几种答案（策略覆盖度）
     - 默认答案好不好（开箱性能）
     - 让不让你换答案（可扩展性）
     - 换的时候疼不疼（易用性）

⇒ 下面的对比，就是沿着这四个维度展开。

2.1 ★★★ 真正该看的：六个设计点上各家怎么选、换来什么、代价是什么

读法：每个设计点下面是两种对立的选法。你要做的不是挑"更好的那个"，而是认出自己项目能接受哪一种代价。

设计点 这一派怎么选（代表） 换来什么 ⚠️ 代价是什么
① 并行原语谁来写 自己写全套（Megatron：tensor_parallel/ 7,330 行） 每个通信点都能改；能压榨到极致 MFU；不受上游进度约束 PyTorch 每次升级都要自己跟；这 7,330 行的 bug 得自己修
借上游 PyTorch（TorchTitan：95 行；VeOmni：FSDP2、DTensor、DCP 全用 PyTorch 原生件） 代码好读（并行逻辑仅 1.1 万行）；自动跟随上游演进 上游没做的你也做不了；精细 TP 切分做不到 Megatron 那么深
② 要不要改模型代码 模型必须为并行改写（Megatron：nn.Linear → ColumnParallelLinear） 切分方式完全可控，能做到最省通信的切法 已有的 HuggingFace 模型要重写一遍才能跑；接新结构成本高
模型一行不动（DeepSpeed ZeRO-3：zero.Init() + module hook） ✅ 接入成本极低，今天就能跑起来 并行方式受限于 hook 能表达的范围；⚠️ 且这个红利在 PP 上不成立（§4.5）
③ 模型与并行的耦合方式 写在模型里（Megatron） 一处看全，不用在两个文件间跳 换并行策略 = 改模型；多模态各塔负载不同时必然失衡（§6.1）
单独声明（VeOmni 的 parallel_plan.py；TorchTitan 的 sharding.py） ✅ 换策略不动模型；DeepSeek-V3 的 EP 策略只要 10 行 多一层间接；要先理解"声明怎么映射到实际切分"
④ 显存不够时的兜底 靠切得更碎（Megatron / FSDP：加 TP、加 PP、加 ZeRO 级别） 全程在 GPU 上，不引入慢链路 切到极限就没招了；⚠️ 切太碎会通信爆炸、MFU 掉
卸载到 CPU / NVMe（DeepSpeed：none/cpu/nvme 三档） ✅ 卡不够也能跑起来；还能只卸载一部分（ratio 可取小数） ⚠️ 换来的是"能不能跑"，不是"跑得快"：PCIe 比 HBM 慢约 55×，NVMe 再慢一个量级
⑤ PP 调度怎么表达 每种调度写一个大函数（Megatron：interleaved 1000+ 行） 每种调度都能单独手工优化到极致 加一种新调度 = 再写一个大函数；三份代码要分别维护
写成一套"指令集"（DeepSpeed：PipeInstruction 家族） ✅ 换调度 = 换生成指令的顺序，执行引擎不动 多一层解释开销；单条路径的极致优化空间小一些
⑥ 上层编排与底层计算的关系 一个框架全包（Megatron 走 SPMD，Single Program Multiple Data，单程序多数据 —— 每张卡跑同一份 train_step，只是喂进去的数据不同） 预训练只有一条数据流时，这是最直接、最快的形态 ⚠️ RL 那种四五条互相依赖的数据流，表达起来很别扭
分层：薄编排 + 厚后端（veRL：single_controller/ 2,247 行 指挥 workers/ 23,797 行） ✅ RL 主循环读起来像单机程序；底层可换 6 种后端 多一层 Ray 调度；⚠️ 要同时懂编排层和你选的那个后端 
★★★ 把这六行压成一句话：

   ①②③ 是同一个取舍的三个侧面 —— 【控制力 vs 接入成本】
        自己写、改模型、并行长在模型里  = 控制力最大，接入最贵
        借上游、不改模型、并行单独声明  = 接入最便宜，控制力受限

   ④ 是【能跑 vs 跑得快】的取舍，不是性能优化手段。

   ⑤⑥ 是【单点极致 vs 换起来容易】的取舍。

★★ 所以"该选谁"真正的问法不是"谁最快"，而是这三个问题：
     - 我的模型结构会频繁变吗？       会 → 往"解耦"那一派走
     - 我的卡够吗？                   不够 → 才考虑卸载
     - 我要压到最后几个点 MFU 吗？    要 → 才值得付 Megatron 的复杂度

3 · Megatron-LM：能力最全，代价是复杂

优势

✅ 并行策略覆盖最全：TP / PP（3 种调度）/ DP / SP / CP / EP 全都有，
   而且是【被万卡规模反复验证过的实现】。

✅ 一手战绩（论文原文，均已回溯 papers/ 下的 PDF）：
   PTD-P (2104.04473)：1T 参数 / 3072 GPU / 502 petaFLOP/s
                        = 单卡理论峰值的 52%
                        ✅ 摘要原文："training iterations on a model with 1 trillion
                           parameters at 502 petaFLOP/s on 3072 GPUs
                           (per-GPU throughput of 52% of theoretical peak)"
                        ⚠️ 注意：这 52% 算了重计算，实为 HFU
                           （Hardware FLOPs Utilization，硬件浮点利用率，
                            分子含重计算的那次重复计算）；
                           MFU ≈39%（见 12 章 §12.2 订正）
   Megatron-3 (2205.05198)：选择性重计算 MFU 54.2% vs 全量重计算 MFU 42.1%
                        ✅ 配置条件（缺了就没法比）：530B GPT-3 式模型 / 2240 张 A100
                        ★ 两个都是 MFU，同配置，可以直接比

★ 生态位：几乎所有国产/开源大模型的预训练，
  要么直接用 Megatron，要么用它的衍生版（NeMo、Megatron-DeepSpeed 等）。
  ⇒ 遇到问题时，能搜到答案的概率最高。

⚠️ 关于上面那个 "54.2% vs 42.1%"，论文原文用的词是 "29% faster"，但这个 29% 不能读成"时间少了 29%"。 ✅ 摘要原句是 "we achieve a Model Flops Utilization of 54.2%, which is 29% faster than the 42.1% we achieve using recomputation"。⇒ 54.2 ÷ 42.1 = 1.287，是吞吐提升 28.7%；换成时间是 1 − 42.1 ÷ 54.2 = 时间减少 22.3%。★ "快 X%" 和 "时间减少 X%" 永远不是同一个数，越到高百分比差得越远（快 100% 只等于时间减半，即减少 50%）。同一篇论文还给了另外两个更好懂的口径：激活显存降到 1/5（"reduces activation memory by 5×"）、重计算带来的时间开销减少 90% 以上。

代价

⚠️ 命令行参数极多：arguments.py 里显式 add_argument 有 419 处，
   ✅ 但这还不是全部 —— 另有一批从配置 dataclass 自动展开
     （仅 TransformerConfig 一个类就声明了约 268 个字段）。
   ⇒ 详见 [拆解文档 §0](Megatron-LM拆解.md)
⚠️ 24 万行代码（✅ 实测 240,726 行），且有【两套 DDP、两套 FSDP、两套算子实现】（见 [拆解文档 §10](Megatron-LM拆解.md)）
⚠️ 加一个新模型结构，往往要动到并行逻辑本身 ——
   ★★ 这正是 VeOmni 论文批评的那一点，见 §6。

★ 一个务实的判断：
  如果你的模型结构是标准 Transformer 的小改动，Megatron 很香；
  如果你的模型结构比较特殊（多模态、非标准注意力），改起来会很痛。

4.2 ★★★ 源码里最值得看的一处：ZeRO-1 和 ZeRO-2 只差一个布尔值

先回忆 ZeRO 三阶段在讲什么（详见 05 章）：

ZeRO-1 → 把【优化器状态】切开分给各卡
ZeRO-2 → 再把【梯度】也切开
ZeRO-3 → 再把【参数】本身也切开

直觉上会以为这是三套实现。源码里不是 —— 目录长这样：

deepspeed/runtime/zero/
├── stage_1_and_2.py          3,153 行  ← ZeRO-1 和 ZeRO-2 共用这一个文件
├── stage3.py                 3,857 行  ← ZeRO-3 是完全独立的另一套
├── partition_parameters.py   2,520 行  ← ZeRO-3 专用：参数切分
├── parameter_offload.py        682 行  ← ZeRO-3 专用：参数卸载
└── partitioned_param_coordinator.py  690 行  ← ZeRO-3 专用：预取调度

★★ ZeRO-1 与 ZeRO-2 的全部区别，就是构造函数里的一个参数。
deepspeed/runtime/engine.py:2378（决定传什么）：

partition_grads=zero_stage == ZeroStageEnum.gradients,

deepspeed/runtime/zero/stage_1_and_2.py:222-223（收到之后）：

self.partition_gradients = partition_grads
self.zero_stage_string = "ZeRO-2" if partition_grads else "ZeRO-1"

⇒ ★ 连"我是几阶段"这个名字都是这个布尔值现算出来的。
所以 ZeRO-1→ZeRO-2 在工程上几乎零成本，而 ZeRO-2→ZeRO-3 是换一整套代码路径（3,857 + 2,520 + 682 + 690 ≈ 7,700 行新代码）。

这解释了一个实践现象：很多团队停在 ZeRO-2。
不是不知道 ZeRO-3 更省显存，而是 ZeRO-3 的复杂度、通信量和踩坑面确实是另一个量级。

顺带一提，阶段编号在源码里是个枚举，deepspeed/runtime/zero/config.py:81-87：

class ZeroStageEnum(int, Enum):
    """ Enum class for possible zero stages """
    disabled = 0
    optimizer_states = 1
    gradients = 2
    weights = 3
    max_stage = 3

名字本身就把"每一阶段多切了什么"写清楚了：optimizer_states（优化器状态）→ gradients（梯度）→ weights（权重），正好对应 ZeRO-1 / 2 / 3。

⚠️ 本文上一版在这段代码里加了 # ZeRO-1 / # ZeRO-2 / # ZeRO-3 三行注释，但源码里没有这些注释（源码只有那一行 docstring）。上面这份是逐字原文。★ 这类"好心加注释"在源码引用里要特别小心 —— 读者会以为注释也是官方写的，进而以为官方文档里有这层对应关系。

4.3 ★★ 它的另一个气质：不要求你改模型代码

这是 DeepSpeed 和 Megatron 最根本的分歧，源码里看得很直接。

Megatron 的做法：你必须把模型里的 nn.Linear 换成 ColumnParallelLinear，也就是模型代码本身要为并行改写。

DeepSpeed ZeRO-3 的做法：用两个 PyTorch 原生机制接管，模型代码一行不动。

① 构造期：一个 with 语句，partition_parameters.py:1024-1026 的官方示例：

with deepspeed.zero.Init():
    model = MyLargeModel()

Init 类（partition_parameters.py:923）继承自 InsertPostInitMethodToModuleSubClasses
—— 它劫持每个 nn.Module 子类的 __init__ 结束时刻，在参数刚被创建出来的那一瞬间就切碎分发。
所以模型从来没有在任何一张卡上完整存在过，这是能装下超大模型的关键。

② 运行期：用 module hook 在每层前后自动聚合/释放，deepspeed/runtime/zero/parameter_offload.py:439-442：

self.forward_hooks.append(module.register_forward_pre_hook(_pre_forward_module_hook))
...
self.forward_hooks.append(module.register_forward_hook(_post_forward_module_hook))

名词解释：hook（钩子）——PyTorch 允许你在某个模块 forward 之前/之后自动插入一段函数。
模型作者不知情，也不用配合。

配合的两个函数就叫 pre_sub_module_forward_function（第 525 行）和post_sub_module_forward_function（第 549 行）—— 语义就是字面意思：进这一层之前把参数聚合回来，出这一层之后立刻放掉。

⇒ ★★★ 这就是 DeepSpeed 最大的产品优势：接入成本极低。
你已有的 HuggingFace 模型，套个 deepspeed.initialize() 就能跑 ZeRO-3；换成 Megatron 则要重写模型定义。
代价是并行方式受限于 hook 能表达的范围 —— 精细的 TP 切分它做不到 Megatron 那么极致。

5 · ★★ FSDP / TorchTitan：PyTorch 原生路线（源码走查）

✅ FSDP (2304.11277) 本质上是 ZeRO-3 的 PyTorch 原生实现。
✅ FSDP2 用 DTensor 重写，分片语义更清晰，是现在的主推版本。
✅ TorchTitan (2410.06511) 是在 FSDP2 之上的一站式训练方案。

DTensor（Distributed Tensor，分布式张量）：PyTorch 原生的"带分片信息的张量"。
一个普通张量只知道自己的形状；一个 DTensor 额外知道"我被切在哪个设备网格的哪一维上"。

6.1 它想解决什么

✅ 论文（2508.02317）的批评原文：

"directly applying these techniques to omni-modal LLMs often leads to load imbalance and poor scalability"

   在 Megatron 里，模型代码和并行代码是【长在一起】的 ——

⚠️ 本文上一版写"一共 6 种"，漏了两个：漏掉的是首尾那两个 —— RANK_ZERO（第 39 行）和 DIRECT_ROLLOUT_METHOD（第 47 行）。上一版引用的"第 40-45 行"恰好只框住中间那 6 个，所以数错了。★ 最后一个尤其值得留意：源码里它上面有一行注释写着 "This is a special dispatch mode for vllm ExternalRayDistributedExecutor" —— 一个为单个推理引擎开的后门，正好印证 §7.5 那句"难点在训练侧和推理侧的接缝上"。

最简单的 ONE_TO_ALL，函数体只有 3 行（第 120-123 行，含 def），一眼能读完：

def dispatch_one_to_all(worker_group, *args, **kwargs):
    args = tuple([arg] * worker_group.world_size for arg in args)
    kwargs = {k: [v] * worker_group.world_size for k, v in kwargs.items()}
    return args, kwargs

第二处：verl/single_controller/ray/base.py:49 的 func_generator——整个桥梁只有 19 行：

def func_generator(self, method_name, dispatch_fn, collect_fn, execute_fn, blocking):
    class Functor:
        def __call__(this, *args, **kwargs):
            args, kwargs = dispatch_fn(self, *args, **kwargs)     # ① 切数据
            padding_count = kwargs.pop(_padding_size_key, 0)
            output = execute_fn(method_name, *args, **kwargs)     # ② 丢给所有 worker
            if blocking:
                output = ray.get(output)                          # ③ 等结果
            output = collect_fn(self, output)                     # ④ 收回来
            ...
            return output
    return type(method_name, (Functor,), {})()

★★★ 这 19 行就是"单控制器"和"多控制器"之间的全部胶水。
主进程调用 actor_wg.update_actor(batch) 时看起来像调用一个普通函数，实际发生的是：切数据 → 广播给 N 个 Ray worker 并行执行 → 等待 → 汇总。

⚠️ 全仓一共 51 处 @register(...)——也就是说整套 RL 流程里需要跨"中心 ↔ worker"边界的操作只有 51 个。接口面很小，这是它能保持轻量的原因。

7.3 ✅ 效果：主循环读起来像单机程序

verl/trainer/ppo/ray_trainer.py（1,823 行）的主循环，顺序如下（行号实测）：

步骤 行号 调用

算旧策略 log prob 1304 actor_rollout_wg.compute_log_prob(...)

★★ 一路读下来是直线的、没有一句 if rank == 0、没有一句显式通信。
这正是 single-controller 想买到的东西：RL 算法的复杂性（谁先谁后、谁喂谁）
留在这份能一眼读完的主循环里，而不是散落在每个 worker 的 rank 判断里。

对照 Megatron 的主循环：那是标准的 SPMD，每张卡都在跑同一份 train_step。
两者不是谁更好，是任务形状不同：预训练只有一条数据流，RL 有四五条互相依赖的数据流。

⚠️ 这个区间不带配置条件就等于没有信息量。 ✅ 回溯论文正文（第 11-12 页）后，它的真实含义是：

这个数字 实际是什么

和谁比 三个基线：DeepSpeed-Chat / OpenRLHF / NeMo-Aligner（不是和 Megatron 比）

下界 1.53× 7B ReMax、128 卡对 OpenRLHF —— ⚠️ 卡多、模型小时优势最薄
论文自报的平均 对 DeepSpeed-Chat 3.67×、对 OpenRLHF 3.25×、对 NeMo-Aligner 12.52× 
★★★ 所以正确的引用方式是：
   "veRL 相对三个同类 RLHF 框架平均快 3.25×~12.52×，
    具体倍数取决于算法、模型规模和卡数"
   而不是 "veRL 快 20 倍"。

⚠️ 还有一条论文自己点明的规律值得记住：
   ★ 卡越多、模型越小，veRL 的优势越小（下界 1.53× 就出现在 7B / 128 卡）。
     原因论文写了：global batch 固定时，卡越多每卡的 local batch 越小，
     GPU 会吃不饱 —— 这时候瓶颈已经不是框架编排了。

9 · ★ 五条容易被忽略的实践经验

① ★★ 换框架很少能解决性能问题
   ⚠️ MFU 低的常见原因（[12 章 §12.5](分布式训练入门/12-并行策略组合与MFU.md)）：
      重计算开成了 full、TP 跨机了、气泡太大、数据管道跟不上。
   ★ 这些换个框架一样会犯。先按排查清单走一遍，再考虑换框架。

② ★★ checkpoint 格式的兼容性，比框架本身的性能更影响你的生活
   预训练用 A、RL 用 B、部署用 C 是常态，
   ⇒ 三者之间的 checkpoint 转换脚本，往往是最脏也最重要的一块。
   ★ 好消息是 PyTorch DCP 正在成为共识（Megatron 的 torch_dist、VeOmni 都支持）。

③ ★★★ 看框架先看"它自己写了多少"
   ✅ 本次实测：同样是张量并行，
      Megatron 7,330 行 / DeepSpeed 393 行 / TorchTitan 95 行。
   ⇒ 这不是谁强谁弱，而是【自研 vs 依赖上游】两条路。
     自研 = 可以极致调优，但每次 PyTorch 升级都要自己跟；
     依赖上游 = 代码好读、跟随演进，但上游没做的你也做不了。
   ★ 选型时问一句"这个能力是它自己实现的，还是转手上游的？"
     ——决定了出问题时你能不能改得动。

④ ⚠️ 论文里的 MFU 数字几乎不可直接横向比较
   模型大小、卡数、上下文长度、是否算重计算（MFU vs HFU）、硬件代次，
   任何一项不同，结论就不同。
   ★ 正确的用法是：拿它们当【同一配置下的相对提升】看，
     而不是当【框架排行榜】看。
     § 6.3 里 VeOmni 的 61.5% 和 MegaScale 的 55.2% 就是最好的例子。

⑤ ★★★ 比性能更早决定选型的，是【要不要改模型代码】
   ✅ 源码实证：
      DeepSpeed ZeRO-3 → `with deepspeed.zero.Init():` + module hook，模型一行不改；
      Megatron TP      → 必须把 nn.Linear 换成 ColumnParallelLinear，模型要重写。
   ⇒ 前者能让已有的 HuggingFace 模型今天就跑起来，
     后者能换来极致的 MFU，但你得先把模型迁过去。
   ★ 现实里这一条往往比"谁快 5%"更能决定项目排期。
   ⚠️ 注意例外：DeepSpeed 的【流水线并行】不享受这个红利 ——
      PipelineModule 要求模型能写成顺序的一串层（见 §4.5）。

10 · 本章小结

① 五家框架都在回答同样的五个问题（切法/通信/显存/容错/数据），
   差别在【策略覆盖度、开箱性能、可扩展性、易用性】的取舍。
   ★★ 而真正能用来选型的，是 §2.1 那张【设计点 / 换来什么 / 代价】表 ——
     功能勾选清单（"谁支持 TP"）几乎没有决策价值，
     因为它把"有"和"有且好用"画成同一个勾，还把代价全藏起来了。

② Megatron-LM：并行最全、验证最充分，代价是复杂度和"模型与并行耦合"。

③ DeepSpeed：ZeRO 与卸载的发源地，气质是【不要求你改模型代码】。
   ✅ 源码实证 —— ZeRO-1 与 ZeRO-2 的全部区别只是一个布尔值
   (`zero_stage_string = "ZeRO-2" if partition_grads else "ZeRO-1"`)，
   而 ZeRO-3 是另外约 7,700 行的独立代码路径 —— 这解释了为什么很多团队停在 ZeRO-2。
   ★ 卸载解决"能不能跑"，不解决"跑得快"。⚠️ 它的 TP 很弱（393 行，且偏推理）。

④ FSDP / TorchTitan：PyTorch 原生，代码最好读，中等规模的默认选择。
   ✅ 源码实证 —— 它的 tensor_parallel.py 只有 95 行（Megatron 是 7,330 行），
   因为并行原语全部借自上游 PyTorch。

⑤ ★★ VeOmni：把并行策略从模型里拆成独立的 parallel_plan.py，
   ✅ 源码实证 —— DeepSeek-V3 的 EP 策略只有 10 行声明，
   且 veomni/models/ 下有 7 个模型自带 parallel_plan.py。
   适合多模态、长上下文、需要频繁接入新模型结构的场景。
   ⚠️ 它的 MFU 61.5% 是 Qwen2-VL 7B / 128 卡 / 192K 的成绩，
     别拿去和万卡规模的数字比大小（§6.3）。

⑥ veRL：RL 后训练的事实标准，核心是【混合控制器 + 3D-HybridEngine】。
   ✅ 源码实证 —— single_controller/ 只有 2,247 行，而它协调的 workers/ 有 23,797 行。
   ★ 这个 1:10 的比例，本身就是"上层薄而灵活、下层厚而高效"的最好注脚。

⑦ ★★★ 最常见的真实架构是【组合使用】，而不是二选一。
   ✅ 源码实证 —— veRL 的 workers/engine/ 下并列着 megatron / fsdp /
   veomni / torchtitan / automodel / mindspeed 六个可选后端（§7.6）。
   ⇒ "选 veRL 还是选 Megatron"是伪问题，它们是上下层关系。
   ⇒ 所以 checkpoint 格式的互通性，实践中比单框架性能更值得关注。
