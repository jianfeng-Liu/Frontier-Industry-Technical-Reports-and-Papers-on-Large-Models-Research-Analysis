# 训练框架横向对比

> **这份文档回答一个问题：这么多训练框架，我该用哪个？**
> ✅ = 论文/官方源码原文披露 ｜ ⚠️ = 本文的推断或经验判断
>
> 涉及的两份源码均已实际拉取走查：
> ✅ [源码/Megatron-LM/](源码/Megatron-LM/) commit `c9676f4`，Megatron-Core 0.20.0
> ✅ [源码/VeOmni/](源码/VeOmni/) commit `c465a63`

## 0 · ★ 三十秒版本

```
   预训练，追极致吞吐，愿意忍受复杂度        →  Megatron-LM
   显存实在不够，想卸载到 CPU/NVMe          →  DeepSpeed
   中等规模，想看懂/改源码，或已在 PyTorch 生态 →  FSDP / TorchTitan
   做 RLHF / RLVR 后训练                    →  veRL (HybridFlow)
   多模态、超长上下文，或想让并行策略与模型解耦 →  VeOmni

★ 但更常见的真实情况是【混着用】：
  用 Megatron 或 VeOmni 训基座 → 用 veRL 做 RL 后训练 → 用 vLLM/SGLang 部署。
  这三段用的是三套不同的框架，靠 checkpoint 格式衔接。
```

## 1 · 先理解一件事：训练框架到底在解决什么

```
   给你 1024 张 GPU 和一个 400B 的模型，你要回答的问题是：

   ① 模型放不下 ───→ 怎么切？                    切法 = 并行策略
   ② 切开后要通信 ─→ 什么时候通信、走哪条链路？   通信 = 性能瓶颈
   ③ 显存还是不够 ─→ 哪些东西可以不存、可以重算？ 显存 = 硬约束
   ④ 卡会坏 ──────→ 怎么存、怎么恢复？           容错 = 能不能跑完
   ⑤ 数据要喂进来 ─→ 怎么不让 GPU 等数据？        数据 = 常被忽略的瓶颈

★★ 所有训练框架都在回答这五个问题。
   它们的差别不在于【答不答】，而在于：
     - 提供了哪几种答案（策略覆盖度）
     - 默认答案好不好（开箱性能）
     - 让不让你换答案（可扩展性）
     - 换的时候疼不疼（易用性）

⇒ 下面的对比，就是沿着这四个维度展开。
```

## 3 · Megatron-LM：能力最全，代价是复杂

### 优势

```
✅ 并行策略覆盖最全：TP / PP（3 种调度）/ DP / SP / CP / EP 全都有，
   而且是【被万卡规模反复验证过的实现】。

✅ 一手战绩（论文原文）：
   PTD-P (2104.04473)：1T 参数 / 3072 GPU / 502 petaFLOP/s
                        = 单卡理论峰值的 52%
                        ⚠️ 注意：这 52% 算了重计算，实为 HFU；
                           MFU ≈39%（见 12 章 §12.2 订正）
   Megatron-3 (2205.05198)：✅ 摘要原文 —— 选择性重计算 MFU 54.2%，
                        比全量重计算的 MFU 42.1% 快 29%（★ 两个都是 MFU）

★ 生态位：几乎所有国产/开源大模型的预训练，
  要么直接用 Megatron，要么用它的衍生版（NeMo、Megatron-DeepSpeed 等）。
  ⇒ 遇到问题时，能搜到答案的概率最高。
```

### 代价

```
⚠️ 419 个命令行参数（✅ 实测 arguments.py 的 add_argument 个数）
⚠️ 24 万行代码，且有【两套 DDP、两套 FSDP、两套算子实现】（见 [拆解文档 §10](Megatron-LM拆解.md)）
⚠️ 加一个新模型结构，往往要动到并行逻辑本身 ——
   ★★ 这正是 VeOmni 论文批评的那一点，见 §6。

★ 一个务实的判断：
  如果你的模型结构是标准 Transformer 的小改动，Megatron 很香；
  如果你的模型结构比较特殊（多模态、非标准注意力），改起来会很痛。
```

### 4.2 ★★★ 源码里最值得看的一处：ZeRO-1 和 ZeRO-2 只差一个布尔值

先回忆 ZeRO 三阶段在讲什么（详见 [05 章](分布式训练入门/05-ZeRO与FSDP.md)）：

```
ZeRO-1 → 把【优化器状态】切开分给各卡
ZeRO-2 → 再把【梯度】也切开
ZeRO-3 → 再把【参数】本身也切开
```

直觉上会以为这是三套实现。源码里不是 —— 目录长这样：

```
deepspeed/runtime/zero/
├── stage_1_and_2.py          3,153 行  ← ZeRO-1 和 ZeRO-2 共用这一个文件
├── stage3.py                 3,857 行  ← ZeRO-3 是完全独立的另一套
├── partition_parameters.py   2,520 行  ← ZeRO-3 专用：参数切分
├── parameter_offload.py        682 行  ← ZeRO-3 专用：参数卸载
└── partitioned_param_coordinator.py  690 行  ← ZeRO-3 专用：预取调度
```

★★ ZeRO-1 与 ZeRO-2 的全部区别，就是构造函数里的一个参数。
`deepspeed/runtime/engine.py:2378`（决定传什么）：

```python
partition_grads=zero_stage == ZeroStageEnum.gradients,
```

`deepspeed/runtime/zero/stage_1_and_2.py:222-223`（收到之后）：

```python
self.partition_gradients = partition_grads
self.zero_stage_string = "ZeRO-2" if partition_grads else "ZeRO-1"
```

⇒ ★ **连"我是几阶段"这个名字都是这个布尔值现算出来的。**
所以 ZeRO-1→ZeRO-2 在工程上几乎零成本，
而 ZeRO-2→ZeRO-3 是换一整套代码路径（3,857 + 2,520 + 682 + 690 ≈ 7,700 行新代码）。

这解释了一个实践现象：**很多团队停在 ZeRO-2**。
不是不知道 ZeRO-3 更省显存，而是 ZeRO-3 的复杂度、通信量和踩坑面确实是另一个量级。

顺带一提，阶段编号在源码里是个枚举，`deepspeed/runtime/zero/config.py:81-87`：

```python
class ZeroStageEnum(int, Enum):
    disabled = 0
    optimizer_states = 1     # ZeRO-1
    gradients = 2            # ZeRO-2
    weights = 3              # ZeRO-3
    max_stage = 3
```

名字本身就把"每一阶段多切了什么"写清楚了：优化器状态 → 梯度 → 权重。

### 4.3 ★★ 它的另一个气质：不要求你改模型代码

这是 DeepSpeed 和 Megatron 最根本的分歧，源码里看得很直接。

**Megatron 的做法**：你必须把模型里的 `nn.Linear` 换成 `ColumnParallelLinear`，
也就是**模型代码本身要为并行改写**。

**DeepSpeed ZeRO-3 的做法**：用两个 PyTorch 原生机制接管，模型代码一行不动。

① **构造期**：一个 `with` 语句，`partition_parameters.py:1024-1026` 的官方示例：

```python
with deepspeed.zero.Init():
    model = MyLargeModel()
```

`Init` 类（`partition_parameters.py:923`）继承自 `InsertPostInitMethodToModuleSubClasses`
—— 它劫持每个 `nn.Module` 子类的 `__init__` 结束时刻，
在参数刚被创建出来的那一瞬间就切碎分发。
所以**模型从来没有在任何一张卡上完整存在过**，这是能装下超大模型的关键。

② **运行期**：用 module hook 在每层前后自动聚合/释放，
`deepspeed/runtime/zero/parameter_offload.py:439-442`：

```python
self.forward_hooks.append(module.register_forward_pre_hook(_pre_forward_module_hook))
...
self.forward_hooks.append(module.register_forward_hook(_post_forward_module_hook))
```

> 名词解释：**hook（钩子）**——
> PyTorch 允许你在某个模块 forward 之前/之后自动插入一段函数。
> 模型作者不知情，也不用配合。

配合的两个函数就叫 `pre_sub_module_forward_function`（第 525 行）和
`post_sub_module_forward_function`（第 549 行）—— 语义就是字面意思：
**进这一层之前把参数聚合回来，出这一层之后立刻放掉。**

⇒ ★★★ **这就是 DeepSpeed 最大的产品优势：接入成本极低。**
你已有的 HuggingFace 模型，套个 `deepspeed.initialize()` 就能跑 ZeRO-3；
换成 Megatron 则要重写模型定义。
代价是并行方式受限于 hook 能表达的范围 —— 精细的 TP 切分它做不到 Megatron 那么极致。

### 4.4 ✅ 卸载：`none / cpu / nvme` 三档

`deepspeed/runtime/zero/offload_config.py:14-18`：

```python
class OffloadDeviceEnum(str, Enum):
    none = "none"
    cpu = "cpu"
    nvme = "nvme"
```

对应两篇论文：ZeRO-Offload（2101.06840，卸载到 CPU 内存）、
ZeRO-Infinity（2104.07857，卸载到 NVMe 固态盘）。

NVMe 那一档不是配置项写写就完事，源码里有专门的一个目录做异步磁盘读写：

```
deepspeed/runtime/swap_tensor/          （合计 1,931 行）
├── optimizer_utils.py              533
├── partitioned_param_swapper.py    418
├── utils.py                        258
├── pipelined_optimizer_swapper.py  242
├── partitioned_optimizer_swapper.py 228
└── async_swapper.py                174
```

> 名词解释：**NVMe**（Non-Volatile Memory express）——
> 高速固态硬盘的接口标准，比传统硬盘快得多，但仍比显存慢两个量级。

⚠️ **务必清楚代价**：
```
卸载到 CPU 走 PCIe（~60 GB/s），比 HBM（~3.35 TB/s）慢约 55×；
卸载到 NVMe 再慢一个量级。
⇒ ★★ 卸载解决的是【能不能跑】，不是【跑得快不快】。
   在卡够的情况下，几乎没人会主动开卸载。
```

配置里还有个细节值得一提，`offload_config.py:99`：

```python
ratio: float = Field(1.0, ge=0.0, le=1.0)
```

—— 卸载比例可以是小数，也就是**只卸载一部分**。
显存差一点点的时候，卸 30% 比全卸的性能损失小得多。

### 4.5 ✅ 流水线并行：一个"指令集"设计

DeepSpeed 的 PP 在 `deepspeed/runtime/pipe/`（合计 3,272 行）：

```
engine.py    1,413      module.py   704
schedule.py    494      topology.py 472      p2p.py 182
```

它的做法在五家里是独一份：**把流水线调度写成一套指令**。
`deepspeed/runtime/pipe/schedule.py` 里定义了这些类：

```
PipeInstruction（基类）
├── ForwardPass / BackwardPass       ← 算
├── SendActivation / RecvActivation  ← 传激活值
├── SendGrad / RecvGrad              ← 传梯度
├── LoadMicroBatch                   ← 取数据
├── ReduceGrads / ReduceTiedGrads    ← 归约
└── OptimizerStep                    ← 更新
```

调度器（`TrainSchedule`，第 189 行）负责生成一串指令，引擎负责逐条执行。
⇒ ★ 好处是**换调度策略 = 换生成指令的顺序**，不用动执行引擎。
这跟 Megatron 把 1F1B、interleaved 各写一份大函数是完全不同的思路。

⚠️ 但 PP 这里 DeepSpeed 又变回"侵入式"了：
`deepspeed/runtime/pipe/module.py:86` 的 `PipelineModule` 要求
**模型必须能表达成一串顺序的层**（像 `nn.Sequential` 那样），
才能按层切给不同卡。ZeRO 的"不改模型"红利在 PP 上不成立。

### 4.6 ⚠️ 边界：TP 是它的短板

| 同一件事 | Megatron | DeepSpeed | TorchTitan |
|---|---|---|---|
| 张量并行（TP）实现 | `tensor_parallel/` **7,330 行** | `runtime/tensor_parallel/` **393 行** | `distributed/tensor_parallel.py` **95 行** |

DeepSpeed 那 393 行主要是配置和管理器（`config.py` 174 / `init_utils.py` 146 / `tp_manager.py` 66），
真正的切分算子在 `module_inject/layers.py`（1,500 行）—— 而 `module_inject` 这个名字已经说明了
它的出身：**为推理注入而生**，训练侧的 TP 并不是 DeepSpeed 的主战场。

⇒ ★★ 所以选型上的分工很清楚：
```
显存不够、不想改模型      → DeepSpeed
要极致 TP、极致 MFU      → Megatron
要好读、跟随 PyTorch 上游 → TorchTitan
```

## 5 · ★★ FSDP / TorchTitan：PyTorch 原生路线（源码走查）

```
✅ FSDP (2304.11277) 本质上是 ZeRO-3 的 PyTorch 原生实现。
✅ FSDP2 用 DTensor 重写，分片语义更清晰，是现在的主推版本。
✅ TorchTitan (2410.06511) 是在 FSDP2 之上的一站式训练方案。
```

> **DTensor**（Distributed Tensor，分布式张量）：PyTorch 原生的"带分片信息的张量"。
> 一个普通张量只知道自己的形状；一个 DTensor 额外知道"我被切在哪个设备网格的哪一维上"。
> **DeviceMesh**（设备网格）：把 N 张卡排成一个多维网格并给每一维起名字（`dp` / `tp` / `pp` …），
> 之后所有并行都表达成"在某个网格轴上做某种操作"。

### 5.1 ✅ 规模实测（commit `9d7dc2f`）

| | 文件数 | 行数 |
|---|---|---|
| 整仓 `.py` | 458 | 145,890 |
| 主包 `torchtitan/` | 374 | 119,882 |

主包各目录（`.py` 行数，实测）：

| 目录 | 行数 | 说明 |
|---|---|---|
| `experiments/` | 64,470 | ⚠️ 占了一半以上——实验性代码（forge / rl / torchft …） |
| `models/` | 26,167 | llama3、deepseek_v3、qwen3、gpt_oss、kimi_k2_7 … |
| `distributed/` | **11,526** | ★ 所有并行逻辑都在这里 |
| `components/` | 6,157 | checkpoint / optimizer / loss / dataloader |
| `config/` | 1,492 | |

★ **第一个反直觉的数字**：TorchTitan 承担全部并行职责的 `distributed/` 只有 **11,526 行**，
而 Megatron 光 `transformer/` 一个目录就有 44,819 行。

### 5.2 ★★★ 为什么能这么小：并行原语是从 PyTorch 借的

最能说明问题的一份文件是 `torchtitan/distributed/tensor_parallel.py`——**整份文件只有 95 行**，
而且里面只定义了一个叫 `NoParallel` 的辅助类，它的注释是这样写的（原文）：

> "Replicate computation on the TP mesh **without sharding**. This style does nothing other than:
> (1) setting the module parameters as DTensors on the given mesh, and
> (2) inserting hooks at module boundary to convert torch.Tensor to DTensor and back."

也就是说：**TorchTitan 自己根本没写张量并行**。
真正的 `ColumnwiseParallel` / `RowwiseParallel` 来自上游 `torch.distributed.tensor.parallel`，
`tensor_parallel.py` 只补了一个"这一层不切但要保持 DTensor 类型"的边角情况
（用于 MoE 的 router gate——因为梯度裁剪和 fused optimizer 假设所有参数在同一个 mesh 上）。

★ 对照 Megatron：`megatron/core/tensor_parallel/` 是 **7,330 行**，
里面自己实现了 `ColumnParallelLinear` / `RowParallelLinear` 和全套 f/f̄ 通信算子。

**同一件事，7330 行 vs 95 行。差别不在能力，在于责任放在哪一层。**

流水线并行同理——`pipeline_parallel.py` 第 16-19 行直接 import 上游：

```python
from torch.distributed.pipelining import PipelineStage
from torch.distributed.pipelining.schedules import (
    _PipelineSchedule,
    _PipelineScheduleRuntime,
```

⇒ Megatron 那份 1000 多行的 interleaved 调度，在 TorchTitan 里是**上游 PyTorch 的一个类名**。

### 5.3 ✅ 主循环：和 Megatron 是同一个形状

`torchtitan/trainer.py:780` 的 `forward_backward_step`：

```python
if parallel_dims.pp_enabled:
    return self.pp_forward_backward_step(...)
...
return self.fwd_bwd_fn(inputs, labels, global_valid_tokens, extra_kwargs)
```

★ 这和 [Megatron 拆解 §2](Megatron-LM拆解.md) 里那 8 行 dispatch 是**同一个决策**：
"开没开 PP？开了走流水线路径，没开走普通路径。"
两个框架长得完全不一样，但骨架的这一处是重合的——说明这不是某家的设计品味，
而是**问题本身的形状**。

### 5.4 ★★ 它也把模型和并行拆开了

`torchtitan/models/llama3/` 的文件分工（实测行数）：

| 文件 | 行数 | 职责 |
|---|---|---|
| `model.py` | 100 | ★ 纯模型定义，几乎没有并行代码 |
| `sharding.py` | 74 | ★ 声明每一层怎么切 |
| `parallelize.py` | 92 | 按 `ParallelDims` 把声明落到实处 |
| `state_dict_adapter.py` | 154 | 和 HuggingFace 权重互转 |

`model.py` 的 `Llama3TransformerBlock.forward` 只有 3 行（第 48-50 行）：

```python
h = x + self.attention(self.attention_norm(x), attention_masks, positions)
out = h + self.feed_forward(self.ffn_norm(h))
return out
```

——**看不到任何 all-reduce、any group、any rank**。切分信息在 `sharding.py` 里单独声明。

★★ 所以：§6 讲的 VeOmni「把并行从模型里拆出来」，TorchTitan 也做了同一件事。
区别在表达方式：
- **VeOmni**：一份独立的 `parallel_plan.py`，用 **FQN 字符串模式**匹配参数名
- **TorchTitan**：在 `sharding.py` 里给每个 sub-config 填 `sharding_config` 字段，用 **DTensor placement**

⚠️ 这说明"模型与并行解耦"不是某一家的独家发明，而是 2024 年之后的**行业共识方向**。

### 5.5 ✅ 并行维度的排列顺序（又一次印证 PTD-P）

`torchtitan/distributed/parallel_dims.py:318` 构造设备网格时，轴的顺序是写死的：

```python
("pp", "dp_replicate", "dp_shard", "cp", "tp"),
```

★★★ **`tp` 在最里层，`pp` 在最外层**——和 [Megatron `parallel_state.py` 的排布完全一致](Megatron-LM拆解.md)，
也就是[速查表 D 章](分布式训练入门/附-速查表.md)那条因果链：
**通信越频繁的并行方式，排得越靠内层（越可能落在同一台机器的 NVLink 上）。**

两个独立团队、两套完全不同的代码，得出同一个顺序——这是这条规律最强的证据。

### 5.6 ⚠️ 边界

```
★ 谁适合走这条线：
   - 规模在几十到几百卡
   - 需要自己改训练逻辑（代码好读是真实优势：并行逻辑只有 1.1 万行）
   - 团队已经很熟 PyTorch，不想再学一套 Megatron 的概念

⚠️ 谁不适合：
   - 万卡规模、要压榨最后几个点 MFU 的场景
     —— Megatron 在这个区间的调优积累更深。
   - ⚠️ 实测发现 experiments/ 占了 64,470 行（超过主包一半），
     说明相当一部分能力还处在"实验目录"状态，选型时要逐个确认成熟度。
```

## 6 · ★★★ VeOmni：把并行逻辑从模型里拆出来

**这是本次新增分析的部分，也是五家里思路最不一样的一个。**

### 6.1 它想解决什么

✅ 论文（2508.02317）的批评原文：

> *"Existing frameworks typically **entangle model definition with parallel logic**"*
> *"directly applying these techniques to omni-modal LLMs often leads to **load imbalance and poor scalability**"*

```
★★ 翻译成人话：

   在 Megatron 里，模型代码和并行代码是【长在一起】的 ——
   你用的不是 nn.Linear，而是 ColumnParallelLinear / RowParallelLinear。
        ↓
   ⇒ 想换并行策略，要改模型代码
   ⇒ 想加新模型，要重新实现一遍并行版的每一层
        ↓
   ⇒ ⚠️ 对【全模态模型】尤其致命：
      文本塔、视觉塔、音频塔的形状和负载完全不同，
      硬套同一套并行策略必然负载不均。
```

### 6.2 ✅ 它的答案：parallel plan（源码实证）

VeOmni 的做法是——**模型就用普通的 HuggingFace 定义，并行策略单独写成一个"计划"文件**。

✅ 源码实证：`veomni/models/transformers/deepseek_v3/parallel_plan.py` 的**全部有效内容**：

```python
def get_parallel_plan():
    ep_plan = {
        "model.layers.*.mlp.experts.gate_up_proj": Shard(0),
        "model.layers.*.mlp.experts.down_proj": Shard(0),
    }
    parallel_plan = ParallelPlan(
        extra_parallel_plan={
            "ep": ep_plan,
        }
    )
    return parallel_plan
```

```
★★★ 就这 10 行。它说的是：

    "DeepSeek-V3 的专家并行，就是把这两个参数沿着第 0 维切开。"

   模型定义本身【一个字都不用改】，还是 HuggingFace 那份。

★ 对比一下 Megatron 的做法：
   Megatron：模型代码里写 ColumnParallelLinear   ← 并行长在模型里
   VeOmni ：模型代码里写普通 nn.Linear，
            并行策略写在旁边的 parallel_plan.py  ← 并行从模型里拆出来了

✅ 实测：veomni/models/ 下有 7 个模型自带 parallel_plan.py
   （含 deepseek_v3、deepseek_v4、gpt_oss、qwen3_5_moe、qwen3_vl_moe 等）
```

## 7 · ★★★ veRL (HybridFlow)：RL 后训练的答案（源码走查）

> **RL**（Reinforcement Learning，强化学习）后训练：模型先"生成"一批回答，
> 打分之后再用这些分数去"训练"自己。所以它同时需要**推理引擎**和**训练引擎**。
>
> **本节只走查 veRL 一家。** RL 框架的**横向调研**（18 个开源框架 + 5 套前沿模型自研系统、同步→全异步的架构主轴、权重同步七档传输、训推一致性、slime 与 OpenRLHF 源码走查）见独立目录 → [../强化学习训练框架/](../强化学习训练框架/)

```
✅ 核心洞察（2409.19256 原文）：
   "utilizing the single-controller paradigm on the inter-node level enables
    flexible expression of various data dependencies... while integrating the
    multi-controller paradigm within intra-node computation enhances
    computation efficiency substantially."

★★ 一句话：【层级少但变化多的地方用灵活方案，层级多但变化少的地方用高效方案】。
   → 详见 [14 章](分布式训练入门/14-RL训练框架.md)
```

> **single-controller**（单控制器）：一个中心进程发号施令，其它进程听命。**灵活，但中心会成为瓶颈**。
> **multi-controller**（多控制器）：每个进程跑同一份代码、各自算自己那一份（Megatron 就是这样）。
> **高效，但想表达"先 A 再 B 再 C"这种复杂依赖就很别扭**。

|---|---|---|

论文标题里的那个机制（hybrid controller）在代码里只有 **2,247 行**，
而它协调的 workers 有 **23,797 行**——**十倍以上的差距**。

⇒ 这本身就是这套设计的论据：
**上面（节点之间）变化多、数量少 ⇒ 用薄薄一层灵活的协调代码；

### 7.2 ★★★ 那 2,247 行到底在干什么

核心只有两处。

**第一处：`verl/single_controller/base/decorator.py` 的 `@register`。**
它给一个方法贴上"这个方法的数据该怎么分发、结果该怎么收集"的标签（第 398 行起）：

```python
def register(dispatch_mode=Dispatch.ALL_TO_ALL, execute_mode=Execute.ALL,
             blocking=True, materialize_futures=True):
```

预置的分发模式（第 40-45 行）一共 6 种：

| 模式 | 含义 |
|---|---|
| `ONE_TO_ALL` | 同一份参数广播给所有 worker（如"加载模型"） |
| `ALL_TO_ALL` | 原样透传 |
| `DP_COMPUTE` | 按数据并行度把 batch 切开 |
| `DP_COMPUTE_PROTO` | 同上，但走 `DataProto` 协议并自动 padding |
| `DP_COMPUTE_PROTO_WITH_FUNC` | 同上，外加把一个函数一起广播 |
| `DP_COMPUTE_METRIC` | 切开算、收回来聚合指标 |

最简单的 `ONE_TO_ALL` 实现只有 3 行（第 120-123 行），一眼能读完：

```python
def dispatch_one_to_all(worker_group, *args, **kwargs):
    args = tuple([arg] * worker_group.world_size for arg in args)
    kwargs = {k: [v] * worker_group.world_size for k, v in kwargs.items()}
    return args, kwargs
```

**第二处：`verl/single_controller/ray/base.py:49` 的 `func_generator`——整个桥梁只有 19 行：**

```python
def func_generator(self, method_name, dispatch_fn, collect_fn, execute_fn, blocking):
    class Functor:
        def __call__(this, *args, **kwargs):
            args, kwargs = dispatch_fn(self, *args, **kwargs)     # ① 切数据
            padding_count = kwargs.pop(_padding_size_key, 0)
            output = execute_fn(method_name, *args, **kwargs)     # ② 丢给所有 worker
            if blocking:
                output = ray.get(output)                          # ③ 等结果
            output = collect_fn(self, output)                     # ④ 收回来
            ...
            return output
    return type(method_name, (Functor,), {})()
```

★★★ **这 19 行就是"单控制器"和"多控制器"之间的全部胶水。**
主进程调用 `actor_wg.update_actor(batch)` 时看起来像调用一个普通函数，
实际发生的是：切数据 → 广播给 N 个 Ray worker 并行执行 → 等待 → 汇总。

⚠️ 全仓一共 **51 处** `@register(...)`——也就是说整套 RL 流程里
需要跨"中心 ↔ worker"边界的操作只有 51 个。**接口面很小，这是它能保持轻量的原因。**

### 7.3 ✅ 效果：主循环读起来像单机程序

`verl/trainer/ppo/ray_trainer.py`（1,823 行）的主循环，顺序如下（行号实测）：

| 步骤 | 行号 | 调用 |
|---|---|---|
| 生成回答 | 1513 | `async_rollout_manager.generate_sequences(...)` |
| 算旧策略 log prob | 1304 | `actor_rollout_wg.compute_log_prob(...)` |
| 算参考模型 log prob | 1621 | `self._compute_ref_log_prob(batch)` |
| 算 value | 1627 | `self._compute_values(batch)` |
| 算 advantage | 1667 | `compute_advantage(...)` |
| 更新 critic | 1679 起 | `self._update_critic(batch)` |
| 更新 actor | 1690 | `self._update_actor(batch)` |

★★ **一路读下来是直线的、没有一句 `if rank == 0`、没有一句显式通信。**
这正是 single-controller 想买到的东西：**RL 算法的复杂性（谁先谁后、谁喂谁）
留在这份能一眼读完的主循环里，而不是散落在每个 worker 的 rank 判断里。**

对照 [Megatron 的主循环](Megatron-LM拆解.md)：那是标准的 SPMD，每张卡都在跑同一份 `train_step`。
两者不是谁更好，是**任务形状不同**：预训练只有一条数据流，RL 有四五条互相依赖的数据流。

```
Megatron  FSDP  VeOmni  TorchTitan  MindSpeed
    （具体怎么把模型切到多卡上算）
```

⚠️ **所以"选 veRL 还是选 Megatron"本身是个伪问题**——
veRL 解决的是"RL 流程怎么编排"，Megatron 解决的是"一次前反向怎么在多卡上算"，
它们在同一个系统里是**上下层关系**，不是竞品关系。
真正互斥的是同一层内部的选择：Megatron vs FSDP vs VeOmni vs TorchTitan。

## 9 · ★ 五条容易被忽略的实践经验

```
① ★★ 换框架很少能解决性能问题
   ⚠️ MFU 低的常见原因（[12 章 §12.5](分布式训练入门/12-并行策略组合与MFU.md)）：
      重计算开成了 full、TP 跨机了、气泡太大、数据管道跟不上。
   ★ 这些换个框架一样会犯。先按排查清单走一遍，再考虑换框架。

② ★★ checkpoint 格式的兼容性，比框架本身的性能更影响你的生活
   预训练用 A、RL 用 B、部署用 C 是常态，
   ⇒ 三者之间的 checkpoint 转换脚本，往往是最脏也最重要的一块。
   ★ 好消息是 PyTorch DCP 正在成为共识（Megatron 的 torch_dist、VeOmni 都支持）。

③ ★★★ 看框架先看"它自己写了多少"
   ✅ 本次实测：同样是张量并行，
      Megatron 7,330 行 / DeepSpeed 393 行 / TorchTitan 95 行。
   ⇒ 这不是谁强谁弱，而是【自研 vs 依赖上游】两条路。
     自研 = 可以极致调优，但每次 PyTorch 升级都要自己跟；
     依赖上游 = 代码好读、跟随演进，但上游没做的你也做不了。
   ★ 选型时问一句"这个能力是它自己实现的，还是转手上游的？"
     ——决定了出问题时你能不能改得动。

④ ⚠️ 论文里的 MFU 数字几乎不可直接横向比较
   模型大小、卡数、上下文长度、是否算重计算（MFU vs HFU）、硬件代次，
   任何一项不同，结论就不同。
   ★ 正确的用法是：拿它们当【同一配置下的相对提升】看，
     而不是当【框架排行榜】看。
     § 6.3 里 VeOmni 的 61.5% 和 MegaScale 的 55.2% 就是最好的例子。

⑤ ★★★ 比性能更早决定选型的，是【要不要改模型代码】
   ✅ 源码实证：
      DeepSpeed ZeRO-3 → `with deepspeed.zero.Init():` + module hook，模型一行不改；
      Megatron TP      → 必须把 nn.Linear 换成 ColumnParallelLinear，模型要重写。
   ⇒ 前者能让已有的 HuggingFace 模型今天就跑起来，
     后者能换来极致的 MFU，但你得先把模型迁过去。
   ★ 现实里这一条往往比"谁快 5%"更能决定项目排期。
   ⚠️ 注意例外：DeepSpeed 的【流水线并行】不享受这个红利 ——
      PipelineModule 要求模型能写成顺序的一串层（见 §4.5）。
```

## 10 · 本章小结

```
① 五家框架都在回答同样的五个问题（切法/通信/显存/容错/数据），
   差别在【策略覆盖度、开箱性能、可扩展性、易用性】的取舍。

② Megatron-LM：并行最全、验证最充分，代价是复杂度和"模型与并行耦合"。

③ DeepSpeed：ZeRO 与卸载的发源地，气质是【不要求你改模型代码】。
   ✅ 源码实证 —— ZeRO-1 与 ZeRO-2 的全部区别只是一个布尔值
   (`zero_stage_string = "ZeRO-2" if partition_grads else "ZeRO-1"`)，
   而 ZeRO-3 是另外约 7,700 行的独立代码路径 —— 这解释了为什么很多团队停在 ZeRO-2。
   ★ 卸载解决"能不能跑"，不解决"跑得快"。⚠️ 它的 TP 很弱（393 行，且偏推理）。

④ FSDP / TorchTitan：PyTorch 原生，代码最好读，中等规模的默认选择。
   ✅ 源码实证 —— 它的 tensor_parallel.py 只有 95 行（Megatron 是 7,330 行），
   因为并行原语全部借自上游 PyTorch。

⑤ ★★ VeOmni：把并行策略从模型里拆成独立的 parallel_plan.py，
   ✅ 源码实证 —— DeepSeek-V3 的 EP 策略只有 10 行声明。
   适合多模态、长上下文、需要频繁接入新模型结构的场景。

⑥ veRL：RL 后训练的事实标准，核心是【混合控制器 + 3D-HybridEngine】。
   ✅ 源码实证 —— single_controller/ 只有 2,247 行，而它协调的 workers/ 有 23,797 行。
   ★ 这个 1:10 的比例，本身就是"上层薄而灵活、下层厚而高效"的最好注脚。

⑦ ★★★ 最常见的真实架构是【组合使用】，而不是二选一。
   ✅ 源码实证 —— veRL 的 workers/engine/ 下并列着 megatron / fsdp /
   veomni / torchtitan / automodel / mindspeed 六个可选后端（§7.6）。
   ⇒ "选 veRL 还是选 Megatron"是伪问题，它们是上下层关系。
   ⇒ 所以 checkpoint 格式的互通性，实践中比单框架性能更值得关注。
```
